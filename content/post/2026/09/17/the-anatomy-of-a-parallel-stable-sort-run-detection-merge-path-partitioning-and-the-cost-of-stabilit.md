Stable sorting is one of those contracts that looks minor until it is violated. A stable sort preserves the relative order of elements that compare equal. That sentence is easy to say and surprisingly expensive to enforce once the sort is parallel. In a database index build, equal keys may need to preserve insertion order so that later scans remain deterministic. In a log compaction pipeline, records with the same timestamp may need to retain arrival order. In a rendering or simulation pipeline, equal-priority work items may need to preserve submission order so that results are reproducible. In each case, the sort is not merely producing a permutation of the input; it is producing a specific permutation among elements the comparator cannot distinguish.

Parallel stable sort is therefore not just a faster version of a serial sort. It is a memory-ordering discipline. The algorithm must partition work without creating cross-partition inversions among equal keys, merge partitions in a defined order, and keep the auxiliary memory traffic under control. The hard part is rarely the comparison function. The hard part is the interaction between stability, parallelism, and the memory hierarchy.

This article focuses on comparison-based stable merge sort over contiguous arrays in shared-memory systems. The assumptions matter. The comparator is a strict weak ordering, and equal elements are equivalent under that comparator. The input is an array of elements, not a stream of opaque records that cannot be randomly accessed. Auxiliary memory is available for a merge buffer, but it is not unlimited. The target is a multicore CPU with a conventional cache hierarchy and, potentially, non-uniform memory access. This is not an external sort, not a GPU sort, and not a radix sort. Those are related design spaces, but they change the cost model enough that they deserve separate treatment. The goal here is to expose the trade-offs that appear when stability is treated as a first-class systems requirement.

## What Stability Actually Buys You

A stable sort guarantees that if two elements compare equal, the element that appeared earlier in the input appears earlier in the output. This is a property of the algorithm, not of the comparator. A comparator can tell you that two elements are equivalent, but it cannot tell you which one came first. The algorithm must carry that information through every transformation.

Stability is useful because it composes. If you sort records by one key and then stably sort by another key, the second sort preserves the ordering established by the first among records that tie on the second key. That is the basis of multi-key sorting without packing all keys into a composite comparator. Stability also gives deterministic output when the input order is deterministic. That matters for reproducible builds, test fixtures, database compaction, and any system where two runs over the same logical data should produce byte-identical results.

Stability is not free. A stable merge must prefer the left run when two elements compare equal. That sounds like a one-character change in a comparison, but it propagates through the design. A stable partition cannot use an arbitrary in-place partition that swaps elements across the array. A stable parallel merge cannot assign output segments to workers without proving that equal keys cannot cross segment boundaries in the wrong order. A stable radix sort needs stable digit passes. The cost of stability is not a single operation; it is a set of constraints on every phase of the algorithm.

It is also worth being precise about when stability is unnecessary. If the comparator is a total order with no equal keys, stability is vacuous. If the application does not care about the order of equal keys, an unstable sort may be faster and simpler. If the application needs a deterministic order among equal keys, the right fix is often to extend the comparator with a tie-breaker, such as a sequence number. That converts stability into an explicit ordering and can make an unstable sort acceptable. The trade-off is that the tie-breaker increases the comparison cost and the element size. Stability is attractive when the tie-breaker is already implicit in the input order and the algorithm can preserve it cheaply.

## The Serial Baseline: Runs and Merges

The natural baseline for a stable comparison sort is a merge sort with run detection. A run is a maximal contiguous sequence that is already sorted, either ascending or strictly descending. An ascending run can be kept as is. A descending run can be reversed in place, which restores ascending order while preserving stability only if the run is strictly descending. If the run contains equal keys, reversing it would invert equal elements, so the run detector must stop at the first equal pair or treat the run as ending before the equality. This is a small detail with large consequences: stability begins at run detection.

Once runs are identified, the sorter merges adjacent runs pairwise. A stable merge of two sorted runs, A and B, walks two indices. If A[i] is less than or equal to B[j], the merge takes A[i]. Otherwise it takes B[j]. The less-than-or-equal condition is the stability rule. If the merge used strict less-than, it would take B[j] when A[i] and B[j] compare equal, inverting their original order. The merge is linear in the total number of elements, with sequential reads and sequential writes. Its cost is dominated by memory traffic, not by comparisons.

Run detection is attractive because it exploits existing order. On partially sorted data, it reduces the number of merge passes and the number of comparisons. On random data, it adds a scan and finds short runs, so the benefit is limited. The serial baseline also has good locality: each merge reads two contiguous runs and writes one contiguous output. The merge tree is a sequence of full-array passes, so the memory traffic is predictable. The algorithm is stable, deterministic, and easy to reason about.

The serial baseline also exposes the first structural problem for parallelism. Run detection is a sequential scan. It can be parallelized by splitting the array into chunks and detecting runs within each chunk, but runs that cross chunk boundaries must be reconciled. A run that starts in one chunk and ends in another cannot be reversed independently without coordinating with the neighboring chunk. The merge tree is also serial at the top: the final merge of two halves is a single linear pass over the entire array. That top merge is a natural bottleneck, and it is exactly where parallel merge techniques become necessary.

## Where Parallelism Enters

There are two broad ways to parallelize a stable merge sort. The first is split-sort-merge: divide the input into contiguous chunks, sort each chunk in parallel with a stable base-case sorter, then merge the sorted chunks in a stable merge tree. The second is parallel merge: keep the run structure and parallelize the merge of two runs by partitioning the output into independent segments. The two approaches are complementary. Split-sort-merge is simple and has good locality within each chunk. Parallel merge is necessary to avoid a serial bottleneck at the top of the merge tree.

Split-sort-merge has a subtle stability property. If the chunks are contiguous and the merge tree merges them in their original left-to-right order, the result is stable. The base-case sorter must be stable within each chunk. The merge tree must merge left chunk before right chunk on ties. If the merge tree is balanced, the order of merges is still deterministic. The problem is load balance. The top merge is a single large merge, and if it is serial, the parallel speedup is capped. The top merge can dominate the total time even if the base-case sorts are perfectly parallel.

Parallel merge addresses that bottleneck by partitioning a merge into segments that can be processed independently. The standard technique is merge path partitioning. Conceptually, consider the merge of two sorted runs A and B as a path through a grid. The horizontal axis represents elements consumed from A, and the vertical axis represents elements consumed from B. The merge path is the sequence of grid cells visited by the serial merge. A split point on the merge path divides the output into two independent segments. If we can find split points for P workers, each worker can merge its segment without communicating with the others.

The stability condition for a split point is precise. Suppose we want to split the merged output at output index k. Let i be the number of elements taken from A among the first k outputs, and let j equal k minus i. The split is stable if A[i-1] is less than or equal to B[j] when both indices are valid, and B[j-1] is strictly less than A[i] when both indices are valid. The first condition allows equal elements from A to be emitted before equal elements from B. The second condition prevents an element from B from being emitted before an equal element from A. These inequalities are the merge path boundary expressed in terms of the two runs. They are also the reason a naive binary search on values is not enough. The search must respect the tie-breaking order.

Merge path partitioning gives each worker a contiguous output segment. The segments are ordered, so the global merge remains stable. The work is balanced by output length, not by input length. That is usually a good property because each segment performs roughly the same number of comparisons and writes. The memory access pattern is less uniform. A worker merging a segment may read from two widely separated positions in the runs, and the two streams may have different locality. The merge path is a load-balancing tool, not a cache-optimization tool. The implementation has to decide whether to compute split points with a binary search per worker, a parallel search over all split points, or a two-level scheme that first partitions into large blocks and then refines within each block.

There is also a base-case threshold. For small segments, the overhead of partitioning and scheduling exceeds the benefit of parallelism. A serial merge of a few thousand elements is often faster than a parallel merge with synchronization and split-point searches. The threshold depends on the comparator cost, the element size, and the memory hierarchy. It is not a universal constant. The right approach is to make the threshold a tunable parameter and to measure it on the target workload, not to hard-code a number from a different machine.

## Memory Traffic and the Stability Tax

Parallel stable merge sort is usually memory-bandwidth bound. Each merge pass reads the input array and writes the output array. A merge tree with log P passes touches the full array multiple times. The comparisons are cheap relative to the cache misses and DRAM traffic. The auxiliary buffer doubles the memory footprint and creates a read-write stream that competes with the input stream. If the merge tree alternates between two buffers, the sorter can avoid an extra copy, but it still pays for the traffic.

Stability imposes a tax on this traffic. A stable merge cannot use an unstable in-place partition that swaps elements across the array. It cannot reorder equal keys to improve locality. It must preserve the left-before-right order on ties, which means the merge path and the split points must be computed with the stability inequalities. A stable radix sort has a similar tax: each digit pass must be stable, so the counting and scattering phases must preserve the order of equal digits. The tax is not necessarily large in absolute terms, but it constrains the design space. It rules out some of the cache-friendly tricks that unstable sorts can use.

There are ways to reduce the traffic. A multiway merge can merge more than two runs at once, reducing the number of passes. A heap or a tournament tree can select the next run, but the tie-breaking rule must prefer the earlier run to preserve stability. Multiway merge increases the comparison cost and the bookkeeping cost, and it can hurt locality because each output element may come from a different run. A cache-aware base case can sort chunks that fit in cache before merging them, so the base-case sort stays in L1 or L2. A blocked merge can process the merge in cache-sized tiles, but the merge path partitioning must still preserve stability across tile boundaries. On NUMA systems, the auxiliary buffer should be allocated with first-touch placement, and workers should merge segments whose input and output pages are local to the same node when possible. False sharing is a real risk when workers write adjacent output segments; padding the segment boundaries or assigning segments at cache-line granularity can help.

These constraints set up the design space for the remaining sections: run detection at scale, merge path partitioning in detail, and the engineering of the merge tree. The stability contract is simple to state, but it reaches into every phase of the parallel sorter. The next sections will examine how to keep that contract while the algorithm is split across cores, caches, and memory nodes.

## Run Detection at Scale

Run detection looks like a serial preprocessing step, but in a parallel sorter it is better understood as a boundary-reconciliation problem. The input is divided into contiguous chunks, and each chunk is scanned independently to produce a list of local run descriptors. A descriptor records the start and end of a run, whether it is ascending or strictly descending, and whether it touches a chunk boundary. The local scan is cheap and parallel, but it cannot finalize runs that cross chunk boundaries. Those runs are the source of most of the subtle bugs.

The scan itself must be strict about stability. An ascending run can be extended while `compare(a[i-1], a[i]) <= 0`. A descending run can be extended only while `compare(a[i-1], a[i]) > 0`, and the detector must stop before any equal pair. If a descending sequence contains equal keys, reversing the whole sequence would invert those equal keys. The detector therefore treats the first equal pair as the end of the descending run and starts a new run at the next element. This is not an optimization detail; it is the point where the stable contract is either preserved or lost.

A parallel implementation should avoid reversing descending runs until boundary reconciliation is complete. If a descending run crosses a chunk boundary, a worker that reverses only its local portion changes the order of elements that belong to a larger run. The safe representation is to mark local descending runs as candidates and defer the actual reversal. After the boundary pass joins adjacent local runs, each finalized run has a direction and a strictness flag. Only then is a descending run reversed, and only if every adjacent pair in the finalized run was strictly descending.

Boundary reconciliation is a short sequential pass over the run descriptors near chunk boundaries. It examines the last run of the left chunk and the first run of the right chunk. If they form one continuous ascending run, they are merged into one descriptor. If they form one continuous descending run with no equal pair, they are merged and marked for reversal. If the boundary pair is equal, the runs remain separate. The pass is sequential but touches only descriptors, not the elements themselves, so its cost is negligible compared with the scan. The result is a global run list in input order, with each run finalized and stable.

Run detection also has to choose a representation that does not create allocator pressure. A descriptor can be as small as two indices and a few flag bits. For an array of millions of elements, the descriptor list is tiny. The scan should write descriptors into per-worker buffers, then concatenate them in chunk order. Concatenation must preserve input order because the merge planner depends on it. If workers write into a shared descriptor array with atomic counters, the order of descriptors becomes nondeterministic. That is not a stability violation by itself, but it makes the merge tree nondeterministic and complicates debugging. A deterministic concatenation step is worth the small cost.

The global run list supports two different merge strategies. A natural merge sort repeatedly merges adjacent runs and can exploit long runs on partially sorted input. A fixed split-sort-merge strategy ignores the natural runs after the base case and merges fixed-size chunks. The natural strategy has fewer merge passes on favorable input, but its run lengths are uneven. Uneven runs make load balancing harder because a single large run may dominate a merge level. A practical hybrid is to detect runs, use them as the base-case boundaries when they are large enough, and otherwise fall back to fixed-size chunks sorted by a stable base-case sorter. The merge planner then works over a list of sorted segments of mixed origin. It must still merge adjacent segments in left-to-right order on ties.

One common mistake is to parallelize run detection by letting each worker sort its chunk immediately and then merge the sorted chunks. That discards the natural-run information and can be slower on partially sorted data. Another mistake is to reverse descending runs locally before reconciliation. Both mistakes look correct on random input because equal keys and boundary-crossing runs are rare. They fail on the workloads where run detection matters most: logs with nearly sorted timestamps, database rows with clustered keys, and arrays with long descending stretches. The boundary pass is not glamorous, but it is the part that makes run detection safe at scale.

## Merge Path Partitioning Without Breaking Ties

Merge path partitioning is the mechanism that turns a serial merge into independent output segments. The idea is simple, but the tie-breaking rule is where stability lives. Consider two sorted runs `A` and `B`, and suppose we want to split the merged output after `k` elements. The split assigns `i` elements from `A` and `j = k - i` elements from `B` to the first segment. The second segment starts at `A[i]` and `B[j]`. For the split to be valid, the last element emitted from `A`, if any, must not be greater than the next element from `B`. In comparator terms, `A[i-1] <= B[j]` when both exist. The last element emitted from `B`, if any, must be strictly less than the next element from `A`: `B[j-1] < A[i]`. The strict inequality is the stability rule. If `B[j-1]` compares equal to `A[i]`, then `A[i]` appeared earlier in the input and must be emitted first.

A binary search can find a valid split without scanning the runs. For a fixed output offset `k`, the feasible range of `i` is bounded by how many elements `A` and `B` can contribute. Within that range, the search looks for the largest `i` satisfying:

```text
i == 0
or j == len(B)
or A[i-1] <= B[j]
```

Using the largest valid `i` yields the stable split. The boundary cases are not exceptions to the rule; they are the rule with an empty run on one side. The predicate is monotone over the feasible range, so the search is logarithmic in the run length. Each worker can compute its own split independently, which avoids a serial partitioning phase. For `P` workers, the split searches cost `O(P log n)` comparisons, usually a small fraction of the merge work.

The implementation must be careful about comparator orientation. If the comparator returns a negative value when the first argument belongs before the second, the condition is `compare(A[i-1], B[j]) <= 0`. If the comparator is a less-than predicate, the condition is `!less(B[j], A[i-1])`. The strict condition on the other side is `less(B[j-1], A[i])`. Mixing these two forms is a common source of off-by-one stability bugs. It is worth writing the split predicate as a named function and testing it against a serial merge on arrays with many equal keys.

Once split points are known, each worker receives a contiguous output range and the corresponding input cursors. Worker `w` merges from `(i_w, j_w)` until it has produced the number of elements assigned to its segment. The segments are concatenated in worker order, which matches input order. Because every split point obeys the stable tie rule, no equal pair can cross a segment boundary in the wrong order. A worker does not need to inspect elements outside its segment, except for the cursors used to start and stop. This independence is what makes the merge scale.

There are practical choices for computing all split points. Independent binary searches are simple and have good locality if each worker searches both runs. A parallel split search can compute all split points in one pass by sorting the requested output offsets, but the overhead is rarely justified unless the number of workers is large. A two-level scheme partitions the output into large blocks, computes block boundaries with binary search, and then refines within each block. The refinement can use the same predicate. The refinement must not use a different tie rule, or the block boundaries and the inner splits will disagree.

Merge path partitioning balances work by output length. That is the right default because each output element is written once and each input element is read once. It does not balance cache misses. A worker may read from two streams whose access patterns differ, and the streams may have different reuse. If the comparator is expensive, output-length balance is close to optimal. If the comparator is trivial and the elements are large, memory traffic dominates, and the split points may need to account for cache-sized tiles. A blocked merge can process one output tile at a time, recomputing or advancing cursors per tile. The tile boundaries still have to respect the same stability inequalities. The tile size should be chosen so that the two active input streams and the output tile fit comfortably in cache; otherwise the merge path has balanced work but poor locality.

## Work Granularity, Buffer Discipline, and the Merge Tree

A parallel stable merge sort spends most of its time moving elements, so the engineering around buffers matters as much as the merge logic. The standard approach is double buffering: the input array and the auxiliary array alternate roles on each merge pass. A pass reads from the current source and writes to the current destination. After the pass, the roles swap. If the number of passes is odd, the final result is in the auxiliary array and must be copied back, or the merge plan must arrange the pass count so that the final output lands in the original array. The pass parity should be decided by the planner, not discovered at the end. An unexpected copy back doubles the final memory traffic and can erase much of the parallel speedup.

Buffer allocation should be done once, not per merge task. A global auxiliary array is simple and has predictable pages. On a NUMA system, a global array with first-touch placement can still be acceptable if each worker touches the pages it will write early. A better scheme allocates per-node buffers and assigns merge segments to workers on the same node when the input pages are local. That requires page or region affinity information that many applications do not have. First-touch placement plus segment assignment that follows the input chunk ownership is a reasonable compromise. The important thing is to avoid a pattern where each worker writes across the entire auxiliary array, because that destroys locality and increases remote traffic.

False sharing at segment boundaries is a smaller but real cost. Workers write adjacent output segments, and if a segment boundary falls in the middle of a cache line, two workers may write different parts of the same line. The writes are to different addresses, but the cache coherence protocol still serializes the line. One mitigation is to align segment boundaries to cache lines when the output length permits. That may leave a few elements at a boundary assigned to one worker, which is fine as long as the split remains stable. Another mitigation is to have workers write to per-worker staging buffers and copy with a final parallel pass, but that adds traffic and is rarely worthwhile for large merges.

The merge tree itself should expose parallelism without creating a barrier at every level. A level-by-level schedule is easy to reason about: all merges at one level are independent, and the next level starts after a barrier. This is deterministic and stable, but it can underutilize cores when run lengths are uneven. A task-based schedule represents each merge as a node with dependencies on its two input merges. Workers take ready tasks and use merge path partitioning to split large tasks further. Small tasks run serially. The task graph preserves the left-before-right merge order, so stability is unaffected. The scheduler should prioritize large tasks and avoid splitting a merge so finely that split-search overhead dominates. A common policy is to split only when the estimated output length exceeds a threshold that depends on comparator cost and element size.

The base-case sorter is part of the stability contract. If the base case is an unstable sort, no amount of correct merging will recover the original order of equal keys inside a base-case chunk. Stable insertion sort is a good choice for tiny chunks because it is simple and has low overhead. For larger chunks, a stable library sort or a stable merge sort with a small auxiliary buffer is appropriate. The threshold between base case and merge should be measured, not guessed. It depends on whether the comparator is inlined, whether the element type is trivially copyable, and whether the chunk fits in cache. A threshold that is optimal for sorting 64-bit integers may be poor for sorting records with expensive comparison functions.

## Comparator Contracts and Element Layout

Stability is defined by the comparator, so the comparator's contract is part of the sorter's correctness surface. A strict weak ordering must be irreflexive, asymmetric, transitive, and must make equivalence transitive. Two elements are equal for sorting purposes when neither compares less than the other. A parallel sorter assumes every worker sees the same equivalence classes. If the comparator captures mutable state, reads a field that another thread updates, or depends on a random source, the merge path can change between split searches and merges. The result is not merely nondeterministic; it can violate stability because a tie that existed during partitioning may not exist during merging.

Comparator cost also shapes the parallel design. A template comparator that inlines into the merge loop can be reduced to a few instructions. A type-erased comparator that goes through a function pointer or virtual call adds overhead to every comparison and to every step of a binary search. When the comparator is expensive, merge path partitioning is cheap relative to the merge and output-length balancing is close to optimal. When the comparator is trivial, the merge is memory-bound, and the split search overhead becomes a larger fraction of the work. The implementation should not assume one regime. It should expose the comparator as a template parameter where possible and provide a type-erased path for runtime polymorphism, with thresholds tuned separately for each.

Element layout is the other half of the cost model. A merge moves whole elements, not just keys. If elements are large records, moving them through every merge pass can dominate the sort. A common technique is to sort an array of indices or handles instead of the records themselves. The comparator reads the key from the record, but the merge moves only the index. Stability is preserved if the index sort is stable: equal keys keep their original index order, and applying the resulting permutation to the records preserves the original order of equal records. This separates key comparison from payload movement and can reduce memory traffic substantially when records are wide.

The index approach has its own costs. It requires a key access pattern that may be less cache-friendly than an array of packed keys, and it adds a final permutation pass over the records. That pass can be done with an auxiliary buffer or with cycle-following in place, but the in-place version must handle duplicate keys and already-placed elements carefully. If the records are trivially copyable and the merge is already moving them, sorting indices may not help. If the comparator is cheap but the records are large, sorting indices can turn a bandwidth-bound merge into a much smaller bandwidth problem for most passes. The decision should be based on element size, comparator cost, and the number of merge passes.

A third layout is structure-of-arrays, where keys and payloads are stored separately. The sorter can merge keys and a permutation array together, then apply the permutation to payloads only once. This is effectively the index approach with the keys already extracted. It is attractive for columnar data and for GPU-like memory access patterns, but it changes the application interface. A stable sorter that accepts an array of records cannot assume this layout. It can, however, offer a customization point that lets the caller supply a key projection and a permutation application. That keeps the stability contract in the sorter while allowing the caller to choose the memory layout that fits the workload.

## Scheduling Stable Merges Under Imbalance

A merge tree is a dependency graph. Each merge node depends on its two input segments being sorted, and its output is an input to a later merge. Stability adds an ordering constraint to that graph: when two segments are merged, the left segment must win ties. If the graph respects the original left-to-right order of the input, the final output is stable regardless of which worker executes which node. This is the key scheduling insight. The scheduler does not need to know about stability as long as the merge tree is built correctly and each merge uses the stable tie rule. It can use work stealing, priority queues, or a static schedule without changing the result.

The hard part is not correctness but balance. Natural runs have uneven lengths. A single long run can dominate a merge level, and the top merge can become a serial bottleneck if it is not split. Merge path partitioning solves the top merge by dividing it into independent output segments. The same technique applies at every level. A large merge can be split into tasks until each task is below a threshold. Small tasks run serially. The threshold should be based on estimated work, not just element count. A task that merges two short runs with an expensive comparator may be better left serial, while a task that merges two long runs with a trivial comparator may benefit from splitting even at a moderate size.

Galloping merge is a useful optimization for skewed runs. If one run's next element is much smaller than the other run's next element, the merge can skip many elements with an exponential search instead of comparing them one by one. The stability rule still applies. When galloping in the left run, the search finds how many left elements are less than or equal to the right element. When galloping in the right run, the search finds how many right elements are strictly less than the left element. The asymmetry is not an implementation quirk; it is the same tie-breaking rule expressed as a search. A galloping merge that uses the same comparison in both directions will invert equal keys when the right run is the one being skipped.

Parallel galloping has an additional constraint. A worker merging a segment may gallop within its segment, but it must not gallop past its segment boundary. The split points define the segment, and the worker must stop when it reaches the assigned output count or the end of one of its input ranges. If a gallop would cross the boundary, the worker falls back to the normal merge for the remaining elements. This keeps the segments independent and preserves stability. It also means that the benefit of galloping is local to a segment. A global gallop that spans segment boundaries would require communication and would break the independence that makes the parallel merge scale.

Task granularity interacts with memory locality. A task that is too small pays for scheduling and split searches. A task that is too large reduces parallelism and may leave cores idle. The best granularity is often expressed as a range of output elements, with a lower bound to amortize overhead and an upper bound to keep the critical path short. The upper bound should shrink as the number of workers grows, but not so much that the merge becomes a collection of tiny tasks. A practical scheduler uses a work-stealing deque with a threshold and lets idle workers steal large tasks and split them further. The split operation itself uses merge path partitioning, so the cost of creating a task is logarithmic in the segment length.

## Cache-Aware and NUMA-Aware Merging

A merge pass reads two input streams and writes one output stream. If the working set fits in cache, the merge is compute-bound and the comparison cost matters. If the working set exceeds cache, the merge is bandwidth-bound and the comparison cost is hidden behind memory latency. The transition between these regimes depends on the element size, the cache size, and the access pattern. A cache-aware merge tries to keep the active portions of the two input streams and the output tile in cache. It processes the merge in tiles, advancing the input cursors and writing the output tile before moving to the next tile. The tile size is chosen so that the two input tiles and the output tile fit comfortably in the last-level cache or in a private cache if the merge is per-core.

Tiling does not change the stability rule. The split points that define tile boundaries must still satisfy the same inequalities as the global merge path. A tile boundary is just another split point, and the worker that processes the next tile starts at the cursors left by the previous tile. If the tiles are computed independently, each tile boundary must be found with the stable predicate. If the tiles are processed sequentially by one worker, the worker simply continues the merge and the tile boundary is a cache hint, not a correctness boundary. The distinction matters for parallel tiling: independent tile boundaries need stable split searches, while sequential tiling within a worker can reuse the merge state.

Software prefetching can hide some of the latency of the two input streams. The merge knows the next elements it will read from each run, so it can issue prefetches a few iterations ahead. The prefetch distance should match the memory latency and the number of outstanding requests the core supports. Prefetching too far ahead can evict useful data; prefetching too little leaves the core stalled. The output stream is write-only and can use streaming stores if the output will not be read soon. In a multi-pass merge tree, the output of one pass is the input of the next, so non-temporal stores may hurt because they bypass the cache that the next pass needs. The right policy depends on the pass distance and the cache size.

NUMA systems add another dimension. The auxiliary buffer should be allocated with first-touch placement so that pages are local to the node that first writes them. If every worker writes across the entire buffer, the pages become interleaved and remote traffic increases. A better scheme partitions the auxiliary buffer by node and assigns merge segments to workers on the same node as the input pages. When the input is already distributed across nodes, the merge tree should preserve that distribution as much as possible. A merge that reads from two nodes and writes to a third pays remote bandwidth twice. A merge that reads and writes locally pays only local bandwidth. The scheduler can use page affinity information to place tasks, but even without it, a first-touch allocation and a segment assignment that follows the input chunk ownership can reduce remote traffic.

False sharing is a smaller but persistent cost. Adjacent output segments may share a cache line at their boundary. Two workers writing different elements in the same line cause coherence traffic even though the writes are disjoint. Aligning segment boundaries to cache lines avoids the worst case, but it can leave a few elements unassigned or assigned to one side. The split must remain stable, so the boundary adjustment cannot move an equal element across the split. A safe approach is to round the split point to a cache-line boundary within the same run, then verify the stable predicate. If the adjustment would violate the predicate, keep the original split. The cost of a few shared lines is usually small compared with the cost of an incorrect tie order.

## Verification and Debugging Stability

Stability bugs are easy to miss because they only appear when equal keys cross a partition boundary. Random tests with unique keys will never exercise the bug. A stability test must use a comparator that ignores a tag and a payload that carries the original index. The test sorts the array, then checks that for every pair of equal keys, the one with the smaller original index appears first. The check can be done in one pass over the output: for each adjacent pair with equal keys, the original index must be increasing. This is a necessary and sufficient condition for stability when the input order is the original index order. It catches errors in run detection, base-case sorting, merge path partitioning, and the merge tree.

Adversarial patterns are more valuable than uniform random data. An array of all equal keys is the extreme case: every comparison is a tie, and every split point must respect the left-before-right rule. An array with two values in alternating order stresses the merge path. A descending run with equal keys tests the run detector's strictness rule. An organ-pipe pattern, where the array increases and then decreases, creates long runs and a large top merge. A sawtooth pattern creates many short runs and stresses the merge planner. A pattern with long runs that cross chunk boundaries tests boundary reconciliation. Each pattern should be run with one worker and with many workers, and the outputs must match a serial stable sort exactly.

Debug assertions should encode the invariants of the parallel merge. A split point assertion checks that the left segment's last left element is less than or equal to the right segment's first right element, and that the left segment's last right element is strictly less than the right segment's first left element. A coverage assertion checks that the segments partition the output without gaps or overlaps. A cursor assertion checks that the input ranges consumed by the segments are contiguous and cover both runs. A run descriptor assertion checks that finalized runs are sorted in the correct direction and that descending runs contain no equal adjacent pair. These assertions are cheap in debug builds and can be compiled out in release builds.

Race detectors and sanitizers are useful but not sufficient. A data race in the sorter may not change the output on a particular run, and a stability violation may occur without a data race if the algorithm is logically wrong. Deterministic replay helps: run the same input with the same number of workers and the same schedule, then compare against a serial stable sort. If the output differs, reduce the number of workers and disable task splitting until the failure disappears. That often points to the smallest merge or split that is wrong. Performance counters can also reveal stability-related costs. A high rate of cache misses in the merge path may indicate that split points are not cache-aligned. A high rate of branch mispredictions may indicate that the comparator is expensive or that the merge is alternating between runs. A low parallel efficiency may indicate that the top merge is still serial or that the task granularity is too fine.

Finally, the comparator itself should be tested for consistency. A comparator that is not a strict weak ordering can make a stable sort produce different results on different runs, even with one worker. A simple test is to generate random triples and check transitivity and equivalence transitivity. A parallel sorter magnifies comparator bugs because different workers may evaluate the comparator in different orders. If the comparator is inconsistent, no amount of merge path correctness will save the output. The stability contract begins with the comparator and ends with the final merge, and every layer in between should have a test that can fail when the contract is broken.

## Choosing the Merge Tree Shape

The merge tree is not a neutral implementation detail. It determines how many times the array is read and written, how many independent tasks are available at each level, and how much of the sort can proceed without synchronization. A balanced binary merge tree is the simplest choice: sort fixed-size chunks with a stable base-case sorter, then merge pairs of adjacent chunks until one segment remains. Its height is logarithmic in the number of chunks, and every level contains many independent merges. That makes it easy to schedule on a fixed thread pool and easy to reason about for stability, because each merge always takes the left input before the right on ties. The cost is that a balanced tree ignores any order already present in the input. On nearly sorted data, it performs the same number of passes as on random data, even though a natural merge sort could finish in a single pass.

A natural merge tree uses the runs found by the run detector. Adjacent runs are merged according to their lengths, often with a stack-based policy that keeps the run lengths balanced. This is the family of algorithms that includes Timsort-style merge policies. The advantage is clear: long existing runs survive into later passes, so the number of passes can drop from logarithmic to constant on favorable input. The disadvantage is imbalance. A single long run can dominate a level, and the top merge can become a serial bottleneck unless it is split with merge path partitioning. Natural merge also makes the merge tree shape depend on the input, which complicates deterministic scheduling and makes performance harder to predict. The stability contract is still straightforward as long as every merge preserves left-before-right order on ties, but the scheduler must respect the dependencies of an irregular graph.

A hybrid policy usually wins in practice. The run detector finds natural runs, but any run shorter than a minimum length is extended by a stable insertion sort to that minimum. The minimum length bounds the imbalance and ensures that the base-case sorter has enough work to amortize its overhead. The merge planner then operates on a list of runs whose lengths are within a bounded factor of each other. It can use a balanced merge tree for the first few levels and switch to a natural policy when the remaining runs are few and large. The important invariant is that the planner never merges a right run before a left run, and that the tie rule inside every merge is the stable one. If those two conditions hold, the shape of the tree affects performance but not correctness.

Bottom-up and top-down merge trees are the two common ways to organize the passes. A bottom-up tree processes the array level by level, merging runs of width w into runs of width 2w. It has excellent locality if the runs are cache-sized, and it exposes a large number of independent merges at each level. A top-down tree recursively splits the array into halves until the base case is reached, then merges on the way back up. It is natural for divide-and-conquer parallelism and can be expressed as a task graph without explicit level barriers. The top-down version must still use a stable base case and a stable merge. Its recursion depth is logarithmic, so stack usage is rarely a problem, but the task graph can become deep and irregular if the splits are not balanced. Many production sorters use a bottom-up schedule for the early levels and a task-based top-down schedule for the large merges near the root.

Multiway merging is the other major shape decision. Merging k runs at once reduces the number of passes from log2(n/C) to logk(n/C). That can be a large reduction in memory traffic when the array is much larger than cache. The cost is that each output element requires selecting the smallest next element among k runs. A binary heap or a tournament tree does this in O(log k) comparisons per element, which increases the comparison count. For a cheap comparator, the trade-off often favors multiway merging because memory traffic dominates. For an expensive comparator, two-way merging is usually better because it minimizes comparisons. Stability in a multiway merge requires a tie-breaking rule that prefers the run with the smallest original index. A tournament tree can encode that rule by comparing run indices when keys are equal. The merge path partitioning for k runs is more complex than the two-run case, but the same principle applies: a split point must not allow an element from a later run to be emitted before an equal element from an earlier run. In practice, two-way merging with merge path partitioning is the safer default, and multiway merging is reserved for workloads where the pass count is the dominant cost.

## Cost Model: Work, Span, and Memory Traffic

A parallel stable merge sort has three cost dimensions that matter: work, span, and memory traffic. Work is the total number of operations performed by all workers. For a comparison-based merge sort, the comparison work is O(n log n), and the element movement work is O(n log n) because each pass moves n elements and there are O(log n) passes. The stability rule does not change the asymptotic work. It changes the constants. A stable merge uses a less-than-or-equal comparison on the left run and a strict less-than on the right run, which can require one extra comparison at each equal pair. Run detection must stop a descending run at the first equal pair, which can create more runs on data with many equal keys in descending order. Those extra runs can increase the number of merge passes. The stability tax is therefore not a single overhead; it is a set of small constant-factor costs that appear in different phases.

Span is the length of the critical path through the dependency graph. In a serial merge sort, the top merge is a single pass over the entire array, so the span is O(n). That single pass can cap the parallel speedup no matter how many workers are available. Merge path partitioning reduces the span of a merge to O(n/P + log n) by splitting the output into P independent segments. Across a merge tree of height log n, the span becomes O((n/P) log n + log^2 n) for a balanced tree. That is much better than O(n), but it is not zero. The logarithmic terms come from the split searches and from the depth of the tree. If the number of workers is large, the span can still be dominated by the sequential split searches and by the final merge's critical path. A task-based scheduler that splits large merges recursively can reduce the span further, but it cannot eliminate the dependency that the final output is produced by a sequence of merges.

Memory traffic is usually the binding constraint. Each merge pass reads two input streams and writes one output stream. If the elements are 8-byte keys, a pass moves 24 bytes per element: 16 bytes read and 8 bytes written. A merge tree with 20 passes moves 480 bytes per element. On a machine with 100 GB/s of memory bandwidth, a 1 GB array takes at least 4.8 seconds just for the traffic, before any comparison or scheduling overhead. That is why parallel stable merge sort is often memory-bandwidth bound rather than compute-bound. The arithmetic intensity is low: roughly one comparison per 24 bytes moved for a cheap comparator. The roofline model predicts that the sort will saturate bandwidth long before it saturates the comparison units. The only ways to improve are to reduce the number of passes, reduce the bytes moved per pass, or increase the effective bandwidth through cache blocking and NUMA-local allocation.

Stability interacts with memory traffic in subtle ways. A stable merge cannot use an in-place partition that swaps elements across the array, because that would reorder equal keys. It must use an auxiliary buffer or a carefully staged in-place merge. The auxiliary buffer doubles the memory footprint and creates a second read-write stream. If the merge tree alternates between two buffers, the sorter avoids an extra copy, but it still pays for the traffic. A stable radix sort has a similar tax: each digit pass must be stable, so the counting and scattering phases must preserve the order of equal digits. The stability tax is not necessarily large in absolute terms, but it rules out some of the cache-friendly tricks that unstable sorts can use. For example, an unstable quicksort can partition in place and achieve better cache locality than a stable merge sort. A stable sort must accept the extra buffer traffic or use a more complex in-place algorithm with worse locality.

The cost model also depends on the element size and the comparator cost. If the elements are large records, moving them through every pass is expensive. Sorting an array of indices or handles instead of the records reduces the bytes moved per pass to the size of an index, plus the key reads. The comparator still reads the key from the record, which may be a cache miss, but the merge writes only indices. The final permutation pass applies the sorted order to the records. If the records are trivially copyable and the merge is already moving them, sorting indices may not help. If the comparator is expensive, the comparison count dominates, and two-way merging with galloping is usually the best choice. If the comparator is cheap, memory traffic dominates, and multiway merging with cache blocking is more attractive. A production sorter should expose these choices as policies rather than hard-coding one strategy.

## Adaptive Strategies and Fallbacks

No single merge policy is optimal for every input. A parallel stable sorter should inspect the input and choose a strategy that fits. Run detection provides the first signal: the number of runs and their lengths. If the entire array is one ascending run, the sort is already done. If the array is one strictly descending run, the sorter reverses it in place and is done. If there are only a few runs, the sorter can merge them directly without a full merge tree. If there are many short runs, a balanced merge tree is appropriate. The run detector should also report the number of equal adjacent pairs in descending runs, because that affects how many runs are created and how much work the merge tree will have.

The comparator cost is the second signal. A cheap comparator, such as an integer comparison, makes the merge memory-bound. In that regime, the sorter should minimize passes and maximize cache reuse. Multiway merging, larger base cases, and cache-blocked merges are all reasonable. An expensive comparator, such as a string comparison or a user-defined predicate, makes the merge comparison-bound. In that regime, the sorter should minimize comparisons. Two-way merging with galloping is usually better than multiway merging because a heap or tournament tree adds comparisons. Merge path partitioning is still useful for parallelism, but the split searches should be kept shallow. The sorter can choose the merge policy dynamically based on a measured or estimated comparator cost.

The element size is the third signal. Small elements, such as 32-bit integers, move cheaply and can be sorted directly. Large elements, such as records with many fields, are expensive to move. Sorting an array of indices or a permutation array reduces the bytes moved during the merge passes, at the cost of a final permutation pass and less cache-friendly key access. The sorter can offer a customization point that lets the caller supply a key projection and a permutation application. That keeps the stability contract in the sorter while allowing the caller to choose the memory layout that fits the workload. If the caller cannot provide a key projection, the sorter can still sort the records directly, but it should document the cost.

Fallbacks are essential for small inputs. The overhead of parallel partitioning, task scheduling, and split searches is not worth paying for a few thousand elements. A serial stable sort with a good base case is faster and simpler. The threshold should be based on the estimated work, not just the element count. A chunk of 10,000 elements with a trivial comparator may be better sorted serially, while a chunk of 1,000 elements with an expensive comparator may benefit from parallelism if the comparator is slow enough. The threshold should be a tunable parameter and should be measured on the target machine. It is not a universal constant, and hard-coding a value from a different architecture is a common source of disappointing performance.

Adaptive scheduling is the final piece. If the number of runs is larger than the number of workers, the scheduler can parallelize across independent merges. If the number of runs is smaller than the number of workers, it should parallelize within large merges using merge path partitioning. A hybrid scheduler does both: it uses work stealing to distribute independent merges, and it splits a merge when a worker would otherwise be idle and the merge is large enough to amortize the split search. The split operation itself uses the stable merge path predicate, so it does not compromise stability. The scheduler should avoid splitting a merge so finely that the split searches and task bookkeeping dominate the actual merge work. A practical policy is to split only when the estimated output length exceeds a threshold that depends on comparator cost and element size.

## Practical Tuning and Measurement

Tuning a parallel stable sorter without measurement is guesswork. The parameter space includes the base-case size, the minimum run length, the split threshold, the cache tile size, the prefetch distance, the alignment of segment boundaries, and the number of workers. Each parameter interacts with the others and with the target machine. The right approach is to build a benchmark suite that covers the input patterns that matter and to measure the metrics that explain performance. The patterns should include uniform random keys, already sorted keys, reverse sorted keys, all equal keys, an organ-pipe pattern that increases and then decreases, a sawtooth pattern with many short runs, a nearly sorted pattern with a few displaced elements, and a pattern with many duplicate keys. Each pattern should be run with one worker and with many workers, and the output should be checked against a serial stable sort.

The stability check is the most important correctness test. It should tag each element with its original index and use a comparator that ignores the tag. After sorting, the test walks the output and verifies that for every adjacent pair of equal keys, the original index is increasing. This catches stability violations in run detection, base-case sorting, merge path partitioning, and the merge tree. The check is cheap and should be part of the benchmark harness, not an afterthought. A sorter that is fast but unstable is worse than useless for the applications that need stability.

Performance counters explain where the time goes. Cache misses in the merge path indicate that the working set does not fit in cache or that the split points are not cache-aligned. TLB misses indicate that the array is large enough to stress the page table, and huge pages may help. Remote NUMA traffic indicates that the auxiliary buffer or the input pages are not local to the workers that use them. Branch mispredictions indicate that the comparator is expensive or that the merge is alternating unpredictably between runs. A high rate of split searches relative to merge work indicates that the task granularity is too fine. These counters turn tuning from guesswork into a feedback loop.

The stability tax can be measured directly. Run the same algorithm with an unstable tie rule, such as taking the right run on ties, and compare the performance. The difference is the cost of stability in that implementation. On random data with unique keys, the difference is usually negligible because ties are rare. On all-equal data, the difference can be larger because the unstable version may be able to skip work or use a different partition. The measurement is useful because it quantifies the trade-off and helps decide whether a tie-breaker in the comparator would be cheaper than a stable sort. In many applications, the tie-breaker is already available as a sequence number, and an unstable sort with an explicit tie-breaker can be faster and simpler. Stability is most valuable when the tie-breaker is implicit in the input order and the sorter can preserve it without extra data.

## Limits and Failure Modes

Parallel stable merge sort has limits that no amount of tuning can remove. Memory bandwidth is the most fundamental. Once the sort is bandwidth-bound, adding workers does not increase throughput; it only increases contention. The speedup saturates at the ratio of the machine's memory bandwidth to the single-core bandwidth, minus overhead. On NUMA systems, the effective bandwidth depends on page placement, and poor placement can make the parallel sort slower than the serial sort. The only way past this limit is to reduce memory traffic: fewer passes, smaller elements, or better cache reuse. Stability does not prevent those optimizations, but it does constrain them. A stable merge cannot use an in-place partition that swaps elements across the array, and a stable radix sort cannot use an unstable digit pass.

Load imbalance is the second limit. Natural runs have uneven lengths, and a single long run can dominate a merge level. Merge path partitioning can split a large merge, but the split searches themselves take time, and a segment that is too small pays more in overhead than it saves in parallelism. The scheduler must balance the cost of splitting against the benefit of parallelism. A work-stealing scheduler with a threshold is a good compromise, but the threshold must be tuned for the target machine and the input pattern. A static schedule is more predictable but can leave cores idle on irregular input.

Correctness failure modes are more dangerous than performance limits. The most common stability bug is an off-by-one in the merge path predicate. Using strict less-than on both sides, or less-than-or-equal on both sides, will invert equal keys at some split points. The bug may only appear when equal keys cross a segment boundary, which is rare on random data. Another common bug is reversing a descending run that contains equal keys. The run detector must stop at the first equal pair, or the reversal will invert those equal keys. A third bug is merging a right run before a left run, which can happen if the merge tree is built from a run list that is not in input order. A fourth bug is using an unstable base-case sorter. No amount of correct merging can recover the order of equal keys inside a base-case chunk if the base case is unstable.

The comparator itself can be a failure mode. A comparator that is not a strict weak ordering can make a stable sort produce different results on different runs, even with one worker. Floating-point comparators that treat NaN as a normal value are a common example: NaN breaks irreflexivity and transitivity, so the sort's behavior is undefined. A comparator that captures mutable state or reads a field that another thread updates can change equivalence classes between the split search and the merge, which can violate stability in a way that is nearly impossible to debug. The stability contract begins with the comparator and ends with the final merge, and every layer in between should have a test that can fail when the contract is broken.

Exception safety is another limit. A parallel merge that throws an exception in one worker must not leave the array in a half-merged state. The sorter must either provide a strong exception guarantee by working on a copy or a basic guarantee by documenting that the array is in an unspecified state after an exception. Most standard library sorts provide a basic guarantee. A parallel sorter should do the same, but it must also ensure that worker threads are joined and that no worker continues to write to the array after an exception. That requires careful use of cancellation and exception propagation. If the comparator can throw, the sorter should be prepared to stop the merge and clean up. Stability is not the only contract that matters; the sorter must also be safe under failure.

Finally, integer overflow and index types are a practical limit. The merge path uses indices into the runs, and the output offsets can be large. Using 32-bit integers for arrays with more than 2^31 elements will overflow. The implementation should use size_t or a signed 64-bit type for indices and should check that the array length fits. The merge path arithmetic must avoid overflow when computing the feasible range of i. A common bug is to compute i + j or to multiply indices without checking. On large arrays, these bugs can cause out-of-bounds accesses that are difficult to reproduce. The stability contract is only as strong as the index arithmetic that supports it.
