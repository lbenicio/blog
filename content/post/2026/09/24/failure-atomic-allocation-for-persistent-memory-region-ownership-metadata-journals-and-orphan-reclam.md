# Failure-Atomic Allocation for Persistent Memory: Region Ownership, Metadata Journals, and Orphan Reclamation

Persistent memory changes the cost of a pointer. In a volatile heap, a pointer is an agreement among threads and the allocator that a byte range will remain valid until freed. After a crash, the agreement disappears. In byte-addressable persistent memory, the bytes survive, but the process that understood them does not. An allocator for this medium cannot merely call mmap on a DAX device and replace malloc with a bump allocator. It has to treat metadata as a durable data structure that may be interrupted at any store boundary.

This article examines a narrow but difficult problem: designing an allocator whose own metadata resides in persistent memory, so that after a crash the heap can be recovered without external reconstruction and without a global allocator lock on the fast path. The setting assumes a byte-addressable non-volatile memory region exposed through a direct mapping, a processor that permits unprivileged cache-line flush and ordering instructions, and a recovery process that runs after a process or machine failure. It does not assume that ordinary stores become durable in program order. It also does not assume that a virtual address is stable across restarts; a persistent allocator must encode offsets relative to a persistent arena, not raw pointers, unless the mapping contract guarantees otherwise.

The scope excludes distributed allocation, remote memory, and general-purpose kernel allocators. The focus is a single-node persistent arena, potentially shared by multiple processes, with allocation and free operations that survive an arbitrary crash. Even with that restriction, the design space is wide. Every choice pushes cost somewhere: journal writes on allocation, copy-on-write metadata pages, cache-line flushes, recovery scans, fragmentation, or lost bytes after a crash. There is no free lunch and no universally correct policy.

## Why Persistent Allocation Is Not malloc With a Different Heap

A conventional allocator is allowed to lose its metadata. If a process dies, the operating system reclaims the address space, and the next process starts with a fresh heap. The allocator's free lists describe memory that no longer exists from the program's point of view. A persistent allocator has the opposite obligation. Its free lists, size classes, block headers, and ownership records are part of the durable state. A crash can happen after the allocator reserved a block but before it returned the pointer, after the application wrote object bytes but before it updated a root pointer, or during a free that removed a block from a free list. Recovery must classify each interrupted operation and leave the heap in a state that is safe to use.

Safety here is asymmetric. A leaked block is usually preferable to a block that is both reachable by an application root and present on a free list. The first wastes capacity; the second creates an aliasing bug that can corrupt an unrelated object. This asymmetry should influence the commit protocol. When in doubt, recovery should preserve allocation and postpone reuse. The allocator can reclaim orphans later if the application provides a way to enumerate roots or if the allocator tracks allocation epochs and the application confirms liveness. Without such cooperation, an allocator cannot distinguish a leaked block from a live object using metadata alone.

There is a second asymmetry between data and metadata. Suppose an allocation operation writes the block header and publishes it in a free-list removal record before the application initializes the payload. A crash at that point leaves an allocated block containing stale bytes. Recovery cannot know that the payload was never initialized. Conversely, if the allocator first initializes the payload and then makes the block reachable, a crash may leave an initialized but unreachable block, which is a leak. For most allocators, the leak is safer. This is why allocation commit should publish metadata last, after the payload is at least in a state the application can recognize, or after the application explicitly performs its own publication.

Store ordering is central. A CPU may reorder stores, and dirty cache lines are not guaranteed to survive a power failure merely because a store retired. Persistent-memory programming therefore uses a persistence discipline: write the data, issue the appropriate cache-line flush or writeback instructions, execute the required fence, then write the metadata that makes the data reachable, flush and fence again. The exact instructions are architecture- and platform-specific. The design principle is portable even when the mnemonics are not: define an ordering primitive that converts program order into persistence order, and never publish a durable pointer before the object it points to is durable.

A third difference is that allocator metadata may be larger than the object. A 32-byte allocation can require a 64-byte header, a free-list link, a size-class record, and a transaction record. In volatile heaps, metadata overhead is often hidden by alignment and batching. In persistent heaps, metadata writes may be the dominant durability cost. The allocator must amortize those writes. Slabs, arenas, and region-local free lists are not just concurrency techniques; they are ways to reduce the number of persistent metadata transitions per object.

## A Crash-Consistent Metadata Protocol

The allocator needs a persistent root. At minimum, the root identifies the arena, the metadata layout version, the region table, and a recovery generation. The root must be updated with a protocol that recovery can validate. A common approach is a small commit record stored in a dedicated cache line: a monotonically increasing generation, a checksum or magic value, and an offset to the current metadata image. The allocator writes the new metadata elsewhere, persists it, then writes the commit record and persists that. On recovery, the latest valid commit record selects the metadata image. This is a form of shadow paging. It is simple to reason about because the old image remains valid until the new image is complete. Its cost is metadata copying and the need to garbage-collect obsolete images.

For hot-path allocation, shadowing an entire region header for every object is too expensive. A journal is often a better fit. The allocator appends intent records to a persistent log: reserve block at offset X from region R, remove block X from free list F, set size class C. It persists the intent, applies the metadata changes, persists them, and then marks the transaction committed. Recovery scans the journal, replays committed transactions, and ignores incomplete ones. The allocator can truncate the journal after a checkpoint. The important invariant is that the commit record is the single point at which a transaction becomes authoritative. A transaction that is fully written but not committed must not be replayed, because the allocator may have intended to abort it. A transaction that is committed but whose metadata changes are only partially persisted must be replayable from the intent records.

Journals have their own failure modes. If the journal is a circular buffer, the allocator must not overwrite an uncommitted record. It needs a head and tail, and the tail update must follow the commit. If the journal is in the same persistent memory as the heap, a corrupted journal can destroy allocator state. Some designs keep two journals or a checksummed record format so recovery can skip damaged entries. Checksums do not provide atomicity, but they help recovery decide whether an entry is complete. A torn write that leaves a record half-written is exactly the case the commit protocol is meant to handle.

A more granular alternative is to design metadata so each transition fits in one naturally atomic store or one cache line. For example, a free-list head can be updated with a single 8-byte compare-and-swap, and that store can be made durable with a flush and fence. The allocator must then ensure that the block's header was persisted before the head update. If the head update is atomic and the block is self-describing, recovery can reconstruct the rest. This approach reduces journal volume but places a heavy burden on layout. It is easiest for fixed-size slabs and hard for variable-size extents with coalescing. Coalescing a freed block with its neighbors is a multi-word metadata update and usually needs a journal or a recoverable intent record.

The allocator also needs a free-space representation that can be validated. Bitmaps are compact and easy to checksum, but scanning a large bitmap at recovery can be slow. Free lists are faster to traverse but harder to make crash-consistent because each removal is a pointer update. A hybrid is common: a per-region bitmap for ownership and a set of free lists for allocation. The bitmap is the authoritative record of whether a block is allocated; the free lists are an acceleration structure. Recovery rebuilds lost free-list entries from the bitmap and marks blocks allocated if the bitmap says so. This is conservative: a block that was freed but not yet reflected in the bitmap remains allocated until a later repair. That is a leak, not corruption, and it matches the safety asymmetry.

The costs are real. Journaling a record per allocation adds persistent writes and fences. Batching transactions amortizes the fences but complicates recovery because a batch may be partially committed. A common compromise is to journal structural changes such as region initialization, extent splits, and coalescing, while using single-word atomic updates for slab-local free-list heads. The allocator's metadata design should therefore separate slow structural operations from fast size-class allocation. Not every operation deserves the same protocol.

## Region Ownership and Concurrency

A single global journal and a single allocator lock simplify correctness and destroy scalability. The usual response is to partition the arena into regions and give each region an owner. The owner can be a thread, a process, a core, or a logical shard. In a persistent allocator, ownership must survive a crash. A region header should contain an ownership epoch, not just an owner identifier. The epoch distinguishes a live owner from a stale one after restart. A recovering process increments a global epoch, claims unowned regions, and clears locks whose owner epoch is older than the current one. This requires care: if multiple processes can access the same persistent arena, a slow process may still be alive while another process believes it has failed. Ownership epochs need a liveness protocol, such as a lease renewed by a heartbeat, or an external coordinator. The allocator cannot infer crash from a stale epoch alone.

For single-process use, the problem is simpler. All locks held at the time of the crash belong to dead threads, so recovery can reset them. The allocator can use ordinary spinlocks or mutexes in persistent memory, provided that recovery clears the locked state before the heap is used. The persistent representation of a lock should include a generation so that a lock word left in the locked state is not mistaken for a live critical section. Still, the safest design is to avoid persistent locks on the allocation fast path. Per-region ownership gives a single writer to each region's metadata, and cross-region frees are forwarded as messages or deferred to a region-local queue. This is a classic partitioned-ownership design, but persistence adds the requirement that forwarded free records themselves be durable or reconstructible.

Region ownership interacts with fragmentation. If each region serves a fixed size class, allocation is fast and metadata is small, but memory cannot move between size classes without a region reclassification protocol. If regions are general-purpose, a thread that frees a block in another region creates cross-thread traffic. A common compromise is a thread-local cache backed by persistent slabs. The thread allocates a slab from a region, persists the slab header, and then hands out sub-blocks with a volatile bump pointer. After a crash, the bump pointer is lost. Recovery must reconstruct which sub-blocks were handed out. If the allocator persisted every sub-block allocation, the cache would be pointless. If it persisted none, recovery would see the whole slab as free and might alias live objects. The practical answer is a persistent high-water mark updated in batches plus a conservative recovery rule: treat all sub-blocks below the high-water mark as allocated unless the application can prove otherwise. That leaks unused sub-blocks but preserves safety. The batch size is a tunable trade-off between recovery waste and fast-path persistence cost.

This is where persistent allocators part company with their volatile cousins. The fast path is not merely a lock-free free-list pop. It is a sequence of durable state transitions with a deliberately chosen commit point. The next design question is how to recover those region headers after a crash and how to distinguish a crashed writer from a slow one; that is where ownership epochs and quiescence protocols enter.

## Ownership Epochs and Quiescence Protocols

A region header that names an owner is not enough to recover safely. The owner identifier tells recovery who last wrote the region, but not whether that writer is still alive. If recovery simply resets every lock and claims every region, it may race with a process that is merely paused, descheduled, or blocked on I/O. The result is two writers on one region and a corrupted free list. The allocator therefore needs a liveness protocol that is itself persistent enough to survive the crash that triggers recovery.

The minimal persistent ownership record contains a magic value, a layout version, a region state, an owner epoch, a lease expiry or heartbeat counter, the offset of the region's journal tail, and a checksum over the record. The owner epoch is a 64-bit value allocated from a global monotonically increasing counter in the arena root. When a process claims a region, it writes its process identifier and a new epoch into the header, persists the header, and then begins allocating. The process identifier is diagnostic; the epoch is authoritative. On recovery, the recovery process reads the arena root, increments the global epoch, and writes a new recovery generation. Any region whose owner epoch is less than the recovery generation is a candidate for reclamation, but only after quiescence is established.

Quiescence means that no live writer can still be in the middle of a metadata transaction against the region. For a single-process arena, quiescence is trivial after a crash: the process is gone, so all threads are gone. The recovery process can reset locks and claim all regions. The only subtlety is that the crash may have occurred during recovery itself. Recovery must be idempotent. It can record its own progress in the arena root, using the same commit protocol, so that a crash during recovery does not leave the arena in a half-recovered state that the next recovery cannot interpret.

For a multi-process arena, quiescence is harder. A process may be alive but not currently scheduled. It may hold a region lock and be waiting for a page fault. Recovery cannot distinguish that from a crashed process using only the persistent header. It needs an external liveness signal. Options include:

- An OS-level advisory lock on a file associated with the arena. The operating system releases the lock when the process dies, even if the process crashes while holding it. Recovery can try to acquire the lock; if it succeeds, no live process holds it. This works for processes on the same machine and for a single machine crash, but not for a distributed shared-memory system.
- A lease with a heartbeat. The owner periodically updates a heartbeat counter in the region header. Recovery reads the heartbeat and compares it to a monotonic clock. If the heartbeat is older than the lease interval, the owner is presumed dead. Clock skew and long pauses make leases fragile. A process paused for longer than the lease can be falsely declared dead.
- An external coordinator or lock service. The coordinator grants ownership leases and is responsible for fencing. This is the most robust approach for multi-node persistent memory, but it adds a dependency and a network round trip to region acquisition. It does not need to be on the allocation fast path; it only needs to be involved when a region changes ownership.
- A generation-based quiescence protocol. Recovery writes a 'recovering' state into the region header, persists it, and then waits for a grace period during which any live owner must observe the state and stop. A live owner checks the region header before each transaction. If it sees a recovery generation greater than its own, it aborts and releases the region. After the grace period, recovery assumes that any owner that did not respond is dead. This is essentially a two-phase claim. It requires that the live owner periodically polls the header, which adds a persistent read to the fast path. That read can be cached and invalidated by a volatile flag, but the flag must be set by a signal or a shared memory notification. The complexity is significant.

In practice, many persistent allocators choose a single-process model or a process-shared model with an external coordinator. The single-process model is common for databases and key-value stores that own the persistent memory region exclusively. The allocator can then treat all locks as volatile and all ownership epochs as monotonic within a process lifetime. The persistent metadata still needs epochs to distinguish allocations from previous runs, but the recovery process does not need to negotiate with live writers. This simplifies the design enormously and is often the right trade-off.

When quiescence is established, recovery can claim a region. The claim itself must be durable. The recovery process writes a new owner epoch, a new region state, and a new journal tail into the region header, then persists the header with a flush and fence. Only after that can it begin replaying the region's journal. If the recovery process crashes after claiming the region but before finishing replay, the next recovery sees the new epoch and knows that the region was being recovered. It can restart replay from the journal tail recorded in the header. The journal tail is the commit point for recovery progress.

## Replaying Region Journals and Validating Metadata

Recovery proceeds region by region, not by scanning the entire heap. A per-region journal bounds the work to the regions that were active before the crash. The arena root contains a region table with offsets and sizes. For each region, recovery reads the header, validates its checksum, and checks the ownership epoch. If the header is invalid, recovery tries an alternate copy. Region headers should be double-buffered or stored with a checksum and a generation number so that a torn header write can be detected. If both copies are invalid, the region is quarantined: its blocks are marked allocated and never reused until an offline repair tool can reconstruct them. Quarantine is a leak, but it prevents corruption.

A journal record should be self-describing and idempotent. A typical record contains:

- A transaction identifier.
- A sequence number within the region.
- A record type: ALLOC, FREE, SPLIT, COALESCE, CLASSIFY, or CHECKPOINT.
- The offsets and lengths of the blocks involved.
- The size class or region state transition.
- A checksum over the record.
- A commit marker written after the record is persisted.

The commit marker is the authoritative signal. Recovery scans the journal from the last checkpoint. It reads records until it finds an invalid checksum or an incomplete record. It then stops. It replays only records that have a valid commit marker and a transaction identifier greater than the last committed transaction in the checkpoint. Replay must be idempotent because recovery itself can crash and restart. For example, an ALLOC record sets a bitmap bit and removes a block from a free list. If replay runs twice, the second run must not corrupt the free list. The allocator can make replay idempotent by checking the bitmap before modifying the free list: if the block is already marked allocated, skip the free-list removal. Similarly, a FREE record checks that the block is currently allocated before adding it to the free list. These checks are cheap and make replay safe.

The journal tail is the point after the last committed record. Recovery should not truncate the journal until it has rebuilt the volatile metadata and written a new checkpoint. The checkpoint record contains the last committed transaction identifier, the region's free-list heads, the bitmap summary, and a checksum. Writing a checkpoint is a structural operation and should use the same commit protocol: write the checkpoint, persist it, then write a pointer to it in the region header, persist the header. After the checkpoint is durable, the journal can be truncated or recycled. A circular journal must not overwrite uncommitted records. The allocator can maintain a head and tail, and only advance the tail after the checkpoint is durable.

After replay, recovery validates the region's metadata. It checks that no block is both allocated and free, that free extents do not overlap, that allocated extents do not overlap, and that every block belongs to exactly one size class or free extent. It also checks that the free list contains only free blocks and that the bitmap agrees with the free list. If the region uses a bitmap as the authoritative allocation record, recovery can rebuild the free lists from the bitmap. This is slower than trusting the free lists, but it is more robust. The allocator can choose to rebuild only when the journal indicates a structural change, such as a split or coalesce, and trust the free lists otherwise. The trade-off is recovery time versus validation strength.

The region header can also store a 'dirty' flag that is set when the region is modified and cleared at checkpoint. If the flag is set at recovery, the region's journal must be replayed even if the journal tail appears clean. This handles the case where a crash occurred after a metadata change but before the journal tail was updated. The dirty flag is a single word and can be updated with an atomic store and a flush. It is a cheap way to avoid missing a transaction.

## Orphan Reclamation and Application Cooperation

Orphan reclamation is the hardest part of persistent allocation because it requires knowledge that the allocator does not have. An orphan is an allocated block that is no longer reachable from any application root. The allocator sees only its own metadata: the block is marked allocated, its header is valid, and no free-list entry points to it. The allocator cannot tell whether the block is a live object that the application will use after recovery or a leftover from a crashed transaction. If the allocator reclaims a live object, the application will read stale or overwritten data. If the allocator never reclaims, the heap leaks.

The safest default is to leak. After a crash, every block that was allocated remains allocated. The application can then run a recovery routine that re-establishes its roots and explicitly frees objects it no longer needs. This is simple and correct, but it places the burden on the application. For long-running systems, leaks accumulate and eventually exhaust the arena. The allocator must offer some form of orphan reclamation, but it must be conservative.

One approach is allocation epochs. Each allocation is tagged with the owner epoch and a generation number. When a process restarts, it bumps the generation and re-registers the objects it wants to keep. Objects from older generations that are not re-registered become candidates for reclamation. This requires an application API: for example, `pmem_alloc` returns a handle, and `pmem_keep` marks a handle as live in the current generation. The application must call `pmem_keep` on every object it still references. If it forgets, the object is reclaimed and the application has a dangling handle. This is a form of manual garbage collection. It is practical when the application already has a durable root structure and can enumerate its live objects.

A more automated approach is root enumeration. The allocator provides a way for the application to register root pointers. After a crash, recovery starts from the registered roots and traces the object graph. To trace, the allocator must know the layout of objects: where pointers are, how to distinguish pointers from integers, and how to handle cycles. This is a typed allocator. It can be built for a specific application or a specific object model. The allocator can then mark reachable blocks and free the rest. The cost is a full heap scan at recovery, plus write barriers on pointer updates to maintain a card table or remembered set. Write barriers are expensive on the fast path. An alternative is stop-the-world tracing only at recovery, when no application threads are running. That avoids write barriers but requires that the application not modify the heap during recovery. If recovery is offline, this is acceptable.

Reference counting is another option. Each object header contains a persistent reference count. When a pointer is stored, the application increments the target's count; when a pointer is removed, it decrements. The allocator frees an object when its count reaches zero. Reference counting handles acyclic structures well, but cycles leak. A cycle collector can be added, but it is complex and expensive. Reference counting also requires atomic updates to the count and a persistence protocol for the count and the pointer update. The ordering is subtle: the count must be incremented and persisted before the pointer is published, and the pointer must be removed and persisted before the count is decremented. This is the same publish-before-reclaim discipline as the allocation commit protocol.

Region-level reclamation is tempting because it is simple: if a region is owned by a dead epoch, reclaim the whole region. This is safe only if no live object from another region points into it. In a general-purpose allocator, cross-region references are common. Region-level reclamation would corrupt live objects. It can work in a partitioned design where objects are region-local and cross-region references are forbidden or tracked. For example, a region could hold a single large object, and the region header records the object's owner. If the owner is dead and no root points to the object, the region can be freed. This is essentially a typed allocator with one object per region. It trades internal fragmentation for simple reclamation.

Deferred free and epoch-based reclamation are useful for live systems, not just crash recovery. A block that is freed may still be read by a concurrent reader that obtained a pointer before the free. The allocator cannot reuse the block until all such readers have quiesced. In a persistent allocator, readers may be in different processes. Epoch-based reclamation requires readers to announce their epoch in a persistent or shared location. That is expensive. A simpler approach is to defer reuse until a global quiescence point, such as a checkpoint or a recovery. After a crash, all old readers are dead, so deferred blocks can be reclaimed. This is why crash recovery and orphan reclamation are related: a crash provides a natural quiescence point.

Slab allocation with a high-water mark is a practical way to bound orphan leakage. The allocator reserves a range of sub-blocks in a slab by persisting a high-water mark that is ahead of the actual allocations. It then hands out sub-blocks from the reserved range without further persistence. On a crash, recovery treats every sub-block below the high-water mark as allocated, even if it was never handed out. This leaks at most the reservation batch size per slab. The application can reduce the batch size to reduce leakage, at the cost of more frequent persistence. Alternatively, the allocator can persist a bitmap of allocated sub-blocks lazily and use the high-water mark as a conservative bound. Recovery uses the bitmap to identify free sub-blocks below the high-water mark only if the bitmap is known to be up to date. If the bitmap is not up to date, recovery treats the entire reserved range as allocated. The allocator can then run a background compaction that scans slabs, verifies liveness with the application, and reclaims unused sub-blocks. This background reclamation must use the same journaling protocol as ordinary frees, because it modifies persistent metadata. If it crashes, recovery must not double-free or free a live block.

The trade-offs in orphan reclamation are stark. Manual cooperation gives the best capacity utilization but requires application changes. Automatic tracing gives the best safety with no application changes, but it requires a typed allocator and a full heap scan. Reference counting is a middle ground for acyclic data. Region-level reclamation is simple but restrictive. In all cases, the allocator should default to leaking rather than risking corruption. Orphan reclamation is a background service, not a fast-path operation. It should be scheduled when the system is quiescent, and it should be idempotent and crash-consistent. The allocator can expose a policy knob: reclaim after N recovery generations without confirmation, or never reclaim automatically. The right policy depends on the application's tolerance for leaks and its ability to enumerate live objects. The remaining question is how these reclamation strategies interact with fragmentation and region reclassification, which is where the allocator's layout policy meets its recovery policy.

## Fragmentation as a Durable Property

Persistent allocators inherit classic fragmentation, but durability changes its meaning. In a volatile heap, fragmentation is transient: a process restart resets the heap, and a bad layout decision can be abandoned. In a persistent arena, a bad layout persists across crashes. An allocation pattern that creates unusable holes remains until explicit compaction or reclassification. Recovery cannot compact on the fast path without risking the same aliasing bugs it is meant to prevent. Therefore layout policy must be more conservative than in a volatile allocator.

Internal fragmentation from size classes is bounded and predictable. External fragmentation from variable extents is open-ended. A persistent allocator should generally prefer segregated storage for common sizes and a separate extent allocator for large objects. But even segregated storage can fragment across regions if size-class demand shifts. A region dedicated to 128-byte objects cannot serve 256-byte objects without reclassification, and reclassification is a structural operation that must be failure-atomic. The allocator must therefore treat region layout as a durable property, not a transient tuning decision.

Durability also makes metadata overhead persistent. A free block too small to hold its own header is a permanent leak unless the allocator has a way to coalesce it with neighbors. Coalescing requires neighbor discovery. Boundary tags at both ends of a block allow constant-time coalescing but double metadata and write amplification. A separate extent map or radix tree can find neighbors with less per-block overhead but more pointer chasing and more journaling. The choice affects recovery: boundary tags can be validated locally, while a tree may require a consistent traversal. A torn tree update can make an entire subtree unreachable. Structural metadata should therefore be journaled or shadowed, not updated in place without recovery support.

Fragmentation is not just space; it is time. A highly fragmented region forces recovery to validate many small extents. If each extent has a header and a journal record, recovery time grows with fragmentation. An allocator with a fixed upper bound on metadata operations per region is easier to bound. Segregated regions give this bound: a region has a small number of size classes, and free lists are per class. Extent allocators need a more complex recovery that can walk the extent tree and rebuild it. That walk can be expensive, so many designs checkpoint the extent tree periodically and journal only deltas. Checkpoint frequency becomes a trade-off between recovery time and steady-state write amplification.

There is also a subtle interaction with persistence granularity. Persistent memory writes happen at cache-line granularity or larger. A free block header that shares a cache line with an adjacent allocated block's payload can cause false sharing on flush. The allocator should align metadata to cache lines and separate metadata from payload where possible. This increases internal fragmentation but reduces write amplification and avoids corrupting a neighbor when persisting a header. For small objects, a slab header can cover many objects, so only the slab metadata is flushed, not per-object metadata. That is another reason slabs dominate persistent allocator designs: they amortize both metadata and persistence granularity.

## Region Reclassification and Ownership Transfer

A region that serves one size class cannot adapt when that size class becomes rare. Reclassification is the operation of changing a region's size class or returning it to a general pool. It is a structural change and must be failure-atomic. The naive approach is to stop the world, free all blocks in the region, and rewrite the region header. That is unacceptable for a live system unless the region is already quiescent. A more practical approach is incremental reclassification with a durable state machine.

The region header contains a state field: ACTIVE, DRAINING, RECLASSIFYING, or FREE. In ACTIVE, the region allocates new blocks from its current class. When the allocator decides to reclassify, it writes DRAINING to the header and persists it. DRAINING means no new allocations from this region. Existing allocations continue to be freed normally. The region's free list is still valid, but the allocator does not hand out new blocks. Once all blocks in the region are free, or once the allocator decides to move live blocks, it can transition to RECLASSIFYING. If live blocks remain, the allocator must either wait for the application to free them or migrate them. Migration requires copying object bytes to a new location and updating every pointer to the object. That is impossible without application cooperation or a typed allocator with pointer tracking. Therefore most persistent allocators drain rather than migrate. A region can remain DRAINING for a long time if a few long-lived objects are pinned in it. The allocator can treat such regions as reserved for those objects and allocate new regions for other size classes. This is a form of fragmentation that is accepted to avoid pointer rewriting.

If the region is fully free, reclassification is straightforward. The allocator writes a RECLASSIFYING record to the journal, persists it, updates the region's free lists and size class, persists the header with the new state, and then marks the transaction committed. Recovery that sees RECLASSIFYING with a committed record completes the transition. If the record is uncommitted, recovery reverts to the previous class. The revert is safe because no allocations occurred during RECLASSIFYING. The region header should store both the old and new class during the transition, or a pointer to a reclassification record in the journal. Double-buffering the region header is another option: write the new header to an inactive slot, persist it, then flip the active slot pointer with an atomic store. This is shadow paging at region granularity. It avoids journal replay for the header itself but requires two header slots per region and a way to garbage-collect stale slots.

Ownership transfer is a related operation. A region owned by one thread or process may need to move to another. If the region is empty, transfer is just a header update. If it is active, transfer must ensure that the old owner has no in-flight transactions. The old owner can write a RELEASING state, persist it, and stop allocating. The new owner waits until the old owner's epoch is no longer live, or until a lease expires. Then it writes a new owner epoch and state ACTIVE. During the interval, the region is unavailable for allocation. This is a pause, but it is bounded by the quiescence protocol, not by the number of blocks. For a single-process allocator, ownership transfer is trivial because there is only one owner. For multi-process, it is another place where an external coordinator or a lease is needed.

Cross-region frees complicate reclassification. If a block allocated from region A is freed by a thread that owns region B, the free must be forwarded to A. The forwarded free must be durable before the block is actually returned to A's free list. If the forwarding queue is volatile, a crash loses the free, and the block leaks. If the queue is persistent, it needs its own journal or a recoverable ring buffer. A common design is a per-region free queue in persistent memory with a head and tail. The freeing thread appends a record and persists it. The owner of A drains the queue, updates A's free list, and advances the head. Recovery replays the queue from head to tail. The queue must be large enough to absorb bursts, or the freeing thread must block. This is a classic producer-consumer problem with persistence: the tail update must be durable before the producer considers the free committed, and the head update must be durable before the consumer reuses the queue slot. The commit point is the tail. If the producer crashes after writing the record but before advancing the tail, recovery ignores the record and the block remains allocated. That is a leak, not corruption.

## Recovery-Aware Layout Policies

The layout of the arena determines what recovery can do and how fast it can do it. A layout that is easy to allocate from may be hard to recover. A layout that is easy to recover may waste space. The allocator should choose a layout based on the expected recovery time and the application's tolerance for leaks.

One useful principle is to make every region independently recoverable. If a region's metadata is self-contained, recovery can process regions in parallel or in any order. A region header should not require a pointer to another region to validate its own free list. Cross-region references should be limited to the region table and the arena root. This isolation makes it possible to quarantine a single corrupt region without affecting the rest of the heap. It also makes incremental recovery possible: the allocator can recover a region on first access after a crash, rather than scanning the whole arena at startup. Lazy recovery reduces startup latency but requires that the region header and journal be recoverable on demand. The first allocation that touches a region must be able to trigger recovery for that region. This is attractive for large arenas where only a fraction of regions were active before the crash.

Another principle is to separate the allocation bitmap from the free lists and to make the bitmap the authoritative record. The bitmap is compact, easy to checksum, and easy to repair. The free lists are an optimization. If the free lists are corrupted, recovery rebuilds them from the bitmap. If the bitmap is corrupted, recovery can rebuild it from the journal and the free lists, but that is harder. Therefore the bitmap should be protected by a checksum and stored in a region that is written only during checkpoint. The journal can contain bitmap deltas, but the bitmap itself should be updated in place only when the corresponding journal record is committed. A common pattern is to write the journal record, persist it, update the bitmap, persist the bitmap, and then mark the transaction committed. The bitmap is not the commit point; the commit record is. Recovery can replay the journal to reconstruct the bitmap if the bitmap is stale. The commit record tells recovery which journal records are authoritative. The bitmap is a materialized view.

Checkpointing is the bridge between journal replay and fast recovery. A checkpoint should be taken when the journal is large enough to make replay expensive, or when the allocator wants to truncate the journal. The checkpoint must be consistent: it must reflect all committed transactions up to a certain point. The allocator can quiesce the region, write the checkpoint, persist it, write a pointer to it in the region header, and persist the header. After that, the journal can be truncated. If the allocator cannot quiesce the region, it can take a fuzzy checkpoint by recording the journal tail at the moment the checkpoint starts and replaying from there after the checkpoint is durable. The checkpoint is a snapshot of the bitmap and free lists at that tail. This is more complex but avoids stopping allocations. The key invariant is that the checkpoint plus the journal after the checkpoint must describe the same state as the journal before the checkpoint. If the checkpoint is written while transactions are in flight, it may include some but not all of a transaction. The journal tail recorded in the checkpoint must be a committed transaction boundary. Otherwise, recovery may see a checkpoint that reflects a transaction that is not yet committed, or miss one that is. The allocator should only checkpoint at a transaction boundary, even if that means waiting for the current batch to commit.

Finally, the allocator should expose its recovery policy to the application. Some applications can tolerate a long recovery scan if it means no leaks. Others need fast startup and are willing to leak. Some can provide a root set and let the allocator reclaim orphans. Others cannot. A persistent allocator is not just a data structure; it is a contract about what survives a crash and what does not. The contract should be explicit: which operations are atomic, what recovery guarantees are provided, how much space can be lost, and what the application must do to help. Without that contract, the allocator may be correct in isolation but unsafe in practice. The next section would normally discuss integration with application transactions, but before that, the allocator must settle the interaction between its own recovery and the application's recovery. That interaction is where the abstractions meet the physical device.

## Coordinating Allocator Recovery with Application Recovery

The allocator's recovery is necessary but not sufficient. After the allocator has replayed its journals, validated its bitmaps, and rebuilt its free lists, the application still has to recover its own state. The application's roots, indexes, and object graphs are also in persistent memory, and they may be inconsistent because the crash interrupted application-level transactions. The allocator cannot repair those structures; it does not know their semantics. But the application cannot repair them without the allocator, because it needs to read and write persistent memory. This mutual dependency requires an explicit protocol.

The simplest protocol is sequential: the allocator recovers first, then the application recovers. The allocator exposes a `recover()` call that completes all metadata repair. After it returns, the heap is in a consistent state: every allocated block is marked allocated, every free block is on a free list, and no metadata transaction is in flight. The application then runs its own recovery, reading its roots and validating its objects. If the application finds a partially written object, it can free it or repair it using the allocator's normal `free` and `alloc` operations. This works well when the application's recovery is fast and does not require concurrent access to the heap. It is the model used by many persistent memory libraries: the allocator is a library that initializes the heap, and the application's recovery runs on top.

The sequential model breaks down when the application's recovery is long or when the application needs to serve requests before recovery finishes. A large database may have billions of objects and cannot afford a full scan at startup. It may want to recover lazily: access a region, recover it on demand, and continue. The allocator can support lazy recovery by making each region independently recoverable, as discussed earlier. The application's recovery can then be interleaved with normal operation: the first access to a region triggers allocator recovery for that region, and the application's recovery logic runs when it touches a root that points into that region. This requires the allocator to expose a `recover_region(region_id)` function and to ensure that a region is not used until it is recovered. The application must also be able to read objects from a region that is recovered but whose application-level state is not yet validated. That is safe as long as the application treats the data as untrusted until its own recovery completes.

A more complex protocol is concurrent recovery: the allocator recovers metadata while the application recovers its state, with synchronization to avoid races. This is attractive for multi-process arenas where different processes can recover different regions in parallel. It requires a shared recovery state machine with a leader. The leader recovers the arena root and the region table, then hands out regions to worker processes. Each worker recovers its assigned regions and reports completion. The leader then marks the arena as recovered. If a worker crashes, the leader reassigns its regions. This is essentially a distributed recovery protocol, and it needs a persistent log of recovery progress. The log can be a simple array of region states in the arena root, updated with the same commit protocol as allocator metadata. The complexity is significant, but it can reduce recovery time from minutes to seconds for large arenas.

The interaction between allocator recovery and application recovery also affects the allocator's API. If the application is responsible for freeing orphans, the allocator must provide a way to enumerate allocated blocks by owner epoch. The application can then iterate over the blocks it owns, check whether each is reachable from its roots, and free the unreachable ones. This is a form of mark-and-sweep where the application provides the marking logic. The allocator provides the sweep: it can free blocks that the application marks as garbage. To avoid a full scan, the application can maintain a persistent allocation log of its own, recording every allocation it makes. After a crash, it can replay its log to rebuild its object table, then free any blocks not in the table. This is application-level orphan reclamation, and it is often more practical than allocator-level tracing.

## Transactional Integration: Allocator as a Resource Manager

Applications that use persistent memory often need transactions that span multiple objects and allocator operations. A transaction might allocate a new object, link it into a data structure, and update an index. If the transaction aborts or the system crashes, the allocator must not leak the object, and the data structure must not contain a dangling pointer. The allocator must therefore participate in the application's transaction protocol, or provide its own transaction mechanism that the application can compose with.

There are two broad approaches. The first is allocator-internal transactions: every `alloc` and `free` is itself a small transaction with its own journal record and commit marker. The application's transaction is then a sequence of these small transactions plus its own data writes. This is simple for the allocator but leads to double journaling: the allocator writes a journal record for the allocation, and the application writes a journal record for the pointer update. The two logs must be ordered correctly. The application must not publish a pointer to a newly allocated block until the allocation is committed. If the application commits its pointer update first and then crashes before the allocation commits, the pointer points to a block that recovery considers free. That is a use-after-free. The safe order is: allocate (allocator commits), write data, persist data, update pointer, persist pointer, commit application transaction. The allocator commit happens before the application commit. If the application aborts after the allocation commits, the application must explicitly free the block. That is correct but adds a free operation on the abort path.

The second approach is application-managed transactions with allocator support. The allocator exposes a transactional API: `tx_begin`, `tx_alloc`, `tx_free`, `tx_commit`, `tx_abort`. The application's transaction manager coordinates all operations. The allocator does not write its own journal; instead, it registers undo or redo records with the application's transaction. On commit, the application writes a single commit record that covers both data and allocator metadata. On abort, the application rolls back the allocator's changes using the undo records. This eliminates double journaling and reduces the number of persistence fences. It is the model used by advanced persistent memory frameworks.

The transactional API has its own challenges. The allocator must support rollback of `alloc` and `free`. Rolling back an `alloc` is easy: the block is marked free again. Rolling back a `free` is harder: the block may have been reused by another allocation within the same transaction or by a concurrent transaction. To avoid this, the allocator must not make freed blocks available for reuse until the transaction commits. It can maintain a transaction-local free list: blocks freed in the transaction are held in a pending list. On commit, they are moved to the global free list. On abort, they are returned to the allocated state. This is safe but can increase memory pressure if transactions are long. It also requires that the pending list be durable if the transaction is durable. If the transaction commits, the pending list must be merged atomically with the global free list. That merge is a structural operation and needs its own journal record or a commit protocol.

Nested transactions complicate this further. An inner transaction may allocate a block and pass it to an outer transaction. If the inner transaction aborts, the block must be freed, but the outer transaction may still hold a reference. The allocator must track ownership across nesting levels. A common solution is to flatten nested transactions into a single transaction at commit time, or to use savepoints. The allocator can support savepoints by recording the state of its transaction-local free list and allocation log at the savepoint. Rolling back to a savepoint discards allocations made after it and restores freed blocks. This is feasible but adds metadata to the transaction.

The commit point is the most critical part of transactional integration. There must be exactly one persistent commit record that makes the entire transaction durable. If the allocator writes its own commit record and the application writes another, a crash between the two can leave the system in an inconsistent state. The application's commit record must be the sole authority. The allocator's metadata changes must be written to persistent memory before the application's commit record is persisted, but they must not be considered committed until the application's commit record is durable. This is the standard write-ahead logging discipline: write the redo/undo records, persist them, write the commit record, persist it. Recovery replays the redo records only if the commit record is present. The allocator's journal records are just part of the application's redo log. The allocator does not need its own commit marker; it relies on the application's.

This integration requires a shared persistence domain. The allocator and application must use the same flush and fence primitives, and they must agree on the order of writes. If the allocator uses its own flush instructions and the application uses different ones, the ordering may not be preserved. In practice, both should use the same low-level persistence library. The allocator can expose a `persist` callback that the application provides, or it can use a standard library like `pmem_persist`. The key is that the allocator's metadata writes and the application's data writes are ordered relative to the same commit record.

## Failure-Atomicity Across Allocator and Application: Ordering and Commit Points

The ordering rules for allocation and free are straightforward but easy to get wrong. For allocation, the safe sequence is:

1. Allocate a block from the allocator. The allocator reserves the block and records the intent in the transaction log, but does not publish it as allocated to other threads.
2. Initialize the block's payload. The application writes the object data.
3. Persist the payload. Flush the cache lines covering the object and execute a fence.
4. Publish the allocation. The allocator updates its metadata (bitmap, free list) and persists it. This makes the block reachable to other threads and to recovery.
5. Update the application's root pointer to reference the block.
6. Persist the root pointer.
7. Commit the transaction. Write the commit record and persist it.

If a crash occurs before step 7, recovery sees no commit record and rolls back the transaction. The block may have been published in step 4, but the rollback will free it. The application's root pointer is not updated, so the block is unreachable. This is safe. If the crash occurs after step 7, recovery replays the transaction. The block is allocated, the payload is durable, and the root pointer is durable. The allocation and the pointer update are both part of the committed transaction.

For free, the sequence is reversed:

1. Remove the application's root pointer to the block.
2. Persist the root pointer removal.
3. Record the free intent in the transaction log.
4. Mark the block as free in the allocator's metadata, but do not make it available for reuse until the transaction commits. The allocator can move it to a pending free list.
5. Commit the transaction. Write the commit record and persist it.
6. After commit, make the block available for reuse. This may be done lazily by a background thread or at the next transaction boundary.

If a crash occurs before step 5, recovery rolls back the transaction. The block remains allocated, and the root pointer removal is undone (or the application's recovery logic re-establishes the pointer). This is safe: the block is not leaked because the application still references it. If the crash occurs after step 5, recovery commits the transaction. The block is freed and can be reused. The root pointer removal is durable. This ordering ensures that a block is never both free and reachable.

These sequences assume that the application's root pointer update is part of the same transaction as the allocation or free. If the application uses a separate transaction, the allocator must provide a way to link transactions. For example, the allocator can return a transaction handle that the application includes in its own commit record. The application's commit record then implicitly commits the allocator's transaction. This is a form of two-phase commit, but it can be simplified if the allocator's transaction is nested inside the application's transaction. The application's commit record is the only durable commit point.

In a multi-threaded application, the transaction log may be per-thread. The allocator must ensure that its metadata changes are visible to other threads only after the transaction commits. If another thread reads the block before the commit, it may see uninitialized data. The allocator can use a read-write lock or a seqlock to protect the block's publication. A simpler approach is to make the block invisible until commit: the allocator does not add it to the global free list or bitmap until commit, so no other thread can allocate it. The application must also not publish the pointer to other threads until commit. This is the application's responsibility.

## Recovery Coordination in Multi-Process Arenas

When multiple processes share a persistent arena, recovery becomes a distributed problem. Each process has its own application state and its own view of the heap. A crash may affect one process or the whole machine. The allocator must recover the shared metadata without corrupting the state of live processes. This requires a recovery leader and a quiescence protocol, as discussed earlier. But the application-level recovery also needs coordination. If process A recovers the allocator and starts allocating, process B may still be running with an old view of the heap. Process B might allocate a block that process A has just freed, or it might free a block that process A has reallocated. The allocator must prevent this by fencing processes that have not yet recovered.

The standard approach is a recovery generation in the arena root. When a process starts, it reads the recovery generation. If the generation is newer than the one it remembers, it must run recovery or wait for the recovery leader to finish. The recovery leader increments the generation and writes a "recovery in progress" flag. Other processes must not access the heap until the flag is cleared. They can spin or block on a condition variable. Once recovery is complete, the leader writes the new generation and clears the flag. Other processes then re-read the generation and continue. This is a barrier, but it only happens after a crash. In steady state, there is no coordination overhead.

If the arena is shared across a network, the recovery leader must be elected. A simple election can use a lock in persistent memory with a lease. The first process to acquire the lock becomes the leader. It writes its process ID and a lease expiry. Other processes see the lease and wait. If the leader crashes, the lease expires, and another process can take over. The lease must be renewed periodically. This is a standard distributed lock, but it is implemented in persistent memory, so it survives crashes. The allocator can provide this as a service.

Application-level recovery in a multi-process arena requires that each process rebuild its own roots. The allocator can help by tagging every allocation with the owner process ID and epoch. After recovery, a process can enumerate all blocks owned by its previous incarnation (same process ID, older epoch). It can then validate each block against its own root set. Blocks that are not reachable can be freed. This is a per-process orphan reclamation. It avoids the need for a global tracing collector. The process must have a way to identify its own blocks. The allocator can maintain a per-owner allocation list or a bitmap of owner IDs. The list must be durable and crash-consistent. It can be journaled like other metadata.

The interaction between allocator recovery and application recovery in a multi-process setting is delicate. If process A finishes allocator recovery and starts allocating, but process B has not yet recovered its application state, process B might read a block that process A has already freed. To prevent this, the recovery leader should not clear the recovery flag until all processes have completed their application recovery. But the leader may not know when other processes are done. A common solution is a two-phase recovery: first, all processes recover the allocator metadata (read-only). Then, each process recovers its application state and reports completion. Finally, the leader clears the flag and allows allocation. During the first phase, no process may allocate or free. This is a stop-the-world recovery, but it is safe. It can be optimized by allowing processes that have completed their application recovery to proceed while others are still recovering, as long as they do not touch regions owned by the recovering processes. This requires fine-grained region ownership and a way to quarantine regions owned by processes that are not yet recovered.

## Performance Implications of Coordination

The coordination protocols described above add latency to recovery, but they should not add latency to the allocation fast path. The fast path in a persistent allocator is already dominated by persistence operations: flushes, fences, and journal writes. Coordination should be off the fast path. The allocator can use per-thread or per-region locks that are acquired and released without persistent writes. The only persistent writes on the fast path are the metadata updates and the journal records. The recovery generation and ownership epochs are read once at startup and cached in volatile memory. They are not updated on every allocation.

The transactional integration, however, can add overhead. If the allocator participates in the application's transaction, every allocation and free must be recorded in the transaction log. This increases the log size and the number of cache lines that must be flushed. The application's commit latency grows with the number of allocator operations in the transaction. To mitigate this, the allocator can batch its metadata updates. Instead of writing a separate journal record for each allocation, it can accumulate a batch of allocations in a volatile buffer and write them to the log as a single record at commit time. The batch record contains the offsets of all blocks allocated and freed in the transaction. This reduces the number of log records and fences. The trade-off is that the allocator must be able to roll back the entire batch if the transaction aborts. It can do so by keeping the batch in volatile memory until commit; if the transaction aborts, the volatile batch is discarded, and the persistent metadata is never updated. Only on commit does the allocator write the batch to the log and update the persistent metadata. This is a write-behind approach: the allocator defers all persistent metadata changes until commit. The risk is that a crash before commit loses the batch, but that is correct because the transaction is not committed. The application's data writes may also be in volatile buffers, so the entire transaction is lost. This is safe.

The write-behind approach requires that the allocator's metadata changes are not visible to other threads until commit. The allocator can use a transaction-local heap view: allocations come from a per-transaction free list or a bump pointer in a reserved region. Frees are recorded in a per-transaction pending list. On commit, the allocator merges the pending list into the global free list and publishes the allocations. This is essentially a persistent memory transaction with a private workspace. It is efficient because the fast path touches only volatile memory. The cost is paid at commit time, when the batch is persisted. The commit protocol must ensure that the batch is durable before the application's commit record is written. The allocator can write the batch to the log, persist it, and then let the application write its commit record. Recovery replays the batch only if the commit record is present.

This design blurs the line between the allocator and the transaction manager. The allocator becomes a transactional resource manager, and the application's transaction manager coordinates all resources. This is the direction that high-performance persistent memory systems are taking. It requires a tight integration between the allocator and the application, but it offers the best performance and the strongest failure atomicity guarantees.

## Testing and Verification of Failure Atomicity

No amount of design reasoning can replace testing. Persistent allocators are notoriously hard to test because the failure modes are rare and hardware-dependent. A bug may only manifest when a crash occurs between two specific stores, and only if the cache line is flushed in a particular order. To gain confidence, the allocator must be tested with fault injection and deterministic replay.

Fault injection can be done at several levels. At the lowest level, a simulator can intercept every store, flush, and fence and record them in a log. The log can then be replayed with a crash injected at any point. The simulator can also model torn writes: a store that is partially persisted. The allocator's recovery code is then run on the simulated persistent memory image, and its invariants are checked. This approach is used by frameworks like Yat, PMTest, and others. It requires that the allocator's persistence primitives be abstracted behind an interface that the simulator can intercept. The allocator should not call `clflush` directly; it should call a `persist` function that can be replaced.

At a higher level, the allocator can be tested on real hardware with a programmable power supply or a kernel module that injects crashes. This is more realistic but less deterministic. It is useful for finding hardware-specific issues, such as cache-line aliasing or memory controller reordering. A combination of both approaches is ideal: use simulation for exhaustive testing of the commit protocol, and use real hardware for validation.

The invariants to check after recovery are:
- No block is both allocated and free.
- No two allocated blocks overlap.
- No two free blocks overlap.
- Every allocated block is reachable from at least one application root, or is marked as leaked.
- Every free block is on exactly one free list.
- The bitmap agrees with the free lists.
- The journal is consistent and can be replayed idempotently.
- The recovery generation is monotonic.
- No lock is held by a dead owner.

These invariants can be checked by a recovery validator that runs after the allocator's recovery. The validator can walk the heap and assert each invariant. It can also compare the recovered heap state to a reference state computed from the pre-crash log. This is a form of differential testing.

Formal verification is another tool. The commit protocols can be modeled in a formal specification language like TLA+ or Alloy. The model can be checked for safety and liveness properties: no reachable state has a double allocation, and recovery eventually terminates. Formal verification is expensive and requires expertise, but it can find subtle bugs in the ordering rules. It is most useful for the core commit protocol, not the entire allocator. The allocator's data structures are too complex to model entirely, but the transaction commit and recovery logic can be abstracted into a small state machine.

Finally, the allocator should be tested under stress with concurrent threads and processes. The tests should include random allocation and free patterns, varying sizes, and crashes at random points. The recovery should be run repeatedly, and the heap should be checked for leaks and corruption. Over time, the test suite can build a corpus of crash scenarios that cover the most common failure points. This is not a proof of correctness, but it is the best practical assurance.

## Open Problems and Remaining Challenges

Despite the progress in persistent allocator design, several problems remain open. The first is the lack of a standard interface for transactional allocation. Every framework has its own API, and applications must be rewritten to use it. A standard like a persistent memory version of `malloc` that composes with transactions would simplify development. The C++ standards committee and the SNIA have proposed interfaces, but adoption is slow.

The second is the cost of recovery for very large arenas. A terabyte-scale persistent memory heap cannot be fully scanned at startup. Lazy recovery and incremental checkpointing help, but they require a more sophisticated metadata layout. The allocator must be able to recover a region in time proportional to the number of allocations in that region, not the size of the region. This means that the journal must be compact and the bitmap must be hierarchical. Hierarchical bitmaps and extent trees are promising, but they add complexity to the fast path.

The third is the interaction with hardware features like memory-side caches and persistent memory interleaving. A memory-side cache may reorder writes in ways that are not visible to the CPU. The persistence primitives may need to be extended to flush the memory-side cache. This is an active area of research. The allocator must be designed to work with the weakest reasonable persistence model, so that it remains correct on future hardware.

The fourth is the problem of orphan reclamation without application cooperation. Automatic tracing requires a typed allocator, which is not always feasible. A hybrid approach where the allocator uses heuristics to guess whether a block is live (e.g., based on allocation age or access patterns) is risky. A better approach is to make the application's root structure explicit and machine-readable, so that the allocator can trace it. This is a language and runtime design problem, not just an allocator problem.

The fifth is the lack of a formal model for persistent allocator correctness. Without a standard specification, it is hard to compare designs or prove that one is better than another. A specification would define the atomicity guarantees, the recovery semantics, and the allowed leak behavior. This would enable rigorous testing and verification.

These challenges are not insurmountable, but they require a multidisciplinary approach: systems, programming languages, formal methods, and hardware architecture. The persistent allocator is a microcosm of the larger problem of building reliable systems on non-volatile memory. It forces us to rethink the boundary between volatile and persistent state, between the allocator and the application, and between the programmer and the machine.
