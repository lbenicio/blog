# Parallel Sparse Triangular Solve: Level Scheduling, Dependency Graphs, and the Limits of Algebraic Reordering

Sparse triangular solve is one of those kernels that looks trivial on paper and becomes stubbornly difficult on real hardware. Given a sparse lower triangular matrix L and a dense vector b, forward substitution computes x such that Lx=b. The sequential algorithm is a loop over rows. For each row i, it forms the dot product of the already computed entries of x with the nonzeros of row i, subtracts that from b_i, and divides by L_ii. If L has unit diagonal, the division disappears. The work is proportional to the number of nonzeros, nnz(L), and the storage is already sparse. What could go wrong?

The problem is that row i cannot be computed until every x_j with L_ij != 0 and j < i is known. That dependency is not an implementation detail; it is the sparsity pattern itself. In a dense lower triangular matrix, row i depends on all previous rows, so the natural row-wise algorithm is a chain. In a sparse matrix, the dependency graph may have many independent rows, but the amount and shape of that independence depend entirely on the matrix ordering. Reordering a sparse matrix to reduce fill-in, the standard first step in sparse direct solvers, can easily destroy the parallelism you were hoping to exploit. Conversely, an ordering that exposes parallelism may create so much fill-in that the parallel solve is slower than a sequential one on a smaller matrix. This tension is the central engineering problem of parallel sparse triangular solve.

This article is about that tension. We will look at the dependency graph as a first-class object, derive level scheduling from it, compare level-synchronous execution with dataflow and task-based execution, and then examine why blocked and supernodal formulations often matter more than row-level parallelism. We will also discuss numerical reproducibility, memory behavior, and the assumptions behind common performance claims. The goal is not to present a single best algorithm, because there is none, but to give you the mental model needed to choose among them.

## The Sequential Kernel and Its Real Cost Model

Let L be an n by n sparse lower triangular matrix with unit diagonal. The standard forward solve is:

```text
for i = 0 to n-1:
    t = b[i]
    for j in nonzeros of row i with j < i:
        t = t - L[i,j] * x[j]
    x[i] = t
```

If the diagonal is not unit, the last line becomes x[i] = t / L[i,i]. The arithmetic cost is roughly 2 nnz(L) flops, one multiply-add per off-diagonal nonzero. On a modern CPU, that is not a lot of arithmetic. The kernel is memory-bound in the sense that the ratio of arithmetic to memory traffic is low, but it is also latency-bound in a way that a simple bandwidth number hides. Each row must wait for its predecessors. If the dependency chain is long, the processor may have plenty of bandwidth but nothing to do.

The access pattern is irregular. The matrix is stored in compressed sparse row (CSR) or a similar format. For row i, the inner loop reads L[i,j] sequentially and x[j] indirectly. The indirect reads are the problem. If x is small enough to fit in cache, the solve can be fast. If x is large, each row may touch a different set of cache lines, and the hardware prefetcher cannot help with the irregular x[j] indices. In a parallel setting, multiple threads may be reading overlapping sets of x entries, which is good for cache sharing but bad for coherence if those entries are being written. The writes to x[i] are distinct, but adjacent x[i] values may share a cache line. If two threads write x[10] and x[11] concurrently, they are not logically conflicting, but they may cause false sharing. Padding the x array or using per-thread buffers can mitigate that, at the cost of memory and a final gather.

The sequential algorithm also has a hidden assumption: the order of the summation. Floating-point addition is not associative. The sequential loop sums over j in increasing order. If a parallel algorithm changes that order, for example by having multiple threads contribute partial sums to the same row, the result may differ in the last bits. For many applications that is acceptable. For some, especially in reproducibility-sensitive workflows, it is not. We will return to this because it constrains which parallel formulations are viable.

## The Dependency Graph

Define a directed graph G=(V,E) with one vertex per row. Add an edge j -> i whenever L_ij != 0 and j < i. The edge means that x_j must be computed before x_i. Because L is lower triangular, all edges go from lower indices to higher indices, so G is a DAG. Any topological order of G is a valid elimination order. The natural order 0,1,...,n-1 is one such topological order. The sequential algorithm is simply a topological traversal that computes each vertex when it is visited.

The parallelism available in the solve is exactly the parallelism available in the DAG. If the DAG is a single chain, there is no row-level parallelism. If the DAG is wide, many rows can be computed concurrently. The critical path, the longest chain of dependencies, sets a lower bound on the parallel time, regardless of how many processors you have. The total work is nnz(L). The maximum speedup is bounded by work divided by critical path, a version of the work-span model. This is a useful first-order model, but it ignores memory effects, synchronization costs, and the fact that not all rows have equal work.

The shape of the DAG is determined by the matrix ordering. Consider a 1D Laplacian matrix from a finite-difference discretization. The lower triangular part is bidiagonal: row i depends only on row i-1. The DAG is a chain. No row-level parallelism exists. Now consider a 2D Laplacian on an m by m grid with natural row-major ordering. The dependency graph has edges from a grid point to its right and down neighbors. The levels of the DAG are anti-diagonals. The width of the widest level is O(m), while the number of levels is O(m). So there is parallelism of order m, but the critical path is also order m. For a 3D grid, the width is O(m^2) and the critical path is O(m). In general, the available parallelism scales with the separator size of the ordering. Nested dissection orderings tend to create large separators and thus more parallelism, but they also create dense blocks and more fill-in. Minimum-degree orderings tend to reduce fill-in but may produce longer dependency chains. This is the first major trade-off: fill-in versus parallelism.

## Level Scheduling

The most direct way to exploit the DAG is level scheduling. Assign each vertex a level:

level(i) = 1 + max over all j -> i of level(j)

with level(i)=0 if i has no predecessors. All vertices in the same level are mutually independent. The algorithm then executes levels in increasing order, and within each level it processes vertices in parallel. This is a wavefront or level-synchronous execution. For a 2D grid, the levels are anti-diagonals. For a banded matrix, the level size is bounded by the bandwidth. For a general sparse matrix, the level sizes can be irregular.

Computing the levels is a topological sort. You can do it in O(nnz(L)) time by iterating over rows in order: for each row i, set its level to one plus the maximum level of its predecessors. Because the natural order is topological, a single pass suffices. This is cheap compared to the solve itself. The level array is small: n integers. The execution loop is simple: for each level, spawn tasks for all rows in that level, wait for them to finish, then proceed. This is easy to implement with OpenMP, CUDA, or a task runtime.

The problem with level scheduling is synchronization. Each level is a barrier. If the DAG has many levels and each level has few rows, the barriers dominate. Even if each level has many rows, the last row in a level may be much slower than the others, and all other threads wait at the barrier. Load imbalance is inherent. You can mitigate it with dynamic scheduling within a level, but the barrier remains. For matrices with thousands of levels, the barrier cost can be significant. On GPUs, the cost of launching a kernel per level or using grid-wide synchronization can be even more pronounced. Some implementations use a single kernel with cooperative groups and grid sync, but that limits occupancy and portability.

There is also a memory effect. Rows in the same level are independent, but they may access x entries from previous levels. If the level is large, the working set of x may exceed cache. If the level is small, you lose parallelism. The level structure does not necessarily improve locality. In fact, a level-synchronous execution can have worse locality than a sequential solve because it interleaves accesses from many rows. The sequential solve processes rows in order, so the x entries are produced and consumed in a predictable pattern. Level scheduling breaks that pattern.

Finally, level scheduling preserves the per-row summation order if each row is computed by a single thread. That is a useful property. It means the numerical result can be bitwise identical to the sequential algorithm, provided the same summation order is used within each row and the same arithmetic is performed. This is often more important than it sounds. Many parallel numerical libraries promise reproducibility, and level scheduling is one of the few ways to get it without changing the algorithm.

## Dataflow Execution

Level scheduling is not the only way to execute the DAG. A dataflow or task-based approach treats each row as a task with dependencies. Instead of global barriers, each task runs as soon as its predecessors are complete. The standard implementation maintains a counter per row: the number of unfinished predecessors. When a row j finishes, it notifies its successors. For each successor i, it atomically decrements count[i]. If the counter reaches zero, i is ready and is pushed onto a work queue. This is Kahn's algorithm for topological sorting, fused with the numerical computation.

The advantage is finer-grained synchronization. A row can start immediately when its last predecessor finishes, without waiting for unrelated rows in the same level. This can improve load balance and reduce the impact of stragglers. It also avoids the per-level barrier, which can be a major cost on large machines. The disadvantage is overhead. You need a successor list for each row, which is the transpose of the sparsity pattern. That doubles the graph storage if you do not already have it. You need atomic operations on counters, which can contend. You need a concurrent work queue, which has its own overhead. And you need to ensure memory visibility: when a predecessor writes x_j, that write must be visible to the successor that reads it. In C++ terms, the decrement of the counter must have release semantics, and the read of x_j after acquiring the task must have acquire semantics. Getting this wrong can produce rare, non-reproducible wrong answers.

The counter approach also has a subtle load-balancing issue. A row with many predecessors will have its counter decremented many times, possibly by many threads. A row with many successors will generate many notifications. High-degree vertices become hot spots. You can reduce contention by using hierarchical counters, by combining notifications, or by falling back to level scheduling for dense regions. But these are engineering decisions that depend on the matrix structure.

Dataflow execution can also be implemented in a push style. Instead of gathering from predecessors, each row j, once computed, scatters its contribution to all successors i: b_i -= L_ij * x_j. This is column-oriented. It avoids the need to wait for all predecessors before starting a row, because the row can accumulate contributions as they arrive. But it requires atomic updates to b_i, which are slow and nondeterministic in floating-point. It also changes the summation order. For these reasons, push-style dataflow is more common in approximate or preconditioning contexts, where exact reproducibility is not required. For an exact solve, gather-style dataflow with counters is usually preferred.

## Why Row-Level Parallelism Is Often Not Enough

Even with perfect level scheduling or dataflow, row-level parallelism has limits. The critical path of the DAG is a lower bound. For a 1D Laplacian, the critical path is n, and there is no row-level parallelism at all. For a dense triangular matrix, the DAG is complete: row i depends on all j < i. The level of row i is i, so each level has exactly one row. There is no row-level parallelism. Yet dense triangular solve is routinely parallelized in libraries. The parallelism does not come from rows; it comes from blocks.

This is the key insight that row-level analyses miss. In a blocked triangular solve, you partition the matrix into blocks. You solve the diagonal block sequentially, or with a small parallel algorithm, then update the trailing submatrix with a matrix-matrix or matrix-vector operation. The updates to different blocks of the trailing submatrix are independent and can be done in parallel. The critical path becomes the number of block columns times the cost of solving a diagonal block. The total work increases slightly because of the blocked formulation, but the parallelism can be much larger. For dense matrices, the updates become GEMM operations, which are highly optimized. For sparse matrices, the updates are sparse matrix-vector products or sparse matrix-matrix products, which are less efficient but still parallel.

Supernodal sparse direct solvers take this further. They group columns with identical nonzero structure into supernodes, which are dense blocks. The triangular solve then operates on dense supernodes and sparse updates. The level of parallelism is the number of supernodes in a level, and the work is dominated by the updates. This is how modern sparse solvers achieve scalability. The row-level DAG is still there, but it is no longer the right abstraction for performance.

The trade-off is fill-in. Blocking and supernodes can increase the number of nonzeros, especially if the ordering is not chosen carefully. A fill-reducing ordering like nested dissection tends to produce large supernodes and more parallelism, but it also produces more fill-in than a minimum-degree ordering. The best choice depends on the matrix, the number of right-hand sides, the available memory, and the target hardware. There is no universal answer.

## Multiple Right-Hand Sides Change Everything

If you are solving LX=B with many columns, the problem becomes much easier to parallelize. You can assign different columns to different threads, or you can use a blocked algorithm that processes multiple right-hand sides together. The arithmetic intensity increases, and the memory access to L can be reused across columns. The dependency graph is the same for each column, but the columns are independent. This is the common case in sparse direct solvers, where the factorization is reused for many right-hand sides. The hard case is a single right-hand side, which is common in preconditioned iterative methods. In that case, the solve is called once per iteration, and the parallelism must come from within the matrix structure. This article focuses on the single right-hand side case because it is the most constrained.

## What Comes Next

We have established the basic model: the sparsity pattern defines a DAG, the DAG defines the available parallelism, and the ordering of the matrix determines the shape of the DAG. Level scheduling and dataflow are two ways to execute that DAG, with different synchronization and memory trade-offs. But row-level parallelism is only part of the story. In the next sections, we will look at blocked and supernodal formulations, the role of algebraic reordering, GPU-specific considerations, and the practical engineering of a parallel sparse triangular solve. We will also examine how to measure performance without fooling yourself, and why a benchmark that works on one matrix may fail on another.

## Blocked Formulations: Turning Dependencies into Panel Updates

The row-level DAG is a useful mental model, but it is rarely the unit of execution in high-performance codes. Instead, the matrix is partitioned into block columns, and the solve proceeds one block column at a time. Let L be partitioned into p block columns of size b, with diagonal blocks L_{kk} and off-diagonal blocks L_{kj} for k>j. Forward substitution becomes:

```text
for j = 0 to p-1:
    x_j = solve_dense_triangular(L_jj, b_j)
    for each k > j with L_kj != 0:
        b_k = b_k - L_kj * x_j
```

This is a column-oriented blocked solve. After solving block j, its contribution is scattered to all trailing blocks that depend on it. The updates to different k are independent, so they can be performed in parallel. The diagonal solve for block j must wait until all previous updates to b_j have completed, but once x_j is available, the trailing updates can proceed while the next diagonal block is being solved. The resulting dataflow graph is coarser than the row-level DAG, and its critical path is the chain of diagonal solves plus the updates that feed the next diagonal block. The width is the number of trailing blocks that can be updated concurrently, multiplied by the internal parallelism of each update.

The diagonal solves are dense triangular systems of size b. If b is small, say 32 to 128, the sequential cost is negligible compared with the updates. If b is large, the dense solve itself becomes a bottleneck, and you may need to parallelize it. Recursive blocking, partitioned inverses, and level scheduling within the dense block are all options. The choice depends on the hardware and the block size. On GPUs, batched dense triangular solves are often used, especially when there are multiple right-hand sides. For a single right-hand side, the diagonal solve is memory-bound and latency-bound, but it is still a small fraction of the total work for typical block sizes.

The updates are sparse matrix-vector products for a single right-hand side, or sparse matrix-matrix products for multiple right-hand sides. The sparse matrix-vector product can be parallelized over rows of L_kj. Each row updates a different entry of b_k, so there is no reduction and no write conflict. This is an important property: the blocked formulation avoids the atomic updates that plague push-style row-level dataflow. The only synchronization is between the diagonal solve of block j and the updates that read x_j. That synchronization is coarse-grained and can be implemented with events, streams, or task dependencies. The blocked formulation also improves memory locality. The off-diagonal blocks L_kj are dense rectangular matrices, so they are stored contiguously and can be streamed efficiently. The x_j vector is read as a contiguous chunk. This is much better than the indirect, scattered access pattern of a row-level solve.

## Supernodal Triangular Solve

Supernodal formulations take the blocked idea to its logical conclusion. In a sparse Cholesky factor, a supernode is a set of contiguous columns with identical nonzero structure below the diagonal. The diagonal block is a dense lower triangular matrix, and the off-diagonal blocks are dense rectangular matrices. The solve proceeds supernode by supernode. For supernode s, you solve the dense triangular system L_{ss} x_s = b_s - sum_{t<s} L_{st} x_t. The sum is over all previous supernodes that have nonzeros in the rows of s. Then you update the trailing rows: for each supernode r>s with L_{rs} != 0, b_r = b_r - L_{rs} x_s.

The updates are dense matrix-vector products. They can be parallelized across the rows of L_{rs}, and different r blocks can be updated concurrently. The diagonal solve is a dense triangular solve. The critical path is the number of supernodes on the longest path in the supernodal elimination tree. The parallelism is the number of supernodes in the same level of that tree, multiplied by the parallelism within each dense update. The supernodal structure also improves locality: the dense blocks are stored contiguously, so the hardware prefetcher can work, and the x vector is accessed in contiguous chunks. This is why supernodal sparse solvers like CHOLMOD, SuperLU, and MUMPS use this formulation. The cost is that supernodes may be small or irregular, and the level structure may be unbalanced. But for many matrices, especially those from 2D and 3D PDEs, supernodes are large enough to make the dense kernels efficient.

The trade-off between blocked or supernodal and row-level is not just about parallelism; it is also about memory traffic. A row-level solve reads L row by row, which is a scattered access pattern. A supernodal solve reads dense blocks, which is streaming. The arithmetic intensity is higher because each x entry is reused across many rows in a dense block. For a single right-hand side, the ratio of flops to bytes is still low, but it is better than row-level. For multiple right-hand sides, it becomes a matrix-matrix operation and the intensity increases further. This is why many sparse direct solvers are optimized for multiple right-hand sides. But even for a single right-hand side, the supernodal formulation is often faster because of the memory access pattern.

The supernodal approach also changes the granularity of synchronization. Instead of synchronizing on individual rows, you synchronize on supernodes. This reduces the number of dependency edges and makes the graph more amenable to task-based runtimes. A supernode can be a task that depends on the supernodes in its update list. The task runtime schedules it when its dependencies are satisfied. The task body consists of a dense triangular solve followed by a set of dense updates. The updates can be further parallelized internally. This is a natural fit for modern task-based systems like StarPU, PaRSEC, and OpenMP tasks with dependencies. The challenge is load balancing: supernodes have different sizes, and the critical path may be dominated by a few large supernodes. Dynamic scheduling and task priorities can help, but they cannot eliminate the fundamental imbalance.

## Algebraic Reordering and the Limits of Exposed Parallelism

Reordering is the primary lever for controlling both fill-in and parallelism. A fill-reducing ordering like approximate minimum degree (AMD) or METIS nested dissection minimizes the number of nonzeros in L. This is crucial for memory and flops. But the same ordering determines the elimination tree, and the elimination tree determines the dependency graph of the solve. In a Cholesky factor, the dependency graph is transitively reduced to the elimination tree: if L_ij != 0, then i is an ancestor of j in the elimination tree. The level of a node in the solve DAG is its depth from the leaves. The number of levels is the height of the elimination tree. The width of a level is the number of nodes at that depth. So the shape of the tree is the shape of the parallelism.

A minimum-degree ordering tends to produce a deep, unbalanced elimination tree. It greedily eliminates vertices with small degree, which often means it peels off leaves one by one. The result is a tree with long chains. The critical path is long, and the levels are narrow. There may be little row-level parallelism. A nested dissection ordering, on the other hand, recursively splits the graph into subgraphs and separators. The elimination tree is balanced: the separators are at the top, and the subgraphs are at the bottom. The height is O(log n) for many graphs, and the levels are wide. The top-level separator alone can contain O(sqrt(n)) vertices for a 2D grid, giving a wide level. So nested dissection exposes more parallelism. But nested dissection typically produces more fill-in than minimum degree. The difference can be a factor of 2 to 10 in nnz(L), depending on the matrix. That extra fill means more memory and more flops, which can offset the parallel speedup. The best choice is problem-dependent.

There are also parallel-friendly orderings that explicitly try to balance fill and parallelism. For example, one can use a hybrid: nested dissection for the top levels to create wide separators, and minimum degree for the small subgraphs at the bottom to reduce fill. Or one can use a parallel variant of minimum degree that limits the depth of the elimination tree. Some libraries provide multiple ordering options and let the user choose. The key point is that you cannot get something for nothing. The available parallelism is bounded by the structure of the graph. For a d-dimensional grid, the separator size is O(n^{(d-1)/d}). Any ordering must have a separator of at least that size to be fill-efficient. The critical path of the solve is at least the size of the largest separator on the path from a leaf to the root. So the maximum speedup is O(n^{(d-1)/d}) for a d-dimensional grid, up to logarithmic factors. For a 2D grid, that is O(sqrt(n)); for a 3D grid, O(n^{2/3}). You cannot achieve linear speedup with a single right-hand side, no matter how you reorder. This is a fundamental limit, not an implementation artifact.

There are graph-theoretic parameters that formalize this. The treewidth of a graph is the minimum over all elimination orders of the maximum clique size minus one, which is related to fill. The pathwidth is the minimum over all elimination orders of the maximum separator size along a path, which is related to the critical path. For many graphs, treewidth and pathwidth are close, but there are graphs where they differ. The trade-off between fill and parallelism is captured by the fact that you can reduce the critical path by increasing fill, but only up to a point. There are lower bounds that say any elimination order with fill F has critical path at least some function of F and the graph. You cannot simultaneously minimize both. This is why parallel sparse triangular solve is hard: the algebraic reordering that makes the factorization efficient often makes the solve sequential, and the reordering that makes the solve parallel often makes the factorization expensive.

It is also worth noting that reordering affects numerical behavior. For a fixed L, reordering is just a permutation, so the solve is exact in exact arithmetic. In floating-point, the order of operations changes, so the result can differ in the last bits. For iterative methods, this can affect convergence. For direct solvers, the factorization itself is affected by the ordering because pivoting and stability depend on the elimination order. A reordering that exposes parallelism may create smaller pivots or require more pivoting, which increases fill and cost. So the choice of ordering is a global optimization problem that couples numerical stability, fill, and parallelism. There is no single ordering that is best for all three.

## GPU and Many-Core Execution Models

On GPUs, the level-synchronous approach is often the starting point because it maps naturally to kernel launches. You compute the level of each row, group rows by level, and launch one kernel per level. Each kernel computes all rows in that level in parallel. The analysis phase is done once and can be reused across solves. The solve phase is a sequence of kernel launches. The problem is that the number of levels can be large. If a matrix has thousands of levels, the kernel launch overhead dominates. Even with CUDA graphs or cooperative groups, the synchronization cost is significant. The level sizes may also be small, leading to low occupancy. To mitigate this, some implementations merge multiple levels into a single kernel if the levels are small and the dependencies allow it. For example, you can process a level and then immediately process its successors if they are ready, using a global work queue. This is dataflow on the GPU. The challenge is that GPUs do not have efficient global synchronization or atomic operations at the scale of millions of threads. Spin-waiting on flags can work, but it requires careful memory fences and can cause deadlock if the block scheduling order does not match the dependency order. Some frameworks use persistent kernels with a work-stealing queue, but this is complex and not portable.

Blocked and supernodal formulations are more GPU-friendly because they expose dense linear algebra. The diagonal solves can be done with batched small dense triangular solves, which are available in libraries like cuBLAS and MAGMA. The updates are sparse matrix-vector products or sparse matrix-matrix products, which can be parallelized across rows or columns. For multiple right-hand sides, the updates become dense matrix-matrix products, which are highly efficient on GPUs. For a single right-hand side, the updates are memory-bound, but the dense blocks still provide better locality than row-level. The main difficulty is the irregularity of the supernodal structure. Supernodes can be small, and the level structure can be unbalanced. Some GPU sparse solvers use a hybrid approach: they use the CPU for the sequential parts and the GPU for the parallel updates, or they use multiple streams to overlap independent supernodes. The key is to keep the GPU busy and minimize synchronization.

Memory behavior is critical on GPUs. The x vector is accessed indirectly in row-level solves, which causes uncoalesced memory access. In supernodal solves, x is accessed in contiguous chunks, which is much better. The L matrix is also accessed in dense blocks, which can be loaded into shared memory or registers. False sharing on x is less of an issue because the writes are to distinct supernodes, but if two threads write to adjacent entries of x, they may share a cache line. Padding or using per-supernode buffers can help. The analysis phase can also precompute the level structure and the successor lists to avoid atomic operations. For dataflow execution, the counters and work queues must be designed to minimize contention. Hierarchical counters, where a group of rows shares a counter, can reduce atomic traffic. But they add complexity.

On many-core CPUs, the same trade-offs apply, but the synchronization mechanisms are different. OpenMP tasks with dependencies can implement dataflow efficiently. The runtime handles the dependency graph and schedules tasks on cores. The overhead per task is higher than on a GPU, so you want tasks to be coarse-grained. Blocked and supernodal formulations are essential to make tasks large enough. You can also use a hybrid: level scheduling for the top levels, where levels are wide, and dataflow for the bottom levels, where levels are narrow. This adapts to the matrix structure. The performance model is similar: the critical path and the total work determine the maximum speedup. The memory hierarchy determines the achieved fraction of that maximum. You should measure both the level structure and the actual runtime to understand where the bottlenecks are. A matrix with many levels but small work per level may be dominated by synchronization. A matrix with few levels but large work per level may be dominated by memory bandwidth. The right algorithm depends on which regime you are in.

## Hybrid Execution: Mixing Levels, Tasks, and Blocks

No single execution strategy dominates across the entire elimination tree. The top of the tree usually has wide levels and large dense updates, while the bottom has narrow levels and tiny tasks. A practical solver therefore mixes strategies. It might use level-synchronous execution for the first few levels, where a barrier is cheap relative to the work, and switch to dataflow or task-based execution for the deeper levels, where barriers would dominate. The switch point can be chosen statically from the symbolic analysis or dynamically by a runtime scheduler.

Supernodes make this hybrid approach natural. Each supernode is a task with a dense triangular solve and a set of dense updates. The update tasks for different supernodes are independent once the source supernode is complete. A task runtime can schedule them as soon as their dependencies are satisfied, without waiting for an entire level. The granularity is coarse enough to amortize scheduling overhead, yet fine enough to keep many cores busy. The challenge is that supernode sizes vary. A few large supernodes may dominate the critical path, while many small supernodes create scheduling overhead. Dynamic priorities and work stealing help, but they cannot create parallelism where the dependency graph does not allow it.

In distributed memory, the same hybrid idea applies at a larger scale. The matrix is partitioned across processes, and the solve requires communicating x entries that are needed by off-process updates. The communication pattern follows the elimination tree. For nested dissection, the tree is balanced, so communication is hierarchical and can be overlapped with computation. For minimum degree, the tree is deep, so communication is effectively sequential. This is another reason nested dissection is often preferred for parallel solvers, even when it produces more fill. The extra fill is a memory cost; the deeper tree is a latency cost. On a large machine, latency is usually the harder constraint.

Overlapping communication with computation is essential. While process p is solving its local diagonal block, it can send the newly computed x entries to processes that need them, and it can receive x entries for its next block. This is a software pipeline. The depth of the pipeline is limited by the dependency graph, but even a modest overlap can hide a significant fraction of the latency. Some solvers use a lookahead strategy: they speculatively start updates that do not depend on the current block, or they partition the matrix so that the critical path is as short as possible. The best partition depends on the matrix ordering, the number of processes, and the network topology. There is no universal recipe.

On GPUs, hybrid execution often means using the CPU for the sequential spine of the elimination tree and the GPU for the dense updates. The CPU handles the small, irregular tasks, while the GPU handles the large, regular ones. Multiple CUDA streams can overlap independent updates. The key is to keep the GPU from going idle during the sequential parts. Some implementations use persistent kernels that spin on flags, but this is fragile and can deadlock if the block scheduling order does not match the dependency order. A safer approach is to launch a sequence of small kernels, or to use CUDA graphs to reduce launch overhead. The trade-off between kernel launch overhead and occupancy is hardware-dependent, so autotuning is often necessary.

## Numerical Reproducibility and Determinism

Reproducibility is not usually the first concern in a sparse triangular solve, but it becomes important when the solve is embedded in a larger simulation that must produce bitwise identical results across runs or across different core counts. Level-synchronous execution with one thread per row is deterministic: each row's summation order is fixed, and the result does not depend on the number of threads. Dataflow execution can also be deterministic if each row is computed by a single thread and the row's nonzeros are processed in a fixed order. The dynamic scheduling changes when a row is computed, but not how. Since each x_i is written exactly once, the final result is the same.

Problems arise when a row is parallelized across threads, or when the algorithm uses atomic updates. A push-style dataflow, where each row scatters contributions to its successors, accumulates into b_i with atomic operations. The order of those atomic additions is nondeterministic, so the result can differ in the last bits from run to run. For many applications this is acceptable, but for debugging, verification, or regulatory compliance it is not. A gather-style dataflow avoids this by having each row read its predecessors and compute its own dot product. The only synchronization is the counter that tracks when all predecessors are ready. That counter can be implemented with atomic operations, but it does not affect the floating-point result.

Parallelizing a single row is another source of nondeterminism. Sparse rows are usually short, so the reduction is sequential and cheap. But some matrices have a few dense rows, and those rows can become a bottleneck. If you parallelize the reduction, you must fix the reduction tree to preserve determinism. A binary tree reduction is deterministic if the tree shape is fixed, even if the threads that execute it vary. Pairwise summation is also deterministic and can be more accurate than sequential summation. But both add overhead. For most sparse triangular solves, the row lengths are small enough that sequential reduction is fine. The rare dense row can be handled as a special case, perhaps with a deterministic parallel reduction or by falling back to a sequential kernel.

Reproducibility across processor counts is a stronger requirement. It means the result must be identical whether you run on 4 cores or 64. Level scheduling with a fixed level assignment satisfies this if each row is one task. Dataflow with work stealing also satisfies it if each row is one task and the row's computation is deterministic. The result does not depend on which thread computes which row. This is a strong argument for row-level gather in applications where reproducibility matters. Blocked and supernodal formulations complicate this because updates to a block from different source blocks are summed. If the order of those updates changes, the result changes. To make blocked solves reproducible, you must fix the order of updates, either by processing source blocks in a fixed order or by using a deterministic reduction. That may limit parallelism, but it is sometimes a price worth paying.

Mixed precision adds another layer. If the solve is done in single precision but the residual is accumulated in double, the result depends on the order of operations in a more complicated way. Some applications use compensated summation to reduce error, but that also changes the operation count and the dependency structure. There is no free lunch. You must decide which forms of reproducibility you need and design the algorithm accordingly.

## Incomplete Factorizations and the Approximate Solve Alternative

Incomplete LU and incomplete Cholesky factorizations are common preconditioners for iterative methods. They are sparser than complete factors, so the triangular solve is cheaper. The dependency graph is also sparser, which can expose more parallelism. But the solve is still sequential in the worst case, and it is applied once per iteration. For a preconditioner, an approximate solve is often good enough. You can replace the exact triangular solve with a few steps of Jacobi, Gauss-Seidel, or a polynomial approximation. These alternatives are more parallel, sometimes embarrassingly so, and they avoid the dependency graph entirely.

The trade-off is iteration count. A weaker preconditioner usually means more Krylov iterations. On a highly parallel machine, that can still be a win. For example, a Jacobi preconditioner requires only a diagonal scaling, which is a vector operation with no dependencies. It is trivially parallel. An ILU(0) preconditioner may reduce the iteration count by a factor of two or three, but its triangular solve may be ten times slower on a GPU because of the sequential dependency and irregular memory access. In that regime, Jacobi wins despite the extra iterations. The same logic applies to polynomial preconditioners and sparse approximate inverses. They replace the triangular solve with sparse matrix-vector products, which are much easier to parallelize.

This does not mean exact triangular solves are obsolete. Direct solvers still need them, and some preconditioners rely on them for robustness. But it does mean that the performance of a parallel sparse triangular solve cannot be evaluated in isolation. You must consider the entire iterative method. A faster solve that reduces the iteration count by a small amount may be less valuable than a slower solve that is more parallel. The right choice depends on the problem, the hardware, and the tolerance. It is a system-level optimization, not a kernel-level one.

Communication-avoiding Krylov methods take this idea further. They restructure the iteration to reduce the number of global synchronizations and triangular solves. This can improve scalability on large machines, but it often requires more memory and can be less numerically stable. The triangular solve is one of the synchronization points they try to eliminate. If you are designing a solver for an exascale machine, you may need to consider these methods even if they are more complex. The alternative is to accept that the triangular solve will limit your scalability.

## Performance Modeling and Benchmarking Pitfalls

Benchmarking a parallel sparse triangular solve is full of traps. The most common mistake is to benchmark only the solve phase and ignore the analysis phase. The analysis includes reordering, symbolic factorization, and level scheduling. It can take longer than the solve itself, especially if the solve is called only once. If you are solving many right-hand sides with the same matrix, the analysis is amortized. If you are solving once, it is not. You must report both and state which regime you are in.

Another trap is using a matrix with a trivial dependency graph. A diagonal matrix has no dependencies, so it parallelizes perfectly. A bidiagonal matrix is a chain, so it has no parallelism. Neither is representative of real sparse matrices. You need a suite of matrices with different structures: 2D and 3D grids, finite element meshes, circuit simulation matrices, and social network graphs. The level structure, the average row length, and the supernode sizes all matter. A single matrix can mislead you.

You should also measure the right metrics. The work-span model gives you the critical path length and the total work. From those you can compute the maximum parallelism, which is work divided by critical path. If your achieved speedup is much less than the maximum parallelism, you are not limited by the dependency graph; you are limited by memory bandwidth, synchronization, or load imbalance. Hardware counters can tell you which. For a single right-hand side, the arithmetic intensity is low: roughly two flops per nonzero, and each nonzero requires reading an index and a value. The solve is memory-bound. For multiple right-hand sides, the intensity increases and the solve becomes more compute-bound. You must benchmark both cases.

Strong scaling is limited by the critical path. Weak scaling is limited by the growth of the critical path with problem size. For a 2D grid, the critical path grows as the square root of the number of unknowns, so weak scaling is not constant. For a 3D grid, it grows even faster. This means that adding more cores does not help indefinitely. You will eventually hit a point where the critical path dominates and additional cores sit idle. You should measure this point and report it. It is a property of the matrix and the ordering, not just the implementation.

Finally, be careful with the sequential baseline. A poorly optimized sequential solve can make your parallel solve look better than it is. Use a well-tuned sequential kernel, or compare against the best available library. Also measure variance. Sparse triangular solve can have high run-to-run variance due to cache effects and scheduling. Report medians and percentiles, not just means. Pin threads to cores and use NUMA-aware memory allocation. These details can change the result by a factor of two or more.

## Case Study: What the Limits Imply for Solver Design

Consider a 2D Laplacian on a 1000 by 1000 grid, so n is one million. With nested dissection, the elimination tree has a critical path on the order of the square root of n, or about one thousand levels. The total work is on the order of n log n, or about twenty million flops. On a single core at one gigaflop per second, the work takes about twenty milliseconds. If each level takes one microsecond, the critical path takes one millisecond. So the maximum speedup is about twenty, even with infinite cores. If each level takes only a tenth of a microsecond, the critical path is one hundred microseconds and the maximum speedup is two hundred. Still far from the thousand cores you might have.

For a 3D Laplacian on a 100 by 100 by 100 grid, n is again one million. The critical path is on the order of n to the two-thirds, or about ten thousand levels. The total work is larger, perhaps a few hundred million flops. The critical path is ten times longer than the 2D case, so the maximum speedup is much smaller. This is a fundamental limit. You cannot reorder your way out of it without increasing fill dramatically. And increasing fill increases the work, which may offset the gain in parallelism.

What does this imply for solver design? If you need more parallelism for a single right-hand side, you must change the problem. You can use multiple right-hand sides, which adds parallelism across columns. You can use an approximate solve, which replaces the triangular solve with a more parallel operation. You can use a different preconditioner that does not require a triangular solve. Or you can accept the limit and optimize within it. The last option is often the most practical. It means using supernodes to improve memory locality, overlapping communication with computation, and choosing an ordering that balances fill and parallelism for your specific matrix and hardware.

These limits also suggest where research is headed. Mixed-precision solves could reduce the cost of each level, shortening the critical path in wall-clock time. Communication-avoiding algorithms could overlap more of the dependency chain. Randomized or sketching methods could approximate the solve in a way that is more parallel. None of these is a silver bullet, but together they expand the design space. The important thing is to know the limits of the standard approach, so you know when to look for something else.

## Symbolic Preprocessing Is Part of the Solve

Parallel sparse triangular solve begins long before the first floating-point operation. The symbolic phase determines the elimination tree, the postorder, the nonzero pattern of each row and column, the supernode partition, and the dependency lists used by the runtime. If this phase is incomplete, the numerical phase either stalls or recomputes dependencies on the fly. The cost of symbolic preprocessing is often amortized across many solves, but for a single solve it can dominate. A practical implementation separates structural analysis, which depends only on the sparsity pattern and the ordering, from an execution plan, which depends on the target architecture and thread count. The structural analysis is portable; the execution plan is not.

The elimination tree is the compact representation of the dependencies. For a Cholesky factor, the parent of column j is the smallest i>j such that L_ij is nonzero. For an LU factor, pivoting complicates the tree, but the column dependency graph still defines a partial order. Once the tree is known, the level of each node is its depth from the leaves. The level sets can be computed with a simple traversal. Successor lists for dataflow execution are the transpose of the tree edges plus fill edges. Storing them explicitly costs O(nnz(L)) integers, which can be a significant fraction of matrix storage. Some implementations avoid explicit successor lists by using the elimination tree and a reach computation, trading memory for time.

The symbolic phase also determines the supernode partition. Columns with identical nonzero structure below the diagonal are merged. The resulting supernodes are the tasks in a supernodal solve. Their sizes affect both dense kernel efficiency and load balance. Large supernodes are good for dense linear algebra; many supernodes are good for parallelism. Relaxed supernode amalgamation can merge columns with similar but not identical structure, increasing block size at the cost of extra zeros. The extra zeros are harmless for memory if stored densely, but they increase flops. The trade-off is matrix-dependent and often tuned empirically.

## Task Granularity and the Shape of the Runtime Graph

The runtime graph is not the mathematical dependency graph. The mathematical graph has one vertex per row or column. The runtime graph has one vertex per task, and a task may contain many rows. Coarsening reduces scheduling overhead and improves locality, but it also reduces the number of independent tasks. If tasks are too coarse, the critical path becomes a sequence of large tasks and the machine is underutilized. If they are too fine, the scheduler spends more time managing tasks than doing arithmetic. The sweet spot depends on hardware, matrix, and runtime.

For a supernodal solve, the natural task is a supernode. Its work is the dense triangular solve plus updates to descendants. Updates can be split into subtasks, one per target supernode. This creates a two-level graph: a supernode task depends on all source supernodes that update it, and each update subtask depends on the source supernode. Scheduling at the update level gives more parallelism but more overhead. Scheduling at the supernode level is simpler but may serialize updates that could run concurrently. A common compromise is to schedule supernodes but allow updates within a supernode to be parallelized by the dense kernel.

Load imbalance is the enemy of any task-based solve. Supernode sizes are irregular. A few large supernodes can dominate the critical path, while many small supernodes create scheduling noise. Priority scheduling can help: give higher priority to tasks on the critical path. Critical path information can be computed during symbolic analysis by assigning each task a bottom-level, the length of the longest path to the end. Tasks with larger bottom-levels are more urgent. This is the same idea used in list scheduling for DAGs. It is not optimal, but it often improves makespan. Work stealing can fill idle cores with off-critical-path tasks, but it cannot shorten the critical path itself.

## Memory Layout, Locality, and the Cost of Indirection

The memory system often determines achieved performance more than the dependency graph. A row-level CSR solve reads L row by row and gathers x entries indirectly. The index array is as large as the value array, so effective memory traffic is at least twice the nonzero count. The gather pattern is irregular, so cache lines are underutilized. A supernodal solve reads dense blocks and accesses x in contiguous chunks. Index overhead is amortized over many rows. Values are streamed, so the hardware prefetcher can work. This is why supernodal formulations are faster even when the dependency graph is identical.

The x vector is a shared resource. In a gather-style solve, many rows read overlapping sets of x entries. If x fits in cache, reads are cheap. If not, each row may miss. Blocking the solve by supernodes improves temporal locality because x entries produced by a supernode are consumed by descendants before eviction. The order of supernode execution matters. A depth-first traversal of the elimination tree keeps the working set small but may expose less parallelism. A breadth-first or level-synchronous traversal exposes more parallelism but has a larger working set. This is another manifestation of the parallelism-locality trade-off.

For multiple right-hand sides, the layout of B and X matters. If B is column-major, each column is contiguous and the solve can process columns independently. If B is row-major, the access pattern is transposed. Many libraries require column-major for this reason. The number of right-hand sides also affects kernel choice. With a few columns, a sparse matrix-vector product is appropriate. With many columns, a sparse matrix-matrix product or dense block update is better. The crossover point depends on the matrix and hardware, usually between 4 and 32 columns, but higher on GPUs with wide vector units.

NUMA effects are significant on multi-socket CPUs. If x is allocated on one socket and read by threads on another, remote memory latency can dominate. First-touch initialization and interleaved allocation mitigate this. Pinning threads and partitioning the matrix so each socket works on local data is better, but requires a topology-aware partition of the elimination tree. For a supernodal solve, this means assigning supernodes to sockets based on data dependencies. The assignment must balance work and minimize cross-socket communication. This is a graph partitioning problem at the supernode level, and it can be solved with the same tools used for matrix ordering.

## Autotuning and Runtime Adaptation

There is no single block size, level-merging threshold, or task granularity that works for all matrices. Autotuning is therefore a practical necessity. Tuning parameters include supernode amalgamation threshold, dense kernel block size, number of levels to merge in a level-synchronous schedule, switch point from level-synchronous to dataflow execution, and number of CUDA streams or OpenMP teams. The search space is large, but it can be pruned with a performance model. For example, the cost of a level-synchronous step is roughly the maximum work in the level plus barrier cost. The cost of a dataflow step is task overhead plus critical path. You can estimate these from symbolic analysis and choose the strategy that minimizes predicted time.

Runtime adaptation is more ambitious. The solver can monitor task progress and adjust the schedule on the fly. If a level is taking too long, it can split large tasks or migrate work to idle threads. If the critical path is dominated by a few supernodes, it can parallelize those supernodes internally. This requires a runtime that supports dynamic task granularity and work stealing, plus low-overhead instrumentation. The overhead of adaptation must be less than the gain. In practice, simple static heuristics capture most of the benefit, and complex adaptation is reserved for extreme cases.

## Mixed Precision and the Dependency Graph

Mixed precision can change the economics of the solve. If the matrix and right-hand side are stored in single precision, memory traffic is halved. The dependency graph is unchanged, but each level completes faster. For a latency-bound solve, this can be a significant win. Accuracy may be insufficient, so iterative refinement is used: solve in single precision, compute the residual in double precision, and correct. The refinement step is a sparse matrix-vector product, which is more parallel than the triangular solve. The triangular solve remains on the critical path, but it is cheaper. This is promising for GPUs, where single-precision throughput is much higher than double-precision throughput. The challenge is ensuring refinement converges and extra passes do not offset the gain. For well-conditioned systems, one or two steps suffice. For ill-conditioned systems, double precision is required.

## Distributed-Memory Considerations

In distributed memory, the triangular solve is a sequence of local solves and remote updates. The matrix is partitioned by block rows or block columns. Each process owns a set of rows of L and a slice of x. When a process computes local x entries, it must send them to processes that need them for updates. The communication pattern follows the elimination tree. For a balanced tree, communication is hierarchical and can be aggregated. For a deep tree, communication is effectively sequential, and latency dominates.

The key optimization is to overlap communication with computation. While a process waits for a remote x block, it can work on local updates that do not depend on that block. This is a software pipeline. The depth of the pipeline is limited by the number of independent tasks. A good partition creates many independent tasks at each level, so the pipeline can be deep. A poor partition creates a long chain, so the pipeline is shallow. This is another reason to prefer orderings that produce balanced elimination trees, even at the cost of extra fill.

Message aggregation is also important. Sending many small messages is inefficient. The solver should combine x entries destined for the same process into a single message. Symbolic analysis can precompute the communication schedule, so the numerical phase only packs and unpacks buffers. This reduces overhead and improves predictability. Some solvers use one-sided communication or remote memory access to avoid synchronization, but the fundamental dependency structure remains.

## Practical Design Patterns

A few design patterns recur in successful parallel sparse triangular solves. First, separate symbolic and numerical phases, and make the symbolic phase reusable. Second, use supernodes or blocks to turn irregular row operations into dense kernels. Third, choose an execution strategy that matches the shape of the elimination tree: level-synchronous for wide, shallow trees, and dataflow for deep, narrow trees. Fourth, keep the critical path in mind when partitioning and scheduling. Fifth, measure memory traffic and synchronization overhead, not just speedup. Sixth, preserve determinism where it matters by fixing the order of reductions and updates. These patterns do not guarantee optimal performance, but they avoid the most common failure modes.

The interaction between these patterns is not fully understood. A supernode partition that is optimal for a single right-hand side may be suboptimal for many right-hand sides. A schedule that preserves determinism may leave performance on the table. A distributed partition that minimizes communication may create a longer critical path. These are open questions that depend on the problem class and the hardware generation. They also suggest that the next generation of sparse triangular solvers will need to be more adaptive, not just more parallel.
