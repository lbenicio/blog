Modern CDCL SAT solvers are one of the quiet triumphs of algorithm engineering. A tool that in the 1990s might have choked on a few hundred variables now routinely discharges instances with millions of variables and tens of millions of clauses — not because the worst case got better (it cannot; satisfiability is NP-complete) but because real instances carry structure that conflict-driven learning exploits with unusual efficiency. For a large class of problems, one core running a well-tuned solver is fast enough that parallelism never enters the conversation.

Then it does. Formal verification, planning, combinatorial design, hardware equivalence checking, and configuration problems all produce instances where a single core runs for hours or days and the answer is worth a rack of machines. At that point the obvious question is why not use sixty-four cores instead of one. The answer is that CDCL search is one of the least parallel-friendly computations in common use, and the techniques that do work are interesting precisely because they are not the obvious ones.

This article is about parallel SAT solving as an engineering discipline: what actually parallelizes, what does not, where the correctness traps are, and how the design of a parallel solver differs from the design of a sequential one. It assumes you know roughly what a CDCL solver does; the first section refreshes the parts that matter for parallelism and explains why they resist it. From there we will cover the three broad families of parallel SAT — portfolios, search-space splitting, and hybrids — the mechanics of clause sharing (the single most consequential design decision), cube-and-conquer as it is actually practiced, the load-balancing and memory problems that appear at scale, and the reproducibility costs that come with all of it.

## What CDCL does, and why it resists parallelism

A CDCL solver is a loop around a small number of tightly coupled components. The loop maintains a partial assignment and a clause database. It repeatedly performs unit propagation: any clause that has all but one literal falsified forces the remaining literal true, and that forced assignment may in turn falsify other clauses. This continues to a fixpoint. If propagation produces a conflict — a clause with all literals falsified — the solver analyzes the implication graph that produced the conflict, derives a new clause (the learned clause), and backjumps to the second-highest decision level in that clause, undoing a chunk of the assignment. If propagation produces no conflict and unassigned variables remain, the solver picks a decision variable according to a heuristic and assigns it a polarity. Periodically it restarts, throwing away the current assignment but keeping learned clauses, and periodically it deletes learned clauses that it judges unlikely to be useful.

Four of those components have state that is global and history-dependent, and that is the root of the difficulty.

Propagation is a fixpoint over a queue, and the queue is data-dependent. You cannot know which clauses will become unit until you have propagated the ones before them. The dependency structure is not a static graph you can partition in advance; it is discovered as the assignment grows. There is a small amount of parallelism available in the frontier of the propagation queue, but the frontier is usually narrow, and the work per element is a handful of memory accesses. Attempts to parallelize unit propagation tend to be memory-bandwidth-bound rather than compute-bound, and the synchronization needed to keep the queue consistent often costs more than the propagation it parallelizes. This is why fine-grained parallelism inside a single solver's inner loop has never delivered the kind of speedup that coarse-grained parallelism has.

Conflict analysis is a backward walk. Starting from the conflicting clause, the solver traverses the implication graph in reverse, resolving clauses until it reaches the first unique implication point. The walk is sequential by construction: each resolution step depends on the previous one, and the set of literals it accumulates determines where it goes next. There are ways to parallelize pieces of it — the graph is available, and some work can be done speculatively — but the critical path is short and irregular, which is the worst case for parallel speedup.

Learned clauses are global state, and they change the future of every branch. A learned clause is not a local annotation on one subtree; it is a fact about the formula that prunes the entire remaining search space. Adding one clause changes propagation everywhere, which changes which conflicts occur next, which changes which clauses are learned. This is the source of CDCL's power and the source of its sequentiality: the search is not a static tree that a scheduler can hand out in slices. It is a tree that is being rewritten as it is traversed.

The heuristics are path-dependent. VSIDS-style activity scores decay over time and are bumped by conflicts; phase saving remembers the last polarity assigned to each variable; restart schedules adapt to the recent history of clause quality. Two solvers that differ in a single early decision will, a few thousand conflicts later, be exploring quite different parts of the space with quite different heuristics. That is a feature for portfolio diversity and a complication for any scheme that assumes workers can be kept in lockstep.

The practical consequence is that the unit of parallelism in SAT is not the clause, the propagation, or the conflict. It is the search context: an entire solver state with its own assignment, its own trail, its own heuristic scores, and its own view of the clause database. Everything that works at scale is built on that observation.

## Three families of parallel SAT

Given that the unit of work is a search context, there are really only two ways to use more than one of them: run several contexts on the same problem and race, or partition the problem so that different contexts work on different subproblems. Everything else is a combination of those two ideas.

**Portfolios.** A portfolio runs N solver instances on the same formula, typically diversified so they do not all do the same thing: different random seeds, different branching heuristics, different restart policies, different clause-deletion aggressiveness, different initial polarities. The first instance to finish determines the answer. The instances are coupled, if at all, only by clause sharing. The appeal is that a portfolio requires no knowledge of the search space, no partitioning logic, and no correctness argument beyond "each instance is a correct solver." The cost is duplicated work: in the worst case, N-1 instances explore regions that another instance already refuted.

**Search-space splitting.** Here the formula is partitioned into subproblems, each solved by a different worker. The partition can be static — generated up front by a lookahead procedure that produces cubes (conjunctions of decisions) whose disjunction covers the space — or dynamic, where workers steer each other apart by committing to different prefixes of the search tree. Splitting avoids duplicate work in principle and can approach linear speedup when the subproblems are comparable in difficulty. The difficulty is that they usually are not: subproblem runtimes in a cube-and-conquer run span many orders of magnitude, so the wall-clock time is set by the unluckiest cube, not by the average one.

**Hybrids.** The most effective configurations in practice are hybrids: split the space into cubes, then run a small portfolio on each cube; or run a portfolio whose members periodically split off into subproblems derived from their own search state. Hybrids inherit both the partition-quality problem and the duplication problem, but they also get the hedging behavior: if the partition is bad, the portfolio inside each part still samples the runtime distribution.

Cutting across that taxonomy is a second axis: shared memory versus distributed memory. A shared-memory solver can afford to exchange clauses frequently and cheaply, because the exchange is a memcpy into a shared buffer plus a lock or two. A distributed solver pays network latency and bandwidth per exchange, so it must filter aggressively and exchange rarely. The two designs converge on the same conceptual structure — a producer side that selects clauses worth exporting, a transport, and a consumer side that imports and integrates — but the parameters are wildly different, and a design tuned for one is usually bad for the other.

## Why portfolios work: heavy tails, not throughput

The intuition that a portfolio wastes N-1 cores assumes that all runs take about the same time. For backtracking search, that assumption is often wrong in a very specific way.

Runtime distributions for randomized backtracking search on satisfiable instances near the satisfiability threshold are frequently heavy-tailed: the distribution has a long tail such that the mean is dominated by rare, extremely long runs. The practical signature is that restarting a solver with a different random seed sometimes finds a solution in seconds after the previous run spent hours in a barren region. When the distribution is heavy-tailed, running N independent runs in parallel and taking the first to finish yields an expected speedup that can exceed N, because the parallel ensemble samples the tail more effectively than any single long run does. The portfolio is not dividing the work; it is buying lottery tickets in a lottery with a favorable tail.

This is a genuine effect and it is the main reason portfolios are competitive at all, but it comes with sharp caveats. It applies to satisfiable instances whose runtime distribution is actually heavy-tailed; for unsatisfiable instances the distribution is usually much more concentrated, and the benefit shrinks accordingly. It requires real diversification — if the runs are correlated, the ensemble is just one run paying N times the memory. And it is a statement about expectations, not about any particular instance: a portfolio can easily be slower than a single solver on the specific formula in front of you, because the single solver might have drawn a short run.

The corollary for design is that portfolio members should be diversified along axes that change the search trajectory, not along axes that change only constant factors. Random seeds and polarity choices change trajectories. Different propagation implementations do not.

The next section turns to the mechanism that makes a portfolio something more than N independent runs: clause sharing, the filters that keep it from drowning the solver, and the correctness conditions that make it sound.

## Clause sharing: the mechanism that couples portfolios

A portfolio of independent solvers is easy to reason about but leaves performance on the table. If one solver learns a clause that prunes a huge region of the search space, the other solvers will eventually rediscover that same clause, or worse, waste time in the pruned region before doing so. Clause sharing is the mechanism that lets portfolios benefit from each other's discoveries. It is also the single most consequential design decision in a parallel SAT solver, because it touches correctness, memory, and the delicate balance of the search heuristics.

The first question is what to share. Every learned clause is a logical consequence of the original formula, so in principle any of them can be shared without compromising soundness. In practice, sharing everything is disastrous. A CDCL solver learns tens of thousands of clauses per second on a hard instance; broadcasting all of them would saturate any communication channel and flood every solver's database with low-quality clauses that slow propagation without pruning much. The art is in the filter.

The most common filter is the literal block distance (LBD) of a clause: the number of distinct decision levels among its literals. Clauses with small LBD — say, two or three — are empirically much more likely to be useful across different search contexts. They capture global structure of the formula rather than incidental details of one solver's trajectory. Many parallel solvers therefore share only clauses with LBD below a threshold, often adjusted dynamically: if the network or shared buffer is congested, the threshold drops; if solvers are starving for useful clauses, it rises. Clause length is a cruder proxy; unit and binary clauses are always worth sharing because they are cheap to propagate and often very powerful. Activity scores, which measure how often a clause participates in conflicts, are another signal, but they are local to a solver and must be recalibrated on import.

The second question is when to share. Sharing after every conflict is impossible; sharing after every restart is a common compromise. Restarts are natural synchronization points: the solver has just discarded its assignment, so its trail is empty and its heuristic scores have been recently decayed. Importing a batch of clauses at that moment integrates them into a relatively clean state. Some solvers share on a timer instead, or when their export buffer reaches a certain size. The frequency trade-off is classic: too frequent and the synchronization overhead and clause pollution dominate; too rare and the portfolio loses its coupling.

The third question is how to share, and this is where shared-memory and distributed-memory designs diverge. In a shared-memory solver, a global clause buffer protected by a lock or a lock-free queue is sufficient. Exporting a clause is a memcpy and an atomic increment; importing is a memcpy and an insertion into the local database. The cost is in the insertion: the imported clause must be checked for duplicates (often via a hash table of clause signatures) and integrated into the two-watched-literal scheme. Duplicate detection is important because a clause can be learned independently by multiple solvers, and adding it twice wastes memory and propagation time. In a distributed solver, the transport is a network, so clauses must be batched, compressed, and filtered aggressively. Latency is measured in milliseconds, not nanoseconds, so the sharing interval is longer and the LBD threshold is stricter. Some distributed solvers share only unit clauses, which are small and almost always useful.

The correctness trap is subtle and worth stating explicitly. A learned clause is implied by the formula *under the assumptions active when it was learned*. In a plain portfolio, all solvers work on the same formula with no extra assumptions, so any learned clause is globally valid. But in cube-and-conquer, each worker solves a subproblem defined by a cube — a conjunction of decisions. A clause learned while solving under a cube is only implied by the original formula together with that cube. If you share it with a worker solving a different cube, that worker may use it to prune assignments that are actually satisfiable under its own cube, potentially missing a solution or deriving a spurious conflict. The fix is to filter out any clause that depends on the cube assumptions. Operationally, this means tracking the decision levels that correspond to cube literals and only sharing clauses whose derivation does not include them. A simpler but more conservative rule is to share only clauses learned at decision level zero, after all assumptions have been propagated and no decisions are active. That eliminates most of the benefit, however, so most cube-and-conquer implementations either disable clause sharing entirely or share only clauses that are independent of the cube (e.g., by checking that the clause does not contain any of the cube's literals). The latter is sound because if a clause is implied by the original formula alone, it remains valid under any cube. The check is not free, but it is cheaper than the alternative of debugging an unsound answer.

Even when clause sharing is sound, it can hurt performance. Imported clauses change the search trajectory of the receiving solver. Sometimes this is exactly what you want: a clause that prunes a large region early. But sometimes it is not: the solver was making progress with its own heuristics, and the imported clauses steer it into a less productive region. This is why clause sharing is often described as a double-edged sword. Adaptive schemes monitor the ratio of imported clauses that participate in conflicts to those that just sit in the database; if the ratio is low, the sharing policy is tightened. Some solvers go further and allow workers to reject imported clauses if their activity is too low or if the database is already large.

The memory cost is the final piece. Every shared clause that is imported increases the receiving solver's database. Over a long run, a portfolio with aggressive sharing can see each solver's database grow to several times its solo size. Clause deletion becomes essential, but deletion interacts with sharing: if a solver deletes a clause, it cannot un-share it. Other solvers may still have it and continue to propagate with it. This is fine for correctness — the clause is still valid — but it means the memory footprint is determined by the union of all shared clauses, not by any single solver's deletion policy. In the worst case, the portfolio's aggregate memory is much larger than the sum of the solvers' individual memories would be without sharing. At scale, this can be the limiting factor. Some systems use a global clause database with reference counting, but that introduces synchronization on every propagation, which is usually too expensive. The common compromise is local databases with periodic, filtered sharing, accepting the memory overhead as the price of coordination.

## Cube-and-Conquer: partitioning the search space

Portfolios attack the problem by redundancy; cube-and-conquer attacks it by division. The idea is to use a lookahead solver to split the search space into a set of subproblems, each defined by a cube — a conjunction of variable assignments. The cubes are mutually exclusive and exhaustive: every complete assignment satisfies exactly one cube, so solving all cubes is equivalent to solving the original formula. If any cube yields a satisfying assignment, the formula is satisfiable; if all cubes are unsatisfiable, the formula is unsatisfiable. This makes cube-and-conquer a sound and complete approach, and because the cubes are independent, it parallelizes trivially.

The lookahead phase is where the quality of the split is determined. A lookahead solver does not just pick a variable and branch; it evaluates candidate variables by the amount of propagation they trigger. A variable that, when assigned, forces many other variables through unit propagation is a good candidate because it simplifies the formula quickly. The lookahead solver recursively builds a decision tree, choosing at each node the variable that maximizes some measure of propagation, until the tree has a desired number of leaves (cubes). The leaves are then handed out to CDCL solvers. The lookahead phase is sequential, but it is usually fast relative to the CDCL phase, and it can be parallelized to some extent by generating subtrees independently.

Why does this help? CDCL is very good at solving subproblems once they are small enough that its learning heuristics can focus on the remaining structure. The lookahead solver is good at finding the decisions that break the problem into such subproblems. The combination is often much more efficient than either alone. Moreover, because the cubes are independent, cube-and-conquer does not suffer from the duplicate work that plagues portfolios. Each cube is solved exactly once. For unsatisfiable instances, this can lead to near-linear speedups, because the work is divided rather than replicated.

The catch is load balancing. The cubes produced by a lookahead solver are not equally hard. In practice, the runtime distribution across cubes is heavy-tailed, just like the runtime distribution of randomized runs. A few cubes may take hours while most take seconds. The wall-clock time of the parallel run is determined by the slowest cube, so a naive static assignment of one cube per core wastes most cores once the easy cubes finish. The solution is dynamic scheduling: generate many more cubes than cores (say, ten or a hundred times as many) and have workers pull cubes from a central queue as they become free. This smooths the load imbalance, but it does not eliminate it entirely: if the hardest cube is ten times harder than the second hardest, the last core will still be running long after the others are idle.

A more adaptive approach is dynamic splitting. Instead of generating all cubes up front, start with a small number of cubes and let workers split them further as needed. A worker that has been solving a cube for a while without finishing can decide to split it into two or more subcubes by picking a variable and branching on it. The subcubes are then pushed back to the work queue, and the worker continues with one of them. This is essentially a work-stealing scheduler with on-the-fly partitioning. The advantage is that splitting is guided by the actual difficulty of the subproblem: easy cubes are solved without further splitting, hard cubes are broken down until they become tractable. The overhead of splitting is the cost of creating new subproblems (copying the clause database or using a copy-on-write mechanism) and communicating them to the scheduler. If the overhead is small relative to the time saved by parallelizing the hard cube, the approach wins.

Implementations of cube-and-conquer often combine both ideas: a lookahead phase generates an initial set of cubes, and a dynamic splitting phase handles the outliers. The lookahead phase can also be interleaved with solving: while some workers solve cubes, others continue to look ahead on the remaining unsolved cubes. This is sometimes called "cube-and-conquer with lookahead on demand." The key engineering challenge is the interface between the lookahead solver and the CDCL solvers. The lookahead solver needs to know when a cube has been solved so it can stop working on that part of the tree. The CDCL solvers need to receive cubes in a format they can use as assumptions, and they need to report back whether the cube is satisfiable or unsatisfiable. In a shared-memory setting, this is a matter of shared data structures and atomic flags. In a distributed setting, it requires a coordinator process and a protocol for claiming and completing cubes.

Memory management in cube-and-conquer is simpler than in a portfolio with clause sharing, because each cube is independent and there is no need to share learned clauses. Each worker maintains its own clause database, which starts as a copy of the original formula plus the cube's assumptions. The original formula can be shared read-only across workers in a shared-memory system, saving memory. In a distributed system, each node must have a copy of the formula, which can be a significant transfer cost for large instances. Compression and incremental loading help, but the formula transfer is a one-time cost that is amortized over the solving time. The learned clauses are local to each worker and can be deleted aggressively, because they are only useful for the current cube. This locality is a major advantage: it keeps memory bounded and avoids the synchronization overhead of clause sharing.

The limits of cube-and-conquer are the limits of partitioning. If the formula has a single hard core that cannot be split further — for example, a subproblem that remains difficult no matter which variable you branch on — then the parallel run will eventually reduce to one core working on that core, and the speedup saturates. This is the same phenomenon that limits portfolios, but it manifests differently: portfolios suffer when the heavy tail is not sampled well; cube-and-conquer suffers when the partition does not isolate the hard part. In practice, the hardest instances are those where neither approach achieves more than a modest speedup, because the search space is not amenable to either redundancy or division.

## Load balancing, memory, and the cost of scale

Scaling a parallel SAT solver from a few cores to a few hundred or thousand changes the bottlenecks. At small scale, the main concern is keeping all cores busy and avoiding duplicate work. At large scale, communication and memory bandwidth become dominant, and the overhead of coordination can eat the gains from parallelism. Understanding where the costs go is essential for designing a solver that scales.

Load balancing is the first hurdle. Static partitioning — assigning each core a fixed set of cubes or a fixed solver configuration — is simple but fragile. It works only if the runtime distribution is predictable, which it almost never is. Dynamic scheduling, where workers pull work from a central queue, is more robust but introduces a central point of contention. At a few dozen cores, a lock-protected queue is fine. At hundreds, the queue becomes a bottleneck. The standard solution is a distributed work-stealing scheduler: each worker has its own deque of work items, and idle workers steal from the back of other workers' deques. Work stealing has low overhead when work items are large, but SAT cubes can be small, so the granularity must be tuned. If cubes are too small, the overhead of stealing and managing them dominates; if they are too large, load imbalance returns. Dynamic splitting helps by allowing workers to create new work items on the fly, but it also creates a feedback loop: a worker that splits a cube produces new work, which may be stolen by others, which changes the load pattern. Tuning this loop is more art than science.

Memory is the second hurdle. A CDCL solver's memory footprint is dominated by the clause database, which grows with learned clauses. In a portfolio without clause sharing, each solver's database grows independently, and the aggregate memory is the sum. With clause sharing, the aggregate memory can be larger because clauses are replicated across solvers. In cube-and-conquer, each worker's database is local to its cube, so the aggregate memory is roughly the sum of the workers' databases plus a shared copy of the original formula. For large instances, the original formula alone can be hundreds of megabytes or several gigabytes. Replicating it per core is infeasible, so shared-memory solvers use a single read-only copy and only keep learned clauses locally. Distributed solvers must send the formula to each node, which can take minutes or hours over a slow network. Some systems use a compressed representation and decompress on each node, trading CPU time for bandwidth.

Clause deletion interacts with memory in a way that is easy to overlook. In a sequential solver, deletion is a local decision: the solver deletes clauses it believes are unlikely to be useful. In a parallel portfolio with clause sharing, deletion is still local, but the shared clauses that a solver imports are not under its control. If another solver keeps generating and sharing clauses, the receiving solver's database grows even if it deletes its own clauses aggressively. The only way to bound memory is to limit the rate of sharing or to impose a global cap on the number of shared clauses. Some solvers implement a shared clause pool with a fixed size and a replacement policy, but that requires synchronization on every import. The common approach is to accept the memory growth and rely on the operating system's virtual memory, which works until it doesn't. At scale, memory exhaustion is a real failure mode, and solvers that run for days must be designed to keep their footprint stable.

Reproducibility is the third hurdle, and it is often ignored until it bites. Parallel SAT solvers are inherently non-deterministic. The order in which clauses are shared, the timing of work stealing, the scheduling of threads on cores, and the latency of network messages all affect the search trajectory. Two runs of the same solver on the same instance with the same number of cores can produce different results, different runtimes, and even different learned clauses. For competition purposes, this is usually acceptable, because the answer (SAT or UNSAT) is checked independently. But for proof logging, it is a serious problem. If the solver is expected to produce a proof of unsatisfiability — a DRAT proof, for example — the proof must be checkable by a deterministic verifier. A non-deterministic proof is still checkable if all learned clauses and deletions are recorded in the correct order, but generating such a proof in a parallel setting requires a global ordering of events. Some solvers use a central proof logger that serializes all clause additions and deletions, but this can become a bottleneck. Others have each worker produce a local proof and then merge the proofs, which is non-trivial because clauses may be shared across workers. The current state of the art is that parallel proof logging is possible but expensive, and many parallel solvers simply disable proof logging or run in a mode that sacrifices parallelism for reproducibility.

The limits of parallel CDCL are therefore not just theoretical. Amdahl's law applies to the sequential parts of the solver — conflict analysis, propagation, heuristic updates — but the coarse-grained parallelism of portfolios and cube-and-conquer avoids most of those. The real limits are the ones we have discussed: imperfect load balancing, communication overhead, memory bandwidth, and the fact that some instances have a hard core that resists partitioning. Empirically, parallel SAT solvers often achieve speedups of 10x to 50x on 100 cores, not 100x. For some instances, the speedup is much worse; for a few, it is better, especially when the portfolio effect kicks in. The takeaway is that parallelism in SAT is not a free lunch. It is a carefully engineered trade-off between coordination and independence, and the best design depends on the instance, the hardware, and the correctness requirements.

## Diversification in Portfolios: More Than Random Seeds

The portfolio effect depends on the members actually exploring different regions of the search space. If all members run the same heuristic with different random seeds, they will still be correlated: the random seed affects tie-breaking and initial polarity, but the core search strategy is identical. The most effective portfolios diversify along axes that change the qualitative behavior of the solver, not just the noise.

The branching heuristic is the most impactful axis. VSIDS (Variable State Independent Decaying Sum) maintains an activity score per variable, bumped when the variable appears in a conflict and decayed periodically. VMTF (Variable Move To Front) uses a queue and moves variables to the front when they are involved in conflicts. LRB (Learning Rate Branching) uses a different signal: the rate at which a variable's assignment leads to conflicts. These heuristics have different biases: VSIDS tends to focus on variables that appear in many conflicts, VMTF is more reactive, and LRB emphasizes variables that are 'learning-relevant'. Running one solver with VSIDS, another with VMTF, and a third with LRB produces genuinely different trajectories, even on the same formula.

Phase saving is another axis. A solver that saves the last assigned polarity for each variable will tend to revisit the same region of the search space after a restart. A solver that randomizes polarity on restarts will explore differently. Some portfolios include one member with aggressive phase saving and another with random phases. The difference is most pronounced on satisfiable instances, where finding a solution is a matter of hitting the right assignment.

Restart schedules also matter. Luby restarts are universal and have good theoretical properties; glucose-style restarts adapt to the recent conflict rate; dynamic restarts based on the moving average of LBD are common in modern solvers. Two solvers with different restart schedules will spend different amounts of time in different parts of the search space. A portfolio might include one solver with frequent restarts (good for heavy-tailed satisfiable instances) and one with infrequent restarts (good for unsatisfiable instances where deep search is needed).

Clause deletion policies are a fourth axis. A solver that keeps learned clauses aggressively will have a large database and slow propagation but may benefit from long-term learning. A solver that deletes aggressively will have fast propagation but may forget useful clauses. The optimal policy depends on the instance, so a portfolio can hedge by including both.

The design question is how many members to include and how to choose them. In practice, portfolios of 4 to 16 members are common. Beyond that, the marginal benefit of another member diminishes, and the memory cost grows linearly. Some systems use algorithm selection offline: they run a set of solvers on a training set, learn which solver is best for which instance features, and then at runtime run only the top few. In a parallel setting, algorithm selection is less necessary because you can run all of them and take the first to finish. But even in parallel, running 64 copies of the same solver with different seeds is usually worse than running 16 distinct configurations with 4 seeds each. The reason is that the heavy-tail benefit saturates: once you have a few independent samples, the expected minimum runtime is dominated by the best configuration, not by the number of seeds.

There is a subtlety about correlated failures. If all portfolio members share the same clause database (via clause sharing), they are no longer independent. A bad clause shared by one member can pollute the others, reducing diversity. This is why some portfolios limit sharing to a subset of members or use a 'gossip' protocol where only a fraction of clauses are exchanged. The trade-off is between the benefit of sharing useful clauses and the cost of homogenizing the portfolio.

## The Tiered Clause Database and Adaptive Sharing Policies

In a sequential CDCL solver, the clause database is often organized into tiers. The 'core' tier contains clauses with very low LBD (typically 2 or 3). These are the glue clauses that capture the essential structure of the problem. The 'tier2' tier contains clauses with moderate LBD (up to 6 or 8). The 'local' tier contains the rest, which are candidates for deletion. The tiers are used to guide deletion: core clauses are never deleted, tier2 clauses are deleted only under memory pressure, and local clauses are deleted aggressively.

In a parallel solver, the tier structure becomes a natural basis for sharing. Instead of sharing all learned clauses, a solver can share only core clauses, or core plus tier2. This reduces the communication volume and the risk of polluting other solvers with low-quality clauses. The LBD threshold for sharing can be set independently of the deletion threshold. For example, a solver might share clauses with LBD <= 4 but keep clauses with LBD <= 8 in its local database. The shared clauses are a subset of the learned clauses, chosen for their likely global utility.

Adaptive sharing policies adjust the threshold based on feedback. A simple policy is to monitor the 'import success rate': the fraction of imported clauses that later participate in a conflict. If the rate is high, the threshold can be relaxed to share more clauses. If the rate is low, the threshold is tightened. The feedback loop must be damped to avoid oscillation. Some solvers use a moving average over a window of recent imports. Others use a more direct signal: the number of conflicts per second. If sharing is helping, the conflict rate should increase (because the solver is pruning more). If sharing is hurting, the conflict rate may drop because the solver is spending time propagating useless clauses.

Another adaptive dimension is the sharing frequency. Instead of sharing at every restart, a solver can share when its export buffer reaches a certain size, or when a timer expires. The optimal frequency depends on the communication medium. In shared memory, frequent small exchanges are cheap. In distributed memory, batching is essential. Some distributed solvers use a 'push-pull' model: each solver periodically pushes its best clauses to a central server and pulls clauses from other solvers. The server can filter and deduplicate, reducing the load on individual solvers. The central server becomes a bottleneck at large scale, so hierarchical or peer-to-peer topologies are used instead.

Duplicate detection is a significant cost. When a clause is imported, the solver must check whether it already has that clause. A hash table of clause signatures (e.g., a 64-bit hash of the literals) is the standard approach. The hash table must be updated whenever a clause is learned or deleted. In a parallel setting, the hash table is local to each solver, so duplicate detection is local. But a clause that is shared by multiple solvers may be imported multiple times by the same solver if it was learned, deleted, and then re-imported. To prevent this, some solvers keep a 'shared clause filter' — a Bloom filter or a compact hash set of clauses that have already been imported. The filter has a false positive rate, so occasionally a useful clause is rejected. The trade-off is between memory for the filter and the cost of duplicate propagation.

Clause sharing also interacts with the two-watched-literal scheme. When a clause is imported, it must be inserted into the watch lists for its two watched literals. This is a local operation, but it can be expensive if the clause is long. For this reason, many solvers share only short clauses (length <= 8 or so) in addition to the LBD filter. Unit and binary clauses are always shared because they are cheap and very useful.

The final piece of the policy is what to do when the shared clause buffer is full. A bounded buffer with a replacement policy (e.g., drop the oldest or the highest LBD) keeps memory in check. Some solvers use a ring buffer and overwrite old clauses. Others use a priority queue keyed by LBD. The choice affects the quality of the shared clauses: a priority queue ensures that only the best clauses are kept, but it requires synchronization on every insertion. A ring buffer is lock-free but may discard useful clauses. In practice, a simple bounded queue with a mutex is often sufficient, because the sharing rate is low enough that contention is not a problem.

## Hardware Realities: NUMA, Cache, and the Memory Wall

Parallel SAT solvers are memory-bound, not compute-bound. The inner loop of unit propagation is a sequence of pointer dereferences and bit operations. The arithmetic intensity is very low: a few operations per memory access. This means that adding cores does not help if the memory bandwidth is already saturated. On a typical server, a single core can consume a significant fraction of the available bandwidth when running a SAT solver. Running 64 cores on the same socket will not achieve 64x speedup; it may achieve 10x or 20x, and the rest is lost to memory contention.

NUMA (Non-Uniform Memory Access) makes this worse. On a multi-socket system, each socket has its own memory controller and local memory. A core on socket 0 can access memory on socket 1, but at a higher latency and lower bandwidth. If a parallel solver allocates all its memory on one socket and runs threads on both, the remote threads will be slow. The solution is to pin threads to cores and allocate memory locally. In a shared-memory solver, each worker should have its own local clause database allocated on the same NUMA node as the thread. The original formula can be replicated per socket or stored in a shared read-only region with interleaved allocation. Thread pinning is essential: without it, the operating system may migrate threads between sockets, causing unpredictable performance.

Cache coherence is another source of overhead. Shared clause buffers and atomic counters generate coherence traffic. Every time a solver exports a clause, it writes to a shared buffer, which invalidates the cache line in other cores. If many cores are exporting frequently, the coherence traffic can dominate. The solution is to batch exports and use per-core buffers that are flushed periodically. Lock-free queues help, but they still generate atomic operations on shared cache lines. Some solvers use a 'gossip' approach where each core writes to its own buffer and other cores read from it at intervals, avoiding write contention.

Hyper-threading is usually harmful for SAT solvers. Two logical cores sharing a physical core compete for the same execution units and memory bandwidth. Since the solver is memory-bound, the second logical core adds little throughput and can even slow down the first by increasing cache pressure. Most high-performance parallel SAT solvers recommend disabling hyper-threading or using only one thread per physical core.

In distributed memory, the network is the bottleneck. Sending a clause over a network involves serialization, kernel calls, and latency. The bandwidth of a typical InfiniBand or Ethernet network is much lower than shared memory. Therefore, distributed solvers must be frugal. They share fewer clauses, batch them into larger messages, and use compression. Some systems use a central clause server that aggregates and filters clauses before broadcasting. The server can also deduplicate, reducing the volume. The latency of the network means that sharing intervals are measured in seconds, not milliseconds. This reduces the coupling between solvers, but it also reduces the benefit of sharing.

GPUs are an attractive target because they offer massive parallelism and high memory bandwidth. However, SAT solving is a poor fit for the SIMT (Single Instruction, Multiple Thread) model. Unit propagation involves irregular control flow: different threads take different branches, and the memory access patterns are unpredictable. GPUs perform best when all threads execute the same instruction and access contiguous memory. SAT solvers do neither. There have been attempts to port CDCL to GPUs, but they typically achieve speedups only on specific subproblems, such as parallel propagation for a fixed assignment. The general CDCL loop remains on the CPU. Some hybrid systems use the GPU for preprocessing or for parallel lookahead, but the core search is still sequential or coarse-grained parallel on CPUs.

The memory wall also affects the choice of data structures. A solver that uses compact representations (e.g., bit-packed literals, implicit watch lists) will have better cache behavior and lower bandwidth requirements. This is why modern solvers pay attention to memory layout: separating hot and cold data, using arrays instead of linked lists, and avoiding pointer chasing. In a parallel setting, these optimizations are even more important because they reduce the pressure on the shared memory subsystem.

## Proof Logging and Certification Under Parallelism

Sequential CDCL solvers can emit a proof of unsatisfiability as they run. The standard format is DRAT (Deletion Resolution Asymmetric Tautology), which records every learned clause and every clause deletion. A deterministic checker replays the proof, verifying that each added clause is a RAT or RUP consequence of the clauses currently in the database. For a parallel solver, the proof problem is not just about generating clauses; it is about establishing a global order in which the checker can verify them.

In a portfolio, each worker learns clauses independently. If worker A learns clause C and shares it with worker B, B may use C in a later conflict analysis. The final proof must therefore contain C before B's use of it. If each worker writes its own proof stream, the streams must be merged in a way that respects these cross-worker dependencies. A simple approach is a central proof logger: every worker sends its learned clauses and deletions to a single thread, which assigns a global sequence number and writes them to disk. This guarantees a linear order, but the logger becomes a serialization point. On a 64-core machine, the logger can easily become the bottleneck, especially if clause sharing is frequent. Batching helps: workers buffer clauses and send them in chunks, and the logger writes them in the order received. The resulting proof is valid as long as the order within each worker is preserved and shared clauses are logged before they are imported.

A more scalable design is to give each clause a globally unique identifier and to record dependencies. When worker B imports clause C from worker A, B records that its subsequent learned clauses depend on C. The proof merger then builds a directed acyclic graph of clause dependencies and topologically sorts it. This avoids a central bottleneck but requires each worker to track provenance. Provenance tracking is cheap for shared clauses (just the clause ID) but can become expensive if every learned clause must record its antecedents. In practice, only shared clauses need global IDs; local clauses can be numbered per worker and merged later.

Cube-and-conquer adds a twist. Each worker solves under a cube, which is a conjunction of assumptions. A clause learned under those assumptions is not implied by the original formula alone; it is implied by the formula plus the cube. If such a clause is shared with a worker solving a different cube, it is unsound to use it without also importing the cube's assumptions. Proof logging must therefore track the assumption context of every shared clause. The standard solution is to disable clause sharing in cube-and-conquer, or to share only clauses that are independent of the cube. A clause is independent if its derivation does not use any cube literal as a decision. Operationally, this means the clause does not contain the negation of any cube literal and was learned at a decision level below the cube's decisions. Checking this condition is cheap, but it filters out most learned clauses, so the benefit of sharing is small.

For UNSAT proofs, cube-and-conquer produces one proof per cube: a derivation that the cube's assumptions lead to a conflict. To assemble a global proof, the solver must combine these local proofs. One way is to extract from each cube proof the clause that is the negation of the cube (a disjunction of negated cube literals). Each such clause is implied by the original formula. Since the cubes are exhaustive, the set of these clauses is unsatisfiable. A final proof step then resolves them along the cube tree to derive the empty clause. This final resolution can be done by a deterministic checker or by a small sequential solver. The local proofs can be checked independently, which is attractive for parallel verification. The catch is that extracting the negation clause from a DRAT proof is not always straightforward; the proof may use assumptions in ways that do not directly yield the clause. Some tools use LRAT (Linear RAT) proofs, which include explicit hints for each resolution step, making it easier to extract the final clause. Generating LRAT proofs in parallel is harder because the hints depend on the exact propagation order, which is affected by clause sharing. As a result, parallel LRAT generation is an active research area, and most parallel solvers that need proofs fall back to a central logger or run a sequential proof-producing phase after the parallel search finds a candidate answer.

## Determinism, Reproducibility, and Replay

Parallel SAT solvers are nondeterministic by default. The sources of nondeterminism are easy to list: thread scheduling, the timing of clause sharing, the order in which work items are stolen, network latency in distributed settings, and even memory allocation patterns that affect cache behavior and thus the order of conflicts. Two runs with the same input and the same number of cores can produce different learned clauses, different runtimes, and different search trajectories. For the final answer, this is usually harmless: SAT is checked by evaluating the model, and UNSAT is checked by a proof. But for debugging, for incremental solving, and for scientific reproducibility, nondeterminism is a problem.

Deterministic parallel SAT is possible but costly. One approach is to impose a fixed schedule: all workers run in lockstep for a fixed number of conflicts, then synchronize at a barrier, then exchange clauses in a deterministic order (e.g., sorted by clause ID). Work stealing is replaced by a static assignment of cubes or by a deterministic round-robin allocation. This eliminates most nondeterminism, but barriers cause idle time when workers have different speeds. The performance loss can be substantial, especially on heterogeneous hardware. A less restrictive approach is to make only the clause sharing deterministic while leaving the search asynchronous. Workers still run independently, but they exchange clauses only at fixed intervals and in a fixed order. The search trajectories can still diverge because the timing of imports affects when clauses are used, but the set of shared clauses is deterministic. This is often enough for proof logging, because the proof only needs to be valid, not identical across runs.

Another approach is record and replay. The solver runs nondeterministically, but every nondeterministic event is logged: which clause was shared, which worker imported it, which work item was stolen, and when. A replay tool can then reproduce the exact run by feeding the events back to the solver. This is useful for debugging a rare failure, but it does not make the solver deterministic in production. The log can be large, especially if clause sharing is frequent. Compression helps, but the overhead is significant.

Floating-point arithmetic is a subtle source of nondeterminism. Many CDCL heuristics use floating-point activity scores. VSIDS, for example, bumps variable activities by a floating-point value and periodically multiplies all activities by a decay factor. If multiple threads update a shared activity array, the order of updates matters because floating-point addition is not associative. Even with atomic operations, the result depends on the interleaving. To avoid this, parallel solvers often use per-thread activity arrays and merge them only at synchronization points, or they use integer scores with fixed-point arithmetic. Integer scores are deterministic if the update order is fixed, but they can overflow, so they must be rescaled periodically. The rescaling must also be deterministic. Some solvers use 64-bit integers and a decay factor that is a power of two, so rescaling is a bit shift. This makes the heuristic fully deterministic regardless of update order, as long as the set of updates is the same.

Reproducibility in competitions is a different matter. The SAT Competition requires that UNSAT answers be accompanied by a proof, but it does not require that the proof be identical across runs. The proof checker is deterministic, so any valid proof is accepted. The competition also runs solvers on a fixed hardware configuration, but the operating system and background processes can introduce timing variations. For the parallel track, solvers are allowed to use a fixed number of cores, and the results are compared by runtime. Nondeterminism means that a solver's ranking can vary from run to run, which is why competitions often run multiple instances or use a timeout. Some competitions have experimented with deterministic parallel tracks, but they are not standard.

Incremental solving is where determinism matters most. Many applications, such as bounded model checking, call a SAT solver repeatedly on related formulas. The solver keeps its learned clauses between calls to speed up subsequent solving. If the parallel solver is nondeterministic, the learned clauses from one call may differ, which affects the next call's performance. This can lead to unpredictable behavior, making it hard to tune the overall verification flow. Some incremental parallel solvers use a deterministic clause sharing policy and a fixed number of workers to keep behavior stable. Others simply disable parallelism for incremental solving, using a sequential solver for the incremental part and a parallel solver for the final hard check.

## Parallel Preprocessing and Inprocessing

Preprocessing is the phase before search where the solver simplifies the formula using techniques like bounded variable elimination, subsumption, self-subsuming resolution, and blocked clause elimination. These techniques are powerful; on some instances they solve the formula outright. Parallelizing them is attractive but tricky because they are not independent. Eliminating a variable removes all clauses containing it and adds resolvents. Those resolvents may enable further eliminations. If two threads try to eliminate variables that share clauses, they can conflict. The standard solution is to use a worklist with locks: each variable is claimed by a thread, and the thread locks the clauses it needs. This limits parallelism because the formula is a shared data structure with many dependencies. For large formulas, the memory bandwidth becomes the bottleneck. Some systems partition the formula into independent components, preprocess each component in parallel, and then merge. Component analysis is itself a preprocessing step, and it often finds many small components that can be simplified independently. The speedup is limited by the largest component, which may be most of the formula.

Inprocessing is the application of similar simplifications during search. In a parallel portfolio, each solver performs its own inprocessing on its local clause database. This is naturally parallel because the databases are separate. However, the results cannot be shared easily. If one solver eliminates a variable, it cannot tell other solvers to do the same, because they may be using that variable in their own search. Sharing simplified clauses is possible, but sharing variable eliminations would require all solvers to agree on the elimination, which is a synchronization point. Most parallel solvers keep inprocessing local. This means that each solver may rediscover the same simplifications, but the cost is usually small compared to the search.

Parallel lookahead is a special case where parallelism is natural. A lookahead solver evaluates candidate variables by assigning them and performing unit propagation. Each candidate evaluation is independent, so they can be done in parallel. The results are combined to choose the variable that maximizes propagation. The number of candidates is typically the number of unassigned variables, which can be large, but the solver usually only evaluates a subset (e.g., the variables with the highest activity). The parallelism is limited by the number of candidates evaluated, which is often tens or hundreds. For large instances, each propagation can be expensive, so parallel lookahead can provide a modest speedup. The main challenge is load balancing: some candidates may trigger much more propagation than others. Dynamic scheduling helps, but the lookahead phase is usually short relative to the CDCL phase, so the overall impact is small.

## Deployment at Scale: Faults, Stragglers, and Cost

Running a parallel SAT solver on a cluster or in the cloud introduces practical concerns that do not appear on a single machine. The first is fault tolerance. A long run on hundreds of cores may last days, and node failures are not rare. In a portfolio, a failed worker is simply lost; the remaining workers continue, and the portfolio still returns the correct answer if any worker finishes. The lost work is the progress of that worker, which may be significant if it was close to a solution. Some systems use checkpointing to recover, but checkpointing a CDCL solver is expensive because the state includes the clause database, the trail, the watch lists, and the heuristic scores. Serializing this state to disk can take minutes and produce gigabytes of data. For cube-and-conquer, fault tolerance is easier: each cube is independent, so a failed worker's cube can be reassigned to another worker. The progress on that cube is lost, but if cubes are small, the loss is bounded. If cubes are large, the loss can be substantial. Dynamic splitting reduces the risk by keeping cubes small.

Stragglers are a related problem. In a heterogeneous cluster, some nodes are slower due to CPU throttling, network congestion, or noisy neighbors. In a portfolio, stragglers do not matter because the first worker to finish determines the answer. In cube-and-conquer, a straggler can delay the completion of a cube. Work stealing helps: if a worker is slow, other workers can steal its cubes. But if the cube is large and cannot be split further, the straggler becomes the bottleneck. Dynamic splitting can break the cube into smaller pieces, but if the cube represents a genuinely hard subproblem, splitting may not help. The solution is to over-decompose: generate many more cubes than workers, so that the probability of a single cube dominating the runtime is low. This is the same strategy used in load balancing, but it also mitigates stragglers.

Cost is the final consideration. Cloud instances are priced per hour, so running 1000 cores for a day can cost thousands of dollars. The cost-effectiveness depends on the value of the answer. For a one-off verification problem, it may be worth it. For a routine check, a sequential solver or a small parallel run is more economical. Spot instances can reduce cost by 70% or more, but they can be preempted with little warning. Checkpointing is essential for spot instances, but as noted, checkpointing a CDCL solver is hard. Cube-and-conquer is more amenable to spot instances because each cube can be restarted independently. Some systems use a hybrid: run a portfolio on reliable on-demand instances for the final answer, and use spot instances for preprocessing or for generating cubes.

Energy consumption is a secondary concern. Memory-bound SAT solvers consume a lot of power, and parallel runs consume proportionally more. The energy efficiency (solutions per joule) may be worse for parallel solvers because of coordination overhead and because idle cores still consume power. At data center scale, this can be significant. Some researchers have proposed energy-aware scheduling for SAT, but it is not yet standard practice.
