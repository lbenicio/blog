Parallel graph traversal looks deceptively simple. Breadth-first search is a textbook algorithm, and the parallel version appears to be a matter of distributing vertices across threads and letting each thread expand its share of the current level. In practice, irregular graph structure turns that straightforward plan into a sequence of engineering decisions about work distribution, synchronization frequency, memory layout, and the difference between doing less work and doing work in parallel.

A useful way to reason about those decisions is to stop thinking primarily in terms of vertices and start thinking in terms of frontiers. At each level of a breadth-first traversal, the active frontier is the set of vertices whose outgoing edges must be examined. The frontier may be a small fraction of the graph or nearly the entire graph. Its vertices may have uniform degree, or a few vertices may have degrees orders of magnitude larger than the rest. The next frontier is produced by discovering unvisited neighbors, which requires either atomic claims on a shared visited structure or a different traversal direction that avoids those claims altogether.

This article focuses on shared-memory parallel graph traversal on multicore CPUs, using compressed sparse row or compressed sparse column adjacency structures as the baseline representation. The same ideas appear in distributed and GPU settings, but the trade-offs change enough that treating them together would obscure the core mechanisms. The goal is not to present a single best implementation. The goal is to make the cost model explicit enough that implementation choices can be defended rather than copied.

## The frontier abstraction

Let G = (V, E) be a graph, with n = |V| and m = |E|. For an unweighted breadth-first traversal, each level has a frontier F, a set of vertices at the current distance from the source. A visited bitmap records which vertices have already been discovered. The traversal computes the next frontier F' by examining edges incident to F and claiming unvisited neighbors.

The top-down formulation is the familiar one. For each vertex u in F, inspect every neighbor v in N(u). If v has not been visited, mark it visited and append it to F'. In parallel, marking must be atomic or otherwise coordinated, because multiple frontier vertices may share the same unvisited neighbor. A compare-and-swap on a visited word is the usual primitive: the thread that successfully changes the bit from zero to one owns the discovery and appends v. The work performed is proportional to the sum of degrees of frontier vertices, written as m_F = sum over u in F of deg(u). This is work-efficient when the frontier is small, because the traversal touches only edges incident to active vertices.

The bottom-up formulation inverts the perspective. Instead of expanding frontier vertices, it scans unvisited vertices and asks whether any neighbor is in the frontier. For each unvisited vertex v, inspect N(v). If some neighbor u is in F, then v belongs to F'. The work is proportional to the sum of degrees of unvisited vertices, written as m_U = sum over v in U of deg(v), where U is the set of vertices not yet visited and not in F. That is usually much more work than expanding F when F is small. But bottom-up has an important property for large frontiers: it does not require atomic discovery claims on individual neighbors. A vertex can be marked as belonging to the next frontier by a local or thread-private write, and the frontier membership test is a bitmap lookup. The parallel formulation becomes a set of independent scans, followed by a merge or bitmap union.

The frontier abstraction matters because it separates correctness from scheduling. A level-synchronous BFS is correct if every vertex in F' is exactly the set of undiscovered vertices adjacent to F, and if visited marks are committed before the next level begins. How those checks are distributed across threads, how F' is materialized, and how the next level is balanced are implementation concerns. That separation is what makes it possible to switch traversal directions without changing the output semantics.

The cost model also needs to include memory behavior. A compressed sparse row adjacency structure stores neighbor identifiers contiguously per vertex, which is good for sequential scanning and prefetching. The visited bitmap is random access by neighbor identifier, which is bad for locality on large graphs. Top-down traversal therefore pays for random bitmap probes and possible atomic contention on hot vertices. Bottom-up traversal scans many adjacency lists that may not be needed, but its frontier membership tests can also be random. On large graphs, the traversal is often limited by memory bandwidth and cache misses rather than by arithmetic. That does not make asymptotic work irrelevant; it means that two formulations with the same asymptotic level cost can have very different constant factors and parallel scalability.

## Top-down and bottom-up traversal

A top-down step is naturally expressed as an edge-parallel loop over the frontier. If the frontier is stored as an array of vertex identifiers, a thread can take a contiguous block and expand each vertex in that block. The inner loop over N(u) is sequential for a given u, but different u values run concurrently. The visited test and claim are the only cross-thread communication. When the graph is sparse and the frontier is small, most claims succeed without contention, and the traversal does useful work proportional to the number of edges it examines.

The main weakness of top-down traversal appears when F is large. If a large fraction of the graph is in the frontier, expanding every edge incident to it may examine many edges that lead to already-visited vertices. The visited bitmap filters them, but the edge scans and random probes have already happened. Atomic claims also become more expensive because many threads compete on popular vertices. In a graph with a heavy-tailed degree distribution, a small number of high-degree vertices can generate a disproportionate number of claims and cache-line invalidations. The traversal is still correct, but its effective parallelism can collapse into contention on a few memory locations.

A bottom-up step addresses both problems, at the cost of scanning more edges. It partitions U, the unvisited vertices, across threads. Each thread scans the adjacency list of its assigned vertices and checks whether any neighbor is in F. The membership test uses a frontier bitmap, not the visited bitmap, because the question is whether a neighbor is in the current frontier. If a match is found, the thread marks the vertex as belonging to F'. There is no need to claim individual neighbors, because the decision is local to the unvisited vertex. Multiple threads may inspect the same frontier vertex through different unvisited vertices, but that is a read-only operation on the frontier bitmap.

The work-efficiency of bottom-up depends on early exit. A thread scanning N(v) can stop as soon as it finds a frontier neighbor, provided the implementation is structured to do so. That early exit is valuable for high-degree vertices, but it also introduces branch divergence and unpredictable loop lengths. If the adjacency list is stored in compressed sparse row form, the scan is still a contiguous read, and a vectorized membership test can be effective. The worst case is a vertex with many neighbors and no frontier neighbor: the thread scans the entire list and finds nothing. Those wasted scans are the price of avoiding atomic claims and of processing a larger candidate set.

Neither direction is universally better. Top-down is the right default while the frontier is a small fraction of the graph. Bottom-up becomes attractive when the frontier is large enough that most unvisited vertices are likely to have a frontier neighbor, and when the cost of atomic claims and repeated edge expansion exceeds the cost of scanning unvisited vertices. The transition is not a property of the algorithm's correctness; it is a performance heuristic. A direction-optimizing traversal keeps both implementations and changes direction at level boundaries. That simple structure is why the technique is widely applicable: the output is still a breadth-first traversal, but the execution strategy adapts to the shape of the level.

## Direction optimization as a cost decision

A common way to choose direction is to compare estimated edge work. Top-down work for the current level is m_F, the sum of degrees of frontier vertices. Bottom-up work is bounded by m_U, the sum of degrees of unvisited vertices. If m_F is much smaller than m_U, top-down is doing less work. If m_U is smaller, or if the two are close enough that bottom-up avoids costly atomics, bottom-up may win. In practice, implementations often use a simpler threshold based on frontier size relative to the number of unvisited vertices, but the degree-sum comparison is more faithful to the actual edge work and is only slightly more expensive to maintain.

The comparison should be made at level boundaries, before the next traversal step begins. A traversal can start top-down, switch to bottom-up when the frontier grows, and switch back when the frontier shrinks. Switching back is important for graphs that have a narrow frontier after a wide level. Without it, the traversal may remain in bottom-up mode and scan large portions of the unvisited graph even though only a few vertices are active. The decision rule therefore needs hysteresis or a clear cost comparison to avoid oscillating between directions on nearly equal estimates.

There is a subtler cost that the edge-work comparison does not capture: synchronization and contention. Top-down requires atomic discovery claims. Bottom-up requires a frontier bitmap and a way to collect or merge F'. If the graph has a few very high-degree vertices, top-down may spend more time contending on their neighbors than the edge count suggests. If the graph is nearly regular, the edge-work comparison is a better predictor. A production traversal may therefore combine the edge-work estimate with counters for failed atomic claims, frontier density, and the cost of the previous level. Those counters are not free, but they are level-granular and inexpensive relative to the traversal itself.

Direction optimization also changes the meaning of load balance. In top-down mode, work is distributed over frontier vertices, whose degree distribution may be extremely skewed. In bottom-up mode, work is distributed over unvisited vertices, which is often a larger and more uniform set, but it still contains high-degree vertices and early-exit behavior. A direction switch that reduces edge work can still produce a load-balancing problem if the work is assigned statically. The next section examines that interaction directly.

## Load balancing the irregular frontier

A static partition of the frontier into one contiguous range per thread is rarely adequate. Frontier vertices have different degrees, and a block of low-degree vertices can finish long before a block containing a few hubs. The resulting tail at the level barrier reduces parallel efficiency even if the total work is modest. The standard remedy is dynamic scheduling: maintain an atomic counter over the frontier array, and have each thread claim the next block of vertices when it finishes its current block. Block size is a trade-off. Small blocks improve balance but increase atomic overhead and reduce locality; large blocks reduce overhead but reintroduce imbalance. A common compromise is to use a block size large enough to amortize the counter and small enough that a single high-degree vertex does not dominate a block.

For bottom-up traversal, the same idea applies to the unvisited vertex array. The work per vertex is the scan of its adjacency list, with early exit. Static contiguous ranges are especially poor here because unvisited vertices are not ordered by degree and high-degree vertices are scattered. Dynamic block claiming over U is straightforward and usually improves tail behavior. If the graph is stored in compressed sparse row form, the adjacency lists are already ordered by vertex identifier, so contiguous blocks over U correspond to contiguous regions of the adjacency array. That locality is worth preserving; randomizing the work distribution can improve balance but damage prefetching.

There is a separate load-balancing question for the next frontier. Top-down traversal produces F' through atomic claims or per-thread append buffers. Per-thread buffers avoid contention on the next-frontier array, but they require a prefix sum and a copy to concatenate the buffers. The prefix sum is cheap relative to the traversal, and it gives a compact frontier array for the next level. Atomic append is simpler but can become a contention point when many vertices are discovered at once. The choice depends on the expected discovery rate and on whether the implementation already needs a barrier for the level transition.

Memory placement matters as much as scheduling. On a non-uniform memory access system, a frontier array allocated and first-touched by one thread may be remote for others. Per-thread buffers should be allocated on the node where the thread runs, and the concatenation step should avoid forcing every thread to read every remote buffer. The visited bitmap is shared and randomly accessed, so its page placement and cache-line layout matter. A bitmap that packs many vertices into a cache line reduces memory footprint but increases false sharing when threads claim neighboring bits. A byte-per-vertex visited array reduces bit manipulation and false sharing but increases memory traffic. Neither choice is universally right; the correct choice follows from the graph size, the number of threads, and the expected contention pattern.

The key point is that load balancing cannot be separated from traversal direction. Top-down mode balances edge expansion over frontier vertices. Bottom-up mode balances adjacency scans over unvisited vertices. A direction switch changes the work distribution, the memory access pattern, and the contention profile at the same time. Treating load balancing as a generic thread-pool configuration misses that interaction.

The next sections examine work-efficiency, contention, and memory layout at the level of individual cache lines, where many of the cost differences between the two directions become visible.

## Work-efficiency at cache-line granularity

Work-efficiency is often defined as the ratio of useful edge examinations to total edge examinations. That definition is necessary but incomplete on modern multicore CPUs. The unit of memory transfer is a cache line, typically 64 bytes, and the traversal's cost is often determined by how many cache lines it touches and how many of those touches are useful. Two traversals that examine the same number of edges can have very different memory behavior depending on whether those edges are contiguous in memory and whether the associated visited or frontier bits are packed into the same lines.

In a compressed sparse row representation, the adjacency list of a vertex is contiguous. When a thread expands a frontier vertex u, it reads deg(u) neighbor identifiers in sequence. If neighbor identifiers are 32-bit integers, a 64-byte cache line holds sixteen of them. The hardware prefetcher can recognize the sequential stream and bring subsequent lines into cache before they are needed. That part of top-down traversal is efficient. The inefficiency comes from the visited bitmap probe that follows each neighbor identifier. The bitmap is indexed by vertex identifier, and the frontier's neighbor identifiers are effectively random with respect to the bitmap. Each probe may touch a different cache line, and only one bit in that line is used. The result is a stream of random reads that the prefetcher cannot predict. On a large graph, those random reads can dominate the cost of the adjacency scan.

Bottom-up traversal changes the access pattern. It scans the adjacency lists of unvisited vertices, which are also contiguous. The membership test is against the frontier bitmap, again random. But there is a crucial difference: early exit. If the first few neighbors of an unvisited vertex are in the frontier, the thread stops scanning and marks the vertex. The random probes are limited to the prefix of the adjacency list that is actually examined. For a dense frontier, that prefix is short, and the total number of random probes can be much smaller than the number of edges in the unvisited set. For a sparse frontier, early exit rarely triggers, and the thread scans the entire list with no discovery. That is the worst case for bottom-up: many sequential reads and many random frontier bitmap probes for no useful result.

The cache-line cost model therefore depends on frontier density in a way that edge counts alone do not capture. Let d = |F| / |V| be the frontier density. In top-down mode, the expected number of edges examined per level is m_F. The expected number of random bitmap probes is also m_F, but each probe is independent. In bottom-up mode, the expected number of edges examined is at most m_U, but the expected number of vertices that find a frontier neighbor is at most |F'|. If the frontier is dense, the probability that a random unvisited vertex has a frontier neighbor is high, and early exit keeps the average scan length low. If the frontier is sparse, that probability is low, and the average scan length approaches the full degree. A direction heuristic that uses only m_F and m_U will switch to bottom-up when |F| is large, which is exactly when early exit is most effective. That alignment is not accidental; it is the reason direction optimization works.

There is also a question of cache-line utilization for the frontier itself. In top-down mode, the frontier is an array of vertex identifiers. A thread reading a block of that array uses every element, so the cache lines are fully utilized. In bottom-up mode, the frontier is a bitmap. A thread testing membership for a neighbor reads one bit from a cache line. If the frontier is dense, many bits in that line are set, but the thread still only uses one bit per probe. The line may be reused by subsequent probes if the neighbor identifiers are close, but that is not guaranteed. A frontier represented as a sorted array can improve locality for bottom-up if the adjacency lists are also sorted: the thread can merge the two sorted sequences and avoid random bitmap probes entirely. However, merging requires a linear scan of both sequences, which loses the early-exit benefit. The bitmap is a compromise that favors constant-time membership over locality.

Directed graphs add another dimension. Top-down traversal follows outgoing edges, so a compressed sparse row structure is the natural representation. Bottom-up traversal asks whether an unvisited vertex has an incoming edge from the frontier. If the graph is directed and only outgoing edges are stored, bottom-up cannot answer that question without scanning the frontier's outgoing edges, which is exactly the top-down work. The standard solution is to maintain a compressed sparse column structure for incoming edges, or to store the reverse graph. The reverse graph doubles memory, but it allows bottom-up traversal to scan the predecessors of unvisited vertices. The direction switch then also switches the adjacency structure. That switch has its own cache cost: the reverse graph may have a different degree distribution and different memory layout. On a graph where in-degrees and out-degrees are both skewed, the two structures can have very different cache behavior. A direction-optimizing implementation for directed graphs must therefore consider whether the reverse graph is available and whether the memory overhead is acceptable. If it is not, bottom-up can still be used in a restricted form, but the work-efficiency advantage may disappear.

## Contention and atomic operations

The cost of synchronization in top-down traversal is concentrated in the visited bitmap. When a thread discovers an unvisited neighbor, it must claim that vertex so that no other thread appends it to the next frontier. The usual primitive is a compare-and-swap on a machine word containing several visited bits. If the word is shared by many threads, the cache line ping-pongs between cores. Each successful claim invalidates the line in every other core's cache. The next claim on the same line must fetch it again. This is false sharing in the technical sense: the threads are not accessing the same bit, but they are accessing the same cache line.

The severity of the problem depends on the graph's degree distribution and the frontier's order. If the frontier is processed in arbitrary order, threads may claim vertices that are scattered across the bitmap, reducing false sharing. If the frontier is sorted by vertex identifier, adjacent frontier vertices may have adjacent neighbors, and claims can cluster on the same cache line. Sorting the frontier can improve locality for adjacency reads but worsen contention on the visited bitmap. That trade-off is rarely discussed, but it is visible in profiles. A common mitigation is to pad the visited bitmap so that each thread's claims are spread across different lines, but that increases memory footprint and reduces the benefit of packing. Another is to use per-thread visited buffers and merge them at the end of the level. Per-thread buffers eliminate contention entirely, but they require each thread to check both its own buffer and the global bitmap. The check against the global bitmap is still a read, and the merge is an extra pass over the discovered vertices. The merge can be done with a prefix sum and a parallel copy, which is work-efficient if the number of discoveries is large. If the number of discoveries is small, the merge overhead may exceed the contention it avoids.

Bottom-up traversal avoids atomic claims on individual neighbors because the decision to include an unvisited vertex in the next frontier is local to that vertex. Multiple threads may read the same frontier bitmap line, but reads do not invalidate the line. The only writes are to the next frontier structure. If the next frontier is a bitmap, each thread writes bits for the vertices it discovered. Those writes can still cause false sharing if two threads discover vertices whose bits share a cache line. The same padding and per-thread buffer techniques apply. If the next frontier is an array built with per-thread append buffers, the writes are to thread-local memory, and the only shared operation is the final concatenation. That concatenation is a prefix sum over per-thread counts, followed by a parallel copy. It is a level-granular operation and is usually negligible compared to the traversal.

The load-balancing counter used for dynamic scheduling is another shared location. If every thread claims a block by incrementing a single atomic counter, that counter becomes a serialization point. The contention is proportional to the number of blocks claimed, which is the frontier size divided by the block size. Choosing a larger block size reduces counter traffic but increases the tail. The counter can be sharded: each thread claims from a local counter and refills from the global counter in larger chunks. That reduces contention while preserving dynamic balance. The same technique applies to both top-down and bottom-up work distribution. The difference is that bottom-up work is over unvisited vertices, which are often more numerous and more uniform, so the counter traffic can be higher. A sharded counter or a hierarchical work-stealing deque may be necessary when the unvisited set is large.

## Memory placement and prefetching

On a non-uniform memory access system, the cost of a cache miss depends on which memory node serves it. The adjacency structure is read-only during the traversal, so it can be interleaved across memory controllers to maximize bandwidth. If the graph is allocated with first-touch policy and then traversed by threads on different nodes, each thread may read remote memory for most of its adjacency scans. Interleaving pages across nodes avoids that imbalance. The visited and frontier structures are written, so their placement affects both bandwidth and coherence. Per-thread buffers should be allocated on the node where the thread runs, and the thread should be pinned to that node. If threads migrate, the buffers become remote, and the prefix sum reads remote memory. Thread pinning is not always possible in a shared environment, but when it is, it removes a source of variance.

Prefetching is the main tool for hiding the latency of random bitmap probes. In top-down traversal, after loading a neighbor identifier, the thread can issue a prefetch for the visited bitmap line that contains the corresponding bit. The prefetch must be issued before the bit test, and the distance between the prefetch and the test must be large enough to cover memory latency. That requires unrolling the neighbor loop and prefetching several neighbors ahead. The prefetch instruction itself consumes bandwidth and issue slots, so it is only beneficial when the bitmap probes are likely to miss in cache. If the visited bitmap is small enough to fit in the last-level cache, prefetching adds overhead without benefit. The same applies to bottom-up traversal and the frontier bitmap. A runtime heuristic can enable prefetching only when the bitmap size exceeds the last-level cache capacity, or when hardware performance counters show a high miss rate.

Hardware prefetchers handle the sequential adjacency scan well, but they cannot handle the random bitmap probes. They also cannot handle the irregular access to the row offsets array when the frontier is processed in arbitrary order. If the frontier is sorted by vertex identifier, the row offsets are accessed in increasing order, and the hardware prefetcher can help. If the frontier is in discovery order, the row offsets are random. Sorting the frontier costs O(|F| log |F|) work, which may be significant for large frontiers. A bucket sort by high bits of the vertex identifier can approximate sorting with linear work and improve locality. The bucket boundaries can be chosen to match the size of the row offsets array or the NUMA node mapping. That is a level-granular optimization that fits naturally with direction switching: the same frontier array can be bucketed before either top-down or bottom-up processing.

Finally, the choice of data types affects memory traffic. Vertex identifiers are often stored as 32-bit integers, but graphs with more than 2^32 vertices require 64-bit identifiers. Doubling the identifier size doubles the adjacency memory traffic and halves the number of neighbors per cache line. If the graph fits in 32-bit identifiers, using 64-bit identifiers for convenience is a measurable performance loss. Similarly, the visited bitmap can use one bit per vertex, one byte per vertex, or one word per vertex. The bit-packed version minimizes memory footprint but requires bit manipulation and can cause false sharing. The byte version is simpler and avoids some bit operations, but it increases the bitmap size by a factor of eight. The word version is rarely justified unless atomic operations require word alignment. The right choice depends on the graph size, the number of threads, and the expected contention. Measuring the actual cache miss rate and coherence traffic is the only reliable way to decide.

These mechanisms—cache-line-aware work estimation, contention control, memory placement, and prefetching—interact with the direction decision. A traversal that switches direction without adjusting its memory layout may lose the benefit of the switch. The next part of the design space is how to combine these choices into a single traversal that remains work-efficient across levels and across graph shapes.

## Hybrid traversal pipelines

A direction-optimizing traversal is easiest to reason about as a pipeline with level-granular stages. The stages are: select direction, prepare the current frontier view, process edges or candidates, materialize the next frontier, and commit the visited state. The pipeline does not need to be implemented as separate passes over memory; the point of naming the stages is to expose where a direction switch changes the data structures and where work can be saved.

The current frontier has two possible views. The array view is a compact list of vertex identifiers. It is the natural input for top-down processing because a thread can claim a contiguous block of frontier vertices and expand their adjacency lists. The bitmap view is a dense membership structure. It is the natural input for bottom-up processing because an unvisited vertex needs a constant-time test for whether a neighbor is in the frontier. A hybrid traversal can maintain both views, but maintaining both costs memory and update time. A more economical approach is to maintain the view that the current direction needs and to convert only when the direction changes. The conversion is a level-granular operation, so its cost is amortized over the edges examined at that level.

The next frontier has the same two representations. Top-down processing naturally produces an array through per-thread append buffers or atomic append. Bottom-up processing can produce either a bitmap or an array. If the next level will also be bottom-up, producing a bitmap avoids a prefix sum and a compaction pass. If the next level will be top-down, producing an array avoids a full scan of the bitmap. The direction heuristic can therefore be applied one level ahead, or the traversal can produce the representation that is cheapest for the current level and convert at the next boundary. The latter is simpler and usually better because the direction decision is more accurate after the next frontier size is known.

The pipeline view also clarifies where synchronization is required. Top-down processing needs a shared visited structure with atomic claims. Bottom-up processing needs a shared frontier bitmap that is read-only during the level. Both need a barrier before the next level begins, because the next frontier must be complete before any thread starts processing it. The barrier is not an implementation detail to be eliminated casually; it is what makes the level-synchronous traversal correct. What can be reduced is the cost of the barrier and the amount of work that must finish before it.

## Frontier compaction and representation switching

Converting a frontier array to a bitmap is a scatter operation. Each thread takes a range of the array and sets the corresponding bit. If the bitmap is shared, the writes can cause false sharing when adjacent frontier vertices map to the same cache line. A per-thread bitmap shard or a padded layout reduces that contention. The scatter is work-efficient: it touches each frontier vertex once. The cost is small when the frontier is large, because the number of writes is proportional to the frontier size and the bitmap is likely to be reused for many membership tests.

Converting a bitmap to an array is a compaction operation. The naive method scans every word in the bitmap, extracts set bits, and appends their indices to a per-thread buffer. The scan cost is O(n / w) word operations, where w is the word size in bits. That is independent of the frontier size. If the frontier is dense, the scan is cheap relative to the number of set bits. If the frontier is sparse, the scan can dominate. A traversal that switches from bottom-up to top-down on a sparse frontier should avoid a full bitmap scan. One way is to keep the array produced by bottom-up processing. Bottom-up processing already visits the unvisited vertices and can append discovered vertices to per-thread buffers. That append is local and does not require atomic claims on individual neighbors. The resulting array can be used directly for the next top-down level, and the bitmap can be discarded or rebuilt only if the traversal switches back to bottom-up.

This suggests a symmetric representation policy. Top-down produces an array. Bottom-up produces an array as well, while using a bitmap for the current frontier. The bitmap is built from the current array when the direction switches to bottom-up. The next array is built during bottom-up processing through per-thread append buffers. The prefix sum over those buffers is the only global operation, and it is proportional to the number of discovered vertices. If the next frontier is dense, the prefix sum is large but the work is still proportional to useful discoveries. If the next frontier is sparse, the prefix sum is small. This policy avoids the O(n / w) bitmap scan at every direction switch. The cost is that bottom-up processing must write discovered vertices to buffers, which adds a store per discovery. That store is cheap compared to the random frontier bitmap probes that bottom-up already performs.

The choice between bitmap-first and array-first next frontiers depends on the expected number of discoveries. If the next frontier is expected to be a large fraction of the unvisited set, a bitmap is a compact representation and avoids the prefix sum. If the next frontier is expected to be small, an array is better because it can be used directly by top-down processing and because the prefix sum is cheap. A heuristic can compare the number of discoveries from the previous level to the number of unvisited vertices. If the ratio is high, produce a bitmap; if it is low, produce an array. The heuristic is level-granular and can be updated with a moving average.

## Reverse graphs and directed work estimates

For directed graphs, the direction decision is not symmetric. Top-down processing follows outgoing edges from the frontier. Bottom-up processing asks whether an unvisited vertex has an incoming edge from the frontier. If the graph is stored only in compressed sparse row form, bottom-up processing cannot answer that question without scanning the outgoing edges of the frontier, which is the same work as top-down. A reverse graph in compressed sparse column form, or an explicit transpose, is required for bottom-up processing. The transpose doubles the adjacency memory and the time to build it, but it enables a work-efficient bottom-up step.

The cost model for directed graphs must use the correct degree sums. Top-down work is the sum of out-degrees of frontier vertices. Bottom-up work is the sum of in-degrees of unvisited vertices. If the graph is not symmetric, these sums can differ by a large factor. A graph with a few high out-degree vertices and many low in-degree vertices may favor top-down even when the frontier is large, because bottom-up would scan many in-lists for little discovery. Conversely, a graph with high in-degree hubs may favor bottom-up because early exit finds a frontier predecessor quickly. The direction heuristic should therefore maintain both out-degree and in-degree sums, or at least the degree arrays needed to compute them incrementally.

Maintaining the reverse graph has its own locality cost. The compressed sparse column structure stores in-neighbors contiguously for each vertex. When bottom-up processing scans the in-list of an unvisited vertex, the scan is sequential, but the frontier bitmap probes are random. The transpose may have a different degree distribution from the original, so the cache behavior of bottom-up processing is not simply the mirror of top-down processing. On a NUMA system, the transpose may be allocated on different memory nodes, and interleaving both structures across nodes is necessary to avoid remote bandwidth bottlenecks.

If memory is too tight for a full transpose, a traversal can use a partial reverse graph. Vertices with in-degree below a threshold can be handled by scanning their in-lists, while high in-degree vertices are handled by a different mechanism. That mechanism might be a top-down expansion of the frontier into a temporary structure, or a compressed representation of the high-degree in-lists. Partial transposes trade memory for work-efficiency and add branching to the level loop. They are most useful when the graph has a few extreme hubs and the transpose would otherwise be dominated by those hubs.

## Scheduling granularity and barrier costs

A level-synchronous traversal has two scheduling granularities: the work within a level and the barrier between levels. Dynamic block claiming handles the first. The barrier handles the second. On a large multicore system, a centralized barrier can cost thousands of cycles, and the cost grows with the number of threads. A hierarchical barrier that synchronizes within a socket or NUMA node and then across nodes reduces that cost. The traversal can also use a sense-reversing barrier with a tree structure. The barrier is still a global synchronization point, but its latency is lower and more predictable.

The work distribution and the barrier interact. If the work is perfectly balanced, the barrier waits for the slowest thread, which is close to the average. If the work is imbalanced, the barrier waits for the longest block. Dynamic scheduling reduces the tail, but it also increases the number of atomic operations on the work counter. A sharded counter reduces that contention. Each thread claims a large chunk from the global counter and then distributes smaller blocks from its local chunk. The global counter is touched once per large chunk, and the local distribution is contention-free. The chunk size can be adapted to the observed tail: if the last block finishes much later than the average, the large chunk is too large; if the counter traffic is high, the large chunk is too small.

For bottom-up processing, the work is over unvisited vertices, which are often more numerous than frontier vertices. The same sharded counter applies, but the block size should be chosen with the early-exit behavior in mind. A block of unvisited vertices may contain a mix of vertices with short scans and long scans. Small blocks improve balance but increase counter traffic. A useful compromise is to sort the unvisited vertices by degree within each thread's chunk, so that long scans are grouped and can be stolen as a unit. That sorting is local and does not require a global reordering of the graph.

## Measurement-driven tuning

The direction heuristic, the block size, the prefetch distance, and the frontier representation are all parameters that depend on the graph, the machine, and the level. Hard-coded constants are a starting point, but a robust traversal should measure and adapt. The measurements are level-granular: edges examined, vertices discovered, atomic claim failures, cache misses, and time spent in each phase. These counters are cheap to collect if they are accumulated in thread-local variables and reduced at the barrier. The reduction is a small tree or a per-thread array read by one thread.

The direction decision should use hysteresis to avoid oscillation. If the estimated work for top-down and bottom-up is nearly equal, the traversal should stay in its current direction. A simple rule is to switch only when one direction is estimated to be cheaper by a factor of, say, 1.2 or 1.5. The factor can be tuned from the observed cost of the previous level. If the traversal switched and the level was slower than predicted, the threshold can be increased. If the traversal stayed and the level was slower than the alternative would have been, the threshold can be decreased. This is a form of online tuning that does not require a model of the machine.

The frontier representation can be tuned in the same way. If the traversal produced an array but the next level is bottom-up, it must build a bitmap. The cost of building the bitmap can be measured and compared to the cost of the alternative, which is to stay top-down for one more level. If the frontier is small, staying top-down may be cheaper than building a bitmap and switching. If the frontier is large, building the bitmap is amortized over many membership tests. The decision can be based on the frontier size and the measured scatter rate.

Measurement-driven tuning does not eliminate the need for a good cost model. It complements the model by correcting for machine-specific effects that are difficult to predict. The model says which direction is likely to do less work. The measurements say whether the implementation actually achieved that work reduction. Together, they make the traversal adaptive without making it unpredictable.

The next part of the design space is how these level-granular decisions interact with the graph's global structure, especially when the traversal is only one phase of a larger computation.

## Traversal state as an explicit object

A direction-optimizing traversal is more than a function that takes a graph and a source and returns distances. It carries state that spans levels and sometimes spans separate traversal phases. Making that state explicit is the difference between an implementation that is easy to reason about and one that allocates and resets structures at every boundary. The state includes the graph descriptors for forward and optional reverse adjacency, the visited structure, the current frontier in array and bitmap form, the pending unvisited work set used by bottom-up steps, per-thread discovery buffers, degree-sum accumulators, and the current direction mode.

Exposing this state does not mean exposing every internal buffer to callers. It means defining a small interface that separates preparation from stepping. Preparation binds a traversal to a graph, a source set, and an epoch. A step processes exactly one level and returns a handle to the new frontier. The handle can be queried for its size, its array view, and its bitmap view, with conversion performed lazily. This interface makes the level boundary visible to the code that drives the traversal, which is where direction decisions and phase transitions belong. It also prevents a common implementation mistake: hiding an allocation or a full bitmap clear inside the step function and then wondering why level times have a large constant component.

The state object should also record which structures are authoritative. After a top-down level, the next frontier is authoritative as an array; its bitmap may be stale or absent. After a bottom-up level, the next frontier may be authoritative as a bitmap and as a compact array produced by discovery buffers, depending on the construction policy. The visited structure is always authoritative. The pending unvisited set may be stale during top-down levels because top-down does not need it. Each of these invariants should be expressed in the interface, not left to comments. When a later phase asks for a bitmap that is absent, the object can build it and charge that cost to the phase that requested it. When a later phase asks for an array after a bitmap-producing step, the object can compact only the set bits that the previous step recorded, rather than scanning the entire bitmap.

This explicit-state approach also makes it possible to run several traversals concurrently without sharing mutable scratch. A traversal that uses a global visited bitmap cannot be nested safely. A traversal that owns an epoch-tagged visited array and per-thread buffers can be nested if memory allows, and it can be batched if the caller is willing to share the graph and a scheduler. The cost is memory proportional to the number of concurrent traversals. For many graph workloads, that cost is acceptable because the adjacency structure dominates memory and the visited structures are small by comparison. For large graphs with many small queries, batching is usually better than nesting.

## Multi-source traversals and batched components

Many practical traversals are not single-source. Connected-component labeling, reachability from a set of roots, and multi-seed propagation all start with several frontier vertices. A multi-source breadth-first traversal can be treated as a single traversal from a virtual super-source whose neighbors are the initial frontier. That formulation is useful because it preserves the level semantics: the first real level contains the sources themselves, and subsequent levels expand from them. The direction heuristic needs one adjustment. The initial frontier may already be a large fraction of the graph, so the traversal may begin in bottom-up mode. Starting top-down with a huge frontier can waste work before the first switch. The preparation step should compute the degree sum of the initial frontier and compare it with the degree sum of the complement before committing to a direction.

Duplicate source identifiers should be filtered during preparation. A source list that contains the same vertex twice would otherwise cause multiple claims in the first top-down level and could inflate the frontier. The cheapest filter depends on the source count. For a small source list, sorting and deduplicating is adequate. For a large list, a temporary epoch-tagged mark array can detect duplicates in linear time. The mark array can be the same structure used for visited state if the epoch is set before filtering, but mixing the two meanings makes the code harder to maintain. A separate temporary mark array that is reused across preparations is often clearer.

Connected-component labeling exposes a different issue: a graph may contain many components, and running a separate level-synchronous traversal for each component can be dominated by barriers. If the components are small, the traversal spends more time synchronizing than expanding edges. One response is to batch components. Each active component contributes its current frontier to a combined frontier, and each discovered vertex inherits the component label of the frontier vertex that discovered it. For undirected graphs, a union frontier bitmap is safe because two distinct active components cannot both be adjacent to the same unvisited vertex; that would imply the components are connected. A single membership test can therefore answer whether any active component is adjacent, and the label can be taken from the first frontier neighbor found.

For directed graphs, the same batching is not generally safe. Two different source sets can reach the same unvisited vertex through different directed paths, and the vertex would need multiple labels or a merge policy. Batching is still possible if the caller wants the union of reachable vertices rather than separate reachability sets, or if the algorithm can tolerate a deterministic label choice. The implementation must state which semantics it provides. A traversal that silently picks one label for a shared descendant is correct for union reachability and incorrect for per-source reachability.

Batched component traversal also changes the load-balancing picture. The combined frontier can be large even when each component is small, which reduces the relative cost of barriers. But the combined frontier can be heterogeneous: some components may have completed, while one component dominates the batch. The direction heuristic then makes a decision for the batch as a whole, not for each component. If the dominant component has a dense frontier, bottom-up is a good choice for the batch even though many small components are inactive. If the small components are numerous and their frontiers are sparse, their combined density may be low, and top-down may be better. A useful refinement is to retire completed components early and recompute the degree sums for the remaining active set. Retiring a component is a compaction over the active component list, which is cheap when the list is small. Recomputing the frontier degree sum is also cheap if each component maintains its own contribution incrementally.

A threshold should decide when batching is worth it. Very small components can be handled by a sequential traversal that avoids atomics and barriers entirely. The threshold can be based on the number of edges incident to the component or on the expected number of levels. Starting a sequential traversal has low fixed cost, and for a component with a handful of vertices it will beat a parallel level-synchronous traversal even on a large machine. The batched path is for the middle ground: components too large to finish trivially but too small to keep every thread busy on their own.

## Maintaining the unvisited work set

Bottom-up traversal derives its work estimate from the unvisited set, and its performance depends on scanning candidates that are actually unvisited. A lazy implementation checks the visited bitmap for every candidate and skips those already discovered. That check costs a random probe per candidate and defeats the purpose of maintaining a separate work set. An eager implementation removes discovered vertices from the pending array. The naive way to remove them is to scan the entire pending array at every level and filter out visited vertices. That scan is O(|U|) and may be comparable to the bottom-up work itself, especially when the frontier is small and few vertices are discovered.

The better approach is to integrate survivor compaction into the bottom-up scan. Each thread claims a block of the pending array and examines each vertex in the block. If the vertex is discovered, it is omitted from the survivor buffer. If it is not discovered, it is copied to the survivor buffer. The adjacency scan and the survivor write happen in the same pass. After all blocks finish, a prefix sum over survivor counts gives the new pending array. The cost is one extra store per surviving vertex and one prefix sum per level. The prefix sum is proportional to the number of blocks, not the number of vertices, if each block writes a count. The copy of survivors is proportional to the new pending size, which is work the traversal would have to do anyway if it maintains the set eagerly. This is work-efficient because every pending vertex is visited exactly once per bottom-up level.

Top-down levels do not scan the pending set, so compacting it during top-down would be wasted work. The pending array can be left stale while top-down is active. The degree-sum estimate for the unvisited set stays correct if the traversal subtracts the degrees of newly discovered vertices as they are claimed. When the traversal switches to bottom-up, it can compact the stale pending array once, or it can rely on the bottom-up scan to skip visited vertices and write only survivors. The latter is simpler and avoids a separate pass, but it means the first bottom-up level after a long top-down phase may scan some already visited vertices. The number of such vertices is bounded by the discoveries since the last compaction. If that number is large relative to the pending set, a compaction before entering bottom-up is worthwhile. If it is small, the lazy handling is cheaper.

The pending array should be ordered to preserve adjacency locality. In compressed sparse row form, vertices are numbered by row, and contiguous ranges of the pending array correspond to contiguous regions of the adjacency array only if the pending array is sorted by vertex identifier. The initial pending array is naturally sorted. Survivor compaction preserves the original order if each thread writes its survivors in the order it encountered them and the block prefix sum preserves block order. That order is worth keeping. Randomizing the pending array may improve load balance slightly, but it destroys the ability of the hardware prefetcher to follow the adjacency stream. A better way to improve balance is to use dynamic block claiming and, for high-degree vertices, split the adjacency scan into multiple tasks rather than reorder the entire set.

## Phase transitions and frontier handoff

When a traversal is part of a larger computation, the frontier often becomes the input to another phase. A reachability phase may produce a set of vertices that a later phase filters or ranks. A component-labeling phase may produce labels that a later phase uses to build a quotient graph. The traversal should support handoff without copying data unnecessarily. The cheapest handoff is an ownership transfer: the traversal returns its frontier buffer, and the caller becomes responsible for it. The traversal then allocates a new buffer for its next use. If the caller is a pipeline that alternates between traversal and another phase, a pool of frontier buffers with explicit ownership is usually better than a single buffer that is copied at every boundary.

The representation at handoff should match what the next phase needs. If the next phase will iterate over the vertices and read their adjacency lists, an array is the right representation. If the next phase needs constant-time membership tests, a bitmap is better. If both are needed, the traversal can expose a lazy pair: the array is built on first request, and the bitmap is built on first request, with a flag that records which representation is current. Building both eagerly wastes work when the next phase uses only one. The lazy pair also gives the caller a way to signal which representation will be needed, so the traversal can produce it directly at the end of the level instead of converting afterward.

Phase boundaries are natural places to reset per-level counters and to recompute direction estimates. They are also natural places to release scratch that will not be used. A top-down phase uses discovery buffers and atomic claim counters. A bottom-up phase uses survivor buffers and frontier bitmap construction. If the two phases are interleaved across levels, the scratch must persist. If the traversal is finished and a different algorithm will run next, the scratch can be returned to a pool. Reusing scratch across phases avoids allocation jitter, but it also means the scratch must be sized for the largest phase. A pool with a high-water mark and a policy for shrinking after a period of low use is a reasonable compromise.

## Work stealing, overdecomposition, and high-degree vertices

Dynamic block claiming is a centralized form of load balancing. It works well when the number of blocks is modest and the atomic counter is not a bottleneck. Work stealing is a decentralized alternative. The frontier or pending set is divided into many tasks, each small enough to balance but large enough to amortize scheduling. Each worker has a deque of tasks. When a worker finishes its own deque, it steals from another worker. Stealing is less frequent than block claiming, and the stolen task can be chosen to preserve locality. A worker can steal the oldest task from a victim, which tends to be a large contiguous chunk, while the victim consumes newer, smaller tasks. That policy reduces contention on the victim's deque and gives the thief a block with good adjacency locality.

Overdecomposition is necessary for work stealing to be effective. If there is exactly one task per thread, there is nothing to steal. The traversal should create several tasks per thread, but not so many that scheduling dominates. A common rule is to create four to eight tasks per thread for top-down frontier chunks and a similar number for bottom-up pending chunks. The best factor depends on the variance of vertex degrees. Graphs with heavy-tailed degree distributions need more tasks because a single high-degree vertex can dominate a chunk. Graphs with nearly uniform degrees need fewer tasks because the work is already balanced.

High-degree vertices deserve special treatment. A top-down task that contains one vertex with degree in the millions will not be balanced by splitting the vertex list, because the expensive unit is the vertex itself. The adjacency range of such a vertex can be split into several edge-parallel tasks. Each task examines a subrange of the neighbor list and performs the same visited test and atomic claim. The tasks are independent except for the shared visited structure. This is safe because the discovery of a neighbor is idempotent at the level of the set of discovered vertices: exactly one task can claim a given unvisited neighbor. The next frontier order may differ from the serial order, but breadth-first traversal does not require a particular order within a level. The traversal should record that it used edge splitting so that the next level can decide whether the extra task overhead was worthwhile.

Bottom-up traversal is harder to split within a single vertex because of early exit. If two tasks scan different subranges of the same adjacency list, one may find a frontier neighbor and set the vertex as discovered while the other continues scanning. The other task can check a per-vertex flag and stop, but the flag check adds overhead to every neighbor. For most graphs, the benefit is small because high-degree vertices are a minority of the pending set. A better policy is to keep one task per pending vertex in bottom-up mode, and to rely on dynamic claiming and survivor compaction for balance. If a single high-degree vertex dominates bottom-up time, the traversal can fall back to top-down for that level or use a specialized in-list scan that partitions the in-neighbors of that vertex rather than the candidate vertices.

## Reuse across traversals and epochs

A traversal library that is called many times on the same graph should not pay a full visited-structure clear for every call. Zeroing a bitmap of n bits costs O(n / 8) bytes of memory traffic, which is small compared with a dense traversal but can dominate a traversal that touches only a small part of the graph. An epoch-tagged visited array avoids the clear. Each vertex stores a 32-bit epoch value. A vertex is visited if its stored epoch equals the current traversal epoch. Starting a new traversal increments the epoch. The array is never cleared during normal operation. The cost is four bytes per vertex instead of one bit, and atomic claims become compare-and-swap operations on 32-bit words rather than bit operations. For small traversals on large graphs, the memory savings of a bitmap are less important than the avoided clear, and the epoch array is often faster. For dense traversals where the visited structure is randomly accessed, the larger array increases cache pressure. The choice should be made per workload, not globally.

The frontier bitmap cannot use the same epoch trick as cheaply because it is queried bit by bit. It can be cleared at the start of each level, or it can be rebuilt from the current frontier array by scattering set bits. Rebuilding is usually cheaper when the frontier is sparse. Clearing is cheaper when the frontier is dense and the bitmap is already large. The traversal can choose based on the ratio of frontier size to bitmap word count. The same reasoning applies to per-thread discovery buffers. They should be reused across levels, but only the used prefix should be read during the prefix sum. Zeroing the entire buffer is unnecessary and can waste bandwidth. The prefix sum over per-thread counts defines the live region.

Reuse also applies to the reverse graph and degree sums. If several traversals run on the same directed graph, the transpose should be built once and shared read-only. The degree sums for out-neighbors and in-neighbors can be precomputed per vertex and maintained in arrays. The direction heuristic then reads the sums for the current frontier and the unvisited set without touching the adjacency structure. If the graph is updated between traversals, the transpose and degree sums become invalid. A version number on the graph descriptor can detect that a cached transpose is stale. Updating the transpose incrementally is possible for edge insertions and deletions, but the update cost must be weighed against rebuilding. For small batches of updates, marking the transpose stale and rebuilding before the next traversal is often simpler and more predictable.

The traversal state object should therefore distinguish between graph-lifetime data and traversal-lifetime data. The transpose, degree arrays, and any vertex reordering are graph-lifetime. The visited epoch, frontier buffers, pending array, and per-thread scratch are traversal-lifetime. Mixing the two makes caching decisions opaque and invites use-after-free errors when a traversal outlives the graph descriptor. Keeping them separate also makes it possible to share graph-lifetime data among concurrent traversals while giving each traversal its own mutable state.
