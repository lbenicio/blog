# The Anatomy of a Parallel Sparse Cholesky Factorization: Elimination Trees, Supernodes, and Task Scheduling

Sparse Cholesky factorization is one of those computations that looks almost trivial on paper and becomes a systems problem the moment the matrix is large enough to matter. For a symmetric positive definite matrix A, the factorization A = L L^T is unique, numerically stable without pivoting, and the natural way to solve A x = b by forward and backward substitution. In dense linear algebra, the algorithm is a familiar sequence of blocked operations. In sparse linear algebra, the same equation hides a graph problem, a scheduling problem, a memory hierarchy problem, and a parallel programming problem inside one another.

This article is about the parallel sparse Cholesky factorization as it is actually built: symbolic analysis first, numeric factorization second, with an elimination tree and a supernodal DAG connecting the two. The goal is not to present a single optimal algorithm. There is no single optimal algorithm. The goal is to explain the assumptions that make the parallel structure possible, the trade-offs that determine whether a factorization runs at memory bandwidth or at a fraction of it, and the design decisions that separate a solver that scales from one that merely has many threads.

We will assume A is real, symmetric, positive definite, and sparse. We will assume the nonzero structure is static: the values may change, but the pattern does not. We will assume no numerical pivoting is required, which is the usual case for Cholesky. We will focus on direct factorization, not iterative methods. Direct methods are often chosen when robustness and predictable work matter more than memory, and they are the setting where elimination trees and supernodes are most visible.

## The Problem and the Shape of the Computation

A sparse Cholesky solver computes L such that A = L L^T, where L is lower triangular. If A is n by n and sparse, L is usually sparse too, but not as sparse as A. The extra nonzeros are called fill-in. Fill-in is the central fact of sparse direct factorization. It determines the operation count, the memory footprint, and the amount of parallelism available. A good ordering can reduce fill by orders of magnitude; a bad ordering can turn a sparse matrix into a dense one.

The computation has two phases. The symbolic phase analyzes the nonzero pattern of A and the chosen ordering. It computes the elimination tree, column counts, row counts, supernodes, and memory requirements. The numeric phase computes the actual floating-point values of L. If only the right-hand side changes, the symbolic phase is reused. If the matrix values change but the pattern stays the same, the symbolic phase is still reused. This separation is one of the most important engineering decisions in a sparse direct solver: symbolic analysis is combinatorial and branch-heavy; numeric factorization is floating-point heavy and can be built around dense kernels.

The ordering step is usually considered part of the symbolic phase, although it is logically separate. Ordering algorithms such as minimum degree, nested dissection, and hybrid methods reorder the matrix to reduce fill. The ordering also determines the shape of the elimination tree, which determines the parallel structure. This is the first major trade-off. Minimum degree often produces low fill and low operation counts, but it can produce deep, unbalanced elimination trees with limited tree parallelism. Nested dissection produces more fill and more operations in many cases, but it creates balanced separators and a more parallel tree. On a serial machine, minimum degree may win. On a parallel machine, nested dissection often wins despite doing more work, because the extra work is parallelizable and the critical path is shorter.

The numeric phase can be organized in several ways. Left-looking factorization computes one column or supernode at a time, gathering updates from previously computed columns. Right-looking factorization computes a column or supernode and immediately scatters updates to future columns. Multifrontal factorization organizes the computation around frontal matrices along the elimination tree, assembling and eliminating dense submatrices. Supernodal factorization groups columns with similar structure into dense blocks and uses BLAS-3 kernels. The distinctions matter because they change the granularity of tasks, the memory access patterns, and the synchronization strategy. In a parallel setting, the supernodal and multifrontal variants are usually preferred because they expose dense linear algebra and reduce the number of small, irregular operations.

The sparse Cholesky factorization is therefore not one algorithm. It is a family of algorithms parameterized by ordering, symbolic analysis, storage format, task granularity, and scheduling. The elimination tree is the common language that describes dependencies across all of them.

## Elimination Trees and the Dependency Structure

The elimination tree is the fundamental dependency graph of sparse Cholesky factorization. For a lower triangular factor L, the parent of column j is defined as the smallest row index i greater than j such that L(i, j) is nonzero. If no such i exists, j is a root. In a connected matrix with a proper ordering, the elimination tree is a single tree, but in general it is a forest.

The tree captures the flow of updates. If column j is an ancestor of column k, then the computation of column j depends on column k. Siblings in the tree are independent in the sense that neither depends on the other, although they may both update a common ancestor. The root of the tree is the last pivot, and it depends on all columns that reach it. The leaves are columns that depend on no earlier columns, so they can be computed first.

This definition is simple, but its consequences are deep. The elimination tree is not the graph of A. It is a transitive reduction of the dependencies induced by the factorization. It tells us the order in which columns can be eliminated without violating the numerical dependencies. It also tells us where fill-in occurs: if L(i, j) is nonzero, then j is an ancestor of i in the elimination tree. The tree can be computed in near-linear time from the nonzero pattern of A and the ordering, without any floating-point arithmetic.

The tree is also the basis for symbolic factorization. Given the elimination tree, we can compute the nonzero pattern of each column of L by traversing from each row to the root, stopping when we hit a previously visited node. This is the classic reachability formulation. The same tree gives column counts, which are the number of nonzeros in each column of L, and row counts, which are the number of nonzeros in each row. These counts determine memory allocation and help estimate the cost of the numeric factorization.

The elimination tree has a natural postordering. A postorder numbers the children of each node before the node itself. Postordering does not change the mathematical factorization, but it improves locality. In a postordered tree, the columns of a subtree are contiguous. This makes it easier to group columns into supernodes and to schedule subtree computations as contiguous blocks of work. Most sparse Cholesky implementations postorder the elimination tree before the numeric phase.

The tree also reveals the limits of parallelism. If the tree is a chain, then each column depends on the previous one, and there is no tree parallelism at all. If the tree is balanced, there are many independent subtrees and tree parallelism is abundant. The shape of the tree is determined by the ordering, not by the matrix alone. This is why ordering and parallel performance are inseparable.

A useful mental model is to separate two kinds of parallelism. Tree parallelism comes from independent subtrees in the elimination tree. Dense parallelism comes from the linear algebra inside a supernode or frontal matrix. A parallel sparse Cholesky solver must exploit both. If it only exploits tree parallelism, it will stall on large supernodes near the root. If it only exploits dense parallelism, it will waste the independent work in the leaves. The elimination tree tells us where tree parallelism lives; the supernode structure tells us where dense parallelism lives.

## Supernodes: From Columns to Dense Blocks

A supernode is a set of consecutive columns in the elimination tree that have the same nonzero structure below the diagonal, or nearly the same structure. In exact terms, a supernode is a maximal set of contiguous columns j, j+1, ..., j+k such that the nonzero pattern of column j is a subset of the pattern of column j+1, and so on, with the same row indices. In practice, implementations relax the exactness condition to allow small variations, because strict supernodes are rare in large matrices.

Supernodes matter because they turn sparse column operations into dense matrix operations. A supernode of width w and height h can be represented as a dense trapezoidal block. The update from one supernode to another becomes a dense matrix-matrix multiplication, typically a GEMM or SYRK. These operations are cache-friendly, vectorizable, and well-supported by optimized BLAS libraries. Without supernodes, sparse Cholesky is dominated by irregular memory access and small vector operations. With supernodes, it can approach the performance of dense linear algebra for the dense parts of the factor.

Supernodes also simplify the dependency graph. Instead of a tree of columns, we get a DAG of supernodes. The edges represent update dependencies: if supernode J updates supernode K, then K cannot be computed until J is complete. The elimination tree still gives a topological order, but the DAG can have additional edges because a supernode may update an ancestor that is not its immediate parent. In a multifrontal method, the dependency graph is often represented by the assembly tree, where each node assembles contributions from its children and sends a contribution to its parent. In a supernodal left-looking method, the dependency graph is represented by the update lists of each supernode.

The supernodal DAG is the object that a parallel scheduler actually sees. The nodes are tasks: factor a supernode, update a descendant, assemble a frontal matrix, or perform a dense triangular solve. The edges are dependencies. The scheduler must assign tasks to threads or processes while respecting the DAG. The quality of the schedule depends on the granularity of the tasks, the balance of the DAG, and the cost of synchronization and memory movement.

There is a tension between supernode size and parallelism. Large supernodes expose more dense parallelism inside each node, but they reduce the number of independent nodes in the DAG. Small supernodes increase tree parallelism, but they also increase overhead and reduce the efficiency of dense kernels. Most implementations use amalgamation: they merge small supernodes into larger ones when the benefit of a larger dense block outweighs the loss of tree parallelism. The amalgamation strategy is a tuning parameter, and it interacts with the ordering and the target hardware.

A second tension is between storage and computation. A supernode can be stored in a compressed sparse format, a dense rectangular block, or a hybrid. The choice affects memory traffic and the ability to use BLAS. In many solvers, the factor is stored as a collection of dense supernodal blocks, with an index structure that maps global row indices to positions within blocks. This layout is efficient for updates but can be expensive to construct and to traverse. The symbolic phase must therefore produce not only the supernode partition but also the row indices and block boundaries needed by the numeric phase.

The next sections will examine how the symbolic phase computes this structure, how the numeric phase turns it into floating-point work, and how schedulers map the resulting DAG onto modern parallel machines. For now, the key point is that the elimination tree and supernodes are not implementation details. They are the bridge between the graph structure of the matrix and the dense linear algebra that makes parallel Cholesky fast. The rest of the design follows from taking that bridge seriously: the symbolic phase must expose enough structure to schedule work, and the numeric phase must preserve enough locality to keep the memory system from becoming the bottleneck.

## Symbolic Analysis: From Pattern to Plan

The symbolic phase is where the solver decides what work exists. It takes the nonzero pattern of A and a permutation P, forms the permuted matrix A' = P A P^T, and computes the elimination tree, postorder, column counts, supernode partition, and memory layout. None of this requires floating-point values. That is the point: the combinatorial structure can be computed once and reused across many numeric factorizations, whether the values change slowly in a nonlinear solver or the same matrix is solved for many right-hand sides.

The first job is to build the elimination tree. A naive approach would perform symbolic factorization to discover the pattern of L and then read off the parent pointers, but that is unnecessary. Liu's algorithm computes the etree directly from the pattern of A' in near-linear time. The idea is to process columns left to right. For each column k, examine the row indices i > k in A'(:,k). For each such i, follow parent pointers from i toward the root until reaching a node that has already been assigned a parent, then set that node's parent to k. The path compression used in union-find makes the total cost effectively linear in the number of nonzeros. The resulting tree is independent of numerical values and depends only on the pattern and the ordering.

Postordering the etree is the next step. A postorder numbers each node after its children, so every subtree occupies a contiguous interval of columns. This contiguity is not mathematically necessary, but it is practically essential. It improves locality in the numeric phase, makes supernode detection a matter of scanning consecutive columns, and allows a subtree to be treated as a unit for scheduling. Depth-first search from the roots produces a postorder in linear time. Some implementations use a variant that also orders children by size, placing larger subtrees earlier to improve load balance.

Column counts come next. The column count of j is the number of nonzeros in L(:,j), including the diagonal. It is the single most important symbolic quantity for memory allocation. If column counts are known, the solver can allocate exactly the storage needed for the factor. The classic algorithm of Gilbert, Ng, and Peyton computes column counts from the etree and the pattern of A' without forming L. It uses the concept of the skeleton matrix and least common ancestors to count, for each row, how many columns it reaches. The result is a set of counts that sum to nnz(L). Row counts, the number of nonzeros in each row of L, can be computed similarly or by a transpose of the symbolic structure. Row counts matter for certain storage schemes and for estimating the cost of triangular solves.

Symbolic factorization proper computes the nonzero pattern of each column of L. Given the etree, the pattern of L(:,j) is the set of nodes on the paths from the row indices of A'(:,j) to j, excluding j itself. A depth-first traversal that stops at already visited nodes yields the pattern in time proportional to nnz(L). In practice, many solvers do not store the full pattern. They store column counts and supernode boundaries, and the numeric phase reconstructs row indices on the fly from the etree or from a compact row-index structure. This saves memory and avoids a costly symbolic factorization step, but it requires the numeric phase to have efficient access to the etree and to the original matrix pattern.

Supernode detection follows from the pattern. A fundamental supernode is a maximal set of consecutive columns j, j+1, ..., j+k such that for each column in the set, the parent in the etree is the next column, and the nonzero pattern of column j, excluding the diagonal, is identical to the pattern of column j+1. In terms of counts, this means parent(j) = j+1 and nnz(L(:,j)) = nnz(L(:,j+1)) + 1. The condition can be checked in one pass over the postordered columns. Fundamental supernodes are the largest possible without relaxing the identical-pattern requirement. In large matrices, however, many fundamental supernodes are tiny, often width one or two, because the pattern changes frequently near the leaves. Using them directly would produce too many small dense blocks and too much scheduling overhead.

Relaxed supernodes, or amalgamated supernodes, merge small fundamental supernodes into larger blocks. The merge may be exact, combining columns with similar but not identical patterns, or it may be approximate, padding the block with explicit zeros to make it rectangular. Amalgamation is guided by a cost model. A larger supernode increases the width of dense kernels, which improves the ratio of computation to memory traffic and makes BLAS more efficient. But it also increases fill-in if zeros are stored explicitly, and it reduces the number of independent tasks in the DAG. The usual strategy is to merge sibling supernodes in the etree when their combined width is below a threshold, or when the resulting block fits in a target cache level. Some solvers use a parameterized rule based on the number of floating-point operations saved versus the extra memory consumed. The optimal rule is hardware-dependent and problem-dependent, which is why supernode amalgamation remains a tuning knob rather than a solved problem.

The output of the symbolic phase is a plan. It includes the permutation, the etree, the postorder, the supernode partition, the row indices for each supernode, the column counts, and the total memory requirement. It may also include an estimated operation count and a predicted critical path. For a multifrontal solver, the plan includes the assembly tree and the sizes of frontal matrices. For a supernodal left-looking solver, it includes the update lists for each supernode. The plan is the interface between symbolic and numeric phases. A well-designed plan exposes enough structure for the scheduler to make good decisions without forcing the numeric phase to rediscover the same information.

Parallel symbolic analysis is possible but less developed than parallel numeric factorization. Ordering is the hardest part to parallelize because minimum degree and nested dissection involve global graph computations. Nested dissection can be parallelized by finding separators in parallel, but the top-level separators are inherently sequential. Etree construction, postordering, and column counts can be parallelized with parallel union-find or by processing independent subtrees. In practice, symbolic analysis is often left serial because it is a small fraction of the total time for a single factorization. That assumption breaks down when the numeric phase is extremely fast, as on GPUs, or when the symbolic phase is repeated many times in an interactive setting. In those cases, parallel symbolic analysis becomes worthwhile, and the algorithms are an active area of research.

## Numeric Factorization: Dense Kernels Inside a Sparse Skeleton

The numeric phase turns the symbolic plan into floating-point work. Its structure depends on the chosen variant. In a supernodal left-looking method, the solver processes supernodes in postorder. For each supernode J, it gathers updates from all descendant supernodes K that have J in their update lists. Each update involves a triangular solve with L(K,K) to compute a block of L(J,K), followed by a symmetric rank-k update to the diagonal block of J. Once all updates are applied, the diagonal block is factored with a dense Cholesky kernel, and the result is stored. In a supernodal right-looking method, the solver factors J and immediately scatters updates to its descendants. In a multifrontal method, the solver assembles a frontal matrix from the original matrix and the contribution blocks of its children, factors the front, and passes the Schur complement to its parent. The three variants produce the same L, but they expose different task granularities and memory access patterns.

The dense kernels are the reason supernodes exist. A triangular solve with a dense triangular block is a TRSM. An update of a diagonal block is a SYRK. An update of an off-diagonal block is a GEMM. The diagonal factorization is a POTRF. These operations are the building blocks of LAPACK and are implemented in optimized BLAS libraries for CPUs and GPUs. In a sparse Cholesky solver, the kernels are called on blocks whose sizes are determined by the supernode partition. If the supernodes are large, the kernels dominate the runtime and the solver achieves a high fraction of peak floating-point performance. If the supernodes are small, the solver spends its time in indexing, memory allocation, and function call overhead. The symbolic phase therefore has a direct effect on numeric performance: a good supernode partition is worth more than a clever micro-optimization.

The arithmetic intensity of the numeric phase is uneven. Near the leaves of the elimination tree, supernodes are small and updates are short. The ratio of floating-point operations to memory traffic is low, and the computation is latency-bound. Near the root, supernodes are large and updates are dense. The ratio is high, and the computation can approach the roofline limit of the machine. A parallel scheduler must recognize this heterogeneity. It should use fine-grained tasks in the leaves to expose tree parallelism and coarse-grained tasks near the root to expose dense parallelism. If it uses a single granularity everywhere, it will either waste parallelism near the root or drown in overhead near the leaves.

The task DAG is the scheduler's view of the numeric phase. Each supernode factorization is a task. Each update from one supernode to another is a task or a set of tasks. The edges are dependencies: an update cannot start until the source supernode is factored, and a supernode cannot be factored until all incoming updates are complete. The DAG is acyclic because the elimination tree is acyclic and all updates go from descendants to ancestors. The critical path is the longest path through the DAG, weighted by task costs. It determines the minimum parallel execution time. The total work divided by the number of processors gives a lower bound, but the critical path gives another. A schedule is good if it keeps all processors busy without lengthening the critical path through unnecessary synchronization.

Scheduling strategies fall into two broad categories: static and dynamic. Static scheduling assigns tasks to processors before execution, using the DAG and estimated costs. It works well when the DAG is regular and costs are predictable, as in dense linear algebra. Sparse Cholesky DAGs are irregular, and task costs vary by orders of magnitude. Static scheduling can suffer from load imbalance. Dynamic scheduling assigns tasks on demand, using a shared queue or work stealing. It adapts to actual execution times and handles irregularity well. The cost is synchronization and task management overhead. The best choice depends on the granularity of tasks. If tasks are large, dynamic scheduling overhead is negligible. If tasks are small, the overhead can dominate.

Memory constraints add another dimension. A supernode factorization needs its input blocks, its output block, and workspace for dense kernels. An update needs the source supernode and the destination block. If too many tasks are active at once, the working set exceeds cache and memory bandwidth becomes the bottleneck. Some schedulers use a memory-aware policy that limits the number of concurrent tasks or prioritizes tasks that free large blocks. In a multifrontal solver, the contribution blocks form a stack. The order in which children are processed determines the peak stack size. A depth-first traversal of the assembly tree keeps the stack small but limits parallelism. A breadth-first traversal exposes more parallelism but increases memory. The trade-off is fundamental: parallelism costs memory.

Distributed-memory implementations add communication to the DAG. The elimination tree is mapped to processors, often by subtree-to-subcube mapping: a subtree is assigned to a subset of processors, and the root is processed by all processors. Updates that cross processor boundaries require messages. The communication volume is related to the separator sizes in the ordering. Nested dissection is attractive here because it produces separators that can be mapped to processor subsets. Communication-avoiding algorithms reduce the number of messages by aggregating updates, but they increase memory. The same trade-offs that appear in shared memory reappear in distributed memory with different constants.

GPU implementations exploit the dense kernels by batching many small operations. The leaves of the elimination tree contain many independent supernodes, and their updates can be executed as batched TRSM or batched GEMM. The root contains a few large supernodes, which are executed as standard dense kernels. The challenge is to keep the GPU busy when the DAG has irregular structure. Some solvers use a hybrid approach: symbolic analysis and scheduling on the CPU, dense kernels on the GPU, with asynchronous transfers to overlap communication and computation. The performance model is different from CPU-only solvers because the GPU has higher floating-point throughput but lower memory capacity and higher sensitivity to irregular memory access. Supernode amalgamation is often more aggressive on GPUs to create larger dense blocks.

The numeric phase is therefore a sequence of dense kernels embedded in a sparse dependency graph. The kernels provide the performance; the graph provides the parallelism. The scheduler's job is to keep the critical path short without starving the memory system. That is where the next set of design decisions begins.

## Task Granularity and the Shape of the DAG

The supernodal DAG is a mathematical dependency graph, not yet a scheduler-ready object. Its nodes can be refined or coarsened depending on the target machine. A supernode factorization can be a single task, or it can be split into panel factorizations and trailing updates. An update from supernode K to supernode J can be one GEMM, or it can be partitioned into tiles scheduled independently. The choice of granularity determines how much parallelism the scheduler can see and how much overhead it must pay.

At one extreme, the DAG has one node per supernode and one node per update. This coarsest useful granularity minimizes task management and simplifies dependency tracking. It is often right when supernodes are large, because each task contains enough work to amortize scheduling costs. At the other extreme, the DAG is a fine-grained dataflow graph where each dense kernel is split into blocks. This exposes maximum parallelism but can generate millions of tasks. The scheduler then spends more time managing tasks than doing arithmetic.

A practical design uses a hierarchy. The top level is a DAG of supernodes. Each supernode task, when executed, may internally use a parallel dense kernel or a set of subtasks. This nested structure matches the memory hierarchy. The outer scheduler assigns supernodes to cores or nodes; the inner scheduler or BLAS library parallelizes the dense kernels. The danger is oversubscription. If the outer scheduler runs many threads and each calls a multithreaded BLAS, the machine thrashes. Most sparse Cholesky solvers resolve this by using sequential BLAS inside tasks and relying on the outer scheduler, or by using a single level of tasking with a thread pool that also executes the dense kernels. The choice depends on the ratio of sparse to dense work and on the BLAS quality.

The shape of the DAG is affected by the ordering. Nested dissection produces a wide top and many independent subtrees. Minimum degree produces a deep, narrow DAG. The former has more tree parallelism; the latter has less. The DAG shape determines the critical path. In a deep DAG, the critical path is long and parallel speedup is limited by the chain of dependencies. In a wide DAG, the critical path is shorter, but total work may be larger. The scheduler cannot change the DAG shape, but it can prioritize tasks on the critical path. In sparse Cholesky, the critical path usually runs through the largest supernodes near the root. Those tasks have the highest flop counts and longest durations. Giving them priority reduces the makespan, but it may create memory pressure because many updates must be held until the large supernode is ready.

Task fusion combines updates from the same source to the same destination. This reduces memory traffic and task overhead. In a supernodal left-looking method, the update list of a supernode may contain many small contributions. Fusing them into one gather-and-update operation is often beneficial. The symbolic phase can precompute fused update lists. In a multifrontal method, fusion happens naturally during assembly: all contributions to a front are assembled into one dense matrix before factorization. Task splitting is the opposite. A large update can be split into panels so multiple threads work concurrently. This is useful near the root, where a single GEMM may dominate. Splitting increases parallelism but also dependencies. The scheduler must ensure panels do not race on the same destination block. In practice, splitting is done along the destination dimension, so each panel writes to a disjoint part.

The DAG can be represented statically or discovered dynamically. Cholesky without pivoting has a static nonzero pattern, so the entire DAG can be built during symbolic analysis. This is a major advantage. Static DAGs enable offline scheduling, graph partitioning, and memory preallocation. They also allow exact flop counts for each task, because the dimensions of every dense kernel are known. Dynamic DAG discovery is only necessary when numerical pivoting changes the pattern, which does not happen in pure Cholesky. Some solvers still use dynamic task discovery for flexibility, but the static approach is generally more efficient.

## Memory-Aware Scheduling and Working Sets

Memory is often the limiting resource in sparse Cholesky. The factor L can be much larger than A, and the working set during factorization includes the factor, update buffers, and contribution blocks. If the scheduler runs too many tasks concurrently, the working set exceeds the last-level cache and memory bandwidth becomes saturated. The result is a slowdown that no amount of parallelism can fix. Memory-aware scheduling tries to keep the working set within a target size.

One approach is to limit the number of active tasks. The scheduler maintains a count of tasks that are executing or whose data is resident. When the count reaches a threshold, no new tasks start until some finish. The threshold is chosen based on cache size and average task footprint. This is concurrency throttling. It is simple but can underutilize the machine if the threshold is too low. A more sophisticated approach tracks the actual memory footprint of each task. The scheduler only starts a task if its footprint plus the current footprint is below the cache capacity. This requires the symbolic phase to provide memory estimates for each task. Those estimates are available because the dimensions of every dense block are known.

Cache blocking within a supernode is another way to control the working set. A large GEMM can be tiled so each tile fits in L2 or L3. The scheduler can treat each tile as a separate task. This increases parallelism and improves cache reuse. The tiling strategy depends on matrix dimensions and the cache hierarchy. For sparse Cholesky, tiles are often rectangular because supernode blocks are trapezoidal. The symbolic phase can compute tile boundaries and store them in the plan. The numeric phase then executes the tiles as a set of tasks. This is a sparse adaptation of dense blocked Cholesky.

Data layout also affects memory performance. Supernodal blocks are usually stored contiguously, with a separate index array mapping global row indices to positions within the block. When an update reads from a source supernode, it must gather rows according to the index array. If rows are scattered, the gather is slow. Postordering the elimination tree improves locality because the rows of a subtree are contiguous. Some solvers go further and reorder rows within a supernode to improve vectorization. The row ordering must be consistent across all supernodes that share rows. This is a global constraint handled during symbolic analysis.

Memory allocation is a practical concern. The numeric phase allocates and frees many blocks. Frequent malloc and free calls are expensive and can fragment memory. Most solvers use a pool allocator: the symbolic phase computes the maximum memory requirement, and the numeric phase allocates one large arena. Blocks are suballocated from the arena. When a block is no longer needed, it is returned to the pool. This reduces allocation overhead and improves locality. In a parallel setting, the pool must be thread-safe or partitioned per thread. Partitioned pools avoid synchronization but can lead to imbalance if one thread's pool is exhausted. A global pool with a lock is simpler but can become a bottleneck. A common compromise is a two-level pool: a global pool for large blocks and per-thread pools for small blocks.

Out-of-core factorization is the extreme case where the factor does not fit in memory. The DAG is partitioned into panels, and each panel is loaded from disk, factored, and written back. The scheduler must overlap I/O with computation. The elimination tree provides a natural partitioning: a subtree can be factored entirely in memory if its working set fits. The root is factored last and may require a large amount of memory. Out-of-core methods are less common today because memory is cheaper, but they remain relevant for very large problems.

## Distributed and Accelerator Considerations

In distributed memory, the elimination tree is mapped to processors. A common strategy is subtree-to-subcube mapping. The root of the elimination tree is assigned to all processors. The children of the root are assigned to disjoint subcubes. This mapping is recursive: each subtree is assigned to a subset of processors, and the root of the subtree is processed by that subset. The mapping minimizes communication because updates within a subtree are local. Only updates that cross subtree boundaries require messages. The volume of communication is related to separator sizes in the ordering. Nested dissection produces small separators, so it is well suited to distributed memory.

The mapping must balance work across processors. If one subtree is much larger than others, the processors assigned to it will be overloaded. The ordering can be adjusted to balance subtree sizes, or the mapping can assign more processors to larger subtrees. This is a graph partitioning problem. The elimination tree is partitioned into subgraphs of roughly equal work, with the constraint that each subgraph is connected. The partitioning also affects communication: cutting more edges increases messages. The trade-off between load balance and communication is central to distributed sparse Cholesky.

Communication primitives depend on the DAG. An update from supernode K to supernode J becomes a message from the processor owning K to the processor owning J. If J is owned by multiple processors, the update may be broadcast or scattered. In a multifrontal method, the contribution block from a child is sent to the parent. The parent may be owned by a different processor. The assembly step combines contributions from all children. If children are on different processors, assembly requires a gather. Nonblocking sends and receives allow communication to overlap with computation. The scheduler must ensure a task does not start until its incoming messages arrive. This is handled by dependency counters decremented when a message is received.

Communication-avoiding algorithms reduce message count by aggregating updates. Instead of sending each update separately, the source processor accumulates all updates destined for the same processor and sends them as one message. This reduces latency but increases memory. In a supernodal method, the update list of a supernode can be sorted by destination processor, and updates can be batched. In a multifrontal method, the contribution block is already an aggregate, so communication-avoiding is natural. The trade-off is between message count and message size. On modern networks, large messages are efficient, so aggregation is usually beneficial.

GPUs and other accelerators change the calculus. They offer high floating-point throughput but limited memory capacity and high sensitivity to irregular memory access. The dense kernels inside supernodes are a natural fit, but the sparse structure and dependency graph are not. A GPU implementation must batch many small operations to keep the device busy. The leaves of the elimination tree contain many independent supernodes, and their updates can be executed as batched TRSM or batched GEMM. Batched kernels process many small matrices in one launch, amortizing kernel launch overhead. The root contains a few large supernodes, executed as standard dense kernels. The challenge is to schedule the DAG so the GPU always has work.

The CPU typically handles symbolic analysis and scheduling. The GPU executes dense kernels. The factor is stored in GPU memory if it fits. If not, blocks are streamed from host memory. Asynchronous transfers overlap communication with computation. The scheduler must manage GPU memory as a resource, just as it manages cache in a CPU-only solver. The DAG is partitioned into phases that fit in GPU memory. Each phase is executed on the GPU, and results are transferred back if needed. Dependencies are respected using events or streams. Modern GPU programming models allow fine-grained dependencies between kernels, which can implement the DAG directly.

Multi-GPU systems add another layer of communication. The DAG is partitioned across GPUs, and updates that cross GPU boundaries require peer-to-peer transfers. The mapping problem is similar to distributed memory, but the network is faster and the memory is smaller. The root is typically distributed across all GPUs using a 2D block-cyclic layout. The leaves are assigned to individual GPUs. The scheduler must balance work across GPUs and minimize communication. The performance model differs from CPU clusters because GPU memory bandwidth is much higher, but capacity is much lower. Supernode amalgamation is often more aggressive on GPUs to create larger dense blocks.

A performance model for sparse Cholesky starts with the operation count. The flop count for a supernode J with width w and height h is approximately w^3/3 for the diagonal factorization plus w^2 h for updates. The total flop count is the sum over all supernodes. Memory traffic is approximately w h for updates plus w^2 for the diagonal block. Arithmetic intensity is therefore roughly w, the width of the supernode. This explains why supernode amalgamation is so important: doubling the width doubles arithmetic intensity, which can move the computation from memory-bound to compute-bound. The critical path length is the sum of costs on the longest path. In a balanced elimination tree, the critical path goes through the root and has length proportional to the root cost plus the logarithm of the number of leaves times the leaf cost. In a chain-like tree, the critical path is proportional to the number of supernodes. Parallel speedup is bounded by total work divided by critical path length. If the critical path is long, adding processors does not help. This is why nested dissection, which produces balanced trees, is preferred for parallel factorization. The extra fill-in increases total work, but the shorter critical path more than compensates when the processor count is high.

## From Performance Model to Scheduler Design

The performance model above gives the scheduler three numbers to reason about: total work, critical path length, and arithmetic intensity. Work tells the scheduler how much parallelism is theoretically available. Critical path tells it how much parallelism is actually usable. Arithmetic intensity tells it whether the machine will be limited by floating-point throughput or by memory bandwidth. A scheduler that ignores any of these will either underutilize the machine or saturate a resource that it cannot see.

The first practical use of the model is task prioritization. In a DAG, the bottom level of a task is the length of the longest path from that task to any sink, weighted by task costs. Tasks with large bottom levels are on or near the critical path. List scheduling with highest-bottom-level-first is a classic heuristic that often produces near-optimal makespans for DAGs with predictable costs. Sparse Cholesky DAGs have predictable costs because the dimensions of every dense kernel are known after symbolic analysis. The bottom level of each supernode factorization and each update can therefore be computed offline and stored in the symbolic plan.

Priority alone is not enough. A task may be on the critical path but not ready to execute because its inputs are not available. The scheduler must distinguish between static priority and dynamic readiness. A common approach is a ready queue ordered by bottom level. When a task completes, its successors have their dependency counters decremented. When a counter reaches zero, the successor is inserted into the ready queue. The scheduler always picks the ready task with the highest bottom level. This is simple and effective, but it can create memory pressure: the highest-priority task may require a large working set that evicts data needed by other ready tasks.

Memory-aware priority adjusts the static bottom level with a penalty for memory footprint. The penalty can be based on the size of the destination supernode, the number of active updates, or the current cache occupancy. The goal is to keep the working set within the last-level cache while still making progress on the critical path. This is a constrained optimization problem. Exact solutions are too expensive, so practical schedulers use heuristics: cap the number of active large tasks, delay tasks whose footprint exceeds a threshold, or schedule memory-heavy tasks in batches to amortize allocation.

A second use of the model is task granularity adaptation. The symbolic phase can produce a DAG at a base granularity, and the runtime can split or fuse tasks dynamically. Splitting is useful when a single task has more work than the average and the machine has idle cores. Fusing is useful when many small tasks share the same inputs and the overhead of scheduling them separately exceeds the benefit of parallelism. The runtime can monitor the ready queue length and the average task duration. If the queue is short and tasks are long, it splits. If the queue is long and tasks are short, it fuses. This adaptive approach is common in task-based runtimes, but it requires the DAG to be expressible as a hierarchy of tasks.

A third use is NUMA-aware placement. On a multi-socket machine, memory access latency depends on which socket owns the data. A supernode that is updated by many tasks should reside on the socket where most of those tasks run. The symbolic phase can partition the elimination tree into subtrees and assign each subtree to a NUMA node. Tasks within a subtree are scheduled on that node. Updates that cross subtrees require remote memory access or explicit communication. The partitioning should balance work across nodes and minimize cross-subtree edges. This is a graph partitioning problem on the elimination tree, with edge weights representing update volume.

## Practical Scheduling Strategies for Sparse Cholesky DAGs

The simplest parallel schedule is a static block schedule. The DAG is topologically sorted, divided into levels, and levels are assigned to processors in a round-robin or blocked fashion. This works when tasks are uniform, but sparse Cholesky tasks are not. A level may contain a few large supernodes and thousands of small updates. Static scheduling leads to load imbalance and idle cores. It is rarely used for the numeric phase, although it can be adequate for the symbolic phase.

Dynamic scheduling is the norm. Work stealing is the most common mechanism. Each thread maintains a deque of ready tasks. It pushes newly created tasks onto its own deque and pops from the same end. When its deque is empty, it steals from the opposite end of another thread's deque. Work stealing is decentralized, has low contention, and adapts to irregular task durations. Its main weakness is locality: a stolen task may access data that is resident in the victim's cache or on the victim's NUMA node. Locality-aware work stealing tries to steal tasks that are likely to reuse the thief's data, or it migrates the data along with the task. In sparse Cholesky, tasks that update the same destination supernode are good candidates for co-scheduling. The scheduler can group them into a composite task or assign them an affinity to the same core.

Subtree-to-subcube mapping is a static strategy for distributed memory that also works on NUMA nodes. The elimination tree is recursively partitioned. The root is assigned to all processors. Each child subtree is assigned to a disjoint subset of processors. The mapping is proportional: larger subtrees get more processors. Within a subtree, tasks are scheduled dynamically. This strategy minimizes communication because most updates are local to a subtree. It also balances work if the subtree sizes are balanced. Nested dissection orderings produce balanced subtrees, which is one reason they are preferred for parallel factorization.

Proportional mapping can be refined with 2D distributions. Instead of assigning a whole subtree to a subcube, the root supernode is distributed over a 2D processor grid. Updates from children to the root are scattered across the grid. This is common in dense linear algebra and is used in sparse Cholesky for the largest supernodes. The 2D layout reduces communication volume for the root, which is often the bottleneck. The children are assigned to processor columns or rows. The mapping must ensure that the data needed by each update is available where the update executes. This is a data distribution problem, and it interacts with the storage format of the factor.

Communication-avoiding scheduling reduces the number of messages by aggregating updates. In a supernodal left-looking method, the update list of a supernode can be sorted by source processor. All updates from the same source are sent as one message. The destination processor unpacks the message and applies the updates. This reduces latency but increases the size of the message buffer. The scheduler must allocate buffer space and ensure that the aggregation does not create a dependency cycle. In a multifrontal method, aggregation is natural because the contribution block from a child is already a dense matrix. The parent assembles contributions from all children, regardless of where they were computed.

Task priorities in a parallel scheduler should reflect both the critical path and the communication pattern. A task that sends a large message to a remote processor should be scheduled early so the message can be in flight while other work proceeds. A task that receives a large message should be scheduled after the message arrives. The scheduler can use lookahead: when a task completes, it notifies its successors and, if the successor is remote, sends the data immediately. The successor is marked ready only when the data arrives. This is the dataflow model used by many task-based runtimes.

GPU scheduling adds another layer. The GPU has thousands of threads but limited memory. The scheduler must batch small tasks into large kernel launches. The leaves of the elimination tree are ideal for batching because they contain many independent supernodes of similar size. The scheduler can collect all ready leaf updates and launch a batched GEMM. The root is handled by a few large kernels. Between these extremes, the scheduler must decide whether to use batched kernels or individual kernels. The decision depends on the number of ready tasks, their sizes, and the available GPU memory. A hybrid scheduler may run small tasks on the CPU while the GPU handles large tasks, or it may use the GPU for all dense kernels and the CPU for scheduling and symbolic work.

## Runtime Systems and Execution Models

Implementing a sparse Cholesky solver from scratch with pthreads or MPI is possible but rarely advisable. Task-based runtime systems provide dependency tracking, scheduling, memory management, and communication. OpenMP tasks with dependences can express a DAG directly. Each supernode factorization is a task, and each update is a task with in, out, and inout dependences on the data blocks. The OpenMP runtime builds a dependence graph and schedules tasks. This works well for moderate DAG sizes, but OpenMP task overhead becomes significant when there are millions of tasks. Taskloops and taskgraph extensions reduce overhead by grouping tasks, but they require compiler support.

More specialized runtimes offer better performance for irregular DAGs. StarPU uses a dataflow model with explicit data handles. Tasks declare which handles they read and write, and the runtime derives dependencies. StarPU schedules tasks across CPUs and GPUs and manages data transfers. It supports several scheduling policies, including eager, priority, and work stealing. PaRSEC uses parameterized task graphs, where a single graph describes a family of tasks with runtime parameters. This is a natural fit for sparse Cholesky, where the DAG has a regular structure at the supernode level but irregular sizes. PaRSEC can generate the DAG on the fly and schedule it with low overhead. Legion uses logical regions and a deferred execution model. The programmer describes the data and the tasks, and the runtime infers dependencies and places data. Legion is designed for distributed heterogeneous machines and can scale to large node counts.

Charm++ and HPX use an actor model. Each task is an object that sends messages to other tasks. The runtime maps objects to processors and migrates them for load balance. This model handles irregular DAGs well, but it requires the programmer to express the computation as messages. For sparse Cholesky, the messages are updates between supernodes. The runtime can overlap communication with computation and migrate tasks to balance load. The overhead is higher than a dataflow runtime, but the flexibility is greater.

The choice of runtime depends on the target machine and the problem size. For a single shared-memory node, OpenMP tasks or a lightweight task library may be sufficient. For a distributed cluster, a runtime with communication support is necessary. For a GPU-accelerated node, a runtime that manages device memory and kernel launches is helpful. In all cases, the runtime should expose enough control for the solver to implement its own scheduling policy. The best policy for sparse Cholesky is not the same as the best policy for dense linear algebra or for graph processing. A runtime that forces a single policy will leave performance on the table.

Memory management is a major responsibility of the runtime. Sparse Cholesky allocates and frees many blocks during factorization. A naive malloc/free per block is too slow. Runtimes provide memory pools, scratch buffers, and data handles. The solver can preallocate the factor and use suballocations for temporary blocks. The runtime tracks dependencies and frees a block when its last consumer completes. This automatic reclamation reduces memory footprint and eliminates leaks. It also allows the runtime to schedule tasks based on memory availability. Some runtimes support out-of-core execution, where blocks are spilled to disk when memory is tight. This is rare but valuable for very large problems.

## Scalability Limits and Diagnostic Metrics

A parallel sparse Cholesky solver can fail to scale for several reasons. The first is insufficient work. If the problem is small, the DAG has few tasks and the critical path dominates. Adding processors does not help. The second is load imbalance. If the DAG has a few large tasks and many small tasks, the large tasks become stragglers. The third is memory bandwidth. If arithmetic intensity is low, the machine is memory-bound and adding cores does not increase throughput. The fourth is communication. If updates cross processor boundaries frequently, the network becomes the bottleneck. The fifth is scheduling overhead. If tasks are too small, the runtime spends more time managing tasks than doing arithmetic.

Diagnostic metrics help identify which limit is active. Parallel efficiency is the speedup divided by the number of processors. It measures how well the machine is utilized. Load imbalance can be measured as the difference between the maximum and average processor busy time. Critical path utilization is the ratio of critical path length to total execution time. If it is close to one, the schedule is critical-path-bound. Memory bandwidth utilization is the ratio of achieved bandwidth to peak bandwidth. If it is close to one, the solver is memory-bound. Communication volume and message count measure the distributed overhead. Tracing tools can record task start and end times, memory accesses, and messages. The resulting trace can be visualized to find gaps, stragglers, and hotspots.

Roofline analysis can be applied per supernode. The arithmetic intensity of a supernode is roughly its width. If the width is small, the supernode is memory-bound. If the width is large, it is compute-bound. The roofline model predicts the maximum achievable performance for each supernode. The solver can use this prediction to decide which supernodes to amalgamate and which to split. It can also use it to set task priorities: memory-bound tasks should be scheduled when memory bandwidth is available, and compute-bound tasks when floating-point units are idle. This is a form of resource-aware scheduling.

Scalability limits are often described by Amdahl's law and Gustafson's law. Amdahl's law assumes a fixed problem size and a serial fraction. In sparse Cholesky, the serial fraction includes ordering, symbolic analysis, and some I/O. If these are not parallelized, they limit strong scaling. Gustafson's law assumes that the problem size grows with the processor count. In sparse Cholesky, fill-in grows with problem size, so the work grows superlinearly. Weak scaling is therefore limited by memory per processor and by communication. Isoefficiency analysis asks how fast the problem size must grow to maintain constant efficiency. For sparse Cholesky, the answer depends on the ordering. Nested dissection has better isoefficiency than minimum degree because it produces more parallelism and less communication.

Practical pitfalls are numerous. Oversubscription occurs when the outer scheduler and the BLAS library both use multiple threads. The solution is to use sequential BLAS inside tasks or to use a single level of tasking. False sharing occurs when two threads write to different variables that share a cache line. Padding and per-thread data structures avoid it. Thread contention occurs when many threads access a shared queue or allocator. Lock-free queues and per-thread pools reduce it. NUMA imbalance occurs when memory is allocated on one socket but used on another. First-touch allocation and memory binding can mitigate it. Load imbalance due to irregular DAGs is handled by work stealing and dynamic scheduling. Stragglers can be caused by a single large supernode or by a slow node in a cluster. Task splitting and replication can help.

Numerical reproducibility is another concern. Different schedules sum updates in different orders, so floating-point results can differ. For many applications, this is acceptable. For others, bitwise reproducibility is required. Deterministic scheduling, fixed reduction trees, and reproducible BLAS can provide it at some performance cost. The trade-off between performance and reproducibility is a design decision that should be made explicitly, not left to the scheduler. Some solvers offer a reproducible mode that fixes the schedule and the reduction order. Others provide a diagnostic mode that reports the maximum difference between runs.

The scheduler is therefore not a separate concern from the mathematics. It is the mechanism that turns the elimination tree and supernode DAG into parallel execution. The quality of the schedule determines whether the solver runs at memory bandwidth, at floating-point peak, or at a fraction of both. The next step is to connect these scheduling ideas to concrete implementation choices in the numeric phase, including storage formats, kernel selection, and the interaction between the factor and the right-hand side solves.
