# A Deep Dive Into Software Distributed Shared Memory: Page-Based Coherence, Multiple-Writer Protocols, And Release Consistency

In 1989, if you wanted to write a parallel program in which threads share a single address space, you bought a multiprocessor. If you wanted to use the dozen workstations sitting idle in the lab, you wrote message passing: explicit sends, explicit receives, and a mental model in which every piece of data has exactly one home. The two worlds had different hardware, different programming models, and different failure modes.

Software distributed shared memory (SDSM, or simply DSM) was the attempt to collapse that distinction. The idea: keep the shared-memory programming model, but implement it in software on top of a network of commodity machines. Each node keeps a piece of the shared address space in its own physical memory. When a node touches a page it does not own, the operating system traps, and a user-level protocol fetches the page from wherever it currently lives. Coherence — the guarantee that all nodes see a consistent view of each location — is maintained by software rather than by snooping buses or directory controllers.

This is worth revisiting for three reasons. First, the engineering is instructive: SDSM systems had to solve the same coherence problem that hardware solves, but with a trap in the critical path instead of a cache controller, which forced every design decision to be about *avoiding* the mechanism rather than *optimizing* it. Second, the consistency models invented to make SDSM viable — release consistency and its many variants — are the intellectual ancestors of the relaxed memory models now standardized in C++, Java, and Rust, and of the ordering rules that govern accelerator and GPU programming. Third, the idea is back. RDMA fabrics, CXL-attached memory pools, and disaggregated memory servers all present the same fundamental question: what does it cost to give a program the illusion of shared memory across a network, and which parts of that illusion can hardware pay for?

This article works from the mechanism outward: how page-based coherence actually functions, why granularity dominates everything, how multiple-writer protocols and release consistency were invented to make the expensive events rare, and what the modern descendants of these designs look like.

## The substrate: why the MMU is a coherence engine

The central trick of SDSM is that a virtual memory system already does something remarkably close to what a cache coherence protocol needs. A page table entry is a small piece of per-page state, consulted on every access, that can be flipped to generate a trap. If you map a shared page read-only on a node that does not have write permission, the first store to that page faults. The fault is delivered to software, which can then do whatever the protocol requires — invalidate copies elsewhere, transfer ownership, merge concurrent writes — before re-enabling the access and restarting the faulting instruction.

This gives you three things for free. You get *access detection*: the hardware tells you exactly when a node first touches a page in a way that requires protocol action. You get *protection*: a node that has not been granted write access physically cannot write, which makes the protocol's invariants enforceable rather than merely conventional. And you get *transparency*: the application is unmodified, because from its perspective it is simply dereferencing a pointer.

What you do not get is speed. A hardware cache coherence protocol resolves a miss in tens to low hundreds of cycles, in the shadow of the load that caused it, without the pipeline ever leaving the fast path. An SDSM protocol resolves a "miss" by taking a page fault: a trap into the kernel, a signal or upcall to a user-level handler, a message to a remote node, a wait for the response, a page table update, and a return. The cost is measured in microseconds at best, and often in tens of microseconds once the network and the remote node's own scheduling are included. That is three to four orders of magnitude more expensive than a cache miss.

Everything else in SDSM design follows from that ratio. If the mechanism is that expensive, the only viable strategy is to make it rare. The history of the field is largely a history of increasingly aggressive ways to make the expensive events rare without breaking the programming model.

## The baseline: page-based coherence with sequential consistency

The canonical early design is IVY, described by Kai Li and Paul Hudak in 1989. IVY implements a shared virtual address space across a set of workstations, with coherence at page granularity and a memory model of sequential consistency. Every node maps the shared region at the same virtual addresses, so a pointer value is meaningful on every node; only the physical page backing that address differs.

The protocol state is a directory holding, for each page, an owner and a set of sharers. IVY explored two placements for this directory. In the centralized scheme, a single manager node holds all directory entries and serializes all requests; the manager is a bottleneck, but the protocol is simple. In the distributed scheme, ownership migrates: the owner of a page is responsible for servicing requests for it, and ownership transfers along with write access. Distributed ownership removes the central bottleneck but introduces an owner-location problem, which requires either a broadcast or a forwarding chain of hints to solve.

The read path is straightforward. A node without a valid copy takes a read fault, sends a request to the owner, and receives the page. It installs the page read-only and adds itself to the copyset. The write path is where the coherence work happens. A node taking a write fault must acquire exclusive ownership: the owner invalidates all other copies, waits for acknowledgements, transfers the page and ownership, and only then does the faulting node install the page writable and retry the store.

The acknowledgement wait is not an implementation detail; it is the enforcement mechanism for sequential consistency. In a sequentially consistent system, a store must not become visible to any other node before all earlier operations are visible everywhere, and no later operation on any node may observe the new value before the store is globally ordered. By refusing to complete the write fault until every cached copy has been invalidated, the protocol guarantees that no other node can hold a stale read-only copy that would let it observe an older value after the write completes. The memory model is enforced by the fault path, one page fault at a time.

That is also the design's central weakness. Sequential consistency at page granularity means every write to a shared page that is currently replicated elsewhere costs a full invalidation round trip, even if the program contains no actual data race and even if the two nodes never touch the same bytes on that page. The protocol is correct, and for programs with coarse-grained sharing and long phases of computation between synchronizations it can perform acceptably. For programs that share fine-grained data structures, it collapses.

## Granularity: the 4 KiB problem

The single most consequential parameter in an SDSM design is the unit of coherence, and the operating system hands you a bad one.

Hardware coherence operates at cache-line granularity — typically 64 bytes on x86-64 and AArch64, 128 bytes on some other designs. A page is 4 KiB on most systems, sometimes larger. That is a factor of 64 or more in linear size, and it means a page can contain data belonging to logically unrelated parts of the program.

The resulting pathology is false sharing, and in SDSM it is not a minor performance nuisance but a correctness-preserving disaster. Suppose two nodes each write to a distinct variable, and both variables happen to land on the same page. Under a write-invalidate protocol, each write requires exclusive ownership of the whole page. Node A takes a write fault, invalidates B's copy, writes, and proceeds. Node B then takes a write fault, invalidates A's copy, writes, and proceeds. The page ping-pongs across the network for the entire duration of the loop, and every iteration pays a fault and a round trip. The program's data has no actual sharing at all; the *layout* created the sharing.

The problem is aggravated by the fact that the faulting granularity is also the transfer granularity. Even when the sharing is real, the protocol moves 4 KiB to satisfy a single-byte store. The bandwidth cost is usually not the dominant term — the round-trip latency is — but it matters for protocols that propagate diffs or updates rather than whole pages.

There are three families of responses, and every real system uses some combination:

1. **Reduce the granularity.** Use smaller pages where the architecture allows it. Some MMUs support sub-page write protection, letting a page be read-only except for a small protected block; this reduces false sharing at the cost of more traps and more complicated handlers. Smaller pages also increase TLB pressure and page-table memory, so there is a floor below which the cure is worse than the disease.

2. **Change the protocol to tolerate concurrent writers.** Instead of invalidating on write, allow multiple nodes to hold writable copies of the same page and reconcile them at synchronization points. This is the multiple-writer approach, and it converts a coherence problem into a merge problem — which is only sound if the memory model permits the merge to be deferred.

3. **Change the memory model to make the merge legal.** This is the deepest of the three responses, and it is the one that produced the most durable ideas.

The second and third responses are where the field's real intellectual contribution lies. They raise the questions that the rest of this article addresses: how twin-and-diff multiple-writer protocols actually merge concurrent page writes, why release consistency makes deferred propagation sound rather than merely convenient, and how lazy propagation turned a page-fault-per-write into a page-fault-per-synchronization — the change that made SDSM competitive with message passing on a meaningful class of programs.

## Multiple-writer protocols: twins, diffs, and the merge at release

The write-invalidate protocol described above has a single, deep assumption baked into it: at any moment, a page has exactly one writer, and every other node's copy is either absent or read-only. That assumption is what makes invalidation necessary, and it is what makes false sharing catastrophic. If two nodes write to different bytes of the same page, the protocol cannot tell the difference between a genuine conflict and a layout accident, so it serializes them.

The alternative is to let several nodes hold writable copies of the same page simultaneously and reconcile them later. This sounds reckless — it is, after all, exactly what cache coherence protocols spend their complexity preventing — but it is sound as long as three conditions hold. First, the writes must be to disjoint locations, or the program must be willing to accept some defined merge order for the overlapping ones. Second, the reconciliation must happen before any node reads a location that another node wrote. Third, the memory model must permit the reconciliation to be deferred to a point where the program has already told you it is safe.

Munin, developed at Rice by John Carter, John Bennett, and Willy Zwaenepoel in the early 1990s, was the system that made this concrete. Munin's central observation was that the expensive part of SDSM is not the transfer of data but the *synchronization* of the protocol with the program's own synchronization. If the program is going to execute a barrier or release a lock anyway, and if the memory model says that no other node can legally observe your writes until that point, then there is no reason to send anything before then. You can accumulate writes locally and flush them at the synchronization point, when the cost is already being paid.

The mechanism Munin introduced for this is the twin-and-diff. When a node acquires a page in a writable state, it makes a *twin*: a byte-for-byte copy of the page as it existed at the moment of acquisition, stored in a shadow buffer. The node then writes to the real page as it pleases, with no protection and no traps. At release time, the protocol walks the page and the twin in parallel, produces a *diff* — a compact description of the byte ranges that changed — and sends only the diff to the home node or to the next acquirer. The twin is then discarded or reused.

The diff is the key data structure. It is typically encoded as a list of (offset, length, bytes) triples, or as a bitmap with run-length compression, and it exploits the fact that most pages in most programs are sparsely modified. A page that holds a 4 KiB array where the program writes 64 scattered elements produces a diff of a few hundred bytes rather than 4096. A page that holds a single flag produces a diff of a few bytes. The cost of computing the diff is proportional to the page size, but it is paid once per release rather than once per write, and it is paid in local memory bandwidth rather than network latency.

Munin's second contribution was to make the protocol *per page* rather than *per system*. Each page is annotated at runtime with a protocol type chosen by the application or by a profiling pass, and the runtime dispatches to the appropriate handler. The types include:

- **Write-once**: the page is written once and then read by everyone. The first writer produces a diff, the home merges it, and subsequent readers get the merged page. This is the common pattern for initialization and for read-only data computed at startup.
- **Write-many**: the page is written repeatedly by one node between synchronizations. The node keeps ownership, accumulates a twin, and produces a diff at release. This is the workhorse for private working data that happens to live in the shared region.
- **Producer-consumer**: one node writes, others read, with the synchronization making the direction explicit. The producer's diffs are propagated at release; consumers invalidate on acquire.
- **Reduction**: many nodes contribute to the same location, typically a counter or a sum. The protocol can accumulate partial results locally and combine them at the barrier, avoiding both the diff and the round trip for every increment.
- **Result**: the page is written by many nodes and read by one after a barrier. The home collects diffs and merges them.
- **Migratory**: the page moves from node to node, with each node writing it in turn. Ownership migrates rather than being replicated.
- **Read-mostly**: the page is read by many nodes and written rarely. It is replicated widely and invalidated on the rare write.
- **Private**: the page is used by one node only and needs no coherence at all.

The per-page protocol dispatch is what lets Munin avoid the worst cases of a one-size-fits-all design. A page holding a reduction variable and a page holding a read-only lookup table have nothing in common, and forcing them through the same invalidation machinery wastes both network bandwidth and protocol logic. The cost is that the application or the compiler must supply the annotations, which is a real burden and a real source of bugs when the annotation is wrong.

The merge itself is where multiple-writer protocols get subtle. When the home node receives two diffs for the same page from two different nodes, it must apply them in some order. If the diffs touch disjoint byte ranges, the order does not matter and the merge is trivially commutative. If they overlap, the result depends on the order, and the protocol must either define a deterministic order (for example, by node rank) or declare the program erroneous. The latter is the usual choice: overlapping writes to the same location without intervening synchronization are a data race, and data races are excluded by the programming model. The protocol's job is to detect the easy cases and to be correct in the common case, not to define semantics for programs that have none.

## Release consistency: the model that made deferral legal

The multiple-writer protocol is only sound if the memory model allows a node's writes to remain invisible to other nodes between synchronizations. Sequential consistency does not allow this: it requires that every store be globally ordered before any subsequent operation. A sequentially consistent SDSM cannot defer propagation, because the deferral itself is observable.

The model that permits deferral was already being developed for hardware multiprocessors, and SDSM adopted it wholesale. The lineage runs through weak consistency, proposed by Michel Dubois, Christoph Scheurich, and Fayé Briggs in 1988, which observed that a program that uses explicit synchronization does not need the hardware to order ordinary accesses against each other — only against the synchronization operations. The hardware can therefore buffer and reorder ordinary accesses freely, as long as it drains the buffers at a synchronization point.

Release consistency, introduced by Kourosh Gharachorloo, Anoop Gupta, John Hennessy, Mark Hill, and David Wood in 1990 in the context of the DASH multiprocessor, sharpened this into a precise contract. It distinguishes two kinds of synchronization operations:

- An **acquire** is an operation that must see all writes that happened before the release it synchronizes with. A lock acquisition is the canonical example: after acquiring the lock, the thread must observe every write made by the previous lock holder.
- A **release** is an operation that makes the current thread's writes visible to whoever acquires next. A lock release is the canonical example: before releasing the lock, the thread must ensure that its writes are ordered before the release.

Everything else — ordinary loads and stores to shared data — is unordered. The model says nothing about when a store becomes visible to another node, only that it must be visible by the time the releasing node's release is observed by an acquiring node. This is the *happens-before* relation that would later become the vocabulary of the C++ and Java memory models: a release and a matching acquire establish a synchronizes-with edge, and everything sequenced before the release happens-before everything sequenced after the acquire.

Gharachorloo's paper distinguished two variants that matter for implementation. **RCsc** (release consistency, sequentially consistent) requires that a release be ordered before a subsequent acquire on the same node, which makes the model easier to reason about but restricts the implementation. **RCpc** (release consistency, processor consistent) relaxes this to allow a release followed by an acquire to be reordered, which is cheaper to implement in hardware but requires more care in the program. Most SDSM systems chose the weaker model, because the software implementation has no fast path to protect and the extra ordering buys little.

The reason release consistency is the right model for SDSM is that it matches what the protocol can actually deliver. The protocol cannot make a store visible instantly; it can only make it visible at the next synchronization. If the model demanded more, the protocol would have to insert communication on the store path, which is exactly the trap-in-the-critical-path problem that SDSM is trying to avoid. Release consistency turns the protocol's natural behavior — accumulate locally, flush at synchronization — from an optimization into a semantic guarantee.

## TreadMarks: lazy release consistency in practice

The most influential SDSM system of the 1990s was TreadMarks, built at Rice by Pete Keleher, Alan Cox, Sandhya Dwarkadas, and Willy Zwaenepoel. TreadMarks took release consistency one step further with *lazy release consistency* (LRC), and in doing so it produced a design that is still worth studying as a piece of systems engineering.

The insight behind LRC is that release consistency, as stated, is still more conservative than it needs to be. It says that a node's writes must be visible to an acquirer, but it does not say *when* the releasing node must send them. An eager implementation sends diffs at release time, pushing them to the home node or to all sharers. A lazy implementation does nothing at release and instead pulls the diffs at acquire time, from whoever has them.

Lazy propagation is a large win for two reasons. First, it avoids sending data to nodes that will never acquire the page. In an eager protocol, every release broadcasts to every sharer, even if only one of them will ever look at the data again. In a lazy protocol, the data moves only when a node actually needs it. Second, it amortizes multiple releases into a single transfer. If a page is modified ten times between two acquires, an eager protocol sends ten diffs; a lazy protocol sends one merged diff, because the intermediate versions were never observed by anyone.

The mechanism TreadMarks uses to make this work is the *write notice* plus the *interval*. Each node maintains a vector timestamp — a vector of logical clocks, one entry per node — that records how much of each other node's history it has observed. A synchronization operation (a barrier, a lock acquire, a lock release) advances the node's own entry in the vector and associates the resulting timestamp with the interval of execution that just ended. A write notice is a small record saying "page P was modified during interval I at node N"; it contains no page data, only the identity of the page and the interval.

When a node executes an acquire, it sends its vector timestamp to the node it is synchronizing with (the previous releaser, or the barrier manager). That node compares the incoming vector against its own and returns the write notices for every interval the acquirer has not yet seen. The acquirer then knows which pages are stale, and it takes a page fault on the first access to each one. The fault handler requests the diff for that page from the node that produced the write notice, applies it to the local copy, and resumes.

The crucial property of LRC is that the set of write notices returned is exactly the set of writes that happened-before the acquire. Not a superset, not a conservative approximation — the vector timestamp comparison computes the happens-before relation precisely, so the acquirer fetches exactly the data it is entitled to see and nothing more. This is what makes LRC both correct and efficient: correctness comes from the fact that happens-before is transitive and the vector clocks capture it, and efficiency comes from the fact that no unnecessary data crosses the network.

The diff mechanism from Munin survives in TreadMarks, but with a different trigger. A TreadMarks node does not compute a diff at release, because it does not know who will ask for it. Instead, it keeps the twin and computes the diff lazily, when the first request for that page arrives. If no request ever arrives, the diff is never computed. This is a further amortization: the cost of diff computation is paid only for pages that are actually shared across the synchronization boundary.

TreadMarks also had to solve the *home* problem. In a multiple-writer protocol, there is no single owner of a page, so where does a newly joined node get the page from? TreadMarks designates one node as the home for each page, typically the node that first touched it, and the home is responsible for maintaining a merged copy. When a node acquires a page it has never seen, it fetches the current merged version from the home, then applies the diffs it learned about from the write notices. The home may itself be stale, in which case the requester must gather diffs from multiple nodes and merge them locally. The protocol handles this by tracking, for each page, which intervals have been applied to the local copy, so that a diff is applied at most once and in a consistent order.

The performance results TreadMarks reported were the first to show that SDSM could be competitive with message passing on a meaningful class of programs. For applications with coarse-grained sharing — SPMD-style codes with barriers between phases — TreadMarks came within a small factor of hand-written message passing, and on some irregular applications it was faster, because the shared-memory model let the programmer express the communication implicitly and the runtime could exploit locality that a static message-passing decomposition would miss. For applications with fine-grained sharing, the page-granularity overhead remained dominant, and no amount of protocol cleverness could close the gap.

## Shasta: moving the check off the fault path

TreadMarks and Munin both live with the page fault as the fundamental mechanism. A different line of work asked whether the fault could be eliminated entirely. Shasta, developed at DEC's Western Research Laboratory by Daniel Scales, Kourosh Gharachorloo, and Chandramohan Thekkath in 1996, answered yes — at the cost of modifying the program's binary.

Shasta's observation is that the page fault is expensive not because of the coherence work but because of the trap: the transition from user to kernel, the signal delivery, the context switch back, and the loss of the pipeline state. If the coherence check could be performed inline, in the instruction stream, with no trap, the cost would drop by an order of magnitude even if the check itself is a memory load and a branch.

Shasta implements this by instrumenting the executable. Every load and store to a shared region is preceded by a check that reads a per-block state word and branches to a slow path if the block is not valid or not writable. The check is a few instructions, predictable and inlinable, and it runs at full processor speed. The slow path is a call into the runtime, which performs the coherence action — fetching a block, acquiring write permission, or invoking a handler — and returns to the instrumented code.

The coherence unit in Shasta is a 64-byte block, matching the cache line size, rather than a 4 KiB page. This eliminates most false sharing: two variables that are logically independent are unlikely to share a 64-byte block, and if they do, the cost is bounded by the block size rather than the page size. The protocol is write-invalidate with a distributed directory, and the state is held in a side table indexed by block address, so the instrumentation does not need to modify the data layout.

The instrumentation is inserted by a binary rewriting tool, which means Shasta can run unmodified source code compiled for a uniprocessor, as long as the binary is processed before execution. This is a significant practical advantage over source-level approaches, which require the programmer to use special annotations or a modified compiler. It also means the overhead is paid at every shared access, not just at the rare fault, which is the fundamental tradeoff: Shasta trades a large cost on a few accesses for a small cost on every access.

In practice, Shasta's overhead was around 1.5x to 2x on the applications it was tested with, which is a very different profile from the order-of-magnitude overheads that page-based systems could exhibit on fine-grained sharing. The tradeoff is that Shasta cannot support arbitrary pointer-based data structures as easily, because the instrumentation must be able to identify which accesses are shared, and that requires either static analysis or a conservative assumption that all accesses through a particular region are shared. Shasta handled this with a combination of compiler analysis and a runtime check that could fall back to a page-protection mode for regions the analysis could not classify. That hybrid — fine-grained checks where the analysis is confident, page protection where it is not — is the design that most modern software coherence systems have converged on, and it is the direct ancestor of the check-and-slow-path pattern used in today's language runtimes for garbage collection and for software transactional memory.

### From Software to Silicon: What SDSM Taught Hardware

The software DSM systems of the late 1980s and 1990s were not just an academic exercise in building shared memory on top of message passing. They were a forcing function for ideas that hardware multiprocessors eventually adopted, often after the software systems had demonstrated both the necessity and the feasibility of the mechanisms. The most direct transfer was the directory protocol. Hardware cache-coherent multiprocessors like the SGI Origin and the Stanford DASH used distributed directories to track sharers and owners, and the design space they explored — centralized versus distributed, full-map versus limited-pointer, owner-based versus sharer-based — mirrors the design space IVY and its successors explored in software. The difference is that hardware could afford to keep the directory in fast SRAM and consult it in parallel with the cache access, while software had to store the directory in main memory and consult it only on a fault.

Release consistency made a similar journey. The model was proposed for hardware, but its adoption was accelerated by the software systems that proved it was not just a theoretical relaxation but a practical necessity. When hardware designers saw that a software protocol could not afford to propagate every store eagerly, they recognized that their own protocols would face the same pressure as processor counts grew. The result was a generation of hardware that exposed acquire and release instructions, or that implemented fence semantics that matched the release consistency contract. The ARM and POWER architectures, with their weak memory models and explicit barrier instructions, are the descendants of that line of thinking, and the C++11 and Java memory models that standardized acquire-release semantics are the direct intellectual heirs.

The lazy propagation idea had a more subtle influence. In hardware, lazy release consistency is difficult to implement because the hardware must respond to a load immediately; it cannot defer the fetch until a synchronization point if the load itself is the synchronization point. But the insight that data should move only when it is needed, and that the set of needed data can be computed from happens-before information, reappears in hardware prefetching and in directory protocols that track sharing patterns. The vector timestamp, in particular, is a software construct that hardware approximates with more compact representations — the coarse vector, the linked list of sharers, the limited pointer scheme — because the full vector is too large to store per cache line.

The most important lesson that hardware took from SDSM was about granularity. Hardware coherence operates at cache-line granularity because that is the natural unit of transfer and the natural unit of state. SDSM systems showed that when the coherence unit is too large relative to the sharing pattern, the protocol becomes pathological, and they developed a rich set of techniques — multiple-writer protocols, diff-based propagation, adaptive protocol selection — to mitigate the problem. Hardware designers, facing the same problem at a smaller scale, responded with sectored caches, sub-block coherence, and adaptive replacement policies. The problem never disappears; it just moves to a different level of the memory hierarchy.

### The Compiler and the Runtime: Making Coherence Invisible

One of the persistent tensions in SDSM is the division of labor between the programmer, the compiler, and the runtime. The shared-memory programming model promises that the programmer does not need to think about coherence, but every real system requires someone to supply information that the hardware or the runtime cannot infer.

Munin made this explicit with its per-page protocol annotations. The programmer, or a profiling tool, had to tell the runtime whether a page was write-once, write-many, producer-consumer, reduction, or one of the other types. Get the annotation right and the protocol is efficient; get it wrong and the program is either slow or incorrect. This is a heavy burden, and it is the main reason Munin-style systems never achieved broad adoption outside the research community.

TreadMarks reduced the burden by making the protocol uniform: every page uses the same lazy release consistency mechanism, and the runtime infers the sharing pattern from the access faults. The programmer only has to insert the synchronization operations — barriers, locks, and the occasional explicit flush — that the model requires. This is a much smaller surface area for error, and it is why TreadMarks became the canonical SDSM system for a generation of researchers.

Shasta pushed the burden in a different direction: the compiler and the binary rewriter had to identify shared accesses and instrument them. The programmer wrote ordinary shared-memory code, but the toolchain had to be smart enough to find the accesses that needed checks. For pointer-based data structures, this is undecidable in general, so Shasta used a combination of static analysis and conservative runtime checks. The hybrid approach — precise instrumentation where possible, page protection as a fallback — is the pattern that modern systems use for garbage collection read barriers, for software transactional memory, and for language runtimes that need to track object references across a heap.

The deeper lesson is that the memory model is the interface between the programmer and the coherence mechanism. A strong model like sequential consistency requires the runtime to do more work on every access, because the ordering constraints are tighter. A weak model like release consistency allows the runtime to defer work, but it requires the programmer to use synchronization correctly. The choice of model is therefore a choice about where to put the complexity: in the runtime, which must be fast and correct, or in the programmer, who must be careful and informed. The industry's long-term trend has been to move complexity into the runtime and the hardware, and to give the programmer a model that is weak enough to be implementable but strong enough to be usable. Release consistency, and its acquire-release refinement, is the sweet spot that the field converged on.

Modern language runtimes face a similar division of labor. The Java memory model, for example, defines happens-before edges through synchronized blocks and volatile fields, and the runtime is responsible for inserting the necessary fences and for ensuring that the just-in-time compiler does not reorder accesses across those edges. The runtime does not use page faults, but it does use the same conceptual machinery: it tracks which threads have observed which writes, and it defers the propagation of writes until a synchronization point. The difference is that the granularity is an object field rather than a page, and the mechanism is a memory barrier rather than a page fault. The intellectual lineage is direct.

### Modern Descendants: RDMA, CXL, and Disaggregated Memory

The hardware substrate that SDSM was built on — Ethernet, ATM, Myrinet, and the early switched fabrics — has been replaced by RDMA over Converged Ethernet (RoCE), InfiniBand, and, increasingly, CXL. But the fundamental problem has not changed. A node still needs to access data that lives in another node's memory, and the cost of that access is still dominated by the round-trip latency of the interconnect and the software overhead of initiating and completing the transfer.

RDMA changes the calculus in an important way: it allows one node to read from or write to another node's memory without involving the remote CPU. This is a form of one-sided communication that maps naturally onto the shared-memory abstraction. A node can issue an RDMA read to fetch a cache line or a page, and the remote node's CPU is not interrupted. The result is a much lower latency than a message-passing send/receive pair, and a much lower CPU overhead. Systems like FaRM use RDMA to implement a distributed shared memory with a relaxed consistency model, and they achieve throughput and latency that would have been unimaginable for a software DSM running on 1990s hardware.

But RDMA does not eliminate the coherence problem. It eliminates the remote CPU from the data path, but it does not provide hardware coherence. Two nodes can still hold stale copies of the same data, and the protocol must still decide when to invalidate, when to fetch, and how to merge concurrent writes. The multiple-writer protocols and the release consistency model are still the right tools. In fact, RDMA makes lazy release consistency even more attractive, because the cost of a remote read is low enough that fetching data on demand is often cheaper than pushing it eagerly to nodes that may never use it.

CXL takes a different approach. It provides a cache-coherent interconnect between a host and attached devices, including memory expanders and memory pools. The coherence is provided by hardware, at cache-line granularity, and the memory appears to the host as ordinary physical memory. This is, in a sense, the hardware finally solving the problem that SDSM solved in software. But CXL introduces new challenges. The latency of a CXL memory access is higher than local DRAM — typically in the hundreds of nanoseconds — and the bandwidth is shared among all hosts attached to the same pool. The coherence protocol must handle the case where multiple hosts map the same memory region, and the hardware must decide how to handle conflicting accesses. The result is a system that looks more like a tightly coupled multiprocessor than a network of workstations, but the performance characteristics are closer to a NUMA system with a very slow remote node.

Disaggregated memory takes the idea further: memory is a separate resource, accessed over a network, and the compute nodes are stateless with respect to the data they operate on. This is the logical extreme of the SDSM vision, and it brings back the same questions. If the memory is remote, what is the coherence unit? If the network is the bottleneck, how do you avoid false sharing? If the memory model is relaxed, how do you ensure that synchronization is correct? The answers are still being worked out, but the vocabulary is familiar: release consistency, acquire-release semantics, diff-based propagation, and adaptive granularity.

The home problem, which TreadMarks solved by designating a home node for each page, reappears in disaggregated memory. If memory is a separate pool, who owns a cache line? If multiple compute nodes can write to the same line, who serializes the writes? Some systems push the coherence into the memory controller, which maintains a directory and invalidates copies on a write. Others push it into the compute nodes, which use explicit synchronization and one-sided RDMA writes to update the memory pool. The tradeoff is the same as it was in software: a centralized directory is simple but becomes a bottleneck, while a distributed directory scales but requires a way to find the current owner. The vector timestamp, or a compact approximation of it, is still the tool for tracking happens-before across nodes.

The most striking continuity is in the memory model. The C++11 and Java memory models, which are now the standard for concurrent programming, are direct descendants of the release consistency work. The `std::atomic` operations with `memory_order_acquire` and `memory_order_release` are the same acquire and release operations that Gharachorloo and his colleagues defined for DASH. The happens-before relation that they formalized is the same relation that TreadMarks used to compute which write notices to send. The fact that a 1990 paper on a hardware multiprocessor and a 1994 paper on a software DSM produced the same abstraction is not a coincidence. It is a sign that the abstraction is the right one: it captures the essential structure of concurrent access to shared data, independent of whether the coherence is implemented in hardware or software.

The page fault, as a mechanism, is gone from modern systems. RDMA and CXL do not trap on a remote access; they either succeed or they fail, and the software must handle the failure. But the page fault was never the point. It was a way to detect the first access to a shared region and to trigger the coherence action. Modern systems detect the first access through explicit calls, through compiler instrumentation, or through hardware page tables that map remote memory. The mechanism has changed; the problem has not. The granularity of coherence, the cost of propagation, and the memory model that determines what can be deferred are still the axes along which every design decision is made. The systems of the 1990s explored that design space thoroughly, and the systems of today are still living in the space they mapped.

## Scope Consistency and the Home-Based Middle Ground

Lazy release consistency computes happens-before precisely, but it can still over-approximate the set of pages that matter to a given synchronization operation. When a node acquires a lock, TreadMarks returns write notices for every page modified in any interval the acquirer has not observed, regardless of whether those pages are protected by that lock. The acquirer does not fetch the data until it touches the page, so the bandwidth cost is deferred, but the bookkeeping cost is not: the node must track a growing set of write notices, and the first access to each stale page still pays a fault. If a program uses many locks protecting disjoint data structures, acquiring one lock can mark pages from another lock's data as stale, creating a form of synchronization-induced false sharing.

Scope consistency, introduced by Liviu Iftode, Jaswinder Pal Singh, and Kai Li in 1996, addresses this by tying coherence to the scope of a synchronization operation rather than to the global happens-before relation. The model says that when a process acquires a synchronization object, it must see all writes made by processes that released the same synchronization object. Writes made under a different lock, or in a different scope, are not guaranteed to be visible. This is weaker than release consistency in the sense that it does not require a global ordering across all synchronization operations, but it is stronger than no consistency at all, and it matches the way most programs are actually written: locks protect data, and data protected by one lock is rarely accessed under another.

JIAJIA is the best-known implementation of scope consistency. It combines a home-based protocol with lazy propagation and diffs. Each page has a home node, which is responsible for maintaining the authoritative copy and for serializing writes. When a node writes a page, it records a write notice and computes a diff at release time, but the diff is sent to the home rather than broadcast to all sharers. When another node acquires a lock in the same scope, it contacts the home for the pages associated with that scope and applies the diffs it has not seen. The home-based design avoids the owner-location problem that plagues pure migration protocols, because the home never changes. It also makes the merge point explicit: the home is the single serialization point for writes to a page, which simplifies the diff application order.

The cost of scope consistency is that the programmer must associate data with synchronization objects, either explicitly or through a compiler analysis. In JIAJIA, this association is often implicit in the structure of the program: a lock protects a region of shared memory, and the runtime infers the scope from the lock's identity. When the association is wrong, the program can observe stale data, because the model does not guarantee visibility across scopes. This is the same tradeoff that entry consistency makes more aggressively, and it is the reason why scope consistency never displaced lazy release consistency as the default model for page-based systems. It is a useful middle ground: more precise than LRC when locks are used to partition data, and less demanding than entry consistency when the programmer is not willing to annotate every object.

## Entry Consistency and Object-Granularity Coherence

Entry consistency, proposed by Brian Bershad, Matthew Zekauskas, and Wayne Sawdon in 1993, pushes the association between data and synchronization to its logical conclusion. Every shared data object is associated with a synchronization variable, and the model guarantees consistency only for the data associated with the synchronization variable being acquired. When a thread acquires a lock, the runtime makes consistent exactly the objects protected by that lock; when it releases the lock, it makes the thread's writes to those objects visible. Data not associated with the lock is not affected.

The appeal of entry consistency is that it eliminates false sharing at the coherence level, not just at the page level. If two variables share a page but are protected by different locks, entry consistency can fetch and invalidate them independently, because the coherence unit is the object, not the page. The implementation typically uses per-object state and a runtime that intercepts lock and unlock operations. On a page-based system, the runtime can map objects to sub-page regions and use multiple page table entries or sub-page protection to enforce the association. This is complex, but it is the right granularity for programs that use fine-grained locking.

Orca took a different route to object granularity: it made shared objects a language-level construct. Orca programs declare shared objects and operate on them through methods, and the runtime implements coherence at the object level. The Orca runtime uses a directory-based protocol with ownership and broadcast invalidation, and it can replicate read-only objects widely while serializing writes through an owner. Because the coherence unit is the object, Orca avoids the page false-sharing problem entirely. It also avoids the need for the programmer to reason about pages or cache lines. The cost is that the program must be written in Orca, or in a language with comparable runtime support, and the runtime must be able to identify all shared accesses. Pointer-based data structures that cross object boundaries are difficult to support, because the runtime cannot easily track which object a pointer refers to without a level of indirection.

The object-based approach also changes the failure and reconfiguration story. In a page-based system, a node failure can leave a page without an owner, and the protocol must recover the page from replicas or from a checkpoint. In an object-based system, the runtime can migrate objects between nodes, and the coherence protocol can be integrated with object placement and load balancing. Orca exploited this to support dynamic load distribution, moving objects to idle nodes and updating the directory accordingly. The same idea reappears in modern actor systems and in distributed object stores, where the unit of coherence is an object or a key, and the runtime is responsible for routing operations to the current owner. The page, in these systems, is an implementation detail of the local memory allocator, not the unit of sharing.

## The Cost Model and the Limits of Lazy Propagation

The performance of any SDSM system can be understood through a simple cost model. Let a program execute in phases separated by synchronization operations. In each phase, a node performs some amount of local computation, touches some number of shared pages, and then synchronizes. The time per phase is roughly the sum of four terms: the computation time, the synchronization time, the fault-handling time, and the diff-propagation time. The computation time is fixed by the algorithm. The synchronization time is the cost of the barrier or lock operation itself, which in a software DSM includes a round trip to the synchronization manager and, in lazy protocols, the exchange of vector timestamps and write notices. The fault-handling time is the cost of trapping, sending a request, waiting for the response, and installing the page. The diff-propagation time is the cost of computing, sending, and applying diffs.

The key ratio is the number of shared pages touched per phase divided by the amount of computation per phase. If a phase computes for milliseconds and touches a handful of pages, the fault and diff costs are amortized and the system can approach the performance of message passing. If a phase computes for microseconds and touches hundreds of pages, the protocol overhead dominates and no amount of optimization in the diff encoding will save it. This is why SDSM systems performed well on SPMD applications with coarse-grained phases and poorly on irregular applications with fine-grained sharing. It is also why the choice of coherence unit matters so much: reducing the page size or using sub-page blocks reduces the number of distinct coherence units touched per phase, but it increases the number of faults and the size of the state tables. There is an optimal granularity for a given access pattern, and it is rarely the same for all pages in a program.

Lazy propagation improves the model by moving the diff cost off the critical path. In an eager protocol, every release sends diffs to all sharers, so the diff cost is proportional to the number of releases times the number of sharers. In a lazy protocol, diffs are sent only when a node acquires and then touches the page, so the cost is proportional to the number of actual consumers. If a page is written many times but read rarely, lazy propagation collapses many diffs into one. If a page is written once and read by everyone, lazy and eager are similar, except that lazy may need to gather diffs from multiple writers. The worst case for lazy propagation is a page that is written by many nodes and read by many nodes in alternating phases, because each reader must gather and merge diffs from all writers. This is the case where multiple-writer protocols can be slower than write-invalidate, and it is why some systems use adaptive protocols that switch between single-writer and multiple-writer modes based on observed access patterns.

Adaptive protocols, such as those explored in the Brazos and Cashmere systems, try to detect the sharing pattern at runtime and choose the protocol that minimizes overhead. A page that is written by one node and read by many is a candidate for write-once or producer-consumer. A page that is written by many nodes and read by none between barriers is a candidate for reduction or result. A page that is written by many nodes and read by many is a candidate for multiple-writer with diff merging, but if the diffs overlap frequently, the protocol may switch to write-invalidate to serialize the writers. The detection is based on counters: the number of write faults, the number of read faults, the number of invalidations, and the size of the diffs. The runtime adjusts the protocol type and, in some systems, the coherence granularity. The overhead of adaptation is small compared to the cost of a page fault, so the approach is practical when the sharing pattern is stable over long periods. When the pattern changes rapidly, the adaptation itself becomes a source of overhead, and the system may be better off with a single conservative protocol.

## Debugging and the Data-Race Assumption

Every SDSM system described so far assumes that the program is data-race-free: that all conflicting accesses to shared data are ordered by synchronization. This assumption is what allows the protocol to merge concurrent writes without defining a semantics for overlapping writes, and it is what allows the memory model to be as weak as release consistency. When the assumption is violated, the program may still produce a result, but the result is not guaranteed to be the same as it would be on a sequentially consistent machine. The protocol may merge diffs in an arbitrary order, or it may fetch a page from one node before another node's write has been applied, and the program can observe a state that no sequential execution would produce.

Debugging such bugs is difficult because the coherence mechanism is invisible. A data race may manifest as a wrong answer only when the timing of page faults and diff propagation happens to expose the stale value. Running the program again may produce a different result, or no error at all. The tools that help are the same ones used for shared-memory debugging, but they must be adapted to the distributed setting. Race detectors can instrument synchronization operations and shared accesses, but in a page-based system the instrumentation is at page granularity, so a race on two bytes of the same page may be reported as a race on the whole page. Some systems use the page fault mechanism itself as a detector: if two nodes take write faults on the same page without an intervening synchronization, the runtime can record the event and report a potential race. This is not a complete race detector, because it only catches races that cause faults, but it catches the common case where two nodes write the same page concurrently.

Performance debugging is a separate problem. A program can be correct and still slow because of false sharing, and the symptom is a high page fault rate that does not correspond to any logical communication. The standard technique is to instrument the runtime to record, for each page, which nodes accessed it and in what mode. If a page is written by multiple nodes in the same phase, and the writes are to disjoint byte ranges, it is a false-sharing candidate. The programmer can then pad the data structure, reorder fields, or change the data layout to separate the variables onto different pages. This is exactly the same advice that hardware cache-line false sharing produces, and it is a reminder that the page is just a larger cache line. The difference is that the cost of a false-sharing event in SDSM is a trap and a network round trip, not a cache miss, so the payoff from fixing it is correspondingly larger.

The data-race assumption also shapes the language and compiler support for SDSM. A compiler that can prove that a region of code is race-free can avoid instrumenting it, and a runtime that can detect races can warn the programmer before the program produces a wrong answer. The trend in modern systems is to combine a weak memory model with a race detector, so that the programmer gets the performance of release consistency and the safety of a sequentially consistent model when a race is present. This is the same combination that the C++ and Java memory models provide: they define the behavior of race-free programs precisely, and they leave racy programs with undefined or implementation-defined behavior, but they also provide tools that can detect the races. The SDSM systems of the 1990s did not have those tools, and that was one of the practical barriers to their adoption. The intellectual barrier was lower than the engineering barrier: the model was sound, but the debugging experience was not.
