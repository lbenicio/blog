## The instruction that pretends to be simple

`call` is one instruction. It pushes the address of the following instruction onto the stack and jumps to the target. `ret` pops that address and jumps back. Two instructions, no checking, no negotiation, no enforcement.

Everything else about a function call — which registers carry arguments, which ones the callee must preserve, where the return value lands, how much stack a function may scribble on below the stack pointer without asking permission, whether a `float` travels in a general-purpose register or a vector register — is a convention. The hardware does not know it exists. The kernel does not enforce it. If you get it wrong, you do not get a fault at the call site. You get a corrupted value three frames up the stack, or a `movaps` fault on a stack slot that was supposed to be 16-byte aligned, or a JIT that happens to work on your machine and miscompiles on someone else's.

That convention, on Linux, macOS, the BSDs, and most other Unix-like systems running on x86-64, is the System V AMD64 ABI — formally the *System V Application Binary Interface, AMD64 Architecture Processor Supplement*, usually shortened to "the psABI." It is a document of a few dozen pages that pins down far more than most engineers realize: register preservation, stack alignment, the red zone, variadic argument passing, structure classification, floating-point control state, the direction flag, and the layout of unwind tables.

This article walks through that contract from the bottom up. Not as a reference table to copy, but as a design: why the rules are what they are, where the sharp edges are, and what the whole thing costs on a modern out-of-order core. The ABI is one of the few places where compiler writers, kernel developers, debugger authors, and JIT engineers all have to agree, and the seams show.

## What an ABI is, and what it is not

It helps to separate three things that get conflated.

**The instruction set architecture** is what the CPU implements. It says `call` pushes a return address and that `movaps` requires a 16-byte-aligned operand. It says nothing about which register holds the first argument.

**The platform ABI** is the contract between separately compiled pieces of code. It says the first integer argument goes in `RDI`, that `RBX` belongs to the caller, and that a `struct` of a given shape travels in a given set of registers. It is a document, not a mechanism.

**The compiler's internal conventions** are whatever the compiler feels like doing for functions it can see. If a function is `static`, has internal linkage, and is never address-taken, the compiler is free to invent a bespoke calling convention for it — passing arguments in whatever registers are free, returning multiple values in whatever registers are convenient, and inlining aggressively enough that no call exists at all. Link-time optimization extends this freedom across translation units.

The ABI only becomes mandatory at *boundaries*: exported symbols in a shared library, function pointers passed to a library you do not control, callbacks from a C library into your code, system calls, signal handlers, and anything a debugger or unwinder needs to walk. Inside those boundaries, the ABI is a lower bound on what actually happens, not a description of it.

This distinction explains a class of confusing bugs. A function that reads a structure argument passed by a caller compiled with a different ABI assumption — say, a Windows-targeted object file linked into a Linux program, or a Rust `extern "C"` declaration that does not match the C definition — will not fail loudly. It will read the right *bytes* from the wrong *place*. The values will be plausible. The corruption will surface later, in a different function, with a stack trace that points nowhere useful.

## The register file as a contract

The x86-64 register file has sixteen general-purpose registers and, with AVX-512, thirty-two vector registers. The ABI splits the general-purpose set into two camps.

| Register | Role | Preserved across a call? |
|---|---|---|
| `RAX` | Return value, scratch | No (volatile) |
| `RBX` | Scratch | Yes (nonvolatile) |
| `RCX` | 4th integer argument, scratch | No |
| `RDX` | 3rd integer argument, 2nd return | No |
| `RSI` | 2nd integer argument | No |
| `RDI` | 1st integer argument | No |
| `RBP` | Frame pointer (conventionally) | Yes |
| `RSP` | Stack pointer | Yes (special) |
| `R8`–`R9` | 5th–6th integer arguments | No |
| `R10`–`R11` | Scratch | No |
| `R12`–`R15` | Scratch | Yes |
| `XMM0`–`XMM15` | Vector arguments and returns | No (all volatile) |

Two things stand out.

First, there are only **six nonvolatile general-purpose registers**: `RBX`, `RBP`, `R12`, `R13`, `R14`, `R15`. And `RBP` is usually consumed as a frame pointer unless the compiler is building with `-fomit-frame-pointer` (which is the default at most optimization levels on modern toolchains). So a function that wants to keep a value live across a call has, in practice, five registers to work with before it starts spilling to the stack.

Second, and more consequentially, **there are zero nonvolatile vector registers**. Every `XMM`, `YMM`, and `ZMM` register is caller-saved. Compare this to AArch64, where `v8`–`v15` are nonvolatile (at least their low 64 bits). The practical effect is that any floating-point or SIMD value that is live across a call must be spilled to memory, because the callee is entitled to destroy it. For code with heavy floating-point work interleaved with calls — numerical kernels that call into library routines, or generated code from a JIT that has not inlined aggressively — this is a real tax. Compilers respond by inlining, by sinking calls out of loops, and by hoisting the spill/reload pairs into the smallest possible live range.

The ABI also governs state outside the general-purpose and vector files. The x87 control word is nonvolatile; the x87 status word is volatile. The control bits of `MXCSR` are nonvolatile; the status bits are volatile. The direction flag `DF` in `RFLAGS` must be clear on function entry and must be clear on return — a function that sets it and forgets to clear it will break any `rep movs` in its caller, in ways that are extremely unpleasant to debug. None of this is enforced. It is checked, if at all, by conformance test suites and by the occasional valgrind-style tool.

## Eightbyte classification: how the compiler decides

Scalars are easy. An `int` goes in an integer register, a `double` goes in a vector register. Aggregates are where the ABI earns its reputation for complexity.

The classification algorithm works in units of **eightbytes** — eight-byte chunks — because that is the natural granularity of a 64-bit register. Each eightbyte of an argument is assigned a class from a small set: `INTEGER`, `SSE`, `SSEUP`, `X87`, `X87UP`, `COMPLEX_X87`, `MEMORY`, and `NO_CLASS`. The rules, paraphrased:

1. Scalars take their natural class. Integer and pointer types are `INTEGER`; `float`, `double`, and `__m64` are `SSE`; `long double` is `X87` + `X87UP`; `__m128` and wider vectors are `SSE` followed by `SSEUP`.
2. An aggregate is decomposed into eightbytes. Each eightbyte is classified by recursively classifying the fields that overlap it, then merging: `NO_CLASS` + *X* = *X*; `INTEGER` dominates `SSE`; `MEMORY` dominates everything.
3. If the aggregate contains unaligned fields, or is too large, the whole thing is `MEMORY`.
4. Post-merge cleanup: if any eightbyte is `MEMORY`, the entire argument is `MEMORY`. `X87UP` not preceded by `X87` becomes `MEMORY`. `SSEUP` not preceded by `SSE` becomes `SSE`.

The upshot, in the common case: an aggregate of **16 bytes or less** whose fields are naturally aligned is classified into at most two eightbytes and can travel in registers. Anything larger goes to memory. Vector types are the explicit exception the spec carves out, and with AVX-512 the classification extends to wider register classes — which is one reason the AVX-512 ABI story took years to settle.

A few examples make the consequences concrete:

- `struct { double x, y; }` — two `SSE` eightbytes. Passed in `XMM0` and `XMM1`. Effectively free.
- `struct { int a; double b; }` — one `INTEGER` eightbyte, one `SSE`. Passed in `RDI` and `XMM0`. Still free, but the two halves go to different register files.
- `struct { float a, b; }` — a single `SSE` eightbyte holding two packed floats. Passed in `XMM0`.
- `struct { int a, b; }` — a single `INTEGER` eightbyte. Passed in `RDI`, with the two halves in the low and high 32 bits.
- `struct { char buf[24]; }` — 24 bytes, three eightbytes, no vector exception applies. `MEMORY`. The caller copies it to the stack.

That last case is the one that bites. A 16-byte structure passed by value costs nothing beyond a register move. A 24-byte structure costs a `memcpy` at every call site, plus a stack adjustment, plus the risk of aliasing that prevents the compiler from keeping anything in registers. The difference between 16 and 17 bytes in a hot interface is not marginal; it changes the instruction mix.

## Where the arguments go

Once classified, arguments are assigned to registers from two independent streams.

**Integer-class arguments** consume `RDI`, `RSI`, `RDX`, `RCX`, `R8`, `R9`, in that order. **Vector-class arguments** consume `XMM0` through `XMM7`, in that order. The streams do not interfere: an integer argument does not consume a vector slot, and a vector argument does not consume an integer slot. So

```c
void f(int a, double b, int c, double d);
```

passes `a` in `RDI`, `b` in `XMM0`, `c` in `RSI`, and `d` in `XMM1`. This is the detail that trips up hand-written assembly most often, because the register numbers no longer line up with the argument positions.

When a stream runs dry, the remaining arguments of that class go on the stack. Stack arguments are laid out in memory in declaration order, which means the caller pushes them in reverse order before the `call`. At function entry, the return address sits at `[RSP]`, and the first stack argument sits at `[RSP+8]`. Each stack argument is padded to an eightbyte boundary; vector types that land on the stack are aligned to 16 bytes, which can introduce gaps.

The stack layout matters for more than argument passing. It is the reason a debugger can find arguments in a stack frame with no frame pointer, and the reason a variadic function can spill its register arguments into a contiguous block and walk them with a pointer.

## Where the return value goes

Returns are simpler, but the `MEMORY` class has a wrinkle.

An `INTEGER`-class return value goes in `RAX`, with a second eightbyte in `RDX`. An `SSE`-class value goes in `XMM0`, with a second eightbyte in `XMM1`. A mixed return — `struct { long a; double b; }` — uses `RAX` and `XMM0` simultaneously.

A `MEMORY`-class return is different. The caller allocates space for the result and passes its address in `RDI` as a hidden first argument. This shifts every subsequent integer argument down one register: what the source code calls the first argument is actually in `RSI`. The callee writes the result through that pointer and returns the pointer itself in `RAX`, which lets callers chain the operation. A function returning a large structure therefore has a signature that looks like a normal function but behaves like one with an extra leading pointer parameter — and the compiler will generate different code depending on whether it can see the definition and prove the pointer does not alias anything else.

That is the data movement. What remains is the part that actually costs: who must save what around a call, how much stack a function may touch below `RSP` without asking, why 16-byte alignment is non-negotiable, how variadic functions reconstruct their arguments, and what a `call` does to a modern out-of-order core's return-address predictor.

## The prologue is a negotiation, not a ritual

A function prologue often looks like a ritual: push the frame pointer, move the stack pointer into it, subtract a round number, and begin. But the ABI does not prescribe a prologue. It prescribes an observable result. When control returns to the caller, every nonvolatile register must contain the value it had at the call site. How the callee achieves that is its own business. It can push the old value at entry, save it only on the branch that actually uses it, spill it to a stack slot and reload before returning, or avoid the register entirely. Compilers exploit all of these. Shrink-wrapping moves the save and restore of a callee-saved register into the cold path, so a function that only touches `RBX` on an error path does not pay for it on the hot path. The prologue is accounting, and the compiler is free to do the accounting late.

The caller-saved and callee-saved split is also a division of labor, not a list of registers that `call` automatically saves. A caller-saved register is not destroyed by the call in any physical sense. It is simply not part of the callee's promise. If the caller needs the value after the call, the caller must preserve it. The callee may use every volatile register as scratch without saving anything. This is why the register allocator treats a call as a clobber of the volatile set: live values must migrate to nonvolatile registers, to the stack, or be recomputed afterward. The pressure this creates is easy to underestimate. The nonvolatile general-purpose set is small, and one member is often consumed as a frame pointer. A function with several values live across a call can run out of callee-saved registers quickly, and the spill code that follows is not visible in the source. It is a direct consequence of the contract.

The lack of nonvolatile vector registers has a sharper effect. Any `XMM`, `YMM`, or `ZMM` value that must survive a call has to be stored somewhere the callee will not touch, which in practice means memory. A numerical kernel that calls a library routine inside a loop may spend more instructions spilling and reloading vectors than doing arithmetic. Compilers fight this by inlining, by hoisting calls out of loops, by keeping live ranges short, and by converting scalar calls into vector-friendly forms. A JIT has the same obligation but less freedom to assume. If generated code keeps a packed value in `XMM6` across a call to a runtime helper, it is wrong, and the failure may only appear when the helper is recompiled with a different register allocation. The ABI does not care that the register looked untouched in testing.

The frame pointer is another place where convention and enforcement separate. `RBP` is callee-saved, but using it as a frame pointer is optional. Modern toolchains omit the frame pointer by default at optimization levels where unwind information is available. Debuggers and profilers then rely on `.eh_frame` and CFI directives rather than a chain of saved `RBP` values. A hand-written assembly function can execute perfectly and still ruin a backtrace if it adjusts the stack without describing the adjustment. The processor has no opinion. The unwinder does.

## Sixteen bytes, or the machine will remind you

The stack alignment rule is one sentence long and responsible for a remarkable number of crashes in hand-written assembly. Immediately before a `call`, `RSP` must be a multiple of 16. The `call` pushes an eight-byte return address, so at the first instruction of the callee, `RSP` is congruent to 8 modulo 16. A leaf function that never calls anything can ignore this. A function that calls another function cannot. It must arrange, before its own `call`, for `RSP` to be a multiple of 16 again.

The conventional prologue makes this automatic. Pushing `RBP` moves `RSP` from 8 modulo 16 to 0 modulo 16. Subtracting a multiple of 16 for locals keeps it there. If a function pushes an odd number of callee-saved registers, it needs an extra eight-byte adjustment before the next call. Compilers track this precisely. Hand-written code often does not, and the resulting misalignment may not fail at the call site. It fails later, when the callee executes a `movaps` to a stack slot that the compiler assumed was aligned. The fault address looks like a random local variable. The actual bug is an arithmetic mistake in a prologue written three functions away.

Alignment is not only about `movaps`. The ABI requires the stack argument area to be aligned appropriately, and wider vector arguments passed on the stack raise the requirement. The exact boundary depends on the widest type in the argument area, and the compiler inserts padding to satisfy it. That padding is part of the call sequence. It changes the offsets of stack arguments, which is why a debugger reading arguments from a stack frame needs the ABI rules and not just a dump of memory. It is also why a function that uses `alloca` or a variable-length array must preserve alignment after every adjustment. The stack pointer is not just a cursor. It is an invariant that every generated aligned access depends on.

## The red zone is a 128-byte secret between leaf functions

Below the stack pointer there is a region the ABI reserves for the current function: 128 bytes that a leaf function may use without adjusting `RSP`. This is the red zone. It exists so that small leaf functions can store a few temporaries at negative offsets from `RSP` without paying for a stack adjustment and without disturbing the caller's frame. Signal handlers and interrupt delivery must not clobber it, so a function can use it even though asynchronous events may arrive while it runs.

The red zone is not a scratch area that survives a call. The moment a function calls another function, the callee is entitled to build its own frame, and the bytes below the caller's `RSP` become part of the callee's territory. A value stored in the red zone across a call is not preserved by any rule. Compilers therefore use the red zone only for leaf functions, or for values whose live range ends before the call. Kernel code often disables red-zone use entirely because interrupt entry has different assumptions, and a kernel stack is not an ordinary user-space stack. The red zone is a small optimization with a sharp boundary: it belongs to the function that has not yet called anyone.

## Variadic functions are where the ABI leaves breadcrumbs

A variadic function such as `printf` cannot know its argument types from its signature. The ABI solves this by making the caller leave enough information for the callee to reconstruct the argument list. The key hidden detail is `AL`. For a call to a variadic function, the caller sets `AL` to the number of vector registers used to pass arguments. This is not the number of variadic arguments and not the number of floating-point values in the source. It is the count of vector registers consumed by the call, and it lets the callee know how many `XMM` registers contain live argument data.

The callee's prologue, if it will use `va_start`, saves the argument registers into a register save area. The general-purpose argument registers and the vector argument registers are spilled into a contiguous block. The `va_list` object then records four things: how far the general-purpose register save area has been consumed, how far the vector save area has been consumed, where the overflow arguments begin on the stack, and where the register save area itself lives. Each `va_arg` checks the offsets. If the requested class still has a register available, it loads from the save area and advances the offset. If not, it reads from the overflow area, which points at the stack arguments above the return address.

This design explains several otherwise strange behaviors. A variadic function that never calls `va_start` can skip the register saves, because the compiler can see that the breadcrumbs are never used. A variadic function that does call `va_start` pays for saving registers it may not need, because the callee cannot know which ones the caller actually populated. Default argument promotions apply before the call: `float` becomes `double`, and small integer types become `int`, so the callee's `va_arg` sees the promoted type rather than the source type. And the format string is not part of the ABI. It is the only thing that tells `printf` how to interpret the bytes the ABI faithfully delivered.

## What `call` really costs

At the instruction level, a direct `call` is cheap. It pushes a return address and changes the instruction pointer. A direct `ret` pops the address and jumps back. In isolation, both are small. On a modern out-of-order core, however, the cost is not the two instructions. It is the machinery around them.

The return address is a store to memory, and the stack engine has to track it. The `ret` is an indirect branch, even though its target is sitting on the stack, so the processor predicts it with a return-address stack. A `call` pushes the predicted return address onto that stack; a `ret` pops it. As long as calls and returns are properly nested and the predictor has room, returns are cheap and speculative execution continues past them. Deep recursion, hand-built stacks, `setjmp` and `longjmp`, and generated code that manipulates `RSP` without matching call and return structure can all confuse the predictor. A mispredicted return flushes the pipeline and turns a two-instruction sequence into a measurable stall.

Indirect calls are more expensive because the target is not encoded in the instruction. The processor must predict the destination through a branch target buffer or a similar structure. A call through a function pointer that alternates between many targets can mispredict repeatedly. Security mitigations make this worse: retpolines and related schemes deliberately replace indirect branches with return-based trampolines so that speculative execution cannot be steered into a gadget. The ABI does not require any of this. The compiler and the operating system choose the mitigation, and the cost appears in profiles that look like ordinary function calls.

There is also the cost that never appears as a `call` instruction: the spills, the argument marshalling, the stack stores for arguments that did not fit in registers, and the lost optimization opportunities that inlining would have removed. A call is a boundary where the compiler must assume the callee can observe memory, clobber volatile registers, and change control flow. That boundary is the point of the ABI, and it is also the reason a profiler can show a function call as cheap while the surrounding code pays for it.

## The unwinder reads the contract too

The ABI is not only a contract for calls that return normally. It is also the only thing that makes it possible to reconstruct machine state when execution is interrupted — by an exception, a signal, a debugger breakpoint, or a profiler sampling the stack. Every function that adjusts `RSP` is implicitly describing a small state machine: at this instruction, the caller's return address is at this offset; at that instruction, `RBX` has been saved at this other offset. The processor does not read that description. The unwinder does.

On ELF platforms, that description lives in `.eh_frame`, a compact DWARF-like table of Call Frame Information. Compilers emit it automatically, but hand-written assembly does not get it for free. A function that pushes `RBP`, subtracts from `RSP`, and later restores both will execute correctly and still break every backtrace, every C++ exception that tries to propagate through it, and every sanitizer that walks the stack. The fix is a handful of assembler directives: `.cfi_startproc`, `.cfi_def_cfa_offset`, `.cfi_offset`, `.cfi_restore`, `.cfi_endproc`. These do not generate instructions. They generate metadata. They are the assembly programmer's half of the ABI's unwinding contract.

The unwinder is not a niche tool. It is what `backtrace()` calls, what `perf` uses to attribute samples, what AddressSanitizer walks to find stack variables, what `gdb` uses to print frames, and what the C++ runtime uses to find `catch` clauses. A JIT that generates code without registering unwind information can run fast and then fail the moment an exception crosses a JIT frame. The usual remedy is `__register_frame` or an equivalent runtime hook, but that only works if the JIT knows the ABI's stack layout well enough to describe its own frames. The contract does not end at `ret`. It extends to every asynchronous event that can arrive while the function is still on the stack.

## System calls are a different calling convention

A system call on x86-64 is not a function call. It is the `syscall` instruction, and it uses a convention that shares registers with the System V ABI but is not the same contract. The syscall number goes in `RAX`. The first six arguments go in `RDI`, `RSI`, `RDX`, `R10`, `R8`, and `R9` — note `R10` where the function-call ABI would use `RCX`. The `syscall` instruction itself clobbers `RCX` and `R11`, because the hardware uses them to save the return instruction pointer and `RFLAGS`. The result comes back in `RAX`, with negative values encoding errors rather than a separate error register.

There is no stack argument area for a system call. The kernel entry path does not read arguments from the user stack, and it does not preserve the user stack beyond what the syscall semantics require. If a system call needs more than six arguments, it takes a pointer to a structure. This is why `clone`, `mmap`, and `futex` have the shapes they do. The libc wrapper around a syscall is ordinary System V code: it loads `RAX` with the number, arranges the argument registers, executes `syscall`, checks the result, and translates a negative value into `errno` and `-1`. The wrapper obeys the ABI. The kernel entry point does not.

Signal handlers sit on the boundary between the two worlds. When a signal is delivered, the kernel builds a frame on the user stack that contains the interrupted register state, the signal mask, and a return trampoline. It then calls the handler using the System V ABI: the signal number in `RDI`, a pointer to `siginfo_t` in `RSI`, and a pointer to the `ucontext_t` in `RDX`. If the handler returns normally, it returns to the trampoline, which invokes `rt_sigreturn` to restore the interrupted state. The kernel is careful not to clobber the 128-byte red zone below the interrupted `RSP`, because the ABI promises that leaf functions may use it. That promise is enforced by the kernel, not by the hardware, and it is one of the few places where the ABI is actively defended by the operating system.

## Where FFI and JITs meet the contract

Foreign-function interfaces are where the ABI stops being an implementation detail and becomes an API. When C++ calls a C function, when Rust calls a C library, when Python calls into a native extension, or when a JIT calls a runtime helper, the two sides must agree on the same register assignment, the same structure classification, and the same preservation rules. C++ name mangling is part of the platform ABI, but the System V psABI does not fully specify it; the Itanium C++ ABI does. Rust's `extern "C"` and `#[repr(C)]` exist precisely to opt out of Rust's unspecified layout and into the platform's contract.

ABI mismatches in FFI code are rarely loud. A `bool` that is one byte in one language and four bytes in another will still pass a value. A structure with a `long double` field may be classified as `X87` by one compiler and `MEMORY` by another. A bitfield layout that one compiler packs differently will produce plausible but wrong values. A function returning a large structure may use a hidden pointer in one convention and registers in another. The call succeeds. The bug appears later, when the wrong bytes are interpreted as a pointer or a length. This is why cross-language interfaces are usually written in terms of scalars and opaque pointers, and why a structure that crosses an FFI boundary is often passed by pointer even when it is small enough to fit in registers.

JITs have more freedom and more responsibility. Inside a single JIT-compiled function, the JIT may invent any convention it likes: arguments in whatever registers are convenient, multiple return values, custom stack layouts. The moment that code calls out to the runtime, accepts a callback from C, or exposes an entry point to the embedder, it must obey the platform ABI exactly. Libraries like `libffi` exist to encode the ABI as data: they build a call frame dynamically, place arguments according to the classification rules, invoke the target, and extract the return value. A JIT that reimplements `libffi` badly will work until it encounters a structure with mixed integer and vector fields, or a variadic function, or a platform where the ABI was revised.

It is useful to remember that System V is not the only answer. Windows x64 passes the first four integer arguments in `RCX`, `RDX`, `R8`, and `R9`, and the first four vector arguments in `XMM0` through `XMM3`. It requires the caller to reserve 32 bytes of shadow space above the return address. It has no red zone. It makes `XMM6` through `XMM15` nonvolatile, which gives vector-heavy code a place to keep live values across calls that System V does not provide. Every one of those choices is a trade-off. The System V ABI chose a larger set of argument registers and a red zone; Windows chose a simpler prologue and nonvolatile vector registers. Neither is enforced by the CPU. Both are enforced by agreement.

## Tail calls and the shape of the stack

A tail call is a function call in the final position of another function, where the caller has nothing left to do after the callee returns. The ABI does not require compilers to optimize tail calls, but it permits them, and the optimization is simple in principle: restore the caller's frame, restore any callee-saved registers, leave `RSP` exactly where it was at function entry, and `jmp` to the callee instead of `call`ing it. The callee then returns directly to the original caller. The intermediate frame never exists.

This is not just an instruction-count optimization. It changes the shape of the stack. A recursive function that tail-calls itself can run in constant stack space, because each call replaces the current frame rather than adding a new one. A chain of tail calls produces a backtrace that omits every intermediate function. Profilers may attribute the callee's time to the original caller, or show a frame that the source-level call stack never contained. Debuggers may print a note about a tail call, or may simply lose the connection. The ABI allows this because the observable behavior at the boundary is preserved: the callee sees the same argument registers, the same stack alignment, and the same return address that the original caller would have provided.

For the transformation to be valid, the caller must not need the red zone after the tail call, must not need to inspect the return value, and must leave `RSP` in the state the callee expects at entry. That means the return address must still be on the stack, and `RSP` must be congruent to 8 modulo 16 if the callee is a normal System V function. The caller's own callee-saved registers must already be restored. If any of those conditions fail, the compiler must emit a real `call` followed by a `ret`. Clang's `musttail` attribute lets a programmer require the optimization and turns a missed tail call into a compile-time error, but the underlying constraints are the ABI's, not the attribute's.

## Stack probes, stack clash, and large frames

A function with a large local array subtracts a large constant from `RSP` in its prologue. If the array is large enough, the first write to the bottom of the array can jump over the guard page that the kernel placed below the stack. The write lands in unmapped memory, the kernel delivers a `SIGSEGV`, and the process dies. This is stack clash, and it is not a bug in the ABI. It is a consequence of the fact that the ABI lets a function move `RSP` by an arbitrary amount without touching the pages in between.

Compilers defend against this with stack probes. Instead of subtracting the full frame size and then writing, the prologue touches each page in the new frame, often with a single `orq $0, (%rsp)` after each adjustment. The exact sequence is target-specific and controlled by flags such as `-fstack-clash-protection`. The probes are not part of the ABI, but they are part of the platform's expectations: a function that skips them may work in testing and fail when the stack is nearly exhausted. The red zone complicates the picture, because a leaf function may legally use 128 bytes below `RSP` without probing. A non-leaf function has no such permission, and a function that uses `alloca` or a variable-length array must probe after every dynamic adjustment.

Dynamic stack allocation also breaks the simple unwinding model. If `RSP` moves by an amount that is not known at compile time, the compiler cannot encode the frame offset as a constant in `.eh_frame`. It must use a DWARF expression — `DW_CFA_def_cfa_expression` — that describes how to recover the caller's stack pointer from the current register state. Hand-written assembly that uses `alloca` and omits that expression will execute correctly and then confuse every unwinder that tries to walk past it. The ABI's stack rules are not just about where arguments go. They are about making the stack describable at every instruction where an asynchronous event might arrive.

## AVX-512 and the vector ABI's moving target

AVX-512 expanded the vector register file from sixteen `XMM` registers to thirty-two `ZMM` registers and added eight opmask registers, `k0` through `k7`. The System V ABI classifies all of them as volatile. There are still no nonvolatile vector registers, and there are no nonvolatile mask registers. A function that keeps a live `__m512` value across a call must spill it to memory, just as it would with `__m128`. The wider registers change the cost of the spill, but not the rule.

The ABI also has to manage the transition between legacy SSE code and AVX code. If a function uses `YMM` or `ZMM` registers and returns to a caller that uses legacy SSE instructions, the processor may incur a penalty when the caller touches the upper halves of the vector registers. The recommended remedy is `vzeroupper` before returning. This is not a correctness requirement in the same way that preserving `RBX` is; it is a performance contract that compilers follow so that code compiled with different vector-width assumptions can coexist. It is a reminder that the ABI is a living document. New instruction sets add new state, and the document has to say who owns it.

That process is not always smooth. AVX-512 adoption required compilers, operating systems, and debuggers to agree on how the wider registers appear in core dumps, how they are saved in signal frames, and how they interact with context switching. Intel AMX added tile registers and a tile configuration that the kernel must manage per thread, and the ABI has had to grow to describe it. Each addition is a new clause in the contract, and each clause has to be implemented by every compiler, every runtime, and every tool that walks a stack or inspects a register. The hardware does not enforce any of it. The agreement does.

## When the contract is broken: a taxonomy of failure modes

ABI violations do not produce a single class of bug. They produce a spectrum. At one end are immediate faults: a misaligned `movaps` to a stack slot, a `ret` to a corrupted return address, a `syscall` with the wrong argument register that returns `-EFAULT`. These are the easy cases, because the failure is close to the mistake. At the other end are silent corruptions: a callee that clobbers `RBX` and returns, leaving the caller with a wrong pointer that is only dereferenced a thousand instructions later; a structure passed by value that is classified differently by two compilers, so the callee reads a length field from the low half of an `XMM` register; a JIT that assumes `XMM6` is preserved because it happened to be preserved in one build of the runtime.

The middle of the spectrum is occupied by bugs that only appear under specific conditions. A function that uses the red zone and then calls another function may work until the callee happens to use the same 128 bytes. A tail call that misaligns the stack may work until the callee executes a vector instruction that requires 16-byte alignment. A variadic function that forgets to set `AL` may work until the caller passes a floating-point argument in `XMM0` and the callee's `va_arg` reads from the general-purpose save area. These bugs are not caught by the linker, the loader, or the CPU. They are caught by tests, by sanitizers, by comparing generated assembly, or by reading the psABI carefully enough to notice the clause that applies.

The contract is enforced by nothing but agreement, and the agreement is only as strong as the weakest implementation. That is why the ABI document is worth reading even when the compiler seems to handle everything. The compiler handles the cases it knows about. The cases it does not know about — a new type, a new register class, a new platform revision, a hand-written assembly stub, a JIT that generates code at runtime — are exactly where the contract has to be understood rather than assumed.

## The call that goes through a table: PLT, GOT, and lazy binding

When a function in one shared library calls a function in another, the caller does not know the callee's address at link time. The address depends on where the dynamic linker places the library in the process's address space, which can vary between runs. The System V ABI solves this with position-independent code and a pair of tables: the Global Offset Table (GOT) and the Procedure Linkage Table (PLT). The result is that a call to an external function is not a direct `call` to the function's entry point. It is a `call` to a PLT stub, which jumps through a GOT entry. On the first call, that GOT entry points back into the dynamic linker, which resolves the symbol and patches the table. On subsequent calls, the GOT entry holds the real address, and the overhead is an indirect jump and a memory load.

The ABI specifies the layout of these tables and the calling convention for the resolver. A PLT entry is a small sequence of instructions. For a function `foo`, the entry might look like:

```asm
foo@plt:
    jmp *foo@GOTPCREL(%rip)
    push $index
    jmp .plt0
```

The first instruction is an indirect jump through the GOT. If the GOT entry has not been resolved, it points to the `push` instruction, which pushes an index into the relocation table and jumps to the common PLT resolver stub, `.plt0`. That stub saves the argument registers, loads the address of the link map, and calls `_dl_runtime_resolve`. The resolver looks up the symbol, writes the real address into the GOT, restores the argument registers, and jumps to the target. The next time the PLT entry is executed, the GOT entry holds the real address, and the `jmp` goes directly to the function.

This lazy binding is a performance optimization: it defers the cost of symbol resolution until the function is actually called. But it adds overhead to every call. The indirect jump is predictable if the target is stable, but it still consumes a branch target buffer entry. The memory load from the GOT is usually a cache hit, but it is an extra memory access. For hot functions, this overhead is measurable. Compilers and linkers offer alternatives. `-Wl,-z,now` (or `LD_BIND_NOW=1`) forces eager binding, resolving all symbols at load time. This removes the lazy binding overhead but increases startup time. `-fno-plt` changes the call sequence to load the function address directly from the GOT and call it indirectly, skipping the PLT stub entirely. This is faster on modern processors because it avoids the extra jump, but it requires the GOT entry to be resolved eagerly or via a different mechanism.

The ABI's role here is subtle. It does not mandate lazy binding; it specifies the interface between the PLT, the GOT, and the dynamic linker. The `_dl_runtime_resolve` function is called with a specific convention: the index is passed on the stack, the argument registers are preserved, and the resolver returns by jumping to the target. This is a function call that does not look like a normal function call. It is a contract between the compiler, the linker, and the dynamic linker, and it is enforced by agreement. A hand-written assembly function that calls an external symbol must use the PLT correctly, or it will fail to link or crash at runtime. The ABI document describes the PLT's structure, but the details are often left to the platform's linker and dynamic linker implementations.

The GOT is also a target for security exploits. If an attacker can overwrite a GOT entry, they can redirect a function call to arbitrary code. This is why modern systems use RELRO (Relocation Read-Only), which makes the GOT read-only after relocation. Full RELRO resolves all symbols at load time and marks the GOT read-only, at the cost of startup time. Partial RELRO leaves the GOT writable but places it after the BSS, making it harder to exploit. The ABI does not require RELRO, but the layout it specifies makes it possible. The design of the PLT and GOT is a trade-off between flexibility, performance, and security, and the ABI is the document that records the agreed-upon shape.

## Thread-local storage: the ABI's hidden register

Thread-local storage (TLS) gives each thread its own copy of a variable. The System V ABI designates a segment register for TLS: on x86-64 Linux, `FS` points to the thread control block (TCB). The TCB contains a pointer to the dynamic thread vector (DTV) and the thread's TLS blocks. Accessing a TLS variable requires knowing the offset of the variable within the TLS block, which depends on the TLS model. The ABI defines four models: general dynamic, local dynamic, initial exec, and local exec. Each model has a different cost and a different set of assumptions.

The general dynamic model is the most flexible and the most expensive. It works for any variable, including those in shared libraries that may be loaded at runtime. To access a variable, the compiler emits a call to `__tls_get_addr` with a pointer to a `tls_index` structure. The `tls_index` contains the module ID and the offset within the module's TLS block. `__tls_get_addr` looks up the module's TLS block for the current thread and returns the address of the variable. This is a function call with its own ABI: the argument is in `RDI`, the result is in `RAX`, and the call may clobber volatile registers. The overhead is significant, so compilers try to use a more efficient model when possible.

The local dynamic model optimizes multiple accesses to the same module. Instead of calling `__tls_get_addr` for each variable, the compiler calls it once to get the base address of the module's TLS block, then accesses variables at fixed offsets from that base. This is cheaper but still requires a function call.

The initial exec model assumes the module is loaded at program startup and its TLS block is allocated at a fixed offset from the thread pointer. The compiler emits a `mov %fs:offset, %rax` instruction. This is fast, but it only works for variables in the main executable or in libraries loaded at startup.

The local exec model is the fastest. It is used for variables in the main executable that are not exported. The compiler emits `mov %fs:offset, %rax` directly, with no indirection. The offset is known at link time. This is the model used for `errno` in glibc, which is why `errno` is a macro that expands to a TLS access.

The ABI specifies the layout of the TCB, the DTV, and the `tls_index` structure. It also specifies the calling convention for `__tls_get_addr`, which is a normal System V function call. The dynamic linker is responsible for allocating TLS blocks for each thread and setting the `FS` base. When a new thread is created, the kernel and the threading library cooperate to allocate the TLS block and set the segment register. The ABI does not specify how the kernel does this, but it specifies what the user-space code expects to find at `FS:0`.

TLS access is a good example of the ABI's reach. It is not just about function calls; it is about the layout of per-thread data and the register that points to it. A function that uses TLS must obey the ABI's rules for the segment register, and a library that exports a TLS variable must ensure its layout matches the ABI's expectations. Mismatches here can cause subtle bugs, such as a variable being read from the wrong offset, or a thread seeing another thread's data. The ABI is the contract that prevents this, and it is enforced by the compiler, the linker, and the dynamic linker working together.

## Exceptions are a function call in disguise

C++ exceptions are often described as a zero-cost abstraction: you pay nothing when no exception is thrown. That is true at the instruction level, but it is not true at the ABI level. The ABI specifies a complex mechanism for propagating exceptions, and that mechanism relies on the same stack layout, register preservation, and unwinding metadata that ordinary function calls use. When an exception is thrown, the runtime library calls `__cxa_throw`, which initiates a two-phase unwinding process. In the first phase, the unwinder walks the stack, looking for a frame that can handle the exception. In the second phase, it unwinds the stack to that frame, running destructors along the way.

The unwinder uses the `.eh_frame` section to find the return address and the saved registers for each frame. It also uses the `.gcc_except_table` section, which contains a language-specific exception handling table. This table maps instruction ranges to landing pads — code that knows how to handle the exception. The unwinder calls a personality routine for each frame. The personality routine is a function provided by the language runtime (e.g., `__gxx_personality_v0` for C++). It inspects the exception and the frame's exception table to decide whether the frame can handle the exception. If it can, the unwinder transfers control to the landing pad. If not, it continues unwinding.

The ABI specifies the calling convention for the personality routine and the landing pad. The personality routine is called with the exception object, the context, and the frame's exception table. It returns a disposition that tells the unwinder what to do. The landing pad is entered with specific registers set: the exception object is in `RAX`, and the selector is in `RDX`. The landing pad then executes the appropriate catch block or cleanup code. This is a function call in disguise: the unwinder is calling into the frame's code, and the frame's code must obey the ABI's register and stack rules.

The cost of an exception is the cost of this unwinding process. It involves walking the stack, reading the `.eh_frame` and `.gcc_except_table` sections, and calling personality routines. This is why exceptions are expensive when thrown, but free when not. The ABI makes this possible by requiring every function to have unwind information and by specifying the format of that information. A function compiled without unwind information (e.g., with `-fno-asynchronous-unwind-tables`) will break exception propagation. A hand-written assembly function that does not provide CFI directives will cause the unwinder to lose its place. The ABI's unwinding contract is as important as its calling contract, and it is enforced by the same agreement.

## The ABI and modern security: CET, shadow stacks, and the end of the free lunch

For decades, the return address on the stack was just another value. An attacker who could overwrite it could redirect execution. The ABI's rule that `call` pushes the return address and `ret` pops it was a convention, not a protection. Intel's Control-flow Enforcement Technology (CET) changes that by adding a shadow stack: a separate stack that stores return addresses and is protected from normal memory writes. When CET is enabled, a `call` pushes the return address onto both the regular stack and the shadow stack. A `ret` pops from both and compares them. If they differ, the processor raises a control-protection fault. This is a hardware enforcement of the ABI's return address convention.

CET also adds indirect branch tracking. Every function that can be called indirectly must start with an `endbr64` instruction. The processor tracks indirect calls and jumps, and if the target does not begin with `endbr64`, it raises a fault. This prevents attackers from jumping into the middle of a function or into a gadget. The ABI has been updated to require `endbr64` at the start of functions that are address-taken. Compilers emit it by default when CET is enabled. This adds a four-byte instruction to every such function, but it is a small price for a significant security improvement.

The shadow stack changes the cost of a `call`. A `call` now writes to two stacks, and a `ret` reads from two. The shadow stack is typically stored in a separate memory region and is not directly accessible to user code. The processor manages it with new instructions like `rdsspq` and `wrssq`. The ABI specifies how the shadow stack is set up and how it interacts with signals, exceptions, and context switches. The kernel must save and restore the shadow stack pointer on context switches, and signal handlers must be careful not to corrupt it. This is a new chapter in the ABI, and it is still being standardized.

The ABI's role in security is not new. The red zone, the direction flag, and the register preservation rules all have security implications. But CET is the first time the hardware actively enforces a part of the ABI. The return address is no longer just a value on the stack; it is a value that the processor checks. This changes the threat model for exploits and the design of compilers and runtimes. It also adds a new clause to the contract: a function that manipulates the stack must do so in a way that keeps the shadow stack consistent. A hand-written assembly function that uses `push` and `pop` without updating the shadow stack will fault. The ABI document now has to describe this, and every tool that generates code must follow it.

The contract is still enforced by agreement, but now the agreement is backed by silicon. The hardware does not know the ABI, but it knows the shadow stack. The ABI tells the compiler how to use it. The result is a stronger contract, but also a more complex one. The anatomy of a function call now includes the shadow stack, and the cost of `call` includes the shadow stack write. It is a reminder that the ABI is not static. It evolves with the hardware, and each evolution adds new rules that must be understood.

## The long double and complex number corner

The System V ABI's eightbyte classification has special cases for `long double` and complex numbers. On x86-64, `long double` is the 80-bit extended precision format, stored in 16 bytes (with 6 bytes of padding). It is classified as `X87` and `X87UP`. The `X87` class means it is passed in the x87 register stack, not in `XMM` or general-purpose registers. The `X87UP` class is for the upper eightbyte, which contains the padding. When a `long double` is passed as an argument, it consumes two eightbytes: the first is `X87`, the second is `X87UP`. The ABI requires that `X87UP` be preceded by `X87`; otherwise, it is treated as `MEMORY`. This means a `long double` is passed on the stack, not in registers, because the x87 register stack is not used for argument passing. The classification is `X87` and `X87UP`, but the rules for argument passing say that if the class is `X87`, the argument is passed in memory. So `long double` is always passed on the stack. This is a significant performance penalty compared to `double`, which goes in `XMM` registers. It is one reason why `long double` is rarely used in performance-critical code.

Complex numbers are even more intricate. A `_Complex double` is two `double` values, so it is classified as two `SSE` eightbytes and passed in two `XMM` registers. A `_Complex long double` is two `long double` values, which would be four eightbytes, but the ABI classifies it as `COMPLEX_X87` and passes it in memory. The rules for complex numbers are specified in the ABI and are a common source of confusion. For example, a `_Complex float` is two `float` values, which fit in a single `SSE` eightbyte, so it is passed in one `XMM` register. A `_Complex double` takes two `XMM` registers. A `_Complex long double` is passed in memory. These rules matter for FFI and for code that uses complex arithmetic. They are a reminder that the eightbyte classification is not just about size; it is about the register file and the calling convention's history.

## Wide integers and the eightbyte merge

The `__int128` type is a 128-bit integer, which is two eightbytes. Both eightbytes are classified as `INTEGER`. It is passed in two general-purpose registers: the low eightbyte in the first available integer register, the high eightbyte in the next. If there are not enough registers, it goes on the stack. The return value is in `RAX` and `RDX`. This is straightforward, but it interacts with the register allocation. A function that takes an `__int128` and several other integer arguments may run out of registers quickly. The ABI does not provide a way to pass a 128-bit integer in a vector register, even though `XMM` registers are 128 bits wide. This is because the `INTEGER` class is separate from the `SSE` class. The choice to use general-purpose registers for integers, even wide ones, is a deliberate design decision. It keeps the integer and vector register files separate, which simplifies the classification but can lead to register pressure.

Bitfields are another area where the ABI's rules have sharp edges. A bitfield's layout is implementation-defined, but the System V ABI specifies how bitfields are packed into storage units. The classification of a structure containing bitfields depends on the underlying types and the bit offsets. A bitfield that straddles an eightbyte boundary can cause the entire structure to be classified as `MEMORY`, even if it is small. This is because the eightbyte classification works on byte boundaries, and a bitfield that crosses a boundary cannot be cleanly assigned to one eightbyte. The ABI's rules for bitfields are complex and are a common source of ABI mismatches between compilers. For example, GCC and Clang may lay out bitfields differently in some cases, leading to incompatible structures. This is why bitfields should be avoided in FFI interfaces. The ABI document specifies the rules, but the rules are intricate enough that even compiler writers sometimes get them wrong.

Unions are classified by merging the classes of their members. If a union contains both an `INTEGER` and an `SSE` member, the merged class is `INTEGER`. If it contains a `MEMORY` member, the whole union is `MEMORY`. This is consistent with the merge rules, but it means that a union's classification can change if a new member is added. A union that is passed in registers today might be passed in memory tomorrow if a new member is added. This is a subtle ABI compatibility issue. The ABI does not guarantee that adding a member to a union preserves the calling convention. This is another reason why unions are often passed by pointer in stable interfaces.

## Half-precision and the vector ABI's expansion

The `_Float16` type is a 16-bit floating-point format. It is classified as `SSE` and passed in the low 16 bits of an `XMM` register. This is similar to `float`, but the smaller size means that multiple `_Float16` values can be packed into a single `XMM` register if they are part of a structure. The ABI specifies that `_Float16` is passed in `XMM` registers, not in general-purpose registers. This is consistent with the rule that floating-point types go in vector registers. The introduction of `_Float16` and `__bf16` (bfloat16) has required updates to the ABI, because the classification algorithm must handle these new types. The ABI document has been revised to include them, and compilers have been updated. This is a recent example of the ABI evolving to accommodate new hardware capabilities. The hardware does not enforce the ABI, but the compiler does. A function that passes a `_Float16` argument must use the correct register, or the callee will read garbage. The contract is still enforced by agreement, but the agreement is constantly being amended.
