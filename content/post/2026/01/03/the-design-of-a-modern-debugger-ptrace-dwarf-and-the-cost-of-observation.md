Every interactive debugger sells the same illusion: the program is frozen, the machine is yours, and you may inspect anything at leisure. None of that is true. A debugger is an ordinary user-space process granted an unusual privilege over another ordinary user-space process, and every inspection it performs is a negotiation with the kernel and the CPU. Breakpoints are bytes patched into the text segment. Variable inspection is a small stack machine interpreting a bytecode that describes where the compiler *might* have put a value. Stepping is a loop of context switches, each costing more than the code being stepped over.

This article is about what a debugger actually does at the system level: which kernel interfaces it uses, what data structures it reads out of the binary, and why the act of observation changes the program observed. It uses Linux and x86-64 as the concrete platform, since that is where the interfaces are most visible, but the design pressures are universal. Every operating system that supports debugging has an equivalent of `ptrace`; every compiler that emits debug information emits something structurally like DWARF; every debugger must solve the same three problems — stop the program, find the data, and resume without changing behavior.

## The Split That Defines Everything

The central constraint is that the debugger must not be part of the program. A debugger linked into the target would change its memory layout, its scheduling, and its failure modes. So debuggers are out-of-process by construction: the debugger is process A, the target is process B, and the operating system mediates. Everything else follows from that split.

That split is why debuggers are slow, and it is also why they are trustworthy. Process A reads process B's memory only through a system call the kernel validates. Process A stops process B only by asking the kernel. The kernel decides what a stopped process looks like, and that decision is thin: a stopped process is one whose threads are parked in `TASK_TRACED`, with register state saved in the kernel's task structure.

There are two ways into that state. The target can ask: `PTRACE_TRACEME`, called on itself before `execve`, which is how debuggers launch programs. Or a privileged process can demand it: `PTRACE_ATTACH` or `PTRACE_SEIZE`, which is how debuggers attach to something already running. Both converge on the same bookkeeping — the target gains a `ptrace` relationship to the tracer, and from that moment the kernel reports certain events to the tracer and suspends the target at each one.

Attach has a subtlety worth knowing. `PTRACE_ATTACH` is implemented as "send `SIGSTOP` and wait for it to be delivered," so the target briefly runs a signal path and can be observed by other processes as stopped rather than traced. `PTRACE_SEIZE` (Linux 3.4 and later) separates the two operations: it establishes the trace relationship without stopping the target, and a later `PTRACE_INTERRUPT` stops it. That removes a class of races around signal delivery, which matters for tools that attach to live servers.

Permissions are enforced by the kernel, not by convention. On Linux, a process may trace another if it has the same real UID or `CAP_SYS_PTRACE`. The Yama LSM adds a further restriction through `/proc/sys/kernel/yama/ptrace_scope`: at the default value of 1, a process may only trace its own descendants, which is why `gdb -p` fails on a process you do not own even when you are the same user. This is a security boundary, and it is the reason that "just attach a debugger" is not a production strategy.

## ptrace: The Kernel's Debugging Interface

`ptrace` is one system call with a large opcode space. Almost every debugger feature is a composition of a few primitives:

- `PTRACE_PEEKTEXT` and `PTRACE_POKETEXT` read and write instruction memory, one machine word at a time.
- `PTRACE_PEEKDATA` and `PTRACE_POKEDATA` do the same for data.
- `PTRACE_GETREGS` and `PTRACE_SETREGS` (or the more portable `PTRACE_GETREGSET` with an `NT_PRSTATUS` note) transfer the register file.
- `PTRACE_CONT`, `PTRACE_SINGLESTEP`, and `PTRACE_SYSCALL` resume the target, optionally stopping at the next instruction or the next system call boundary.
- `PTRACE_SETOPTIONS` enables event reporting: `PTRACE_O_TRACECLONE` to follow new threads, `PTRACE_O_TRACEEXEC` to stop after `execve`, `PTRACE_O_TRACESYSGOOD` to mark syscall stops with a distinguishable signal number, and `PTRACE_O_EXITKILL` to kill the target if the tracer dies.

Two properties of this interface dominate debugger design. First, memory access is word-at-a-time and costs a system call per word; the faster bulk path is a separate interface, `process_vm_readv` and `process_vm_writev`. Second, every resume operation is asynchronous: `PTRACE_CONT` returns immediately, and the tracer learns what happened by calling `waitpid`.

That asymmetry — issue a control operation, then block in `waitpid` — is the debugger's main loop, and it explains the sensitivity to the number of stops. Each stop costs at minimum two context switches plus one more to resume, plus scheduler latency on a machine that is not idle. On a loaded host, that latency is the dominant cost, and nothing the debugger does bounds it.

## Stops, Signals, and the Wait Loop

The tracer observes a stop through `waitpid`'s status word: the low byte is the signal that caused the stop, and the high byte carries ptrace event bits. The main loop is therefore a signal dispatcher that decodes the status, decides whether the stop is interesting, and issues the next resume request.

The key consequence is that signals are entangled with control flow. If the target receives `SIGSEGV` while traced, the tracer sees a stop carrying `SIGSEGV` and must decide whether to deliver it, swallow it, or convert it into something else. A debugger that swallows a signal the program was supposed to handle changes the program's behavior; one that forwards a signal it generated itself confuses the program. Hence the delicacy of `SIGTRAP` handling, and hence `PTRACE_O_TRACESYSGOOD`, which sets bit 7 of the signal number so that a syscall-entry stop is distinguishable from a genuine `SIGTRAP`.

Stops come in flavors. A *group stop* halts every thread in the process, which is what `PTRACE_ATTACH` produces. A *signal-delivery stop* occurs when a signal is queued for the target. A *syscall stop* occurs at system call entry or exit when `PTRACE_SYSCALL` is in use. A *single-step stop* follows one instruction. A *breakpoint stop* is just a signal-delivery stop carrying `SIGTRAP`, which is why disambiguating it from every other reason `SIGTRAP` might appear is a recurring chore.

Modern debuggers support *non-stop mode*, in which threads are resumed and stopped independently and events are reported per-thread. That is a substantial architectural change: the main loop can no longer treat "the process" as a single schedulable entity, and per-thread state machines become necessary. It is also the only way to debug a server without freezing all of its request handlers, which is why several IDE debuggers default to it even though it complicates every other feature.

## Software Breakpoints: One Byte of Violence

The classic breakpoint is a single byte: `0xCC`, the `INT3` instruction. To set a breakpoint at address `A`, the debugger reads the byte at `A`, saves it, writes `0xCC`, and records the substitution in a table. When execution reaches `A`, the CPU raises an `INT3` trap, the kernel delivers `SIGTRAP` to the tracee, and the tracee stops.

The recovery dance is the interesting part. On x86-64, `INT3` is a one-byte instruction, so when the trap is delivered, the saved instruction pointer points at the byte *after* the breakpoint. The debugger must restore the original byte, decrement the instruction pointer by one, let the program execute the real instruction (usually by single-stepping), and re-insert `0xCC` before resuming. Every hit therefore costs a memory write, a single-step stop, and another memory write — four `ptrace` operations and two extra stops on top of the original trap.

Several consequences show up in practice:

- **The text segment must be writable.** Breakpoints work because text pages are private, copy-on-write mappings, so a write from the tracer (which bypasses the target's page protections) triggers a COW break. On truly read-only memory — ROM, or a shared mapping the kernel refuses to break — software breakpoints cannot be used at all.
- **Breakpoints are visible.** A program that checksums its own `.text` section will notice. JIT engines and self-modifying code can overwrite a breakpoint byte and silently disable it.
- **Breakpoints are shared state.** If two debuggers, or a debugger and a `uprobe`, target the same address, the byte-level protocol breaks. This is a real problem in production tooling, where `perf` and `gdb` may both want to instrument the same function.
- **The single-step is observable.** Between the restore and the re-insert, the program runs untrapped for exactly one instruction. A signal delivered in that window, or a concurrent thread executing the same code, sees a different world than the debugger believes.

A variant avoids the re-insertion dance: leave `0xCC` in place and emulate the displaced instruction. This is what hypervisor- and emulator-based debuggers do, and it is how Linux `uprobes` work — the kernel copies the probed instruction to an out-of-line execute slot, patches the original with a breakpoint, and redirects execution. It is more complex, but it makes breakpoints atomic with respect to other observers.

## Hardware Breakpoints and Watchpoints

x86-64 provides four debug registers, `DR0` through `DR3`, each holding a linear address, plus `DR6` for status and `DR7` for control. A hardware breakpoint is an entry in that table; the CPU compares every instruction fetch against the four addresses and traps without modifying memory. Configured differently, the same mechanism produces *data breakpoints* — watchpoints — that trap on reads or writes to an address range.

The advantages are real: no text modification, no COW, no re-insertion, and the ability to watch memory rather than code. The limits are equally real. There are only four slots, and they are per-thread: a multithreaded program needs four slots *per thread*, so watching a shared variable across 32 threads needs 32 independent hardware watchpoints, which the CPU does not have. Lengths are constrained — 1, 2, 4, or 8 bytes on x86-64 — and the trap fires on the *access*, not the value change, so writing the same value still stops.

When hardware slots run out, debuggers fall back to *software watchpoints*: mark the page read-only, catch the fault, single-step to find which instruction faulted, compare the old and new values, and resume. This is correct but catastrophically slow, because every instruction that touches the page is single-stepped. Anyone who has watched GDB grind through a loop because of a software watchpoint has seen this path.

## Symbols and DWARF: From Addresses to Names

Everything above operates on addresses; everything a programmer wants to see is expressed in names. The bridge is the symbol table, and it comes in two flavors that are easy to confuse.

*Minimal symbols* come from the ELF symbol tables (`.symtab` for static symbols, `.dynsym` for dynamic ones) and give an address, a size, and a name. They answer the question of which function an address belongs to even when the binary has no debug information, which is why stripped binaries still produce names for exported symbols. *Full debug information* is a separate, much richer structure — usually DWARF — held in sections like `.debug_info`, `.debug_line`, `.debug_loc`, `.debug_str`, and `.debug_frame`. It describes types, variables, scopes, inlining, and the mapping from machine addresses back to source lines. It is not loaded into memory at run time; a debugger reads it from the file, from a separate debug file located by build ID, or from a `debuginfod` server.

That distinction explains a common frustration. A stripped release build still shows a stack trace of function names, because minimal symbols survive in `.dynsym`; it will not show local variables, because those live only in DWARF. An optimized build with DWARF will still sometimes show *wrong* values, because DWARF describes where a variable lives, and optimization moves variables around.

DWARF is not a vague blob of debug information; it is a database with a schema. Its entries are *Debugging Information Entries* (DIEs), organized as a tree: a compilation unit contains subprogram DIEs, which contain variable DIEs, which contain type DIEs. Each DIE has a tag (what it is) and a list of attributes (what it knows), encoded compactly using abbreviation tables so that repeated shapes do not repeat their names.

Two parts of DWARF do most of the work in an interactive debugger.

The first is the **line number program** in `.debug_line`. It is a bytecode for a small state machine whose registers include address, file, line, column, `is_stmt`, `prologue_end`, and `end_sequence`. Opcodes like `DW_LNS_advance_pc` and `DW_LNS_advance_line` move the state, `DW_LNS_copy` emits a row, and special opcodes pack common address and line deltas into a single byte. Running this program produces the address-to-line table that lets a debugger say "you are on line 42." The `is_stmt` flag distinguishes a line you can break on from one that is merely part of an expression, and the prologue markers let a debugger skip a function's prologue and set a breakpoint at the first statement that belongs to the user's source.

The second is the **location description**, which answers "where is this variable right now?" It is a stack-machine expression, not a fixed address. `DW_OP_fbreg -24` means "24 bytes below the frame base"; `DW_OP_reg3` means "it is in register 3"; `DW_OP_breg6 8` followed by `DW_OP_deref` means "load the pointer in register 6, add 8, dereference." Location *lists* attach these expressions to address ranges, because a variable's location changes as the program runs: it starts on the stack, gets promoted to a register, gets spilled back, and is finally dead. A debugger that prints "optimized out" is reporting that no location list entry covers the current program counter.

That is the machinery. What remains is the part most engineers actually feel: how a debugger walks a stack, how it steps without single-stepping forever, and why all of this costs so much that the bug you are chasing often disappears the moment you attach.

## Stack Walking: Reconstructing the Call Chain

A debugger that can stop a program and read its registers has only a snapshot. To be useful, it must turn that snapshot into a call stack. On x86-64 the raw material is simple: `%rsp` points at the current stack frame, `%rbp` may point at a saved frame pointer, and `%rip` says where execution is. The hard part is that compilers are not obliged to keep `%rbp` as a frame pointer. With `-fomit-frame-pointer`, which is default at most optimization levels, `%rbp` is just another general-purpose register. The debugger must recover the caller's frame from metadata.

That metadata is DWARF Call Frame Information, stored in `.debug_frame` for debug builds and `.eh_frame` for exception handling. Both encode a table of rules: for a given program counter range, how to compute the Canonical Frame Address (CFA) — usually the value of `%rsp` at the call site — and where the return address and saved registers live relative to it. The rules are not code; they are a compact description of the prologue and epilogue. A typical rule says: CFA is `%rsp + 8`; return address is at CFA - 8; `%rbp` is at CFA - 16. To unwind one frame, the debugger evaluates those rules, reads the saved return address and saved registers from the stack, sets `%rip` to the return address, sets `%rsp` to the CFA, and repeats.

The rules are encoded as Common Information Entries (CIEs) and Frame Description Entries (FDEs). A CIE holds shared setup: the return address register, the initial CFA rule, and the encoding of pointers. An FDE covers one address range and lists instructions that modify the rules — `DW_CFA_def_cfa_offset`, `DW_CFA_offset`, `DW_CFA_remember_state`, `DW_CFA_restore_state`. The debugger executes this small bytecode to build the rule set for the current PC. It is the same idea as the line number program: a bytecode interpreter over a table.

Unwinding is therefore a memory-reading loop. Each frame costs a lookup in the FDE table, evaluation of CFI instructions, and one or more reads from the target's stack. Those reads go through `process_vm_readv` if available, because `PTRACE_PEEKDATA` is one word per system call. Even so, a deep stack of a thousand frames means a thousand lookups and thousands of memory reads. Debuggers cache FDEs and parsed CFI, but they cannot cache the stack contents, because the stack changes every time the program runs.

There are cases where CFI is absent or wrong. Hand-written assembly may lack `.cfi` directives. JIT-compiled code has no FDEs at all. A corrupted stack can make the unwinder follow a bogus return address into unmapped memory. Debuggers handle this with heuristics: if `%rbp` looks like a valid frame pointer — aligned, within the stack mapping, pointing to a higher address — use it. Otherwise scan the stack for values that look like return addresses into executable memory. These heuristics are why stack traces from optimized or corrupted programs sometimes contain `??` or obviously wrong frames. They are not laziness; they are the absence of a trustworthy rule.

Signals and exceptions add another layer. When a signal is delivered, the kernel pushes a signal frame onto the stack and redirects execution to a handler. That frame is not described by the function's normal CFI in a way the unwinder can use directly, so the debugger must know the kernel's signal frame layout. On x86-64 Linux, the kernel places a `ucontext` and `siginfo` on the stack; the debugger can recognize the signal trampoline and unwind through it to the interrupted frame. This is how a backtrace from inside a `SIGSEGV` handler still shows the faulting function. It is also fragile: if the signal handler modifies the stack or the debugger misidentifies the trampoline, the unwind stops.

Inlined functions complicate the picture further. DWARF does not emit a separate FDE for an inlined function, because no call instruction exists. Instead, the inlined subroutine DIE carries `DW_AT_call_file`, `DW_AT_call_line`, and `DW_AT_call_column`, and the address ranges of the inlined code are nested inside the caller's ranges. A debugger that wants to show an inlined frame must, for each PC, find the deepest DIE whose range contains it, then walk outward through `DW_AT_abstract_origin` and call-site attributes. This is why stack traces in optimized C++ can show several logical frames for a single physical frame, and why stepping into an inlined function is a source-level illusion maintained entirely by metadata.

## Stepping: The Illusion of One Line at a Time

Stepping is where the debugger's abstraction leaks most visibly. The user asks to go to the next line; the machine has no concept of lines. The debugger must translate that request into a sequence of stops, and the sequence is chosen to approximate the source-level control flow while minimizing the number of stops.

The simplest implementation is instruction-level single-stepping. On x86-64, the debugger sets the trap flag (`TF`) in `EFLAGS` via `PTRACE_SETREGS` and resumes with `PTRACE_CONT`. After one instruction, the CPU raises a debug exception, the kernel delivers `SIGTRAP`, and the target stops. The debugger reads the new `%rip`, consults the line table to see whether the source line changed, and decides whether to stop for the user or continue. This works everywhere, requires no code modification, and is brutally slow: every instruction costs a trap, a context switch into the kernel, a `waitpid` wakeup, a `ptrace` register read, and a resume. A tight loop of ten instructions takes ten full round trips.

Source-level stepping is an optimization over that. The debugger knows the address range of the current source line from `.debug_line`. If the line contains no branches, no calls, and no instructions that can change control flow, the debugger can set a temporary breakpoint at the first instruction of the next line and resume with `PTRACE_CONT`. The program runs at full speed until it reaches the breakpoint. If the line does contain branches, the debugger must consider all possible successors: the fall-through address, the branch target, and any call return addresses. It sets temporary breakpoints at each and resumes. Whichever one hits first is the next stop. This is often called *line-range stepping* or *branch-target stepping*.

The subtlety is that the debugger must not stop at a breakpoint it set for a different purpose, and it must remove temporary breakpoints before resuming. If two threads hit two different temporary breakpoints simultaneously, the debugger must handle both stops, remove both, and decide which thread the user meant to step. In non-stop mode, this becomes a per-thread state machine.

Step-over is a special case with its own trick. To execute a function call without stopping inside it, the debugger reads the return address from the stack, sets a temporary breakpoint there, and resumes. The function runs to completion, the breakpoint traps, and the debugger removes it. This is why stepping over a function that never returns — an infinite loop, a `longjmp`, an exception unwind — can leave the debugger waiting forever or stopping at the wrong place. The return address is a prediction, and the program is not obliged to honor it.

Step-out uses the same prediction in reverse. The debugger unwinds one frame to find the caller's return address, sets a temporary breakpoint there, and resumes. If the current function was inlined, there is no return address; the debugger must instead use the inlined call-site information to find the address in the caller that corresponds to the return point. If the function was tail-called, the frame may already be gone. These are not edge cases in optimized code; they are the normal case.

Hardware single-step has a cost beyond the traps. Setting `TF` changes the state of the thread, and the kernel must handle a debug exception on every instruction. On some CPUs, single-stepping disables certain speculative optimizations and flushes pipelines more aggressively. The observed program is not just slower; it may take different branches in a timing-dependent algorithm. A debugger that single-steps through a lock acquisition can turn a race into a deterministic success.

Modern debuggers try to reduce the number of stops with *range stepping*. Instead of setting breakpoints at every possible successor, the debugger asks the target to run until the PC leaves a specified address range. On architectures that support it, this is a hardware feature; on x86-64, GDB implements it by setting breakpoints at the range boundaries and at any branch targets inside the range. The effect is fewer stops for straight-line code, but the implementation is still breakpoint-based, so it still modifies text and still pays the trap cost at the boundaries.

## The Cost of Observation

The final theme is the one that matters most in practice: observation is not free, and it is not neutral. A debugger that stops a process changes its scheduling, its memory access patterns, its signal timing, and sometimes its address space layout. The bug you are chasing may depend on any of those.

The most obvious cost is time. Every stop is a context switch into the kernel, a wakeup of the tracer, a `waitpid` return, a set of `ptrace` calls, and a resume. On an idle machine, that round trip is microseconds; on a loaded machine, it is scheduler-dependent and can be milliseconds. A program that normally runs for ten milliseconds can take seconds under a debugger. That slowdown is not uniform: it affects code around breakpoints, code that takes locks, and code that waits on timers. A timeout that fires in production may never fire under the debugger, because the debugger has stretched the interval between the timer's start and the check.

The second cost is perturbation of memory. Software breakpoints write to the text segment, which triggers copy-on-write and splits pages that were previously shared between processes. That changes the target's memory footprint and can change the behavior of a program that measures its own resident set size. Hardware watchpoints consume debug registers, which are per-thread and limited; a program that uses them itself — a JIT, a profiler, a sandbox — may find them unavailable or may clobber the debugger's settings. Reading target memory through `process_vm_readv` touches pages that might otherwise have remained unmapped, causing page faults and I/O that change timing.

The third cost is scheduling. Stopping all threads to inspect one thread is the simplest model, but it is also the most invasive. A server with a thousand threads cannot afford to freeze them all for every breakpoint, so non-stop mode exists. But non-stop mode changes the debugger's own complexity and can still perturb the target: the tracer is a runnable process competing for CPU, and the `ptrace` relationship changes how signals are delivered. A signal sent to a traced process is first reported to the tracer, which adds a scheduling hop. Real-time programs can miss deadlines simply because a debugger is attached.

The fourth cost is semantic. Debuggers often disable address space layout randomization to make addresses stable across runs. That is convenient for setting breakpoints by address, but it changes the addresses the program sees, which can hide or expose bugs that depend on layout. Some debuggers set environment variables, change the stack size, or install signal handlers. `LD_PRELOAD`-based tools and `ptrace`-based tools can conflict. A program that checks whether it is being traced — for anti-debugging, for security, or for legitimate reasons — will see a different world.

This is the central irony of debugging: the tool that gives you visibility is also a source of noise. The best debuggers are designed around that irony. They minimize stops, use hardware features when possible, cache metadata, and offer non-stop and remote modes to reduce perturbation. But they cannot eliminate it. The only way to observe a program without changing it is to observe a recording, and even a recording changes the program's timing during capture.

That is why modern practice increasingly separates *debugging* from *tracing*. A debugger is for interactive inspection of a stopped program. A tracer — `perf`, `ftrace`, eBPF, `uprobes` — is for low-overhead observation of a running one. The two share the same metadata: DWARF line tables, symbol tables, and unwind information. They differ in how much they are willing to stop the world. The debugger stops it completely and pays the cost. The tracer samples it, or instruments it with minimal disruption, and accepts less precision. Understanding the trade-off is understanding why the debugger feels slow, why the bug disappears, and why the most powerful debugging tool is sometimes a well-placed log line.

## Remote Debugging and the GDB Remote Serial Protocol

Not every target can run a debugger. An embedded board may have no operating system, a kernel may have no user-space ptrace, and a cloud container may not allow the debugger to share a process namespace with the target. The answer is to split the debugger into two parts: a front end that a human uses, and a target stub that speaks a small protocol over a serial line, a JTAG probe, or a socket. The GDB Remote Serial Protocol is the most widely implemented version of that idea.

RSP is deliberately text-based and packet-oriented. A packet begins with `$`, ends with `#` followed by two hexadecimal checksum digits, and is acknowledged with `+` or rejected with `-`. The protocol is small because it must run over links where every byte costs time. A debugger starts by sending `qSupported`, and the stub replies with a list of features: `PacketSize`, `multiprocess`, `qXfer:features:read`, `vCont`, `QNonStop`, `swbreak`, `hwbreak`, `memory-map`. That negotiation is how one debugger supports decades of targets without hardcoding every quirk.

Registers are read with `g` and written with `G`; individual registers use `p` and `P`. Memory uses `m` and `M`, with `X` for binary transfers. Breakpoints and watchpoints use `Z` and `z`: `Z0` is a software breakpoint, `Z1` a hardware breakpoint, `Z2` a write watchpoint, `Z3` a read watchpoint, and `Z4` an access watchpoint. The stub decides how to implement each type. The debugger only knows the type, which is why the same command can map to an `INT3` byte on x86 and to a debug register on a microcontroller.

Threads are selected with `Hg` and `Hc`, enumerated with `qfThreadInfo` and `qsThreadInfo`, and controlled with `c`, `s`, and `vCont`. `vCont` is the modern execution packet because it can specify an action per thread, which is what non-stop mode requires. Stop replies begin with `T` and carry a signal number, register values, and a thread ID. Exit is reported with `W` or `X`. A debugger that wants to attach to a running process sends `vAttach`; one that wants to launch a program sends `vRun`.

The protocol also carries the metadata that makes the target legible. `qXfer:features:read:target.xml` returns an XML description of the register file: names, sizes, types, and groupings. Without that document, every new architecture would require a new debugger build. With it, a stub can describe a chip the debugger has never seen. `qXfer:memory-map:read` describes address spaces and permissions, which matters for bare-metal targets that have no MMU. `qXfer:auxv:read` exposes the auxiliary vector, and `qXfer:threads:read` lists threads with their names and states. The protocol is not just a way to move bytes; it is a way for the target to teach the debugger what it is.

Remote debugging changes the economics of observation. The stub runs on the target, so it can use local ptrace or hardware debug registers without shipping the entire address space to the debugger. But every packet is a round trip. Reading one register per packet over a slow serial link is unusable, so `g` reads the whole register file at once and `qXfer` streams larger objects. Latency, not bandwidth, is often the limit. A stub that stops the target for every packet adds latency to the target itself, which is why some stubs buffer and some debuggers pipeline. The protocol is a negotiation between two computers that disagree about what is expensive.

## Core Dumps and Post-Mortem Debugging

A core dump is a program frozen after the fact. The kernel writes an ELF file with type `ET_CORE`. Its program headers include `PT_LOAD` segments for the memory mappings that were dumped and `PT_NOTE` segments for metadata. The notes are the interesting part. `NT_PRSTATUS` holds the register set for one thread, including the signal that killed it. `NT_PRPSINFO` holds the command line, working directory, and UID. `NT_AUXV` holds the auxiliary vector, including the entry point and the address of the program headers. `NT_FILE` holds the list of file-backed mappings: start address, end address, file offset, and path. `NT_SIGINFO` holds the `siginfo_t` for the fatal signal. A debugger that opens a core file parses these notes and reconstructs a process image: threads, registers, memory, and the files that were mapped.

The reconstruction is incomplete by design. The kernel does not dump file-backed read-only pages, because they can be read from the file on disk. The debugger must therefore find the original executable and shared libraries, map them at the recorded addresses, and use them to satisfy reads. That is why a core dump is only as good as the files it references. If the binary was rebuilt, the addresses in the core no longer match the code in the file. If a shared library was upgraded, its symbols and line tables are wrong. The build ID note, `.note.gnu.build-id`, is the anchor: the debugger reads the build ID from the core's mapped file, then looks for a matching binary or debug file. `debuginfod` turns that lookup into an HTTP request, which is how a debugger on a developer laptop can resolve symbols for a crash from a production container.

Post-mortem debugging has no control. There is no process to ptrace, no thread to resume, no breakpoint to set. The debugger can read memory, unwind stacks, and evaluate expressions that do not require execution. It cannot call a function, because there is no inferior to call into. It cannot continue, because there is no scheduler. It can still be extremely effective: most crashes are understood by looking at the faulting instruction, the register state, and the stack. The absence of execution is also a virtue. A core dump is a consistent snapshot; it does not change while you inspect it, and it can be shared, archived, and analyzed repeatedly.

The practical difficulty is size and privacy. A core dump can be gigabytes. It contains passwords, keys, and user data. Production systems often disable core dumps or pipe them to a handler like `systemd-coredump` or `apport`, which compresses, stores, and sometimes redacts them. The `core_pattern` sysctl controls the filename and whether the kernel pipes the core to a program. A pipe handler can decide to keep or discard the core based on the executable, the UID, or the signal. That policy is a security boundary as much as a storage decision. A debugger that can read a core dump can read everything the process had in memory.

## Deterministic Replay and Time-Travel Debugging

The most ambitious answer to the cost of observation is to record execution once and replay it deterministically. If the replay is exact, the debugger can stop, inspect, and even run backward without perturbing the original program. The recording is the only perturbed run; every subsequent analysis is on a replica.

`rr` is the best-known Linux implementation. It records a process by intercepting the inputs that make execution nondeterministic: system calls and their results, signals, thread scheduling decisions, shared memory, and reads from special files. It uses `ptrace` to control the target and `perf_event_open` to count retired conditional branches and other hardware events. The branch counts let the replay engine know when to stop at a particular point without single-stepping every instruction. During replay, `rr` re-executes the program from a checkpoint, feeds it the recorded inputs at the recorded points, and schedules threads in the recorded order. The result is a program that behaves the same way every time.

Reverse execution is built on that determinism. To step backward, the debugger does not undo an instruction; it replays from an earlier checkpoint to the previous event. Checkpoints are periodic snapshots of memory and registers. The cost of a reverse step is the cost of replaying from the nearest checkpoint, which is why checkpoints are frequent enough to bound the replay distance. Forward execution is fast because it is native; reverse execution is slower because it is replay. The user experience is still transformative: a crash can be examined backward from the fault to the cause, and a data race can be replayed until the interleaving that triggers it appears.

GDB has its own record and replay facilities. `record full` logs instructions and memory writes in software, which is portable but extremely slow and memory-hungry. `record btrace` uses hardware branch tracing: Intel Processor Trace on x86, or ARM CoreSight ETM. The CPU emits a compressed trace of control flow, and the debugger reconstructs the path. This is low overhead but limited: the trace shows branches, not data, and the buffer is finite. It is enough for reverse stepping through control flow, but not for reconstructing every register value. A hybrid approach uses hardware trace for control flow and checkpoints for state.

Deterministic replay has hard limits. It cannot record a program that reads from an external device that does not produce reproducible data, unless the device is virtualized. It cannot replay a program that uses shared memory with a process outside the recording, unless that process is also recorded. It cannot replay GPU work or real-time deadlines exactly. It changes the program's timing, so a program that depends on wall-clock time may record one behavior and replay another unless the clock is also virtualized. And it is not free: recording adds overhead, checkpoints consume memory, and the replay engine is a complex piece of systems software. But it is the closest thing to a debugger that observes without changing the observed run, because the observed run is already over.

## Debug Information at Scale: Indexing, Splitting, and Compression

The DWARF sections described earlier are a database, and like any database they become unusable without an index. A large C++ binary can carry hundreds of megabytes of `.debug_info`, and the DIE tree is stored as a linear byte stream. Finding the DIE for a function by name would require walking the entire tree, decoding abbreviation tables and skipping over attributes, for every lookup. A debugger that did that would spend seconds on the first `break main`.

The first fix was `.gdb_index`, a section that GDB and some linkers generate. It is a hash table mapping names to offsets in `.debug_info`, plus a table of address ranges to compilation units. Building it is a separate step — `gdb-add-index` or a linker flag — and it is easy to forget, which is why the first `gdb` invocation on a large binary often prints "Reading symbols..." and then "done" after a long pause. If the index is present, the same lookup is a hash probe.

DWARF 5 standardized a better answer: `.debug_names`. It is a more complete index, with a name table, a hash table, and an entry table that can map both names and addresses to DIEs. It supports case-insensitive lookup and can be generated by the compiler itself. The advantage over `.gdb_index` is that it is part of the standard, so every debugger and every tool can use it. The disadvantage is the same as any index: it must be rebuilt when the binary changes, and it adds size. A binary with `.debug_names` can be larger than one without, but the lookup time drops from seconds to milliseconds.

The size problem has a second solution: split DWARF. With `-gsplit-dwarf`, the compiler writes only a skeleton compilation unit into the executable's `.debug_info`. The full type and function DIEs go into a separate `.dwo` file, one per compilation unit. The executable becomes smaller, and the linker does not have to process all that data. But the debugger now needs the `.dwo` files at debug time. If they are not shipped with the binary, the debugger can show function names and line numbers from the skeleton, but not variables or types. This is a common deployment mistake: the build produces `.dwo` files, the packaging step drops them, and the debugger silently degrades.

A `.dwp` file packages many `.dwo` files into one. It is built by `dwp` and can be shipped alongside the executable or served by `debuginfod`. Distros that use split DWARF often ship `.dwp` files for their debug packages. The debugger looks for the `.dwp` first, then falls back to individual `.dwo` files. The lookup is by the `DW_AT_dwo_name` and `DW_AT_comp_dir` attributes in the skeleton unit, which is why moving a binary without its `.dwo` files breaks debugging in a way that moving a normal binary does not.

`dwz` attacks the size problem from another angle. It is a tool that takes many executables and shared libraries and deduplicates their DWARF. Common types — `std::string`, `std::vector`, every template instantiation — appear in every object file. `dwz` moves them into a shared file and replaces the originals with references. The result is a `.gnu_debugaltlink` section pointing at the shared file. Fedora and openSUSE use this to shrink debug packages. The debugger must follow the altlink, which is another file lookup that can fail if the shared file is missing.

Compression is the final layer. DWARF sections can be compressed with `SHF_COMPRESSED` and zlib or zstd. The debugger decompresses them on demand, trading CPU for disk. This matters most for `debuginfod`, where the cost of transferring a gigabyte of debug info over the network dwarfs the cost of decompressing it locally. A compressed section is still a section; the debugger reads the header, allocates a buffer, and inflates. The only visible effect is a delay on first access and a smaller cache footprint.

All of these mechanisms depend on one thing: knowing which debug file belongs to which binary. The `.note.gnu.build-id` section holds a unique hash of the binary, and the debugger uses it to construct a path: `/usr/lib/debug/.build-id/ab/cdef....debug`. The older `.gnu_debuglink` section holds a filename and a CRC, and the debugger searches a list of directories. `debuginfod` turns the build ID into an HTTP request, so a debugger on a laptop can fetch debug info for a crash from a container in a data center. The build ID is the anchor; without it, the debugger is guessing.

The kernel world has its own answer to the size problem: BTF, the BPF Type Format. BTF is a compact, deduplicated type format designed for eBPF. It is generated from DWARF by `pahole` and embedded in the kernel image and in BPF object files. It has no line tables, no location lists, and no expression bytecode. It has types: structs, unions, enums, typedefs, function prototypes. That is enough for eBPF programs to know the layout of kernel structures. CO-RE — Compile Once, Run Everywhere — uses BTF to relocate field offsets at load time, so a BPF program compiled on one kernel can run on another with different struct layouts. DWARF could not do this: it is too large, too complex, and not available on a running kernel without reading a file. BTF is the minimal viable type information for a kernel that must be self-describing.

The practical consequence of all this machinery is that debug information is fragile. It is a separate artifact from the code, produced by different tools, shipped in different packages, and often missing in production. A stripped binary still has dynamic symbols, so a stack trace shows function names. It has no DWARF, so local variables are gone. A binary with DWARF but no `.dwo` files shows types but not variables. A binary with a mismatched build ID shows the wrong source lines. The debugger's first job is often to determine what it does not have.

## Observing Without Stopping: eBPF, uprobes, and the Tracepoint Ecosystem

The debugger's model is stop-the-world: halt the process, inspect it, resume. The tracer's model is observe-in-flight: let the program run, collect data as it passes, and accept that you cannot pause to ask questions. The two models exist because they answer different questions. A debugger answers "what is the value of this variable right now?" A tracer answers "how often does this function run, with what arguments, and how long does it take?" The second question is often the one that matters in production, where stopping the process is not an option.

The oldest tracing infrastructure on Linux is `ftrace`, built into the kernel and controlled through `/sys/kernel/debug/tracing`. It can trace function calls, function returns, and static tracepoints compiled into the kernel. It can also attach dynamic probes: `kprobes` for kernel functions and `uprobes` for user-space functions. The overhead is low because the tracing happens inside the kernel, not through a user-space debugger. There is no `ptrace` relationship, no context switch to a tracer process, and no stop for every event. The kernel writes events to a ring buffer, and a user-space tool reads them.

`uprobes` is the user-space half, and its mechanism is worth understanding because it solves the breakpoint problem differently from a debugger. When a uprobe is attached to an address, the kernel copies the original instruction to an out-of-line "execute" slot, patches the original with a breakpoint instruction, and records the mapping. When execution reaches the breakpoint, the CPU traps, the kernel's uprobe handler runs, and then execution is redirected to the out-of-line slot to execute the displaced instruction. After that, execution returns to the instruction after the probe. The key property is that the kernel handles the trap, not a user-space debugger. There is no single-step stop, no re-insertion dance, and no ptrace relationship. Multiple probes can attach to the same address, because the kernel maintains a list of handlers. This is why uprobes can be used in production: the overhead is a trap and a handler call, not a full debugger round trip.

`eBPF` builds on these hooks. An eBPF program is a small piece of bytecode that the kernel verifies and then runs in response to an event: a kprobe, a uprobe, a tracepoint, a perf event, a network packet, a syscall. The verifier ensures the program cannot crash the kernel: it checks that every memory access is bounded, that loops terminate, that the stack is not exceeded, and that the program does not call arbitrary kernel functions. The program communicates with user space through maps, which are shared data structures. This is a programmable tracer: instead of a fixed set of events, you can write a program that filters, aggregates, and enriches the data before it reaches user space.

The type information for eBPF comes from BTF, described earlier. A BPF program that wants to read a field from a kernel struct needs to know the offset of that field. BTF provides it. CO-RE uses BTF to relocate the offset at load time, so the same program works on different kernel versions. This is the same problem a debugger solves with DWARF location lists, but with a different trade-off: BTF is smaller and available on a running kernel, but it lacks the line tables and expression machinery that a debugger needs for source-level inspection.

User-space applications can also define tracepoints. USDT — User Statically Defined Tracepoints — is a DTrace-compatible mechanism. A library or application embeds a `nop` instruction at each probe site and a note in the `.note.stapsdt` section describing the probe's name, arguments, and location. When a tracer enables the probe, the kernel patches the `nop` to a breakpoint. When disabled, the probe costs nothing but the space of the `nop`. USDT probes are used in libc, PostgreSQL, Node.js, Java, and many other systems. They are how a tracer can observe a specific event without instrumenting every function.

`perf` is the sampling profiler that ties much of this together. It uses hardware performance counters — cycles, instructions, cache misses, branch misses — and software events to sample the program at a fixed frequency. Each sample records the instruction pointer and, optionally, a call stack. The call stack can be collected with frame pointers, with DWARF unwinding, or with hardware branch tracing. The result is a statistical profile: not every event is seen, but the distribution is representative. The overhead is low enough to run in production, and the data is aggregate. You cannot inspect a variable at a sample, but you can see which functions dominate and which call paths are hot.

The trade-off between debugging and tracing is the trade-off between precision and perturbation. A debugger gives exact values at exact points, but it stops the world and changes timing. A tracer gives approximate values over many events, but it runs in flight and changes timing less. Neither is free. An eBPF program runs in the kernel and consumes CPU; a uprobe trap costs a context switch into the kernel; a perf sample interrupts the program and walks the stack. The observer effect is still there, but it is distributed and often smaller.

The convergence is in the metadata. Both debuggers and tracers need to map addresses to names, and both need type information to interpret memory. DWARF serves the debugger; BTF serves eBPF; symbol tables serve both. `debuginfod` serves both. A tool like `bpftrace` can use BTF to print struct fields, and a debugger can use perf events to set hardware watchpoints. The line between the two is blurring: `rr` records execution for deterministic replay, and eBPF can trace the same execution with lower overhead but less precision. The choice is not which tool is better, but which question you are asking and how much you are willing to change the program to get the answer.

## The Debugger's Own Architecture: From CLI to Target Stack

A debugger is not a monolith. GDB, the most widely used, is a layered system: a command-line interface, a machine interface (MI) for IDEs, a Python scripting layer, and a target stack. The target stack is the abstraction that matters most. It defines operations like `resume`, `wait`, `read_memory`, `write_memory`, `read_registers`, `insert_breakpoint`, and `remove_breakpoint`. Each concrete target implements them: a local `ptrace` target, a remote serial target, a core file target, a `fork` child target. The rest of the debugger is written against the target stack, which is why the same `break main` works on a local process, a remote board, and a core dump. The target stack also handles the distinction between a live process and a core file. A core file target implements the same read operations but returns errors for resume. This uniformity is what allows a debugger to switch from a live session to a core dump without changing the user's commands.

The architecture layer describes the machine: register names, sizes, and how to decode instructions. The frame unwinder layer turns a PC and registers into a stack. The breakpoint layer manages the byte-level protocol. The expression evaluator parses and evaluates user expressions. The symbol layer reads ELF and DWARF. The type layer represents types. Each layer is replaceable. LLDB uses a similar decomposition but with a stronger emphasis on plugins and a public API. The design pressure is the same: a debugger must support many architectures, many operating systems, and many front ends without duplicating the core logic.

## Expression Evaluation and the Debugger's Virtual Machine

When you type `print x + 1`, the debugger does not compile that expression. It parses it, resolves `x` to a DIE, evaluates the variable's location, reads the value, and applies the operator. The location evaluation is a DWARF expression: a bytecode for a stack machine. The debugger has an interpreter for that bytecode. `DW_OP_fbreg -24` pushes the frame base minus 24. `DW_OP_deref` pops an address and pushes the value at that address. `DW_OP_reg3` pushes the contents of register 3. The stack machine is small but sufficient to describe where a variable lives at any PC.

If the expression calls a function, the debugger must execute code in the inferior. That requires a dummy frame: the debugger saves the current registers, sets up the stack and registers according to the ABI, sets a breakpoint at the return address, and resumes. The called function runs in the target, and the debugger waits for the breakpoint. This is why `call malloc(100)` can work, but it can also deadlock if the function takes a lock held by another thread, or corrupt state if the function has side effects. The debugger cannot know whether a call is safe. It offers the operation and warns that it may change the program.

The evaluator must also handle types. `x` may be a `std::vector<int>`, a Rust `Vec`, or a Swift `Array`. The debugger's type system must know how to interpret the raw bytes. For C, the mapping is simple. For C++, it must handle inheritance, virtual tables, templates, and references. For Rust, it must handle enums with discriminants, slices, and `Option`. For Swift, it must handle existentials and generics. The debug info describes the layout, but the debugger must know the language's rules to display it correctly. This is why debuggers have language-specific support. The evaluator must also handle the case where the expression is not valid in the current context, such as a variable that is not in scope. The debugger uses the DIE tree to find the variable's scope and reports an error if the PC is outside it.

## Pretty Printers, Type Systems, and the Display Problem

A raw `std::vector` is three pointers. A debugger that prints three pointers is useless. Pretty printers are scripts that know how to interpret the type and produce a readable representation. GDB uses Python; LLDB uses Python or its own formatters. The printer can call other printers, so a `std::map` can print its keys and values. The printer can also be lazy: it can print only the first few elements and offer a way to see more. This is essential for large containers. Pretty printers are not part of the debug info. They are external code that the debugger loads. This means they can be version-specific and can break when the library changes. It also means they can be shared across projects, which is why libraries like `libstdc++` ship with pretty printers.

The display problem is not just about containers. It is about the impedance mismatch between the machine's representation and the programmer's mental model. A `std::string` may be a small-string optimization: the characters are in the object itself if short, or in a heap buffer if long. A `std::variant` may have a discriminator and a union. A Rust `enum` may have a niche optimization. The debug info describes the layout, but the printer must know the semantics. This is why pretty printers are version-specific and why they break when the standard library changes.

The type system also affects expression evaluation. `x.size()` in GDB may call the `size()` method, which requires the debugger to know the C++ ABI. Or it may use a pretty printer's `size` function. The debugger must decide. This is a constant tension: the debugger wants to be language-agnostic, but the languages are not.

## Kernel and Hypervisor Debugging

Debugging a kernel is not like debugging a user process. There is no `ptrace` for the kernel. Instead, the kernel provides `KGDB`, a remote serial protocol that connects to a host debugger. `KDB` is an in-kernel debugger with a simple command-line. `QEMU` provides a `gdbstub` that emulates a target and allows GDB to connect to a virtual machine. Hardware debuggers use JTAG or similar to control the CPU directly. Hardware debuggers are the most direct. They connect to the CPU's debug port and can halt, step, and inspect registers without any software running on the target. This is essential for bring-up, boot loaders, and firmware. The trade-off is cost and complexity: a JTAG probe is another device, another driver, and another protocol. But when the target has no OS, it is the only option.

The differences are fundamental. The kernel has no process context; it has threads and interrupts. The debugger must understand per-CPU state, interrupt disabling, and spinlocks. Stopping the kernel on one CPU may not stop the others. Reading memory may require page table walks. The debugger cannot rely on the OS to handle faults because it is debugging the OS. This is why kernel debugging is a specialized skill and why tools like `crash` exist for post-mortem analysis of kernel core dumps. Kernel debugging also requires a different approach to breakpoints. A software breakpoint in the kernel modifies the text of the running kernel, which is shared across all processes. This is dangerous. Hardware breakpoints are safer but limited. `KGDB` uses a special serial protocol that can stop the kernel and transfer control to the host debugger.

Hypervisor debugging adds another layer. A hypervisor can introspect a guest without the guest's knowledge. This is used for security, forensics, and debugging. The hypervisor can read guest memory, set breakpoints, and intercept events. The guest cannot detect the introspection if the hypervisor is careful. This is the ultimate out-of-band debugger, but it requires control of the hypervisor, which is not always available.
