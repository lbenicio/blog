A histogram is one of the simplest data structures in computing: an array of counters indexed by a value. Given a stream of integers, each update increments `hist[value]`. Sequentially, the operation is a load, an add, and a store. There is no pointer chasing, no allocation, no complex control flow. It is the kind of code that fits in a few lines and is easy to reason about.

Parallelize it, however, and the simplicity becomes a trap. A single shared array of counters turns every update into a potential point of contention. Two threads that touch the same bucket must coordinate; two threads that touch adjacent buckets may still interfere because of cache-line granularity; and two threads that touch different buckets may be serialized by the memory system if the array is not laid out carefully. The parallel histogram is therefore a small but complete case study in parallel systems design: it exposes the tension between work partitioning, data layout, synchronization, and memory hierarchy.

This article is about that tension. We will build a mental model of parallel histogram construction, starting from the sequential baseline and moving through the major strategies: atomic updates, thread-local privatization, sharded histograms, and hybrid designs. We will look at why false sharing is not a side note but often the dominant cost, why privatization trades memory for scalability, and how the choice of update primitive changes the shape of the algorithm. The goal is not to present a single best histogram. There is no such thing. The goal is to make the trade-offs explicit so that you can choose the right design for a given workload and machine.

We assume a shared-memory multiprocessor: multiple cores, a coherent cache hierarchy, and a programming model with threads and either atomic operations or locks. We also assume that the input is large enough that parallel speedup matters, but not so large that the histogram itself becomes the bottleneck. The discussion applies to CPUs primarily, but many of the same ideas appear on GPUs and other accelerators, where the memory hierarchy and synchronization costs are even more pronounced.

## The sequential baseline

Let us start with the sequential algorithm. In C-like pseudocode:

```c
void histogram_sequential(const uint32_t *data, size_t n, uint64_t *hist, size_t bins) {
    for (size_t i = 0; i < n; i++) {
        hist[data[i]]++;
    }
}
```

This is about as fast as a dependent memory operation can be. Each iteration performs a load from `data`, a load from `hist`, an increment, and a store to `hist`. The loads and stores to `hist` are to a small working set: if `bins` is small enough, the histogram fits in L1 or L2 cache. The input stream is sequential, so the hardware prefetcher can hide much of the DRAM latency. The only real dependency is the read-modify-write to the same bucket, which creates a loop-carried dependency when consecutive values collide. Even then, the store-to-load forwarding and out-of-order execution can overlap many independent increments.

The sequential baseline is important because it defines the lower bound of work. Any parallel algorithm must do at least the same number of increments, plus whatever synchronization and partitioning overhead it introduces. If the parallel version is slower than the sequential version, it is usually because the overhead dominates: cache-line ping-pong, atomic contention, or poor load balance.

The baseline also tells us what the hardware is optimized for. Modern CPUs are designed to execute a single instruction stream with high instruction-level parallelism. They have large out-of-order windows, multiple load/store units, and deep cache hierarchies. A sequential histogram with a small number of bins can often run at near memory bandwidth for the input stream. The histogram updates themselves are hidden in the pipeline. This is a high bar for any parallel implementation.

## The parallelization problem

The obvious parallelization is to split the input into chunks and let each thread process a chunk. Each thread runs the same loop, but updates a shared histogram. The question is how to update the shared counters safely.

There are three broad families of solutions:

1. **Atomic updates**: each thread performs an atomic increment on the shared bucket.
2. **Privatization**: each thread maintains a private histogram, and the private histograms are merged at the end.
3. **Sharding**: the histogram is partitioned into shards, and threads are assigned to shards (or buckets are distributed across shards) to reduce contention.

These families are not mutually exclusive. A production implementation might use per-thread private histograms for the hot path, then merge them with atomic operations or a tree reduction. It might also shard the input to improve locality or to balance the merge cost.

The choice depends on several factors:

- **Number of bins**: a small histogram (e.g., 256 bins) fits in a few cache lines; a large histogram (e.g., 1 million bins) may not fit in cache.
- **Distribution of values**: uniform, skewed, or adversarial. Skewed distributions create hot buckets, which amplify contention.
- **Update rate**: how many updates per bucket per unit time.
- **Thread count**: more threads mean more potential contention, but also more private storage.
- **Memory budget**: privatization costs `threads * bins` counters, which may be prohibitive for large bin counts.
- **Merge cost**: private histograms must be combined, which costs time proportional to `threads * bins` (or less if sparse).

The rest of this article explores these factors in detail. We will start with atomic updates, because they are the simplest to implement and the easiest to get wrong.

## Atomic updates and the cost of contention

An atomic increment is a read-modify-write operation that is indivisible with respect to other threads. On x86-64, this is typically implemented with a `lock` prefix on an `add` instruction, or with a `lock cmpxchg` loop. On ARM, it might use `ldxr`/`stxr` (load-exclusive/store-exclusive) or large system extension atomics. The exact instruction sequence matters, but the high-level behavior is the same: the cache line containing the counter is acquired in an exclusive state, the value is updated, and the line is released.

If two threads increment the same counter, they serialize. The first thread acquires the cache line, updates it, and releases it. The second thread then acquires it, updates it, and releases it. The cost of this serialization is not just the atomic instruction itself; it is the cache coherence traffic. The cache line bounces between cores, and each bounce has a latency on the order of tens to hundreds of cycles, depending on the architecture and the distance between cores.

If two threads increment different counters that happen to share a cache line, they also serialize, even though there is no logical conflict. This is **false sharing**. False sharing is often more insidious than true sharing because it is invisible in the source code. A histogram with 8-bit or 16-bit counters is particularly vulnerable: a 64-byte cache line can hold 64 8-bit counters or 32 16-bit counters. If two threads update two different bins that map to the same cache line, they will ping-pong that line.

The standard mitigation for false sharing is padding: each counter is padded to a cache line, or counters are grouped so that hot bins are separated. Padding a histogram with 1 million bins is obviously impractical: it would consume 64 MB per thread. But padding a small histogram with 256 bins is often feasible, and it can turn a contention-bound workload into a bandwidth-bound one.

However, padding is not a universal solution. If the distribution is skewed, the hot bins will still be updated frequently, and padding does not help when multiple threads update the same bin. In that case, we need to reduce the frequency of updates to the shared counter, or give each thread its own copy.

## Privatization: trading memory for scalability

Privatization is the most common technique for parallel histograms. Each thread maintains a private histogram in its own memory space. The thread updates its private histogram without any synchronization. At the end, all private histograms are merged into a final histogram.

The advantages are clear:

- **No contention on the hot path**: each thread owns its counters, so updates are just ordinary loads and stores.
- **Cache locality**: the private histogram can be sized to fit in L1 or L2 cache, and it stays in that cache for the duration of the thread's work.
- **Predictable performance**: the update loop is similar to the sequential baseline, just with a different base pointer.

The disadvantages are equally clear:

- **Memory overhead**: `T` threads require `T * B` counters, where `B` is the number of bins. For `T = 64` and `B = 1,000,000`, that is 64 million counters. If each counter is 8 bytes, that is 512 MB, which may exceed cache and even memory budgets.
- **Merge cost**: merging `T` histograms of `B` bins costs `O(T * B)` work. If `B` is large, the merge can dominate the total runtime. The merge is also a synchronization point: all threads must finish before the merge begins.
- **Load imbalance**: if one thread processes a disproportionately large or hot chunk, its private histogram may become the bottleneck during merge, or its update loop may be slower due to cache misses.

The memory overhead can be reduced by using smaller counters. If the maximum count per bin per thread is less than 2^16, a 16-bit counter suffices. If it is less than 2^32, a 32-bit counter suffices. The final histogram may need 64-bit counters, but the private histograms can be narrower. This is a common optimization: use 32-bit private counters and 64-bit final counters, or use 16-bit private counters with periodic flushing to avoid overflow.

The merge cost can be reduced by merging in parallel. Instead of a single thread merging all private histograms, multiple threads can merge disjoint ranges of bins. For example, if there are `T` private histograms and `B` bins, we can partition the bin space into `T` ranges, and each thread merges its range across all private histograms. This turns the merge into a parallel reduction. The cost is still `O(T * B)` work, but it is distributed across threads. If `T` is large and `B` is small, the merge may still be dominated by synchronization overhead.

Another approach is to use a **hierarchical merge**: first merge private histograms within a socket or NUMA node, then merge across nodes. This reduces remote memory traffic and improves locality. The same idea applies to GPU histograms, where shared memory is used for private histograms and global memory is used for the final merge.

Privatization is not always the right choice. If the histogram is very large and the input is small, the memory overhead and merge cost may outweigh the benefits. In that case, atomic updates with careful sharding may be better. The decision is a function of the workload and the machine.

## Sharding and the shape of contention

Sharding is a middle ground between atomic updates and full privatization. Instead of giving each thread a complete private histogram, we partition the histogram into shards. Each shard is a subset of bins, and each shard is protected by a lock or updated with atomics. Threads update the shard that contains their value. If the shards are chosen well, contention is reduced because different threads tend to update different shards.

There are several ways to shard:

- **Bucket sharding**: assign each bin to a shard. For example, bin `i` belongs to shard `i % S`. This is simple, but it can create hot shards if the distribution is skewed and the hot bins map to the same shard.
- **Value-range sharding**: partition the value range into contiguous ranges, and assign each range to a shard. This preserves locality for sorted or clustered inputs, but it can still create hot shards if the distribution is concentrated in one range.
- **Hash sharding**: apply a hash function to the value and use the hash to select a shard. This spreads hot bins across shards, but it destroys locality and adds a hash computation to the hot path.

Sharding with locks is often slower than atomics because locks have higher overhead and can cause blocking. Sharding with atomics is essentially a partitioned atomic histogram: each shard is a separate array of counters, and threads use atomic increments on the shard they select. The advantage over a single atomic histogram is that the cache lines for different shards are less likely to be contended. The disadvantage is that the total number of counters is `S * B`, which is the same as privatization if `S = T`. The difference is that sharding can be dynamic: threads can choose a shard based on the value, not on their thread ID. This can reduce contention even when the number of shards is smaller than the number of threads.

The key insight is that contention is not just about the number of threads; it is about the number of threads that touch the same cache line at the same time. If the distribution is uniform and the bins are spread across cache lines, a single shared histogram may be fine. If the distribution is skewed, even a few hot bins can dominate. Sharding and privatization both work by giving each thread (or each value range) a separate cache line, so that updates to different logical counters do not interfere.

## False sharing in practice

False sharing deserves a more detailed treatment because it is often the hidden cost in parallel histograms. Consider a histogram with 256 bins of 8-bit counters. The entire histogram is 256 bytes, which is 4 cache lines on a typical 64-byte cache line machine. If 8 threads each update random bins, the probability that two threads update the same cache line is high: with 4 cache lines and 8 threads, by the pigeonhole principle, at least some threads will share a line. Every update to a shared line causes a coherence miss if the line is not already in the exclusive state. The result is that the histogram behaves as if it has only 4 independent counters, not 256.

Padding each bin to a cache line solves the false sharing but increases the memory footprint by 64x. For 256 bins, that is 16 KB per thread, which is acceptable. For 1 million bins, that is 64 MB per thread, which is not. In that case, we can use a hybrid approach: pad only the hot bins, or use a two-level histogram where the first level is a small, padded histogram for hot values, and the second level is a larger, unpadded histogram for cold values. This is similar to a cache: the hot bins are kept in a fast, contention-free structure, and the cold bins are updated less frequently.

Another technique is to use **cache-line-sized buckets**: instead of one counter per bin, use a small array of counters per bin, and each thread increments a different slot. This is a form of privatization at the cache-line level. For example, each bin could have 8 counters, one per thread, but they are packed into a single cache line. When a thread updates the bin, it updates its own slot. The cache line is still shared, but the updates are to different words within the line. On some architectures, this can still cause false sharing because the cache coherence protocol operates on cache lines, not words. However, if the threads are on the same core (e.g., SMT), they share the L1 cache, and the updates may not cause coherence traffic. On different cores, the line will still bounce. The only way to avoid coherence traffic is to ensure that each thread's counters are on different cache lines, or to use a non-coherent memory space (e.g., shared memory on a GPU).

This is where the hardware details matter. On x86, the cache coherence protocol is typically MESI or a variant. A store to a shared line requires the line to be in the Modified or Exclusive state. If another core has the line in Shared state, the store must first invalidate the other copies. This is a coherence miss. The cost of a coherence miss is much higher than a cache hit, but lower than a DRAM access. On NUMA systems, the cost depends on whether the line is in a remote node. On GPUs, shared memory is explicitly managed and has bank conflicts instead of coherence misses.

The practical lesson is that false sharing is a function of the cache line size, the number of threads, and the access pattern. It is not enough to say use atomics or use privatization. You must also consider the layout of the counters in memory. A histogram that is logically correct can still be slow if the counters are packed too tightly.

## Choosing a design

At this point, we have enough vocabulary to sketch a decision procedure. The first question is: how many bins? If the histogram fits comfortably in L1 cache (e.g., a few hundred bins of 8-bit counters), then a single shared histogram with atomics may be sufficient, provided that false sharing is mitigated by padding or by using a cache-line-aware layout. If the histogram is larger, privatization becomes more attractive, but the memory overhead grows.

The second question is: what is the distribution? If the distribution is uniform, contention is spread across bins, and the probability of two threads hitting the same bin is low. If the distribution is skewed, hot bins will be updated frequently, and contention will be concentrated. In that case, privatization or sharding is almost mandatory. If the distribution is adversarial (e.g., all values are the same), then even privatization may not help if the merge becomes the bottleneck, but at least the hot path is contention-free.

The third question is: what is the cost of the merge? If the number of bins is large and the number of threads is large, the merge can dominate. In that case, consider a hierarchical merge or a parallel merge. If the input is small relative to the histogram, the merge may be more expensive than the update loop. In that case, atomic updates may be better because they avoid the merge entirely.

The fourth question is: what is the memory budget? Privatization requires `T * B` counters. If `B` is 1 million and `T` is 64, that is 64 million counters. At 8 bytes each, that is 512 MB. At 4 bytes each, 256 MB. At 2 bytes each, 128 MB. The choice of counter width is a trade-off between memory and overflow risk. If the input size is known, you can compute the maximum count per bin per thread and choose the smallest safe width.

The fifth question is: what is the target architecture? On a CPU with a deep cache hierarchy and coherent caches, false sharing and coherence traffic are the main concerns. On a GPU, the concerns are different: shared memory bank conflicts, global memory atomics, and the cost of merging across thread blocks. On a distributed system, the histogram may be partitioned across nodes, and the network becomes the bottleneck. The same principles apply, but the constants change.

## Atomic increments under the hood

The atomic histogram is the simplest parallel design to write, but the instruction that implements it is not a single abstract operation. On x86-64, an atomic increment of a 32-bit counter usually compiles to `lock addl $1, (ptr)`. The `lock` prefix turns the read-modify-write into an atomic operation and, on x86, also acts as a full memory barrier. A 64-bit counter uses `lock addq`. If the return value is needed, the compiler may emit `lock xadd`, which returns the old value. A compare-and-swap loop uses `lock cmpxchg` and retries until the observed value matches the expected value. The first two forms are preferable when the old value is not needed: they are a single instruction and do not contain a retry loop. The CAS loop is useful when the update is conditional, but for a plain increment it adds branch and retry overhead.

The cost of these instructions is dominated by cache coherence, not by the arithmetic. When a core executes a locked instruction, it must obtain exclusive ownership of the cache line containing the counter. If the line is already in the core's L1 cache in the exclusive or modified state, the operation can complete quickly. If the line is shared with another core, the core must invalidate the other copies and wait for ownership. If the line is in another core's modified state, the core must fetch it. The latency of these transitions is measured in tens to hundreds of cycles. Under heavy contention, the line bounces between cores, and the throughput of the counter is limited by the coherence protocol's ability to hand off ownership. This is why a single hot counter can become a serialization point even on a machine with many cores.

Memory ordering matters for correctness, but it also affects code generation. In C++, `std::atomic<uint64_t>::fetch_add(1, std::memory_order_relaxed)` is sufficient for a histogram counter because the update does not need to order other memory operations. The relaxed ordering still guarantees atomicity and a consistent modification order for the counter. On x86, a relaxed `fetch_add` typically compiles to the same `lock add` instruction, because x86's memory model does not provide a cheaper locked read-modify-write. On weakly ordered architectures such as ARM, the compiler may emit a load-exclusive/store-exclusive loop or a large system extension atomic instruction. The relaxed ordering can avoid unnecessary fences around the atomic, but the atomic itself still requires exclusive ownership of the line. The practical lesson is that choosing a weaker memory order does not eliminate coherence traffic; it only removes fences that would otherwise order surrounding memory operations.

The ABA problem is often mentioned in discussions of CAS loops. For a histogram increment, ABA is mostly irrelevant. The counter is monotonically increasing, so a value cannot return to a previous value unless the counter overflows. If the counter is wide enough to avoid overflow for the duration of the run, a CAS loop that reads the old value, adds one, and compares the old value again cannot observe a false match. The value may have changed, but it cannot have changed back to the same old value. If the counter wraps, ABA becomes possible: another thread could increment the counter from `UINT64_MAX` to `0`, and a delayed CAS could mistake the wrapped value for the original. The usual fix is to use a counter width that cannot overflow, or to detect overflow and switch to a wider counter. For most histogram workloads, the input size is known and the maximum count per bin is bounded, so overflow is a design-time concern rather than a runtime hazard.

Atomic increments also interact with false sharing in a subtle way. Two atomic counters that are adjacent in memory share a cache line. Even if the program uses two different atomic variables, the hardware sees one line. A locked increment to one counter invalidates the line for the other. The result is the same ping-pong as if both threads updated the same counter. Padding each atomic counter to a cache line is the standard fix, but it multiplies memory usage. For a large histogram, padding every bin is not viable. A better approach is to avoid a shared atomic histogram altogether and use privatization or sharding. Atomics are most useful when the histogram is small, the contention is low, or the update rate is modest. They are least useful when the histogram is large and the distribution is skewed.

## A privatized histogram in C++

The privatized histogram moves the contention out of the hot loop. Each thread owns a complete array of counters. The update loop is an ordinary load, increment, and store. The only synchronization happens at the end, when the private arrays are merged. The design is simple, but the implementation details determine whether it actually scales.

The first detail is alignment. If the private histograms are allocated as one contiguous block of `T * B` counters, the boundary between thread `t` and thread `t + 1` may fall in the middle of a cache line. Thread `t` writes to the last bins of its array while thread `t + 1` writes to the first bins of its array. The two arrays are logically separate, but the cache line is shared. This is false sharing at the boundary. The fix is to align each thread's array to a cache line and to round its size up to a multiple of the cache line. The padding at the end of each array is wasted memory, but it prevents the boundary from being shared. The alignment must be applied to the actual counter storage, not just to a struct that holds a pointer. A struct with `alignas(64)` does not necessarily align the heap allocation it points to. Use an aligned allocation function or a custom allocator.

The second detail is initialization. Zeroing `T * B` counters costs time and memory bandwidth. If `B` is one million and `T` is 64, the private histograms occupy 256 MB when each counter is 32 bits. Zeroing that much memory can take longer than processing a small input. The operating system may provide zero-filled pages lazily, but the first write to each page still incurs a page fault and a cache miss. For small inputs, the initialization cost can dominate. One mitigation is to use a sparse representation for cold bins, but that adds complexity to the hot path. Another is to size the private histograms to the actual value range observed in the input, if that range is known or can be computed cheaply. A third is to use a two-level design: a small, dense histogram for hot values and a larger, sparse structure for cold values. The right choice depends on the ratio of input size to bin count.

The third detail is counter width. The final histogram may need 64-bit counters, but the private counters can be narrower. If each thread processes `n / T` elements and the maximum count per bin per thread is less than `2^32`, a 32-bit private counter is sufficient. If the maximum is less than `2^16`, a 16-bit counter halves the memory footprint and may improve cache behavior. The trade-off is overflow risk. A 16-bit counter overflows after 65,535 updates to the same bin by the same thread. If the distribution is skewed, a single hot bin can reach that threshold quickly. One solution is to flush the private histogram to a shared accumulator when a counter approaches the limit. The flush is a rare event, but it must be implemented carefully to avoid contention. Another solution is to use saturating counters and a separate overflow path, but that complicates the update loop. For most workloads, 32-bit private counters and 64-bit final counters are a good compromise: the memory overhead is manageable, and overflow is unlikely unless the input is extremely large.

The merge phase is where the privatized design pays its synchronization debt. A naive merge loops over all bins and all threads:

```cpp
for (size_t b = 0; b < bins; ++b) {
    uint64_t sum = 0;
    for (size_t t = 0; t < threads; ++t) {
        sum += private_hist[t][b];
    }
    final_hist[b] = sum;
}
```

This is `O(T * B)` work. If `T` and `B` are both large, the merge can be a significant fraction of the total runtime. The merge is also a join point: every thread must finish its update loop before the merge can start. If the input chunks are uneven, some threads idle while others finish. A parallel merge can reduce the wall-clock time. Partition the bin space into ranges and assign each range to a thread. Each thread merges its range across all private histograms. The work is still `O(T * B)`, but it is distributed. If `B` is small, the parallel merge may be dominated by thread creation and synchronization; in that case, a sequential merge is fine. If `B` is large, the parallel merge is essential.

A hierarchical merge can improve locality on NUMA systems. Threads on the same NUMA node first merge their private histograms into a node-local histogram. Then one thread per node merges the node-local histograms into the final histogram. This reduces remote memory traffic: most of the merge reads are local to the node. The node-local histograms are also smaller than the full set of private histograms, so the final merge is cheaper. The same idea applies to sockets and to clusters of cores that share an L3 cache. The hierarchy should match the memory hierarchy; otherwise, the merge may add overhead without improving locality.

The privatized histogram is not a universal answer. It is a good fit when the histogram is small enough to fit in cache, when the input is large enough to amortize the merge, and when the memory budget allows `T * B` counters. It is a poor fit when the histogram is huge and the input is small, because the initialization and merge costs dominate. In those cases, a sharded atomic histogram or a hybrid design may be better. The next step is to make the trade-off explicit in code: choose the counter width, the alignment, the merge strategy, and the fallback path based on the workload parameters. That is the engineering work that turns a textbook idea into a fast histogram.

## Sharded histograms with locks

A sharded histogram with locks partitions the counter array into shards and protects each shard with a lock. The update path computes the shard index, acquires the lock, increments the counter, and releases the lock. The appeal is that the critical section is tiny: a single increment. The danger is that the lock itself becomes the contended object. A lock is a shared variable, and acquiring it requires an atomic read-modify-write. If many threads target the same shard, they serialize on the lock, and the cache line holding the lock bounces between cores. The counter update is no longer the bottleneck; the lock handoff is.

The granularity of sharding determines how often this happens. Bucket sharding assigns bin `b` to shard `b % S`. If the distribution is uniform, the load is balanced across shards, and contention is low. If the distribution is skewed, a hot bin maps to one shard, and all updates to that bin serialize on that shard's lock. Value-range sharding assigns contiguous ranges to shards. It preserves locality for sorted inputs, but a distribution concentrated in one range can overload one shard. Hash sharding spreads values across shards, which reduces the chance of a hot shard, but it adds a hash computation and destroys the spatial locality of the histogram. For a small histogram, the hash cost may be larger than the contention it avoids.

Locks also introduce blocking. If a thread is descheduled while holding a lock, other threads wait. Spinlocks avoid the context switch but waste cycles. A ticket lock or an MCS lock can reduce cache-line bouncing by queueing waiters, but the queue itself is a shared data structure. For a histogram, the critical section is so short that the lock overhead often dominates. This is why lock-based sharding is rarely the fastest option on modern CPUs. Atomics are usually better when the update is a simple increment, because they avoid the lock acquire/release pair and the associated control flow. Locks become more attractive when the update is complex, such as a conditional update or a multi-counter transaction, but those are not typical histogram operations.

A middle ground is to use a lock only for the hot bins and atomics for the rest. The hot bins can be detected by sampling or by tracking the distribution at runtime. If a bin exceeds a threshold of updates, it is promoted to a locked or privatized structure. This adaptive approach adds complexity but can handle adversarial distributions without penalizing uniform ones.

## Atomic sharding and the illusion of independence

An atomic sharded histogram gives each shard its own array of counters and uses atomic increments within the shard. There are two common layouts. In the first, the bins are partitioned across shards: shard `s` contains a subset of the bins. An update to bin `b` goes to the shard that owns `b`. There is no duplication, so the final histogram is simply the concatenation of the shards. Contention is reduced only if the hot bins are spread across shards. If all hot bins belong to the same shard, the sharding does nothing.

In the second layout, each bin has multiple counter slots, one per shard. An update to bin `b` chooses a slot, for example by hashing the thread ID or the value, and performs an atomic increment on that slot. The final histogram sums the slots for each bin. This is essentially privatization with a fixed number of copies per bin. It reduces contention because different threads tend to update different slots. The cost is a larger memory footprint and a merge step. If the number of slots equals the number of threads, this is the same as a privatized histogram, except that the slots are interleaved by bin rather than grouped by thread. The interleaved layout can be better for cache locality when threads update the same bin: the slots for that bin are in the same cache line, so a thread that updates the bin brings the whole line into its cache. But that also means the line is shared, and false sharing can occur. The grouped layout avoids false sharing at the cost of a larger stride between a thread's counters.

The choice between interleaved and grouped layouts depends on the access pattern. If threads update random bins, the interleaved layout has poor locality: each update touches a different cache line. The grouped layout has better locality because a thread's private histogram is contiguous. If threads update the same hot bin, the interleaved layout allows them to share the cache line, but the atomic updates still serialize on the cache line. The grouped layout gives each thread its own copy of the hot bin on a separate cache line, which eliminates contention but increases memory traffic during the merge. In practice, grouped privatization is usually faster for skewed distributions, while interleaved atomic sharding can be competitive for uniform distributions with a small number of bins.

## NUMA-aware and hierarchical histograms

On a non-uniform memory access (NUMA) machine, the cost of accessing a cache line depends on which node it resides on. A thread that updates a counter allocated on a remote node pays a higher latency and consumes interconnect bandwidth. If the histogram is shared and large, remote accesses can dominate. Privatization helps because each thread updates its own counters, but the private histograms must be allocated on the local node. If they are allocated with a first-touch policy, the thread that first writes to a page determines its node. That thread should be the one that will use the page, so the allocation and initialization should be done by the owning thread. If a single thread initializes all private histograms, the pages may be placed on the initializing thread's node, and all other threads will access them remotely.

A hierarchical merge reduces remote traffic. Threads on the same node merge their private histograms into a node-local histogram. The node-local histogram is allocated on that node and is updated only by threads on that node. Then one thread per node merges the node-local histograms into the final histogram. The final merge reads `nodes * B` counters instead of `threads * B`, which can be much smaller. The merge is also a tree reduction: if there are multiple sockets, the node-local histograms can be merged per socket before the global merge. The hierarchy should match the hardware topology. If the machine has two sockets and eight cores per socket, a two-level merge (per-socket then global) is usually sufficient. If the machine has multiple NUMA nodes per socket, a three-level merge may be better.

The update path can also be NUMA-aware. If the input is partitioned by node, each node processes its local data and updates its local histogram. This avoids remote memory traffic for the input stream as well as the histogram. The partitioning can be static or dynamic. Static partitioning is simple but can suffer from load imbalance if the input is not evenly distributed. Dynamic partitioning with work stealing can balance the load, but stolen work may require remote data access. A hybrid approach is to partition the input into large chunks, assign chunks to nodes, and allow stealing only at chunk boundaries. The chunk size should be large enough to amortize the cost of stealing and to preserve locality.

## GPU histograms: shared memory, bank conflicts, and global atomics

On a GPU, the parallel histogram problem is both easier and harder. It is easier because the hardware provides a fast, explicitly managed scratchpad memory: shared memory. Each thread block can build a private histogram in shared memory, update it with shared memory atomics, and then merge it into a global histogram. Shared memory atomics are much faster than global memory atomics, and they do not involve cache coherence in the CPU sense. It is harder because the SIMT execution model and the shared memory banking scheme introduce new sources of serialization.

Shared memory is divided into banks, typically 32 banks of 4 bytes each. If two threads in the same warp access the same bank but different addresses, the accesses serialize. A histogram update to a random bin can cause bank conflicts if multiple threads in the warp hit bins that map to the same bank. For a dense histogram with one counter per bin, the bank is determined by the bin index modulo the number of banks. If the values are uniformly distributed, the probability of a bank conflict is moderate. If the values are skewed, a hot bin can cause a 32-way conflict: every thread in the warp updates the same bin, and the shared memory atomic serializes all of them. The result is a 32x slowdown for that warp.

The standard mitigation is to replicate the histogram. Each warp, or each group of threads, gets its own private copy of the histogram in shared memory. Threads update their own copy, so there is no conflict between warps. Within a warp, threads can still conflict if they update the same bin. Some algorithms use a warp-level aggregation: threads sort or match their values, and one thread per distinct value performs the update. On modern GPUs, warp match instructions can identify threads with the same value, and a leader can perform a single atomic update for the group. This reduces the number of atomics and bank conflicts. The aggregation has a cost, but it is often worth it for skewed distributions.

After the block-level histogram is built, it must be merged into the global histogram. Global memory atomics are expensive, but the number of updates is reduced by the block-level aggregation. Each block performs at most `bins` global atomic updates, not one per input element. If the number of blocks is large, the global histogram still sees contention on hot bins. A hierarchical merge can help: each block writes its histogram to a per-block buffer in global memory, and a separate kernel merges the buffers. The merge kernel can be parallelized over bins, and it can use a tree reduction to avoid a single hot counter. The trade-off is extra global memory traffic and an extra kernel launch.

The occupancy of the histogram kernel is limited by the shared memory footprint. If each block allocates a full histogram, the number of blocks per SM is limited by the shared memory capacity. For a large bin count, the histogram may not fit in shared memory, and the kernel must fall back to global atomics or a multi-pass approach. A common technique is to use a smaller number of bins per block and to process the input in multiple passes, or to use a hash table in shared memory for sparse values. The right design depends on the bin count, the distribution, and the GPU architecture.

## Measuring and modeling contention

To choose among these designs, you need measurements. A histogram benchmark should report more than total time. It should separate the update phase, the merge phase, and the initialization phase. It should vary the number of threads, the number of bins, the input size, and the distribution. It should report the throughput in updates per second and the scaling efficiency relative to the sequential baseline. It should also report hardware counters: cache misses, coherence misses, instructions per cycle, and memory bandwidth. On Intel CPUs, the performance monitoring unit can count L1 and L2 misses, LLC misses, and offcore responses. On AMD, similar counters exist. On GPUs, the profiler can report shared memory bank conflicts, global memory atomics, and achieved occupancy.

A simple model can guide the design. Let `n` be the number of input elements, `B` the number of bins, and `T` the number of threads. The sequential time is approximately `n * c_seq`, where `c_seq` is the cost of one update in the sequential loop. The parallel time has three components: update, merge, and initialization. The update time is `n / T * c_par`, where `c_par` includes the cost of any contention or false sharing. The merge time is `T * B * c_merge` for a sequential merge, or `T * B * c_merge / T_merge` for a parallel merge. The initialization time is `T * B * c_init`. The total time is the sum, plus synchronization overhead. If `T * B` is large, the merge and initialization terms can dominate, even if the update term is small. This is why privatization is not always a win.

Contention can be modeled as a function of the hotness of the distribution. If the distribution is uniform, the probability that two threads update the same bin is roughly `1 / B` per pair of updates. If the distribution is skewed, the hot bins receive a disproportionate share of updates. A simple metric is the maximum bin frequency divided by the average frequency. If this ratio is large, contention is concentrated. The number of threads that simultaneously target the hot bin determines the serialization. In the worst case, all threads update the same bin, and the throughput is limited by the coherence protocol's handoff rate. This is the same as a single shared counter, regardless of the number of bins.

Load imbalance is another factor. If the input is partitioned into equal-sized chunks, but the distribution varies across chunks, some threads may finish early. Dynamic scheduling can balance the work, but it may hurt locality and increase synchronization. A good compromise is to use a moderate number of chunks per thread and to schedule chunks dynamically. The chunk size should be large enough to amortize the scheduling overhead and to keep the private histogram in cache. If the input is sorted or clustered, static partitioning may be better because it preserves locality and avoids the overhead of dynamic scheduling.

## Hybrid designs and adaptive strategies

No single design is best for all workloads. A hybrid design can combine the strengths of privatization and atomics. One approach is a two-level histogram: a small, private, padded histogram for the hot bins, and a larger, shared, atomic histogram for the cold bins. The hot bins are identified by sampling the input or by maintaining a small direct-mapped cache of recently used bins. If a value falls into the hot set, the thread updates its private counter. Otherwise, it performs an atomic update on the shared histogram. The hot set can be adjusted dynamically: bins that exceed a threshold are promoted to the private structure, and bins that become cold are demoted. This adapts to the distribution without a full privatization of the entire bin space.

Another hybrid is to use privatized histograms with periodic flushing. Each thread maintains a private histogram, but when a counter reaches a threshold, the thread flushes that bin to a shared accumulator using an atomic add. The flush reduces the private counter to zero or to a base value. This bounds the private counter width and reduces the merge cost, because the private histograms are partially reduced during the update phase. The flush threshold must be chosen carefully: too low, and the shared accumulator becomes contended; too high, and the private counters overflow. If the distribution is known, the threshold can be set to the maximum expected count per bin per thread divided by the number of flushes. If the distribution is unknown, an adaptive threshold can be used.

Sparse histograms are another hybrid. If the number of bins is huge but the number of distinct values in the input is small, a dense array is wasteful. Each thread can maintain a hash map from value to count. The update is a hash lookup and an increment. The merge combines the hash maps. The advantage is memory efficiency: only the observed values consume space. The disadvantage is that hash lookups are slower than array indexing, and the hash map may have collisions and resizing overhead. For a small number of distinct values, a sorted array or a small linear-probing table can be faster than a general-purpose hash map. The choice depends on the number of distinct values, the distribution, and the cost of hashing relative to the cost of a dense array access.

## Practical engineering checklist

When you set out to implement a parallel histogram, the following questions will shape the design. They are not a conclusion; they are a checklist to run before writing code.

- What is the number of bins? If it is small enough to fit in L1 or L2, a shared atomic histogram with padding may be sufficient. If it is large, privatization or sharding is likely necessary.
- What is the value range? If the values are dense and bounded, a dense array is best. If they are sparse or unbounded, a hash map or a two-level structure may be needed.
- What is the distribution? Uniform distributions tolerate atomics and sharding. Skewed distributions demand privatization or hot-bin replication. Adversarial distributions (all values equal) require a design that handles a single hot bin without serializing all threads.
- What is the input size relative to the bin count? If the input is small, initialization and merge costs dominate. If the input is large, the update loop dominates.
- How many threads? More threads increase contention but also increase the memory overhead of privatization. The optimal number of threads may be less than the maximum available if the merge cost grows faster than the update speedup.
- What is the memory budget? Privatization costs `T * B` counters. The counter width can be reduced to 32, 16, or even 8 bits if the maximum count per bin per thread is bounded. Overflow must be handled explicitly.
- What is the memory hierarchy? False sharing is a function of cache line size. Padding and alignment can eliminate it for small histograms. For large histograms, a layout that groups counters by thread is usually better than one that interleaves them by bin.
- Is the machine NUMA? If so, allocate private histograms on the local node and use a hierarchical merge. Avoid remote memory traffic in the hot path.
- Is the target a GPU? Shared memory atomics and bank conflicts replace cache coherence. Warp-level aggregation and block-level privatization are the key techniques.
- How will you measure? Separate update, merge, and initialization. Vary threads, bins, input size, and distribution. Use hardware counters to confirm whether the bottleneck is coherence, bandwidth, or instruction throughput.

These questions do not have universal answers. The right design is the one that matches the workload and the machine. A parallel histogram is a small problem, but it contains the same tensions that appear in larger parallel systems: work partitioning, data layout, synchronization, and the cost of sharing. The next step is to build a few variants, measure them, and let the measurements guide the choice. That is the only way to know which trade-off matters for your data.

## The merge as a reduction tree

The merge phase is often treated as a fixed cost, but its structure determines how much of the private histogram work is actually parallel. A flat merge loops over bins and threads, accumulating into the final array. A tree reduction merges private histograms pairwise: in the first step, thread 0 merges histograms 0 and 1, thread 2 merges 2 and 3, and so on. After log2(T) steps, one histogram remains. The total arithmetic is still O(T B), but the critical path is O(B log T) rather than O(T B), and the memory traffic can be arranged to stream through cache. Pairwise merging also avoids the single final array being written by many threads at once, which would reintroduce contention on the output bins.

For a large B, the merge loop is memory-bandwidth bound. Use contiguous arrays, avoid aliasing with restrict pointers, and let the compiler vectorize the inner loop. When private counters are 32-bit and final counters are 64-bit, the widening add is still vectorizable on AVX2 and AVX-512. If the private histograms are padded for false sharing, the padding must be skipped during merge; merge only the logical bins, not the padding. A common mistake is to merge the padded arrays as if they were dense, which adds useless work and pollutes cache.

On NUMA systems, the reduction tree should follow the topology. Merge within a node first, then across nodes. The intra-node merge reads only local memory; the inter-node merge reads one histogram per node. If the node-local histograms are allocated on the node that produces them, the final merge touches remote memory only once per node, not once per thread. This can cut merge traffic by a factor of the number of threads per node.

## Input partitioning and locality

The way input elements are assigned to threads changes both load balance and the shape of each private histogram. Contiguous chunks preserve sequential access and hardware prefetching, which matters when the input stream is the bandwidth bottleneck. Interleaved assignment (thread t takes elements t, t+T, t+2T, ...) balances skewed distributions across threads, because each thread sees a representative sample. But interleaved access defeats prefetchers that expect unit-stride streams, and it can increase the number of cache lines touched per element. A compromise is to use moderate contiguous chunks and schedule them dynamically: each thread grabs a chunk, processes it, and grabs another. The chunk size should be large enough to amortize the scheduling atomic and small enough to balance the load. For skewed data, chunk-level balancing is usually sufficient unless the skew is extreme.

Locality also affects the private histogram. If a chunk contains a narrow value range, the thread's private histogram touches only a few cache lines, which is good. If the chunk is a random sample, the private histogram touches many bins, which can exceed L1. Thus contiguous chunks can improve private-histogram locality for clustered inputs, while interleaved chunks can improve load balance for adversarial inputs. There is no single answer; the partitioning strategy should be chosen together with the histogram layout.

## Counter width and flush policies

Counter width is a memory-bandwidth decision. If each private counter is 8 bytes and B is one million, each thread's histogram is 8 MB, which does not fit in L2. Halving the width to 4 bytes halves the cache footprint and the merge traffic. A 16-bit counter halves it again. The safe width is determined by the maximum count a single bin can reach in one thread's private histogram, which is bounded by the number of elements that thread processes. If each thread processes at most 65,535 elements, a 16-bit counter cannot overflow, regardless of distribution. This is a strong argument for smaller chunks: they permit narrower counters, which improve cache behavior. The trade-off is scheduling overhead and merge frequency.

When the input is too large for narrow counters, use periodic flushing. A flush adds the private counter to a shared accumulator and resets the private counter to zero. The flush can target an atomic shared histogram, a per-thread overflow array, or a node-local accumulator. Flushing to a shared atomic reintroduces contention, but only every 2^w updates per bin, where w is the counter width. Flushing to a per-thread overflow array avoids contention but requires a second merge pass. A hybrid is to flush only hot bins, detected by a small counter or by a threshold on the private counter value. The hot-bin flush keeps the common case cheap and bounds the worst case.

## Microbenchmark harness and metrics

A useful histogram benchmark separates four phases: allocation and initialization, update, flush, and merge. Time each phase independently. Use a monotonic clock with low overhead, and pin threads to cores to avoid migration noise. Generate at least three distributions: uniform, Zipf-like, and adversarial (all values identical). Vary the number of bins, the number of threads, and the input size. Report updates per second, scaling efficiency, and the fraction of time spent in merge. If the update phase scales but total time does not, the merge is the bottleneck. If update throughput drops as threads increase, contention or false sharing is the bottleneck.

Hardware counters turn guesses into evidence. On CPUs, measure L1/L2/LLC misses, coherence misses, and offcore responses. A high rate of coherence misses on the histogram array indicates false sharing or true sharing. On GPUs, measure shared memory bank conflicts, global atomics, and achieved occupancy. Compare a padded layout against an unpadded one; the difference isolates false sharing. Compare a private histogram against a shared atomic histogram; the difference isolates contention. These measurements are not optional if you want a design that holds up outside a microbenchmark.
