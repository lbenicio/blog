January 13, 2026

Disaggregated memory is one of those ideas that sounds simple until you try to build it. The premise: instead of buying DRAM with every server, put memory in a pool and let compute nodes borrow it over a network. The benefits are obvious—higher utilization, independent scaling, lower stranded capacity. The costs are less obvious: every load becomes a network operation, every allocator becomes a distributed system, and every failure becomes a data-loss event unless you design for it.

This article is about the design of a disaggregated memory pool. We will focus on the RDMA-based variant, where compute nodes access a memory server's DRAM using one-sided verbs. We will look at the fast path, the allocator, consistency, failure semantics, and the performance model. The goal is not to sell disaggregation; it is to make the trade-offs precise.

## The two axes of disaggregation

When engineers say disaggregated memory, they usually mean one of two things. The first is capacity disaggregation: a compute node needs more memory than its local DIMM slots provide, so it borrows remote memory for a while. The second is pooling: many compute nodes share a common memory resource, and the pool is managed as a first-class system component. Capacity disaggregation is easier because the remote memory is an extension of a private heap. Pooling is harder because the memory server must handle allocation, isolation, reclamation, and failure for many clients.

There is also a hardware split. CXL-based disaggregation puts memory on a cache-coherent fabric, so remote memory can be accessed with load and store instructions and cached by the CPU. RDMA-based disaggregation puts memory behind a network interface, so remote access is explicit: a thread posts a work request, the NIC transfers data, and the CPU observes a completion. CXL promises lower latency and a familiar programming model, but it is still constrained by fabric topology, switch hop count, and the limits of coherent domains. RDMA is more mature, more widely deployed in datacenters, and more flexible in how the memory server is built. It also forces the programmer to confront the network explicitly.

This article focuses on the RDMA variant because it exposes the design questions most clearly. The same questions appear in CXL systems, but they are often hidden behind hardware coherence and vendor-specific fabric managers.

## The memory server as a first-class system

A disaggregated memory pool is not just a server with a lot of DRAM and a fast NIC. It is a system with its own control plane, data plane, and failure domain. The data plane is the one-sided RDMA path: compute nodes read and write remote memory without involving the memory server's CPU. The control plane handles connection setup, memory registration, allocation, reclamation, failure detection, and reconfiguration.

The memory server's data plane consists of a NIC, a registered memory region, and a set of queue pairs. Each compute node opens one or more queue pairs to the memory server and exchanges remote keys, or rkeys, that authorize access to specific memory regions. The server's CPU does not touch the fast path. That is the point: one-sided RDMA avoids remote procedure calls, remote scheduling, and remote cache pollution. A compute node can issue an RDMA READ or WRITE and have the remote NIC DMA the data directly to or from DRAM.

The control plane is where the complexity lives. The server must know which regions are allocated, which clients own them, and when they can be reclaimed. It must detect failed clients and reclaim their memory without corrupting live allocations. It must handle network partitions, queue pair errors, and NIC resets. It must also provide a way for clients to discover the pool, authenticate, and obtain rkeys. None of this is free, and none of it should be on the fast path.

A useful design principle is to keep the fast path stateless. The data plane should be a set of registered buffers and queue pairs. The control plane should be a separate protocol, ideally over TCP or a reliable message layer, that manages leases, epochs, and metadata. If the fast path needs to consult a lock or a reference count, the design has already lost much of its advantage.

## One-sided RDMA mechanics

RDMA provides three primitives that matter for memory disaggregation: READ, WRITE, and atomic operations. An RDMA READ asks the remote NIC to fetch data from a remote memory region and return it to the local node. An RDMA WRITE pushes data from the local node into a remote memory region. Atomic operations include fetch-and-add, compare-and-swap, and masked compare-and-swap. These are executed by the remote NIC and are atomic with respect to other RDMA atomics on the same memory region.

The programming model is built around queue pairs, completion queues, and work requests. A queue pair is a pair of send and receive queues. The compute node posts a work request to the send queue. The NIC processes it and posts a completion to the completion queue. For one-sided operations, the remote side does not post a receive request and does not receive a completion. That is what makes one-sided RDMA attractive for a memory pool: the remote CPU is not involved.

But the details matter. Memory must be registered and pinned before it can be accessed remotely. Registration is expensive and can consume significant memory for translation tables. The NIC's translation cache, often called a memory translation table or MTT, has limited reach. Large regions can cause cache misses and reduce bandwidth. A memory server should register a small number of large regions, not a large number of small ones, and it should be prepared to handle registration failures and memory pressure.

Ordering is another subtle area. RDMA provides reliable transport, but the ordering of operations and completions is not always what a naive programmer expects. Writes from different queue pairs may be observed in different orders. Even on a single queue pair, the visibility of a write to a remote reader depends on the memory ordering rules of the NIC and the remote CPU. A common mistake is to write data with RDMA WRITE and then write a flag with another RDMA WRITE, assuming the flag will not become visible before the data. In practice, this requires a fence or a protocol that does not rely on implicit ordering. The safe approach is to use a release operation on the sender and an acquire operation on the receiver, or to use a single atomic operation that carries the flag and a sequence number.

Atomic operations are the synchronization primitive of choice for many disaggregated memory designs. A remote fetch-and-add can implement a ticket lock. A compare-and-swap can implement a lock-free stack or a reference count. But atomics are not free. They consume NIC resources, they serialize at the memory controller, and they can become a bottleneck under contention. A design that uses a remote atomic for every allocation or every reference count will not scale.

## The remote allocator

The allocator is the heart of a memory pool. On a local machine, malloc and free are already complex. In a disaggregated pool, the allocator must handle remote clients, network failures, and partial failures. It must also avoid becoming a central bottleneck.

There are three broad approaches. The first is a centralized allocator: the memory server owns all metadata and hands out blocks in response to client requests. This is simple to reason about, but it puts the server's CPU on the critical path for every allocation. It also creates a single point of failure and a scalability bottleneck.

The second is a client-side allocator with server-side regions. The memory server carves its DRAM into large regions and leases a region to each client. The client then runs its own allocator inside that region. The server does not see individual allocations. This keeps the fast path one-sided and scales well, but it can waste memory if clients over-allocate or if their workloads are bursty. It also makes reclamation harder: if a client fails, the server can reclaim the whole region, but it cannot easily reclaim individual blocks without client cooperation.

The third is a hybrid: a global allocator for large objects and per-client suballocators for small objects. The global allocator uses a control-plane protocol to allocate and free large extents. The suballocators are local to each client and use remote atomics only when they need to grow or shrink their extent. This is the approach used by many practical systems because it balances scalability, simplicity, and memory efficiency.

A key design question is how to handle free. In a local allocator, free is a local operation. In a disaggregated pool, free must be communicated to the server or to a global metadata service. If the client crashes, the server must eventually reclaim the memory. Leases and epochs are the usual tools. A client holds a lease on a region. The lease is renewed periodically. If the server does not hear from the client before the lease expires, it can reclaim the region. The client must ensure that it does not use the region after the lease expires. This requires a local failure detector and a way to stop using remote memory when the lease is lost.

Epochs are useful for safe reclamation. Each allocation can be tagged with an epoch. The server advances the epoch periodically. Memory that is no longer referenced by any active epoch can be reclaimed. This is similar to epoch-based reclamation in lock-free data structures, but the epochs are global and the participants are distributed. The cost is that memory cannot be reused immediately; it must wait for the epoch to advance. That is a trade-off between safety and memory efficiency.

## Consistency and coherence

A disaggregated memory pool is not cache-coherent across compute nodes. If two compute nodes both read the same remote cache line, and one writes it, the other will not see the update unless the writer explicitly publishes it and the reader explicitly checks for it. This is the fundamental difference between disaggregated memory and shared-memory multiprocessing.

There are several ways to build consistency on top of one-sided RDMA. The simplest is to use remote atomics for all synchronization. A lock can be implemented with a compare-and-swap. A reader-writer lock can be implemented with fetch-and-add. A queue can be implemented with a linked list and a compare-and-swap on the tail pointer. The advantage is that the synchronization is explicit and the memory model is well understood. The disadvantage is that every synchronization operation is a network round trip, and contention can be expensive.

A second approach is to use a directory-based coherence protocol implemented in software. The memory server maintains a directory that tracks which compute nodes have cached which cache lines. When a node wants to write a line, it sends a request to the directory, which invalidates other copies. This is essentially a distributed cache coherence protocol running over RDMA. It can reduce network traffic for read-shared workloads, but it adds latency and metadata overhead. It also requires the memory server's CPU to be involved in coherence transactions, which violates the one-sided fast path.

A third approach is to avoid sharing altogether. Each compute node gets its own private region, and sharing is done through message passing or through a shared log. This is the simplest model, and it is often the right one for disaggregated memory. If the workload can be partitioned so that each node owns its data, the pool becomes a set of private memory regions with a shared control plane. That is much easier to reason about than a coherent shared address space.

In practice, most systems use a mix. They provide one-sided RDMA for bulk data transfer and remote atomics for synchronization. They expose a shared address space, but they require the programmer to use explicit synchronization. They may also provide a higher-level library that implements locks, queues, and hash tables on top of the primitives. The key is to make the consistency model explicit and to avoid pretending that remote memory is just slower local memory.

## Failure semantics

Failure is where disaggregated memory gets hard. A memory server crash can lose all data in the pool. A compute node crash can leak memory. A network partition can split the pool into two independent halves. A NIC failure can cause in-flight operations to be lost or duplicated. A power failure can leave the memory server's DRAM contents undefined.

The first question is durability. Remote DRAM is volatile. If the memory server loses power, the data is gone. If the pool is used as a cache, that may be acceptable. If it is used as primary storage, it is not. The usual solution is replication or erasure coding. A write is not acknowledged until it has been written to multiple memory servers. That adds latency and network traffic, but it is the only way to survive a server failure. The alternative is to use persistent memory or battery-backed DRAM, which changes the cost and capacity trade-offs.

The second question is atomicity. An RDMA WRITE is not atomic beyond the size of a single atomic operation. A large write can be partially completed if the NIC fails or the server crashes. A reader may observe a torn write. To avoid this, writes must be made atomic through a protocol: write to a shadow buffer, then atomically update a pointer or a version number. This is the same pattern used in local databases, but the atomic update is a remote atomic operation.

The third question is reclamation. If a compute node crashes, the memory server must eventually reclaim its regions. Leases are the standard mechanism. A client renews its lease periodically. If the lease expires, the server can reclaim the region. The client must ensure that it does not use the region after the lease expires. This requires a local failure detector and a way to stop using remote memory when the lease is lost. The server must also handle the case where the client is alive but the network is partitioned. A lease that is too short causes false reclamation; a lease that is too long delays recovery. There is no perfect answer, only a trade-off between availability and safety.

The fourth question is recovery. After a failure, the pool must be rebuilt. If the data is replicated, the recovery process can copy data from the surviving replicas. If the data is erasure-coded, the recovery process must reconstruct the missing shards. If the data is not replicated, it is lost. The recovery process must also rebuild the allocator metadata, the directory, and the lease table. This is a distributed recovery problem, and it should be designed before the first failure, not after.

## Performance model

The performance of a disaggregated memory pool is determined by three resources: the network, the memory server's DRAM, and the compute node's NIC. The network adds latency and limits bandwidth. The memory server's DRAM has finite bandwidth and bank conflicts. The compute node's NIC has a limited number of outstanding requests and a limited completion queue depth.

Latency is the most visible difference. A local DRAM access is measured in tens of nanoseconds. An RDMA READ or WRITE is measured in microseconds, even on a fast network. The exact number depends on the NIC, the switch, the cable, and the PCIe topology, but the order of magnitude is clear: remote memory is at least an order of magnitude slower than local memory. That means a workload that is latency-bound will not benefit from disaggregation unless it can hide the latency with concurrency.

Bandwidth is more forgiving. A modern NIC can sustain hundreds of gigabits per second, and a memory server can have multiple NICs and multiple memory controllers. For bulk transfers, the network can approach the bandwidth of local memory. The challenge is to keep enough requests in flight. Little's law applies: to saturate a link, the product of throughput and round-trip time must be less than the amount of data in flight. If the round-trip time is a few microseconds and the link is hundreds of gigabits per second, the required in-flight data is substantial. The NIC must support many outstanding work requests, and the software must post them efficiently.

CPU overhead is another factor. One-sided RDMA is designed to avoid remote CPU involvement, but the local CPU still has to post work requests and poll for completions. Polling reduces latency but consumes a core. Interrupts reduce CPU usage but add latency. Most high-performance systems use polling for the fast path and interrupts for the control plane. They also use batched work requests and selective signaling to reduce the number of completions.

The memory server's CPU should not be on the data path, but it is still responsible for the control plane. If the control plane is slow, allocation and reclamation become bottlenecks. If the control plane is fast but the data plane is not, the pool is underutilized. The design must balance the two.

## Workloads that fit and workloads that do not

Disaggregated memory is not a universal replacement for local memory. It fits workloads that have large working sets, low locality requirements, and enough concurrency to hide latency. Examples include in-memory key-value stores with large values, graph processing with irregular access patterns, and machine learning training with large embedding tables. It also fits workloads that need elastic capacity, such as serverless functions that occasionally need a lot of memory.

It does not fit workloads that are latency-sensitive and single-threaded. A pointer-chasing workload that performs a dependent load on every access will be dominated by network latency. It also does not fit workloads that require strong cache coherence and fine-grained sharing. Those workloads need hardware coherence, and even then, the fabric topology matters.

The best way to decide is to measure. Build a prototype, run a representative workload, and compare the end-to-end performance against a local-memory baseline. Do not assume that disaggregation will save money just because it improves utilization. The cost of the network, the memory server, and the operational complexity may outweigh the savings.

## Design principles

Several principles emerge from the discussion so far. First, keep the fast path one-sided. The remote CPU should not be involved in data transfers. Second, make the control plane explicit. Allocation, reclamation, and failure detection should be separate from the data path. Third, use leases and epochs for reclamation. They are the only practical way to handle client failures without global coordination. Fourth, design for failure from the beginning. Replication, atomicity, and recovery are not optional. Fifth, measure tail latency, not just average latency. A pool that is fast on average but slow on the 99th percentile will be unusable for many applications.

The next section turns to the control plane in more detail: how memory servers are discovered, how regions are registered, how leases are renewed, and how the system recovers from partial failures.

## The control plane as a distributed protocol

The control plane is not a single service. It is a set of protocols that manage membership, capacity, and ownership. At minimum, it must answer four questions: which memory servers exist, which clients may use them, which regions are allocated to which clients, and when those allocations can be reclaimed. A design that answers these questions with a central database will eventually hit scalability limits. A design that answers them with no coordination will eventually corrupt data. The practical middle ground is to push ownership decisions to the memory server that owns the DRAM, and to use a lightweight coordination service only for membership and epoch advancement.

Each memory server should be the authority for its own regions. It knows which extents are free, which are leased, and which are pending reclamation. It does not need consensus for every allocation because the allocation is local to its DRAM. It does need a way to advertise capacity and to detect when it is partitioned from the rest of the pool. A coordination service can maintain a pool manifest: a list of memory servers, their endpoints, their failure domains, and a monotonically increasing pool epoch. The manifest changes slowly. It is not on the allocation fast path.

Clients run a local agent. The agent maintains queue pairs to the memory servers it uses, caches rkeys and lease state, and exposes a local allocator API to applications. The agent is responsible for renewing leases, handling QP errors, and stopping access when a lease is lost. It is also responsible for reporting failures to the control plane. The agent is not a central component; it is replicated across every compute node, and it can fail independently. That independence is important: a client crash should not require a global reconfiguration.

## Discovery, authentication, and connection establishment

Discovery can be as simple as a DNS name that resolves to a set of memory server endpoints, or as complex as a Kubernetes custom resource that tracks pool membership. The important property is that discovery returns a consistent view of the pool. If two clients see different sets of memory servers, they may allocate overlapping regions or fail to find replicas. A versioned manifest with a pool epoch solves this. A client that sees an old manifest can be told to refresh before it allocates.

Authentication is where one-sided RDMA becomes uncomfortable. An rkey is a bearer token. Anyone who possesses it can read or write the associated memory region, subject to the NIC protection checks. There is no per-operation identity in the RDMA packet. If a client is compromised, it can use its rkeys until they are revoked. Revocation is not instantaneous. The server can tear down the queue pair or invalidate a memory window, but in-flight operations may still complete. The practical approach is to scope rkeys narrowly, rotate them frequently, and treat the control plane as the root of trust. A client authenticates to the control plane with a strong identity, receives a short-lived rkey, and uses it only for the region it was granted.

Connection establishment follows the RDMA connection manager model. The client resolves the server endpoint, exchanges queue pair information, and transitions the queue pair through RESET, INIT, RTR, and RTS. The server allocates a queue pair context and records the client identity. The client receives the remote rkey and the remote virtual address of its region. From that point, the data path is one-sided. The control plane connection can remain open for lease renewals and failure notifications. It should be separate from the data path queue pairs so that a control plane hiccup does not stall bulk transfers.

Scaling connections is a real constraint. If there are N clients and M memory servers, and every client connects to every server, the pool has N times M queue pairs. Each queue pair consumes NIC cache, host memory, and server-side state. A thousand clients and ten servers is ten thousand queue pairs, which is manageable on modern hardware but not free. A hundred thousand clients is not. The alternatives are hierarchical: clients connect to a small number of proxy nodes, or the pool uses a connectionless transport such as RDMA over Converged Ethernet with unreliable datagram, or it uses dynamic connected transport that multiplexes queue pairs. Each alternative changes the failure and ordering semantics. The design should choose one and document it.

## Region registration and memory layout

Memory registration is expensive. Pinning pages, building translation tables, and programming the NIC memory translation cache can take milliseconds for large regions. A memory server should register its DRAM once at startup, in large chunks, and never unregister on the data path. Huge pages reduce the number of translations and improve MTT cache hit rates. If the server uses 1 GB pages, a terabyte of memory requires only a thousand translations. If it uses 4 KB pages, it requires millions, and the NIC will thrash.

The pool should be divided into extents. An extent is the unit of allocation and reclamation. It is large enough to amortize control plane overhead, but small enough to limit fragmentation. A typical extent might be tens or hundreds of megabytes. The server maintains a free list of extents and a lease table. When a client requests memory, the server allocates an extent, creates an rkey for it, and returns the rkey, the remote address, a lease identifier, and an epoch number. The client local allocator then carves the extent into smaller objects. The server never sees those objects. That is what keeps the fast path one-sided.

Metadata placement matters. The server free list and lease table should live in local memory that is not remotely accessible. If they are remotely accessible, a buggy or malicious client could corrupt them. The only remotely accessible memory should be the data extents and, optionally, a per-client metadata page for atomics. That metadata page can hold a lock word, a sequence number, or a reference count. It should be in a separate registered region with a different rkey, so that a client cannot use its data rkey to modify another client metadata.

Memory windows can provide finer-grained access. A memory window is a temporary authorization to a subregion of a registered region. The server can create a window for a client, and the client uses the window rkey for a specific operation. Windows add overhead, but they allow revocation at a granularity smaller than a whole region. They are useful for short-lived allocations or for enforcing read-only access. The trade-off is that window creation and destruction involve the server CPU, so they should not be on the hot path for every small object.

## Leases, epochs, and safe reclamation

A lease is a promise. The server promises not to reclaim an extent while the lease is valid. The client promises not to use the extent after the lease expires. Both sides need a clock, and clocks are not perfectly synchronized. The server should use its own clock to decide when a lease has expired, and the client should use a conservative margin when it decides to stop using memory. If the client clock is fast, it may stop early; if it is slow, it may use memory after the server has reclaimed it. A safety margin of one or two heartbeat intervals is usually enough, but it must be chosen with the clock drift in mind.

Lease duration is a trade-off. Short leases allow quick reclamation after a client crash, but they generate more renewal traffic and more opportunities for false failure detection. Long leases reduce control plane load, but they delay recovery and increase the window in which a failed client memory is unavailable. The right duration depends on the workload. A batch job that runs for hours can tolerate a long lease. A serverless function that lives for milliseconds needs a short lease or a different ownership model. Some systems use adaptive leases: the server lengthens the lease for stable clients and shortens it for clients that are new or have recently failed.

Epochs complement leases. An epoch is a logical time. The server advances the epoch periodically, and clients announce the epoch they are currently using. Memory that was allocated in an epoch older than the minimum active epoch can be reclaimed, because no client should still hold a reference to it. This is the same idea as epoch-based reclamation in lock-free data structures, but the participants are distributed. The client must announce a quiescent state when it is not using remote memory. The server can then compute a safe epoch. If a client fails, its epoch is removed from the active set, and reclamation can proceed.

The combination is powerful. A lease tells the server whether the client is alive. An epoch tells the server whether any in-flight operation could still reference the memory. The server reclaims an extent only when the lease has expired and the epoch has advanced past the extent allocation epoch. This avoids the classic use-after-free that occurs when a client is declared dead but a delayed RDMA operation is still in the network. The cost is that memory cannot be reused immediately. It must wait for the epoch to advance, which may take milliseconds or seconds. For a pool that is sized for peak capacity, that delay is acceptable. For a pool that is sized for average capacity, it may not be.

## Failure detection and fencing

Failure detection is never perfect. A heartbeat timeout can be caused by a slow network, a busy CPU, or a garbage collection pause. If the server declares a client dead too early, it may reclaim memory that the client is still using. If it waits too long, it may run out of capacity. The usual approach is to use a suspicion-based detector: the server becomes suspicious after a missed heartbeat, and it declares failure only after a longer timeout or after corroborating evidence from another component. The client can also send an explicit goodbye message when it shuts down cleanly, which avoids the timeout entirely.

Fencing is the mechanism that makes reclamation safe. When the server decides that a client is dead, it increments a generation number for the client region. Any operation that carries the old generation is rejected. But one-sided RDMA operations do not carry a generation number unless the client includes one in the data. The server cannot inspect every RDMA WRITE. The practical fencing mechanisms are queue pair teardown and memory window invalidation. Tearing down the queue pair stops the client from issuing new operations, but in-flight operations may still complete. Invalidating the memory window or rotating the rkey prevents new operations from being authorized, but the NIC may have cached the old translation. The server must wait for a grace period before reusing the memory. That grace period is exactly what the epoch mechanism provides.

A more robust approach is to use a fencing token in every atomic operation. If the client must use a remote atomic to publish a result, the atomic can include a generation number. The server can then reject stale generations. This works for synchronization operations, but it does not protect bulk RDMA WRITEs that do not go through an atomic. For those, the server must rely on queue pair teardown and the epoch grace period. The design should be explicit about which operations are fenced and which are not.

## Recovery and reconfiguration

Recovery begins with the control plane. If a memory server fails, the coordination service removes it from the pool manifest and increments the pool epoch. Clients that had regions on that server must be notified. If the pool uses replication, the clients can fail over to a replica. If it does not, the data is lost, and the clients must handle the loss. The control plane should not pretend that recovery is transparent. It should expose the failure to the application and let the application decide whether to retry, restore from a checkpoint, or fail.

If a client fails, the memory server reclaims its extents after the lease expires. The server must also clean up any shared metadata that the client owned. If the client held a lock, the lock must be released. If the client was a member of a consensus group, the group must be reconfigured. This is why shared metadata should be minimized. Every shared data structure that a client can own is a potential orphan after a crash. A design that uses a single remote lock per extent is easier to recover than a design that uses a complex lock-free data structure with many pointers.

Metadata durability is another recovery concern. If the memory server lease table is in volatile DRAM, a server crash loses it. After restart, the server does not know which extents were allocated. It can either start with an empty pool and let clients re-register, or it can persist the lease table to local storage. Persisting every lease renewal is expensive. A common compromise is to persist only epoch advances and allocation changes, and to treat lease renewals as soft state. After a crash, the server can wait for a full lease timeout before reusing memory, which gives clients time to reconnect and re-establish their allocations. If the server DRAM itself is lost, then the data is gone regardless of metadata.

Rolling upgrades are a form of planned recovery. To upgrade a memory server, the operator must drain its extents. Draining requires migrating data to other servers or asking clients to release their regions. Live migration of remote memory is hard because clients hold rkeys and may be actively using the memory. A safe approach is to quiesce the clients, copy the data, update the rkeys, and resume. That requires application cooperation. A less safe approach is to rely on replication and simply fail over. Either way, the control plane must support a drain state and must prevent new allocations on the draining server.

## Operational visibility

A disaggregated memory pool is harder to operate than a local memory system because failures can be partial and asynchronous. The control plane should export metrics for allocation latency, lease renewal latency, reclamation latency, queue pair errors, and epoch advancement. It should also export per-client and per-server bandwidth, atomic operation rates, and memory fragmentation. These metrics are not just for dashboards. They are the inputs to capacity planning and failure diagnosis.

Debugging is especially difficult. A one-sided RDMA operation leaves no trace on the remote CPU. If a client writes to the wrong address, the memory server may not notice until another client reads corrupted data. If a queue pair enters an error state, the completion queue may report a generic error that does not identify the offending work request. The control plane should maintain an audit log of rkey grants, lease renewals, and reclamations. It should also provide a way to dump the lease table and the free list. Without that visibility, operators will be reduced to guessing.

Security operations also belong here. rkeys should be rotated on a schedule and immediately after a suspected compromise. The control plane should support revocation and should be able to tear down a client queue pairs. The memory server should rate-limit atomic operations per client to prevent a single client from monopolizing the NIC or the memory controller. Multi-tenancy adds another layer: the pool must enforce quotas, isolate failure domains, and prevent one tenant from observing another tenant traffic patterns. Some of these protections can be implemented in the NIC; others must be in the control plane. The design should document which is which.

## Protocol versioning and compatibility

The control plane is a protocol, and protocols change. A memory server may run a newer version than a client. The pool may be upgraded incrementally. The protocol should be versioned, and every message should carry a version and a pool epoch. A client that speaks an old version should be rejected or downgraded gracefully. A server that receives an unknown message should log it and ignore it. The data plane is simpler: the RDMA verbs are stable, but the rkey format and the memory layout may change. The control plane should negotiate the layout before the client registers its queue pairs. If the negotiation fails, the client should not proceed to the data path.

Compatibility also applies to failure semantics. If a new server version changes the lease duration or the epoch advancement policy, clients must understand the new behavior. A mixed-version pool can have subtle bugs: an old client may assume a longer lease than the new server provides, or a new client may expect an epoch field that an old server does not send. The safest approach is to make the pool homogeneous during upgrades, or to use feature flags that are negotiated per connection. The control plane is the place to enforce those rules. It is not glamorous, but it is what keeps a disaggregated memory pool from becoming a collection of incompatible islands.

## Remote data structures and synchronization patterns

One-sided RDMA gives you three primitives: READ, WRITE, and atomics. Building shared data structures on top of them is an exercise in minimizing round trips and making failure atomic. The first rule is to avoid remote synchronization for every operation. A remote lock is a network round trip; under contention, it is also a serialization point. If a data structure requires a lock per insert or per lookup, the pool's throughput is bounded by the RTT of the network, not by DRAM bandwidth.

A better pattern is to batch. A client can post multiple RDMA READs in a single doorbell ring, then process the results as they arrive. For a hash table lookup, that means reading the bucket metadata and the candidate entries in parallel. If the table uses open addressing, the client can probe several slots at once. If it uses chaining, it can fetch the head pointer and the first few nodes in parallel. The NIC will pipeline the reads, and the total latency is close to the latency of a single read plus the bandwidth-limited transfer time. This is the same idea as memory-level parallelism in a local CPU, but the parallel unit is the NIC's outstanding request queue rather than the CPU's load-store unit.

Remote atomics are best used for ownership changes, not for every read. A compare-and-swap can claim a slot in a hash table. A fetch-and-add can reserve space in a ring buffer. A fetch-and-add can also implement a ticket lock, but a ticket lock over RDMA has a subtle problem: the waiters must poll the lock word with RDMA reads, which consumes bandwidth and NIC resources. A better remote lock is the MCS lock, where each waiter enqueues a node and then waits on its own local cache line. The unlock operation writes to the next waiter's node, which is a single RDMA WRITE. That eliminates polling on a shared cache line and scales better under contention. The cost is more metadata: each waiter needs a node in remote memory, and the lock must handle the case where a waiter crashes while holding a node in the queue. That is a reclamation problem, and it requires epochs or lease-based cleanup.

Lock-free data structures are attractive because they avoid the crash-while-holding-lock problem, but they are harder to build over RDMA. The ABA problem is worse because a remote atomic can be delayed or reordered relative to other operations. Tagged pointers are one solution: pack a generation counter into the same 64-bit word as the pointer, and use a 128-bit compare-and-swap if the NIC supports it. Not all NICs support 128-bit atomics, and even those that do may not support them at full rate. An alternative is to use a global generation counter that is incremented by the server, and to validate the generation before using a pointer. That adds a second remote read, which may double the latency of a lookup.

For queues, a ring buffer is usually better than a linked list. A ring buffer has a fixed size, so it can be allocated as a single extent and accessed with RDMA READ and WRITE. The head and tail pointers can be managed with remote atomics. A producer does a fetch-and-add on the tail to reserve a slot, writes the data, and then writes a sequence number to mark the slot valid. A consumer reads the sequence number, reads the data, and advances the head. The sequence number prevents a consumer from reading a slot that is being overwritten. This is the same pattern as a local lock-free queue, but the writes are RDMA WRITEs and the atomics are remote. The performance depends on how many outstanding operations the NIC can sustain. If the producer and consumer are on different nodes, the queue becomes a network round trip per element unless both sides batch.

A remote hash table is often the core data structure of a disaggregated key-value store. The metadata—bucket array, size, hash function—can live in a small registered region that is read-mostly. The entries themselves can live in larger extents. A lookup reads the bucket, follows a chain or probes, and returns the value. If the table is read-mostly, a client can cache the bucket array locally and invalidate on updates. If updates are frequent, the client must read the bucket remotely or use a directory-based coherence protocol. The trade-off is the same as in local concurrent hash tables, but the cost of a remote read is much higher, so the design should minimize metadata reads. One approach is to keep the bucket array in the client's local memory and use the remote pool only for values. The client then owns the index and can rebuild it after a failure. That makes the index a local cache rather than a shared structure. It also means the index is not part of the pool's failure domain, which simplifies recovery.

Allocation metadata is another data structure that must be designed carefully. A remote allocator that hands out small objects cannot afford a remote round trip per object. The solution is to allocate in bulk. A client requests a slab or a block of many objects from the server, and then allocates and frees within that block locally. The server only sees the block. This is the hybrid allocator described earlier, but the data structure details matter. The client needs a local free list, a local bitmap, or a size-class allocator. The server needs a global free list of blocks. When a client's block is exhausted, it requests another block. When a client frees all objects in a block, it can return the block to the server. Returning a block is a control plane operation, not a data plane operation, so it can be batched and amortized. The result is that the fast path never touches the server's allocator metadata.

The hardest part of remote data structures is failure atomicity. A client can crash in the middle of a multi-step update. A lock can be held when the client dies. A queue can have a half-written element. A hash table can have a partially linked chain. The standard solution is to make each update a single atomic operation, or to use a write-ahead log in remote memory. A single atomic operation is faster but limited in what it can express. A write-ahead log is more general but adds a remote write for every update. Some systems use a combination: a small atomic operation to reserve a log slot, then a bulk RDMA WRITE to store the log record, then a remote atomic to commit. The commit is the linearization point. If the client crashes before the commit, the log record is ignored. If it crashes after, the log record is replayed. This is essentially a distributed transaction protocol over RDMA, and it has the same costs as any transactional system: extra network round trips and extra metadata.

In practice, many disaggregated memory systems avoid general-purpose data structures and instead expose a narrow API: `put`, `get`, `delete`, and compare-and-swap on a key. That API can be implemented with a simple hash table and a log. It is not general, but it is enough for many applications, and it keeps the design tractable. The lesson is that the more general the remote data structure, the more the network latency dominates. Specialization is a feature, not a limitation.

## Network fabric and congestion control for memory pools

A disaggregated memory pool is a network application. The fabric is not just a transport; it is part of the memory hierarchy. The latency and bandwidth of the fabric determine the effective memory latency and bandwidth. The fabric's congestion control determines tail latency. The fabric's topology determines failure domains and placement constraints. A pool that ignores these factors will be unpredictable and hard to operate.

RDMA is usually deployed on one of two fabrics: InfiniBand or RDMA over Converged Ethernet (RoCE). InfiniBand is a dedicated lossless fabric with credit-based flow control. It provides predictable latency and is common in HPC and AI clusters. RoCE runs RDMA over Ethernet and relies on Priority Flow Control (PFC) to make the network lossless. PFC can cause head-of-line blocking and congestion spreading, and it requires careful configuration of priorities, buffers, and watchdog timers. RoCEv2 adds IP routability, which makes it attractive for datacenter deployment, but it also means the RDMA traffic shares the network with other traffic. Without strict isolation, a burst of TCP traffic can starve RDMA and cause latency spikes.

Congestion control for RDMA is not optional when many clients share a memory server. A single memory server can be a hotspot: every client that reads from a popular key sends traffic to the same NIC and the same memory controller. If the clients all send at line rate, the switch buffers fill, PFC pauses are triggered, and the congestion spreads through the fabric. The result is a congestion tree that can stall unrelated flows. The standard solution is end-to-end congestion control. In InfiniBand, that is often credit-based flow control plus adaptive routing. In RoCE, it is Data Center Quantized Congestion Notification (DCQCN) or a similar algorithm. DCQCN uses Explicit Congestion Notification (ECN) marks from switches to signal congestion, and the NIC reduces its rate. The algorithm has parameters that must be tuned: the ECN marking threshold, the increase and decrease rates, and the reaction point's timer. Tuning is workload-dependent, and a misconfigured pool can oscillate between underutilization and congestion collapse.

For a memory pool, the traffic pattern is often incast: many clients read from the same memory server. Incast is hard on switches because the bottleneck is the server's NIC or memory controller, not the network. Increasing switch buffers only delays the problem. The better approach is to limit the number of outstanding requests per client and to use admission control. The memory server can advertise a maximum number of outstanding requests, and the client's agent can enforce it. The server can also rate-limit per client at the NIC using hardware queues or at the control plane by issuing tokens. The goal is to keep the server's memory controller and NIC at their optimal operating point without letting any single client monopolize them.

Multirail and multipath can improve bandwidth and resilience. A memory server with multiple NICs can spread traffic across them, and a client with multiple NICs can use them to increase its own bandwidth. But multirail introduces ordering problems: operations on different rails may complete out of order, and a failure on one rail may leave a queue pair in an error state. The control plane must track which rails are healthy and must migrate queue pairs when a rail fails. Multipath routing within a fabric can also cause reordering. Some NICs handle reordering in hardware; others leave it to software. If the software assumes in-order delivery, it must either disable multipath or add sequence numbers to detect gaps. This is another place where the failure semantics of the fabric leak into the design of the memory pool.

Topology and placement matter more than they do for local memory. A compute node and a memory server in the same rack have lower latency and higher bandwidth than nodes separated by several switch hops. If the scheduler is unaware of the pool topology, it may place a latency-sensitive workload on a compute node that is far from its memory. The pool should expose topology information to the scheduler, either as a metric or as a placement constraint. In Kubernetes, this could be a topology-aware scheduling hint or a device plugin that reports the memory server's rack. The scheduler can then co-locate compute and memory where possible, and use remote memory only when local capacity is exhausted.

Fabric failures are inevitable. A cable can be unplugged, a switch can reboot, a NIC can reset. The memory pool must be designed so that a single fabric failure does not corrupt data. If a queue pair enters an error state, the client must stop using the associated rkey and must not assume that in-flight operations completed. The server must detect the error and reclaim the client's regions after the lease expires. The control plane must update the pool manifest if a memory server becomes unreachable. If the pool uses replication, the client can fail over to a replica on a different fabric path. If not, the data is unavailable until the fabric is repaired. The design should make the failure domain explicit: a rack, a switch, or a power domain. The pool's replication and placement policies should be aligned with those domains.

Finally, the fabric is a shared resource. Multiple tenants may share the same switches and the same memory servers. Without isolation, one tenant's burst can affect another tenant's latency. Isolation can be implemented with separate queue pairs, separate traffic classes, or separate physical rails. The strongest isolation is separate physical rails, but it is also the most expensive. The weakest is a shared queue pair with QoS weights, which requires careful tuning. The design should choose a point on that spectrum and document the assumptions. A pool that claims multi-tenancy but shares a single queue pair per server will not provide predictable performance under contention.

## Operating system and runtime integration

A disaggregated memory pool is only useful if applications can use it without rewriting everything. That means integration with the operating system, the memory allocator, and the language runtime. The integration points are where the abstraction leaks, and they are often the difference between a research prototype and a deployable system.

The most common abstraction is memory tiering. The operating system treats remote memory as a slower tier of DRAM. Pages are placed in the local tier or the remote tier based on access frequency. On a page fault or a migration decision, the OS moves the page between tiers. This works for applications that have a large working set and can tolerate some migration latency. It does not work for applications that require predictable latency, because a remote page fault is much slower than a local page fault. The OS must also handle the fact that remote memory is not cache-coherent. If a page is mapped into multiple address spaces, the OS must manage coherence in software, which is expensive and error-prone. For these reasons, memory tiering is usually implemented as a user-space runtime or a library, not as a transparent kernel feature.

A user-space runtime can provide a remote malloc. The application calls `remote_malloc`, which returns a pointer in a remote region. The runtime maintains a local mapping from the pointer to the remote address and rkey. The application can read and write the memory through the runtime's API, or the runtime can use `userfaultfd` to trap accesses and perform RDMA operations. The `userfaultfd` approach is powerful because it allows existing applications to use remote memory without source changes. The runtime installs a page fault handler, maps the remote region as `PROT_NONE`, and on a fault, it fetches the page via RDMA, maps it locally, and resumes the application. This is essentially demand paging over RDMA. The performance depends on the page size and the fault rate. If the application has good locality, most accesses hit local pages after the first fault. If it has poor locality, every access becomes a page fault and the runtime becomes a bottleneck.

A more efficient approach is to use huge pages and to prefetch. The runtime can fetch a 2 MB page with a single RDMA READ, which amortizes the latency over many accesses. It can also use access hints from the application or from a profiler to decide which pages to fetch. The challenge is that prefetching can waste bandwidth if the application does not use the whole page. The runtime must balance the cost of a fault against the cost of fetching unused data. This is the same trade-off as local prefetching, but the bandwidth cost is higher because it consumes the network.

Language runtimes have their own memory managers. A Java runtime uses a garbage-collected heap. Making that heap remote is difficult because the garbage collector needs to traverse pointers and update them. If the heap is remote, every pointer dereference is an RDMA operation, which is far too slow. The practical approach is to keep the heap local and use remote memory for off-heap data, such as large caches or buffers. The Java runtime can expose `ByteBuffer` or `DirectByteBuffer` backed by remote memory. The application uses the buffer explicitly, and the garbage collector does not need to traverse it. Similarly, a Go runtime can use remote memory for large byte slices that are managed manually or with finalizers. The key is to avoid making the garbage collector scan remote memory.

For C and C++, the allocator is the integration point. A custom allocator can be plugged into the application, or the application can use a library that provides remote memory pools. The allocator must handle alignment, size classes, and thread safety. It must also handle the fact that remote memory is not directly addressable from the CPU. The application cannot dereference a remote pointer; it must use the allocator's API to copy data to a local buffer. That is a significant programming model change. Some systems hide it by mapping remote memory into the process address space and using `userfaultfd`, but that reintroduces the page fault overhead.

GPU memory is another integration point. GPUs have their own memory hierarchies and their own interconnects. An RDMA NIC can DMA directly to GPU memory using GPUDirect RDMA, which allows a compute node to read or write GPU memory without involving the CPU. This is useful for machine learning workloads that need to access large embedding tables or datasets. The memory server can be a GPU server with a large HBM pool, or a CPU server with DRAM. The RDMA operations are the same, but the memory registration and the completion paths are different. GPUDirect RDMA requires the GPU driver to pin the memory and expose it to the NIC. The control plane must coordinate with the GPU scheduler to ensure that the memory is not migrated or freed while it is remote-accessible.

Kernel bypass is another integration choice. RDMA user-space verbs bypass the kernel for data path operations, which reduces latency and CPU overhead. But the kernel still controls memory registration, queue pair creation, and event handling. If the pool is used by a kernel component, such as a swap device or a filesystem, the data path goes through the kernel's RDMA stack, which has different performance characteristics. The design should decide whether the pool is a user-space library, a kernel module, or a hybrid. A user-space library is easier to develop and debug. A kernel module can support transparent memory tiering and remote swap. A hybrid can use the kernel for control plane and user-space for data plane. Each choice affects failure handling, security, and observability.

Remote swap is a special case of memory tiering. The OS swaps pages to a remote memory server instead of a local disk or SSD. The advantage is lower latency and higher bandwidth than disk. The disadvantage is that the network becomes a critical resource for memory pressure. If the network fails or the memory server fails, the system may lose pages. Remote swap is therefore suitable only for data that can be regenerated or for deployments with redundant network paths. It is not a replacement for persistent storage. It is a way to extend the effective memory capacity of a node without adding local DIMMs. The OS must be careful not to thrash: if the working set exceeds local memory and the network bandwidth is limited, swapping to remote memory can be slower than swapping to local SSD. The decision should be based on measured latency and bandwidth, not on the assumption that remote DRAM is always faster than local storage.

Finally, observability must cross the OS boundary. A remote memory access is not visible in the local CPU's performance counters. The runtime must export its own metrics: fault rate, prefetch hit rate, RDMA operation counts, and error counts. It should also correlate those metrics with the application's throughput and latency. Without that correlation, operators will not know whether a performance problem is in the application, the local memory, the network, or the memory server. The pool is a distributed system, and its observability must be distributed as well.
