Every parallel system eventually asks the same question: *what is the most urgent thing left to do?* A thread pool with deadlines asks it. A shortest-path search asks it. A discrete-event simulator asks it. A branch-and-bound solver asks it. A top-k aggregation in a query engine asks a close cousin of it.

The data structure that answers it is the priority queue, and the workhorse implementation is the binary heap. The binary heap is a beautiful piece of engineering: an implicit tree stored in an array, O(1) find-min, O(log n) insert and delete-min, and cache behavior good enough that it beats asymptotically superior structures on nearly every workload that fits in memory.

Then you add threads, and it falls apart.

The usual diagnosis is "locks are slow," and the usual prescription is "use a lock-free heap." Both are incomplete. The problem is not the lock. The problem is the shape of the heap. Every delete-min in a binary heap touches the root, and the root is one cache line. Replacing the mutex with a compare-and-swap does not remove the contention; it relocates it from the lock's waiter queue into the cache coherence protocol, where it is harder to see and harder to reason about.

This article is about the design space that opens up once you accept that. The central move is not a better lock or a cleverer atomic. It is a redefinition of what the structure promises. Once you allow a priority queue to return *approximately* the minimum — one of the k smallest, say, or one whose rank is bounded with high probability — a large amount of design space opens up, and the contention wall stops being a wall.

We will start with the sequential heap's invariants and identify exactly which of them cause the trouble. Then we will quantify the contention. Then we will define correctness precisely enough to talk about relaxing it. Then we will look at the fine-grained locking designs that tried to fix the heap without giving up linearizability, and see why they disappoint.

## The binary heap, and which invariants cost you

A binary heap over n elements is an array `a[0..n-1]` satisfying two invariants:

1. **Shape.** The tree is complete: every level except possibly the last is full, and the last level is filled left to right. Equivalently, the children of `a[i]` are `a[2i+1]` and `a[2i+2]`, and the parent of `a[i]` is `a[(i-1)/2]`.
2. **Order.** `a[parent(i)] <= a[i]` for every non-root `i`.

Three operations matter:

- `find_min()` reads `a[0]`. O(1).
- `insert(x)` writes `x` at index `n`, increments `n`, then sifts up: while `x` is smaller than its parent, swap. O(log n) worst case, O(1) amortized for random keys.
- `delete_min()` reads `a[0]`, moves `a[n-1]` to `a[0]`, decrements `n`, then sifts down: repeatedly swap with the smaller child until both children are larger. O(log n).

Notice what the operations touch. `find_min` and `delete_min` both read index 0. `delete_min` also *writes* index 0, on every single call, because the replacement element comes from the tail. `insert` and `delete_min` both read and write index `n-1` — the shape invariant makes the array's tail global state, exactly like the root.

So a binary heap has two globally shared locations that every mutating operation touches: the root and the tail. They sit at opposite ends of the array, which is to say at opposite ends of the access pattern. The root is in the first cache line; the tail is wherever the array currently ends.

Now consider the sift-down path. Starting at the root, `delete_min` visits exactly one node per level, all the way to a leaf. The path length is `floor(log2 n)`. The nodes it touches are `a[0]`, then `a[1]` or `a[2]`, then one of `a[3..6]`, and so on. The first four levels of a heap of any size fit in two 64-byte cache lines if the elements are 8 bytes wide — 15 nodes, 120 bytes. Every `delete_min` writes into that region.

This is the structural fact that matters: the heap's *only* global guarantee is at the root. Unlike a B-tree, a skiplist, or a balanced BST, the heap has no local ordering between siblings and no notion of "the region of the key space I care about." You cannot descend toward a key, because there is nothing to compare against except the current node and its children. Any operation that removes the minimum must start at the top.

## The contention wall, quantified

Let us put a number on the root contention, because the number explains why fine-grained locking does not save the heap.

Suppose `m` threads are executing `delete_min` concurrently. Each one follows a root-to-leaf path. At each level, the path goes left or right depending on which child is smaller. If the keys are drawn from a distribution that does not correlate with position — which is the normal case, and in particular the case right after a random replacement element is placed at the root — then the direction chosen at each level is roughly a fair coin, independent across operations.

Under that assumption, the expected number of the `m` operations that touch a *particular* node at depth `d` is `m / 2^d`. The root is touched by all `m`. A given depth-1 node is touched by about `m/2`. A given depth-2 node by about `m/4`. Contention, in the sense of "more than one operation wants this location," persists down to depth `log2 m`. With 64 threads, the top six levels — 63 nodes, well under a kilobyte of memory — are contended. Everything below that is effectively private.

The assumption is an approximation, and the real distribution is skewed by the key distribution and by the fact that the replacement element placed at the root is the *last* element of the array, which after many operations is not a uniformly random key. But the qualitative conclusion is robust and is confirmed by every implementation that has been measured: the top of the heap is a bottleneck whose severity grows with the number of threads, and no amount of fine-grained locking at the leaves helps, because the leaves are not where the conflict is.

There is a second, subtler cost. The root's cache line is read by every thread, so it is present in many cores' caches in the Shared state. Every `delete_min` writes it. Each write must invalidate every other copy before it can proceed, which is a coherence transaction across the interconnect. On a single socket this is on the order of a few tens of nanoseconds; across sockets on a NUMA machine it is several times that, and the line migrates between home nodes. The throughput ceiling for operations on a single cache line is set by that round trip, not by the number of cores. Adding cores does not raise the ceiling; it just adds more threads waiting behind it.

This is why "lock-free" is not the answer by itself. A lock-free heap that CASes the root has the same coherence traffic as a mutex-protected heap, minus the lock's own atomic operations. The serialization point moved from the lock word to the root pointer, but it did not disappear.

## What "correct" means, and what it could mean instead

To talk about relaxing a data structure, we need to say precisely what we are relaxing.

The standard notion is **linearizability**. A concurrent priority queue is linearizable if there is a sequential history of the operations in which (a) each operation takes effect at some instant between its invocation and its response, (b) the sequential order is consistent with the real-time order of non-overlapping operations, and (c) the sequential history is a legal history of a sequential priority queue — that is, every `delete_min` returns the smallest element present at that instant.

Linearizability is a strong, composable guarantee, and it is exactly what makes the heap hard. It forces a total order on `delete_min` operations, and the natural serialization point for that total order is the element being removed — which lives at the root. Two concurrent `delete_min` calls cannot both remove the current minimum; one of them must see the other's effect. That is a genuine dependency, not an implementation artifact.

The relaxations that matter in practice take one of three forms.

**k-out-of-order.** `delete_min` returns one of the k smallest elements currently in the queue, for a fixed parameter k. Nothing else changes: no element is lost, no element is duplicated, and the queue still eventually drains. This is the guarantee offered by the sub-queue designs we will look at later.

**Rank bounds with high probability.** `delete_min` returns an element whose rank among the current elements is at most `f(n)` with probability at least `1 - 1/n^c`, for some function `f` and constant `c`. The bound is probabilistic and the parameters are tunable. This is the guarantee offered by randomized spraying.

**Quasi-linearizability and related quantitative relaxations.** A more general framework in which each operation is allowed to "see" a bounded amount of disorder, parameterized by a real number. Useful for reasoning about composition, less useful for writing code.

The reason these relaxations are worth considering is not that exactness is overrated. It is that the applications which use priority queues are frequently insensitive to small rank errors. A task scheduler that runs the third-most-urgent task instead of the first is fine. A top-k aggregation that returns the k smallest elements in an arbitrary order is fine. An optimistic discrete-event simulator that processes events slightly out of timestamp order is fine, because it already has a rollback mechanism for exactly that case. A branch-and-bound search that explores nodes in a slightly wrong order still finds the optimum; it just prunes less effectively.

Where relaxation is *not* fine is worth stating just as clearly, because the failure mode is subtle. Dijkstra's algorithm, in its standard form, extracts a vertex and marks it settled, relying on the fact that the extracted key is the true shortest distance. If a relaxed queue hands back a vertex whose key is larger than the current minimum, you may settle it too early, and no later relaxation will fix it, because you have already marked it final. The same applies to A*. Relaxed priority queues are not drop-in replacements for `std::priority_queue` in these algorithms. They are used in variants — Δ-stepping, or searches that re-insert and re-check rather than settling — that are designed for the relaxation. If you take one thing from this section, take that: the relaxation is a property of the *algorithm plus the data structure*, not of the data structure alone.

## Fine-grained locking: the first attempt

The first serious response to heap contention was to keep the heap and keep the semantics, and replace the single lock with many.

The straightforward version locks a node and its children before descending. Rao and Kumar's 1988 design did something along these lines: a `delete_min` acquires the root and its two children, decides which child to descend into, releases the locks it no longer needs, acquires the next level, and so on. The invariant is that you never hold locks on two nodes that are not ancestor and descendant, which prevents deadlock as long as every operation moves strictly downward.

Hunt, Michael, Parthasarathy, and Scott's 1996 design refined this with lock coupling plus a per-node dirty bitmask. The mask records which of a node's subtrees have been modified since the last time a reader looked at it. A thread that finds a clean mask can read a child's value without locking it, because nothing has changed it. This lets readers and writers overlap and substantially reduces the number of lock acquisitions on the sift-down path.

Both designs are correct, and both are disappointing on many-core hardware, for a reason that is visible in the level analysis above. The root lock is required by every `delete_min`, and it must be held at least long enough to read the root's value and decide which child to descend into. That is a short critical section, but it is a critical section on the hottest location in the structure, and it is unavoidable: the decision about which way to go cannot be made without the root's contents. Fine-grained locking moves the bottleneck from "the whole heap" to "the top two levels of the heap," which is a real improvement at low thread counts and a rounding error at high ones.

There is a second problem, specific to the heap's shape invariant. A `delete_min` must remove the last element of the array and place it at the root. Those are two locations at opposite ends of the array, and they must be updated together: if you remove the tail element and then fail to place it, you have lost an element; if you place it and then fail to remove it, you have duplicated one. The shape invariant makes the tail a second global serialization point, and no amount of locking cleverness at the root addresses it.

## Sub-queue designs: k heaps and the k-out-of-order guarantee

The simplest way to break the root bottleneck is to have more than one root. Instead of a single heap, maintain `k` independent heaps, each with its own lock (or its own lock-free algorithm). The data structure's state is the tuple of heaps. An `insert(x)` picks one heap — uniformly at random, or by hashing the key — locks it, and performs a sequential insert. A `delete_min()` must return an element that is among the `k` smallest currently present. The design that achieves this guarantee without a global lock is the *k-sub-queue*.

The core idea is to make `delete_min` sample a subset of the sub-queues, rather than all of them. If it sampled all `k`, it would find the true minimum, but it would also serialize on the global selection: every `delete_min` would need to lock every sub-queue, or at least read every sub-queue's root. That is a contention point with `k` locations instead of one, which is better but still scales poorly as `k` grows. The relaxation is to sample `s` sub-queues, where `s` is a small constant or grows slowly with `n`. The `delete_min` locks the sampled sub-queues, reads their minima, picks the smallest, removes it, and unlocks. The returned element is the minimum of the sampled sub-queues, which is not necessarily the global minimum. But its rank is bounded.

Why is the rank bounded? Suppose inserts are spread uniformly at random across the `k` sub-queues. Then each sub-queue holds a random subset of the elements, of expected size `n/k`. If `delete_min` samples `s` sub-queues uniformly at random, it effectively considers a random subset of the elements of expected size `s * (n/k)`. The minimum of that subset is the minimum of a random sample of size `m ≈ s n / k` from the `n` elements. For any distribution of keys, the expected rank of the minimum of a random sample of size `m` is `(n+1)/(m+1) ≈ k/s`. So on average, the returned element is among the top `k/s` elements. If we want a guarantee of rank at most `k`, we need `s ≥ 1`, which is trivial. But we want a high-probability bound. The probability that the rank exceeds `k` is the probability that none of the `k` smallest elements is in the sampled sub-queues. If the `k` smallest elements are spread across the sub-queues, the chance that a given one is missed is `(1 - 1/k)^s ≈ e^{-s/k}`. For all `k` to be missed, the probability is roughly `e^{-s}`. So with `s = O(log n)`, the probability of exceeding rank `k` is polynomially small. This is the k-out-of-order guarantee: `delete_min` returns one of the `k` smallest with probability at least `1 - 1/n^c`, for a constant `c` that depends on `s`.

The implementation details matter. Each sub-queue can be a simple binary heap protected by a mutex. The `insert` operation is cheap: one lock, one sift-up. The `delete_min` operation locks `s` sub-queues. To avoid deadlock, the locks must be acquired in a fixed order, e.g., by sub-queue index. The critical section is short: read the root of each locked sub-queue, compare, remove the minimum from the chosen one. The removal itself is a sift-down, which touches only that sub-queue. The other `s-1` sub-queues are unlocked immediately after their roots are read. So the contention is spread across `s` roots, and each root is touched by only a fraction of the `delete_min` operations. If `s` is small, the probability that two concurrent `delete_min` operations sample the same sub-queue is moderate, but the lock hold time is short. The throughput scales until the number of threads approaches `k`, at which point the probability of collision on a sub-queue becomes significant. Increasing `k` reduces collisions but increases the cost of sampling if `s` is fixed. There is a trade-off: `k` should be at least the number of threads, and `s` should be large enough to give the desired rank bound but small enough to keep the per-operation cost low.

The k-sub-queue design is appealing because it is simple to implement on top of an existing sequential heap, and it provides a clear, quantitative relaxation. Its main drawback is that it does not eliminate the serialization point entirely; it just multiplies it by `k`. If `k` is large, the memory overhead of `k` separate heaps becomes noticeable, and the cache footprint of the sub-queue roots grows. But for many applications, `k` in the range of 8 to 64 is sufficient to remove the bottleneck for dozens of threads.

## Skiplist-based relaxed priority queues

A skiplist is a probabilistic search structure that supports insert, delete, and search in expected `O(log n)` time. It is built from a bottom-level linked list containing all elements in sorted order, plus a hierarchy of express lanes that skip over ranges of elements. The head of the skiplist has a tower of forward pointers, one per level. The minimum element is always the first element of the bottom-level list.

A sequential priority queue can be implemented on a skiplist by inserting elements in sorted order and having `delete_min` remove the first element. The advantage over a heap is that skiplists have well-known concurrent implementations, both lock-based and lock-free, that scale well for insert and search. The disadvantage is that `delete_min` must remove the first element, which is a single location at the head of the list. That head is the new root bottleneck.

The relaxation that works well with skiplists is again k-out-of-order, but the structure makes it more natural to implement. Because the bottom-level list is sorted, the first `k` elements are exactly the `k` smallest. A relaxed `delete_min` can remove any one of the first `k` elements. To do so concurrently, it locks a window of the first `k` nodes (or uses a lock-free technique with a helping mechanism) and removes one of them. The choice can be random, or it can be the first one it successfully locks. The returned element is guaranteed to be among the `k` smallest, because it is one of the first `k` elements in sorted order. This is an exact k-out-of-order guarantee, not probabilistic. The only probabilistic element is the skiplist's balance, which affects the expected depth of the nodes but not the ordering.

The challenge is to maintain the window of the first `k` elements under concurrent insertions and deletions. If a new element smaller than the current window is inserted, it must be added to the front, potentially pushing the window. If an element in the window is deleted, the window may need to be extended. A simple approach is to lock the head node and the first `k` nodes whenever a `delete_min` is performed. That serializes all `delete_min` operations on the head, which defeats the purpose. A better approach is to use a fine-grained locking scheme where each node has its own lock, and a `delete_min` acquires locks on a contiguous range of nodes starting from the head. To avoid deadlock, locks are acquired in order from left to right. The operation then picks one of the locked nodes to remove, updates the links, and releases the locks. The contention is spread across the `k` nodes in the window. If `k` is large enough, multiple `delete_min` operations can proceed in parallel, as long as their windows overlap only partially. The probability of collision decreases as `k` grows.

There is a subtlety: the skiplist's forward pointers at higher levels must be updated when a node is removed. If the removed node is not the head, the higher-level pointers that skip over it must be adjusted. This is the standard skiplist deletion algorithm, and it can be done under the node's lock. The fact that we are removing an arbitrary node from the first `k` rather than the head does not change the deletion logic; it only changes which node is chosen. The `delete_min` operation must still find the node's predecessors at each level, which requires traversing from the head. That traversal touches the head, so there is still some contention on the head's cache line. However, the traversal is read-only until the node is locked, and read-only accesses to a shared cache line scale much better than writes. The writes are distributed across the `k` nodes in the window. This is a significant improvement over the heap, where every `delete_min` writes the root.

The skiplist design also has a natural way to handle the shape invariant problem that plagued the heap. There is no global tail; each node is allocated independently, and the list's length is not stored in a single location. The only global state is the head's forward pointers, which are read-mostly. This makes the skiplist a better fit for relaxed priority queues than the array-based heap, despite its higher constant factors.

## Randomized spraying and probabilistic rank bounds

The k-sub-queue and skiplist designs both maintain a single logical priority queue, partitioned into sub-queues or a sorted list. Randomized spraying takes a more radical approach: it abandons the single logical queue entirely. Instead, it maintains `k` independent priority queues, and both `insert` and `delete_min` are sprayed across them at random. There is no attempt to coordinate the sub-queues during `delete_min` beyond sampling a few of them.

The basic spraying design works as follows. There are `k` sub-queues, each a sequential priority queue with its own lock. `insert(x)` picks a sub-queue uniformly at random and inserts `x`. `delete_min()` picks `s` sub-queues uniformly at random, locks them in a fixed order, reads their minima, selects the smallest, removes it, and unlocks. The returned element is the minimum of the sampled sub-queues. If `s = 1`, this is pure spraying: each `delete_min` just removes the minimum of a random sub-queue. If `s = k`, it is equivalent to a single priority queue with a global lock, because it samples all sub-queues. The interesting regime is `1 < s < k`.

The rank guarantee for spraying is probabilistic and depends on the assumption that inserts are spread uniformly at random. Under that assumption, each sub-queue contains a random subset of the elements. When `delete_min` samples `s` sub-queues, it considers the union of those subsets, which is a random subset of the elements of expected size `m = s n / k`. The minimum of this subset is the minimum of a random sample of size `m`. As we derived earlier, its expected rank is `n/(m+1) ≈ k/s`. To get a high-probability bound, we can use the fact that the rank of the minimum of a random sample of size `m` is at most `k` with probability at least `1 - (1 - k/n)^m ≈ 1 - e^{-mk/n} = 1 - e^{-s}`. So if we want the probability of exceeding rank `k` to be at most `1/n^c`, we need `e^{-s} ≤ n^{-c}`, which means `s ≥ c ln n`. Thus, sampling `O(log n)` sub-queues is sufficient to guarantee that the returned element is among the `k` smallest with high probability. This is a powerful result: the per-operation cost is `O(s log(n/k))`, which is `O(log n log(n/k))`, and the contention is spread across `s` sub-queues. The parameter `k` controls the trade-off between rank error and memory/contention. Larger `k` means more sub-queues, which reduces contention on each sub-queue but increases the expected rank for a fixed `s`. To keep the rank bound at `k`, `s` must grow with `k`? Actually, the bound `s ≥ c ln n` is independent of `k` for the probability of exceeding rank `k`. Wait: the probability of exceeding rank `k` is `e^{-s}` only if the `k` smallest elements are all missed. But if `k` is large, the probability that a given one is missed is `(1 - 1/k)^s`. For all `k` to be missed, the probability is roughly `(1 - 1/k)^{s k} ≈ e^{-s}`. So indeed, the bound is independent of `k` as long as `k` is not too small. So you can choose `k` to be large (e.g., number of threads) and `s = O(log n)` to get a high-probability guarantee of rank ≤ `k`. That is a very favorable scaling.

In practice, `s` is often set to a small constant like 2 or 3, because the high-probability bound is pessimistic and the actual rank distribution is concentrated. The spraying design is used in systems where the priority queue is a bottleneck and the application can tolerate occasional rank errors. It is particularly effective for task scheduling, where the cost of processing a slightly less urgent task is negligible compared to the cost of waiting for a lock.

The main challenge in implementing spraying is ensuring that the random distribution of inserts is maintained. If the insert policy is biased — for example, if it uses a round-robin counter — the sub-queues may become correlated with the key distribution, and the rank bound may fail. A simple random choice or a hash of the key is usually sufficient. The `delete_min` sampling must also be uniform and independent of the insert policy. The locks on the sampled sub-queues must be acquired in a consistent order to avoid deadlock. Since the sub-queues are independent, the lock order can be the sub-queue index. The critical section is short: read the root, compare, remove. The removal is a standard heap delete-min on one sub-queue. The other sampled sub-queues are unlocked as soon as their roots are read. This means the lock hold time is dominated by the sift-down on the chosen sub-queue, which is `O(log(n/k))`. The contention is therefore on the chosen sub-queue's root, but only one out of `s` sampled sub-queues is actually modified. The other `s-1` are only read. Read-read sharing of a cache line is cheap; it is the write that causes invalidation. So the number of coherence invalidations per `delete_min` is one, on the chosen sub-queue's root. The other sampled roots are read without invalidating. This is a significant improvement over the single heap, where every `delete_min` invalidates the root.

## Choosing parameters and the cost model

The three designs we have discussed — k-sub-queues, relaxed skiplists, and randomized spraying — all share a common structure: they partition the priority queue into `k` independent or semi-independent parts, and they relax the `delete_min` guarantee to allow returning an element that is not the global minimum. The parameters `k` and `s` (where applicable) control the trade-off between scalability and rank error.

A simple cost model can guide the choice. Let `T_lock` be the time to acquire and release a lock, `T_cache` be the time for a cache miss or coherence transaction, and `T_sift` be the time to sift down one level. For a single heap with a global lock, the throughput ceiling is roughly `1 / (T_lock + T_cache + log n * T_sift)`. The `T_cache` term is the root invalidation, which is on the critical path. For a k-sub-queue or spraying design with `s` sampled sub-queues, the critical path is `s * T_lock` (for locking the sampled sub-queues) plus `T_cache` (for the chosen root) plus `log(n/k) * T_sift`. The `s * T_lock` term grows with `s`, but `T_lock` is small compared to `T_cache` on a contended cache line. The key benefit is that the `T_cache` term is no longer multiplied by the number of threads, because the writes are spread across `k` roots. The probability that two threads write the same root is roughly `1/k` per operation, so the effective contention on a single root is reduced by a factor of `k`.

The rank error is bounded by `k` in the k-sub-queue and skiplist designs, and by `k` with high probability in the spraying design when `s = O(log n)`. In practice, `k` is chosen to be a small multiple of the number of threads, e.g., `k = 4 * P` for `P` threads. This ensures that the probability of two threads colliding on the same sub-queue is low. The sampling parameter `s` is chosen to be as small as possible while still meeting the rank bound. For spraying, `s = 2` or `3` is often enough to get a rank bound of `k` with high probability in practice, even though the theoretical bound requires `s = O(log n)`. The discrepancy is because the theoretical bound is worst-case over all key distributions, while real workloads often have more structure.

The memory overhead of these designs is `k` times the size of a single priority queue, plus the locks. For a heap, that is `k` arrays of size `n/k`, which sums to `n` elements plus `k` array headers. The cache footprint of the roots is `k` cache lines, which is small. The skiplist design has a single list, so its memory overhead is just the extra pointers for the express lanes. The spraying design has `k` separate heaps, so its memory overhead is similar to the k-sub-queue design.

The choice among the designs depends on the application. If the application requires an exact k-out-of-order guarantee with no probability of failure, the k-sub-queue or relaxed skiplist is appropriate. If the application can tolerate a probabilistic guarantee and wants the simplest possible implementation, spraying is attractive. If the application needs to support concurrent inserts and deletes with a single logical queue and wants to avoid the array tail problem, the skiplist is a good fit. In all cases, the relaxation is the key that unlocks scalability. The contention wall is not a law of nature; it is a consequence of insisting that every `delete_min` return the exact minimum from a single shared location. Once that insistence is dropped, the wall becomes a slope, and the slope can be made as gentle as the application requires.

## The contention wall is a workload property

The cost model above treats `T_cache` as a constant, but contention is not a property of a data structure in isolation. It is a property of the offered load. A single heap with a global lock can serve millions of operations per second when one thread is doing all the work. The same heap collapses when sixty-four threads each demand a `delete_min` at the same rate. The difference is not the code; it is the arrival process.

The right mental model is a queueing system. Each `delete_min` has a service time that includes the time to acquire the serialization point, read the root, perform the sift-down, and release. If the serialization point is a single cache line, the service time includes a coherence round trip. When the arrival rate approaches the reciprocal of that service time, the wait time grows without bound. The wall is the utilization asymptote, not a fixed core count. Adding cores increases the arrival rate; it does not increase the service rate of the shared line. Relaxation works because it multiplies the service points, which lowers the utilization of each one.

This framing explains why the wall appears at different thread counts for different workloads. A workload with a 90/10 insert-to-delete ratio spends most of its time on inserts. Inserts touch the array tail, not the root, and the tail is a different shared location. If the heap is large and inserts are spread, the tail is still a single index, but the sift-up path is short for random keys. The root is touched only by the 10 percent of operations that delete. The wall may be far away. A workload with a 10/90 ratio hits the root constantly. The same data structure, the same thread count, and a different mix produce different knees in the throughput curve.

Key distribution matters just as much. Random keys produce sift-down paths that branch roughly evenly. Sorted or equal keys produce paths that all go the same way. If every key is equal, the comparison at each level always chooses the same child, so every `delete_min` follows the same root-to-leaf path. The contention is not just at the root; it is along an entire path of `log n` nodes. A sub-queue design helps because each sub-queue has its own path, but within a sub-queue the path is still shared. A simple mitigation is to break ties randomly: when the two children compare equal, choose one with a per-operation coin flip. That does not change the heap's correctness, and it spreads the path across the tree. It is a small change with a large effect on pathological workloads.

The operation mix also determines whether the bottleneck is a write or a read. `find_min` is read-only. Read-only sharing of a cache line scales well because the line can be replicated in Shared state in every core's cache. `delete_min` writes the root, which invalidates every other copy. A workload that calls `find_min` a thousand times per `delete_min` is dominated by reads and may scale acceptably even with a single heap. A workload that calls `delete_min` exclusively is dominated by invalidations. The relaxed designs change the ratio of writes to shared locations: spraying reads `s` roots and writes one. The read traffic increases, but the write traffic per operation stays at one, and it is spread across `k` lines. That is the trade.

Finally, thread count and oversubscription interact with the wall. If there are more runnable threads than cores, a blocked thread is descheduled and another runs. A lock-based heap may look better than it is because the operating system is hiding the contention in context switches. A lock-free or relaxed heap may look worse because it keeps threads spinning and consuming cycles. The wall is still there; it has moved into the scheduler. When measuring, pin threads to cores and report both throughput and CPU time per operation. A design that doubles throughput while tripling CPU time may not be an improvement for a latency-sensitive scheduler.

## Batching, elimination, and combining

Relaxation is a semantic move. There are structural moves that preserve exactness and still reduce contention, and they are worth knowing because they often compose with relaxation. The first is batching. If the application can ask for a batch of minima, the cost of the serialization point is amortized over the batch. A `delete_min_many(m)` operation locks the heap once, removes `m` elements, and returns them. If the caller needs them in sorted order, the queue can sort the batch, or the caller can sort. If the caller only needs a set of urgent tasks, the batch can be unordered. The elements are still exactly the `m` smallest at the moment of removal. The lock hold time grows with `m`, but the number of coherence transactions per element falls. A batch of sixteen can cut the root invalidation rate by an order of magnitude.

Batching changes the API and the latency profile. A thread that asks for one element waits for the whole batch to be assembled. If the queue is nearly empty, the batch is short and the benefit disappears. If the queue is deep, the batch is long and other threads may starve while one thread holds the lock. An adaptive batch size helps: start with a small batch, grow it while the queue is deep and the lock is contended, and shrink it when the queue is shallow. The batch size becomes another relaxation parameter, but it relaxes latency rather than ordering.

Combining is the second structural move. In flat combining, threads publish their operations to a shared publication list. One thread becomes the combiner, takes the lock, and executes all published operations in sequence. The other threads wait or spin. The heap is touched by only one thread at a time, so the cache line stays in one core's cache and the coherence traffic collapses. The cost is that the combiner serializes execution. Throughput is bounded by the combiner's speed, but the per-operation overhead can be much lower than a lock acquisition per operation. For a heap with a short critical section, flat combining can be a net win at moderate thread counts.

For priority queues, combining has a subtlety: the order of operations matters. If two `delete_min` operations are combined, the first one removes the current minimum and the second removes the next. That is a legal sequential history. If an `insert` and a `delete_min` are combined, the order determines whether the inserted element can be removed. The combiner must choose an order that is consistent with the real-time order of non-overlapping operations. For overlapping operations, any order is legal. A relaxed queue can be more aggressive: it can reorder operations within a batch as long as the returned elements satisfy the rank bound. That makes combining easier and faster. The combination of flat combining and relaxed semantics is a natural fit: one thread does the work, and the order within the batch is chosen to minimize sift-down cost.

Elimination is the third structural move. In a stack or a queue, an insert and a delete can cancel each other without touching the central structure. For a priority queue, cancellation is harder because the delete must return the minimum. But there are cases where elimination is exact. If the queue is empty, an insert and a delete can pair directly. If the inserted key is smaller than every key currently in the queue, a delete can take it without consulting the heap. A small elimination array can hold recently inserted keys; a `delete_min` scans the array for a key smaller than the heap's current minimum. If it finds one, it returns it. This is exact, because the key is smaller than the minimum of the rest. If it does not find one, it falls back to the heap. The elimination array acts as a contention filter: it handles the operations that do not need the root. The filter is most effective when inserts and deletes are balanced and keys are diverse. It is useless when every operation deletes and no inserts arrive.

Combining and elimination preserve exactness but change the API or add latency. Relaxation preserves the API but changes the guarantee. The design space is not a single axis from exact to relaxed. It is a product of semantic relaxation, API changes, and structural contention reduction. A production system may use all three: a relaxed sub-queue design for the bulk, a batched exact path for urgent elements, and an elimination array for the common case of a nearly empty queue.

## NUMA and the second-order contention

On a multi-socket machine, the root cache line has a home node. Every write to the root must migrate the line to the writer's node, or invalidate the writer's copy and fetch from the home node. The round trip is longer than on a single socket, and the bandwidth of the interconnect is finite. A single heap on a two-socket machine can hit the wall at half the thread count of the same heap on one socket. The wall is not just a core-count phenomenon; it is a topology phenomenon.

Sub-queue designs help, but only if the sub-queues are distributed across the topology. If all `k` sub-queues are allocated on one node, the contention is spread across `k` lines on that node. Threads on the other node access them remotely. The locks and the roots are remote, and the coherence traffic crosses the interconnect. The throughput may improve over a single heap, but the ceiling is set by the remote node's link. The fix is to allocate sub-queues on the nodes where the threads run, and to make the sampling policy locality-aware. A thread should sample mostly local sub-queues, plus a few remote ones to preserve the rank bound.

Locality-aware sampling changes the probabilistic analysis. If inserts are also locality-aware, each sub-queue contains keys from the threads on its node. If the key distribution is independent of the node, local sampling still sees a random subset of the global key distribution. If the key distribution is correlated with the node — for example, one node handles a class of tasks with shorter deadlines — local sampling can miss the global minimum for a long time. The rank bound becomes a bound relative to the local distribution, not the global one. The design must either hash keys across nodes to break the correlation, or periodically exchange minima between nodes. Hashing keys across nodes costs remote inserts; exchanging minima costs a small amount of cross-node traffic. A hybrid is often best: insert locally, but maintain a cached copy of each remote node's minimum, refreshed on a timer or when a local delete finds nothing urgent. The cache is a hint, not a guarantee. It bounds the rank error only if the refresh rate is high enough relative to the arrival rate of small keys.

The second-order contention is the metadata. A relaxed queue has more shared state than a single heap: locks, sub-queue sizes, random number generators, and counters. Each of these can become a bottleneck. A shared random number generator is a classic hidden serialization point; every operation that calls it contends on its state. Use a per-thread generator seeded from a thread-local source. A shared atomic counter for the total queue size is another. If every insert increments a global counter and every delete decrements it, the counter's cache line becomes the new root. Shard the counter, or approximate the size. A shared array of sub-queue locks can suffer false sharing if the locks are smaller than a cache line. Pad each lock to a cache line, or pack them so that locks used together are not on the same line. The goal is to ensure that the only shared writes are the ones the algorithm actually needs.

NUMA also changes the cost of memory reclamation. A node that frees memory may return it to a global allocator, which then gives it to another node. The allocation and free paths cross the interconnect. For a skiplist-based relaxed queue, node allocation and reclamation can dominate the cost of the priority operations. Per-node pools help: each node allocates from its own pool and frees to its own pool. The pool is a stack or a free list protected by a local lock. The memory stays on the node, and the remote traffic is limited to the occasional refill. This is another place where the relaxed queue's partitioning pays off: the same partitioning that spreads the root contention can spread the allocator contention.

## Memory reclamation and the hidden serialization

Array-based heaps have a quiet advantage: they do not reclaim individual elements. A `delete_min` moves the last element to the root and decrements the size. The array's memory is reused. There are no pointers to invalidate and no nodes to free. A sub-queue design built from arrays inherits that advantage. The sub-queues are arrays; the only shared state is the array headers and the locks. Reclamation is trivial. This is one reason the k-sub-queue design is attractive despite its simple rank bound.

A skiplist-based relaxed queue does not have that advantage. Each element is a node with a tower of forward pointers. Removing a node from the first `k` requires updating the pointers at every level, and freeing the node requires knowing that no other thread can still reach it. In a lock-based design, the node's lock protects its lifetime: a thread that holds the lock can remove the node and free it after releasing the lock, because any other thread that wants to read the node must first acquire its lock. The lock is doing double duty as a mutual exclusion mechanism and a reclamation mechanism. That is simple, but it adds a lock acquisition to every node read. The lock-free design avoids the lock but needs hazard pointers or epoch-based reclamation. Each thread publishes the pointers it is reading; a writer checks the published set before freeing. The check is a shared read of the hazard array, which can itself become a contention point if the array is not sharded. Epoch-based reclamation is cheaper on the read side but defers frees, which increases memory footprint and can cause long pauses when an epoch advances.

The allocator is the hidden serialization point in all of these designs. A lock-free skiplist that calls `malloc` and `free` on every operation has moved the contention from the queue's root to the allocator's free lists. Modern allocators use per-thread caches to reduce this, but the caches are finite and the slow path is shared. A relaxed priority queue with a high operation rate can exhaust the cache and fall into the shared path. The fix is to pool nodes by size and height. A skiplist node's tower height is random; pool the common heights separately. A sub-queue heap does not need this, because its storage is a single array. If the application can tolerate the memory overhead, the array-based design is often faster in practice for exactly this reason.

Reclamation also affects progress guarantees. A lock-free queue may be theoretically non-blocking, but if a thread is descheduled while holding a hazard pointer, other threads may be unable to free memory and may run out of space. The queue may still make progress on operations, but the system as a whole can stall. A blocking design with short critical sections is often more predictable. For a task scheduler, predictability matters more than the strongest theoretical progress guarantee. The design should state its progress property honestly: lock-free, obstruction-free, or blocking with bounded critical sections. The relaxed semantics do not change the progress property; they change the contention profile.

## Adaptive relaxation and hybrid designs

Fixed parameters are a compromise. A queue tuned for sixty-four threads may be wasteful for four. A queue tuned for a deep backlog may be too relaxed for a nearly empty queue. Adaptive designs change `k` or `s` in response to observed conditions. The simplest adaptive rule is to set `k` to a small multiple of the number of active threads. When a new thread starts, it claims a sub-queue or creates one. When a thread stops, its sub-queue is merged or left idle. The number of sub-queues tracks the parallelism, so the contention per sub-queue stays roughly constant. The rank bound also stays roughly constant if the sampling rate is adjusted.

Splitting a hot sub-queue is harder. The sub-queue's lock must be held while its elements are moved to a new sub-queue. The move is a bulk operation: pop half the elements and push them into the new sub-queue. The cost is proportional to the number of elements moved, so the split should be infrequent. A contention monitor can trigger a split when the lock's failed-acquisition rate exceeds a threshold. The monitor must use hysteresis to avoid thrashing: split when contention is high for a sustained period, merge when a sub-queue is idle for a long period. The metadata for the split is itself shared, so the monitor should be per-thread or sharded.

A two-tier design is often more practical than dynamic resizing. The queue maintains a small exact structure for the most urgent elements and a relaxed structure for the bulk. An insert compares the key against a threshold. If the key is below the threshold, it goes into the exact tier; otherwise, it goes into the relaxed tier. A `delete_min` checks the exact tier first. If it is empty, it uses the relaxed tier. The exact tier is small, so its lock is held briefly. The relaxed tier is large, so its contention is spread. The threshold can be a quantile estimate, updated periodically. The design gives exactness for the elements that matter most and scalability for the rest. The risk is that the exact tier grows if the threshold is set too high. A size cap on the exact tier prevents that; when the cap is exceeded, the largest elements in the exact tier are demoted to the relaxed tier.

The application's tolerance for rank error should be part of the API. A queue can expose a `relaxation_budget` parameter: the maximum rank error the caller will accept. The queue chooses `s` to meet the budget with high probability. If the budget is zero, the queue falls back to an exact mode. If the budget is large, the queue uses a small `s` and maximizes throughput. The budget is a contract, not a hint. The queue should document how it is enforced and what happens when the workload violates the assumptions. For example, if inserts are not uniformly distributed, the rank bound may fail. The queue can detect skew by sampling sub-queue sizes and adjusting the sampling policy. It cannot guarantee the bound for an adversarial workload without paying the exact cost.

Hybrid designs also appear at the application level. A task scheduler often has local work deques and a global priority queue. The local deques provide locality and low overhead; the global queue provides urgency and load balancing. A relaxed priority queue is a good fit for the global role because the scheduler can tolerate a small rank error. The local deques are exact and LIFO. The global queue is relaxed and sprayed. A thread that runs out of local work steals from another local deque or takes from the global queue. The global queue's rank error affects which urgent task is chosen, but the local deques ensure that the common case is fast. This two-level structure is more robust than either structure alone. It also shows that the design space of concurrent priority queues is not closed: the queue is a component in a larger scheduling design.

## How to evaluate a relaxed priority queue

The first metric is throughput, but throughput alone is not enough. Measure operations per second as a function of thread count, from one thread to twice the number of cores. Look for the knee. A well-designed relaxed queue should move the knee to the right as `k` increases. If the knee does not move, the bottleneck is not the root; it may be the allocator, the random number generator, or a shared counter. Use hardware performance counters to find the cache line with the most invalidations. A contention profile that names the line is more useful than a throughput number.

The second metric is the rank error distribution. For each `delete_min`, compute the true rank of the returned element. In a test harness, this is easy: maintain a shadow exact priority queue and compare. In production, it is expensive. A sampled approach works: periodically record the returned element and the current minimum from a shadow structure, or use an application-level proxy. The distribution matters more than the mean. A queue with a mean rank error of two but a p99 of one thousand is worse for a scheduler than a queue with a mean of five and a p99 of ten. Report the p50, p99, and p999. Report the maximum over a long run. The maximum is sensitive to outliers, but it is the number that causes missed deadlines.

The third metric is latency. Relaxed queues can have lower mean latency and higher tail latency, or the reverse. A lock-free design may have a fast uncontended path and a slow contended path with retries. A lock-based design may have a long wait in the lock queue. Measure the full distribution. For a scheduler, the p99 latency of a `delete_min` when the queue is deep is the number that matters. A queue that is fast on average but occasionally stalls for a millisecond may be unacceptable. The tail is often caused by a single hot sub-queue or by a reclamation pause. The contention profile should explain the tail.

The fourth metric is correctness under relaxation. The queue must not lose or duplicate elements. A multiset checker verifies that the total number of inserts equals the total number of deletes plus the final size. For a k-out-of-order queue, the checker also verifies that each returned element is among the k smallest at the time of removal. This requires a shadow structure or an offline replay. An offline replay records the operation history and replays it sequentially. The replay computes the true minimum at each delete. The rank error is the difference between the returned element's position in the sorted order and the minimum. The replay is deterministic and reproducible. It is the best way to compare designs.

The workload matters as much as the metrics. Test with uniform random keys, ascending keys, descending keys, equal keys, and keys drawn from a heavy-tailed distribution. Test with balanced insert/delete ratios and with skewed ratios. Test with a queue that is always deep and a queue that is often nearly empty. The worst case for a heap is equal keys or sorted keys; the worst case for spraying is correlated inserts. A design that looks good on uniform random keys may fail on a workload where one thread inserts all the small keys. The evaluation should include an adversarial case where the key distribution is correlated with the thread or the sub-queue.

Benchmarking pitfalls are plentiful. Dead-code elimination can remove the queue operations if the results are not used. CPU frequency scaling can make a single-thread run look faster than a multi-thread run. NUMA imbalance can make a thread on one node slower than a thread on another. Pin threads to cores and report the pinning. Warm up the queue and run multiple trials. Measure the queue in isolation and in the application. The application may have other bottlenecks; Amdahl's law limits the end-to-end gain. A queue that is twice as fast may improve the application by ten percent if the queue is only twenty percent of the runtime.

Finally, report the parameters. A throughput number without `k`, `s`, thread count, key distribution, and queue size is meaningless. The same design can be exact or relaxed depending on the parameters. The same parameters can be fast or slow depending on the workload. The evaluation should state the assumptions and the failure modes. A relaxed priority queue is a tool with a contract; the evaluation is how you learn what the contract is worth.
