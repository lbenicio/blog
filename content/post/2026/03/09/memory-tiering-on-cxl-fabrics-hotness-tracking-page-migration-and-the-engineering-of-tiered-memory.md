Memory tiering is one of those ideas that sounds simple until you try to make it survive contact with a real kernel. Put the hot pages in DRAM. Put the cold pages in CXL-attached memory. Update the page tables. Repeat. The sentence is short; the engineering is not. The interesting part is not the copy loop. It is the policy, the observability, and the long list of invariants that a page migration must preserve while the rest of the system keeps running.

Compute Express Link, or CXL, has made this idea newly practical. A CXL Type 3 device can expose memory to the CPU over a cache-coherent fabric using CXL.mem. The CPU loads and stores to that memory with ordinary instructions. The device is not a disk, not a remote server, and not a software cache. It is a memory tier with different latency, bandwidth, and failure characteristics from local DRAM. That difference is the opportunity and the problem.

This article is not a product review and it does not assume a specific kernel version. It is a design discussion for engineers who have to reason about tiered memory in real systems. The first sections establish the assumptions, explain why tiering is not caching, and examine what hardware actually exposes. Later sections will turn to hotness tracking and migration mechanics. The goal is not to produce a single policy. The goal is to make the trade-offs explicit enough that a policy can be defended.

## Assumptions and scope

The design space is large, so start with a concrete baseline. Assume a cache-coherent CXL fabric with one or more Type 3 memory devices. The host has local DRAM and a CXL memory pool. The operating system manages both as a single physical address space. The kernel can migrate pages between tiers at page granularity. The fabric may include a switch, so not all CXL memory has the same latency. The device may have an internal memory-side cache, but the OS does not control it.

Assume the workload is general-purpose: anonymous memory, file-backed pages, shared libraries, and some pinned memory. Assume no application hints by default. Assume the kernel uses 4 KiB base pages and may use transparent huge pages. Assume migration is implemented in software by the kernel, not by a hardware migration engine. Assume the CXL device can report health and poison events, but not per-page access counts. These assumptions are not universal, but they are representative enough to expose the hard parts.

The first consequence is that tiering is a capacity decision. DRAM is fast and scarce. CXL memory is slower and more plentiful. The system wants to keep the working set in DRAM and use CXL memory for the rest. The second consequence is that tiering is a placement decision. A page is in one tier or the other. Moving it is a state change. The third consequence is that tiering is a policy problem. The kernel must decide which pages to move, when to move them, and when to stop moving them. Every decision has a cost.

## Why tiering is not a cache

The most common mistake is to treat CXL memory as a cache. A cache is a copy. A tier is a placement. If a page is in a cache, the authoritative copy is elsewhere. If a page is in a tier, that tier is the authoritative location. The distinction matters because caches are usually transparent and hardware-managed. Tiering is visible to the operating system and often to the application through performance. A cache can evict a line without changing the virtual address. A tier migration changes the physical address and the page-table entry.

This is not a semantic nicety. A page migration must preserve correctness while the system runs. The kernel must update the page table, the reverse mapping, the page refcount, and the TLB. It must handle concurrent faults, pinned pages, DMA, and IOMMU mappings. It must handle dirty pages and writeback. It must handle memory cgroups and quotas. It must handle huge pages and compound pages. It must handle memory failure and poison. A cache miss is a performance event. A migration failure is a correctness event.

The cache analogy also misleads policy. A cache usually has a simple hit rate objective. A tier has a cost-benefit objective. Moving a page costs a copy, a TLB shootdown, and a period of reduced locality. The benefit is the expected reduction in future access latency. If the page is accessed once and never again, the move is pure overhead. If the page is accessed frequently, the move may pay for itself. The policy must estimate both the future access rate and the cost of the move. That estimate is where hotness tracking enters.

## What the hardware exposes, and what it does not

CXL.mem gives the CPU coherent load and store access to the device. It does not give the CPU a per-page access counter. The device may expose link-level counters, media health, and error information. It may expose performance counters for the fabric. It does not normally expose a page-granular hotness map that the OS can read cheaply. The OS must infer hotness from signals it already has.

The most portable signal is the CPU page-table accessed and dirty bits. The accessed bit tells the kernel that a page has been referenced since the bit was last cleared. The dirty bit tells the kernel that a page has been written. These bits are coarse. They are set by hardware on a page-table walk and may be set for a TLB fill rather than every access. They are also sampled. The kernel does not see every access. It sees a binary signal at the time it reads the bit. That is enough for a statistical policy, but it is not a precise access count.

Clearing the accessed bit is expensive. On many architectures, clearing a page-table bit requires a TLB shootdown so that stale translations do not hide future accesses. A shootdown sends inter-processor interrupts and forces other CPUs to invalidate translations. Doing this at a high frequency can cost more than the migration it is trying to guide. The kernel therefore tends to use multi-generational aging: scan page tables at a controlled rate, read the accessed bit, and advance an age counter. If the bit is set, the page is marked young. If it is clear, the page ages. This produces a rough LRU-like ordering without clearing bits on every scan.

The second signal is performance-monitoring hardware. Modern CPUs can sample load and store addresses with events such as PEBS on Intel and IBS on AMD. These samples are statistical. They have skid, meaning the reported address may be slightly after the instruction that caused the event. They are not free. They consume PMU resources and can perturb the workload. They also require privilege and architecture-specific code. They are useful for profiling and for calibrating a policy, but they are not a general-purpose per-page hotness oracle.

The third signal is application hints. An application can use madvise, mbind, or a similar interface to tell the kernel about expected access patterns. Hints can be useful, but they are often wrong. Applications do not always know their future access patterns. They may be conservative, optimistic, or simply uninformed. A policy that trusts hints blindly can be gamed or misled. A policy that ignores hints loses information that is cheap to obtain. The practical answer is to treat hints as a bias, not as ground truth.

The fourth signal is the CXL fabric itself. A switch may expose per-port counters. A device may expose internal cache hit rates. These signals are aggregate. They can tell the operator that a link is congested or that a device is under pressure. They do not tell the kernel which page is hot. They are useful for capacity planning and for detecting fabric-level problems. They are not a substitute for page-level tracking.

## Hotness tracking as a sampling problem

Hotness tracking is a sampling problem because the kernel cannot observe every access. The policy must decide how often to sample, what to sample, and how to turn samples into decisions. The sampling rate controls the trade-off between responsiveness and overhead. A fast scan reacts quickly to changing working sets, but it consumes CPU and causes TLB shootdowns. A slow scan is cheap, but it may be stale. A page that became hot after the last scan may remain in CXL memory for a long time. A page that became cold may remain in DRAM and waste capacity.

The aging algorithm matters. A simple two-bit scheme, young and old, is easy to implement but has little hysteresis. A multi-bit age counter gives the policy more information. A page that is accessed repeatedly can be distinguished from a page that was accessed once. A page that was hot and is now cooling can be distinguished from a page that was never hot. The cost is more metadata and more bookkeeping. The benefit is a policy that can avoid ping-pong.

The scan must also be NUMA-aware. On a multi-socket system, a page may be accessed by CPUs on different nodes. The accessed bit is set by any CPU that walks the page table. The policy must decide whether to migrate the page to the tier local to the accessing node or to keep it in a shared tier. The answer depends on the access distribution. A page accessed by one node is a good candidate for local DRAM. A page accessed by many nodes may be better in a shared CXL tier, even if it is hot, because moving it to one node would penalize the others. This is the same tension that NUMA balancing already faces, but the tier adds another dimension.

The scan must also account for page size. A 4 KiB page is a fine-grained unit. A 2 MiB huge page is a coarse unit. Migrating a huge page copies more data and causes a larger TLB shootdown. It also affects a larger region of the address space. A policy that treats huge pages like base pages can over-migrate. A policy that ignores huge pages can miss the dominant part of the working set. The practical approach is to track hotness at the base-page level when possible and to make migration decisions at the huge-page level only when the expected benefit justifies the cost. That is a policy choice, not a hardware requirement.

## Migration mechanics and their hidden costs

A page migration is a sequence of steps, and each step has a cost. The kernel allocates a destination page in the target tier. It copies the contents. It updates the page table to point to the new page. It updates the reverse mapping so that the old page can be found and unmapped. It flushes the TLB on CPUs that may have a stale translation. It handles concurrent faults and pinned pages. It may need to wait for writeback or for DMA to complete. It may need to update IOMMU mappings. The copy is only one part of the cost.

The TLB shootdown is often the most disruptive part. A migration changes the physical address behind a virtual address. Every CPU that has a translation for that virtual address must invalidate it. The kernel sends inter-processor interrupts and waits for acknowledgments. The cost grows with the number of CPUs and the number of pages migrated. Batching migrations can amortize some of the cost, but it also increases the latency before the policy reacts. A policy that migrates one page at a time may be more responsive but more expensive. A policy that migrates in batches may be cheaper but less precise.

The copy itself competes for memory bandwidth. Moving a page from DRAM to CXL memory reads from DRAM and writes to CXL. Moving a page from CXL to DRAM reads from CXL and writes to DRAM. Either direction consumes bandwidth that the workload could use. The copy also pollutes the cache. A large migration can evict useful lines and slow down the workload even after the migration completes. The policy must account for this cost, not just the latency difference between tiers.

Pinned pages are a special case. A page that is pinned for DMA, RDMA, or a device driver cannot be migrated without coordinating with the pin owner. The kernel may use migration entries or may fail the migration. A policy that ignores pinned pages will waste time trying to migrate them. A policy that treats all pinned pages as cold will misclassify a hot buffer that happens to be pinned. The practical answer is to track pin state and to exclude pinned pages from automatic migration unless the application explicitly opts in.

Memory failure is another special case. A CXL device can report poison or uncorrectable errors. The kernel must offline the affected page and avoid migrating it. A policy that treats CXL memory as uniformly reliable will eventually be surprised. The tiering policy must integrate with the memory failure path. It must not migrate a page that is known to be bad. It must not copy data from a poisoned page without handling the error. It must not leave a page in a tier that is about to be taken offline.

## The policy problem ahead

The opening sections have established the constraints. Tiering is a placement problem, not a cache. The hardware exposes coarse and sampled signals, not a per-page hotness oracle. Migration is a correctness-sensitive operation with hidden costs. The policy must balance responsiveness against overhead, precision against scalability, and locality against sharing. It must handle pinned pages, huge pages, memory failure, and cgroups. It must avoid ping-pong and migration amplification. It must be defensible under workloads that the designer did not anticipate.

The next sections will examine how to combine these signals into a policy. They will look at promotion and demotion, hysteresis and rate limiting, per-node and per-cgroup accounting, and the interaction between tiering and the rest of the memory manager. The goal is not to find a universal answer. The goal is to make the design space legible enough that an engineer can choose a policy, measure it, and explain why it behaves the way it does.

## Promotion, demotion, and the asymmetry of mistakes

Promotion and demotion are not symmetric operations. Promotion moves a page from CXL memory to local DRAM. It is a bet that the page will be accessed often enough to justify the copy and the TLB shootdown. Demotion moves a page from local DRAM to CXL memory. It is a bet that the page will not be accessed often enough to justify keeping scarce DRAM. The costs are similar in mechanics, but the consequences of being wrong are different.

A false promotion consumes DRAM capacity that could hold a genuinely hot page. It also causes a copy and a shootdown. If the promoted page turns out to be cold, the system has spent work to make the working set worse. A false demotion sends a hot page to a slower tier. Every subsequent access pays the latency of the CXL fabric. If the page is accessed frequently, the penalty compounds. In many workloads, a false demotion is more damaging than a false promotion, because latency is on the critical path. But a false promotion can trigger cascading demotions: the new page evicts another page, which may itself be hot, and the policy can enter a cycle of churn.

This asymmetry suggests different thresholds. Promotion should require stronger evidence than demotion. A page should be clearly hot before it is promoted. A page should be clearly cold before it is demoted. The gap between the two thresholds is hysteresis. Without it, a page whose access rate hovers near the threshold will oscillate between tiers. Each oscillation costs a copy and a shootdown. The system can spend more bandwidth moving pages than the workload spends accessing them.

The asymmetry also suggests different time constants. Promotion can be relatively slow. A page that is hot now will probably still be hot in a few hundred milliseconds. Demotion can be slower still, because DRAM capacity pressure builds gradually. A policy that reacts to every short burst will over-migrate. A policy that waits too long will let DRAM fill with cold pages and force the allocator into reclaim. The right time constant depends on the workload and on the cost of reclaim. If reclaim is expensive, demotion should start earlier. If migration is expensive, demotion should start later.

## Hysteresis, rate limiting, and migration budgets

Hysteresis is necessary but not sufficient. A policy also needs a migration budget. The budget limits how much memory bandwidth and CPU time can be spent on migration. Without a budget, a large workload with a rapidly changing working set can trigger a migration storm. The storm consumes fabric bandwidth, fills queues, and increases latency for the pages that are not being migrated. The workload slows down, which may change its access pattern, which may trigger more migrations. The result is a feedback loop that is hard to debug.

A migration budget can be expressed as a rate: pages per second, bytes per second, or a fraction of available memory bandwidth. It can also be expressed as a concurrency limit: at most N migrations in flight. The budget should be enforced at multiple levels. A global budget prevents the system from saturating the fabric. A per-node budget prevents one NUMA node from monopolizing the migration engine. A per-cgroup budget prevents one container from imposing migration costs on its neighbors. The budgets should be adjustable at runtime, because the cost of migration changes with fabric load and device health.

Rate limiting interacts with batching. Batching migrations amortizes the cost of TLB shootdowns and queue setup. Instead of shooting down one page at a time, the kernel can collect a batch of pages that share an address space or a page-table page and invalidate them together. Batching also allows the copy engine to issue larger requests, which can improve bandwidth utilization. But batching increases the delay between the decision and the effect. A page that is promoted in a batch may wait behind other pages. If the batch is too large, the policy becomes sluggish. If the batch is too small, the overhead dominates.

A practical design uses a two-level queue. The policy enqueues candidate pages into a per-tier or per-node queue. A worker drains the queue at a rate that respects the budget. The worker sorts or groups the queue to maximize batching. It may prioritize promotions over demotions, or vice versa, depending on the current pressure. If DRAM is nearly full, demotions should be prioritized to avoid reclaim. If CXL latency is high, promotions should be prioritized to move hot pages back. The queue also provides a natural place to apply backpressure: if the queue is full, the policy stops adding candidates until it drains.

The queue must be bounded. An unbounded queue can grow without limit during a migration storm. A bounded queue forces the policy to drop candidates, which is usually better than letting the system thrash. The drop policy matters. Dropping the oldest candidate may discard a page that is still hot. Dropping the newest may ignore a sudden change. A common approach is to keep a small number of candidates per page-table region and to refresh their hotness when they are dequeued. If a page is no longer hot at dequeue time, it is dropped. This prevents stale decisions from being executed.

## Per-node, per-cgroup, and shared pages

NUMA awareness is not optional on modern servers. A CXL device may be attached to one socket, to a switch, or to a fabric that spans sockets. The latency from a CPU to a CXL page depends on the path. The policy must know which CPUs are accessing the page and which tier is closest to them. The accessed bit alone does not tell the policy which CPU set the bit. The kernel can use per-node page-table scans or per-CPU sampling to estimate the access distribution. This is more expensive than a single global scan, but it is necessary for good placement.

Shared pages complicate the picture. A page that is accessed by multiple nodes may be hot in aggregate but cold from the perspective of any single node. Promoting it to one node's DRAM penalizes the others. Keeping it in CXL memory may be the best compromise, even though CXL is slower than local DRAM. The policy should therefore track not just total hotness but also the concentration of hotness. A page with a high access rate on one node is a promotion candidate. A page with a moderate access rate spread across many nodes may be a candidate for a shared tier, or for replication if the hardware and kernel support it. Replication is expensive and complex, but it can be the right answer for read-mostly shared data.

Memory cgroups add another layer. A container's memory limit is usually expressed in bytes, not in tiers. If the kernel charges all pages equally, a container can fill its limit with CXL pages and still be considered within its limit. That may be acceptable if the container is not latency-sensitive. It is not acceptable if the container expects DRAM-class performance. The policy must decide how to account for tier differences. One option is to charge different weights: a CXL page counts as more than a DRAM page, or less, depending on the policy goal. Another option is to expose tier-aware limits: a container can have a DRAM limit and a total limit. The kernel then demotes pages from the container's DRAM allowance when the container exceeds it.

The cgroup interaction also affects reclaim. When a cgroup hits its limit, the kernel reclaims pages from that cgroup. If tiering is active, reclaim can demote pages instead of evicting them. Demotion is often cheaper than writeback or swap, because the page stays in memory and remains mapped. But demotion is not free, and it can push the cgroup's pages into a slower tier without the container's knowledge. The policy should account for this by making demotion visible in memory.stat or a similar interface. Operators need to know how much of a container's memory is in each tier and how much migration is happening on its behalf.

## Interplay with reclaim, compaction, and huge pages

Tiering does not operate in isolation. It shares the memory manager with reclaim, compaction, and huge-page allocation. The interactions can be subtle. Reclaim selects pages to evict based on age and reference state. If tiering demotes a page before reclaim sees it, reclaim may never consider it. That is good if demotion is cheaper than eviction. It is bad if the page is actually cold and should be evicted to free DRAM for a hotter page. The policy must coordinate with reclaim so that demotion and eviction are not competing for the same pages.

One approach is to treat demotion as a reclaim action. When the kernel needs to free DRAM, it first tries to demote cold pages to CXL memory. If the CXL tier is also under pressure, it evicts or writes back. This unifies the two paths and avoids double work. It also means that the demotion policy inherits the reclaim policy's notion of coldness. The reclaim policy already has an LRU list and a reference bit. The tiering policy can reuse that machinery instead of building a separate hotness tracker. The risk is that the LRU list is optimized for eviction, not for tiering. A page that is cold enough to evict may be too cold to keep in CXL memory. A page that is warm enough to keep in CXL memory may not be cold enough for the LRU list to select. The policy needs a separate threshold or a separate list for demotion candidates.

Compaction adds another interaction. Compaction moves pages to create contiguous free blocks, often for huge pages. If tiering is migrating pages at the same time, compaction may find that its carefully arranged blocks are being scattered. The kernel should serialize or coordinate the two. One option is to give compaction priority over tiering when a huge page is being formed. Another is to let tiering migrate only base pages and to leave huge pages alone. The right choice depends on the workload. A workload that benefits from huge pages may prefer compaction. A workload that benefits from tiering may prefer migration. The policy should expose a knob or a heuristic that reflects the trade-off.

Huge pages themselves are a challenge. A 2 MiB huge page is a large migration unit. Copying it takes longer and consumes more bandwidth. The TLB shootdown is more expensive because it invalidates a larger translation. The page may be partially hot: one 4 KiB subpage is accessed frequently, while the rest is cold. A policy that promotes the whole huge page wastes DRAM on the cold subpages. A policy that splits the huge page to migrate only the hot subpage pays the cost of splitting and loses the TLB benefits of the huge page. Neither choice is free. The practical answer is to track hotness at base-page granularity and to make promotion decisions at the huge-page level only when the hot subpages dominate. If they do not, the policy can either leave the huge page in CXL memory or split it, depending on the expected benefit.

## Observability and metrics that matter

A tiering policy without observability is a black box. The operator cannot tell whether the policy is helping or hurting. The kernel should expose enough counters and traces to answer basic questions. How many pages were promoted and demoted? How many migrations failed? How long did a migration take? How much memory bandwidth did migration consume? How many TLB shootdowns were caused by tiering? What is the distribution of page hotness in each tier? What is the ping-pong rate?

The ping-pong rate is especially important. It measures how often a page is promoted and then demoted, or demoted and then promoted, within a short window. A high ping-pong rate means the thresholds are too close or the scan interval is too short. It is a direct measure of wasted work. The kernel can track it with a per-page generation counter or with a global counter that increments when a page reverses direction. A simple counter is enough to detect the problem; a per-page counter helps identify which pages are oscillating.

Latency percentiles are also important. Average migration latency can hide long tails. A few slow migrations can stall the worker queue and delay many other pages. The operator should be able to see the 99th percentile and the maximum. If the tail is long, the policy may need to reduce batch size, lower the migration rate, or avoid migrating pages that are pinned or under writeback.

Finally, the policy should be testable. The kernel should provide a way to simulate or replay access patterns. It should provide tracepoints at the decision points: when a page is considered for promotion, when it is enqueued, when it is migrated, and when it is dropped. These tracepoints let an engineer reconstruct why a page moved. Without them, debugging a tiering policy is guesswork.

## Failure modes and anti-patterns

The most common failure mode is migration amplification. A small change in the workload triggers a migration, which changes the memory pressure, which triggers more migrations. The system spends its bandwidth moving pages instead of serving requests. The fix is usually a combination of hysteresis, rate limiting, and a longer scan interval. The policy should also avoid reacting to a single sample. A page should need multiple consecutive observations before it is promoted or demoted.

Another failure mode is hotness blindness. The policy tracks only the accessed bit, but the workload uses non-temporal stores or DMA, which do not set the accessed bit. The policy sees the page as cold and demotes it. The next access is slow, and the policy may not notice because the access does not set the bit either. The fix is to use additional signals, such as dirty-bit tracking, device counters, or application hints. No single signal is sufficient.

A third failure mode is TLB shootdown storms. A policy that migrates many pages in a short time can generate a flood of inter-processor interrupts. The CPUs spend more time handling shootdowns than running the workload. The fix is to batch migrations, rate-limit them, and avoid migrating pages that are mapped in many address spaces. The kernel can also use lazy TLB invalidation or address-space isolation to reduce the scope of a shootdown.

A fourth failure mode is CXL latency under load. The CXL fabric may be fast when idle and slow when congested. A policy that assumes a fixed latency difference will over-promote when the fabric is busy. The policy should measure or estimate the current cost of CXL access and adjust its thresholds. If the fabric is congested, promotion is more valuable, but migration also consumes fabric bandwidth. The trade-off is dynamic.

A fifth failure mode is memory failure. A CXL device can develop bad pages. If the policy migrates a page from a failing device without checking, it may copy corrupted data. The kernel must integrate tiering with the memory failure path. It must refuse to migrate poisoned pages and must offline them. It must also avoid demoting pages to a device that is about to be taken offline.

## A minimal reference policy

A minimal reference policy can be described without pretending it is optimal. It has four components: a scanner, an age counter, a pair of thresholds, and a rate-limited migration queue. The scanner walks page tables at a fixed interval, reads the accessed bit, and updates the age counter. The age counter saturates at a maximum and decays on each scan if the accessed bit is clear. The promotion threshold is higher than the demotion threshold. A page in CXL memory is promoted when its age exceeds the promotion threshold. A page in DRAM is demoted when its age falls below the demotion threshold. The queue enforces a global migration budget and a per-node budget. It batches pages by address space and page-table page. It drops candidates that are no longer hot when they reach the front of the queue.

This policy is not clever. It does not use PMU samples, application hints, or fabric counters. It does not distinguish shared pages from private pages. It does not coordinate with compaction. But it is understandable, measurable, and safe. It provides a baseline against which more complex policies can be compared. If a more complex policy cannot beat it on the metrics that matter, the complexity is not justified.

The reference policy also makes the trade-offs explicit. The scan interval controls responsiveness and overhead. The age counter controls hysteresis. The thresholds control the balance between promotion and demotion. The migration budget controls the maximum disruption. Each parameter has a clear effect. An engineer can tune them, measure the result, and explain why the system behaves the way it does. That is the minimum standard for a tiering policy in a production kernel.

## Calibrating against the fabric, not the datasheet

The latency that matters to a tiering policy is not the idle-load number in a device datasheet. It is the latency a page's accesses experience while the workload, the migration engine, and other tenants are using the fabric. A CXL memory device attached through a switch has a best-case read latency, a loaded read latency, and a tail that grows with queue occupancy. Writes follow different rules. A memory-side cache can hide some of the cost for some pages, but it is shared, opaque, and not a placement decision. A policy that assumes a constant latency gap will promote too aggressively when the fabric is congested and too timidly when it is idle.

There are two costs to estimate separately. The first is the continuing penalty of leaving a page in CXL memory: the expected number of future accesses multiplied by the latency difference between tiers. The second is the one-time cost of moving the page: bytes copied, bandwidth consumed, TLB invalidations, queue delay, and the risk of disturbing a page that is pinned or under writeback. The first cost is per access and often dominates for hot pages. The second cost is per migration and can dominate for pages whose hotness is marginal. A workable policy does not need a precise model, but it needs to keep these two quantities in the same units and to update both as conditions change.

Continuous calibration is possible without a dedicated profiler. The migration queue already measures service time: how long a page waits before its copy starts, how long the copy takes, and how long the TLB invalidation takes. Those measurements are biased by the pages being migrated, but they are still useful. If queue delay rises, the marginal cost of adding another migration rises with it. The policy can raise its promotion threshold or lower its demotion threshold to reduce pressure. If queue delay falls and the CXL latency estimate rises, the policy can lower the promotion threshold to move more hot pages back to DRAM.

Fabric-level counters provide a second calibration input. A switch or device may expose occupancy, retry, and error counters. The kernel does not need to understand every counter. It needs a small number that correlate with the latency a page will see. If those counters are unavailable, the policy can fall back to a conservative default and to the queue's own service-time measurements. The important point is that the policy should have a feedback path. A static latency constant is a policy without feedback, and it will be wrong at exactly the times when the system is under stress.

Calibration should also account for region and topology. A CXL device on the same package may have a different cost from one behind a switch, and both may differ from a device on a remote socket. If the kernel exposes CXL memory as NUMA nodes, the topology is partly visible. If it hides the topology behind a single tier, the policy loses the ability to distinguish a local CXL page from a remote one. The cost of a migration depends on both the source and the destination region, not just on the tier labels. A page promoted from a remote CXL device to local DRAM may be worth more than a page promoted from a device on the same socket. The policy should carry region identifiers, not just a binary tier.

There is a temptation to calibrate with synthetic probes: allocate a few pages, access them in a pattern, and measure. Probes are useful during bring-up, but continuous probing is intrusive. A probe competes for fabric bandwidth, occupies page-table entries, and may be affected by the same caches that the workload uses. A better use of synthetic measurements is to establish bounds and to validate the counters, not to drive every migration decision. The policy should prefer signals that come from the workload and the migration path itself.

## Virtual machines, guests, and two layers of physical addresses

Virtualization complicates tiering because there are now two translations. The guest kernel maps a guest virtual address to a guest physical address. The hypervisor maps that guest physical address to a host physical address. The CXL tier is a property of host physical memory. The guest may not know which of its pages are in DRAM and which are in CXL memory. If the guest runs its own tiering policy, it can move a page between guest physical frames, but it cannot choose the host tier directly. The hypervisor can move the backing page between host tiers, but it may not know the guest's hotness. Neither layer has the full picture.

The accessed and dirty bits appear in both layers, but they are not equivalent. The guest page table's accessed bit tells the guest that the page was touched. The nested page table's accessed bit tells the hypervisor that the guest physical page was touched. Both are sampled and both can be cleared only with TLB invalidation. A hypervisor that scans nested page tables can infer hotness at the granularity of guest physical memory, but it cannot easily attribute that hotness to a guest process or a virtual address. A guest that scans its own page tables can infer process-level hotness, but it may not know the host tier of the backing page. A cooperative design can combine the two signals: the guest exports hotness hints, and the hypervisor decides host placement. The hints must be advisory, because a malicious or buggy guest can otherwise manipulate host memory placement.

Nested paging also changes the cost of migration. When the host moves a page, it must update the nested page table and invalidate translations in the IOMMU and in the guest's TLBs. The guest may have its own translations that are still valid because the guest virtual address and guest physical address have not changed. The host must ensure that the old host physical page is no longer reachable. This is manageable, but it adds a layer of synchronization. A migration that is cheap on bare metal can become expensive in a virtual machine because the hypervisor must coordinate with guest state.

Device assignment makes the problem harder. A passthrough device may have DMA mappings to guest physical pages. Moving a page in the host tier changes the host physical address behind that mapping. The IOMMU must be updated, and the device must not be actively transferring to the old page. The hypervisor and the guest driver must coordinate. A tiering policy that ignores assigned devices will eventually migrate a page that is under DMA, and the result is data corruption or a device error. The safe policy excludes pages with active DMA pins or requires an explicit opt-in from the device owner.

The practical conclusion for virtualized environments is that tiering is a host-level policy with guest-level inputs. The host owns the physical tiers, so it must own the final placement decision. The guest can provide hotness information through a paravirtual interface, but it should not be able to force a host migration. The host can also expose a stable performance profile: a guest that is told its memory is DRAM-class should not be silently demoted to CXL under pressure without some visible signal. Without that signal, the guest's own scheduling and QoS decisions are based on a false model of its memory.

## Interleaving, striping, and the myth of one tier

The word tier suggests a small number of homogeneous pools. Real CXL fabrics are often interleaved. A physical address range may be striped across multiple devices or across channels inside a device. The stripe improves bandwidth and resilience, but it also means that a single page's accesses may touch more than one device. The latency of a page is then an average over the devices that serve its lines, and the tail is set by the slowest device in the stripe. A policy that treats all CXL memory as one tier with one latency will mis-rank pages when some devices are slower than others.

Interleaving also affects migration. If a page is allocated from an interleaved region, moving it to DRAM removes it from the stripe. That may reduce fabric traffic, but it also changes the memory controller's load balance. Moving many pages out of one device can leave the remaining devices underutilized or overloaded. The migration policy should consider device-level load, not just tier-level capacity. A page that is hot but whose device is already congested may not be worth promoting, because the copy would add to the congestion. A page that is cold but whose device is lightly loaded may be a better migration candidate.

The kernel's memory model may not expose this granularity. If CXL memory is presented as a single NUMA node, the policy sees one distance and one set of counters. If it is presented as multiple nodes, the policy can distinguish devices but must also handle the possibility that a single page is interleaved across them. Some systems expose CXL memory as a separate node with a distance that represents the fabric path. Others present it as local memory and rely on the device to hide the difference. Neither presentation is wrong, but each hides information that the policy might want. The engineering choice is whether to expose enough topology for good placement or to keep the memory model simple and accept coarser decisions.

A useful abstraction is the memory class rather than the tier. A memory class is a set of physical regions that share a similar cost profile and failure domain. Local DRAM is one class. A local CXL device is another. A remote CXL device behind a switch is a third. The policy ranks pages within and across classes. Migration is allowed within a class for capacity balancing and across classes for latency. This avoids pretending that all CXL memory is equal while still keeping the policy manageable. It also gives a place to attach device health: a class can be marked degraded or offline without renaming the whole tier.

The myth of one tier is dangerous because it encourages binary thinking. A page is either hot or cold, local or remote, DRAM or CXL. Real systems have gradients. The policy should be allowed to say that a page is warm, that its device is congested, that its migration would be cheap, and that it should stay where it is. That kind of decision requires more state than a single bit, but it does not require a perfect model. It requires a representation that matches the hardware's actual cost structure.

This representation also affects observability. If the kernel reports only total CXL memory usage, the operator cannot tell whether one device is overloaded. If it reports per-class usage, migration rates, and queue delays, the operator can see where the pressure is. The same counters that drive the policy can drive dashboards and alerts. The policy and the observability should share the same concepts, or the operator will be forced to reverse-engineer the policy from aggregate numbers.

The next question is not whether to tier, but how much state the policy can afford to carry. Every additional dimension, such as region, class, device, cgroup, and page size, multiplies the number of thresholds and counters. The engineering task is to find the smallest set of dimensions that explains the performance problems the system actually encounters. A policy that carries every dimension will be expensive and hard to tune. A policy that carries too few will be blind to the fabric. The answer will differ by deployment, but the trade-off is unavoidable.

## Concurrency, locking, and the cost of being correct

A migration is not a memcpy with a page-table edit. It is a transaction that must be serialized against faults, get_user_pages, writeback, truncation, reclaim, and device DMA. The page lock is the primary serialization point, but it is not sufficient by itself. A page can be mapped in many address spaces, and each mapping has its own page-table lock and reverse-mapping structure. The kernel must prevent a concurrent fault from installing a translation to the old page after the migration has decided to move it. It must also prevent a concurrent unmap from freeing the old page while the copy is in flight.

The usual mechanism is a migration entry. The kernel replaces the page-table entry with a special entry that causes a fault to wait for the migration to complete. The migration entry preserves the accessed and dirty bits so that hotness information is not lost. It also allows the kernel to find the page again if the migration fails. Installing and removing migration entries requires the page-table lock and, on some architectures, a TLB invalidation. The cost scales with the number of mappings, not just with the size of the page.

Reverse mapping is the next bottleneck. To update all mappings, the kernel must walk the anon_vma or i_mmap structure. A page mapped by one process is cheap to migrate. A page mapped by thousands of processes is expensive. The walk itself consumes CPU and may contend with fault handling. The policy should therefore treat mapcount as a cost input. A hot page with a high mapcount may still be worth promoting, but the benefit must clear a higher bar. A cold page with a high mapcount may be better left in CXL memory than demoted, because demotion would also require updating every mapping.

Pinned pages and get_user_pages add another layer. A page pinned for DMA or long-term direct I/O cannot be migrated without coordinating with the pin owner. The kernel may use a migration entry that fails the migration if the page is pinned, or it may wait for the pin to be released. Waiting is dangerous because a long-term pin may last for the lifetime of a device. The policy should exclude pinned pages from automatic migration and provide an explicit interface for applications that want to opt in. The same applies to pages under writeback or under direct I/O. Migrating a page that a device is actively writing to can corrupt data or cause an I/O error.

Lock ordering is a correctness issue, not just a performance issue. The migration path must acquire locks in an order that is compatible with the fault path, the reclaim path, and the truncate path. A mistake can deadlock the system. This is one reason tiering is difficult to retrofit into a mature memory manager. The migration code must be integrated with the existing locking rules, not bolted on beside them. The engineering cost of that integration is often larger than the copy loop itself.

## File-backed memory, writeback, and the page cache

Anonymous memory is the easy case for tiering. File-backed memory is harder because the page cache already has a placement policy: keep hot pages in memory, evict cold pages to storage. Tiering adds a third option: keep cold pages in CXL memory instead of evicting them. That can be useful when storage latency is high and re-faulting is expensive. It can also be wasteful when the page is clean and could be dropped with no copy cost. A clean file page that is cold enough to demote is often cold enough to evict. The policy should distinguish between pages that are expensive to re-fault, such as pages from a slow or congested storage device, and pages that are cheap to re-read.

Dirty file pages are a different problem. A dirty page must eventually be written back. If it is migrated to CXL memory, the writeback path must read from the CXL tier, which may be slower than reading from DRAM. The migration also competes with writeback for bandwidth. The policy should avoid migrating pages with writeback in flight. If it must migrate a dirty page, it should either wait for writeback to complete or ensure that the writeback path can handle the new physical address. The page lock and the writeback state bits provide the necessary synchronization, but the policy should not create unnecessary work.

Shared file mappings multiply the cost. A page cache page may be mapped into many processes. Migrating it requires updating every mapping and invalidating every TLB that holds a translation. The benefit of moving the page to DRAM is shared by all those processes, so the decision is not obviously wrong. But the cost is also shared, and a single migration can cause a system-wide TLB shootdown. The policy should track the number of mappings and the distribution of access. A page mapped by one process is a good candidate for promotion. A page mapped by many processes may be better left in a shared tier, or promoted only if the aggregate access rate is high enough to justify the shootdown.

Truncation and hole punching race with migration. A file can be truncated while a page is being migrated. The kernel must ensure that the page is not reinserted into the page cache after the truncation has removed it. The page lock and the i_mmap lock provide the necessary exclusion, but the migration path must participate in the same locking protocol. A tiering policy that ignores file-backed pages avoids this complexity, but it also ignores a large fraction of memory in many workloads. The practical approach is to start with anonymous memory, then add file-backed support with conservative thresholds and careful coordination with reclaim and writeback.

## Hardware offload, asynchronous migration, and the limits of copy engines

Software migration uses the CPU to copy page contents. That is simple and portable, but it consumes cycles and pollutes the cache. A DMA engine or a CXL device with an internal migration engine could copy pages without CPU involvement. The appeal is obvious: the CPU can continue running the workload while the copy happens in the background. The engineering reality is more complicated. The engine must be coherent with the CPU caches, or the kernel must perform cache maintenance. It must handle faults, errors, and partial completions. It must not access memory that the kernel has not authorized. It must provide a completion notification that the kernel can trust.

Asynchronous migration also changes the policy. If a copy takes a long time, the page may become hot or cold while the copy is in flight. The kernel must decide whether to cancel the migration, let it complete, or start another migration in the opposite direction. Cancellation is expensive and may not be supported by the hardware. Letting it complete may waste bandwidth on a page that is no longer a good candidate. The policy should therefore avoid starting migrations that are likely to be stale by the time they finish. That argues for shorter queues and smaller batches when the workload is changing quickly.

The most promising use of offload is for large pages. Copying a 2 MiB huge page with the CPU takes time and occupies a core. A DMA engine can do it in the background while the CPU handles other work. The TLB shootdown is still required, and it may be the dominant cost. If the shootdown can be batched with other migrations, the offload becomes more attractive. If the shootdown must be immediate, the offload may not help. The policy should model the copy cost and the shootdown cost separately. Offload reduces the first but not the second.

There is also a security dimension. A migration engine that can read and write arbitrary physical memory is a powerful device. The kernel must ensure that the engine is programmed with the correct source and destination addresses and that it cannot be tricked into copying memory that belongs to another tenant. In a multi-tenant environment, the engine should be isolated per virtual machine or per security domain. The kernel should not expose a raw migration engine to unprivileged users. These constraints may limit the usefulness of offload in shared cloud environments, even if the hardware supports it.

## Quality of service, isolation, and multi-tenancy

Tiering is a shared resource. The migration engine, the CXL fabric, and the DRAM capacity are all shared among workloads. A policy that optimizes global throughput can still produce unacceptable latency for a latency-sensitive tenant. The kernel needs a way to express and enforce quality of service. Memory cgroups provide the basic mechanism: a tenant can have a DRAM limit, a total memory limit, and a migration budget. The policy then promotes and demotes pages within those limits. The tenant's latency depends on how much of its working set fits in DRAM, not on how much total memory it has.

The hard part is deciding how much DRAM a tenant deserves. A simple approach is proportional sharing: each cgroup gets a share of DRAM based on its weight. A latency-sensitive cgroup can be given a larger weight or a guaranteed minimum. The policy then enforces the minimum by refusing to demote pages below the guarantee. This is similar to memory.low, but it applies to a tier rather than to total memory. The implementation must handle the case where the sum of guarantees exceeds available DRAM. In that case, the kernel must either overcommit and accept that some guarantees will be violated, or refuse to start new workloads. Neither choice is pleasant.

Bandwidth isolation is equally important. A tenant that migrates many pages can consume fabric bandwidth and increase latency for other tenants. The migration budget should be enforced per cgroup, not just globally. The kernel can use a token bucket or a rate limiter per cgroup. If a cgroup exceeds its budget, its migration candidates are delayed or dropped. The tenant still gets its pages eventually, but it cannot monopolize the fabric. The same mechanism can be used to protect the CXL device from a migration storm caused by a single workload.

Observability is part of quality of service. A tenant should be able to see how much of its memory is in each tier, how many migrations it is causing, and what latency it is experiencing. Without that information, the tenant cannot tune its own workload or ask for more DRAM. The kernel should expose per-cgroup counters for promotions, demotions, migration failures, and tier residency. It should also expose latency histograms for CXL accesses, if the hardware supports them. These metrics turn tiering from a hidden policy into a visible service level.

## Operational lifecycle, control loops, and what to measure

CXL memory is not always present for the lifetime of the system. Devices can be hotplugged, firmware can be updated, and hardware can fail. The tiering policy must handle these events without corrupting data or hanging the system. When a CXL device is removed, the kernel must migrate its pages to other tiers or offline them. This is similar to memory hotremove, but the source tier is slower and may be congested. The migration may take a long time, and the kernel must not block the removal indefinitely. The policy should prioritize offlining over normal tiering and should stop promoting pages to a device that is being removed.

Firmware and ACPI tables describe CXL memory to the kernel. The SRAT and HMAT tables may provide latency and bandwidth information. That information is useful for initial placement, but it is often static and may not reflect the current state of the fabric. A policy that trusts HMAT blindly will make bad decisions when the fabric is congested or when a device is in a low-power state. The kernel should use HMAT as a starting point and then calibrate with runtime measurements. If the tables are wrong, the policy should be able to override them.

Failure domains are a design consideration. A single CXL device may hold a large fraction of a system's memory. If it fails, the system may lose many pages at once. Tiering can increase exposure by moving more data to CXL memory. For critical data, the policy should keep pages in DRAM or replicate them across devices. Replication is expensive and not typically supported for volatile memory, but the policy can at least avoid demoting kernel data, page tables, and other critical structures. It can also use memory failure handling to offline bad pages before they cause a crash. The policy should be aware of the device's health and should stop using a device that is reporting errors.

Power management adds another dimension. A CXL device may enter a low-power state when idle. The first access after the transition may be much slower than the steady-state latency. A policy that promotes a page to DRAM because of one slow access may be overreacting. The policy should either keep the device in a high-power state when it is in use, or account for the wake-up latency in its cost model. The trade-off between power and latency is a system-level decision, not just a memory policy decision.

Tiering is also a control loop. The policy observes hotness, decides on migrations, and the migrations change the system state, which changes future observations. Like any control loop, it can oscillate. The classic failure is a page that is promoted, becomes cold, is demoted, becomes hot again, and is promoted again. Each cycle costs a copy and a shootdown. Hysteresis reduces the amplitude, but it does not eliminate the problem if the workload's access pattern is inherently oscillatory. The policy should detect oscillation and increase hysteresis or reduce the scan rate.

A stable policy needs a setpoint. The setpoint could be a target DRAM utilization, a target CXL latency, or a target migration rate. The policy adjusts its thresholds to move the system toward the setpoint. If DRAM utilization is too high, the policy lowers the demotion threshold to move more pages to CXL. If CXL latency is too high, the policy raises the promotion threshold to move more pages to DRAM. The setpoint should be configurable, because different deployments have different priorities. A latency-optimized deployment may keep DRAM nearly full and accept more migrations. A capacity-optimized deployment may keep DRAM less full and accept higher latency.

Anti-windup is necessary. If the migration queue is full, the policy should stop accumulating error. Otherwise, the thresholds will drift far from the correct value, and the system will overreact when the queue drains. The policy should also reset its state when a device is added or removed, or when a cgroup's limits change. A control loop that assumes a fixed system configuration will misbehave when the configuration changes.

Before choosing a policy, measure the workload and the system. The workload's working set size, reuse distance, access skew, read/write ratio, and page size distribution determine how much benefit tiering can provide. A workload with a small working set that fits in DRAM will not benefit from tiering. A workload with a large working set and high locality will benefit a lot. A workload with no locality will benefit little, because every page is equally likely to be accessed. The measurement should be done at the page level, not just at the aggregate level. Averages hide the hot pages that tiering is supposed to find.

Measure the system's CXL latency and bandwidth under load, not just at idle. The difference between idle and loaded latency determines how aggressive the policy should be. If the loaded latency is close to DRAM latency, tiering is less valuable. If the loaded latency is much higher, promotion is more valuable, but migration also consumes more bandwidth. Measure the cost of a migration: copy time, TLB shootdown time, and queue delay. These costs vary with page size, CPU count, and fabric load. A policy that assumes a fixed cost will be wrong under load.

Measure the safety properties. Test with pinned pages, huge pages, memory failure, hotplug, and cgroup limits. A policy that works in a benchmark but fails when a device is removed is not ready for production. Test with virtual machines and device assignment. Test with multiple tenants and verify that one tenant cannot starve another. Test the observability: can an operator tell why a page moved? Can they see the migration rate and the tier residency? If not, the policy is not operable.

Finally, compare against a baseline. The baseline could be no tiering, or a simple LRU policy, or an oracle that knows the future. The comparison should use metrics that matter: average latency, tail latency, throughput, migration bandwidth, CPU overhead, and fairness. A policy that improves average latency but doubles tail latency may not be acceptable. A policy that reduces migration bandwidth but increases DRAM pressure may cause reclaim storms. The right policy depends on the workload and the service level objective. The measurement process is what makes that choice defensible. The next step is to turn those measurements into a policy that can be tuned without constant supervision.
