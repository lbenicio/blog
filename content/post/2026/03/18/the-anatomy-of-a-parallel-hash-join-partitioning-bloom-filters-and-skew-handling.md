# The Anatomy of a Parallel Hash Join: Partitioning, Bloom Filters, and Skew Handling

A hash join looks simple in a diagram: build a hash table from one input, probe it with the other, emit matches. In a parallel query engine, that diagram hides most of the engineering. The operator has to route rows to partitions, keep hash tables cache-resident, avoid contention on shared memory, skip probes that cannot match, and survive the one partition that contains a disproportionate share of the data. The join key comparison is rarely the bottleneck. The bottleneck is usually data movement, random memory access, and load imbalance.

This article focuses on the shared-memory parallel hash join inside a single node: multiple worker threads, one build input, one probe input, and a memory budget that is large but finite. The distributed case adds network shuffles and remote memory, but the local operator still determines whether the distributed plan has a chance. The assumptions are an equi-join on one or more key columns, a build side expected to be smaller than the probe side, no useful index on either side, and a storage layer that delivers rows in batches. The goal is not to present one canonical implementation. It is to expose the design choices that decide whether the implementation is correct and fast.

## The Join Is Not the Hard Part; the Data Movement Is

A hash join has two phases. In the build phase, rows from the smaller input are inserted into a hash table keyed by the join key. In the probe phase, rows from the larger input are hashed, looked up, and compared against candidate rows. For an inner join, a match emits a combined row. For outer joins, the table must track whether a build row was matched. For duplicate keys, the table must preserve every build row, or at least a chain of rows, so probe rows can emit the full multiplicity. These are semantic requirements, not performance details. A parallel implementation that loses duplicate rows or emits a build row twice is not a faster hash join; it is a different, wrong operator.

The first performance lesson is that the join key comparison is rarely dominant. The dominant costs are partition routing, hash table insertion, random memory access during probing, and output materialization. A probe that misses the cache hierarchy can cost far more than the arithmetic needed to compare two integers. A parallel hash join is therefore a memory-system design problem disguised as a database operator. The design must arrange data so workers touch memory in predictable, cache-friendly patterns and so the parallel decomposition does not create contention on the same cache lines.

The second lesson is that parallelism does not remove serial dependencies. A build table must be fully populated before a probe can safely read it, unless the implementation uses a more complex concurrent structure. The barrier between build and probe is a synchronization point. A partitioned design can reduce the cost of that barrier by building and probing partition by partition, but it still has to respect the dependency for each partition. The choice between a single global table and many partition-local tables is one of the central trade-offs in the operator.

## A Baseline Parallel Hash Join

A reasonable baseline is a partitioned hash join. The build input and the probe input are both partitioned by the same hash function on the join key. Each partition is assigned to a worker or a group of workers. For each partition, the worker builds a local hash table from the build rows and then probes it with the matching probe rows. The output is appended to a per-worker or per-partition output buffer. This design has several attractive properties. The hash table for a partition is smaller than a global table, so it is more likely to fit in cache. Workers do not contend on a single table during the build phase. The probe phase can be scheduled partition by partition, which improves locality. The partitioning step itself is parallelizable.

The baseline also has costs. Partitioning reads both inputs and writes them to temporary storage. If the inputs are already in memory, the temporary storage may be memory buffers; if the inputs are large, the temporary storage may spill to disk. The partitioning step adds a pass over the data and a hash computation per row. The partition count must be chosen before the data distribution is fully known. If the count is too small, partitions are large and the hash tables do not fit in cache. If the count is too large, the partitioning overhead and the number of small partitions dominate. The partition count is usually a power of two so that the low bits of the hash can be used as a partition id, but that choice interacts with the hash function and the key distribution.

A non-partitioned baseline is also possible. All workers build into a shared concurrent hash table, and all workers probe the same table. This avoids the partitioning pass and the temporary storage. It also concentrates contention on the table and on the memory allocator. A shared table can be a good choice when the build side is small enough to fit in cache and the join is short-lived. It is usually a poor choice when the build side is large, because the table becomes a shared random-access structure with synchronization on insertion and potentially on probing. The partitioned design trades an extra pass for locality and reduced contention. The right choice depends on the size of the build side, the selectivity of the join, and the cost of the partitioning pass relative to the rest of the query.

## Partitioning: The First Expensive Decision

Partitioning determines the shape of the rest of the operator. There are two common families: hash partitioning and radix partitioning. Hash partitioning computes a hash of the key and uses some bits to select a partition. Radix partitioning uses a histogram of the high-order bits or a sequence of passes over the key to assign rows to partitions. Radix partitioning can be more cache-friendly because it can be implemented as a sequence of counting and scattering passes, and because it can use the key bits directly rather than a full hash. It also has a cost: it may require multiple passes over the data, and it is sensitive to the distribution of the key bits. Hash partitioning is simpler and more uniform when the hash function is good, but it requires a high-quality hash to avoid skew.

The partition count should be chosen with the memory budget in mind. A useful rule is to size partitions so that the build-side hash table for a partition fits in the last-level cache or in a modest fraction of memory. The exact target depends on the hardware and on the probe-to-build ratio. If the build side is much smaller than the probe side, a larger number of partitions can be beneficial because each probe partition is small and the build table is cache-resident. If the build side is large, the partitioning pass and the temporary storage become significant, and the partition count should be kept moderate. The partition count is also constrained by the number of workers. If there are more partitions than workers, the scheduler can assign multiple partitions to a worker and use work stealing to balance the load. If there are fewer partitions than workers, some workers will be idle during the build or probe phase.

The partitioning step must also handle the case where the build side is too large to fit in memory. In that case, the operator must spill partitions to disk and process them in a multi-pass or recursive manner. A grace hash join partitions both inputs, writes the partitions to disk, and then processes each partition pair one at a time. If a partition is still too large, the operator recursively partitions it. The recursion adds complexity and I/O, but it is the standard way to keep memory usage bounded. The alternative is to let the hash table grow until the system runs out of memory, which is not a design; it is an outage waiting to happen.

## Hash Table Layout and Cache Behavior

The hash table is the heart of the build phase. The two broad choices are chaining and open addressing. In a chained table, each bucket points to a linked list or a vector of rows. In an open-addressed table, rows are stored directly in an array and collisions are resolved by probing. Chaining is simpler to make concurrent and handles high load factors gracefully, but it adds pointer chasing and allocator overhead. Open addressing has better cache locality and no per-row pointer, but it requires a good load factor and a careful deletion strategy. For a build-only table that is discarded after the join, deletion is usually not needed. That makes open addressing more attractive.

The layout of the row matters as much as the layout of the table. A common mistake is to store a pointer to the full row in the hash table and then dereference it during probing. That adds an extra memory access and defeats the purpose of a cache-friendly table. A better design stores the join key and a compact payload in the table, or stores an offset into a contiguous row array. The key comparison should happen on data that is already in the cache line. If the payload is large, the table can store a pointer to the payload and a small key copy. The trade-off is between table size and the number of memory accesses per probe. A table that stores too much per entry will not fit in cache; a table that stores too little will require an extra indirection for every match.

The hash function also matters. A weak hash function can create clusters in an open-addressed table and hot buckets in a chained table. A strong hash function spreads keys uniformly but costs more cycles. For integer keys, a multiplicative hash or a finalizer from a well-known mix function is often sufficient. For string keys, the hash must process the string and should avoid reading beyond the key length. The hash function should be deterministic across workers and across partitioning and probing. If the build and probe use different hash functions, the join will miss matches. This sounds obvious, but it is a common source of bugs in parallel implementations where one phase uses a partition hash and another uses a table hash.

## Bloom Filters and Semi-Joins

A Bloom filter is a compact probabilistic structure that can answer whether a key is possibly present or definitely absent. In a hash join, a Bloom filter built from the build side can be used during the probe phase to skip rows whose keys cannot match. This is especially useful when the join is selective and the probe side is large. The filter is built during the build phase and probed before the hash table lookup. A negative result means the probe row can be discarded without touching the hash table. A positive result means the probe row must still be checked, because the filter can produce false positives. The false-positive rate depends on the number of bits per key and the number of hash functions. More bits and more hash functions reduce false positives but increase memory and computation.

The Bloom filter is not free. It adds a memory structure that must be built and probed, and it adds a branch per probe row. If the join is not selective, the filter may reject few rows and the added cost may outweigh the benefit. The filter also has to be shared across workers or replicated per partition. A shared filter can become a contention point if it is updated concurrently; a per-partition filter avoids contention but duplicates memory. In a partitioned hash join, a per-partition Bloom filter is often a good compromise because each partition is processed by a small number of workers. The filter can be built after the build rows for the partition are known, and it can be discarded when the partition is finished.

A related technique is the semi-join. Instead of building a Bloom filter, the operator can build a set of distinct keys from the build side and use it to filter the probe side before the main join. A semi-join can be exact, using a hash set, or approximate, using a Bloom filter. The exact version has a higher memory cost but no false positives. The approximate version has a lower memory cost but may pass rows that do not match. The choice depends on the selectivity of the join and the cost of the probe. In a parallel operator, the semi-join can also be used to reduce the amount of data that is partitioned. If the build side is small, a broadcast semi-join can filter the probe side before the shuffle in a distributed plan. In a shared-memory plan, the semi-join is usually applied after partitioning to avoid an extra pass over the probe input.

## Skew: The Failure Mode That Looks Like a Slow Node

Skew is the most common reason a parallel hash join underperforms. If the join key is not uniformly distributed, one partition can contain far more rows than the others. That partition becomes a straggler. The worker assigned to it does more work while other workers finish and idle. The overall runtime is determined by the slowest partition, so the parallel speedup collapses. Skew can come from the data itself, such as a few popular keys in a fact table, or from the hash function, such as a poor mix that maps many keys to the same partition. It can also come from the partitioning scheme, such as using only the low bits of a key that has a regular pattern.

There are several ways to handle skew. The first is to detect it. A histogram of the build-side keys can reveal hot keys before the join begins. The histogram can be built during the partitioning pass or from metadata. If the hot keys are known, the operator can handle them separately. A common technique is to salt the hot keys: append a salt value to the key so that the hot key is spread across multiple partitions. The probe side must use the same salt expansion, which means the probe row for a hot key is replicated across the salted partitions. This increases the probe work for hot keys but balances the build work. The trade-off is between build skew and probe amplification. If the hot key is very frequent on the probe side, salting can make the probe phase more expensive. The operator should choose the salt count based on the relative sizes of the build and probe sides.

Another technique is dynamic partitioning. Instead of fixing the partition count in advance, the operator can split hot partitions after the first pass. A hot partition is detected by its size or by the number of rows relative to the average. The partition is then re-partitioned with a different hash or a different set of bits. Dynamic partitioning adds a second pass and more complexity, but it can adapt to the data distribution. A related technique is to use a work-stealing scheduler that assigns partitions to workers dynamically. Work stealing does not eliminate skew, but it can reduce the idle time caused by a straggler if the straggler is split into smaller tasks. If the straggler is a single indivisible partition, work stealing cannot help. The partition must be split or the hot key must be handled separately.

Skew also interacts with memory. A hot partition may be too large to fit in memory even if the average partition fits. The operator must detect this case and spill or recursively partition the hot partition. A naive implementation that assumes all partitions fit in memory will fail on skewed data. The failure may look like an out-of-memory error or a sudden drop in throughput as the system starts swapping. A robust implementation monitors partition sizes and applies the same spilling strategy to hot partitions as it does to large partitions. The goal is to keep the memory footprint bounded and the work balanced, even if the data is not.

## Memory Pressure and Spilling

Memory pressure is the constraint that turns a hash join from a simple in-memory operator into a storage engine problem. The build side must fit in memory for a pure in-memory hash join. If it does not, the operator must spill. Spilling can be implemented by partitioning the build and probe inputs to disk and then processing one partition pair at a time. The partitioning step writes rows to temporary files. The build phase reads a build partition, builds a hash table, and probes the corresponding probe partition. If the build partition is still too large, the operator recursively partitions it. The recursion depth is bounded by the number of key bits or by a configured limit. The operator must also handle the case where a single key has more rows than fit in memory. In that case, the join cannot be completed with a simple hash table; the operator must use a different strategy, such as sorting or blocking, or it must report an error.

Spilling has a cost. It adds I/O, serialization, and temporary storage management. It also changes the access pattern from random memory access to sequential disk access. On modern NVMe storage, sequential I/O can be fast, but it is still orders of magnitude slower than memory. The operator should avoid spilling when possible by choosing a partition count that keeps the build side in memory. If spilling is necessary, the operator should use large I/O requests and avoid small random writes. The temporary files should be preallocated or managed by a buffer pool to avoid filesystem overhead. The operator should also consider compression. Compressing spilled partitions can reduce I/O at the cost of CPU time. The trade-off depends on the compression ratio and the relative cost of I/O and CPU.

The memory budget must be shared across workers. If each worker independently allocates a hash table, the total memory can exceed the budget. A common approach is to divide the budget by the number of concurrent partitions or workers. The operator must also account for the partitioning buffers, the output buffers, and the Bloom filters. A worker that is building a partition should not be allowed to grow its table beyond its share without triggering a spill or a repartition. This requires coordination between the scheduler and the memory manager. A simple approach is to process partitions in waves: a fixed number of partitions are active at a time, and each active partition gets a fixed memory budget. A more dynamic approach uses a global memory manager that grants memory to workers and reclaims it when partitions finish. The dynamic approach is more efficient but more complex. The static approach is easier to reason about and is often sufficient for a first implementation.

## Initial Design Commitments

At this point, the shape of a reasonable parallel hash join is visible. It should partition both inputs by the same hash function, use a partition count that keeps build-side tables cache-resident and within the memory budget, build a partition-local hash table with a compact row layout, use a Bloom filter or semi-join when the join is selective, and handle skew with hot-key detection, salting, or dynamic partitioning. It should spill when memory pressure demands it and should share the memory budget across workers. These are not independent choices. A larger partition count reduces the size of each hash table but increases the partitioning overhead. A Bloom filter reduces probe work but consumes memory that could be used for the build table. Salting balances build work but can amplify probe work. The operator must be tuned as a whole, not as a collection of isolated optimizations.

The next part of this article will examine the scheduling and synchronization details that determine how these commitments play out in practice: how to assign partitions to workers without creating a barrier at every step, how to overlap partitioning with building and probing, how to handle the build-probe dependency for each partition, and how to measure the operator without confusing throughput with latency. Those details are where the difference between a correct parallel hash join and a production-grade one usually lives.

## Scheduling Partitions Without a Global Barrier

A partitioned hash join invites a simple schedule: partition everything, wait for all partitions, build all tables, wait again, probe all partitions. That schedule is easy to reason about and easy to debug. It is also wasteful. The wait after partitioning leaves workers idle while the last partition is still being written. The wait after building leaves probe workers idle while the last build table is still being populated. On a large machine with many workers, those idle windows can dominate the runtime. The alternative is to schedule at the granularity of a partition and let each partition move independently through its own lifecycle.

The lifecycle has three stages: partition, build, and probe. A partition is not a global object; it is a pair of row collections, one from the build side and one from the probe side. The build collection must be complete before the build stage can start. The build table must be complete before the probe stage can start. Those are the only dependencies. There is no dependency between partition A's build stage and partition B's probe stage. A scheduler can therefore treat each partition as a small pipeline and overlap stages across partitions. While partition 7 is being probed, partition 8 can be built, and partition 9 can still be receiving rows from the partitioning pass.

Implementing this schedule requires a task queue and a per-partition state machine. The state machine has states such as `partitioning`, `build_ready`, `building`, `probe_ready`, and `probing`. A worker that finishes partitioning a chunk of input for a partition updates the partition's row count and, when the last chunk arrives, transitions the partition to `build_ready`. A worker looking for work can pick a `build_ready` partition, claim it with an atomic compare-and-swap, and build its table. When the build finishes, the worker transitions the partition to `probe_ready` and either probes it immediately or returns it to the queue. The queue should be work-stealing so that idle workers can take partitions from busy workers. The atomic claim prevents two workers from building the same partition.

The granularity of partitioning tasks matters. If each task partitions a single row, the queue overhead and atomic operations dominate. If each task partitions a large batch, the last batch determines when the partition becomes build-ready, and the pipeline stalls. A common compromise is to partition in morsels of a few thousand rows. The morsel size should be large enough to amortize queue operations and small enough to keep all workers busy near the end of the partitioning pass. The same reasoning applies to build and probe tasks. A build task can insert a morsel of build rows into the partition table. A probe task can process a morsel of probe rows. The table itself is shared by the workers that process the same partition, so the build stage must be serialized per partition or protected by synchronization.

## Synchronization at the Partition Level

The build-probe dependency is the only hard synchronization point in the operator. A probe must not read a hash table that is still being written. The simplest correct approach is a per-partition lock or a completion flag. A worker that wants to probe a partition checks the flag. If the build is not complete, the worker either waits or chooses another partition. Waiting is acceptable if there is other work, but a spin-wait on a flag can waste cycles. A condition variable or a futex-based wait is more appropriate when the expected wait is long. The choice depends on the scheduler. If the scheduler only hands out `probe_ready` partitions, the probe worker never waits. The build worker signals readiness by transitioning the state and pushing the partition back to the queue.

Memory ordering matters here. The flag that indicates build completion must be published with release semantics, and the probe worker must read it with acquire semantics. Without those semantics, the probe worker could observe the flag before the table writes are visible. On x86, the hardware often makes this work by accident, but a correct implementation should not rely on that. Atomics with explicit memory orders, or a mutex around the state transition, make the dependency clear. A mutex per partition is usually cheap because the critical section is short and the number of partitions is much larger than the number of workers. The mutex protects the state, not the entire hash table. The table itself is read-only after the build completes, so probe workers do not need to lock it.

A more aggressive design uses a single writer and multiple readers with a read-copy-update style. The build worker constructs the table in a private buffer and then publishes a pointer to it. Probe workers read the pointer and use the immutable table. The old table, if any, is retired after a grace period. This pattern is common in concurrent data structures, but it is overkill for a hash join because the table is built once and never modified. A simple atomic pointer with release-acquire semantics is enough. The build worker writes the table, then stores the pointer with a release store. The probe worker loads the pointer with an acquire load. If the pointer is null, the build is not ready.

The partitioning phase also needs synchronization, but of a different kind. Multiple workers may append rows to the same partition. If each partition has a single writer, no synchronization is needed. If multiple writers append to the same partition, the partition needs a lock or a lock-free append structure. A lock-free append can use a per-partition atomic tail pointer and a preallocated buffer. Each writer reserves space with a fetch-add, then writes its rows into the reserved slot. The order of rows within the partition does not matter for a hash join, so the writers do not need to coordinate beyond the reservation. The buffer must be large enough to hold the partition, or it must be a linked list of chunks. A chunked buffer avoids the need to know the final size in advance. The chunk size should be a multiple of the cache line to avoid false sharing between writers.

False sharing is a subtle but important issue. If two workers append to the same partition and their tail pointers or counters share a cache line, the cache line ping-pongs between cores. Padding the counters to a cache line eliminates the sharing. The same applies to per-worker statistics, output buffers, and any other frequently updated state. In a parallel hash join, the hot shared state should be minimal. The partition state machine, the work queue, and the output buffers are the main candidates. Everything else should be thread-local or partition-local.

## Overlapping Phases and Pipeline Parallelism

Once partitions move independently, the operator can overlap the three phases across partitions. The partitioning pass for partition 10 can run while partition 9 is being built and partition 8 is being probed. This overlap hides the latency of memory allocation, cache misses, and even disk I/O if the partitions are spilled. The overlap also changes the memory pressure profile. At any moment, the operator may have several partitions in different stages, each holding buffers or hash tables. The memory manager must account for all of them, not just the active build table.

A practical way to bound the overlap is a window of active partitions. The scheduler keeps at most W partitions in the build or probe stage at once. W is chosen so that the combined memory footprint of W build tables plus their partitioning buffers fits in the budget. When a partition finishes probing, its table is freed and a new partition can enter the window. The window size can be static or dynamic. A static window is easier to implement and reason about. A dynamic window can adapt to the actual sizes of the partitions, but it requires a memory manager that can grant and revoke memory. For a first implementation, a static window with a conservative W is often sufficient. The operator can measure the average build table size and adjust W between queries or between runs.

Pipeline parallelism also interacts with the output stage. Probe workers emit rows to output buffers. If the output is consumed by a parent operator, the parent may apply backpressure. If the output buffer is full, the probe worker must wait or spill. A non-blocking design uses per-worker output buffers and a separate consumer thread or task that drains them. The producer never blocks on the consumer; it only blocks when its own buffer is full, and then it can flush to disk or to a shared queue. The shared queue must be bounded to avoid unbounded memory growth. The bound should be part of the memory budget. A queue that grows without limit can consume the memory that the build tables need, which defeats the purpose of the budget.

The build phase can also be pipelined with the partitioning phase. Instead of waiting for an entire partition to be partitioned, the build worker can start inserting rows as soon as the first chunk of the partition is available. This requires the build table to support concurrent insertion or the build worker to process chunks in order. If the partition has a single writer for the build side, the writer can insert rows as they arrive. The probe phase still cannot start until the build is complete, but the build itself overlaps with partitioning. This reduces the time between the first row of a partition and the last row. The benefit is largest when the partitioning pass is long and the build table is small.

## NUMA and Memory Locality

On a multi-socket machine, memory access is not uniform. A worker on socket 0 can access memory attached to socket 1, but the access is slower and consumes interconnect bandwidth. A parallel hash join that ignores NUMA can lose a significant fraction of its performance. The first step is to allocate memory close to the worker that will use it. The partitioning buffers for a partition should be allocated by the worker that partitions the partition, or by the worker that will build it. The hash table for a partition should be allocated by the build worker. The probe workers that read the table should ideally run on the same socket. If the scheduler is NUMA-aware, it can assign partitions to workers on the same node. If it is not, the operator can still use first-touch allocation and hope that the build worker touches the table first. First-touch is not a guarantee, but it is better than interleaving all memory across all sockets.

Interleaving is a deliberate opposite choice. If a partition is read by many workers on different sockets, interleaving its memory across sockets can balance the bandwidth. For a hash join, the build table is usually read by a small number of probe workers, often on the same socket. Interleaving is more appropriate for shared read-only data that all workers access uniformly, such as a dimension table in a broadcast join. For the partitioned hash join, local allocation is usually the better default. The operator should also pin threads to cores or sockets to prevent the OS from migrating them. Migration invalidates cache locality and can move a worker away from its memory. Pinning is not always possible in a managed runtime, but when it is, it is worth the effort.

NUMA also affects the work queue. A single global queue can become a contention point and a source of remote memory access. A hierarchical queue with one queue per socket and work stealing between sockets reduces contention. Workers first take work from their local queue. If it is empty, they steal from another socket. The steal rate should be low, because stealing is expensive. The queue should be designed so that the common case is local. The same principle applies to the output buffers and the memory allocator. A per-socket allocator with local free lists avoids global locks and remote memory.

## Adaptive Repartitioning and Runtime Statistics

The initial partition count is a guess. The actual data distribution is only known after the partitioning pass, and sometimes only after the build pass. A robust operator collects statistics as it runs and adapts. The most useful statistics are the number of build rows per partition, the number of probe rows per partition, the number of distinct keys, the size of the largest partition, and the number of spills. These statistics are cheap to collect with per-partition counters. They can be aggregated periodically or at the end of the partitioning pass. If the largest partition is much larger than the average, the operator can trigger a repartition of that partition before building it. The repartition can use a different hash function or a different set of bits. It can also use a salt for the hot key if the hot key is identified.

Adaptive repartitioning is not free. It adds a pass over the hot partition and requires additional buffers. The decision to repartition should be based on a cost model. If the hot partition is only slightly larger than the average, the cost of repartitioning may exceed the benefit. If it is several times larger, the benefit is clear. A simple heuristic is to repartition when the largest partition exceeds a threshold, such as twice the memory budget for a build table, or when the skew ratio exceeds a configured value. The threshold should be tuned for the hardware and the workload. A more sophisticated approach uses a histogram of the key distribution to decide before the build. The histogram can be built during the partitioning pass with a small amount of memory per partition. The operator can then choose the partition count and the salt count for the next run.

Runtime statistics are also useful for tuning the Bloom filter. If the probe side is much larger than the build side and the measured false-positive rate is high, the operator can increase the number of bits per key. If the filter rejects few rows, the operator can disable it for the remaining partitions. The filter parameters can be chosen per partition based on the build row count. A partition with few build rows needs a small filter; a partition with many build rows needs a larger one. The memory for the filters competes with the build tables, so the operator should account for it in the budget. A filter that consumes memory and does not reject rows is worse than no filter at all.

## Concurrency in Outer Joins and Duplicate Handling

Outer joins add state that must be updated during probing. In a left outer join, every build row must be emitted at least once, even if no probe row matches. The build table must therefore track whether each build row has been matched. A simple implementation uses a per-row boolean flag. The probe worker sets the flag when it matches. After the probe phase, the operator scans the build table and emits unmatched rows. In a parallel operator, multiple probe workers may read the same build row, but only one should set the flag. The flag can be an atomic bit, or it can be a non-atomic byte if each build row is owned by a single probe worker. Ownership is difficult to guarantee when duplicate keys are spread across workers. An atomic bit is safer. The bit can be packed into a bitset to reduce memory overhead. The bitset is per partition and is read by the final scan.

Duplicate keys complicate the probe phase. A build row with a duplicate key is stored in the table, and a probe row with that key must emit all matching build rows. In an open-addressed table, duplicates can be stored in the same bucket or in a chain. In a chained table, the probe walks the chain. In an open-addressed table, the probe must continue probing until it finds an empty slot or a different key. The order of duplicates does not matter for an inner join, but it may matter for an outer join if the output order is specified. Most parallel query engines do not guarantee order for a hash join, so the operator can emit duplicates in any order. If order is required, the operator must either sort the output or use a different join algorithm. That is a planning decision, not a hash join detail.

The build phase must also handle duplicates correctly. If the table uses open addressing and the load factor is high, inserting many duplicates can cause long probe sequences. A common optimization is to store a small chain of duplicate rows in the same bucket or in a separate overflow area. The chain can be a linked list of rows with the same key. The probe then walks the chain and emits all matches. The chain adds a pointer per duplicate, but it keeps the main table compact. The alternative is to allow multiple entries with the same key in the open-addressed table. That is simpler but can degrade probe performance when duplicates are frequent. The choice depends on the expected multiplicity of the join key. If the key is a primary key, duplicates are rare and the simple approach is fine. If the key is a foreign key with many duplicates, a chain or a dedicated duplicate structure is better.

The parallel aspect of duplicate handling is that the build table for a partition may be built by one worker and probed by several. The duplicate chain must be immutable after the build completes. The build worker constructs the chain and publishes it. The probe workers read it without synchronization. The matched flags are the only mutable state, and they are updated atomically. The final scan for unmatched build rows can be parallelized over the table. Each worker scans a range of buckets and emits unmatched rows. The output from the scan must be merged with the output from the probe phase. The merge can be a simple concatenation of per-worker buffers. If the output must be ordered, the merge is more complex, but again, order is usually not guaranteed.

## Output Materialization: The Phase That Pays for Everything

The probe phase does not end when a match is found. It ends when the joined row is written to the output buffer. In many engines, output materialization is where the hash join spends an underappreciated share of its time. A probe that finds a match must combine columns from the build row and the probe row, evaluate any residual predicates, project the required columns, and append the result to a buffer. If the build side is wide, the build row may be stored in a compact format in the hash table, and the full payload may live in a separate array. The probe worker must then fetch the payload, which is another random access. The layout of the payload array should match the layout of the hash table entries so that a match touches as few cache lines as possible.

Columnar storage adds another layer. If the build and probe inputs are columnar batches, the join may produce a selection vector rather than materialized rows. The probe phase records the matching build row ids and probe row ids. The parent operator later gathers the columns it needs. This is often faster because the join does not materialize columns that are not used by the query. It also changes the memory access pattern: the hash table stores row ids, and the gather happens in a separate, vectorized pass. The trade-off is that the row ids must be stable and the build side must remain available until the gather completes. If the build side is spilled or freed early, the row ids become dangling. The operator must coordinate with the memory manager to keep the build data alive as long as the output references it.

Backpressure is the other half of output materialization. A probe worker that emits rows faster than the parent can consume them will fill its output buffer. If the buffer is unbounded, the operator can exhaust memory. If the buffer is bounded, the worker must wait, which can stall the entire pipeline. A common solution is to give each worker a fixed-size output buffer and to flush it to a shared queue when full. The shared queue is bounded and applies backpressure to the workers. The workers then block on the queue, which frees their cores for other work if the scheduler is cooperative. In a thread-per-worker model, blocking on a queue can waste a core. An asynchronous model uses continuations or futures to suspend the probe task and resume it when the queue has space. The right choice depends on the execution engine, but the hash join must expose enough state to make the choice possible.

## Hash Function Engineering for Real Join Keys

The hash function is not a detail to be chosen at the end. It determines the partition distribution, the collision rate in the build table, and the cost of every row in both phases. For a single integer key, the hash function can be a multiply-shift or a finalizer from a known mixing function. The multiply-shift hash is cheap and provides good distribution for many key distributions, but it can be poor for keys that differ only in high bits if the multiplier is not chosen carefully. A finalizer that xors the high and low halves is more robust and still inexpensive. The hash function should be deterministic and independent of the worker, the partition, and the memory address. Address-dependent hashing, such as hashing a pointer, is a bug because it makes the join result depend on allocation.

Multi-column keys require a composite hash. The straightforward approach is to combine the individual column hashes with a mixing step, such as multiply by a constant and xor. The order of columns must be fixed, and the combination must not be commutative unless the join key is also treated as unordered, which is almost never the case. A common mistake is to add the column hashes, which makes `(a, b)` and `(b, a)` collide. That can turn a selective join into a hot partition if the data contains many swapped pairs. The combination should be order-sensitive and should mix the bits of each column before combining. For variable-length columns, the hash must process the bytes and include the length. A hash that ignores the length can collide a prefix with a longer string. The cost of hashing a string is proportional to its length, so the operator should avoid hashing the full string if a prefix is known to be selective. A prefix hash followed by a full comparison on collision is a common optimization, but it adds a comparison path that must be correct for all types.

Null handling interacts with the hash function. In SQL, null is not equal to null for join purposes. A build row with a null join key cannot match any probe row, and a probe row with a null key cannot match any build row. The operator can handle nulls by filtering them before the hash table, or by assigning them a special hash value and ensuring that the comparison always fails. Filtering is usually cheaper because it removes rows from the build table and from the probe. For outer joins, the null rows still need to be emitted on the appropriate side. A left outer join with a null build key must emit the build row as unmatched; a right outer join with a null probe key must emit the probe row as unmatched. The operator must therefore track nulls separately or mark them as unmatched during the final scan. The hash function should never be called on a null value if the comparison semantics treat null as unequal, because the hash value is meaningless.

## Partitioning Mechanics: Counting, Scattering, and Write Combining

A partitioned hash join usually needs two passes over the input: one to count rows per partition and one to scatter them. The counting pass builds a histogram of partition ids. The scatter pass uses the histogram to compute offsets and writes each row to its partition buffer. This is the classic radix partitioning pattern. It is cache-friendly because the counting pass reads the input sequentially and the scatter pass writes to a small number of buffers. The buffers should be sized from the histogram so that no reallocation is needed. If the input is larger than memory, the scatter pass can write directly to disk, but then the histogram must be exact or the writes must be append-based.

Write combining is a technique for reducing the number of cache lines touched during scattering. Instead of writing a row to its partition buffer immediately, the scatter pass keeps a small cache of recent rows per partition. When the cache is full, it flushes the rows as a contiguous block. The cache is small enough to fit in L1 or L2, and the flush writes a full cache line or a few cache lines. This reduces the number of partial cache line writes and improves memory bandwidth. The cache can be a simple array of row slots per partition, with a per-partition count. The number of partitions must be small enough that the cache array fits in cache. If there are hundreds of partitions, the cache array itself becomes a cache problem. A common compromise is to partition in two levels: a small number of coarse partitions first, then a second level within each coarse partition. The first level uses write combining, and the second level uses a larger partition count.

The scatter pass must also handle the case where a partition buffer is full. If the histogram was exact, the buffer cannot overflow unless the input changed. If the input is streaming or the histogram is approximate, the buffer can overflow. The operator must then allocate a larger buffer or spill the partition. Spilling during the scatter pass is expensive because the partition is not yet complete. A safer design uses a histogram that is exact for the current input. If the input is a batch from a parent operator, the batch size is known and the histogram can be computed from it. If the input is a stream, the operator can buffer a batch, compute the histogram, and then scatter the batch. This adds a buffering step but keeps the scatter pass simple.

## Instrumentation: What to Measure and What to Ignore

A parallel hash join has many counters, and not all of them are useful. The most important measurements are per-phase time, per-partition row counts, the maximum partition size, the number of spills, and the number of probe rows rejected by the Bloom filter. Per-phase time tells you whether the operator is dominated by partitioning, building, probing, or output. If partitioning is dominant, the partition count or the hash function may be wrong. If building is dominant, the table layout or the load factor may be wrong. If probing is dominant, the probe side may be large, the Bloom filter may be ineffective, or the table may be missing cache. If output is dominant, the parent operator may be applying backpressure or the projection may be expensive.

Per-partition row counts reveal skew. A histogram of partition sizes is more useful than a single average. The maximum partition size determines the memory requirement and the straggler. The ratio of the maximum to the average is a simple skew metric. If the ratio is close to one, the hash function is distributing well. If it is much larger than one, the operator should consider salting or dynamic repartitioning. The number of spills is a direct measure of memory pressure. If the operator spills even though the build side should fit, the memory budget or the partition count is misconfigured. The Bloom filter rejection rate tells you whether the filter is worth its memory. If the rejection rate is low, the filter is not paying for itself.

Hardware counters can explain why a phase is slow. Cache miss rates, TLB miss rates, and memory bandwidth utilization are useful for the build and probe phases. A high L1 miss rate with a low L2 miss rate suggests that the table is larger than L1 but fits in L2. A high last-level cache miss rate suggests that the table is too large or the access pattern is random. TLB misses are common when the hash table is large and the access pattern is random. Huge pages can reduce TLB misses, but they must be allocated and managed. The operator should not assume that hardware counters are available or accurate in every environment, but when they are, they can turn a vague performance problem into a specific fix.

## Testing and Debugging Parallel Hash Joins

Parallel hash joins are difficult to debug because the bugs are often nondeterministic. A race in the build-probe dependency may only appear when the machine is loaded or when the partition count is unusual. A missing memory barrier may work on x86 and fail on ARM. A duplicate handling bug may only appear when the build side contains multiple rows with the same key and the probe side contains a row that matches all of them. A skew bug may only appear when the data distribution is different from the test data. The test suite should therefore include randomized data, skewed data, duplicate-heavy data, null keys, empty inputs, and inputs that are larger than the memory budget. Each test should compare the join output against a reference implementation, such as a nested loop join or a single-threaded hash join. The comparison should be order-independent unless the operator guarantees order.

Race detection tools are essential. ThreadSanitizer can catch data races in the build-probe handoff, the partition state machine, and the output buffers. It cannot catch missing memory barriers that are not data races in the C++ sense, but it can catch unsynchronized accesses. Stress testing with many iterations and varied thread counts increases the chance of hitting a rare interleaving. The test should also run with a deterministic scheduler if the engine has one, because deterministic scheduling can make races reproducible. If the engine does not have one, a random seed and a large number of iterations are the next best thing.

Memory debugging is equally important. A parallel hash join allocates many buffers, and a use-after-free in a partition buffer can corrupt the hash table or the output. AddressSanitizer can catch out-of-bounds accesses and use-after-free. Valgrind is slower but more thorough. The operator should also have internal consistency checks that can be enabled in debug builds. For example, after the build phase, the operator can verify that the number of rows in the table equals the number of build rows for the partition. After the probe phase, it can verify that the number of emitted rows equals the expected number of matches. These checks are too expensive for production, but they are invaluable during development.

## Integration with the Query Scheduler and Memory Manager

A hash join does not run in isolation. It competes with other operators for memory and CPU. The query scheduler must decide how many hash joins can run concurrently and how much memory each can use. If the scheduler admits too many concurrent joins, they will all spill and the system will thrash. If it admits too few, the CPU will be underutilized. The memory manager must enforce the budget and provide a way for the operator to request more memory or to release memory when a partition finishes. A simple model gives each query a fixed memory grant and lets the operator divide it among partitions. A more sophisticated model uses a global memory pool with reservations and eviction. The operator should not assume that it can allocate memory at will; it should treat memory as a resource that can be denied.

The scheduler also decides where the hash join runs. If the build side is small, the join may be broadcast to all nodes in a distributed plan. If the build side is large, the join may be partitioned. In a shared-memory engine, the scheduler may co-locate the hash join with the scan that produces its build input to avoid materializing the input. It may also overlap the hash join with other operators that are not dependent on it. The hash join should expose enough information to the scheduler: the estimated build size, the estimated probe size, the join key distribution if known, and the current memory usage. The scheduler can then make better decisions about admission and placement. Without that information, the scheduler is guessing, and the hash join will be the first operator to suffer when the guess is wrong.

## Alternative Designs and When Hash Join Is the Wrong Choice

Hash join is not always the best join algorithm. If both inputs are already sorted on the join key, a sort-merge join can avoid the build table and the partitioning pass. It reads both inputs sequentially and merges them. The merge is cache-friendly and can be parallelized by splitting the sorted inputs into ranges. The cost is the sort, but if the sort is already required by the query plan, the merge is nearly free. If the inputs are not sorted, a hash join is usually faster because sorting is more expensive than building a hash table. The exception is when the data is skewed and the hash join cannot balance the load; a sort-merge join can handle skew more gracefully because the merge is a sequential scan and the ranges can be sized by the data distribution.

A nested loop join is appropriate when the build side is very small or when the join predicate is not an equi-join. It has no partitioning or hash table, but it can be quadratic if the build side is not tiny. A block nested loop join improves locality by processing blocks of the outer input. A hash join with a Bloom filter can be seen as a hybrid: the filter acts like a precomputed semi-join, and the hash table handles the matches. The choice between these algorithms is a planning decision, but the hash join implementation should be honest about its costs. If the build side is larger than memory, the hash join will spill, and a sort-merge join may be a better choice if the data can be sorted within the memory budget. If the join key is heavily skewed, the hash join may need salting or dynamic partitioning, and the planner should account for that cost.

The next area to explore is how the hash join behaves when it is embedded in a larger pipeline with multiple joins, aggregations, and sorts. The memory budget is shared across all of them, and the scheduling decisions interact. A hash join that is fast in isolation can be slow when it competes for memory with a sort that is also spilling. A production engine needs a global view of memory and work, not just a local view of one operator. That is a harder problem than any single hash table layout, and it is where the next set of design choices begins.
