# Roaring Bitmaps and Compressed Bitmap Indexes: Container Selection, SIMD Intersections, and the Engineering of Set Operations at Scale

A query engine receives a conjunction of three predicates. Each predicate has already been evaluated against an inverted index, producing a sorted list of matching document IDs. The lists contain 12 million, 800,000, and 3,000 entries respectively. The engine must intersect them and then iterate the result in document order to score hits.

How those lists are stored decides whether this takes a few milliseconds or a few hundred. As sorted arrays of 32-bit integers, the intersection is a linear merge over roughly 12.8 million elements, each step a compare and a hard-to-predict branch. As dense bitmaps over a 100-million-document universe, the intersection is a word-wise AND over 1.56 million 64-bit words — but the third list, with 3,000 entries, would occupy 12.5 MB on its own, and a thousand such lists would exhaust memory long before the query planner got involved. As hash sets, the intersection is a scatter-gather with no ordering, no locality, and no bulk operation worth vectorizing.

None of these representations is wrong. Each is wrong *for a particular density*. And density is not a property of the collection as a whole — it is a property of the region of the key space you happen to be looking at. A posting list can be dense across one range of document IDs and nearly empty across another, because document IDs are assigned in crawl or ingestion order and topical clusters are not uniformly distributed over that order. A column of a fact table can have a million distinct values in one partition and forty in the next.

That observation — density is local — is the foundation of compressed bitmap indexes in general and of the Roaring format in particular. This article works through the design space. We will look at why the earlier compressed bitmap schemes (WAH, EWAH, Concise) hit a wall on sparse random data, how Roaring's two-level partitioning and per-container representation choice route around that wall, how the set operations are actually implemented down to the SIMD shuffle, and where the design still costs you in memory, cache behavior, and implementation complexity.

## Three Baseline Representations And Their Cost Models

Before compressing anything, it helps to be precise about what we are optimizing. For a set `S` drawn from a universe of size `U`, we care about five operations, and they have different cost structures:

- **Membership test** — is `x` in `S`?
- **Intersection** — `S ∩ T`, usually the dominant cost in query evaluation.
- **Union** — `S ∪ T`, common in disjunctive queries and in incremental index construction.
- **Cardinality** — `|S|`, needed for selectivity estimation and for choosing join orders.
- **Iteration** — enumerate the elements in order, which is what you do after the boolean algebra is finished.

A **sorted array** of 32-bit integers costs `4|S|` bytes. Membership is a binary search, `O(log |S|)` with poor locality on large arrays but acceptable. Intersection is a linear merge, `O(|S| + |T|)`, with sequential access on both sides — genuinely cache-friendly. Iteration is free. Union requires either a merge into a new array or an in-place insertion, and repeated insertion into a sorted array is `O(|S|)` per element because of the memmove. This representation is excellent when `|S|` is small or moderate and the universe is huge.

A **dense bitmap** costs `U/8` bytes regardless of `|S|`. Membership is a shift, a mask, and a load. Intersection is `U/64` word-wise ANDs, which vectorizes trivially and runs at memory bandwidth. Cardinality is a popcount over `U/64` words. Iteration requires scanning for set bits, which costs `U/64` word reads even if only three bits are set. The fatal property is that the memory cost is independent of the cardinality: for `U = 2^32`, a dense bitmap is 512 MiB. You cannot materialize one per posting list.

A **hash set** costs roughly `8–16` bytes per element with open addressing and load-factor headroom. Membership is `O(1)` expected. Intersection requires probing every element of the smaller set against the larger, which is `O(min(|S|,|T|))` probes with random access — the worst possible access pattern for a modern memory hierarchy. There is no useful SIMD formulation because the probe addresses are data-dependent. Hash sets win when the workload is dominated by point queries and the sets are never bulk-combined, which is exactly the workload that bitmap indexes are not built for.

The cost model that matters for index structures is not asymptotic complexity. It is bytes touched per element combined with the sequentiality of the touch. Sorted arrays touch 4 bytes per element sequentially. Dense bitmaps touch 1 bit per universe element sequentially. Compressed bitmaps try to get the density advantage of the bitmap while paying only for the elements that are actually present — and the whole history of the format is a sequence of attempts to do that without giving up the sequential access pattern.

## The Compressed Bitmap Lineage: WAH, EWAH, And Concise

The first generation of compressed bitmap indexes exploited a simple observation: real bitmaps contain long runs of identical bits. A posting list for a common term may have thousands of consecutive set bits; a posting list for a rare term has long stretches of zeros between isolated ones. Run-length encoding at the word level captures both.

**WAH (Word-Aligned Hybrid)** encodes a bitmap as a sequence of 32-bit words. If the high bit of a word is 0, the remaining 31 bits are literal payload. If the high bit is 1, the word is a *fill word*: the next bit indicates whether the run is all zeros or all ones, and the remaining 30 bits encode the run length in units of fill words. A single fill word can therefore represent up to `2^30 × 31` bits. Decoding is a single pass with a small state machine, and the encoder is streaming — it never needs to look ahead more than one word.

WAH's weakness is that its runs are word-aligned. A run of 40 set bits that starts at bit 17 and ends at bit 56 spans two literal words plus a partial fill, and the encoder must emit the literal words to preserve the boundary. The cost of a run is therefore rounded up to the next word boundary, which for short runs is pure overhead.

**EWAH (Enhanced WAH)** attacks a different problem: WAH's decoder must still touch every fill word to advance the cursor, so a bitmap that is 99% zeros still costs `U/32` word reads to scan. EWAH changes the encoding so that each run is described by a pair of words — a running-length word giving the number of clean (fill) words, followed by a count of the literal words that come after. A decoder can skip an entire clean run by adding the running length to its cursor, without reading the fill words themselves. This makes EWAH markedly better for the sparse, clustered bitmaps that appear in column stores and in version-control systems, where the common operation is a full intersection of two bitmaps that are mostly empty.

**Concise** refines WAH from the other direction. Instead of encoding run length in word units, it encodes the number of dirty words followed by the position of the next flipped bit, which lets it represent runs that do not align to word boundaries. The encoding is denser than WAH for short, misaligned runs, at the cost of a decoder that is meaningfully more intricate and an encoder that must buffer more state.

All three schemes share a structural limitation that no amount of encoding cleverness removes. Their cost is proportional to the number of *words* spanned by the bitmap, not to the number of set bits. Consider a bitmap over a 32-bit universe where set bits are uniformly random and the density is one in a thousand. There are no runs to exploit. Every set bit sits in its own literal word, and each literal word costs 32 bits. The compressed bitmap therefore costs about 32 bits per element — exactly the same as a sorted array of 32-bit integers, with a more expensive decoder and no ability to binary-search. Worse, the top-level structure still spans the full universe: the encoder emits fill words covering the gaps, so the encoded size is proportional to `U` even when `|S|` is tiny.

This is the regime that modern workloads live in. Document IDs, user IDs, and row IDs are not clustered in the way that the WAH-era workloads were. They are hashed, sharded, or assigned by a distributed system that has no reason to keep related entities adjacent. A compressed bitmap format that degrades to 32 bits per element on random sparse data is not a general-purpose index.

## Roaring's Central Move: Two-Level Partitioning

The Roaring format, introduced in 2016, starts from a different premise. Instead of encoding a 32-bit bitmap as a single word-aligned stream, it partitions the 32-bit key space into `2^16` buckets by the high 16 bits. Each bucket is called a **container** and holds the low 16 bits of every key that falls into it. Only non-empty containers exist.

This single structural decision changes the cost model completely. A container covers at most 65,536 distinct values, so a fully dense container is exactly 8 KiB. And because the partition is by high bits, the containers are naturally ordered — the top-level index is a sorted list of 16-bit container keys, which supports binary search and, more importantly, supports a *merge* intersection over the container keys that skips entire 64K ranges without decoding anything inside them.

The second half of the design is that the representation *inside* a container is chosen adaptively, based on the container's cardinality and distribution. This is the move that WAH, EWAH, and Concise cannot make, because they commit to a single encoding for the entire bitmap. Roaring commits to an encoding per 64K chunk, and it can change its mind as the container grows and shrinks.

The top-level index itself uses the same trick. It can be a sorted array of 16-bit keys, or — when more than a few thousand containers are populated — a bitmap of 65,536 bits. The same crossover logic that governs containers governs the index over containers. This self-similarity is not incidental; it is why the format's worst case is bounded.

## The Three Container Types

A Roaring container holds a set of 16-bit values. There are three representations, and the choice among them is the heart of the format.

**Array container.** A sorted array of `uint16` values. Membership is a binary search. Intersection with another array container is a linear merge. Iteration is a sequential scan. The cost is `2` bytes per element.

**Bitmap container.** A fixed array of 1024 `uint64` words — 65,536 bits, 8 KiB. Membership is a shift, mask, and load. Intersection is 1024 word-wise ANDs. Cardinality is a popcount, cached in the container header so that `cardinality()` is `O(1)` rather than `O(1024)`. The cost is 8 KiB regardless of how many bits are set.

**Run container.** A sequence of `(start, length)` pairs of `uint16`, where `length` is the number of additional values in the run. The cost is `2 + 4r` bytes for `r` runs. This is the only container whose cost depends on the *distribution* of values rather than their count, which makes it the right choice for clustered data and the wrong choice for scattered data.

The crossover between array and bitmap is not a tuned constant. An array container holding 4096 values costs `4096 × 2 = 8192` bytes. A bitmap container costs 8192 bytes. At exactly 4096 elements the two representations are the same size, and below that the array is strictly smaller while also being faster to scan for iteration and faster to binary-search for membership. The threshold falls out of the arithmetic.

The run container's crossover is a comparison against both alternatives. It beats an array container when `2 + 4r < 2c`, that is, when the number of runs is less than half the cardinality. It beats a bitmap container when `2 + 4r < 8192`, that is, when there are fewer than roughly 2048 runs. A container with 60,000 set bits arranged in 100 runs is 402 bytes as a run container, 8 KiB as a bitmap, and 120 KB as an array — a 20× difference in the direction that matters for cache residency.

Because the representation is per-container, a single Roaring bitmap can mix all three. A 32-bit set with a dense cluster of IDs in one 64K range, a scattered handful in another, and a long contiguous run in a third will use a bitmap container, an array container, and a run container respectively — each chosen because it is the smallest and fastest option for that specific chunk. The container type is recorded in the top-level index, so an operation on two bitmaps can dispatch per container pair without inspecting the contents first.

## Container Selection in Practice: Hysteresis, Conversion, and the Cost of Being Wrong

The arithmetic crossover between array and bitmap containers is clean at exactly 4096 elements, but an index that flips representation at that point will thrash if the workload oscillates around the threshold. A container that repeatedly gains and loses a single element near the boundary would convert between a 2-byte-per-element array and an 8 KiB bitmap on every other mutation. The conversion cost is not trivial: array-to-bitmap requires allocating 8 KiB, zeroing it, and setting one bit per element; bitmap-to-array requires scanning 1024 words, extracting set bits, and writing them into a sorted array. Both are `O(container size)`, which is fine once but pathological in a loop.

Production implementations therefore add hysteresis. The array-to-bitmap transition happens when cardinality exceeds 4096. The bitmap-to-array transition happens only when cardinality drops below a lower threshold, or when a bulk operation produces a result that is known to be small. Some implementations never convert a bitmap back to an array except during explicit optimization passes. The asymmetry is deliberate: bitmap containers are the stable representation for mutable, dense-ish containers, and array containers are the stable representation for small, read-mostly containers. The exact thresholds are implementation details, but the principle is general — representation choice is a policy, not a pure function of cardinality.

Run containers complicate the policy because their cost depends on the number of runs, not the number of elements. A container with 50,000 set bits in 20 runs is tiny as a run container and enormous as an array. But maintaining run containers under random insertions is expensive: inserting a value into the middle of a run splits it, inserting adjacent to a run extends it, and inserting into a gap creates a new run. Each operation may require shifting the run list. For this reason, run containers are usually produced by an explicit `runOptimize` pass over a bitmap or array container, or by a bulk loader that knows the input is clustered. They are a read-optimized representation. If your workload is insert-heavy and random, the run container will rarely be selected, and the format will behave like an array/bitmap hybrid.

The cost of being wrong is asymmetric. Choosing an array container when a bitmap would be better costs memory and makes intersection slower because the merge is linear in the number of elements rather than 1024 word operations. Choosing a bitmap when an array would be better costs 8 KiB per container, which for a million sparse containers is 8 GB of mostly zero words. Choosing a run container when the data is scattered costs 4 bytes per run, and a scattered container has one run per element, so it is worse than an array. The selection policy is therefore the difference between a format that scales to billions of elements and one that does not.

## The Container-Pair Dispatch Matrix

Intersecting two Roaring bitmaps begins with the top-level index. Both bitmaps have a sorted sequence of 16-bit container keys. The engine performs a merge over these keys, and for each key present in both, it dispatches to a container-level intersection routine. The dispatch is a function of the two container types, and there are nine cases. Each case has a different optimal algorithm, and the result type is chosen independently.

Array-array intersection is a linear merge over two sorted `uint16` arrays. The loop is simple: advance the pointer with the smaller value, emit when equal. The branch predicting which side advances is data-dependent and mispredicts often on random data. For arrays of similar size, this is still the fastest option because the data is contiguous and the loop is short. For skewed sizes — say 100 elements against 100,000 — the linear merge touches all 100,000 elements of the larger array, which is wasteful. The alternative is galloping search: iterate the smaller array, and for each element, perform an exponential search followed by a binary search in the larger array. The cost becomes `O(min × log(max))`, which for a 1000× skew is roughly 100 × 17 = 1700 comparisons instead of 100,100. The crossover between merge and galloping is usually expressed as a ratio: when `min × 64 < max`, galloping wins. The constant depends on cache behavior and branch prediction, but the shape is universal.

Array-bitmap intersection is asymmetric. The array is small by definition, so the natural algorithm is to iterate the array and test each value against the bitmap. Each test is a shift, a mask, and a load from the 8 KiB bitmap. The access pattern is random within the container, but the container is only 8 KiB, so it fits in L1. The result is an array container, because the result cardinality is at most the array's cardinality, which is below 4096. If the array is large and the bitmap is sparse, the same algorithm still works; the bitmap is dense by representation, not necessarily by cardinality. A bitmap container can have as few as 4097 set bits, in which case testing an array of 4096 elements against it is reasonable.

Bitmap-bitmap intersection is the case that vectorizes. It is 1024 word-wise ANDs, followed by a popcount to determine the result cardinality. If the popcount is below 4096, the result is materialized as an array container by extracting the set bits. If it is above, the result stays as a bitmap container. The extraction step is where the SIMD shuffle earns its keep, because a naive extraction loop over 1024 words with a `ctz` per set bit is slower than the AND itself for sparse results. The implementation must balance the cost of computing the popcount, the cost of extraction, and the cost of allocating the result container.

Run container intersections are interval merges. Two run containers are lists of `(start, length)` pairs. The intersection walks both lists, computes the overlap of the current intervals, and emits a new run when the overlap is non-empty. This is linear in the number of runs, which is why run containers are so effective for clustered data: a container with 100 runs intersects in 100 steps, regardless of whether those runs cover 100 elements or 60,000. Run-array intersection iterates the array and checks membership in the run list, either by binary search over run starts or by a merge if the array is sorted and the runs are sorted. Run-bitmap intersection is the hybrid case: if the run container has few runs, iterate the runs and mask the corresponding bits in the bitmap; if the bitmap has few set bits, iterate the bitmap's set bits and check them against the runs. The dispatch decision is based on the cardinality of the bitmap and the number of runs.

## SIMD Intersection of Bitmap Containers

The bitmap-bitmap intersection is the only container pair that is unconditionally memory-bandwidth bound. Each container is 8 KiB, so an intersection reads 16 KiB and writes up to 8 KiB. On a machine with 20 GB/s of memory bandwidth, that is roughly 1.2 microseconds per container pair if the data is in cache and the loop is vectorized. If the data is in DRAM, the latency is higher, but the sequential access pattern means the hardware prefetcher can hide much of it. The goal of the SIMD implementation is to saturate the load ports and the vector ALUs, not to reduce the asymptotic complexity.

The basic loop is a sequence of 256-bit or 512-bit ANDs. With AVX2, each iteration processes four 64-bit words: load 32 bytes from each input, AND them, and store 32 bytes to the result. The popcount is computed either by a scalar popcount per word or, on AVX-512, by `VPOPCNTQ`, which produces eight 64-bit popcounts in one instruction. The result of the popcount is a vector of counts; summing them gives the total cardinality. If the total is below the array threshold, the implementation discards the materialized bitmap and extracts the set bits into an array container. This means the AND is done twice in the worst case — once to count, once to extract — unless the implementation keeps the ANDed words in registers or in a temporary buffer. Most implementations write the ANDed words to a stack buffer, count them, and then either keep the buffer as a bitmap container or extract from it.

Extraction is the interesting part. Given a 64-bit word with `k` set bits, the goal is to append the positions of those bits to an output array. The scalar approach is a loop over `word & -word` and `ctz`, which is branchless but serial: each iteration depends on the previous `word` value. For a word with many set bits, this is slow. The SIMD approach uses a lookup table indexed by an 8-bit mask. The 64-bit word is converted to an 8-bit mask via `_mm256_movemask_epi8` after a comparison against zero, or via a sequence of shifts and `pmovmskb`. Each bit in the mask corresponds to a byte in the word. A 256-entry table maps the mask to a vector of byte indices where the mask is set. The indices are then added to a base offset and compacted into the output array using a shuffle instruction. This turns the extraction into a table lookup and a shuffle per 8 bytes, which is much faster than the scalar loop for dense words. The tradeoff is the 256-entry table, which is 256 × 8 bytes = 2 KiB, small enough to stay in L1.

The result container type for bitmap-bitmap intersection is determined after the popcount. If the cardinality is below 4096, the result is an array container. If it is above, the result is a bitmap container. There is a third possibility: if the result has very few runs, a run container might be smaller. Some implementations run a run-detection pass on the result if the cardinality is in a range where run encoding could win. That pass costs an extra scan, so it is usually only done during explicit optimization, not during query evaluation.

## Metadata, Locality, and the Overhead of Many Small Containers

Every container stores its cardinality. For an array container, the cardinality is the length of the array. For a bitmap container, the cardinality is a cached `int` that is updated on mutation or computed during construction. For a run container, the cardinality is the sum of the run lengths, which can be cached or computed on demand. The top-level index stores the container keys and types, and it may also store a prefix sum of cardinalities to support `rank` and `select` in logarithmic time. Without the prefix sum, `rank(x)` requires summing the cardinalities of all containers with keys less than `x`'s high bits, which is `O(number of containers)`. With the prefix sum, it is a binary search followed by a container-level rank.

Container-level rank is straightforward for array containers: binary search for the value and return the index. For bitmap containers, rank requires a popcount over the words before the target word, plus a masked popcount within the target word. This is `O(1024)` in the worst case if done naively, but with a cached prefix sum per word it becomes `O(1)`. Some implementations store a rank index every 64 words, which trades memory for speed. For run containers, rank requires walking the runs and summing lengths until the target is found, which is `O(number of runs)`. If the run container is large, this can be slow, so some implementations convert to a bitmap container for rank-heavy workloads.

Select is the inverse: find the k-th set bit. For array containers, it is a direct index. For bitmap containers, it requires a scan over words, accumulating popcounts until the target word is found, then a bit-level select within that word. For run containers, it is a walk over runs, subtracting lengths until the target run is found. The cost of select is dominated by the container type. This is another reason why the container type matters beyond memory: it determines the asymptotic cost of the metadata operations that query planners use for selectivity estimation and join ordering.

Roaring's two-level structure improves locality at the container level but introduces pointer chasing at the top level. The top-level index is a sorted array of container keys and a parallel array of pointers to container data. Iterating the bitmap means walking the index and dereferencing each pointer. If the containers are allocated separately on the heap, each dereference is a potential cache miss. For a bitmap with 1000 containers, that is 1000 cache misses, which at 100 ns each is 100 microseconds — significant compared to the microseconds spent on the actual set operations. Some implementations mitigate this by allocating containers in a single contiguous arena, so that the pointer dereference is a simple offset and the containers are laid out in key order. This improves iteration and intersection locality, but it makes mutation harder because inserting a new container requires shifting the arena or leaving gaps.

Serialization has the same tension. The portable Roaring format writes the top-level index first, then the containers in key order. This is compact and allows memory-mapped access, but it does not compress the containers themselves. A bitmap container is always 8 KiB, even if it has only 4097 set bits. A run container is variable-length, which makes random access harder. The format is designed for fast deserialization, not for minimal size. If size is the priority, the serialized bytes can be passed through a general-purpose compressor, but that destroys the ability to operate on the bitmap without full decompression. This is the classic tradeoff between compressed representation and queryable representation: Roaring chooses queryability at the container level and leaves global compression to the storage layer.

The overhead of many small containers is the format's main weakness. A container with a single element costs a top-level index entry — 2 bytes for the key, 1 byte for the type, 4 bytes for the cardinality, and 8 bytes for the pointer, plus the 2-byte array itself — roughly 17 bytes for one element. A sorted array of 32-bit integers would store that element in 4 bytes. If the data is uniformly distributed over the 32-bit key space and the set is sparse, almost every element lands in its own container, and Roaring becomes an expensive sorted array. The format is at its best when the data is clustered in the high 16 bits, so that containers are populated and the per-container overhead is amortized. This is not a flaw in the design; it is the boundary of its applicability. Knowing where that boundary lies is as important as knowing how the containers work.

## Multiway Intersection and the Cost of Intermediate Results

A conjunction of three or more posting lists is rarely evaluated as a sequence of independent pairwise intersections. The naive left-to-right fold materializes an intermediate bitmap after every pair, and those intermediates can be larger than the final result. If the first two lists are both large and their intersection is still large, the engine writes a full bitmap only to read it again for the third list. The memory traffic is proportional to the sum of the intermediate sizes, not to the size of the answer.

The alternative is to drive the intersection from the smallest list. For two lists, this is the galloping or leapfrog join: iterate the smaller list, and for each element, probe the larger lists using binary search or a bitmap membership test. For three or more lists, the same idea generalizes: pick the list with the smallest cardinality as the driver, iterate its elements, and probe every other list. The cost is `|S_min|` probes, each `O(log |S_i|)` for array containers or `O(1)` for bitmap containers. This avoids materializing intermediates entirely, and it terminates early if the driver is exhausted. The tradeoff is that the driver is re-scanned for each consumer, so if the result is needed more than once, materialization may still win.

At the container level, multiway intersection can be done in a single pass over the union of container keys. Each bitmap contributes a sorted sequence of container keys. A k-way merge advances through the keys in order. For a given key, if any bitmap lacks a container for that key, the intersection for that 64K range is empty and the merge can skip to the next key present in all inputs. If all inputs have the key, the engine dispatches to a multiway container intersection. For bitmap containers, the operation is an AND across all containers word by word, accumulating the popcount. This reads each container once, rather than once per pairwise step. For array containers, the engine picks the smallest array as the driver and probes the others. For run containers, it intersects the interval lists. Mixed container types are handled by choosing the most restrictive representation as the driver and probing the rest.

The top-level merge is where Roaring's sorted container keys pay off. Because the keys are 16-bit integers, the merge is over at most 65,536 values per bitmap. A k-way merge with a heap is `O(total_keys log k)`, but for small k a simple linear scan over the smallest bitmap's keys is faster. The engine can also use a bitmap of 65,536 bits to represent the set of keys present in each input, turning the merge into a word-wise AND over 1024 words. This is the same self-similar trick: the index over containers can be a bitmap when the number of containers is large.

Early termination is not just an optimization; it is often the difference between a query that fits in a latency budget and one that does not. The container headers give exact cardinalities without decoding. Before any container-level work, the engine can compute an upper bound on the result cardinality: the minimum cardinality among all inputs. If that bound is below a threshold, the engine can switch strategies entirely, using the smallest bitmap as a driver and probing the others with membership tests. If the bound is zero, the intersection is empty and the engine returns immediately. For disjunctions, the bound is the sum of cardinalities, which is less useful for pruning but still helps with memory allocation.

## Iterators, SkipTo, and Lazy Materialization

Set operations are only half of the query pipeline. The other half is iteration: after the boolean algebra, the engine must enumerate the matching documents in order, usually to score them or to fetch columns. Roaring supports forward and reverse iteration, and both are implemented as stateful cursors over the container sequence.

A forward iterator holds three pieces of state: the index of the current container in the top-level index, the current position within that container, and the container type. Advancing is a type dispatch. For an array container, advancing means incrementing an index into the sorted `uint16` array. For a bitmap container, advancing means scanning 64-bit words from the current position, using `ctz` to find the next set bit, and refilling the word when it is exhausted. For a run container, advancing means walking the run list, incrementing the offset within the current run and moving to the next run when the run length is exhausted. The cost per element is `O(1)` for all three, but the constant differs. Array iteration is the fastest because it is a sequential read. Bitmap iteration is slower for sparse containers because it scans zero words. Run iteration is fastest for long runs and slower for many short runs.

SkipTo is the operation that makes leapfrog joins possible. Given a target value `x`, the iterator must advance to the smallest element greater than or equal to `x`. The top-level index is searched for the container whose key matches the high 16 bits of `x`. If the container exists, the iterator positions itself within the container: binary search for array containers, a mask-and-`ctz` for bitmap containers, and a binary search over run starts for run containers. If the container does not exist, the iterator advances to the next container in key order. SkipTo is `O(log n)` for arrays and runs, and `O(1)` for bitmaps, but it may touch a new container and incur a cache miss. In a multiway join, the driver iterator calls SkipTo on the other iterators, and the cost is dominated by the number of SkipTo calls, not by the size of the probed bitmaps.

Lazy materialization is the natural extension. Instead of computing `S ∩ T` and returning a new bitmap, the engine returns a cursor that wraps the two input iterators and performs the intersection on demand. The cursor uses the smaller input as the driver and probes the larger input for each element. This is exactly the leapfrog join, exposed as an iterator. The advantage is that no result container is allocated and no intermediate bitmap is written. The disadvantage is that the intersection is recomputed if the cursor is rewound or if multiple consumers need the result. Most query engines materialize when the estimated result cardinality is above a threshold and use a lazy cursor otherwise. The threshold is workload-dependent: a result of a few thousand elements is cheaper to materialize than to re-probe, while a result of a few dozen elements is cheaper to probe.

## Memory Layout, Frozen Bitmaps, and Copy-on-Write

The default Roaring layout allocates each container separately and stores a pointer in the top-level index. This is flexible: containers can grow and shrink independently, and the index can be updated without moving data. But it is hostile to iteration and intersection. Walking the index dereferences a pointer per container, and the containers are scattered across the heap. For a bitmap with thousands of containers, the pointer chasing dominates the actual bitwise work.

A frozen bitmap removes the pointers. After construction, the containers are laid out contiguously in key order, and the top-level index stores offsets instead of pointers. The offsets are relative to the start of the bitmap, so the entire structure can be serialized as a single buffer and memory-mapped. Iteration becomes a sequential scan over the buffer. Intersection becomes a merge over two buffers with predictable access patterns. The cost is that frozen bitmaps are immutable. Any mutation requires copying the affected containers and rebuilding the index, which is acceptable for read-mostly workloads and for snapshots.

Copy-on-write builds on the same idea. A bitmap is a reference-counted pointer to a shared container arena. When a mutation is applied, the engine copies only the containers that change, leaving the rest shared with the original bitmap. This is how systems implement MVCC snapshots and incremental index updates without doubling memory. The overhead is the reference count per container and the indirection through the shared arena. For read-heavy workloads, the indirection is amortized because the containers are still laid out in key order. For write-heavy workloads, the copying can dominate, and a mutable layout with separate allocations may be faster.

The portable serialization format is a middle ground. It writes the top-level index as a sequence of container descriptors, each containing the 16-bit key, the container type, and the cardinality. The container data follows in key order. Bitmap containers are always 8 KiB, array containers are `2 × cardinality` bytes, and run containers are `2 + 4 × number_of_runs` bytes. The format is compact enough to be stored on disk and loaded with a single read, but it does not support zero-copy access because the container data must be parsed into the in-memory layout. The frozen format is the zero-copy variant: it stores offsets instead of descriptors and aligns the container data so that it can be used in place.

## SIMD Beyond the Basic AND

The bitmap-bitmap intersection is the only container operation that is unconditionally vectorizable, and the basic AVX2 loop is well understood. The engineering effort shifts when the vectors widen and when the operation is not a pure AND. AVX-512 changes the calculus in three ways. First, the vectors are 512 bits wide, so the AND processes 64 bytes per iteration. Second, `VPOPCNTQ` computes eight 64-bit popcounts in one instruction, eliminating the nibble table for counting. Third, the `VPTERNLOG` instruction can compute `A AND NOT B` in a single operation, which accelerates difference and symmetric difference. The extraction step can use `VPCOMPRESSQ` or `VPCOMPRESSD` to compact indices without a shuffle table, although the compression is per-lane and still requires a final merge. The main caveat is that AVX-512 frequency throttling can make wide vectors slower than AVX2 on some microarchitectures, especially when the vector units are not saturated. A common approach is to use AVX2 for sparse intersections and AVX-512 for dense ones, or to rely on the runtime's frequency governor to choose.

ARM NEON is 128 bits wide, which is half the AVX2 width. The AND is `vandq_u64`. Popcount is available as `vcntq_u8` followed by `vaddvq_u8` or `vpaddq_u64`. Extraction uses `vshrn` and a lookup table, similar to the x86 approach but with 16-byte vectors. On ARMv8.2 and later, the `CNT` instruction and the `SVE` extension provide wider vectors and better popcount support, but the portable implementation must still handle the 128-bit case. The performance difference between x86 and ARM for bitmap intersection is usually within a factor of two, which is small compared to the difference between a bitmap container and an array container for the same data.

Multiway SIMD intersection adds another dimension. When three or more bitmap containers are ANDed together, the loop can process all inputs in one pass, loading each container once and accumulating the AND in a register. This reduces the number of memory reads from `k × 8 KiB` to `k × 8 KiB` but eliminates the intermediate writes that a pairwise fold would produce. The popcount is accumulated at the end, or computed per iteration and summed. If the result cardinality is known to be small, the loop can skip the materialization step and extract set bits directly from the register, which avoids writing the result bitmap at all. This is the container-level equivalent of lazy evaluation, and it is where the multiway algorithm earns its keep.

Software prefetching is the other lever. The container sequence in a frozen bitmap is contiguous, so the engine can prefetch the next container while processing the current one. The prefetch distance is tuned to the memory latency: on a machine with 100 ns of DRAM latency and a 1.2 microsecond per-container processing time, one or two containers of lookahead is enough. For bitmap containers, the prefetch is a single cache line touch at the start of the container; the hardware prefetcher handles the rest because the access is sequential. For array containers, the prefetch is also sequential, but the container size varies, so the engine must prefetch based on the container header rather than a fixed stride.

## Concurrency, Persistence, and Operational Realities

Immutable bitmaps are the foundation of concurrent access. Once a bitmap is frozen, any number of reader threads can intersect and iterate it without locks, because no state is mutated. Writers create a new version by copying the affected containers and publishing a new pointer. This is the same pattern as persistent data structures: readers see a consistent snapshot, and writers never block readers. The cost is memory amplification: a sequence of updates to a large bitmap can create many versions, each sharing most containers but holding references to the ones that changed. Reference counting must be thread-safe, and the arena must be reclaimed when the last reference is dropped. In practice, this is handled by epoch-based reclamation or by a garbage collector, depending on the host language.

Persistence follows the same split. The portable format is self-contained and can be written to disk, shipped over the network, and read back by any implementation. The frozen format is memory-mappable and can be used directly from the page cache, which means the operating system manages residency and eviction. The tradeoff is that the frozen format is endian-sensitive and alignment-sensitive, so it is usually treated as a local cache format rather than an interchange format. For distributed systems, the portable format is the safe choice, with an optional compression layer on top. The compression layer can be a general-purpose codec like LZ4 or Zstandard, but it destroys the ability to operate on the bitmap without decompression. A common compromise is to compress only the array and run containers, which are already variable-length, and leave bitmap containers uncompressed.

The operational metrics that matter for a Roaring index are not just total size and average cardinality. The container type histogram tells you whether the format is being used as intended. A healthy index for a text search workload has a mix of array containers for rare terms, bitmap containers for common terms, and run containers for sorted columns. An index that is almost entirely bitmap containers with cardinalities near the array threshold is a sign that the selection policy is too eager to convert, or that the data is denser than expected. An index that is almost entirely array containers with high cardinalities is a sign that the conversion threshold is too high, or that the run optimization pass is not being run. Monitoring these distributions over time catches data drift before it turns into a latency regression.

## Union, Difference, and Symmetric Difference: The Other Half of the Algebra

Intersection dominates query evaluation, but it is not the only set operation a bitmap index must support. Disjunctive queries require union. Negation and anti-joins require difference. Symmetric difference appears in change detection and in incremental index maintenance, where you need to know which documents entered or left a set. Each operation has the same container-pair dispatch structure as intersection, but the algorithms and the result-type decisions differ in ways that matter for performance.

Union is the most expensive of the four because the result is at least as large as the larger input. For two array containers, the union is a linear merge that emits both elements when they differ and one when they are equal. The result is an array container if the merged cardinality stays below 4096; otherwise it is converted to a bitmap container. The conversion can be done during the merge: once the output count exceeds 4096, the engine allocates an 8 KiB bitmap, copies the already-emitted elements into it, and continues setting bits instead of appending to an array. This avoids a second pass. The cost is `O(|A| + |B|)` with a branch per element to decide which side advances, which is the same branch pattern as intersection but with a different outcome. For array containers of similar size, the merge is fast because both arrays are contiguous and the branch predictor learns the pattern if the data is not adversarial.

Bitmap-bitmap union is 1024 word-wise ORs. On AVX2, each iteration loads 32 bytes from each input, ORs them, and stores 32 bytes to the result. The popcount is computed after the fact, or during the loop if the result cardinality is needed immediately. The result is a bitmap container unless the popcount is below 4096, in which case the engine can either keep the bitmap or convert to an array. Converting a bitmap to an array requires scanning the 1024 words and extracting set bits, which costs more than the OR itself for sparse results. Many implementations therefore keep the result as a bitmap container even when the cardinality is low, deferring the conversion to a later optimization pass. This is a deliberate trade: memory is cheap, but extraction is expensive during query evaluation.

Run-run union is an interval merge. Two run containers are lists of `(start, length)` pairs sorted by start. The union walks both lists, merging overlapping or adjacent intervals. The result is a run container. The cost is linear in the number of runs, which is why run containers are so effective for union of clustered data. A union of two run containers with 100 runs each takes 200 steps, regardless of whether the runs cover 100 elements or 60,000. The result may have fewer runs than either input if the intervals overlap. Array-run union is the mixed case: the array is a set of isolated points, and the run container is a set of intervals. The natural algorithm is to iterate the array and merge each point into the run list, either by extending an existing run, creating a new run, or bridging two runs. This is `O(|A| + r)` if the array is sorted and the runs are sorted, but it requires careful handling of the run list mutations. In practice, many implementations convert the array to a run container first or convert the run container to a bitmap, depending on which is cheaper. The decision is based on the number of runs and the array cardinality.

Difference, `A \ B`, is the set of elements in `A` that are not in `B`. For array containers, it is a merge that emits elements of `A` when they are less than the current element of `B`, and advances both when they are equal. The result is an array container. For bitmap containers, it is `A AND NOT B`, which on AVX-512 can be done with a single `VPTERNLOG` instruction per 512-bit block. The result cardinality is the popcount of the AND NOT. The result type follows the same rule as intersection: array if below 4096, bitmap otherwise. Run-run difference is the most intricate of the container operations. It walks the run lists, and for each run in `A`, it subtracts the overlapping portions of runs in `B`. The result is a list of intervals that may be split by the subtraction. The cost is linear in the total number of runs, but the implementation must handle the case where a single run in `A` is split into multiple runs by several runs in `B`. This is where run containers lose some of their simplicity: the code is more complex than the union or intersection, and the result may have more runs than either input.

Symmetric difference, `A XOR B`, is the set of elements in exactly one of the two sets. For bitmap containers, it is 1024 word-wise XORs. For array containers, it is a merge that emits elements when they differ. For run containers, it is the union of the two differences, which can be computed as `(A \ B) ∪ (B \ A)`. The result type is chosen by cardinality. Symmetric difference is rarely used in query evaluation but is common in incremental index maintenance: when a document is updated, the index needs to remove the old terms and add the new ones, and the set of changed documents is the symmetric difference of the old and new posting lists. In that context, the operation is often applied to small sets, so array containers dominate and the merge is fast.

The result-type decisions for union, difference, and symmetric difference follow the same thresholds as intersection, but with one important difference: these operations are more likely to produce bitmap containers because the result cardinality is larger. A union of two array containers with 3000 elements each will exceed 4096 and become a bitmap. A difference of two bitmap containers can produce a small result, but the engine does not know that until after the operation. The cost of converting a bitmap result to an array is the extraction scan, which is `O(1024)` word reads plus the popcount. For a result with 100 elements, the extraction is more expensive than the operation itself. This is why many implementations delay the conversion: they keep the result as a bitmap container and let the next operation decide whether to extract. The container type is metadata, not a commitment. A bitmap container with 100 set bits is still a valid bitmap container; it is just not the smallest representation. The format tolerates this because the alternative — extracting during every operation — would make sparse results expensive.

## SIMD Techniques for Array Containers and Mixed Operations

The bitmap-bitmap intersection is the only container pair where SIMD is unambiguously the right tool. For array containers, the story is more nuanced. Array containers hold at most 4096 `uint16` values, which is 8 KiB of data. That fits in L1 cache on most microarchitectures. The intersection of two array containers is a linear merge over sorted lists, and the bottleneck is the branch that decides which side advances. On random data, that branch mispredicts frequently, and the misprediction penalty can dominate the cost. SIMD does not eliminate the branch; it can only process multiple elements at once if the merge can be vectorized.

Vectorizing a sorted merge is not straightforward because the output order depends on the comparison results. One approach is to use SIMD to compare blocks of elements and compute a bitmask of matches, then use the bitmask to guide the merge. For example, load 8 elements from each array, compare all pairs using `_mm_cmpgt_epi16` and `_mm_cmpeq_epi16`, and extract a mask of equal elements. This can identify matches in a block of 8×8 comparisons in a few instructions. But the merge still needs to advance the pointers by the number of elements that are less than the current match, which requires a popcount and a conditional advance. The resulting code is complex and may not be faster than the scalar merge for small arrays. The overhead of loading and comparing 8×8 blocks is 64 comparisons, which is more work than the scalar merge for arrays of size 8. The SIMD approach only pays off when the arrays are large, but array containers are capped at 4096, so the maximum size is 8 KiB. At that size, the scalar merge is already fast enough that SIMD gains are marginal.

There is a different SIMD technique that does pay off for array containers: vectorized binary search. When intersecting an array container with a bitmap container, the array is small and the bitmap is 8 KiB. The natural algorithm is to iterate the array and test each value against the bitmap. Each test is a shift, a mask, and a load. This is scalar, but the loads are from a small bitmap that stays in L1. The branch that tests the bit is data-dependent and mispredicts often. A SIMD approach can test 8 values at once by gathering the bits from the bitmap using `_mm_i32gather_epi32` or by using a shuffle-based lookup. The gather instruction is slow on many microarchitectures, so the scalar loop is often faster. The real optimization for array-bitmap intersection is to sort the array (it already is) and use the bitmap's word-level structure to test multiple values in the same word. If the array values are clustered, several values may fall into the same 64-bit word, and the engine can load the word once and test multiple bits with shifts and masks. This is a form of blocking that reduces the number of memory accesses, but it requires detecting when values share a word, which adds branches.

Run container intersections are interval merges, and they are inherently scalar. The number of runs is usually small (tens to hundreds), so the cost is dominated by the branch that decides which interval advances. SIMD could compare multiple run starts at once, but the merge is sequential and the output depends on the overlaps. The complexity is not worth the marginal gain. The same applies to run-array and run-bitmap intersections: the run list is small, and the scalar loop is fast.

The conclusion for array and run containers is that SIMD is not the primary lever. The primary lever is the representation choice: using an array container when the data is sparse, a bitmap container when it is dense, and a run container when it is clustered. Once the right representation is chosen, the scalar algorithms are fast enough that SIMD yields only incremental improvements. The engineering effort is better spent on reducing the number of container pairs that need to be processed, which is where the top-level index and the multiway merge come in.

## Memory Overhead, Allocation Strategies, and Cache-Aware Layouts

The per-container overhead is the price Roaring pays for its adaptivity. A container in the top-level index carries a 16-bit key, a 1-byte type, a 4-byte cardinality, and either an 8-byte pointer or a 4-byte offset. That is 15 to 19 bytes per container, before any container data. For a bitmap with 65,536 containers — the maximum for a 32-bit universe — the index alone is about 1 MB. That is small compared to the container data, which can be up to 512 MB if all containers are bitmaps. But for a sparse bitmap with 10,000 containers, the index is 150–190 KB, and the container data may be only 20 KB if most containers are arrays with a few elements each. In that regime, the index is the dominant memory cost.

The allocation strategy determines whether that overhead is paid in cache misses or in contiguous memory. The default layout allocates each container separately with `malloc` or the language equivalent. The top-level index stores pointers. Iterating the bitmap means following 10,000 pointers, each of which may point to a different cache line. The hardware prefetcher cannot help because the access pattern is pointer-chasing, not sequential. The result is that iteration and intersection of sparse bitmaps are latency-bound rather than bandwidth-bound. A single cache miss is 100 ns, and 10,000 misses is 1 ms, which is significant for a query that should take microseconds.

The fix is to allocate containers in a single arena, in key order, and store offsets instead of pointers. The top-level index becomes an array of structs with a key, type, cardinality, and offset. The container data follows in the same buffer. Iteration walks the index and then the data sequentially. The hardware prefetcher sees a linear access pattern and hides the DRAM latency. The cost is that mutation is harder: inserting a new container requires shifting the arena or leaving gaps. For immutable bitmaps, this is not a problem. For mutable bitmaps, the arena can be over-allocated with gaps, or the bitmap can be converted to the frozen layout when it is published.

Copy-on-write adds another layer. A frozen bitmap can be shared by many readers. When a writer needs to modify a container, it copies that container into a new arena and updates the index. The old arena remains valid for readers that hold a reference. The overhead is the reference count per container and the indirection through the shared arena. For read-heavy workloads, the indirection is amortized because the containers are still in key order. For write-heavy workloads, the copying can dominate, and a mutable layout with separate allocations may be faster because it avoids the copy. The choice depends on the read/write ratio and on the cost of memory allocation.

Cache-aware layout goes beyond contiguous allocation. Bitmap containers are 8 KiB, which is 128 cache lines. Aligning them to 64-byte boundaries ensures that SIMD loads do not cross cache lines. Array containers are variable-length, so aligning each one wastes memory. A better approach is to pack array containers tightly and rely on the small size to keep them in L1. Run containers are also variable-length, but they are usually small. The top-level index should be aligned to a cache line so that a binary search touches as few lines as possible. If the index is large, it can be split into a hot cache of frequently accessed containers and a cold store for the rest, but this adds complexity and is rarely worth it for general-purpose use.

Huge pages are a system-level optimization that can reduce TLB misses for large bitmaps. A 512 MB bitmap spans 131,072 4 KiB pages, which exceeds the TLB capacity of most processors. Using 2 MB huge pages reduces the number of TLB entries to 256, which fits. The operating system must support huge pages, and the application must allocate the bitmap in a huge-page-backed region. This is a deployment concern rather than a format concern, but it can make a measurable difference for large-scale intersections.

## Integration with Query Engines and Real-World Workloads

Roaring bitmaps are not a standalone data structure; they are a component in a query engine. The way they are integrated determines whether their performance advantages are realized. The first integration point is the posting list abstraction. A query engine typically has an interface for posting lists with methods like `iterator()`, `intersect(other)`, `union(other)`, and `cardinality()`. Roaring implements this interface, but the engine must be aware of the container structure to exploit it. For example, the engine can ask for the container type distribution to decide whether to use a bitmap-based or array-based join strategy. It can also use the cardinality of each container to estimate the selectivity of a term in a specific document ID range, which is useful for query planning.

The second integration point is caching. Roaring bitmaps are immutable once frozen, so they can be cached in memory without locks. A query engine can maintain an LRU cache of bitmaps for frequently accessed terms. The cache key is the term, and the value is a frozen bitmap. When a query needs a posting list, it checks the cache first. If the bitmap is not cached, it is loaded from disk or computed from the index. The frozen format is memory-mappable, so the cache can be backed by the page cache, which allows the operating system to evict pages under memory pressure. This is how systems like Lucene and Druid manage large posting lists: they memory-map the bitmap files and let the OS handle residency.

The third integration point is distributed query execution. In a sharded system, each shard has its own bitmap for a term. A query that spans shards must union the bitmaps from each shard, or intersect them with a global filter. Roaring's portable serialization format is designed for this: it is compact, self-contained, and can be shipped over the network. The receiving shard can merge the bitmaps without knowing the internal layout of the sender. The merge is a container-wise union, which is efficient because it only touches containers that exist in either input. If the shards are partitioned by document ID range, the bitmaps may have disjoint container keys, in which case the union is a simple concatenation of the top-level indexes. This is a significant advantage over dense bitmaps, which would require a full 512 MB transfer per term.

The fourth integration point is workload adaptation. The container type distribution changes as the data changes. A term that was rare becomes common, and its containers convert from arrays to bitmaps. A term that was common becomes rare, and its containers may convert back. A query engine can monitor the distribution and adjust its strategy. For example, if a term's bitmap is mostly array containers, the engine can use a galloping join instead of a bitmap intersection. If it is mostly bitmap containers, the engine can use a SIMD intersection. The monitoring can be done periodically, or it can be triggered by a change in the term's document frequency. The goal is to avoid the pathological cases: an array container with 4095 elements that is intersected with a bitmap container using a linear merge, or a bitmap container with 4097 elements that is intersected with an array using a bit test. The thresholds are chosen to make these cases rare, but they are not impossible, and monitoring catches them.

Real-world workloads vary in how well they fit Roaring's assumptions. Text search on a web-scale corpus produces posting lists that are highly skewed: a few terms have millions of documents, and most have a few dozen. The large posting lists are dense in some document ID ranges and sparse in others, which is exactly the case Roaring handles well. Analytics workloads on fact tables produce bitmaps for low-cardinality columns, which are often run-length encoded and benefit from run containers. Time-series workloads produce bitmaps for time ranges, which are contiguous and also benefit from run containers. The worst case is a workload with uniformly random document IDs and moderate cardinality, where every container is an array with a few thousand elements and the per-container overhead is paid without the density benefit. This is rare in practice because document IDs are usually assigned in a way that clusters related documents, but it can happen with hashed IDs or with synthetic data.

The engineering lesson is that Roaring is not a universal replacement for sorted arrays or dense bitmaps. It is a format that adapts to local density, and its performance depends on the data having some structure in the high bits. When that structure exists, it is dramatically better than any single-representation format. When it does not, it degrades to a sorted array with extra overhead. Knowing which regime you are in is the first step to using it effectively.
