## The wall is a proof obligation, not a hardware limit

Consider three loops that a modern optimizing compiler will refuse to parallelize:

```c
/* 1. Indirect scatter */
for (int i = 0; i < n; i++)
    hist[key[i]]++;

/* 2. Recurrence through a pointer chain */
for (node *p = head; p != NULL; p = p->next)
    p->weight = f(p->weight);

/* 3. Graph relaxation */
for (int i = 0; i < m; i++)
    dist[to[i]] = min(dist[to[i]], dist[from[i]] + w[i]);
```

Each of these is *probably* parallel. In the first, the keys are usually distinct; in the second, the list is usually long enough that the work per node dominates the traversal; in the third, most edges usually relax nothing. But "usually" is not a proof, and the compiler needs a proof.

The reason is the memory model. To parallelize a loop, a compiler must show that no iteration writes a location that another iteration reads or writes, or that the ordering of such accesses does not affect the result. For arrays indexed by affine functions of the loop variable, this is decidable and often easy. For `key[i]`, `p->next`, or `to[i]`, the indices are data-dependent, and the compiler's only sound answer is "unknown". The standard escape hatch is a *may-alias* analysis, and may-alias analyses are conservative by construction: they must be sound for every input, so they must report "may alias" whenever they cannot prove otherwise. The result is a large class of loops that are embarrassingly parallel in practice and strictly sequential in theory.

There are three conventional responses. The first is to give up and serialize. The second is to ask the programmer to assert independence — an OpenMP `parallel for` with a promise, an explicit reduction clause, or an atomic. The third is to run the loop in parallel anyway and *check at runtime* whether the assumption held, undoing the work if it did not. That third response is **thread-level speculation** (TLS), and it is the subject of this article.

TLS is one of the more interesting corners of parallel computing because it is a pure engineering trade: it converts a static proof obligation into a dynamic check plus a recovery mechanism, and then bets that the check almost never fires. Whether that bet is worth taking depends on the workload, the cost of the check, and the cost of recovery — and the history of the idea is largely a history of those three numbers refusing to line up.

## The speculation contract: versioning, detection, recovery

It helps to state precisely what a speculative parallel execution must guarantee. Let the original program be a sequence of operations in program order. Partition that sequence into contiguous *speculative tasks* T₀, T₁, …, Tₖ. We want to execute the tasks on multiple cores and still produce exactly the result that the sequential execution would have produced — not merely *some* sequentially consistent result, but the result of *that* order. This is stricter than what a transactional memory system must guarantee, and the strictness matters: TLS is not allowed to reorder independent operations in a way that is observable, because the programmer never asked for transactions in the first place. The contract is invisible, so it must be exact.

To honor that contract, a TLS implementation needs three things:

**Versioning.** Speculative writes must not be visible to the outside world, and must be reversible. Either the write goes to a private buffer and reads are redirected to it (*lazy* versioning), or the write goes to memory in place and an undo record is kept so the old value can be restored (*eager* versioning). Versioning is what makes a squash possible at all.

**Violation detection.** The implementation must detect when one task has read a location that a later task writes, or when two tasks write the same location, in a way that would have changed the sequential outcome. Detection requires tracking read sets and write sets — or approximating them.

**Commit and squash.** Tasks must become visible in program order. If a task is found to have violated a dependence, it and all tasks after it must be discarded and re-executed from the point of the violation.

The word "speculative" is doing real work here. A task is speculative because its inputs are not yet known to be final. When T₂ reads a location that T₁ might later write, T₂ is reading a value that may be stale. TLS does not prevent that; it detects it and throws the work away.

This is the same machinery that transactional memory uses, and the resemblance is not a coincidence — both are optimistic concurrency control applied to a different unit of work. But the failure modes are different in a way that shapes the entire design space. In an STM, a transaction is a region the programmer deliberately marked, typically small, with a bounded read set and a bounded write set, and conflicts are expected under contention. In TLS, a task is an arbitrary slice of sequential code chosen by a compiler or a runtime, with a read set and write set that can be arbitrarily large and that grow over the task's lifetime. A speculative task that walks a linked list may touch thousands of cache lines; a speculative task that runs a query may touch millions. The cost of tracking those sets, and the cost of discarding them when the bet fails, is what makes TLS hard.

There is a second asymmetry. In STM, the programmer's intent is atomicity, and a conflict is a signal that the program is contended. In TLS, the programmer's intent is *nothing at all* — the code was written sequentially, and speculation is an implementation detail. A TLS system that aborts frequently is not just slow; it is slow on code the programmer believes is already correct and has no way to fix, because the fix would be to restructure the algorithm, which is exactly the work TLS was supposed to avoid.

## Where the check lives, and when it fires

TLS designs differ along two axes that determine almost everything else about their cost: *where the versioning and detection machinery lives*, and *when detection happens*.

### Hardware versus software

In **hardware TLS**, the processor provides speculative state directly. The canonical designs are the mid-1990s research machines: the Multiscalar processor (Sohi and colleagues), Hydra (Olukotun and colleagues), and the Trace Processors (Rotenberg and colleagues). They differ in how tasks are formed and how state is versioned, but they share a shape. A sequential program is partitioned into tasks — by the compiler, or by hardware following a control-flow trace. Each task is assigned to a processing element. Each element executes with its own versioned view of memory, usually implemented by adding a speculative bit and a task identifier to each cache line. A dependence predictor or an address comparison detects violations. Tasks commit in order.

The appeal of hardware TLS is that the checks are nearly free: the versioning bits ride along in the cache tags, and the address comparisons happen in the same cycle as the cache lookup. The cost is silicon area, design complexity, and — critically — the fact that the mechanism must be designed before anyone knows which workloads will use it. The research machines of that era were built to demonstrate feasibility, and they did; they were not built to be shipped.

In **software TLS**, the compiler and runtime provide the machinery. The compiler inserts checkpointing code, instruments memory accesses or arranges for them to be trapped, and emits validation checks; the runtime maintains versioned data structures and a task scheduler. The POSH compiler framework is the standard reference point for this approach. Software TLS is portable and can be tuned, but it pays a per-access cost that hardware does not. Instrumenting every load and store in a loop can double or triple its instruction count, which means the speculation must buy back more than a factor of two in parallelism just to break even.

Hybrid designs try to split the difference: hardware support for conflict detection or versioning, software for scheduling and task formation. These are attractive in principle and awkward in practice, because they require an ISA extension that must be justified by workloads nobody has written yet.

### Eager versus lazy, on both axes

The second axis is timing, and it applies independently to versioning and to detection. The four combinations have sharply different cost profiles:

| Versioning | Detection | Commit cost | Squash cost | Per-access cost |
| --- | --- | --- | --- | --- |
| Eager (in place, undo log) | Eager (check on access) | Low — discard the log | High — replay the undo log | High — check every access |
| Eager | Lazy (check at commit) | Low | High | Low |
| Lazy (buffered writes) | Eager | High — copy buffer back | Low — drop the buffer | High |
| Lazy | Lazy | High | Low | Low |

The table is a simplification — real systems mix strategies per access type, and read-set tracking is usually cheaper than write-set tracking — but the shape of the trade is right. Eager versioning makes reads cheap and recovery expensive, because the old values must be restored in the right order. Lazy versioning makes recovery cheap and reads expensive, because every read must first check the buffer. Eager detection fails fast and wastes little work; lazy detection batches checks and wastes more work but pays less per access.

The choice is not arbitrary. It depends on the expected violation rate and on the ratio of reads to writes. A workload where violations are rare and read sets are huge — a graph traversal that mostly reads — favors lazy detection. A workload where violations are common and tasks are short favors eager detection, because aborting early is cheaper than aborting late.

Two details deserve emphasis before we go further. First, commit order is not an implementation detail. TLS commits tasks in program order, which means a task that finishes early must wait for its predecessors. That wait is a serialization point, and it caps the speedup at roughly the ratio of the slowest task to the average task — the classic straggler problem, made worse by the fact that task boundaries are chosen by a compiler that cannot see the runtime distribution of work. Second, the read set is the expensive thing to track. Write sets are naturally bounded by the code's store instructions, and a system can often track them at cache-line granularity with a few bits per line. Read sets are bounded by nothing at all: any load can touch any address, and the set of addresses a task has read must be remembered until the task commits, because a later task might write one of them.

## Dependence prediction: guessing which accesses matter

TLS detection is exact, but exactness is expensive. The read set of a task can be huge, and checking every load against every in-flight write set is quadratic in the worst case. Dependence prediction is the escape hatch: instead of checking every access, predict which accesses are likely to conflict and check only those. The predictor is trained on the program's history, and it is allowed to be wrong — but only in the direction of *more* checking, never less. A predictor that says *no conflict* must be backed by a mechanism that would catch the conflict anyway; otherwise the system is unsound. In practice, this means prediction is used to *skip* checks only when the underlying representation can prove no conflict, or to *prioritize* checks when the representation is approximate.

The simplest predictor is a **last-writer table**. For each memory location (or cache line), the hardware records the task that last wrote it. When a task loads from that location, it checks whether the writer is a predecessor that has not yet committed. If so, the load is a potential violation. If the writer is the task itself or an already-committed task, the load is safe. This is exact for the locations it tracks, but the table is finite; misses must be handled conservatively. The table is essentially a cache of dependence information, and its hit rate determines how much of the read set can be ignored.

A more aggressive approach is **signature-based detection**. Each task maintains a Bloom filter of the addresses it has written and a Bloom filter of the addresses it has read. When a task commits, its write signature is compared against the read signatures of its successors. A Bloom filter can answer *definitely not present* with certainty, so if the comparison says no overlap, the system can skip a detailed check. If it says *maybe*, the system falls back to exact comparison. The false-positive rate is tunable via the filter size, and the cost is a few bits per address plus the hash computation. For tasks with thousands of accesses, signatures can reduce detection from O(n²) to O(n) with a small constant, at the price of occasional unnecessary squashes.

**Value prediction** is a different kind of bet. Instead of predicting *whether* a dependence exists, it predicts the *value* that a dependent load will produce. If the prediction is correct, the load can proceed without waiting for the producer, breaking the dependence chain entirely. If the prediction is wrong, the task must roll back. Value prediction is most attractive for recurrences like `p->weight = f(p->weight)` or `dist[to[i]] = min(...)`, where the values often follow a pattern. But the accuracy required is brutal: a 99% accurate predictor still mispredicts once every hundred loads, and each misprediction can cost hundreds of cycles. For a recurrence with a long dependence chain, the misprediction rate compounds, and the expected cost quickly exceeds the benefit. This is why value prediction has remained a research topic rather than a mainstream technique.

The deeper issue is that dependence prediction is a **second-order speculation**. TLS already bets that the sequential code is parallel; dependence prediction bets that the conflict detector can be approximated. Each layer adds a failure mode. A mispredicted dependence does not just waste work; it can cause a cascade of squashes that interact with the scheduler, the cache, and the commit order. The predictor must therefore be evaluated not by its accuracy alone, but by the *cost-weighted* accuracy: a false positive that causes a squash of a long task is far more expensive than a false positive that causes an extra address comparison. Good predictors are conservative in the direction of cheap checks and aggressive only where the payoff is large.

## The anatomy of a rollback

When a violation is detected, the system must undo the speculative work of the violating task and all tasks that depend on it. The mechanics vary, but the steps are universal. First, the violating task is identified. Second, its speculative state is invalidated: buffered writes are dropped, or undo records are replayed. Third, all successor tasks in the commit order are squashed, even if they did not themselves conflict, because their inputs may have been derived from the invalidated state. Fourth, the squashed tasks are re-executed from the point of the violation, often with a narrower speculation window or a serialized fallback.

The direct cost of this process is the work that must be redone. If a violation occurs in task T_i, and there are k tasks in flight after it, the wasted work is the sum of the work already done by T_i through T_{i+k}. In the worst case, that is the entire speculative window. This is why rollback cost scales with the *width* of speculation, not just the frequency of violations. A system that speculates 64 tasks ahead pays 64 times more for a violation in the first task than a system that speculates one task ahead. The width is chosen to hide latency and keep cores busy, so there is a direct tension: wider speculation means more parallelism but more expensive rollbacks.

The indirect costs are often larger. A squash invalidates the cache lines that the speculative tasks have touched, or at least marks them as unusable. The re-execution then has to warm the cache again, paying the same misses twice. The scheduler must refill the pipeline, which may involve waking threads, redistributing work, and updating bookkeeping structures. If the violation is detected late — at commit time rather than at access time — the system may have already committed some successors, forcing a more complex partial rollback. And if the violation triggers a cascade of further violations, the system can enter an **abort storm**, where the overhead of rollback dominates the useful work and throughput collapses.

Abort storms are the TLS equivalent of thrashing in virtual memory. They are not a theoretical concern; they are the reason many TLS prototypes were never productized. Once the violation rate crosses a threshold, the system spends more time recovering than executing, and the parallel version becomes slower than the sequential one. The threshold depends on the task size and the rollback cost, but it is often surprisingly low. If a task takes 10,000 cycles and a rollback costs 5,000 cycles, a 10% violation rate means the expected overhead is 500 cycles per task, or 5% — manageable. But if the rollback cost includes cache misses and scheduler delays, it can easily exceed the task time. The only robust defense is **feedback control**: monitor the abort rate and reduce the speculation width when it rises. Some systems serialize after a few consecutive aborts; others dynamically merge tasks to reduce the number of speculative boundaries. The controller must be conservative, because the cost of a wrong decision is asymmetric: too little speculation leaves cores idle, but too much speculation can make the program arbitrarily slow.

## Task formation and the granularity problem

The choice of task boundaries is the TLS equivalent of choosing a block size in a parallel algorithm, with one crucial difference: the boundaries are chosen *before* the runtime knows the conflict pattern. A compiler can slice a loop into iterations, basic blocks, or traces. A runtime can steal work at function boundaries. Each choice implies a different read set, write set, and rollback cost. Small tasks are cheap to roll back and offer fine-grained load balancing, but they pay the versioning and detection overhead more often. Large tasks amortize the overhead and reduce the number of commit-order stalls, but they waste more work on a squash and can leave cores idle if the tasks are unbalanced.

The optimal granularity is a function of the violation rate, the core count, and the variance in task execution time. If violations are rare, large tasks are better. If violations are common, small tasks limit the damage. If task times are highly variable, small tasks help with load balancing but increase the chance that a straggler blocks commit. There is no single answer, which is why adaptive schemes are attractive. A runtime can start with large tasks, measure the abort rate, and split tasks when aborts occur. This is essentially a control loop over granularity, and it must balance the cost of re-partitioning against the benefit of a better fit.

Task formation also determines the **commit window**. TLS commits in program order, so a task that finishes early cannot commit until all its predecessors have committed. The set of tasks that have executed but not committed is the commit window. If the window is full, no new tasks can be started, even if cores are idle. The window size is limited by the versioning resources: in hardware, the store buffer or checkpoint storage; in software, the memory allocated for undo logs or buffered writes. A small window limits lookahead and caps parallelism. A large window increases the cost of a rollback, because more tasks must be squashed. The commit window is therefore the central resource constraint of any TLS design, and it is the reason why TLS systems are often described in terms of *how many tasks can be in flight* rather than *how many cores are available*.

The straggler problem is a natural consequence. If one task takes much longer than the others, it holds the commit window open, and all successors wait. The cores that finished early are idle, and the speculation width shrinks. This is exactly the same problem that in-order commit creates in superscalar processors, and the solutions are similar: predict which tasks are likely to be slow, schedule them first, or allow out-of-order commit for independent tasks. Out-of-order commit is difficult in TLS because it requires proving that the committing task does not depend on any uncommitted predecessor. Some systems approximate this with dependence prediction; others simply accept the straggler cost and try to form tasks with uniform work.

## The economics of rollback: a simple model

It is worth putting numbers on the tension. Suppose a sequential program is divided into N tasks, each with execution time t. The tasks are executed on P cores with a speculation window of W tasks. Assume a violation occurs in a task with probability p, independently per task, and that a violation in task i discards all tasks from i to i+W-1 that have not yet committed. The expected wasted work per violation is roughly W/2 tasks. The expected total work is N t (1 + p W / 2). The parallel execution time is at least the total work divided by P, plus the commit-order stalls. The speedup is therefore approximately:

S ≈ P / (1 + p W / 2)

This is a simplified model, but it captures the essential trade. If p = 0.01 and W = 32, the denominator is 1.16, so the speedup is capped at P / 1.16. If p = 0.05 and W = 32, the denominator is 1.8, and the speedup is capped at P / 1.8. For P = 8, that is 4.4×. If p = 0.1, the denominator is 2.6, and the speedup is 3.1×. The model ignores the overhead of detection and versioning, which adds another multiplicative factor. The conclusion is stark: to get near-linear speedup, the violation rate must be very low, or the speculation window must be very small. But a small window limits the number of tasks that can execute in parallel, which limits speedup directly. The system is squeezed from both sides.

The model also shows why **rollback cost is not just wasted work**. The term p W / 2 is the expected number of tasks discarded per task executed. If W is large, even a tiny p is expensive. A violation rate of 0.1% with a window of 1000 tasks gives a denominator of 1.5, which is already a 33% overhead. This is why real systems keep the window small — often 4 to 16 tasks — and why they invest heavily in dependence prediction to reduce p. It is also why TLS is most successful on loops where the conflict rate is not just low but *predictably* low, because the predictor can avoid the checks that would otherwise be needed to discover the low rate.

There is one more economic factor: the cost of the fallback. When a violation occurs, the system can either re-execute the task speculatively again or fall back to sequential execution for that region. Re-execution is cheaper if the violation was a transient conflict; sequential fallback is cheaper if the conflict is likely to recur. The choice depends on the history of the task. A task that has already aborted once is more likely to abort again, because the conflict is probably structural. A good runtime remembers this and uses a **backoff** strategy: after the first abort, retry with a smaller window; after the second, serialize the region. This prevents abort storms and bounds the worst-case slowdown. The cost is complexity, but it is the price of making a speculative system robust enough to be used without programmer intervention.

## The compiler's burden: outlining, checkpointing, and the semantics of rollback

A TLS system does not appear from nowhere. Someone — usually a compiler — must decide where tasks begin and end, what state must be saved, and how to restore it. This is the least glamorous part of speculative parallelization and the part most likely to sink a deployment. The hardware or runtime can provide the mechanisms for versioning and detection, but the compiler must produce code that uses them correctly, and "correctly" here means preserving the exact sequential semantics of a program that was never written with speculation in mind.

The first job is **task outlining**. Given a loop, the compiler must extract the loop body into a separate function that can be executed on a different core. This is straightforward for simple loops but becomes delicate when the body contains `break`, `continue`, `return`, or `goto` out of the loop. Each of these control-flow edges must be handled: a `break` in a speculative task cannot simply jump out, because the task's writes may later be squashed. The compiler must either transform the loop to eliminate the early exit (e.g., by predicating the remaining iterations) or insert a check that forces the task to commit before taking the branch. The latter is a serialization point, and it can destroy the parallelism the compiler was trying to create.

The second job is **checkpointing**. Before a speculative task begins, the compiler must save enough state to restore the program if the task is squashed. This includes not just the task's own local variables but any live values that the task might overwrite. In a register-based machine, this means spilling live registers to a checkpoint area; in a stack-based runtime, it means saving the stack frame. The checkpoint must be cheap, because it is paid on every task, not just on aborts. A checkpoint that costs hundreds of cycles per task can easily outweigh the benefit of speculation for short tasks. This is one reason why TLS works best on loops with substantial bodies: the checkpoint cost is amortized over more work.

The third job is **handling side effects**. A speculative task must not perform I/O, acquire locks, or call functions with observable side effects until it is guaranteed to commit. The compiler must either prove that a call is pure or insert a runtime check that defers the effect. This is difficult in languages with dynamic dispatch or reflection, where the compiler cannot know what a function does. Some TLS systems simply forbid speculation across calls, which limits the loops that can be parallelized. Others use a "speculative call" mechanism that records the call and replays it at commit time, but this requires the callee to be idempotent or to have a transactional interface. In practice, most software TLS systems restrict speculation to loops whose bodies are self-contained and free of calls, which excludes a large fraction of real code.

The fourth job is **validation code**. The compiler must insert checks that compare the task's read set against the write sets of its predecessors, and it must generate the commit and squash paths. The validation code must be correct with respect to the memory model: if the original program used atomics or volatile accesses, the speculative version must preserve their ordering. This is a subtle point. Speculation reorders memory operations, and a naive implementation can violate the ordering guarantees that the programmer relied on. The compiler must either treat such accesses as barriers that prevent speculation or use a memory model that is strong enough to make the reordering invisible. The latter is hard, because most weak memory models do not provide the necessary guarantees.

Finally, the compiler must **optimize the speculative code**. The whole point of TLS is to make the parallel version faster than the sequential one, and that requires the usual optimizations — inlining, loop unrolling, strength reduction — to be applied to the outlined task. But these optimizations interact with speculation. Inlining a function into a speculative task increases the task's read set and may introduce side effects; unrolling a loop increases the task size and the rollback cost. The compiler must balance the desire for efficient code against the cost of speculation. This is a global optimization problem, and it is one that no production compiler has fully solved.

## Speculation meets the memory hierarchy: coherence, false sharing, and NUMA

TLS detection is usually described in terms of addresses, but real hardware operates on cache lines. This mismatch is a source of both efficiency and error. Tracking at cache-line granularity is cheap: a few bits per line can record which task last wrote it. But it is imprecise. Two tasks that write to different words in the same cache line are treated as conflicting, even though their accesses are independent. This is **false sharing**, and in a speculative system it causes unnecessary aborts. A loop that updates an array of counters, where each counter is a word and several counters share a cache line, can abort constantly even though the logical accesses are disjoint. The fix is to track at a finer granularity — word or byte level — but that increases the storage and the comparison cost. Some hardware TLS designs use a hybrid: cache-line granularity for the common case, with a fallback to word-level tracking when a conflict is detected. The fallback is triggered rarely, so the average cost stays low.

False sharing is not just a performance issue; it can also cause **livelock**. If two tasks repeatedly conflict on the same cache line and both are squashed, they may re-execute and conflict again indefinitely. A backoff mechanism is needed: after a squash, a task should wait or change its access pattern. But in TLS, the tasks are generated by the compiler, and they cannot easily change their access pattern. The only recourse is to serialize the conflicting tasks, which reduces parallelism. This is why TLS systems often include a **conflict resolution** policy that decides which task to squash and which to let proceed. The policy can be as simple as "squash the later task" or as complex as "squash the task with the smaller read set." The choice affects both the abort rate and the fairness of the system.

The memory hierarchy also affects **commit**. When a task commits, its speculative writes must become visible to other cores. In a cache-coherent system, this means invalidating or updating the copies of the cache lines in other caches. If the task wrote many lines, the commit can trigger a storm of coherence traffic, which slows down the very cores that are trying to execute other tasks. This is another reason to keep tasks small and their write sets bounded. A task that writes a large array can saturate the interconnect at commit time, turning a parallel speedup into a memory-bandwidth bottleneck.

On **NUMA** machines, the problem is worse. A speculative task may be scheduled on a core that is far from the memory it accesses. The read set tracking must account for the latency of remote accesses, and the rollback must restore state that may be replicated across nodes. If the task is squashed, the remote cache lines it fetched are wasted, and the re-execution must fetch them again. The cost of a rollback on a NUMA machine can be several times higher than on a uniform-memory machine, which shifts the economics against speculation. Some systems try to place tasks near their data, but the compiler rarely knows the data layout at runtime. The result is that TLS on NUMA systems requires careful tuning of task placement and memory affinity, and it is often easier to use explicit parallelism than to rely on speculation.

## When speculation fails: conflict-prone workloads and the limits of optimism

The economic model in the previous section assumed that violations occur independently with probability p. In reality, p is not a constant. It depends on the input data, the task boundaries, and the state of the caches. Some workloads have a conflict rate that is effectively zero, and TLS gives near-linear speedup. Others have a conflict rate that is high and unpredictable, and TLS is worse than sequential execution. Understanding which is which is essential to using TLS effectively.

The worst case is a loop where every iteration writes the same location. A histogram with a single hot key, a reduction into a scalar, or a loop that updates a global counter will conflict on every iteration. No amount of speculation can help, because the dependence is real and frequent. The compiler cannot know this statically, and the runtime cannot fix it without serializing the loop. In such cases, the only solution is to recognize the pattern and fall back to a different algorithm — for example, using per-thread accumulators and a final reduction. But that is a programmer's job, not a compiler's, and it defeats the purpose of automatic speculation.

Between the trivial and the impossible lies a large middle ground. Consider the histogram example from the beginning: `hist[key[i]]++`. If the keys are uniformly distributed, conflicts are rare, and TLS works well. If the keys are skewed — say, 90% of the keys are the same value — then conflicts are frequent, and TLS aborts constantly. The same code can be parallel-friendly for one input and parallel-hostile for another. A static compiler cannot distinguish these cases, and a runtime predictor can only react after the fact. This is the fundamental problem with speculation: it is a bet on the input distribution, and the input distribution is not known until runtime.

Graph algorithms are another difficult case. A breadth-first search or a shortest-path computation may have low conflict rates on sparse graphs but high conflict rates on dense graphs or graphs with high-degree vertices. The read set of a task that explores a vertex's neighbors can be large, and the write set can overlap with other tasks' read sets. The result is frequent aborts, and the cost of rollback is high because the tasks are long. Some systems use **speculative work-stealing** to break large tasks into smaller ones, but this adds overhead and can still conflict. In practice, graph algorithms are often parallelized with explicit synchronization or with algorithmic transformations (e.g., delta-stepping) rather than with TLS.

The lesson is that TLS is not a general-purpose solution. It is a technique that works when the conflict rate is low and the task size is large enough to amortize overhead. It fails when conflicts are frequent, when tasks are small, or when the rollback cost is high. The economics are unforgiving: a 10% conflict rate with a window of 32 tasks can cut speedup in half. To be useful, TLS must either reduce the conflict rate (through better task formation or dependence prediction) or reduce the cost of rollback (through cheaper versioning or faster recovery). Neither is easy, and both require a deep understanding of the workload.

## Speculation in managed runtimes and dynamic languages

The original TLS research targeted C and Fortran, where the compiler has a full view of the program and the memory model is relatively simple. But the most interesting modern applications of speculation are in managed runtimes: Java, JavaScript, Python, and their JIT compilers. These environments offer both opportunities and challenges. The opportunity is that the JIT compiler has runtime profile information, which can guide speculation. The challenge is that the language semantics are more complex, with dynamic types, garbage collection, and side effects that are not visible to the compiler.

Consider JavaScript. A loop that manipulates an array is a prime candidate for speculative parallelization, but the language allows the array to be modified by a getter or a proxy, and the loop body may call a function that has side effects. A JIT compiler can speculate that the array is a plain array and that the function is pure, but if the speculation fails, it must deoptimize and fall back to the interpreter. This is a form of speculation that is already used in JavaScript engines for optimization, but using it for parallelization adds a new dimension: the speculation must be validated across threads, and the rollback must undo the effects of multiple tasks. The machinery is similar to TLS, but the granularity is different: instead of speculating on memory dependences, the engine speculates on types and object shapes.

Python is even harder, because of the global interpreter lock (GIL). The GIL serializes all Python bytecode execution, so speculation cannot run in parallel without removing the GIL. Some research systems have tried to use TLS to parallelize Python loops by speculating that the GIL is not needed for certain operations, but the complexity is high and the performance gains are limited. The problem is that Python's dynamic features make it difficult to prove that a loop is free of side effects, and the cost of rollback is high because the interpreter state is complex. As a result, speculative parallelization in Python remains a research topic.

Managed runtimes do offer one advantage: **garbage collection** can be used to reclaim speculative state. If a task is squashed, its allocated objects can be discarded without explicit undo logs, because the GC will collect them. This simplifies versioning for heap-allocated data, though it does not help with writes to existing objects. Some systems use a **transactional heap** to manage speculative writes, but this adds overhead to every allocation and every write. The trade-off is similar to software TLS in C: the runtime support is flexible but costly.

The most promising direction in managed runtimes is **speculative parallelization of streams and pipelines**. A data-parallel loop that processes a stream of records can be speculatively parallelized if the records are independent. The JIT compiler can profile the loop and decide whether to speculate. If conflicts occur, the runtime can fall back to sequential execution for a while and then retry. This is essentially the same feedback control used in hardware TLS, but implemented in software. It is likely that the first widespread use of TLS will be in managed runtimes, where the compiler and runtime can cooperate and where the programmer does not need to rewrite code.

## Correctness beyond conflict detection: the simulation argument

A TLS system that detects conflicts and rolls back is not automatically correct. It must be shown that the speculative execution is observationally equivalent to the sequential execution for every possible input. This is a simulation argument: the speculative machine must simulate the sequential machine, step by step, with the same observable effects in the same order. Commit order handles the order of memory writes, but memory is not the only observable state. Registers, exceptions, signals, file descriptors, locks, atomics, and thread-local storage all have sequential semantics that speculation can disturb.

The first subtlety is that read-set tracking must include loads that influence control flow and address computation, not just loads whose values are stored. Suppose a task reads a flag, branches on it, and conditionally writes a location. If a later task writes the flag, the first task's branch was based on a stale value, and its write may be wrong. A detector that tracks only the addresses written by the first task will miss this. The read of the flag must be in the read set. This is why read sets are large: every load is potentially a dependence, because every load can affect the future path of the task. Hardware detectors that track only data addresses are incomplete unless the compiler inserts explicit checks for control dependences.

The second subtlety is that validation must be transitive. If task T1 writes x, T2 reads x and writes y, and T3 reads y, then a violation in T1 can invalidate T3 even if T3 never touched x. Commit order and the squash of all successors handle this, but only if the successor set is defined by program order, not by data flow. TLS squashes all tasks after the violating task, which is conservative but correct. A more precise system could squash only dependent tasks, but computing the dependence graph at runtime is expensive. The conservative approach is one reason rollback cost scales with window width.

The third subtlety is that speculation must not change the behavior of undefined or implementation-defined operations. In C, signed overflow, strict aliasing violations, and out-of-bounds accesses are undefined; a compiler may assume they do not happen. A speculative execution that exposes such an operation may produce a different result than the sequential execution, which is allowed by the standard but surprising to the programmer. In managed languages, the runtime must preserve exceptions, finalizers, and synchronization. A speculative task that throws an exception cannot simply propagate it until commit, because the exception may be caught by a handler outside the task. The compiler must either prevent speculation across exception boundaries or checkpoint enough state to replay the exception in order.

The fourth subtlety is memory model conformance. TLS reorders memory operations across tasks, and the validation must ensure that the reordering is invisible under the language's memory model. On a weak model, a speculative read may see a value that no sequential execution could see, even if the read set is later validated. The system needs fences or dependencies to prevent such reads from affecting committed state. This is the same problem that transactional memory faces, but TLS has less freedom: the programmer did not ask for transactions, so the system cannot require transactional annotations or stronger fences. The result is that TLS is easiest to implement on a strong memory model, or on programs that do not rely on weak-model behaviors.

## The runtime's half: scheduling, feedback, and resource management

The compiler chooses task boundaries, but the runtime decides when tasks run, how many are in flight, and what to do when a violation occurs. This half of the system is often underestimated. A TLS runtime is a scheduler with a correctness obligation: it must not start a task whose inputs are not yet available, and it must not commit a task out of order. It must also manage the resources that versioning and detection consume: buffers, tables, signatures, and checkpoint storage.

The first runtime responsibility is thread management. Speculative tasks are usually assigned to a fixed pool of worker threads. If the pool is too small, cores idle; if it is too large, context switches and cache pressure increase. The runtime must also handle preemption. If the OS preempts a speculative thread, the commit window stalls, and all successors wait. This is worse than a normal preemption because the stalled task may hold versioning resources. Some systems pin speculative threads to cores and disable preemption for short windows, but this is not portable and can harm other workloads. The scheduler must also avoid placing speculative tasks on cores that are far from their data, especially on NUMA machines.

The second responsibility is feedback control. The runtime must measure the abort rate, the commit stall time, and the useful work per task. When aborts rise, it can reduce the speculation window, merge tasks, or serialize the region. When aborts fall, it can widen the window and split tasks. The controller must be stable: a naive policy that reacts to every abort can oscillate between wide and narrow speculation. A common approach is exponential backoff: after a squash, wait for a period proportional to the number of recent aborts before retrying. Another approach is to maintain a per-task confidence score: tasks that have aborted before are less likely to be speculated. The cost of the controller must be small relative to the task, or it becomes the bottleneck.

The third responsibility is resource accounting. The commit window is bounded by the versioning storage. If the storage is full, no new tasks can start, even if cores are idle. The runtime must therefore decide which tasks to start based on the available storage, not just on the number of cores. This is a form of admission control. It must also reclaim storage when tasks commit or squash. In software TLS, reclamation may involve garbage collection or free-list management; in hardware TLS, it involves clearing speculative bits and invalidating buffers. The latency of reclamation affects how quickly the window can be refilled.

The fourth responsibility is interaction with the operating system. Speculative tasks should not block on I/O, acquire locks, or wait on condition variables. If they do, the commit window can deadlock: a task holding a lock cannot commit because a predecessor is waiting for the lock, and the predecessor cannot commit because the task holds the lock. The compiler can prevent speculation across blocking operations, but the runtime must also detect and handle cases where a task blocks unexpectedly. One solution is to abort the blocking task and re-execute it non-speculatively. Another is to use non-blocking versions of system calls. Neither is free.

## Metrics that matter: beyond speedup

TLS research often reports speedup on a handful of benchmarks, but speedup alone hides the mechanisms that make or break the system. A useful evaluation should report at least four families of metrics: work efficiency, detection cost, rollback cost, and resource utilization.

Work efficiency measures how much of the executed work is useful. The simplest metric is the speculation efficiency: committed task work divided by total task work, including squashed work. A system with 90% efficiency wastes one in ten cycles. The rollback amplification is the average number of tasks squashed per violation, which is roughly half the speculation window under uniform violation. The abort rate is the number of violations per committed task. These three numbers together predict the overhead better than speedup alone.

Detection cost measures the price of finding violations. It includes the per-access instrumentation overhead, the size of the read and write sets, the number of signature comparisons, and the false-positive rate of approximate detectors. A detector with a high false-positive rate may have a low abort rate but still squash useful work. The detection cost should be reported per access and per task, because it scales differently with task size.

Rollback cost measures the price of recovery. It includes the time to invalidate speculative state, the time to re-execute squashed tasks, and the cache misses caused by re-execution. A useful metric is the rollback latency: the number of cycles from violation detection to the restart of the squashed task. This latency is often dominated by scheduler and cache effects, not by the undo log itself. Reporting only the undo-log size understates the cost.

Resource utilization measures how well the system uses the commit window and the cores. The window occupancy is the average number of tasks in flight divided by the window size. A low occupancy means the system is not extracting the available parallelism. The commit stall time is the time tasks spend waiting for predecessors to commit. The straggler ratio is the maximum task time divided by the average task time. These metrics explain why a system with a low abort rate can still fail to scale.

Finally, evaluation should include an oracle bound. Given perfect knowledge of the conflict pattern, what is the best possible task partition and schedule? The gap between the TLS system and the oracle is the cost of speculation itself. Without this bound, it is impossible to tell whether a poor result is due to a bad design or an inherently difficult workload. The oracle is not implementable, but it is computable offline for small inputs, and it provides a target.

## Speculation, security, and power: the new constraints

Two constraints that were secondary in the 1990s are now central: security and power. Speculative execution leaves traces. Even if a task is squashed, its loads may have brought cache lines into a private cache, and its stores may have updated coherence state. An attacker who can observe cache timing or coherence traffic may learn information about data that was never committed. This is the same class of vulnerability as microarchitectural speculation attacks, but at a coarser granularity. A TLS system that speculates on untrusted input may therefore need to flush caches or invalidate state on squash, which increases rollback cost. Alternatively, it may restrict speculation to code that does not handle secrets, which limits its applicability.

Power is the other constraint. Speculative work consumes energy even when it is discarded. On a power-limited chip, the metric is not time but energy per committed operation. A system that achieves speedup by burning more energy may be unacceptable in mobile or datacenter settings. The energy cost of rollback includes the re-execution, the cache refills, and the coherence traffic. It can be several times the energy of the original work. This shifts the economics: a violation rate that is tolerable for performance may be intolerable for energy. Future TLS designs must therefore be evaluated under a power budget, not just a time budget.

## Open problems in task formation under uncertainty

Task formation remains the least solved part of TLS. The compiler must choose boundaries without knowing the conflict pattern, the input distribution, or the runtime state of the machine. A static choice is either too conservative or too aggressive. A dynamic choice requires runtime information that is expensive to collect and may arrive too late. The ideal system would form tasks adaptively, using profile data and feedback from the conflict detector, while keeping the re-partitioning cost low. It would also account for the memory hierarchy, the core count, and the power budget. No current system does all of this.

A related problem is how to compose TLS with other parallelization techniques. A loop may be partially parallel: some iterations are independent, some are not. A TLS system could speculate on the independent parts and serialize the rest, but deciding which is which at runtime is difficult. It could also combine TLS with explicit parallelism, using speculation to handle the irregular parts of a program and explicit synchronization for the regular parts. This hybrid approach is promising but requires a programming model that lets the compiler and runtime cooperate. Without such a model, TLS remains a specialized technique, useful for a narrow class of loops and a narrow class of machines.

## Rollback is a scheduling event, not just wasted work

When a violation is detected, the system does not merely redo instructions. It changes the state of the scheduler. Workers that were executing successors become idle or are redirected. The commit window contracts. Versioning resources are released, but the release may be asynchronous. The core that was running the violating task may wait for a checkpoint to be restored, and the cores running successors may discard partially filled pipelines. A rollback is therefore a global perturbation, not a local one. It can be modeled as a latency spike: useful work stops for L cycles, then resumes. If rollbacks cluster, the spikes overlap and the system enters a low-throughput mode. This is why abort rate alone is not predictive. Two systems with the same abort rate can behave very differently if one squashes one task per violation and the other squashes eight. The cost is in the fan-out.

Rollback-aware scheduling tries to keep fan-out low. One technique is to delay commit of a task until its successors have reached a safe point, so a violation in the task does not invalidate work that has already committed. Another is to checkpoint at coarse boundaries and re-execute from the last checkpoint rather than from the violating task. Both trade parallelism for recovery cost. The scheduler can also prioritize tasks with small read sets, because they are cheaper to validate and less likely to be invalidated. This is a heuristic, but it changes the distribution of rollback costs. A task with a small read set is not necessarily independent, but it is easier to prove independent, and that is often enough to keep the window moving.

## The verification gap

Conflict detection is not a correctness proof. It is a filter that catches the violations the implementation knows how to name. A TLS system can pass every benchmark and still be wrong on an input that triggers a control dependence through an address, an exception caught outside the speculative region, or a weak-memory reordering that the detector does not model. The gap between no conflict detected and observationally equivalent to sequential execution is the verification gap. Closing it requires either a formal argument that the detector covers every observable effect, or a testing strategy that explores the space of interleavings and inputs. The former is hard because the memory model and the language semantics are large. The latter is hard because the space is enormous and the failures are rare.

Differential testing helps: run the speculative version and the sequential version on the same input and compare results. But a mismatch may take millions of runs to appear, and the input that triggers it may be adversarial. Model checking can prove the absence of certain classes of bugs in a small model, but scaling to real programs is difficult. The practical result is that TLS implementations often rely on a small set of invariants—commit order, read-set inclusion, and conservative fallback—and accept that the remaining gap is covered by testing. This is not unique to TLS; it is the normal state of concurrent systems. But it explains why TLS has been slow to ship: the mechanism is easy to describe, and the correctness argument is not.

## Speculating on the tail

Most economic models assume uniform tasks and independent violations. Real programs have heavy tails: a few iterations dominate the runtime, and a few addresses dominate the conflicts. Speculating on the tail is attractive because overlapping one long task with many short ones can hide the straggler. But the tail is also where rollback is most expensive. A long task has a large read set, a large write set, and a large checkpoint. If it is squashed, the wasted work is large. This creates a paradox: the tasks most worth speculating are the ones most costly to roll back.

One response is to split long tasks early, but the system does not know which tasks are long until they run. Profile-guided task formation can mark likely-long iterations, but profiles drift with input. Another response is to make long tasks commit incrementally, so a violation only invalidates the suffix. Incremental commit requires finer-grained versioning and a way to prove that the committed prefix is independent of later work. That is essentially a transactional memory with nested transactions, and it inherits the same overheads. A third response is to serialize the tail and speculate only the body, which sacrifices the largest potential win. None of these is a complete answer. The tail remains the place where the economics of rollback are least forgiving.

## The cost of proving no conflict

The only way to avoid rollback entirely is to prove independence. Static analysis can prove it for affine accesses; runtime checks can prove it for a specific execution. A TLS system that validates a read set at commit is proving independence for that execution, but only after the fact. If the proof fails, rollback. This is optimistic concurrency control in its purest form. The cost of the proof is the cost of tracking: every load must be recorded, every store must be versioned, and every commit must compare sets. There is a spectrum. No tracking means no proof and no parallelism. Full tracking means a proof but high overhead. The interesting designs find a middle: track only what is likely to matter, use signatures to summarize, use hardware bits to make the common case cheap. But no middle removes the need for a fallback. The fallback is the price of optimism, and it is paid in the currency of rollback.
