## The question a local collector never has to ask

A local garbage collector answers a deceptively simple question: which objects can the program still reach? It answers it with a trick that evaporates the moment a program spans more than one address space — it stops the world (or arranges barriers that approximate stopping it), enumerates every root, and walks the object graph from those roots. Reachability is a global property of a single, directly addressable heap, and the collector is inside that heap.

Distributed garbage collection must answer the same question with none of those affordances. There is no global heap to walk. There is no pause that freezes every mutator simultaneously without coordinating every process in the system. And there is a category of reference that has no analogue in a local collector: a reference that exists *in flight*, sitting in a socket buffer or a message queue, not owned by any heap, not visible to any root scan, but perfectly capable of resurrecting an object the instant it is delivered.

This is not an exotic problem confined to the distributed-object systems of the late 1980s and 1990s. Every system that hands out a handle to state it owns — a session identifier, a remote actor reference, a lease on a shard, a cached document token, a task handle in a cluster scheduler — is running some variant of this protocol, whether it knows it or not. Sometimes the protocol is a full reference-counting scheme. More often it is a timer and a prayer. Understanding why the full schemes are hard, and precisely what the timer-and-a-prayer approach gives up, is the point of this article.

## Why this problem exists at all

Start with a concrete shape. A routing service holds handles to session objects owned by a session service. A worker process holds a cached handle to a document owned by a storage node. A coordinator holds references to task descriptors that workers own. In each case, the *owner* is the process that allocated the object and is responsible for freeing it. The owner is also, crucially, not the process that knows whether the object is still reachable.

Local collection rests on four assumptions, and distribution breaks all four.

**The root set is observable at a single instant.** A local collector reads stacks, registers, and globals because it shares an address space with the mutator. In a distributed system, each process can scan only itself. Asking another process to scan is a round trip, and the answer is stale the moment it is produced — the remote process may have acquired a new reference while the reply was in flight. Getting a genuinely consistent view requires a distributed snapshot protocol, which is exactly the Chandy–Lamport machinery: it is correct, it captures channel contents, and it costs a full coordination round over the entire system.

**Pointers exist or they do not.** In a local heap, a reference is a value in memory. In a distributed system, a reference occupies a third state between existence and non-existence: *sent but not yet delivered*. A reference-counting protocol that decrements on send and increments on receive has a window in which the count is wrong. A protocol that increments before sending has a window in which the count is conservative, which is safe but leaks if the message never arrives. There is no third option that eliminates the window; there is only a choice about which side of it you fail on.

**The graph is inspectable.** A local collector can read an object's fields to find outgoing pointers. A remote object's fields are behind an RPC boundary. You cannot scan a foreign heap without cooperation, and that cooperation costs messages proportional to the size of the graph you are scanning.

**Failure is local and recoverable.** A local collector assumes the mutator will eventually resume. A distributed collector must assume that a process may crash and take with it every piece of knowledge it held: which references it had received, which it had sent, and which of its own objects were reachable from elsewhere. When a process dies, the question "did it hold the last reference to this object?" may become unanswerable, because the only witness is gone.

That last point is where the difficulty concentrates. The distributed collector's core problem is deciding when the *last* reference to an object has been dropped, and "last" is a negative existential claim: no further reference will ever arrive. Proving a negative in an asynchronous system with unreliable failure detection is the same shape of problem as distributed consensus, and it has the same character of answer — you cannot do it safely without an assumption you have to buy with time, coordination, or knowledge of who holds references.

## Safety, completeness, and the trade you cannot avoid

Two properties define the correctness envelope of any reclamation scheme.

**Safety** means the collector never reclaims an object that is still reachable. Violating safety produces a dangling reference: a use-after-free across a network, which in the best case is an error and in the worst case is a security boundary collapse. If a session handle is reclaimed while a client still holds it, and the underlying storage slot is reused, that client may end up reading another tenant's data.

**Completeness** (sometimes called reclamation liveness) means every object that becomes unreachable is eventually reclaimed. Violating completeness produces a space leak: memory, storage, or file descriptors that are never returned. Leaks are expensive but bounded in their damage; they degrade capacity rather than correctness.

Local collectors generally achieve both. Distributed collectors generally cannot, without additional assumptions. The intuition is worth stating plainly, because it explains almost every design decision in this space.

To be *complete*, a collector must eventually conclude "no further reference will arrive." That conclusion requires one of three things: (a) knowledge of the complete set of processes that could hold a reference, plus the ability to query all of them and know that none is slow rather than crashed; (b) a bound on message delivery time, so that waiting long enough is a valid proof of absence; or (c) exact reference tracking that detects the transition to zero. Option (c) is the reference-counting family, and it fails precisely when a message is lost or a process dies mid-protocol, because the decrement that would have driven the count to zero never happens — or worse, the increment never happens and the count hits zero early.

To be *safe*, a collector must never conclude absence prematurely. That means it must be conservative in the presence of ambiguity: if a reference might be in flight, treat it as live. Conservatism is safe by construction and incomplete by construction.

So the design space is not "which algorithm is correct." It is "which failure mode do you prefer, and what assumption are you willing to buy to shrink the other one?" The industry's answer for three decades has been to buy time: leases, time-to-live values, and lifecycle policies that convert an unsolvable reachability question into a solvable scheduling question. We will get to why that trade is usually the right one, and what it costs.

## The four families of designs

It helps to sort the space before diving into mechanisms. Almost every practical scheme is a member of one of four families.

**Reference counting.** Each object carries a count of the references that point at it, maintained by the processes that hold them. When the count reaches zero, the owner reclaims the object. Variants — weighted reference counting, indirect reference counting, backpointer-based schemes — differ in how they avoid the round trip that a naive increment/decrement protocol would require on every reference transfer. The family is safe under message loss and process failure, and it leaks. It also cannot, by itself, collect cycles.

**Tracing.** A distributed mark-and-sweep that computes reachability globally, usually by piggybacking on some form of snapshot or timestamp ordering. This family is complete and coordination-heavy, and its cost scales with graph size rather than with the rate of reference churn. Historically important; rarely deployed in systems with high mutation rates.

**Hybrid and cycle-collecting schemes.** Trial deletion, distributed cycle collection, and generational schemes that use a periodic trace to correct the leaks that reference counting accumulates. These buy back completeness at the price of an occasional global or semi-global pass.

**Policy-based reclamation.** No reachability analysis at all. The application or the platform declares that a resource is live for a bounded duration — a lease, a TTL, a session timeout, a lifecycle rule — and reclamation happens when the timer fires. Correctness rests on an assumption about time or on the application's discipline in renewing and releasing. This is what most production systems ship.

The rest of this article examines each family in turn: the mechanisms, the exact point at which each fails, and the engineering consequences of that failure. But first it is worth pinning down a system model, because the informal statements above ("safe under message loss") only mean something relative to assumptions about channels, ordering, and failure.

## A model to reason against

The distributed GC literature is full of algorithms that are correct under one set of assumptions and broken under another, and most of the confusion in reading it comes from losing track of which assumptions are in force. A minimal model is enough to keep the analysis honest.

The system consists of processes with local heaps, each capable of allocating objects and holding references. A **reference** is either local (a pointer within one heap) or remote (an object identifier plus enough addressing information to reach the owner). A **root** is a reference held directly by a process's computation — a variable, a stack slot, a table entry. An object is **reachable** if there is a path of references from some root to it, where the path may cross process boundaries.

Channels carry messages between processes. The interesting assumptions to vary are ordering (FIFO per channel versus arbitrary), reliability (no loss versus silent loss and retransmission), and delay (unbounded versus bounded). Failures are crash-stop: a process either runs correctly or stops permanently. Failure detection is unreliable — a process that has not responded may be crashed or merely slow, and no local observation distinguishes the two.

Against this model, two invariants characterize a correct collector. First, **no premature reclamation**: an object with at least one reachable reference, including a reference currently in flight, is never reclaimed. Second, **eventual reclamation**: an object with no reachable references and no in-flight references is eventually reclaimed.

What makes the second invariant hard is the phrase "in flight." A reference in a channel is not in any heap and not in any root set, so no amount of local scanning will find it. Any algorithm that decides reclamation by looking only at local state must therefore either (i) delay its decision until it can be sure no message is in flight, or (ii) arrange that in-flight references are always accompanied by a compensating piece of state somewhere, so that the sum of local state across the system is never prematurely zero. The first approach is the lease. The second is reference counting, and the whole family's design energy goes into making that compensating state survive loss and failure.

With the model fixed, we can start on the mechanisms — beginning with the simplest reference-counting protocol, the two messages it needs per reference transfer, and the reason that cost drove the field toward weighted and indirect schemes that keep counts consistent without a round trip on every pointer copy.

## The naive count and the two-message tax

The simplest distributed reference-counting protocol is almost embarrassingly direct. The owner of an object maintains an integer count. When a process acquires a remote reference to that object, it sends an `increment` message to the owner. When it drops the reference, it sends a `decrement` message. The owner reclaims the object when the count reaches zero. If every message is delivered exactly once, in order, and no process crashes, this works. It is safe, because the count never falls to zero while a reference exists. It is complete, because every dropped reference eventually produces a decrement, and the count eventually reaches zero.

The problem is that the qualifier at the start of that paragraph is doing all the work. Real networks lose messages, duplicate them, reorder them, and partition processes from one another. Processes crash. The moment any of those events occurs, the naive protocol splits into two distinct failure modes. A lost `increment` makes the owner undercount, which can drive the count to zero while a live reference exists: a safety violation, and the dangerous kind. A lost `decrement` makes the owner overcount, which means the object is never reclaimed: a completeness violation, and the merely expensive kind. A crashed process that held references produces the same leak, because its decrements will never arrive. A duplicate `decrement`, by contrast, can produce premature reclamation, because the owner subtracts twice for a reference that was dropped once.

The protocol therefore needs more than counts. It needs identity. Each reference must be named, so that the owner can recognize a duplicate increment or decrement and ignore it. That means the owner keeps a record of which reference identifiers have already been applied, which is itself state that must be reclaimed. It needs ordering, or at least a way to distinguish a decrement that arrives before its matching increment from a decrement that belongs to a reference the owner never learned about. It needs acknowledgments, because a sender cannot know whether its message was applied. And it needs a handoff protocol, because transferring a reference from one process to another is not a single event. If A sends a reference to B and drops its own copy immediately, the owner may see the count fall to zero before B's increment arrives. If A waits for B to confirm receipt before dropping its copy, the transfer now costs a round trip through B and possibly a round trip to the owner. The count is correct, but the latency of moving a reference has become a distributed transaction.

This is the two-message tax in its purest form: every remote reference acquisition and every remote reference release requires a message to the owner, and safe transfer requires additional coordination to close the window between the two. For an object with a small number of long-lived references, the tax is irrelevant. For an object referenced by thousands of processes, or for a workload that copies and drops remote handles at high rates, the owner becomes a serialization point. Every message must be ordered with respect to every other message for that object, and the owner's count is the single point of truth. The design energy of the reference-counting family is largely an attempt to avoid paying that tax on every pointer copy while preserving the safety property that made the count attractive in the first place.

## Weighted reference counting: splitting the count instead of calling home

Weighted reference counting removes the increment message entirely. Instead of a single integer count, an object has a total weight. Each reference to the object carries a portion of that weight. When a process wants to create a new reference from an existing one, it splits its weight into two parts: it keeps one part and gives the other to the new reference. No message to the owner is needed. The owner's total weight is unchanged, because the sum of all reference weights plus the owner's own weight always equals the original total. When a reference is dropped, the holder sends its weight to the owner in a `decrement` message. The owner subtracts that weight. When the owner's weight reaches zero, the object is reclaimed.

The elegance is real. Acquiring a reference is a local operation. Copying a reference is a local operation. The only communication is on release, and even then only when a reference is dropped. If a process holds many references to the same object, it can merge their weights locally and send a single decrement when the last one goes away. The owner is no longer involved in the common case of reference creation.

The costs are equally real. Weight is a finite quantity. If references are split repeatedly, the individual weights become smaller and smaller. Eventually a reference may have weight one, and it cannot be split further without creating a zero-weight reference that the owner will never see. Practical schemes therefore include a replenishment step: when a reference's weight falls below a threshold, its holder asks the owner for more weight. The owner can increase the total weight and send a new portion to the holder, which restores the ability to split. Replenishment reintroduces the round trip, but it happens rarely rather than on every copy. The protocol trades a per-copy message for an occasional per-reference-list message.

The failure modes also change shape. A lost decrement still leaks, because the owner never subtracts the weight. A duplicate decrement is still unsafe, because the owner subtracts twice and may reclaim early. A crashed process leaks all the weight it held, because no one else knows those weights exist. Weighted reference counting is safe under message loss in the sense that lost messages do not cause premature reclamation, but it is not complete. It is also vulnerable to a subtler problem: if a reference message itself is lost, the weight it carried is gone from the system. The sender may have already split its weight and given the new portion to a message that never arrives. The owner's total weight still includes that portion, so the object cannot be reclaimed. The leak is silent and permanent unless some other mechanism detects it.

Weighted reference counting is most attractive when references are copied frequently but released relatively rarely, and when the system can tolerate leaks better than it can tolerate premature reclamation. It is a classic example of buying completeness with time and eventual reconciliation, but it does not solve the cycle problem, and it does not remove the need for a failure-recovery story.

## Indirect reference counting: amortizing the conversation

Indirect reference counting attacks the same tax from a different angle. Instead of counting individual references, the owner counts reference holders. Each process that holds one or more references to a remote object maintains a local reference list for that object. The owner keeps a count of how many such lists exist. When a process acquires its first reference to the object, it sends an `increment` to the owner. Subsequent local copies are free: they are just entries in the local list. When the process drops its last reference, it sends a `decrement` to the owner. The owner reclaims the object when the count of reference lists reaches zero.

This amortizes the conversation beautifully. A process that holds a thousand references to the same object pays one increment and one decrement, not two thousand messages. The owner's count is small and stable. The local list can be as large as the process needs, and it can be managed with local data structures. For workloads where a small number of processes hold many references to the same objects, indirect reference counting is a substantial improvement over the naive scheme.

The failure modes are inherited from the naive scheme, but they are concentrated at the boundaries of the list. A lost increment means the owner does not know the process holds a reference, so the owner may reclaim the object while the process is still using it: a safety violation. A lost decrement means the owner thinks the process still holds a reference, so the object leaks: a completeness violation. A crashed process leaks every list it held, because the owner has no way to know the process is gone. The protocol still needs reliable delivery, acknowledgments, and a way to clean up after crashes. It also needs a way to handle the case where a process holds a reference list but has not yet sent the increment, or has sent the decrement but the message is still in flight. Those windows are smaller than in the naive scheme, but they are not zero.

Indirect reference counting becomes more interesting when combined with backpointers. If the owner maintains a list of the processes that hold reference lists, it can contact them during a cycle-collection pass. That list is a form of reverse edge, and it is exactly what a distributed cycle collector needs to trace the graph. The cost is that the owner must maintain and update the backpointer list, which reintroduces messages on list creation and destruction. The trade is between the cost of maintaining backpointers continuously and the cost of discovering them on demand during collection.

## Cycles: the leak that reference counting cannot see

Reference counting, in all its variants, has a blind spot: cycles. Consider two processes, A and B. A owns object X, and B owns object Y. A holds a remote reference to Y, and B holds a remote reference to X. There is no root anywhere in the system pointing to either object. The counts are one for each: X is referenced by B, Y is referenced by A. Neither count will ever reach zero, because each object is kept alive by the other. The objects are unreachable, but the collector cannot prove it. This is the same cycle problem that local reference counting has, but distribution makes it worse in three ways.

First, no single process can see the cycle. A sees its reference to Y and its ownership of X. B sees its reference to X and its ownership of Y. The cycle spans two address spaces, and neither process has enough information to conclude that the pair is garbage. Second, the cycle can be arbitrarily long and can cross many processes. A cycle of length ten involves ten owners, each holding one piece of the puzzle. Third, the cycle can be created and destroyed concurrently with the collection attempt. A reference that completes the cycle may be in flight while a collector is examining the graph, so any snapshot taken by one process is stale with respect to another.

Local cycle collectors solve the problem with trial deletion. A candidate object is marked gray, and its outgoing references are recursively decremented. If the trial decrements drive some object's count to zero, that object is part of a cycle that is now provably unreachable. If the counts do not reach zero, the trial is rolled back and the objects are restored. The algorithm is local because the graph is local. In a distributed system, the recursion crosses process boundaries. Each step of the trial requires a message to the owner of the next object, and each message introduces delay and the possibility of concurrent mutation. A reference added during the trial can make a live object appear unreachable, which is a safety violation. A reference removed during the trial can make a garbage object appear live, which is a completeness violation. To avoid these errors, the collector must either freeze the relevant part of the graph, take a consistent distributed snapshot, or use a protocol that can tolerate concurrent mutation and retry.

Distributed cycle collection therefore tends to be expensive and rare. Some systems run a global mark-and-sweep when memory pressure crosses a threshold, using a snapshot protocol to capture a consistent graph. Others use a distributed trial-deletion variant that coordinates marks and decrements across processes, with retries when conflicts are detected. Others simply do not collect cycles at all. They rely on the application to avoid them, or on leases and timeouts to break them. A session object that references a client object, and a client object that references the session, can be broken by expiring the session after a period of inactivity. The cycle is not collected; it is dissolved by policy.

This is an important engineering lesson. Reference counting gives you safe, incremental reclamation for acyclic graphs. Cycles force you into either global coordination or policy-based expiration. Most production systems choose the latter, not because it is theoretically elegant, but because it is predictable and cheap.

## The lease compromise: turning reachability into a timer

A lease is a time-bounded grant of access. The owner of a resource issues a lease to a holder, valid until a specified expiration time. The holder may use the resource until that time, but it must renew the lease before expiration if it wants to continue. If the holder does not renew, the owner reclaims the resource after the expiration time. The lease is a soft-state protocol: the grant persists only as long as it is refreshed.

The appeal of leases is that they convert an unsolvable reachability question into a solvable scheduling question. The owner does not need to know whether the holder still has a reference. It only needs to know whether the lease has expired. If it has, the owner reclaims. If the holder is still alive and still needs the resource, it renews. If the holder crashes, the lease expires and the resource is reclaimed. If the network partitions, the lease expires and the resource is reclaimed. The owner does not need to track individual references, maintain counts, or coordinate with other processes. It needs a clock and a renewal protocol.

The safety of a lease depends on time assumptions. If the owner's clock and the holder's clock disagree, the owner may believe the lease has expired while the holder still believes it is valid. If the renewal message is delayed beyond the expiration time, the owner may reclaim while the holder is still using the resource. To be safe, the lease duration must be longer than the maximum expected clock skew plus the maximum expected message delay plus the time needed to process a renewal. In practice, systems choose a duration that is long enough to make these violations rare, and they add fencing tokens to make the consequences of a violation recoverable.

A fencing token is a monotonically increasing number attached to each lease. When the owner reclaims a resource and issues a new lease, the new lease has a higher token than any previous lease. If the old holder attempts to use the resource after its lease has expired, its token is stale, and the resource can reject the operation. The old holder may still believe it has access, but it cannot corrupt the resource. This is the standard pattern in distributed storage and lock services: leases provide liveness and failure detection, while fencing tokens provide safety against stale holders. The combination does not eliminate the time assumption; it makes the failure mode an error for the stale holder rather than a data corruption for everyone else.

Leases are not a garbage-collection algorithm in the classical sense. They do not compute reachability. They do not maintain reference counts. They do not collect cycles. They are a policy that says: if you want to keep a resource, prove it by renewing. If you cannot renew, you lose it. This is the compromise that most production systems actually ship, because it is simple, it scales, and it degrades in a way that operators can reason about. A leaked resource is reclaimed after a timeout. A crashed process does not leave permanent garbage. A partition does not require a global consensus round to resolve. The cost is that a live holder can lose access if it is slow or partitioned, and the system must be designed to handle that loss gracefully. That is a trade most distributed systems are willing to make.

## The lease is a failure detector with a timeout

A lease is often described as a time-bounded grant, but it is more precise to call it a failure detector with a timeout. The owner does not directly observe whether the holder is alive. It observes only whether a renewal arrived before the deadline. That observation is a suspicion, not a proof. The holder may be alive, healthy, and actively using the resource while its renewal is delayed by a congested link, a garbage-collection pause in the holder's own runtime, or a scheduling hiccup. The owner cannot distinguish that case from a crash. The lease protocol resolves the ambiguity by choosing a side: after the timeout, it treats the holder as gone. This is exactly the behavior of an eventually perfect failure detector, and it inherits the same impossibility results. In an asynchronous system, no timeout can be both safe and live for all executions. The lease duration is the parameter that selects which executions are handled correctly.

The practical consequence is that lease durations are not arbitrary. They must be longer than the worst-case renewal latency the system is willing to tolerate, plus the maximum clock skew between owner and holder, plus a safety margin for processing and queueing. If the duration is too short, healthy holders lose resources under load, producing spurious revocations and retry storms. If it is too long, crashed holders hold resources for longer, reducing the effective capacity of the system and delaying recovery. Operators tune this parameter the way they tune TCP retransmission timers: by measuring the distribution of renewal latencies and choosing a percentile that balances false suspicion against detection delay.

Fencing tokens change the nature of the trade. Without fencing, a false suspicion is a correctness violation: the owner reclaims the resource, issues it to a new holder, and the old holder may still write to it. With fencing, the old holder's writes are rejected because its token is stale. The false suspicion becomes a liveness violation for the old holder, which must detect the rejection and reacquire the resource. This is a much better failure mode. It means the system can use aggressive timeouts without risking data corruption, as long as every resource mutation carries a token and the resource validates it. The token is a monotonically increasing sequence number, often combined with an epoch that changes when the owner restarts. The combination ensures that a reference from a previous incarnation of the owner cannot be confused with a reference to the current one.

## Tombstones, epochs, and the resurrection problem

Reclaiming an object is not the end of its identity. A delayed message may still be in flight, carrying a reference to the object. If the owner has already freed the object and reused its identifier for a new object, the delayed reference will resolve to the wrong object. This is the distributed analogue of a dangling pointer that happens to point at a valid but unrelated allocation. The consequences can be severe: a client that held a reference to a deleted session may suddenly find itself operating on another tenant's session.

There are three standard defenses. The first is to never reuse identifiers. A 128-bit identifier space makes accidental reuse vanishingly unlikely, and a monotonic counter per owner makes it impossible until the counter wraps. The second is to attach an epoch or generation number to every reference. The epoch changes when the owner restarts or when the identifier space is recycled. A reference with an old epoch is rejected even if the identifier matches. The third is to keep a tombstone: a record that the identifier was reclaimed, retained for a period at least as long as the maximum message lifetime. When a delayed reference arrives, the tombstone causes it to be rejected rather than resolved.

Tombstones are themselves garbage. They consume memory and must eventually be reclaimed. The lease compromise reappears here: the tombstone can be retained for a bounded time, after which the system assumes no message referencing the old object can still be in flight. That assumption is only valid if the network has a bounded message lifetime, or if the system is willing to accept the risk of a very old message arriving after the tombstone is gone. In practice, systems combine a long tombstone lifetime with a large identifier space and epochs, so that the probability of a harmful resurrection is negligible even if the tombstone is eventually discarded.

The resurrection problem is a reminder that distributed GC is not only about counting references. It is about maintaining a consistent mapping from identifiers to objects across time, despite message delay, process restart, and identifier reuse. A collector that ignores this mapping may be safe in the sense of not freeing live objects, but it can still be unsafe in the sense of resolving a stale reference to the wrong object. The two safety properties are distinct: no premature reclamation of a live object, and no misresolution of a stale reference. Leases and epochs address the second; reference counts address the first.

## Hybrid designs: fast path, slow path, and the backstop

No single mechanism dominates. Production systems tend to combine them, assigning each mechanism to the failure mode it handles best.

The fast path is usually local. A process that holds a reference to a remote object keeps it in a local table. Acquiring and releasing the reference is a local operation. The remote owner is not involved. This is the indirect reference counting model, and it is cheap because it amortizes communication over many local operations.

The slow path is the lease renewal. The holder periodically renews its claim to the remote object. The renewal is a heartbeat that says 'I am still here, and I still care about this object.' If the renewal stops, the owner eventually reclaims. This path handles crashes, partitions, and lost messages. It does not need to know how many references the holder has, only that the holder is still interested. The lease is per holder, not per reference, which keeps the message rate proportional to the number of holders rather than the number of references.

The backstop is a periodic reconciliation or cycle collection. Even with leases, a system can leak if a holder renews a lease for an object it no longer uses, or if a cycle of leases keeps itself alive. A backstop can be a mark-and-sweep over the lease graph, run rarely, or a policy that caps the number of leases per holder, or an application-level audit that detects and breaks cycles. The backstop does not need to be fast or frequent. It exists to catch the cases that the fast path and slow path miss.

This layered design is common in distributed storage, cluster schedulers, and service meshes. The fast path provides low latency and high throughput. The slow path provides failure recovery. The backstop provides a safety net against bugs and pathological cases. The layers are not redundant; they cover different time scales and different failure modes. The engineering challenge is making them compose without conflicting. For example, a lease renewal that arrives after the owner has reclaimed the object must be rejected cleanly, and the holder must be able to reacquire the object if it still needs it. That requires the holder to treat a failed renewal as a signal to revalidate its state, not as a fatal error.

## The application knows more than the collector

A general-purpose distributed collector must treat every object as opaque. It cannot know that a session is idle, that a cache entry is stale, or that a lock is held by a process that is making progress. It can only observe references and messages. That limitation is fundamental: the collector does not have access to the application's semantics.

The application, by contrast, often knows exactly when a resource is no longer useful. A session service knows that a session with no activity for thirty minutes can be closed. A cache knows that an entry with a TTL has expired. A lock service knows that a lock held for longer than the maximum transaction duration is suspicious. In each case, the application can define a policy that is more accurate than any reachability analysis, because it is based on the meaning of the resource rather than on the pattern of references to it.

This is why policy-based reclamation is not a failure of distributed GC theory. It is a recognition that reachability is a proxy for usefulness, and that in many distributed systems the proxy is weak. An object can be reachable but useless, or unreachable but still needed by a client that has not yet learned it is gone. The application's policy can capture the former; the latter is handled by leases and fencing. The combination gives the system a reclamation strategy that is both safe and complete with respect to the application's definition of garbage, rather than with respect to an abstract graph property.

The practical implication is that distributed GC should be designed alongside the application's lifecycle model, not as a separate layer. The collector should expose primitives — leases, epochs, fencing tokens, explicit release — that the application can use to express its own reclamation policy. The collector should not try to infer reachability from message patterns alone, because that inference is expensive and often wrong. The best distributed collectors are those that make the application's policy easy to implement correctly, and that provide a backstop for the cases where the policy fails.

## The protocol state machine of a single reference

A reference is not a boolean. In any scheme that survives loss and failure, it passes through a sequence of states, and the collector's job is to ensure that no state transition creates a window in which reclamation is unsafe. The states are worth naming because most bugs in distributed GC are bugs in the transitions, not in the counting arithmetic.

- **Local**: the holder has a valid handle and believes it can use the object. The owner may or may not know the holder exists, depending on the scheme.
- **Announced**: the holder has sent an increment or lease request, but the owner has not acknowledged it. The reference is usable by the holder, but the owner may not yet count it.
- **Acknowledged**: the owner has recorded the reference or lease. The holder may proceed with confidence.
- **Renewing**: the lease is approaching expiration and the holder has sent a renewal. The owner may still reclaim if the renewal is late.
- **Expired**: the owner's timer has fired. The owner may reclaim the object even if the holder has not released it.
- **Revoked**: the owner has explicitly invalidated the reference, usually after reclaiming the object or detecting a stale epoch.
- **Tombstoned**: the object is gone, but the identifier is retained to reject delayed messages.

The transitions between these states are where the interesting engineering lives. Consider the move from Local to Announced. If the holder uses the object before the announcement is acknowledged, and the owner reclaims concurrently, the holder is using a freed object. To prevent this, the holder must either wait for acknowledgment before using the object, which adds a round trip to every acquisition, or the owner must not reclaim until it is sure no announcement can be in flight. The latter is the lease approach: the owner waits for a timeout before reclaiming, which gives the announcement time to arrive. The former is the reference-counting approach: the holder pays the round trip up front, and in exchange the owner can reclaim immediately when the count reaches zero.

The move from Renewing to Expired is equally delicate. The holder sends a renewal before the deadline, but the message is delayed. The owner's timer fires, and it reclaims. The holder's next operation fails. If the operation is idempotent and carries a fencing token, the failure is clean. If not, the holder may have performed a partial mutation. This is why lease-based systems require operations to be idempotent or transactional, and why fencing tokens are attached to mutations rather than just to reads. The state machine makes the requirement explicit: any transition that can be triggered by a timeout must have a recovery path that the holder can execute without knowing whether the timeout was a false suspicion.

The move from Revoked to Tombstoned is the one that protects against resurrection. A revoked reference may still be in flight. The tombstone ensures that if it arrives, it is rejected. The tombstone must outlive the maximum message lifetime, which is the same quantity that determines the lease duration. This is not a coincidence: both are estimates of how long the system must wait before it can treat silence as absence. The two parameters should be chosen together, because a tombstone that is shorter than the maximum message lifetime is a safety hole, and a lease that is shorter than the maximum renewal latency is a liveness hole.

## The orphan problem: when the owner is the one that dies

All the schemes discussed so far assume that the owner of an object is alive and authoritative. The owner maintains the count, the lease table, or the weight. The holder may crash, and the system recovers by expiring its references. But what happens when the owner crashes? The objects it owned may still be referenced by other processes. Those references now point to an owner that no longer exists. The objects are not garbage in the reachability sense — there are live references to them — but they are unreachable in the practical sense, because no one can service them. They are orphans.

Orphan recovery is a separate problem from reference counting, and it is often neglected. There are three broad strategies.

**Abandonment.** The system declares that objects owned by a crashed process are lost. Remote references to them are invalidated, and holders must reacquire or reconstruct their state. This is simple and safe if the objects are replicable or if the application can tolerate the loss. It is unacceptable for durable state, which is why storage systems replicate the owner's metadata rather than relying on a single owner.

**Reconstruction from references.** If the owner's state can be rebuilt from the references that point to it, then a new owner can take over. This requires that every holder announce its references to a known location, or that the references themselves carry enough information to reconstruct the object. Backpointer lists are a form of this: the owner knows who holds references, and if that list is replicated, a new owner can contact the holders and rebuild the count. The cost is that the backpointer list must be maintained and replicated, which is exactly the overhead that indirect reference counting tries to avoid.

**Lease-based takeover.** If every reference is a lease, then the owner's death is handled by the same timeout that handles holder death. The lease expires, the resource is reclaimed, and a new owner can issue new leases. The old leases are invalid because their epoch is stale. This is the most common approach in production, because it reuses the lease machinery and does not require replicating per-reference state. The cost is that the resource is unavailable for at least one lease period after the owner crashes, and any holder that was using it must revalidate.

The orphan problem exposes a deeper issue: distributed GC is not just about counting references. It is about maintaining an authoritative mapping from object identifiers to owners. If the mapping is lost, the references are useless. If the mapping is replicated, the replication protocol becomes part of the GC protocol, and its consistency requirements must be understood. A system that replicates the owner's count but not the owner's identity can still lose objects. A system that replicates identity but not the count can resurrect objects. The two must be designed together.

## Hot objects and the serialization tax

Reference counting has a scalability problem that is easy to miss in small systems: the owner of an object is a serialization point. Every increment, decrement, lease renewal, and cycle-collection probe for that object must be ordered with respect to every other. If the object is hot — referenced by thousands of processes, or copied and dropped at a high rate — the owner becomes a bottleneck. The network link to the owner becomes a bottleneck. The owner's lock on its count becomes a bottleneck. The system's throughput is limited by the rate at which a single process can process messages about a single object.

There are several ways to attack this. The first is to shard the count. Instead of one count per object, maintain a set of partial counts, each owned by a different process. A holder updates the partial count that is closest to it, and the owner sums the partials when it needs to decide reclamation. Sharding reduces contention but introduces a new problem: the sum of partials can be stale, so the owner may not see a zero count immediately. It must wait for all shards to report, which reintroduces the coordination delay that reference counting was supposed to avoid. Sharding is a trade of latency for throughput.

The second is to batch updates. A holder that acquires and releases many references to the same object can accumulate the net change and send a single message. This is the indirect reference counting idea generalized to time rather than to holder identity. Batching reduces message rate but increases the window in which the count is wrong. The owner must be conservative: it cannot reclaim until it has received all batched updates, or until a timeout has passed. The timeout is, once again, a lease.

The third is to delegate ownership. The original owner transfers the object to a new owner that is closer to the hot set of references. The new owner becomes the serialization point. This is analogous to work stealing or load balancing in a scheduler. It requires a handoff protocol that preserves safety: the old owner must not reclaim while the new owner is taking over, and references that arrive during the handoff must be forwarded. The handoff is a distributed transaction, and it is only worth doing if the object remains hot for long enough to amortize the cost.

The fourth is to avoid counting altogether for hot objects. If an object is known to be long-lived — a configuration object, a shared cache entry, a broadcast channel — the system can declare it immortal and exempt it from reclamation. The application is responsible for eventually removing it. This is a policy decision, not a GC algorithm, but it is often the right one. The collector's job is to reclaim the objects that are not worth tracking individually; hot objects are exactly the ones where tracking is most expensive and least valuable.

## Partition tolerance and the split-brain of reclamation

A network partition is the hardest case for any reclamation scheme. The owner and the holder can still run, but they cannot communicate. The owner's lease timer fires, and it reclaims the object. The holder's lease timer has not fired yet, or the holder has renewed but the renewal is stuck in the partition. The holder continues to use the object. When the partition heals, the system has two conflicting beliefs: the owner believes the object is free, and the holder believes it still holds a valid reference.

Fencing tokens are the standard defense, but they only work if the resource enforces them. If the resource is a block of memory on the owner, the owner can reject the holder's writes because the holder's token is stale. If the resource is a file on a shared storage system, the storage system must validate the token. If the resource is an external side effect — a payment, a message send, an API call — the token must be carried into the side effect and validated there. This is why fencing is often described as a property of the resource, not of the lease. A lease without a fencing mechanism is a timer that can cause data corruption.

Partitions also raise the question of who is allowed to reclaim. If the owner is replicated, and the replicas are partitioned, which replica decides that a lease has expired? If each replica decides independently, they may disagree, and the resource may be reclaimed twice or not at all. The safe answer is to require a quorum for reclamation decisions. A lease is only considered expired if a quorum of replicas agrees that the deadline has passed and no renewal has been observed. This turns reclamation into a consensus problem, with the same latency and availability trade-offs as any other consensus decision. Many systems avoid this by making the owner a single process and accepting its unavailability during a partition. The resource is unavailable until the partition heals, which is safe but not always acceptable.

The split-brain of reclamation is a reminder that distributed GC is not a purely local optimization. It is a distributed agreement problem whenever the resource being reclaimed is unique and its misuse can cause harm. For memory, the harm is limited to the process that misuses a freed pointer. For locks, sessions, and storage, the harm can cross tenants. The design must match the cost of agreement to the cost of violation. If violation is cheap, a timeout is enough. If violation is expensive, a quorum is necessary.

## The cost model: messages per reference per unit time

Choosing a scheme requires a rough cost model. Let R be the rate at which remote references are acquired and released, H be the number of distinct holders per object, and T be the lease period. The naive reference-counting scheme sends 2 messages per acquisition and 2 per release, so its message rate is proportional to R. The indirect scheme sends 2 messages per holder per object, so its rate is proportional to the rate at which holders join and leave, not to the rate at which references are copied. If a holder copies a reference many times, indirect is much cheaper. The weighted scheme sends 1 message per release plus occasional replenishment, so its rate is proportional to the release rate, which is half of R. The lease scheme sends 1 renewal per holder per T, so its rate is proportional to H/T. It does not care about R at all.

This simple model explains why leases dominate. In a system with high reference churn and many holders, the lease message rate can be orders of magnitude lower than the reference-counting rate. The lease does not track individual references, so it is insensitive to the number of copies. It only tracks the existence of the holder. The trade is that the lease cannot reclaim an object while the holder is still alive and renewing, even if the holder has dropped all references to it. The object leaks until the holder stops renewing or explicitly releases it. In practice, holders are expected to release explicitly, and the lease is a backstop for crashes. The message rate is low because the backstop is rare.

The model also shows where reference counting wins. If holders are short-lived and hold exactly one reference, the indirect scheme degenerates to the naive scheme, and the lease scheme pays a renewal per holder per T even if the holder is gone in a fraction of T. If T is large, the lease leaks for a long time. If T is small, the renewal rate is high. Reference counting reclaims immediately when the reference is dropped, which is valuable for objects that are expensive to hold — file descriptors, memory buffers, exclusive locks. The right choice depends on the cost of holding the object versus the cost of tracking it.

## Debugging distributed GC: leaks, dangling references, and the tools that help

Distributed GC bugs are among the hardest to debug because they are timing-dependent, they cross process boundaries, and they often manifest as corruption rather than as a clean error. A dangling reference may be used hours after the object was reclaimed, and the resulting failure may look like an application bug rather than a collector bug. A leak may be invisible until the system runs out of memory, and by then the evidence may be gone. The tools that help are the ones that make the state of the collector observable.

The first tool is a per-object reference ledger. Every increment, decrement, lease grant, renewal, and revocation is recorded with a timestamp, a source, and a sequence number. The ledger does not need to be global; it can be per owner, with enough information to reconstruct the history of a single object. When a leak is suspected, the ledger shows whether the count is stuck because of a lost decrement, a crashed holder, or a cycle. When a dangling reference is suspected, the ledger shows whether the object was reclaimed before or after the reference was acquired.

The second tool is a lease table with expiration times and last renewal times. The table makes it easy to see which holders are renewing and which are not. A holder that is alive but not renewing is a candidate for a bug in the renewal logic. A holder that is renewing but not using the object is a candidate for a leak. The table also exposes the distribution of renewal latencies, which is the input to choosing the lease duration.

The third tool is a tombstone log. When an object is reclaimed, the tombstone records its identifier, epoch, and reclamation time. When a stale reference arrives, the log shows whether the reference was rejected because of a tombstone or because of an epoch mismatch. This distinguishes a resurrection attempt from a simple stale reference.

The fourth tool is distributed tracing that follows a reference from acquisition to release. A trace can show the exact sequence of messages and the state of the owner at each step. Without tracing, a dangling reference is a mystery; with tracing, it is a timeline. The cost of tracing every reference is high, so production systems usually sample. Sampling is enough to catch systematic bugs, which are the ones that matter.

Finally, a fault-injection harness is essential. Distributed GC protocols are designed for message loss, duplication, reordering, and process crashes. If those faults are not injected during testing, the protocol's failure paths are never exercised. A good harness can delay messages, drop them, duplicate them, partition processes, and crash owners at the worst possible moment. The bugs it finds are exactly the ones that would otherwise appear in production at 3 a.m.

## Designing for reclamation from the start

The most reliable way to avoid distributed GC bugs is to design the application so that reclamation is explicit and idempotent. The collector cannot know when a resource is no longer useful, but the application can. The collector's role is to provide the primitives that make the application's knowledge actionable, and to provide a backstop for the cases where the application forgets.

The first pattern is the scoped handle. A handle is valid only within a scope — a request, a transaction, a session. When the scope ends, the handle is released. The release is idempotent, so a duplicate release is harmless. The owner can reclaim the object when all scopes that hold it have ended. This pattern works well with reference counting, because the scope boundary is a natural place to send the decrement. It also works with leases, because the scope can be renewed as long as it is active.

The second pattern is the generation number. Every handle carries the generation of the object it refers to. When the object is reclaimed and reallocated, the generation changes. A handle with an old generation is rejected. This pattern is cheap and effective, and it eliminates the resurrection problem without requiring tombstones to be retained forever. The generation number can be combined with a fencing token: the generation identifies the object incarnation, and the token identifies the lease.

The third pattern is revalidation on lease loss. When a holder fails to renew a lease, it must not assume the object is gone. It must revalidate its state by contacting the owner or a new owner. The revalidation may succeed, in which case the holder gets a new lease, or it may fail, in which case the holder must release its local state and report the loss to the application. The application must be prepared to handle the loss, which means operations must be idempotent or transactional. This is the price of using leases: the application must tolerate temporary unavailability and possible revocation.

The fourth pattern is explicit release. Even with leases, holders should release objects when they are done. The lease is a backstop, not a replacement for release. Explicit release reduces the leak window and makes the system's behavior more predictable. It also gives the owner more accurate information about which objects are in use, which can be used for capacity planning and for detecting cycles.

The fifth pattern is a reclamation audit. Periodically, the system should audit its reclamation state: count the objects that are leased but not used, the holders that are renewing but not releasing, the tombstones that are older than the maximum message lifetime. The audit is a form of garbage collection for the collector itself. It catches the slow leaks that individual protocols miss, and it provides the data needed to tune lease durations and tombstone lifetimes.

## What to measure before choosing a scheme

Before choosing a distributed GC scheme, measure the workload. The measurements that matter are: the distribution of reference lifetimes, the number of holders per object, the rate of reference churn, the cost of holding an object, the cost of a premature reclamation, and the cost of a leak. These measurements determine which family is appropriate. If references are long-lived and holders are few, reference counting is cheap and precise. If references are short-lived and holders are many, leases are cheaper but leak more. If objects are cheap and reclamation is not urgent, a TTL is enough. If objects are expensive and reclamation is urgent, reference counting with explicit release is worth the message overhead. The measurements also determine the lease duration and tombstone lifetime, which are the two parameters that control the safety-completeness trade. A system that does not measure these quantities is guessing, and the guess will be wrong under load.
