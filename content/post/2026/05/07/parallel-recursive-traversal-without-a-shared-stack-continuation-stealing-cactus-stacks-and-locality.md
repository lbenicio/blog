# Parallel Recursive Traversal Without a Shared Stack: Continuation Stealing, Cactus Stacks, and Locality

Recursive traversal is one of the most common shapes in software. A compiler walks an abstract syntax tree. A build system walks a dependency graph. A renderer walks a scene graph. A filesystem tool walks a directory tree. A solver walks a game tree. A graph algorithm explores a reachable component. In each case, the natural serial implementation is a recursive function: inspect a node, decide what to do, recurse into children, and combine results on the way back.

Parallelizing that shape is harder than parallelizing a loop over an array. An array loop has a static iteration space. A recursive traversal has a dynamic call stack. The stack is not just a data structure; it is the program counter's memory. It records where to resume, which local variables are live, and which partial results are waiting to be combined. If two threads share that stack, every push and pop becomes a synchronization point. If each thread has its own stack, the runtime must decide how work moves from one stack to another without losing the context that makes the work meaningful.

This article examines a specific design space: parallel recursive traversal without a shared stack. The goal is not to present a single universal scheduler. The goal is to make the trade-offs explicit. We will look at continuation stealing, work-first and help-first scheduling, cactus stacks, segmented stacks, memory reclamation, locality, termination detection, and the practical costs that decide whether a parallel traversal is faster than its serial counterpart.

The assumptions matter. We assume a shared-memory multicore machine with hardware atomics and a coherent cache hierarchy. We assume tasks are closures or continuations: a function pointer plus captured state. We assume the traversal is irregular enough that a static partition would be poorly balanced. We assume the runtime cannot know the size of a subtree without traversing it. We do not assume that every traversal is pure; some nodes may mutate shared state, allocate memory, or perform I/O. Those cases change the design, and we will call them out.

## The Recursive Traversal Problem as a Task Graph

A serial recursive traversal defines a depth-first order. The order may be semantically important, or it may be an implementation detail. If the order is important, parallelism must preserve it or provide a deterministic merge. If the order is not important, parallelism can reorder freely, but it must still avoid duplicate work and lost work.

Abstractly, a recursive traversal is a directed acyclic graph of tasks. Each task corresponds to one call. A task may spawn child tasks for recursive calls. A task may also have a continuation: the code that runs after its children complete. In a divide-and-conquer traversal, the continuation combines child results. In a search traversal, the continuation may simply return a boolean or update a shared visited set.

The task graph gives two standard measures. Work is the total number of operations if one worker executes every task serially. Span, or critical path, is the longest dependency chain. The maximum speedup from parallelism is bounded by work divided by span. For a balanced binary tree, the span is the height of the tree, so the bound is large. For a degenerate tree, the span is the number of nodes, so parallelism offers little. Real traversals lie between these extremes, and the runtime often cannot know which regime it is in until it starts.

The first design decision is where to store ready tasks. A shared stack is the obvious choice: push children, pop the next task, use a lock or lock-free stack. This preserves depth-first order naturally. It also creates a single point of contention. Every push and pop touches the same cache line. On a machine with dozens of cores, the shared stack becomes the bottleneck even when the traversal has abundant parallelism. Lock-free stacks avoid blocking, but they still serialize on the top-of-stack pointer. They also introduce memory reclamation problems: a thread that pops a node cannot free it until it knows no other thread is still reading it.

The alternative is per-worker stacks or deques. Each worker executes tasks from its own deque. When a worker runs out of work, it steals from another worker. This is the work-stealing model. It reduces contention because most operations are local. The hard part is stealing. A deque is not a simple list of independent tasks; it is a representation of a call stack. Stealing from the middle of a call stack requires either copying the stack, sharing frames, or reconstructing the continuation.

## Work-First and Help-First Scheduling

Two scheduling disciplines dominate work-stealing runtimes: work-first and help-first. They differ in which branch runs immediately and which branch becomes stealable.

In work-first scheduling, when a task spawns a child, the worker pushes the continuation onto its deque and executes the child immediately. The continuation represents the rest of the parent after the child returns. If another worker steals, it steals the continuation. This is continuation stealing. The victim keeps executing the child, so it follows a depth-first path. The thief takes over the parent's remaining work, which may include other children and the combine step. Work-first tends to preserve locality for the victim because the child is usually near the parent in memory. It also keeps the serial execution fast: a single worker never pays the cost of pushing the child and popping it again.

In help-first scheduling, the worker pushes the child onto its deque and continues executing the parent. The child becomes available for stealing. This exposes more parallelism earlier, because children are visible as soon as they are created. It can also create many more tasks. If the traversal has a high branching factor, help-first may fill deques with millions of small tasks, increasing memory pressure and steal overhead. Help-first can be better when the parent has significant work before the child is needed, or when the runtime wants to maximize parallelism at the cost of locality.

The choice is not binary. A runtime can use work-first for some spawns and help-first for others. It can adapt based on deque depth, steal failure rate, or the size of the remaining work. For example, a runtime might use work-first while the deque is shallow and switch to help-first when the deque grows beyond a threshold. The trade-off is complexity: adaptive policies are harder to reason about and tune.

Continuation stealing has a subtle property. The thief steals a continuation, not a child. The continuation may depend on the child's result. If the victim is still executing the child, the thief cannot complete the continuation until the child finishes. In a fork-join model, the parent continuation waits for the child. If the thief takes the parent continuation, it must either wait for the victim or execute other work and later synchronize. This is why continuation stealing is often paired with a join protocol: the thief can continue the parent's other children, but the final combine must wait for all children. The runtime must track dependencies, not just tasks.

## Stack Representation: Cactus Stacks, Segmented Stacks, and Continuation Frames

The central data structure in a shared-stack-free traversal is the representation of the call stack. A naive per-worker stack is easy: each worker has a contiguous stack, and the runtime copies a portion of the stack when stealing. Copying is simple and correct. It is also expensive. If the stack is deep, copying a segment on every steal can dominate the cost of the work being stolen. The copy must include live frames, local variables, and return addresses. It must be consistent: the victim cannot mutate the copied frames while the thief reads them.

A cactus stack avoids copying by sharing frames. The name comes from the shape: multiple stacks branch from a common trunk, like a cactus. Each worker has a current stack, but frames can have multiple children. When a worker steals a continuation, it receives a pointer to a frame in the victim's stack. That frame remains alive as long as any worker can reach it. The victim may continue deeper, creating new frames below the shared frame. The thief may execute the continuation, which may create its own frames. The result is a tree of stacks, not a single linear stack.

Cactus stacks introduce two problems: synchronization and reclamation. Synchronization is needed because a frame may be read by a thief while the victim is still using it. If the frame contains mutable local variables, the runtime must either freeze the frame, copy it lazily, or prove that the victim will not touch it again. In a continuation-stealing model, the victim typically abandons the stolen continuation and continues with the child. If the continuation's frames are not modified by the victim after the steal, sharing is safe. If they are modified, the runtime needs a copy or a lock.

Reclamation is the harder problem. A frame cannot be freed until all workers that can reach it have finished. Reference counting is the straightforward solution: each frame has a count of incoming references from workers or child frames. When a worker finishes a continuation, it decrements the count. If the count reaches zero, the frame can be freed. Reference counting adds atomic operations to every frame access, which can be costly. Epoch-based reclamation amortizes the cost: workers announce an epoch, and frames retired in an older epoch can be freed once all workers have advanced. Hazard pointers are another option: a worker publishes the pointers it is currently using, and reclamation waits until no hazard pointer refers to the frame. Each approach has trade-offs in memory overhead, latency, and implementation complexity.

Segmented stacks offer a middle ground. Instead of one contiguous stack, the runtime allocates stack segments on the heap. A segment is a fixed-size block of frames. When a worker needs more stack, it allocates a new segment and links it to the previous one. Stealing can copy a segment or share it with reference counting. Segmented stacks avoid the need to move a large contiguous stack when it grows. They also make it easier to free frames incrementally. The cost is indirection: every frame access may need to follow a segment link, and the runtime must handle segment overflow.

A continuation frame is a more explicit representation. Instead of relying on the native call stack, the runtime represents a continuation as a heap-allocated object with a function pointer and a captured environment. This is common in languages with first-class continuations or in runtimes that compile recursive functions into state machines. Continuation frames make stealing trivial: the runtime steals a pointer. They also make the cost of allocation explicit. Every recursive call that may be stolen must allocate a continuation frame. For deep traversals, that allocation can be significant. The trade-off is control: the runtime knows exactly what state is live, so it can copy or share precisely.

The choice of stack representation determines the steal granularity. Copying a stack segment steals a batch of work. Sharing a cactus stack steals a single continuation. Continuation frames steal a heap object. Batch stealing reduces overhead but may imbalance load. Fine-grained stealing balances better but increases synchronization and memory management costs.

## Locality and Ordering

Locality is often the difference between a parallel traversal that scales and one that does not. Recursive traversals tend to have strong locality in serial execution. A parent and its children are often allocated near each other. A depth-first order keeps a small working set in cache. When a worker steals a task from another worker, the task may be far away in memory. The thief pays remote cache misses and possibly remote NUMA access. If the traversal is memory-bound, stealing can reduce performance even when it improves load balance.

The deque discipline affects locality. If workers steal from the opposite end of the deque from where they push, they steal the oldest task. The oldest task is usually higher in the recursion tree and represents a larger subtree. Stealing it gives the thief a lot of work, which amortizes the steal cost. It also gives the thief a cold cache and a task that may have poor locality with the victim's current work. If workers steal from the same end, they steal the newest task. The newest task is small and hot in cache, but the thief may finish it quickly and need to steal again. Many runtimes use the opposite-end policy because it reduces contention and provides larger work chunks.

NUMA adds another dimension. On a multi-socket machine, memory is partitioned. A task that allocates memory on socket 0 should ideally run on socket 0. If a worker on socket 1 steals it, the task's allocations may be remote. Affinity-aware stealing can mitigate this: a worker prefers to steal from workers on the same socket, and only steals remotely when local deques are empty. This reduces remote traffic but can leave cores idle when work is unevenly distributed. The runtime can also migrate tasks back to their home socket after a steal, but migration costs are high.

Ordering is a semantic concern. If the traversal must produce results in a deterministic order, parallel execution cannot simply append to a shared list. The runtime must either serialize the ordered part or use a deterministic reduction. For example, a parallel tree traversal that computes a sum can use a commutative and associative reduction. A traversal that builds an ordered list cannot, unless it records positions and merges later. Determinism often requires synchronization at the combine step, which reduces parallelism. The trade-off is between semantic simplicity and parallel scalability.

## Termination Detection and Load Balancing

A work-stealing runtime must know when the traversal is complete. Termination is not as simple as checking that all deques are empty. A worker may be in the middle of a steal, a task may be about to spawn children, or a continuation may be waiting for a child result. The runtime needs a termination detection protocol that is correct under concurrency.

One common approach is a global epoch counter. Each worker increments a counter when it starts looking for work and decrements when it finds work. If the counter reaches zero and all deques are empty, the runtime can conclude termination. The check must be atomic with respect to task creation. Another approach is a distributed termination detection algorithm, such as the Dijkstra-Scholten algorithm, which tracks parent-child relationships between workers. For work stealing, a simpler scheme is often sufficient: a worker that fails to steal from all other workers a certain number of times can signal termination, and a coordinator verifies that no worker has created new work since the last check.

Load balancing is the other side of termination. Work stealing is dynamic and usually effective for irregular traversals. The victim selection policy matters. Random selection is simple and robust. Round-robin selection can be unfair if some workers have much more work than others. Hierarchical selection groups workers by NUMA node or cache domain, which improves locality. The runtime can also use a work-sharing policy: workers with large deques push tasks to a global queue for idle workers. Work sharing reduces steal overhead but adds contention on the global queue.

Batching is a practical optimization. Instead of stealing one task, a thief steals several. Batching amortizes the cost of synchronization and memory management. It also gives the thief a larger working set, which may improve locality. The trade-off is granularity: a batch that is too large can cause load imbalance, especially near the end of the traversal. Adaptive batching can adjust the batch size based on the number of idle workers and the depth of the deque.

Backpressure is necessary when tasks spawn more tasks. A recursive traversal can generate work faster than workers can consume it. If the runtime uses unbounded deques, memory usage can grow without bound. A bounded deque forces the producer to slow down or spill tasks to a slower tier. Spilling can be as simple as writing tasks to a concurrent queue or as complex as serializing continuations to disk. The design must balance throughput, latency, and memory footprint.

## A Design Sketch: Continuation-Stealing Traversal Runtime

A concrete design can make the trade-offs clearer. Consider a runtime with one deque per worker. Each deque holds continuation frames. A continuation frame contains a function pointer, a pointer to the captured environment, a parent pointer, and a reference count. The runtime uses work-first scheduling: when a task spawns a child, it pushes the continuation and executes the child. When a worker's deque is empty, it picks a victim at random and attempts to steal the oldest continuation from the victim's deque.

The steal operation must be atomic with respect to the victim's push and pop. A Chase-Lev deque provides this: the owner pushes and pops from one end, and thieves steal from the other end. The owner's operations are mostly local; the thief uses an atomic compare-and-swap on the top index. The deque also needs a memory reclamation scheme. The runtime can use epoch-based reclamation: each worker announces an epoch, and retired continuation frames are freed when all workers have advanced past the epoch in which the frame was retired.

When a thief steals a continuation, it increments the reference count on the continuation and on any frames it can reach. The victim does not modify the stolen continuation; it continues executing the child. When the child completes, the victim may need to join with the stolen continuation. The join protocol uses the parent pointer and a counter of outstanding children. The last child to finish executes the continuation's combine step. This is a standard fork-join join protocol, but the continuation may be running on a different worker.

The runtime must handle stack overflow. If a worker's recursive depth exceeds a threshold, it can allocate a new stack segment or spill the continuation to the heap. The threshold should be large enough to avoid frequent spills but small enough to prevent native stack overflow. The runtime can also use a guard page to detect overflow and convert it into a controlled allocation.

Correctness invariants are essential. Every continuation must be executed exactly once. Every child must be joined exactly once. Every frame must be freed after its last reference disappears. The runtime should be tested with a deterministic scheduler that explores interleavings, or with a model checker for the deque and join protocols. The memory model matters: the deque's atomic operations must use acquire-release semantics to ensure that a thief sees a fully initialized continuation. Reference count updates must be atomic, but they can use relaxed ordering if the reclamation scheme provides the necessary synchronization.

The next sections will examine how this design behaves under different traversal shapes, how to measure steal overhead and locality, how to adapt scheduling policies at runtime, and how to integrate the runtime with languages that expose recursive traversal as a library. They will also look at failure modes: false sharing on deques, contention on the join counters, and the cost of reference counting on deep stacks.

## Traversal Shape as a Runtime Input

A continuation-stealing runtime treats every spawn as a statement about future parallelism, but the traversal shape decides whether that statement is true. The runtime should therefore read shape continuously rather than assume that a recursive call is a useful steal point. Branch factor, depth, node cost, and the distribution of subtree sizes are the first signals. A shallow tree with high fan-out creates many independent continuations near the root; a deep, narrow tree creates long chains where most continuations are nearly sequential. A tree with uniform small nodes makes stealing cheap but join overhead frequent. A tree with a few expensive subtrees makes stealing valuable but uneven. The runtime cannot know subtree size without traversing it, yet it can use cheap hints: the number of children already visible, the depth of the call, the size of the captured frame, and whether the parent has completed any children.

Those hints should influence scheduling without becoming a burden on the programmer. A common mistake is to require the caller to annotate exact work estimates. Estimates age quickly, are wrong for irregular data, and often force users to duplicate traversal logic. A better boundary is a small set of traversal classes. A pure reduction combines child results with associative operations and can be stolen freely. A search traversal may terminate early and needs a cancellation token shared by all branches. An effectful traversal mutates external state and needs either ownership of a region or a serialization discipline. The runtime can choose different steal points for each class while preserving one programming model: recursive calls that return a value or complete a continuation.

The distinction between expansion and combination is equally important. Early in a traversal, workers are expanding the task graph; deques fill with continuations that have not yet acquired results. Later, workers are combining results; deques empty quickly and join traffic rises. A policy tuned for the expansion phase can perform badly in the combination phase. For example, aggressive help-first scheduling exposes many children early, which is useful when the traversal is expanding, but it can create a large number of continuations that all wait on small results near the end. Work-first scheduling keeps the expansion path local and defers the parent continuation, which is helpful when the traversal is deep and child creation is cheap. Neither policy is correct for every phase, so the runtime should avoid committing permanently based on the first few milliseconds.

Traversal shape also appears in memory layout. If children are stored in contiguous arrays, a stolen continuation may represent a cache-friendly batch. If children are linked through pointers scattered across the heap, every child visit is a potential cache miss and stealing may move work to a worker that has no useful locality with the data. The runtime can use addresses as hints, but addresses are not semantics. A stolen continuation whose frame is near the thief's current allocations is cheaper than one from a distant arena. Allocation behavior therefore belongs in the scheduling feedback loop, not only in the memory allocator.

## Measuring What Stealing Costs

Before adapting a scheduler, measure what a steal actually costs on the target machine. The useful metrics are not limited to throughput. Count steal attempts, successful steals, failed steals caused by an empty deque, failed steals caused by contention, and the number of tasks executed per successful steal. Track how long a worker remains idle after a failed steal and how long a continuation waits at a join before its last child completes. Record deque occupancy separately from useful work: a deep deque may hold many continuations that are blocked on children and cannot be executed, so deque depth alone can overstate available parallelism.

Measure the work carried by a steal, not just the number of steals. A thief that steals one tiny continuation pays synchronization, reference counting, and cache-miss costs for almost no work. A thief that steals a batch of continuations amortizes those costs but may leave the victim with too little work and create imbalance later. The right diagnostic is a distribution: work per steal, steal latency, and the time until the next steal by the same worker. If most steals are small but a few are large, the scheduler needs adaptive granularity rather than a single batch size.

Locality measurement requires separating at least three cases: a continuation stolen by a worker on the same core, a worker on the same socket, and a worker on a different socket. Hardware counters for last-level cache misses, remote NUMA accesses, and memory bandwidth are more informative than wall-clock speedup alone. A traversal can show high CPU utilization and poor speedup because every stolen continuation triggers remote memory traffic. Conversely, a traversal can show moderate utilization but good speedup because stolen work is large and local enough. Instrumentation should be sampled or scoped to phases; full tracing of every steal can change the behavior being measured.

Tail behavior deserves its own measurement. Many traversals finish with a long period in which most workers are idle and a few workers finish the last large subtree. If the runtime reports only average utilization, this tail is invisible. Measure the time from the first worker becoming idle to the last worker finishing, and count how many tasks remain executeable during that interval. A runtime that batches steals aggressively may improve the middle of the traversal while worsening the tail, because the last batch cannot be split. A runtime that steals single continuations may balance the tail better while paying more overhead earlier.

Finally, measure reclamation and join costs as first-class costs. Reference-count updates, epoch advancement, hazard-pointer publication, and atomic join counters can appear as unexplained slowdowns. A join counter on a cache line shared by many continuations can serialize completion even when the traversal has abundant parallelism. A reclamation scheme that waits for all workers to advance can delay memory reuse and increase the working set. These costs are part of the scheduling design, not an implementation detail to be optimized later.

## Adaptive Scheduling Without a Global Coordinator

An adaptive runtime does not need a global coordinator. Each worker can observe its own recent history: deque depth, successful steals, failed steals, average work per steal, and time spent waiting at joins. These local observations are enough to adjust a small policy. The danger is overreaction. A worker that alternates between work-first and help-first on every spawn creates unstable behavior and makes performance difficult to explain. Use hysteresis: change policy only after a sustained signal, such as several consecutive steals that return too little work or a deque that remains above a high-water mark across many spawns.

Granularity is the most valuable thing to adapt. Start with one continuation per steal. If repeated steals succeed and the victim's deque remains deep, increase the batch size. If a steal returns a batch that is too large relative to the remaining work, decrease it. The batch size should be bounded by both a task count and an estimated work measure; counting continuations alone is misleading when some continuations represent large subtrees and others represent trivial combines. A practical compromise is to batch only continuations at similar depth, because depth is a cheap proxy for subtree size in many balanced traversals.

Victim selection can also be local. Random selection is robust and avoids herd behavior, but a pure random choice ignores NUMA topology and cache domains. A worker can sample two or three victims and prefer one with a non-empty deque on the same socket. If no local victim has work, it can attempt a remote victim. The sampling cost is small, and the bias improves locality without requiring a global work queue. The runtime should avoid always choosing the same victim, because a busy victim can become a hotspot even when other workers are idle. Randomized tie-breaking is usually enough.

Work sharing should be a fallback, not the default. A global queue reintroduces the shared-stack problem at a different level: every push and pop touches a contended structure. A per-socket overflow queue is a better compromise. When a worker's deque exceeds a high-water mark, it moves a batch of continuations to the socket-local overflow queue. Idle workers check their local overflow queue before attempting remote steals. This preserves locality and limits contention. The overflow queue should be bounded and should apply backpressure to producers, but backpressure must not block a worker that is holding a join dependency needed by other workers.

Adaptive policies must preserve safety under adversarial scheduling. No worker should be able to starve another worker indefinitely through repeated steal failures. A worker that fails to steal for a long time should back off with randomized delays and eventually attempt a wider search. Termination detection should be separate from load balancing. A worker that finds no work should not immediately declare termination; it should participate in a quiescence protocol that accounts for in-flight steals and continuations that may still spawn children. The policy can be approximate, but the correctness protocol cannot.

## Locality-Aware Continuation Placement

Continuation stealing keeps the child on the victim and moves the parent's remaining work to the thief. That choice is good for the victim's locality because the child is often near the parent's data. It is less good for the thief, which receives a continuation that may later read results produced by the victim. If those results are large, the combine step becomes a remote-memory operation. A locality-aware runtime can mark continuations with a home node and prefer thieves on that node. It can also delay stealing a continuation until its first child result is available, but delay reduces parallelism. The trade-off is between moving work early and moving results later.

A useful distinction is between continuations that mostly combine results and continuations that mostly expand work. Expansion continuations can be stolen early because they will generate new work and can establish fresh locality on the thief. Combination continuations should be stolen later or kept near the workers that produced their inputs. The runtime can infer the distinction from the call site or from the continuation's captured frame: a frame containing child-result buffers is more locality-sensitive than a frame containing only loop indices. This inference is imperfect, but it is cheaper than asking users to classify every function.

Search traversals add another locality problem: the visited set. Even with per-worker stacks, a shared visited set can dominate performance through atomic operations and false sharing. Sharded visited sets reduce contention, but they also make duplicate-work detection less immediate. A traversal that steals continuations across shards may visit the same region twice before either worker publishes its discovery. Epoch-based filters can reduce duplicates: each worker records discoveries locally and merges them at safe points. The merge points become scheduling decisions, because a worker should not steal a continuation whose likely discoveries overlap its own unpublished set. This is a place where traversal semantics and runtime scheduling must meet; a generic work-stealing deque cannot solve it alone.

For graph traversals, stealing a continuation is not the same as stealing a neighborhood. A subtree in a tree is disjoint from its siblings, but a graph frontier may contain overlapping neighbors. The runtime can support work donation at the level of a frontier partition rather than at the level of a single continuation. That requires the traversal to expose a split operation, not just a recursive call. The split operation returns two independent work descriptors and a merge operation. The scheduler can then steal partitions without touching the original stack representation. The cost is that the traversal must be written against an explicit frontier abstraction, which is a different programming model from plain recursion.

## When the Traversal Is Effectful

Effectful traversals break the simple assumption that any continuation can run anywhere. If a node mutates a global table, appends to a shared log, or writes a file, moving its continuation to another worker may violate ordering, ownership, or thread-affinity requirements. The runtime cannot make arbitrary effects safe. It can provide regions: a region marked sequential is executed by the worker that created it and is not stealable. A region marked parallel must use its own synchronization. This lets a compiler traverse an immutable syntax tree in parallel while serializing symbol-table updates, or lets a filesystem walker parallelize independent directory reads while serializing cache metadata.

Sequential regions create load-balancing problems because they are invisible to thieves. If most of the work is sequential, stealing only the parallel parts may leave workers idle. If the sequential parts are large, a single worker becomes the critical path. The runtime can expose the boundary between parallel and sequential work as a scheduling hint: steal only continuations that are likely to contain parallel children, and keep sequential continuations local. This is a heuristic, not a guarantee. A runtime that over-promises parallelism on effectful traversals will produce speedups that disappear under real contention.

Cancellation and exceptions are part of the same boundary. If one branch of a search finds an answer, other branches must stop. With per-worker stacks, cancellation requires a shared atomic flag and a policy for continuations that are already in flight. A stolen continuation may not observe the flag until it reaches a safe point. The runtime can check cancellation at spawn and join boundaries, which bounds the amount of wasted work without requiring a check on every node. Exceptions are harder because a stolen continuation unwinds on the thief. Resources captured by the continuation must be released on the thief or transferred back to the victim. The design should make ownership explicit at the continuation boundary rather than relying on thread-local cleanup that may run on the wrong thread.

## Boundaries Between Runtime and Language

The final design boundary is the language interface. A runtime that implements continuation stealing in a library must cooperate with the language's own stack, exceptions, debuggers, and garbage collector. If the language exposes stackful coroutines, the runtime can reuse the coroutine's stack representation and steal at suspension points. If the language exposes only async functions, the runtime can steal at await boundaries, but recursive traversals that never await will not be parallelized. If the language exposes first-class continuations, the runtime can capture continuations explicitly and avoid native stack copying. Each choice changes the cost model more than the scheduling policy does.

A practical runtime should make the boundary visible. It should document which continuations are stealable, which regions are sequential, how cancellation is observed, and how resources are reclaimed. It should provide a deterministic mode for testing, even if the production mode is nondeterministic. It should expose counters for steals, joins, reclamation, and idle time so that users can diagnose scaling failures rather than guessing. The scheduler can remain sophisticated internally, but the contract at the language boundary must be small enough to reason about. That contract, more than any single deque algorithm, determines whether a parallel recursive traversal is both correct and fast.

## Verification and Debugging of Continuation-Stealing Runtimes

A continuation-stealing runtime is a concurrent algorithm with subtle invariants. It is not enough to test it on a few traversals and observe speedup. The runtime must be exercised under interleavings that expose lost continuations, double execution, premature reclamation, and join deadlocks. The first line of defense is a deterministic simulator. The simulator replaces hardware atomics with a controlled scheduler that can pause a worker before or after every deque operation, steal attempt, reference count update, and join. It records a trace of operations and can replay it. Because the runtime is nondeterministic, a failing trace is valuable only if it can be replayed. Record the initial traversal, the sequence of scheduling decisions, and the memory reclamation events. Then run the same trace against a debug build with assertions.

Assertions should cover the core invariants. Every continuation has a state: created, stolen, executing, waiting-for-children, completed, or retired. Transitions must be legal. A continuation cannot be executed twice. A child cannot be joined twice. A frame cannot be freed while any worker holds a reference. A join counter cannot go negative. A deque cannot contain a continuation that is already executing. These assertions are cheap in a debug build and catch many bugs before they become rare production failures. For memory reclamation, assert that no worker can reach a retired frame and that the epoch of a retired frame is older than the minimum epoch of all active workers.

Model checking is practical for the deque and join protocols. The state space of a Chase-Lev deque with a few workers and a few continuations is small enough for TLA+ or a custom model checker. The model can check linearizability of the deque, absence of lost work, and correct join semantics. It cannot check the entire traversal runtime, but it can check the core synchronization. For the cactus stack, separation logic can prove that frame ownership transfers correctly and that no frame is accessed after its reference count reaches zero. These proofs are not a substitute for testing, but they force the designer to make ownership explicit.

Runtime tracing should be low-overhead and selective. Tracing every steal changes the timing and can hide races. Use per-worker ring buffers that record events without locks. When a worker detects an anomaly, it can dump its buffer and request other workers to dump theirs. The combined trace shows the global order of steals and joins. Visualization tools can render the task graph over time, showing which worker executed which continuation and where idle time occurred. This is invaluable for diagnosing load imbalance and tail latency. It also reveals false sharing: if many workers are updating counters on the same cache line, the trace shows frequent cache-line transfers even when the logical operations are independent.

Race detectors and memory sanitizers are necessary but not sufficient. They can catch data races on frames and deques, but they do not understand the runtime's logical invariants. A race detector may flag a benign race on a reference count that is protected by an epoch protocol. The runtime should provide annotations or wrappers that tell the sanitizer which accesses are synchronized by the reclamation scheme. Similarly, a memory sanitizer can catch use-after-free, but it cannot tell whether a frame was freed too early because a reference count was decremented twice. The assertions and model checking cover that gap.

Stress testing should vary traversal shape, worker count, steal policy, and memory pressure. Run with more workers than cores to force preemption and migration. Run with a single worker to verify that the serial path is correct. Run with a traversal that is deliberately unbalanced so that some workers finish early and attempt many failed steals. Run with a traversal that allocates heavily so that reclamation is exercised. Run with cancellation and exceptions. The goal is not to find a single bug but to build confidence that the runtime's invariants hold across the space of inputs.

## Integration with Garbage Collection and Stack Maps

A continuation-stealing runtime that manages its own stacks must cooperate with the language's garbage collector. The collector needs to find roots in every worker's stack, including stolen continuations that are waiting on other workers. If the runtime uses native stacks, the collector must scan them conservatively or the compiler must emit stack maps. Conservative scanning is simpler but can retain dead objects and cannot move objects that are referenced from the stack. Precise stack maps allow moving collection but require the runtime to know the layout of every frame, including frames that are shared in a cactus stack or copied to a thief.

Cactus stacks complicate scanning because a frame may be reachable from multiple workers. The collector cannot simply scan each worker's current stack; it must traverse the shared frame graph. Each frame needs a descriptor that lists its live references and their offsets. The descriptor must be valid regardless of which worker is executing the frame. If the runtime uses copy-on-steal, the thief gets a copy of the frame, and both copies must be scanned. The collector must treat the shared frame as a root until all references to it are gone. This is another reason to make reclamation explicit: the collector and the runtime must agree on when a frame is dead.

Moving collectors add a further constraint. If the collector moves an object, it must update every reference to that object, including references in stolen continuations. A thief that is executing a continuation may hold a raw pointer to an object that the collector wants to move. The runtime must either pin the object, use a read barrier, or stop the thief at a safepoint. Read barriers are common in concurrent collectors: every load of a reference goes through a barrier that can forward the pointer. This adds overhead to every frame access, which can dominate the cost of fine-grained stealing. The runtime can reduce the overhead by batching: scan a frame's references once when it is stolen, and then execute without barriers until the next safepoint.

Per-worker heaps can improve locality and reduce collector contention. Each worker allocates from its own arena. When a worker steals a continuation, the continuation's captured environment may reference objects in the victim's arena. The collector must handle cross-arena references. A common approach is to use a global heap for shared objects and per-worker heaps for thread-local objects. The runtime must decide which captured variables are shared. This decision is similar to the decision about which frames are stealable. A variable that is read-only after capture can be shared safely. A variable that is mutated by the continuation must be owned by the worker that executes it. The language can express this with ownership types or escape analysis.

Reference counting collectors interact directly with the runtime's own reference counting. If the runtime already reference-counts frames, the collector can use the same counts to reclaim frames. But the runtime's counts track frame reachability, not object reachability. A frame may be alive while all objects it references are dead. The collector must still scan the frame to find those objects. Conversely, an object may be referenced by a frame that is retired but not yet reclaimed. The collector must wait for the runtime to release the frame before it can reclaim the object. This coupling means that reclamation latency affects both memory footprint and collector pause times. A runtime that batches frame reclamation can reduce collector work but increase peak memory.

Safepoints are the synchronization points where a worker can be stopped for collection. In a continuation-stealing runtime, safepoints must be placed at steal boundaries, join boundaries, and allocation points. A worker that is executing a tight recursive loop without allocation may not reach a safepoint for a long time. The compiler can insert safepoint polls at loop back-edges and function entries. The runtime can also use a cooperative safepoint mechanism: a global flag that workers check at safepoints. If a worker is blocked in a steal or join, it must be able to respond to the flag. This requires the blocking operations to be interruptible. The design must ensure that a worker does not hold a lock or a reference count that prevents collection while waiting.

## Performance Modeling and Bottleneck Analysis

A performance model for continuation stealing must account for more than work and span. The standard work-span model assumes that stealing is free and that all workers have equal access to memory. In practice, the runtime pays for steal attempts, join synchronization, reclamation, and remote memory access. A more realistic model adds a steal cost \(C_s\), a join cost \(C_j\), and a locality penalty \(C_l\) per stolen continuation. The total time is at least the critical path plus the sum of these costs. When the traversal is shallow and the tasks are small, the overhead terms dominate, and parallelism can slow down the program.

The steal rate is a useful diagnostic. If workers attempt many steals but few succeed, the deques are either empty or contended. Empty deques mean the traversal has insufficient parallelism or that work is concentrated in a few deep continuations that cannot be stolen. Contended deques mean that the victim selection policy is causing hotspots. A high steal failure rate can also indicate that continuations are blocked on children and cannot be executed. In that case, the runtime should count blocked continuations separately from ready continuations. A deque full of blocked continuations is not a source of work.

Queueing theory can model the deque as a queue with arrivals (spawns) and services (executions). If arrivals exceed services, the deque grows and memory pressure increases. If services exceed arrivals, the deque empties and workers idle. The runtime can use Little's law to estimate the average waiting time of a continuation: \(L = \lambda W\), where \(L\) is the average number of continuations in the system, \(\lambda\) is the arrival rate, and \(W\) is the average time a continuation spends in the system. This helps set batch sizes and backpressure thresholds. A batch size that is too small increases the number of steals and the associated overhead. A batch size that is too large increases the waiting time of continuations and can cause load imbalance.

Cache behavior is often the dominant bottleneck. A recursive traversal has a working set that depends on the depth and branching factor. When the working set exceeds the last-level cache, performance becomes memory-bound. Stealing moves work to another core, which may have a different cache state. If the stolen continuation reads data that the victim has already cached, the thief pays remote cache misses. The runtime can use prefetching: when a continuation is stolen, prefetch its captured environment and the first few nodes it will visit. Prefetching can hide some latency but adds memory traffic. The trade-off depends on the memory bandwidth and the latency of remote accesses.

False sharing is a common source of unexplained slowdown. Join counters, deque indices, and reference counts are often small integers that share a cache line with other frequently updated variables. Padding these variables to cache-line size reduces false sharing but increases memory footprint. The runtime should place per-worker deques on separate cache lines and align atomic counters to their own lines. The cost is small compared to the benefit when many workers are active. Profiling tools that show cache-line contention can identify the worst offenders.

Tail latency is the final bottleneck. As the traversal finishes, the number of ready continuations drops. Workers that finish early attempt to steal but find little work. The last few large continuations determine the completion time. The runtime can mitigate tail latency by splitting large continuations when they are stolen. If a continuation represents a subtree, the thief can split it into two halves and process one while making the other available for stealing. This requires the traversal to expose a split operation. Without splitting, the runtime can only wait for the large continuation to finish. The trade-off is that splitting adds overhead and may duplicate work if the split is not clean. A hybrid approach splits only when the remaining work is large and the number of idle workers is high.

Adaptive control can tune the runtime's parameters based on these measurements. A simple feedback loop adjusts batch size based on steal success rate and deque depth. If steals are succeeding and the deque is deep, increase the batch size. If steals are failing or the deque is shallow, decrease it. The loop should have hysteresis and bounds to avoid oscillation. More sophisticated controllers can use reinforcement learning, but the state space is large and the cost of exploration is high. For most runtimes, a few well-chosen thresholds and a randomized policy are sufficient. The key is to measure the right things and to make the policy transparent enough to debug.

## Deque Microarchitecture and Memory Ordering

A work-stealing deque is a small concurrent data structure, but its memory-ordering contract shapes the entire traversal runtime. In the usual Chase-Lev arrangement, one owner pushes and pops at the bottom while thieves take from the top. The owner can often use a plain load and store because it is the only writer of the bottom index. Thieves must coordinate through an atomic top index, and the owner must coordinate with them when the deque contains one element. The subtle case is the last item: a pop and a steal may race, and exactly one must succeed. Implementations resolve that race with a compare-and-swap on the top index or a more elaborate protocol. A runtime that gets this wrong can lose a continuation or execute it twice, and neither failure is visible in a simple unit test.

The ordering around continuation initialization is equally important. When an owner pushes a continuation descriptor, it must publish the initialized frame before a thief can observe the descriptor through the top index. A release store on the push side and an acquire load or successful compare-and-swap on the steal side establish that ordering. Reference-count increments and join-counter updates can use weaker ordering only if the surrounding protocol provides the necessary synchronization. Lazy reference counting is tempting because it removes atomics from the common path, but it must be paired with a reclamation scheme that cannot free a frame while a thief is still reading its descriptor. The runtime should document which atomics are required for correctness and which are only for performance. Mixing the two produces code that appears to work on x86 and fails on architectures with weaker memory models.

Deque resizing adds another dimension. A circular array that grows must not copy a continuation while a thief is reading it. Copy-on-resize with a versioned array is one option; a split array with a forwarding pointer is another. Both add indirection and complicate reclamation. For traversals with bounded parallelism, a fixed-size array per worker is often sufficient. The runtime can detect overflow and switch to a slower segmented deque rather than paying resize costs on every push. The threshold should be based on the number of ready continuations, not on total memory, because a deque full of blocked continuations does not indicate useful parallelism.

False sharing is not limited to counters. The deque's top and bottom indices, the array pointer, and the owner's local metadata can share a cache line. Padding the indices to separate lines increases the size of each worker's state, but it reduces cache-line transfers between a victim and its thieves. The array elements themselves can also cause false sharing if descriptors are smaller than a cache line and adjacent steals touch different elements. Batching steals can align with cache lines, but it also changes granularity. A runtime should measure cache-line contention before padding everything. On a machine with few workers, padding may waste cache without helping. On a machine with many workers, unpadded indices can serialize the steal path even when the logical operations are independent.

## Heterogeneous Cores and Constrained Execution Environments

Work stealing usually assumes homogeneous workers. Modern machines often violate that assumption. Big.LITTLE and similar designs have cores with different performance and energy characteristics. Simultaneous multithreading makes two logical workers share execution resources on one physical core. Containers and cgroups impose CPU quotas that can throttle a worker for part of a scheduling period. A continuation stolen by a worker on a small core may take far longer than the same continuation on a large core, and a worker that is throttled may appear idle to the runtime while it is simply not running. The scheduler cannot fix these conditions, but it can avoid making them worse.

Victim selection should account for worker capability. A thief on a performance core can afford to steal larger batches, because it will finish them quickly and return for more. A thief on an efficiency core should prefer smaller batches or work that is already local, because a large batch may become a tail that outlives the rest of the traversal. The runtime can expose a worker class and use it as a hint in steal decisions. It should not hard-code core IDs, because the operating system may migrate workers at any time. Instead, the runtime can sample its own throughput and adjust its batch size accordingly. A worker that consistently completes stolen continuations faster than its peers can be treated as a preferred thief for large subtrees.

Throttling is harder. If a cgroup allows two CPUs of execution across eight workers, the runtime may create eight worker threads that are time-sliced. A worker that fails to steal may be descheduled before it can retry. Termination detection must not interpret a long pause as quiescence. One approach is to require a worker to observe an empty deque across multiple scheduling opportunities before it participates in termination. Another is to use a separate watchdog that checks whether all workers have made progress since the last epoch. The watchdog itself must not become a bottleneck, and it must be disabled when the runtime cannot observe CPU quotas. The practical lesson is that termination detection and load balancing have different failure modes under oversubscription. A runtime tuned for one worker per core can behave poorly when workers outnumber cores.

Heterogeneous memory adds a related problem. A continuation that allocates on a performance-core socket may later be stolen by an efficiency-core worker attached to a different memory controller. The thief pays remote access costs for every allocation the continuation makes. The runtime can prefer local victims before remote ones, but it should not refuse remote steals when local deques are empty. A hybrid policy samples a few local victims, then a few remote victims, and randomizes the order to avoid hotspots. The policy should be explicit about its assumptions: if the machine reports no topology, it should fall back to random selection rather than guessing.

## Continuation Descriptors as a Compact ABI

The continuation descriptor is the runtime's interface to the traversal. If the descriptor is large and allocated separately for every spawn, the allocator becomes a bottleneck. A compact descriptor can be allocated from a per-worker slab and initialized with only the fields the runtime needs: a function pointer, an environment pointer, a parent pointer, a depth, a reference count, and a small set of flags. The environment can live in the frame or in a separate allocation depending on whether it is shared. A descriptor that fits in one or two cache lines is much easier to batch and reclaim than a descriptor with dozens of fields.

The descriptor should also carry a call-site identifier. The call site tells the runtime which traversal function created the continuation and whether that function is known to split cleanly. A compiler can assign call-site IDs and emit metadata about captured variables, such as whether they are read-only after capture. The runtime can use this metadata to decide whether a continuation can be stolen without copying, whether it can be batched with adjacent continuations, and whether it requires a join barrier. This is a small amount of static information, but it is more reliable than inferring behavior from runtime samples alone.

The hardest part of the ABI is ownership. A continuation may capture a pointer to a mutable object that the victim expects to update after the child returns. If the thief executes the continuation before the victim finishes, both may access the object. The runtime cannot solve this generically. It can require the traversal to mark captured state as read-only, owned, or shared-with-lock. Read-only state can be shared freely. Owned state must move with the continuation. Shared-with-lock state must use the traversal's lock. These annotations do not need to be on every variable; they can be attached to the call site and refined by escape analysis. The cost of getting ownership wrong is a data race that appears only under stealing, so the runtime should check annotations in debug builds and reject unsupported captures at the API boundary.

A compact descriptor also makes splitting easier. If a continuation represents a range of children, the runtime can split the range without copying the entire frame. The split operation returns two descriptors that share the read-only prefix and own disjoint suffixes. The join operation combines their results. This is a middle ground between stealing a single recursive call and stealing an entire stack segment. It gives the scheduler control over granularity without requiring the traversal to expose every internal frame. The descriptor must record the split boundary and the merge function, but those are small compared with the captured environment. A runtime that supports splitting can reduce tail latency without changing the programmer's recursive code.

These microarchitectural and ABI choices are less visible than the stealing policy, but they determine whether the policy can be implemented efficiently. A runtime with a slow deque, imprecise memory ordering, or a bloated descriptor will struggle to scale even when the traversal has abundant parallelism. A runtime that treats descriptors and deques as first-class design objects has a much better chance of turning theoretical parallelism into measured speedup.
