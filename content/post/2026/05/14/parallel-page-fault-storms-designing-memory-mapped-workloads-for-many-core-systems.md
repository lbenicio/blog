# Parallel Page-Fault Storms: Designing Memory-Mapped Workloads for Many-Core Systems

A memory-mapped workload often looks ideal on paper. A file is mapped into the address space, threads process disjoint ranges, and the kernel handles paging in the background. The data plane is simple: each thread reads or writes its own slice of a contiguous buffer. The control plane is hidden inside the kernel. When the mapping is first exercised, every touched page can generate a fault. On a single core, that cost is usually tolerable. On a many-core machine, the same pattern can turn into a parallel page-fault storm: dozens or hundreds of threads enter the kernel fault path at once, contend on address-space locks, allocate pages, zero memory, walk page tables, and occasionally trigger TLB shootdowns because another part of the program is changing mappings concurrently. Throughput collapses not because the algorithm is wrong, but because the transition from virtual address space to resident physical memory is serialized in places the application never modeled.

This article is about that transition. It is not an introduction to virtual memory, and it is not a guide to writing a page-table simulator. The focus is narrower and more operational: why page faults become a scalability problem in memory-mapped parallel workloads, how anonymous and file-backed mappings fail in different ways, and which design patterns reduce the chance that a data-parallel job spends its time in the kernel fault path. The assumptions are mainstream 64-bit Linux on x86-64 or arm64, a shared-memory model within one process, and a machine where the cost of cross-core synchronization is significant relative to memory access. The trade-offs apply broadly, but the details depend on kernel version, mapping flags, huge-page policy, NUMA topology, storage latency, and whether the data is anonymous memory or page cache.

## The control-plane event hidden in every data-plane design

A page fault is a hardware exception raised when a virtual address cannot be translated according to the current page tables or permission bits. The CPU traps into the kernel, and the kernel decides whether the access is valid. For a valid mapping, the handler finds the virtual memory area, determines whether the page is in the page cache, allocates an anonymous page or performs file I/O, installs a page-table entry, updates accounting, and returns to user space to retry the instruction. For an invalid access, it delivers a signal. The programmer sees a normal load or store. The system sees a synchronous trap on the critical path of that thread.

That distinction matters because parallel programs are usually designed around data-plane costs: arithmetic, memory bandwidth, cache misses, and synchronization. A fault is control-plane work. It is not proportional to bytes processed in the same way as a vector load. It is a per-page transition with kernel locking, allocation, and bookkeeping. If a workload touches one page per thread at startup, the fault cost is noise. If a workload streams through a fresh anonymous buffer, maps a large file, or repeatedly unmaps and remaps regions, the fault path can become the dominant serialized component. The application then exhibits a familiar but misleading profile: high system time, poor scaling with core count, and long stalls that look like memory bandwidth problems but are actually kernel-side contention.

A useful mental model is to separate three layers. The first is the virtual address space: VMAs, permissions, and page tables. The second is physical page supply: anonymous page allocation, page-cache lookup, zeroing, and NUMA placement. The third is translation caching: TLB entries, page-walk caches, and the cost of invalidating them. A page fault can touch all three. A parallel workload can amplify cost in any one of them. The mistake is to treat the mapping as free after `mmap` returns. `mmap` creates a mapping, not resident memory. The first access is where the kernel does the work, and in a parallel program the first accesses from many threads can arrive at the same time.

## What a page fault actually costs

The cheapest fault is still not free. On a minor anonymous fault, the kernel may map the shared zero page for a read, or allocate and zero a page for a write. It must find the VMA, check permissions, acquire the appropriate address-space or VMA lock, allocate or locate a page, install a page-table entry, and update memory accounting. If transparent huge pages are eligible, the fault may attempt to allocate and zero a much larger region, possibly invoking compaction. The retry after the fault is another user-space instruction, but the kernel work happened synchronously. The thread made no forward progress in the application while the fault was being resolved.

A major fault adds storage or page-cache latency. For a file-backed mapping, a fault may find the page already in the page cache, in which case it is minor from the process perspective even if the data arrived earlier through readahead. If the page is not cached, the fault initiates I/O and the thread blocks. Under a parallel scan of a large file, many threads can generate major faults at once. The kernel may merge or cluster some requests, and readahead may hide some latency, but the fault path is still the point where the application discovers that its supposedly contiguous mapping is not resident. Major faults are less about lock contention and more about waiting, but the two interact: threads waiting on I/O occupy worker slots, and the remaining threads may fault more aggressively into the same regions.

Copy-on-write faults are a third category. A `MAP_PRIVATE` file mapping or a forked process starts with page-table entries pointing at shared physical pages. A write triggers a COW fault: the kernel allocates a new page, copies the old contents, updates the page table, and resumes the write. In a parallel workload that forks workers after mapping a large read-mostly dataset, a few writes scattered across the mapping can generate a burst of COW faults. The cost is a page copy plus allocation plus fault-path locking. If the intention was to share read-only data, `MAP_SHARED` or an explicit read-only mapping avoids the copies. If the intention was isolation, the COW cost is real and should be paid before parallelism begins, not discovered by worker threads in the middle of a computation.

The fault path also has internal lock granularity that changes across kernel versions and mapping types. Historically, page faults on the same address space took the `mmap_lock` in read mode, while `mmap`, `munmap`, and `mprotect` took it in write mode. Modern kernels have introduced per-VMA locking and other refinements, so the exact contention profile is not universal. The design lesson survives: the fault path is not a pure hardware operation. It acquires kernel locks, consults shared data structures, and allocates from shared pools. A parallel program that faults on many pages simultaneously is exercising a kernel subsystem that was not designed as a high-throughput data plane for application threads.

## Two mapping types, two different storms

Anonymous memory and file-backed memory fail differently under parallel first touch. Anonymous memory has no backing file. A read fault can map the shared zero page; a write fault allocates a fresh page, zeroes it, and installs a writable PTE. The page is placed according to the NUMA policy and the CPU that faulted, typically first touch. If all worker threads touch disjoint regions of one large anonymous mapping, they are not sharing data, but they are sharing the address space and the page allocator. The kernel must allocate pages, zero them, and update page tables. The zeroing is unavoidable for security and correctness: newly allocated anonymous pages must not expose another process's data. That zeroing consumes memory bandwidth and core time. At high core counts, page allocation, zeroing, and page-table updates can compete with the application's own memory traffic.

File-backed memory has a different bottleneck. A read fault checks the page cache, may initiate readahead, and maps the cached page. If the file is already cached, the fault is minor from the process perspective, but the cache lookup and page-table work remain. If the file is not cached, the fault waits on storage. A shared file mapping also has writeback semantics: dirty pages must eventually be written back, and the kernel tracks them. A private file mapping adds COW on write. The same `mmap` call can therefore produce three very different workloads: a read-only shared scan of cached data, a cold major-fault scan of an uncached file, and a write-heavy private mapping with COW and dirty-page accounting. Designing for one and deploying the other is a common source of disappointing scaling.

There is also a difference in how much the application can control residency. Anonymous memory can be pre-faulted by writing one byte per page, or by using `MAP_POPULATE` where applicable, but the NUMA placement depends on which CPU performs the first touch. File-backed memory can be pre-read with `madvise(MADV_WILLNEED)` or by explicit reads into a buffer, but readahead is advisory. A file mapping can look resident in one benchmark run and cold in another because the page cache state changed. That makes file-backed parallel scans especially sensitive to deployment history: a warm cache hides fault costs that a cold cache exposes. For systems that need predictable startup, the mapping strategy must account for cold cache, not just the warm steady state.

## Amplification on many cores

The dangerous pattern is not a single fault. It is synchronization of faults. A program starts many threads, each is assigned a contiguous range, and each begins by touching its first page. If the ranges are large and the mapping is not resident, every thread faults at roughly the same time. The kernel fault handler runs on many CPUs concurrently, but the work converges on shared structures: the address space's VMA tree and locks, the page allocator's per-node and per-CPU structures, page-table page allocation, memory cgroup accounting if enabled, and the page cache for file-backed mappings. Per-CPU caching helps, but it does not eliminate global limits. Higher-order allocations for huge pages can be more likely to enter slow paths. Zeroing large pages consumes bandwidth. Page-table pages may need to be allocated and linked. The result is a burst of kernel work that scales worse than the application's arithmetic.

Mapping churn makes it worse. Calling `mmap` and `munmap` around each work item, or repeatedly `mprotect`ing regions, forces write-side address-space operations. Removing a mapping requires invalidating translations on other CPUs that may have cached them. That is a TLB shootdown: an inter-processor interrupt or equivalent coordination mechanism that interrupts other cores and makes them flush translations. A single `munmap` in a multithreaded process can therefore interrupt every core running the process. If the program remaps buffers frequently, the shootdown traffic can dominate. The application may believe it is doing a simple buffer swap; the system sees a cross-core synchronization event. The same concern applies to `mprotect`, `mremap`, and any operation that changes page-table permissions or removes mappings while other threads are running.

First-touch allocation adds a NUMA twist. In a parallel program, the CPU that first writes an anonymous page determines where the physical page is placed under the default policy. If thread 0 pre-touches the entire buffer before worker threads start, all pages may land on thread 0's node. The workers then access remote memory, and the resulting bandwidth and latency penalties can look like a fault problem or a memory-bandwidth problem. Conversely, if each worker pre-touches its own range while pinned to the correct CPU, the pages are placed locally, but the pre-touch phase itself generates the fault storm. The choice is not between fault costs and NUMA costs; it is where to pay each cost and how to overlap them with useful work. A common design is a parallel, affinity-aware pre-touch phase that is separate from the main compute phase, so the fault burst is controlled rather than smeared through the hot loop.

Huge pages change the shape of the problem. A larger page size reduces the number of faults and page-table entries for a given region, which can be a significant win for large sequential scans and sparse data structures. But a huge-page fault is more expensive per event: it must allocate and zero a larger contiguous block, and it may trigger compaction or reclaim. Transparent huge pages can also introduce unpredictable latency if the kernel decides to collapse or split pages during execution. For a latency-sensitive service, a single huge-page fault can be worse than several small faults spread over time. For a batch scan, fewer faults are usually better if the memory is available. The right policy depends on whether the workload values tail latency, throughput, or memory efficiency. `MADV_HUGEPAGE` and explicit huge-page mappings are not free performance toggles; they are allocation-policy decisions with different failure modes.

## Design patterns that avoid the storm

The first pattern is to separate population from parallelism. If a mapping must be resident before workers start, populate it before starting the workers, or dedicate a controlled number of threads to pre-faulting it. `MAP_POPULATE` can prefault page tables for a mapping, and `madvise(MADV_WILLNEED)` can initiate readahead for file-backed data, but neither is a universal guarantee of residency or NUMA placement. For anonymous memory, explicit first-touch writes are more predictable, because the thread that writes the page controls the placement under first-touch policy. The goal is not to eliminate faults; it is to prevent an uncontrolled burst of faults from every worker at once. A phased startup with a barrier between population and compute is often more effective than adding more worker threads.

The second pattern is to reuse mappings. Allocating a large arena once and subdividing it is usually better than mapping and unmapping per task. Reuse avoids write-side address-space operations, TLB shootdowns, and page-table churn. It also makes residency predictable: a warm arena stays warm across work items. The trade-off is memory footprint and fragmentation. A service that reuses a fixed arena must decide what happens when a workload exceeds it. Growing an arena by mapping a new region is fine if it is infrequent; growing it per request reintroduces the storm. Pooling and recycling are not just allocator optimizations in this context; they are fault-avoidance mechanisms.

The third pattern is to partition ownership. Per-thread arenas reduce contention in user-space allocators, but they do not automatically reduce kernel fault contention if all threads still fault through one address space. They do help when each thread touches only its own pages: the kernel can process faults on different VMAs and page-table ranges with less interference, and the application avoids false sharing at page granularity. Process isolation goes further: separate processes have separate address spaces, separate page tables, and separate fault-path lock domains, at the cost of IPC and shared-memory setup. For workloads that allocate heavily and then process, a supervisor that forks workers after pre-populating read-only data can be a better fit than one process with many threads and a shared heap. The trade-off is that shared-memory communication must be explicit, and `MAP_SHARED` mappings still involve page-cache and writeback behavior.

The fourth pattern is to choose the mapping type deliberately. Read-only shared data should be mapped shared and read-only, not private and writable, so that writes do not trigger COW. Write-heavy private data should be anonymous memory with a clear first-touch and NUMA policy, not a private file mapping that generates COW and dirty-page traffic. Large sequential file scans should account for page-cache state and readahead, and should not assume that `mmap` replaces explicit I/O buffering in every case. In some systems, a bounded pool of reusable buffers filled by `read` or asynchronous I/O is more predictable than a large file mapping, because the application controls residency and concurrency directly. In others, the zero-copy properties of `mmap` win. The decision should be made from the fault profile, not from the API's simplicity.

The next section will examine how these patterns interact with allocator design, `userfaultfd`, memory cgroups, and writeback, and how to instrument fault behavior without turning the measurement into another source of contention.

## Allocator design after the fault

Once a workload has survived its first-touch phase, the allocator decides whether the fault storm returns. A general-purpose allocator may satisfy large requests by creating new mappings, and each new mapping can introduce fresh VMAs, page-table ranges, and first-touch faults. Thread-caching allocators reduce user-space lock contention, but they still request memory from the kernel in bursts. In a many-core process, those bursts can synchronize: several allocator arenas grow at once, each asks the kernel for pages, and the fault path becomes a shared bottleneck again.

The safer pattern is to reserve a large virtual region once and commit it gradually. A service can map a generous arena at startup, divide it into per-thread or per-NUMA-node slabs, and keep freed memory in user-space free lists instead of returning it to the kernel. Reuse keeps page tables warm and avoids repeated `mmap` and `munmap` calls. The trade-off is footprint and fragmentation. An arena that never shrinks can hide a leak or waste memory in a multi-tenant deployment. The answer is not to return memory after every request, but to define a high-water mark and a controlled compaction or release phase that runs outside the hot path.

Discard operations deserve special care. `madvise(MADV_DONTNEED)` on anonymous memory discards pages, and the next touch faults them back in. In a multithreaded process, that can produce a zero-fill storm and may invalidate translations on other cores. `MADV_FREE` is lazier: it marks pages as reclaimable and lets the kernel decide when to discard them. Neither is a free memory-management primitive in a latency-sensitive workload. If an allocator calls discard operations while worker threads are active, it can recreate the same cross-core fault pattern that a phased startup was meant to avoid. Release memory at quiescent points, or isolate the release to a dedicated maintenance phase.

Huge-page policy belongs at the arena level, not at the individual allocation level. Calling `madvise(MADV_HUGEPAGE)` on a large region tells the kernel that the region is a candidate for transparent huge pages. That can reduce fault counts for sequential scans, but it also changes allocation behavior: a huge-page fault may require a contiguous block, may enter compaction, and may fail or fall back to small pages. If the workload is latency-sensitive, a failed huge-page allocation followed by a small-page fallback can be worse than consistently using small pages. If the workload is throughput-oriented and the memory is available, huge pages are often worth the coarser granularity. The design should decide this per arena and measure the result, not toggle it globally and hope for the best.

Allocator metadata is another hidden fault source. A allocator that stores free-list pointers inside the pages it manages can fault on metadata pages as it grows. In a parallel workload, many threads may touch different metadata pages at once, adding to the fault burst. Keeping metadata in a separate, pre-populated region avoids mixing allocator control structures with application data. The same principle applies to hash tables, queues, and work-stealing deques: if their backing memory is lazily allocated, the first parallel access can fault across many pages. Pre-populating control structures before starting workers is usually cheaper than letting the scheduler discover them under load.

## userfaultfd and controlled fault handling

`userfaultfd` moves missing-page handling from the kernel fault path into a user-space handler. A thread that touches an absent page blocks, the kernel delivers an event to a registered file descriptor, a handler resolves the page, and the faulting thread resumes. This is useful for live migration, checkpoint and restore, lazy loading from storage, and sparse address spaces where the application knows more about the data than the kernel does. It is also a way to make fault handling explicit and measurable. But it does not remove serialization; it relocates it.

In a many-core workload, a single userfaultfd handler thread can become the new bottleneck. Every missing page produces an event, and every event requires a wakeup, a syscall, and a copy or page installation. If hundreds of worker threads fault at once, the handler queue fills, workers block, and the application looks like it is stalled on I/O even when the handler is CPU-bound. The design should use multiple handlers, ideally partitioned by NUMA node or by address range, and should batch work where the interface allows it. A handler that takes a global lock or allocates from a shared pool under contention has simply recreated the kernel fault path in user space.

Handler placement matters. A handler running on the same node as the faulting thread can install pages with local memory placement. A handler on a remote node adds cross-node traffic and may place pages on the wrong node. The handler must also avoid faulting on its own memory while servicing a fault. If the handler touches a lazily mapped buffer, it can deadlock or recursively enter the fault path. Pre-fault the handler's control structures and keep its working set resident. The handler should not hold application locks that faulting threads might need; otherwise a page fault can turn into a priority inversion or a deadlock.

`userfaultfd` is not a general replacement for normal anonymous first touch. For ordinary anonymous memory, the kernel fault path is already optimized and runs on the faulting CPU. Routing every page through a user-space handler adds context switches and queueing. The feature is most valuable when the application needs custom resolution: fetching a page from a remote store, decompressing a chunk, or restoring a checkpoint. In those cases, the goal is to bound the number of outstanding faults and keep the handler's throughput above the workers' fault rate. If the handler cannot keep up, adding more worker threads only increases the queue. Measure handler latency and queue depth, not just aggregate fault count.

## Memory cgroups and reclaim pressure

In containerized deployments, the memory cgroup is part of the fault path. When a cgroup approaches its limit, a page allocation can trigger direct reclaim, writeback, or the OOM killer. Under a parallel fault storm, many threads can push the cgroup toward its limit at the same time. Reclaim work is not free: it scans LRU lists, may write back dirty pages, and may take locks that other faults also need. The application sees a latency spike that looks like a page-fault problem but is really a reclaim problem.

A fault-aware design leaves headroom. Setting `memory.high` below `memory.max` gives the kernel a throttle point before hard reclaim. The workload can then slow allocation or shed work instead of entering direct reclaim. Pre-populating a large mapping before a burst is safer than letting the burst discover the limit. If the workload is a batch job, size the cgroup for the high-water mark plus page-cache and metadata overhead. If it is a service, use per-workload cgroups so that one workload's fault storm does not drive reclaim for unrelated workloads. More cgroups add accounting overhead, but they also contain the blast radius.

File-backed mappings interact with cgroup reclaim through the page cache. A read-only shared mapping may look cheap, but if the cgroup is under pressure, the kernel can reclaim cached pages and the next access becomes a major fault. A warm benchmark can hide this cost. For predictable behavior, measure cold-cache and near-limit runs, not only the warm steady state. Watch `memory.events` for high, max, and OOM events, and watch `memory.stat` for fault and reclaim counters. A workload that never hits its limit in the average case can still have a tail where a burst of faults triggers reclaim and a long stall.

## Writeback and dirty-page pacing

Writable file mappings add dirty-page accounting and writeback to the fault path. A write to a shared file mapping can be a minor fault if the page is already in the page cache, but the page becomes dirty. Under memory pressure or dirty-page throttling, writeback can stall the writing thread. Many threads writing to the same file can create a large dirty set quickly. The kernel may throttle them, and the application experiences pauses that are not explained by its own I/O pattern.

The design choice is to separate data production from writeback pacing. Use `MAP_SHARED` for data that must be visible to other processes or persisted, and avoid `MAP_PRIVATE` for large write-heavy regions unless copy-on-write isolation is genuinely required. Preallocate file blocks with `fallocate` before the parallel phase so that block allocation does not happen inside the fault path. Bound the amount of dirty data per worker or per file, and checkpoint with `msync` at controlled barriers rather than letting writeback accumulate until the kernel throttles. If multiple workers write to one file, consider separate files or separate regions with independent writeback behavior to reduce inode and page-lock contention. None of these choices eliminates writeback, but they move it from an uncontrolled background event into a planned phase.

## Instrumenting fault storms without adding contention

The measurement plan should be phase-based. Counting every fault with a syscall or a log line in the hot path changes the workload and can add the very contention being measured. Instead, record per-thread fault counts at phase boundaries with `getrusage(RUSAGE_THREAD)`, and sample system-wide counters from `/proc/vmstat` and `/proc/self/stat` between phases. Use `perf stat` for page faults, context switches, and CPU migrations when the overhead is acceptable. Compare warm-cache and cold-cache runs, and compare a phased startup with an unpinned parallel first touch. The goal is not a perfect fault trace; it is to identify whether system time, major faults, or reclaim is scaling with core count.

Tracepoints are useful when a phase-level view is not enough. Page-fault tracepoints, reclaim tracepoints, and scheduler tracepoints can show whether faults are clustering at a barrier or spreading across the run. Sampling is usually safer than tracing every event. If the workload uses `userfaultfd`, measure handler queue depth and handler service time directly. If it uses file mappings, measure major faults and writeback stalls separately from minor faults. The final design question is not how many faults occurred, but whether the faults were paid in a controlled phase or discovered by workers in the middle of the data plane.

## Fault-around, readahead, and the illusion of sequential access

When a file-backed page fault occurs, the Linux kernel does not always map just the faulting page. The filemap fault handler may map a cluster of pages around the faulting address, a behavior known as fault-around. The rationale is simple: file access is often sequential, and mapping several pages at once amortizes the fault cost. The default fault-around window is typically 16 pages, though it can be tuned. For a single-threaded sequential scan, this is a clear win: one fault brings in a batch of pages, and the thread continues without trapping. For a parallel workload, fault-around can become a source of hidden contention and redundant work.

Consider a large file mapped shared and read-only, with N worker threads each assigned a contiguous range. If the ranges are aligned to the fault-around window, each thread faults on its first page, and the kernel maps the surrounding pages. The threads then proceed through their ranges without further faults until they cross a window boundary. This can work well if the ranges are large and the threads do not overlap. But if the ranges are small or interleaved, multiple threads may fault on pages within the same fault-around window. The kernel will map pages that another thread is about to map, and both threads may contend on the page cache's radix tree locks or the page table locks for the same PTE page. The redundant mapping work is wasted, and the contention can serialize what should be independent progress.

Read-ahead adds another layer. The kernel's read-ahead logic detects sequential access patterns and issues I/O for pages ahead of the faulting address. In a parallel scan, each thread may trigger its own read-ahead stream. If the threads are reading disjoint regions, the read-ahead requests are independent and can be serviced in parallel, up to the limits of the storage device and the page cache. But if the threads are interleaved or if the file is not cached, the read-ahead streams can compete for I/O bandwidth and page cache locks. The kernel may also merge or split read-ahead requests in ways that are not obvious from the application's access pattern. The result is that a parallel scan of a cold file can behave very differently from a warm-cache scan, and the difference is not just I/O latency but fault-path contention.

The `madvise` interface gives the application some control. `MADV_SEQUENTIAL` tells the kernel to expect sequential access and to aggressively read ahead. `MADV_RANDOM` disables read-ahead and fault-around, which can reduce contention for random access patterns but increases the number of faults for sequential ones. `MADV_WILLNEED` initiates read-ahead without blocking, but it is advisory and asynchronous; it does not guarantee that pages will be resident when the worker threads start. For a parallel workload that needs predictable startup, explicit pre-reading with `read` or `io_uring` into a pre-allocated buffer may be more controllable than relying on fault-around and read-ahead. The trade-off is an extra copy, but the copy can be done in a controlled phase with bounded concurrency, avoiding the fault storm entirely.

Newer kernels provide `MADV_POPULATE_READ` and `MADV_POPULATE_WRITE`, which populate page tables for a range without actually accessing the data. This can be used to pre-fault a mapping in a controlled phase. Unlike `MAP_POPULATE`, which populates at mmap time, these madvise flags can be applied to a subrange and at a chosen time. They are still synchronous and can be slow for large ranges, but they give the application more control. For file-backed mappings, `MADV_POPULATE_READ` will trigger readahead and wait for pages to be resident. This can be useful before starting worker threads, but it must be done with bounded concurrency to avoid a fault storm during the population phase itself.

When using file mappings, align thread ranges to large boundaries. A 2 MiB boundary is a natural choice because it corresponds to a huge page and to a PTE page on x86-64. Aligning to 2 MiB ensures that threads fault on different PTE pages and different fault-around windows. If the file is not a multiple of 2 MiB, the last thread handles the remainder. This simple alignment can reduce page-table lock contention and redundant fault-around work. For anonymous memory, the same alignment helps with first-touch placement and page-table contention, as discussed next.

## Page-table granularity and hidden lock contention

The kernel's page tables are hierarchical. On x86-64, a four-level (or five-level) table translates a virtual address to a physical address. The lowest level is the page table entry (PTE), which points to a 4 KiB page. A single PTE page contains 512 entries and covers 2 MiB of virtual address space. The kernel uses a per-PTE-page lock, often called the pte lock, to serialize updates to the PTEs within that page. When a thread takes a page fault, it must acquire the pte lock for the PTE page that contains the faulting address, install the PTE, and release the lock. If another thread faults on a different address within the same 2 MiB region, it contends on the same pte lock. This is a hidden serialization point that is invisible to the application's data partitioning.

In a many-core system, this contention can be significant. Suppose a program has 64 threads, each processing a 1 MiB chunk of a large anonymous mapping. The chunks are contiguous, so four threads share a 2 MiB region. When the threads start and fault on their first pages, all four threads in the same 2 MiB region contend on the same pte lock. The kernel processes their faults one at a time, even though the threads are touching disjoint pages. The same applies to file-backed mappings, especially with fault-around: a single fault may map multiple pages within the same PTE page, and subsequent faults from other threads in that region will contend. The pte lock is held for a short time, but under a burst of faults, the queueing delay adds up.

The problem is analogous to false sharing in cache lines, but at the page-table level. The granularity is 2 MiB, not 64 bytes. To avoid it, partition the address space so that each thread's range is aligned to a 2 MiB boundary. If the data is a large array, this means assigning each thread a multiple of 2 MiB. If the data is a file, the same alignment applies. For small objects, this may be impractical, but the objects can be grouped into per-thread arenas that are 2 MiB aligned. The goal is to ensure that concurrent faults from different threads touch different PTE pages.

Huge pages change the equation. A 2 MiB huge page is represented by a single PMD entry, not by 512 PTE entries. A fault on a huge page acquires the PMD lock, which covers a 1 GiB region (on x86-64, a PMD page covers 1 GiB). So huge pages reduce the number of page-table entries and the number of locks, but they increase the granularity of those locks. If multiple threads fault on different 2 MiB huge pages within the same 1 GiB region, they contend on the same PMD lock. This can be worse than small pages if the threads are densely packed. The design must consider the page-table hierarchy: for small pages, align to 2 MiB; for huge pages, align to 1 GiB. In practice, huge pages are often used for large sequential regions, and the number of concurrent faults on the same PMD lock may be low if the region is large. But in a many-core system with hundreds of threads, even a few concurrent huge-page faults can serialize on the PMD lock.

Page table pages themselves must be allocated. When a process grows its address space, the kernel allocates page-table pages (PTE pages, PMD pages, etc.) on demand. These allocations come from the page allocator and may contend with other faults. In a parallel first-touch scenario, many threads can trigger page-table page allocation simultaneously, leading to contention on the page allocator and on the locks that protect the page-table hierarchy. Pre-faulting a large region in a single thread can allocate the page-table pages in advance, so that parallel faults only need to install PTEs, not allocate page-table pages. This is another argument for a phased population step.

Recent kernel versions have introduced per-VMA locking and speculative page faults (SPF) to reduce contention on the `mmap_lock`. Per-VMA locking allows faults on different VMAs to proceed without taking the address-space lock, and SPF allows some faults to be handled without any kernel lock at all. These features improve scalability, but they do not eliminate pte lock or PMD lock contention. The application can still hit the lower-level locks. The design lesson is to think about the page-table hierarchy when partitioning work. Aligning ranges to 2 MiB or 1 GiB boundaries, depending on page size, is a cheap way to reduce hidden serialization. It also improves TLB behavior, because threads will not share TLB entries for the same page-table page unless they are actually sharing data.

## NUMA balancing: the fault storm you did not start

On NUMA systems, the kernel can automatically balance memory placement with a feature called automatic NUMA balancing. When enabled, the kernel periodically scans the address space of running tasks, unmaps pages that have not been accessed recently, and records faults when they are touched again. The goal is to detect which pages are being accessed by which CPUs and migrate them to the node that accesses them most. For irregular workloads with changing access patterns, this can improve performance. For a memory-mapped parallel workload that has already been carefully partitioned and first-touched, automatic NUMA balancing can be a source of unexpected page faults, TLB shootdowns, and page migrations.

The mechanism works by clearing the present bit or the young bit in the page-table entries for a task's pages. When a thread accesses a page whose PTE has been cleared, it takes a fault. The fault handler records the access, may migrate the page to the faulting node, and reinstalls the PTE. In a many-core system, the balancing scan can run on multiple CPUs and can generate a burst of faults across the address space. If the application is already experiencing a fault storm from first touch or file mapping, the additional faults from NUMA balancing can compound the contention. The kernel may also migrate pages while worker threads are accessing them, causing remote accesses and cache misses.

For latency-sensitive workloads, it is often better to disable automatic NUMA balancing and manage placement explicitly. The sysctl `kernel.numa_balancing` can be set to 0. Alternatively, the application can use `mbind`, `set_mempolicy`, or `numactl` to bind memory to specific nodes and CPUs. Explicit placement avoids the background scanning and migration, at the cost of losing the kernel's automatic adaptation. For a workload with a static partitioning and first-touch placement, explicit policy is usually sufficient and more predictable. The trade-off is that if the workload's access pattern changes or if threads migrate across nodes, the explicit policy may become suboptimal. Pinning threads to CPUs with `sched_setaffinity` helps keep first-touch placement stable.

For workloads that need to change NUMA policy dynamically, the `move_pages` syscall can migrate pages between nodes. This is an explicit operation that can be done at a barrier, avoiding the background scanning of automatic NUMA balancing. Similarly, `MPOL_INTERLEAVE` can spread pages across nodes, which may be useful for memory-bandwidth-bound workloads that do not have a clear local node. These explicit policies are not free: they require the application to know its access pattern and to manage migration. But they replace unpredictable kernel heuristics with predictable application-controlled behavior.

NUMA balancing interacts with huge pages and transparent huge pages. The scanning and migration of huge pages is more expensive, and the kernel may split huge pages to migrate them. This can cause additional faults and TLB shootdowns. If the workload uses huge pages, consider disabling NUMA balancing or using `MADV_NOHUGEPAGE` on regions where migration is not desired. The interaction is complex, and the best approach is to measure with `numastat` and `perf` to see if NUMA balancing is causing faults or migrations. A simple test is to run the workload with balancing enabled and disabled and compare the fault counts and system time. If the difference is significant, explicit placement is likely better.

The broader point is that page faults are not only caused by the application's first touch or file access. The kernel itself can generate faults through background mechanisms like NUMA balancing, khugepaged, and memory reclaim. A design that aims to avoid fault storms must account for these background activities. Isolating the workload in a cgroup, disabling unnecessary kernel features, and using explicit policies can reduce the noise. The goal is not to eliminate all faults, but to ensure that the faults that occur are the ones the application planned for, not ones introduced by the kernel's heuristics.

## Mapping lifecycle operations are collective, not local

A page fault brings a translation into existence. Unmapping, permission changes, remapping, and discards remove or rewrite translations that other CPUs may have cached. The second class is often more dangerous in a parallel program because it is initiated by one thread but paid by many. The thread that calls `munmap` or `mprotect` may think it is doing local bookkeeping. The kernel must make the change visible to every CPU that might have a stale TLB entry. That requires cross-processor coordination, and the cost rises with the number of cores running the process.

The design consequence is that mapping lifecycle calls belong on a control plane, not in a request handler. A worker that maps a fresh buffer for each batch, or that discards pages after each item, turns a data-plane loop into a sequence of address-space mutations. Even if the individual syscall is cheap, its effect is not local. Other workers may take translation faults because their cached entries were invalidated, or may stall while the kernel waits for acknowledgment from cores that are busy. The application sees a latency spike that does not correlate with the size of the data processed. It correlates with the fan-out of the address-space operation.

Per-VMA locking and newer kernel fault-path refinements reduce read-side contention, but they do not make write-side operations free. A change to a VMA or a page-table range still requires exclusion against concurrent faults and still requires translation invalidation. That is why a program can scale well while its mappings are stable and fall apart when buffers are recycled through `munmap`. The stable state is not an optimization detail; it is a precondition for scalability. The practical rule is to keep the mapping lifecycle outside the hot path and to batch any unavoidable changes at barriers.

Deferred reclamation is one way to do that. Instead of returning a region immediately, the owner moves it to a retired list. A maintenance phase waits until no worker can be using the region, then performs the unmap, discard, or remap. Epoch counters, quiescent-state reporting, or a simple barrier can establish that window. The cost is memory held slightly longer. The benefit is that the kernel performs the write-side operation once, with no concurrent faults racing against it and no repeated invalidation during the compute phase. For services with predictable request boundaries, a double-buffered or multi-slot arena works the same way: all slots are mapped up front, and the lifecycle operation is limited to switching which slot is active.

`madvise` needs the same discipline. `MADV_DONTNEED` discards pages and makes the next touch fault them back in. `MADV_FREE` is lazier, but it still changes the state of the mapping and can lead to later reclaim or zero-fill behavior. Neither is a harmless way to shrink a cache in a multithreaded program. If a worker calls discard on a range another worker is about to access, the second worker pays a fault that the first worker created. Release operations should be issued at quiescent points, and discard should be reserved for memory that the application can prove is cold. A maintenance thread that runs discard while the data plane is active is a fault generator with a scheduler of its own.

## Establishing residency with bounded concurrency

The most reliable way to avoid a parallel fault storm is to make residency a phase. The phase has a beginning, an end, a known concurrency level, and a barrier before the compute phase starts. It is not enough to call `MAP_POPULATE` or `madvise(MADV_WILLNEED)` and assume the mapping is ready. Those interfaces are useful, but their exact behavior depends on mapping type, kernel version, memory pressure, and whether the range is anonymous or file-backed. A phase with explicit completion criteria is more predictable than an advisory hint.

For anonymous memory that will be written, the completion criterion is simple: every page that workers will write has been written once during the population phase. That write allocates the page, zeroes it, installs the PTE, and places the page according to the faulting CPU under first-touch policy. The population phase should use a bounded pool of threads, each pinned to the CPU or node that will own the corresponding range. The pool size should be chosen to saturate the page allocator without oversubscribing the machine. More population threads are not automatically better. Past a point, they contend on page-table locks, allocator locks, and memory bandwidth for zeroing. The useful metric is pages established per second, not threads launched.

`MADV_POPULATE_WRITE` can perform the same commitment without a user-space write, and `MADV_POPULATE_READ` can establish read mappings for file-backed data. The advantage is that the population work is expressed as one operation per range rather than a loop of dummy writes. The disadvantage is that the call is synchronous and the range size is under application control. Large ranges can stall a population worker for a long time. Split the range into chunks that are large enough to amortize syscall overhead and small enough to preserve responsiveness. For file-backed mappings, population may wait on storage. Use a smaller concurrency limit for storage-bound population than for anonymous memory, or the population phase becomes an I/O queue with no backpressure.

Admission control is the missing piece in many designs. A fault storm is a burst of demand for pages. If the application can admit work only as fast as pages become resident, the burst never forms. The simplest form is a semaphore around the population step: a fixed number of workers may establish pages at once, and the rest wait before entering their data ranges. A more adaptive form is a token bucket that observes fault latency and reduces the number of outstanding page-establishment requests when latency rises. The point is not to throttle the compute phase forever. It is to prevent every worker from discovering a cold mapping at the same instant.

Thread startup is part of the same problem. Newly created threads receive stacks that are lazily mapped. The first deep call chain, the first large local array, or the first signal delivery can fault on stack pages. In a program that creates hundreds of threads at once, stack first touch becomes a startup fault burst that has nothing to do with the data mapping. Thread pools avoid repeated stack creation, and pre-touching a reasonable stack depth during thread initialization moves the cost to a controlled point. This is easy to overlook because the stack is not part of the application's explicit buffer layout. The kernel still sees it as anonymous memory and still allocates pages on first write.

Population also has a placement contract. If the population thread is not pinned, the scheduler can move it between nodes, and the page is placed on whichever node happened to be current at the fault. That makes first-touch placement noisy. Pin the population workers, or use explicit NUMA policy for the arena. If the workload later migrates its compute threads, the placement may no longer match. That is a scheduling decision, not a page-fault decision, but the two interact. A thread that migrates after population may pay remote-memory latency for pages that were correctly placed relative to its old CPU.

## Address-space layout that avoids accidental sharing

Partitioning data by thread is not enough if the partitions share page-table pages. On x86-64, a PTE page covers 2 MiB of virtual address space, and a PMD page covers 1 GiB. Two threads that touch addresses in the same PTE page can contend on the same page-table lock even if their data bytes are disjoint. This is the page-table analogue of false sharing. It does not show up in a cache-coherence profiler because the sharing is in kernel metadata, not in application cache lines. The fix is layout: align per-thread arenas to a PTE page boundary, and align large per-node regions to a PMD boundary when huge pages are in use.

The same reasoning applies to file mappings and fault-around. A file mapping may map a cluster of pages around the faulting address. If two threads fault on nearby offsets, the kernel may perform redundant mapping work and contend on the same page-cache structures. Aligning thread ranges to 2 MiB, or to the fault-around window, reduces the overlap. For small files or fine-grained partitions, alignment may waste address space. In that case, group small objects into larger per-thread arenas rather than assigning adjacent small objects to different threads. The arena becomes the unit of fault ownership.

VMA layout matters as well. Each distinct permission, mapping type, or `madvise` policy can require a separate VMA. A large number of small VMAs increases the work of address-space operations and can make the fault path walk a more complex tree. It is usually better to create a few large VMAs with uniform policies than many small ones with different flags. If per-thread arenas need different policies, group them by policy and by node. The goal is to keep the mapping structure stable and coarse during the compute phase, while retaining fine-grained ownership inside the mapped regions.

Guard pages and redzones are useful for correctness, but they are also mappings. A guard page per allocation can multiply VMA count and page-table work. Use guard regions at arena boundaries, not around every object, unless the debugging benefit justifies the cost. Similarly, repeatedly calling `mprotect` to toggle permissions on a region creates write-side address-space operations and TLB invalidations. If a region must be read-only during one phase and writable during another, make the transition at a barrier and keep the phase long enough to amortize the change.

## Work distribution after residency

Even with a fully resident mapping, work distribution can recreate faults indirectly. A work-stealing scheduler may hand a chunk to a thread on a different node from the one that first touched the data. The pages are resident, so there is no page fault, but the access is remote. If the scheduler responds by migrating threads or pages, the migration machinery can introduce faults of its own. The safer default for first-touch-sensitive data is owner-computes: the thread or node that established a region processes that region. Work stealing is still useful for load balance, but it should steal within a node or within an arena whose pages are interleaved by policy.

Dynamic chunk sizes interact with page granularity. A chunk that is smaller than a page can cause multiple workers to touch the same page, which is fine for correctness but bad for ownership and false sharing. A chunk that is not a multiple of the page size straddles page boundaries, so two workers may share the last page of one chunk and the first page of the next. Choose chunk sizes that are multiples of the base page size, and preferably multiples of the PTE-page span for large parallel scans. This is not just an alignment aesthetic. It ensures that ownership boundaries coincide with the kernel's translation boundaries.

For file-backed scans, the page cache is shared regardless of which thread reads which range. If the file is cold, the first thread to touch a page initiates I/O, and other threads that touch nearby pages may wait on the same readahead or page-cache locks. A bounded prefetch phase can fill the cache before the scan, but it must not issue an unbounded number of concurrent readahead requests. Use a fixed number of prefetch workers and a queue of ranges. If the storage cannot keep up, the scan will wait anyway; the prefetch phase at least makes the waiting visible and bounded rather than spreading it unpredictably through the compute phase.

## CPU quota and the cost of being in the kernel

On systems with CPU cgroups, fault handling consumes CPU time that counts against the cgroup's quota. A fault storm can therefore trigger CPU throttling even when the application's user-space work is modest. Once throttled, the cgroup is not allowed to run for the remainder of the period, including the threads that would have resolved faults or continued compute. The result is a feedback loop: kernel time from faults consumes quota, throttling lengthens the wall-clock time of the phase, and more threads pile up waiting for pages. The application may appear to have a memory problem when the immediate cause is CPU quota exhaustion.

Capacity planning should include system time. A workload that needs N cores for user-space compute may need additional CPU headroom during population, reclaim, and writeback. If the cgroup is sized only for steady-state compute, the startup phase will throttle. One remedy is to perform population before the cgroup reaches its steady-state CPU load, or to give the population phase a larger quota for a short window. Another is to reduce the number of concurrently faulting threads so that kernel work is spread over time rather than concentrated. The right choice depends on whether the service is latency-sensitive or throughput-oriented, but ignoring kernel CPU time is not neutral.

The scheduler adds its own queueing. A thread that takes a page fault blocks, and the kernel may run another thread on that CPU. If all runnable threads are faulting, there is no useful work to overlap with the fault latency. Oversubscribing the machine with workers makes this worse: more threads mean more concurrent faults, more context switches, and more pressure on the same kernel structures. A common mistake is to size the worker pool to the number of logical CPUs and then add extra threads for I/O or population. During a fault storm, those extra threads compete for the same CPUs and can delay the fault handlers that would drain the queue. Keep the total number of runnable, faulting threads bounded, and separate population concurrency from compute concurrency.

These mechanisms point to a single discipline: treat page residency, mapping changes, and CPU quota as shared resources with explicit phases and limits. The data plane can remain simple only if the control plane is designed rather than left to the scheduler and the fault handler.
