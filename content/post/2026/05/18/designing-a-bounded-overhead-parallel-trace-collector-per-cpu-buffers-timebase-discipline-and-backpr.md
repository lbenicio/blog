## The problem with tracing a moving target

Tracing a parallel program is not the same problem as logging a request in a web service. A web request produces a handful of structured records over milliseconds. A scheduler, lock library, memory allocator, or runtime event source inside a parallel program can produce records at a rate tied to the machine's instruction throughput, not to a human-visible transaction boundary. The collector must observe work that is already trying to saturate cores, caches, memory bandwidth, and I/O. Every instruction added to the producer path is contention with the workload being measured. Every lock added to the consumer path becomes a place where a worker can stall. Every unbounded queue converts a transient burst into a memory-pressure event.

The design goal is therefore not maximum fidelity at any cost. It is a defensible position on a three-way trade-off: overhead, completeness, and ordering. A useful parallel trace collector makes those choices explicit. It bounds its own instruction count on the producer fast path, bounds its memory footprint, and defines what happens when events outrun the drain path. If it cannot state those bounds, it is not a collector so much as an allocation-heavy diagnostic mode that happens to run concurrently.

This article describes a reference design for a bounded-overhead event tracer aimed at parallel runtimes and systems software. The design uses per-CPU or per-thread fixed-size ring buffers, batched draining, explicit timestamp discipline, and a loss policy chosen by the application. It is not a replacement for sampling profilers. Sampling answers questions about where time goes with statistical confidence. Tracing answers questions about sequences, interactions, and rare events. They have different cost profiles and different failure modes.

## Assumptions and workload model

The first design decision is to state the workload model. Without one, every requirement sounds reasonable and the implementation becomes a pile of conditionals.

Assume the following. Events are generated by instrumented code inside worker threads, runtime callbacks, or kernel-adjacent probes. Event rates are bursty rather than uniform. A mutex acquisition trace might be quiet for milliseconds and then produce a dense burst when a phase boundary releases hundreds of threads. Events have a small fixed maximum payload, perhaps a few machine words: an event type, a timestamp, a thread or CPU identifier, a couple of arguments, and maybe a call-site token. The collector must support a live drain path so that a separate consumer can write to disk or a network socket without forcing producers to perform those operations. The program may run on tens to hundreds of cores. The tracer may be enabled for a bounded experiment, not permanently in a production binary.

Those assumptions matter. A fixed maximum payload permits fixed-size slots and a ring buffer without per-event allocation. A live drain path decouples producer cost from I/O latency. Bursty generation argues for absorbing short bursts, but not for absorbing an unbounded storm. A bounded experiment permits a coordinated start and stop protocol, preallocated metadata, and a consumer that can be granted privileges or pinned to a CPU before measurement begins.

If the payload is variable-sized, the collector either copies into a ring of bytes with careful alignment and commit records, or it stores references to objects that must outlive the event. The second option is usually a trap in parallel systems: object lifetime becomes a synchronization problem, and the consumer may observe a reference after the producer has reused the memory. The first option is more work in the encoder, but it keeps the fast path self-contained. This design assumes a fixed-size record with optional tail bytes in a bounded byte ring; the initial implementation can start with fixed-size slots and add variable payloads only when the measurement question demands them.

The workload model also sets the success criterion. The tracer should not claim zero overhead. It should claim a bounded producer path whose cost is visible and measurable: a small number of stores, one timestamp read, a sequence reservation, and a branch on whether the ring has space. The collector should not claim lossless tracing under arbitrary load. It should claim that loss is detected, attributed, and reported rather than hidden.

## The cost model of an event

A trace event is not free just because it avoids `malloc`. The producer path touches several scarce resources.

First, it writes memory. The record itself consumes cache lines and eventually memory bandwidth. If each worker writes into a separate cache line, producers avoid false sharing but increase footprint. If workers share a cache line to save space, they create coherence traffic on every event. The design should keep producer-owned ring metadata on separate cache lines and pack event records densely inside the buffer.

Second, it reads a timestamp. Timestamp reads are not uniform. A system call such as `clock_gettime` may use a vDSO fast path, but it still involves a clock source and ordering concerns. A cycle counter is cheaper, but its interpretation is platform-dependent. On x86, an invariant TSC provides a constant-rate counter, but it is not a portable wall-clock source and its cross-socket synchronization is not something an application should assume without checking. On other architectures, equivalent counters have different stability and privilege characteristics. The collector needs a calibration step and a monotonic fallback.

Third, it updates shared state. A global atomic counter for event sequence numbers will become a cache-line ping-pong point. A global lock will serialize the very thing being measured. A per-thread counter avoids contention but complicates global ordering. A per-CPU counter avoids contention only if preemption is controlled or the producer can tolerate migration between reservation and commit. The collector should prefer per-producer sequence numbers and reconstruct global order at the consumer, not impose a total order on the producer fast path.

Fourth, it may generate a wakeup. Waking a consumer thread from the producer path is expensive and can cause scheduler interference. A better pattern is opportunistic draining: the consumer polls or sleeps on a timer, and the producer only performs a cheap notification when a threshold is crossed. The threshold should be a policy knob, not a hard-coded assumption about latency.

Finally, it may allocate. Allocation on the producer path is almost always the wrong default. Even a thread-local allocator can hit a slow path, and a slow path in a tracer is indistinguishable from a perturbation. Preallocate rings, metadata, consumer batches, and output buffers before the traced region begins.

## Reference architecture

The reference collector has four components: producers, per-producer rings, a drain coordinator, and a consumer pipeline. A control plane configures the experiment, records metadata such as CPU count, buffer sizes, clock calibration, and event schema identifiers, and then starts producers. Producers emit records into owned rings. The drain coordinator decides which rings to empty and when. The consumer pipeline decodes batches, orders or annotates them as needed, and writes output.

The important structural choice is that producers never write directly to the final output. Disk writes, compression, formatting, and network sends belong on the consumer side. Producers own a small region of memory and a local cursor. The consumer observes committed records and advances a tail. This is a single-producer, single-consumer ring per producer, not a multi-producer queue. That distinction removes most of the hard synchronization from the fast path.

A per-thread ring is the simplest ownership model. The producer uses thread-local storage to find its ring and writes without atomics except for the publish fence. The cost is memory: a ring per thread can be excessive if the runtime creates short-lived threads. A per-CPU ring is more compact and maps naturally to low-level probes, but it requires either disabling preemption around emission or accepting that a thread may be migrated between reservation and commit. The control plane must choose. For runtime-level events where the thread identity matters more than the CPU, per-thread is usually clearer. For kernel-adjacent or scheduler-level tracing, per-CPU is usually the right unit.

The consumer needs a way to discover committed records without reading a producer's private head on every poll. A common shape is a monotonically increasing head cursor with release semantics and a tail cursor owned by the consumer. The producer writes records into slots below the head reservation, then publishes the new head. The consumer reads the published head with acquire semantics, copies or decodes records up to that point, and advances the tail. Because the producer never overwrites beyond the consumer's tail, the ring must either be large enough for the worst tolerated backlog or must drop events when the gap between head and tail is too small.

This architecture deliberately separates ordering from transport. Transport order is per ring and therefore per producer. Global order is reconstructed by the consumer from timestamps and sequence metadata. If the consumer tries to enforce a single total order on the producer path, it reintroduces contention. If it ignores ordering entirely, the resulting trace may not answer questions about causality. The next sections examine the producer fast path, timestamp discipline, and the loss policy that connects them.

## Producer fast path: reservation, commit, and the shape of the hot loop

The producer fast path should look like a short, predictable function. It takes an event type, a few arguments, and a call-site token. It returns without allocating, without taking a lock, and without calling into the consumer. The implementation can be broken into four steps: locate the ring, read the timestamp, reserve a slot, and publish the record.

Locating the ring is a thread-local load in the per-thread design. In the per-CPU design, it is a read of the current CPU identifier followed by an index into an array of ring pointers. The per-CPU lookup is cheap on architectures that expose a CPU ID register, but it is not free, and it can change if the thread migrates. If the collector uses per-CPU rings and the runtime does not disable preemption around emission, the producer must re-read the CPU ID after the record is written and verify that it still matches the ring it reserved from. If it does not match, the record is in the wrong ring. A safer approach is to disable preemption for the few instructions of the fast path, or to use per-thread rings and let the consumer annotate CPU migration separately. The design should not pretend that per-CPU ownership is free; it is a trade of memory footprint and lookup cost for lower contention and better cache locality.

The timestamp read is the next decision. A cycle counter read is usually the cheapest source, but it is not a wall-clock timestamp. The collector should store the raw counter value in the record and defer conversion to the consumer. That keeps the producer path free of multiplication and division. The consumer has the calibration metadata and can convert raw ticks to nanoseconds in batches. If the platform does not provide a stable, invariant counter, the producer must fall back to a clock read. That fallback should be selected at configuration time, not on every event. A branch on a global flag is acceptable; a branch on a per-event capability check is not.

Reservation is where the ring's single-producer property pays off. The producer owns a head cursor. It does not need a compare-and-swap to claim a slot. It reads its cached tail, checks whether the distance from head to tail is less than the ring size, and if there is room, uses the slot at head and increments head. The cached tail is a lower bound on the consumer's progress. The producer refreshes it only when the space check fails. This avoids a load from the consumer-owned cache line on every event. When the check fails, the producer reads the real tail with acquire semantics. If there is still no room, the loss policy runs. If there is room, the cached tail is updated and the fast path continues.

Publishing the record is a release store of the new head. The record fields must be written before the head is published. On weakly ordered architectures, that means a release fence or a release store. On x86, a plain store followed by a compiler barrier is often enough for the head, but the collector should use the language's release semantics rather than rely on a specific memory model. The consumer reads the head with acquire semantics, then reads the record. If the consumer reads a head that includes a record, it is guaranteed to see the record's fields.

The hot loop should avoid function calls that are not inlined. A trace macro that expands to a few stores and a branch is easier to reason about than a general-purpose `trace_event` function with a switch on payload size. If the collector supports multiple payload sizes, the encoder can be a small inline function with a compile-time size parameter. The call-site token should be a constant integer or a pointer to static metadata, not a string. String formatting belongs on the consumer side. The producer should never call `printf`, allocate a formatted buffer, or take a lock to update a global event count.

## Timestamp discipline: local counters, calibration, and ordering domains

A trace without a defensible timebase is a sequence of anecdotes. The collector must define what its timestamps mean, how they are compared across producers, and what happens when the underlying clock is not comparable.

The first rule is that the producer stores a raw timestamp from a single source per clock domain. A clock domain is a set of CPUs or threads whose counters can be converted to a common timebase with a known offset and skew. On a single-socket x86 machine with an invariant TSC, the domain may be all cores. On a multi-socket machine, the TSC may not be synchronized across sockets, and the collector must either calibrate per-socket offsets or treat each socket as a separate domain. On ARM and other architectures, the counter may be per-core and may not be synchronized at all. The collector should not assume that two counters read at the same instant produce the same value.

Calibration happens before tracing starts. The control plane rendezvouses the producers, reads a reference clock, and reads each producer's local counter. The difference between the reference clock and the local counter gives an offset. Repeating the rendezvous a few times gives an estimate of skew. The calibration data is written into the trace metadata. The consumer uses it to convert raw ticks to nanoseconds. If the calibration shows that counters are not stable or not synchronized, the collector should either fall back to a global clock source or mark the trace as having per-domain time. Marking is better than silently producing a misleading merged timeline.

The producer path should not perform calibration or conversion. It should not call `clock_gettime` if a local counter is available. It should not compute a nanosecond timestamp by multiplying by a frequency. It should store the raw counter and a small clock-domain identifier if the domain is not implicit from the ring. The domain identifier can be packed into the record header or derived from the ring's metadata. The consumer already knows which ring produced the record, so it can look up the domain. That avoids an extra field in the common case.

Ordering across producers is the hard part. If all producers share a synchronized counter, the consumer can merge records by timestamp. If they do not, timestamp order is only valid within a domain. The collector should provide a way to express causality that does not depend on clock synchronization. One option is a per-producer sequence number and a small set of cross-producer tokens. For example, a lock acquisition event can carry the address of the lock and the sequence number of the previous holder. The consumer can reconstruct the wait-for graph without a global timestamp order. Another option is to use a logical clock per domain and a synchronization event when domains interact. That is more work, but it is honest about what the clocks can prove.

The consumer should not sort the entire trace in memory. A global sort is an unbounded operation and defeats the bounded-overhead goal. Instead, the consumer can maintain a small merge window. It reads batches from rings, inserts them into a bounded heap keyed by timestamp, and emits records once the window is large enough or a timeout expires. The window size is a policy knob. A larger window improves ordering at the cost of latency and memory. A smaller window reduces latency but may emit records out of order. The trace metadata should record the window size and the ordering guarantee, so downstream analysis knows what it is looking at.

## Backpressure and loss: making the bound explicit

The ring is the bound. When the producer cannot reserve a slot, the collector must do something that is both cheap and visible. The wrong answer is to block. Blocking the producer turns the tracer into a synchronization point and changes the behavior being measured. The wrong answer is also to allocate a larger buffer on demand. That converts a burst into a memory-pressure event and makes the overhead unbounded. The right answer is a loss policy chosen by the application and reported in the trace.

The simplest policy is drop-newest. The producer increments a per-producer lost counter and returns. The record that could not fit is discarded. Earlier records remain in the ring and will be drained. This policy preserves the beginning of a burst and loses the tail. It is easy to implement and easy to explain. The lost counter is a single non-atomic increment in the single-producer case, or a relaxed atomic increment if the consumer reads it concurrently. The producer should also record the timestamp of the first and last lost event in a small loss metadata block. That block is written only when loss occurs, so it does not affect the common path. The consumer reads the block when it drains the ring and emits a synthetic loss record that says, for example, 'producer 7 lost 1,234 events between t1 and t2.' That record is part of the trace, not a side channel.

Drop-oldest is another option. The producer overwrites the oldest unread record and advances the tail. This keeps the most recent events, which is useful for debugging a crash or a hang. It is more complex because the producer now writes the consumer-owned tail and the consumer must detect that records were overwritten. The ring needs a generation or sequence number per slot so the consumer can tell whether a slot still contains the record it expects. Drop-oldest is a valid policy, but it should not be the default. It makes the consumer's job harder and can produce a trace that looks complete but has holes.

A third option is to switch to sampling when the ring is full. The producer increments a counter and emits every Nth event. This keeps the trace bounded and still provides a statistical view of the storm. The sampling rate can be fixed or adaptive. Adaptive sampling requires the producer to read a shared rate, which adds a load and a branch. A fixed rate chosen at configuration time is cheaper. The trace metadata must record the sampling policy and the rate, otherwise the consumer will misinterpret the event counts.

The collector should also support a fail-fast policy for experiments where loss invalidates the result. In that mode, the producer sets a global abort flag and the control plane stops the experiment. The abort flag is checked by the consumer and by the control plane, not by every producer on every event. The producer only sets it when loss occurs. This gives the application a way to say, 'I would rather have no trace than a lossy one,' without paying for a check on the hot path.

Backpressure from the consumer is inevitable when the output device is slower than the event rate. The consumer should not hide this. It should expose metrics: ring fill levels, drain rates, loss counts, and output queue depth. If the consumer cannot keep up, the rings fill and the producer loss policy runs. That is the correct behavior. The alternative, an unbounded queue between consumer and output, only moves the problem and makes memory usage unpredictable. The consumer should use a bounded output buffer and a policy for what to do when it is full. It can block, which causes rings to fill and producers to drop, or it can drop low-priority records. Either way, the loss is accounted for.

## Draining, batching, and consumer-side ordering

The consumer's job is to turn committed records into a stream that can be written to disk, sent over a network, or analyzed in memory. It should do this in batches. Reading one record at a time from a ring is inefficient because it touches the same cache lines repeatedly and advances the tail too often. A batch of 32 or 64 records amortizes the cost of the head load, the tail store, and the output write.

The drain loop for a ring is straightforward. The consumer reads the producer's head with acquire semantics. It compares the head to its own tail. If the distance is zero, the ring is empty. If the distance is positive, it computes the number of records available, capped by the batch size. It reads those records, decodes them, and appends them to an output batch. After the records are safely copied or written, it advances the tail with release semantics. The producer will eventually see the new tail when it refreshes its cached tail.

The consumer should not advance the tail until the records are no longer needed. If the output batch holds references into the ring, the tail cannot advance until the output is flushed. That is a dangerous coupling. The safer design is to copy records into the output batch, or to decode them into a compact form that does not reference the ring. Copying costs memory bandwidth, but it decouples the ring from the output path. If the records are small and the output batch is preallocated, the copy is predictable and cache-friendly.

Ordering on the consumer side can be done in stages. The first stage is per-ring ordering, which is free because the ring is a FIFO. The second stage is cross-ring ordering. If the clocks are synchronized, the consumer can use a merge window. If the clocks are not synchronized, the consumer should preserve per-domain order and annotate cross-domain relationships with causality tokens. The third stage is output ordering. If the output format requires a total order, the consumer can sort within the merge window. If it does not, the consumer can write records in arrival order and let the analysis tool handle ordering. The collector should not force a total order on the producer path just to make the output pretty.

The consumer should also handle metadata. At the start of the trace, it writes the schema, the clock calibration, the CPU topology, and the ring configuration. At the end, it writes the final loss counters and any abort reason. If the consumer crashes, the metadata should be recoverable from the ring headers. A ring header can contain a magic number, a version, a producer ID, a clock domain ID, and a pointer to the event schema. That makes the raw buffers self-describing enough for a post-mortem tool.

## Sizing, tuning, and what to measure

Sizing starts with the burst. The ring must hold the largest burst that the application wants to capture without loss. If the burst is 10 million events over 10 milliseconds and the consumer can drain 1 million events per second, the ring needs to hold about 9.9 million events minus what the consumer drains during the burst. That is a large ring. If the application cannot afford that memory, it must accept loss or reduce the event rate. The collector should make this arithmetic visible in the configuration tool. A ring size that is chosen by guesswork will either waste memory or drop events.

The slot size is the next factor. A 32-byte slot packs an event type, a 64-bit timestamp, a 32-bit producer ID, a 32-bit call-site token, and two 64-bit arguments. A 64-byte slot adds more arguments or a longer payload. The ring size in bytes is the slot size times the number of slots. If the ring is a byte ring with variable-length records, the sizing is more complex because a large record can consume multiple slots and alignment padding can waste space. The fixed-slot design is easier to size and easier to reason about. Start there.

The consumer's throughput must be measured, not assumed. Decoding, formatting, and writing to disk are all slower than reading from the ring. A consumer that can process 500,000 events per second will not keep up with a producer that emits 5 million events per second. The collector should include a benchmark mode that runs the producer and consumer without the traced workload. That gives a baseline for the maximum sustainable rate. The application can then compare its event rate to that baseline and choose a loss policy.

The overhead of the producer path should be measured in cycles per event. A microbenchmark can run the fast path in a loop with tracing enabled and disabled. The difference is the tracing overhead. It is not a single number; it depends on whether the ring is empty, whether the consumer is draining, and whether the timestamp source is a cycle counter or a clock read. The collector should report a distribution, not just an average. The worst case is the case that matters for tail latency.

Finally, the collector should expose its own health. A trace that silently drops 30% of events is worse than a trace that says it dropped 30%. The control plane should provide a summary at the end: total events, events per producer, loss counts, ring high-water marks, clock domain warnings, and output queue overflows. That summary is part of the experiment result. It tells the analyst whether the trace can answer the question it was collected for. A bounded-overhead collector is not one that never loses events. It is one that knows its bounds and reports when it hits them.

## Preemption, migration, and the per-CPU ownership contract

A per-CPU ring is only single-producer if the collector can guarantee that exactly one execution context writes to it at a time. In user space, that guarantee is often unavailable. The scheduler can preempt a thread between the reservation of a slot and the publication of the head. If the ring is per-CPU and shared by all threads that run on that CPU, a second thread can be scheduled on the same CPU and begin writing to the same ring while the first thread is suspended. The ring is now multi-producer, and the simple head/tail protocol is no longer correct. The first thread may have reserved a slot but not written it; the second thread may reserve the next slot and publish a head that includes the first thread's unwritten slot. The consumer can then read a record that was never completed.

There are three ways out. The first is to disable preemption around the fast path. In kernel code, this is a standard and cheap operation. In user space, it is not generally possible without privileges, and even with privileges it can distort the scheduler behavior being measured. The second is to make the ring multi-producer. That reintroduces atomic claims or per-slot commit flags, which raises producer cost and complexity. The third is to use per-thread rings and accept the memory cost. For most user-space parallel runtimes, the third option is the most honest. It preserves the single-producer invariant without asking the scheduler to cooperate.

If the collector does use per-CPU rings, it should treat the CPU identifier as part of the event metadata rather than as the ring owner. A thread can emit into a per-thread ring and record the CPU it was running on at the time of the event. The consumer can then aggregate by CPU if needed. This avoids the migration problem entirely. The cost is one extra field in the record and a CPU ID read on the producer path. That read is usually cheaper than the synchronization required to make a shared per-CPU ring safe.

Migration also affects timestamp interpretation. If a thread emits events while migrating between CPUs, and each CPU has its own clock domain, the thread's events may appear to jump backward or forward in time. The collector should record the clock domain identifier with each event, or at least with each ring. If the thread stays on one ring but migrates across domains, the ring's domain is no longer sufficient. In that case, the record needs a domain field, or the collector must treat the thread as a domain of its own. The latter is simpler if the thread's timestamp source is a per-thread counter, but most hardware counters are per-CPU or global.

A practical compromise is to pin the producer threads to CPUs for the duration of the experiment and use per-CPU rings with preemption disabled by pinning and priority. That is not a general solution, but it is a defensible one for a bounded experiment. The control plane can record the pinning policy in the metadata. If a thread migrates anyway, the collector can detect it by comparing the CPU ID at reservation and at commit. If they differ, it can mark the record as suspect or drop it according to policy. This is another place where an explicit bound beats a silent assumption.

## Control plane: start, stop, and metadata that survives failure

The control plane is not on the hot path, but it determines whether the hot path can be trusted. It must perform four jobs: allocate and initialize rings, calibrate clocks, synchronize the start of producers, and finalize the trace. Each job has failure modes that can corrupt the trace if ignored.

Allocation should happen before any producer is allowed to emit. The control plane allocates each ring, its header, and the consumer's batch buffers. It writes a magic number, a format version, a producer identifier, a clock domain identifier, and the ring capacity into the header. It also writes a pointer or offset to the event schema. The schema describes the event types, the payload layout, and the call-site tokens. Without the schema, the raw records are just bytes. The schema should be written once and referenced by all rings. If the trace is written to a file, the schema can be a separate section at the beginning. If the trace is streamed, the schema should be sent before any records.

Calibration should happen after allocation and before the start signal. The control plane rendezvouses the producers on a barrier, reads a reference clock, and reads each producer's local counter. It repeats this a few times to estimate offset and skew. The results are stored in the metadata. If a producer's counter is not stable, the control plane should mark that domain as untrusted and either exclude it from cross-domain ordering or fall back to a global clock. The fallback should be chosen before tracing starts, because changing the timestamp source mid-trace creates a discontinuity that the consumer cannot resolve without additional metadata.

The start signal should be a release store to a shared epoch counter or a per-producer start flag. Producers spin or block until the flag is set, then begin emitting. The control plane should not start producers one by one with a system call per producer if the experiment is sensitive to start skew. A barrier or a broadcast flag is better. The start skew should be measured and recorded. If the application cares about events in the first few microseconds, the start skew is part of the measurement error.

Stopping is the reverse. The control plane sets a stop flag. Producers observe it on their next event and stop emitting. The consumer continues to drain until all rings are empty or a timeout expires. Then the control plane writes the final loss counters, the stop timestamps, and a summary. If the consumer crashes, the rings still contain the committed records and the headers still contain the configuration. A post-mortem tool can scan the headers, find the rings, and recover whatever was published. This is why the ring header should be self-describing and why the producer should publish the head only after the record is complete.

The control plane should also handle the case where a producer dies without finalizing. A thread that exits should mark its ring as closed. The consumer can then drain the ring and treat the missing finalization as an abnormal end. If the thread is killed, the ring may contain a partially written record. The head publication protocol prevents the consumer from seeing a partial record, but it does not prevent the producer from reserving a slot and dying before writing it. The consumer will simply not see that slot because the head was never advanced. The slot is wasted, but the trace is not corrupted. The control plane can detect the waste by comparing the head and tail at finalization.

## Portability notes: fences, atomics, and clock sources

The collector should be written against a memory model, not against a particular CPU. The producer publishes the head with release semantics and the consumer reads it with acquire semantics. The producer's cached tail is a relaxed load. The consumer's tail update is a release store. These are the minimum requirements. On x86, many of these operations compile to plain loads and stores, but the source should still express the intent. On weakly ordered architectures, the compiler and CPU need the explicit ordering to avoid reordering the record writes after the head publication.

The record fields themselves do not need atomic types if they are only written by the producer and read by the consumer after the head is acquired. The head publication acts as the synchronization point. The loss counters, however, may be read by the consumer while the producer is incrementing them. They should be relaxed atomics or per-producer counters that the consumer reads only after the producer has stopped. A relaxed atomic increment is cheap on most architectures, but it is not free. If the loss counter is only read at finalization, it can be a plain per-producer counter. If it is read live for monitoring, it should be atomic.

Clock sources are the least portable part. The collector should define an interface with at least two implementations: a fast local counter and a portable clock. The fast counter is selected when the platform provides a stable, invariant, synchronized source. The portable clock is the fallback. The selection should be made at configuration time and recorded in the metadata. The producer should not branch on the clock source per event. If the fast counter is unavailable, the producer uses the portable clock for all events in that domain.

The calibration step should test for invariance. A counter is invariant if its frequency does not change with CPU frequency scaling. It is synchronized if two CPUs read the same value at the same instant within a known tolerance. The collector can test invariance by reading the counter before and after a busy loop and comparing the elapsed counter ticks to a reference clock. It can test synchronization by having two producers read their counters while a barrier is held and comparing the values. If the test fails, the collector should not pretend the counters are comparable.

## Validating the bound: microbenchmarks and adversarial tests

A bounded-overhead collector must be tested under conditions that try to break the bound. The first test is the empty-ring fast path. The producer emits into a ring that the consumer is draining as fast as possible. The measured cost is the best-case overhead. The second test is the full-ring fast path. The consumer is stopped, and the producer emits until the ring is full. The measured cost includes the loss policy. The difference between the two is the cost of the space check and the loss branch.

The third test is the burst test. The producer emits a dense burst while the consumer drains at a fixed rate. The collector should report the loss count and the ring high-water mark. The fourth test is the slow-consumer test. The consumer is deliberately slowed, and the producer continues. The rings should fill, the loss policy should run, and the reported loss should match the number of events that could not be drained. If the reported loss does not match, the accounting is wrong.

The fifth test is the preemption test. A high-priority thread is used to preempt the producer between reservation and commit. If the collector uses per-CPU rings without preemption control, this test should expose the race. If it uses per-thread rings, the test should show no corruption. The sixth test is the migration test. The producer is allowed to migrate across CPUs. If the collector records the CPU ID, the trace should show the migration. If the timestamps jump, the metadata should explain why.

The seventh test is the clock-skew test. The collector is run on a machine with unsynchronized counters, or the counters are artificially skewed. The consumer should either correct the skew using calibration or mark the domains as separate. A trace that silently interleaves unsynchronized timestamps is not a valid trace. The eighth test is the crash test. The consumer is killed mid-trace. A post-mortem tool should recover the committed records from the rings and the metadata from the headers. The recovered trace should be missing only the records that were never published.

These tests are not a substitute for measuring the actual workload. They are a way to establish that the collector's bounds are real. The application should still run a pilot experiment with tracing enabled and disabled, compare the event rate, and check the loss summary. If the pilot shows unacceptable loss, the application can reduce the event rate, increase the ring size, or change the loss policy. The collector's job is to make those choices visible, not to hide them behind an unbounded queue.

## Loss descriptors: representing absence without inventing events

A loss counter tells the analyst that something vanished, but it does not say which sequence range vanished, whether the loss was contiguous, or which policy produced it. For causality questions, absence is data. The collector should represent it with the same discipline as a normal record.

The cleanest unit is a per-producer loss descriptor array with a fixed number of slots, allocated before the experiment. Each descriptor describes one coalesced loss interval: first attempted sequence number, last attempted sequence number, first and last raw timestamp, dropped count, reason code, policy epoch, and a small flags word. The array is not in the event ring. Writing a loss descriptor into a full ring would fail exactly when it is needed. The descriptor array sits on its own cache line, owned by the producer, and is published to the consumer through a version counter or a release store to a valid flag.

Attempted sequence numbers are the key to making gaps visible. The producer increments a per-ring attempt counter for every trace call, whether or not a slot is reserved. A successful record carries the attempt sequence number in its header. A dropped call also increments the attempt counter and updates the open loss descriptor. The consumer can then compare the sequence numbers of surviving records and see that, for example, sequence 1043 is followed by sequence 1198, and the loss descriptor explains the interval 1044 through 1197. If sequence numbers were assigned only to committed records, the consumer would see a dense sequence and have no way to align it with the loss counter. The extra increment on the producer path is a local operation on producer-owned memory, not a shared atomic. It is part of the overhead budget, not an afterthought.

Coalescing keeps the descriptor array bounded. When a call cannot reserve a slot, the producer examines the most recent open descriptor. If it has the same reason, the same policy epoch, and its last attempted sequence is exactly one less than the current attempt, the producer updates the descriptor count, last sequence, and last timestamp. Otherwise it closes the current descriptor and opens the next slot. A timestamp gap threshold can also force a close, so that a loss interval spanning a long quiet period is reported as separate intervals. When the descriptor array is full, the producer does not allocate. It increments an overflow count and a per-reason aggregate, then either merges the new interval into the last descriptor by widening its range or sets an overflow flag that tells the consumer the descriptor list is incomplete. The aggregate remains exact even when the interval detail is coarse. The trace metadata should state the descriptor capacity and the overflow policy.

The loss path can afford a seqlock because it is cold. The producer writes the descriptor fields, then publishes a new version. The consumer reads the version before and after copying the descriptor; if the version changed or is odd, it retries. If live monitoring reads descriptors while the producer is still running, a bounded retry is enough. At finalization, the producer publishes a final version and the consumer can read without retrying. The descriptor fields themselves do not need to be atomic. The version publication is the synchronization point.

The consumer turns each descriptor into a synthetic loss record in the output stream. The synthetic record should have its own event type, not a fake normal event. It should appear at the position where the first missing event would have appeared, which means the consumer must use the sequence numbers, not just arrival order. If the consumer maintains a merge window, it can place the loss record before the first surviving record whose sequence is greater than the descriptor's first attempted sequence. If the window is too small to decide, it can place the loss record at the batch boundary and mark it with the sequence range. Downstream analysis can still reconstruct the gap from the sequence numbers. The important rule is that synthetic loss records are counted separately from real events. A trace summary that adds them to the event count hides the loss.

Loss descriptors also need to distinguish reasons. A ring-full drop is not the same as a sampling decision or a consumer-side discard. Reason codes should be stable integers defined in the schema: ring full under drop-newest, ring full under drop-oldest, sampling skip, class disabled by degradation, consumer output shed, and timestamp source failure. Each reason has a policy epoch. If the control plane changes the loss policy in the middle of a trace, the epoch changes and descriptors from different epochs are not merged. Without the epoch, the analyst cannot tell whether a gap means the ring was undersized or the collector deliberately reduced fidelity.

Drop-oldest needs special handling because the overwritten range is not a simple tail gap. The producer advances the tail and overwrites slots. The descriptor should record the overwritten sequence range and the generation of the slot at the time of overwrite. The consumer, when it reads a slot, checks the slot generation against the sequence it expected. If the generation is newer, the slot was reused and the consumer has already missed it. The loss descriptor can then be validated against the observed sequence jump. This is more complex than drop-newest, which is one reason drop-newest should be the default. Drop-oldest is a flight-recorder policy, not a general-purpose backpressure policy.

## Bounded output: the second ring and the shape of backpressure

The producer rings are only the first bound. A collector can have perfectly bounded producer rings and still allocate without limit between the drainer and the writer. The output path needs the same treatment: fixed batch buffers, a fixed ready queue, and an explicit policy for what happens when the writer cannot keep up.

A simple structure is a pool of batch buffers with four states: free, filling, ready, and writing. The drainer owns filling buffers. It copies records out of producer rings into a filling buffer, decodes or annotates them as needed, and when the buffer reaches a size threshold or a flush deadline, it moves the buffer to a single-producer, single-consumer ready queue. The writer thread owns writing buffers. It dequeues a ready buffer, writes it to the output device, and returns it to the free pool. The ready queue has a fixed number of entries. The free pool has a fixed number of buffers. No stage allocates memory after the start signal.

This structure makes backpressure visible and local. If the writer stalls, the ready queue fills, the drainer runs out of free buffers, and the drainer stops reading producer rings. The rings then fill and the producer loss policy runs. That is the intended propagation. The alternative, letting the drainer allocate another buffer when the pool is empty, moves the failure to the allocator and makes the collector's memory footprint depend on the output device's latency. The collector should not do that.

The writer should be a separate thread or a separate event loop stage, not a function called inline by the drainer. A blocking disk write inside the drainer would prevent the drainer from advancing tails and serving other rings, even when some rings still have free space. A separate writer allows the drainer to keep reading until the output queue is full. It also gives the control plane a place to apply a timeout: if the writer has not made progress for a configured interval, the control plane can mark the trace as truncated and stop the experiment rather than waiting forever.

The batch size is a latency and memory knob. A large batch amortizes the tail update and the write syscall, but it increases the time between a record entering the ring and the record being durably written. It also increases the amount of memory tied up in the output queue. A small batch reduces latency but increases per-batch overhead. The batch size should be chosen together with the flush deadline. A 256 KiB batch and a 10 ms deadline are a reasonable starting point for file output; a network sink may need a smaller batch and a different deadline. The metadata should record both values.

Kernel buffering is part of the bound only if the collector accounts for it. A buffered file write returns after copying data into the page cache. The page cache can grow and the kernel can write back later. If the collector treats a successful write as durable progress, it may continue producing while the kernel accumulates dirty pages. That is not an unbounded userspace queue, but it is still memory that the experiment can exhaust. The control plane should either use a bounded kernel buffer, apply periodic writeback or sync points, or record the dirty-page limit as part of the experiment contract. For network output, the socket send buffer is bounded by the socket option, but the collector must still set it and handle `EAGAIN` or a blocking send. A nonblocking send that retries forever is an unbounded busy loop. A nonblocking send that drops batches needs consumer-side loss records.

Consumer-side dropping should be an explicit mode, not an accident. In the default backpressure mode, once a record is copied out of a producer ring, it is committed to the output. If the output queue is full, the drainer stops. In a flight-recorder or best-effort mode, the drainer may discard entire batches to keep the producer rings moving. That mode needs its own loss descriptors, counted separately from producer loss. It should also record which stage discarded the data: decode, ordering, encoding, or write. Without that attribution, the summary cannot distinguish an undersized producer ring from an undersized output queue. Most experiments should start in backpressure mode, because it keeps the loss in one place and makes the sizing arithmetic honest.

The output queue also needs a drain policy for metadata. Schema records, clock calibration, and loss summaries should not compete with event batches for the same queue if the writer is stalled. A small reserved control channel or a reserved control section in the output file is better. If the writer never drains the control channel, the trace is already lost. The control plane should write metadata to the file header or a sidecar before the event stream, not enqueue it behind millions of event batches. At finalization, the loss summary can be appended if the writer is alive; otherwise the ring headers and loss descriptors must contain enough information for recovery.

## Admission control, degradation ladders, and the experiment contract

A bounded collector still needs a decision about how many events the experiment is allowed to ask for. That decision belongs to admission control, not to the ring buffer. Before tracing starts, the control plane should compute a budget from the event schema, the number of producers, the ring sizes, the consumer throughput, and the output bandwidth. The budget should be written into the metadata as an explicit contract: maximum event rate, maximum encoded bytes per second, maximum memory, maximum acceptable loss, timebase confidence, and ordering guarantee.

Admission control works best at the event-class level. Each class has an identifier, a priority, and a cost estimate. A high-rate class that is useful only in aggregate can be assigned a counting mode: the producer increments a per-thread counter and emits a summary record at a phase boundary, rather than emitting one record per occurrence. A class that is useful only for rare events can be enabled permanently because its expected rate is low. A class that is useful for burst analysis can be enabled with a fixed sampling rate chosen before the run. The instrumentation site should check the class enable word before evaluating expensive arguments. A trace macro that formats a string and then checks whether tracing is enabled has already paid most of the cost.

The degradation ladder should be explicit and recorded. A typical ladder is: full fidelity; fixed-rate sampling of low-priority classes; counting mode for high-rate classes; disabling low-priority classes; drop-newest with loss descriptors; and, if the experiment requires lossless data, aborting the experiment. Each transition has a policy epoch. If transitions happen asynchronously, the consumer needs to know which epoch produced each record. That can be done with a per-record epoch field, but it adds a field to every event. A cheaper approach is to perform transitions at phase boundaries with a barrier, then publish the new epoch in the ring header. Producers update their local configuration at the barrier. Records before and after the barrier belong to different epochs, and the consumer can split the stream at the barrier record. If a transition must happen asynchronously, the collector should pay for a per-record mode bit only on classes that can be sampled or disabled. It should not add a mode word to every event just to support a rare policy change.

Sampling needs its own accounting. A fixed-rate sampler that emits every Nth event should record the sampling period and the phase. The consumer can then estimate the true count, but it should not present the sampled count as exact. If the sampler uses a per-thread counter, the phase differs per producer and the combined estimate needs the per-producer period. If it uses a global counter, the counter becomes a contention point. The per-thread counter is the right default. The loss descriptor should not be used for sampling skips if the sampling is expected; a separate skip counter is clearer. Loss means the collector intended to record an event and failed. Sampling means the collector never intended to record it. Mixing the two makes the loss rate meaningless.

The experiment contract is also a validation tool. At the end of the run, the control plane can compare observed values to the declared budgets: peak ring occupancy, total loss, loss by reason, producer cycles per event, output queue high-water mark, writer stall time, start skew, and clock-domain warnings. If the observed values exceed the contract, the trace is still useful, but its claims are weaker. The summary should say which budget was exceeded and by how much. That is more honest than a single pass/fail flag, and it gives the analyst a reason to reduce the event rate or increase the buffer for the next run.

The contract should not be a marketing number. A producer overhead budget of a few dozen cycles per event may be achievable on one machine with a cycle counter and an empty ring, but not on another machine with a clock read and a nearly full ring. The collector should report the conditions under which the number was measured. A trace collected under sustained loss is not a full-fidelity trace, even if the producer fast path was fast. The bound that matters is the bound on the whole experiment: memory, loss, and timebase confidence, not just the instruction count of one function.
