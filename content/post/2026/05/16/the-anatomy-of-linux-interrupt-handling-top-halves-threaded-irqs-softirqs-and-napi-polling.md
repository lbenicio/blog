## Why the interrupt path is a design problem

Every I/O completion in a Linux system — a packet arriving, a block read finishing, a timer expiring — ends in an interrupt or in a polling loop that stands in for one. The code that runs in response is among the most constrained code in the kernel: it executes on a small stack, it runs while the local CPU's interrupt delivery is at least partly disabled, it cannot sleep, and it shares the machine with every other device. Getting it wrong rarely produces a crash. It produces tail latency, dropped packets, and throughput ceilings that only appear under load.

The design problem is about *where to do work*. Interrupt context is the only place where the kernel is guaranteed to be told promptly that a device needs attention, but it is the worst place to do anything expensive. Linux resolves this with a two-part structure: a hard IRQ handler — the "top half" — that acknowledges the device and captures the minimum state needed to make progress, followed by a deferred mechanism — the "bottom half" — that does the real work in a context with fewer restrictions.

Linux does not have one bottom-half mechanism. It has several, with materially different concurrency and latency properties, and choosing among them is the central design decision in a driver. The choice is not cosmetic: it determines whether two CPUs can process the same kind of work simultaneously, whether the work can block on a mutex, whether it can be preempted by a higher-priority task, and how much of the system's latency budget it can consume before something else starts dropping work.

This article follows the whole path: hardware delivery, the generic IRQ layer that abstracts it, the top-half contract, the softirq/tasklet/workqueue/threaded-IRQ family, NAPI's polling hybrid, interrupt affinity, and the observability machinery that makes the behavior measurable.

## The hardware path, briefly

A device signals the CPU in one of two ways. Legacy INTx uses a physical line wired to an interrupt controller; the line is shared, level- or edge-triggered, and the controller reports the assertion to the CPU. MSI and MSI-X are message-signaled: the device performs a memory write to a special address. On x86 the address encodes the destination local APIC ID and the payload encodes the vector. MSI-X gives each device a table of vectors, each with its own address/data pair and its own mask bit, which is why modern multi-queue devices can spread interrupts across CPUs without any shared-line arbitration at all.

When interrupt remapping is enabled (Intel VT-d or AMD-Vi), the write is translated by the IOMMU's interrupt remapping table before it reaches the APIC. The table validates that the device is permitted to use the vector and rewrites the destination. Without remapping, a device that can write to memory can inject arbitrary vectors; with it, MSI is no less trustworthy than a physical line.

The local APIC on the target CPU receives the message, compares its priority against the processor priority register, and if it is allowed to proceed, interrupts the core. The core finishes (approximately) the instruction in flight, pushes a minimal frame, and reads the interrupt descriptor table entry for the vector. On x86-64, vectors 0–31 are reserved for exceptions and 32–255 are available to devices. Linux installs the device entries as interrupt gates, which clear the interrupt flag: the handler begins with interrupts disabled on that CPU. A handful of vectors — NMI, double fault, machine check, debug — use the Interrupt Stack Table so that they can run even if the current kernel stack is unusable.

## The generic IRQ layer

Between the architecture-specific entry code and a driver's handler sits a portable abstraction whose broad shape has been stable since the 2.6.19 rework. Its components are worth naming because they explain most of the behavior you observe at runtime.

`irq_desc` is the per-interrupt descriptor: the flow handler that drives the state machine for this line, the `irq_chip` that knows how to manipulate the hardware, the lock, the status bits, and a linked list of `irqaction` structures — one per registered handler. `irq_chip` is the driver-facing view of the interrupt controller: `irq_mask`, `irq_unmask`, `irq_ack`, `irq_eoi`, `irq_set_type`, `irq_set_affinity`, and friends. `irq_domain` maps hardware interrupt numbers to Linux IRQ numbers, and modern systems use hierarchical domains: a top-level domain for the main controller, with child domains for GPIO expanders, MSI controllers, and similar.

The flow handler is the piece that most often surprises people. It is not the device driver's code; it is the state machine that decides when to mask, when to acknowledge, and when to call the handlers. `handle_level_irq` masks the line before invoking the handlers and unmasks it after, because a level-triggered line stays asserted until the device is serviced. `handle_edge_irq` masks the line, acknowledges it, and unmasks when no further edges are pending. `handle_fasteoi_irq` calls the handler first and sends the end-of-interrupt afterwards, which is the model most modern controllers and MSI use. `handle_percpu_devid_irq` handles per-CPU interrupts where the vector itself identifies the device, so no shared action chain is involved. Getting the flow handler wrong for a given controller produces either missed interrupts or interrupt storms, and it is the kind of bug that only manifests on specific hardware.

## What hard IRQ context actually forbids

The top half runs in a context with properties that are easy to state and easy to violate:

- **It cannot sleep.** No mutexes, no `GFP_KERNEL` allocation, no blocking I/O, no waiting on a completion. Sleeping in interrupt context is not a subtle failure; it is a "scheduling while atomic" splat and usually a dead system.
- **It runs with interrupts disabled on the local CPU.** Other CPUs are unaffected, which is why per-CPU data is safe to touch and shared data is not. On the CPU running the handler, no other interrupt can preempt it, apart from NMI-class events.
- **Its stack is small.** Kernel stacks are on the order of 8–16 KiB depending on architecture and configuration, and on some architectures interrupt handlers run on a separate stack of similar size. Deep call chains and large on-stack buffers are a real hazard.
- **It has no user context.** You cannot copy to or from userspace, and you cannot rely on the current task being the one that submitted the I/O.
- **It blocks progress for everything else on that CPU.** Every microsecond spent in the handler is a microsecond of added latency for the scheduler, for other devices, and for the network stack.

The last point is the one that drives the whole design. A handler that takes 50 microseconds and fires 200,000 times per second on a single CPU consumes ten seconds of CPU time per second — it cannot keep up, and the system livelocks in interrupt context. The kernel's response is to bound the work done per interrupt and to push the rest into a context that can be preempted, throttled, and scheduled alongside everything else.

## The taxonomy of deferral

Linux offers several deferred-execution mechanisms. They differ along three axes: the context they run in, whether they can sleep, and how they serialize concurrent invocations.

| Mechanism | Context | Can sleep | Concurrency |
|---|---|---|---|
| Hard IRQ | Interrupt | No | One per CPU at a time; other CPUs run in parallel |
| Softirq | Interrupt (softirq) | No | The same softirq can run on multiple CPUs simultaneously |
| Tasklet | Interrupt (softirq) | No | A given tasklet runs on one CPU at a time |
| Threaded IRQ | Process | Yes | One kthread per line, or per the driver's design |
| Workqueue | Process | Yes | Configurable: per-CPU bound or unbound pools |
| NAPI poll | Softirq (`NET_RX`) | No | Per-device instance, budgeted |

The distinction between softirqs and tasklets is precisely the concurrency column: a softirq is a per-CPU vector that can execute concurrently with itself on different CPUs, so its handlers must be reentrant and must use per-CPU state or explicit locking. A tasklet is implemented on top of a softirq but is serialized — the kernel guarantees that the same tasklet will not run concurrently on two CPUs. That guarantee is what makes tasklets easy to write and what makes them a bottleneck in high-rate drivers.

## The top half: a contract, not a suggestion

A top-half handler is registered with `request_irq()` or `request_threaded_irq()` and receives the IRQ number and a `void *` cookie. Its return value is a claim about ownership: `IRQ_HANDLED` means "this interrupt was mine," and `IRQ_NONE` means "this line is not mine, or my device is not asserting." On a shared line, the kernel calls every registered handler in turn, and the return values are how it decides whether the interrupt was genuine.

That accounting matters more than it looks. `note_interrupt()` tracks unhandled interrupts per line, and if a line produces a long run of `IRQ_NONE` results — on the order of a hundred thousand — the kernel disables it and logs a complaint. This is the mechanism that prevents a stuck or misconfigured device from consuming the entire machine. It also means that a handler which returns `IRQ_NONE` incorrectly, or which fails to check its own device's status register before claiming the interrupt, will eventually get its line shut off.

The handler's job is narrow by design:

1. Determine whether the device is the source, and return `IRQ_NONE` if it is not.
2. Acknowledge the device so that it stops asserting. For level-triggered lines this is mandatory before returning; for edge-triggered lines it prevents a lost edge.
3. Capture whatever state is needed to make progress — a pointer to the completed descriptor, a head index from the device's completion queue.
4. Hand the work to a deferred mechanism.
5. Return.

Everything else belongs somewhere else. A driver that parses a packet, copies it into a socket buffer, and walks a protocol stack in its top half will work on a quiet machine and collapse under load, because the work is unbounded and uninterruptible.

There is one more subtlety: the order of acknowledge and handle. For level-triggered interrupts, acknowledging the controller before the device has deasserted the line produces an immediate re-interrupt. For edge-triggered interrupts, the edge is already latched, so acknowledging early is safe and narrows the window in which a second edge can be lost. The flow handler encodes these rules, which is exactly why drivers should not try to manage masking and EOI themselves.

That contract — acknowledge, capture, defer — is what makes the bottom-half mechanisms necessary and what determines which one is appropriate. The next sections take them one at a time, starting with softirqs and the per-CPU machinery they depend on.

## Softirqs and the per-CPU engine

A softirq is a bit in a per-CPU bitmask, not a queued work item. The kernel defines a fixed set of vectors — `HI`, `TIMER`, `NET_TX`, `NET_RX`, `BLOCK`, `IRQ_POLL`, `TASKLET`, `SCHED`, `HRTIMER`, `RCU` — and each has exactly one action function registered at boot with `open_softirq()`. There is no supported way for a driver to add a vector, and that is intentional: the softirq array is indexed by vector number, and the kernel wants a small, predictable set of contexts that can run on every CPU.

`raise_softirq()` disables interrupts, sets the bit in the current CPU's `__softirq_pending` mask, and wakes `ksoftirqd` if the call did not originate in interrupt context. Because the pending state is a bitmask, raising the same softirq twice before it runs still results in one execution. Softirq actions are therefore idempotent by construction: they drain whatever state caused the raise, not a specific event.

Execution happens at three points. `do_softirq()` is called from `irq_exit()` when a hard IRQ handler returns, provided the kernel is not already in interrupt context or a bottom-half-disabled region. It is also called from `local_bh_enable()` when the last disabled region ends. If neither path runs the work — because the CPU is busy, because `need_resched()` is set, or because the loop exceeded its budget — the per-CPU `ksoftirqd` thread is woken.

The core loop in `__do_softirq()` is bounded in two dimensions: at most `MAX_SOFTIRQ_RESTART` (10) restarts and at most `MAX_SOFTIRQ_TIME` (2 ms) before deferring to `ksoftirqd`. It also checks `need_resched()` and yields if a higher-priority task is waiting. Without these bounds, a device that generates softirq work faster than the CPU can drain it would starve the scheduler. With them, the kernel trades a small amount of latency for the guarantee that softirq processing cannot monopolize a CPU indefinitely.

The concurrency model is the part that trips up driver authors. The same softirq vector can run simultaneously on multiple CPUs. `NET_RX_SOFTIRQ` on CPU 0 and on CPU 1 are independent executions of the same action function. Per-CPU data is safe without locking, but any state shared between CPUs needs explicit synchronization. `local_bh_disable()` protects against softirq reentrancy on the local CPU, but it does nothing to stop another CPU from running the same softirq. That distinction is the source of a large fraction of networking and block-layer bugs.

`ksoftirqd` is a per-CPU kernel thread, normally at `SCHED_NORMAL` priority. It runs the same `__do_softirq()` loop in process context, so it can be preempted and can yield. Its existence is why a burst of softirq work does not necessarily become unbounded interrupt-context latency: once the in-interrupt budget is exhausted, the remaining work becomes a schedulable entity that competes with user tasks. The trade-off is that on a busy system `ksoftirqd` may not run promptly, and deferred work can accumulate. Monitoring its CPU time is one of the quickest ways to detect that a system is spending more time on deferred interrupt work than it can afford.

## Tasklets: serialization on top of softirqs

A tasklet is a `struct tasklet_struct` with a function pointer, a data word, and a state field. It is scheduled with `tasklet_schedule()` (or `tasklet_hi_schedule()` for the high-priority variant) and runs from the `TASKLET_SOFTIRQ` (or `HI_SOFTIRQ`) action function. The implementation is small: `tasklet_schedule()` sets the `TASKLET_STATE_SCHED` bit, adds the tasklet to a per-CPU list, and raises the corresponding softirq. The softirq action takes the entire per-CPU list, clears the schedule bit, and calls each tasklet's function.

The defining property of a tasklet is that the same tasklet will not run concurrently on two CPUs. The kernel enforces this with `TASKLET_STATE_RUN`. Before invoking the function, the softirq action calls `tasklet_trylock()`, which atomically tests and sets the run bit. If the bit is already set, the tasklet is rescheduled on the current CPU and skipped. A slow tasklet does not block other tasklets on other CPUs, but it does block itself: a second scheduling request while it is running results in another execution after the current one finishes. The serialization guarantee is per-tasklet, not per-CPU or per-softirq.

That guarantee is why tasklets were popular in older drivers. They offered a simple way to defer work from a hard IRQ handler without worrying about reentrancy on the same data structure. A driver could take a spinlock in the hard IRQ handler, queue a tasklet, and then take the same spinlock in the tasklet without fear that two CPUs would enter the tasklet simultaneously. The cost is that the tasklet becomes a serialization point. If the work is frequent and the tasklet takes a long time, all of that work is forced through a single execution stream, even on a many-core machine.

Tasklets inherit the restrictions of softirq context. They cannot sleep, they run with bottom halves disabled on the local CPU, and they contribute to the same 2-millisecond softirq budget. A tasklet that blocks or takes too long will trigger the `ksoftirqd` fallback and can cause the kernel to log warnings about softirq processing taking too long. `tasklet_disable()` and `tasklet_enable()` provide a reference count that prevents a tasklet from running, and `tasklet_kill()` waits for a scheduled tasklet to finish and prevents it from being rescheduled. Those primitives are necessary for driver teardown, but they are also a sign that the tasklet is being used as a synchronization object rather than just a deferral mechanism.

Modern kernel development has turned against tasklets. They are being removed from the tree in favor of threaded IRQs and workqueues, and new code should not introduce them. The reasons are structural: tasklets run in softirq context, so they cannot be preempted by the scheduler, they cannot sleep, and they cannot be priority-inverted. A threaded IRQ or a workqueue item gives the kernel a `task_struct` to schedule, which means the work can be preempted, can block on a mutex, and can be accounted for in the scheduler's statistics. For a driver that needs serialization, a mutex or a single-threaded workqueue is usually a better fit.

## Workqueues: process context with scheduling

Workqueues move deferred work into process context. A `struct work_struct` is a function pointer plus a small amount of state, and `schedule_work()` queues it on the system-wide `system_wq`. The work is executed by a kernel worker thread — a `kworker` — which is a real `task_struct` with a kernel stack, a scheduling class, and the ability to sleep. That single property changes everything: a workqueue handler can take a mutex, can allocate memory with `GFP_KERNEL`, can perform blocking I/O, and can be preempted by a higher-priority task.

The default workqueues are convenient but not interchangeable. `system_wq` is the general-purpose queue; `system_highpri_wq` runs its workers at elevated priority (typically nice -20) for latency-sensitive work; `system_long_wq` is for work items that may run for a long time; `system_unbound_wq` is not bound to any CPU and can run on any CPU in the system; `system_power_efficient_wq` may be unbound to save power; and `system_freezable_wq` is frozen during system suspend. A driver that queues a long-running item on `system_wq` can delay unrelated work items that share the same worker pool, which is why the kernel provides separate queues and why `alloc_workqueue()` exists for drivers that need their own pool.

`alloc_workqueue()` takes a name, a set of flags, and a `max_active` value. `WQ_UNBOUND` creates an unbound workqueue whose worker pool is not tied to a specific CPU. `WQ_HIGHPRI` creates a high-priority pool. `WQ_CPU_INTENSIVE` marks the workqueue as CPU-intensive, so its work items do not count against the concurrency limit of the pool. `WQ_MEM_RECLAIM` guarantees a worker is available even under memory pressure. `WQ_FREEZABLE` makes the workqueue freeze during suspend, and `WQ_POWER_EFFICIENT` makes an unbound workqueue use power-efficient scheduling.

The concurrency model of a bound workqueue is per-CPU. Each CPU has a worker pool, and `max_active` limits how many work items from a given workqueue can run simultaneously on that CPU. A workqueue with `max_active = 1` is effectively a per-CPU serialized queue: only one work item from that workqueue runs at a time on

on that CPU, but other CPUs can run their own instance of the same workqueue concurrently. A bound workqueue therefore gives you per-CPU serialization without global serialization, which is usually what a driver wants: each CPU processes its own queue of work items, and the only shared state is whatever the driver explicitly shares.

Unbound workqueues behave differently. With `WQ_UNBOUND`, the workqueue is not associated with any CPU. Instead, the kernel maintains a pool of worker threads that can run on any CPU, and it tries to place work items where they will be most efficient. Unbound workqueues are useful when the work is not CPU-local — for example, when it touches data that is shared across the system or when it should be scheduled on a CPU that is otherwise idle. They are also the basis for `WQ_POWER_EFFICIENT`, which allows the kernel to move work to a CPU that is already awake rather than waking an idle core. The trade-off is that an unbound workqueue has no per-CPU affinity, so you lose the cache locality that a bound workqueue provides. For high-rate networking or storage work, bound workqueues are usually the right choice; for background maintenance or power-sensitive workloads, unbound pools can be better.

The `max_active` parameter is the concurrency limit per CPU for bound workqueues, and per worker pool for unbound workqueues. Setting it to 1 gives you a serialized execution context. Setting it higher allows multiple work items from the same workqueue to run simultaneously, which is useful when the work items are independent. The kernel also has a global limit on the number of worker threads, and `WQ_CPU_INTENSIVE` work items are exempt from the per-pool concurrency limit so that a CPU-intensive item does not block other work in the same pool. That flag exists because the workqueue subsystem's default behavior is to assume work items may sleep and therefore should not consume a worker indefinitely; CPU-intensive items are expected to run for a long time without sleeping, and the kernel schedules them differently.

One subtlety is that `schedule_work()` on a bound workqueue queues the work on the current CPU by default. If the work is related to an interrupt that was handled on a different CPU, the driver may want to queue it on the CPU where the interrupt occurred, using `queue_work_on()`. This preserves cache locality and avoids cross-CPU synchronization. The kernel's `irq_work` mechanism is a lighter-weight alternative for work that must run in interrupt context but can be deferred to the next interrupt or to a timer tick; it is used by the scheduler, the RCU subsystem, and performance monitoring. `irq_work` runs from a softirq or from the timer interrupt, so it still cannot sleep, but it avoids the overhead of waking a worker thread.

## Threaded IRQs: moving the handler into a kthread

Threaded IRQs are the kernel's answer to the problem of drivers that need to do more than a few microseconds of work in response to an interrupt but cannot tolerate the latency of a workqueue scheduling delay. They split the handler into two parts: a primary handler that runs in hard IRQ context, and a threaded handler that runs in a dedicated kernel thread. The primary handler is registered with `request_threaded_irq()`, and the threaded handler is invoked by the IRQ core after the primary handler returns `IRQ_WAKE_THREAD`. The threaded handler runs in process context, so it can sleep, take mutexes, and perform blocking I/O. It is also scheduled like any other thread, which means it can be preempted by higher-priority tasks and can be assigned a real-time priority if needed.

The `IRQF_ONESHOT` flag is almost always required for threaded IRQs. Without it, the IRQ line would be unmasked as soon as the primary handler returns, allowing the device to interrupt again before the threaded handler has finished. With `IRQF_ONESHOT`, the line remains masked until the threaded handler completes, which prevents interrupt storms and ensures that the device's condition is fully serviced before the next interrupt is delivered. This is particularly important for level-triggered interrupts, where the line stays asserted until the device is acknowledged and its status register is cleared. The threaded handler is responsible for clearing the condition, and the IRQ core unmasks the line when the handler returns.

The primary handler in a threaded IRQ setup is usually minimal. It may check a status register to confirm the interrupt is for this device, then return `IRQ_WAKE_THREAD`. If the interrupt is not for this device, it returns `IRQ_NONE`. Some drivers pass `NULL` for the primary handler and let the IRQ core use a default primary handler that always returns `IRQ_WAKE_THREAD`; this is convenient when the device is the only one on the line and there is no need to check. However, on shared lines, a real primary handler is necessary to avoid waking the thread for interrupts that belong to another device.

The threaded handler's context has several advantages. It can take a mutex, which means the driver can use the same locking primitives in the interrupt path as it does in its other entry points. It can allocate memory with `GFP_KERNEL`, which is essential for drivers that need to build large data structures in response to an interrupt. It can perform DMA operations that require sleeping, and it can wait for a hardware handshake to complete. It can also be frozen during system suspend, which is important for power management: the kernel can stop the thread before suspending the device and resume it afterwards, avoiding races with the suspend path.

The cost of a threaded IRQ is latency. Waking a thread involves a scheduler decision, and if the thread is not already running, there may be a delay of several microseconds or more before it starts. For devices that require sub-microsecond response times, a threaded IRQ is not appropriate; the work must be done in the primary handler or in a softirq. For most devices, however, the latency is acceptable, and the benefits of process context outweigh the cost. The kernel's real-time preemption patches and the `PREEMPT_RT` configuration make threaded IRQs mandatory for most drivers, because on a real-time kernel all interrupt handlers are threaded so that they can be preempted by higher-priority tasks and so that the kernel can enforce bounded latencies. In `PREEMPT_RT`, even softirqs are threaded, and the distinction between hard IRQ context and process context is blurred in favor of a fully preemptible model.

Threaded IRQs also interact with CPU affinity. Each threaded handler is a kernel thread, and its affinity can be set independently of the IRQ's affinity. The IRQ core creates the thread on the CPU where the interrupt was first handled, and the thread inherits the affinity of the IRQ. Tools like `irqbalance` can move the thread along with the IRQ, or the driver can set the thread's affinity explicitly with `kthread_bind()`. This is useful for isolating latency-sensitive work on a dedicated CPU, a technique that is common in real-time and high-frequency trading systems.

## NAPI: polling as a first-class citizen

NAPI — New API — is the networking subsystem's hybrid interrupt-and-polling mechanism. It was introduced to solve the problem of high-speed network interfaces that generate more interrupts than the CPU can handle. At 10 GbE and beyond, the interrupt rate for small packets can exceed a million per second, and each interrupt costs hundreds of cycles just to enter and exit the handler. NAPI reduces the interrupt rate by disabling interrupts after the first packet arrives and switching to a polling loop that processes a batch of packets before re-enabling interrupts.

The core of NAPI is the `napi_struct`, which is registered with `netif_napi_add()` and typically embedded in the driver's private data structure. When the driver's hard IRQ handler runs, it calls `napi_schedule()`, which adds the NAPI instance to the current CPU's poll list and raises the `NET_RX_SOFTIRQ`. The softirq action function, `net_rx_action()`, iterates over the poll list and calls each NAPI instance's `poll()` method. The poll method processes a budget of packets — typically 64 — and returns the number of packets processed. If it processes the full budget, the kernel reschedules the instance and continues polling; if it processes fewer, the instance is removed from the poll list and interrupts are re-enabled.

The budget is the key to NAPI's fairness. It bounds the amount of work done in a single softirq invocation, preventing a single high-traffic interface from monopolizing the CPU. The `net_rx_action()` function also has a time limit: it will stop polling if it has run for more than 2 milliseconds or if it has processed more than 300 packets, and it will defer the remaining work to `ksoftirqd`. This ensures that the scheduler can run user tasks even under heavy network load. The driver's poll method must respect the budget and must not block; it runs in softirq context, so it cannot sleep. It can, however, disable interrupts on the device, which is what allows NAPI to avoid the interrupt overhead entirely during the polling phase.

NAPI also supports busy polling, a technique where the kernel polls the device for a short period after the last packet is received, hoping to catch the next packet without an interrupt. Busy polling is controlled by the `net.core.busy_poll` and `net.core.busy_read` sysctls, and it can reduce latency for latency-sensitive applications at the cost of increased CPU usage. It is implemented as a variant of NAPI that runs in process context, and it is used by protocols like UDP and by `SO_BUSY_POLL` sockets.

The `IRQ_POLL` softirq is a related mechanism for block devices. It allows a driver to poll for I/O completions instead of taking interrupts, which is useful for high-performance NVMe devices that can complete I/O faster than the interrupt overhead allows. The block layer's `blk-mq` polling mode uses `IRQ_POLL` to check for completions, and the driver registers a poll queue with `irq_poll_init()`. Like NAPI, it uses a budget to limit the work done per invocation, and it falls back to interrupts when the polling does not find work.

## Interrupt affinity and queue steering

On a multi-core system, the distribution of interrupts across CPUs is a major factor in performance. If all interrupts from a high-rate device are delivered to a single CPU, that CPU becomes a bottleneck while the others sit idle. The kernel provides several mechanisms to control affinity. The `/proc/irq/<num>/smp_affinity` file contains a bitmask of CPUs that are allowed to handle the interrupt, and writing to it changes the affinity. The `smp_affinity_list` file provides a comma-separated list of CPU numbers for convenience. Drivers can also set an affinity hint with `irq_set_affinity_hint()`, which suggests a CPU to the kernel but does not force it; the hint is used by `irqbalance` and by the kernel's own affinity management.

Modern network and storage devices use multiple queues, each with its own MSI-X vector. The driver can map each queue to a different CPU, spreading the interrupt load. This is the basis of Receive Side Scaling (RSS) for networking and of multi-queue block layers. The kernel's `irq_set_affinity()` function sets the affinity for a specific IRQ, and the driver can call it during initialization to pin each queue's interrupt to a specific CPU. The `netif_set_xps_queue()` function controls the transmit side, mapping outgoing packets to specific CPUs and queues to improve cache locality.

`irqbalance` is a userspace daemon that periodically reads `/proc/interrupts` and adjusts affinities to balance the load. It is useful on general-purpose systems but can be counterproductive on systems with carefully tuned affinities. For high-performance workloads, it is common to disable `irqbalance` and set affinities manually. The kernel also supports IRQ affinity notifiers, which allow drivers to be notified when the affinity of an IRQ changes; this is used by some drivers to update their internal state when the CPU mapping changes.

## Observability: seeing the interrupt path

The first tool for understanding interrupt behavior is `/proc/interrupts`. It shows, for each IRQ, the number of interrupts handled per CPU, the type of interrupt (level, edge, MSI), and the name of the registered handler. A large imbalance between CPUs indicates that affinity is not spread evenly. A rapidly increasing count for a single IRQ indicates a device that is generating more interrupts than expected, possibly due to a misconfiguration or a hardware fault. The file also shows the number of spurious interrupts, which are interrupts that were not claimed by any handler; a high count suggests a shared line with a misbehaving device or a driver that is not checking its status register correctly.

`/proc/softirqs` shows the number of times each softirq vector has run on each CPU. The `NET_RX`, `NET_TX`, `BLOCK`, and `TASKLET` columns are the most interesting for driver developers. A high count for `NET_RX` on one CPU while others are idle indicates that NAPI polling is not balanced, which often points to an affinity problem or to a single-queue device. A high count for `TASKLET` suggests that a driver is using tasklets for heavy work, which may be a scalability bottleneck.

`/proc/stat` includes the `softirq` line, which breaks down the time spent in each softirq vector. The `ksoftirqd` threads are visible in `ps` and `top` as `ksoftirqd/<cpu>`, and their CPU usage is a direct measure of deferred interrupt work. If `ksoftirqd` is consuming a significant fraction of a CPU, the system is spending more time on bottom-half processing than it can afford, and the driver may need to use a threaded IRQ or a workqueue to move the work into a schedulable context.

For deeper analysis, the kernel's tracing infrastructure provides tracepoints for IRQ entry and exit (`irq_handler_entry`, `irq_handler_exit`), softirq entry and exit (`softirq_entry`, `softirq_exit`), and NAPI polling (`napi_poll`). These can be enabled with `ftrace`, `perf`, or `bpftrace`, and they allow you to measure the latency of individual handlers, the time spent in each softirq, and the number of packets processed per NAPI poll. The `perf` tool can also sample on interrupt events, providing a profile of which handlers are consuming the most CPU time. For network-specific analysis, the `netdev` tracepoints and the `napi` statistics in `ethtool -S` provide per-queue packet counts and drop counts, which are essential for diagnosing whether the interrupt path is keeping up with the device.

## Interrupt mitigation and coalescing

The deferred-execution machinery described so far assumes that interrupts arrive at a rate the CPU can absorb. That assumption fails long before a device reaches its theoretical maximum. A 100 GbE port receiving minimum-size frames can see roughly 148 million packets per second, and a modern NVMe drive can complete millions of I/Os per second across its queues. No interrupt-per-event model survives that. The kernel and the hardware both respond by reducing the number of interrupts, not by making each interrupt cheaper.

Interrupt coalescing is the hardware-side answer. The device counts events or waits for a timer, and only then raises an interrupt. A network controller might be configured to interrupt after receiving 64 packets or after 100 microseconds, whichever comes first. An NVMe controller can be programmed with an interrupt coalescing threshold and timeout, so that completions are batched before the host is notified. The parameters are exposed through `ethtool -C` for network devices: `rx-usecs`, `rx-frames`, `tx-usecs`, `tx-frames`, and their adaptive variants. Setting `rx-usecs` to 0 disables the timer and makes the device interrupt as soon as possible; setting it to a large value reduces CPU load at the cost of latency.

The trade-off is not linear. At low packet rates, coalescing adds latency without saving much CPU, because interrupts are already infrequent. At high rates, it is the difference between a system that keeps up and one that spends all its time in interrupt entry and exit. Adaptive coalescing tries to find the middle ground: the driver monitors the packet rate and adjusts the timer and frame thresholds on the fly. The kernel's `net_dim` library provides a generic implementation of this idea, and many modern network drivers use it. The algorithm watches for changes in packet rate and latency, and moves the coalescing parameters in small steps toward a target.

For storage, the equivalent is completion coalescing. NVMe controllers support an Interrupt Coalescing feature that can aggregate completion queue entries before raising an MSI-X interrupt. Linux's NVMe driver does not enable it by default, because the completion path is already efficient and because polling mode is available for the highest-performance workloads. But the mechanism exists, and it is worth knowing about when a system is interrupt-bound rather than I/O-bound.

Coalescing interacts with NAPI in a way that is easy to misunderstand. NAPI already reduces interrupts by switching to polling after the first packet. Coalescing reduces the number of times NAPI is entered in the first place. The two are complementary: a driver can use hardware coalescing to batch packets, and NAPI to drain them without an interrupt per packet. The budget in `net_rx_action()` then bounds how long the drain can run before yielding to `ksoftirqd`. Tuning one without the other can produce surprising results. For example, disabling coalescing on a high-rate interface may cause the interrupt handler to run so often that NAPI never gets a chance to poll a full batch, while enabling aggressive coalescing on a latency-sensitive workload may add hundreds of microseconds of jitter.

The same logic applies to block devices. The `blk-mq` layer supports polling for completions, and the `IRQ_POLL` softirq provides a generic polling framework. A driver that supports polling can avoid interrupts entirely when the application is waiting for I/O, which is common in high-performance databases and storage benchmarks. The trade-off is CPU usage: polling burns cycles that could otherwise be used by other tasks. The kernel exposes polling through `io_poll` and through the `QUEUE_FLAG_POLL` flag, and the driver registers a poll queue with `irq_poll_init()`. The polling budget is similar to NAPI's: a limited number of completions per invocation, after which the driver falls back to interrupts.

## Per-CPU data, lockless synchronization, and memory ordering

Interrupt context is hostile to shared mutable state. The top half runs with interrupts disabled on the local CPU, so it cannot be preempted by another interrupt on that CPU, but it can run concurrently with the same handler on another CPU. Softirqs are worse: the same softirq vector can execute simultaneously on every CPU. The kernel's answer is to make the common case per-CPU, and to reserve locking for the cases that genuinely share state.

Per-CPU variables are the foundation. `DEFINE_PER_CPU()` declares a variable with one instance per CPU, and `this_cpu_inc()`, `this_cpu_read()`, and `this_cpu_write()` access the current CPU's instance without locking. In interrupt context, the current CPU cannot change, so these operations are safe and cheap. The compiler and the kernel cooperate to generate a single instruction with a segment prefix on x86, or an equivalent on other architectures. The cost is close to a normal memory access, which is why per-CPU counters are used throughout the networking and block layers.

The subtlety is migration. If code can be preempted or can sleep, the CPU it runs on may change between two per-CPU accesses. In interrupt context, preemption is disabled, so this is not a concern. In process context, the kernel provides `get_cpu_ptr()` and `put_cpu_ptr()`, which disable preemption around the access. A driver that reads a per-CPU variable in a workqueue handler and then writes it after a sleeping call will corrupt another CPU's data. The rule is simple: per-CPU access is safe only while preemption is disabled, and interrupt context is the strongest form of that guarantee.

For state that must be shared, the choice of synchronization primitive depends on the context. A spinlock is the only option in hard IRQ context, and it must be taken with `spin_lock_irqsave()` if the same lock can be taken from process context. A mutex is not allowed in hard IRQ or softirq context, because it can sleep. RCU is often the best fit for read-mostly data: `rcu_read_lock()` is cheap, does not sleep, and can be used in interrupt context, while writers use `synchronize_rcu()` or `call_rcu()` to defer freeing. The networking stack uses RCU extensively for routing tables, neighbor entries, and socket lookups. A driver that publishes a configuration structure to its interrupt handler can use RCU to avoid locking in the hot path.

Memory ordering is the other half of the problem. On a weakly ordered architecture, the CPU and the device may observe writes in a different order than the program issued them. A descriptor ring is the classic example. The driver writes a descriptor, then writes a doorbell register to tell the device that the descriptor is ready. Without a barrier, the device may see the doorbell before the descriptor, and read stale data. The kernel provides `dma_wmb()` for this case: it orders writes to DMA-coherent memory before subsequent writes to device memory. On the receive side, the driver reads a status field written by the device, and only then reads the rest of the descriptor. `dma_rmb()` ensures that the status read is not reordered after the data reads. These barriers are not optional; they are part of the contract with the hardware.

Cache-line bouncing is the performance consequence of getting this wrong. If two CPUs write to the same cache line, the line ping-pongs between their caches, and each write costs a coherence transaction. Per-CPU data avoids this by construction, but shared counters and producer/consumer indices can reintroduce it. The kernel provides `____cacheline_aligned` and `____cacheline_aligned_in_smp` for structures that must not share a line. A driver that puts a per-CPU counter next to a global flag will pay for it in every interrupt. The fix is to separate the hot fields into their own cache lines, even if it wastes memory. In interrupt-heavy workloads, that waste is almost always worth it.

## Real-time, CPU isolation, and latency budgets

The mechanisms described so far are designed for throughput and fairness. Real-time systems care about a different property: bounded worst-case latency. The `PREEMPT_RT` patch set, much of which has been merged into the mainline kernel, changes the interrupt path to make it fully preemptible. In a `PREEMPT_RT` kernel, almost all interrupt handlers are threaded by default. The hard IRQ handler is reduced to a minimal stub that acknowledges the interrupt and wakes the threaded handler. Softirqs are also threaded, and `ksoftirqd` runs at a real-time priority. The result is that the only code that runs in hard IRQ context is the code that absolutely must, and everything else can be preempted by a higher-priority task.

The `IRQF_NO_THREAD` flag marks handlers that must remain in hard IRQ context even on `PREEMPT_RT`. Timers, the scheduler tick, and some low-level controllers use it. A driver that can tolerate threading should not use it. The default threaded IRQ priority is 50, which is in the `SCHED_FIFO` range. A driver can adjust it with `chrt` or by writing to the thread's scheduling parameters. In a real-time system, the threaded handler should be pinned to a CPU and given a priority that reflects its deadline. If it is too low, it may be delayed by other real-time tasks; if it is too high, it may starve the application.

CPU isolation is the other half of real-time tuning. The `isolcpus`, `nohz_full`, and `rcu_nocbs` kernel parameters remove CPUs from the scheduler's general load balancing and from the timer tick. Interrupts must also be moved away from those CPUs, or the isolation is incomplete. The `irqaffinity` kernel parameter sets the default affinity for all interrupts, and `/proc/irq/<num>/smp_affinity` can be used to move individual lines. A common configuration is to reserve one or more CPUs for a real-time application, move all interrupts to the remaining CPUs, and pin the application's threads to the isolated cores. The threaded IRQ handlers for devices used by the application are then pinned to a different CPU, so that the application is never interrupted by device work.

Latency tracing is how you verify that the configuration works. The `irqsoff`, `preemptoff`, and `wakeup` tracers in ftrace record the longest period during which interrupts or preemption were disabled, and the longest wakeup latency. `cyclictest` measures the difference between the intended and actual wakeup time of a high-priority thread, and it is the standard tool for real-time validation. `perf sched` can show scheduling latencies for individual threads, including threaded IRQ handlers. If the worst-case latency is too high, the trace usually points to a long irq-disabled section, a spinlock held too long, or a softirq that is not threaded. The `CONFIG_DEBUG_ATOMIC_SLEEP` and `CONFIG_PROVE_LOCKING` options catch the programming errors that cause those latencies before they reach production.

The design rules for real-time interrupt handling follow directly. Keep the hard IRQ handler as short as possible. Use a threaded IRQ for anything that can sleep or that may take more than a few microseconds. Pin the threaded handler to a CPU that is not running the real-time application. Use per-CPU data and RCU instead of global locks. Avoid tasklets and softirqs for work that is not already in a real-time-aware subsystem. And measure, because the worst-case latency is not something you can reason about from the source code alone.

## Case study: NVMe completion handling

NVMe is a useful case study because it sits at the intersection of high interrupt rates, multi-queue hardware, and a driver that must make a context decision for every completion. A modern NVMe device exposes multiple MSI-X vectors, typically one per I/O queue pair. The driver allocates a submission queue and a completion queue for each CPU or for each application thread, and it programs the device with the base addresses and queue sizes. When a command completes, the device writes a completion queue entry and, depending on its interrupt coalescing configuration, raises an MSI-X interrupt on the vector associated with that queue.

The Linux NVMe driver's interrupt handler is deliberately simple. It reads the completion queue entries, processes them, and updates the queue's head pointer. It does not defer to a tasklet or a workqueue. The work is bounded by the queue depth, and the driver can process a batch of completions in the time it would take to schedule a thread. This is a deliberate choice: for a device that can complete millions of I/Os per second, the overhead of a threaded IRQ would be significant, and the completion processing itself is short. The driver relies on the fact that the hard IRQ handler can do a bounded amount of work, and it uses polling mode when the application is waiting for I/O and the latency of an interrupt is not acceptable.

The completion queue protocol illustrates the memory-ordering rules. Each completion entry has a phase bit that toggles when the queue wraps. The driver reads the phase bit and compares it with the expected phase. If it matches, the entry is valid. The driver must ensure that it reads the phase bit before reading the rest of the entry; otherwise, it might process a stale entry. The device, on the other side, must ensure that it writes the entry before updating the phase bit. The NVMe specification defines the ordering requirements, and the Linux driver uses `dma_rmb()` and `dma_wmb()` to enforce them. A driver that gets this wrong will work most of the time and fail under load, which is the worst kind of bug.

The submission path has a similar structure. The driver writes a command to the submission queue, then writes a doorbell register to notify the device. The doorbell write must not be reordered before the command write, so the driver uses `dma_wmb()`. The device reads the command, executes it, and writes the completion. The driver's interrupt handler then reads the completion and wakes the waiting task. The entire cycle is a study in bounded work, per-CPU queues, and careful ordering. It is also a reminder that the choice between hard IRQ, threaded IRQ, and polling is not a matter of style. It is a function of the device's rate, the work per event, and the latency the application can tolerate.

## The IRQ lifecycle: registration, enablement, and teardown

The interrupt path does not begin when the handler runs. It begins when a driver registers a handler, and it ends when the driver unregisters it. The lifecycle is where many driver bugs live, because the rules change depending on whether the device is shared, whether the system is suspending, and whether the CPU that owns the interrupt is still online.

`request_irq()` and `request_threaded_irq()` are the entry points. The former registers a single hard IRQ handler; the latter registers a primary handler and a threaded handler. Both take the IRQ number, a function pointer, a flags word, a name, and a cookie. The flags are not decorative. `IRQF_SHARED` declares that the line may be shared and permits multiple `irqaction` structures on the same `irq_desc`. Without it, a second registration on an already-claimed line fails with `-EBUSY`. With it, every handler on the line is called for every interrupt, and each must return `IRQ_NONE` if the interrupt is not its own. The shared-line contract is what makes the `IRQ_NONE` accounting in `note_interrupt()` necessary: a line that produces too many unclaimed interrupts is disabled to protect the rest of the system.

The trigger flags — `IRQF_TRIGGER_RISING`, `IRQF_TRIGGER_FALLING`, `IRQF_TRIGGER_HIGH`, `IRQF_TRIGGER_LOW` — are hints to the interrupt controller. On modern systems with device-tree or ACPI descriptions, the trigger type is usually configured by firmware and the driver should not override it. On legacy platforms, the driver may be the only source of that information. Getting it wrong produces either missed interrupts or a storm, and the failure often appears only on one board revision.

`IRQF_ONESHOT` is required for threaded handlers that do not have a separate primary handler capable of masking the line. It keeps the interrupt masked until the threaded handler completes, which is essential for level-triggered interrupts and for devices that assert the line until their status register is cleared. `IRQF_NO_AUTOEN` requests the IRQ but leaves it disabled, so the driver can finish initialization before interrupts begin. `IRQF_NO_SUSPEND` prevents the IRQ from being disabled during system suspend, which is necessary for wakeup sources. `IRQF_EARLY_RESUME` and `IRQF_FORCE_RESUME` control when the IRQ is re-enabled on the resume path. `IRQF_PERCPU` marks an interrupt as per-CPU, so it is not balanced across CPUs and is not disabled when the system goes to sleep. `IRQF_NOBALANCING` keeps `irqbalance` from moving the line.

The managed variants — `devm_request_irq()` and `devm_request_threaded_irq()` — tie the registration to the device's lifetime. When the device is unbound or the driver is removed, the kernel frees the IRQ automatically. This removes a common teardown bug, but it does not remove the need to stop the device from generating interrupts before the handler is freed. A device that continues to assert its line after the handler is gone will produce spurious interrupts and may trigger the `nobody cared` path.

Disabling and enabling an IRQ is reference-counted. `disable_irq()` increments a count and waits for any currently executing handler to finish. `disable_irq_nosync()` increments the count without waiting. `enable_irq()` decrements the count and unmasks the line only when the count reaches zero. The asymmetry matters: `disable_irq()` cannot be called from interrupt context, because it waits, while `disable_irq_nosync()` can. A driver that calls `disable_irq()` from its own hard IRQ handler deadlocks. The same rule applies to `free_irq()`, which waits for the handler to complete and must not be called from atomic context.

Teardown is where the deferred mechanisms meet the IRQ lifecycle. Before freeing an IRQ, a driver must ensure that no work queued by the handler is still running or can be queued again. The order is usually: disable the device's interrupt generation, call `disable_irq()` or `free_irq()` to synchronize with the handler, then cancel or flush any workqueue items, tasklets, or NAPI instances. `synchronize_irq()` waits for the handler on a specific IRQ to finish without disabling the line; it is useful when the driver has already masked the device and wants to wait for an in-flight handler. `cancel_work_sync()` waits for a work item and prevents it from being requeued. `napi_disable()` waits for a NAPI instance to stop polling and prevents it from being scheduled again. `tasklet_kill()` does the same for a tasklet. Using the wrong primitive, or using them in the wrong order, produces use-after-free bugs that only appear when the device is unbound under load.

## CPU hotplug, suspend, and the moving target

An interrupt is not permanently attached to a CPU. Affinity can change, CPUs can go offline, and the system can suspend. Each of these transitions interacts with the deferred mechanisms, and a driver that ignores them will work on a stable desktop and fail on a server with CPU hotplug or on a laptop that suspends.

CPU hotplug is the most disruptive. When a CPU is taken offline, the kernel migrates its interrupts to other CPUs. For a normal IRQ, this is transparent: the `irq_desc` is updated and the next interrupt is delivered elsewhere. For a per-CPU interrupt (`IRQF_PERCPU`), there is no migration; the interrupt is tied to a specific CPU and is disabled when that CPU goes down. Drivers that use per-CPU interrupts must register a CPU hotplug notifier or use the `irq_set_affinity_hint()` and managed IRQ facilities to handle the transition. The kernel's managed IRQs, activated with `pci_alloc_irq_vectors()` and the `PCI_IRQ_AFFINITY` flag, are automatically spread across CPUs and automatically migrated when CPUs go offline. That automation is one of the reasons modern drivers rarely call `irq_set_affinity()` directly.

Suspend and resume add a different set of constraints. During system suspend, the kernel disables non-wakeup interrupts. A device that is a wakeup source must have its IRQ marked with `IRQF_NO_SUSPEND` or must call `enable_irq_wake()`, which tells the interrupt controller to keep the line armed and to wake the system. A threaded IRQ handler is a kernel thread, and kernel threads are frozen during suspend unless they are marked as freezable or are explicitly excluded. The driver's suspend callback must ensure that no threaded handler is running when the device is powered down, and the resume callback must reinitialize any state that the handler depends on. A workqueue item that was queued before suspend may run after resume, so the driver must either flush the workqueue in its suspend callback or make the work item safe to run against a suspended device. `WQ_FREEZABLE` workqueues are frozen automatically, but the driver still has to cancel or flush non-freezable work.

NAPI has its own suspend interaction. `napi_disable()` must be called before the device is powered down, and `napi_enable()` after it is powered up. If the device is a wakeup source, the driver may need to keep a minimal interrupt handler active to detect the wake event, while the normal NAPI polling is disabled. The `netif_device_detach()` and `netif_device_attach()` calls tell the networking core that the device is not available, and the driver must not call `napi_schedule()` while the device is detached.

These transitions are why the interrupt path is not just a performance problem. It is a lifecycle problem. The handler must be correct when the device is shared, when the CPU is offline, and when the system is asleep. The kernel provides the primitives, but the driver must choose the right ones and order them correctly. A registration that works on a single-socket workstation can still fail on a hotplug-capable server, and a handler that survives normal operation can still race with suspend. The same discipline that keeps the top half short also keeps the teardown path short: stop new work first, synchronize with work already in flight, then free the resources that the work depends on.
