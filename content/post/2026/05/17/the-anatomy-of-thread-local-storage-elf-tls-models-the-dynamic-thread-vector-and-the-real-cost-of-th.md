# The Anatomy of Thread-Local Storage: ELF TLS Models, the Dynamic Thread Vector, and the Real Cost of `__thread`

Every thread-local variable in your program is a promise that the compiler, the assembler, the linker, the dynamic loader, the C library, and the kernel all keep together. None of them can keep it alone.

You write `__thread int counter;` or `thread_local Cache cache;` and the result looks like an ordinary global. You read it, you write it, you take its address. But the address you get is different in every thread, and the machinery that makes that true is spread across the entire toolchain. The contract binding those pieces together is a document most working engineers have never read: the *ELF Handling for Thread-Local Storage* ABI, usually shortened to the ELF TLS ABI.

This is worth understanding for three reasons.

**Thread-local state is the default escape hatch from data races, and it is frequently the wrong one.** A per-thread arena, a per-thread random number generator, a per-thread scratch buffer — these are all reasonable. A per-thread cache that shadows shared state is a correctness hazard wearing a performance costume. Knowing what the mechanism actually guarantees (and what it does not) is the difference between using it deliberately and using it because it made a benchmark go faster.

**TLS access is not free, and the cost varies by more than an order of magnitude depending on choices you may not know you are making.** The best case is a single load instruction with a segment prefix. The worst case is a call into the dynamic loader with a lazy allocation path and a generation check. The difference between those two cases is decided by how a library is compiled and how it is loaded — decisions that are often invisible in the source.

**The failure modes are strange and appear far from their cause.** The `dlopen` error `cannot allocate memory in static TLS block` has nothing to do with memory pressure. It means a library asked for a fixed-size resource that the loader computed at startup, and the request did not fit. Understanding why requires knowing that two entirely different allocation strategies exist for the same feature.

This article works from the bottom up: the ELF data model, the four access models and the machine code they generate, the dynamic thread vector and its lazy growth, the static TLS surplus and the `dlopen` problem, TLS destructors, the interaction with signals and stack-switching runtimes, and finally what all of this costs on a modern core.

## Two mechanisms share one name

Before going further, it is worth separating two things that both get called "thread-local storage" but have almost nothing in common.

**ELF TLS** is the mechanism this article is about. It is a linker-and-loader feature. Variables are placed in special sections, each thread gets a private copy of those sections, and the compiler emits addressing modes that resolve through a per-thread base pointer. The number of such variables is fixed at link time, access is a handful of instructions, and the storage is allocated as part of thread creation.

**The POSIX thread-specific data API** — `pthread_key_create`, `pthread_setspecific`, `pthread_getspecific` — is a completely different thing. It is a fixed-size array of key slots in the thread control block, with a second level of indirection once you exceed the first block. On glibc, `PTHREAD_KEYS_MAX` is 1024, the first-level array holds 32 entries, and lookups for keys beyond that do a linear scan of the second-level blocks. You can create and destroy keys at runtime, which ELF TLS does not allow, and you pay for that flexibility with a function call and, in the worst case, a scan.

Both mechanisms live in the same per-thread structure. Both are managed by the same library. But when someone says "TLS" in a performance discussion, they almost always mean the ELF mechanism, and that is what the rest of this article covers.

## The ELF TLS data model

Start with what the linker produces.

A thread-local variable declared with an initializer goes into a section named `.tdata`. A thread-local variable without an initializer (or with a zero initializer) goes into `.tbss`. These are the thread-local analogues of `.data` and `.bss`, with one important difference: `.tbss` occupies no space in the file at all. It is a size, not bytes. A library can declare a megabyte of zero-initialized thread-local state and add nothing to its on-disk footprint.

The linker collects `.tdata` and `.tbss` from all input objects and emits a `PT_TLS` program header describing them. That header carries the file offset and size of the initialized template, the total memory size (initialized plus zero-initialized), and the required alignment. It is, in effect, a recipe: *each thread needs this many bytes, laid out like this, with these initial contents.*

Every thread that runs your program gets a private copy of that region. The copy is made at thread creation — `memcpy` for the initialized part, and the zero-initialized part is simply left as whatever the allocator handed back, which is why the region is normally obtained from fresh, already-zeroed memory or explicitly cleared.

Now the addressing problem. A thread-local variable has a *fixed offset within the TLS block*. That offset is known at link time and is identical in every thread. What differs between threads is the base address of the block. So the entire mechanism reduces to: **where is this thread's TLS block, and how does the compiler find it?**

The answer is the thread pointer, a register that each thread's context carries. On x86-64 it is `%fs`; on AArch64 it is `TPIDR_EL0`; on RISC-V it is `tp`; on PowerPC it is `r13`. The kernel sets it during thread creation, and the C library initializes it before any user code runs. On x86-64, `%fs` is not a real segment in the 1980s sense — the base address lives in the `IA32_FS_BASE` model-specific register, and address generation reads it directly. There is no descriptor table walk on the hot path.

The thread pointer points at the **thread control block** (TCB), a small structure the C library owns. On x86-64 glibc, `%fs:0` holds a pointer to the TCB itself, `%fs:8` holds a pointer to the dynamic thread vector, `%fs:0x10` holds a self-pointer, and `%fs:0x28` holds the stack guard value that `-fstack-protector` reads on every function entry. That last one is worth pausing on: because the stack canary lives in the TCB, the cache line containing the start of the TCB is touched by essentially every function call in a stack-protected binary. It is one of the hottest cache lines in the process.

The TLS block itself sits adjacent to the TCB, and the ABI fixes which side. On x86-64 with glibc the block is placed *before* the TCB, which is why local-exec offsets on that platform are negative — you will see disassembly like `mov %fs:0xfffffffffffffffc,%eax` for a thread-local `int`. On other architectures the block may follow the TCB and the offsets will be positive. The compiler does not care; it emits whatever the ABI says.

Finally, there is the question of *which* TLS block. A process can have many modules — the main executable, the C library, every shared object loaded at startup or later — and each contributes its own slice of `.tdata` and `.tbss`. Each module gets a **module ID** assigned by the loader, and each thread's TLS area is a concatenation of per-module blocks. The offset of a variable is therefore really a pair: `(module ID, offset within module)`. For statically-known modules the linker can fold that pair into a single constant. For dynamically-loaded ones it cannot, and that is where the dynamic thread vector comes in.

## The four access models

The ELF TLS ABI defines four ways to reach a thread-local variable. They are not alternatives in the sense of "pick one and use it everywhere"; they are a hierarchy of assumptions, and the compiler picks the strongest one it can justify for each access.

| Model | Assumption | Typical code | Cost |
|---|---|---|---|
| Local-exec (LE) | Variable is in the main executable or a static binary; offset known at link time | `mov %fs:off, %rax` | One load |
| Initial-exec (IE) | Module is loaded at startup; offset from TP fixed at load time | `mov foo@gottpoff(%rip), %rax` then `mov %fs:(%rax), %rax` | Two dependent loads |
| Local-dynamic (LD) | Module knows its own ID but not its offset | call `__tls_get_addr` with a locally-built index | A call |
| General-dynamic (GD) | Nothing is known; module may be `dlopen`ed | `lea foo@tlsgd(%rip), %rdi` then `call __tls_get_addr@PLT` | A call, plus GOT traffic |

**Local-exec** is the ideal. The linker knows the variable's offset from the thread pointer at link time, so the access is a single instruction with a segment prefix. This model is only available to the main executable and to statically linked binaries, because only there is the layout of the TLS block fully determined before the program starts. A shared library can never use local-exec for its own variables, because the library's position in the TLS block is not known until it is loaded.

**Initial-exec** relaxes the assumption slightly. The offset from the thread pointer is still fixed, but it is not known until load time, so it is stored in the GOT and loaded at runtime. The access becomes two dependent loads: read the offset from the GOT, then use it as a displacement from the thread pointer. The critical property is that the offset is *fixed for the lifetime of the process*, which means the loader must be able to allocate the module's TLS block at startup, before any threads exist. That is exactly the constraint that produces the static TLS surplus problem discussed later.

**Local-dynamic** is for the case where a module can determine its own module ID but not its offset — the classic example being a shared library that accesses its own thread-local variable and cannot assume it was loaded at startup. The compiler builds a `tls_index` structure containing the module ID and the offset within the module, and calls `__tls_get_addr` to resolve it. The call is necessary because the module's block may be allocated lazily.

**General-dynamic** is the most pessimistic and the default for position-independent shared libraries. The compiler emits a reference to a pair of GOT entries that the loader fills in, then calls `__tls_get_addr`. It is the only model that works unconditionally, and it is the slowest.

Two things soften this picture in practice.

First, **the linker can relax a weaker model into a stronger one.** When linking a shared library, a general-dynamic reference to a symbol that turns out to be local and hidden can be relaxed to initial-exec, because the linker knows the module will be loaded with the library and the offset can be computed at load time. When linking a non-PIE executable, general-dynamic and initial-exec references can both be relaxed all the way to local-exec. This is why a `-fPIC` shared library sometimes shows up with faster TLS access than its source suggests: the relaxation happened at link time, and nothing in the source records it.

Second, **there is a newer dialect.** On x86-64 and AArch64, recent GCC versions support `-mtls-dialect=gnu2`, which emits a *TLS descriptor*: a small two-word structure containing a resolver function pointer and an argument. The first access calls the resolver, which patches the descriptor in place; subsequent accesses call through the patched pointer directly. This gives general-dynamic code a fast path after the first touch without requiring the initial-exec constraint. It is not the default everywhere, and it changes the ABI surface for the symbol, so it is a build-wide decision rather than a per-variable one.

The practical consequence is that the model is not a property of your source code. It is a property of the compilation flags, the linkage of the module, the visibility of the symbol, and the linker's willingness to relax. A thread-local variable in a plugin loaded with `dlopen` and one in the main executable can be the same three lines of C++ and differ by a factor of ten in access cost.

## The dynamic thread vector

For general-dynamic and local-dynamic accesses, the compiler cannot compute the address of the variable. It knows the module and the offset within the module, but not where the module's TLS block lives in the current thread. That question is answered by `__tls_get_addr`, and the data structure it consults is the dynamic thread vector.

The argument to `__tls_get_addr` is a pointer to a `tls_index` structure — two words, `ti_module` and `ti_offset`. The module ID is an index into the DTV. The DTV itself is per-thread. On glibc, the thread control block contains a pointer to the DTV at a fixed offset (`%fs:8` on x86-64). The DTV is a pointer to an array of `void *`, and the first element of that array is not a pointer to a TLS block at all: it is a generation counter.

The layout looks like this:

```c
struct dtv {
    uintptr_t counter;   // generation number
    void *pointer[];     // one entry per module, indexed by module ID
};
```

The generation counter exists because modules can be loaded after threads have been created. When a new module is loaded, the loader assigns it a module ID and increments a global generation counter. Every thread's DTV has its own counter, which records the generation at which that thread last synchronized its DTV with the global module list. When `__tls_get_addr` runs, it first checks whether the thread's DTV counter matches the global generation. If it does not, the thread's DTV is out of date: it may be too small to hold the new module's entry, or its entries may be missing. The slow path reallocates the DTV array if necessary and fills in the new entries with NULL, then updates the counter.

After that check, `__tls_get_addr` looks up `dtv[ti_module]`. If the entry is non-NULL, it simply adds `ti_offset` and returns the address. If the entry is NULL, the module's TLS block for this thread has not been allocated yet. The function calls into the loader's allocation routine, which uses the module's `PT_TLS` template to allocate a block of the right size and alignment, copies the initialized data from `.tdata`, zeroes the `.tbss` portion, and stores the resulting pointer in the DTV. Then it returns the address.

This is lazy allocation at its finest: a thread pays for a module's TLS block only when it first touches a variable from that module. A server with 500 threads and 200 loaded modules might have 200 DTV entries per thread, but if only a handful of modules are actually used per thread, only those blocks are allocated. The DTV array itself, however, is per-thread and grows to accommodate the highest module ID. That array is small — one pointer per module — but it is allocated with `malloc` and can be reallocated as modules are loaded. In a program that loads and unloads many plugins, the DTV array can churn.

The generation check is cheap: one load and one compare on the fast path, both from the DTV's first cache line. The module lookup is another load. The call overhead is the dominant cost. This is why `-mtls-dialect=gnu2` exists: it replaces the call with a TLS descriptor that caches the resolved address, so subsequent accesses are a call through a function pointer that has been patched to a simple `lea` or `mov`. Even then, it is still a call.

There is one more wrinkle: `__tls_get_addr` must be reentrant and async-signal-safe in the fast path? The ABI does not guarantee async-signal-safety. The first access to a dynamic TLS variable in a thread can allocate memory, take locks, and call into the dynamic loader. If a signal arrives during that window and the signal handler also accesses the same variable, you can get deadlock or corruption. The practical rule is: do not access a dynamic TLS variable for the first time in a signal handler. Either initialize it before installing the handler, or use initial-exec/local-exec for variables that signal handlers touch. This is a subtle trap that has bitten real programs.

## The static TLS surplus and the `dlopen` failure

The initial-exec model is attractive because it reduces TLS access to two dependent loads with no function call. The trade-off is a hard constraint: the offset from the thread pointer must be known at load time. For the main executable and its dependencies, that is easy — the loader lays out their TLS blocks at startup and fixes the offsets. But for a shared library loaded later with `dlopen`, the loader cannot know its offset in advance, because existing threads already have their TLS blocks allocated and their thread pointers set. You cannot insert a new block into the middle of every thread's TLS area without moving memory that other threads are actively using.

The loader's solution is a reservation. At startup, it allocates a static TLS area for all initial-exec modules, and then adds a little extra space on top. That extra space is the **static TLS surplus**. When a library is `dlopen`ed and requests initial-exec TLS, the loader can carve its block out of the surplus, because the surplus is at the end of the static TLS area and its size was fixed before any threads were created. As long as the library's TLS requirement fits in the remaining surplus, the load succeeds and the offset can be computed relative to the thread pointer.

The surplus is a fixed, per-thread resource. On glibc x86-64, the default surplus is 1664 bytes. Other architectures and libc implementations use different numbers. It can be adjusted with the `glibc.rtld.optional_static_tls` tunable, but that affects every thread in every process on the system. The surplus is consumed by `dlopen` calls in order. If you load one library that needs 1024 bytes of TLS, the remaining surplus is 640 bytes. If you then load another library that needs 800 bytes, the second `dlopen` fails with:

```
cannot allocate memory in static TLS block
```

This error has nothing to do with the system's free memory. It means the fixed-size reservation is exhausted. The process may have gigabytes of RAM available, but the per-thread static TLS surplus is a hard limit.

Why do libraries request initial-exec TLS in the first place? Usually for performance. A library that is compiled with `-ftls-model=initial-exec` will use the faster access model, but it then becomes unloadable unless it fits in the surplus. Many distributions build libraries with initial-exec TLS by default for this reason, which is why `dlopen` failures are not rare. The library author may not have considered that their library would be loaded dynamically. The fix is to compile the library with `-ftls-model=global-dynamic` (the default for PIC) or to ensure it is loaded at startup via `LD_PRELOAD` or as a direct dependency. Alternatively, the application can increase the surplus, but that is a global setting and wastes memory in every thread.

There is a second-order effect: the surplus is per-thread, so even if it is never used, it is allocated for every thread. On a system with 10,000 threads, a 2 KB surplus costs 20 MB of address space and, if touched, memory. The surplus is not touched unless a `dlopen`ed library uses it, so the pages may remain untouched and not consume physical memory. But the virtual address space is reserved, and the TCB and static TLS are allocated together, so the surplus contributes to the size of the thread's initial stack and TLS area. This is a fixed overhead that is easy to overlook.

## TLS destructors

A thread-local variable declared with `__thread` is just memory. It has no destructor. But C++ `thread_local` objects can have non-trivial destructors, and those destructors must run when the thread exits. The mechanism for this is `__cxa_thread_atexit_impl`, a function provided by the C library. When a `thread_local` object with a destructor is constructed, the compiler emits a call to `__cxa_thread_atexit_impl` with the destructor function, the object's address, and a `dso_symbol` argument that identifies the module. The C library stores this in a per-thread list.

At thread exit, the C library walks the list in reverse order of registration and calls each destructor. This is the same LIFO order that C++ guarantees for objects with static storage duration at program exit, but scoped to the thread. The `dso_symbol` argument is used to handle `dlclose`: if a module is unloaded while a thread is still alive, the loader marks the module's destructor entries as invalid so they are skipped at thread exit. Without this, calling a destructor in an unloaded module would crash.

The destructor list is allocated with `malloc` and grows as needed. Each `thread_local` object with a destructor adds an entry. If a thread constructs many such objects — say, in a loop — the list can grow large, and the destructors will all run at thread exit. This is a hidden cost: thread creation and destruction become more expensive, and the memory used by the list is not freed until the thread exits.

There is also an interaction with `pthread_key_create` destructors. The POSIX thread-specific data mechanism has its own destructor list, and it is separate from the `__cxa_thread_atexit_impl` list. The order in which the two lists are processed is not specified. In glibc, the `__cxa_thread_atexit_impl` destructors run first, then the `pthread_key` destructors. This can matter if a `thread_local` object's destructor uses a `pthread_key` value that is also destroyed. The general advice is to avoid relying on cross-mechanism ordering.

Another subtlety: `__cxa_thread_atexit_impl` is not available on all platforms. On some systems, the compiler emits a call to `__cxa_thread_atexit` (without `_impl`) or uses a different mechanism. The ABI for thread-local destructors is not part of the ELF TLS ABI itself; it is a C++ ABI extension. This means that mixing compilers or C libraries can cause link errors or runtime failures for `thread_local` objects with destructors. The `__thread` keyword, by contrast, is pure ELF TLS and has no such dependency.

## What it costs

We can now put numbers on the cost. The absolute cycle counts depend on the microarchitecture, but the ratios are stable.

**Local-exec** is a single load with a segment prefix. On a modern x86-64 core, if the variable is in L1 cache, the load has a latency of about 4–5 cycles and a throughput of one per cycle. There is no extra address computation. The thread pointer is in a register, so there is no memory access to get it. This is as cheap as a global variable access, except that the address is not a link-time constant, so it cannot be used in a `mov` immediate; it must go through the segment register.

**Initial-exec** is two dependent loads: first the offset from the GOT, then the variable. The GOT entry is almost always in L1 because it is read by every access. The two loads have a combined latency of about 8–10 cycles. Throughput is one per cycle once the pipeline is full, because the two loads can be pipelined across independent accesses. The extra load is the price of position independence.

**General-dynamic** is a function call. On x86-64, a call and return pair costs a few cycles by itself, but the real cost is the work inside `__tls_get_addr`: load the DTV pointer from the TCB, check the generation, load the module pointer, add the offset, return. That is maybe 10–15 instructions plus the call overhead. The total latency is often 20–40 cycles, and the function call may clobber registers, forcing the caller to spill. If the DTV is not in cache, it can be much worse. With TLS descriptors (`-mtls-dialect=gnu2`), the first access is a call to the resolver, but subsequent accesses are a call through a patched descriptor, which is a few cycles plus the call. That brings general-dynamic down to maybe 10–15 cycles, still slower than initial-exec but much better than the classic path.

**Local-dynamic** is similar to general-dynamic but the `tls_index` is built locally, so there is no GOT load for the module ID. The call to `__tls_get_addr` remains. The cost is within a few cycles of general-dynamic.

For comparison, `pthread_getspecific` on glibc is a function call that indexes into the first-level array of the TCB. If the key is in the first 32 keys, it is a single load and return. The function call overhead dominates, so it is roughly comparable to general-dynamic TLS for a single access. The advantage of `pthread_getspecific` is that you can create keys at runtime and it works with `dlopen` without the surplus problem. The disadvantage is that you manage the storage yourself and you pay a function call on every access.

The memory cost of TLS is per-thread. Every thread has a TCB, a static TLS block, and a DTV. The TCB is a few hundred bytes. The static TLS block is the sum of all initial-exec TLS variables in all modules loaded at startup, plus the surplus. For a program with many threads, this is a fixed cost. For example, if the static TLS is 4 KB and you have 1000 threads, that is 4 MB of address space. The DTV is an array of pointers, one per module. For 100 modules, that is 800 bytes per thread on a 64-bit system, plus the array header. If the DTV is allocated with `malloc`, each thread's DTV is a separate allocation, which can fragment the heap.

Dynamic TLS blocks are allocated per thread on first access. They are not freed until the thread exits, because there is no mechanism to free them earlier (a thread might access the variable again). This means a thread that briefly uses a dynamic TLS variable from a plugin will hold that memory for its entire lifetime. In a thread pool with long-lived threads, this is usually fine. In a system that creates and destroys threads frequently, the allocator sees churn.

Thread creation itself has a TLS cost. The kernel sets the thread pointer, but the C library must allocate the TCB and static TLS, copy the `.tdata` template, zero the `.tbss`, and initialize the DTV. For a thread that does a small amount of work, this setup can dominate. This is one reason why thread pools are preferred over creating a thread per task.

Finally, there is the cost of TLS destructors. Each `thread_local` object with a non-trivial destructor registers an entry in the thread's destructor list. The registration is a function call that may allocate memory. At thread exit, the destructors run in reverse order. If a thread has many such objects, both construction and destruction become more expensive. The destructor list itself is a linked list, so walking it is O(n). For a thread that constructs thousands of `thread_local` objects with destructors, the exit path can take milliseconds.

The ELF TLS mechanism is a remarkable piece of engineering: it turns a per-thread variable into a single load in the best case, and it handles dynamic loading and destruction in the worst case. The cost is not in the access itself, but in the choices that determine which access model you get. A `__thread` variable in the main executable is nearly free. The same variable in a `dlopen`ed plugin is a function call and a lazy allocation. The difference is not visible in the source, and it is not a micro-optimization: it is the difference between a cache-friendly data structure and a call into the dynamic loader. Knowing which one you have is the first step to using TLS deliberately.

## Signals, stack switching, and the thread pointer contract

A thread-local variable is tied to the thread pointer, not to the stack. That distinction matters as soon as a signal handler runs or a coroutine switches stacks.

When a signal is delivered to a thread, the kernel runs the handler in that same thread's context. The thread pointer is unchanged. If the handler reads `errno` or a `thread_local` variable, it sees the same instance the interrupted code would see. An alternate signal stack changes only the stack pointer; the thread pointer still points at the same TCB and the same TLS block. This is why TLS is a natural place for per-thread error state and why `errno` is implemented as a thread-local variable on modern libc implementations.

The danger is not the address calculation; it is the first access to a dynamic TLS variable. A general-dynamic access compiles to a call to `__tls_get_addr`. If the module's TLS block for this thread has not been allocated, that call can allocate memory, take loader locks, and copy the `.tdata` template. If the signal arrives while the thread is already inside `malloc` or the dynamic loader, and the handler then touches a dynamic TLS variable from a module whose block is not yet allocated, the handler can deadlock or corrupt allocator state. The same hazard exists if the handler's first access triggers a DTV generation check that decides the thread's DTV is stale. The generation check itself is cheap, but the slow path behind it is not async-signal-safe.

The practical rule is simple: do not perform the first access to a dynamic TLS variable inside a signal handler. Touch the variable once during thread startup, before installing the handler, or compile the variable's module with initial-exec or local-exec so the access is a plain load. If a signal handler must use TLS, prefer a variable in the main executable or in a library that is guaranteed to be loaded at startup. The same reasoning applies to `longjmp` out of a signal handler: if the handler interrupts `__tls_get_addr` while it holds a loader lock and then jumps away, the lock may remain held. Longjmp from a signal handler is already a narrow technique, but TLS makes the window harder to reason about.

Stack switching is a different trap. User-level fibers, coroutines, and green threads switch stacks without changing the thread pointer. The TLS block remains the OS thread's block. Code that reads a `thread_local` variable after a stack switch sees the value belonging to the OS thread, not to the fiber. That is correct for the ELF TLS contract, but it is often wrong for the abstraction the fiber runtime is trying to provide. A fiber-local cache must be stored in the fiber's context object or in a runtime-specific slot, not in `thread_local`. Some runtimes do use TLS to store a pointer to the currently running fiber; that is fine as long as the runtime updates the pointer on every switch. The TLS variable then holds a per-thread pointer to a per-fiber object, and the indirection is explicit.

The compiler also assumes the thread pointer is stable for the lifetime of the thread. Anything that changes it invalidates every TLS address the compiler has computed. Creating a thread with raw `clone` and `CLONE_SETTLS` sets the thread pointer, but the new thread's TCB and DTV must be initialized before any TLS access. The C library normally does this as part of `pthread_create`; a custom thread runtime that bypasses libc must reproduce that setup or TLS access will crash. Changing the thread pointer later with `arch_prctl(ARCH_SET_FS)` on x86-64 without rebuilding the TCB has the same effect. The thread pointer is not a general-purpose register you can repurpose.

## Reading the disassembly and controlling the model

The TLS model is not a source-level property. It is visible in the relocations and instructions the compiler emits, and it can be changed by compiler flags, symbol visibility, and linker relaxation. Learning to read those signals is the fastest way to know what you actually built.

On x86-64, a local-exec access looks like a single instruction with a segment prefix: `mov %fs:0xfffffffffffffffc,%eax`. The offset is a link-time constant. An initial-exec access loads the offset from the GOT first: `mov foo@gottpoff(%rip),%rax` followed by `mov %fs:(%rax),%eax`. The two loads are dependent. A general-dynamic access sets up an argument and calls the resolver: `lea foo@tlsgd(%rip),%rdi` followed by `call __tls_get_addr@PLT`. A local-dynamic access uses a locally built `tls_index` and also calls `__tls_get_addr`, but it does not need the GOT entry for the module ID. The exact instruction prefixes vary by compiler version and alignment settings; the relocation names are more reliable.

`readelf -r` or `objdump -dr` shows the relocations. `R_X86_64_TPOFF64` indicates a local-exec offset. `R_X86_64_GOTTPOFF` indicates an initial-exec GOT offset. `R_X86_64_TLSGD` indicates general-dynamic. `R_X86_64_TLSLD` indicates local-dynamic. `readelf -l` shows the `PT_TLS` program header, which gives the size and alignment of the module's TLS template. `readelf -s` shows the TLS symbols and their sizes. If a shared library's disassembly contains `__tls_get_addr`, it is using a dynamic model. If it contains only `%fs:` accesses with GOT loads, it is using initial-exec. If it contains only `%fs:` accesses with immediate offsets, it is using local-exec, which means the linker relaxed the reference all the way down.

The build controls are straightforward but easy to misuse. `-ftls-model=global-dynamic` is the default for position-independent shared libraries. `-ftls-model=initial-exec` asks for the faster model but imposes the static TLS surplus constraint. `-ftls-model=local-exec` is only valid for the main executable or a static binary. `-ftls-model=local-dynamic` is useful for a shared library that knows its own module ID but cannot assume startup loading. The model can also be set per variable with a compiler attribute, which is useful for a single hot variable in an otherwise dynamic library. `-fvisibility=hidden` helps the linker relax general-dynamic to local-dynamic for symbols that cannot be interposed, because the module no longer needs to ask the loader for its own module ID. It does not by itself make the access initial-exec; that requires the initial-exec model or a guarantee that the module is loaded at startup. `-mtls-dialect=gnu2` changes the general-dynamic code sequence to use a TLS descriptor, which caches the resolved address after the first call. It is a build-wide choice on the architectures that support it, and it changes the ABI surface for the symbol.

The most common mistake is forcing initial-exec on a library that is meant to be `dlopen`ed. The library will work when loaded at startup and fail when loaded later, and the failure will appear as the static TLS surplus error. The second most common mistake is assuming that a `-fPIC` build always uses general-dynamic. Linker relaxation can turn a general-dynamic reference into local-dynamic or initial-exec when the symbol is hidden or the module is known to be loaded at startup. The source code does not record which relaxation happened; the disassembly does.

## Unloading, generations, and the lifetime of a module's TLS

`dlclose` is where the TLS abstraction becomes visibly incomplete. The loader can unmap a module's code and data, but it cannot easily visit every thread's DTV and free that module's TLS block. Threads may be running, blocked, or parked in a thread pool. The ABI does not provide a stop-the-world mechanism for TLS reclamation. Implementations therefore handle module unloading with a mixture of generation counters, reserved module IDs, and deferred cleanup.

The generation counter in the DTV is the synchronization point. When a module is loaded or unloaded, the global generation changes. A thread's DTV records the generation at which it last synchronized. The next dynamic TLS access in that thread sees the mismatch and takes the slow path, which can grow the DTV array or refresh its entries. A thread that never touches dynamic TLS again never synchronizes, which is fine because it never consults the stale entries. The subtle part is module ID reuse. If a module is unloaded and its ID is later assigned to a different module, an old DTV entry must not be mistaken for the new module's block. The loader must either keep the old ID reserved or clear the relevant entries before reuse. The ABI does not promise which strategy an implementation uses, so the safe assumption is that a thread that has touched a dynamic TLS variable from a plugin may hold that plugin's TLS block until the thread exits.

This has a practical consequence for plugin hosts. A long-lived worker thread that loads a plugin, touches a thread-local variable in it, and then unloads the plugin may retain the plugin's TLS block for the lifetime of the thread. Repeated load-unload cycles can accumulate per-thread allocations even though the plugin's code is gone. The memory is not visible to a heap profiler that only tracks `malloc` call sites in the plugin, because the allocation was made by the loader on behalf of the thread. The same applies to the static TLS surplus: when an initial-exec plugin is loaded from the surplus, the surplus is consumed as a bump allocation. Unloading the plugin does not generally rewind the bump pointer. A host that repeatedly loads and unloads libraries with initial-exec TLS can exhaust the surplus even though each individual library was unloaded cleanly.

TLS destructors add another layer. A `thread_local` object with a non-trivial destructor registers an entry with `__cxa_thread_atexit_impl`, and that entry carries a `dso_symbol` identifying the module. If the module is unloaded while the thread is still alive, the loader marks the entry invalid so the destructor is skipped at thread exit. Skipping the destructor avoids calling into unmapped code, but it also means the object's resources are not released. The object's storage may still be in the retained TLS block. For a plugin that owns file descriptors or locks in thread-local objects, unloading while threads are alive is a resource leak by design. The safe pattern is to ensure all threads that might have touched the plugin's TLS have exited or have been explicitly cleaned up before unloading the plugin.

None of this makes TLS unsuitable for plugin architectures. It means the lifetime rules must be explicit. A plugin that uses thread-local state should document whether it expects to be loaded at startup, whether it uses initial-exec TLS, and what happens to per-thread state on unload. A host that loads plugins dynamically should either keep them loaded for the process lifetime or provide a quiescence point where no thread can be using the plugin's TLS. The ELF TLS ABI gives you a fast per-thread variable; it does not give you a garbage collector for the per-thread copies.

## The per-thread guard: dynamic initialization of `thread_local` objects

`__thread int x;` is pure storage. `thread_local std::string s("hello");` is not. The difference is dynamic initialization, and it changes the generated code for every access.

When a `thread_local` variable has a constant initializer, the compiler places the value in `.tdata` and the loader copies it into each thread's block. No code runs. When the initializer is not a constant expression — a constructor call, a function call, anything that must execute — the compiler cannot put the value in `.tdata`. Instead, it emits a per-thread guard variable and an initialization function. The guard is a byte in `.tbss`, zero for every thread. The initialization function, with a mangled name like `_ZTH9my_string`, constructs the object and registers its destructor with `__cxa_thread_atexit_impl`.

The access pattern becomes:

```cpp
if (!guard) {
    __tls_init();  // constructs the object, sets guard
}
// use object
```

The guard check is a load and a branch. It is not free, but it is cheap: the guard byte shares a cache line with other TLS data and is almost always in L1. The branch is perfectly predicted after the first access in each thread. The cost is the load and the compare, plus the branch, on every access. For a hot loop that touches a dynamically initialized `thread_local` object, this is a measurable overhead. The compiler cannot hoist the check out of the loop unless it can prove the object is already initialized, which it usually cannot because the initialization is per-thread and the loop may run in a thread that has not initialized it.

The initialization function itself runs once per thread. It constructs the object in the thread's TLS block, then calls `__cxa_thread_atexit_impl` to register the destructor. The registration allocates an entry in the thread's destructor list. If the constructor throws, the guard is reset to zero and the exception propagates; the next access in that thread retries the initialization. This matches the C++ rules for function-local statics, but scoped to the thread.

There is a subtlety with the guard and the destructor. If a thread never accesses the variable, the initialization function never runs, the object is never constructed, and the destructor is never registered. That is correct: an unconstructed object has nothing to destroy. But it also means that a `thread_local` object with a non-trivial constructor and destructor can exist in a state where the storage is allocated (it is part of the thread's TLS block) but the object is not alive. Code that takes the address of the variable without triggering initialization — for example, passing `&var` to a function — can observe this. The C++ standard says the object is initialized before any odr-use, and taking the address is an odr-use, so the compiler must emit the guard check before the address is taken. The generated code does this by placing the guard check at the point of use, not at the point of declaration.

The initialization order of `thread_local` objects is another sharp edge. Within a single thread, objects are initialized in the order they are first used, not the order they appear in the source. Across translation units, there is no defined order. This is the same "static initialization order fiasco" that affects global objects, but it is per-thread and therefore harder to reproduce. A `thread_local` object in one translation unit that is initialized by a constructor that reads a `thread_local` object in another translation unit may see the second object uninitialized, because the second object's guard has not been triggered yet. The fix is the same as for globals: avoid cross-translation-unit dependencies in constructors, or use a function-local `thread_local` that initializes on first use in a controlled order.

The compiler also has to handle the case where the `thread_local` object is defined in a shared library. The initialization function is emitted in the library, and the guard is in the library's TLS block. The access from another module goes through the dynamic TLS model to find the guard and the object. This means that even if the variable is in the main executable, a `thread_local` with dynamic initialization in a `dlopen`ed library will use general-dynamic access for both the guard and the object, with the associated call overhead. The guard check is on top of that.

For performance-critical code, the pattern to prefer is constant-initialized `thread_local` or `__thread` with manual initialization. A `thread_local` object with a constructor is convenient, but it adds a guard check to every access and a registration call to every thread's first use. If the object is a simple POD, the compiler will usually treat it as constant-initialized and skip the guard entirely. If it is a class with a trivial constructor, the compiler may still emit the guard if the initializer is not a constant expression. Checking the disassembly is the only reliable way to know.

It is worth noting that C does not have this problem. C11's `_Thread_local` requires initializers to be constant expressions, so a `_Thread_local` variable is always placed in `.tdata` or `.tbss` and accessed without a guard. The dynamic initialization guard is a C++ feature, introduced to support `thread_local` objects with constructors. If you are writing C, you get the simpler model by default. If you are writing C++, you pay for the convenience.

## The kernel's part: setting and switching the thread pointer

The ELF TLS ABI describes how the compiler and linker address thread-local variables, but the thread pointer itself is a kernel and libc concern. The kernel does not parse `PT_TLS`, does not know about `.tdata`, and does not call `__tls_get_addr`. It provides a register — `%fs` on x86-64, `TPIDR_EL0` on AArch64 — and the ability to set it for a new thread. Everything else is user space.

On x86-64, the thread pointer is the base address stored in the `IA32_FS_BASE` model-specific register. The kernel exposes it through `arch_prctl(ARCH_SET_FS, addr)` and `arch_prctl(ARCH_GET_FS, &addr)`. The `clone` syscall with `CLONE_SETTLS` takes the thread pointer as an argument and sets it for the new thread. The libc calls `clone` with `CLONE_SETTLS` and the address of the new thread's TCB, which it has already allocated and initialized. The kernel stores the value in the task structure and programs the FS base on the next context switch to that thread.

The context switch cost is where the kernel's implementation matters. On CPUs without the `FSGSBASE` instruction set, changing the FS base requires a write to the `IA32_FS_BASE` MSR. `wrmsr` is a serializing instruction that can cost on the order of a hundred cycles or more, and it cannot be executed in a tight loop. Every context switch between threads with different FS bases pays this cost. On CPUs with `FSGSBASE` (Intel since Ivy Bridge, AMD since Zen), the kernel can use the `wrfsbase` and `rdfsbase` instructions, which are much cheaper and can be executed in user space if enabled. Linux 5.9 and later enable `FSGSBASE` for user space, which allows the kernel to switch the FS base with a simple instruction and also allows user-space code to read and write it directly. This reduces context-switch overhead for threaded programs. The same pattern exists on AArch64 with `TPIDR_EL0`, which is a regular system register that can be written without a serializing MSR access.

There is a historical contrast on 32-bit x86. The thread pointer was not a full base register; it was a segment selector pointing into the Global Descriptor Table. Setting it required `set_thread_area`, which allocated a GDT entry for the thread. The GDT has a limited number of entries, and the kernel had to manage them, which limited the number of threads and added complexity. On x86-64, the FS base is a full 64-bit register, and no GDT entry is needed. This is one of the reasons x86-64 handles large thread counts more gracefully.

The kernel also has to handle the case where a thread is migrated between CPUs. The FS base is part of the thread's context, not the CPU's, so the kernel restores it on the new CPU as part of the context switch. The thread pointer is stable from the thread's perspective. The only way it changes is if user space explicitly changes it, which is rare and dangerous.

For a program that creates and destroys many threads, the cost of setting the thread pointer is part of the thread creation path. The libc allocates the TCB and static TLS, initializes the DTV, copies the `.tdata` template, and then calls `clone` with `CLONE_SETTLS`. The kernel then sets the FS base. The `clone` call itself is a system call, which costs on the order of a few hundred cycles even on a fast path. The TLS setup adds to that. For short-lived threads, this overhead can dominate the work the thread does.

## `fork()` in a multithreaded program

`fork()` creates a new process with a single thread: the one that called `fork`. The child's address space is a copy-on-write duplicate of the parent's, including the calling thread's TCB and TLS block. The other threads' TCBs and TLS blocks are not present in the child, because those threads do not exist. The child's thread pointer points at the copied TCB, and the copied TLS block contains the calling thread's thread-local variables. From the child's perspective, it is the same thread, with the same TLS, in a new process.

This is correct per the POSIX model, but it creates several hazards. The first is locks. If another thread held a lock at the moment of `fork`, the child inherits the lock in the locked state, and no thread in the child can release it because the thread that held it does not exist. This is the classic fork-in-multithreaded-program problem, and it is not specific to TLS. `pthread_atfork` handlers are the usual mitigation: a prepare handler acquires all locks before `fork`, a parent handler releases them in the parent, and a child handler releases them in the child. The prepare and child handlers run in the context of the calling thread, so they can access its TLS. They must not access the TLS of other threads, because those threads' TLS blocks are not present in the child.

The second hazard is resource leaks. If thread-local state represents a per-thread resource — a per-thread arena, a per-thread file descriptor, a per-thread cache — the child inherits the calling thread's resource and loses the others. The other threads' resources are not closed or freed in the child, because the destructors for their TLS objects do not run. The child may also inherit the calling thread's resource in a state that is not safe to use, because the resource was shared with other threads in the parent. For example, a per-thread arena that is part of a shared allocator may have internal pointers into shared metadata. The child's copy of the arena is a copy-on-write duplicate, but the shared metadata is also duplicated. If the child allocates from the arena, it may corrupt the metadata in a way that affects only the child, because the parent's copy is separate. This is usually fine, but it can be surprising.

The third hazard is `errno` and other thread-local state. The child's `errno` is a copy of the calling thread's `errno` at the moment of `fork`. If the `fork` call itself fails in the child (for example, because of a resource limit), the child's `errno` is set by the failure, overwriting the copied value. The parent's `errno` is set by the `fork` call in the parent. This is standard.

The fourth hazard is the dynamic thread vector. The child inherits a copy of the parent's DTV, including the generation counter and the pointers to dynamically allocated TLS blocks. Those blocks are in the child's address space as copy-on-write copies. If the child accesses a dynamic TLS variable, it will see the copied block. If the child loads a new module with `dlopen`, the loader assigns a new module ID. The child's DTV may need to grow, and the new block will be allocated in the child's heap. The parent's DTV is unaffected. There is no cross-process sharing of TLS state, so this is safe. The only subtlety is that the module ID counter is copied from the parent at the time of `fork`. If the parent later loads a module and the child also loads a module, they may assign the same module ID to different modules. That is fine because the processes are separate and their DTVs are separate. The module IDs are only meaningful within a process.

The most important practical rule is that `fork` in a multithreaded program is only safe if the child immediately calls `exec`. The `exec` call replaces the entire address space, including the TCB and TLS block, so all the hazards disappear. If the child must continue running without `exec`, it should limit itself to async-signal-safe functions until it has reinitialized the process state. Accessing a dynamic TLS variable is not async-signal-safe if it triggers the first allocation of a TLS block or a DTV generation check, because those paths take locks and call `malloc`. The child should avoid such accesses until it has called `pthread_atfork` handlers or otherwise reestablished a consistent state.

`vfork` is even more restrictive. The child shares the parent's address space, including the TCB and TLS block. If the child writes to a thread-local variable before calling `exec` or `_exit`, it modifies the parent's variable. The child must not return from the function that called `vfork`, and it must not access TLS in a way that could trigger allocation. The only safe action is to call `exec` immediately. `posix_spawn` is implemented on top of `vfork` on some systems and has the same constraints internally, but it handles them for you by calling `exec` without running user code in the child.

For programs that use `fork` as a way to spawn workers, the safe pattern is to `fork` early, before creating many threads, or to use `posix_spawn` with a fresh process image. If `fork` must be called in a multithreaded program, the `pthread_atfork` handlers should be used to make the child's state consistent, and any thread-local resources that are not safe to inherit should be reset in the child handler. The child handler runs after `fork` in the child, in the calling thread's context, so it can access the calling thread's TLS and reinitialize it. This is the place to reset per-thread caches, re-open per-thread file descriptors, and clear any state that refers to other threads.

## Static binaries and static PIE: the local-exec-only world

When a binary is statically linked, the dynamic loader is not present. There is no `dlopen`, no lazy binding, and no module IDs. Every thread-local variable in the program is in a module that is known at link time, so the linker can compute the offset from the thread pointer for every one of them. The result is that static binaries use local-exec for all TLS accesses. There is no GOT indirection, no `__tls_get_addr`, and no DTV generation check. Every TLS access is a single load or store with a segment prefix.

This is the simplest possible world for TLS, but it still requires setup. The C library's startup code must allocate the static TLS block, copy the `.tdata` template, zero the `.tbss` region, and set the thread pointer. In glibc, this is done by `__libc_setup_tls`, which is called during libc initialization before `main`. The function locates the `PT_TLS` program header in the executable, computes the total size and alignment, allocates the block, and initializes the TCB. It also sets up a minimal DTV for compatibility, but no dynamic modules will ever be added.

The `PT_TLS` program header is the only thing the C library needs to set up TLS. It contains the file offset and size of the initialized data, the total memory size, and the alignment. The linker emits it automatically when it sees `.tdata` or `.tbss` sections. For a static binary, the `PT_TLS` segment is part of the executable file, and the libc reads it directly from memory. The kernel's ELF loader does not process `PT_TLS`; it is purely a user-space concern. The kernel loads the executable and its segments, but the TLS block is allocated by the libc on the heap or in a dedicated area.

Static PIE binaries are a middle ground. They are position-independent, so they can be loaded at any address, but they are statically linked, so there is no dynamic loader. The TLS offsets are still known at link time relative to the thread pointer, because the thread pointer is set by the libc and the TLS block layout is fixed. The local-exec model works because the offset is a constant, not an absolute address. The segment prefix `%fs:` adds the offset to the thread pointer, and the thread pointer is a runtime value. The fact that the binary is position-independent does not affect TLS addressing. This is why static PIE can use local-exec even though the code is relocatable.

The absence of dynamic TLS in static binaries has a performance benefit: no `__tls_get_addr`, no DTV growth, no lazy allocation. It also has a functional limitation: no `dlopen`. A static binary cannot load plugins at runtime, so the static TLS surplus problem does not exist. The entire TLS area is sized at startup, and there is no need for a surplus. This is one of the reasons static binaries are attractive for embedded systems and for programs that need deterministic startup.

The alignment of the TLS block is determined by the maximum alignment of any thread-local variable in the program. The `p_align` field of the `PT_TLS` header records this, and the libc must allocate the block with that alignment. For over-aligned variables — say, `alignas(64) thread_local char buf[64];` — the alignment can be larger than the default. In a static binary, the startup code handles this once. In a dynamic binary, the static TLS surplus must accommodate the alignment padding. A 64-byte aligned variable of 64 bytes can consume 128 bytes of surplus if the current pointer is not already aligned. This is a subtle way to exhaust the surplus faster than the raw size suggests, and it is easy to miss when auditing a library's TLS footprint.

For a library that is linked statically into an executable, the linker relaxes its TLS references to local-exec as part of the static link. The library's `.tdata` and `.tbss` sections are merged into the executable's `PT_TLS` segment, and the library's thread-local variables become indistinguishable from the executable's own. This is the opposite of the `dlopen` case, where the library must use a dynamic model and pay the cost of `__tls_get_addr`. The same library source can produce radically different TLS code depending on whether it is linked statically or loaded dynamically.
