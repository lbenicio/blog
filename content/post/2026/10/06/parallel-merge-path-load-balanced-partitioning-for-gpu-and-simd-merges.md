# Parallel Merge Path: Load-Balanced Partitioning for GPU and SIMD Merges

Merging two sorted sequences is one of those primitives that looks solved until you try to parallelize it. The sequential merge is simple: two indices, compare the heads, emit the smaller, advance. It runs in O(m+n) time and touches each input once. On a single core, it is about as good as it gets. On a GPU, a many-core CPU, or a SIMD lane array, the same algorithm becomes a bottleneck because the output position is not known without walking the input. A thread cannot know which input element belongs at output index k without doing work proportional to k. That is the central problem.

The usual first attempt is to split the output range evenly. If there are P workers, worker p handles output indices [p*(m+n)/P, (p+1)*(m+n)/P). To start, it needs to know how many elements from A and B precede that output index. A binary search in A for the boundary and a binary search in B for the boundary can find it. That works, but it is not as clean as it sounds. The two binary searches are independent, and they can disagree about the split. You need a consistent co-rank, not just two local searches. If you search A for the position where A[i] crosses the output index and search B separately, you can end up with i+j != k, which means the workers overlap or leave a gap. You can repair it, but the repair logic is where bugs live.

The merge path gives a better abstraction. It turns the merge into a geometric object: a monotone path through an m by n grid. Once you see the merge as a path, load balancing becomes a partition of the path, and the partition points are computable with one binary search per boundary. The same primitive handles union, intersection, difference, and sort-merge join. It also maps well to GPUs and SIMD because it produces contiguous input ranges with predictable work.

## The merge path as a monotone lattice path

Let A be a sorted array of length m and B a sorted array of length n. Assume ascending order and a stable merge rule: when A[i] equals B[j], take A first. The merge path starts at the grid point (0,0) and ends at (m,n). At each step, if A[i] <= B[j], move right by one; otherwise move down by one. Moving right means the next output element comes from A. Moving down means it comes from B. After m+n steps, the path reaches (m,n). The path is monotone: it never moves left or up. Every merge corresponds to exactly one such path, and every such path corresponds to a merge.

The key observation is that the path intersects each anti-diagonal exactly once. An anti-diagonal is the set of grid points with i+j=d, for d from 0 to m+n. The value d is the number of output elements emitted so far. The intersection point is the co-rank of d. If the co-rank is i, then j=d-i, and the first d output elements contain exactly i elements from A and j elements from B. The co-rank is the unique i in [max(0,d-n), min(d,m)] that satisfies two inequalities: if i>0 and j<n, then A[i-1] <= B[j]; if j>0 and i<m, then B[j-1] < A[i]. The first inequality says the last A element taken is not greater than the next B element. The second says the last B element taken is strictly less than the next A element. Together they ensure the merge is stable and the split is consistent.

This is more than a pretty picture. It means you can partition the merge by choosing a set of diagonals d0 < d1 < ... < dP = m+n. For each diagonal, compute the co-rank. Then worker p merges the subarrays A[i_{p-1}..i_p) and B[j_{p-1}..j_p), where i_p and j_p are the co-rank components at d_p. The subarrays are contiguous, disjoint, and cover the whole input. The output ranges are also contiguous and disjoint. No locking, no atomics, no conflict resolution. The only shared work is computing the co-ranks, which is a set of independent binary searches.

## Co-ranking: the binary search that balances work

The co-rank can be computed with a binary search over the possible i values. The search range is lo = max(0, d-n) and hi = min(d,m). The invariant is that the co-rank lies in [lo, hi]. At each step, pick mid = (lo+hi)/2 and set j = d-mid. If mid < m and j > 0 and B[j-1] > A[mid], then we have taken too many B elements relative to A, so the co-rank must be greater than mid. Set lo = mid+1. Otherwise, set hi = mid. When lo == hi, that is the co-rank. The search takes O(log(min(m,n))) time in the worst case, but the range is often smaller because d constrains i and j.

The binary search is the only nontrivial part. It is branchy, but it is short. On a GPU, a warp can compute several co-ranks in parallel, or one thread can compute one co-rank while other threads wait. The cost is negligible compared to the merge work if the tiles are large enough. The rule of thumb is that the binary search should be less than a few percent of the tile work. For a tile of 4096 output elements, a 12-step binary search is noise. For a tile of 64 elements, it is a significant fraction. This trade-off is the main tuning knob.

There is a subtlety with duplicates. The inequalities above assume a stable merge rule that takes A before B on equality. If you use a different rule, the co-rank definition changes. For example, if you take B before A on equality, the second inequality becomes B[j-1] <= A[i]. The binary search condition changes accordingly. This matters for sort-merge join and for any application where the relative order of equal keys affects the result. The merge path itself is agnostic; the tie-breaking rule is a parameter. You must encode it consistently in the co-rank predicate and in the sequential merge kernel. If you do not, you can get overlapping or missing elements at tile boundaries.

### A minimal co-rank implementation

The co-rank function can be written in a few lines. In pseudocode:

```
function co_rank(A, B, d):
    lo = max(0, d - len(B))
    hi = min(d, len(A))
    while lo < hi:
        mid = (lo + hi) / 2
        j = d - mid
        if mid < len(A) and j > 0 and B[j-1] > A[mid]:
            lo = mid + 1
        else:
            hi = mid
    return lo
```

This returns i; j is d-i. The function assumes A and B are sorted ascending and that ties take A first. For descending order, you flip the comparison. For a different tie rule, you adjust the strictness. The boundary cases are handled by the range of lo and hi. If d is 0, lo=hi=0. If d=m+n, lo=hi=m. If d is between, the search finds the unique split. The invariant is that for all i < lo, the predicate is false, and for all i >= hi, the predicate is true. The predicate is monotone because the merge path is monotone. That monotonicity is what makes binary search valid.

The function does not allocate memory, does not branch on data except in the predicate, and is safe to call from multiple threads. It is the only serial dependency in the partitioner. Everything else is data-parallel. This is why the merge path is a useful building block: it isolates the irregular, data-dependent part into a tiny, well-understood routine.

## Why the diagonal view matters on real hardware

On a CPU, the merge path partitioner gives you a simple fork-join structure. You compute P co-ranks, then spawn P tasks. Each task merges two contiguous ranges. The tasks are independent, so you can use OpenMP, TBB, or a thread pool. The memory access pattern is sequential within each task. The only concern is false sharing at output boundaries, which you can avoid by aligning output ranges to cache lines or by using per-task buffers. The merge path does not eliminate memory bandwidth limits, but it makes them predictable. Each input element is read once, each output element is written once. The total traffic is (m+n) reads plus (m+n) writes, plus the co-rank searches. That is optimal.

On a GPU, the merge path is even more attractive. A GPU kernel wants many independent tiles with balanced work. The merge path gives exactly that. You can launch one thread block per tile. Each block computes its co-rank boundaries, loads its subarrays into shared memory or registers, and merges. The load is coalesced if the subarrays are contiguous, which they are. The output is coalesced if the block writes its output range contiguously, which it does. The only irregularity is the start offset of each subarray, which can be unaligned. You can handle that with a small scalar prologue or by using vectorized loads with a misalignment penalty. The merge path does not make the problem disappear, but it localizes it to the tile boundaries.

The diagonal view also helps with SIMD. In a SIMD merge, you want to process multiple output elements per instruction. The merge path lets you split the output into blocks of, say, 8 or 16 elements. For each block, you can compute the co-rank and then use a vectorized merge network or a bitonic merge. The co-rank ensures that the block boundaries are correct. Without it, you would need to compare and shuffle across lanes in a way that depends on the data, which is expensive. With it, the data-dependent control flow is pushed to the co-rank search, which is scalar and short, and the inner loop is regular.

## The partitioner in practice

A practical merge path partitioner has three stages. First, choose the diagonal boundaries. The simplest choice is uniform: d_p = p*(m+n)/P. This balances the output count, not the input count. If one array is much larger than the other, the work per tile is still balanced because the output count is the sum of the input counts consumed. The number of comparisons is at most the output count, so uniform diagonals give balanced comparison work. The memory traffic is also balanced because each tile reads exactly the number of elements it outputs. The only imbalance is in the co-rank search range, which is bounded by min(m,n). That is usually acceptable.

Second, compute the co-ranks. You can do this in parallel. On a CPU, a parallel for loop over the boundaries. On a GPU, a small kernel with one thread per boundary, or a single warp if P is small. The co-rank function is pure and has no side effects, so it is easy to parallelize. You should compute the boundaries in a way that avoids redundant work. For example, you can compute all co-ranks independently; there is no need to carry state from one boundary to the next. The binary search is O(log n) and independent.

Third, run the merge kernels. Each kernel takes the four indices (i0, i1, j0, j1) and the output offset. It merges A[i0..i1) and B[j0..j1) into the output. The merge is the standard sequential merge, but it can be vectorized or unrolled. The output offset is d0, the diagonal of the first boundary. The kernel writes exactly (i1-i0)+(j1-j0) elements, which is d1-d0. This is the key invariant: the output range size equals the diagonal difference. If your kernel writes a different number, you have a bug in the co-rank or in the merge predicate.

The partitioner is also useful for set operations. For union, you merge and emit duplicates only once. For intersection, you emit only when A[i] == B[j]. For difference, you emit A elements not in B. The co-rank for these operations is slightly different because the output size is not m+n. You cannot use the diagonal d as the output index directly. Instead, you partition by input ranges and compute the output size per tile. The merge path still gives you the input ranges, but you need a separate count for the output. This is a common pattern in parallel set operations: first partition the inputs, then compute per-tile output counts with a prefix sum, then write. The merge path provides the input partition; the output prefix sum provides the write offsets. This two-phase approach is standard for parallel union and intersection.

The same idea applies to sort-merge join. You partition both relations by key ranges using the merge path, then each tile joins its subranges. The co-rank gives you the key boundaries. If the join is many-to-many, the output size per tile can be large and variable. You can use the merge path to balance the input work, but the output work may be skewed. In that case, you might need a second level of partitioning or a work-stealing queue. The merge path is not a complete solution for all skew, but it removes the input-side imbalance.

The remainder of this article will develop the co-rank primitive in more detail, including vectorized co-rank search, tile size selection, memory alignment, and the application of merge path to parallel union, intersection, and sort-merge join. The goal is not to present a single optimal kernel, but to show how the diagonal view turns a sequential dependency into a partitioning problem that modern hardware can execute efficiently.

## Vectorizing the co-rank search

The co-rank routine is short, but it is still a serial binary search. When you need many co-ranks, one per tile boundary, you can compute them in parallel. The obvious way is one thread per boundary. On a CPU, that means a parallel for loop. On a GPU, a small kernel with one thread per boundary. But you can do better by vectorizing across boundaries. Since every co-rank solves the same predicate with a different diagonal d, you can pack multiple diagonals into SIMD lanes and run the binary search in lockstep.

The first step is to make the predicate branchless and safe. The naive predicate checks mid < len(A), j > 0, and B[j-1] > A[mid]. Those bounds checks create branches and limit vectorization. A standard trick is to pad the arrays with sentinels. Append a sentinel +inf to A at index m. For B, create a shifted view B' where B'[0] = -inf and B'[j] = B[j-1] for j >= 1. Then the predicate becomes simply B'[j] > A'[mid], where A' is A with the +inf sentinel. If j=0, B'[0] = -inf, so the comparison is false. If mid=m, A'[m] = +inf, so the comparison is false. No bounds checks are needed. The sentinels cost one extra element per array, or you can handle the edge cases with masked loads if you cannot modify the inputs.

With sentinels, the binary search loop becomes:

```
lo = max(0, d - n)
hi = min(d, m)
while lo < hi:
    mid = (lo + hi) >> 1
    j = d - mid
    pred = B_shifted[j] > A_padded[mid]
    lo = pred ? mid + 1 : lo
    hi = pred ? hi : mid
return lo
```

This is branchless if the compiler uses conditional moves. On a GPU, it compiles to predicated instructions. On a CPU, it compiles to cmov. The loads B_shifted[j] and A_padded[mid] are unconditional, which is safe because of the sentinels. This is the scalar version. To vectorize, you take V diagonals, one per lane. Each lane has its own lo, hi, and d. In each iteration, all lanes compute mid and j, gather the two values, compare, and update lo/hi with vector selects. Lanes that have already converged (lo == hi) can be masked off, or they can continue harmlessly because mid will equal lo and the update will keep lo == hi. The loop runs until all lanes converge. The number of iterations is at most ceil(log2(min(m,n)+1)). For 32-bit indices, that is at most 32 iterations. In practice, the range [lo, hi] is often much smaller.

The gathers are the main cost. If A and B are large, each gather may miss cache. But the co-rank search only touches O(log n) elements per boundary. For P boundaries, the total number of gather operations is P * log(min(m,n)). If P is small relative to the tile size, this is negligible. For example, if you have 1 million elements and tile size 4096, P is about 244. With log2(1e6) approximately 20, that is about 4880 gathers. The merge itself reads 1 million elements. The overhead is less than 0.5%. Even with cache misses, the co-rank search is a small fraction of the total time.

You can further reduce the cost by computing co-ranks hierarchically. First compute a few coarse co-ranks at widely spaced diagonals. Then for each coarse interval, compute finer co-ranks using the coarse bounds to narrow the search range. This reduces the total number of binary search steps. For example, if you compute 16 coarse co-ranks, each covering a range of 1/16 of the output, the remaining co-ranks can search within a range that is 1/16 of the original. The total work becomes O(P log(min(m,n)/P) + P_coarse log(min(m,n))). This is a classic parallel binary search optimization. It is especially useful when P is large and the arrays are huge. On a GPU, you can do this with two kernels: one for coarse co-ranks, one for fine co-ranks. The coarse kernel is small, and the fine kernel has a much smaller search range.

## Choosing tile sizes and diagonal spacing

The tile size T is the number of output elements per worker. It determines the trade-off between co-rank overhead and load balance. If T is too small, the co-rank search dominates. If T is too large, you have too few tiles to fill the machine, and the tail effect appears. The optimal T depends on the hardware, the element size, and the merge kernel.

A simple cost model helps. Let C_search be the cost of one co-rank search. Let C_merge be the cost per output element in the merge kernel. The total time per tile is C_search + T * C_merge. The parallel efficiency is T * C_merge / (C_search + T * C_merge). To keep efficiency above 95%, you need T * C_merge > 19 * C_search. If C_search is about 200 cycles, including a few cache misses, and C_merge is about 2 cycles per element, then T > 1900. So T = 2048 or 4096 is a reasonable starting point. If C_search is lower because the arrays fit in cache, T can be smaller. If C_merge is higher because of branch mispredictions or unaligned accesses, T can be smaller too.

On a GPU, the tile size is also constrained by shared memory. If each block loads its A and B subarrays into shared memory, the shared memory footprint is T * (size of A element + size of B element) in the worst case. Actually the sum of A and B elements consumed equals T, so the total shared memory is T * sizeof(element). For 4-byte elements and T=4096, that is 16 KB. For 8-byte elements, 32 KB. Modern GPUs have 48-96 KB of shared memory per block, so T=4096-8192 is feasible. If you use registers instead of shared memory, the limit is register file size. For a merge kernel, you can keep the current heads in registers and stream the rest from global memory. Then shared memory is not needed. In that case, T can be larger, limited by the number of blocks and occupancy.

On a CPU, the tile size should fit in L2 cache. If T=8192 and each element is 8 bytes, the input subarrays are 64 KB. L2 is typically 256 KB to 1 MB per core, so this fits. The output range is also T elements, which adds another 64 KB. If you write to a separate output buffer, the total working set is 128 KB. That fits in L2. So T=8192 is a good target for CPU. For AVX-512, you process 16 elements per vector, so T should be a multiple of 16, preferably a multiple of 64 or 128 to amortize loop overhead.

Diagonal spacing does not have to be uniform. Uniform spacing balances output count, which balances comparison work. But if the merge kernel has different costs for A and B elements, for example if A elements are larger or require more processing, you might want to balance input work instead. You can do this by choosing diagonals that equalize a weighted sum of A and B elements. The co-rank function already gives you the split for any diagonal. To find a diagonal that gives a certain number of A elements, you can invert the co-rank. But that is more complex. In practice, uniform diagonals are sufficient for most merges because the per-element work is symmetric.

There is one case where uniform diagonals are not ideal: when one array is much smaller than the other. Suppose m = 1,000,000 and n = 1,000. The merge path is mostly horizontal. Uniform diagonals will produce tiles that each consume about T elements from A and very few from B. The co-rank search range is small because n is small. The merge kernel will mostly read from A. That is fine. The work is balanced because each tile outputs T elements. The only imbalance is that some tiles may consume a few more B elements than others, but the difference is at most n. So uniform diagonals are still good.

## Handling alignment and vectorized loads

The merge path partitioner gives contiguous subarrays, but the start indices i0 and j0 are arbitrary. For SIMD, you want aligned loads. On x86, unaligned loads are allowed but may have a penalty if they cross a cache line. On ARM, unaligned loads are also allowed but may be slower. On GPUs, vector loads must be aligned to the vector size. If you want to use 128-bit loads, the address must be 16-byte aligned. The merge path does not guarantee that.

The standard solution is a scalar prologue. Before entering the vectorized loop, you process elements one by one until both the A pointer and the B pointer are aligned. Since you have two pointers, you may need to advance them independently. The merge kernel already has a comparison loop; you can simply run the scalar merge until the alignment condition is met. The number of scalar iterations is at most the vector width minus one for each pointer, so at most 2*(V-1) elements. For V=8, that is at most 14 elements. For a tile of 4096, this is negligible. The scalar prologue also handles the case where one subarray is empty or exhausted.

After the prologue, both pointers are aligned. You can then load vectors from A and B, compare them, and produce a vector of output elements. The output pointer may not be aligned. You can either write unaligned vectors or use a scalar epilogue. Writing unaligned vectors is usually fine on modern CPUs. On GPUs, you can write to shared memory and then do a coalesced write to global memory. The shared memory write can be unaligned; the global write is aligned if the block output range is aligned. But the block output range starts at d0, which may not be aligned. You can align the output range by adjusting the diagonal boundaries. For example, you can round d0 down to a multiple of the vector width and let the first tile handle the remainder. But that breaks the equal-work property. A simpler approach is to have each block write its output to a shared memory buffer, then have the threads cooperatively write the buffer to global memory. The global write can be aligned if the block output offset is aligned. If it is not, you can do a scalar prologue for the output as well. Since the output is written once, the cost is small.

Another approach is to pad the input arrays so that all subarray starts are aligned. You can copy the inputs into aligned buffers, but that adds memory traffic. For large merges, the copy is O(m+n), which doubles the input traffic. That is usually not worth it. The scalar prologue is cheaper.

For SIMD merge networks, alignment is less of an issue because you load elements into registers and use shuffles. The merge path gives you the boundaries, and you can load the subarrays into registers with unaligned loads. The merge network then operates on registers. The output is written with unaligned stores. The overhead is in the load/store, which is a small fraction of the total work.

## Merge path for parallel union, intersection, and difference

The merge path is not limited to pure merges. It is a general partitioning primitive for any operation that can be expressed as a monotone path through two sorted sequences. Union, intersection, and difference all fit this model. The key difference is that the output size is not known in advance. For union, the output size is m + n - duplicates. For intersection, it is the number of matches. For difference, it is m - matches. You cannot use the diagonal d as the output index because d counts input elements, not output elements.

The standard parallel pattern for these operations is two-phase. In the first phase, you partition the inputs using the merge path. You choose P boundaries in the input space, not the output space. For example, you can partition A into P equal-sized chunks, and for each chunk, find the corresponding range in B using binary search. Or you can partition the merge path itself by choosing P points on the path. Each point gives a pair of indices (i, j). The tiles are the subarrays between consecutive points. In the first phase, each tile runs a sequential union, intersection, or difference on its subarrays and counts the output size. The counts are stored in an array of size P. Then you compute a prefix sum over the counts to get the write offset for each tile. In the second phase, each tile runs the same sequential operation again and writes its output to the correct offset. The two phases are both parallel and load-balanced because the input partition is balanced.

The cost of the two-phase approach is roughly twice the comparison work of a single sequential pass. The first phase does the comparisons to count, the second phase does them again to write. You can avoid the second comparison by storing the intermediate results in the first phase, but that requires memory proportional to the output size, which may be large. For union and intersection, the output size is at most m+n, so you could allocate a temporary buffer and write the output with gaps, then compact. But that adds a compaction pass. The two-phase approach is simpler and often faster because the second phase is memory-bound and the comparisons are cheap.

For sort-merge join, the same idea applies, but the output size can be much larger than the input size. If the join is one-to-many or many-to-many, a single tile can produce a huge number of output tuples. The merge path still gives you a balanced input partition, but the output work per tile can be skewed. You can handle this by partitioning the join into two levels. First, partition by key ranges using the merge path on the keys. Then, for each key range, if the output size is too large, partition further by the multiplicity of the keys. For example, you can split a tile by the number of matching tuples. This is essentially a work-stealing or dynamic partitioning scheme. The merge path provides the initial static partition, which is enough to get good load balance for the input side. The output side may need additional balancing, but that is a separate problem.

The co-rank primitive is also useful for parallel set operations on more than two arrays. You can merge multiple sorted arrays by building a merge tree. At each level of the tree, you merge pairs of arrays using the merge path. The same partitioner works for each pair. The load balancing is hierarchical: you partition the output of each merge, which gives you balanced work at every level. This is how parallel merge sort is often implemented on GPUs. The merge path makes each merge step load-balanced, so the overall sort is load-balanced.

## Multi-way merging with the merge path

The two-array merge path extends naturally to multi-way merging through a merge tree. Suppose you have k sorted sequences. A common strategy is to merge them pairwise in a balanced tree: level 0 merges pairs (0,1), (2,3), and so on; level 1 merges the results, and so forth. Each pairwise merge is an independent two-array merge, so each can use the merge path partitioner. The load balancing is hierarchical: at every level, the output is partitioned into tiles of equal diagonal length, and each tile is assigned to a worker. The total work is O(N log k), where N is the total number of elements. The merge path does not eliminate the log k factor, but it ensures that no level becomes a serial bottleneck.

The merge tree also gives a clean way to handle stability. If the input sequences are ordered by a key and you need a stable merge, you must define a consistent tie-breaking rule across all levels. One approach is to attach a sequence index to each element and use it as a secondary key. When two elements have equal primary keys, the one from the lower sequence index comes first. The co-rank predicate then compares the pair (key, index) instead of just the key. The merge path itself is unchanged; only the comparison function changes. This is important for parallel merge sort, where the initial runs are produced by sorting blocks and the merge tree must preserve the original order of equal elements.

For k-way merging without a tree, you can generalize the merge path to a k-dimensional monotone path. The path starts at the origin and ends at (n_0, n_1, ..., n_{k-1}). At each step, you advance along one axis, corresponding to taking the next element from that sequence. The anti-diagonal d = sum of coordinates represents the number of output elements emitted. The co-rank is a vector of k coordinates that sum to d. Finding this vector is harder than in the two-array case because there are k-1 degrees of freedom. You can still find it with a binary search if you use a tournament tree to determine the next element, but the search is no longer a simple one-dimensional predicate. In practice, the pairwise merge tree is simpler and often faster because each merge is a well-optimized two-array merge. The k-way path is more useful for theoretical analysis than for implementation.

A hybrid approach is to use a k-way merge for small k, such as 4 or 8, and a merge tree for larger k. For k=4, you can compute the co-rank by doing two binary searches: first split the output between two pairs of sequences, then split each pair. This is equivalent to a shallow merge tree. The advantage is that you can keep the data in registers and avoid the overhead of multiple passes. On a GPU, a 4-way merge can be implemented with a warp-level tournament, where each lane holds one sequence head and the minimum is broadcast with shuffle instructions. The merge path partitioner provides the starting positions for each lane, so the tournament starts at the correct offset. This combines the load balancing of the merge path with the low latency of a warp-level tournament.

## SIMD merge networks after partitioning

Once the merge path has divided the output into tiles, each tile is a standard two-array merge of contiguous subarrays. The inner loop of that merge can be vectorized using a merge network. The most common network for two sorted sequences is the bitonic merge. Given two sorted sequences X and Y, reverse Y and concatenate it with X to form a bitonic sequence. A bitonic sequence first increases and then decreases. A bitonic merge network then sorts it with a fixed pattern of compare-exchange operations. The network has log2(L) stages, where L is the total length. At each stage, elements are compared at a fixed distance and swapped if they are out of order. The pattern is data-independent, which makes it ideal for SIMD.

For small L, such as 8 or 16, the entire bitonic merge can be held in registers. On AVX-512, you can load 16 elements from X and 16 from Y, reverse one vector, and then run the network using min/max and permute instructions. The merge path ensures that the tile boundaries are correct, so you do not need to handle cross-tile comparisons. The network produces a sorted vector of 32 elements, which you can store with two vector stores. The number of instructions is fixed and does not depend on the data. This is a significant advantage over a scalar merge, which has unpredictable branches.

On a GPU, the same idea works at the warp level. Each lane holds one element, and the bitonic merge is implemented with shuffle instructions. A warp of 32 lanes can merge two sorted sequences of 16 elements each. The merge path partitioner assigns each warp a tile of 32 output elements and computes the co-rank boundaries. The warp then loads its subarrays, performs the bitonic merge with shuffles, and writes the result. The shuffle network is fixed, so there is no divergence. For larger tiles, you can use a block-level merge where each thread processes a small run and then threads cooperate through shared memory. The merge path still provides the global partitioning.

The choice between a bitonic network and a sequential merge depends on the element size and the hardware. For 32-bit integers, a bitonic network in registers is very fast. For 64-bit keys with payloads, the cost of shuffling payloads may outweigh the benefit. In that case, a scalar merge with branchless comparisons and conditional moves may be better. The merge path is agnostic to the inner merge algorithm; it only provides the partition. This separation of concerns is one of its strengths. You can tune the inner merge independently of the partitioning.

One subtlety with SIMD merge networks is the handling of duplicates. The bitonic network is not stable by default. If you need a stable merge, you must augment the comparison with a tie-breaker, such as the source index. This increases the comparison cost. Alternatively, you can use an odd-even merge network, which can be made stable with a careful ordering of compare-exchange operations. The merge path co-rank predicate must use the same tie-breaker, otherwise the tile boundaries will not match the network's output order. Consistency between the partitioner and the inner merge is essential.

## Weighted and adaptive partitioning under skew

Uniform diagonal spacing balances the number of output elements per tile. That is optimal when every output element costs roughly the same to produce. In many real workloads, the cost varies. For example, in a sort-merge join, producing an output tuple may require copying a payload, evaluating a predicate, or updating a hash table. If one tile contains many matches and another contains few, the work per tile is skewed even though the output count is equal. The merge path can be extended to balance a weighted work function instead of the raw output count.

Let w_A(i) be the cost of consuming A[i], and w_B(j) the cost of consuming B[j]. The total work along the merge path up to diagonal d is the sum of w_A over the A elements taken and w_B over the B elements taken. This is a monotone function of d. To partition the path into P segments of equal work, you need to find diagonals d_0 < d_1 < ... < d_P such that the work between consecutive diagonals is equal. You can find each boundary by binary searching over d. For a target cumulative work W, you search for the smallest d such that cumulative_work(d) >= W. Each evaluation of cumulative_work(d) requires a co-rank computation and a prefix sum lookup. If you precompute prefix sums of w_A and w_B, the cumulative work is prefix_A[i] + prefix_B[j], where (i,j) is the co-rank at d. The binary search over d takes O(log(m+n)) steps, and each step takes O(log(min(m,n))) for the co-rank. This is more expensive than uniform partitioning, but it can be worthwhile when the work is highly skewed.

For sort-merge join, the output multiplicity is often the dominant cost. You can estimate the multiplicity per key range using histograms or sampling. Then you can define the weight of a key range as the product of the input cardinalities. The merge path partitioner then balances the estimated join output rather than the input size. This is a form of cost-based partitioning. It is not exact because the estimate may be off, but it is usually better than uniform partitioning. If the skew is extreme, you can combine static partitioning with dynamic work stealing. The static partitioner assigns each worker a range of the merge path. If a worker finishes early, it can steal a subrange from a busy worker. The merge path makes stealing easy because any subrange of the path is a valid merge task. You just need to compute the co-rank for the new boundaries.

Adaptive partitioning can also be done in a single pass. Instead of choosing all diagonals in advance, you can use a persistent kernel where each block atomically claims the next tile from a global counter. The tile size can be fixed or variable. If variable, the block can claim a diagonal range based on the remaining work. This is essentially dynamic scheduling. The merge path provides the mapping from diagonal to input indices, so the block can start immediately. The overhead is the atomic claim, which is small compared to the merge work. This approach handles unknown skew gracefully and is common in GPU implementations of merge sort and join.

## GPU-specific merge path kernels

On a GPU, the merge path partitioner is usually implemented as a small kernel that computes the co-ranks for all tile boundaries. The main merge kernel then launches one thread block per tile. Each block reads its A and B subarrays, merges them, and writes the output. The block size and tile size determine occupancy. For a merge of 32-bit keys, a tile of 4096 elements and a block of 256 threads gives 16 elements per thread. That is enough to amortize the co-rank search and the block launch overhead. The block can load its subarrays into shared memory in a coalesced fashion, then each thread merges a portion of the tile. The merge within the block can be done with a parallel merge algorithm, such as merge path applied recursively within the block, or with a sequential merge per thread if the per-thread ranges are contiguous.

Shared memory bank conflicts are a common pitfall. When threads read from A and B simultaneously, the access pattern may cause conflicts if the arrays are stored in shared memory without padding. A simple fix is to pad the shared memory arrays so that the stride between consecutive elements is not a multiple of the bank count. For example, if there are 32 banks, you can add one padding element every 32 elements. This shifts the bank mapping and reduces conflicts. Alternatively, you can use a register-based merge where each thread holds its own run of elements and does not use shared memory for the merge itself. This avoids bank conflicts entirely but requires more registers. The trade-off depends on the element size and the register pressure.

For warp-level merges, the co-rank can be computed by a single thread and broadcast to the warp using shuffle. The warp then loads its subarrays with coalesced loads. If the subarrays are not aligned, you can use a scalar prologue or unaligned vector loads. On modern GPUs, unaligned loads are supported but may be split into multiple transactions. For a warp of 32 threads, a 128-byte transaction is optimal. If the subarray start is not 128-byte aligned, the first load may touch two cache lines. This is a minor penalty for large tiles. You can also use the merge path to align the tile boundaries to 128-byte boundaries in the output, but that may unbalance the work. In practice, the unaligned penalty is small compared to the merge work.

A persistent kernel can process many tiles with a single block launch. Each block loops over a set of tiles, computes the co-rank for the next tile, and merges. This reduces the overhead of launching many blocks and allows the block to keep its state in registers. The tile assignment can be static or dynamic. For static, each block gets a contiguous range of diagonals. For dynamic, a global atomic counter assigns tiles. The dynamic version handles skew better but has atomic overhead. The static version is simpler and often sufficient when the work is balanced. The merge path makes both versions straightforward because the tile boundaries are independent and can be computed on the fly.

## CPU multicore implementation patterns

A CPU implementation of the merge path partitioner usually starts as a parallel for loop over tile boundaries. That is the right first version, but it is not the right final version. A fixed number of tasks equal to the number of cores creates a tail whenever one tile runs longer than the others, and the scheduler has no way to recover. The merge path makes it easy to use more tiles than cores because each tile is independent. A common structure is to create a pool of worker threads and a shared atomic counter. Each worker claims the next tile index, computes the two co-ranks for that tile, merges the corresponding subarrays, and repeats. The atomic fetch-add is cheap relative to the merge work, and the dynamic assignment absorbs small variations in tile cost.

There is a locality trade-off. If workers claim tiles in arbitrary order, consecutive output ranges may be written by different cores, which can hurt write-combining and NUMA locality. A hybrid scheme avoids most of the problem. Divide the output into a small number of coarse stripes, at least one per NUMA node or L3 cache domain. Assign each stripe to a group of workers. Inside the stripe, workers claim tiles dynamically from a local counter. The coarse stripes preserve first-touch locality and reduce contention on a single global counter. The inner dynamic scheduling handles skew. This is especially useful on multi-socket machines where writing a large output across sockets can cost more than the merge itself.

Output allocation deserves attention. For a pure merge, the output length is known, so a single allocation is enough. For union, intersection, or difference, the two-phase count-then-write pattern needs a prefix sum over tile counts. That prefix sum should be computed over the tile counts, not over per-element counts, to keep it parallel. The prefix sum is O(P) and can be done with a small parallel scan or even a serial loop when P is small. The second phase then writes into disjoint output ranges. If the operation is a sort-merge join and the output size is unknown, overallocate based on an estimate, or use a per-tile buffer and compact afterward. The merge path does not dictate the output strategy; it only guarantees that the input ranges are disjoint.

The inner merge on a CPU should be written to avoid unpredictable branches when possible. A scalar merge with a branch for A[i] <= B[j] is short, but the branch is data-dependent and can mispredict frequently, especially when the two inputs are interleaved. A branchless variant uses conditional moves or selects. In C++, the compiler often turns a ternary expression into a conditional move if both sides are cheap. The loop body becomes: compare the two heads, select the smaller value, select the source index, advance the selected source, and store. The comparison result also drives the advance. This is more instructions than the branchy version, but it has no misprediction penalty. For large random merges, the branchless version often wins; for long runs from one input, the branchy version may win because the branch predicts perfectly. The best choice depends on the data, so a production library may provide both and select based on a sampling pass.

Software prefetching can help when the inputs are much larger than cache. The merge reads A and B sequentially, so the next cache lines are predictable. Issuing prefetches one or two iterations ahead hides some memory latency. The output writes are also sequential. Non-temporal stores may help when the output is huge and will not be read soon, but they bypass cache and can hurt if the output is consumed immediately by a later stage. Measure both. The merge path does not change the memory access pattern within a tile; it only makes the tiles independent. That means cache behavior is mostly determined by tile size and by whether workers are reading the same cache lines. With disjoint tiles, there is no sharing except at boundaries, which is exactly what you want.

For AVX2 and AVX-512, the inner merge can be implemented as a sequence of vector comparisons and permutes. The merge path gives a tile boundary that is not necessarily aligned to the vector width. A scalar prologue handles the first few elements until the active pointers are aligned, and a scalar epilogue handles the last few. The middle of the tile uses vector code. If the tile is too small, the prologue and epilogue dominate. This is another reason to choose tiles of at least a few thousand elements. The vector merge itself can use a bitonic network or a merge network based on compress and expand. Both are data-independent and avoid branches. The merge path is the outer partitioner; the network is the inner engine. Keeping these two layers separate makes it possible to tune the network without touching the partitioning logic.

## Correctness invariants and verification harness

The merge path partitioner is small enough to reason about, but it has several invariants that should be checked explicitly during development. The first is co-rank consistency. For a diagonal d, the returned i and j = d - i must satisfy the predecessor and successor conditions for the chosen tie rule. In a debug build, assert that i is within the allowed range, that j is within the allowed range, and that the boundary elements are ordered correctly. If A[i-1] and B[j] are both present, assert A[i-1] <= B[j] for a stable merge that takes A first. If B[j-1] and A[i] are both present, assert B[j-1] < A[i]. These assertions catch off-by-one errors in the binary search and tie-rule mistakes immediately.

The second invariant is monotonicity. If d0 < d1, then the co-rank for d0 must be no greater than the co-rank for d1 in both components. This follows from the monotone path, but a buggy search range or an overflowing midpoint can violate it. A cheap check is to compute all boundaries and assert that i_p and j_p are nondecreasing. This also catches cases where the partitioner accidentally swaps the arrays or uses a descending comparator on ascending data. The third invariant is coverage. The first tile must start at (0,0), the last tile must end at (m,n), and the end of one tile must equal the start of the next. If the boundaries are stored as four indices per tile, check that i1 of tile p equals i0 of tile p+1 and similarly for j. Coverage failures usually mean the co-rank search returned a value outside the valid range for the final diagonal.

The fourth invariant is output length. For a pure merge, tile p must write exactly (i1 - i0) + (j1 - j0) elements, which must equal d1 - d0. If the kernel writes a different count, either the co-rank is wrong or the merge predicate differs from the predicate used in the co-rank. This is a common bug when the tie rule is changed in one place but not the other. For set operations, the output count is not the diagonal difference, so the invariant becomes a count equality: the number of elements the tile emits must equal the count recorded during the first phase. The same predicate must be used in both phases. A debug mode can run the sequential operation on each tile and compare the count with the stored count.

A differential test against a trusted sequential implementation is the most effective verification. Generate two sorted arrays using a variety of distributions: random keys with many duplicates, disjoint ranges, interleaved runs, one array much smaller than the other, and arrays that are already merged. For each case, run the parallel merge path implementation and the sequential merge, then compare element by element, including the order of equal keys. Stability bugs often appear only with duplicates, so the duplicate-heavy case is essential. For set operations, compare against a sequential set union, intersection, or difference that uses the same tie rule. For sort-merge join, compare against a nested-loop reference on small inputs and against a hash join on larger inputs where the output is order-insensitive.

Memory debugging is also useful. Fill the output buffer with a poison pattern before the merge and check that every output position is written exactly once. This catches gaps caused by incorrect co-ranks and overlaps caused by double-counting. Run under a race detector when using a dynamic tile queue; the merge itself should have no data races, but the tile counter and any per-tile metadata can. If the implementation uses shared scratch buffers, verify that each tile uses a disjoint region. A deterministic checksum over the output is a fast way to compare runs across thread counts and schedules. The checksum should include the source index of each output element, not just the value, because a stable merge with duplicate keys can produce the same values in different orders and still be wrong.

Edge cases deserve explicit tests. Empty A, empty B, both empty, one element, all elements equal, and inputs containing the minimum and maximum representable values. If sentinels are used, test with keys equal to the sentinel value; an infinity sentinel is safe for floating-point keys only if the input cannot contain infinity, or if the comparator treats it as a total order. NaN is a separate problem: a comparator that is not a strict weak ordering will break both the co-rank search and the inner merge. Either reject NaN at the API boundary or use a total-order comparator that places NaN consistently. For integer keys, test with 64-bit indices that exceed 32-bit range, and make sure diagonal calculations use 64-bit arithmetic. A common overflow is computing p * (m+n) in 32-bit before dividing by P; compute the quotient and remainder separately or cast before multiplying.

## Performance modeling and profiling

A merge path implementation is usually memory-bound. For a pure merge of N = m + n elements, the ideal traffic is N reads from A and B combined, plus N writes to the output. If each element is 4 bytes, that is 8N bytes. The merge path partitioner adds a small number of co-rank searches, but their traffic is negligible for reasonable tile sizes. The first performance question is therefore whether the kernel is close to the memory bandwidth roofline. Measure the achieved bandwidth and compare it with a simple copy kernel on the same machine. If the merge reaches most of the copy bandwidth, further instruction-level optimization will not help much. If it is far below, the bottleneck is likely branch misprediction, poor vectorization, or insufficient memory-level parallelism.

Profiling should separate the partitioner from the merge. On a GPU, the co-rank kernel and the merge kernel can be timed with separate events. On a CPU, use a dedicated phase or a sampling profiler to attribute time to the binary searches. The co-rank cost is proportional to P log(min(m,n)), while the merge cost is proportional to N. If the co-rank phase is more than a few percent of the total, either the tiles are too small or the search is doing redundant work. Hierarchical co-ranking often fixes this without changing the merge kernel. On the GPU, also check occupancy and register pressure. A merge kernel that uses too many registers per thread can reduce the number of resident warps and limit memory-level parallelism. A tile size that is too large increases shared memory usage and has the same effect.

Benchmark inputs should cover the distributions that matter in practice. A uniformly random merge with independent keys exercises branch misprediction in the scalar merge and produces a smooth path. Disjoint ranges produce long runs from one input and are friendly to branch prediction. Duplicate-heavy inputs stress the tie rule and the stability logic. Skewed inputs where one array is much smaller than the other exercise the co-rank search range. Payload-carrying keys test the cost of moving data rather than just comparing integers. Report results for each distribution separately; a single random benchmark hides the cases where the implementation is weak.

For sort-merge join, the performance model must include output multiplicity. The input-side merge path may be perfectly balanced while the output side is not. Profile the number of output tuples per tile and look at the tail, not just the mean. A weighted partitioner that balances estimated output work can reduce the tail, but it adds a binary search over the work function. If the join is highly skewed, a static partitioner may still leave one worker with most of the output. In that case, a two-level scheme is better: use merge path for a coarse input partition, then use a dynamic queue for subranges within each coarse partition. The merge path provides the safe boundaries; the dynamic queue provides the elasticity.

Finally, record the configuration with every measurement: tile size, thread or block count, vector width, comparator, tie rule, and input distribution. Merge path performance is sensitive to all of these, and a result without the configuration is not reproducible. A small benchmark harness that can sweep tile sizes and thread counts and emit a table of times is more valuable than a single hand-tuned number. The next implementation change can then be evaluated against the same matrix instead of against a vague memory of past performance.
