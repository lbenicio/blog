State machine replication is often described as a serialization technology. That description is accurate at the level of the replicated log and misleading at the level of execution. Consensus decides the order in which commands become durable; it does not require every replica to execute those commands one at a time. The serial execution model is a conservative implementation choice, not a theorem. Once we separate ordering from execution, a new design space opens: parallel state machine replication, where a replica executes non-conflicting commands concurrently while preserving the same externally observable behavior as a serial execution of the agreed order.

## Order Is Not Execution

A replicated state machine has two distinct pipelines. The ordering pipeline takes client requests, runs them through consensus, and produces a log. The execution pipeline applies log entries to the state machine and produces replies. In the common design, the executor is a single loop. It reads the next entry, applies it, and advances. That loop is easy to reason about, easy to checkpoint, and easy to recover. It is also a bottleneck when the machine is CPU-bound, when commands perform substantial computation, or when the log has enough concurrency across independent keys to keep several cores busy.

Parallelizing the executor does not mean weakening the log. The log remains the authority. The executor may process multiple entries concurrently only if their effects commute or if their conflicts are resolved in the log order. The goal is not to replace consensus with a faster scheduler. The goal is to extract parallelism inside the already-ordered stream. This distinction matters because it keeps safety arguments local: consensus provides a total order, and the executor provides an equivalent parallel schedule.

## The Correctness Contract

The contract for a serial state machine is familiar. All replicas start from the same state. They receive the same commands in the same order. Each command is a deterministic function from state to state and from state to reply. Given those conditions, every replica produces the same replies and reaches the same state. The contract says nothing about how long a command takes or which thread executes it.

A parallel executor needs a stronger operational contract but not a different observable one. For every log prefix, the parallel execution must be linearizable with respect to that prefix. Informally, there must be a serial order of the executed commands that respects the log order and yields the same state and replies. Commands that commute can be reordered freely. Commands that conflict must preserve their log order. The executor may run independent commands in parallel, but it must not allow a later conflicting command to observe an earlier one out of order.

This is where determinism becomes subtle. It is not necessary for every replica to use the same operating-system thread schedule, the same number of worker threads, or the same physical memory addresses. Those details are unobservable if commands are properly isolated. It is necessary for every replica to make the same logical decisions about conflicts, aborts, and state transitions. If one replica aborts a speculative command because a local thread pool is saturated and another replica commits it, the replicas diverge. The decision to abort must be a function of replicated data, not of local resource pressure.

The usual serial SMR model can hide a class of bugs. A command that is single-threaded cannot race with itself. In a parallel executor, two commands that touch the same state can race even if each command is individually single-threaded. The executor therefore needs either strict partitioning, conflict detection, or a deterministic runtime that isolates commands from each other. A data race that was latent in the application becomes a correctness failure in the replicated system.

## Where Parallelism Comes From

There are several distinct sources of parallelism, and they have different costs.

Intra-command parallelism is the easiest to reason about. A single command performs a large scan, a matrix operation, a batch lookup, or an expensive query. The executor can parallelize inside that command without changing inter-command order. The state machine must still produce deterministic results; parallel reductions over floating-point values or unordered hash tables can break that unless the implementation imposes a deterministic order or a reproducible reduction tree.

Inter-command parallelism is the more interesting case. Two commands in the same batch write disjoint keys and can execute concurrently. Two commands read the same key and write nothing can also execute concurrently. A command that reads a key while another writes it conflicts and must be ordered. The executor can build a dependency graph whose nodes are commands and whose edges represent conflicts. The graph is derived from the state and the command semantics, so it is reproducible across replicas.

Pipeline parallelism overlaps consensus and execution. Replicas can execute entry N while entry N+1 is still being ordered, as long as the execution does not depend on an entry that has not yet been ordered. This form of parallelism is often more valuable than intra-batch concurrency because it hides consensus latency, but it complicates recovery and client reply ordering.

Partition parallelism shards the state by key or namespace. Each partition has its own executor and its own ordered stream. Single-partition commands stay within one executor. Multi-partition commands require a protocol that orders them across partitions, and that protocol can easily erase the gains. Partitioning is a data-model decision as much as a scheduling decision.

Batching is the usual enabler for inter-command parallelism. A batch gives the executor a window of commands to analyze. The batch boundary is not a semantic boundary. A command does not become safer because it arrived in the same batch as another command. The executor must still enforce conflicts across batch boundaries and across entries that are applied while earlier speculative work is in flight. Batching trades latency for scheduling information. A larger batch gives the scheduler more independent work but delays the first reply.

## Deterministic Scheduling As A Replicated Artifact

A deterministic scheduler is a pure function of replicated inputs and configuration. Its inputs should be the log prefix, the current state, the batch contents, and any replicated scheduling metadata. It must not consult wall-clock time, thread identifiers, random number generators seeded from the host, pointer values, file-system layout, or the current load on the machine.

That constraint rules out many convenient techniques. Work stealing is an obvious example. A classic work-stealing scheduler makes decisions based on which deque is empty, which worker is idle, and how the operating system scheduled the workers. Those decisions are not reproducible. A deterministic executor can still use work stealing internally if the stealing decisions do not affect the logical schedule of conflicting commands, but that requires careful isolation. A simpler approach is to compute a static schedule or a dependency graph and then assign ready nodes to workers. The assignment can vary as long as the logical effects and conflict resolution are fixed.

Another approach is deterministic multithreading. The runtime reserves cores, passes tokens, and constrains interleavings so that the same program and input produce the same schedule. This is attractive because it can make existing code deterministic without rewriting it. The cost is runtime overhead and reduced utilization when the deterministic schedule leaves cores idle. It also tends to serialize synchronization operations that a speculative executor could overlap.

A third approach is schedule annotation. A leader or coordinator records the schedule it used, and followers replay that schedule. This avoids re-deriving the schedule on every replica, but it adds metadata to the log and creates a new failure mode: the schedule must be durably ordered and recovered with the commands. It also raises a trust question. If the coordinator can choose the schedule, it can choose a legal but slow schedule. That is a performance problem, not a safety problem, provided the schedule is validated and replicated.

Checkpoints must include enough scheduling state to resume safely. If the executor is in the middle of a speculative batch when a snapshot is taken, the snapshot must represent a consistent cut: either the speculative work is included with its validation state, or it is discarded and recomputed from the log. A snapshot that contains application state but not the executor's conflict metadata can recover into a different schedule. The safe default is to checkpoint only at quiescent execution boundaries, but that may be too expensive. The alternative is a richer checkpoint that captures the executor's logical frontier.

## Speculation And Deterministic Conflict Resolution

Speculative execution is the most aggressive form of parallel SMR. The executor runs commands optimistically, records the read and write sets, and validates them in log order. If a command reads a value that a later-ordered command has overwritten, or writes a value that an earlier-ordered command also writes, it is aborted and restarted. The validation order is the replicated log order, not the order in which commands finish.

The critical rule is that abort decisions must be identical on every replica. A command may abort because of a conflict, but not because a worker thread was slow, a queue was full, or a timeout expired. This means the executor cannot use completion-time heuristics to decide which command to abort. It can use them to choose which command to execute first, as long as the choice does not affect the final schedule. If the choice can affect aborts, the choice must be deterministic or replicated.

Speculation is most useful when conflicts are rare and commands are expensive. It hides the latency of conflict detection behind useful work. It is least useful when the workload has many hot keys, because aborts consume the same CPU time as commits and can amplify contention. The executor needs a way to detect that speculation is not paying off and fall back to a conservative schedule. That fallback must also be deterministic. A local decision to stop speculating on one replica but not another is a divergence bug.

Conflict detection granularity is a design parameter. Key-level or row-level tracking finds more parallelism than page-level tracking, but it costs more metadata and more validation work. Coarse tracking is simpler and can still be correct, but it may serialize commands that do not actually conflict. The right granularity depends on the state layout and the command mix. It is a performance trade-off, not a safety one, as long as the conflict relation is conservative: the executor may report a conflict that does not exist, but it must not miss one.

## The Cost Structure

Parallel state machine replication does not make consensus free. The log still has to be ordered, replicated, and durable. If consensus latency dominates the workload, a faster executor may not improve end-to-end throughput. If execution dominates, the executor is the right place to invest. Many real systems sit somewhere in between, and the balance changes with batch size, network conditions, and command cost.

The overheads are concrete. Dependency tracking adds metadata and validation work. Speculation adds rollback and recomputation. Deterministic scheduling can reduce utilization by leaving cores idle. Batching adds latency. Partitioning adds cross-partition coordination. Recovery becomes more complex because the executor's frontier and scheduling state must be reconstructed or checkpointed. These costs are not incidental; they are the price of preserving the serial semantics while using more cores.

The benefits are also concrete. A CPU-bound state machine can use multiple cores without weakening its replication guarantees. A batch of independent commands can finish faster than a serial loop. A pipelined executor can overlap consensus with computation. The design question is whether the workload has enough conflict-free parallelism to pay for the machinery. That question cannot be answered by a slogan about parallelism; it requires measuring the conflict rate, the command cost distribution, and the cost of the scheduling metadata for the actual state machine.

## Scope And Assumptions

This article focuses on crash-fault-tolerant replication with deterministic state machines. It assumes that commands can be made deterministic, that external side effects are either absent or mediated by a replicated mechanism, and that the consensus layer provides a durable total order. It does not assume Byzantine faults, and it does not propose a new consensus protocol. The subject is the execution layer: how to run the ordered stream in parallel without changing what clients observe.

The next sections turn to the design of the executor itself: how to represent conflicts, how to schedule batches deterministically, how to validate speculative work, how to checkpoint a parallel frontier, and how to recover without replaying the entire log. The central constraint will remain the same. Parallelism is allowed only when every replica can make the same logical decisions from the same replicated inputs.

## Conflict Representation as a First-Class Replicated Structure

A parallel executor is only as good as its conflict relation. The relation must be conservative, deterministic, and cheap enough to evaluate on every replica. It is tempting to treat conflict detection as an implementation detail hidden inside the executor, but that view is too narrow. The conflict relation is part of the replicated semantics because it determines which schedules are legal. If two replicas disagree about whether commands A and B conflict, they may choose different legal schedules and produce different states. The relation therefore needs the same care as the state machine transition function.

The most direct representation is a read-write set per command. Before a command executes, it declares the keys, ranges, or predicates it will read and write. After it executes, the executor compares those sets with the sets of other commands in the current window. A write-write overlap is a conflict. A read-write overlap is a conflict. A read-read overlap is not. This is the standard optimistic concurrency control model, but in SMR the validation order is fixed by the log, not by transaction start time.

Declared access sets are attractive because they allow scheduling before execution. They are also dangerous because a declaration can be incomplete. A command that reads a key through a secondary index, a range scan, or a dynamic dispatch may touch data that its declaration does not mention. If the executor trusts the declaration, it can miss a conflict. If it does not trust the declaration, it must track accesses at runtime and fall back to validation. The practical compromise is to use declarations for scheduling and runtime tracking for validation. The declaration proposes a schedule; the runtime read and write sets decide whether that schedule survives.

Predicate reads require special handling. A command that scans all accounts with balance above a threshold reads a predicate, not a fixed set of keys. If another command inserts an account that satisfies the predicate, the scan result changes. This is the phantom problem. The executor can handle it by tracking predicate locks, by versioning ranges, or by assigning a version to the predicate evaluation itself. A predicate version increments whenever any write could affect the predicate. The command validates its predicate version at commit time. This is conservative and can cause aborts on unrelated writes, but it is deterministic and safe.

Versioned state makes validation cheaper. Each key or range carries a version number. A command records the versions it read. At commit time, the validator checks that those versions have not changed. If they have, the command aborts. Write sets are validated against the current version and then advance the version. The version numbers are replicated state. They must be updated in log order, not in completion order. A command that finishes early does not get to commit early if a conflicting command precedes it in the log.

The conflict graph is the central data structure. Nodes are commands. Edges point from earlier log positions to later log positions when the earlier command conflicts with the later one. The graph is acyclic because edges follow log order. A topological order that respects all edges is a legal serialization. The executor can execute any antichain of nodes in parallel. The graph must be deterministic. If two replicas build different graphs from the same log and state, they may choose different parallel schedules. The graph construction must therefore use deterministic iteration over keys and deterministic tie-breaking for equal log indices or equal keys.

Hash maps are a common source of nondeterminism. If the executor iterates over a hash map to build the conflict graph, the iteration order depends on the hash function and the insertion history. If the hash function uses pointer addresses or randomized seeds, the order differs across replicas. Even if the hash function is deterministic, the insertion history can differ if commands are processed in different physical orders. The safe approach is to sort keys before graph construction, or to use an ordered map with a deterministic comparator. The cost is extra CPU time, but it is bounded and predictable.

The granularity of conflict tracking is a tuning parameter. Key-level tracking maximizes parallelism but requires per-key metadata. Page-level or block-level tracking reduces metadata but may serialize commands that touch different keys on the same page. Range-level tracking is useful for scans but can be overly conservative. The executor can use multiple granularities: fine-grained for hot keys, coarse-grained for cold regions. The choice must be deterministic. It can depend on replicated state, such as a hot-key list that is updated by a replicated command, but it cannot depend on local cache misses or timing.

## Deterministic Batch Scheduling

Batching is the executor's scheduling window. The log provides an ordered stream, but the executor does not have to apply one entry at a time. It can collect a batch of entries, analyze their conflicts, and schedule the batch as a directed acyclic graph. The batch boundary must be deterministic. It cannot be 'whatever arrived in the last millisecond.' It can be a fixed number of entries, a fixed number of bytes, or a boundary marked in the log. A fixed-size batch is simple and reproducible. A byte-size batch is also reproducible if the size calculation is deterministic. A time-based batch is not reproducible unless the time is replicated, which is usually impractical.

Once the batch is fixed, the executor builds the conflict graph. The graph may include dependencies on commands outside the batch. A command in the batch may read a key that was written by a command in a previous batch that is still speculative. The executor must either wait for that previous command to commit or include it in the dependency graph. The cleanest approach is to maintain a sliding window of speculative commands. The window has a deterministic lower bound, called the commit horizon. Commands before the horizon are committed and their effects are visible. Commands after the horizon are speculative. The batch scheduler only schedules commands within the window.

The schedule itself can be represented as a sequence of waves. Wave zero contains commands with no dependencies inside the window. Wave one contains commands whose dependencies are all in wave zero or earlier committed state. The executor can run all commands in a wave concurrently. The wave assignment is deterministic because it depends only on the conflict graph. The number of workers does not change the wave assignment. If there are more commands in a wave than workers, the executor processes them in a deterministic order, such as ascending log index. If there are fewer commands than workers, some workers idle. That is a utilization cost, not a correctness problem.

A more flexible schedule uses a ready queue. Initially, all commands with no unresolved dependencies are ready. The executor pops ready commands in a deterministic order, assigns them to workers, and runs them. When a command completes, the executor removes its outgoing edges and adds newly ready commands to the queue. The queue order must be deterministic. A priority queue ordered by log index is a simple choice. The worker assignment can vary because it does not affect the logical order of commits. The only requirement is that a command does not observe the effects of a later conflicting command.

Speculative execution can start before the entire batch is known. The executor can begin executing a command as soon as it appears in the log, record its read and write sets, and validate later. This is useful for hiding consensus latency. It also creates a longer window of speculative state. The executor must track which commands are speculative and which are committed. A command's speculative effects must not be visible to commands that are ordered after a conflicting command that has not yet committed. The executor can maintain a private speculative view for each command or a multi-version state that keeps old versions until the commit horizon passes.

Deterministic fallback is essential. If the conflict rate is high, speculation wastes CPU on aborts. The executor can switch to a conservative mode that executes commands serially or in coarse-grained partitions. The switch must be deterministic. It can be triggered by a replicated counter of aborts per batch, or by a replicated flag set by a coordinator. It cannot be triggered by local queue depth. The fallback mode is part of the replicated configuration. Changing it requires a replicated command or a deterministic rule based on the log.

## Validation and Commit Protocols

Validation is the gate between speculative execution and visible state. A command that has finished execution is not committed until its read set is validated against the current committed state and its write set is checked for conflicts with earlier commands. The validation order is the log order. If command A precedes command B in the log and they conflict, A must validate first. If B validates first and commits, A may see a state that includes B's writes, which violates the log order. The executor therefore maintains a validation queue ordered by log index. Commands can execute out of order, but they commit in order.

Read-set validation checks that every version read by the command is still current at commit time. If a version has advanced, the command read stale data and must abort. Write-set validation checks that no earlier uncommitted command writes the same keys. If there is a write-write conflict, the later command aborts. The abort is deterministic because it depends only on the log order and the read and write sets. The executor may also abort a command if its read set overlaps a write set of an earlier command that has not yet committed, even if the earlier command eventually aborts. This is called a cascading abort. It is safe but can amplify aborts. The executor can avoid cascading aborts by waiting for the earlier command to resolve before validating the later one.

Commit protocols must handle replies. A client that receives a reply expects the command to be durable and applied. If replies are sent as soon as a command executes speculatively, a later abort would require retracting the reply, which is usually impossible. The executor must therefore delay replies until commit. The reply order can be different from the log order if the client can tolerate it, but many clients expect at least per-session ordering. The executor can maintain a per-session reply queue and release replies in log order for that session. This adds a small amount of state but preserves the familiar client semantics.

Exactly-once execution is another concern. A client may retry a command if it does not receive a reply. The state machine must deduplicate requests. In a parallel executor, deduplication must be deterministic. The deduplication table is part of the state. A command that is aborted and restarted must not apply its effects twice. The executor can assign each command a unique log index and use that index as the deduplication key. The table is updated at commit time, not at speculative execution time. If a speculative command reads the deduplication table, it must validate that entry like any other read.

## Checkpointing a Parallel Frontier

Checkpointing a serial executor is straightforward: stop the loop, snapshot the state, record the last applied log index. Checkpointing a parallel executor is harder because the executor may have speculative commands in flight, partially validated commands, and a conflict graph that spans multiple log entries. The snapshot must represent a consistent cut. It cannot include the effects of a command that has not committed, and it cannot omit the effects of a command that has committed. The cut must be at a point where the commit horizon is well defined.

One approach is to checkpoint only at quiescent points. The executor drains all speculative work, commits or aborts everything up to a chosen log index, and then snapshots. This is simple and produces a clean checkpoint. It is also expensive because it serializes execution and may stall the pipeline. The stall can be reduced by taking the checkpoint in the background while new commands continue to execute, but then the snapshot must capture a consistent cut of the state and the executor metadata.

A more efficient approach is to use copy-on-write or persistent data structures. The state is represented as a persistent tree or a versioned key-value store. A checkpoint records the root of the tree at a particular log index. Commands that execute after the checkpoint create new versions without modifying the old root. The checkpoint is consistent because it refers to an immutable version. The executor still needs to record the commit horizon and the validation state. If a command was speculative at the checkpoint index, it is not included in the checkpoint. It will be re-executed during recovery from the log. The checkpoint must therefore record the last committed log index, not the last executed log index.

The checkpoint must also include the executor's deterministic configuration. This includes the batch size, the conflict tracking granularity, the scheduling policy, and any replicated hot-key lists. If these are derived from the log, they can be reconstructed by replay. If they are configuration parameters, they must be stored with the checkpoint. A checkpoint that is restored with a different scheduling policy may still be safe, but it may produce a different schedule. That is acceptable only if the schedule does not affect the observable state. The safest approach is to treat the scheduling policy as part of the replicated state and change it only through the log.

Log truncation interacts with checkpointing. The executor can truncate log entries that are before the checkpoint and are no longer needed for recovery. If the checkpoint includes the commit horizon, the log can be truncated up to that horizon. Entries after the horizon are still needed because they may be speculative or uncommitted. The truncation point must be deterministic. A replica that truncates more aggressively than another may be unable to recover a command that the other replica still needs. The consensus layer usually coordinates truncation, but the executor must provide a safe lower bound.

## Recovery Without Full Replay

Recovery starts from the latest checkpoint and replays the log from the checkpoint's last committed index. The executor must reconstruct the parallel scheduling state. It does not need to reconstruct the exact thread schedule, but it does need to reconstruct the conflict graph and the commit order. The simplest recovery mode is serial replay: apply commands one at a time until the executor reaches the point where it can resume parallel execution. This is correct but slow. A faster approach is to rebuild the conflict graph from the log and the checkpointed state, then resume the parallel schedule at the same logical frontier.

The recovery process must be deterministic. If the checkpoint was taken at log index 1000, and the log contains entries 1001 through 2000, the recovering replica must apply those entries in a way that produces the same state as a replica that never crashed. The recovering replica may have a different number of workers, so its physical execution order may differ. Its logical commit order must be the same. The conflict graph is the bridge between physical and logical order. As long as the graph is built from the same log and state, the commit order is the same.

Partial batches are a recovery hazard. If the checkpoint was taken in the middle of a batch, the recovering replica must know which commands in the batch were committed. The checkpoint's commit horizon provides that information. Commands before the horizon are committed and included in the checkpoint. Commands after the horizon are not committed and must be replayed. The recovering replica can discard any speculative state from the checkpoint and start fresh from the horizon. This is why the checkpoint should record the commit horizon rather than the execution frontier.

State transfer is another recovery path. A new replica can receive a checkpoint from a peer instead of replaying the entire log. The checkpoint must be verifiable. The receiving replica can verify the checkpoint by replaying a suffix of the log and comparing the resulting state hash. If the checkpoint includes the commit horizon, the suffix replay is deterministic. The receiving replica can also verify that the checkpoint's conflict metadata is consistent with the state. A mismatch indicates a corrupted or malicious checkpoint. In a crash-fault-tolerant system, the primary concern is corruption, not Byzantine behavior, but verification is still useful.

## Workloads and Measurement

The decision to use parallel state machine replication should be based on measurements, not on the availability of cores. The first measurement is the conflict rate. If most commands in a batch touch disjoint keys, inter-command parallelism is promising. If most commands touch a small set of hot keys, the conflict graph will be narrow and the executor will serialize on those keys. The conflict rate can be measured by running the serial executor with instrumentation that records read and write sets. This instrumentation does not change the state machine's behavior if it is read-only.

The second measurement is the command cost distribution. Parallelism helps when commands are expensive. If commands are short, the overhead of conflict tracking, scheduling, and validation may exceed the execution time. The executor should measure the time spent in command execution versus the time spent in scheduling and validation. If scheduling dominates, the batch size or tracking granularity is wrong. If validation dominates, the conflict rate is too high or the read sets are too large.

The third measurement is the abort rate. A high abort rate means speculative work is being wasted. The executor can reduce aborts by increasing the commit horizon, waiting for conflicting commands to resolve, or switching to a conservative schedule. The optimal abort rate depends on the cost of aborts relative to the cost of waiting. A cheap command should not be speculated if it is likely to abort. An expensive command may be worth speculating even with a moderate abort rate.

End-to-end throughput is the final metric. Parallel execution may improve throughput but increase latency. A larger batch improves scheduling but delays the first reply. A longer speculation window hides consensus latency but increases the chance of aborts. The executor should expose these trade-offs as configuration parameters and measure them under realistic workloads. A microbenchmark with uniform random keys will overstate the benefits. A realistic workload with hot keys, range scans, and multi-key transactions will show the true cost of replicated concurrency.

## Implementation Patterns

A deterministic parallel executor can be built from a small set of patterns. The first is a deterministic work queue. Commands are assigned to workers in a deterministic order. The queue is ordered by log index or by a deterministic priority. Workers do not steal work in a way that changes the logical order. If work stealing is used, it must be confined to commands that are known to be independent and whose completion order cannot affect validation.

The second pattern is immutable command descriptors. Each command has a descriptor that contains its log index, its declared read and write sets, and its session identifier. The descriptor is immutable. Workers read it and produce a result. The result contains the actual read and write sets and the output. The executor validates the result against the descriptor and the current state. Immutability simplifies sharing and avoids data races.

The third pattern is versioned state. The state is a collection of versioned keys or ranges. Reads return a value and a version. Writes create a new version. The version numbers are updated in commit order. The executor can use a multi-version store to keep old versions for validation. Old versions can be garbage-collected after the commit horizon passes.

The fourth pattern is deterministic memory management. If the executor uses hash maps keyed by pointers, the iteration order may vary. If it uses memory addresses for tie-breaking, the schedule may vary. The executor should use logical identifiers, such as log indices and key hashes, for all deterministic decisions. Memory allocation can still be non-deterministic as long as it does not affect the logical schedule. False sharing and NUMA effects can affect performance but not correctness.

The fifth pattern is deterministic floating-point and collection handling. If commands perform floating-point reductions, the executor must impose a deterministic order or use a reproducible reduction tree. If commands iterate over unordered collections, the executor must sort the results or use an ordered collection. These are application-level requirements, but the executor can provide helpers that make them easier to satisfy.

Finally, the executor should be testable with a deterministic simulator. The simulator can run the same log through many different worker counts and scheduling policies and check that the final state and replies are identical. This is the most direct way to catch nondeterminism. It also provides a way to measure the cost of different conflict tracking granularities and scheduling policies without deploying to a cluster.

## Contention, Skew, and Deterministic Backpressure

A conflict graph is a snapshot of a batch, but real workloads have skew that persists across batches. A few keys may receive a large fraction of writes, while the rest of the key space is cold. The executor cannot respond to that skew by consulting local queue depths or cache miss rates, because those signals are not replicated. It can respond by using replicated signals: per-key contention counters, hot-key sets, and abort statistics that are updated by commands themselves. Those signals advance with the log, so every replica sees the same skew at the same logical time.

The simplest replicated signal is a per-key write count over a sliding window. The window can be defined in log indices rather than seconds. A command that updates a key increments the counter for that key when it commits. The executor can read the counters when it schedules the next batch. If a key is hot, the scheduler can group all commands that touch that key into a single wave and order them by log index. This does not reduce the serialization on the hot key, but it prevents the executor from wasting workers on speculative commands that are likely to abort.

A more aggressive technique is deterministic priority inversion. Commands that touch hot keys are scheduled earlier in the ready queue, even if they have higher log indices than cold commands. This is safe as long as the hot-key priority does not allow a later command to commit before an earlier conflicting command. The priority only affects execution order; commit order remains the log order. The executor may execute a later hot-key command first, but it cannot validate it before the earlier conflicting command. If the earlier command has not committed, the later command waits at validation. The waiting is deterministic because it depends on the conflict graph, not on thread scheduling.

Backpressure is harder. If clients submit more commands than the executor can process, the system needs to slow them down. A local decision to reject or delay a request on one replica but not another would break the replicated input stream. The safe place for backpressure is the ordering pipeline or the client itself. The consensus leader can refuse to propose new entries when the log is too far ahead of the commit horizon, and clients can be told to retry. The decision to apply backpressure can be based on a replicated metric, such as the gap between the last ordered index and the last committed index. If the gap exceeds a deterministic threshold, the leader stops accepting new proposals until the gap shrinks. Followers observe the same gap because they see the same log and the same commit messages.

The executor can also apply internal backpressure by limiting the number of speculative commands per session or per key range. Those limits must be part of the replicated configuration. A session-level limit prevents one client from filling the speculation window. A key-level limit prevents a hot key from generating unbounded aborts. Both limits are enforced by the deterministic scheduler, not by worker thread availability. If the limit is reached, the executor stops scheduling new commands for that session or key until the commit horizon advances. This is a logical wait, and it produces the same schedule on every replica.

Skew also affects partitioning. If the state is partitioned by key, a single hot key can overload one partition while other partitions idle. The deterministic response is to replicate the hot key or to split its range. Both are data-model changes that must be applied through the log. Replicating a hot key allows multiple partitions to serve reads, but writes still need a single order. Splitting the range can distribute writes if the key can be decomposed. The executor cannot dynamically migrate keys based on local load without risking divergence. It can only follow a deterministic migration plan that is itself a sequence of replicated commands.

## Cross-Partition Execution and Distributed Commit

Partitioning the state is one of the most effective ways to use more cores, but it changes the shape of the executor. Each partition has its own state, its own conflict graph, and its own pool of workers. A command that touches one partition is local and can be scheduled without coordination. A command that touches multiple partitions requires a protocol that gives all participating partitions the same commit decision at the same log index. The log is the natural coordinator, but the partitions still need to agree on when a cross-partition command is prepared, committed, or aborted.

The first design decision is how to represent a cross-partition command. The command descriptor should list the partitions it touches and the keys or ranges within each partition. The descriptor is part of the log entry, so it is identical on every replica. The global executor can then dispatch subcommands to partition executors. Each partition executes its subcommand speculatively and records its local read and write sets. The partition does not commit locally until the global validator says the command is committed.

The second decision is the commit protocol. A two-phase protocol is natural. In the prepare phase, each participating partition locks or versions the keys it will write, checks its local read set, and votes. In the commit phase, the global validator collects the votes and decides. The decision must be deterministic. If any partition votes abort, the global command aborts. If all vote commit, the global command commits and each partition applies its writes. The votes are derived from the conflict graph and the current state, not from timing. If a partition is slow, the global validator waits; it does not abort because of a timeout. A timeout-based abort would be nondeterministic unless the timeout is measured in logical time, such as a fixed number of log entries.

The third decision is lock ordering. Cross-partition commands can deadlock if they acquire locks in different orders. The executor avoids deadlock by ordering all lock acquisitions by partition identifier and then by key. Because the order is deterministic, all replicas acquire locks in the same order. A command that needs multiple partitions will always acquire them in ascending partition order. Within a partition, keys are acquired in sorted order. This makes deadlock impossible without relying on timeouts. The cost is that a command may wait for a partition that is busy, even if another partition is free. That is a performance cost, not a safety problem.

Speculative cross-partition execution is possible but expensive. A partition can execute its subcommand before the global decision, but it must keep the effects in a private overlay. The overlay is merged into the committed state only after the global commit. If the global command aborts, the overlay is discarded. The private overlay must not be visible to other commands in the same partition unless those commands are ordered after the global commit. The executor can enforce this by giving each speculative cross-partition command a version number and by making local commands read the committed version unless they are part of the same global command.

Checkpointing across partitions requires a consistent cut. A global checkpoint cannot simply snapshot each partition at its own convenience, because a cross-partition command may be committed in one partition and speculative in another. The executor needs a barrier log entry that marks a global checkpoint. When a partition reaches the barrier, it stops starting new speculative work and drains its in-flight cross-partition commands. Once all partitions reach the barrier, each can snapshot its state and its commit horizon. The barrier is part of the log, so it is ordered with all other commands. The snapshot records the barrier index and the per-partition commit horizons. Recovery replays from the barrier and rebuilds the global state.

The performance of cross-partition execution depends on the fraction of commands that touch multiple partitions. If that fraction is low, partitioning scales well. If it is high, the global coordinator becomes a bottleneck and the system resembles a single executor with extra network hops. The executor can reduce coordination by grouping cross-partition commands into batches and by co-locating frequently co-accessed keys in the same partition. Both are data-model decisions that should be driven by workload measurements, not by an assumption that more partitions always help.

## Failure, Reconfiguration, and Executor Lifecycle

A crash can happen at any point in the speculative pipeline. The replica may have executed commands, validated some, and committed none. On restart, the executor must reconstruct a state that is consistent with the log and the latest checkpoint. The checkpoint gives a committed state at a known log index. The log gives the commands after that index. The recovering executor can choose any legal parallel schedule for those commands, as long as the commit order matches the log. It does not need to reconstruct the exact speculative state that existed before the crash. Discarding speculative work is always safe because speculative effects were never visible to clients.

Reconfiguration changes the execution environment. The number of worker threads may change, partitions may be added or removed, and the scheduling policy may be updated. These changes must not affect the logical commit order. Worker count is a local resource, so it can differ across replicas without breaking safety. Partition assignment is replicated state, so it must change through a replicated command. When a partition is split or merged, the executor must quiesce the affected partitions, apply the migration as a sequence of deterministic operations, and then resume. The migration command should be ordered in the log like any other command. During the migration, cross-partition commands that touch the moving range are blocked or redirected by a deterministic rule.

Membership changes interact with the executor through state transfer. A new replica receives a checkpoint from an existing replica and then catches up on the log. The checkpoint includes the committed state and the commit horizon. The new replica can start executing from the horizon. It does not need the old speculative state. If the new replica has a different number of workers or a different cache size, its physical execution will differ, but its logical commits will match. The only requirement is that the new replica uses the same deterministic scheduling policy for any decisions that affect commits. If the policy is part of the replicated configuration, this is automatic. If it is local, it must be restricted to choices that cannot change the commit decision.

Coordinator changes are another lifecycle event. If a coordinator records schedule annotations in the log, a new coordinator may produce different annotations. That is acceptable if followers validate annotations rather than trust them. Validation means checking that the annotated schedule respects the conflict graph and the log order. A malicious or buggy coordinator could produce a legal but slow schedule, but it cannot produce an illegal one without detection. If the system cannot afford validation, then schedule annotations become a replicated consensus decision and should be treated with the same care as any other log entry.

Rolling upgrades are the most delicate lifecycle event. A new software version may change the conflict tracking granularity, the batching rule, or the speculative window. If those changes affect how commands are validated, they are semantic changes. A replica running the new version may make different logical decisions from a replica running the old version. The safe approach is to treat the upgrade as a state machine version change. The log records the version at which each command should be interpreted. A checkpoint taken at the upgrade boundary captures the old state. Commands after the boundary are interpreted by the new version. During the transition, the system may need to run both versions or to drain the log before switching. This is operationally expensive, but it is the only way to preserve the determinism contract across code changes.

## Verifying and Debugging Parallel Execution

The most valuable test for a parallel executor is differential execution. The same log is run through many different configurations: one worker, many workers, different batch sizes, different conflict granularities, different scheduling policies. All runs must produce identical state hashes and identical replies for every prefix. If a configuration produces a different state, the executor has a determinism bug. Differential execution catches bugs that are invisible to single-threaded tests because it explores different physical schedules while requiring the same logical outcome.

A deterministic simulator is the right platform for this test. The simulator replaces the network and disk with in-memory queues and runs the ordering pipeline and execution pipeline in one process. It can inject failures, reorder messages, and vary worker counts. It can also record the conflict graph and the validation decisions for each command. When a divergence occurs, the simulator can replay the exact log and configuration that produced it. Because the simulator is deterministic, the replay is exact. This is much easier than reproducing a race in a distributed cluster.

Runtime divergence detection is the production counterpart. Each replica can compute a hash of its committed state after every batch and include that hash in a periodic heartbeat. If two replicas report different hashes for the same log index, the system has diverged. The replicas can stop accepting new commands and preserve their state for analysis. The hash must be computed deterministically. If the state is a hash map, the hash must iterate keys in a deterministic order. If the state contains floating-point values, the hash must use a canonical representation. These requirements are the same as those for the state machine itself.

Debugging a divergence requires comparing logical traces, not thread traces. A logical trace records the log index of each command, the keys it read and wrote, the versions it read, and whether it committed or aborted. Two replicas that commit the same commands in the same order should produce the same trace, even if their worker threads scheduled the commands differently. If the traces differ, the divergence is in the conflict relation or the validation logic, not in the thread scheduler. This narrows the search space considerably.

Instrumentation has a cost. Recording every read and write set can double the memory footprint of a command and slow execution. The executor can sample traces, or it can enable full tracing only in test environments. For production, it can keep lightweight counters: number of aborts, number of validation failures, number of speculative commands in flight, and the size of the conflict graph. These counters are not used for scheduling, but they are useful for detecting anomalies. If the abort rate suddenly changes without a workload change, a replica may have a different view of the state.

The boundary between local observations and replicated decisions is where most practical determinism bugs live. A code review checklist can help: every branch that can affect a commit, an abort, or a reply must depend only on the log, the state, and replicated configuration. Local thread counts, queue depths, cache statistics, and wall-clock timers belong on the performance side of that boundary. They may guide how fast a replica runs, but they must never decide what a replica does.

## Deterministic Time, Randomness, and Environmental Inputs

A parallel executor can fix every scheduling decision and still diverge if a command reads a clock, a random device, or an environmental value that differs across replicas. The usual deterministic state machine rule says that those inputs must be absent or replicated. Parallelism makes the rule easier to violate because commands run concurrently and developers often reach for local time to implement timeouts, leases, jitter, or cache expiry. The executor needs an explicit boundary between the replicated transition and the local runtime.

Logical time is the safe substitute. Each command carries its log index, and the executor can derive a monotonically increasing logical timestamp from the log itself. If the application needs calendar time, the timestamp must be part of the command payload or replicated state, not sampled by the executor. A leader can attach a proposed wall-clock reading to a command when it proposes the entry, but that reading becomes an input only after it is ordered. Followers use the ordered value, not their own clocks. The leader's clock can be wrong without breaking safety; it can only make the logical time less accurate. If the application needs bounded clock error, that is a separate protocol requirement, not an executor scheduling decision.

Timers follow the same pattern. A local timer that fires after a fixed interval is nondeterministic because the firing point depends on scheduling and clock granularity. A replicated timer must be a command or a deterministic function of log progress. One design registers a timer with a deadline expressed in logical time, such as a future log index or a replicated timestamp. When the log reaches that point, a timer command appears in the stream. The executor does not wake up on its own and inject an event. If the timer needs wall-clock semantics, the leader emits the timer command when its clock passes the deadline. The command is then ordered and applied like any other. Replicas that are slow or fast still apply the same timer event at the same log position.

Randomness is similar. A command that needs a random value must derive it deterministically from replicated data. A common approach is a keyed pseudorandom function whose key is part of the replicated configuration and whose input includes the command's log index and session identifier. The executor computes the value during execution. It does not call the host random device. If the application needs unpredictable randomness for security, the key must be generated by a replicated protocol and kept stable across replicas. A per-replica seed is a divergence bug even if the resulting values are used only for load balancing inside the command.

Environmental inputs include configuration files, environment variables, DNS results, file metadata, and feature flags read from a local service. Any value that can change the state must be captured in the log or in replicated configuration. Reading it locally at execution time creates a hidden input that consensus never ordered. The practical rule is to resolve environmental inputs at proposal time, place the resolved value in the command, and let the executor treat it as immutable data. If the value is large, the command can carry a content hash and a reference to a replicated blob, but the executor must still verify the hash and fetch the blob deterministically.

External side effects need an outbox. The state transition writes a durable record describing the effect, and a separate worker performs the effect after commit. The record includes the log index as an idempotency key. The worker may retry, fail, or run late; those events do not change the state machine unless they are fed back as new commands. This separation is important in a parallel executor because a speculative command may abort. If the command sent an email or charged a card before validation, the abort cannot undo the effect. The outbox ensures that side effects happen only after the command's commit is final, and the idempotency key lets the worker retry safely.

## Memory Reclamation and Local Failure

Multi-version state and speculative execution retain old versions until validation finishes. The reclamation point must be deterministic. A version can be discarded once every command that could read it has either committed or aborted, which is exactly the commit horizon. The executor should compute that horizon from the log and the validation queue, not from a local garbage collector's idea of memory pressure. If the horizon has not advanced because an early command is slow, old versions remain. That is a capacity cost, and it is visible to every replica in the same logical position.

A memory-pressure policy that discards versions early can change validation outcomes. If a replica runs out of memory and drops a version that another replica still holds, it may abort a command that would otherwise commit. The safe response to local memory exhaustion is to crash and recover from the checkpoint, not to make a local scheduling decision. Recovery is expensive, but it preserves the invariant that commit decisions depend only on replicated inputs. The same rule applies to disk exhaustion, file descriptor limits, and thread creation failures. They are local faults. They may stop a replica, but they must not alter the logical schedule.

Managed runtimes add another source of hidden nondeterminism. Finalizers, weak references, and object-identity hash codes can make state depend on collection order. A state machine should avoid them in any path that affects committed state. If they are unavoidable, the executor must provide deterministic object identifiers and deterministic destruction ordering. Garbage collection pauses can vary across replicas, but pauses alone do not break correctness if they do not change the schedule. The executor may run slower on one replica, but it must make the same commit decisions.

The execution envelope should therefore be explicit. Replicated inputs define what a command may observe. The commit horizon defines which versions remain reachable. Local resources define only how fast a replica can process the work and whether it must restart. Keeping those categories separate is what makes a parallel executor auditable: a reviewer can point to every branch that affects state and verify that it depends on the log, the replicated configuration, or deterministic derived data, while treating timers, thread pools, memory pressure, and external effects as runtime concerns that cannot move the logical frontier.
