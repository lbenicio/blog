Sparse matrix-vector multiplication looks deceptively simple: compute `y = A x`, where `A` is sparse and `x` and `y` are dense. The operation has low arithmetic intensity, irregular memory access, and a work distribution that depends on the matrix. Those properties make SpMV a useful case study in parallel systems design because the hard part is not the arithmetic; it is the coordination between the memory hierarchy, the partitioner, and the numerical semantics.

This article assumes a single shared-memory node, a static CSR matrix, dense `x` and `y`, and a conventional multicore CPU. It does not assume a GPU or a distributed cluster. The goal is to expose the design choices that determine whether a parallel SpMV is balanced, vectorized, and reproducible. The right choices depend on the matrix, the hardware, and the numerical requirements.

## The baseline: CSR and the owner-computes loop

Compressed sparse row (CSR) stores a sparse matrix as three arrays: `row_ptr`, `col_idx`, and `values`. For row `i`, the nonzeros are in `values[row_ptr[i] : row_ptr[i+1]]`, and their column indices are in the corresponding slice of `col_idx`. The serial kernel is a row-wise dot product:

```c
for (int i = 0; i < m; ++i) {
    double sum = 0.0;
    for (int k = row_ptr[i]; k < row_ptr[i+1]; ++k) {
        sum += values[k] * x[col_idx[k]];
    }
    y[i] = sum;
}
```

The parallel baseline partitions rows among threads. Each thread owns a contiguous range of rows and writes the corresponding range of `y`. This is owner-computes: row `i` owns `y[i]`. No locks are needed because `x`, `row_ptr`, `col_idx`, and `values` are read-only, and each thread writes disjoint `y` entries. The baseline is simple, preserves the serial summation order within each row, and has good locality for `y` and for the row slices of `A`.

The baseline has two structural problems. First, the row nonzero distribution is often heavy-tailed. A static block partition assigns equal row counts, not equal nonzeros. A thread that receives a few dense rows can dominate the runtime. Second, the inner dot product is a serial dependency chain. Short rows cannot fill SIMD pipelines, and long rows may not be split. The owner-computes loop also ties parallelism to the number of rows. If `m` is small relative to the number of cores, there is not enough parallelism even if `nnz` is large.

The first design decision is whether to preserve owner-computes. If rows are balanced and `m` is large, it is the right default. If not, row splitting or merge-based partitioning is needed.

## Row splitting: more parallelism, more reduction

Row splitting divides each row into segments of at most `L` nonzeros. Each segment computes a partial sum, and the final `y[i]` is the sum of the partials. This increases parallelism and can turn long rows into vectorizable segments. It also breaks the owner-computes property: multiple threads may write the same `y[i]`.

The reduction options are explicit. The first is atomic addition into `y[i]`. Atomic floating-point addition is not universally available as a primitive, and even where it is, it is not associative. The result can vary from run to run. The second is per-thread partial arrays. Each thread accumulates partial sums into a local buffer keyed by row, and a separate pass combines the buffers. This preserves determinism if the combine order is fixed, but it costs memory and an extra pass. The third is a two-phase scheme: each thread writes partials to a temporary array indexed by row and segment, then a reduction kernel combines them. The temporary array size is proportional to the number of segments, which can be large.

Row splitting has a clear trade-off. For long rows, it increases parallelism and enables vectorization. For short rows, the reduction overhead dominates. The threshold `L` should be chosen from the row-length distribution and the core count. A common heuristic is to split only rows with more than a few times the average row length, but the exact threshold is workload-dependent. The split also changes the floating-point summation order, so reproducibility must be considered.

There is a second-order effect: false sharing. If partial sums for adjacent rows land in the same cache line, threads writing different rows can contend for the same line. Padding the partial buffers to cache-line size reduces this contention at the cost of memory. The same issue applies to `y` when row splitting causes multiple threads to write adjacent rows. Aligning row blocks to cache lines can help, but it changes the indexing and memory footprint.

## Merge-based partitioning: balance nonzeros, not rows

Merge-based partitioning ignores row boundaries when dividing work. It partitions the nonzero index space `[0, nnz)` into contiguous ranges of roughly equal length. Each thread receives a range and processes the row segments that intersect it. A row may be touched by multiple threads, so the same reduction problem appears.

The advantage is balance by construction. The partitioner equalizes nonzeros, not rows, so a few dense rows no longer dominate. The thread's range is contiguous in `values` and `col_idx`, which is good for prefetching. The partitioner only needs to find the row boundaries at the start and end of each range. Because `row_ptr` is sorted, a binary search finds the first row whose nonzero range extends past the range start. The thread then iterates forward, processing each row segment until the range end.

The cost is cleanup and reduction. Ranges can start and end in the middle of a row, so the kernel needs masked or partial segments. The row-boundary search and per-row overhead are small when ranges are large, but they matter for matrices with many short rows. The reduction is the same as row splitting: atomics, per-thread partials, or a two-phase combine. Merge-based partitioning also complicates vectorization because the first and last segments of a range may be unaligned. The interior segments are regular and can be vectorized; the edges need scalar cleanup.

Merge-based partitioning balances work but not necessarily memory traffic. If a row is split across threads, the same `y` cache line may be written by multiple threads. The partitioner should align range boundaries to row boundaries when possible, or use per-thread partials to avoid direct writes. The trade-off is between exact balance and reduction overhead.

## Vectorization: the indirection is the enemy

The inner loop is a dot product with indirect indexing: `sum += values[k] * x[col_idx[k]]`. The compiler cannot vectorize this easily because `col_idx` is a gather. On x86, AVX2 and AVX-512 provide gather instructions, but gathers have latency and throughput costs. On some CPUs, scalar loads with unrolling outperform gather for irregular access. The choice depends on the matrix and the hardware, and it should be measured rather than assumed.

The dependency chain on `sum` is the more fundamental bottleneck. A single accumulator serializes the floating-point additions. Using four or eight accumulators breaks the chain and exposes instruction-level parallelism. The accumulators are reduced at the end of the row or segment. For long rows, this is effective. For short rows, the reduction overhead dominates. Row splitting can create longer segments from long rows, but it also increases the number of partial sums.

Data layout matters. CSR stores `values` and `col_idx` in separate arrays. Each iteration loads from two streams. Interleaving them as an array of structs reduces the number of streams but increases the footprint and can waste bandwidth if the struct is larger than the useful data. The standard separate arrays are usually the right default. Software prefetching `col_idx` and `values` ahead of the loop can hide some latency. Prefetching `x[col_idx[k+d]]` is harder because the address depends on a load from `col_idx`; the latency chain is `col_idx` load, then `x` load. Unrolling with multiple accumulators allows multiple independent chains and gives the prefetcher more to work with.

Sorting column indices within a row can improve locality if `x` is accessed in increasing order, but it changes the summation order and costs preprocessing. Blocked or ELL formats can improve vectorization for matrices with regular row lengths, but they are outside the CSR focus. The point is that vectorization is not a flag; it is a consequence of the data layout, the row-length distribution, and the reduction strategy.

## Load balancing and NUMA: the memory system is the scheduler

Static row partitioning is simple but can be imbalanced. Dynamic scheduling with an atomic counter over rows or row blocks can balance the work. The cost is atomic contention and reduced locality. Chunked dynamic scheduling amortizes the counter: each thread grabs a block of rows. Smaller chunks balance better but add overhead; larger chunks reduce overhead but may leave stragglers. The right chunk size depends on the row-length variance and the cost of the atomic operation.

Merge-based partitioning is static but balanced by nonzeros. It avoids the atomic counter and keeps each thread's access contiguous. It can still be imbalanced if the cost per nonzero varies, for example because cache misses depend on the column pattern. A hybrid scheme can partition by nonzeros and then use work stealing within ranges, but the complexity grows quickly.

NUMA adds another dimension. On a multi-socket system, memory is local to a socket. The first-touch policy places pages on the node that first writes them. If `y` is initialized by a single thread, all `y` pages may be on one node, and threads on other nodes write remotely. Parallel initialization is the fix: each thread initializes the `y` rows it will own. For row splitting and merge-based partitioning, ownership is more complex; initialize `y` by the thread or node that will perform the final reduction. The extra pass costs time but avoids remote memory traffic during the kernel.

`x` is dense and read by all threads. If `x` is large, remote reads can be significant. Replicating `x` per NUMA node increases memory but reduces remote traffic. The trade-off depends on the relative sizes of `x` and `A`. If `nnz` is much larger than `n`, replicating `x` is cheap. If `n` is large and `nnz` is small, replication may be expensive. Thread affinity should match memory placement; otherwise the first-touch policy is undermined by the scheduler.

False sharing is the final memory-system concern. `y` entries for adjacent rows share cache lines. If different threads write adjacent `y` entries, the cache line ping-pongs between cores. Padding `y` or aligning row blocks to cache lines reduces this contention at the cost of memory. The same applies to per-thread partial buffers. The trade-off is explicit: padding wastes memory but reduces coherence traffic.

## Determinism and the cost of ordering

Floating-point addition is not associative. Row splitting and merge-based partitioning change the order of summation. If reproducibility is required, the kernel must use per-thread partials and combine them in a fixed order. The fixed order may reduce parallelism or increase memory. Compensated summation can improve accuracy but adds arithmetic. Reproducible reduction algorithms exist, but they trade performance for determinism. The choice should be explicit: many applications accept nondeterminism, but debugging and testing often do not.

The baseline owner-computes loop preserves the serial summation order within each row. That is a useful property. Row splitting and merge-based partitioning give up that property in exchange for parallelism and balance. The design should document which property matters and why.

The next design question is how to combine these choices into a single kernel that is balanced, vectorized, and predictable across matrices and NUMA topologies.

## A hybrid work plan: blocks for short rows, segments for long rows

The previous sections treated row splitting and merge-based partitioning as alternatives. A practical kernel often combines them. The observation is that row-length distributions are rarely uniform. They have a large mass of short rows and a long tail of dense rows. Short rows do not benefit from splitting: the reduction overhead and partial-sum traffic outweigh the extra parallelism. Dense rows do benefit: they contain enough work to fill SIMD lanes and can be split across threads without creating too many partials. A hybrid plan classifies rows by length and applies the appropriate strategy to each class.

The classification threshold `T` is a tuning parameter. Rows with `row_ptr[i+1] - row_ptr[i] <= T` are short. Rows above `T` are long. Short rows are grouped into blocks with a target nonzero count `B`. Each block is a work item that one thread processes with the owner-computes loop. Long rows are split into segments of at most `L` nonzeros. Each segment is a work item that computes a partial sum. The work items are generated in row order, so the plan is a sorted list of disjoint nonzero ranges. This ordering is important for locality and for deterministic reduction.

The planner does not need to inspect `values` or `col_idx`. It only needs `row_ptr`. That makes planning cheap and cache-friendly. The planner can be run once per matrix and reused across many SpMV calls, which matters in iterative solvers where the matrix is fixed and `x` changes every iteration.

A compact work item can be represented as a struct with `row_begin`, `row_end`, `nnz_begin`, `nnz_end`, and a segment identifier. For a block of short rows, `row_begin` and `row_end` delimit the rows, and `nnz_begin` and `nnz_end` delimit the corresponding nonzeros. For a segment of a long row, `row_begin == row_end - 1` and the nonzero range is the segment. The segment identifier is `-1` for blocks and a unique integer for segments. The executor uses the identifier to write partials into a segment-indexed array.

The cost model for assigning work items to threads should reflect the actual work. For a block, the cost is the number of nonzeros plus a per-row overhead. For a segment, the cost is the segment length plus a smaller fixed overhead. The per-row overhead accounts for the loop setup, the `y` store, and the reduction. If the cost model is wrong, the static schedule will be imbalanced. A simple calibration run can estimate the overhead by timing a matrix with known row lengths. Alternatively, the planner can use a heuristic: `cost = nnz + alpha * rows` for blocks and `cost = nnz + beta` for segments, with `alpha` around 4 to 16 and `beta` around 8 to 32, depending on the architecture.

The assignment itself is a partition of the work item list into `P` contiguous chunks of roughly equal cost. Contiguous assignment has three benefits. First, it preserves the row order within each thread, which improves locality for `y` and for the row slices of `A`. Second, it reduces false sharing on the partial array because adjacent segments are usually written by the same thread. Third, it makes the reduction deterministic: the partials for a row are written by a known set of threads in a known order. The cost is that a single expensive work item can create a straggler. The planner can mitigate this by splitting long rows into smaller segments, so no single work item is too large.

## Segment-indexed partials and deterministic reduction

The reduction strategy determines both performance and reproducibility. The hybrid plan uses a segment-indexed partial array. For each long row, the planner records the range of segment identifiers that belong to that row. The executor writes `partials[segment_id] = sum` for each segment. After the kernel, a reduction loop sums the partials for each long row in increasing segment order. Short rows are written directly to `y` by the owner-computes loop, so they need no reduction.

This scheme has several advantages. It avoids atomics entirely. It avoids per-thread dense partial arrays, which can consume `P * m * 8` bytes and become prohibitive for large `m`. The partial array size is the number of segments, which is at most `nnz / L` for long rows. For `L = 256` and `nnz = 10^9`, that is about four million doubles, or thirty-two megabytes. That is usually acceptable. The reduction is a separate parallel loop over rows, which can use all threads and has good locality because each row's partials are contiguous.

The scheme also gives deterministic results. The partials for a row are summed in segment order, which is the order in which the segments appear in the row. That order is fixed by the planner, independent of thread scheduling. If the executor uses a static assignment, the result is bitwise reproducible across runs on the same machine and thread count. If the executor uses dynamic scheduling, the partials are still written to the same segment slots, so the reduction order remains fixed. The only source of nondeterminism would be if the executor used atomics or if the reduction order depended on thread arrival. Neither happens here.

There is a cost to the separate reduction pass. The partials must be written to memory and read back. For long rows, the arithmetic intensity of the segment kernel is low, so the extra write and read can be a noticeable fraction of the total traffic. The trade-off is between reduction traffic and the parallelism gained by splitting. The planner should split only when the row is long enough that the extra parallelism outweighs the reduction cost. The threshold `T` controls this. A useful heuristic is to set `T` to a small multiple of the average row length, but the best value depends on the memory bandwidth and the number of threads. Autotuning can find it.

The reduction loop can be optimized. For each row, the partials are contiguous. The loop can use SIMD to sum four or eight partials at a time. The final sum is written to `y[row]`. If the number of partials per row is small, the loop overhead dominates. In that case, the planner can merge adjacent segments of the same row into a single work item, or the executor can accumulate multiple segments of the same row locally before writing a single partial. The latter is possible if a thread processes several consecutive segments of the same row. Since work items are sorted by row and assigned contiguously, this happens naturally when a thread's chunk covers multiple segments of a long row. The executor can keep a current row and a running sum, flushing when the row changes. This reduces the number of partials and the reduction traffic. The flush order is still segment order, so determinism is preserved.

## Vectorizing the segment kernel

The segment kernel is where vectorization pays off. A segment has a known length `L` and a contiguous range of nonzeros. The inner loop computes a dot product with indirect indexing. The key is to break the dependency chain and to give the compiler or the intrinsic code enough independent work.

A common pattern is to use four or eight vector accumulators. For AVX2 with doubles, four accumulators of type `__m256d` cover sixteen scalar additions in flight. For AVX-512, two `__m512d` accumulators cover sixteen as well. The loop processes `V` nonzeros per iteration, where `V` is the vector width. It loads a vector of `values`, gathers the corresponding `x` entries, multiplies, and accumulates. The gather can be done with `_mm256_i32gather_pd` or `_mm512_i32gather_pd`, but gathers are not always the fastest choice. On many microarchitectures, a sequence of scalar loads into a vector register is competitive or faster, especially when the column indices are irregular. The compiler may generate a gather automatically if the code is written with an array of indices, but it may also generate scalar loads. The only reliable way to know is to measure.

An alternative is to load `values` as a vector and load `x` entries scalar-wise into a vector using `_mm256_set_pd`. This avoids the gather instruction but uses four scalar loads and a vector insert. The scalar loads can issue in parallel, and the out-of-order engine can overlap them with the multiply-add. This approach often wins for irregular matrices because the gather unit is a bottleneck. It also makes prefetching easier: the compiler can issue prefetches for the scalar loads.

The tail of a segment is handled with a scalar loop. If `L` is a multiple of the vector width, the tail is empty. The planner can choose `L` to be a multiple of 8 or 16, but the last segment of a row may be shorter. The executor can process the tail with a scalar loop or with a masked vector operation. Masked operations are available on AVX-512 and on some ARM architectures. They avoid a branch but may have a higher latency. For short tails, a scalar loop is usually fine.

Software prefetching is important for large matrices. The address of `x[col_idx[k]]` depends on a load from `col_idx`. The latency chain is: load `col_idx[k]`, compute address, load `x[address]`. To hide this, the kernel can prefetch `col_idx[k + d]` and then prefetch `x[col_idx[k + d]]` after the index is loaded. A two-stage pipeline with distance `d` (typically 8 to 32) can hide a significant fraction of the memory latency. The prefetch instructions add overhead, so the distance should be tuned. On some CPUs, the hardware prefetcher handles the sequential access to `values` and `col_idx` well, but it cannot prefetch `x` because the access pattern is irregular. Software prefetch for `x` is often the difference between memory-bound and latency-bound performance.

The segment kernel should also use multiple accumulators to break the floating-point dependency chain. A single accumulator serializes the additions: each FMA depends on the previous one. With four accumulators, the processor can issue four independent FMAs per cycle, limited by the FMA throughput. At the end of the segment, the accumulators are summed. The summation order is fixed: accumulator 0 plus accumulator 1 plus accumulator 2 plus accumulator 3. That order is part of the deterministic reduction. If the compiler reorders the reduction, the result may change. Use `-ffp-contract=off` or explicit intrinsics to control the order. For reproducible results, the reduction order must be specified and enforced.

## NUMA placement for the hybrid kernel

The hybrid kernel has three data structures that matter for NUMA: `x`, `y`, and the partial array. `x` is read by all threads. `y` is written by the owner-computes loop for short rows and by the reduction loop for long rows. The partial array is written by the segment kernel and read by the reduction loop.

The first-touch policy applies to all of them. If `x` is initialized by a single thread, all its pages are on one node. Threads on other nodes will read remotely. The fix is to initialize `x` in parallel with the same thread affinity that will be used during the kernel. If `x` is produced by a previous operation, that operation should also be parallel and NUMA-aware. If `x` is read-only and large, replicating it per node can help. The replication cost is `O(n)` per node, which is small compared to `O(nnz)` if `nnz >> n`. The replicated copies should be allocated on the local node and initialized by a local thread. During the kernel, each thread reads the copy on its own node. This eliminates remote reads for `x` at the cost of memory and a copy.

`y` is more difficult because it is an output. If `y` is initialized by a single thread, its pages are on one node. The owner-computes loop writes short rows, and the reduction loop writes long rows. The threads that write `y` may be on different nodes. One solution is to allocate `y` with interleaved pages across all nodes. Then every thread has a mix of local and remote writes. Interleaving spreads the traffic but does not eliminate remote access. Another solution is to assign rows to nodes and have the reduction for a row run on the node that owns the row. The planner can partition rows by node, and the executor can use thread affinity to ensure that each node's threads process its rows. For short rows, the owner-computes loop naturally writes the rows it owns. For long rows, the segment kernel may be spread across nodes, but the reduction for a row can be assigned to the node that owns the row. The partials for that row may be on other nodes, so the reduction reads remotely. To avoid that, the partials can be replicated or the segment kernel can be restricted so that all segments of a row are processed by threads on the same node. That reduces parallelism for very long rows, but it may be worth it if remote traffic is the bottleneck.

The partial array is written by the segment kernel. If the segments are assigned contiguously to threads, each thread writes a contiguous range of the partial array. The first-touch policy places those pages on the thread's node. The reduction loop then reads all partials. If the reduction is parallelized by rows, each row's partials may be on a different node. The reduction thread reads remotely. To improve locality, the reduction can be partitioned by the same node assignment as the partials. For example, each node reduces the partials that were written by its threads. But a row may have partials on multiple nodes. That requires a cross-node reduction, which is complex. A simpler approach is to interleave the partial array across nodes. Then the reduction reads a mix of local and remote pages, but the traffic is spread evenly. The best choice depends on the relative cost of remote reads and the size of the partial array.

Thread affinity is essential for all of these strategies. Use `OMP_PROC_BIND=close` or `OMP_PLACES=cores` to pin threads to cores. Use `numactl --cpunodebind` and `--membind` for explicit control. If the threads migrate between nodes, the first-touch placement is undermined, and remote traffic increases. Measure with `perf stat -e node-loads,node-load-misses` or with a NUMA-aware profiler. The goal is to keep the majority of memory accesses local. For SpMV, which is memory-bound, a small increase in remote traffic can have a large impact on runtime.

## Autotuning the hybrid parameters

The hybrid plan has four main parameters: the split threshold `T`, the segment length `L`, the block target `B`, and the number of accumulators `A`. These interact with the matrix, the hardware, and the thread count. A single static configuration will not be optimal for all matrices. Autotuning is the practical solution.

The autotuner runs the kernel on a small number of candidate configurations and measures the runtime. The matrix is fixed, so the tuning cost is amortized over many SpMV calls. The candidate set can be small: `T` in `{2*avg, 4*avg, 8*avg}`, `L` in `{64, 128, 256, 512}`, `B` in `{1024, 2048, 4096, 8192}`, and `A` in `{2, 4, 8}`. That is 3 * 4 * 4 * 3 = 144 configurations, which is too many for a quick tune. A staged search reduces the cost. First, fix `A` to 4 and `B` to 4096, and tune `T` and `L`. Then fix the best `T` and `L`, and tune `B` and `A`. This requires about 12 + 12 = 24 runs. Each run can use a single SpMV call, which is cheap for a matrix that will be used for hundreds of iterations.

The autotuner should also consider the thread count. If the number of threads is small, splitting may not be necessary. If the number of threads is large, splitting is more important. The tuning can be done once per thread count, or the parameters can be scaled with the thread count. For example, `L` can be chosen as `max(64, nnz / (P * 16))` so that each thread gets a reasonable number of segments. The threshold `T` can be chosen as `max(16, avg_row_length * 2)`. These heuristics are starting points, not final answers.

The autotuner must be careful about measurement noise. SpMV is memory-bound, and the runtime can vary with cache state and NUMA placement. Use multiple iterations and take the median. Warm up the cache and the TLB before measuring. Pin threads to cores. Use a high-resolution timer. If the matrix is small, the tuning overhead may dominate, so use a default configuration.

## Validation and measurement

A hybrid SpMV kernel should be validated on three axes: correctness, balance, and memory behavior. Correctness is checked against a serial CSR kernel. The comparison should allow a tolerance for floating-point differences, but if reproducible mode is enabled, the results should match bitwise across runs. The reproducible mode is activated by using the segment-indexed partial array and a fixed reduction order. If the results differ, the reduction order or the segment assignment is not deterministic.

Balance is measured by timing each thread's work. In OpenMP, each thread can record its start and end time, or the executor can count the nonzeros processed per thread. If the difference between the maximum and minimum work is more than ten percent, the cost model or the chunk size is wrong. The planner can adjust by splitting long rows into smaller segments or by changing the block target `B`. For matrices with extreme row-length variance, a dynamic schedule may be necessary, but it complicates reproducibility. A compromise is to use a static schedule with more work items than threads, so the granularity is finer and the imbalance is smaller.

Memory behavior is measured with hardware counters. The key metrics are memory bandwidth, L2 and L3 miss rates, TLB miss rates, and remote NUMA traffic. For a memory-bound kernel, the achieved bandwidth should be close to the peak for the access pattern. If it is not, the bottleneck may be latency, insufficient parallelism, or poor prefetching. The gather instruction throughput and the number of outstanding cache misses are also useful. On Intel processors, `perf stat -e offcore_response.demand_data_rd.any_response` and `uncore_imc_0/cas_count_read/` give memory traffic. On AMD, use `perf stat -e ls_dmnd_fills_from_sys.ext_cache_local` and similar events. The exact event names vary by microarchitecture, but the principle is the same: measure the memory system, not just the instruction count.

The final check is scalability. Run the kernel with one thread, two threads, four threads, and so on. The runtime should decrease until the memory bandwidth saturates. If it stops decreasing early, the kernel is not memory-bound but limited by a serial section, such as the reduction or the planner. If it decreases and then increases, false sharing or NUMA effects are likely. The hybrid plan is designed to scale, but scaling is not automatic. It requires the right parameters, the right affinity, and the right memory placement. The measurements tell you which one is wrong.

## Sparse matrix reordering and the shape of the work

A CSR matrix can be permuted in two independent ways. A row permutation reorders the rows, and a column permutation reorders the columns and, if the vector is permuted consistently, the entries of `x`. Both permutations change the memory access pattern of SpMV even though they do not change the mathematical result. They are usually applied once, before the first SpMV, and then reused for every iteration of a solver.

Row permutation affects the work distribution and the locality of `y` and `A`. If rows are sorted by length, a static block partition can be balanced without splitting rows. The longest rows are known in advance, and the planner can assign them to threads in a way that equalizes the total nonzero count. But sorting rows by length can destroy spatial locality. Many sparse matrices come from discretizations of physical domains, and the original ordering reflects that structure. Rows that are close in index often access similar columns, so the corresponding entries of `x` stay in cache when a thread processes a contiguous block of rows. Sorting by length scatters those rows, and the cache reuse disappears. The trade-off is between balance and locality. A compromise is to sort rows within blocks: divide the rows into blocks of a few hundred, sort each block by length, and keep the blocks in their original order. This preserves coarse locality while improving balance within each block.

Column permutation affects the access pattern to `x` and the vectorization of the inner loop. If columns are ordered so that the nonzeros in a row are clustered, the corresponding `x` entries are also clustered. A row that accesses columns 100 through 110 touches one or two cache lines instead of eleven. This reduces the effective memory traffic for `x` and improves the cache hit rate. Reverse Cuthill-McKee and similar bandwidth-reduction algorithms produce such orderings. They are standard in sparse direct solvers, but they are also useful for SpMV. The cost is that the permutation must be applied to `x` before the multiplication and to `y` after, or the matrix must be stored with permuted columns and the vectors permuted consistently. If the solver already permutes for factorization, the SpMV kernel should use that permutation rather than imposing its own.

Column permutation also changes the summation order within each row. Floating-point addition is not associative, so the result may differ from the original ordering. If reproducibility is required, the permutation must be fixed and the reduction order must be defined in terms of the permuted columns. That is usually acceptable because the permutation is part of the matrix definition, not a runtime choice. The kernel should document that the result is reproducible for a given permutation.

A more aggressive reordering clusters rows that share columns. The idea is to partition the rows into groups such that rows in the same group access a small set of columns. If a thread processes all rows in a group, the `x` entries for those columns stay in cache across multiple rows. This is a form of temporal blocking. Graph partitioning algorithms can find such groups by treating the matrix as a bipartite graph and minimizing the cut between row groups and column groups. The cost is preprocessing time and a more complex work assignment. The benefit is reduced `x` traffic, which can dominate the runtime when `x` does not fit in cache. The optimal group size depends on the cache size and the column overlap. If the group is too large, the working set exceeds the cache; if it is too small, the parallelism is limited.

Reordering interacts with the hybrid work plan. The planner classifies rows by length, and the classification depends on the row permutation. If rows are sorted by length, the short rows and long rows are contiguous, which simplifies the planner. But if the original ordering is preserved for locality, the planner must handle interleaved short and long rows. The work item list can still be generated in row order, but the cost model must account for the varying row lengths. The executor can process the list in order, and the static assignment will naturally group nearby rows together. This is another reason to keep the row order intact: it preserves the locality that the original ordering provides.

## Cache blocking, multiple vectors, and the arithmetic intensity ceiling

SpMV has an arithmetic intensity of roughly 0.1 floating-point operations per byte. Each nonzero requires a load of the value, a load of the column index, a load of the corresponding `x` entry, one multiply-add, and an eventual store to `y`. The store is amortized over the row, so for long rows the bytes per nonzero are about 8 for the value, 4 for the index, and 8 for `x`, for a total of 20 bytes and 2 flops. The operation is firmly memory-bound. The only way to increase arithmetic intensity is to reuse the matrix or the vector more effectively.

One way to reuse the matrix is to process multiple right-hand sides. If `x` and `y` become matrices with `k` columns, each nonzero of `A` is loaded once but used `k` times. The bytes per nonzero become 8 for the value, 4 for the index, and 8k for the `x` entries, while the flops become 2k. The arithmetic intensity approaches 0.25 flops per byte as `k` grows. This is still low, but it is enough to improve performance when the kernel is limited by the index and value loads. Block iterative methods, such as block Jacobi or block GMRES, naturally produce multiple vectors. The SpMM kernel can be organized so that the inner loop over `k` is vectorized, and the matrix is streamed once. The load balance is the same as SpMV, but the cost per nonzero is higher, so the relative overhead of row splitting and reduction is lower.

Cache blocking for a single vector is more subtle. The goal is to keep the working set of `x` in cache while streaming the matrix. If `x` is small enough to fit in L2, then every `x` access after the first is a cache hit, and the effective memory traffic for `x` drops to zero. The kernel becomes limited by the value and index streams, which are sequential and prefetchable. In that case, the simple owner-computes loop is close to optimal. If `x` does not fit in cache, the accesses to `x` may miss, and each miss brings a full cache line that is used only once. The effective bytes per nonzero can then be dominated by the cache line size, not the useful data. For a 64-byte line and 8-byte `x` entries, one miss per nonzero means 64 bytes of traffic for 8 bytes of useful data. That is an eightfold increase in `x` traffic.

Column blocking can reduce this penalty by processing the matrix in column blocks that fit in cache. For each column block, the kernel iterates over all rows and processes only the nonzeros whose column indices fall in the block. The `x` entries for the block stay in cache across all rows. The cost is that the matrix must be traversed multiple times, once per column block. If the matrix is stored in CSR, the traversal is not efficient because the nonzeros for a column block are scattered across rows. A reordered format, such as a blocked CSR or a doubly compressed sparse column (DCSC) format, can group the nonzeros by column block. The preprocessing cost is significant, but it is amortized over many SpMV calls. The trade-off is between the extra memory traffic for multiple passes and the reduced traffic for `x`. The optimal block size is the one that fits in L2 and minimizes the number of passes.

Compressed sparse block (BSR) formats take a different approach. They store dense blocks of the matrix, for example 4x4 or 8x8, with a single column index per block. This reduces the index storage and enables vectorization within the block. If the matrix has dense sub-blocks, BSR can be much faster than CSR because the index overhead is amortized and the inner loop is regular. If the matrix is not block-dense, the zero padding increases the flop count and the memory traffic for values. The decision to use BSR should be based on the sparsity pattern. A common heuristic is to convert to BSR if the average number of nonzeros per row is high and the matrix has a block structure, such as in finite element problems with multiple degrees of freedom per node. The block size should match the SIMD width or the number of degrees of freedom.

The arithmetic intensity ceiling for SpMV is low, and no amount of blocking can change that for a single vector. The fundamental limit is the need to read the matrix. Compression can reduce the bytes read. For example, if the column indices fit in 16 bits, the index stream is halved. If the values are stored in single precision, the value stream is halved, but the accumulation must still be in double precision to preserve accuracy. Delta encoding of column indices within a row can reduce the index stream further, at the cost of a decompression step. Bitmap formats are efficient for very sparse rows. Each compression scheme has a decompression cost and a preprocessing cost. The best choice depends on the matrix and the hardware. The performance model should include the compression ratio and the decompression overhead.

## Hardware-specific vectorization and the gather question

The inner loop of SpMV is a dot product with indirect indexing. Vectorizing it requires either a gather instruction or a sequence of scalar loads that are assembled into a vector. The gather instruction is the natural choice, but it is not always the fastest. On Intel AVX2, `_mm256_i32gather_pd` has a throughput of several cycles per element and a high latency. On AVX-512, `_mm512_i32gather_pd` is improved but still slower than a sequential load. On AMD Zen, gather is implemented but also has limited throughput. On ARM SVE, `svld1_gather_f64` is available, but its performance depends on the microarchitecture. The general rule is that gathers are best when the indices are clustered and the hardware has a dedicated gather unit. For random indices, scalar loads often win because they can issue in parallel and overlap with the multiply-add.

A scalar-load vectorization pattern loads the values as a vector and then loads the `x` entries one by one into a vector register. On AVX-512, this can be done with `_mm512_set_pd`, which takes eight scalar arguments. The compiler may generate a sequence of `vmovsd` and `vinsertf64x4` instructions. The scalar loads can execute in parallel, and the out-of-order engine can overlap them with the FMAs. This pattern also makes software prefetching easier because the compiler can issue prefetches for the scalar loads. The disadvantage is that it uses more instructions than a gather, but instruction throughput is rarely the bottleneck for SpMV. The bottleneck is memory latency and bandwidth.

The choice between gather and scalar loads should be made per segment, not per matrix. A segment with clustered column indices may benefit from gather, while a segment with random indices may benefit from scalar loads. The kernel can use a heuristic based on the variance of the column indices or the number of distinct cache lines touched. A simpler approach is to autotune the choice for the whole matrix. The autotuner can compile two versions of the segment kernel and select the faster one. This adds code complexity but is effective.

Prefetching is essential for both approaches. The address of `x[col_idx[k]]` depends on a load from `col_idx`. The latency chain is: load `col_idx[k]`, compute the address, load `x[address]`. To hide this, the kernel can prefetch `col_idx[k + d]` and then prefetch `x[col_idx[k + d]]` after the index is loaded. A two-stage pipeline with distance `d` can hide a significant fraction of the memory latency. The distance should be tuned; typical values are 8 to 32. On some CPUs, the hardware prefetcher handles the sequential access to `values` and `col_idx` well, but it cannot prefetch `x` because the access pattern is irregular. Software prefetch for `x` is often the difference between memory-bound and latency-bound performance. The prefetch instructions add overhead, so the distance should be chosen to balance the benefit of hiding latency against the cost of the extra instructions.

The reduction of the vector accumulators must also be considered. After the inner loop, the kernel has several vector accumulators that must be summed into a scalar. On AVX-512, `_mm512_reduce_add_pd` performs a horizontal reduction. The order of the reduction is defined by the intrinsic, but it may not be the same as the scalar order. For reproducible results, the reduction order must be fixed and documented. If the kernel uses a fixed sequence of shuffles and adds, the order is deterministic. If it uses a compiler-generated reduction, the order may vary with the compiler version or optimization level. Use explicit intrinsics or a fixed reduction tree to ensure reproducibility.

Scalable vector architectures like ARM SVE change the calculus. SVE does not have a fixed vector length; the hardware can choose any multiple of 128 bits up to 2048 bits. The code must use `svcntd()` to query the number of doubles per vector and `svwhilelt` to handle the tail. SVE's gather instruction is `svld1_gather_f64`, and it also has `svprfw` for prefetch. The predication avoids scalar cleanup loops, which can improve performance for short rows. However, the same gather performance issues apply. SVE's advantage is portability across vector lengths, not necessarily faster gathers. The best approach is to write the kernel with SVE intrinsics and let the compiler generate the best code for the target. If intrinsics are not available, use `#pragma omp simd` and rely on the compiler. Measure on the target hardware.

The gather question has no universal answer. It depends on the matrix, the hardware, and the compiler. A robust SpMV kernel should provide both paths and select the faster one at runtime or during autotuning. The selection can be based on a microbenchmark that mimics the access pattern of the matrix. For example, the autotuner can run a small kernel that performs gathers and scalar loads on a subset of the matrix's rows and measure the throughput. The winner is used for the full kernel. This adds a small tuning cost but can improve performance significantly on matrices with irregular column patterns.

## Performance modeling for SpMV

A simple performance model helps explain why SpMV behaves the way it does and guides the choice of parameters. The roofline model combines arithmetic intensity with the machine's peak floating-point throughput and peak memory bandwidth. For SpMV, the arithmetic intensity is low, so the model predicts memory-bound performance. The expected time is the total bytes moved divided by the achieved bandwidth. The total bytes include the value array, the column index array, the `x` vector, and the `y` vector. For a matrix with `nnz` nonzeros and `m` rows, the bytes are approximately `8 * nnz` for values, `4 * nnz` for indices, `8 * nnz` for `x` accesses, and `8 * m` for `y` stores. The `x` accesses are the most variable because they may hit or miss in cache. If `x` fits in cache, the effective `x` bytes are much lower. If `x` does not fit and the accesses are random, each access may bring a full cache line, multiplying the effective `x` bytes by the cache line size divided by the element size.

The model can be refined with cache hit rates. Let `h` be the fraction of `x` accesses that hit in cache. Then the effective `x` bytes per nonzero are `8 * h + 64 * (1 - h)` if a miss brings a 64-byte line. For `h = 0`, the `x` traffic is 64 bytes per nonzero, which dominates the value and index traffic. This explains why reordering and blocking can have a large impact. The model also shows that the benefit of row splitting is not in reducing bytes but in increasing parallelism and hiding latency. If the kernel is bandwidth-bound, splitting does not increase bandwidth; it only helps if the kernel is latency-bound or if the work distribution is imbalanced.

The number of threads affects the model through the achieved bandwidth. Memory bandwidth is a shared resource. Adding threads increases the number of outstanding memory requests until the bandwidth saturates. Beyond that point, additional threads do not help and may hurt due to contention. The model should include a saturation point. The optimal thread count is the one that reaches the saturation bandwidth with minimal overhead. For a NUMA system, the achieved bandwidth also depends on the placement of data. Local accesses are faster than remote accesses. The model can be extended with a NUMA factor: the effective bandwidth is a weighted average of local and remote bandwidths, weighted by the fraction of accesses that are local. This is why first-touch initialization and thread affinity matter.

The model can be used to predict the benefit of autotuning. For example, if the model predicts that `x` misses dominate, the autotuner should focus on column blocking or `x` replication. If the model predicts that the kernel is bandwidth-bound on values and indices, the autotuner should focus on compression or BSR. If the model predicts that the kernel is latency-bound, the autotuner should focus on prefetching and unrolling. The model is not a substitute for measurement, but it narrows the search space.

A practical performance model can be implemented as a small function that takes matrix statistics and hardware parameters and returns an estimated time. The matrix statistics include `nnz`, `m`, `n`, average row length, maximum row length, and the variance of row lengths. The hardware parameters include peak bandwidth, cache sizes, and the number of cores. The function can be calibrated with a few microbenchmarks. The autotuner can then use the model to rank candidate configurations before running them. This reduces the tuning cost and makes the kernel more portable across matrices.

## Mixed precision and the accumulation contract

SpMV is memory-bound, so reducing the number of bytes read per nonzero is one of the few ways to improve performance without changing the algorithm. Mixed precision is a direct application of that idea. The kernel can load `values` and `x` in a narrower type, such as `float`, while accumulating in `double`. The output `y` can be stored in either precision, depending on the solver's needs. The contract is explicit: input precision `P`, accumulation precision `A`, output precision `O`. The inner loop converts `P` to `A`, multiplies, and accumulates. On AVX-512, this means loading eight `float` values, converting them to eight `double` values, and issuing FMAs against `double` entries of `x`. The value and `x` streams are halved, but register pressure and conversion instructions increase. The arithmetic intensity in flops per byte improves because the same number of flops is performed on fewer bytes, but the operation remains memory-bound.

The accuracy implications are not optional. Single precision has a 24-bit mantissa. For a row with thousands of nonzeros, the accumulated rounding error can be significant, especially when the terms cancel. Compensated summation can recover much of the accuracy at the cost of extra arithmetic. A simpler approach is to accumulate in `double` even when the inputs are `float`. That removes the accumulation error but not the representation error in the inputs. The kernel should document which errors are controlled and which are not. Reproducibility is preserved if the conversion is deterministic and the reduction order is fixed. Mixed precision changes the result relative to a double-precision kernel, so it should be treated as a numerical choice, not just a performance flag.

Index precision is a separate axis. If `nnz` is below `2^31`, 32-bit column indices halve the index stream relative to 64-bit indices. For matrices with more than two billion nonzeros, 64-bit indices are required. A common compromise is to store 32-bit local indices within a block and a 64-bit base offset per block. The kernel adds the base to the local index before accessing `x`. This keeps the index stream narrow while supporting large matrices. The addition is cheap and can be vectorized. The planner must ensure that each block's local indices fit in 32 bits, which is usually true if blocks are sized to a few million nonzeros.

## Structural zeros, empty rows, and non-canonical CSR

Real CSR matrices are not always canonical. They may contain explicit zeros, unsorted column indices, or duplicate entries for the same row and column. The kernel can process all of these as ordinary nonzeros, but they waste bandwidth and complicate reproducibility. Preprocessing should remove explicit zeros, sort columns within each row, and sum duplicates. This produces a canonical CSR that is smaller and faster to traverse. The preprocessing changes the summation order, so it should be done once and the canonical matrix should be used for every SpMV call. The kernel should not attempt to detect or fix non-canonical entries at runtime; the overhead would dominate.

Empty rows are a correctness detail that is easy to miss. If `row_ptr[i] == row_ptr[i+1]`, row `i` has no nonzeros. The owner-computes loop writes `y[i] = 0.0` naturally because the inner loop does not execute. Row splitting and merge-based partitioning generate no work item for an empty row, so `y[i]` may be left untouched. The planner must either emit a zeroing work item or the executor must initialize `y` to zero before the kernel. Parallel initialization is the better choice because it also handles the NUMA placement of `y`. If initialization is not possible, the reduction loop can set `y[i] = 0` for empty rows. That adds a branch but preserves correctness.

Unsorted columns affect the summation order. If the columns are not sorted, the kernel sums in storage order. That is deterministic for a fixed matrix, but it may differ from the order used by a canonicalized matrix. Duplicate entries are similar: summing them separately is mathematically equivalent to summing them first, but floating-point results can differ. For reproducibility, canonicalize once and freeze the order. If the solver reorders the matrix between iterations, the SpMV results may change even though the mathematical operation is the same. The kernel should expose whether it assumes canonical input. If it does, the caller is responsible for canonicalization. If it does not, the kernel must document that results depend on storage order.

## Workspace management and thread-local buffers

The hybrid kernel needs workspace: the partial array, the segment metadata, the work item list, and per-thread accumulators. Allocating these in every SpMV call is expensive and can introduce nondeterministic memory placement. Allocate once per matrix and reuse the workspace across calls. The workspace should be aligned to cache lines to avoid false sharing. Use `posix_memalign` or `std::aligned_alloc` with an alignment of 64 bytes or the cache line size. For NUMA systems, allocate each buffer on the node where it will be used, or initialize it with the same thread affinity that the kernel will use. The partial array is shared, so its pages should be interleaved across nodes or placed according to the reduction strategy. The work item list is read-only after planning; it can be replicated per node if remote reads are a problem. Per-thread accumulators should be in thread-local storage or on the stack. If they are in a shared array, pad each thread's slot to a cache line.

The executor should not allocate memory in the inner loop. If dynamic scheduling is used, the atomic counter should be in its own cache line to avoid contention with the work items. The reduction loop should use a parallel for over rows, with each thread processing a contiguous range. If the partials for a row are contiguous, the reduction is a simple SIMD loop. If they are not, the planner should reorder them so that they are. The reduction can use four or eight accumulators to break the dependency chain, and the final sum is written to `y[row]`. The order of the partials is fixed by the planner, so the reduction is deterministic even if the executor uses dynamic scheduling.

Thread-local partial buffers are an alternative to a global segment-indexed array. Each thread accumulates partials for the rows it processes, and a separate combine step merges them. This saves memory when the number of segments is large, but it complicates the reduction and can introduce nondeterminism if the combine order depends on thread arrival. The global segment-indexed array is simpler and deterministic. The choice depends on the number of segments and the memory budget. If the partial array would exceed a few hundred megabytes, thread-local buffers may be necessary. Otherwise, the global array is the better default.

Finally, the kernel should expose a workspace query function. The query returns the required size and alignment for the partial array, the work item list, and any other buffers. This lets the caller allocate the workspace once, on the correct NUMA node, and reuse it across iterations. It also makes the kernel embeddable in a solver without hidden allocations. The solver can then focus on the numerical algorithm while the SpMV kernel focuses on the memory system.
