Log-structured merge trees turn random writes into sequential ones, but they do not make the cost of those writes disappear. They defer the cost to compaction: a background merge that takes overlapping sorted runs, resolves versions, drops obsolete records where safe, and writes new runs in a more favorable shape. Compaction is therefore not housekeeping after the write path. It is the write path's second act, and in write-heavy systems it often determines steady-state throughput, tail latency, and how much device endurance the workload consumes.

Parallel compaction is an attractive lever because a single large merge can leave most cores idle while it waits on storage, and a backlog of pending compactions can leave writers stalled. Running compactions concurrently or splitting one compaction into subcompactions can shorten the time a large merge occupies the background pool. It can also make the storage engine less predictable. Compactions compete for the same page cache, I/O queues, compression and checksum CPU, memory for iterators, and metadata locks. More concurrency can raise aggregate merge throughput while increasing write amplification, fragmenting output files, or starving the compactions that protect read latency. A scheduler that simply starts as many compactions as there are worker threads is not a design. It is an admission-control failure waiting for a workload.

This article examines the scheduler as a resource allocator. The discussion assumes a leveled LSM tree with block-based sorted tables, range-partitioned compaction, and a background thread pool shared by flush and compaction work. Tiered and hybrid layouts change the economics, but they do not remove the core contention: compaction consumes durable storage bandwidth and produces new durable data that will itself be compacted later. The scheduler's job is to spend that bandwidth where it reduces risk fastest, not merely where it produces the highest instantaneous merge rate.

## The Compaction Workload Is Not a Generic Thread-Pool Problem

An LSM tree absorbs writes into a mutable memtable, flushes that memtable to an immutable sorted run, and periodically merges runs across levels. Each level has a target size and a target number of sorted runs. A compaction selects input runs, merges them by key and sequence number, emits new runs at the next level, and removes the old inputs after the new outputs are durable. The write amplification of this process is the ratio of bytes written to storage to bytes written by the application, including flush and every subsequent level rewrite. Read amplification is the number of runs or files that a point lookup or range scan may need to consult. Space amplification is the ratio of physical bytes stored to logical live bytes.

These three amplifications are coupled. A policy that compacts aggressively reduces read and space amplification but increases write amplification and background I/O. A policy that compacts lazily preserves write bandwidth for foreground work but allows runs to accumulate, which raises read cost and can force emergency compactions later. Parallelism changes the shape of this trade-off because it changes how quickly the engine can retire compaction debt. It does not eliminate the debt. If a level needs to rewrite ten units of data to reclaim one unit of obsolete data, running that rewrite on eight threads still writes ten units. It may finish sooner, but it may also compete with the flushes and compactions that keep newer levels from stalling.

A generic thread pool is a poor abstraction for this work because compaction tasks are not interchangeable. Some compactions reduce read amplification by merging a small number of overlapping runs. Some reclaim space by dropping tombstones at the bottom level. Some are urgent because a level has exceeded its file-count trigger and foreground writes will stall until the level drops below the trigger. Some are large and low-priority but become urgent if ignored. The scheduler must distinguish these cases and must account for resources that are not captured by a simple runnable-thread count.

## Two Kinds of Parallelism

The first design decision is to separate inter-compaction concurrency from intra-compaction parallelism. Inter-compaction concurrency runs multiple independent compaction jobs at once. Intra-compaction parallelism splits one logical compaction into subcompactions that cover disjoint key ranges and merge those ranges concurrently. The two mechanisms have different costs.

Inter-compaction concurrency improves utilization when individual compactions are I/O-bound and the storage device can sustain more outstanding requests. It also increases the number of active iterators, open files, output writers, and metadata operations. On a device with a deep queue, several compactions may overlap well. On a device with limited endurance or a shared multi-tenant volume, the same concurrency can turn background work into a noisy neighbor for foreground reads. It can also create pathological interactions at level boundaries: two compactions that both read from the same level and write to the same next level may compete for overlapping key ranges, forcing serialization through locks or causing one job to pick inputs that the other is about to invalidate.

Intra-compaction parallelism attacks a different problem: a single compaction can be too large to finish promptly, even though its key range could be partitioned. If the input runs are already divided into files, the engine can assign file ranges to subcompactions and merge each range independently. The benefit is lower latency for large jobs and better core utilization during a merge that would otherwise be dominated by a few long sequential scans. The cost is boundary management. Splitting a compaction is only correct if every record that belongs to a key range is processed by the subcompaction responsible for that range, including all versions of a user key and any range tombstones that cover the boundary. If the split is made at a user-key boundary and all input iterators honor that boundary, the merge logic can remain the same per range. If the split is made at a file boundary that cuts through a user key's version chain, the output can contain an older version in one subcompaction and a newer version in another, and the engine may resurrect stale data or drop a live record.

A practical engine therefore treats subcompaction boundaries as merge invariants, not as scheduling hints. The boundary selection must be derived from the input key space and must preserve the rule that, for any user key, all relevant versions and tombstones land in exactly one subcompaction. Range tombstones make this stricter because a tombstone may cover keys that do not appear in the input at all. A subcompaction that owns only part of a range tombstone's span cannot independently decide whether the tombstone is obsolete. The safe approach is to keep the tombstone's full span within one subcompaction or to carry enough metadata to make the drop decision at a higher level.

## What the Scheduler Is Actually Choosing

A compaction scheduler is choosing which debt to pay, in what order, and with how much concurrency. The inputs to that choice are not just the number of pending jobs. They include the current level sizes, the number of runs per level, the overlap between candidate inputs, the estimated bytes to read and write, the age of the oldest pending compaction, the number of write stalls observed or predicted, and the resources currently consumed by flush work. The scheduler also needs a notion of urgency that is tied to foreground impact. A compaction that reduces the file count at a level just below its trigger is more urgent than a compaction that rewrites cold data at the bottom level, even if the latter has more bytes.

This is why compaction scheduling is not equivalent to maximizing background throughput. Throughput is a rate. The system cares about the rate at which it retires the specific compaction debt that would otherwise block writes or inflate read amplification. A scheduler that always picks the largest job may keep the device busy while small urgent jobs wait. A scheduler that always picks the oldest job may preserve fairness but ignore the fact that some old jobs have low impact. A scheduler that always picks the job with the highest predicted reduction in read amplification may starve space reclamation. The policy needs explicit weights and explicit starvation bounds.

Admission control is the other half of the decision. Even if a job is selected, the scheduler must decide whether to start it now, wait for a resource budget, or split it into subcompactions. The budget should cover more than thread count. It should include a cap on concurrent compactions per level, a cap on total compaction bytes in flight, a cap on open output files, and a reserve for flush work. Flush work is not optional. If flush is starved, the memtable fills, foreground writes stall, and the scheduler has failed at the one job that matters most: keeping the write path moving.

## Fan-In Is a Resource Cost Function

Fan-in is the number of input runs or files merged by a compaction. It is often discussed as a tuning knob for write amplification, but it is better understood as a resource cost function with several dimensions. Higher fan-in can consolidate more overlapping data in one pass, which may reduce the number of future rewrites if it moves the level closer to its target shape. It also increases the number of active iterators, the working set of index blocks, the memory needed for merge buffers, and the duration of the job. A high-fan-in compaction is harder to split cleanly because its inputs may have different key ranges and different file boundaries. It is also more likely to overlap with other compactions, which increases the chance of lock contention or wasted work.

Lower fan-in produces smaller, more schedulable jobs. That can improve responsiveness and make it easier to keep many cores busy on independent ranges. But small jobs can increase write amplification if they rewrite the same level repeatedly instead of merging enough data to cross a size threshold. They can also increase metadata pressure because more output files mean more file handles, more index blocks, and more entries in the version set. The right fan-in is therefore not a universal constant. It depends on the level's size ratio, the distribution of key ranges, the device's queue depth, and the scheduler's ability to batch small jobs without violating the merge invariant.

A useful way to model fan-in is to treat each additional input as buying a chance to reduce future work at the cost of current memory and latency. If the level is far below its target size, a larger merge may be wasteful because the data will be rewritten again soon. If the level is near its file-count trigger, a larger merge may be necessary to make durable progress. If the inputs have little overlap, high fan-in adds iterator overhead without much consolidation benefit. The scheduler should estimate overlap from file metadata rather than assume that every input contributes equally.

## Scheduling Under Backpressure

Backpressure is where compaction scheduling becomes a control problem. The engine observes write stalls, pending compaction bytes, L0 file counts, and read latency. It must translate those signals into admission decisions before the system enters a failure mode where compaction cannot keep up and foreground writes are throttled continuously. The common mistake is to treat backpressure as a reason to increase concurrency. If the device is already saturated, more compactions add queueing delay and memory pressure without increasing completed work. If the bottleneck is CPU for compression or checksums, more compactions may help only until the cores are saturated. If the bottleneck is a metadata lock or a version-set update, more compactions make the contention worse.

A scheduler with backpressure awareness should reserve capacity for urgent work, cap the number of compactions that can hold large output buffers, and prefer jobs that reduce the specific trigger causing the stall. When L0 file count is the trigger, the scheduler should prioritize compactions that move data out of L0 and into lower levels, even if those jobs are not the largest. When pending compaction bytes are the trigger, it should prefer jobs that reduce the debt with the least additional write amplification. When read latency is the trigger, it should prefer jobs that reduce the number of overlapping runs for hot key ranges, which may require range-aware prioritization rather than level-wide FIFO ordering.

Starvation bounds matter because every priority scheme can be gamed by a workload. A bottom-level compaction that reclaims space may never be urgent until the disk is nearly full. A low-priority range may never become hot. The scheduler needs a maximum deferral budget per job class, after which the job is promoted regardless of its current estimated impact. That budget should be expressed in terms of progress, not wall-clock time alone, because a stalled device can make a short wall-clock budget meaningless. The goal is to keep the system responsive without letting any class of compaction debt accumulate until it becomes an emergency.

The first constraint on any parallel compaction scheduler is therefore not how many threads it can use. It is whether it can explain, for every job it starts, which debt it is retiring and which resource budget it is consuming. A scheduler that cannot answer those questions will eventually optimize the wrong thing: it will maximize merge throughput while increasing write amplification, or it will minimize write amplification while allowing read amplification and write stalls to grow. The remaining design space is about making those trade-offs explicit and measurable, and about keeping the merge invariant intact when one logical compaction becomes several concurrent ones.

## Subcompaction Boundaries as a Correctness Contract

A subcompaction is not merely a slice of work. It is a claim about ownership of a key range. The claim is valid only when every record that could affect the output of that range is visible to the subcompaction. For a point key, that means all versions of the user key, across every input run, must be processed by the same subcompaction. If version 7 of key K is in one subcompaction and version 3 in another, neither subcompaction can decide the final visible value. The one holding version 7 may emit it, while the one holding version 3 may also emit it because it does not know a newer version exists. The result is either a duplicate or a stale resurrection, depending on how the outputs are ordered later. The merge invariant is therefore simple to state and easy to violate: for every user key, the set of input records that belong to that key must be partitioned, not split, across subcompactions.

Range tombstones make the invariant more demanding. A range tombstone does not name every key it covers. It may cover keys that appear in one input run and not another, and it may extend across boundaries that look natural from file metadata. If a subcompaction owns only part of a tombstone's span, it cannot know whether the tombstone is obsolete at the bottom level, because obsolescence depends on whether older data exists outside its range. One safe policy is to keep the full span of every range tombstone inside a single subcompaction. Another is to replicate the tombstone into every subcompaction whose range intersects the span, so each output retains the deletion semantics for its own keys. Replication increases write amplification and metadata, while non-splitting reduces parallelism for workloads with wide tombstones. The scheduler must know which policy the merge code implements before it treats a range as splittable.

Boundary selection should also respect sequence-number visibility. A subcompaction that drops a tombstone or an older version must be certain that no snapshot or transaction can still observe that version. Snapshot isolation and long-running read transactions turn compaction into a visibility problem, not just a merge problem. The scheduler cannot fix a visibility bug by running fewer subcompactions; it can only avoid making the bug more likely. The merge layer should expose the minimum sequence number that must be preserved, and the scheduler should treat that value as a boundary constraint when partitioning ranges.

Finally, subcompaction boundaries must be stable enough to produce output files that the manifest can describe without ambiguity. If two subcompactions emit files that overlap in user-key space, the version set may contain overlapping runs at the same level. Some engines tolerate this temporarily, but it complicates read amplification and future compaction. The cleaner contract is that subcompactions for one logical compaction produce disjoint key ranges, and the union of those ranges equals the logical compaction's range. The scheduler can then treat the outputs as a single level-shape change even though several threads produced them.

## A Cost Model for Parallel Compaction

To schedule parallel compaction, the engine needs a cost model that predicts both work and critical path. Total work is the sum of bytes read, bytes written, and CPU spent on compression, checksums, and merge comparisons. Critical path is the longest chain of dependent work that cannot be parallelized. For a compaction split into subcompactions, the critical path is the slowest subcompaction plus any shared serialization, such as manifest updates or version-set locks. Parallel efficiency is total work divided by the product of width and critical path. A width of eight does not deliver eight times the throughput if one subcompaction owns a hot key range and the others finish early.

The cost model should estimate overlap from file metadata. Two input files that share key ranges will produce more merge comparisons and more output than two files that are disjoint. A compaction that merges many files with little overlap pays iterator and memory overhead without consolidating much data. A compaction that merges few files with heavy overlap may reduce read amplification but rewrite the same keys repeatedly. The scheduler can approximate overlap by comparing the smallest and largest keys of candidate files and by using per-file key-range histograms when available. The estimate does not need to be exact. It needs to rank jobs by the debt they retire per unit of resource consumed.

The model should also account for output file size. Subcompactions that are too narrow produce small output files. Small files increase the number of runs at the next level, which raises read amplification and can increase future fan-in because a single file from the upper level may overlap many small files below. The scheduler should therefore enforce a minimum subcompaction range that can produce an output file near the target file size. This minimum is a function of the level's target file size and the expected density of live keys. If the range is too sparse, the subcompaction may still be worth running, but it should not be split further.

Resource consumption is multi-dimensional. A compaction consumes read bandwidth, write bandwidth, CPU for compression, memory for iterators and merge buffers, file descriptors, and metadata lock time. The scheduler should maintain separate budgets for these resources and admit a job only when all required budgets are available. A job that needs a large output buffer should not start just because a thread is free. A job that writes to a device with limited endurance should not start just because the CPU is idle. The cost model turns the scheduler from a thread dispatcher into a resource allocator.

## Fan-In Limits and Subcompaction Width

Fan-in and subcompaction width multiply. If a compaction merges F input runs and is split into W subcompactions, the engine may need up to F times W active iterators, though some inputs may not overlap every subcompaction. Each iterator holds index blocks, data blocks, and merge state. The memory cost is roughly proportional to F times W times the per-iterator buffer, plus the output buffers. A scheduler that independently maximizes fan-in and width will exhaust memory and trigger allocation failures or forced serialization. The safe approach is to cap the product F times W and to make the cap adaptive to available memory and to the number of concurrent compactions.

Fan-in limits are also a function of level shape. In a leveled tree with size ratio T, a compaction from level i to level i+1 typically selects one file from level i and all overlapping files from level i+1. The expected fan-in is therefore related to T. If T is ten, a fan-in of ten is normal; a fan-in of fifty may indicate that the next level has many small files or that the key range is unusually dense. The scheduler should not impose a single global fan-in limit. It should derive a limit from the level's target size, the target file size, and the observed overlap. When the limit is exceeded, the job can be split by key range instead of merging all inputs in one pass.

Subcompaction width should be chosen to balance skew and overhead. If the input range is uniformly distributed, a width equal to the number of available cores may be reasonable. If the range has hot spots, a static split can leave most workers idle while one worker processes the hot range. The scheduler can mitigate this by splitting the hot range further, but only if the split preserves the merge invariant. It can also use work stealing at the level of output ranges, where a worker that finishes early takes a new range from a queue. Work stealing reduces idle time but increases the number of output files and manifest updates, so it should be bounded by a minimum range size.

A practical rule is to set width from the estimated critical path, not from the thread count. If the largest subcompaction is predicted to take much longer than the others, increasing width does not help until that subcompaction is split. If the largest subcompaction is already near the minimum range size, increasing width may only add overhead. The scheduler should compute a width that makes the maximum subcompaction work comparable across workers, subject to the minimum range and the F times W memory cap.

## Scheduling Policies and Admission Windows

A compaction scheduler needs a policy for ordering and a policy for admission. Ordering decides which job is most valuable. Admission decides whether the system can afford to start it now. The two must be separate because a high-value job can still be a bad idea if it would consume the last flush reserve or exceed the memory budget. Admission windows are a way to express this separation. A job enters the ready queue when it is eligible, but it starts only when its resource vector fits the current window. The window shrinks when flush work is pending, when read latency is high, or when the device queue is saturated. It expands when the system is idle and compaction debt is growing.

Priority classes should reflect the failure mode each job prevents. Stall-prevention compactions keep L0 file count and level size below their triggers. Read-amplification compactions reduce the number of overlapping runs for hot ranges. Space-reclamation compactions drop tombstones and obsolete versions at the bottom level. Background compactions improve shape without an immediate trigger. Each class needs a weight and a maximum deferral. The deferral bound prevents a low-priority class from being starved by a workload that always produces urgent work. It also prevents the scheduler from ignoring space reclamation until the disk is full.

Range-aware scheduling is often more effective than level-wide FIFO. If the workload has hot key ranges, the scheduler can prioritize compactions that cover those ranges, because they reduce read amplification where reads actually occur. If the workload is uniform, level-wide ordering by urgency is sufficient. Range awareness requires the scheduler to track access statistics or at least to use file metadata to identify ranges with many overlapping runs. It also requires coordination so that two compactions do not reserve overlapping ranges and duplicate work. A range reservation table can enforce this: a job reserves its input range and output level, and other jobs cannot start until the reservation is released or until they choose a disjoint range.

Backpressure should feed into admission, not into priority alone. When the device is saturated, the scheduler should reduce the number of concurrent compactions and prefer jobs with higher debt reduction per byte written. When CPU is saturated by compression, it should prefer jobs that can use lighter compression or that merge fewer bytes. When memory is tight, it should reduce fan-in and width before it reduces the number of jobs, because a single high-fan-in job can be more memory-hungry than several small ones. The control loop should be explicit and measurable, with hysteresis to avoid oscillation.

## Write Amplification Economics Under Concurrency

Parallelism does not change the bytes that a given compaction must read and write. It changes which compactions run, when they run, and how their outputs are shaped. That is where write amplification economics enter. If concurrency causes the scheduler to pick overlapping inputs, two jobs may rewrite the same data, and the second rewrite is pure waste. If concurrency causes subcompactions to emit many small files, future compactions may need higher fan-in to merge them, which increases write amplification. If concurrency delays a bottom-level compaction that would have dropped obsolete data, the engine may rewrite that data again at an upper level before it is finally discarded.

The marginal cost of an additional concurrent compaction is therefore not zero even when the device has spare bandwidth. The marginal benefit is the reduction in expected future write amplification or the reduction in stall risk. A scheduler should start another compaction only when that benefit exceeds the marginal cost. This is an economic decision, not a mechanical one. The cost model from the previous section provides the prices: bytes read, bytes written, memory, CPU, and lock time. The benefit model provides the demand: stall probability, read-amplification reduction, and space reclamation. The scheduler's job is to clear the highest-value debt at the lowest resource price.

Fan-in limits and subcompaction width are the main levers for controlling this economics. Higher fan-in can reduce future rewrites by consolidating more data in one pass, but it raises memory and critical path. Higher width can reduce latency for a large job, but it can fragment outputs and increase metadata overhead. The scheduler should treat both as variables in an optimization, not as constants. It should also measure the realized write amplification after the fact, because the best model is still an approximation. A feedback loop that compares predicted and actual bytes written can recalibrate the overlap estimates and the minimum range size.

The goal is not to eliminate write amplification. That is impossible in an LSM tree that must reorganize data. The goal is to avoid paying for the same data more than once when a different schedule would have retired the debt in one pass. Parallel compaction is valuable when it shortens the critical path without increasing the total bytes rewritten or the number of future merges. It is harmful when it turns one large, well-shaped merge into several small, overlapping ones. The scheduler is the mechanism that decides which of those outcomes the workload gets.

## Coordinating Flush and Compaction: The Shared Thread Pool

Flush and compaction are not independent workloads. They share the same thread pool, the same page cache, the same I/O queues, and often the same compression and checksum pipelines. A scheduler that treats compaction as the only important background work will eventually starve flush, and a starved flush is a write stall. The memtable fills, foreground writes block, and the system loses the sequential-write advantage that made the LSM tree attractive in the first place. Flush must therefore have a reserved capacity that compaction cannot consume.

The simplest way to enforce this is to separate flush and compaction into distinct queues with different priorities, but to admit work from both into a shared worker pool. Flush jobs are typically small, predictable, and latency-critical. They read a memtable and write one or more sorted tables. Compaction jobs are larger, more variable, and throughput-critical. The scheduler should admit flush work immediately when a memtable becomes immutable, even if that means preempting or delaying a compaction. Preemption is rarely possible mid-merge, so the practical approach is to reserve a fraction of worker threads or a fraction of the I/O budget for flush. If flush work is pending, compaction admission should shrink until the flush queue is drained.

The interaction with L0 is where this coordination becomes delicate. Flush produces L0 files. If flush runs faster than L0 compaction can drain, the L0 file count rises, read amplification increases, and the engine approaches the write-stall trigger. If the scheduler throttles flush to protect compaction, memtables accumulate and writes stall sooner. The control loop must therefore balance flush rate against L0 compaction capacity. One effective policy is to monitor the number of immutable memtables and the L0 file count together. When both are low, compaction can use most of the background capacity. When either is high, the scheduler should prioritize the work that reduces the corresponding trigger: flush for immutable memtables, L0-to-L1 compaction for L0 files.

Flush parallelism is another dimension. A single memtable flush is usually single-threaded because it reads one immutable memtable and writes sorted runs. But multiple immutable memtables can flush concurrently if the engine allows it. That concurrency can help drain a backlog of memtables, but it also competes with compaction for write bandwidth and output file descriptors. The scheduler should cap the number of concurrent flushes based on the device's ability to absorb sequential writes and on the memory available for flush buffers. Too many concurrent flushes can fragment L0 with many small files, which increases the fan-in required for the next L0 compaction and raises write amplification.

A useful abstraction is a global I/O budget expressed in outstanding bytes or requests. Flush and compaction both draw from this budget. Flush has a higher priority, but it should not be allowed to consume the entire budget if that would leave compaction unable to make progress. The scheduler can assign a minimum share to each class and allow the shares to shift based on backlog. For example, if the L0 file count is below its trigger, flush can use up to 80% of the budget. If L0 is near its trigger, compaction gets a larger share. The shares should change gradually to avoid oscillation, and the scheduler should measure the actual completion rate of each class rather than assuming that admission equals progress.

Finally, flush and compaction share the manifest and version-set update path. Every flush adds a new L0 file to the manifest. Every compaction removes input files and adds output files. These updates are serialized through a lock or a single-threaded metadata thread. If flush and compaction both try to update the manifest frequently, the metadata path can become a bottleneck. The scheduler should batch manifest updates where possible and avoid starting compactions that will produce many small output files, because each output file adds metadata work. The cost model should include manifest update cost as a resource, not just bytes read and written.

## Level-Specific Scheduling: L0 Is Not Like the Others

A leveled LSM tree has levels with different structural properties, and those differences should be reflected in the scheduler. L0 is the most distinctive. L0 files are typically not range-partitioned relative to each other. They are sorted internally but can overlap arbitrarily. A point lookup must check every L0 file whose range contains the key, which is why L0 file count is a direct contributor to read amplification. L0 also has a hard file-count trigger in many engines: when the count exceeds a threshold, foreground writes stall until compaction reduces it. L0 compactions are therefore urgent in a way that lower-level compactions are not.

The urgency of L0 changes the scheduler's priorities. A compaction that moves data from L0 to L1 should be preferred over a compaction that rewrites cold data at the bottom level, even if the latter has more bytes. The scheduler should maintain a separate queue for L0 compactions and admit them as soon as resources allow, subject to the flush reserve. It should also limit the number of concurrent L0 compactions. If two L0 compactions run at once, they both write to L1 and may compete for overlapping key ranges. Since L0 files overlap, two L0 compactions can easily select inputs that share key ranges, leading to duplicate work or lock contention. A per-level concurrency limit of one or two for L0 is common, with the exact number depending on the device's queue depth and the engine's ability to coordinate ranges.

Subcompaction of L0 compactions is possible but constrained. To split an L0 compaction by key range, the subcompaction for a given range must merge all L0 files that overlap that range. If L0 has many files with wide overlapping ranges, each subcompaction may need to read most of L0. That increases memory for iterators and may not reduce the critical path much because the input set is not partitioned. In practice, L0 compactions are often run as a single job or split into a small number of subcompactions only when the L0 files have relatively narrow ranges. The scheduler should estimate the overlap among L0 files before deciding to split. If overlap is high, a single-threaded L0 compaction may be more efficient than several subcompactions that each read the same files.

Lower levels are different. L1 and below are usually maintained as non-overlapping sorted runs. A compaction from level i to level i+1 selects one or a few files from level i and all overlapping files from level i+1. Because the inputs are range-partitioned, subcompaction by key range is natural. The scheduler can split the key range into disjoint intervals and assign each to a worker without violating the merge invariant, as long as the boundary respects user-key version chains and range tombstones. This makes lower-level compactions good candidates for intra-compaction parallelism. The scheduler can use wider subcompaction widths at lower levels, where the data is colder and the jobs are larger.

Bottom-level compactions have their own character. They often involve the largest amount of data and are the place where tombstones and obsolete versions can finally be dropped. They are low-priority in the sense that they do not prevent write stalls directly, but they are critical for space reclamation. If the scheduler ignores them, disk usage grows and eventually forces emergency compactions. The scheduler should assign bottom-level compactions a lower priority than L0 or read-amplification compactions, but with a maximum deferral budget. When the deferral budget expires, the bottom-level compaction is promoted. The budget can be expressed in terms of bytes of obsolete data accumulated or in terms of disk space headroom. When headroom falls below a threshold, the priority of space-reclamation compactions should rise sharply.

Per-level concurrency limits should also reflect the write amplification economics. Running many compactions at the same level can increase contention on the next level's files and cause overlapping rewrites. A common pattern is to allow more concurrency at higher levels (L0, L1) where jobs are smaller and more urgent, and less concurrency at lower levels where jobs are large and write amplification is already high. But this is not universal. On a device with deep queues and abundant CPU, lower-level concurrency can improve throughput if the key ranges are disjoint. The scheduler should use range reservations to ensure that concurrent compactions at the same level do not overlap in key space. If they do, one should wait.

## Adaptive Fan-In and Dynamic Subcompaction Width

Static fan-in limits and fixed subcompaction widths are easy to implement but hard to tune. A fan-in of ten may be optimal for one workload and disastrous for another. A subcompaction width of eight may reduce latency for a uniform key distribution but leave half the workers idle for a skewed one. The scheduler should treat both as dynamic variables that respond to observed conditions. The goal is not to find a single best value but to adjust continuously as the workload, device state, and compaction debt change.

Adaptive fan-in starts with a cost model that estimates the benefit of merging additional inputs. The benefit is the reduction in future write amplification: if merging an extra input now allows the engine to avoid rewriting that data in a later compaction, the extra fan-in is worthwhile. The cost is the additional memory for iterators, the longer critical path, and the increased risk of overlapping with other compactions. The scheduler can estimate overlap from file metadata. If the candidate inputs have little overlap, adding more inputs may not reduce future work much, so fan-in should be kept low. If overlap is high, a larger fan-in can consolidate versions and tombstones in one pass, reducing future rewrites. The scheduler can also use the level's size ratio: when a level is far below its target size, a large fan-in may be premature because the data will be rewritten again soon. When the level is near its target, a larger fan-in may be necessary to make durable progress.

A practical adaptive policy is to set a base fan-in from the level's size ratio and then adjust it based on the observed write amplification. If the measured write amplification for a level is above a threshold, the scheduler can increase the maximum fan-in for that level, up to a memory cap. If the write amplification is low and the device is saturated, it can decrease the fan-in to reduce memory pressure and improve responsiveness. The adjustments should be small and infrequent, with hysteresis to avoid oscillation. The scheduler should also track the realized overlap among inputs; if the estimate was wrong, it can recalibrate the overlap model.

Dynamic subcompaction width is similar. The scheduler should choose a width that balances the critical path across workers. If the estimated work per range is uniform, a width equal to the number of available cores may be appropriate. If the work is skewed, the scheduler should split the hot ranges further and merge the cold ranges into fewer subcompactions. This requires a range partitioning algorithm that can estimate the density of each range from file metadata or from a sample of keys. The algorithm should respect the minimum range size, which is derived from the target output file size. If a range is too small, merging it with a neighbor is better than creating a tiny output file.

Work stealing can complement static width. The scheduler can divide the compaction into more ranges than there are workers and let workers pull ranges from a queue. This naturally balances skew and reduces idle time. The cost is more output files and more manifest updates. To control that cost, the scheduler should set a minimum range size and a maximum number of output files per compaction. When the queue is empty, workers can help with other compactions, but only if those compactions have disjoint key ranges. A global range reservation table can prevent two compactions from working on overlapping ranges at the same time.

Adaptation should also consider the device. On a device with limited endurance, the scheduler should favor lower fan-in and narrower subcompactions to reduce write bursts, even if that increases the critical path. On a device with deep queues and high endurance, wider subcompactions and higher fan-in can improve throughput. The scheduler can read device characteristics at startup or infer them from observed latency and queue depth. The control loop should be explicit: measure, predict, adjust, and verify. The metrics that matter include compaction bytes read and written per level, fan-in distribution, subcompaction width distribution, memory usage of compaction iterators, manifest update latency, and the frequency of write stalls. By closing the loop on these metrics, the scheduler can avoid the twin failures of a static policy: over-compacting when the system is already saturated, and under-compacting when debt is accumulating.

## Instrumentation for a Scheduler That Must Be Auditable

A parallel compaction scheduler cannot be tuned by intuition alone. The interactions between fan-in, subcompaction width, flush pressure, and device saturation are too nonlinear. The engine needs instrumentation that explains not only what happened but why the scheduler made each decision. Without that explanation, operators see write stalls and high write amplification but cannot tell whether the cause is an aggressive priority policy, an overly wide subcompaction split, a flush reserve that is too small, or a workload whose key distribution defeats the overlap estimator.

The first layer of instrumentation is per-job accounting. Every compaction job should record its level transition, input file count, input bytes, output bytes, fan-in, subcompaction width, number of output files, overlap estimate, actual overlap, and the resource budgets it consumed. The job should also record its wait time in the ready queue, its admission delay, and the reason it was admitted or rejected. A job that waits a long time because the flush reserve was active is different from a job that waits because its range conflicted with a running compaction. The scheduler should distinguish these causes in counters and logs.

The second layer is per-level and per-class aggregation. The engine should expose compaction bytes read and written per level, the distribution of fan-in and width, the number of compactions by priority class, the number of deferrals that hit their maximum, and the frequency of write stalls attributed to each level. These aggregates reveal whether the scheduler is consistently favoring L0 at the expense of bottom-level space reclamation, or whether lower-level compactions are being split so finely that output files are below the target size. They also show whether the adaptive fan-in policy is actually changing behavior or merely oscillating around a default.

The third layer is critical-path tracing. For each logical compaction, the scheduler should record the predicted work per subcompaction, the actual work per subcompaction, the start and end times, and the time spent waiting on shared resources such as the manifest lock or the version-set update. This trace makes skew visible. If one subcompaction takes three times longer than the others, the scheduler can adjust the range partitioning or lower the width for similar jobs. If all subcompactions finish quickly but the logical compaction takes much longer, the bottleneck is shared serialization, not parallel work.

Prediction error is a first-class metric. The scheduler should compare predicted bytes read, bytes written, and overlap against actual values. A persistent overestimate of overlap may cause the scheduler to choose larger fan-in than necessary, increasing memory pressure. A persistent underestimate may cause it to split ranges that should have been merged. The feedback loop should recalibrate the overlap model and the minimum range size using these errors, with smoothing to avoid reacting to a single outlier.

Finally, instrumentation must be cheap enough to run continuously. High-cardinality labels per key range can overwhelm a metrics system. The scheduler should sample ranges, aggregate by level and class, and retain detailed traces only for slow or anomalous compactions. The goal is not a complete record of every merge comparison. The goal is enough evidence to answer whether the scheduler is retiring the right debt at an acceptable resource price.

## Scheduler Architecture: Queues, Reservations, and Budgets

A production scheduler is best structured as a set of cooperating components rather than a single priority queue. The debt estimator observes level sizes, file counts, pending compaction bytes, read amplification, and space headroom. It converts those observations into urgency scores for each candidate compaction. The candidate generator selects input files according to the level's compaction policy and the merge invariant. The priority queue orders candidates by urgency and class. The resource ledger tracks available threads, memory, file descriptors, I/O budget, and manifest capacity. The range reservation table prevents overlapping jobs from running concurrently. The admission controller decides whether a selected job can start now. The executor runs the job, possibly as multiple subcompactions. The manifest committer atomically installs the outputs and removes the inputs.

Separating these components makes the scheduler testable. The debt estimator can be exercised with synthetic level shapes. The candidate generator can be validated against the merge invariant. The admission controller can be simulated with different resource budgets. The range reservation table can be checked for deadlock and starvation. A monolithic scheduler that combines all of these concerns in one loop is harder to reason about and harder to instrument.

The priority queue should support multiple classes, not a single global order. Stall-prevention compactions, read-amplification compactions, space-reclamation compactions, and background shape improvements have different value functions. Each class should have a weight and a maximum deferral. Priority aging can promote jobs that have waited too long, but aging should be based on progress toward the class's objective rather than wall-clock time alone. A bottom-level compaction that has waited an hour may still be low priority if disk headroom is ample, while one that has waited ten minutes with headroom shrinking should be promoted quickly.

The resource ledger is the scheduler's accounting system. It should track at least four budgets: worker slots, compaction memory, output file descriptors, and I/O bytes in flight. A job reserves these resources before it starts and releases them when its outputs are committed. Reservations should be conservative. If a job is split into subcompactions, the ledger should reserve for the maximum concurrent width, not the average. If the reservation cannot be satisfied, the job remains ready but not admitted. This prevents the common failure where several large compactions start together, exhaust memory, and force the engine to abort or serialize them after they have already read input data.

The range reservation table is the concurrency control mechanism for key space. Each running compaction reserves its input range and output level. A new job that overlaps an existing reservation must either wait or choose a disjoint range. The table should support interval insertion, deletion, and conflict queries efficiently. It should also prevent deadlock by imposing a global order on reservations, such as by level and then by smallest key. Deadlock is possible if one job holds a range and waits for a resource held by another job that waits for the first job's range. A strict ordering or a timeout with rollback avoids this.

The executor should treat subcompactions as first-class tasks. Each subcompaction has its own input iterators, output writer, and merge state. The executor should bound the number of concurrent subcompactions per logical job and across all jobs. Work stealing can be used within a logical compaction to balance skew, but it should not allow a worker to join a different logical compaction unless the range reservation table confirms that the ranges are disjoint. Uncontrolled work stealing can turn a well-partitioned schedule into a set of overlapping merges that duplicate reads and produce conflicting outputs.

The manifest committer is often the least parallel part of the system, and it should be designed accordingly. Subcompactions may finish at different times, but their outputs should not become visible until the logical compaction is complete and the version edit is atomic. The committer can batch output file additions and input file deletions into one manifest update. It should also handle crash recovery: if the process dies after some subcompactions have written files but before the manifest commit, those files are orphans. The scheduler should record enough state to clean them up on restart without exposing them to readers.

## Read Path Feedback and Cache-Aware Compaction

Compaction and reads share the block cache, the page cache, and the storage device. A compaction that reads cold input files can evict hot data blocks, and a compaction that writes large output files can pollute the cache with data that will not be read soon. The scheduler cannot ignore the read path, because the purpose of compaction is ultimately to make reads cheaper. A schedule that reduces read amplification in metadata but evicts the working set can still increase read latency.

The engine should feed read statistics back to the scheduler at range granularity. If a range has many overlapping runs and a high lookup rate, compaction of that range has high value. If a range is cold, compaction can be deferred unless it is needed for space reclamation or level shape. The scheduler can use per-range access counters or a sampled sketch of recent lookups. It does not need exact counts. It needs a ranking that distinguishes hot ranges from cold ones. The debt estimator can then combine read amplification with access frequency to produce a read-impact score.

Cache-aware admission can further reduce interference. Compaction reads can use a lower cache priority or direct I/O where the engine supports it, so they do not displace hot blocks. Compaction writes can bypass the block cache because output files are unlikely to be read immediately. This reduces cache pollution but may increase I/O latency if the device benefits from write-back caching. The right choice depends on the storage stack. The scheduler should treat cache priority as a resource dimension, not as an afterthought.

Bloom filters and index blocks also interact with compaction. A compaction rewrites these structures for its output files. If subcompactions produce many small files, the engine creates many small filters and indexes, which increases memory overhead and read cost. The scheduler's minimum range size should therefore be derived from the target file size and the expected filter density. If a range cannot produce a file large enough to amortize its filter and index, it should be merged with a neighbor rather than split.

Read path feedback can also reveal when compaction is making things worse. If read latency rises during a compaction despite a decrease in overlapping runs, the cause may be device contention or cache eviction. The scheduler should reduce compaction concurrency or change its cache hints. This is a control loop, not a one-time policy. The goal is to keep read amplification and read latency moving in the same direction.

## Multi-Tenant and QoS-Aware Compaction Scheduling

Many LSM engines host multiple tenants, column families, or tables in one process. Each tenant has its own write rate, key distribution, read pattern, and service-level objective. A global compaction scheduler that treats all pending work as one pool can let a single noisy tenant consume the background capacity and degrade every other tenant. The scheduler needs per-tenant debt accounting and a fairness policy that prevents starvation without sacrificing global throughput.

Weighted fair queueing is a natural starting point. Each tenant receives a weight based on its provisioned capacity or its service tier. The scheduler selects compactions from tenant queues in proportion to their weights, subject to resource budgets. A tenant that is far behind its compaction debt can receive a temporary boost, but the boost should be bounded so it does not starve others. Deficit round robin or a similar algorithm can provide fairness with low overhead.

Per-tenant isolation also requires per-tenant admission limits. One tenant's L0 backlog should not force another tenant's flush to wait. If the engine uses separate memtables and L0 files per tenant, the scheduler can reserve flush capacity per tenant and cap compaction concurrency per tenant. If the engine shares a single memtable, the isolation problem moves to the write path, and the scheduler can only prioritize flush and compaction work after the fact. The design should make the isolation boundary explicit.

Service-level objectives should influence priority. A tenant with a strict tail-latency SLO may need read-amplification compactions to run sooner than a tenant with a throughput-oriented batch workload. A tenant with a low write quota may tolerate higher write amplification to reduce space usage. The scheduler can translate these objectives into weights and deferral budgets. It should also measure per-tenant write stalls and read latency, because a global aggregate can hide a single tenant's pain.

Global resource budgets still apply. A tenant cannot reserve more compaction memory than the process has available, and the sum of per-tenant reservations cannot exceed the global ledger. The admission controller should check both tenant and global budgets. If a tenant's job cannot be admitted because of a global shortage, the scheduler should record that cause so operators can distinguish tenant-level unfairness from process-level saturation.

## Disaggregated and Remote Storage Considerations

When LSM storage runs on disaggregated or remote storage, compaction economics change. Reads and writes may traverse a network, incur request costs, and have much higher latency than local block devices. The scheduler must account for bytes and requests, not just bytes. A subcompaction that produces many small objects can be cheap in bytes but expensive in request count and metadata operations. A high-fan-in compaction that reads many remote objects can be expensive in network round trips even if the total bytes are moderate.

Remote storage favors fewer, larger output files. The minimum subcompaction range should be larger than on local storage, because small files increase request amplification for future reads and compactions. The scheduler should also consider object storage class. Compaction between hot and cold tiers may be driven by access patterns rather than level size alone. A range that is rarely read may be compacted into a cold tier with a larger fan-in to reduce future request costs, while a hot range may be kept in a local cache tier with smaller, more frequent compactions.

Network bandwidth and request concurrency are shared resources. The resource ledger should include outstanding remote requests and network bytes in flight. Admission control should limit compaction concurrency when the network is saturated, even if local CPU and memory are available. Tail latency on remote storage can be highly variable, so the scheduler should use timeouts and retries carefully. A compaction that times out and retries may duplicate work and increase write amplification. The job should be idempotent at the output file level, and the manifest commit should be atomic.

Local caching can mitigate remote latency but adds another resource to schedule. If compaction reads are cached, they may evict data needed by foreground reads. If compaction writes are cached, they may delay durability. The scheduler should coordinate with the cache manager to reserve capacity for compaction and to avoid polluting hot read cache. The cost model should include cache occupancy as a resource, not just bytes read and written.

## Failure Modes and Safety Invariants

Parallel compaction introduces failure modes that do not exist in a single-threaded merge. The most serious is a violation of the merge invariant. If subcompactions split a user key's version chain, the engine can resurrect stale data or drop a live record. If a range tombstone is split incorrectly, deleted data can reappear. If output files overlap in key space, later compactions may produce incorrect results or read amplification may spike unexpectedly. These are correctness failures, not performance regressions, and they must be prevented by construction rather than detected by luck.

The scheduler should validate boundaries before starting subcompactions. It should confirm that every input iterator is positioned at the subcompaction's start key and that no user key crosses the boundary. It should also confirm that range tombstones are either wholly contained or replicated according to the engine's policy. Validation can be expensive if done for every job, so it can be sampled or performed only when the boundary is derived from file metadata rather than from a known key. The merge layer should expose a boundary-checking function that the scheduler can call.

Manifest atomicity is another invariant. A logical compaction must appear as a single version edit, even if it produced multiple output files through subcompactions. If the process crashes after some outputs are written but before the edit is committed, those outputs must not be visible. The scheduler should assign a unique job identifier to every logical compaction and record it in output file metadata. On restart, the engine can identify orphan files and delete them. The manifest commit should be the linearization point for the compaction.

Resource exhaustion is a performance failure mode that can become a correctness issue if it causes the engine to abort a compaction after partially writing outputs. The scheduler should reserve resources before starting a job and should not start a job that cannot complete within its reservation. If the device fails or slows down, the job may still stall, but it should not be forced to abort because memory was overcommitted. Admission control should be conservative under uncertainty.

Deadlock and starvation are scheduling failures. Range reservations can deadlock if jobs acquire ranges in different orders. Priority policies can starve a class if urgent work never stops arriving. The scheduler should use timeouts, ordered acquisition, and maximum deferral budgets to prevent these. It should also have a circuit breaker that reduces concurrency when the system is overloaded, rather than continuing to admit work that cannot make progress.

## Verification and Testing of Parallel Compaction

Testing a parallel compaction scheduler requires more than throughput benchmarks. The engine needs deterministic tests for the merge invariant, property-based tests for subcompaction boundaries, and fault-injection tests for crash recovery. A useful approach is to build a model of the LSM tree that can generate random keys, versions, tombstones, and snapshots, then compare the output of a parallel compaction against a single-threaded reference merge. The comparison should check not only the final visible value for each key but also the set of retained versions for active snapshots.

Boundary tests should include adversarial cases: a user key with versions spread across many input files, a range tombstone that spans several candidate subcompaction ranges, a snapshot that pins an old version, and a key distribution with extreme skew. The scheduler should be forced to split at boundaries that are close to these cases. The test should verify that the merge invariant holds and that no tombstone is dropped while an older version remains visible.

Fault injection should cover crashes at every stage of a logical compaction: after reading inputs, after writing some subcompaction outputs, after writing all outputs but before the manifest commit, and during the manifest commit. The recovery path should remove orphan files, restore the previous version set, and allow the compaction to be retried. The test should also verify that readers never observe a partially committed compaction.

Performance tests should measure write amplification, read amplification, and tail latency under different fan-in limits and subcompaction widths. They should include workloads with uniform keys, skewed keys, wide range tombstones, and long-running snapshots. The results should be compared against a single-threaded baseline and against a naive parallel scheduler that ignores resource budgets. The goal is not to prove that one policy is always best, but to show that the scheduler's decisions are explainable and that its failure modes are bounded.

These tests are not a substitute for production telemetry, but they are the only way to know whether the scheduler's invariants hold before a workload finds the edge case. A scheduler that passes a throughput benchmark but fails a boundary test is not a faster LSM tree. It is a data corruption incident waiting for a compaction to run at the wrong moment.
