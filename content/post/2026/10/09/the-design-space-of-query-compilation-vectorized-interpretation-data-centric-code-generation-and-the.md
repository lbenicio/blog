Analytical query execution looks like a solved problem from a distance. A hash join is a hash join; a group-by is a hash table with a probe loop. But the distance between a textbook algorithm and a machine that runs it at memory bandwidth is filled with a design space that has occupied database systems research for three decades. The central question is deceptively simple: **what is the unit of execution?**

The answer determines almost everything else — how operators compose, where intermediate results live, how much memory a query touches, how well the CPU's front end predicts branches, and how much the engine can exploit data parallelism. Two families of answers dominate: *interpretation*, where the engine walks an operator tree and calls into per-operator code, and *compilation*, where the engine emits specialized code for the specific query. Within interpretation there is a further split between tuple-at-a-time and vectorized (batch) processing. Within compilation there is a split between operator-at-a-time code generation and data-centric, pipeline-oriented generation.

This article maps that design space. It is not a survey of who is fastest; benchmark claims in this area are notoriously sensitive to data distributions, hardware generations, and whether the comparison was run by the authors of one of the systems. It is instead an attempt to describe the *mechanisms*: what each approach removes from the critical path, what it adds, and where the trade-offs actually bite. The goal is to give engineers enough of a mental model to reason about their own engine, or to evaluate the claims of someone else's.

## The Iterator Model and Its Cost Structure

The dominant execution model in relational engines for the past thirty years is the iterator model, often called the Volcano model. Every physical operator implements a small interface — typically `open()`, `next()`, and `close()` — and `next()` returns one tuple at a time. A query plan is a tree of operators; the root pulls tuples from its children, which pull from theirs.

The model's virtues are real. Operators compose without knowing anything about each other; a new operator is a new class implementing the interface. Pipelining falls out naturally: a filter can pass a tuple to its parent before the scan beneath it has finished. Memory consumption is bounded by the operators that must materialize (sorts, hash-table builds) rather than by the whole intermediate result. The plan is a tree of polymorphic objects, which makes it easy to build, print, optimize, and instrument.

The cost structure is equally real, and it is dominated by *per-tuple overhead*. Each `next()` call is a virtual (indirect) function call. For a simple scan-filter-project pipeline, a single output tuple may traverse four or five operators, each with a call, a return, and some state update. Modern CPUs execute such a call in a handful of cycles when the target is predictable, but an indirect branch is exactly the kind of control flow that branch predictors handle poorly when the operator tree is deep and call sites are shared. The result is a pipeline that issues perhaps one useful instruction for every several cycles of overhead, with poor instruction-level parallelism because each tuple's processing depends on the previous tuple's completion through the same call chain.

There is a second cost: tuple-at-a-time execution forces each operator to be written as a general loop over an abstract tuple representation, which usually means pointer chasing into a row-oriented record. That is close to the worst possible access pattern for a modern cache hierarchy. The CPU can prefetch sequential streams; it cannot prefetch through a linked structure it has not yet decoded.

None of this was a mistake. The iterator model was designed for an era when I/O dominated and when extensibility mattered more than instruction efficiency. When a disk seek costs milliseconds, a few hundred nanoseconds of call overhead per tuple is noise. The model persisted because it is genuinely good at the things it was designed for — composability, streaming, bounded memory — and because the alternatives require giving up some of those properties.

## Vectorized Interpretation: Amortizing the Abstraction

The first systematic attack on per-tuple overhead was to stop processing one tuple at a time. In a vectorized (batch) engine, each `next()` call returns a *batch* of values — typically on the order of a thousand — and operators are implemented as tight loops over arrays of primitive types rather than over tuples.

The mechanism is straightforward once you see it. If a filter processes 1024 values per call, the virtual call overhead is amortized by a factor of 1024. More importantly, the inner loop is now a loop over a contiguous array of integers or doubles, which the compiler can unroll, the hardware can prefetch, and the vector unit can process several elements at a time. Selection is represented by a *selection vector* — an array of indices of surviving rows — rather than by copying tuples, so filtering does not move data.

The MonetDB/X100 line of work is the canonical articulation of this design, and the reasoning behind it is worth stating precisely, because it is often summarized as "batch size makes it fast." The real argument is about *where the data lives during a query*. In a tuple-at-a-time engine, each operator's intermediate result is a tuple somewhere in memory, and performance is bounded by the cost of materializing and re-reading those tuples. In a vectorized engine, intermediates are arrays of fixed-width values that fit in L2 or L3 cache, and operator boundaries are crossed with a pointer and a count. The engine is transformed from a pointer-chasing machine into a streaming machine.

The limits of vectorization are equally instructive. First, vectorization does not remove materialization; it makes materialization cheap. Each operator still writes its output batch to memory (or to a cache-resident buffer) and the next operator reads it. That is fine when batches are cache-resident, but it means the engine still pays a store and a load per value per operator boundary. Second, vectorized operators are still *operators*: the engine evaluates a predicate against a column, then the next operator evaluates another predicate, and so on, with no opportunity for the compiler to see that two predicates are mutually exclusive or that a constant column makes a branch unreachable. Third, the batch is a fixed abstraction; complex operators — a hash join probe with a long collision chain, a sort with variable-length keys — do not always decompose into clean loops over fixed-width arrays, and the code that handles the awkward cases reintroduces the branching that vectorization was meant to remove.

Vectorized engines also inherit the abstraction cost of *expression evaluation*. A predicate such as `a + b * c > 100` is typically evaluated by walking a small expression tree or interpreting a bytecode program per batch, which is far cheaper than per tuple but still not free. Every value in the expression must be fetched from a column, the operation must be dispatched on its type, and the result must be written to a temporary vector.

## Data-Centric Compilation: Pipelines, Not Operators

The compilation approach asks a different question: instead of making the interpreter cheaper, why not eliminate it? If the query plan is known, the engine can generate code specialized to that plan — predicates with constants folded in, types resolved, operator boundaries erased.

The naive form of this idea is *operator-at-a-time code generation*: for each physical operator, emit a loop that reads from its input and writes to a materialized output. This removes virtual dispatch and gives the compiler visibility into each operator's inner loop, but it does not remove materialization, and it does not fuse operators. The generated code is a sequence of loops over materialized columns, structurally similar to what a vectorized engine does — with the added cost of compiling the loops.

The more interesting form is *data-centric* compilation, which starts from the observation that the natural code-generation unit is not the operator but the **pipeline**. A pipeline is a maximal chain of operators that can pass tuples from producer to consumer without an intervening materialization point. The materialization points — pipeline breakers — are things like sort, hash-table build, and any operator that must consume its entire input before producing output. Between breakers, tuples can flow from a scan through filters and projections into, say, a hash-table build without ever being written to memory.

In the data-centric model, the generated code for a pipeline is a set of *produce* and *consume* functions. A produce function scans its input and calls a consume function for each tuple; a consume function is the body of the next operator in the pipeline. Tuples are passed as arguments — in registers, ideally — rather than through memory. The compiler can then inline the consume call into the produce loop, keep the tuple's fields in registers across the whole pipeline, and perform optimizations that are impossible when operators are separate functions: constant propagation of predicates, elimination of dead columns, strength reduction of arithmetic, and branch pruning when a predicate is statically known to be true or false for a given pipeline stage.

This is the essential difference between compiling operators and compiling pipelines. The former produces code that looks like a hand-written vectorized operator; the latter produces code that looks like a hand-written query. The HyPer line of work is the clearest articulation of the data-centric model, and the term *hyper-pipelining* describes the resulting execution style, in which a tuple's journey through a pipeline is a single straight-line code path with no materialization and no dispatch.

What compilation buys, concretely:

- **Dispatch elimination.** No virtual calls in the hot path; the call graph is static and inlinable.
- **Type and constant specialization.** A comparison between two `int64` columns becomes a machine comparison; a predicate against a literal becomes a constant test, and if the constant makes the predicate always true, the branch disappears.
- **Cross-operator optimization.** The compiler sees the whole pipeline, so it can eliminate redundant computation, hoist loop-invariant work, and fuse loops that an interpreter would run separately.
- **Register-resident tuples.** Intermediate values live in registers rather than in a materialized buffer, which removes both the store and the load.

What it costs:

- **Compilation latency.** Generating and optimizing code takes time, and for short queries that time can exceed the execution time. This is the central practical objection to compilation, and it drives a great deal of engineering: caching generated code by plan shape, using cheap code generators for simple queries, and falling back to interpretation when the plan is not worth compiling.
- **Code size and instruction-cache pressure.** A compiled query is a large, specialized function. If the working set of compiled code exceeds the instruction cache, the engine trades dispatch overhead for fetch stalls.
- **Complexity of the code generator.** Expressing a hash join's probe loop, a sort's merge, or a window function's frame computation as generated code is substantially harder than writing it once as an operator. Many engines therefore compile only the "easy" part of the plan and call out to precompiled functions for the rest — which is a hybrid, not a pure design.
- **Debugging and portability.** A generated function is harder to inspect than an operator tree, and code generation must target whatever execution substrate the engine supports: LLVM IR, C source, or a custom bytecode.

These trade-offs explain why the vectorization-versus-compilation debate has never resolved into a winner. The next part of this article turns to the mechanics of code generation itself — how a plan becomes a function, how the compilation pipeline is kept short enough to be worth it, and how parallel execution fragments the very pipelines that compilation tries to fuse.

## From Plan to Function: The Mechanics of Code Generation

A query compiler is a compiler with an unusually short life. It sees one program—the query plan—and must produce a function that runs for milliseconds to seconds before being discarded or cached. The first job is to decide what the function is. In a data-centric compiler, the answer is a set of functions, one per pipeline, plus the materialization points that connect them. The plan is partitioned into pipelines by identifying pipeline breakers: operators that cannot emit output until they have consumed all input. Hash join build, sort, distinct, and any blocking aggregation are the usual breakers. A scan feeding a filter feeding a projection feeding a hash-table build is one pipeline; the probe side is another; the final aggregation is a third.

The decomposition is not merely an implementation detail. It determines where tuples can live in registers and where they must live in memory. Inside a pipeline, the compiler can keep a tuple's fields in virtual registers and pass them as arguments from one consume function to the next. At a pipeline breaker, the tuple must be written into a data structure—a hash table, a sorted run, a partition—and the next pipeline reads it back. The breaker is therefore both a synchronization point and a materialization point. The compiler's job is to make the regions between breakers as long and as straight-line as possible, because every breaker reintroduces the memory traffic that compilation was meant to avoid.

The lowering from plan to code proceeds in stages. First, the plan's expression trees are converted into a typed intermediate representation. Each expression node becomes an operation on values of known types: a column reference becomes a load from a tuple or a vector, a comparison becomes a typed comparison, an arithmetic node becomes an arithmetic instruction. Null handling is made explicit. In a vectorized engine, nulls are often a separate bitmap; in compiled code, they can become a branch or a select, or be eliminated entirely when the compiler can prove a column is non-null. This is one of the places where compilation has a real advantage: nullability is a property of the data, and a specialized function can be generated for the non-null case and a slower path for the general case.

Second, control flow is introduced. Filters become conditional branches or predicated updates to a selection vector. Joins become loops over hash buckets. Aggregations become updates to a hash table keyed by the group-by columns. The compiler must decide how much of this control flow to expose to the optimizer. A generated loop over a hash table with a long collision chain is a data-dependent branch that no compiler can predict; a vectorized probe, by contrast, can process a batch of keys and use a selection vector to defer the collision handling. The best code generators often do both: they generate straight-line code for the common case and call into a precompiled helper for the collision path.

Third, the IR is optimized and lowered to machine code. The choice of substrate matters. LLVM IR gives the query compiler a mature optimizer and a portable backend, but it also imposes compile latency: constructing IR, running passes, and emitting code can take tens of milliseconds, which is too much for an OLTP query and often too much for a short analytical query. A custom bytecode or a direct-to-machine-code emitter can be much faster to compile, at the cost of weaker optimization. Many engines therefore use a tiered approach: interpret the query for the first few executions, and if it is executed often enough, compile it. The threshold is a bet on future reuse, and it is exactly the kind of bet that a query optimizer is already making about plan reuse.

Code caching is the other half of the latency problem. If the same plan shape appears repeatedly—same operators, same types, different constants—the engine can generate code once and patch the constants. This is sometimes called specialization by plan shape. It works well for prepared statements and for dashboards that issue the same query with different parameters. It works less well for ad-hoc queries, where every query is a new shape and the cache is a source of memory pressure rather than a source of speed. The cache key must be precise enough to avoid incorrect reuse and coarse enough to hit often; getting that balance right is an engineering problem with no clean theoretical answer.

## The Cost of Abstraction, Revisited

The phrase 'removing abstraction' sounds like an unqualified good. In practice, every abstraction that a query engine removes from the execution path is replaced by an assumption that the code generator must maintain. The iterator model's next() call is an abstraction that hides the operator's internal state; compiling the operator exposes that state to the rest of the pipeline, which means the compiler must reason about it. The row format is an abstraction that hides column layout; a compiled engine that reads fields directly must know the exact offsets and types, and must generate different code for every combination.

Null handling is a useful case study. In a tuple-at-a-time engine, a null is a flag on a value, and every operator checks it. In a vectorized engine, nulls are a bitmap alongside a column, and operators can often process the bitmap with bitwise operations. In compiled code, the compiler can specialize: if a column is known to be non-null, the null check disappears; if it is nullable, the compiler can generate a branch or a select. The abstraction has not vanished—it has moved from runtime to compile time. The cost is that the compiler must now handle the combinatorial explosion of nullability, type, and encoding. That explosion is why many compiled engines still call into precompiled kernels for complex operations.

String handling is another. Variable-length strings are the bane of vectorized execution because they cannot be stored in a fixed-width array without indirection. A vectorized engine typically represents a string column as a list of offsets plus a character buffer, and operators process offsets and bytes. A compiled engine can inline the offset arithmetic and the byte comparison, but it must also handle dictionary encoding, compression, and collations. If the compiler specializes for a dictionary-encoded column, it can compare codes instead of bytes; if the column is not dictionary-encoded, it must fall back. The abstraction of 'a string column' hides a set of physical representations, and the code generator must either specialize for each or give up and call a generic function.

Branch prediction is a related cost. Vectorization often wins not because it executes fewer instructions but because it executes more predictable ones. A filter that produces a selection vector has a data-dependent branch per value, but the branch is inside a tight loop and the selection vector can be built branchlessly. A compiled pipeline that checks a predicate per tuple has the same data-dependent branch, but it may be spread across a larger code path with more state. The compiler can sometimes convert the branch to a conditional move, but only if the operation is simple and side-effect-free. For complex predicates, the branch remains, and the advantage of compilation shrinks.

SIMD is the mirror image. A vectorized engine can explicitly use SIMD intrinsics or rely on the compiler to auto-vectorize a loop over arrays. A data-centric compiled engine often produces code with complex control flow—hash probes, variable-length loops, early exits—that auto-vectorization cannot handle. To get SIMD in compiled code, the engine must either generate vectorized code deliberately or structure the pipeline so that the compiler can vectorize it. This is one reason why the vectorization-versus-compilation debate is not a clean either/or: a compiled engine that generates vectorized code is a hybrid, and a vectorized engine that compiles its expressions is also a hybrid.

## Parallelism and the Fragmentation of Pipelines

Parallel execution changes the pipeline decomposition in a way that is often underestimated. A single-threaded pipeline is a chain of produce and consume calls; a parallel pipeline is a set of chains that must be synchronized at pipeline breakers and fed with disjoint slices of data. The exchange operator—the operator that repartitions or broadcasts data between threads—is itself a pipeline breaker. It materializes data into buffers, hands those buffers to other threads, and waits for them to be consumed. The abstraction of the exchange hides a great deal of complexity: buffer management, backpressure, NUMA-aware allocation, and the scheduling of work units.

Morsel-driven parallelism is one answer to this. The input is divided into small morsels—typically a few thousand tuples—and worker threads pull morsels from a queue. Each worker executes the entire pipeline on its morsel, so the pipeline's compiled code is reused across morsels and the data stays in a local cache. The exchange becomes a queue of morsels rather than a materialized intermediate result. This works well when the pipeline is long and the morsels are small, because the cost of scheduling is amortized over the pipeline's work. It works less well when the pipeline contains a pipeline breaker that must see all data, such as a global aggregation; then the workers must coordinate through a shared hash table or a repartitioning step.

Parallelism also fragments the code generation problem. A compiled pipeline that runs on one thread can assume exclusive access to its local state. A pipeline that runs on many threads must handle shared state: a shared hash table for a build side, a shared aggregation table, a shared sort. The code generator must emit atomic operations, locks, or partitioning logic. These are exactly the abstractions that compilation was supposed to remove. In practice, most engines keep the shared data structures as precompiled, carefully tuned components and compile only the per-thread pipeline that feeds them. The result is a hybrid: compiled code for the streaming part, interpreted or precompiled code for the shared part.

NUMA adds another layer. On a multi-socket machine, a thread that reads memory allocated by another socket pays a latency penalty. A parallel query engine must decide where to allocate hash tables, how to partition data across sockets, and how to schedule workers so that they read local memory. A vectorized engine can make these decisions at the batch level; a compiled engine can make them at the pipeline level. Neither can make them for free. The abstraction of a single shared memory space is a lie that the hardware exposes, and the engine must either hide it with careful placement or pay for it with remote memory accesses.

The cost of abstraction, then, is not a fixed quantity that compilation eliminates. It is a budget that the engine spends in different places. The iterator model spends it on dispatch and row materialization. Vectorization spends it on batch materialization and expression interpretation. Data-centric compilation spends it on compile latency and code size. Parallelism spends it on exchange and synchronization. The design space is not a line from slow to fast; it is a set of trade-offs among latency, throughput, memory traffic, and engineering complexity. The next part of this article examines how engines blend these approaches—compiling hot paths while interpreting cold ones, vectorizing compiled code, and using runtime feedback to decide when specialization is worth its cost.

## Hybrid Execution: Compiling the Hot Path, Interpreting the Cold

The tiered approach mentioned earlier is not merely a fallback for short queries; it is a statement about where an engine chooses to spend its abstraction budget. Interpreting a query plan is cheap to start and expensive per tuple. Compiling it is expensive to start and cheap per tuple. The break-even point depends on the number of tuples the query will process, the complexity of the pipeline, and the cost of the code generator itself. An engine that compiles every query pays the compile cost even for a point lookup that returns one row. An engine that never compiles pays the interpretation cost even for a scan that touches a billion rows. Neither extreme is rational for a general-purpose system, so most engines live somewhere in between.

The simplest hybrid is a threshold on execution count. The engine interprets a query the first time it sees a plan shape, records how often that shape recurs, and compiles it once the count exceeds a threshold. The threshold is a heuristic: too low and the engine wastes time compiling queries that will never run again; too high and it leaves performance on the table for queries that run just often enough to matter. The shape of the plan matters as well. A plan with a single filter and a projection is cheap to interpret and cheap to compile; the threshold can be low. A plan with a dozen joins and a complex aggregation is expensive to interpret and expensive to compile; the threshold should be higher, because the compile cost is larger and the risk of wasting it is greater.

A more sophisticated hybrid profiles the interpreted execution. It measures the actual number of tuples flowing through each pipeline, the selectivity of each predicate, and the time spent in each operator. That profile then informs the decision to compile: if a pipeline is processing millions of tuples and dominating the query's runtime, it is a candidate for compilation; if it is processing a few hundred, it is not. Profiling also provides information that the optimizer lacked at plan time—actual cardinalities, actual data distributions—which can be used to generate better code. This is the query-engine analogue of profile-guided optimization in a general-purpose compiler, with the same caveat: profiles are only as good as the workload that produced them, and a change in data distribution can invalidate them.

Parameter changes complicate the picture. A compiled query often has constants baked into its code: a predicate against a literal, a limit value, a date boundary. If the same plan shape is re-executed with a different constant, the compiled code is either wrong or must be regenerated. Engines handle this in one of three ways. The first is to treat the constant as a runtime parameter, loading it from a parameter block on each execution. This preserves code reuse but sacrifices the optimizations that constant folding would have enabled—the branch that could have been eliminated remains, the arithmetic that could have been strength-reduced stays general. The second is to recompile for each new constant, which is correct but expensive if constants change frequently. The third is a compromise: compile with the constant as a parameter, but also generate a specialized version when the engine observes that the same constant is used repeatedly. The choice between these strategies is a microcosm of the entire design space: specialization buys speed at the cost of flexibility, and the engine must decide how much flexibility it can afford to lose.

## Adaptive Execution and Runtime Feedback

Cardinality estimation is the optimizer's perennial weakness. A plan that is optimal for one thousand rows may be catastrophic for ten million, and the optimizer often cannot tell the difference until the query is already running. Adaptive execution addresses this by changing the plan at runtime: switching a join order, changing a build side, or abandoning a nested-loop join for a hash join when the outer cardinality turns out to be larger than expected. The mechanism is appealing because it uses information that is only available during execution, but it collides directly with compilation. A compiled pipeline is a static artifact; if the plan changes, the compiled code is no longer valid.

The collision is resolved in one of two ways. The first is to compile multiple variants of the plan—one for each plausible cardinality regime—and switch between them at runtime. This is essentially a decision tree embedded in the execution engine, and it multiplies the compile cost by the number of variants. The second is to compile with guards. A guard is a runtime check on an assumption that the compiler made: that a column is non-null, that a hash table fits in memory, that a join input is smaller than a threshold. If the guard fails, the engine deoptimizes—it abandons the specialized code and falls back to a generic, interpreted path that can handle the unexpected case. Deoptimization is familiar from managed language runtimes, where it allows a JIT compiler to speculate aggressively and recover gracefully when speculation fails. In a query engine, the same idea applies: the compiler can specialize for the common case and rely on a fallback for the rare one.

The cost of deoptimization is that the engine must maintain both the specialized and the generic paths, and must ensure that they produce identical results. That is a correctness burden, not just a performance one. Every guard introduces a branch, and every branch is a potential source of divergence between the fast path and the slow path. The engineering effort required to keep them in sync is substantial, and it is one reason why many engines limit deoptimization to a small set of well-understood conditions.

Runtime feedback also drives the decision to recompile. If the engine observes that a compiled pipeline is spending most of its time in a branch that the compiler predicted would be rare, it can recompile with a different assumption. This is adaptive specialization: the code evolves as the engine learns about the data. The danger is oscillation. If the data distribution changes back and forth, the engine may recompile repeatedly, spending more time compiling than executing. Engines mitigate this with hysteresis—requiring a sustained change before recompiling—and with a cap on the number of recompilations per plan shape. The cap is a blunt instrument, but it prevents pathological behavior.

## Vectorization Inside Compiled Code

The opposition between vectorization and compilation is often presented as a choice between two execution models, but the boundary is porous. A compiled engine can generate vectorized code, and a vectorized engine can compile its expressions. The interesting question is not which model wins, but where the vectorization happens and what it costs to generate it.

Consider a compiled pipeline that processes a batch of tuples. Instead of passing one tuple at a time from a produce function to a consume function, the engine passes a batch—an array of values, or a set of parallel arrays for each column. The generated code is still specialized: the predicate is inlined, the types are resolved, the operator boundaries are erased. But the inner loop operates on arrays rather than scalars, which means the compiler can use SIMD instructions, unroll the loop, and amortize the loop overhead over many values. The selection vector, that hallmark of vectorized execution, reappears: the filter writes the indices of surviving rows into an array, and the next operator consumes that array. The difference from a pure vectorized engine is that the operator boundaries are compiled away. There is no virtual call between the filter and the projection; the generated code is a single function that scans, filters, and projects in one pass.

This hybrid is attractive because it combines the strengths of both models. It removes interpretation overhead, which is the point of compilation. It also exposes data parallelism, which is the point of vectorization. The cost is code generation complexity. Generating a vectorized loop is harder than generating a scalar loop, because the compiler must reason about alignment, tail handling, and the interaction between SIMD lanes and selection vectors. It must also decide when vectorization is profitable: for a predicate that is highly selective, a scalar loop with early exits may be faster than a vectorized loop that processes all values and then discards most of them. The decision is data-dependent, and a static compiler cannot always make it correctly. Runtime feedback can help, but it reintroduces the adaptivity problem described above.

There is also a tension between vectorization and the register-resident tuple model. In a data-centric compiler, tuples are passed as arguments in registers, which is efficient for scalar code but awkward for vectorized code. A batch of tuples does not fit in registers; it lives in memory. The compiler must therefore choose between keeping a single tuple in registers across a pipeline and keeping a batch in memory. The former minimizes memory traffic but limits data parallelism; the latter enables SIMD but reintroduces the store-and-load pattern that compilation was meant to avoid. The best choice depends on the pipeline's shape and the data's width. A narrow pipeline with simple arithmetic may benefit from register-resident scalars; a wide pipeline with expensive predicates may benefit from vectorized batches. An adaptive engine can switch between the two, but each switch is a new code generation problem.

## The Engineering Economics of Multiple Execution Paths

Maintaining an interpreter and a compiler in the same engine is expensive in ways that are easy to underestimate. The two paths must be semantically equivalent: every operator, every expression, every null-handling rule must produce the same result whether it is interpreted or compiled. That equivalence is not free. It requires a shared specification of semantics, a test suite that exercises both paths, and a discipline that prevents one path from drifting ahead of the other. In practice, bugs often appear in one path and not the other, which makes debugging harder and erodes confidence in the engine.

Performance tuning is similarly duplicated. An optimization that helps the interpreter—say, a faster hash table probe—may not help the compiler, because the compiler inlines the probe and the optimization is subsumed by inlining. Conversely, an optimization that helps the compiler—say, better register allocation—has no analogue in the interpreter. The two paths have different bottlenecks, and tuning one can leave the other behind. This is a strong argument for choosing a single execution model and optimizing it relentlessly. But no single model dominates all workloads. Vectorized interpretation is excellent for scans and aggregations over wide tables; data-centric compilation is excellent for complex pipelines with many joins and predicates; tuple-at-a-time interpretation is excellent for short OLTP queries where compile latency would dominate. A general-purpose engine that wants to serve all three must either support multiple models or accept that it will be mediocre for some workloads.

The trend in modern engines is toward adaptivity, but adaptivity has its own economics. Every adaptive decision—when to compile, when to deoptimize, when to recompile, when to switch from scalar to vectorized—adds a branch to the engine's control flow and a case to its test matrix. The complexity grows superlinearly with the number of adaptive features, because the features interact. A deoptimization triggered by a cardinality change may invalidate a compilation decision, which may trigger a recompilation, which may produce code that is slower than the original interpretation. The engine must be designed to avoid such cycles, or at least to detect and break them.

The limits of specialization are also economic. Every specialization consumes compile time, code space, and engineering effort. There is a point beyond which further specialization yields diminishing returns: the compiler has already eliminated the obvious overheads, and the remaining gains are small and data-dependent. Finding that point is an empirical exercise, and it varies by workload. An engine that specializes too aggressively becomes fragile; an engine that specializes too little leaves performance on the table. The design space is not a ladder from slow to fast, but a landscape of trade-offs, and the right position depends on the queries the engine is expected to run. The next part of this article examines how these trade-offs play out in specific execution substrates—LLVM IR, C source, and custom bytecode—and what each substrate implies for compile latency, code quality, and portability.

## Execution Substrates: LLVM IR, C Source, and Custom Bytecode

The decision to compile a query is only the beginning. The next decision is what to compile *to*. A query compiler can target LLVM IR, emit C source and invoke a system compiler, generate bytecode for a custom virtual machine, or write machine code directly. Each substrate imposes its own latency, code quality, and portability constraints, and those constraints shape the rest of the engine's design.

LLVM IR is the most powerful substrate for optimization. The query compiler constructs an IR module representing the pipeline, runs LLVM's optimization passes, and asks the JIT to emit machine code. The optimizer can inline consume functions into produce loops, propagate constants, eliminate dead code, unroll loops, and vectorize where possible. The result is often the fastest code an engine can produce. The cost is compile latency. Constructing IR, running passes, and emitting code can take tens of milliseconds for a moderately complex query, and the latency grows with the size of the pipeline. LLVM also has a large memory footprint and a complex API; embedding it in a database engine is a significant engineering commitment. The generated code is large, which can pressure the instruction cache, and the JIT must manage code memory, relocation, and cleanup. Engines that use LLVM often mitigate the latency by caching compiled modules by plan shape, by compiling only the hottest pipelines, or by using a lighter-weight JIT for simple expressions.

C source generation takes a different approach. The query compiler emits a C function as a string, writes it to a file, invokes the system C compiler to produce a shared library, and dynamically loads it. The advantages are portability and inspectability: the generated C can be read, debugged, and optimized by a mature compiler. The C compiler's optimizer is excellent, and the resulting code is often comparable to LLVM's. The disadvantages are latency and operational complexity. Invoking an external compiler can take hundreds of milliseconds, which is prohibitive for short queries. It requires a writable filesystem, a compiler toolchain on the target machine, and a mechanism to load and unload code. It also raises security concerns: generating and executing code from strings is a code injection risk if the query plan can be influenced by untrusted input. Some systems use C generation only for long-running analytical queries, where the compile latency is amortized over seconds or minutes of execution.

Custom bytecode is the lightweight option. The query compiler emits a compact bytecode program, and a virtual machine interprets it. Code generation is fast—often microseconds—and the bytecode is portable across architectures. The VM can be designed for the engine's specific needs: vectorized operations, selection vectors, null handling. The cost is execution speed. A bytecode interpreter has dispatch overhead per instruction, and it cannot perform the cross-operator optimizations that an IR-level compiler can. Some engines JIT the bytecode to machine code after it has been executed enough times, combining fast startup with high steady-state performance. This tiered approach is common in managed language runtimes and is increasingly common in query engines.

The choice of substrate is not permanent. An engine can use bytecode for cold queries, LLVM for hot ones, and C generation for offline batch processing. The important point is that the substrate determines the shape of the compilation pipeline: how long it takes, how much memory it uses, and what optimizations are available. A query compiler that targets LLVM must be designed around latency hiding; one that targets bytecode must be designed around interpretation efficiency.

## The Compilation Pipeline and Its Latency Budget

Compilation latency is the most cited objection to query compilation, and it deserves a precise accounting. The latency of compiling a query is the sum of several stages: plan analysis, IR construction, optimization, code emission, and linking or loading. Each stage has a different cost profile, and each can be optimized independently.

Plan analysis is usually cheap. The compiler walks the physical plan, resolves types, and builds a symbol table. This is linear in the size of the plan and typically takes microseconds. IR construction is more expensive because it allocates objects for every operation and every value. For a pipeline with thousands of expressions, this can take milliseconds. Optimization is the most variable stage. A few passes over a small IR module take milliseconds; aggressive inlining and vectorization can take tens of milliseconds. Code emission and linking depend on the substrate: LLVM's JIT emits machine code directly, while C generation invokes an external compiler and loads a shared library.

The break-even point is the execution time at which the compile cost is repaid by faster execution. If a query runs for 10 milliseconds and compilation takes 20 milliseconds, compilation is a net loss. If it runs for 10 seconds, compilation is a rounding error. The break-even point depends on the speedup that compilation provides. If compiled code is twice as fast as interpreted code, the break-even execution time is roughly the compile latency divided by the speedup minus one. For a 20-millisecond compile and a 2x speedup, the break-even is 20 milliseconds of interpreted execution. Queries shorter than that should not be compiled.

This simple model explains why tiered execution is so common. The engine interprets a query until it has accumulated enough execution time to justify compilation, then compiles it. The threshold can be expressed in executions, in estimated cardinality, or in measured runtime. A threshold on estimated cardinality is attractive because it is available before execution, but cardinality estimates are often wrong. A threshold on measured runtime is more accurate but requires a profiling pass. Many engines combine both: they use cardinality estimates to decide whether to profile, and runtime measurements to decide whether to compile.

Compilation latency can be reduced in several ways. The most effective is caching. If the same plan shape is compiled once and reused, the amortized compile cost approaches zero. The cache key must include the plan structure, the types, and any constants that are baked into the code. If constants are parameters rather than baked-in values, the cache hit rate improves at the cost of less specialization. Engines often maintain two versions: a generic compiled version with parameters, and a specialized version for frequently used constants.

Another technique is partial evaluation. The compiler specializes the parts of the query that are known at compile time—types, operator boundaries, predicate structure—and leaves the data-dependent parts as runtime parameters. This reduces the amount of code that must be generated and the number of optimizations that must be run, while still removing the dispatch and interpretation overhead that dominates the hot path. Partial evaluation is particularly effective for predicates: the comparison operator and the column offsets are known, but the literal value is a parameter. The compiler generates a comparison against a parameter, which is still much faster than interpreting an expression tree.

A third technique is speculative compilation. The engine begins interpreting a query and, in parallel, compiles a specialized version. If the query runs long enough, the compiled version takes over; if it finishes first, the compilation is abandoned. This hides compile latency behind execution, but it consumes CPU resources that could be used for execution. It works best on multi-core machines with spare capacity.

The latency budget also depends on the query's concurrency. In a multi-tenant system, compiling every query can saturate the CPU and starve execution. The engine must limit the number of concurrent compilations, queue them, or fall back to interpretation when the compiler is overloaded. This is a scheduling problem as much as a compilation problem, and it is often solved with a separate compilation thread pool.

## Memory Management and Data Layout in Compiled Pipelines

Compiled code does not eliminate memory management; it changes where memory management happens. A compiled pipeline still needs to allocate tuples, hash tables, sort buffers, and intermediate results. The difference is that the allocation pattern is known at compile time, so the compiler can generate specialized allocation code and avoid the general-purpose allocator.

Arena allocation is the standard technique. The engine allocates a large block of memory and hands out tuples by bumping a pointer. There is no per-tuple free; the entire arena is released when the pipeline finishes. This is fast and predictable, and it works well with the short lifetimes of query intermediates. The compiler can inline the bump allocation, turning it into a pointer increment and a bounds check. If the arena is sized correctly, the bounds check is predictable and the branch is rarely taken.

Tuple layout is another compile-time decision. In a row-oriented engine, a tuple is a contiguous record with fixed offsets for each column. In a columnar engine, a tuple is a set of values in separate arrays, and the pipeline passes a row index or a selection vector. Compiled code can specialize for either layout. If the layout is row-oriented, the compiler generates loads at fixed offsets. If it is columnar, the compiler generates loads from separate arrays, which may be more cache-friendly for wide tables but requires more registers to hold the intermediate values. The compiler can also choose a hybrid: keep frequently used columns in a row-like structure and less frequently used columns in separate arrays.

The register-resident tuple model is the logical extreme of compile-time layout specialization. The compiler keeps a tuple's fields in virtual registers and passes them from one consume function to the next. No memory is touched for the tuple itself. This works well for narrow tuples with a few fields, but it breaks down when the tuple is wide or when an operator needs to materialize it—for example, a hash join build must store the tuple in a hash table. The compiler must then spill the tuple to memory, and the register-resident advantage disappears. The best code generators choose which tuples to keep in registers based on the pipeline structure and the tuple width.

Hash tables are the most performance-critical data structure in many analytical queries. A compiled hash join can generate a specialized probe loop: the hash function is inlined, the bucket address is computed, and the comparison is generated for the specific key type. The probe loop can be scalar or vectorized. A scalar probe processes one key at a time and follows the collision chain; a vectorized probe processes a batch of keys, computes their hashes, gathers bucket pointers, and uses SIMD to compare keys. The vectorized probe is faster when the hash table fits in cache and the keys are short, but it is more complex to generate. The compiler must decide which to emit based on the key type, the expected cardinality, and the cache size.

Sorting is another area where compiled code can specialize. A comparison-based sort generates a comparison function for the specific key type and uses a cache-aware merge sort. A radix sort generates passes over the key bytes, and the compiler can unroll the passes and use SIMD to extract digits. The choice depends on the key distribution and the sort size. Compiled code can switch between algorithms at runtime, but each algorithm must be generated.

NUMA awareness adds a spatial dimension to memory management. On a multi-socket machine, the compiler can generate code that allocates memory on the local socket and schedules work on the same socket. This requires the engine to know the machine's topology and to expose it to the code generator. The abstraction of a flat memory space is replaced by a topology-aware allocation policy, and the compiler must generate code that respects it. The cost is portability: a NUMA-aware compiled query will not run efficiently on a single-socket machine unless the code generator also emits a fallback path.

Compression and encoding are the final layer. Analytical engines often store data in compressed form: dictionary encoding for strings, run-length encoding for sorted columns, bit-packing for integers. A compiled pipeline can specialize for the encoding. If a column is dictionary-encoded, a predicate on a string becomes a predicate on a dictionary code, which is a simple integer comparison. If the column is not dictionary-encoded, the compiler must generate a string comparison. The compiler can generate multiple versions of the pipeline for different encodings and choose at runtime based on the column's metadata. This is another form of specialization that trades code size for speed.

## Vectorization vs Compilation: A False Dichotomy?

The debate between vectorization and compilation is often framed as a choice between two execution models. In practice, they are orthogonal. Vectorization is about the granularity of execution: tuple-at-a-time versus batch-at-a-time. Compilation is about how the execution logic is produced: interpreted versus generated. The four combinations are all viable, and modern engines often occupy more than one quadrant.

Tuple-at-a-time interpretation is the classic Volcano model. It is flexible and easy to extend, but it has high per-tuple overhead. Vectorized interpretation amortizes that overhead over a batch and exposes data parallelism. Tuple-at-a-time compilation removes dispatch and specializes types, but it does not expose data parallelism. Vectorized compilation combines both: it generates code that processes a batch, uses SIMD where possible, and eliminates operator boundaries.

Vectorized compilation is the most aggressive point in the design space. The generated code is a single function that scans a batch, applies predicates, builds a selection vector, and projects the surviving rows. The compiler can inline the predicate evaluation, keep the selection vector in registers, and use SIMD to compare multiple values at once. The result is code that looks like a hand-written vectorized kernel, but specialized for the query's types and expressions. The cost is code generation complexity. The compiler must handle tail cases when the batch size is not a multiple of the SIMD width, manage alignment, and decide when vectorization is profitable. For a highly selective predicate, a scalar loop with early exits may be faster than a vectorized loop that processes all values and discards most of them. The compiler must either generate both versions and choose at runtime, or rely on heuristics that may be wrong.

The choice between scalar and vectorized compiled code is data-dependent. If the predicate is selective, the scalar loop exits early and touches fewer cache lines. If the predicate is not selective, the vectorized loop amortizes the loop overhead and uses SIMD. An adaptive engine can profile the predicate's selectivity and switch between the two. This is another example of runtime feedback driving code generation, and it adds another dimension to the compilation decision.

Vectorized interpretation has its own advantages. It is easier to implement than vectorized compilation because the operators are written once and reused across queries. It is easier to debug because the operator code is static. It is easier to extend because a new operator is a new function, not a new code generation pattern. For engines that need to support many operators and data types, vectorized interpretation may be the better engineering choice, even if it is slower on some queries.

The practical conclusion is that the choice is not binary. An engine can interpret vectorized operators for most queries and compile the hottest pipelines. It can compile scalar code for complex control flow and vectorized code for simple scans. It can use runtime feedback to choose between them. The design space is a set of trade-offs, and the best point depends on the workload, the hardware, and the engineering resources available.

## Portability and Heterogeneous Hardware

Compiled code is tied to the instruction set architecture it targets. A query compiled for x86-64 with AVX-512 will not run on an ARM server or a GPU. Vectorized interpretation, by contrast, is portable: the bytecode or operator implementation can run on any architecture that supports the engine's runtime. This portability is a significant advantage in cloud environments where the same query may run on different hardware generations.

Engines that compile queries must handle hardware heterogeneity. One approach is to generate multiple versions of the code, one for each target, and dispatch at runtime based on CPU features. This is common in general-purpose compilers and is increasingly common in query engines. The engine detects the CPU's capabilities—AVX2, AVX-512, NEON—and selects the appropriate compiled version. The cost is code size and compilation time: each version must be generated and cached. Another approach is to compile to a portable intermediate representation and JIT for the local machine at load time. LLVM supports this, but the JIT latency is paid on every machine that runs the query.

GPUs present a different challenge. A GPU has thousands of cores and a deep memory hierarchy, and code generation for a GPU is fundamentally different from code generation for a CPU. The query compiler must generate kernels that map well to the GPU's SIMT execution model, manage memory transfers between host and device, and handle synchronization. Some engines compile query fragments to CUDA or OpenCL, but the compilation latency is high and the code must be specialized for the GPU's architecture. Vectorized interpretation on the CPU is often more practical for general-purpose analytical queries, and GPUs are used for specific operations where their parallelism pays off.

FPGAs and ASICs are the extreme end of specialization. A query can be compiled to a hardware circuit, which can be extremely efficient for streaming operations. The compile time is minutes to hours, and the circuit is fixed once programmed. This is only viable for repetitive queries on static data, such as financial analytics or network packet processing. It is a reminder that the cost of compilation is not just latency but also flexibility: the more specialized the target, the less adaptable the engine.

The trade-off between portability and performance is a recurring theme. Vectorized interpretation is portable but leaves performance on the table. Compiled code is fast but tied to a target. Most engines choose a middle ground: they interpret by default and compile for the local architecture when the query is hot enough to justify it. The compilation is done at runtime, on the machine that will execute the query, so the code is specialized for that machine. This is the JIT model, and it is the dominant approach in modern analytical engines.

## Debugging, Observability, and Correctness

Compiled code is harder to debug than interpreted code. The operator tree is gone; the generated function is a flat sequence of instructions with inlined operations and optimized-away variables. A debugger sees machine code, not query operators. A profiler attributes time to addresses, not to operators. This makes performance analysis and correctness debugging more difficult, and it is a real cost of compilation that is often overlooked.

Engines mitigate this by preserving a mapping from generated code to the query plan. The compiler emits debug information that associates instruction ranges with plan nodes, so a profiler can report time per operator. It can also emit comments or metadata that identify the pipeline and the expression being evaluated. This mapping is essential for observability, and it must be maintained across optimizations. If the compiler inlines a consume function into a produce loop, the mapping must still attribute the inlined instructions to the original operator. This is non-trivial, but it is necessary for a production engine.

Correctness is another concern. A compiled query must produce exactly the same result as an interpreted one. The compiler must handle all the edge cases: nulls, overflow, type coercion, collation, and floating-point semantics. A bug in the code generator can produce wrong results that are hard to detect because the code is generated and not written by hand. Differential testing is the standard defense: run the same query through both the interpreter and the compiler and compare results. Fuzzing can generate random queries and data to exercise the code generator. Formal verification of the code generator is an active research area, but it is not yet practical for full query engines.

The cost of abstraction, then, is not only performance. Removing abstraction removes safety nets. The iterator model's virtual calls are slow, but they are easy to trace and easy to test. Compiled code is fast, but it requires new tools and new disciplines to keep it correct and observable. An engine that adopts compilation must invest in that infrastructure, or it will trade correctness and debuggability for speed.

## Open Problems in Query Compilation

Several open problems remain. The first is how to make compilation latency negligible. If compile time were zero, every query could be compiled, and the tiered execution problem would disappear. Current research explores lightweight code generation, template-based compilation, and partial evaluation, but no technique has eliminated the latency entirely. The second is how to automatically choose the right execution model for each query. The decision depends on cardinality, selectivity, data layout, and hardware, and it is currently made with heuristics. A principled cost model that includes compilation cost and code quality would be valuable, but it is difficult to build because the cost of generated code is hard to predict without running it.

The third is how to combine compilation with adaptive execution without oscillation. Adaptive execution changes the plan at runtime; compilation produces a static artifact. Reconciling the two requires either compiling multiple variants or using guards and deoptimization. Both approaches add complexity and can lead to thrashing if the data distribution changes frequently. The fourth is how to compile for heterogeneous hardware without duplicating the code generator for each target. A portable intermediate representation that preserves enough information for hardware-specific optimization is an open design problem.

The fifth is how to verify generated code. As query engines become more complex and more specialized, the risk of code generation bugs grows. Formal methods, model checking, and differential testing are all partial solutions, but none provides a complete guarantee. The sixth is how to make compiled code as observable as interpreted code. Debugging and profiling tools for generated code are still immature compared to those for hand-written code. Solving these problems would not end the debate between vectorization and compilation, but it would change the terms of the trade-off. The design space would still be a landscape of choices, but the cost of abstraction would be lower, and engines could specialize more aggressively without paying the full price in latency, portability, and correctness.
