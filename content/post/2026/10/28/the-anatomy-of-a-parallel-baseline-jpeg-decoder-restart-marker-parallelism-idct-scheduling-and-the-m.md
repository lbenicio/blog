Baseline JPEG is one of those formats that engineers stop noticing. It is old, stable, and everywhere, and because it is everywhere it is easy to treat decoding as a solved library call. That abstraction hides a useful systems problem. A JPEG decoder is not one algorithm. It is a pipeline of stages with sharply different parallelism, different memory access patterns, and different failure modes when a scheduler gets them wrong. The entropy-coded bitstream has a serial spine. The block transforms and color conversion fan out into independent work. The boundary between those two worlds is where decoder performance is won or lost.

This post looks at baseline sequential JPEG decoding as a parallel systems design problem. The assumptions matter. We are talking about baseline DCT-based JPEG with Huffman coding, 8-bit sample precision, and a single scan, as described by SOF0. We are not covering progressive JPEG, arithmetic-coded JPEG, lossless JPEG, or JPEG 2000. We are also focusing on decoding a single image on a multicore CPU, not on throughput-oriented server workloads that decode many images at once, although some of the same trade-offs apply. The goal is not to present a universal decoder architecture. There is no universal architecture. The goal is to make the dependency graph explicit so that parallelism can be placed where it is actually safe and profitable.

## The pipeline is a dependency graph, not a loop

A baseline JPEG file is a sequence of marker segments followed by entropy-coded scan data. The decoder parses SOI, application markers, quantization tables in DQT, frame headers in SOF0, Huffman tables in DHT, restart interval information in DRI, and the start of scan in SOS. After that come entropy-coded MCUs, then EOI. Some markers can appear in different orders. Some tables can be redefined. The parser has to be strict enough to reject malformed files and tolerant enough to accept the variation produced by real encoders.

The decoding stages are usually described as entropy decode, dequantize, inverse DCT, upsample chroma, convert color, and pack output samples. That description is accurate but too linear. The real structure is a dependency graph. Marker parsing and table construction must happen before entropy decode. Entropy decode must happen before dequantization and IDCT for a given block, because the entropy decoder produces the quantized DCT coefficients. Once a block's coefficients exist, dequantization and IDCT for that block are independent of every other block, subject only to output placement. Chroma upsampling and color conversion need neighboring blocks or MCU rows depending on the sampling factors and the filter used. Output packing depends on the destination format, row stride, color space, and whether alpha or padding is present.

That graph has a long serial prefix and a wide parallel suffix. The serial prefix is not just file parsing. It includes the Huffman decoder itself. In baseline JPEG, the entropy decoder reads a variable-length bitstream. Huffman codes are prefix codes, so the decoder cannot know where the next code begins until it has decoded the current one. The DC coefficient of each block is differential: it is coded relative to the previous DC coefficient in the same component. The AC coefficients use run-length symbols and end-of-block markers. The bit reader state, the DC predictors, and the Huffman table selection all carry forward from MCU to MCU. This is the serial spine.

## Baseline JPEG's one serial spine

The entropy-coded segment is not self-synchronizing at arbitrary byte boundaries. A decoder cannot jump into the middle of the scan and start decoding unless it knows the exact bit position, the current DC predictors, and the Huffman state. In the general case, those are produced only by decoding everything before that point. This is why naive attempts to parallelize JPEG decoding by splitting the compressed byte stream into equal chunks fail. The chunks do not correspond to independent decoding units. A worker starting at an arbitrary offset will interpret a Huffman code at the wrong bit position, produce garbage coefficients, and often desynchronize completely.

The serial spine has three kinds of state. First, there is the bit reader state: the current byte, the number of valid bits remaining, and the handling of byte stuffing. In JPEG entropy-coded data, a literal 0xFF byte is followed by 0x00 so that it cannot be confused with a marker. The decoder must remove that stuffed byte. Second, there are the DC predictors, one per component. Each block's DC coefficient is coded as a difference from the previous DC value in the same component. Third, there is the Huffman decoding state, which is mostly implicit in the bit position and the selected tables, but it determines how many bits are consumed for each symbol.

None of this means the entropy decoder is inherently single-threaded for the entire image. It means the decoder needs legitimate boundaries at which the state can be reset or reconstructed. Baseline JPEG has one such boundary built into the format: the restart marker.

## Restart markers turn intervals into tasks

The DRI marker defines a restart interval in MCUs. When restart markers are present, the encoder inserts an RST0 through RST7 marker after every restart interval, cycling through the eight marker codes. At each restart marker, the DC predictors are reset to zero, the bit reader is byte-aligned, and the next interval begins with fresh predictor state. The marker itself is not entropy-coded data. It is a marker, and because of byte stuffing it can be found without fully Huffman-decoding the intervening bits.

That property is the basis of restart-marker parallelism. A decoder can scan the entropy-coded segment for RST markers, record the byte offsets of the intervals, and assign intervals to worker threads. Each worker creates a new bit reader at the start of its interval, resets the DC predictors to zero, and decodes the fixed number of MCUs in that interval. The intervals are independent in the sense that matters for correctness: no DC prediction crosses an RST boundary, and no bit position crosses it either. The workers do not need to communicate during entropy decode. They need only write their coefficient blocks into the correct locations in the output coefficient buffer.

There are caveats. The scan for RST markers must respect JPEG marker semantics. A 0xFF byte inside entropy-coded data is always followed by 0x00, so an 0xFF followed by D0 through D7 is a genuine restart marker and not a false positive from data. The decoder still has to validate that the marker sequence is plausible, that the interval count is consistent with the DRI value, and that the final interval is handled correctly. Some encoders omit restart markers entirely. Some insert them at large intervals. Some produce files where the last interval is shorter than the declared restart interval, as expected at the end of the scan. The parallel decoder has to handle all of these cases without turning a malformed file into a memory-safety bug.

The trade-off is not free. Restart markers add a small amount of compressed data and reset the DC predictors, which can slightly reduce compression efficiency. They also impose a fixed MCU count per interval. If the interval is too large, the number of parallel tasks is small. If the interval is too small, marker overhead and per-task setup costs grow. The encoder chooses this trade-off, not the decoder. A decoder can exploit restart markers when they exist, but it cannot invent them. When they are absent, the entropy decode remains a serial stage, and parallelism has to come from pipelining rather than from independent entropy intervals.

## Pipelining the serial decoder with parallel block work

When restart markers are absent or too sparse, the decoder can still overlap entropy decoding with downstream work. The entropy decoder becomes a producer. It decodes MCUs in scan order and emits quantized coefficient blocks or, if the design chooses, dequantized blocks. A pool of workers consumes those blocks and performs IDCT, chroma upsampling, color conversion, and output packing. The producer is serial, but the consumers are not. As long as the producer stays ahead of the consumers on average, the pipeline keeps the parallel stages busy. If the consumers fall behind, the queue fills and the producer blocks. If the producer is the bottleneck, the consumers starve.

This is a classic producer-consumer design, but JPEG adds details that matter. The unit of work should not be one 8x8 block. A single block is too small for most schedulers; the queue operations and wakeups can cost more than the arithmetic. The unit should be an MCU or a small group of MCUs, depending on the sampling factors. For 4:2:0, an MCU contains four luma blocks and one Cb block and one Cr block. For 4:4:4, it contains three blocks. For 4:2:2, it contains two luma blocks horizontally and one chroma block for each component. The worker task should carry enough blocks to amortize scheduling while preserving locality.

The queue should be bounded. An unbounded queue turns backpressure into memory growth. A bounded queue with a small number of MCU rows is usually enough to smooth burstiness without destroying cache locality. The producer writes coefficient blocks into a ring buffer. Consumers read from the ring buffer, transform, and write output samples into the destination image. The ring buffer can be organized by MCU row so that chroma upsampling has the neighboring rows it needs. This is also where output ordering becomes subtle. Workers can complete out of order, but their output offsets are deterministic. They do not need to write in scan order as long as they write to disjoint regions or use proper synchronization. Disjoint output rows or MCU groups are preferable to atomic updates on shared pixels.

The pipeline also exposes a scheduling question. The entropy decoder is serial and has variable cost per MCU because Huffman codes and run lengths vary. The IDCT and color conversion stages have more uniform cost per block, although chroma upsampling and color conversion depend on the sampling factors and output format. A work-stealing pool can balance the downstream stages, but the producer cannot be stolen. If the producer is slower than the consumers, adding workers does not help. The decoder should measure the stage balance or, more practically, use a queue depth and worker count that avoid excessive contention. The right answer depends on the image, the CPU, the memory system, and the output format. This is not a place for a universal constant.

## Where the memory bandwidth goes

It is tempting to think of JPEG decoding as arithmetic-bound because of the IDCT. In practice, the arithmetic is only part of the story. The decoder moves compressed bytes, coefficient blocks, dequantized coefficients, intermediate samples, upsampled chroma, converted color samples, and final output pixels. Each of those transitions can add a memory traffic tax. A decoder that materializes every intermediate stage in global memory can spend more time waiting on cache misses and memory bandwidth than doing useful transform work.

The coefficient representation matters. Quantized DCT coefficients are small integers, often stored as 16-bit values. Dequantized coefficients may need wider integers or floating point depending on the IDCT implementation. The IDCT output is 8-bit samples after clamping. If the decoder writes dequantized coefficients to memory, then reads them back for IDCT, then writes IDCT output, then reads it for upsampling, then writes upsampled output, then reads it for color conversion, the data has made several round trips. Fusing stages reduces traffic but complicates the pipeline. Fusing dequantization with IDCT is straightforward. Fusing IDCT with chroma upsampling and color conversion is possible per MCU row, but it requires the worker to own enough neighboring blocks to produce the output row. The trade-off is between a simple staged design with more memory traffic and a fused design with a more complex scheduler and tighter buffer ownership.

The output format adds another dimension. Converting YCbCr to RGB and packing into a tightly packed RGB buffer is not the same as writing into a row-strided image with padding, nor the same as writing into a planar format or a format with alpha. If the destination is a GPU texture or a shared-memory buffer, the decoder may need to match its layout exactly to avoid a copy. Every copy is a chance to lose the benefit of parallel IDCT. The scheduler should treat output packing as a first-class stage, not as an afterthought.

Once the pipeline stages are separated, the next question is not whether to parallelize but where to put the queue, how much state each worker must own, and which intermediate buffers can be fused away. That question leads directly to buffer ownership and the memory-bandwidth accounting that determines whether a parallel decoder actually scales.

## Buffer ownership and the shape of the working set

Once stages are fused, the next decision is memory ownership. A global coefficient buffer is simple but forces every block through DRAM and a barrier. Per-worker private buffers minimize sharing but make chroma upsampling hard because a worker may need neighboring rows. A ring of MCU rows is usually the best compromise: the entropy producer writes into a small number of row buffers, and consumers take ownership of a row, transform it, upsample it, convert it, and write output. The working set should be sized by MCU row, not by image. For 4:2:0 at 3840 pixels wide, one MCU row has 240 MCUs, six blocks each, or about 184 KB of 16-bit coefficients. That fits in L2. The output row is about 11.5 KB in RGB24, which fits in L1. Keeping those rows hot is more valuable than keeping the whole image in memory. The ring also provides backpressure: the producer cannot run more than a few rows ahead, so memory use stays bounded.

False sharing is the hidden tax. A 64-coefficient block is 128 bytes, two cache lines. If two workers write adjacent blocks without padding, they can share a cache line and generate coherence traffic. Padding blocks to 128 bytes or aligning MCU rows to cache-line boundaries avoids that. The same applies to row completion counters and queue indices. A single atomic counter shared by all workers can cost more than the IDCT. Padding counters and batching updates, such as once per MCU row instead of once per block, removes most of the bottleneck. Per-worker state should be private: bit reader, DC predictors, Huffman table pointers, output row pointer. Quantization tables, Huffman tables, and frame metadata can be shared read-only. The queue is the only mutable shared structure, and workers should touch it in batches. Popping one MCU at a time spends more time on atomics than decoding; popping a run of MCUs or an entire restart interval amortizes that cost.

## IDCT scheduling: blocks, rows, and task cost

The inverse DCT is arithmetic-heavy, but task granularity matters as much as the transform itself. A scalar 8x8 IDCT may take a few hundred operations. A SIMD implementation can process multiple blocks, but only if the data layout cooperates. Handing a worker one block is usually a mistake: queue pop, function call, and constant setup can exceed the transform. An MCU, a pair of MCUs, or a contiguous run within an MCU row is better. For 4:2:0, an MCU already has six blocks. For 4:4:4, three blocks may be too small; batch two or four MCUs.

The coefficient layout should be chosen for the IDCT, not just for entropy decode. A block stored as 64 contiguous 16-bit values is convenient for Huffman decoding but awkward for a separable transform that wants rows and columns. Some decoders store coefficients transposed so the first pass reads contiguous rows and the second reads contiguous columns without an explicit transpose. Others transpose in registers with SIMD shuffles. Either can work. The key is to fuse zigzag reorder, dequantization, and IDCT so the coefficient buffer is written once in the layout the transform prefers. That eliminates a full pass over the coefficients.

Scheduling IDCT independently of entropy decode is easy when coefficients are already available. Static partitioning by MCU row usually balances well because IDCT cost per block is nearly constant. If entropy decode is fused with IDCT, cost per MCU becomes variable, and work stealing or a dynamic atomic counter over MCU rows can smooth it out. The counter should be incremented per row, not per block. Cache blocking matters more than thread count. Processing one MCU row at a time keeps the coefficient row in L2 and the output row in L1. Processing the whole image streams coefficients from DRAM and writes output back to DRAM, which is the bandwidth wall. A row-based schedule also allows prefetching the next coefficient block a few blocks ahead, enough to cover latency without evicting useful data.

## Chroma upsampling and color conversion as a fused stage

Chroma upsampling is where the decoder stops being independent blocks and starts needing neighborhood information. In 4:2:0, each chroma sample covers a 2x2 luma region. Replication needs only the current chroma block. A vertical filter needs the chroma row above and below. A horizontal filter needs the neighboring chroma block in the same row. If the decoder processes one luma row at a time, it may lack the neighboring chroma rows. Processing two luma rows at a time gives full vertical context for 4:2:0.

Fusing upsampling with color conversion avoids writing an upsampled chroma plane and reading it back. The fused worker takes the luma block, the corresponding chroma blocks, and produces RGB directly. For 4:2:0, a worker assigned to two luma rows can upsample the chroma row once and reuse it for both luma rows. The output is written once in the final format. This reduces traffic to one read of coefficients and one write of pixels. The cost is that the worker must own the chroma blocks for the row, so the scheduler must assign work in units that include the necessary chroma context, usually an MCU row or a band of MCU rows.

Color conversion is a fixed-point matrix multiply. The YCbCr to RGB coefficients can be scaled to integers and implemented with shifts and adds. SIMD versions process 8 or 16 pixels at a time. Clamping must be branchless. Output packing depends on the destination format. RGB24 is three bytes per pixel, which makes SIMD stores awkward because the stride is not a power of two. A common trick is to convert to a temporary RGB row in a SIMD-friendly layout, then pack with a shuffle. RGBA or planar output is simpler. The decoder should treat output packing as part of the pipeline, because a slow packing step can undo a fast IDCT.

## The memory-bandwidth wall in practice

The arithmetic intensity of baseline JPEG is low enough that memory bandwidth often dominates. A 4:2:0 MCU has six 8x8 blocks, or 384 samples. Quantized coefficients are 6 * 64 * 2 = 768 bytes. The final RGB output for 16x16 pixels is 256 * 3 = 768 bytes. Even in the best case, the decoder reads 768 bytes of coefficients and writes 768 bytes of pixels per MCU. If coefficients are dequantized to 32-bit integers, coefficient traffic doubles. If IDCT writes 8-bit samples to an intermediate buffer, that is another 384 bytes written and read. If upsampling writes a chroma plane, more traffic. A staged decoder can move three to five times as much data as a fused decoder.

The cache hierarchy helps only if the working set is small. A 4K image has 240 MCUs per row and 135 MCU rows for 4:2:0. The coefficient row is about 184 KB, fitting in L2 but not L1. The output row is about 11.5 KB, fitting in L1. Processing one MCU row at a time keeps the coefficient row in L2 and the output row in L1. Processing the whole image makes the coefficient array tens of megabytes, so every stage streams from DRAM. The difference can be a factor of two or more. Parallelism does not change this equation. Adding cores increases bandwidth demand but not bandwidth. Beyond a point, more threads only add contention.

Non-temporal stores can help when the output is large and will not be read soon, because they avoid read-for-ownership traffic. If the output is immediately consumed by a display pipeline, they can hurt by bypassing the cache. The decoder should expose output usage as a hint rather than hard-code a policy. Prefetching compressed bytes during entropy decode can hide latency, but prefetching too far can evict Huffman tables or coefficient rows. NUMA adds another layer: a worker writing to remote memory pays a bandwidth penalty. Row buffers should be allocated on the node where the worker runs, or first-touch allocation with pinned workers should be used. A global coefficient buffer written by all workers is a NUMA anti-pattern.

## Restart-marker edge cases and scheduling policy

Restart-marker parallelism depends on finding markers correctly. The scanner must treat 0xFF00 as stuffed data, 0xFFD0 through 0xFFD7 as restart markers, and any other 0xFF-prefixed code as the end of the entropy-coded segment. It must handle a restart marker at the end of the scan, a final interval shorter than the DRI value, and files that declare a restart interval but contain no markers. A decoder that assumes a perfect marker sequence will fail on real files. A decoder that scans for RST markers without validating the DRI value may create intervals that do not match MCU boundaries. The total MCU count is computable from SOF0, so the decoder can calculate the expected number of intervals. If the marker count disagrees, it can fall back to serial entropy decode or mark the file damaged.

If a worker hits an invalid Huffman code inside its interval, the error is contained. Other intervals still decode. This fault isolation is an underrated benefit of restart-marker parallelism. The damaged interval can be filled with a neutral color or DC-only blocks, and the rest of the image remains usable. In a serial decoder, an error often desynchronizes the bit reader and corrupts everything after it. The final interval needs special handling: if the total MCU count is not a multiple of the restart interval, the last interval contains the remainder. The scanner cannot know the remainder from markers alone because the last interval ends at EOI. The decoder must use frame dimensions to compute it. Extra RST markers beyond the expected count should be ignored or treated as corruption; missing markers can be treated as one large final interval, reducing parallelism.

The scheduler should match synchronization cost to work granularity. Restart intervals and MCU rows are large enough for an atomic counter. Individual blocks are not. A single global queue with one entry per block will spend most of its time on atomic operations and cache-line ping-pong. One entry per MCU row or per restart interval keeps the queue overhead negligible. The queue should be bounded and padded, with head and tail on separate cache lines. Producers and consumers should batch updates.

Two-phase decoding is the simplest correct design. In phase one, workers decode restart intervals in parallel and write coefficients to a global buffer. A barrier separates phases. In phase two, workers process MCU rows in parallel: dequantize, IDCT, upsample, convert, and write output. The barrier cost is negligible for large images, and the design avoids row completion counters. The downside is no overlap between entropy decode and IDCT. For a single large image, that overlap is often small because entropy decode is much faster than IDCT in well-optimized decoders. For low-latency decoding or many small restart intervals, a pipelined design can be faster but needs careful synchronization.

A hybrid design is often best. The entropy decoder runs serially or in restart-interval parallel mode, depending on the file. It writes coefficients into a ring of MCU rows. A row completion counter tracks when all intervals overlapping that row are done. Once a row is complete, a worker claims it for IDCT and color conversion. This overlaps the semi-serial entropy stage with the parallel transform stage. Counters must be padded and updated in batches. Row buffers must be recycled only after all readers are done; a reference count per row can manage that without a global barrier. The choice depends on image size, restart interval, core count, and output format. There is no single best answer. The dependency graph makes the safe boundaries explicit: restart markers, MCU rows, and fused output stages. The memory system provides the final constraint.

## Huffman decoding is a serial bottleneck with a fast path

The entropy decoder is often assumed to be irreducibly slow because it is serial, but a baseline Huffman decoder can be made fast enough that it stops being the bottleneck in many images. The key is to avoid per-bit loops and unpredictable branches. A canonical Huffman decoder can build a lookup table indexed by the next N bits of the bitstream. For baseline JPEG, the maximum code length is 16 bits. A table of 2^8 entries is a common compromise. Each entry stores the symbol, the code length, and possibly a flag for codes longer than eight bits. If the next eight bits index an entry with a valid symbol, the decoder consumes that many bits and continues. If the entry indicates a long code, the decoder falls back to a slower path that examines more bits or walks the code-length counts. This fast path handles the majority of symbols because short codes are common in JPEG Huffman tables. The slow path should be small and cold, not inlined into the main loop.

The bit reservoir is the other half. Reading one bit at a time from a byte buffer is simple but slow. A 32-bit or 64-bit accumulator lets the decoder consume multiple bits per operation. The refill path must handle byte stuffing: when the next byte is 0xFF, the following byte must be 0x00 and is discarded. It must also detect marker codes, which end the entropy-coded segment. The refill should be branch-predictable. In most intervals, there is no stuffing and no marker, so the common path is a simple load and shift. The rare 0xFF case can be handled by a cold function. The accumulator must not read past the end of the buffer; a padded input buffer or a bounds check on refill avoids overreads. The decoder should also track the bit position for error reporting and for restart marker alignment.

DC and AC decoding have different shapes. DC decoding reads a Huffman symbol for the difference category, then reads that many bits and extends the value to a signed integer. The extension is a branchless operation: if the value is less than half the range, subtract the full range minus one. The DC predictor is updated and stored. AC decoding loops over run-length symbols until an end-of-block symbol or until 63 coefficients have been written. Each symbol gives a run of zeros and a size. The decoder writes zeros for the run, reads the coefficient bits, and stores the value. The loop is serial within a block, but it is short. A branchless zero-fill for the run can help, especially for sparse blocks. The coefficient buffer should be zeroed before decoding, or the decoder should explicitly write zeros for the run. Zeroing the whole block first is often faster because it is a fixed-size memset that the compiler can vectorize, but it adds a write for every block. For blocks with many nonzero coefficients, writing zeros only for the run is better. The choice depends on the image.

Huffman table selection is per component and can change between scans, but in baseline JPEG there is a single scan. The decoder can cache pointers to the active DC and AC tables for each component. Table lookups should not go through a map or a switch in the inner loop. The component descriptor should hold the table pointers directly. The same applies to quantization table pointers. The inner loop should touch as few pointers as possible. The entropy decoder is not a place for object-oriented abstraction. It is a place for a tight loop with a small amount of state.

SIMD is difficult for Huffman decoding because the bitstream is variable-length and serial. There are research decoders that use vectorized table lookups or decode multiple bitstreams in parallel, but for a single baseline scan the serial dependency remains. The practical approach is to make the scalar decoder fast, keep the tables in L1, and use the parallelism described earlier at the interval and block level. The entropy decoder should not be the place where the decoder tries to be clever with SIMD. It should be the place where it avoids branches, avoids cache misses, and keeps the bit reservoir full.

## Fixed-point IDCT and dequantization: precision, scaling, and SIMD layout

The inverse DCT is the arithmetic center of the decoder, but the arithmetic is not the only concern. The IDCT must produce 8-bit samples that match the reference decoder closely enough to avoid visible differences. JPEG does not define a single exact IDCT; it defines an inverse DCT with a tolerance. Different implementations use different fixed-point approximations. The decoder designer must choose between speed, precision, and simplicity. A floating-point IDCT is easy to write and accurate, but it can be slower and may not vectorize as well as fixed-point on some CPUs. A fixed-point IDCT uses integer arithmetic and shifts, which maps well to SIMD. The most common algorithms are the AAN (Arai, Agui, Nakajima) fast IDCT and the Loeffler-Ligtenberg-Moshovitz algorithm. Both reduce the number of multiplications compared with a direct 8x8 transform. The AAN algorithm is popular because it has a simple scaling structure: the forward and inverse transforms share factors that can be folded into dequantization.

Dequantization is a multiply per coefficient. The quantized coefficient is an integer, and the quantization table value is a 16-bit integer. The product can be up to 16 bits times 16 bits, which fits in 32 bits. The IDCT then operates on these dequantized values. If the IDCT expects its inputs to be pre-scaled by the AAN factors, the dequantization step can multiply by the quant table value and the scale factor in one operation. This avoids a separate scaling pass. The scale factors depend on the position in the 8x8 block, so the decoder needs a combined table or a way to apply the scale during dequantization. A combined table of 64 32-bit values per quantization table can be precomputed when the DQT marker is parsed. The dequantization loop then reads the quantized coefficient, multiplies by the combined value, and writes the result. This is a good place to use SIMD: load eight 16-bit coefficients, widen to 32-bit, multiply by eight 32-bit combined values, and store. The combined values are constant for the block, so they stay in registers or L1.

The IDCT itself is separable. An 8x8 inverse DCT can be computed as eight 1D IDCTs on the rows followed by eight 1D IDCTs on the columns. The intermediate values need enough precision to avoid overflow and rounding errors. A common fixed-point design uses 16-bit inputs, 32-bit intermediates, and shifts after each 1D pass. The final pass clamps to 0..255 and adds 128 for the level shift. The clamping must be branchless; SIMD min and max instructions are ideal. The output is 8-bit samples, usually stored in a row buffer. If the decoder processes multiple blocks in SIMD, it can pack the results into a contiguous row. The layout of the coefficient buffer should match the IDCT's preferred order. Some implementations store the coefficients in natural order and perform a transpose between the row and column passes. Others store the coefficients transposed so the first pass reads contiguous rows and the second pass reads contiguous columns without an explicit transpose. The transpose can be done with SIMD shuffles, but it costs instructions. The best layout depends on whether the entropy decoder can write coefficients in the transposed order without extra work. The zigzag reorder can be combined with the transpose: the decoder can map the zigzag index directly to the transposed position. This is a small change in the coefficient write path that saves a full transpose later.

Precision matters for compliance. The JPEG standard defines a maximum error tolerance for the IDCT. A fixed-point implementation that is too aggressive with shifts can produce visible banding or block artifacts. The decoder should be tested against a reference implementation on a set of images, including smooth gradients and high-frequency textures. The error should be measured in the spatial domain, not just the DCT domain. The IDCT is also a place where different CPUs have different instruction sets. A portable C implementation with compiler auto-vectorization can be surprisingly good, but hand-written SIMD for x86 SSE2/AVX2 or ARM NEON can be significantly faster. The decoder should have a scalar fallback and runtime dispatch. The dispatch should happen once per image, not per block. The IDCT function pointer should be selected based on CPU features and image parameters. The function pointer call per block is a small overhead, but it can be avoided by selecting a whole-image decode function or by using a macro-generated loop. The key is to keep the inner loop free of conditionals that depend on CPU features.

## Thread pool topology and synchronization costs

Parallel JPEG decoding is not just about dividing work. It is about how threads communicate. The synchronization primitives can dominate if they are used at the wrong granularity. A thread pool with a global queue and a mutex is easy to write, but it can be slow. Each enqueue and dequeue takes a lock, and the lock becomes a contention point. A lock-free queue with atomic operations is better, but it still has a single cache line for the head and tail, which ping-pongs between cores. The queue should be padded so the head and tail are on separate cache lines. The producers and consumers should batch their operations. For example, the entropy decoder can decode an entire restart interval and enqueue one work item for that interval. The workers can dequeue multiple items at once. This reduces the number of atomic operations by orders of magnitude.

The choice between spinning and blocking matters. If a worker has no work, it can spin on the queue for a short time before sleeping. Spinning avoids the latency of a futex or condition variable wakeup, but it burns CPU cycles. For a decode that lasts tens of milliseconds, a short spin is usually worth it. The spin count should be tuned to the CPU and the expected work duration. A hybrid approach uses a few thousand cycles of spin, then blocks on a condition variable. The condition variable should be signaled only when the queue transitions from empty to non-empty, not on every enqueue. This avoids unnecessary wakeups. The thread pool should also support work stealing: if a worker's local queue is empty, it can steal from another worker's queue. Work stealing is useful when the work items have variable cost, such as entropy intervals with different numbers of nonzero coefficients. However, work stealing adds complexity and can cause cache misses if the stolen work is not local. For JPEG, the work items are large enough that the cost of stealing is small compared with the decode time.

Thread affinity can improve performance by keeping a worker on the same core and the same NUMA node. If the decoder allocates row buffers with first-touch policy, the worker that first writes to a buffer owns it in the local memory. Pinning workers to cores prevents migration and improves cache reuse. However, pinning can hurt if the system is oversubscribed. The decoder should expose affinity as an option, not a hard requirement. The number of workers should be chosen based on the number of physical cores, not logical cores, because hyperthreads share execution units and caches. For memory-bandwidth-bound stages, hyperthreads may not help and can even hurt by increasing contention. The decoder should allow the user to set the worker count. A default of one worker per physical core is a reasonable starting point.

Synchronization also appears in the output stage. If multiple workers write to the same output image, they must not write to overlapping regions. The simplest approach is to assign each worker a set of MCU rows. The rows are disjoint, so no synchronization is needed for the output writes. The only shared state is the row completion counter. The counter should be updated with a release fence so that the writes to the row buffer are visible before the row is marked complete. The worker that claims the row for IDCT must acquire the counter. This is a classic producer-consumer pattern with acquire-release semantics. In C11, this can be done with atomic_fetch_add and atomic_load with memory_order_acquire/release. In C++, std::atomic with the same memory orders. The counter should be padded to avoid false sharing with other counters. If the decoder uses a barrier between entropy decode and IDCT, the barrier itself provides the necessary ordering. A barrier is simpler but prevents overlap. The choice depends on the image and the target latency.

## Profiling and validation: how to know where the wall is

A parallel decoder can be fast on one image and slow on another. The difference is often in the image content, the restart interval, the sampling factors, and the output format. Profiling is the only way to know where the bottleneck is. The decoder should have built-in counters for the time spent in each stage: entropy decode, dequantization, IDCT, upsampling, color conversion, and output packing. These counters can be per-thread and aggregated at the end. They should be lightweight, using cycle counters or clock_gettime with low overhead. The counters reveal whether the decoder is entropy-bound, transform-bound, or memory-bound. If entropy decode is the bottleneck, restart-marker parallelism or a faster Huffman decoder is the answer. If IDCT is the bottleneck, the IDCT implementation or the scheduling granularity is the answer. If the counters show that all stages are fast but total time is high, the bottleneck is synchronization or memory bandwidth.

Hardware performance counters are more detailed. On Linux, perf can measure cache misses, instructions per cycle, and memory bandwidth. The decoder developer can use perf stat to see if the decode is hitting the memory-bandwidth wall. A roofline model can help: the arithmetic intensity of the decoder is low, so the achievable performance is limited by the memory bandwidth. If the measured bandwidth is close to the peak, adding threads will not help. The decoder should then focus on reducing traffic: fusing stages, using smaller intermediate representations, and improving cache locality. If the measured bandwidth is well below peak, the bottleneck is elsewhere, such as branch mispredictions in the Huffman decoder or a lock contention in the queue.

Validation is as important as profiling. A parallel decoder must produce the same output as a reference decoder, within the JPEG tolerance. The test suite should include images with restart markers at different intervals, images without restart markers, images with odd dimensions, images with different subsampling factors (4:4:4, 4:2:2, 4:2:0, 4:1:1), and images with unusual quantization tables. The decoder should also be tested with truncated files, files with extra restart markers, and files with missing restart markers. The output should be compared pixel by pixel with a reference decoder, allowing for the JPEG tolerance. A hash of the output is not enough because different IDCT implementations can produce slightly different pixels. The comparison should be done in the spatial domain with a maximum absolute difference threshold. The decoder should also be tested for thread safety with race detectors such as ThreadSanitizer. The parallel paths are where data races hide. A race that only occurs on a specific core count or a specific image size is easy to miss in normal testing. ThreadSanitizer can catch unsynchronized access to the row buffers and the completion counters. The decoder should be run with different worker counts, including one worker, to ensure that the serial path and the parallel path produce the same output. The one-worker path is also a useful fallback for debugging.

Finally, the decoder should be benchmarked on realistic workloads. A single 4K image is a different workload from a batch of 1080p images. The restart interval and the sampling factors change the balance between entropy decode and IDCT. The decoder should be tested on a range of images and the results should be reported with the image characteristics. A benchmark that only uses one image can be misleading. The goal is not to find a single number but to understand the shape of the performance curve. The memory-bandwidth wall is a real constraint, but it is not the only one. The serial spine, the synchronization costs, and the IDCT precision all interact. Profiling and validation turn those interactions from guesses into measurements.

## Restart interval sizing as an encoder-decoder contract

The DRI marker gives the restart interval as a 16-bit count of MCUs. That single number determines the maximum number of independent entropy tasks in the scan. It is chosen by the encoder, often with no knowledge of the decoder's core count or memory system. A decoder can still adapt. It can coalesce adjacent restart intervals into a single work item. It can also assign one interval per worker when the interval is large. The important distinction is that the decoder cannot split an interval, because there is no reset point inside it. The interval is the atomic unit of restart-marker parallelism.

The scheduling math is straightforward. If the scan contains N MCUs and the restart interval is R, the number of intervals is ceil(N/R). For a 4K 4:2:0 image, N is 240 * 135 = 32,400. An interval of 16 MCUs produces 2,025 intervals. An interval of 256 produces 127 intervals. An interval of 1,024 produces 32 intervals. On an eight-core machine, 127 intervals is plenty to keep workers busy, while 32 intervals leaves some cores idle at the tail. The tail effect is the last wave of tasks. If the number of intervals is not much larger than the number of workers, the decode time is dominated by the slowest interval. Variable Huffman cost makes the slowest interval unpredictable. A decoder can reduce tail effects by using smaller intervals, but only if the encoder provided them.

Small intervals have their own cost. Each interval begins with a byte-aligned bit reader and zeroed DC predictors. The marker itself is two bytes, and the encoder may pad to a byte boundary before it. The decoder pays a task setup cost: initialize the bit reservoir, load the Huffman table pointers, set the output coefficient pointer, and enqueue the work. If the interval is one MCU, the setup can exceed the decode time for that MCU. A decoder can group many small intervals into one task to amortize setup. It decodes the group serially, resetting state at each RST marker. This preserves correctness and reduces queue traffic. The group size can be chosen so that each task has a few thousand MCUs, which is enough to amortize setup while still providing many tasks.

Large intervals are the opposite problem. If R is 4,096 and the image has 32,400 MCUs, there are only eight intervals. On an eight-core machine, that is exactly one task per core, with no work stealing and no load balancing. If one interval contains a complex region and another contains a flat region, the cores finish at different times. The decoder can still pipeline downstream work, but the entropy decode itself is limited to eight-way parallelism. In that case, row-wave pipelining is more effective than restart-marker parallelism. The decoder can treat the entire scan as a serial producer and overlap it with parallel IDCT and color conversion. The restart markers are not useful for entropy parallelism, but they still provide error isolation and a place to reset state.

A decoder should therefore inspect the DRI value and the total MCU count before choosing a strategy. If the number of intervals is at least, say, four times the worker count, restart-marker parallelism is a good fit. If it is smaller, the decoder can use a hybrid: assign intervals to workers, but also pipeline row processing so that downstream stages start before the entropy decode finishes. If there are no restart markers, the entropy decode is serial, and the decoder must rely on pipelining. The DRI value is a contract, but the decoder can choose how to honor it.

## Decoding without restart markers: row waves and speculative boundaries

When restart markers are absent, the entropy-coded segment is one long serial dependency. The decoder cannot jump into the middle of the scan without knowing the bit position and the DC predictors. That does not mean the entire decode is serial. It means the entropy decode is serial, while the block transforms and color conversion are parallel. The practical design is a row-wave pipeline. The entropy decoder decodes MCUs in scan order and writes quantized coefficients into a ring of MCU row buffers. A pool of workers consumes completed rows, performs dequantization, IDCT, chroma upsampling, color conversion, and output packing. The producer runs ahead until the ring is full, then blocks. The consumers run behind, and the ring provides backpressure.

The ring size should be measured in MCU rows, not in MCUs. For 4:2:0, one MCU row contains 2 luma rows and 1 chroma row for each chroma component. The worker that processes that row needs the chroma samples for the corresponding luma rows. If the worker processes one luma row at a time, it may need the chroma row above and below for a vertical filter. Processing a full MCU row gives it all the context it needs. The ring can hold three to six MCU rows. That is enough to absorb bursts in entropy decode and to keep the consumers busy, while keeping the working set inside L2. A larger ring increases memory traffic and may evict the coefficient rows that are about to be consumed.

Row completion is the synchronization point. The entropy decoder knows when it has finished writing a row. It can publish a row completion counter with a release fence. A worker that claims the row performs an acquire load. The counter should be padded so that updates from different rows do not share a cache line. If the decoder uses a single global counter for all rows, the workers will contend on it. A per-row counter or a small array of counters indexed by row is better. The worker can also claim a row by atomically incrementing a row index, which is simpler and avoids per-row counters. The row index is a single atomic variable, but it is updated once per row, not once per block. That is cheap enough.

Speculative boundaries are tempting but rarely worth it. One could imagine starting a worker at an MCU row boundary, guessing the bit position and DC predictors, and then correcting later. The problem is that the bit position at a row boundary depends on every Huffman code before it. The DC predictors depend on every DC coefficient before it. A wrong guess produces garbage that cannot be corrected without re-decoding the entire prefix. For a single image, the cost of re-decoding is usually higher than the benefit of speculation. The exception is when the decoder has a fast way to compute the state at row boundaries, such as a previous pass that recorded the state. But that previous pass is itself a serial entropy decode. It can be useful for very large images if the first pass only records bit offsets and DC predictors, and the second pass decodes in parallel. However, recording DC predictors requires decoding the DC coefficients, which is a significant fraction of entropy decode. The two-pass approach doubles the entropy work and adds memory traffic. It is rarely a win on a CPU with a fast scalar Huffman decoder.

A better use of row boundaries is error recovery. If a worker encounters an invalid Huffman code, it can stop at the current MCU row and report the error. The rest of the rows can still be decoded by the serial producer, because the producer has the correct state. The damaged row can be concealed with DC-only blocks or a neutral fill. This is not full fault isolation like restart markers, but it prevents a single error from corrupting the entire image. The decoder can also record the bit position of the last valid MCU and resume from there if the error is recoverable. In practice, most baseline JPEG files are valid, and the error path is cold. The main benefit of row-wave pipelining is that it overlaps the serial entropy stage with the parallel transform stage, which is exactly what is needed when restart markers are absent.

## Coefficient handoff and the cost of getting data into SIMD shape

The entropy decoder produces quantized DCT coefficients in zigzag order. The IDCT wants them in natural order, or in a transposed natural order, depending on the implementation. The dequantization step multiplies each coefficient by the corresponding quantization table value. These three operations—zigzag reorder, dequantization, and layout transpose—can be fused into the coefficient write path. The entropy decoder already knows the zigzag index of each coefficient. It can use a lookup table that maps the zigzag index to the transposed position in the coefficient block. It can also multiply by the combined dequantization and IDCT scale factor at the same time. The result is that the coefficient buffer is written once, in the layout the IDCT prefers, with the scaling already applied. This eliminates a separate pass over the coefficients and a separate transpose.

The combined scale table is per quantization table and per coefficient position. When the DQT marker is parsed, the decoder can precompute 64 values for each quantization table. If the IDCT uses fixed-point AAN scaling, the combined value is the quantization table value multiplied by the AAN scale factor for that position. The product must fit in 32 bits. Quantization table values are 1..255, and the AAN scale factors are small integers or fixed-point fractions. The combined value is typically less than 2^24, so a 32-bit multiply is safe. The dequantization loop then loads the quantized coefficient, multiplies by the combined value, and stores the result. With SIMD, the decoder can process eight coefficients at a time: load eight 16-bit coefficients, widen to 32-bit, multiply by eight 32-bit combined values, and store. The combined values are constant for the block, so they can be loaded once and kept in registers.

Sparse blocks are common in JPEG, especially in flat regions. A block with only a DC coefficient has no AC coefficients. Its IDCT output is a constant value in every pixel. The decoder can detect this case and fill the 8x8 output block with the DC value, skipping the IDCT entirely. A block with all zero coefficients is even simpler: it produces a constant 128 after the level shift. These fast paths can significantly reduce IDCT work on smooth images. The entropy decoder can set a flag when it decodes a block. The flag can indicate DC-only, all-zero, or full. The worker can then choose the appropriate path. The flag should be stored in the coefficient buffer or in a separate small array. The separate array is more cache-friendly if the coefficient buffer is large, because the worker can scan flags and only touch coefficients for full blocks.

The coefficient buffer layout should also consider false sharing. A block is 64 coefficients. If each coefficient is 16 bits, a block is 128 bytes, exactly two cache lines. If two workers write adjacent blocks and the blocks are not aligned, they can share a cache line. Aligning each block to 128 bytes avoids this. The alignment costs memory, but it prevents coherence traffic that can be more expensive than the extra memory. If the decoder uses a row of blocks, it can pad the row to a cache-line boundary. The same applies to the row completion counters and the queue indices. Padding is cheap insurance against false sharing.

## Allocation, page faults, and the hidden cost of first touch

A parallel decoder allocates several buffers: the compressed input, the coefficient ring, the output image, and per-worker scratch space. The allocation strategy affects performance as much as the scheduling. If the decoder uses malloc for each row buffer during decode, the allocator lock can become a bottleneck. A better approach is to allocate all buffers once, before decoding starts, and recycle them. The row ring is a fixed array of row buffers. The worker scratch space is per-worker and allocated when the thread pool is created. The output image is allocated by the caller, but the decoder should know its layout and alignment.

Page faults are a hidden cost. When a large buffer is allocated with malloc or mmap, the pages are not physically mapped until they are touched. The first write to each page triggers a page fault, which can be expensive. If the decoder touches the pages during decode, the page faults are spread across the decode and can dominate the early rows. A better approach is to pre-touch the buffers before the timed decode. The decoder can write a zero to each page or use mmap with MAP_POPULATE. Pre-touching moves the page fault cost to setup, where it can be measured separately. For a 4K image, the output buffer is about 24 MB. Pre-touching it takes a few milliseconds, but it avoids unpredictable stalls during the parallel stages.

Huge pages can reduce TLB misses. A 4K image's coefficient ring and output buffer can span many pages. If the system supports transparent huge pages, the decoder can advise the kernel with madvise(MADV_HUGEPAGE). Explicit huge pages are more reliable but require configuration. The benefit is largest for the output buffer, which is written sequentially and read by the display pipeline. The coefficient ring is smaller and fits in L2, so huge pages matter less there. The decoder should not require huge pages, but it can use them when available.

NUMA adds another layer. On a multi-socket system, memory is local to a node. A worker that writes to a buffer allocated on a remote node pays a bandwidth penalty. The decoder should allocate row buffers with first-touch policy on the node where the worker runs. If the thread pool pins workers to cores, the worker can allocate its own scratch space and touch the row buffers it will process. A global coefficient buffer written by all workers is a NUMA anti-pattern. The row ring avoids this because each row buffer can be owned by the worker that processes it, and the producer writes into rows that are local to the consumer if the scheduler assigns rows carefully. The simplest approach is to allocate the ring on the node of the first worker and accept some remote traffic, but for large images, per-node rings are better.

## Adaptive scheduling and feedback from the bitstream

A static schedule is easy to reason about, but JPEG bitstreams are not uniform. Some restart intervals contain many nonzero coefficients and take longer to decode. Some MCU rows contain high-frequency detail and take longer to IDCT. A decoder can adapt by measuring the cost of work items and adjusting the schedule. The entropy decoder can record the number of bytes or the number of nonzero coefficients per interval. The IDCT scheduler can use that information to balance work. If the decoder uses a global atomic counter for work items, the workers naturally balance because they pull the next item when they are free. The counter does not need to know the cost. It only needs to have enough items. The tail effect is reduced when the number of items is much larger than the number of workers.

For row-wave pipelining, the producer can publish rows as they complete. The consumers pull rows in order. If one row is expensive, the workers that finish early can steal the next row. The row index atomic counter provides this naturally. The only constraint is that a row cannot be processed until its chroma context is available. For 4:2:0, the chroma rows are tied to the luma rows, so the producer must finish the corresponding chroma blocks before publishing the row. The producer can publish a row when the last MCU in that row is decoded. The consumers can then process rows out of order, as long as each row has its own buffer and the output rows are disjoint. Out-of-order processing improves load balancing but can hurt cache locality if the rows are far apart. A small window of rows, such as four to eight, is usually enough to balance without destroying locality.

Feedback can also control the ring size. If the consumers are consistently faster than the producer, the ring stays full and the producer blocks. That is fine; it means the entropy decoder is the bottleneck. If the producer is faster, the ring stays empty and the consumers starve. The decoder can then increase the number of consumers or fuse stages to reduce their cost. The decoder can expose these counters through a profiling interface. The counters are per-stage and per-thread, and they can be aggregated at the end. The goal is not to build a self-tuning decoder that changes its strategy mid-image. The goal is to give the developer enough information to choose the right strategy for the target workload. A decoder that is fast on a 4K 4:2:0 image with restart markers may be slow on a 1080p 4:4:4 image without them. The dependency graph is the same, but the balance between stages is different. The scheduler should be explicit about which stage it is optimizing, and the profiler should show whether that stage is actually the bottleneck.
