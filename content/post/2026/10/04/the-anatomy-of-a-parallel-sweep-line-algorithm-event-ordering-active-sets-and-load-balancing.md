Sweep-line algorithms are one of the most productive ideas in computational geometry. They turn a two-dimensional problem into a one-dimensional event stream, process that stream in order, and maintain a small amount of state that captures the relationship between the sweep line and the geometry. The sequential version is elegant: sort the events, walk the sweep line, update an active set, and report intersections or build an arrangement. The parallel version is hard for a reason that is easy to state and difficult to engineer around: the sweep line is a moving serialization point. The event order is data-dependent, the active set is mutable, and the next event may be discovered only after processing the current one.

This article examines the design space for parallel sweep-line algorithms for planar segment intersection and closely related planar arrangement problems. It assumes familiarity with sequential sweep-line algorithms, balanced search trees, and basic parallel programming. It does not claim a universal speedup. Parallel sweep-line algorithms are not a drop-in replacement for the sequential algorithm. They are a different engineering trade-off: more complex state management, more memory, and more careful determinism in exchange for the possibility of using multiple cores on large geometry workloads.

## A concrete model and its invariants

Consider a set of line segments in the plane. A sweep-line algorithm processes events in order of a sweep coordinate. For a vertical sweep line, the events are segment endpoints and segment intersections. The sweep line is the line x = t. The active set is the set of segments currently crossing that line, ordered by their y-coordinate at x = t. The event queue is a priority queue ordered by x, with tie-breaking by y and event type. The algorithm repeatedly removes the next event, updates the active set, and may insert new intersection events. For Bentley-Ottmann, the active set is a balanced search tree; each event touches a constant number of neighbors. The sequential complexity is O((n + k) log n), where n is the number of segments and k is the number of intersections reported. The log n comes from active-set operations and event-queue operations; the k comes from reporting.

The state is not just the active set. It includes the event queue, which contains future intersections discovered so far. The event queue is a consequence of the active set history. If two segments become adjacent in the active set, their intersection may be scheduled. If they later cease to be adjacent, the scheduled event may be stale. The algorithm therefore carries a mixture of geometric state and speculative state. A parallel implementation must preserve both the geometric invariants and the staleness rules.

The usual assumptions are general position: no two events share an x-coordinate except endpoints, no three segments intersect at one point, no vertical segments, and no overlapping collinear segments. Real systems cannot assume general position. Vertical segments, shared endpoints, collinear overlaps, and multiple intersections at one point are common in CAD, GIS, and map rendering. These degeneracies are not cosmetic. They change the active-set ordering and the event ordering, and they create ties that a parallel scheduler must resolve deterministically. A robust parallel sweep-line algorithm needs a symbolic perturbation or an explicit tie-breaking scheme that is consistent across partitions.

## The sequential sweep as a state machine

The sequential sweep is a state machine. The state consists of the active set, the event queue, and the output accumulated so far. The transition function takes the next event, updates the active set, and may enqueue new events. The invariant is that the active set contains exactly the segments crossing the sweep line, ordered by their y-coordinate, and that the event queue contains all future events that are currently known to be relevant. The algorithm is correct if it processes events in the total order defined by x, then y, then event type, and if it never discards an event that could affect the active set or the output.

The active set is the obvious serialization point. Every event reads and mutates the ordered set. Two events at nearby x-coordinates may touch the same neighbors. If the active set is a balanced tree, concurrent updates require locking or a concurrent ordered map. But the deeper problem is not data-structure contention. It is that the event order is data-dependent. The next event depends on intersections discovered by previous events. You cannot simply sort all events up front because intersection events are not known until the sweep reaches the segments that create them.

This is different from a parallel sort or a parallel scan. In a parallel scan, the dependency is a fixed associative operation over a known array. In a sweep-line algorithm, the dependency is a dynamic geometric state. The active set at x = t is a function of all events before t. The event queue at x = t is a function of the active set history before t. The output at t is a function of the active set and the event. The sweep is a sequential fold over a stream whose future elements are generated by the fold itself. That is the core difficulty.

There are still sources of parallelism. The input segments can be preprocessed in parallel. The plane can be partitioned into slabs. Events within a slab can be processed in parallel if the slab's entry state is known. The active set can be represented as a persistent data structure so that slabs can share state without copying. The output can be written in parallel if the ordering is deterministic. The challenge is to find a decomposition that does not require the full sequential state at every step.

## Event ordering and the partial order

A parallel sweep-line algorithm needs a partial order on events. The full order is a total order by x, then y, then event type. The partial order is the subset of that order that actually affects correctness. Two events that are geometrically independent can be reordered. Two events that share an active-set neighbor or a discovered intersection cannot. The partial order is dynamic because new events create new dependencies. A scheduler can exploit the partial order only if it can compute or approximate it cheaply.

One approach is to define a static partial order by x-coordinate. Events in disjoint x-intervals are independent if no segment crosses both intervals in a way that creates an intersection event. But segments can cross many intervals. A long segment is active across a wide range of x. It can interact with events far away. Static partitioning by x alone does not eliminate dependencies; it only moves them to the boundaries.

Another approach is to use a two-phase algorithm. In the first phase, compute the active set at a set of vertical cut lines. In the second phase, process each slab between cuts in parallel, starting from the computed active set. The first phase is itself a sweep, but it only needs to compute the active set at the cuts, not all intersection events. This is a form of parallel prefix over the sweep state. The cost of the first phase depends on how many segments cross the cuts and how many intersections are needed to establish the active set. If the cuts are sparse, the first phase is cheap but the slabs are large. If the cuts are dense, the first phase is expensive but the slabs are small. The trade-off is between boundary-state computation and slab parallelism.

## Slab decomposition and boundary state

Slab decomposition is the most natural parallelization. Choose cut lines x = c0 < c1 < ... < cm. Each slab is the region between two cuts. The sweep within a slab is sequential, but slabs can run in parallel if each slab knows the active set at its left cut. The active set at a cut is the set of segments crossing that cut, ordered by y. It also includes the event queue state at that cut: which intersections have been discovered and which are pending. The event queue state is harder to compute than the active set because it depends on the history of adjacency changes.

If we ignore intersection events and only compute the active set, the boundary state is just the set of segments crossing the cut. That is easy to compute in parallel: for each segment, find the cuts it crosses, and insert it into the corresponding cut's active set. The hard part is the event queue. A segment pair may become adjacent before the cut and produce an intersection after the cut. The slab processor needs to know about that pending intersection. If it does not, it may miss an intersection or report it twice. The boundary state must therefore include a conservative superset of pending events. A conservative superset is safe but may cause duplicate work and false conflicts. A precise superset is expensive to compute.

This is a classic trade-off in parallel sweep-line design: conservative boundary state versus precise boundary state. Conservative state is easier to compute and makes the algorithm correct with less synchronization. Precise state reduces redundant work but requires more sequential computation. The right choice depends on the density of intersections and the cost of duplicate reporting. In a map-rendering pipeline where intersections are rare, conservative state may be fine. In a CAD kernel where intersections are dense, precise state may be necessary.

## Load balancing

Load balancing is the second major challenge. Even if the boundary state is known, slabs are not equally expensive. A slab with many segments and many intersections takes longer than a sparse slab. A static assignment of slabs to threads will suffer from skew. Dynamic assignment helps, but the work is not independent: a slab's cost is not known until it runs. A scheduler can use a work-stealing queue of slabs, but it must respect the boundary-state dependencies. A slab can start only after its left boundary state is ready. This creates a wavefront: slab i depends on slab i-1's boundary state. If boundary states are computed sequentially, the parallel section is limited. If boundary states are computed in a parallel prefix, the wavefront can be wider.

There is also intra-slab parallelism. Within a slab, the active set operations are sequential in the sweep order, but the slab may contain independent clusters of segments. A cluster is a connected component of the intersection graph within the slab. Clusters can be processed in parallel if their active sets are disjoint. Finding clusters is itself a geometric problem, but it can be approximated by spatial indexing. The cost of clustering must be amortized against the work saved. For small slabs, clustering overhead dominates. For large slabs, clustering can expose useful parallelism.

## Memory and determinism

Parallel sweep-line algorithms stress memory systems. The active set is an ordered structure with pointer chasing. The event queue is a priority queue with irregular access. The output is a stream of intersections that may be written in parallel. False sharing and allocation contention can erase the gains from parallel slabs. A practical implementation should use arena allocation per slab, batch event insertion, and avoid global locks in the active set. If the active set is a concurrent tree, the contention on the root and the cache-line ping-pong on hot nodes can be severe. A slab-local active set with a merge step is often better than a single global concurrent active set.

Determinism is another constraint. If the output order matters, parallel slabs must produce results in a deterministic order. This usually means buffering per-slab output and merging in slab order. Buffering costs memory and can become a bottleneck if one slab produces many intersections. An alternative is to assign each intersection a deterministic key and sort the output, but sorting is expensive. The best choice depends on whether the consumer needs a total order or only a set. For a set, per-slab buffers can be concatenated. For a total order, the merge must respect the sweep order.

The next design question is how to compute boundary states without serializing the whole sweep. That is where the event-order partial order and the active-set representation meet.

## Boundary state as a geometric query, not a sweep artifact

The active set at a vertical cut x = c is a geometric fact: it is the set of segments that intersect the line x = c, ordered by their y-coordinate at that line. This order is independent of the sweep history. Two segments may have swapped order earlier due to an intersection, but at x = c their relative order is determined solely by their y-values at c. This observation has a strong consequence: the boundary state for a slab can be computed without simulating the sweep up to that cut. We do not need to know which intersections occurred before c. We only need to know which segments cross c and how they are ordered at c.

This does not mean the sweep history is irrelevant for the slab itself. The slab processor must still run a sweep from c to the next cut, discovering intersections and updating the active set. But the initial state is a pure geometric query. The event queue can be reconstructed from the boundary state and the set of segment endpoints inside the slab. Specifically, the slab processor starts with the active set at c. It inserts all segment endpoints with x in (c, c_next]. It also schedules intersections between adjacent segments in the initial active set whose intersection x lies in (c, c_next]. As the sweep proceeds, new adjacencies are created and new intersection events are scheduled. This is exactly the sequential algorithm, but with a known initial active set.

The cost of computing boundary states is therefore the cost of answering many vertical stabbing queries and sorting the results. For a single cut, we can find all crossing segments by testing each segment, which is O(n). Sorting the crossing segments by y at the cut takes O(k log k), where k is the number of crossings. For m cuts, the naive cost is O(m n + sum k_i log k_i). If m is large, this dominates. We can do better by using a parallel segment tree or an interval tree. We can also process cuts in a sweep that only maintains the set of active segments, but we still need to sort them at each cut. Sorting at each cut is the expensive part. However, if cuts are evenly spaced, the active sets at adjacent cuts differ by a small number of insertions and deletions (segments that start or end between the cuts). The relative order of segments that cross both cuts can change only if they intersect between the cuts. But wait: the order at cut c1 and cut c2 can change due to intersections between c1 and c2. So we cannot simply update the sorted order by insertions and deletions; we must account for swaps. But the swaps are exactly the intersections. If we do not process intersections, we cannot know the order at c2 from the order at c1. However, we can compute the order at c2 directly by evaluating y at c2. That is a geometric computation. So the only way to avoid O(k log k) per cut is to use a data structure that can answer the order at a cut efficiently. For example, we can use a kinetic sorted list? Not exactly.

Actually, the order of segments at a cut is determined by their y-values. If we have many cuts, we can compute the y-value of each segment at each cut it crosses. This is a set of points (c, y). We can sort them per cut. The total number of such points is sum k_i. If segments are long, this can be O(n m). So we want to choose cuts such that the total number of crossings is manageable. This is a load-balancing problem: we want to partition the x-axis into slabs such that each slab has a similar number of segment-crossings and endpoints. The number of crossings per slab is the integral of the number of active segments over x. If we choose cuts at equal intervals of the cumulative active-segment count, we can balance the boundary-state computation. This is analogous to choosing cut points in a parallel prefix sum. We can compute the active-segment count as a function of x by a sweep that only processes endpoints. This sweep is sequential but cheap: it does not process intersections. It just maintains a count of active segments. We can compute the cumulative count at any x. Then we can choose cuts so that each slab has approximately the same total active-segment length. This gives a balanced partition for the boundary-state computation. However, the actual work in a slab depends on the number of intersections, not just the active-segment length. A slab with many crossings but few intersections may be cheap, while a slab with few crossings but many intersections may be expensive. So we need a better cost model.

## Adaptive cut placement and work estimation

Static cuts based on segment endpoints are easy but can be unbalanced. Adaptive cut placement refines the partition based on estimated work. The process can be parallel and iterative. Start with a small number of cuts, say one per thread. Compute the boundary states for these cuts. Then run the slabs and measure their actual work: number of events processed, number of intersections reported, time spent. If a slab is overloaded, split it by inserting a new cut inside it. The new cut's boundary state can be computed independently using the geometric query. Then the slab is replaced by two slabs. This is a form of parallel divide-and-conquer. The splitting can be done concurrently for different slabs. The challenge is to avoid oversplitting and to keep the boundary-state computation cheap.

Work estimation without running the slab is possible if we have a spatial index. For a slab, we can estimate the number of intersections by counting pairs of segments whose bounding boxes overlap and whose intersection x lies in the slab. This can be done with a sweep or a range query. It is not exact but can guide splitting. Another approach is to use a random sample of segments to estimate intersection density. For CAD and GIS workloads, intersection density is often clustered. A slab that contains a dense cluster will be expensive. We can detect clusters by building a grid over the slab and counting segments per cell. If a cell has many segments, it is likely to have many intersections. We can then split the slab at the cluster boundary. This is a heuristic but can be effective.

Adaptive cut placement also interacts with determinism. If we split a slab, the new cut must be placed at an x-coordinate that does not coincide with an event. We can choose a cut at a random x within the slab, or at the midpoint. The boundary state at that cut is computed geometrically. The slab processors then use the new boundary state. The output must still be deterministic. Since the cuts are only used for partitioning, the final output is the union of intersections from all slabs. If we merge outputs by global event key, the result is deterministic regardless of how we partition. So adaptive partitioning does not affect determinism as long as the tie-breaking is global.

## Active-set representations for slab-local sweeps

Within a slab, the active set is accessed by a single thread. This removes the need for concurrency control, but it does not remove the need for efficient ordered-set operations. The active set must support insertion, deletion, predecessor, successor, and swap of adjacent elements. A balanced binary search tree is the standard choice. For slab-local use, a treap or a red-black tree with parent pointers is sufficient. The tree can be allocated from a per-slab arena to avoid global allocator contention. If the boundary state is provided as a sorted array, we can build the initial tree in O(k) time by recursively choosing the median. This is faster than inserting k elements one by one.

During the sweep, we insert segments when their left endpoint is encountered. If multiple segments share the same left endpoint x, we can sort them by y and insert them in order. This is important for degeneracies. We also delete segments when their right endpoint is encountered. The swap operation at an intersection exchanges the positions of two adjacent segments. In a balanced tree, this can be done by deleting both and reinserting them in swapped order, or by a specialized rotation. The latter is more efficient but more complex. For a slab-local tree, the simpler delete-and-reinsert is often acceptable because the number of swaps is proportional to the number of intersections, which is the dominant cost anyway.

An alternative to a tree is a skip list. Skip lists are easier to implement with concurrent operations, but for slab-local use, they have higher constant factors. A B-tree can be more cache-friendly. For very small slabs, a sorted array with binary search and insertion via memmove may be faster than a tree. The choice depends on the slab size and the number of events. A hybrid approach can use a sorted array for small active sets and switch to a tree when the size exceeds a threshold.

If we want to avoid recomputing boundary states for every slab, we can use a persistent active set. The left slab's active set at its right cut is exactly the right boundary state. If the left slab uses a persistent tree, it can pass the tree to the right slab without copying. The right slab then starts its sweep with that tree. This eliminates the need to compute the boundary state at the cut by a geometric query. However, the left slab's final active set must exactly match the geometric active set at the cut. If there are degeneracies or if the left slab's sweep is not perfectly synchronized with the cut, there may be discrepancies. Also, persistent trees require path copying on every update. If the slab has many updates, the memory overhead can be large. A hybrid approach is to use a persistent tree only for the boundary state, but use a mutable tree within the slab. The boundary state is computed once and then converted to a mutable tree. This avoids path copying during the sweep.

## Intra-slab parallelism and cluster decomposition

Within a slab, the sweep is sequential, but the slab may contain independent geometric clusters. Two segments belong to the same cluster if they are connected by a chain of intersections within the slab. If the clusters are separated in y, their active sets are disjoint. We can process them in parallel by splitting the active set into y-intervals. This is a form of 2D decomposition. The slab is divided into horizontal bands. Segments that cross a band boundary complicate the split. We can handle them by duplicating the boundary state. This is similar to the slab decomposition but in the y-direction. The combination of x and y decomposition leads to a grid. Each cell in the grid can be processed independently if we know the boundary states on its left and bottom edges. This is more complex because the sweep line is vertical, so the bottom edge is not a natural boundary. However, we can use a different sweep direction for each cell, or we can use a divide-and-conquer approach.

A simpler form of intra-slab parallelism is to process independent connected components of the intersection graph. We can build the graph by using a spatial index to find pairs of segments whose bounding boxes overlap and whose intersection x lies in the slab. This is expensive. A cheaper heuristic is to use the active set itself: when the sweep line is at x, the active set is ordered by y. If there is a large gap in y between two consecutive segments, it is unlikely that any segment will cross that gap. We can split the active set at such gaps and process the two halves in parallel. This is a dynamic split. The two halves are independent until a segment crosses the gap. We can detect crossings by monitoring the gap. If a segment is inserted that spans the gap, we merge the halves. This is a form of speculative parallelism. It can be effective if the geometry has natural separations. However, it adds complexity and may not be worth it for dense intersections.

For most workloads, the slab-level parallelism is sufficient. The number of slabs can be much larger than the number of threads, so dynamic scheduling can balance the load. Intra-slab parallelism is only needed if the number of slabs is small or if a single slab dominates. In that case, adaptive cut placement can split the slab further. So intra-slab parallelism is an alternative to adaptive cuts. It may be more efficient because it avoids recomputing boundary states. But it requires a more complex active-set representation that supports splitting and merging.

## Event ordering within a slab and deterministic output

Within a slab, the event queue is a priority queue ordered by x, then y, then event type, then segment IDs. The slab processor processes events in this order. When it discovers a new intersection, it inserts it into the queue. The queue must handle duplicate events: the same intersection may be scheduled multiple times if the segments become adjacent, then non-adjacent, then adjacent again. The standard technique is to check if the intersection is still valid when it is popped. This check requires comparing the current neighbors of the two segments. If they are no longer adjacent, the event is stale and is discarded. This is the same as the sequential algorithm.

Determinism requires that the tie-breaking at equal x and y is consistent across slabs. If two events have the same x and y but different segment IDs, the order is determined by the segment IDs. This is a global order. The slab processor can use it without knowing about other slabs. The only issue is events exactly at slab boundaries. We must define whether a boundary event belongs to the left slab or the right slab. A common convention is to use half-open intervals: a slab covers [c_i, c_{i+1}). Events at c_i are processed by the slab that starts at c_i, except for events that are exactly at the cut and involve segments that end at c_i. This requires careful handling. A simpler convention is to assign each event to the slab that contains its x-coordinate, with ties broken by y and segment ID. If an event is exactly at a cut, it is assigned to the slab on the right. The left slab stops before the cut. This avoids double processing.

Output merging: each slab produces a stream of intersections sorted by the global event key. To produce a total order, we can merge these streams. Since slabs are processed in parallel, we can buffer each slab's output and then perform a k-way merge. The merge can be done with a heap of size m, where m is the number of slabs. The total cost is O(K log m), where K is the total number of intersections. This is usually acceptable because K is the dominant cost. If K is small, the merge overhead is negligible. If K is large, the log m factor is small compared to the sweep cost. Alternatively, we can use a concurrent priority queue that allows slabs to insert intersections directly. But that creates contention. Buffering and merging is simpler and more deterministic.

## Load balancing with dependencies: wavefront scheduling

If boundary states are computed upfront for all cuts, slabs are independent and can be scheduled dynamically. This is the simplest parallel structure: a parallel phase for boundary states, then a parallel phase for slabs. The boundary-state phase can be load-balanced by distributing cuts across threads. The slab phase can use a work-stealing queue of slabs. Since slabs have different costs, dynamic scheduling is important. We can also use a priority queue of slabs ordered by estimated cost, so that the most expensive slabs start first. This reduces the tail effect.

If boundary states are computed on demand, we have a wavefront. Slab i can start only after slab i-1 has finished and produced its right boundary state. This serializes the slabs. To avoid this, we can compute boundary states for a subset of cuts in parallel, then start slabs between those cuts. This is a two-level scheme. For example, we can compute boundary states for every 10th cut in parallel, then start 9 slabs between each pair of computed cuts. The inner slabs can compute their own boundary states on demand? No, they need the boundary state at their left cut. If we only computed every 10th cut, the inner slabs do not have boundary states. They would need to compute them. But they can compute them by running a sweep from the nearest computed cut? That defeats the purpose. Alternatively, we can compute all boundary states in parallel. The cost is O(m * k log k). If m is chosen so that each slab has enough work, the boundary-state cost is amortized.

The real dependency issue is that the boundary state at a cut depends on all segments crossing that cut, which is a global property. It does not depend on other boundary states. So all boundary states can be computed independently in parallel. There is no wavefront for boundary-state computation. The wavefront only appears if we try to compute boundary states by sweeping from left to right. But we do not need to do that. We can compute each boundary state directly. This is a key insight: the parallel sweep-line algorithm does not need a sequential sweep to compute boundary states. It can use a parallel geometric query. This eliminates the serialization point. The only serialization is within each slab, which is local.

So the parallel algorithm is:
1. Choose cuts.
2. Compute boundary states at all cuts in parallel.
3. Process all slabs in parallel.
4. Merge outputs.

This is embarrassingly parallel except for the boundary-state computation, which is also parallel. The challenge is load balancing and degeneracies.

## Degeneracies and symbolic perturbation in parallel

Degeneracies break the assumptions of general position. Vertical segments cannot be handled by a vertical sweep line. A common solution is to rotate the plane by a small angle so that no segment is vertical. But this rotation must be consistent across all slabs. If we use floating-point, the rotation may introduce inconsistencies. We can use exact arithmetic or a symbolic perturbation. A symbolic perturbation can be applied to the input segments before partitioning. For example, we can perturb the endpoints by a tiny amount based on their index. This makes all coordinates distinct and removes vertical segments. The perturbation must be global. If each slab applies its own perturbation, the segments may not match at boundaries. So the perturbation is applied once, before any partitioning. The perturbed segments are then used for all boundary-state computations and slab sweeps. The output is the intersections of the perturbed segments, which may differ slightly from the original. In many applications, this is acceptable if the perturbation is small enough. Alternatively, we can use exact arithmetic and handle degeneracies explicitly. This is more expensive but robust.

Collinear overlaps are another degeneracy. Two segments that overlap along a line create infinitely many intersection points. The standard approach is to split the segments at the overlap boundaries. This preprocessing can be done in parallel by sorting segments by their supporting line and then finding overlaps. The result is a set of non-overlapping segments. This increases the number of segments but makes the sweep well-defined.

Multiple intersections at the same point: if three or more segments intersect at a single point, the active set order is ambiguous. The standard solution is to process all events at that point in a batch. When the sweep line reaches the point, all segments involved are adjacent in some order. The algorithm must report the intersection and then reorder the segments. In a parallel setting, this is local to the slab. The batch processing can be done sequentially within the slab. The tie-breaking by segment ID ensures a deterministic order.

## Memory and cache considerations for slab-local active sets

Slab-local active sets are mutable and can be allocated in an arena. Each slab gets a memory pool. This reduces allocation contention and improves locality. The event queue can be a binary heap or a pairing heap. For small slabs, a sorted array with binary search may be faster due to cache locality. For large slabs, a heap is better. The active set tree nodes should be small and packed. Use indices instead of pointers to reduce pointer chasing. A B-tree or a cache-aware tree can improve performance. False sharing: if multiple slabs write to adjacent memory, we need padding. Per-slab arenas avoid this. Output buffering: each slab writes intersections to a local buffer. The buffer is flushed when full. To avoid contention on the global output, we can use a concurrent queue or per-slab files. If we need deterministic order, we can write to per-slab buffers and merge.

The boundary-state arrays are read-only during the slab sweep. They can be shared across threads without locks. This is a big advantage of computing boundary states upfront. The arrays should be stored in a compact format: an array of segment IDs sorted by y. The slab processor builds a balanced tree from this array. Building a tree from a sorted array takes O(k) time and can be done with a simple recursive function. This is much faster than inserting k elements one by one. The tree can be built in parallel? No, it is local to the slab.

The event queue can be initialized with a batch of events. We can sort the initial events by the global event key and build a heap in O(e) time. This is faster than inserting them one by one. During the sweep, new events are inserted one at a time. The heap operations are O(log e). The active set operations are O(log k). The total cost per event is O(log n). This is the same as the sequential algorithm. The parallel speedup comes from processing multiple slabs concurrently.

Memory usage is a concern. Each slab needs its own active set and event queue. If we have many slabs, the total memory can be large. We can limit the number of active slabs by using a work-stealing queue with a bounded number of threads. Each thread processes one slab at a time. So the memory per thread is the size of one slab's state. This is manageable. The boundary-state arrays for all cuts must be stored. If we have m cuts and each cut has k segments, the total memory is sum k_i. This can be large if m is large. We can reduce memory by computing boundary states on demand or by using a compressed representation. For example, we can store the boundary state as a persistent tree, which shares structure between adjacent cuts. But this requires that the boundary states are computed by a sweep that updates the tree. If we compute them independently, we cannot share structure. So there is a trade-off between memory and computation.

## A sketch of a parallel algorithm

We can now sketch a complete parallel algorithm for planar segment intersection. The input is a set of n segments. The output is a set of intersection points.

1. Preprocess: handle degeneracies by symbolic perturbation or explicit splitting. Compute bounding boxes.
2. Choose initial cuts. A simple choice is to divide the x-range into m equal-width slabs, where m is a multiple of the number of threads. A better choice is to use the cumulative active-segment count to balance the expected number of crossings.
3. Compute boundary states. For each cut, find all segments that cross it. This can be done in parallel by distributing segments across threads and having each thread insert its segments into the cuts they cross. Then sort each cut's segments by y at the cut, with tie-breaking by segment ID. The result is a sorted array for each cut.
4. Estimate work per slab. Use the number of segments crossing the slab, the number of endpoints in the slab, and a heuristic for intersection density. If a slab is estimated to be too expensive, split it by inserting a new cut. Recompute the boundary state for the new cut. Repeat until the estimated work is balanced or a maximum number of cuts is reached.
5. Process slabs in parallel. Use a work-stealing queue. Each slab runs a sequential Bentley-Ottmann sweep. The initial active set is built from the sorted array at the left cut. The event queue is initialized with all segment endpoints in the slab and all intersections between adjacent segments in the initial active set that fall in the slab. The sweep processes events, updates the active set, and writes intersections to a local buffer.
6. Merge outputs. If a total order is required, merge the per-slab buffers using a k-way merge by the global event key. If only a set is required, concatenate the buffers.

This sketch leaves many details open: how to choose the number of cuts, how to estimate work, how to handle degeneracies, and how to optimize memory. But it shows that the parallel sweep-line algorithm is not a single algorithm but a family of algorithms parameterized by the boundary-state computation and the load-balancing strategy. The next sections will explore these parameters in more detail.

## Cost models for cut placement

The first sketch suggested equal-width or equal-active-count cuts. Neither is sufficient for planar geometry workloads with clustered intersections. A better cut set minimizes the maximum estimated slab cost while keeping boundary-state computation affordable. This is a min-max partitioning problem over a one-dimensional domain with a cost function that is not known exactly. We can approximate the cost of slab i as

C_i = α E_i + β A_i + γ P_i + δ K_i,

where E_i is the number of endpoints in the slab, A_i is the integral of the active-segment count over the slab, P_i is an estimate of the number of intersecting pairs, and K_i is the number of intersections. K_i is what we ultimately care about, but it is unknown before the sweep. E_i and A_i are cheap to compute exactly with a parallel prefix over segment endpoints. P_i can be estimated from a spatial index or a grid.

The active-segment integral A_i captures the amount of work in maintaining the active set. If a slab has many long segments, A_i is large even if there are few intersections. The endpoint count E_i captures the number of insertions and deletions. The pair estimate P_i captures the potential for intersection events. For many CAD and GIS datasets, P_i is the dominant term. A simple estimator is to overlay a uniform grid on the slab, count the number of segments whose bounding boxes overlap each cell, and sum choose(c, 2) over cells. This overestimates because not every pair in a cell intersects, but it correlates well with intersection density. The grid can be built in parallel per slab, and the sum can be reduced with a parallel reduction. The grid resolution should be chosen so that the average number of segments per cell is small, say between 2 and 8. If the grid is too coarse, the estimate is noisy; if it is too fine, the grid construction dominates.

A more accurate estimator uses a random sample of segment pairs. For each slab, sample S pairs from the active set and test whether their bounding boxes overlap and whether their intersection x lies in the slab. The fraction of sampled pairs that intersect gives an unbiased estimate of the intersection density, up to the sampling variance. The sample size S can be chosen based on the desired confidence and the cost of the sweep. This is a form of Monte Carlo load estimation. It is cheap and can be done in parallel. The downside is variance: a slab with a small number of intersections may be misclassified. To reduce variance, combine the grid estimate with the sample estimate. Use the grid to identify dense regions and the sample to calibrate the density.

Once we have a cost model, we can choose cuts by a parallel greedy algorithm. Sort the candidate cut positions by the cumulative cost function. The cumulative cost F(x) = ∫ C(t) dt. We want to choose m cuts such that F(c_{i+1}) - F(c_i) is approximately equal. This is a parallel prefix sum followed by a search for quantiles. The search can be done with a parallel binary search or a sample-based quantile selection. The result is a set of cuts that balance the estimated cost. Because the cost estimate is approximate, the actual load may still be skewed. Adaptive refinement, described later, can correct the imbalance.

## On-demand boundary states and memory trade-offs

Storing boundary states for all cuts can be memory-prohibitive. If there are m cuts and each cut has k_i crossing segments, the total memory is sum k_i. For long segments and many cuts, sum k_i can be O(n m). For example, n = 10^6 segments and m = 10^4 cuts gives 10^10 entries in the worst case, which is impossible. In practice, segments are not all long, but the worst case is real for map data with long roads or power lines. We need a way to avoid storing all boundary states.

The simplest solution is on-demand boundary-state computation. Each slab computes its own left boundary state when it starts. It does not store it for other slabs. The right boundary state is not needed unless the slab is split or unless the next slab is processed by the same thread. If slabs are independent and scheduled dynamically, each slab can compute its left cut by a geometric query. The cost is one stabbing query per slab, which is O(n) if done naively, or O(log n + k) with an interval index. The interval index is built once and shared. The query returns the segments crossing the cut. The slab then sorts them by y at the cut. This sorting is O(k log k). The total cost over all slabs is O(m (log n + k log k)). This is the same as computing all boundary states upfront, but the memory is O(k) per active slab instead of O(sum k). The trade-off is recomputation: if a cut is used by two slabs (as the right boundary of the left slab and the left boundary of the right slab), it may be computed twice. But if we assign each cut to exactly one slab as its left boundary, and the right boundary of a slab is the left boundary of the next slab, then each cut is computed once, except the last cut. The left slab does not need its right boundary state because it stops at the cut. The right slab computes its left boundary state. So each interior cut is computed exactly once, by the slab on its right. This is efficient.

The on-demand approach also simplifies adaptive splitting. When a slab is split, the new cut's boundary state is computed by the slab that continues on the right. The left half does not need to know the new boundary state except to stop at the new cut. The right half computes it. This avoids a global synchronization point. The only shared state is the interval index and the output buffers.

The interval index must support stabbing queries for arbitrary x. A segment tree over x-coordinates is a natural choice. Build the segment tree over the sorted unique x-coordinates of all endpoints and intersections? We do not know intersections in advance. We only need to query at cut positions, which we choose. We can build a segment tree over the x-range, with each node storing the segments that span the node's interval. A stabbing query at x traverses the root-to-leaf path and collects segments stored at each node. This returns all segments crossing x. The tree can be built in parallel by distributing segments and inserting them into the nodes they span. The insertion is O(log n) per segment. The query is O(log n + k). The memory is O(n log n) in the worst case, but with a balanced segment tree and interval stabbing, the storage can be O(n log n). For n = 10^6, this is about 20 million entries, which is manageable. If memory is tight, use an interval tree with O(n) storage and O(log n + k) query. The interval tree is harder to build in parallel but can be built by sorting endpoints and using a parallel divide-and-conquer.

## Duplicate suppression and event ownership at cuts

When boundary states are computed independently, an intersection may be discovered by more than one slab. This can happen if the intersection lies exactly on a cut, or if a conservative boundary state includes segments that do not actually intersect in the slab. The standard sequential algorithm avoids duplicates by processing each event exactly once in the total order. In a parallel setting, we need a global ownership rule.

Define the sweep domain as the half-open interval [x_min, x_max). For each slab i, let its interval be [c_i, c_{i+1}). The slab processes all events with x in [c_i, c_{i+1}). Events with x = c_i belong to slab i, not to slab i-1. Events with x = c_{i+1} belong to slab i+1. This rule assigns every event to exactly one slab. The boundary state at c_i includes all segments crossing c_i. The slab i starts with this active set. It must process any intersection at x = c_i that involves two segments in the active set. But wait: if an intersection is exactly at c_i, it is an event at the left boundary. The active set at c_i contains both segments. The slab i should schedule and process that intersection. However, the intersection may have been already discovered by the previous slab if the previous slab's sweep reached c_i? No, the previous slab stops before c_i. It does not process events at c_i. It may have discovered the intersection earlier if the segments became adjacent before c_i. But if the intersection is exactly at c_i, the segments are adjacent at c_i. The previous slab would have scheduled the intersection when they became adjacent, but the event x is c_i, which is outside its interval. So the previous slab should discard or not schedule events with x >= c_i. The slab i, starting with the active set at c_i, will see that the two segments are adjacent in the initial active set. It must schedule their intersection at c_i. This is a special case: the initial active set may contain adjacent pairs whose intersection is exactly at c_i. The slab i must check all adjacent pairs in the initial active set and schedule those whose intersection x >= c_i and < c_{i+1}. If the intersection x is exactly c_i, it is scheduled and processed. If it is less than c_i, it should not happen because the segments are ordered by y at c_i; if they intersected before c_i, their order would have swapped. But due to degeneracies or floating-point error, it might happen. The slab should ignore intersections with x < c_i. This is a robustness check.

For intersections strictly inside the slab, the slab's sweep will discover them exactly once, because the active set is local. However, if the boundary state is conservative and includes segments that do not actually cross the cut (e.g., due to bounding-box overestimation), the slab may see false adjacencies. These false adjacencies can schedule false intersections. To avoid this, the boundary state must be exact: it must contain exactly the segments crossing the cut, ordered by their y at the cut. This is achievable with exact predicates or careful floating-point. If exactness is not possible, the slab must validate every intersection event when it is popped, by checking that the two segments are still adjacent and that their intersection x lies in the slab. This is the same staleness check as in the sequential algorithm. It handles false events and duplicates.

Duplicate intersections across slabs can also occur if a segment is active in two adjacent slabs and an intersection is exactly at the cut. The ownership rule assigns it to the right slab. The left slab does not process it. The right slab processes it. So no duplicate. If an intersection is reported by both slabs due to a bug or due to conservative state, the output merge must deduplicate. Since every intersection has a canonical key, duplicates will be adjacent in the sorted merge. A simple merge with equality check removes them. If the output is a set, a hash set can be used.

## Parallel boundary-state construction with interval indexes

The interval index is the enabling data structure for on-demand boundary states. Building it in parallel is a key implementation task. A segment tree over the x-axis can be built by a parallel divide-and-conquer. The x-range is divided into intervals. Each segment is assigned to the nodes it spans. This is a classic parallel segment tree construction. The tree has O(n) nodes if we use a dynamic segment tree or O(n log n) if we use a static array. For stabbing queries, a static segment tree with sorted arrays at each node is efficient. Each node stores the segments that span its interval, sorted by y at the node's midpoint? Actually, for stabbing at x, we need the segments sorted by y at x. The order can change with x. So we cannot store a single sorted order per node. We must sort at query time. This is the expensive part.

An alternative is to use a kinetic sorted list? No. The order at a cut is determined by y at that cut. If we query many cuts, we can precompute the y-values of each segment at each cut it crosses. This is a set of points. We can sort them per cut. This is exactly the boundary-state computation. There is no way around sorting per cut if we want the exact order. However, we can avoid sorting from scratch by using the fact that the order at adjacent cuts changes only by swaps at intersections. But we do not know intersections. If we did, we could update the order incrementally. But computing intersections is the goal. So we must sort each cut independently. The total sorting cost is sum k_i log k_i. This is acceptable if m is small relative to n. If m is large, we can use a parallel radix sort or a parallel sample sort per cut. For integer coordinates, radix sort is O(k) per cut. For floating-point, we can use a parallel merge sort.

The stabbing query itself can be parallelized by distributing cuts across threads. Each thread handles a subset of cuts. For each cut, it traverses the segment tree and collects segments. The traversal is independent per cut. The segments collected are then sorted. This is embarrassingly parallel. The only shared state is the read-only segment tree. The tree construction can also be parallelized by distributing segments across threads and using atomic updates or per-thread buffers. A simpler approach is to build the tree sequentially if n is moderate, or use a parallel sort of segments by left endpoint and a sweep to build the tree. The sweep is sequential, but it can be replaced by a parallel prefix over the endpoints.

If the number of cuts is very large, the memory for the segment tree may be large. We can use a grid instead. A uniform grid over the x-axis with cell size chosen so that each cell contains a manageable number of segments. For a cut, we only need to examine segments in the cell containing the cut and neighboring cells if segments span multiple cells. This is an approximation but can be made exact by storing segments in all cells they span. The grid is easier to build in parallel: each segment is inserted into the cells it spans. The insertion can be done with atomic append to per-cell lists. The query is then a simple lookup. The grid is less memory-efficient than a segment tree for long segments, but it is simpler and often faster for moderate n. The choice depends on the segment length distribution. For map data with many short segments, a grid is excellent. For CAD data with many long segments, a segment tree is better.

## Adaptive splitting and work stealing

With on-demand boundary states, a slab is self-contained: it can compute its left boundary state, run its sweep, and produce output. This makes it easy to schedule slabs dynamically. A work-stealing queue of slab intervals can be used. Each thread pops a slab, computes its left boundary state, and sweeps. If the slab is estimated to be too large, the thread can split it. Splitting requires choosing an x-coordinate inside the slab, computing the boundary state at that x, and creating two new slabs. The left slab continues on the same thread, and the right slab is pushed to the work queue. This is a form of parallel divide-and-conquer. The split point can be chosen by the cost model: find the x that divides the estimated cost into two roughly equal halves. This requires evaluating the cost function over the slab, which can be done with the same grid or sampling used for cut placement. The cost of evaluating the split point is amortized against the work saved.

The threshold for splitting should be based on the total remaining work and the number of active threads. A simple heuristic is to split if the estimated number of events in the slab is greater than some constant times the average slab size. The average slab size can be estimated from the total number of endpoints and the number of threads. If a slab is split too aggressively, the boundary-state computation overhead dominates. If it is not split enough, the tail effect remains. A practical approach is to start with a small number of slabs (e.g., 4 times the number of threads) and let adaptive splitting refine the load. The work-stealing queue ensures that idle threads pick up new slabs. The splitting can be done by the thread that owns the slab, so no global coordination is needed.

One subtlety is that splitting a slab changes the event ownership. The new cut becomes a boundary. Events exactly at the new cut must be assigned to the right slab. The left slab must stop before the cut. The right slab computes the boundary state at the cut and processes events with x >= cut. This is consistent with the half-open interval rule. The left slab may have already processed some events before the split? No, the split happens before the sweep starts. The thread estimates the cost and decides to split before processing any events. So no events are lost. If the split happens after some events are processed, it is a more complex operation. We can avoid this by splitting only at the beginning of a slab. If a slab turns out to be expensive after starting, it is too late to split without rolling back. To handle this, we can use a speculative approach: process the slab in chunks, and if a chunk is too slow, split the remaining part. This requires the active set at the split point, which is known after processing the chunk. This is essentially a dynamic split during the sweep. It is possible but requires careful handling of the event queue and output. For most workloads, pre-sweep splitting based on a good cost estimate is sufficient.

## Deterministic output merging and memory layout

The final output must be deterministic if the application requires it. With on-demand boundary states and adaptive splitting, the set of slabs is dynamic. The output order must be independent of the scheduling. The simplest way to achieve this is to assign each intersection a global key and sort the output. The key is (x, y, type, segment IDs). If the number of intersections is large, sorting can be expensive. A better approach is to buffer output per slab and merge in slab order. But with dynamic splitting, the slab order is a tree. We can assign each slab a deterministic interval [c_i, c_{i+1}). The intervals are disjoint and cover the x-range. We can collect the output of all leaf slabs and sort them by their left cut. Then merge. Since the intervals are ordered, the merge is a simple concatenation if each slab's output is already sorted by the global key. Within a slab, the sweep produces events in the global order. So each slab's buffer is sorted. The concatenation of buffers in slab order is sorted. This is true if the slabs partition the x-axis and each slab processes events with x in its interval. The only issue is events exactly at cuts: they are assigned to the right slab, so the left slab's buffer contains events with x < c, and the right slab's buffer contains events with x >= c. Concatenation in order gives a globally sorted stream. No merge is needed! This is a powerful property of the half-open interval assignment. If we split a slab, the left part covers [c_i, c_new) and the right part covers [c_new, c_{i+1}). The concatenation of left then right is still in order. So the output is deterministic and requires only a concatenation of per-slab buffers in the order of their intervals. This avoids the O(K log m) merge. The only cost is buffering all output until the end. If memory is a concern, we can write each slab's buffer to a separate file and concatenate the files. Or we can use a streaming approach: process slabs in order, but that would serialize. For parallel processing, buffering is necessary. The memory for output is O(K), which is the size of the result. This is usually acceptable because K is the output size. If K is huge, we can use a concurrent queue with a deterministic ordering by having each slab wait for its turn to flush. That would serialize the flush but not the computation. The flush can be done in a separate thread that merges buffers as they become ready. This is a producer-consumer pattern.

Memory layout for the per-slab state should be cache-friendly. The active set tree nodes can be stored in an array with indices. The event queue can be a binary heap in an array. The output buffer can be a dynamic array of intersection records. Each intersection record should be compact: two doubles for x and y, and two integers for segment IDs. If the segment IDs are large, use 64-bit integers. The total size is 24 bytes. For 10^8 intersections, this is 2.4 GB, which is large but manageable on modern servers. If memory is tight, compress the output or stream it to disk.

The boundary-state array is read-only and can be shared. It should be stored as a contiguous array of segment IDs sorted by y. The slab builds a balanced tree from this array. Building a tree from a sorted array can be done in O(k) time by recursively choosing the median. The tree nodes are allocated from the slab's arena. The arena is a large block of memory that is reset after the slab finishes. This avoids malloc/free overhead. The arena size can be estimated from the number of events and the active set size. If the estimate is too small, the arena can grow by allocating additional blocks. The blocks are linked together. This is a standard arena allocator.

False sharing is a concern when multiple threads allocate from their own arenas. The arenas should be aligned to cache lines. The output buffers should also be padded. If the output buffers are written by different threads, they should not share cache lines. Use per-thread buffers with padding. When merging, copy the buffers into a contiguous output array. The copy can be done in parallel by dividing the output array into chunks.

These implementation details determine whether the parallel sweep-line algorithm achieves good performance. The algorithmic structure—cuts, boundary states, slab-local sweeps, and deterministic concatenation—is sound. The engineering is in the cost models, the interval index, the arena allocator, and the work-stealing scheduler.
