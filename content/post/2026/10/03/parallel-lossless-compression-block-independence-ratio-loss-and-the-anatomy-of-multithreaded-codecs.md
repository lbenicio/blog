Lossless compression is a search for redundancy, and redundancy does not respect the boundaries of the machine that has to find it. A match at byte 4,000,000 may point back to byte 12. A Huffman table built from the first megabyte of a file may be exactly the wrong table for the last megabyte. Every serious general-purpose format is therefore a sequential algorithm wearing a disguise: a state machine that walks the input in order, updating a window, a set of frequencies, or a model as it goes. Modern hardware is built for the opposite. A 64-core server spends most of its compression time in one or two threads while the rest of the machine waits.

The obvious fix is to split the input, compress the pieces in parallel, and concatenate the results. That works, and it is what most production parallel compressors do. It also costs compression ratio, and the size of that loss — not the peak speedup — is the central engineering question of the field. This article is about the trade-off: where ratio goes when you parallelize, how much of it can be bought back, and how the format's own structure constrains what is possible.

## Why Lossless Compression Resists Parallelism

Three mechanisms account for almost all of the difficulty.

### Sliding-window matching is a serial state machine

The dominant technique in general-purpose compressors is LZ77 and its descendants: emit a literal byte, or emit a length-and-distance pair that points at earlier data. The set of legal distances is bounded by the window — 32 KiB in deflate, larger in LZMA and zstd — and the contents of that window at position i are a function of the input up to i. To know which matches are available at position i, you must already have processed everything before i. The encoder's decision at i is not just expensive to compute in isolation; it is *undefined* in isolation, because a match is only valid if the decoder, replaying the same prefix, will have the referenced bytes in its window.

This is the hard constraint, and it is worth stating precisely. Match finding is not a pure function of a local neighborhood. It is a function of the prefix. Any parallelization scheme either preserves that dependency or pays a price for breaking it.

Decompression has the mirror-image problem: to decode the last block you must decode the first, because the window is built from earlier output. That symmetry matters later, when we consider what a format has to declare in order to be parallelizable at all.

### Entropy coders carry adaptive state

The second stage — Huffman, arithmetic, or range coding — is frequently adaptive. The probability model is updated after every symbol, which makes the coder a strict serial recurrence. Even a non-adaptive static Huffman coder must be fed symbols in the order the match finder produced them.

Where the entropy coder is *not* adaptive within a block, the entropy stage parallelizes almost for free. Deflate's dynamic Huffman blocks each carry their own code tables. zstd's entropy-coded blocks carry precomputed tables. So the entropy stage rarely limits parallel speedup, while the match-finding stage almost always does. This asymmetry explains why nearly every practical parallel compressor parallelizes at the *block* level rather than at the *stage* level: the block boundary is the natural place where the entropy coder's state can be reset cheaply.

### Global transforms break the input apart

A third family applies a permutation to an entire block before coding. bzip2 is the canonical example: Burrows–Wheeler transform, move-to-front, run-length encoding, then Huffman. The transform is inherently global. The sorted rotation index depends on every byte of the block, and you cannot compute the BWT of two halves and combine the results, because the sort interleaves them.

That looks like a dead end for parallelism, but it is not, for a reason specific to the format: bzip2 already forces block boundaries. The format caps a block at 900,000 bytes, and a bzip2 file is a sequence of independent blocks, each with its own BWT, move-to-front state, and Huffman tables. A parallel bzip2 therefore does not need to invent a splitting strategy. It inherits one from the format specification, and the ratio cost is exactly zero relative to a serial bzip2 that would have made the same block boundaries anyway.

The general lesson is that parallelizability is a property of the format as much as of the implementation. Deflate has a 32 KiB window and no block-level state reset for match finding; LZMA2 has explicit dictionary-reset and state-reset flags; zstd has frames with independently coded blocks. A format that declares where state resets is a format that can be parallelized without heuristics.

## A Taxonomy of Parallel Compression Strategies

Four families cover essentially all deployed systems, and they differ mainly in where they spend ratio to buy speed.

**Independent blocks.** Split the input into chunks; compress each chunk as a self-contained stream; concatenate. Ratio cost is real but bounded and predictable. Speedup scales with cores until memory bandwidth or I/O saturates. This is what pigz, pbzip2, and multithreaded xz do.

**Stage parallelism.** Keep one serial match finder but run the entropy coder on a different core, feeding it through a queue. Ratio cost is zero. Speedup is limited by the slowest stage and by pipeline depth — typically a factor of two to three at best, because the stages are not equally expensive and the queues add latency.

**Assisted or speculative match finding.** Run match finding in parallel over overlapping regions, then reconcile the results serially at commit time. Ratio cost can be near zero if the reconciliation is done carefully. This is the family that academic work has focused on, and it is where the interesting algorithmic content lives.

**Intra-block data parallelism.** Vectorize the match finder, the entropy coder, or both using SIMD, bit-parallel techniques, or a GPU. This does not break the dependency chain; it makes each step of the chain cheaper. It composes with all of the above.

The rest of this article examines each family in turn, starting with the one that ships in your operating system.

## Family One: Independent Blocks

### Mechanics

The design is almost embarrassingly simple. Read the input, cut it at fixed offsets, hand each chunk to a worker, and write the resulting compressed streams in order. For formats that already define concatenation semantics — gzip members, bzip2 blocks, xz streams, zstd frames — this requires no format change at all.

pigz does exactly this with deflate: each chunk becomes its own gzip member with its own header, its own deflate stream, and its own CRC. Chunk sizes are on the order of a hundred kilobytes. pbzip2 splits at bzip2's 900 kB block ceiling. Multithreaded xz splits the input into blocks whose default size is a multiple of the LZMA2 dictionary size, and each block is compressed with a dictionary and state reset.

The LZ4 frame format makes the trade-off explicit in the bitstream rather than in the compressor's configuration. A frame header declares the maximum block size — 64 KiB, 256 KiB, 1 MiB, or 4 MiB — and carries a *block independence* flag. When the flag is set, blocks are decodable in any order and any number of decoders can work in parallel. When it is clear, each block may reference the previous 64 KiB, and decoding is a chain. The format designer chose to put the parallelization decision in the file, where the decoder can see it, instead of in a build flag.

### Where the ratio goes

Three effects reduce compression when you split a stream into independent blocks.

First, matches that would have crossed a boundary are lost. If the input contains a 200 KiB repeated region and your blocks are 128 KiB, at least one copy of that repeat falls on the wrong side of a boundary and cannot be referenced.

Second, each block must relearn its entropy tables. For a 1 MiB block this is negligible; for a 4 KiB block it can dominate, which is why nobody parallelizes deflate at 4 KiB granularity.

Third, and most subtly, each block's window starts empty. The first W bytes of a block cannot reference anything before them, where W is the window size. For deflate, W is 32 KiB; for LZMA with a 64 MiB dictionary, W is 64 MiB. The warm-up penalty as a fraction of block size is roughly W/B, so a 64 MiB LZMA dictionary in a 128 MiB block wastes about half of the block's potential match range on data that has nothing to match against. This is a back-of-the-envelope argument, not a measurement, but it captures the shape of the problem correctly: the block size must be comfortably larger than the window, or the ratio collapses.

The two effects compound in a way that makes small blocks much worse than the linear estimate suggests, and it explains why parallel compressors tend to use the largest blocks their memory budget allows.

### Choosing a block size

Four constraints pull in different directions.

*Format limits.* bzip2 cannot exceed 900 kB per block. LZ4 frames top out at 4 MiB per block. Deflate has no block-level limit but a 32 KiB window that sets a floor on sensible chunk sizes.

*Load balance.* You want enough blocks that every core has work, plus headroom for stragglers. A common heuristic is at least four blocks per worker, so that a core that draws an unusually compressible chunk does not become the critical path.

*Memory.* Every worker holds a window or dictionary of size W, plus input and output buffers. With 64 MiB LZMA dictionaries and 32 workers, the dictionaries alone consume 2 GiB. On a machine compressing a 10 GiB file, that is the binding constraint, not the ratio.

*Ratio target.* Everything above is subordinate to how much ratio the application can afford to lose. For a nightly archival job that runs once and is read rarely, take the largest blocks the memory allows. For a network protocol compressing small messages, block independence is forced by the message boundaries and the ratio question is moot.

### Determinism

Independent-block parallelism has a property that is easy to overlook and hard to retrofit: it is deterministic. Block boundaries are a pure function of the input, and each block's compressed representation depends only on that block. The output bytes are the same whether you use one thread or sixty-four, whether the scheduler runs blocks left to right or right to left.

That matters more than it used to. Content-addressed storage keys objects by the hash of their compressed form. Reproducible build systems compare artifact hashes across machines. Deduplicating backup systems want the same input to yield the same chunks regardless of how many cores the client had. A compressor that produces different bytes on different machines is a compressor that silently breaks all three.

The one wrinkle is metadata. gzip's member header contains a modification timestamp and an operating-system byte. If the compressor copies the source file's mtime into every member, two runs on identical input at different times produce different bytes. Implementations that care about reproducibility zero the field. This is a small detail with an outsized effect on whether a parallel compressor can be used in a content-addressed pipeline.

### Buying ratio back: priming and recompression

The independent-block design has a cheap refinement that recovers a meaningful fraction of the lost ratio. Instead of starting each block with an empty window, feed the tail of the preceding input as a prefix dictionary. The worker still needs only the raw input, which is available immediately — the dependency is on bytes of the *input*, not on the *compressed output* of the previous block, so the blocks remain fully parallel. The decompressor, however, must have those same bytes, which means the format must either store the prefix explicitly or require sequential decoding. zstd's multithreaded mode handles this by having each job use a prefix of the preceding input as a dictionary, with the overlap size controlled by a parameter; the cost is a slightly larger frame and a decoder that must respect the dependency.

A second, more aggressive refinement is two-level compression: compress each block independently, then compress the concatenation of the compressed blocks with the same or a cheaper codec. The second pass sees structure that the first pass could not — repeated headers, repeated entropy tables, repeated literal sequences — and recovers a portion of the inter-block redundancy at the cost of a full extra pass over the (much smaller) intermediate stream. It is not free, and it is not universally applicable, but it is a useful pattern for archival systems where write throughput matters less than final size.

The independent-block family is the simplest, the most widely deployed, and the easiest to reason about. It is also the family with the crudest ratio model: it trades ratio for speed in a way that depends entirely on how much redundancy happens to be long-range. The next family attacks the problem from the opposite direction, keeping the ratio exactly and paying for parallelism in coordination instead.

## Family Two: Stage Parallelism

Stage parallelism accepts the serial match finder and asks a different question: if one stage must be serial, can the other stages run concurrently with it? The answer is usually yes, and the ratio cost is usually zero. The price is paid in speedup rather than in bits.

A typical LZ encoder has three stages. The match finder walks the input, maintains the window, and decides whether each position is a literal or a length-distance pair. The entropy coder takes that token stream and turns it into bits, using Huffman tables, range coding, or some other model. The writer emits bytes and checksums. Only the match finder needs the window. The entropy coder needs the tokens in order and, for adaptive coders, its own model state. The writer needs the encoded bytes. Those are different resources, and they can live on different cores.

The mechanical design is a producer-consumer pipeline. The match finder produces a batch of tokens for block n; the entropy coder consumes the batch for block n-1. A bounded queue connects them. The queue provides backpressure: if the entropy coder falls behind, the match finder blocks instead of allocating unbounded memory. If the match finder falls behind, the entropy coder idles. Batch size is the tuning knob. Small batches reduce latency and increase synchronization overhead. Large batches amortize synchronization but increase memory and pipeline fill time. A batch covering 64 to 256 KiB of input is a reasonable starting point for general-purpose compressors.

The ratio is unchanged because the token sequence is unchanged. There is no new block boundary, no window reset, and no entropy-table reset. The decoder sees exactly the stream a serial encoder would have produced, assuming the parser's decisions do not depend on asynchronous entropy state. In deflate, the Huffman tables are built from token frequencies after parsing, so the parser never needs to wait for the entropy coder. In zstd, entropy tables are chosen after parsing as well. The separation is clean. In LZMA, the optimal parser uses price estimates derived from a probability model; if the entropy coder updates that model asynchronously, the parser may see stale prices and make different decisions. To preserve exact output, the parser can keep a synchronized copy of the model, or the implementation can accept a small divergence. Many encoders use approximate prices anyway, so byte-identical output across thread counts is not automatic. That is a determinism issue, not a ratio issue, but it matters for content-addressed storage and reproducible builds.

The speedup is bounded by Amdahl's law in its simplest form. Let f be the fraction of serial execution time spent in the match finder. A two-stage pipeline that perfectly overlaps the entropy coder can do no better than 1/f. If match finding is 70 percent of the work, the ceiling is about 1.43x. If it is 50 percent, the ceiling is 2x. If it is 90 percent, the ceiling is 1.11x, and the pipeline is barely worth the complexity. At high compression levels, match finding usually dominates, so stage parallelism gives a modest constant-factor improvement rather than core-count scaling. At low compression levels, the entropy coder is a larger fraction, but total time is small and I/O often dominates. Stage parallelism is therefore not a strategy for using sixty-four cores. It is a strategy for recovering one or two cores when ratio cannot be sacrificed and block splitting is unavailable.

The design becomes more interesting in formats where blocks share a window but reset entropy state. The match finder for block n+1 can run while the entropy coder for block n is still working. It does not need block n's compressed bytes; it needs the raw bytes of block n, which are already in memory. The decoder will decode block n first, so matches from block n+1 into block n are valid. If the entropy state carries across blocks, the entropy coder remains a serial chain and cannot be parallelized without a reset, but the match finder can still run ahead. This is a useful pattern for chained formats: serial entropy, pipelined match finding, no ratio loss. If the entropy state resets per block, the entropy coder can also be parallelized across blocks, and the design becomes a hybrid of stage parallelism and independent blocks.

Implementation details matter more than the high-level diagram. The token queue should be a single-producer, single-consumer ring buffer with cache-line padding on the indices to avoid false sharing. Tokens should be packed, not allocated individually. A deflate token can fit in a 32-bit word for literals and a 64-bit word for matches; a tagged union or a pair of arrays avoids per-token branching. The window should be allocated with huge pages when available and placed on the same NUMA node as the match finder. The entropy coder is memory-light, so pinning it to a core on the same node reduces queue traffic. Avoid placing the two stages on hyperthread siblings of the same physical core; they compete for execution resources and the pipeline stalls. For small inputs, skip the pipeline entirely and compress serially. The fill and drain overhead is not worth it below a few hundred kilobytes.

Stage parallelism is a bad fit when the format interleaves parsing and entropy coding symbol by symbol, so the parser cannot proceed without the coder's exact state. Some arithmetic-coded LZ variants have that property. It is also a poor fit when the entropy coder is the bottleneck and the match finder is already vectorized. In that case, adding a queue does not help; the coder needs to be parallelized, which usually means block resets. The family is at its best when the match finder is expensive, the entropy coder is cheap, and the format forbids or discourages block independence. It buys ratio neutrality at the cost of a hard speedup ceiling.

## Family Three: Assisted and Speculative Match Finding

The independent-block family breaks the prefix dependency. Stage parallelism preserves it but leaves match finding serial. The third family tries to have both: parallel match finding with the full prefix available to every worker. The enabling observation is that LZ77 matches are defined by raw bytes, not by prior token decisions. If worker j is given the W bytes before its segment, it can construct the same window the serial encoder would have at the segment start. It can then find matches for positions in its segment exactly as the serial encoder would, at least for matches that begin and end within the segment. The compressed output of earlier blocks is irrelevant; only the decompressed bytes are needed, and those are the input.

This is not a loophole; it is the structure of LZ. The serial dependency is on the window contents, which are a prefix of the input. Since the input is available, the dependency can be satisfied by reading backwards. That is why parallel LZ is possible at all. The difficulty is everything else: parse decisions, token ownership, entropy state, and memory.

Two designs dominate. The first separates candidate generation from parsing. Workers compute matches for each position in their segment, using the prefix as context. They do not decide the final parse; they produce a list of candidate matches. A serial parser consumes the candidates in order and makes the same decisions it would have made serially, provided the candidate lists are complete enough. If the parser only needs the best few matches at each position, the lists can be pruned. Pruning is where ratio can be lost: if the parser would have chosen a match that was pruned, the output diverges. Keep enough candidates and the loss is negligible. The serial parser is simple and fast relative to match finding, so the parallel workers do the expensive work and the parser does the cheap coordination. This design is attractive because it preserves a single token stream and a single compressed stream. The decoder is unchanged and serial.

The second design lets workers parse independently and reconciles at boundaries. Each worker parses its segment using the prefix, emitting a complete token sequence. At a boundary, the left worker may emit a match that extends into the right worker's segment. That is legal in the token stream; the decoder does not know about segments. The right worker may also have emitted tokens for those same positions. The reconciler discards the redundant right tokens and resumes the right stream at the first position not covered by the left match. If a right token crosses the resume point, it must be split or the right worker must reparse a small suffix. This is speculative parsing: workers speculate that their tokens will survive, and the reconciler repairs the few that do not. The amount of repair depends on the overlap. If workers are given a lookahead of at least the maximum match length, the left worker can compute the full length of any match that starts near the boundary, so the reconciler knows exactly how far the left token reaches. The right worker's tokens that are covered are discarded. The ratio loss is limited to cases where the right worker's parse would have been better if it had known the left worker's choice. Since LZ parsing is greedy or near-greedy, these cases are rare. With a larger overlap and a smart cut point, the loss can be made arbitrarily small at the cost of duplicated work.

The important architectural consequence is that assisted match finding does not require block independence in the format. The output is a normal single stream. The decoder rebuilds the window by decoding from the beginning, exactly as it would for a serial encoder. This is the opposite trade-off from independent blocks: compression is parallel, decompression is serial. That is acceptable for write-once archival, log ingestion, and offline batch compression, where the encoder is the bottleneck and the decoder runs later, perhaps on a machine with different parallelism. It is not acceptable for a format that must support parallel random access, where independent blocks are mandatory.

Memory is the tax. Each worker needs the prefix window, the segment, and a match index. The prefix is read-only and could in principle be shared, but the index over it is not: hash chains and binary trees are built by insertion, and each worker builds its own over prefix plus segment. If the window is 64 MiB and the segment is 128 MiB, the worker builds an index over 192 MiB. That is a lot of memory per worker. The usual mitigation is to make segments much larger than the window, so the prefix is a small fraction of the work and the memory. If the segment is ten times the window, the prefix index costs ten percent extra. If the segment equals the window, the prefix index doubles the work and the memory. This is the same warm-up arithmetic that governs independent blocks, but it appears in the encoder's memory budget rather than in the compressed size.

Entropy coding remains a constraint. If the format has adaptive entropy state that spans the whole stream, the entropy coder is still serial. The parallel match finder can produce tokens faster than the coder consumes them, so the coder becomes the bottleneck. At that point the design is a pipeline: parallel match finding feeding a serial entropy coder. The speedup is bounded by the entropy coder's share of the work. If the format resets entropy state per block, the entropy coder can also be parallelized across blocks, and the design becomes a hybrid. If the format uses static tables per block, the entropy stage is embarrassingly parallel once the tables are known. The tables depend on the token frequencies, which depend on the parse, so there is still a barrier between parsing and coding for each block. But that barrier is per block, not per stream.

A two-level design often makes sense. The outer level splits the input into independent frames for decoder parallelism. The inner level uses assisted match finding within each frame to keep encoder parallelism. The frame boundary costs ratio, but the inner parallelism recovers encoder speed without further ratio loss. Alternatively, the outer level uses chained frames with a shared dictionary for ratio, and the inner level uses speculative parsing for speed. The decoder remains serial across frames, but that may be fine if the application is asymmetric. The choice depends on which side of the pipeline is the bottleneck and how much ratio the application can afford to lose at the outer boundaries.

Determinism is harder here than in independent blocks. The reconciler must make the same decisions regardless of thread scheduling. If it chooses between two crossing matches based on arrival order, the output depends on timing. The fix is to define a deterministic merge order: always prefer the leftmost token, or the longest token, or the token with the smallest distance, with ties broken by position. The workers must produce enough information for the reconciler to apply that rule without seeing the schedule. This is a design constraint, not an afterthought. A speculative compressor that is fast but nondeterministic is difficult to use in content-addressed storage or reproducible builds. The same discipline that makes independent blocks deterministic can be applied, but it has to be designed into the reconciliation protocol from the start.

The family is best understood as a spectrum. At one end is pure candidate generation with a serial parser: ratio is exact or near-exact, parallelism is limited by the parser, and the implementation is simple. At the other end is fully speculative parsing with a lightweight reconciler: parallelism is high, ratio loss is small but nonzero, and the implementation is complex. The right point depends on the format's entropy model, the cost of match finding relative to parsing, and the application's tolerance for ratio loss. The next family pushes parallelism inside a single block, where the window itself becomes the unit of vectorization and the boundary problem disappears into the instruction set.

## Family Four: Intra-Block Data Parallelism

The first three families change the shape of the dependency graph. The fourth leaves it alone and makes each node cheaper. The prefix dependency is still there. The window is still built in order. But the operations that build it -- hashing, comparing, inserting, scanning -- are performed on multiple bytes at a time, using the vector units that have been sitting in every CPU since the late 1990s. This is not a way to use sixty-four cores. It is a way to make one core do the work of four or eight, and it composes with every other family in the taxonomy.

The easiest place to apply SIMD is the match finder's inner loop. A hash chain search compares the current position against a list of previous positions. Each comparison is a memcmp of up to the maximum match length. A scalar memcmp checks one byte at a time or uses a word-at-a-time loop. A vectorized version loads 16, 32, or 64 bytes from both positions, compares them, and finds the first mismatch with a mask and a count-trailing-zeros instruction. For long matches, the loop is memory-bound and the limit is cache bandwidth, not instruction count. For short matches, which dominate in most inputs, the vector compare can cut the search cost by a factor of two to four. The same idea applies to hash computation: a rolling hash over a 4-byte or 8-byte window can be computed for several positions at once, though the dependency between consecutive positions limits the benefit for strong hashes.

The parser is harder to vectorize because it is a dynamic program. Optimal parsing for LZ77 computes a cost for each position and chooses the best predecessor. The recurrence is sequential: cost at position i depends on the cost at position i minus length for all valid lengths. There are parallel algorithms for dynamic programming, but they are not a natural fit for the small, irregular state of an LZ parser. A more practical approach is to vectorize the price computation and the range checks, while keeping the sequential scan. This is what many high-performance encoders do: the parser remains scalar, but the match finder and the entropy coder are vectorized. The parser is often not the bottleneck at high compression levels; match finding is.

The entropy coder is a different story. Huffman decoding can be vectorized with multi-symbol tables, but encoding is a serial bit-packing problem. Range coding is worse: the state update is a serial recurrence, and the multiplication and normalization steps are not independent. There are vectorized range coders that process multiple independent streams, but that requires the format to define multiple streams. Some formats do: a block can be split into several sub-streams, each with its own entropy coder, and the decoder interleaves them. This is a form of intra-block parallelism that does not break the match window. The sub-streams share the same token sequence and the same window, but they are coded independently. The ratio cost is small if the sub-streams are long enough to amortize the model reset. The decoder can decode them in parallel, which is useful for read-heavy workloads. The encoder can also encode them in parallel, but it must first produce the token sequence, which is serial. So the speedup is limited to the entropy stage.

GPUs take intra-block parallelism to an extreme. A GPU has thousands of threads and high memory bandwidth. Match finding can be mapped to a GPU by computing hashes for all positions in parallel, then using a parallel sort or hash table to find candidates. The candidate lists are then filtered and scored on the GPU or copied back to the CPU. The prefix dependency is handled by processing the input in chunks and including the previous chunk as context. This is essentially assisted match finding with a very wide SIMD machine. The challenges are the same: memory allocation, load balancing, and the PCIe transfer. For large files, the transfer can be overlapped with computation, but the match finder's random access patterns are not GPU-friendly. The technique is most attractive for specialized workloads where the input is already on the GPU or where the compression ratio can be slightly lower.

The important point is that intra-block parallelism does not change the ratio. It changes the constant factor. If a serial compressor achieves 3:1 and a vectorized version achieves 3:1, the vectorized version is strictly better. The only ratio cost is the one imposed by the format's block structure, which is orthogonal. This is why every serious compressor implementation uses SIMD where it can. It is free ratio-wise, and it is often the difference between one core keeping up with a 10 GbE link and not.

## Two-Level Designs: Combining Independent Blocks with Assisted Match Finding

The families are not mutually exclusive. The most practical parallel compressors combine them. A two-level design uses independent blocks at the outer level to enable parallel decoding, and assisted match finding or stage parallelism at the inner level to enable parallel encoding. The outer level sets the ratio floor. The inner level sets the encoder speed. The decoder sees a sequence of independent blocks and can decode them in any order. The encoder sees a sequence of large blocks and can use multiple threads within each block.

The key parameter is the outer block size. It must be large enough that the ratio loss from block independence is acceptable. It must be small enough that the decoder can use many cores. It must also be small enough that the encoder's per-block working set fits in memory. For a 64 MiB LZMA dictionary, an outer block of 256 MiB gives a warm-up penalty of about 25 percent of the block, which is significant. An outer block of 1 GiB gives about 6 percent, which is better but limits decoder parallelism to the number of blocks. If the file is 10 GiB, 1 GiB blocks give ten blocks, which is enough for ten cores but not sixty-four. The trade-off is unavoidable: more blocks means more parallelism and more ratio loss.

A common compromise is to use a shared dictionary across blocks. The first block is compressed normally. Each subsequent block is compressed with a dictionary primed from the previous block's uncompressed data. The decoder must decode the previous block before it can decode the current block, so decoder parallelism is lost. But the encoder can still compress blocks in parallel if it has the raw data. This is a write-optimized design. It is used in some backup and archival systems where the encoder is the bottleneck and the decoder runs later. The ratio is close to a single-stream compressor because the dictionary is warm. The cost is that the decoder is serial. If the decoder is also parallel, the design must store the dictionary explicitly or use a format that allows random access to the dictionary. Some formats store a dictionary at the start of each block, which is a form of priming that costs space but preserves decoder parallelism.

A more sophisticated two-level design uses a hierarchical structure. The input is divided into superblocks. Each superblock is divided into blocks. The blocks within a superblock share a dictionary, so they can be decoded in parallel if the dictionary is available. The superblocks are independent. The dictionary for a superblock is either the tail of the previous superblock or a separate dictionary stored in the file. This gives a tunable trade-off: more superblocks means more parallelism and more dictionary resets; larger superblocks means better ratio and less parallelism. The format can declare the superblock size and the dictionary policy, so the decoder knows what to expect. This is essentially what LZ4's block independence flag does at a smaller scale, and what zstd's frame and block structure allows at a larger scale.

The two-level design also helps with load balancing. If the outer blocks are large, the encoder can split each block into smaller segments for parallel match finding. The segments are not independent for decoding; they are just work units for the encoder. The decoder still sees the outer block as a single unit. This is the assisted match finding family applied within each outer block. The encoder can use all cores, and the decoder can use all cores on different outer blocks. The ratio loss is only at the outer boundaries. The inner segments are reconciled into a single token stream, so there is no additional ratio loss. This is the design that most high-performance parallel compressors should aim for if the format allows it.

The implementation complexity is significant. The encoder needs a work-stealing scheduler, a segment-based match finder, a reconciler, and a parallel entropy coder. The decoder needs a block index, a way to allocate dictionaries, and a thread pool. The format must define the block boundaries, the dictionary policy, and the checksum granularity. None of this is insurmountable, but it is a lot of engineering for a feature that many users will never notice. The alternative is to use a format that already has these features, like zstd or LZ4, and let the format handle the parallelization. That is the pragmatic choice for most applications.

## What the Format Must Declare

The deepest lesson from all of this is that parallelization is a format-level decision. A compressor cannot invent parallelism that the format does not allow. It can only exploit the resets that the format already defines. Deflate defines a 32 KiB window and no block-level match reset. A parallel deflate must either use independent gzip members or accept a serial match finder. LZMA2 defines dictionary resets and state resets, so a parallel LZMA2 can use those resets to create independent blocks. Zstd defines frames and blocks, and its block independence flag makes the trade-off explicit. LZ4 defines a block independence flag in the frame header. bzip2 defines a 900 kB block limit. The format is the contract.

A format that wants to be parallelizable should declare at least four things. First, the window size or dictionary size. This determines the warm-up penalty and the minimum sensible block size. Second, the block boundaries. These can be fixed, variable, or determined by the encoder. Third, the state resets. A block boundary may or may not reset the match window, the entropy model, and the checksum. The format should say which. Fourth, the dictionary policy. If blocks can reference a shared dictionary, the format must say where the dictionary comes from and how it is stored. Without these declarations, a parallel implementation is guessing, and the ratio loss is unpredictable.

The decoder side is equally important. A parallel decoder needs to know which blocks can be decoded independently. If the format says a block depends on the previous block, the decoder must respect that dependency. If the format says a block is independent, the decoder can decode it in any order. The decoder also needs to know the maximum block size so it can allocate buffers. It needs to know the checksum granularity so it can verify blocks in parallel. It needs to know the dictionary policy so it can reconstruct the window. These are not optional details; they are the difference between a format that scales and a format that does not.

## Measuring the Cost of Parallelism

The ratio cost of parallelization is not a single number. It is a function of the input, the block size, the window size, and the format's reset policy. To measure it, you need to compare three things: the serial compressor, the parallel compressor with the same format, and the parallel compressor with a different format. The first comparison isolates the cost of the parallelization strategy. The second isolates the cost of the format.

A good methodology is to compress a representative corpus at several block sizes and record the compressed size, the compression time, and the decompression time. The block size should be varied from the window size to the file size. The ratio loss curve typically has three regions. At small block sizes, the loss is dominated by the warm-up penalty and the entropy table reset. At medium block sizes, the loss is dominated by cross-boundary matches. At large block sizes, the loss is small and the curve flattens. The knee of the curve is the smallest block size that gives acceptable ratio. That is the block size to use.

It is also useful to separate the loss into components. The warm-up loss can be estimated by compressing each block with a dictionary primed from the previous block and comparing the size. The cross-boundary match loss can be estimated by compressing the whole file serially and then compressing each block independently, then looking at the difference in match counts. The entropy table loss can be estimated by measuring the size of the entropy tables in each block. These estimates are rough, but they tell you which effect dominates and where to focus.

The measurements are sensitive to the input. A file with long-range redundancy, such as a source tree with many similar files, will suffer more from block independence than a file with mostly local redundancy, such as a binary executable. A file with a skewed byte distribution will suffer more from entropy table resets. A file with many short matches will suffer more from warm-up. There is no universal block size. The right choice depends on the data. A compressor that can adapt its block size to the data will outperform one that uses a fixed size, but adaptation adds complexity and can make the output nondeterministic if the adaptation depends on timing.

The cost of parallelization is also not just ratio. It is memory, CPU, and code complexity. A parallel compressor that uses 2 GiB of RAM to save 1 percent of ratio may be a bad trade on a machine that is also running a database. A parallel compressor that uses 64 threads to save 10 percent of time may be a bad trade on a machine that is already oversubscribed. The engineering decision is always multi-dimensional. The ratio loss is the most visible cost, but it is not the only one.

## Open Questions in Parallel Compression

The design space is still being explored. Several questions do not have settled answers.

How should a format expose parallelism without forcing a particular implementation? The current approach is to define blocks and resets, but that pushes a lot of complexity onto the encoder. A more declarative approach might let the encoder specify a dependency graph, and let the decoder schedule blocks accordingly. That would allow finer-grained parallelism and better ratio, but it would require a more complex decoder and a more expressive format.

How much ratio loss is acceptable for a given speedup? The answer depends on the application, but there is no standard way to express the trade-off. A user who is compressing a database backup cares about ratio and does not care about encoder speed. A user who is compressing a live video stream cares about encoder speed and can tolerate some ratio loss. A format that can adapt to both would be more useful than one that forces a single point on the curve.

Can we recover the ratio lost to independent blocks without giving up decoder parallelism? Priming and overlap help, but they require the decoder to have access to the dictionary. Storing the dictionary costs space. Deriving it from the previous block costs serial decoding. A hybrid approach might store a small dictionary and use it to prime several blocks, with a dependency graph that allows some parallelism. This is an open area of research.

How do we make parallel compression deterministic across different thread counts and schedules? Independent blocks are deterministic by construction. Assisted match finding and speculative parsing are not, unless the reconciliation protocol is carefully designed. A deterministic parallel compressor is easier to test, easier to cache, and easier to use in content-addressed storage. The extra discipline is worth it, but it is not free.

These questions are not just academic. They determine what the next generation of compression formats will look like. The answers will come from a combination of theory, measurement, and implementation experience. The important thing is to keep the trade-offs visible. A parallel compressor that hides its ratio cost is a compressor that will surprise its users. A format that declares its costs is a format that can be used with confidence.

## Work Scheduling and Load Balance in Parallel Codecs

Once block boundaries are chosen, the next problem is assigning blocks to threads. Static assignment is tempting: divide blocks evenly among workers. But compression time per block is not uniform. A block of zeros compresses quickly because match finding finds long matches immediately and entropy coding emits few symbols. A block of encrypted or already-compressed data compresses slowly because match finding fails repeatedly and the entropy coder emits many literals. The ratio between fastest and slowest block can be an order of magnitude. Static assignment therefore leaves cores idle while one worker finishes a straggler.

Dynamic scheduling fixes this. A shared queue of block indices; workers pop a block, compress it, write output. The queue can be a lock-free MPMC queue or a simple mutex-protected deque. For compression, the output order must be preserved. Workers write into preallocated slots indexed by block number. The final concatenation is a sequential copy of slots in order. This decouples execution order from output order.

Work stealing is a refinement. Each worker has a local deque of blocks; when idle, it steals from the back of another worker's deque. This reduces contention on a central queue. The granularity of stealing matters. Stealing one block at a time is fine if blocks are large. If blocks are small, stealing overhead dominates. A common approach is to steal half of the victim's remaining blocks. This is the same pattern used in task runtimes.

Over-decomposition is the scheduling analogue of small blocks. If you split the input into many small work units, load balance improves but ratio may suffer if each unit is independently compressed. The two-level design solves this: outer blocks are large for ratio, inner segments are small for scheduling. The encoder can split an outer block into segments for match finding, but the segments are not independent for decoding. The scheduler operates on segments, and the reconciler merges them into a single token stream for the outer block. This gives both ratio and balance.

Priority can matter. If the input is a stream, the compressor may want to emit early blocks first so the decoder can start. This is a latency concern, not a throughput concern. For batch compression, priority is irrelevant. For streaming, a scheduler that processes blocks in order but allows out-of-order completion may need a reorder buffer. The buffer size is bounded by the number of in-flight blocks. If the network or disk is the bottleneck, the reorder buffer can grow. Backpressure is needed.

Thread affinity and NUMA-aware scheduling also matter. A worker should process blocks whose input is on its local memory node. If the input is read from disk, the first touch determines the node. A scheduler that assigns blocks round-robin across nodes may cause remote memory access. A better policy is to partition the input by node and assign workers on the same node. This is an implementation detail, but at high core counts it can be the difference between linear and sublinear scaling.

Finally, scheduling must be deterministic if the output must be reproducible. The assignment of blocks to threads does not affect the compressed bytes if each block is independent. The output order is fixed by block index. So dynamic scheduling is safe for determinism as long as the compressor does not use timing-dependent decisions within a block. If it does, the scheduler can still be deterministic by recording the decisions, but that is a different problem.

## Memory Hierarchy, NUMA, and Cache Effects

Parallel compression is often described as CPU-bound, but at high thread counts it becomes memory-bound. The match finder's working set is the window plus the hash tables. The window is accessed sequentially for the current position, but match candidates are scattered. A hash chain lookup reads a chain of positions, each of which is a random access into the window. For a 32 KiB deflate window, the entire window fits in L1 or L2, so the random accesses are cheap. For a 64 MiB LZMA dictionary, the window is far larger than any cache. Every match candidate is a potential cache miss. The hash tables themselves are large and also cause misses. The result is that a single core's match finder is often limited by memory latency, not by instruction throughput. Adding more cores increases memory-level parallelism, which helps up to a point. Beyond that point, the memory controller saturates.

The first implication is that block size and window size should be chosen with the cache hierarchy in mind. A window that fits in L2 (typically 256 KiB to 1 MiB) gives fast match finding. A window that fits in L3 (several MiB to tens of MiB) gives moderate speed. A window larger than L3 gives slow match finding but better ratio. The parallel compressor's block size should be at least a few times the window size, so that the warm-up cost is amortized. But a huge window also means a huge working set per worker. With 32 workers, a 64 MiB window each is 2 GiB of windows alone, plus hash tables. That memory traffic can easily exceed the memory bandwidth of the machine.

NUMA adds another dimension. On a multi-socket server, memory is attached to sockets. A thread on socket 0 accessing memory on socket 1 pays a higher latency and consumes interconnect bandwidth. If the compressor allocates windows and hash tables with first-touch policy, the worker that initializes the memory determines its node. A common mistake is to allocate all buffers in the main thread, which places them on one node, then run workers on all nodes. The workers on the remote node suffer. The fix is to allocate per-worker buffers on the worker's node, either by initializing them in the worker thread or by using NUMA-aware allocation APIs. The input itself is usually read from disk or network; if it is read by a single thread, it lands on one node. A NUMA-aware reader can distribute pages across nodes, or the scheduler can assign blocks to workers on the node where the input resides.

Huge pages help. A 64 MiB window backed by 4 KiB pages requires 16,384 TLB entries. The TLB is much smaller. Every random access into the window can cause a TLB miss, which adds latency. Transparent huge pages or explicit hugetlbfs can reduce TLB misses dramatically. The same applies to hash tables. For a compressor that runs for minutes or hours, the cost of setting up huge pages is negligible.

False sharing is a classic pitfall. If two workers update counters or indices that share a cache line, the line ping-pongs between cores. In a token queue, the head and tail indices should be on separate cache lines. In a statistics array, per-worker counters should be padded to a cache line. In the output buffer, workers writing to adjacent blocks may share a cache line if block boundaries are not aligned. Aligning each block's output buffer to a cache line avoids this.

Prefetching can hide some latency. The match finder can prefetch the next hash bucket while processing the current match. The entropy coder can prefetch the next token batch. Software prefetch is most effective when the access pattern is predictable. Hash chains are not perfectly predictable, but the next chain pointer is known after the current read, so a prefetch of the next pointer can help. Hardware prefetchers are less useful for random accesses. A common technique is to process a batch of positions: compute hashes for all positions in a small window, then perform lookups. The hash computation is sequential and cache-friendly; the lookups are random but can be issued in parallel by the out-of-order engine. This batching improves memory-level parallelism without explicit prefetch.

The entropy coder is much more cache-friendly. It reads tokens sequentially and writes bits sequentially. Its working set is the probability model, which is small. The entropy stage rarely limits memory bandwidth. The match finder does. This is another reason why stage parallelism gives limited speedup: the match finder is memory-bound, and the entropy coder is not. Moving the entropy coder to another core does not reduce the match finder's memory traffic. It only overlaps the entropy coder's work with the match finder's stalls. If the match finder is already saturating memory bandwidth, the entropy coder on another core competes for the same bandwidth.

For parallel decompression, the memory behavior is similar but reversed. The decoder reads compressed bits, reconstructs tokens, and writes output. The output write is sequential. The window lookup for a match is a random read from the already-decoded output. If the window is large, the decoder also suffers cache misses. But the decoder does less work per byte than the encoder, so it is often less memory-bound. Independent blocks allow multiple decoders to run, each with its own window, which increases memory traffic. If the blocks are small, the windows are small and fit in cache. If the blocks are large, the windows are large and the decoder may be memory-bound. The block size that is optimal for compression ratio is not necessarily optimal for decompression speed.

## Parallel Decompression: The Other Half of the Problem

Compression is often the bottleneck in write-heavy workloads, but decompression is the bottleneck in read-heavy workloads. A backup system compresses once and decompresses many times. A web server decompresses static assets on every request. A database decompresses pages during queries. If the format does not support parallel decompression, the read path is limited to one core, and the entire system's throughput is capped. This is why block independence is not just a compression-time optimization; it is a read-time requirement for many applications.

The decoder's parallelism is determined entirely by the format's dependency graph. If every block depends on the previous block's window, the decoder is a chain. It can still use stage parallelism: one thread parses tokens, another reconstructs output, another verifies checksums. But the window dependency remains serial. The speedup is bounded by the serial window update. If blocks are independent, the decoder can assign blocks to threads and reconstruct them in any order. The only coordination is writing the output in the correct order and verifying checksums.

A format that wants parallel decompression must provide an index. The index maps block numbers to compressed offsets, uncompressed offsets, and checksums. Without an index, the decoder must scan the compressed stream from the beginning to find block boundaries. Scanning is cheap compared to decompression, but it is serial and can become a bottleneck for many small blocks. The index can be stored at the end of the file, at the beginning, or in a separate sidecar. zstd's seekable format and LZ4's frame index are examples of this pattern. The index adds a small amount of space, but it enables random access and parallel decoding.

Even with an index, shared dictionaries complicate parallel decompression. If block n uses a dictionary derived from block n-1, the decoder must decode block n-1 first. This creates a chain. The chain can be broken by storing the dictionary explicitly. For example, each block could store the dictionary it uses, which is a copy of the previous block's tail. That duplicates data and costs ratio, but it allows independent decoding. A more efficient approach is to store the dictionary once per superblock, where a superblock is a group of blocks that share a dictionary. The decoder decodes the superblock's dictionary first, then decodes the blocks in parallel. The dictionary itself is compressed, so decoding it is a small serial step. The superblock size controls the trade-off: larger superblocks mean fewer dictionary resets and better ratio, but less decoder parallelism.

Output ordering is a practical concern. If blocks are decoded out of order, the decoder must write each block's output to the correct offset in the output file or buffer. This requires random access to the output, which is fine for files but may be awkward for streaming APIs. A streaming decoder can use a reorder buffer: it decodes blocks as they arrive, holds them in memory until all previous blocks are decoded, then writes them out in order. The reorder buffer size is bounded by the number of blocks in flight. If the network delivers blocks out of order, the buffer can grow. Backpressure is needed to limit memory.

Error handling is another advantage of independent blocks. If a block is corrupted, the decoder can report an error for that block and continue decoding others. For a chained format, a single corrupted byte can make the rest of the stream undecodable because the window is wrong. Independent blocks localize errors. This is valuable for archival storage, where a bit rot event should not destroy an entire file. The format can include per-block checksums and a block index, so a recovery tool can identify which blocks are bad and attempt to reconstruct them from redundancy or from other copies.

The cost of parallel decompression is the same ratio cost that parallel compression pays. There is no free lunch. A format that is easy to decompress in parallel is a format with independent blocks, and independent blocks lose cross-boundary matches. The engineering question is whether the read-time speedup is worth the write-time ratio loss. For a write-once, read-many workload, the answer is often yes. For a write-many, read-once workload, the answer may be no. The format should allow the encoder to choose the block independence policy, as LZ4 does, so the application can make the trade-off.

## Adaptive and Content-Defined Block Boundaries

Fixed-size blocks are the default for parallel compression because they are simple, deterministic, and easy to index. But fixed boundaries can be pathological. If the input contains a long repeat that straddles a boundary, the repeat is split and the compressor loses a match that would have been found serially. If the input has a natural structure, such as a sequence of records or a source file with functions, a fixed boundary may cut through a record and force the compressor to relearn context on both sides. An adaptive boundary policy can reduce these losses.

Content-defined chunking (CDC) is a technique from deduplication. A rolling hash is computed over a sliding window, and a boundary is declared when the hash matches a pattern, such as the low bits being zero. The boundaries are determined by the content, not by fixed offsets. This means that if the same content appears at different offsets, it will be chunked the same way. For compression, CDC has a different benefit: it can place boundaries at points where the content changes, such as between records, so that each block is more homogeneous. A homogeneous block compresses better because its entropy model is more accurate and its match finder sees fewer unrelated patterns.

The challenge is that CDC requires a first pass over the input to find boundaries. The rolling hash is sequential, but it is cheap: a few arithmetic operations per byte. It can be vectorized or run at memory bandwidth. The first pass reads the entire input, which adds I/O if the input is not already in memory. For a compressor that reads from disk, the first pass can be overlapped with the second pass if the input is cached, or it can be combined with the compression pass by buffering. But the compression pass needs to know the boundaries before it can assign blocks to workers. A common approach is to run the boundary finder in parallel with the first compression stage: the boundary finder scans ahead, and workers compress the blocks that have been identified. This is a pipeline, not a pure parallel decomposition.

Adaptive block sizes based on compressibility are another option. The encoder can compress a fixed-size block, measure the compression ratio, and if the ratio is poor, split the block into smaller pieces and recompress. This is expensive because it requires recompression. A cheaper heuristic is to estimate compressibility from a sample. For example, compute the entropy of a small sample or count the number of matches in a prefix. If the estimate is poor, use a smaller block. If the estimate is good, use a larger block. The block boundaries are still fixed at the encoder's chosen sizes, but the sizes vary across the file. The decoder needs an index to know the boundaries. The index adds overhead, but it is small compared to the potential ratio gain.

Variable block sizes complicate load balancing. A worker that draws a large block takes longer than one that draws a small block. The scheduler must account for block sizes when assigning work. A simple approach is to sort blocks by size and assign the largest first, which is the LPT (longest processing time) heuristic. It is not optimal, but it is close for many distributions. A more dynamic approach is to use work stealing with size-aware stealing: a worker steals a block only if its remaining work is less than the stolen block's estimated time. The estimate can be based on the block's uncompressed size and a running average of compression speed.

The format must declare whether block boundaries are fixed, content-defined, or encoder-chosen. If they are encoder-chosen, the format must include an index that maps each block to its uncompressed offset and size. The index can be compressed itself. For content-defined boundaries, the decoder does not need to recompute the rolling hash; it can rely on the index. This is important because the decoder may not have the same rolling hash implementation, and recomputing boundaries would be error-prone. The index makes the boundaries explicit and portable.

There is a subtle interaction with determinism. Content-defined boundaries are deterministic because they depend only on the input. Encoder-chosen boundaries may depend on the encoder's speed measurements or on the number of threads, which are not deterministic. If the encoder chooses different boundaries on different runs, the compressed output differs, which breaks content-addressed storage and reproducible builds. To preserve determinism, the boundary policy must be a pure function of the input and the compression parameters, not of the runtime environment. For example, the encoder can choose boundaries based on a fixed-size window and a fixed compressibility estimate, regardless of how many threads are available. The number of threads then affects only the scheduling, not the output.
