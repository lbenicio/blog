# Memory Bandwidth Is the Real Parallel Machine: Roofline Limits, Saturation, and Bandwidth-Aware Algorithm Design

In parallel computing, we habitually count the things that are easy to count: cores, hardware threads, SIMD lanes, warps, and FLOPS. Those numbers are real, but they are not the whole machine. For a large class of workloads, the scarce resource is not arithmetic throughput. It is bytes per second arriving from the memory hierarchy. A modern server CPU may execute hundreds of billions of instructions per second across dozens of cores, yet its socket-level DRAM bandwidth is measured in tens to low hundreds of gigabytes per second. When an algorithm needs several bytes for every floating-point operation, the arithmetic units spend most of their time waiting, and adding cores does not fix the problem. It often makes it worse.

This article is about treating memory bandwidth as a first-class design constraint in parallel and systems software. The goal is not to catalog a particular processor or benchmark. It is to build a durable mental model: how to reason about operational intensity, where the roofline bound comes from, why bandwidth is shared and non-uniform, how saturation and latency interact, and what all of this implies for data layout, algorithm structure, and performance measurement. The discussion applies to CPUs, GPUs, accelerators, and distributed systems, because the same accounting appears at every level of the memory and interconnect hierarchy.

## The arithmetic illusion

Processor marketing encourages an arithmetic view of performance. A core has a clock frequency, issue width, vector width, and peak FLOPS. Multiply those together and you get a number. The trouble is that this number is only reachable when operands are already in registers or very close to the core. Every operand that must come from L1, L2, L3, or DRAM consumes bandwidth somewhere in the hierarchy. If the data does not fit in the closest level, the arithmetic peak becomes irrelevant.

Consider a simple vector addition: C[i] = A[i] + B[i]. For each element, we read two values and write one. In double precision, that is 24 bytes of logical traffic and one floating-point addition. The operational intensity is roughly 0.042 flops per byte if we count only the add, or 0.083 if we count the add as two operations. On a machine with 100 GB/s of achievable DRAM bandwidth, the bandwidth ceiling is about 4 to 8 GFLOP/s. If the same machine has a 1 TFLOP/s compute peak, vector addition uses less than one percent of the arithmetic capability. More cores do not change that ratio. The memory system is already the bottleneck.

This is the memory wall, and it is not new. What is new is the scale of the imbalance and the degree to which parallel software still ignores it. A parallel program that scales perfectly in a cache-resident microbenchmark can flatten immediately when the working set exceeds last-level cache. Performance counters show high memory-controller utilization, long stalls on demand loads, and disappointing speedup. The fix is rarely a better scheduling policy. It is usually a change in how many bytes the algorithm moves.

## The roofline model as a reasoning tool

The roofline model gives us a compact way to classify kernels. It says that attainable performance is bounded by two roofs: a horizontal roof representing peak compute throughput, and a sloped roof representing peak memory bandwidth multiplied by operational intensity. Operational intensity, often written I, is the ratio of work performed to bytes moved between the kernel and some level of the memory hierarchy. For floating-point kernels, I is usually flops per byte. For integer, graph, or data-processing kernels, it may be operations per byte, edges per byte, or records per byte.

Plot I on a logarithmic x-axis and performance on a logarithmic y-axis. The sloped roof rises until it meets the horizontal roof. The intersection is the ridge point, I* = peak compute / peak bandwidth. Kernels to the left of the ridge point are memory-bound: their performance is limited by bytes per second. Kernels to the right are compute-bound: their performance is limited by arithmetic or logic throughput. The ridge point is a property of the machine and the chosen memory level. A kernel can be compute-bound at L1 but memory-bound at DRAM. That distinction matters because blocking and tiling can move a kernel from the DRAM roofline to the L1 roofline without changing its arithmetic.

The roofline is not a performance prediction. It is an upper bound under idealized assumptions: perfect cache reuse, no latency stalls, full overlap of computation and memory traffic, and no contention beyond the modeled bandwidth. Real kernels fall below the roof because of imperfect prefetching, bank conflicts, non-contiguous access, synchronization, and queueing. But the model is still useful because it tells you which roof you are under. If you are far below the bandwidth roof, the problem may be latency or insufficient memory-level parallelism. If you are near the bandwidth roof, the only way forward is to reduce bytes or increase reuse.

## Operational intensity in practice

Operational intensity is easy to define and hard to measure correctly. The numerator is straightforward if the kernel is arithmetic. The denominator is where mistakes happen. Do not count logical array elements as bytes. Count cache lines transferred between the kernel and the memory level you care about. A loop that reads one 8-byte field from each element of an array of structs may fetch 64 bytes per element if the struct is 64 bytes and the access pattern is dense. The useful intensity is then eight times lower than a naive calculation suggests. Conversely, a loop that reads contiguous data and uses every byte of each cache line has good spatial locality and higher effective intensity.

Data layout is therefore an algorithmic decision, not an afterthought. Array-of-structs versus struct-of-arrays changes how many cache lines are touched. Padding can eliminate false sharing but also increase footprint. Tiling changes the order of accesses so that a block of data is reused from cache before it is evicted. Fusion combines multiple passes over the same data into one pass, reducing compulsory traffic. Recomputing a value can be cheaper than storing and reloading it when bandwidth is the constraint. Mixed precision reduces bytes per element at the cost of numerical range and accuracy. Compression reduces bytes further, but only if the decompression cost is lower than the saved bandwidth and the compressed representation is actually smaller in memory.

Sparse and irregular workloads deserve special attention. Sparse matrix-vector multiplication reads a matrix with mostly zeros, but it must read the index structure and the nonzero values. The operational intensity is low, and the access pattern is irregular. Graph traversal is worse: each edge or vertex access may touch a different cache line, and the working set can be enormous. These kernels are often latency-bound before they are bandwidth-bound. The fix is not simply more bandwidth. It is better locality, partitioning, and sometimes a different representation.

## Bandwidth is shared, hierarchical, and non-uniform

A single bandwidth number is a dangerous abstraction. On a multicore CPU, bandwidth is shared across cores on a socket, across sockets through an interconnect, and across memory channels within a NUMA node. On a GPU, bandwidth is partitioned across memory controllers and L2 slices. On a distributed system, bandwidth is shared across the network fabric and the storage layer. When multiple threads or nodes compete for the same memory controllers, per-thread bandwidth falls. Aggregate bandwidth may rise, plateau, or even decline if queueing and conflict traffic dominate.

NUMA makes this concrete. A thread can access local memory attached to its socket or remote memory attached to another socket. Remote bandwidth is lower and remote latency is higher. If the operating system places memory pages on the wrong node, a parallel program can spend much of its time crossing the interconnect. First-touch page placement, memory binding, and explicit migration policies matter. They are not micro-optimizations. On a large multi-socket machine, they can determine whether a workload scales at all.

The hierarchy also means that bandwidth is not consumed uniformly. A kernel may saturate DRAM while leaving L2 bandwidth underused, or it may thrash L2 while DRAM sits idle. Roofline analysis at multiple levels helps identify which resource is actually saturated. Hardware performance counters can report bytes transferred at each cache level, miss rates, and memory-controller utilization. Without that visibility, it is easy to optimize the wrong level.

## Saturation, latency, and memory-level parallelism

Bandwidth is a throughput limit, but memory is also a latency problem. A single load may take tens of nanoseconds to reach DRAM and return. To sustain a given bandwidth, the system must keep enough requests in flight. Little's law applies: concurrency equals latency multiplied by throughput. If DRAM latency is 80 nanoseconds and the target bandwidth is 100 GB/s, the memory system needs about 8,000 bytes in flight, which is roughly 125 cache lines. A single core has a limited number of outstanding misses, so it may be unable to saturate DRAM on its own. Multiple cores, hardware prefetchers, and out-of-order execution provide the necessary memory-level parallelism.

This creates a distinction that matters for diagnosis. If bandwidth counters show low utilization but latency is high, the workload may be latency-bound: there are not enough outstanding requests. Adding threads can help, up to a point. If bandwidth counters show near-peak utilization, the workload is bandwidth-bound: more threads will only increase queueing. In the first case, the answer may be prefetching, software pipelining, or more concurrency. In the second, the answer must be fewer bytes or more reuse.

Saturation is not a cliff. As utilization approaches the peak, queueing delays grow nonlinearly. A memory controller at 80 percent utilization may have acceptable latency; at 95 percent, small bursts of traffic can cause large stalls. This is why tail latency in memory-bound services is sensitive to background activity. A co-located process, a periodic flush, or a garbage collection cycle can push the memory system past the knee of the curve. The same principle applies to network bandwidth in distributed systems.

## Measurement pitfalls

Measuring memory bandwidth correctly is harder than it looks. The first trap is using theoretical peak bandwidth. DRAM vendors quote a signaling rate and bus width, but achievable bandwidth is lower because of refresh, bank conflicts, read-write turnaround, ECC overhead, and protocol inefficiency. A well-tuned STREAM triad benchmark might reach 60 to 80 percent of theoretical peak on a CPU. Real applications often reach less because their access patterns are not perfectly contiguous.

The second trap is counting the wrong bytes. Performance counters may report cache-line fills, which include prefetched lines that are never used. They may count read-modify-write traffic for partial writes. They may include ECC or metadata traffic. They may not distinguish local from remote NUMA traffic. If you are trying to compute operational intensity, you need to know which bytes are useful and which are overhead. A profiler that reports DRAM bytes is more useful than one that reports only LLC misses, but even then you must understand what the counter includes.

The third trap is ignoring frequency and power state. Memory bandwidth and core frequency can change with turbo, thermal limits, and power capping. A benchmark run on an otherwise idle machine may see higher bandwidth than the same code in production. The fourth trap is measurement perturbation. Instrumenting every memory access or collecting high-frequency counters can change scheduling and cache behavior. Sampling is usually better, but sampling has its own bias.

Finally, be skeptical of single-number summaries. Bandwidth is a vector: read bandwidth, write bandwidth, copy bandwidth, local bandwidth, remote bandwidth, and bandwidth at each cache level. A kernel that is read-heavy, write-heavy, or mixed will stress different parts of the system. Report the numbers that correspond to the workload.

## Design consequences

Once bandwidth is treated as a first-class resource, design decisions change. The first question is not how many threads to use, but how many bytes per unit of work the algorithm must move. A byte budget is as useful as a time budget. If a kernel must process a data set of size N within a time T, and the achievable bandwidth is B, then the algorithm can move at most B times T bytes. If the required traffic exceeds that, the algorithm must be restructured, not merely parallelized.

The second consequence is that data layout and algorithm structure are inseparable. Tiling, blocking, fusion, and compression all trade computation or complexity for reduced traffic. They are not optimizations to apply after correctness. They are part of the parallel design. The third consequence is that scalability must be defined in terms of the bottleneck resource. A program that scales linearly in compute but saturates memory bandwidth at four threads is not scalable in any useful sense. The fourth consequence is that heterogeneity matters. A GPU may have much higher bandwidth than a CPU, but it also has different latency, cache structure, and programming model. Moving work to the GPU only helps if the kernel is bandwidth-bound and the data transfer cost is amortized.

The same reasoning applies beyond a single machine. In distributed systems, network bandwidth is the shared resource. In storage systems, device bandwidth and write amplification are the constraints. In machine learning, training and inference have different byte budgets: training often streams activations and gradients, while inference streams weights. The roofline model is a general accounting tool, not a CPU-specific curiosity.

The next sections will examine concrete case studies: dense linear algebra and tiling, sparse and graph workloads, NUMA placement and first-touch, GPU memory hierarchies, and a practical methodology for bandwidth-aware optimization.

## Dense linear algebra: tiling as bandwidth engineering

Dense matrix multiplication is the canonical example of an algorithm whose performance is determined by data reuse. A naive triple loop performs O(n^3) floating-point operations but moves O(n^3) data if every access goes to memory, because each element of the output is written repeatedly and each input element is read many times. The arithmetic intensity is low, and the kernel sits on the bandwidth roof. Blocking changes the accounting. Partition the matrices into tiles of size b x b that fit in a cache level. Each tile of A and B is loaded once, and a tile of C is updated. The work per tile is 2b^3 flops, while the traffic to the next level is roughly 3b^2 elements: b^2 for A, b^2 for B, and b^2 for C. The operational intensity is therefore about 2b/3 flops per element, or 2b/(3s) flops per byte for an element size of s bytes. Increasing b increases intensity until the tiles no longer fit in cache. This is why high-performance GEMM implementations use a hierarchy of blocks: register blocks, L1 blocks, L2 blocks, and sometimes L3 blocks. Each level is sized to the capacity and bandwidth of the corresponding memory.

The same reasoning applies to other dense kernels. A stencil computation reads a neighborhood of each output point. Without tiling, each input point is read multiple times from DRAM. With temporal blocking, a block of the grid is advanced several time steps while resident in cache, reducing DRAM traffic by a factor equal to the number of steps. A convolution can be transformed into a matrix multiplication or implemented with tiling and register blocking. A reduction reads a large array and produces a small result; it is almost purely bandwidth-bound, and the only optimizations are vectorized loads, unrolling, and enough concurrency to saturate memory. A transpose is bandwidth-bound but also sensitive to access patterns; tiled transposes use shared memory or cache blocks to avoid strided writes that waste bandwidth.

Data layout interacts with tiling. Row-major and column-major storage change which dimension is contiguous. Packing tiles into contiguous buffers can improve prefetching and reduce TLB pressure. Padding can avoid cache set conflicts and bank conflicts. Mixed precision can reduce bytes per element: storing inputs in 16-bit formats and accumulating in 32-bit can halve the input traffic while preserving accuracy for many workloads. The trade-off is that conversion and accumulation may add compute, and the numerical properties change. When the kernel is bandwidth-bound, that trade can be favorable. When it is compute-bound, it may not be.

## Sparse and graph workloads: irregular bytes

Sparse matrix-vector multiplication, y = A x, is a staple of scientific computing and graph analytics. In compressed sparse row (CSR) format, each nonzero stores a value and a column index, and each row stores a pointer. For a double-precision matrix, a nonzero costs 8 bytes for the value and 4 or 8 bytes for the index, depending on the index width. The vector x is accessed indirectly through the column indices, and y is updated. The arithmetic is two flops per nonzero, so the operational intensity is roughly 2 flops per 20 bytes, or 0.1 flops per byte. This is far to the left of the ridge point on any modern processor. The kernel is memory-bound, and often latency-bound because the indirect accesses to x are irregular.

Optimizing SpMV is therefore a problem of reducing bytes and improving locality. Blocked CSR stores small dense blocks, which amortizes index overhead and improves reuse of x. ELLPACK and its variants store a fixed number of nonzeros per row, which enables coalesced access but wastes storage for irregular matrices. Hybrid formats combine multiple representations for different row lengths. Reordering rows and columns can improve locality and reduce the number of cache lines touched. Splitting the matrix into tiles that fit in cache can increase reuse of x and y. In all cases, the goal is to move fewer bytes per nonzero and to make the bytes that are moved contiguous.

Graph traversal is even more challenging. Breadth-first search expands a frontier of vertices, reading the adjacency lists of each vertex and writing the next frontier. The adjacency lists are irregular, and the frontier can be large. The working set may exceed cache, so each edge traversal can cause a cache miss. The kernel is often latency-bound rather than bandwidth-bound because the accesses are dependent and scattered. Direction-optimizing BFS switches between top-down and bottom-up traversal depending on frontier size, which reduces the number of edges examined. Partitioning the graph so that each thread or node works on a subgraph with local adjacency can improve locality. Compressing vertex identifiers and using bitmaps for frontiers can reduce bytes. For very large graphs, the network becomes the bandwidth constraint, and the algorithm must be designed to minimize communication, not just local memory traffic.

Sparse and graph workloads illustrate a general point: the roofline model still applies, but the bytes are not perfectly contiguous. The effective bandwidth is lower than the peak because of poor spatial locality and limited memory-level parallelism. A kernel may be far below the bandwidth roof not because the algorithm is inefficient in flops, but because the memory system cannot deliver bytes fast enough due to access patterns. Improving locality is the primary lever.

## NUMA placement and first-touch

On a multi-socket server, memory is not a single pool. Each socket has its own memory controllers and DRAM. A core can access local memory attached to its socket or remote memory attached to another socket through an interconnect. Remote bandwidth is lower and remote latency is higher. The exact ratio depends on the machine, but it is common for remote bandwidth to be half or less of local bandwidth, and remote latency to be significantly higher. For bandwidth-bound workloads, this matters enormously.

The operating system uses a first-touch policy for anonymous memory on many systems. The physical page is allocated on the NUMA node of the CPU that first writes to it. If a parallel program initializes an array with one thread and then processes it with many threads spread across sockets, most of the array may be placed on a single node. The other sockets will then access it remotely, and aggregate bandwidth will suffer. The fix is to initialize the data in parallel with the same thread-to-data mapping that will be used during computation, or to use explicit memory binding and migration. Memory policies such as interleaving can spread pages across nodes, which may help if the workload is not sensitive to locality, but for bandwidth-bound kernels local placement is usually better.

Thread affinity is equally important. If threads migrate between sockets, their data becomes remote. Pinning threads to cores and binding memory to the same node keeps accesses local. Work-stealing schedulers can improve load balance but may move threads away from their data. For bandwidth-bound workloads, locality often beats perfect load balance. A hybrid approach is to partition the data by node and use local work queues, with limited stealing across nodes.

NUMA effects also appear at the cache level. Last-level caches are often shared per socket or per core complex. A thread that reads data from another socket's cache may incur interconnect traffic. Performance counters can distinguish local and remote memory accesses. When tuning, measure bandwidth per node and cross-node traffic. A roofline analysis should use the bandwidth of the memory level that is actually serving the kernel. If half the accesses are remote, the effective bandwidth is a weighted average of local and remote bandwidth, and the ridge point shifts.

## GPU memory hierarchies: bandwidth with a different shape

GPUs are often described as having enormous memory bandwidth. A high-end GPU may have several terabytes per second of HBM bandwidth, which is an order of magnitude more than a server CPU socket. But the GPU memory hierarchy has a different shape. Latency is high, and a single thread cannot hide it. The GPU relies on massive thread-level parallelism to keep many memory requests in flight. To saturate bandwidth, a kernel needs enough active warps and enough independent memory operations per warp. Occupancy and instruction-level parallelism both matter.

Coalescing is the central access pattern concern. A warp of 32 threads should access contiguous memory so that the hardware can combine the accesses into a small number of cache-line transactions. If threads access strided or scattered addresses, the memory system may issue many transactions for the same amount of useful data, wasting bandwidth. For example, a warp reading one 4-byte value per thread from consecutive addresses uses 128 bytes of useful data and one or two transactions. A warp reading one 4-byte value per thread with a stride of 32 elements uses 128 bytes of useful data but touches 32 different cache lines, wasting most of the fetched bytes. The effective bandwidth can drop by an order of magnitude.

Shared memory is a software-managed cache that can reduce global memory traffic. Tiling a matrix multiplication or a stencil into shared memory allows each global memory access to be reused many times. The programmer must manage bank conflicts, because shared memory is divided into banks and simultaneous accesses to the same bank serialize. Padding shared memory arrays can avoid conflicts. On newer GPUs, asynchronous copy instructions and tensor memory accelerators can overlap global-to-shared transfers with computation, which improves memory-level parallelism and hides latency.

The GPU roofline has a much higher ridge point than a CPU because compute throughput is very high relative to bandwidth. Many GPU kernels are still memory-bound. Vector addition, reduction, and simple elementwise operations are limited by HBM bandwidth. Stencils and convolutions can be memory-bound unless tiled. Sparse operations on GPUs are often latency-bound and load-imbalanced. The L2 cache is shared across the GPU and is partitioned into slices; access patterns that concentrate on a subset of slices can cause partition camping and reduce effective bandwidth. Distributing accesses across addresses can help.

Host-device transfer is another bandwidth constraint. Data must cross PCIe or NVLink between CPU and GPU. If a kernel is memory-bound on the GPU but the data transfer dominates, the overall application may be limited by the interconnect. Pipelining transfers with computation, using unified memory carefully, and keeping data resident on the GPU across multiple kernels are standard techniques. The roofline model can be applied to the interconnect as well: the operational intensity of the transfer is low, so it is almost always bandwidth-bound.

## A practical methodology for bandwidth-aware optimization

The following methodology is a starting point for treating bandwidth as a design constraint. It is not a recipe for a specific machine, but a sequence of questions that can be applied to any parallel workload.

First, define the memory level that matters. Is the kernel limited by L2, L3, DRAM, the interconnect, or the network? The answer determines which bandwidth number to use and which optimizations are relevant. A kernel that fits in L2 may be compute-bound, while the same kernel with a larger working set may be DRAM-bound.

Second, measure achievable bandwidth on the target hardware. Run a simple copy or triad benchmark with the same access pattern and thread configuration as the real kernel. Do not use theoretical peak. Measure read-only, write-only, and mixed bandwidth if the workload requires them. This gives a realistic ceiling.

Third, estimate or measure the kernel's actual traffic. Use hardware performance counters where available. If counters are not available, build a byte-accounting model: count cache lines touched, not just array elements. Include index structures, metadata, and write-allocate traffic. Compute operational intensity as work divided by bytes moved at the relevant level.

Fourth, place the kernel on the roofline. Compare its intensity to the ridge point. If it is far to the left, it is bandwidth-bound. If it is near the ridge, it may be balanced. If it is to the right, it is compute-bound. Also check whether the kernel is latency-bound: low bandwidth utilization with high stall counts suggests insufficient memory-level parallelism.

Fifth, if the kernel is bandwidth-bound, reduce bytes. The options include fusing multiple passes into one, tiling to increase reuse, changing data layout to improve spatial locality, compressing data, using lower precision, recomputing values instead of storing them, and eliminating unnecessary writes. Each option has a cost in compute, complexity, or accuracy. Choose the one that fits the algorithm.

Sixth, if the kernel is latency-bound, increase memory-level parallelism. Unroll loops to expose independent loads, use software prefetching, increase the number of threads or warps, use asynchronous copies, and ensure that the access pattern is as contiguous as possible. Sometimes the best fix is to change the algorithm to have more independent work per thread.

Seventh, check placement and affinity. On NUMA systems, ensure that memory is allocated locally and threads are pinned. On GPUs, ensure that data is resident and that transfers are overlapped. On distributed systems, minimize cross-node communication and use locality-aware partitioning.

Eighth, validate with counters and end-to-end measurements. After an optimization, re-measure bandwidth, traffic, and time. The bottleneck may have shifted. A kernel that was DRAM-bound may become L2-bound or compute-bound. Iterate until the kernel is near the appropriate roof or until further optimization is not worth the complexity.

This methodology is iterative and hardware-specific, but the underlying accounting is universal. Bytes per second is a resource, and algorithms that respect that resource scale better than algorithms that merely expose more parallelism.

## Bandwidth beyond the socket: distributed and networked systems

The roofline model does not stop at the memory controller. In a distributed system, the scarce resource is often the network fabric, and the same accounting applies. Each node has local DRAM bandwidth, but communication between nodes consumes network bandwidth and adds latency. A distributed kernel's operational intensity can be defined as useful operations per byte communicated. If that ratio is low, the algorithm is network-bound, and adding nodes will not help; it may increase contention and tail latency.

MapReduce-style shuffles are a classic example. A word count or a group-by aggregation reads data locally, then redistributes records by key. The shuffle writes to local storage or memory, sends partitions over the network, and reads them on the receiving side. The arithmetic per record is trivial, so the shuffle is bandwidth-bound at multiple levels: local disk, local network, and remote memory. The optimizations are familiar from single-node memory work: combine partial aggregates before sending, compress intermediate data, partition to minimize cross-node traffic, and use locality-aware scheduling so that keys are processed where they are already stored. When the network is saturated, the bottleneck is no longer CPU; the reducer may sit idle waiting for bytes.

Collective communication in distributed training shows the same pattern. An all-reduce operation exchanges gradients across workers. The byte volume is proportional to model size and is repeated every iteration. The computation per gradient element is small, so the collective is bandwidth-bound. Ring all-reduce reduces the number of bytes each worker sends by pipelining chunks around a logical ring, but it still consumes network bandwidth. Overlapping communication with backward-pass computation helps only if the network has spare capacity; if the fabric is already saturated, overlap does not create bandwidth. Gradient compression, quantization, and sparsification trade accuracy for fewer bytes. They are bandwidth-aware algorithmic choices, not merely implementation details.

Message aggregation is a general principle. Sending one large message is usually more efficient than sending many small messages because per-message overhead, headers, and interrupt costs dominate at small sizes. Batching, coalescing, and vectorized network APIs reduce the number of transactions. The same is true inside a machine: memory controllers prefer long bursts of contiguous requests. At every level, the overhead per transaction means that effective bandwidth depends on request size and access pattern.

Network latency and bandwidth interact through Little's law just as they do in memory. To sustain a high bandwidth-delay product link, the sender must keep enough bytes in flight. A single request-response exchange cannot fill a long fat pipe. Pipelining, multiple outstanding requests, and windowing are required. In distributed storage or RPC systems, this is why queue depth and concurrency limits matter as much as raw link speed. A system that issues one synchronous request at a time will be latency-bound regardless of the advertised bandwidth.

## Storage, I/O, and the extended memory hierarchy

Storage devices extend the memory hierarchy beyond DRAM. An NVMe SSD may deliver gigabytes per second, but it does so with different granularity, latency, and read-write asymmetry than DRAM. Hard disks deliver far less bandwidth and have seek latency measured in milliseconds. The roofline model still applies, but the memory level is now a device with a queue, a block size, and a write amplification factor.

For I/O-bound workloads, operational intensity can be expressed as useful records per byte read or written. A scan that reads a columnar file and computes an aggregate may process many records per byte, but it still must read every byte of the columns it touches. A point lookup may read only a few bytes but pay a full block or page transfer. The effective bandwidth for random small reads is much lower than for large sequential reads because the device and the filesystem transfer entire blocks. This is why databases and file systems batch, cache, and prefetch.

Write bandwidth is often more constrained than read bandwidth. Flash cells must be erased before rewriting, and the flash translation layer may perform garbage collection that amplifies writes. A workload that performs many small random writes can consume far more device bandwidth than its logical byte count suggests. Log-structured designs, append-only files, and write coalescing reduce write amplification. They are bandwidth-aware algorithms for storage. The same idea appears in persistent memory and log-structured merge trees: sequential writes are cheap, random in-place updates are expensive.

The page cache and buffer cache act as additional memory levels. A workload that fits in the page cache may be DRAM-bound; one that does not becomes device-bound. Direct I/O bypasses the cache to avoid double buffering, but it also loses the cache's ability to absorb small random reads and to prefetch. Memory-mapped files can simplify programming, but page faults, TLB misses, and unpredictable readahead can make performance difficult to model. For bandwidth-sensitive systems, explicit asynchronous I/O with a controlled queue depth often gives more predictable results than relying on the kernel's heuristics.

External memory algorithms are the algorithmic counterpart to this hierarchy. When a data set exceeds DRAM, the cost model changes from random access to block transfers. Sorting, joining, and graph traversal must be designed to minimize passes over the data and to use large sequential I/O. Multiway merges, radix partitioning, and hash partitioning are standard techniques because they convert random traffic into sequential traffic. A roofline-style analysis for external memory counts bytes transferred between levels, not cache lines. The ridge point is determined by device bandwidth and the amount of computation per byte.

## Machine learning workloads: byte budgets in training and inference

Machine learning has become a major driver of bandwidth-aware design. Training and inference have different byte budgets, and both are often memory-bound despite the prominence of matrix multiplication.

During training, the forward pass reads activations and weights, writes intermediate activations, and the backward pass reads activations and gradients and updates weights. The optimizer step reads and writes model parameters and optimizer state. For a large model, the optimizer state can double or triple the bytes per parameter. Adam, for example, stores first and second moment estimates in addition to the parameters. An update step that reads and writes all of these tensors is bandwidth-bound, even though the arithmetic per parameter is small. This is why fused optimizers, mixed precision, and parameter sharding matter. They reduce bytes moved per parameter per step.

The attention mechanism in transformers provides another clear example. Computing attention requires multiplying queries, keys, and values, then applying softmax to the scores. A naive implementation materializes the attention matrix, writes it to memory, reads it back for softmax, and reads it again for the value multiplication. The matrix is quadratic in sequence length, so the memory traffic dominates. Flash Attention and similar algorithms tile the computation so that the attention matrix never leaves on-chip memory. They recompute parts of the softmax rather than storing the full matrix. This is a bandwidth-aware algorithmic transformation: it trades extra computation for fewer bytes moved between DRAM and cache. The roofline model explains why it helps; the kernel moves from the DRAM roof to the on-chip roof.

Inference has its own bandwidth profile. During autoregressive decoding, the model generates one token at a time. Each token requires reading the entire model's weights and the KV cache. The arithmetic intensity per weight is low, so decoding is bandwidth-bound on the weight stream. Batching increases intensity by reusing the same weights for multiple sequences, but it also increases latency and memory footprint. The KV cache grows with sequence length and batch size, and reading it can dominate memory traffic. Paged attention, KV cache quantization, and grouping queries by shared prefixes reduce bytes per token. Speculative decoding and draft models change the trade-off between compute and bandwidth. In all cases, the goal is to increase the number of useful operations per byte of weight or KV data.

Quantization is a direct bandwidth reduction technique. Storing weights in 8-bit or 4-bit formats reduces bytes per parameter by a factor of two to eight compared to 32-bit floating point. The compute may need to dequantize or use integer arithmetic, and accuracy may degrade. When the model is bandwidth-bound, the trade can be strongly favorable. The same reasoning applies to activations and gradients. Mixed-precision training with 16-bit or bfloat16 tensors reduces traffic for activations and gradients while keeping a master copy of weights in higher precision. The roofline model gives a way to estimate when the saved bytes outweigh the conversion and error costs.

Data loading is often the hidden bandwidth bottleneck. Training pipelines read images, text, or other data from storage, decode or tokenize it, and transfer it to the accelerator. If the input pipeline cannot keep up, the accelerator sits idle. Prefetching, parallel data loading, caching, and format conversion are essential. On-device memory is also shared: activations, weights, gradients, and optimizer state compete for HBM bandwidth. Kernel fusion reduces the number of reads and writes between kernels. For example, fusing elementwise operations, normalization, and activation functions into a single kernel can cut memory traffic dramatically. These fusions are bandwidth optimizations, not just launch-overhead optimizations.

## Multi-level roofline and cache-aware modeling

A single roofline is a simplification. Real memory hierarchies have multiple levels, each with its own bandwidth and capacity. A kernel that is DRAM-bound may still be far below the L2 roofline. A multi-level roofline model plots bounds for each level. The kernel's performance is limited by the lowest roof that it actually touches. As the working set grows and cache reuse falls, the effective roof moves down. This is why capacity matters as much as bandwidth.

Cache-aware modeling makes the traffic between levels explicit. For a tiled algorithm, we can write recurrence relations for the number of bytes transferred between levels as a function of tile sizes. The goal is to choose tile sizes that fit in the faster level while maximizing reuse. For matrix multiplication, the classic result is that blocking for a cache of size M with block size b yields O(n^3 / sqrt(M)) traffic between DRAM and cache for an n x n multiply. The exact constants depend on layout and on whether the algorithm uses register blocking, but the scaling intuition is robust: larger tiles and deeper blocking reduce DRAM traffic until the tile no longer fits.

Stencil temporal blocking follows a similar logic. A stencil with a radius r reads a halo of r cells around each output. Without temporal blocking, each time step reads the entire grid from DRAM. With temporal blocking, a block of the grid is loaded into cache and advanced for t time steps. The halo overhead grows with t, but the DRAM traffic per time step falls. The optimal t balances cache capacity, halo size, and the cost of recomputation at block boundaries. This is a bandwidth optimization expressed as an algorithmic transformation.

Reuse distance and stack distance provide another way to reason about cache behavior. The reuse distance of an access is the number of distinct bytes touched since the previous access to the same line. If the reuse distance is larger than the cache capacity, the line will have been evicted, and the access becomes a miss. Cache-aware algorithms reduce reuse distance by reordering accesses, tiling, and partitioning. They do not change the arithmetic; they change the sequence of bytes. Profilers that estimate reuse distance can reveal why a kernel misses more than expected.

The multi-level view also clarifies the role of shared memory on GPUs and scratchpad memories on accelerators. These are explicitly managed caches. The programmer decides what to keep on chip and when to move it. A bandwidth-aware kernel treats scratchpad capacity as a scheduling constraint. It loads a tile, computes on it, and writes results back, with the goal of maximizing the number of operations per byte transferred from the next level. The roofline at the scratchpad level may be very high, while the roofline at HBM is much lower. The kernel's job is to move the bottleneck to the higher roof.

## Bandwidth-aware patterns and anti-patterns

Certain access patterns consistently waste bandwidth. Strided access touches a cache line to use only a few bytes. Pointer chasing serializes memory accesses and reduces memory-level parallelism. False sharing causes cache lines to bounce between cores even though different cores touch different variables. Write-allocate reads a cache line before a partial write, consuming read bandwidth for data that will be overwritten. Repeated passes over the same array multiply traffic. Materializing intermediate results that could be streamed or fused adds bytes. Small messages and small I/O requests pay per-transaction overhead. These anti-patterns are not exotic; they appear in ordinary code whenever data layout and loop structure are chosen without considering bytes.

The corresponding patterns are straightforward. Use structure-of-arrays when the kernel touches a subset of fields. Tile and block loops so that reused data stays in a faster memory level. Fuse elementwise operations and reductions to avoid intermediate arrays. Batch messages and I/O requests to amortize overhead. Use non-temporal stores for streaming writes that will not be read soon. Prefetch when access patterns are predictable. Compress, quantize, or use narrower types when the numerical requirements allow. Recompute cheap values instead of storing and reloading them. Align data to cache-line boundaries and pad to avoid conflicts. Pin threads and place memory locally on NUMA systems. Overlap communication and computation with asynchronous primitives.

These patterns are not one-size-fits-all. Each has a cost: compression costs decompression cycles, quantization may cost accuracy, fusion can increase register pressure and reduce occupancy, tiling can add boundary complexity, and batching can increase latency. The roofline model helps decide when the trade is worthwhile. If the kernel is far under the bandwidth roof, reducing bytes usually wins. If it is near the compute roof, adding computation to save bytes may not help.

This is where bandwidth accounting becomes a design discipline. The programmer who counts bytes alongside flops, and who measures the right memory level, can predict when an algorithm will scale and when it will flatten. The machine may have many cores, but the bytes per second are finite. Algorithms that respect that limit are the ones that use the parallel machine well.

## Memory controllers, DRAM organization, and effective bandwidth

A DRAM device is not a linear array. It is organized into banks, rows, and columns. Accessing a row activates it into a row buffer. Subsequent accesses to the same row are row-buffer hits and are much cheaper than row-buffer misses, which require precharging and activating another row. The memory controller schedules requests to maximize row-buffer hits and to overlap activations across banks. Bank groups and multiple channels provide parallelism, but the controller must also manage read-to-write turnaround, refresh cycles, and command bus contention. These overheads mean that the theoretical peak bandwidth derived from bus width and signaling rate is not achievable for arbitrary access streams.

Effective bandwidth depends on the spatial and temporal pattern of requests. A long sequential stream that walks through rows in order gives the controller many opportunities for row-buffer hits and for prefetching. A stream that jumps between distant addresses forces row activations and may leave banks idle. Fine-grained interleaving across channels spreads addresses so that consecutive cache lines map to different channels, which increases parallelism but can also reduce row-buffer locality if the interleaving granularity is too small. The address mapping is usually hashed to avoid pathological conflicts, and it is not exposed to software. The practical consequence is that algorithms should express locality in large contiguous chunks rather than assuming that any contiguous address range will map perfectly.

Refresh is another source of overhead. DRAM cells leak charge and must be refreshed periodically. During refresh, some banks are unavailable, reducing available bandwidth. Temperature affects refresh rate. ECC adds additional bits and may require read-modify-write for partial writes. Link compression, if present, can reduce bytes over the interconnect but adds latency and complexity. None of these effects are visible in a simple bandwidth number, yet they shape the achievable ceiling.

For bandwidth-aware design, the lesson is to avoid random small accesses when sequential large accesses are possible, to batch requests so that the controller can schedule them efficiently, and to leave headroom. A kernel that drives the memory controller to 100 percent utilization will suffer large queueing delays and will be sensitive to any background activity. A kernel that runs at 70 to 80 percent may achieve nearly the same throughput with much better tail behavior. The roofline model uses a peak bandwidth, but the practical design point is often below that peak.

## Bandwidth as a shared service: isolation, fairness, and QoS

On a multicore or multi-tenant machine, memory bandwidth is a shared service. Every core, every virtual machine, and every container competes for the same memory controllers. Without isolation, a bandwidth-hungry workload can starve a latency-sensitive workload even if the latter uses little bandwidth. The victim sees inflated memory latency, longer stalls, and unpredictable tail latency. This is not a scheduling problem in the traditional CPU sense; it is a memory-system contention problem.

Hardware and software provide several mechanisms to manage this contention. Memory controllers may implement arbitration policies that prioritize reads over writes, or that enforce per-requestor quotas. Cache allocation and memory bandwidth allocation technologies can partition last-level cache ways and memory bandwidth among classes of service. Hypervisors and operating systems can bind workloads to NUMA nodes, assign memory bandwidth limits, or schedule tasks to avoid co-locating two bandwidth-heavy workloads on the same socket. GPUs have their own mechanisms for concurrent kernel execution and stream priorities, but they also share device memory bandwidth across kernels.

The design consequences are significant. A latency-critical service should not be co-located with a batch job that streams large data sets unless the memory system can isolate them. A parallel application that assumes it has the full bandwidth of a socket will underperform when another application is running. A runtime that schedules tasks solely by CPU load may create memory hot spots. Bandwidth-aware scheduling considers the expected bytes per second of each task and the available bandwidth on each memory domain. It may deliberately leave some cores idle to avoid saturating a memory controller, or it may spread tasks across sockets to use more channels.

Fairness is not the same as equal sharing. Some workloads need low latency, while others need high throughput. A memory QoS policy might give a latency-sensitive workload a small but guaranteed share of bandwidth and best-effort access to the rest. A throughput-oriented workload might be rate-limited to prevent it from causing queueing delays. The right policy depends on the service-level objectives. What matters is that bandwidth is treated as a managed resource, not an infinite commodity.

This view also changes how we benchmark. A single application running alone on an idle machine is not representative of a shared production environment. Benchmarking should include interference scenarios: run the target workload alongside a streaming copy, a random-access workload, or another instance of itself. Measure not only average bandwidth but also the distribution of latency and the degradation under contention. A kernel that is robust to interference is often more valuable than one that is slightly faster in isolation.

## Interconnects, chiplets, and disaggregated memory

The memory hierarchy does not end at the DRAM controller. Modern processors are increasingly built from chiplets connected by high-speed interconnects, and memory may be attached to a different chiplet than the core that uses it. Cache-coherent interconnects such as CXL allow memory expansion and pooling, but they also introduce another level with its own bandwidth and latency. Accessing memory across a chiplet or a CXL link is not the same as accessing local DRAM. The bandwidth may be lower, the latency higher, and the traffic may compete with cache-coherence traffic.

Disaggregated memory takes this further. Memory can be pooled and assigned dynamically to compute nodes. A node may access memory that is physically attached to another node over a fabric. This improves utilization and flexibility, but it makes bandwidth and latency placement-sensitive. An algorithm that assumes uniform memory access will be disappointed. Tiered memory systems combine fast local DRAM with slower far memory, and the operating system or runtime must decide which pages to keep where. Hot pages should stay local; cold pages can migrate. But migration itself consumes bandwidth, and a poorly chosen policy can cause thrashing.

For bandwidth-aware algorithm design, these interconnects introduce a new roofline level. The ridge point for far memory is lower because bandwidth is lower and latency is higher. Kernels that are compute-bound on local memory may become bandwidth-bound on far memory. The same tiling and fusion techniques apply, but the tile sizes and reuse targets change. Data placement becomes part of the algorithm: which data is local, which is remote, and how often it moves. In some cases, it is better to move computation to the data than to move data to the computation. That is the principle behind near-memory processing and in-situ processing, where simple operations are performed close to the memory arrays to avoid transferring raw bytes.

Near-memory and in-memory computing are still emerging, but they illustrate the logical endpoint of bandwidth-aware design. If moving bytes is the bottleneck, then reduce the distance the bytes must travel. Cache, scratchpad, and registers are the familiar versions of this idea. Memory-side caches and processing elements are the next step. They do not eliminate the need for bandwidth accounting; they change the level at which the accounting is done. The programmer must still decide what data to keep close, what to recompute, and what to stream.

## Bandwidth-aware scheduling and runtime systems

A runtime system that ignores memory bandwidth will eventually hit a wall. Thread pools, task schedulers, and GPU stream managers typically optimize for load balance and CPU utilization. When the workload is bandwidth-bound, maximizing CPU utilization can be counterproductive. More runnable threads create more outstanding memory requests, which increases queueing at the memory controller and can reduce overall throughput. The system may be better off running fewer threads with more work per thread, or scheduling tasks that reuse data already in cache.

Bandwidth-aware scheduling requires an estimate of each task's memory demand. That estimate can come from static analysis, from profiling, or from runtime counters. A task that streams a large array has high demand; a task that computes on a small working set has low demand. The scheduler can then co-schedule tasks with complementary demands, or serialize high-demand tasks to avoid saturating the memory system. On NUMA systems, the scheduler should also consider memory locality: a task that reads a large data structure should run on the node where that structure is allocated. Work stealing can undermine locality if it moves tasks away from their data. A locality-aware scheduler may prefer to leave a core idle rather than migrate a task across sockets.

GPU runtimes face similar issues. Concurrent kernels share device memory bandwidth, L2 cache, and memory controllers. Launching a memory-bound kernel alongside a compute-bound kernel can improve utilization if the compute-bound kernel leaves spare bandwidth. Launching two memory-bound kernels together usually just divides the bandwidth and may increase latency. Stream priorities and kernel fusion can help, but the fundamental limit remains. A runtime that can classify kernels by operational intensity and schedule them accordingly can do better than one that treats all kernels as interchangeable.

Power and energy management add another dimension. Memory bandwidth and memory clock frequency are often coupled to power states. Reducing memory frequency saves energy but lowers bandwidth. A bandwidth-bound workload may be limited by the memory clock even if the core clock is high. Conversely, a compute-bound workload may benefit from higher core clocks while memory runs slower. Runtime power managers must balance these trade-offs. For the algorithm designer, the implication is that energy per byte and energy per operation are both part of the cost model. When bandwidth is the bottleneck, reducing bytes often reduces energy as well.

The scheduling perspective also applies to I/O and network queues. A storage device has a limited queue depth and a limited bandwidth. Issuing more requests than the device can handle increases latency without improving throughput. A network interface has a bandwidth-delay product; sending more data than the link can carry causes buffering and drops. In both cases, the right concurrency is determined by Little's law and the service rate. Bandwidth-aware software controls the number of outstanding requests, batches small operations, and avoids over-subscription. It treats the memory system, the storage device, and the network as finite resources with queues, not as ideal pipes.

These runtime considerations close the loop between algorithm design and system software. The roofline model tells us what the hardware can sustain. The algorithm decides how many bytes are needed. The runtime decides how those bytes are scheduled and where they are placed. When all three are aligned, a parallel program can approach the bandwidth roof without falling off the latency cliff. When they are not, adding cores or threads only adds contention.

## A byte budget in practice

Suppose a service must aggregate 1 TB of logs per hour. The achievable read bandwidth after decompression is 2 GB/s, and the aggregator writes 100 GB of partial results. The byte budget is 1.1 TB per hour, or about 305 MB/s. That is well within bandwidth, so the bottleneck might be decompression or parsing. If the input is compressed at 4:1, the raw storage read is 250 GB/h, but decompression produces 1 TB/h in memory. The memory bandwidth cost is the decompressed stream, not the compressed bytes. This distinction matters: compression saves storage and interconnect bandwidth, but it does not reduce the bytes the CPU must read from memory unless the decompressor writes directly into cache and the parser consumes it immediately.

If the same service instead performs a join that shuffles 1 TB across the network, the network byte budget dominates. A 10 Gb/s link delivers about 4.5 TB/h at full utilization, so the shuffle consumes a large fraction of the fabric. Batching records, combining partial aggregates, and partitioning by key reduce bytes. The roofline question becomes: how many records can be processed per byte shuffled? If the answer is low, the algorithm must change before the cluster grows.

The arithmetic is simple, but it forces an explicit choice: reduce input bytes, reduce intermediate bytes, or reduce output bytes. Each choice has a different cost in CPU, latency, and code complexity.
