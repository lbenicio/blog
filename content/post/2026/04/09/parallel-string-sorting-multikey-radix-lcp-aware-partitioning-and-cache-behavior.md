# Parallel String Sorting: Multikey Radix, LCP-Aware Partitioning, and Cache Behavior

Sorting strings is a different engineering problem from sorting integers. An integer sort moves fixed-width values, and the comparison is a single machine instruction with predictable branch behavior. A string sort moves references to variable-length byte sequences, and the comparison walks memory until it finds a difference or reaches the end of one string. The cost is dominated by cache misses, branch mispredictions, and memory bandwidth rather than by arithmetic. Parallelism does not remove those costs. It changes where they appear and makes the partitioning and data-layout decisions more important.

This article examines parallel string sorting as a systems design problem. The target is an array of byte strings, or an array of offsets into a byte arena, that must be ordered lexicographically. The strings may be short identifiers, long paths, genomic sequences, log keys, or document terms. The workload may contain many duplicate prefixes, many duplicates, or almost no common structure. The implementation may be in-place or out-of-place, stable or unstable, single-threaded or multi-threaded. Each choice changes the cache behavior and the parallel schedule.

The focus is on multikey radix sorting, also called MSD radix sort, and on LCP-aware partitioning. MSD radix sort partitions strings by their first byte, then recursively partitions each bucket by the next byte. It avoids full-string comparisons in the common case and turns the sort into a sequence of histogram, prefix-sum, and scatter phases. LCP-aware partitioning extends the idea by tracking the longest common prefix of a bucket so that recursion can skip bytes that are already known to be equal. Both techniques are attractive for parallel systems because they expose coarse-grained partitioning work and because they can be made cache-conscious. They also introduce hard trade-offs around memory traffic, load balance, stability, and the treatment of prefixes.

## The Problem: Ordering Byte Strings at Scale

The first design decision is the ordering semantics. Lexicographic order over byte strings is defined by comparing bytes from left to right. If two strings differ at some position, the string with the smaller byte value at that position comes first. If one string is a prefix of the other, the shorter string comes first. This definition is simple, but it requires an explicit length for every string. A null-terminated C string cannot represent embedded null bytes, and a length-prefixed representation cannot be compared correctly without carrying the length. In a parallel implementation, the representation should make the length cheap to access, because the comparison and the radix partitioner both need to know when a string ends.

The second decision is the memory layout. A common representation is an array of pointers or offsets into a contiguous byte arena. The sort permutes the offsets, not the bytes. This keeps the sort cheap when strings are long, but it introduces pointer chasing: each comparison or radix scatter follows an offset into a different part of the arena. Another representation is an array of fixed-size inline strings with a length field. This improves locality for short strings but wastes memory and adds copying for long strings. A third representation is a packed arena with offsets and lengths stored in a separate array. The offset array is cache-friendly, but the length array and the byte arena are separate streams. The best choice depends on the string length distribution and on whether the sorted output must preserve key-value pairs.

The third decision is stability. MSD radix sort is naturally unstable unless the scatter phase preserves the input order within each bucket. Stability matters when the strings are keys in a key-value record and ties must retain the original order. It also matters when the sort is used as a component of a larger pipeline that expects deterministic output for equal keys. An unstable sort can be faster because it can use in-place partitioning and can avoid auxiliary arrays. A stable sort usually needs an out-of-place scatter or a stable merge step. In a parallel setting, stability also constrains how partitions are concatenated: the output order of buckets must match the byte order, and the order within a bucket must match the input order.

The fourth decision is the treatment of duplicates. If many strings are equal, a radix sort may create large buckets that never split. A comparison sort can detect equality early and stop, but it still pays the comparison cost. A radix sort can detect a bucket where all strings have the same remaining bytes and stop partitioning that bucket. The implementation must distinguish between a bucket that is fully sorted because all strings are equal and a bucket that is sorted because all strings have ended. This distinction affects the base case and the LCP tracking.

## Why String Sorting Is Not Integer Sorting

Integer sorting benefits from fixed-width keys and dense distributions. Radix sort on integers can use counting sort over a small number of digits, and the scatter phase writes fixed-size records. String sorting has variable-width keys and sparse byte distributions. The first byte of a set of strings may be concentrated in a small alphabet, such as lowercase letters or ASCII path separators, or it may be spread across all 256 byte values. The distribution changes at every recursion depth. A histogram over 256 buckets is cheap, but the scatter phase writes variable-length records or offsets, and the memory access pattern is less predictable.

Comparison-based string sorting has a different cost profile. Each comparison may examine only a few bytes if the strings differ early, or it may examine a long common prefix if the strings are similar. The comparison is branchy: the loop checks for equality, checks for the end of a string, and then compares bytes. Modern processors can predict the loop exit for random strings, but they mispredict when common prefixes are long or when the distribution changes. The comparison also touches memory in a pointer-chasing pattern. For an array of offsets, each comparison follows two offsets into the arena. If the strings are long and the arena is large, each comparison can cause multiple cache misses. The sort may perform O(n log n) comparisons, and each comparison may touch a different cache line. The result is a sort whose cost is dominated by memory latency rather than by the number of comparisons.

MSD radix sort avoids full-string comparisons by examining one byte at a time. It still touches memory, but the access pattern is more structured. The histogram phase reads the byte at the current depth for every string in the bucket. The scatter phase writes each string to a bucket determined by that byte. The recursion then processes each bucket independently. The total work is proportional to the number of bytes examined, not to the number of comparisons. For strings with long common prefixes, MSD radix sort can examine the same prefix repeatedly at each level unless it tracks the LCP. For strings with short common prefixes, MSD radix sort can be very efficient because it stops as soon as the buckets are small enough for a base-case sort.

The parallelization strategy follows from this structure. The top-level partition by the first byte is a large histogram and scatter operation. It can be parallelized by splitting the input into chunks, building per-chunk histograms, summing the histograms, and scattering each chunk into the output. The recursive partitions are independent tasks. They can be processed by a work-stealing scheduler or by a static assignment. The challenge is load balance: one bucket may contain most of the strings, while many buckets contain only a few. A static assignment can leave threads idle. A dynamic assignment adds scheduling overhead and can cause remote memory access. The partitioner must choose a granularity that is large enough to amortize the scheduling cost but small enough to keep all threads busy.

## Multikey Radix Sort as a Baseline

MSD radix sort is the baseline for parallel string sorting. The algorithm starts with a bucket containing all strings and a current depth of zero. It computes a histogram of the byte at the current depth for every string in the bucket. Strings that have ended at the current depth are placed in a separate prefix bucket. The remaining strings are partitioned by their byte value. The algorithm then recurses on each non-empty bucket with the next depth. The recursion stops when a bucket is small enough for a comparison sort, when all strings in the bucket are equal, or when all strings have ended.

The histogram phase is a read-only pass over the bucket. It reads the byte at the current depth for each string. If the strings are stored as offsets into an arena, the histogram phase follows each offset and reads one byte. This is a random access pattern, but it is bounded by the number of strings in the bucket. The scatter phase is a write pass. It writes each string to the output position determined by the histogram prefix sum. If the output is an array of offsets, the scatter writes offsets. If the output is an array of inline strings, the scatter copies the strings. The scatter phase is more expensive because it writes to multiple output buckets and because the write pattern is scattered.

The in-place variant, often called American flag sort, avoids the auxiliary output array. It uses the histogram to compute bucket boundaries and then permutes the strings in place by cycling elements into their correct buckets. The in-place variant reduces memory traffic and memory footprint, but it is harder to parallelize because the permutation cycles create dependencies. The out-of-place variant is simpler to parallelize: each thread can scatter a chunk of the input into a shared output array, and the histogram prefix sum gives each thread a disjoint output range. The trade-off is memory: the out-of-place variant needs an auxiliary array of offsets or strings, which can be large for big inputs.

The base case matters. For small buckets, a comparison sort such as insertion sort or a specialized string insertion sort can be faster than continuing the radix recursion. The base case avoids the histogram and scatter overhead for buckets with only a few strings. The threshold depends on the string length, the distribution, and the cache size. A bucket of 32 strings with long common prefixes may still benefit from LCP-aware recursion, while a bucket of 32 random short strings may be faster with insertion sort. The implementation should make the threshold tunable and should measure it on the target workload rather than assuming a universal constant.

## Parallelizing the Top-Level Partition

The top-level partition is the most parallelizable phase. The input is split into chunks, and each thread builds a local histogram of the first byte. The local histograms are then reduced into a global histogram. A prefix sum over the global histogram gives the starting output position for each byte bucket. Each thread then scatters its chunk into the output array using the global bucket positions. To avoid contention, each thread can reserve a contiguous range within each bucket by using a per-thread offset array. The offset array is updated with atomic operations or with a two-phase reservation scheme. The two-phase scheme first computes the number of elements each thread will write to each bucket, then computes the prefix sum over those counts, and finally scatters without atomics. This avoids atomic contention on the bucket counters and improves scalability.

The scatter phase is sensitive to false sharing. If multiple threads update counters or offsets that share a cache line, the cache coherence protocol serializes the updates even though the logical counters are independent. The implementation should pad the per-thread counters to cache-line boundaries or use a layout that groups counters by thread rather than by bucket. The choice depends on the number of buckets and the number of threads. Padding every counter for 256 buckets and 64 threads wastes memory but may be acceptable for a top-level partition. A more compact layout uses a two-dimensional array with thread-major order and cache-line padding between threads.

The recursive partitions are independent tasks. A simple approach is to process the largest buckets first and to use a work-stealing deque for the remaining buckets. The largest-first order improves load balance because the largest bucket is the most likely to dominate the runtime. The work-stealing scheduler can then distribute the smaller buckets across idle threads. The task granularity should be chosen so that each task has enough work to amortize the scheduling cost. A task that contains only a few strings is too small. A task that contains a large bucket can be split further by the recursive partitioner. The implementation can use a threshold to decide when to stop splitting and when to switch to a base-case sort.

## LCP-Aware Partitioning and Recursion

LCP-aware partitioning tracks the longest common prefix of the strings in a bucket. If all strings in the bucket share a prefix of length k, the recursion can start at depth k instead of depth zero. This avoids re-examining the common prefix at every level. The LCP can be computed when the bucket is created, or it can be maintained incrementally during the partition. A common approach is to compute the LCP of the first and last strings in the bucket after sorting by the current byte, because the lexicographic minimum and maximum of a set of strings share the longest common prefix of the set. This is a useful property: the LCP of the minimum and maximum strings is the LCP of the entire bucket. The implementation can compute this LCP once per bucket and pass it to the recursive calls.

LCP-aware partitioning is most valuable when the workload has long common prefixes. File paths, URLs, log messages, and genomic sequences often share long prefixes. Without LCP tracking, MSD radix sort examines the same prefix bytes at every recursion level. With LCP tracking, the sort skips the shared prefix and partitions only on the first differing byte. The trade-off is the cost of computing and maintaining the LCP. For workloads with short common prefixes, the LCP computation is overhead. The implementation should detect whether the workload benefits from LCP tracking and should fall back to plain MSD radix sort when it does not.

LCP-aware partitioning also changes the parallel schedule. A bucket with a long common prefix may have a large LCP and a small number of differing bytes. The recursion depth is reduced, but the bucket may still contain many strings. The partitioner must decide whether to split the bucket by the next differing byte or to use a comparison sort. If the bucket is large and the LCP is long, the partitioner can skip directly to the first differing byte. If the bucket is small, a comparison sort may be faster because it can use the LCP to avoid re-comparing the common prefix. The base case should use the LCP information when it is available.

## Cache Behavior and Memory Traffic

The cache behavior of parallel string sorting is shaped by three access patterns: the histogram reads, the scatter writes, and the recursive bucket processing. The histogram reads are random accesses into the byte arena. Each read touches one cache line, but the cache line may contain bytes for many strings if the strings are stored contiguously. If the strings are stored as offsets into a large arena, the histogram reads have poor locality. The scatter writes are also scattered: each string is written to a different output bucket. The output buckets are contiguous ranges in the output array, but the writes from different threads interleave across buckets. The recursive processing then reads the buckets in order, which improves locality if the buckets are processed one at a time.

The implementation can improve locality by partitioning the input into cache-sized chunks before the top-level scatter. Each chunk is processed independently, and the output for each chunk is written to a separate region. This reduces the working set and improves cache reuse. The trade-off is that the output regions must be merged or concatenated in the correct order. The merge step can be cheap if the regions are contiguous and the buckets are ordered. The implementation can also use huge pages or transparent huge pages to reduce TLB misses when the arena is large. The choice depends on the operating system and the memory allocation strategy.

False sharing is another cache-level concern. In the parallel partitioner, per-thread counters and offsets are updated frequently. If those counters share cache lines, the coherence traffic can dominate the runtime. The implementation should align hot counters to cache-line boundaries and should avoid sharing counters between threads unless necessary. The same applies to the task queue and the work-stealing deque. The deque should use padded slots or a cache-line-aware layout to avoid false sharing between the owner thread and the thieves.

## Ordering Semantics and Stability

The ordering semantics must be preserved through the parallel partition. The top-level partition orders strings by their first byte. The recursive partitions order each bucket by the next byte. The concatenation of the buckets must follow the byte order. If the implementation uses a stable scatter, the order within each bucket is preserved. If the implementation uses an unstable scatter, the order within each bucket may change. The final output is still sorted lexicographically, but equal strings may appear in a different order. For key-value records, stability may be required. The implementation can use a stable scatter by writing each chunk to the output in input order and by reserving output ranges per bucket per chunk. The trade-off is additional memory and a more complex reservation scheme.

The treatment of prefixes is also an ordering issue. A string that ends at the current depth is a prefix of the strings in the same bucket. The prefix bucket must be placed before the non-prefix buckets in the output. The implementation must handle the prefix bucket separately and must not recurse on it with the next depth. If the prefix bucket contains duplicate strings, the base case can sort them or leave them as is if they are equal. The implementation must also handle the case where all strings in a bucket have ended. This bucket is fully sorted and should not be partitioned further.

## When to Use Comparison Sort Instead

MSD radix sort and LCP-aware partitioning are not always the best choice. For small arrays, a comparison sort such as insertion sort or a standard library sort is simpler and often faster because it avoids the histogram and scatter overhead. For nearly sorted arrays, a comparison sort can exploit the existing order and finish quickly. For short strings with little common structure, a parallel comparison sort or a parallel merge sort may be competitive because the comparison cost is low and the partitioning overhead is avoided. For memory-constrained systems, an in-place comparison sort may be preferable to an out-of-place radix sort that needs an auxiliary array.

The choice also depends on the parallel runtime. A task-based runtime with work stealing is well suited to recursive radix partitions. A data-parallel runtime with bulk synchronous operations is well suited to the top-level histogram and scatter. A hybrid implementation can use a data-parallel top-level partition and a task-parallel recursive partition. The implementation should measure the cost of the histogram, the scatter, and the recursive tasks on the target workload. The best design is the one that minimizes memory traffic and load imbalance, not the one that maximizes the number of threads.

The next design question is how to build a partitioner that preserves cache locality while keeping all threads busy. That question leads to the details of bucket scheduling, output reservation, and the interaction between LCP tracking and the base case.

## Scheduling Buckets Without Losing Locality

The recursive partitioner is a producer and consumer of buckets. A bucket is not just a range of strings; it is a range plus a depth and an LCP. The scheduler must decide which bucket to process next and where to process it. A naive global queue maximizes load balance but destroys locality: each thread pulls a bucket from a distant part of the output and reads strings that were scattered by another thread. A purely static assignment preserves locality but creates idle threads when the byte distribution is skewed. The practical design is a two-level schedule. The top-level partition produces a set of first-byte buckets. Those buckets are grouped into ranges that are large enough to amortize task creation. Each range is assigned to a worker or placed in a work-stealing deque. Within a worker, buckets are processed in output order. This keeps the worker's reads and writes within a contiguous region of the output array and reduces the number of distinct cache lines touched by the recursive partitioner.

The grouping should be based on estimated work, not on bucket count. A bucket with one string and a bucket with a million strings are both one bucket. The partitioner can estimate work from the number of strings and the average LCP. A bucket with many strings and a long LCP may be expensive because it will require several recursive levels. A bucket with many strings and a short LCP may be cheap because the next byte will split it quickly. The estimate does not need to be exact. It only needs to prevent the scheduler from assigning a huge bucket to a worker that already has a full queue. The top-level histogram can provide the bucket sizes before the scatter, so the scheduler can build a work list before any recursive partitioning begins. This is a useful separation: the top-level partition computes the bucket sizes, and the scheduler uses those sizes to create tasks. The recursive partitioner then updates the work list as buckets split.

A work-stealing deque with a single global queue is simple but can become a contention point. Each push and pop touches the queue's head or tail, and the queue's cache line is shared by all workers. A distributed deque per worker reduces contention. The owner pushes and pops from one end, and thieves steal from the other end. The deque should be padded to avoid false sharing between the owner's index and the thieves' index. The bucket metadata should be small: a range, a depth, an LCP, and a pointer to the output region. If the metadata is large, the deque becomes a memory stream of its own. Packing the metadata into a few words keeps the deque cache-friendly. The strings themselves are not moved by the scheduler; only the metadata is moved. The output array is shared and is written by the scatter phases.

Locality also depends on when a bucket is processed. If a worker processes a bucket immediately after the top-level scatter, the bucket's strings may still be in cache from the scatter writes. If the worker waits until all top-level buckets are scattered, the cache may have been evicted. The implementation can interleave the top-level scatter with recursive processing: as soon as a top-level bucket is complete, a worker can start partitioning it while other workers finish the scatter. This overlaps the write traffic of the scatter with the read traffic of the recursion. The overlap is beneficial when the memory system is not saturated. It can be harmful when the scatter and the recursion compete for the same cache lines. The implementation should make the overlap optional and should measure the effect on the target workload.

## Output Reservation and Stable Scatter

The scatter phase writes each string to a bucket-specific output range. In a parallel implementation, multiple threads scatter into the same bucket. The bucket's output range must be divided among the threads without overlap. A common approach is to reserve space per thread per bucket. The reservation can be done with atomics or with a two-phase count. The two-phase count is usually better for large buckets because it avoids atomic contention. In the first phase, each thread counts how many strings it will write to each bucket. In the second phase, a prefix sum over the per-thread counts gives each thread a starting offset within each bucket. The thread then writes its strings in input order. This preserves the relative order of strings within each thread's chunk. If the input chunks are ordered and the per-thread ranges are ordered by thread, the scatter is stable with respect to the input. The output within each bucket is the concatenation of the thread chunks in thread order. This is stable if the thread order matches the input order. The implementation can assign chunks to threads in input order and can reserve ranges in the same order. The cost is an extra pass over the per-thread counts, but the pass is over a small array of counters, not over the strings.

The reservation array has a shape that matters for cache behavior. A layout indexed by bucket and then by thread is natural for the scatter: each thread walks its own column? Actually if bucket-major, a thread writing to many buckets touches many cache lines. If thread-major, a thread writing to many buckets touches a contiguous region of counters. The thread-major layout is better for the scatter because each thread updates its own row. The prefix sum over threads for a given bucket then reads a column, which is strided. The prefix sum is a small part of the work, so the strided read is acceptable. The implementation can transpose the array after the count phase or can compute the prefix sum in a separate pass. The choice depends on the number of buckets and the number of threads. For 256 buckets and 64 threads, the array is small enough to fit in cache, and the layout has little effect. For a recursive partitioner with many buckets and many threads, the array can become large. The implementation should use a compact counter type and should avoid padding every counter unless false sharing is measured.

Stability also affects the treatment of the prefix bucket. Strings that end at the current depth are prefixes of the other strings in the bucket. They must be placed before the non-prefix buckets. If the scatter is stable, the prefix bucket preserves the input order of the prefix strings. If the sort is unstable, the prefix bucket can be written in any order. The implementation should not recurse on the prefix bucket with the next depth. The prefix bucket is already sorted with respect to the current depth, but it may contain strings that are equal. If the sort must be stable, the prefix bucket's order is already correct. If the sort is unstable, the prefix bucket can be left as is. The partitioner should mark the prefix bucket as complete and should not schedule it. This reduces the number of tasks and avoids unnecessary work.

## LCP Tracking in the Recursive Partitioner

LCP tracking changes the metadata that the scheduler must carry. A bucket's LCP is the number of bytes that are known to be equal for all strings in the bucket. The partitioner can start the next histogram at depth equal to the LCP. The LCP is not just an optimization for the histogram; it also changes the base case. If the LCP is long and the bucket is small, a comparison sort can use the LCP to skip the common prefix. The comparison sort must still compare the remaining bytes, but it can start at the LCP. This is valuable when the strings are long and the bucket is small. The partitioner can pass the LCP to the base-case sort as a hint. The base-case sort can then compare only the suffixes after the LCP. The hint must be correct: if the LCP is underestimated, the sort still works but does extra comparisons. If the LCP is overestimated, the sort can produce an incorrect order. The implementation must compute the LCP conservatively. The LCP of the minimum and maximum strings in the bucket is a safe lower bound. It is also the exact LCP of the bucket if the bucket is sorted by the current prefix. The partitioner can compute this LCP after the scatter by comparing the first and last strings in the bucket. The comparison is cheap because it only needs to compare two strings. The result is a single integer that can be stored in the bucket metadata.

The LCP computation itself can be a cache miss. Comparing the first and last strings follows two offsets into the arena and walks their bytes. If the strings are long and the LCP is long, the comparison touches many cache lines. The partitioner can avoid this cost by computing the LCP incrementally during the histogram. When the histogram reads the byte at the current depth for each string, it can also track whether all strings share the same byte. If they do, the LCP can be incremented. This incremental approach avoids a separate comparison but requires the histogram to track the common byte. The histogram already reads the byte, so the extra work is a comparison and a branch. The branch is predictable when the bucket has a long common prefix. The incremental approach is attractive for buckets that are processed in a single pass. The first-and-last approach is attractive when the bucket is already sorted by the current prefix and the partitioner needs an exact LCP. The implementation can use both: incremental tracking during the histogram and a first-and-last check at the end of the scatter.

LCP tracking also interacts with load balance. A bucket with a long LCP may have a small number of differing bytes but a large number of strings. The partitioner may skip many levels and then find a byte that splits the bucket into two large buckets. The work estimate should account for the LCP: a bucket with a long LCP is likely to require fewer histogram passes, but each pass may process many strings. The scheduler should not assume that a long LCP means a cheap bucket. The cost is proportional to the number of strings times the number of bytes examined, not to the recursion depth alone. The partitioner can estimate the cost as the number of strings times the average remaining suffix length. The average suffix length is hard to know without scanning. A simpler estimate is the number of strings times a constant plus the LCP. The constant accounts for the histogram and scatter overhead. The estimate is only a heuristic, but it helps the scheduler avoid assigning a large bucket to a worker that is already busy.

## Base Cases and Hybrid Switches

The base case is where the radix partitioner hands control to a comparison sort. The switch should be based on the bucket size, the LCP, and the remaining suffix length. A bucket of 16 strings with a long LCP may be faster with insertion sort than with another radix level. A bucket of 16 strings with a short LCP may also be faster with insertion sort, because the histogram and scatter overhead dominates. A bucket of 256 strings with a long LCP may still benefit from radix partitioning if the next byte has a skewed distribution. The implementation should not use a single threshold for all workloads. It should measure the cost of a radix level and the cost of a comparison sort on the target strings. The measurement can be done offline or at runtime with a small sample. A runtime switch can adapt to the distribution: if a bucket's histogram shows that most strings fall into one byte bucket, the partitioner can continue with radix; if the histogram is nearly uniform and the bucket is small, the partitioner can switch to comparison sort.

The base-case sort should be aware of the string representation. For an array of offsets, insertion sort compares offsets by following them into the arena. The comparisons are branchy and may cause cache misses. A better base case is a small radix sort over the remaining bytes if the strings are short. For long strings, a comparison sort that uses the LCP hint is often better. The base case should also avoid copying strings. If the output is an array of offsets, the base case permutes offsets. If the output is an array of inline strings, the base case may need to copy strings. The implementation should choose the base case that minimizes memory traffic. For inline strings, a small bucket can be sorted by copying the strings into a temporary array and then writing them back in order. The temporary array fits in cache if the bucket is small. The copy cost is offset by the improved locality.

The hybrid switch also applies to the top-level partition. If the input is small, a parallel comparison sort may be faster than a parallel radix sort because it avoids the histogram and scatter. If the input is large but the strings are short and random, a parallel radix sort may be faster because the histogram is cheap and the scatter is sequential. The implementation should choose the algorithm based on the input size and the string length distribution. The choice can be made once at the start of the sort. It does not need to be dynamic. The important point is that the parallel string sort should not be a single algorithm. It should be a family of algorithms with a shared partitioning framework. The framework provides the histogram, scatter, and bucket scheduling. The algorithm choice determines whether the framework uses LCP tracking, whether it uses a stable scatter, and when it switches to a comparison sort.

## NUMA-Aware Partitioning and Memory Placement

On a multi-socket machine, the memory hierarchy is not a single cache. Each socket has local DRAM and a path to remote DRAM. The latency difference between local and remote memory can be a factor of two or more, and the bandwidth difference is similar. A parallel string sort that ignores NUMA placement can spend much of its time waiting on remote memory even when the aggregate bandwidth is not saturated. The first-touch policy of most operating systems means that a page is placed on the node of the thread that first writes to it. If the input arena is allocated and filled by one thread, all of its pages are local to one node. If the output array is allocated by one thread and then scattered by all threads, the output pages are also concentrated on one node. The result is that most threads read and write remote memory.

The fix is to control placement explicitly. The input arena is read-mostly and is accessed in a random pattern during the histogram phase. Interleaving its pages across all nodes balances the read bandwidth. The output array is write-heavy during the scatter and read-heavy during the recursive partition. Its pages should be placed on the node that will process the corresponding buckets. This is easier if the top-level partition assigns buckets to nodes before the scatter. The partitioner can compute the global histogram, divide the byte buckets into node-local groups, and have each node scatter only into its own output range. The input chunks are still read from the interleaved arena, but the writes stay local. The recursive partitioner then processes each node-local group on the node that owns it. Work stealing can still move a bucket to another node, but the scheduler should prefer local buckets and should steal only when a node is idle. A stolen bucket may cause remote reads and writes, but that is better than leaving a node idle.

The counters and metadata used by the partitioner must also be NUMA-aware. A single global histogram is reduced across nodes, which is cheap because the histogram is small. The per-thread reservation counters are more problematic. If they are allocated on one node, every thread updates remote memory during the scatter. The counters should be replicated per node and reduced at the end of the count phase. The reduction is a small all-to-all operation over a few kilobytes. The same applies to the work-stealing deques. Each node should have its own deque, and thieves should steal from remote deques only when local deques are empty. The deque metadata should be padded to avoid cache-line bouncing across sockets. On some systems, the cache line size is 64 bytes, but the coherence granule is 128 bytes or larger. Padding to 128 bytes is a safe choice for hot counters.

Huge pages reduce TLB misses, which are a hidden cost in string sorting. A large arena with random offsets can cause a TLB miss for every few strings. Transparent huge pages help, but they can introduce compaction stalls and unpredictable latency. Explicit huge pages, allocated from a hugetlbfs mount, give stable performance but require preallocation. The output array should also use huge pages because the scatter writes touch many pages in a short time. Page faults during the scatter are especially harmful because they serialize the worker that triggers them. The implementation should pre-fault the output array before the timed sort, or use a memory allocator that populates pages eagerly. The cost of pre-faulting is paid once and is usually small compared to the sort itself.

## Vectorized Histograms and Branchless Classification

The histogram phase is a natural target for vectorization, but it is not a simple vector reduction. Each string contributes one byte to a 256-bin histogram. A scalar loop loads an offset, loads a byte from the arena, checks whether the string has ended, and increments a counter. The branch that checks for the end of the string is unpredictable when the bucket contains a mix of ended and non-ended strings. The counter increment is a read-modify-write to a small array, which is fast if the array is in L1 but can suffer from store-to-load forwarding stalls when the same counter is updated repeatedly.

A vectorized histogram can process several strings at once. With AVX2, a gather instruction can load eight 32-bit offsets from the offset array. With AVX-512, it can load sixteen. The same gather can fetch the bytes at the current depth from the arena. The lengths, if stored separately, can be gathered in the same way. The vector comparison against the lengths produces a mask of ended strings. The non-ended bytes are then classified. The classification can be a direct byte value or a dense rank if the alphabet has been compressed. The hard part is the histogram update. Scattering into a shared 256-bin histogram from vector lanes creates conflicts. The standard solution is to give each lane its own histogram. Eight lanes times 256 bins times four bytes is 8 KB, which fits in L1. Sixteen lanes would be 16 KB, which is at the edge of L1 on many processors. The per-lane histograms are reduced at the end of the chunk. This increases the instruction count but removes the conflicts and the serialization.

An alternative is a two-level histogram. The first pass counts the high nibble of each byte, using sixteen bins. The second pass counts the low nibble within each high-nibble bucket. The two-level approach uses fewer counters and has better cache behavior, but it requires two passes over the strings. For short strings, the extra pass may cost more than the conflict-free update. For long strings, the first pass can be fused with the LCP check, and the second pass can be fused with the scatter. The implementation should choose based on the average string length and the alphabet size. For a DNA alphabet, a four-bin histogram is enough, and the byte values can be packed into two bits. For ASCII lowercase, a 26-bin histogram is enough, but the mapping from byte to rank costs a table lookup. The table is 256 bytes and stays in L1, so the cost is low.

Branchless classification is also useful in the scalar path. Instead of branching on whether a string has ended, the implementation can compute an index that is either the byte value or a special prefix index. For example, if the string has ended, the index is 256; otherwise, it is the byte value. The histogram has 257 bins. The increment is unconditional. The branch is replaced by a conditional move, which is cheaper than a mispredicted branch. The same trick applies to the scatter phase: the output position is computed from the prefix sum, and the string is written to that position regardless of whether it is a prefix. The prefix bucket is just another bucket at the beginning of the output range. This simplifies the control flow and makes the scatter more regular.

Vectorization also helps the LCP computation. Comparing two strings byte by byte is slow when the common prefix is long. A vectorized comparison loads 32 bytes from each string, compares them, and uses a movemask to find the first differing byte. If the mask is zero, the strings match for 32 bytes, and the comparison advances by 32. The loop continues until a difference is found or the end of a string is reached. The same routine can be used in the base-case sort and in the first-and-last LCP check. The main caveat is page safety: loading 32 bytes from a string near the end of a page can cross into an unmapped page. The arena should be padded with at least 32 bytes of readable memory after each string, or the comparison should use masked loads. Padding the arena is simpler and costs little memory.

## Prefetching and Software Pipelining

Memory latency is the dominant cost in the histogram phase. The offset array is read sequentially, so the hardware prefetcher handles it well. The arena accesses are random, so the hardware prefetcher cannot help. Software prefetching can hide the arena latency. The implementation can prefetch the cache line containing the byte at the current depth for a string that will be processed several iterations later. The prefetch distance depends on the memory latency and the number of strings processed per cycle. A distance of 8 to 16 strings is a good starting point. The prefetch address is computed from the offset and the depth. If the depth is large, the prefetch may cross into a different cache line, but the offset is still valid. The prefetch instruction does not fault if the address is invalid, so the implementation can prefetch aggressively without a safety check.

A software pipeline can overlap the offset load, the arena prefetch, and the histogram update. The loop loads the offset for iteration i + D, prefetches the arena line for that offset, and then processes iteration i. The offset array is small enough to stay in cache, so the load is cheap. The arena prefetch is the expensive part. The pipeline increases the number of outstanding memory requests, which improves memory-level parallelism. On a saturated memory system, the prefetches may not help, but they rarely hurt if the distance is tuned. The implementation should measure the effect on the target workload rather than assuming that prefetching is always beneficial.

The scatter phase has a different access pattern. The output positions are computed from the histogram prefix sum, so the writes are scattered across the output array. The implementation can prefetch the output cache line before writing. The prefetch address is the output position for a string that will be processed later. The output array is write-heavy, and the prefetches bring the lines into cache in exclusive state. This can reduce the latency of the store, but it also increases the number of cache lines in flight. If the output array is much larger than the cache, the prefetched lines may be evicted before the store arrives. The prefetch distance should be shorter than in the histogram phase. A distance of 4 to 8 strings is often enough.

Non-temporal stores are sometimes suggested for the scatter because they bypass the cache and avoid write-allocate traffic. In a string sort, the output is read again by the recursive partitioner, usually very soon after the scatter. Bypassing the cache would force the recursive partitioner to read from DRAM, which is slower than reading from cache. Non-temporal stores are only appropriate when the output is written once and not read until much later, such as in an external-memory sort. For an in-memory parallel string sort, temporal stores are the right choice. The implementation should keep the output in cache and should process the buckets in the order they were written.

## Skewed Alphabets and Adaptive Bucketing

The byte alphabet has 256 possible values, but real string workloads rarely use all of them. A histogram over 256 bins is cheap to compute, but the scatter phase creates up to 256 output buckets, many of which are empty. Empty buckets cost nothing to write, but they add to the prefix sum and to the task metadata. For a workload with a small alphabet, such as DNA or lowercase ASCII, the implementation can compress the alphabet to a dense set of ranks. The compression table is built from the top-level histogram. Each byte is translated to its rank before the histogram and scatter. The rank is smaller, so the counter array is smaller and fits more easily in cache. The translation adds a table lookup per byte, but the table is 256 bytes and stays in L1. The benefit is a smaller working set and fewer empty buckets.

Skewed distributions are more challenging than small alphabets. A workload may have 90 percent of its strings starting with the same byte. The top-level partition creates one huge bucket and many tiny buckets. A static assignment of buckets to threads leaves most threads idle while one thread processes the huge bucket. The scheduler should detect this and split the huge bucket further. The split can happen before the top-level scatter is complete. The partitioner can process the huge bucket first, using all threads to partition it by the next byte. This is a parallel partition within a bucket. The same histogram and scatter machinery is used, but the input range is the huge bucket and the output range is a subrange of the output array. The subrange is contiguous because the huge bucket occupies a contiguous range. The parallel partition within the bucket produces smaller buckets that can be distributed to other threads.

Adaptive bucketing also helps when a bucket has a long LCP. If all strings in a bucket share the next byte, the partitioner can increment the LCP and skip the scatter. The histogram phase reads the byte at the current depth, finds that all non-ended strings have the same value, and advances the depth. No output is written, and no new buckets are created. This is a cheap pass that reduces the number of scatter operations. The pass can be vectorized and prefetched like a normal histogram. The implementation should detect the all-equal case and continue the loop until a differing byte is found or the bucket is exhausted. The LCP is updated by the number of bytes skipped. This is especially effective for file paths, where many strings share a long directory prefix.

The choice between a 256-bin histogram and a compressed alphabet is not permanent. The top-level partition can use the full 256 bins because it only runs once. The recursive partitions can use a compressed alphabet if the histogram shows that only a few bytes are present. The compression table can be built per bucket, but building it costs a pass over the strings. A simpler approach is to use the global alphabet from the top level. If the global alphabet is small, the compressed ranks are valid for all recursive levels. If the global alphabet is large but a particular bucket uses only a few bytes, the implementation can fall back to the full histogram for that bucket. The decision can be made from the bucket's histogram after the first pass. The overhead of the first pass is small compared to the savings in the recursive levels.

## Instrumentation and Cost Attribution

Performance work on parallel string sorting fails when it treats the sort as a single timed region. The useful unit is the phase. A histogram pass, an LCP scan, a scatter, a recursive dispatch, and a base-case comparison sort have different bottlenecks, and averaging them into one number hides the decisions that matter. The implementation should accumulate time per phase per worker using low-overhead counters. Calling a high-resolution timer for every string is counterproductive; the timer itself becomes a measurable cost. Instead, sample at chunk boundaries or accumulate cycle counts around coarse blocks. The resulting profile shows whether the sort is spending its time reading the arena, writing the output, updating counters, or waiting for work.

Hardware counters fill in what wall-clock timers cannot. Instructions retired, cycles, L1 and L2 misses, last-level cache misses, data TLB misses, and memory bandwidth separate latency-bound phases from bandwidth-bound phases. A histogram pass that reads one byte per string from a large arena is usually latency-bound: the processor has few independent requests in flight unless the implementation prefetches or processes multiple strings per iteration. A scatter pass that writes offsets into many output buckets is often bandwidth-bound, but it can also suffer from write-allocate traffic and false sharing. The same phase can switch regimes as the bucket size changes. A top-level scatter over millions of strings may saturate memory bandwidth, while a recursive scatter over a few thousand strings may fit in cache and become instruction-bound.

Load imbalance needs its own metric. The ratio of the slowest worker's time to the mean worker time captures the tail, but it does not say why the tail exists. The implementation should also record the largest bucket processed by any worker, the number of steals, and the time spent waiting for work. A sort with a good mean but a long tail is a poor parallel sort. The tail often comes from one bucket that was not split early enough. Recording bucket size and LCP at dispatch time makes that visible. If the largest bucket is an order of magnitude larger than the median, the scheduler needs a split-before-scatter rule or a work-stealing policy that targets the large bucket first.

Cache-line utilization is another useful measurement. For the arena reads, the implementation can count how many bytes of each touched cache line are actually used. If the strings are short and scattered, a 64-byte line may yield only a few useful bytes. That ratio explains why a histogram pass with a low instruction count can still be slow. For the output writes, the implementation can count how many stores fall into the same cache line and whether the line is written by multiple threads. A high false-sharing rate shows up as coherence traffic and as a gap between store instructions and completed writes. These measurements are more informative than a single cache-miss count because they connect the miss to the data layout.

Benchmark design should separate cold-cache and warm-cache behavior. A cold run measures the cost of bringing the arena and output into cache; a warm run measures the steady-state cost. Both are valid, but they answer different questions. The input generator should produce several distributions: random bytes, short identifiers, long shared prefixes, duplicate-heavy keys, and adversarial skew. Reporting only the median hides the tail that matters for scheduling. The median, the 95th percentile, and the maximum worker time together give a clearer picture. The implementation should also report the effective bytes processed per second and the number of arena bytes touched per string, because those numbers expose whether the sort is doing more memory traffic than the algorithm requires.

## Failure Modes and Guardrails

Pathological inputs are not edge cases in string sorting; they are common. A workload where all strings are equal defeats a radix partitioner that assumes every level will split the bucket. The histogram finds one non-empty byte bucket and one prefix bucket, and the recursion makes no progress. The guardrail is an explicit all-equal check before the next histogram. If every non-ended string has the same byte at the current depth and the prefix bucket is empty, the partitioner can advance the depth and skip the scatter. If the bucket contains only equal strings, it is already sorted. This check costs one pass, but it prevents an unbounded recursion that would otherwise consume the same strings repeatedly.

Long common prefixes create a different failure mode. LCP tracking reduces the number of passes, but the LCP computation itself can become a cache-miss stream if it compares the first and last strings naively. The guardrail is to compute the LCP incrementally during the histogram when possible and to use the first-and-last check only when the bucket is already ordered by the current prefix. If the LCP is long and the bucket is small, the partitioner should switch to a comparison sort with the LCP hint rather than continue radix recursion. The switch should be based on measured cost, not on a fixed depth. A depth limit without a cost check can force a comparison sort on a bucket that would have split cheaply on the next byte.

Prefix-heavy inputs stress the treatment of strings that end at the current depth. If the prefix bucket is accidentally included in the recursive partition, the sort either loses strings or compares past their end. The guardrail is to mark the prefix bucket as complete and to place it before all non-prefix buckets. The prefix bucket does not need further radix levels, but it may still contain duplicates that require stable ordering. The implementation should preserve the input order within the prefix bucket when stability is required and should avoid scheduling the bucket as a separate task.

Adversarial skew is the load-balance failure mode. One byte value may contain most of the strings, while hundreds of buckets contain one string each. A static assignment leaves most workers idle. The guardrail is to split the large bucket before the top-level scatter completes. The split uses the same histogram and scatter machinery on a subrange, producing smaller buckets that can be distributed. The scheduler should also cap the number of steals per worker; a steal storm can replace useful work with queue contention. Local deques with occasional remote steals are usually better than a single global queue under skew.

Memory blowup is the final common failure. An out-of-place scatter with per-thread reservations can allocate more auxiliary memory than the input itself if the reservation array is padded for every bucket and every thread. The guardrail is to size the reservation array from the actual number of non-empty buckets and to reuse buffers across recursive levels. Counter overflow is related: a 32-bit counter is sufficient for many inputs but not for billion-string arenas. The implementation should use 64-bit counts for global totals and 32-bit offsets only after a range check. These guardrails do not make the sort correct by themselves, but they prevent the common cases where a parallel string sort degrades into a memory-bound or serialized path.
