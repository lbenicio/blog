# Deterministic Parallel Reductions: Floating-Point Non-Associativity, Reproducibility, and the Cost of Ordering

Parallel reductions look deceptively simple. You have an array, an associative operator, and many cores. Split the array into chunks, compute a partial result per chunk, then combine partials. If the operator is associative, the final result should not depend on how you split or combine. That assumption is true for integer addition modulo a word size, bitwise OR, min, max, and set union. It is not true for floating-point addition. It is not true for floating-point multiplication. It is not true for many user-defined operators that look associative but are only approximately so. Once you accept that, the design space of parallel reductions changes. You are no longer just optimizing bandwidth and synchronization. You are choosing a numerical contract, a scheduling discipline, and a reproducibility guarantee.

This article is about that design space. It focuses on deterministic parallel reductions: how to compute a reduction in parallel while producing a result that is independent of thread count, scheduling order, and hardware topology. The motivating case is floating-point summation, because it is the most common reduction in scientific computing, machine learning, graphics, and data analysis. The same reasoning applies to dot products, norms, means, variances, histograms weighted by floats, and reductions over user-defined types.

The central tension is simple. Determinism usually costs performance. You can make a parallel reduction deterministic by fixing the order of operations, but fixed order can destroy locality, limit parallelism, or force synchronization. You can make it fast by letting threads combine partials in whatever order they finish, but that introduces run-to-run variation. The engineering question is not whether one is better. It is where on the spectrum your application needs to sit, and what mechanisms let you move along that spectrum without rewriting the entire kernel.

## The reduction abstraction and its hidden assumption

A reduction takes a sequence of values and an operator, and produces a single value. In sequential code, the order is usually obvious: left to right. In parallel code, the order is a graph. A binary tree reduction combines pairs, then pairs of pairs, until one value remains. A blocked reduction computes per-block partials and combines them. A work-stealing reduction lets idle workers steal chunks and combine partials in completion order. A GPU reduction might use warp shuffles, shared memory, and atomic operations. All of these are valid if the operator is associative and commutative, or at least associative with a known order. Floating-point addition is commutative in IEEE 754 for normal values, but it is not associative. That single fact invalidates the usual proof that a parallel reduction is equivalent to the sequential one.

Consider three values: `a = 1e20`, `b = -1e20`, `c = 1`. In left-to-right order, `(a + b) + c = 0 + 1 = 1`. In a different order, `a + (b + c) = 1e20 + (-1e20 + 1) = 1e20 - 1e20 = 0`. The exact result depends on rounding at each step. This is not a pathological corner case. It appears whenever values span a wide dynamic range, which is common in sums of residuals, gradients, log-likelihoods, and physical simulations. It also appears in parallel reductions over large arrays where partial sums grow and then cancel.

The hidden assumption in most parallel reduction libraries is that associativity is close enough. For many applications, it is. A neural network training run does not need bitwise reproducibility across different GPU counts. A graphics shader does not care if the sum of a few hundred floats varies in the last bit. But a regression test does. A deterministic build does. A scientific result that must be reproducible across clusters does. A financial calculation that must be auditable does. A debugging session where a bug appears only with 7 threads and not 8 does.

When you decide to make a reduction deterministic, you are not just adding a sort or a lock. You are deciding that the numerical result is part of the interface. That decision has consequences for how you schedule work, how you allocate memory, and how you test.

## Floating-point addition is not associative

IEEE 754 defines floating-point operations as if computed with infinite precision and then rounded to the destination format. The rounding mode is usually round-to-nearest, ties-to-even. Each addition produces a result that is the correctly rounded sum of its two operands. But the next addition rounds again. The error from each rounding accumulates. The order of additions determines the sequence of roundings. Different orders produce different errors.

This is not a bug in IEEE 754. It is the fundamental trade-off of finite precision. The standard gives you predictable per-operation behavior, not algebraic laws. Floating-point addition is commutative: `a + b` equals `b + a` for normal values, except for NaN payloads and signed zero. It is not associative. It is not distributive. Multiplication is not associative either. Subtraction is just addition with a sign flip, so it inherits the same problems.

The practical consequence is that a parallel reduction over floats has a different error profile than a sequential reduction. Sometimes the parallel version is more accurate, because tree reductions have lower error growth than linear summation. Sometimes it is less accurate, because a bad combination order can create cancellation. The error is not random. It is determined by the data and the order. If the order changes, the result changes.

For integer addition, the situation is different. If you use fixed-width integers, addition is associative modulo 2^N. Overflow wraps or saturates depending on the type. If you use arbitrary-precision integers, addition is truly associative and commutative. That is why parallel integer reductions are easy: you can combine partials in any order and get the same answer. The difficulty is almost entirely in floating-point and in user-defined types that emulate floating-point behavior.

## Where nondeterminism enters a parallel reduction

Nondeterminism in a parallel reduction does not come from a single source. It comes from several layers, and each layer has its own fix.

The first layer is the decomposition. If you split the array into a fixed number of chunks, the set of partial sums is fixed. If you split dynamically, the chunks depend on scheduling. A dynamic split is often faster because it balances load, but it makes the combination order depend on thread timing.

The second layer is the combination order. Even with fixed chunks, the order in which partials are combined can vary. A tree reduction with a fixed tree is deterministic. A reduction that uses a shared accumulator protected by a lock is not. A reduction that uses atomic adds is not, because the order of atomic operations depends on hardware arbitration and timing. A reduction that uses a work-stealing deque is not, because the stealing order depends on which worker is idle.

The third layer is the hardware. Floating-point units may use different precisions internally, such as x87 80-bit registers or fused multiply-add. Compilers may reassociate expressions under fast-math flags. Vectorization may change the order of operations. Different CPU architectures may have different rounding behavior for denormals or for fused operations. If you need bitwise reproducibility across machines, you must control all of these.

The fourth layer is the algorithm. If you use a different algorithm for different input sizes, the result can change when the size crosses a threshold. If you use a different number of threads, the result can change. If you use a different block size on a GPU, the result can change. Determinism is a property of the entire execution, not just the reduction kernel.

A deterministic parallel reduction must fix the decomposition, the combination order, the hardware behavior, and the algorithm across all configurations that are supposed to produce the same result. That is a strong requirement. It is also achievable, but it requires designing the reduction around a canonical order rather than around the scheduler.

## Determinism, reproducibility, and accuracy are different goals

It is useful to separate three properties that are often conflated.

Determinism means that the same program with the same inputs produces the same output every time it runs on the same machine and configuration. It does not necessarily mean the output is the same across different thread counts or different machines.

Reproducibility means that the same program with the same inputs produces the same output across different configurations, such as thread counts, block sizes, or hardware. This is stronger. It usually requires a canonical reduction order that is independent of the number of workers.

Accuracy means that the result is close to the exact mathematical result. Accuracy is a numerical property, not a scheduling property. A deterministic reduction can be inaccurate. A nondeterministic reduction can be accurate on average. Accuracy depends on the summation algorithm, the condition number of the data, and the error analysis.

A common mistake is to assume that determinism implies accuracy. It does not. A fixed left-to-right sum is deterministic but can be much less accurate than a pairwise tree sum. A fixed tree sum is deterministic and often more accurate, but it can still lose precision if the tree is unbalanced. A compensated summation algorithm can be accurate but may not be deterministic if it uses parallel combination without care.

The right goal depends on the application. A test suite for a numerical library might need bitwise reproducibility across thread counts. A production training job might need determinism on a fixed configuration but not across configurations. A visualization might not need either. The engineering effort should match the requirement.

## A taxonomy of reduction strategies

Parallel reduction strategies can be classified by how they choose the combination order and how they handle synchronization.

The simplest is the sequential reduction. It is deterministic and easy to reason about, but it does not use multiple cores. It is the baseline for correctness, not for performance.

The fixed tree reduction is the classic parallel approach. The array is divided into a fixed number of leaves, and a binary tree combines them in a fixed order. The tree structure is independent of the number of threads. Threads compute leaf partials, then combine them according to the tree. This is deterministic and reproducible if the leaf assignment and tree shape are fixed. It can be less efficient than dynamic scheduling because the tree imposes synchronization points.

The blocked reduction with fixed block count is similar. The array is divided into a fixed number of blocks. Each block is reduced sequentially. The block partials are then reduced in a fixed order. This is deterministic if the block boundaries and combination order are fixed. It is often faster than a strict tree because each block can be processed independently, but it may suffer from load imbalance if block costs vary.

The dynamic blocked reduction uses a work queue or work-stealing scheduler. Blocks are assigned to threads as they become available. This balances load well, but the combination order depends on completion order. It is not deterministic unless the partials are stored in a fixed array indexed by block and combined in a fixed order after all blocks finish. That two-phase approach, dynamic computation with fixed combination, is a common way to get determinism without sacrificing load balance.

The atomic reduction uses atomic operations to combine partials directly into a shared accumulator. It is simple and can be fast for small numbers of threads, but the order is nondeterministic. It also has high contention for large thread counts. It is usually not suitable when reproducibility is required.

The warp-level or subgroup reduction uses hardware shuffles to combine values within a warp or subgroup. It is fast and deterministic within the subgroup if the shuffle order is fixed. The cross-warp combination must still be handled carefully. On GPUs, the block-level reduction often uses shared memory and a fixed tree, which is deterministic per block. The grid-level combination across blocks is where nondeterminism usually enters, especially if atomic adds are used.

The hierarchical reduction combines multiple levels: thread-local partials, warp partials, block partials, and grid partials. Each level can have its own determinism properties. A well-designed deterministic reduction fixes the order at every level and stores partials in a deterministic layout.

The compensated reduction uses algorithms like Kahan summation, Neumaier summation, or pairwise summation to improve accuracy. These algorithms can be parallelized, but the combination step must preserve the compensation terms. A naive parallel combination of Kahan sums is not equivalent to a sequential Kahan sum. To make it deterministic, you must define a canonical combination order and apply the compensation consistently.

The superaccumulator or expansion-based reduction represents the sum exactly or with much higher precision using a fixed-point or multi-component representation. These methods can be made deterministic and reproducible because they avoid the order-dependent rounding of floating-point addition. They are more expensive in memory and arithmetic, but they are useful when accuracy and reproducibility are critical. Examples include long accumulators, floating-point expansions, and fixed-point accumulators with sufficient range.

The binned or reproducible summation approach groups values by exponent and sums them in a way that is independent of order. This is the idea behind reproducible BLAS and similar libraries. It is not magic. It requires extra work to bin values, and the binning itself must be deterministic. But it can provide bitwise reproducibility across thread counts and even across some hardware differences.

In the next sections, we will examine these strategies in more detail, starting with the arithmetic of fixed tree reductions and the scheduling boundary that separates deterministic computation from nondeterministic combination. We will then look at compensated summation, superaccumulators, and the practical cost of enforcing a canonical order in OpenMP, MPI, CUDA, and task-based runtimes.

## Fixed trees as a numerical specification

A fixed tree reduction is not merely a scheduling pattern; it is a numerical specification. The tree defines a parenthesization of the sum. For an array `x[0..n-1]`, a binary tree with leaves `L_0..L_{m-1}` and internal nodes defines the exact sequence of additions. If the tree shape and leaf boundaries are fixed, the result is a deterministic function of the input. The number of threads, the order in which leaves are computed, and the hardware used to compute each leaf do not affect the parenthesization, provided each leaf's internal sum is also computed in a fixed order. This is the key separation: parallelism evaluates the leaves and internal nodes, but the dependency graph of additions is fixed.

The shape of the tree affects both accuracy and cost. A balanced binary tree over `m` leaves has depth `ceil(log2 m)`. The error bound for pairwise summation is proportional to `log2 n` times the sum of absolute values, rather than `n` times for left-to-right summation. If each leaf contains `k` elements summed sequentially, the error bound grows roughly as `(k - 1 + log2 m) * eps * sum |x_i|`. This gives a practical knob: smaller `k` reduces sequential error, while smaller `m` reduces combination overhead. For double precision, `k` in the range of 128 to 4096 is often reasonable. But for reproducibility, `k` and `m` must be functions of the problem size, not the thread count. If `k` changes when you run with 16 threads instead of 32, the result changes. The numerical contract must be independent of the execution configuration.

A fixed tree can also be made hierarchical. The first level might use a fixed block size to produce partials. The second level might combine those partials with a fixed fan-in, such as 8 or 16. The third level might combine the results of the second level. This keeps the tree depth small while allowing many partials. The fan-in can be chosen to match vector widths or cache lines, but it must be fixed. If the fan-in is chosen dynamically based on hardware, reproducibility across machines is lost. You can still have multiple deterministic configurations, but each configuration defines a different numerical result. The application must decide which configuration is canonical.

## The scheduling boundary: dynamic compute, canonical combine

The most practical way to get determinism without giving up load balancing is to split the reduction into two phases. Phase one computes a fixed set of partial results. The mapping from input elements to partial slots is fixed. Threads can process those slots in any order, using dynamic scheduling, work stealing, or even different machines. Each slot's partial is computed by a fixed internal algorithm. Phase two combines the partials in a fixed order. The combine phase may be sequential, or it may be a fixed parallel tree. The important property is that the combine order does not depend on which thread computed which partial or when it finished.

This pattern is sometimes called deterministic reduction by index. It requires storage for `P` partials. `P` is typically much smaller than `N`. For a sum of doubles, each partial is 8 bytes. If `P = 4096`, storage is 32 KB, which fits in L1 or shared memory. For compensated sums, each partial might be 16 bytes or more. For superaccumulators, each partial might be hundreds of bytes, so `P` must be smaller. The combine phase reads `P` values and produces one. The cost of the barrier between phases is usually small compared to the cost of processing `N` elements, unless `P` is very large or the reduction is extremely fast.

Choosing `P` is a trade-off. It should be large enough to expose parallelism and balance load, but small enough to keep combine overhead low. On a 64-core machine, `P` might be 4x to 16x the number of threads. But if `P` depends on thread count, reproducibility across thread counts is lost. So `P` must be fixed by the problem size. For example, `P = min(4096, ceil(N / 1024))` or `P = 2^ceil(log2(N / 1024))`. This gives a fixed `P` for a given `N`. If you run on 8 threads or 64 threads, the same `P` is used. The compute phase may be less efficient on 8 threads if `P` is large, but the result is the same. You can also use a fixed `P` that is independent of `N`, such as `P = 4096` always, with each partial handling a variable number of elements. But then the internal sum length varies, which affects accuracy. A fixed `P` with variable chunk sizes is still deterministic if the chunk boundaries are fixed. For example, partition `[0, N)` into `P` contiguous ranges with sizes either `floor(N/P)` or `ceil(N/P)`. The first `N mod P` ranges get one extra element. This is a fixed partition. It is deterministic and reasonably balanced.

## Blocked partials and the arithmetic of chunking

Blocked partials are the simplest fixed decomposition. The array is divided into contiguous chunks. Each chunk is reduced sequentially. The chunk partials are then combined. The chunk boundaries must be fixed. If you use a dynamic chunk size based on cache or load, you lose reproducibility. But you can still have a fixed chunk size that is chosen for performance. For example, chunk size 1024 elements. If `N` is not a multiple of 1024, the last chunk is smaller. That is a fixed rule. The result is deterministic.

The arithmetic of chunking is straightforward but important. Suppose chunk size `k`. Each chunk sum `s_i` is computed in left-to-right order. Then the `s_i` are combined in a fixed tree. The error bound is roughly `(k - 1 + log2 P) * eps * sum |x|`. If `k` is large, the sequential error dominates. If `k` is small, the tree error dominates. For double precision, `k = 128` gives sequential error around `127 eps`, tree error around `log2 P eps`. For `P = 4096`, `log2 P = 12`, total around `139 eps`. For `k = 4096`, sequential error around `4095 eps`, total around `4107 eps`. So smaller chunks improve accuracy. But smaller chunks mean more partials and more combine overhead. There is a sweet spot. For many applications, `k = 128` or `256` is good. But for performance, larger chunks may be better because they reduce loop overhead and improve vectorization. The deterministic choice may sacrifice some accuracy for speed, or vice versa. If accuracy is critical, use compensated summation within chunks.

Handling the remainder is another place where determinism can be lost. If `N` is not divisible by `k`, the last chunk is smaller. That is fine. But if you use a fixed number of chunks `P`, the chunk sizes vary by at most one. The internal sum length varies, which slightly changes error. But it is deterministic. If you want exactly equal chunk sizes, pad with zeros. Adding zero is exact for normal numbers, but can affect signed zero and NaN. Better to handle the remainder explicitly with a fixed rule. For example, the first `N mod P` chunks get `ceil(N/P)` elements, and the rest get `floor(N/P)`. This rule is independent of scheduling and hardware.

## Compensated summation in parallel

Kahan summation is a sequential algorithm. To parallelize it deterministically, you need a combine operation that merges two compensated sums. A compensated sum is a pair `(s, c)` representing the value `s + c`, where `s` is the running sum and `c` is the compensation. The sequential Kahan update for a new value `x` is:

```
y = x - c
t = s + y
c = (t - s) - y
s = t
```

This is not associative as a pair operation. But you can define a combine function for two pairs `(s1, c1)` and `(s2, c2)`. One way is to treat them as four values and run a short compensated sum over them in a fixed order. For example:

```
function combine((s1, c1), (s2, c2)):
  s = s1
  c = c1
  y = s2 - c
  t = s + y
  c = (t - s) - y
  s = t
  y = c2 - c
  t = s + y
  c = (t - s) - y
  s = t
  return (s, c)
```

This is a deterministic function. It is not associative in floating-point, but if you use a fixed tree of combines, the result is deterministic. The error is typically better than plain summation. However, the result is not the same as sequential Kahan summation over the whole array. It is a different algorithm. If you need the exact sequential Kahan result, you cannot parallelize without changing the order. You can only parallelize if you accept a different but deterministic result.

Neumaier summation is similar but more robust. The combine function is slightly different. Again, a fixed tree gives determinism. The cost is that each partial stores two doubles. The combine does about six to ten floating-point operations. The compute phase does about four operations per element. So compensated summation is roughly two to four times slower than plain summation. But it can be much more accurate, especially for ill-conditioned sums where cancellation is severe. For a deterministic parallel reduction, compensated summation is often the best compromise between accuracy and cost.

## Superaccumulators and exact accumulation

A superaccumulator represents the exact sum of a set of floating-point numbers using a fixed-point integer with enough bits to cover the entire exponent range. For IEEE 754 double precision, the exponent range is from `-1074` to `1023`, so the exact sum can require about 2098 bits of integer. That is about 33 64-bit limbs. For single precision, it is about 277 bits, or 5 limbs. Each addition decomposes the float into sign, exponent, and mantissa, shifts the mantissa into the accumulator, and adds it to the appropriate limbs with carry propagation. This is exact for finite values. The order of additions does not matter because integer addition is associative and commutative. Therefore, a parallel superaccumulator reduction is trivially deterministic: each thread or block has its own superaccumulator, and the final combine is an integer addition of the limb arrays. The result is then rounded once to double or float. This gives bitwise reproducibility across thread counts, block sizes, and even hardware, assuming the same rounding mode and handling of special values.

The cost of superaccumulators is significant. Each addition requires shifting and adding multiple limbs. The carry propagation can be done lazily or with a small number of limbs. For double precision, adding a value with a small exponent may touch only a few limbs, but the worst case touches many. The memory per accumulator is 33 words, so if you have 64 threads, that is `64 * 33 * 8 = 16.9 KB`, which is acceptable. But the arithmetic per element is higher than a single FP add. In practice, superaccumulators can be five to twenty times slower than plain summation. They are used when exactness or reproducibility is paramount, such as in reproducible BLAS, interval arithmetic, and some numerical libraries. There are optimizations: binned superaccumulators, which split the exponent range into bins and use smaller accumulators per bin. This reduces the number of limbs touched per addition. The binned approach is the basis of many reproducible summation algorithms.

## Binned reproducible summation

The binned approach groups values by exponent. For each exponent bin, you maintain a fixed-point accumulator that can exactly sum all values in that bin. Because the exponent range of a bin is limited, the accumulator can be small. For example, you might use bins of 64 exponents. A value is assigned to a bin based on its exponent. The sum within each bin is exact if the accumulator has enough bits to cover the maximum number of values times the maximum mantissa. Then the bin sums are combined using exact fixed-point addition. The final result is rounded once. This is order-independent because each value goes to a fixed bin, and integer addition within and across bins is associative. It is also parallelizable: each thread has local bins, and the reduction combines bins by integer addition. The combine order does not matter.

The binned method is more efficient than a full superaccumulator because most additions only touch a small accumulator. However, it still requires extra memory for bins. For double precision, you might need 40 to 80 bins, each with a few 64-bit words. That is a few hundred bytes per thread. The arithmetic per element is a few operations to extract the exponent and add to the right bin. This can be faster than a full superaccumulator but still slower than plain summation. It provides bitwise reproducibility and high accuracy. It is used in libraries like ReproBLAS and in some deterministic deep learning frameworks. The trade-off is clear: if you need reproducibility across thread counts and hardware, and you cannot fix the order, binned summation is a strong candidate.

## The cost of ordering: synchronization, memory, and lost fusion

Enforcing a canonical order has costs that go beyond arithmetic. The first is synchronization. A fixed tree combination requires a barrier after the compute phase. If the combine phase is parallel, it may require multiple barriers, one per tree level. Barriers are expensive on large machines, especially across NUMA nodes or GPUs. The second is memory. Deterministic reductions typically store partials in a global or shared array. This increases memory traffic. For a memory-bound reduction, the extra traffic can reduce performance by 10 to 30 percent or more. The third is lost fusion. In a nondeterministic atomic reduction, the final combination is fused into the same loop that reads the data. In a deterministic reduction, you often need a separate kernel or loop to combine partials. This adds launch overhead and may reduce cache locality. The fourth is reduced flexibility. You cannot change the block size or tree shape based on runtime conditions without changing the result. This can prevent auto-tuning. You may need to choose a fixed configuration that is good on average but not optimal on every machine.

There are ways to mitigate these costs. You can use a hierarchical reduction: first combine within a warp or block using fast shuffles, then store block partials, then combine block partials in a fixed order. This reduces the number of global partials. You can use a two-level tree where the first level is deterministic per block and the second level is a fixed tree across blocks. You can use cooperative groups on GPUs to do a grid-wide barrier and a fixed tree, avoiding a second kernel launch. You can use asynchronous barriers or split-phase barriers to overlap computation and synchronization. But these techniques add complexity. The engineering cost is real.

## Practical patterns in OpenMP, MPI, CUDA, and task runtimes

In OpenMP, the `reduction` clause is convenient but its combination order is implementation-defined. It may be deterministic for a given compiler and schedule, but it is not guaranteed across versions or thread counts. To get a deterministic reduction, use a manual pattern. Allocate an array of partials with one slot per thread or per fixed block. Use `#pragma omp parallel for schedule(static)` with a fixed chunk size to compute partials. Each thread writes to a private slot. After the parallel region, combine the partials in a fixed order. If you want parallel combination, use a second parallel region with a fixed tree. Avoid `atomic` and `critical` for the final sum. For nested loops, ensure the inner reduction is also deterministic.

In MPI, `MPI_Reduce` does not guarantee a deterministic combination order. The standard allows the implementation to choose any order. To be reproducible, use `MPI_Gather` or `MPI_Allgather` to collect partials from all ranks, then combine them in a fixed order on each rank. This is more expensive in communication but gives reproducibility. Alternatively, use a user-defined operation that is truly associative and commutative, such as a superaccumulator combine. If the operation is exact integer addition, MPI can combine in any order and still be deterministic. For floating-point, you can implement a user-defined reduction that uses a fixed tree by manually doing `MPI_Send` and `MPI_Recv` in a fixed pattern, but that is rarely worth it. The gather-and-combine pattern is simpler and often fast enough because the number of ranks is usually much smaller than the number of elements.

In CUDA, block-level reductions are typically deterministic if you use a fixed tree in shared memory. The warp shuffle order is fixed. The block tree order is fixed. The nondeterminism usually comes from grid-level combination. Using `atomicAdd` for the final sum is fast but nondeterministic. To be deterministic, use a two-pass approach: kernel one writes block partials to a global array, kernel two reduces the partials in a fixed order. Kernel two can be a single block or a fixed tree. Alternatively, use cooperative groups grid sync and a fixed tree across blocks. This requires the grid to be co-resident, which limits grid size. For large grids, the two-pass approach is more practical. The cost is an extra kernel launch and global memory traffic for partials. For a memory-bound reduction, the extra traffic is small if the number of blocks is small. For a compute-bound reduction, the extra launch overhead may be noticeable.

In task runtimes like TBB, Rayon, or Cilk, `parallel_reduce` often combines partials in a tree that depends on task splitting. This can be nondeterministic because task splitting depends on scheduling. To get determinism, use `parallel_for` to compute partials into a fixed array, then combine sequentially or with a fixed tree. Some runtimes offer deterministic reduction options, but you must verify the guarantee. The general pattern is the same: separate the computation of partials from the combination. The computation can be as dynamic as you like. The combination must be canonical.

These patterns show that determinism is not a single switch. It is a set of choices about where to fix order and where to allow flexibility. The next part of the design space is how to encode these choices in an API, so that callers can request a reproducibility level without knowing the details of the tree, the block size, or the accumulator.

## Precision, contraction, and the arithmetic environment

A deterministic reduction plan is only as strong as the arithmetic environment it assumes. Thread-count invariance on one binary is mostly a scheduling property, but bitwise reproducibility across compilers and machines additionally requires that every floating-point operation in the leaf sums and the combine tree be the same operation with the same rounding. That is harder than it sounds. Compilers may contract a multiply and an add into a fused multiply-add, change the evaluation order of a vectorized loop, keep intermediate values in wider registers, or enable flush-to-zero behavior for subnormals. A plan that promises bitwise results must either forbid those transformations or make them part of the plan and validate them on each target.

For reductions that only sum values, the most important compiler boundary is contraction and reassociation. A leaf that computes a running sum with one accumulator is easy to reason about, but the compiler may still vectorize it by maintaining multiple accumulators and folding them at the end. That changes the parenthesization inside the leaf. If the plan says the leaf is a left-to-right scalar sum, the implementation must prevent that transformation or redefine the leaf as the vectorized form. The same issue appears in dot products, where contraction changes whether each product is rounded before it enters the sum. A fused multiply-add is not a faster version of the same arithmetic. It is a different rounding sequence. Both can be deterministic, but a contract that mixes them across machines is not.

Mixed precision adds another layer. Summing single-precision values into a double-precision accumulator is often more accurate and can be made deterministic, because each float converts exactly to double and the double additions follow a fixed tree. Summing single-precision values into a single-precision accumulator, then combining with doubles, is a different plan. Neither is inherently more reproducible, but the conversion points and accumulator widths must be fixed. The same applies to half precision and bfloat16 in machine learning. If the reduction uses hardware-specific dot-product instructions with internal widening or block-floating-point behavior, the numerical result may depend on the instruction chosen. A reproducible plan for those types must specify the exact accumulation semantics or use a software path with a fixed order.

Hardware adds special-value and exception behavior that is easy to overlook. Denormals may be flushed to zero on some targets. NaN propagation may select different payloads depending on operand order. Signaling NaNs may raise exceptions or be quieted at different points. Signed zero can change the sign of an exact zero result. A bitwise plan needs policies for all of these, and the policies must be enforced by the implementation rather than left to the target. If the plan does not promise cross-machine reproducibility, it can inherit the target behavior, but it should still document the boundary. Otherwise a user who moves from one GPU generation to another will see a numerical change that looks like a bug.

## Debugging nondeterminism in a reduction

When a reduction produces differences between runs, the first task is to determine which layer is varying. The useful technique is to make the plan observable. Hash the partial buffer after the compute phase, hash it again after the combine phase, and log the plan identifier, leaf count, leaf boundaries, and combine fan-in. If the partial hash changes between runs, the compute phase is not writing the same partials. That points to a race, an uninitialized slot, a chunk assignment that depends on scheduling, or a leaf boundary that depends on thread count. If the partial hash is stable but the final hash changes, the combine phase is reading slots in a different order or using an atomic operation. If both hashes are stable but the result differs from a reference, the plan itself is different, not the scheduling.

A second technique is to remove parallelism from the combination while leaving it in the computation. Force the combine phase to run sequentially in canonical index order. If the nondeterminism disappears, the problem is in the combine tree or the reduction of partials. If it remains, the problem is in how the partials are produced. A similar bisection works for parallelism in the compute phase: run the same fixed leaf assignment with one worker, then with many workers, and compare partial buffers. A deterministic plan should produce identical partials regardless of which worker computed each leaf. If that fails, the leaf code itself is reading state that depends on the worker, such as a thread-local scratch buffer that is not initialized consistently.

Compiler and runtime flags deserve a place in the debug checklist. Fast-math flags, architecture-specific vectorization, OpenMP scheduling clauses, GPU compiler options, and math library settings can all change the arithmetic without changing the source. A reduction that is deterministic in a debug build and nondeterministic in a release build is often a victim of reassociation or contraction, not a race. A reduction that is deterministic with static scheduling and nondeterministic with dynamic scheduling is usually a completion-order combine. A reduction that changes only when the thread count changes is usually using the thread count to choose a partial count or chunk size. These signatures are more informative than a tolerance-based comparison, which can hide a real order change until the data becomes ill-conditioned.

## Hybrid plans and adaptive accumulator selection

A single reduction plan does not have to use the same accumulator everywhere. A practical deterministic reduction can use plain leaves and a compensated combine, or compensated leaves and an exact combine, or binned accumulators only at the top of the tree. The important rule is that the choice must be a deterministic function of the problem and the declared plan, not of runtime load or the number of workers. A leaf can decide to switch from plain to compensated accumulation based on the magnitude of the values it has seen so far, provided the decision rule is fixed and the switch is applied in a fixed order. That can improve accuracy without changing reproducibility. The switch is part of the algorithm, and the algorithm is part of the plan.

Exact accumulation at the combine phase is often a good compromise. Leaves can use fast floating-point sums, and the combine phase can add the leaf values with a superaccumulator or an expansion. This limits the number of exact additions to the number of leaves, which is small, while still making the final result independent of leaf completion order. If the leaves are large enough that their own rounding error matters, the plan must either use compensated leaves or accept that the result is deterministic but not exact. The former is usually the right choice for ill-conditioned data. The latter is acceptable when the leaf error is below the application's tolerance and the goal is only reproducibility.

Adaptive plans that change the algorithm based on input size are common and can be deterministic, but they create plan boundaries. A sum of ten thousand elements might use one leaf size, while a sum of ten million elements uses another. If the result must be reproducible across sizes, the plan boundary must be documented and tested. A caller that concatenates results from different sizes is effectively combining two different numerical algorithms. That is not necessarily wrong, but it is a decision the caller should see. Hiding the boundary behind an autotuner makes the result depend on a performance heuristic, which is exactly the kind of dependence a deterministic reduction is supposed to remove.

Autotuning can still be useful if it tunes only execution choices. The plan can fix the logical leaf count, the combine tree, and the accumulator semantics, while the runtime tunes thread placement, vector width within a leaf, and memory layout. Those choices affect speed but not arithmetic. If the runtime must change the arithmetic to hit a performance target, it should switch to a different named plan, not silently change the current one. That keeps the numerical contract inspectable and makes benchmarks comparable.

## Plans across ranks, devices, and accelerators

Distributed reductions make the plan boundary more visible because they cross process and device boundaries. A fixed tree over ranks is reproducible if the rank order and the per-rank partial layout are fixed. A tree that depends on the number of ranks is reproducible only for a fixed rank count. If the application must produce the same result on sixteen ranks and sixty-four ranks, the reduction must gather partials to a canonical order or use an order-independent accumulator. A rank-count-invariant plan cannot use a different number of leaves just because the job was launched with more ranks. It can use more ranks to compute the same fixed leaves, but the leaves themselves must be a function of the problem.

Accelerators complicate the plan because the host and device may use different arithmetic modes. A GPU may use a different denormal policy, a different fused-operation set, or a different rounding behavior for half-precision operations. A plan that promises bitwise reproducibility across host and device must either use operations with identical semantics on both or perform the combine on one side with a fixed accumulator. The common pattern is to compute device partials, copy them to the host in a fixed layout, and combine them in a canonical tree. That sacrifices some device-side performance for a simpler contract. The alternative is to keep the combine on the device and certify the device arithmetic as part of the plan. Both are legitimate; the mistake is to assume that moving the combine changes only speed.

The same reasoning applies to heterogeneous clusters. A plan can be reproducible within a class of machines and not across classes, or it can use exact accumulation to bridge classes. The cost of bridging is usually paid in the combine phase, where the number of values is small. That is often the best place to spend the extra arithmetic. It keeps the fast path fast and confines the reproducibility machinery to the part of the reduction that is already synchronization-heavy. The result is a plan that is deterministic by construction, not by hoping that the scheduler repeats itself.

## Reproducibility as an interface contract

A deterministic reduction is not a boolean property that a kernel either has or lacks. It is a contract with levels. One level might promise only that repeated runs on the same binary and same thread count produce the same bits. A stronger level might promise that the result is independent of thread count on the same machine. A stronger level still might promise independence from block size, rank count, and device generation. Each level requires more fixed choices and more validation. The API should let callers ask for the level they need and should make the level visible in logs and test reports.

A useful representation is a plan object. The plan identifies the leaf partition, the leaf accumulator, the combine tree, the special-value policy, the rounding mode, and the contraction policy. The plan should have a stable identifier, such as a hash of its parameters. When a library changes a default leaf size or a combine fan-in, the identifier changes. Callers that need bitwise stability across library upgrades can pin the old plan. Callers that only need current performance can use the default. Without a plan identifier, a numerical change looks like a regression or a hardware fault. With one, it is a visible change in the numerical contract.

The contract should also state what is not promised. A plan that is thread-count invariant on one machine may not be invariant across machines if the leaf code uses fused multiply-add on one target and separate multiply and add on another. A plan that is invariant across machines may not be invariant across compiler versions if the compiler reassociates a leaf loop. The contract does not need to be maximal. It needs to be honest. A plan that promises too much will fail in a way that is hard to debug. A plan that promises too little will be ignored by users who need reproducibility.

Plan selection should be explicit at the boundaries where it matters. A test suite can request a pinned plan. A production job can request a level and accept the library's current plan for that level. A library can expose a function to enumerate available plans and their guarantees. This avoids the common failure where a user assumes that setting a thread count to one will reproduce a parallel result, or that setting it back to many threads will reproduce a single-thread result. Those are different plans unless the implementation deliberately makes them the same.

Autotuning is compatible with this contract only if it tunes execution choices rather than arithmetic. Thread placement, vector width inside a leaf, memory layout, and prefetch distance can vary without changing the parenthesization. Leaf count, leaf boundaries, accumulator type, and combine tree cannot vary without changing the plan. If a runtime must change one of those to hit a performance target, it should switch to a different named plan. That keeps the numerical result inspectable and makes benchmark comparisons meaningful.

## Testing deterministic reductions

Testing a deterministic reduction is different from testing a numerical kernel for accuracy. Accuracy tests compare against a reference within a tolerance. Determinism tests compare against a reference exactly, or compare multiple executions against each other exactly. Both are necessary. A deterministic plan can be consistently wrong. A nondeterministic plan can be accurate on average. The test suite should separate the two concerns.

The first tool is a hash of the partial buffer. After the compute phase and before the combine phase, the implementation can write the partials to a buffer in canonical order and hash it. If the hash changes between runs with the same inputs and plan, the compute phase is not deterministic. The cause might be a race, an uninitialized slot, a chunk assignment that depends on scheduling, or a leaf that reads thread-local state. If the partial hash is stable but the final hash changes, the combine phase is reading partials in a different order or using an atomic operation. If both hashes are stable but the result differs from a reference, the plan itself is different from the reference plan. This three-way split is more useful than a single final hash because it localizes the fault.

The second tool is a test matrix. A plan that claims thread-count invariance should be run with 1, 2, 3, 4, 7, 8, 16, and 31 threads, or whatever counts are available. A plan that claims schedule invariance should be run with static, dynamic, guided, and task-based schedules. A plan that claims machine invariance should be run on every target in the support matrix, including different CPU generations, different GPU models, and different compilers. The matrix does not need to be exhaustive on every commit, but it should be part of release qualification. A plan that is only tested with one thread count is not a reproducible plan. It is a sequential plan with extra steps.

The third tool is adversarial data. The usual random uniform values are too easy. They rarely produce cancellation, they rarely exercise denormals, and they rarely stress the exponent range. A good test set includes values that cancel exactly, values that cancel almost exactly, values with exponents at the extremes of the format, values that are all denormal, values that include infinities and NaNs, and values that include positive and negative zero. The test should check not only the final sum but also the sign of zero, the payload of NaN if the plan specifies it, and the behavior of signaling NaNs if exceptions are enabled. These cases are where a plan that ignores special values will produce different results on different targets.

The fourth tool is an exact reference. For a test of moderate size, the expected sum can be computed with a superaccumulator or an arbitrary-precision library. The reference does not need to be fast. It only needs to be exact for the input format. Comparing a deterministic plan against an exact reference gives both an accuracy check and a reproducibility check. If the plan is deterministic but far from exact, the test can report the error bound and the condition number. If the plan is close to exact but not deterministic, the test can report the scheduling dependence. The two properties are independent, and the test should say so.

Differential testing is useful when a new plan is introduced. Run the old plan and the new plan on the same inputs and compare. If the plans are supposed to produce the same result for a given reproducibility level, the comparison is exact. If they are allowed to differ, the comparison is within a documented tolerance. This catches accidental changes in leaf boundaries, combine order, or accumulator type. It also catches compiler changes that alter the arithmetic inside a leaf. A plan identifier in the test output makes the comparison interpretable. Without it, a difference between two runs is just a number.

## Performance modeling and measurement

The cost of a deterministic reduction can be modeled as four components: element processing, partial storage, combination, and synchronization. Element processing is the cost of reading the input and updating a leaf accumulator. Partial storage is the cost of writing partials to memory and reading them back. Combination is the cost of the combine tree. Synchronization is the cost of barriers, kernel launches, and inter-rank communication. The deterministic overhead is the sum of the last three components, minus whatever overlap the implementation can achieve.

Let N be the number of elements, P the number of partials, and T the number of workers. The extra memory traffic from partials is roughly 2P values, one write and one read, compared with N reads. The fraction is 2P/N. If P is much smaller than N, the extra traffic is negligible. If P is a large fraction of N, the reduction becomes partial-bound. This is why a fixed leaf size is a performance decision as well as a numerical one. A leaf size of 128 gives P = N/128, so the extra traffic is about 1.6 percent. A leaf size of 8 gives P = N/8, so the extra traffic is 25 percent. The numerical benefit of small leaves must be weighed against the memory cost.

Combination cost is P times the cost of one combine plus the tree overhead. If the combine is a simple floating-point add, the cost is small. If the combine is a compensated sum, the cost is several operations. If the combine is a superaccumulator addition, the cost is larger but P is usually small. The tree overhead is log P barriers if the combine is parallel, or one barrier if the combine is sequential. On a large machine, a barrier can cost thousands of cycles. A sequential combine avoids multiple barriers but serializes P operations. For P in the thousands, a sequential combine is often faster than a parallel tree because the barrier cost dominates. For P in the millions, a parallel tree is necessary.

Measurement must control for the same factors that affect any parallel benchmark. Thread affinity should be pinned. The machine should be otherwise idle. The input should be large enough to amortize launch and synchronization overhead. The timing should include multiple warmup runs and report the distribution, not just the minimum. On GPUs, clock throttling and power management can change the compute time by tens of percent. On NUMA systems, memory placement can change the bandwidth by a factor of two. A deterministic reduction that is measured without these controls will produce misleading overhead numbers.

The most useful comparison is between two plans that differ only in the property being measured. Compare a deterministic plan against a nondeterministic plan with the same leaf accumulator and the same combine arithmetic, but with atomic combination. The difference is the cost of ordering. Compare a compensated plan against a plain plan with the same tree. The difference is the cost of accuracy. Compare a binned plan against a compensated plan. The difference is the cost of exactness. Reporting a single speedup number hides these trade-offs. Reporting the components makes the engineering choice visible.

## Implementation patterns for plan enforcement

A library that offers multiple reproducibility levels needs a way to enforce the plan at every level of the call stack. The simplest pattern is a plan registry. The registry stores plan descriptors by identifier. A reduction call takes a plan identifier or a reproducibility level. The library looks up the plan, validates that the input type and operation are compatible, and dispatches to a kernel specialized for that plan. The kernel does not consult the thread count or the hardware to choose leaf boundaries. It reads them from the plan.

Compile-time dispatch is useful when the plan is fixed for an application. A template parameter can select the leaf accumulator, the leaf size, and the combine tree. The compiler can inline the combine and unroll the leaf loop. The plan identifier can be a compile-time constant. This gives the best performance and the strongest guarantee, because the arithmetic is fixed at build time. The cost is that changing the plan requires recompiling. For libraries that ship precompiled kernels, runtime dispatch is necessary.

Runtime dispatch can still be deterministic if the plan is selected before execution and does not change during the reduction. The kernel can use a switch on the plan identifier to call a specialized function. The important rule is that the plan must not be selected based on the number of threads or the available parallelism. If the application requests thread-count invariance, the plan must be the same for one thread and many threads. The runtime can choose how to schedule the leaves, but not how many leaves there are.

Partial storage should be laid out in a canonical order. If the partials are stored in a global array indexed by leaf number, the combine phase can read them in index order. If the partials are stored per thread or per block, the combine phase must first gather them into canonical order. The gather can be parallel, but the mapping from worker to leaf must be fixed. A common mistake is to store partials in the order they are produced. That order depends on scheduling. The fix is to write each partial to its leaf slot, even if the slots are computed out of order. The write is a scatter, but the slot is fixed.

Serialization and checkpointing need the same discipline. If a long-running job writes a partial reduction to disk and resumes later, the partial layout and plan identifier must be saved. A resumed job that uses a different plan will produce a different result. The checkpoint should include the plan identifier, the leaf boundaries, the accumulator state, and the special-value policy. This is especially important for distributed jobs where different ranks may be restarted at different times. A rank that resumes with a different plan can corrupt the final combine.

## Numerical validation and error bounds

A deterministic plan should come with an error bound. The bound does not need to be tight, but it should be stated in terms of the input size, the leaf size, the combine tree depth, and the unit roundoff. For a plain sum with leaf size k and P leaves, the bound is roughly (k - 1 + log2 P) * u * sum |x_i|, where u is the unit roundoff. For a compensated sum, the bound is much smaller, often independent of k and P to first order. For an exact accumulator, the only error is the final rounding. These bounds help users choose a plan. They also help testers decide when a difference is a bug and when it is expected.

Validation should include a condition-number estimate. The condition number of a sum is the sum of absolute values divided by the absolute value of the sum. If the condition number is large, cancellation is severe, and the error bound is large. A deterministic plan can still be reproducible in this case, but it may not be accurate. A test that only checks reproducibility will pass. A test that checks accuracy will fail. The test report should include both. If the application needs accuracy and reproducibility, it should use a compensated or exact plan. If it needs only reproducibility, a plain plan may be sufficient.

Higher-precision references are useful for validation but not for production. A reference sum computed in double-double or arbitrary precision can be compared against the plan's result. The difference is the forward error. The forward error can be compared against the theoretical bound. If the forward error exceeds the bound, the plan may have a bug, or the bound may be too optimistic for the data. This kind of validation is expensive, so it is usually done on a sample of inputs rather than every input. The sample should include the adversarial cases from the test suite.

Plan changes should be validated like any other numerical change. When a new plan is introduced, run it against the old plan on a representative input set. If the new plan is supposed to be equivalent, compare exactly. If it is supposed to be more accurate, compare against an exact reference and report the improvement. If it is supposed to be faster, report the performance and the accuracy. A plan change that is not validated is a silent change in the numerical contract. The plan identifier makes the change visible, but it does not make it correct. Validation is still required.

## Integration checklist for deterministic reductions

Before a deterministic reduction is used in a production or test setting, the following questions should have answers. What reproducibility level is required? What plan identifier implements that level? What are the leaf boundaries and combine tree? What accumulator is used in the leaf and in the combine? What is the special-value policy for NaN, infinity, and signed zero? What compiler flags are required to preserve the arithmetic? What is the test matrix for thread counts, schedules, and hardware? What is the reference for accuracy? What is the measured overhead compared with the nondeterministic alternative? How is the plan versioned, and what happens when the library default changes? These questions are not a final conclusion. They are the minimum set of decisions that turn a parallel reduction from a scheduling accident into a reproducible numerical operation.
