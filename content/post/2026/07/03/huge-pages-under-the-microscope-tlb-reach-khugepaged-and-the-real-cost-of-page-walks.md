## The tax that never shows up in the profile

A flame graph of a memory-bound service usually shows a handful of fat frames: a hash probe, a B-tree descent, a pointer chase through a graph, a matrix kernel. What it rarely shows is address translation, because address translation is not a function you call. It is a tax levied on every single memory access, and it is levied by hardware, below the level at which profilers normally operate.

The mechanism is simple enough. The CPU issues a virtual address; the memory management unit (MMU) must produce a physical address before the load can proceed. To avoid doing that translation from scratch on every access, the MMU caches recent translations in the translation lookaside buffer (TLB). Like every cache, the TLB has a fixed number of entries. When a translation misses, the hardware must *walk* the page table — a dependent chain of memory loads that terminates in the physical address.

Here is the part that matters for systems design: **you cannot buy more TLB entries.** They are silicon, fixed at fabrication, and the ratio of TLB entries to the rest of the core has been roughly flat for years. The only lever you have is the *size of the thing each entry covers*. One TLB entry mapping a 4 KiB page covers 4 KiB of address space. The same entry mapping a 2 MiB page covers 2 MiB. Nothing else about the workload changes; the translation coverage changes by a factor of 512.

That is the entire appeal of huge pages. It is also, unfortunately, where most discussions stop — as if the lever were free. It is not. Huge pages are a trade of memory granularity and allocation latency for translation coverage, and the bill arrives in resident set size, in tail latency, and in the behavior of a kernel thread most engineers have never looked at.

This article is about that trade. We will start from the mechanics of a page walk, derive the arithmetic of TLB reach, and then work through where huge pages are actually produced on Linux and what each production mechanism costs.

## What a page walk actually does

On x86-64 with four-level paging, a virtual address is split into five fields: four 9-bit indices and a 12-bit offset. Translation starts at a physical address held in the `CR3` register, which points to the top-level table (PML4). The MMU reads the PML4 entry indexed by the top 9 bits, extracts the physical base of the next-level table, reads the PDPT entry indexed by the next 9 bits, and so on down through the page directory (PD) to the page table (PT), whose entry supplies the physical page frame. The 12-bit offset then selects the byte within that 4 KiB frame.

Five-level paging (Intel's LA57, and the equivalent on recent AMD parts) adds a PML5 level and extends the virtual address to 57 bits. It changes the arithmetic at the top of the tree but not the structure of the walk.

The critical property is that this is a **pointer chase**. Each level's load supplies the address for the next level's load. The MMU cannot issue all four loads in parallel because it does not know where the later tables live until the earlier ones resolve. On a machine with a warm cache hierarchy, this chain is short — a few cycles per level. On a machine where the page-table entries have been evicted from L1 and L2, each level can become an L3 or DRAM access, and a single TLB miss can cost hundreds of cycles. Modern cores mitigate this by running multiple page walkers concurrently and by caching intermediate results in *paging-structure caches* (often called page-walk caches), which memoize the upper levels so that a walk for an address near a recently translated one only needs the final level. But the mitigation is a cache, and caches miss.

There is a second-order cost that is easy to overlook: **page tables are memory too.** A 4 KiB page table holds 512 entries of 8 bytes each, and each entry maps one 4 KiB page — so a single page table covers 2 MiB of address space. A process with a 1 GiB resident anonymous working set therefore needs 512 page tables, or 2 MiB of page-table memory, and those structures are touched on the walk path. If the workload's access pattern is random across that 1 GiB, the page-table entries themselves become a cache-resident working set competing with application data.

Switch the same 1 GiB to 2 MiB pages and the picture changes: 512 page-directory entries cover the whole region, and they fit in a single 4 KiB page table. Translation metadata shrinks by a factor of 512. That reduction is often as valuable as the TLB reach itself, because it removes a stream of cache misses that were never attributed to anything.

## TLB reach arithmetic

Define TLB reach as the amount of address space that can be translated without a miss:

```
reach = (number of TLB entries) × (page size)
```

Because the entry count is fixed by the microarchitecture, reach scales linearly with page size. The absolute numbers vary considerably across vendors, generations, and whether you are looking at the L1 data TLB or the unified second-level TLB, so the figures below should be read as illustrative shapes rather than specifications. Measure your own hardware.

| Page size | Illustrative entry count | Illustrative reach |
|---|---|---|
| 4 KiB | ~1,500 in the second-level TLB | single-digit MiB |
| 2 MiB | tens to low hundreds | hundreds of MiB |
| 1 GiB | a handful | tens of GiB |

The structural observation is what matters. With 4 KiB pages, a working set of even a few tens of megabytes already exceeds what the TLB can hold, so a random-access pattern across that set will miss on a substantial fraction of accesses. With 2 MiB pages, the same entry budget covers two to three orders of magnitude more address space, and the miss rate collapses.

This is why the workloads that benefit most from huge pages are precisely the ones with poor *spatial* locality but large *footprint*: hash tables probed at random, B-tree and B+-tree descents, graph traversals, in-memory column stores scanning wide ranges, garbage-collected heaps, and the weight matrices of a neural network read in a streaming-but-large pattern. In each case the application touches a large region in an order that defeats the hardware prefetcher, and the TLB becomes the bottleneck rather than DRAM bandwidth.

Conversely, a purely sequential streaming workload — memcpy, a linear scan, a well-tiled stencil — already has excellent TLB behavior. Each 4 KiB page is touched once before being retired, the prefetcher hides the misses, and the translation overhead is amortized to near zero. Huge pages may still help slightly by shrinking the page-table footprint, but the headline benefit is not there. If a workload touches a small fraction of each large page, huge pages can be an outright loss: you pay for the whole page in resident memory while using a sliver of it.

## Where huge pages come from on Linux

Linux does not have one huge-page mechanism; it has several, with different guarantees, different failure modes, and different operational costs. Confusing them is the source of most bad advice on the subject.

**HugeTLB / hugetlbfs** is the explicit mechanism. You reserve a pool of huge pages at boot or at runtime by writing to `/sys/kernel/mm/hugepages/hugepages-2048kB/nr_hugepages` (or the corresponding directory for other supported sizes), and processes obtain them either with `mmap(..., MAP_HUGETLB, ...)` or by mapping a file on a mounted `hugetlbfs`. The advantages are strong: the pages are reserved up front, so allocation cannot fail due to fragmentation, and the pool size is a hard, observable bound. The cost is that the pool is a fixed resource — memory sitting in it is unavailable to the rest of the system, and huge pages obtained this way are not reclaimable under memory pressure the way ordinary anonymous pages are. This is the mechanism used by DPDK, by many database deployments, and by hypervisors that want predictable guest memory.

**Transparent Huge Pages (THP)** is the kernel-managed mechanism. Its mode is controlled by `/sys/kernel/mm/transparent_hugepage/enabled`, with the familiar `always`, `madvise`, and `never` settings. In `always` mode the kernel attempts to back anonymous mappings with huge pages opportunistically; in `madvise` mode it does so only for regions explicitly marked with `MADV_HUGEPAGE`. There is a second, separate control — `/sys/kernel/mm/transparent_hugepage/defrag` — that governs how hard the allocator will try to find physically contiguous memory, ranging from `always` (synchronous compaction on the fault path) through `defer` and `defer+madvise` to `never`. That second knob is the one that causes latency incidents, and it is the one people forget.

THP works through two paths. The first is at fault time: when an anonymous page is faulted in, the kernel may allocate a huge page directly if it can find contiguous memory and the faulting pattern suggests the region will be used densely. The second is **khugepaged**, a background kernel thread that periodically scans anonymous mappings, looks for runs of 512 contiguous resident 4 KiB pages, allocates a 2 MiB page, copies the contents across, remaps the region, and frees the small pages. khugepaged is what makes THP work for long-lived heaps that grew one fault at a time, and it is also a source of background CPU consumption and of remap-induced TLB shootdowns across every CPU that has the address space loaded.

**Multi-size THP**, added in recent 6.x kernels, generalizes the idea beyond the single 2 MiB size. Per-size controls under `/sys/kernel/mm/transparent_hugepage/` let an operator enable, say, 64 KiB anonymous THP without enabling 2 MiB, and threshold parameters govern how many non-present or swapped entries a candidate region may contain before collapse is attempted. This matters because the 2 MiB granularity is often too coarse: a workload that wants better TLB coverage but cannot tolerate 2 MiB of internal fragmentation per allocation now has intermediate options.

**`MADV_COLLAPSE`**, introduced in the same era, gives applications a synchronous, on-demand collapse primitive. Instead of waiting for khugepaged to notice a region, a process can ask the kernel to collapse a range right now and observe the result. For latency-sensitive services this is the difference between paying the collapse cost at a controlled point during startup and paying it unpredictably at minute forty of a production run.

Finally, huge pages are not purely an anonymous-memory feature. Shared memory backed by tmpfs can be mapped with large pages, and read-only file-backed THP exists for executable and data mappings that meet the alignment and contiguity requirements. These paths have their own eligibility rules, and a mapping that looks like an obvious candidate may silently remain 4 KiB because a single misaligned extent disqualifies it.

That is the mechanism inventory. What none of it tells you is what the mechanisms cost when they run — the zeroing on the fault path, the compaction stalls, the resident-set inflation, the interaction with NUMA placement and memory cgroups, and how to tell from the outside whether any of it is happening.

## The fault-path bill: zeroing, allocation, and the first touch

Most huge-page discussions describe steady-state TLB behavior and skip the moment the page is created. That moment is where much of the cost lives. A 4 KiB anonymous fault allocates one page frame, clears 4096 bytes, installs a PTE, and returns. A 2 MiB THP fault allocates an order-9 buddy block, clears 2 MiB, installs a PMD, and returns. The zeroing is not optional: handing a process stale kernel or another process's data is a security bug. The hardware may use non-temporal stores or `rep stosb`, but 2 MiB of writes still consumes memory bandwidth and cache capacity. On an otherwise idle machine the cost may be a hundred microseconds; on a busy one it competes with the application's own traffic and with every other core faulting pages. If the process touches one byte of the page and never returns, the kernel has done 512 times the work and committed 512 times the memory.

The allocation side is less deterministic. An order-9 block must be physically contiguous. The buddy allocator can satisfy the request only if a free block of that order exists on the relevant zone and node. Early in boot, when memory is mostly free, that is easy. After hours of mixed allocation, it depends on fragmentation. The kernel may invoke compaction, which migrates movable pages to create a contiguous run. That migration is not a passive background activity on the fault path; it scans pageblocks, isolates pages, copies contents, updates mappings, and issues TLB shootdowns. A single fault can therefore block for milliseconds while the kernel rearranges physical memory. The `/sys/kernel/mm/transparent_hugepage/defrag` setting decides how aggressively this happens. `always` permits direct compaction in the fault path. `defer` and `defer+madvise` push the work to `kcompactd` but reduce allocation success. `never` avoids compaction entirely and turns most THP faults into 4 KiB fallbacks. None of these settings changes the application's virtual access pattern; they change who pays and when.

This is why a service can show excellent median latency and terrible p99 after enabling THP in `always` mode. The median request finds a warm TLB and a preallocated heap. The unlucky request faults a new region, triggers compaction, and waits behind a migration scan. The effect is workload-dependent and often invisible in CPU profiles because the time is spent in kernel code that the application's profiler may not symbolize or may collapse into a generic system frame.

## Compaction, reclaim, and the latency cliff

Compaction is the mechanism that makes huge pages possible in a long-running system, and it is also the mechanism that makes their latency unpredictable. It works by separating movable pages from unmovable ones, then migrating movable pages out of a pageblock so that the block can be promoted to a higher order. Migration requires copying data and remapping every reference to the old page. For anonymous memory that means walking page tables and updating PTEs; for page-cache pages it means updating the radix tree or xarray. The copies consume memory bandwidth. The remaps consume CPU time and generate TLB shootdown IPIs to every core that has the address space active.

Under memory pressure, compaction competes with direct reclaim. A THP fault may first try to allocate, fail, enter compaction, fail again, and then reclaim or fall back. Each stage has its own latency profile. Direct reclaim can write dirty pages and wait on I/O; that is a far larger stall than the page walk the huge page was supposed to avoid. The kernel tries to avoid this by treating high-order allocations specially, but the special handling is heuristic. A workload that allocates many short-lived large objects can drive the system into a state where compaction runs constantly and succeeds rarely. The CPU cost of the attempts is real even when the allocation fails.

The practical consequence is that huge pages should be treated as a capacity-planning decision, not a toggle. If the workload's memory is long-lived and densely used, the one-time cost of creating huge pages is amortized over millions of accesses. If the workload allocates and frees large regions frequently, or if its resident set is close to the machine's memory limit, the allocator may spend more time trying to create huge pages than the TLB misses would have cost. The right experiment is not whether THP improves a microbenchmark; it is whether the production service's tail latency and memory headroom remain stable across a full allocation cycle.

## Resident-set inflation and the fragmentation you cannot see

A huge page changes the unit of memory accounting as well as the unit of translation. When a 2 MiB page is installed, the process's resident set and the memory cgroup's charge can jump by the full 2 MiB, even if only a small part of the page has been touched. The kernel may later split the page under pressure, but splitting is not free and is not guaranteed to happen before the cgroup hits its limit. For a service with a hard `memory.max`, this turns a sparse heap into a liability: the allocator sees a large contiguous charge, the cgroup approaches its limit, and the kernel must reclaim or invoke the OOM killer earlier than the application's actual byte usage would suggest.

Internal fragmentation is the other half of the same problem. A 4 KiB page wastes at most 4 KiB per mapping. A 2 MiB page wastes up to 2 MiB. If the application's data structures are small and interleaved with unmapped guard pages, file-backed mappings, or regions that are deliberately `MADV_DONTNEED`, a huge page may cover address space that is not densely used. The kernel's THP heuristics try to avoid this by requiring a certain number of present pages before collapse, and multi-size THP adds smaller sizes precisely to soften the granularity. But heuristics are not a contract. A mapping that is eligible in one kernel version may be ineligible in the next because the threshold or the scan logic changed.

There is also a subtler form of inflation: page-table memory. Huge pages reduce the number of page-table pages, which is a win, but the reduction is not free if the kernel must keep both the old small-page tables and the new huge-page mapping during a collapse. The transient state can double the metadata for the region being collapsed. On a machine already tight on memory, that transient cost can be the difference between a successful collapse and a fallback.

## khugepaged in production

khugepaged is easy to ignore because it has no application-facing API. It wakes on a timer, scans a portion of each eligible address space, and attempts to collapse runs of 4 KiB pages into 2 MiB pages. Its tunables live under `/sys/kernel/mm/transparent_hugepage/khugepaged/`: `scan_sleep_millisecs`, `alloc_sleep_millisecs`, `pages_to_scan`, `max_ptes_none`, and related thresholds. The defaults are conservative enough to avoid saturating a machine, but conservative also means that a long-lived heap may take minutes to become huge-page-backed. For a service that starts, warms up, and runs for days, that delay is usually acceptable. For a batch job that lives for thirty seconds, khugepaged may never do useful work, and the scanning it does perform is pure overhead.

The collapse operation itself is not a simple flag flip. The kernel must allocate a huge page, copy the contents of the small pages, replace the PTE entries with a single PMD entry, and free the small pages. During the copy, the region is effectively frozen for the collapsing thread. Other threads in the process may continue to access the old mappings until the remap, but the remap requires TLB shootdowns. On a large machine, those IPIs can pause every core running the process for tens of microseconds. If the process has hard latency targets, a khugepaged collapse in the middle of a request is indistinguishable from a brief stop-the-world event. `MADV_COLLAPSE` exists to let the application choose when that event happens, but it does not make the event free; it makes it schedulable.

The scan rate also matters on hosts with many processes. khugepaged is a single thread, and it must divide its attention across all eligible address spaces. A host running hundreds of containers may see each container's heap collapse slowly, or may see khugepaged consume a steady percentage of a CPU without ever catching up. The per-process `MADV_HUGEPAGE` hint helps by narrowing the scan, but it does not eliminate the background work.

## NUMA, cgroups, and the placement tax

Huge pages are physical-memory objects, so they inherit every property of the physical memory system. On a NUMA machine, an order-9 allocation must be satisfied within a node, and the node is usually chosen from the faulting CPU's policy. If the process later migrates to another node, the huge page remains where it was allocated. A 2 MiB page that is remote is still one translation, but every access to it crosses the interconnect. The TLB win can be partially offset by the NUMA penalty. Automatic NUMA balancing can migrate pages, but migrating a 2 MiB page is a much larger operation than migrating a 4 KiB page, and the kernel may decline or throttle it.

Memory cgroups add another layer. The charge for a huge page is coarse, and the reclaim path must decide whether to split the page, migrate it, or reclaim it as a unit. Under a tight `memory.max`, the kernel may prefer to split huge pages rather than evict them, which silently returns the workload to 4 KiB mappings just when the TLB pressure is highest. The cgroup's `memory.stat` will show the anon and file totals, but it will not necessarily show you that the huge pages you expected were split. You need to look at the process's `smaps` and the system's `vmstat` counters to see the difference.

## Reading the signals

The first signal is `AnonHugePages` in `/proc/<pid>/smaps` or `smaps_rollup`. It tells you how much of the mapping is currently backed by huge pages. The second is the set of THP counters in `/proc/vmstat`: `thp_fault_alloc`, `thp_fault_fallback`, `thp_collapse_alloc`, and `thp_collapse_alloc_failed`. A high fallback count with a low allocation count means the kernel is trying and failing, which usually points at fragmentation or cgroup limits. A high collapse count means khugepaged is doing work, but it does not tell you whether that work helped; pair it with TLB miss counters.

On Intel cores, `perf stat` can expose page-walk events such as `dtlb_load_misses.walk_completed` and the page-walker load events. On AMD cores the names differ, and on virtual machines the counters may be unavailable or virtualized. The point is not to memorize event names; it is to compare the same workload with and without huge pages while watching both the translation events and the application's own tail latency. If the walk count falls but latency does not improve, the bottleneck was never the TLB. If latency improves but memory headroom collapses, the huge pages are being paid for with capacity that the service may need later. The useful measurement is the pair, not either number alone.

## The mitigation multiplier: KPTI, PCID, and effective TLB capacity

The TLB is not only a performance structure. It is also an attack surface, and the side-channel disclosures of 2018 changed how kernels use it. Kernel page-table isolation (KPTI) splits the page tables into two hierarchies: a user hierarchy containing user mappings plus a small trampoline, and a kernel hierarchy containing the full kernel mapping. Before KPTI, one hierarchy served both modes, and a syscall needed no change to `CR3`. After KPTI, every entry to the kernel switches to the kernel tables and every return switches back.

That switch is the operation that historically flushed the TLB. Process-context identifiers (PCIDs) let the TLB tag entries with a 12-bit address-space ID, and `INVPCID` allows selective invalidation, so a `CR3` write no longer has to discard everything. But KPTI consumes PCIDs. The user and kernel halves of a process need distinct tags, and the kernel tag is shared only to the extent the kernel mapping is identical across processes. The PCID space is finite — 4096 tags on current hardware — and on a host running hundreds of containers it is a genuinely scarce resource. When tags are recycled, translations that would otherwise have survived are discarded, and the effective capacity available to any one address space shrinks.

The consequence is that the TLB entry count printed in a vendor optimization guide is an upper bound, not a working number. The working number depends on how many address spaces are active, how often the process crosses the user-kernel boundary, and how the kernel allocates tags. Workloads that trap frequently — I/O-heavy services, anything making many syscalls, anything taking interrupts at a high rate — pay both the switch and the loss of resident translations. Workloads that run in user mode for long stretches and touch a large working set are the ones where the loss is most visible, because they are the ones that most needed the entries.

Huge pages compensate for this in a way that is not marginal. If the TLB holds fewer usable entries but each entry covers 512 times more address space, the reach that matters to the application can be preserved. This is one reason transparent huge pages moved from a database-tuning curiosity to a default-on kernel feature. It is also a reason to re-examine workloads that were tuned before the mitigations landed. A service sized against a translation budget that assumed a full TLB is now running against a smaller one, and the symptom is not a crash but a slow drift in the miss rate as concurrency rises.

Other mitigations add to the same pressure without touching the TLB directly. L1TF and MDS required flushing microarchitectural buffers on context switches; those flushes are not TLB flushes, but they lengthen the transitions that already disturb translation state, and they make the kernel's choice of when to switch address spaces more conservative. The general lesson is that effective TLB capacity is not a constant you can look up. It is a function of the kernel's mapping strategy, the number of active address spaces, and the frequency of privilege transitions, and any of those can change with a kernel update. A performance model that assumes a fixed entry count will surprise you on the next upgrade.

There is no userspace interface that reports PCID pressure, which makes the effect hard to see directly. The closest thing to a probe is a controlled comparison: run the same memory-bound workload with and without a high rate of system calls, or run it on a bare host and inside a container alongside many other tenants, and watch whether the translation-event rate diverges more than the data-cache behavior would explain. If the syscall-heavy variant shows a disproportionate rise in page-walk activity for the same data footprint, tag recycling is a plausible culprit. The fix is the same as for any other translation pressure: reduce the number of distinct translations the workload needs by increasing the page size, so that the smaller effective TLB is asked to cover the same region with fewer entries.

## Nested paging: the walk that happens twice

Everything above assumed the machine translates one virtual address to one physical address. Under virtualization, the guest's physical address is not the host's physical address, and the hardware must translate twice. The guest maintains its own page tables mapping guest-virtual to guest-physical. The hypervisor maintains a second structure — Intel's extended page tables (EPT), AMD's nested page tables (NPT) — mapping guest-physical to host-physical. A guest TLB miss therefore cannot be satisfied by walking the guest page tables alone, because each guest page-table entry is itself at a guest-physical address that must be translated through the second structure.

The arithmetic is unforgiving. A four-level guest walk is four dependent memory accesses to guest page tables. If each of those accesses misses in the nested translation caches, each requires its own walk of the EPT, up to four levels deep. The worst case is on the order of twenty memory accesses for a single data translation, and that is before the data itself is fetched. Real hardware caches aggressively at every level — guest paging-structure caches, nested paging-structure caches, combined TLB entries tagged by virtual processor ID — so the worst case is rare. But the shape of the cost is what matters: nested paging multiplies the penalty of every translation miss, and the multiplier grows with the depth of both walks.

| Guest page size | Guest levels walked | Host levels per guest access | Approximate worst-case accesses |
|---|---|---|---|
| 4 KiB | 4 | 4 | 20 |
| 2 MiB | 3 | 4 | 15 |
| 1 GiB | 2 | 4 | 10 |
| 4 KiB, 2 MiB host pages | 4 | 3 | 16 |
| 2 MiB, 2 MiB host pages | 3 | 3 | 12 |

The table makes the design rule obvious: reduce the depth on both sides. A guest that backs its heap with 2 MiB pages removes one level from the guest walk. A hypervisor that backs guest memory with 2 MiB or 1 GiB pages removes a level or two from the host walk. Neither change is optional for a latency-sensitive virtualized workload; both are cheap relative to the alternative. This is also why cloud providers expose 1 GiB pages for EPT backing even when the guest never uses huge pages itself: the nested walk benefit accrues regardless of what the guest does.

There is a second, less discussed cost. The TLB is not virtualized. A guest cannot be granted more entries, and the hypervisor cannot partition the TLB between virtual machines the way it partitions memory. All guests on a core compete for the same tags and the same entries, and a guest with a large working set can evict translations belonging to another guest's vCPU. The hypervisor's only real lever is to reduce the number of translations each guest needs — which again means large pages, on both sides of the nested walk.

Measuring this is harder than measuring native translation cost. Hardware performance counters for page walks may be unavailable inside a guest, or may count host-side events without exposing the guest's own misses. The practical approach is to measure the guest's application-level latency and the host's counters simultaneously, and to test the same workload with and without large-page backing at each layer. If enabling EPT huge pages on the host improves a guest benchmark that itself uses 4 KiB pages, the nested walk was the bottleneck. If it does not, the guest's own translation depth is the problem.

## Sizing the explicit pool: arithmetic that has to be done up front

HugeTLB pages are a reservation, and reservations have to be sized. The pool is configured per size, per NUMA node, through `/sys/kernel/mm/hugepages/hugepages-2048kB/nr_hugepages` and the `nr_hugepages` file under the per-node directories in `/sys/devices/system/node/node*/hugepages/`. On a multi-node machine, a global write distributes the request across nodes according to their relative memory, which is rarely what you want. A latency-sensitive service pinned to one node should set the per-node counts explicitly and verify them, because an allocation that lands on the wrong node turns a translation win into an interconnect penalty.

The sizing arithmetic starts from the working set that needs coverage, not from total memory. If a database buffer pool is 64 GiB and the pool must be entirely huge-page-backed, that is 32768 2 MiB pages. Add headroom for per-connection allocations and for the kernel's own structures. If the workload can tolerate a mix, it is usually better to back the hot region explicitly and leave the rest on small pages than to force everything into the pool; a partially covered region still gets most of the TLB benefit for the covered part, and it avoids the failure mode where the pool is exhausted and a critical allocation falls back to 4 KiB with no warning.

Overcommit changes the character of the reservation. Setting `nr_overcommit_hugepages` allows the kernel to satisfy huge-page requests from the general page allocator when the reserved pool is empty, which trades the strong guarantee of the pool for flexibility. It is useful for workloads with bursty huge-page demand, but it reintroduces exactly the fragmentation-dependent allocation behavior that the pool exists to avoid. If the service's latency target depends on allocation always succeeding, overcommit is the wrong tool.

The cost of the reservation is that pool pages are not reclaimable. They are not swapped, not dropped under pressure, and not available to other tenants. On a dedicated host that is fine. In a container or a shared node it means the pool must be accounted against the same budget as everything else, and it must be visible to whoever is capacity-planning the machine. A pool sized for peak demand sits idle at trough, which is a real cost even when it does not appear in the application's own metrics. The correct size is the working set that needs translation coverage during the peak, plus a margin that reflects how badly the service behaves if allocation fails.

## Measuring translation cost without fooling yourself

The experiments that decide whether huge pages help are easy to design badly, because translation cost is confounded with cache behavior at every turn. A larger page changes the TLB footprint, the page-table footprint, and — through allocator behavior — the physical placement of the data. Changing all three at once and attributing the result to TLB reach is a common mistake.

The first discipline is to hold the working set constant. Allocate the same number of bytes, touch the same number of distinct cache lines in the same order, and change only the page size backing the region. The cleanest way to do that is to run the identical access pattern twice: once on a buffer obtained with `mmap` and touched one 4 KiB page at a time, and once on a buffer explicitly backed by huge pages, with the kernel configured so that the small-page case does not silently get transparent huge pages. If you cannot prevent the kernel from collapsing the small-page buffer, you are not running the experiment you think you are.

The second discipline is to defeat the prefetcher. A linear scan over a large region has near-perfect TLB behavior regardless of page size, because each page is touched once and the misses are amortized. To expose translation cost you need either a stride larger than the prefetcher's reach or a random permutation. A stride of exactly one page size is a useful probe: it touches every page once and nothing within a page twice, which isolates translation from cache-line effects. A random permutation over the same region is a better model of a hash table or a tree, but it also stresses the data cache, so it must be paired with a small-footprint control to separate the two.

The third discipline is to measure the translation events themselves, not just wall time. On native x86, `perf stat` can report data-TLB load misses that completed a page walk, along with the walk-duration and walk-active events that indicate whether the walker was busy. The names and availability differ across vendors and kernel versions, so the right move is to list the events on the target machine rather than copying a command from a blog post. What you want is a ratio: walk completions per thousand loads, or walk cycles as a fraction of total cycles. Comparing that ratio between the 4 KiB and huge-page runs tells you whether translation was actually the difference.

The fourth discipline is to test on the deployment kernel and the deployment topology. THP defaults, multi-size THP availability, defrag policy, cgroup limits, and NUMA placement all vary across distributions and versions, and a microbenchmark on a laptop will not reproduce a container under a memory limit. In particular, run the experiment inside the same cgroup configuration as production, because a `memory.max` that forces splitting or reclaim will erase the huge-page benefit and attribute the loss to something else entirely.

Finally, resist the single-number summary. The useful output of a huge-page experiment is a pair: the change in translation events and the change in tail latency, plus a note on resident memory. A result that lowers walk counts by an order of magnitude while leaving p99 unchanged means the bottleneck was elsewhere. A result that improves p99 while raising RSS by twenty percent is a trade that must be evaluated against the service's headroom, not against the benchmark's throughput. The measurement is cheap; the misinterpretation is what costs.

One more habit is worth building: keep the negative result. A workload that does not benefit from huge pages is as informative as one that does, and the reason usually falls into a small set of categories — the working set already fits in the TLB, the access pattern is sequential enough that the prefetcher hides the misses, the bottleneck is DRAM bandwidth rather than translation, or the pages are being split under pressure. Recording which category applies saves the next engineer from repeating the experiment, and it keeps the huge-page toggle from becoming a cargo-culted default applied to services that never needed it.

## Allocators, runtimes, and the page-size contract

Even when the kernel is willing to hand out huge pages, the application's allocator can make them impossible to form. THP collapse requires a run of present, contiguous, small pages within a single virtual region. An allocator that returns memory to the kernel after every free — using `MADV_DONTNEED`, `MADV_FREE`, or `munmap` — creates holes in that run. khugepaged sees non-present PTEs, and depending on the configured `max_ptes_none` threshold, it may skip the region entirely. The same allocator that keeps RSS low also keeps THP from ever becoming effective.

glibc's malloc is the default for many services, and its behavior is controlled by a set of tunables that most operators never set. `MALLOC_ARENA_MAX` bounds the number of per-thread arenas; fewer arenas mean less virtual address space and less fragmentation, but more lock contention. `M_MMAP_THRESHOLD` decides when an allocation is served by `mmap` rather than by extending the heap with `brk`. `M_TRIM_THRESHOLD` decides when freed top-of-heap memory is returned to the kernel with `sbrk` or `madvise`. A low trim threshold returns pages promptly, which is good for RSS and bad for THP. Raising `MALLOC_TRIM_THRESHOLD_` or `MALLOC_TOP_PAD_` keeps pages resident and gives khugepaged something to collapse. The trade is memory that looks unused but is not available to other processes.

jemalloc and tcmalloc make the same trade with explicit decay parameters. jemalloc's `dirty_decay_ms` and `muzzy_decay_ms` control how long freed extents are retained before being purged. Setting them to zero makes the allocator return memory immediately; setting them to a few seconds or more keeps pages present and makes THP collapse possible. tcmalloc has similar knobs, including aggressive decommit settings that trade RSS for lower allocation latency. The right value is workload-specific: a service that allocates and frees large regions in steady state benefits from retaining memory, while a service with a shrinking heap may prefer to return it and accept 4 KiB translations.

The Go runtime has its own scavenger. It periodically returns unused heap memory to the kernel, historically with `MADV_FREE` and, under some configurations, with `MADV_DONTNEED`. `MADV_FREE` marks pages as reclaimable but keeps them present until memory pressure arrives, which is friendlier to THP. `MADV_DONTNEED` zaps the mappings immediately, which creates the holes that defeat collapse. The `GODEBUG=madvdontneed=1` setting forces the more aggressive behavior and can lower RSS at the cost of losing huge-page coverage. `GOMEMLIMIT` increases scavenging when the heap approaches the limit, so a service running close to its limit may see THP coverage disappear exactly when the working set is largest. That interaction is rarely intentional.

The JVM exposes the page-size choice directly, but the flags interact. `-XX:+UseTransparentHugePages` asks the kernel to back the heap with THP where possible. `-XX:+UseLargePages` uses explicit hugetlbfs pages instead, which requires a reserved pool and is not reclaimable. `-XX:+AlwaysPreTouch` touches every heap page at startup, which makes the heap resident and contiguous early; that is often the difference between a heap that collapses and one that never does. Heap resizing works against this: if the JVM shrinks the heap under `-XX:MaxHeapFreeRatio`, it returns memory to the kernel, and the remaining huge pages may be split or the freed regions may become ineligible for future collapse. A stable heap size with pretouch is usually the most predictable configuration for huge pages.

The common thread is that huge pages are a contract between the kernel and the allocator. The kernel can only collapse memory that the allocator leaves present and contiguous. If the allocator's goal is to minimize RSS, it will actively work against that contract. The observable symptom is a service with `transparent_hugepage/enabled` set to `always`, a large anonymous heap, and `AnonHugePages` near zero in `smaps_rollup`. The fix is not another kernel tunable; it is to make the allocator retain memory, or to switch to an explicit hugetlbfs pool for the regions that matter.

## File-backed large folios and mmap'd data

Anonymous memory is only half the address space. Page cache pages are allocated as folios, and recent kernels can allocate large folios for file-backed pages. A large folio is a physically contiguous group of pages managed as one unit. It reduces per-page metadata, improves readahead, and reduces the number of operations needed to move data between page cache and storage. For mmap'd files, if the folio is large enough and the mapping is eligible, the kernel can install PMD-sized mappings for read-only file mappings. This gives the same TLB reach benefit as anonymous THP without consuming anonymous memory.

Eligibility is narrower than for anonymous memory. Read-only executable mappings and read-only data mappings can be backed by huge pages when alignment and filesystem support allow. Writable shared mappings generally cannot, because a write to one sub-page must not require copying the entire 2 MiB page; the kernel would have to break the huge mapping. tmpfs is an exception: it is memory-backed, and its pages can be huge, so shared memory segments on tmpfs can benefit. Databases that place data files on tmpfs, or that mmap read-only snapshots, are the common beneficiaries. A database that mmaps a regular file writable will usually remain on 4 KiB translations.

Large folios in the page cache have a benefit even without user-visible huge mappings. Buffered reads and writes move data in larger units, which reduces the number of `struct page` operations and improves throughput for sequential I/O. The effect is most visible on high-bandwidth storage. It does not, by itself, improve TLB reach for a process that copies data into a 4 KiB-mapped buffer. The translation benefit requires the process to map the file directly and for the mapping to be eligible for huge pages.

Operationally, file-backed huge pages are harder to observe. `AnonHugePages` does not count them. You need to look at `/proc/<pid>/smaps` for `FilePmdMapped` and `ShmemPmdMapped`, or the system-wide `FilePmdMapped` in `/proc/meminfo`. If those counters are zero, your file-backed workload is not getting huge translations, no matter how large the page cache is. The tuning levers are different too: mount options, filesystem support, and the read-only nature of the mapping matter more than `khugepaged` thresholds. For a workload that reads a large immutable dataset, the right design is often to map it read-only and let file-backed THP provide the coverage, rather than to copy it into anonymous memory and hope khugepaged collapses the copy.

## Multi-size THP and the granularity spectrum

Multi-size THP breaks the binary choice between 4 KiB and 2 MiB. On kernels that support it, the system exposes per-size control directories under `/sys/kernel/mm/transparent_hugepage/`, such as `hugepages-64kB/`, `hugepages-128kB/`, and so on up to the PMD size. Each has its own `enabled` and `defrag` knobs, and the thresholds that govern how many non-present or swapped PTEs a candidate region may contain. The point is to let an operator enable, say, 64 KiB anonymous folios without enabling 2 MiB PMD mappings for every heap.

It is important to be precise about what these intermediate sizes do. On x86-64, the hardware page sizes are 4 KiB, 2 MiB, and 1 GiB. A 64 KiB THP is not a hardware page size; it is a physically contiguous folio mapped by 16 contiguous 4 KiB PTEs. The TLB still caches 4 KiB translations for that region. The benefit is not a 16x increase in per-entry reach. The benefits are fewer page faults, less `struct page` overhead, better physical contiguity, and a smoother path toward a later 2 MiB collapse. The TLB reach win still comes from the PMD-sized mappings.

That distinction matters for tuning. If the goal is to reduce page-walk frequency for a large random-access working set, intermediate sizes will not deliver the same result as 2 MiB pages. If the goal is to reduce allocation and fault overhead, or to avoid the internal fragmentation of 2 MiB pages for a heap that is only a few hundred kilobytes per allocation, intermediate sizes are a better fit. They are also useful as a transitional state: a workload can start with 64 KiB folios and later, once the heap is dense and long-lived, collapse to 2 MiB.

The thresholds are where the operational subtlety lives. `max_ptes_none` controls how many non-present PTEs may exist in a candidate range before the kernel declines to collapse. A higher value makes collapse more likely for sparse heaps, at the cost of allocating memory that is not yet touched. `max_ptes_swap` does the same for swapped-out entries. `max_ptes_shared` governs shared anonymous memory. Raising these thresholds can turn a heap that never collapsed into one that does, but it also increases the chance that a collapse allocates a large folio that is mostly unused. The right setting depends on whether the workload's sparse regions are transient or permanent. A heap that grows in bursts and later fills the holes should be treated differently from a heap that permanently uses one page per 2 MiB.

Multi-size THP also changes the failure mode. With only 2 MiB THP, a failed collapse leaves the region on 4 KiB pages. With intermediate sizes, a failed 2 MiB collapse may still leave 64 KiB or 128 KiB folios in place, which softens the latency cliff. That is a meaningful improvement for services that cannot tolerate the full 2 MiB allocation stall but still want some translation amortization. The cost is more kernel bookkeeping and more tunables to validate. As with every THP feature, the only way to know is to measure the translation events and the tail latency on the deployment kernel.

## Huge pages on the I/O path: pinning, IOMMU, and RDMA

Translation pressure is not only a CPU concern. Devices that perform DMA must be given physical addresses, and the IOMMU translates device-visible addresses to physical addresses using its own cache — the IOTLB. Like the CPU TLB, the IOTLB has a finite number of entries, and each entry covers a page. A device that streams data through a 4 KiB-mapped buffer will miss in the IOTLB frequently; a device that streams through a 2 MiB or 1 GiB buffer will miss far less often. This is why high-performance networking and storage stacks have used huge pages for years: DPDK packet buffers, RDMA memory regions, io_uring registered buffers, and AF_XDP UMEM are all designed around large, pinned, contiguous memory.

Pinning is the second half of the story. A buffer used for DMA must be pinned in physical memory so that it does not move or get reclaimed. Pinning 4 KiB pages means the kernel must track and pin each page individually, and the IOMMU must map each one. Pinning a 2 MiB huge page means one pin and one mapping for 512 times the memory. The difference shows up in registration latency, in the size of the IOMMU page tables, and in the rate at which the IOTLB can be filled. For a service that registers and deregisters buffers frequently — a common pattern in RDMA and in some storage stacks — huge pages reduce the per-registration cost by an order of magnitude.

Transparent huge pages are a weaker fit for the DMA path than explicit hugetlbfs pages. Long-term pinning of THP pages can interfere with the kernel's ability to split or migrate them, and the kernel may refuse to pin or may split the page before pinning. For a device buffer, the explicit pool is usually the right choice: reserve the huge pages at boot, map them with `MAP_HUGETLB`, and register those mappings with the device. That gives deterministic allocation and avoids the compaction and splitting paths entirely. The cost is the same as any hugetlbfs reservation: the memory is dedicated and not reclaimable.

The I/O path also has a translation-depth analogue. A device behind an IOMMU may use a multi-level page table, and a miss can walk several levels. Nested virtualization adds another layer, because the guest's I/O virtual address must be translated through the guest's IOMMU tables and then through the host's. The same arithmetic as nested CPU paging applies: reduce the depth on both sides, and use the largest page size the hardware supports. For a virtualized database or a containerized network function, huge-page-backed I/O buffers are often the difference between line-rate and a fraction of it, and the bottleneck is not the NIC but the translation path.

## Confidential computing and encrypted memory

Confidential computing adds another cost to the translation path. AMD SEV and Intel TDX encrypt guest memory, including the page tables. A page walk therefore touches encrypted memory, and the hardware must decrypt each level before it can read the next pointer. The encryption and integrity overhead is small per access but nonzero, and it is paid on every page-walk level that misses in the paging-structure caches. The result is that a TLB miss costs more in a confidential VM than in a conventional one, which raises the value of every mechanism that reduces TLB misses. Huge pages are one of the few levers available to the guest, and they become more attractive as the cost of a miss rises.

Nested paging is already mandatory in these environments, because the hypervisor must protect the guest's memory from the host. The guest's page tables are encrypted, but the host's nested page tables are not accessible to the guest, and the two-level walk is the norm. A confidential guest that uses 4 KiB pages therefore pays the deepest walk the platform supports, with encryption overhead on each guest level. Backing the guest's hot working set with 2 MiB pages removes one guest level and reduces the number of encrypted page-table reads. The benefit compounds with host-side large pages for the nested tables.

There is a tension with memory overcommit. Confidential VMs typically cannot have their memory swapped or ballooned by the host, because the host cannot read or move the encrypted contents. The guest's memory is effectively pinned. That makes the resident-set cost of huge pages less of a surprise — the memory was never reclaimable anyway — but it also means internal fragmentation is permanent. A confidential guest that allocates a 2 MiB page for a sparse region cannot rely on the host to reclaim the unused part. Sizing the heap and the huge-page pool carefully is therefore more important, not less, in this environment.

Observability is limited. The guest may not have access to the host's nested page-walk counters, and the hardware may not expose the same `perf` events inside a confidential VM. The practical approach is to measure application-level latency and throughput across configurations, and to use the guest's own `/proc/vmstat` THP counters to confirm that huge pages are actually being used. If `AnonHugePages` is high but latency does not improve, the bottleneck may be elsewhere; if it is low, the guest is not getting the translation benefit at all. The measurement is coarser than on bare metal, but it is still enough to decide whether the page size is helping.

## Fork, copy-on-write, and the huge-page penalty

The fork system call is a translation and memory-management event as much as a process-creation event. It duplicates the page tables, marks the parent's and child's pages copy-on-write, and lets the two processes share physical memory until one of them writes. For a service with a large heap, the page-table duplication is proportional to the number of mapped pages. A heap backed by 4 KiB pages has 512 times as many PTEs as the same heap backed by 2 MiB pages, so fork must copy far more metadata. That alone can make fork latency visible on a multi-gigabyte process.

The more notorious interaction is copy-on-write at huge-page granularity. If a 2 MiB page is marked copy-on-write and either process writes to any byte in it, the kernel must preserve the other process's view. Historically, that meant copying the entire 2 MiB page, which turns a single store into a large memcpy and a fresh allocation. Modern kernels often split a THP before performing the copy, reducing the copy to 4 KiB, but splitting has its own cost: it must allocate a page table, replace the PMD entry with 512 PTE entries, and flush the relevant TLB entries on every CPU that has the mapping. The latency is smaller than copying 2 MiB, but it is still a kernel operation that can appear in the tail.

This is why in-memory databases that fork for snapshots have a complicated relationship with THP. A background save that forks a large process and then writes to a subset of the heap will trigger copy-on-write faults across the touched region. With 4 KiB pages, only the written pages are copied. With 2 MiB pages, the fault granularity is much coarser unless the kernel splits first. The result can be a latency spike during the snapshot, a spike in memory usage as pages are duplicated, or both. The safe configuration for such a service is often to disable THP for the database process and use explicit hugetlbfs pages only for regions that are never written after fork, or to use a snapshot mechanism that does not rely on fork at all.

The same logic applies to any workload that uses fork as a cheap way to create a copy of a large address space: web servers with preloaded heaps, language runtimes that fork workers, and build tools that fork compilers. The cost is not the fork call itself but the first write in each shared huge page. If the workload's write pattern is sparse, huge pages amplify the cost by the ratio of the page size to the write granularity. If the write pattern is dense, the amplification is small and the fork-time page-table savings may dominate. As always, the deciding factor is the ratio of touched bytes to mapped bytes, and the only reliable way to know is to measure the fork path under the production workload.

Page-table duplication is not the only fork-time cost. The kernel must also mark the page-table entries read-only in both processes and flush the TLB on every CPU that has the address space active. That is a TLB shootdown, and its cost scales with the number of CPUs and the number of mappings. A process with a 2 MiB-backed heap has fewer mappings to update, which reduces the shootdown work. The copy-on-write fault path, however, becomes coarser. The two effects pull in opposite directions, and which one wins depends on how much of the heap the child touches and how many CPUs are running the process. A single-threaded batch job on a small machine may see fork become cheaper with huge pages; a many-threaded service on a large machine may see the tail latency get worse. The only way to resolve it is to measure both the fork duration and the write-fault duration with the real concurrency and the real page-size configuration.
