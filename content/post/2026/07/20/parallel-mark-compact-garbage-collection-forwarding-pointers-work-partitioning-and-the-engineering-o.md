Modern managed runtimes rarely get to choose a garbage collector on purely theoretical grounds. They choose among collectors that satisfy a set of constraints: pause-time bounds, memory overhead, throughput, locality, and the ability to coexist with native code. Copying collectors are attractive because they are easy to parallelize: live objects are evacuated from one semispace to another, and no object is overwritten in place. The cost is a second semispace and a full copy of all live data. Mark-sweep collectors avoid the second semispace and avoid moving objects, but they leave holes and fragment the heap. Mark-compact collectors sit between those poles. They mark live objects, then slide or otherwise compact them into a dense region. They avoid a full semispace and avoid fragmentation, but compaction is a graph-wide address-rewriting problem. That makes parallelization harder than it first appears.

This article focuses on stop-the-world parallel mark-compact collection for a precise, tracing runtime. The assumptions are deliberate. The mutator is stopped during compaction. The runtime has precise pointers and object headers with enough space for a forwarding pointer or a side table. Objects are not pinned by native code during the core algorithm. The heap is partitioned into regions for work distribution. The goal is not to survey every collector in existence. The goal is to examine the mechanics that make parallel compaction correct: forwarding pointers, prefix sums over live bytes, phase barriers, and the dependency structure of moving objects in place. The first sections establish the compaction model and the forwarding protocol. Later sections will examine the update and move phases, region sizing, load balance, and the trade-offs against evacuation and mark-sweep.

## The compaction problem

A mark-compact collector starts with a mark phase. The mark phase traverses the object graph from roots and sets a mark bit for every reachable object. At the end of the mark phase, the collector knows which objects are live. It does not yet know where those objects will live after compaction. That is the compaction problem: assign every live object a new address and rewrite every reference to point to that address.

Sliding compaction is the simplest mental model. The collector walks the heap in address order and slides each live object down to the first available address after the previously compacted object. Dead objects disappear. Live objects keep their relative order. If the heap is a contiguous sequence of objects, the new address of a live object is the compact base plus the total size of all live objects that precede it. That total is a prefix sum over live object sizes. The prefix sum is the key algorithmic primitive. It is also the point where parallelism becomes interesting.

A serial collector can compute the prefix sum and move objects in one pass. A parallel collector cannot casually do the same, because the prefix sum is a global dependency. If two threads compact different parts of the heap independently, they need to agree on where the first part ends and the second part begins. The boundary depends on the number of live bytes in the first part. That is a reduction followed by a scan. The reduction counts live bytes per region. The scan turns those counts into region base addresses. Only then can each thread compute per-object destinations inside its region.

This two-level structure is common in parallel compaction. The heap is divided into regions. Each region has a live-byte count. An exclusive prefix sum over region counts gives each region a destination base. Inside a region, each thread computes an exclusive prefix sum over the sizes of live objects in that region. The result is a forwarding address for each live object. The region-level prefix sum is a small global step. The object-level prefix sum is local to the region. The split keeps the global synchronization short and the local work parallel.

The trade-off is region size. Large regions reduce the number of region counters and the cost of the global prefix sum. They also make the local prefix sum longer and can create load imbalance if live data is concentrated in a few regions. Small regions improve load balance and reduce the longest local scan, but they increase the number of counters and the overhead of the global scan. The right size depends on heap size, object size distribution, and the number of collector threads. There is no universal constant. A region size that works for a heap dominated by small objects may be poor for a heap with many large arrays.

There is another subtlety: sliding compaction preserves allocation order, but it does not preserve dead space. The destination of an object can overlap the source of a dead object or the source of an already moved live object. In a serial collector, moving in ascending address order is safe when compacting toward lower addresses. The destination of the current object is at or below its source. The collector copies the object forward, possibly with an overlapping memmove, and then continues. Earlier objects have already been moved. Later objects have not been overwritten because their sources are above the current source. The ordering argument is simple but fragile. It breaks when multiple threads move objects concurrently.

That fragility is the central engineering issue. Parallel marking is a graph traversal problem with atomic mark bits and work stealing. Parallel compaction is an address-space rewriting problem with dependencies between source and destination ranges. The dependencies are not arbitrary. They follow the monotonicity of sliding compaction. An object's destination is less than or equal to its source. That monotonicity gives the collector a partial order. The collector can exploit that order, but it must not violate it. A thread that moves an object into a low address may overwrite a source object that another thread has not yet copied. The collector needs either a scheduling discipline, a dependency-tracking mechanism, or a heap layout that avoids the conflict.

## Forwarding pointers and the three-pass structure

The forwarding pointer is the contract between the phases. After the mark phase, every live object has a mark bit. During the compute-forwarding phase, the collector writes the object's destination address into its header or into a side table. The forwarding pointer is valid only for live objects. Dead objects do not need one. The mark bit distinguishes the cases. If the header uses a tagged word, the collector must ensure that a mark bit and a forwarding pointer cannot be confused. A common design uses a separate forwarding slot in the header. Another design uses a side table indexed by object address. The header slot is faster to access but costs header space for every object. The side table avoids header changes but adds a memory indirection and a cache miss for every reference update. The choice is a classic space-time trade-off.

The forwarding pointer must be published before any other thread reads it. In a stop-the-world collector, the mutator is stopped, but collector threads still run concurrently. The compute-forwarding phase has a natural barrier at the end. Within the phase, a thread computes forwarding pointers for its region. Other threads do not read those pointers until the barrier. The barrier provides the necessary ordering. If the collector wants to overlap phases, it needs explicit release and acquire operations. A release store after writing the forwarding pointer ensures that the destination address is visible before any thread observes the pointer. An acquire load before reading the pointer ensures that the thread sees the complete write. On weakly ordered architectures, these operations are not optional. The collector also needs to ensure that the forwarding pointer write is atomic with respect to reads. A pointer-sized aligned store is usually atomic on the target architecture, but the collector should not assume that without a documented guarantee. If the header is not aligned or the pointer is not word-sized, the collector needs a different protocol.

The three-pass structure is the simplest correct schedule. Pass one computes forwarding pointers. Pass two updates every reference in every live object and every root. Pass three moves the objects. The passes are separated by barriers. The order matters. If the collector moves objects before updating all references, it can overwrite an old copy that still contains the only reference to some object. The reference update pass must complete before the move pass begins. The update pass reads forwarding pointers and writes new addresses into object fields. The move pass reads object headers and copies object bodies to their destinations. The move pass does not need to read forwarding pointers for correctness if the destination is stored in the header, but it does need to know object sizes. The header remains valid until the object is overwritten. The move pass must not overwrite a source object before it has been copied. That is the dependency that the scheduling discipline must respect.

The three-pass structure has a cost. It touches every live object at least three times: once to compute forwarding, once to update references, and once to move. A copying collector touches live objects twice: once to copy and once to update references. A mark-sweep collector touches live objects once to mark and once to sweep. The extra pass is the price of in-place compaction. The collector can fuse some work. For example, the compute-forwarding pass can also compute per-region live counts. The update pass can also update roots. The move pass can also clear mark bits. But the fundamental dependency remains: all forwarding pointers must exist before any reference update, and all reference updates must complete before any object is overwritten. Fusing passes across those barriers is possible only with more complex synchronization.

The forwarding pointer also interacts with object alignment. If objects are aligned to 8 or 16 bytes, the low bits of a forwarding address are zero. The collector can use those low bits as tags if the header word is otherwise used for mark bits. This is a common trick, but it requires care. The tag must be cleared before the address is used. The collector must also ensure that the mark bit and the forwarding tag do not collide with other header fields. A conservative collector or a runtime with moving and non-moving objects may need a more elaborate header encoding. The simplest design is a dedicated forwarding word that is only meaningful during compaction. The cost is one word per object. For small objects, that cost can be significant. For large objects, it is negligible. The collector designer must decide whether the header cost is acceptable or whether a side table is better.

The next section examines the update and move phases in more detail. The update phase is conceptually simple: scan every live object, find every reference, and replace the old address with the forwarding address. The move phase is where the dependency structure becomes visible. The collector must decide whether to schedule moves by source region or by destination region, and that choice determines which conflicts are possible. The answer is not a single algorithm. It is a family of schedules with different trade-offs in pause time, parallelism, and implementation complexity.

## The update phase: rewriting references without a graph walk

The update phase is where the collector replaces every reference to a moved object with the object's forwarding address. It is conceptually simple because the collector does not need to traverse the object graph. The mark phase already identified every live object, and the compute-forwarding phase already assigned every live object a destination. The update phase can therefore scan the live objects in address order and rewrite their fields. There is no recursion, no worklist, and no need to follow pointers. The only requirement is that every reference in every live object is visited exactly once. Dead objects are ignored because they will be overwritten during the move phase and cannot be reached by the mutator after the collection finishes.

The parallel structure of the update phase follows the region partitioning used for forwarding computation. Each collector thread owns one or more source regions. Within a region, the thread scans objects in address order, skipping dead objects by checking mark bits. For each live object, it decodes the object's layout, walks its reference fields, looks up the forwarding address of each target, and writes the new address back into the field. The forwarding lookup can be a header read if the forwarding pointer is stored in the object header, or a side-table probe if the collector uses a side table. The header read is faster but requires that the object header remains intact until the move phase. The side-table probe avoids header changes but adds an indirection that can miss in cache. A hybrid design stores forwarding pointers in the header for small objects and in a side table for large objects, but that complicates the lookup path.

Roots require separate treatment. The roots are not heap objects, so they do not have forwarding pointers of their own. They contain references to heap objects, and those references must be updated using the same forwarding pointers. Because the mutator is stopped, the root set is stable. The collector can partition roots by thread, by stack frame, or by global data structure. In many runtimes the root set is small compared to the live heap, so a single work item may be sufficient. In runtimes with many threads or large thread-local heaps, parallel root scanning can matter. The important constraint is that root updates must complete before the move phase begins. If the move phase overwrites an old object while a root still points to it, the root becomes dangling. There is no safe way to move first and update roots later unless the collector keeps the old copy alive, which defeats in-place compaction.

The update phase also has to respect pointer encoding. If the runtime uses compressed pointers, the collector must decode the compressed reference, add the heap base, look up the forwarding address, subtract the heap base, and re-encode. If the runtime uses tagged pointers, the collector must preserve the tag bits. If references are stored in arrays, the collector can parallelize within a large array by splitting it into chunks. That improves load balance but increases the number of forwarding lookups. The lookups themselves are random accesses to object headers or side-table entries, so the update phase is often memory-bound. Prefetching forwarding pointers for a batch of references can hide some latency. The collector can also sort references by target address, but that requires a temporary buffer and may not pay off for small objects.

## The move phase: scheduling copies under sliding compaction

The move phase is where the dependency structure of sliding compaction becomes visible. Each live object has a source address and a destination address. The destination is less than or equal to the source. The object's body must be copied from source to destination, and the old copy becomes dead space that can be overwritten. If the collector moved objects in an arbitrary order, a thread could write to a destination that overlaps the source of an object that another thread has not yet copied. That would corrupt the unmoved object and break the heap. The scheduling discipline must prevent that.

The key property of sliding compaction is monotonicity. If object A precedes object B in source order, then A's destination precedes B's destination. Moreover, A's destination range ends at or before B's source begins. This is not an accident; it follows from the definition of sliding compaction. The collector packs live objects contiguously in source order, so the destination of an object is the compact base plus the total size of all live objects before it. For any two live objects A and B with A before B in source order, the destination of A plus the size of A is at most the destination of B. Since B's destination is at most B's source, it follows that A's destination range ends at or before B's source. This property is the foundation of every safe move schedule.

One safe serial schedule is to move objects in ascending source order. When the collector moves object A, all objects before A have already been moved. Their destinations are below A's destination, so they cannot be overwritten by A's copy. Objects after A have sources above A's source, and by the property above, A's destination range ends at or before the source of any later object. Therefore, moving A cannot corrupt any unmoved source. The same argument shows that moving objects in ascending destination order is also safe. In fact, ascending destination order and ascending source order are the same order for live objects, because destinations preserve the source order.

The difficulty is parallelizing this order. If two threads move objects from the same source region concurrently, a later object's destination might overlap an earlier object's source. The earlier object has not been moved yet, so the later thread's write would corrupt it. The collector can avoid this by assigning each thread a contiguous range of destinations and ensuring that no thread writes to a destination range that overlaps the source of an object assigned to another thread that has not yet completed. This is a dependency problem. A destination region can be written only after all objects whose sources overlap that destination region have been moved. Those objects have destinations that are lower than or equal to the destination region, because their sources are above the destination region and their destinations are at most their sources. The dependency graph is therefore acyclic and directed from lower destinations to higher destinations.

A practical scheduler can process destination regions in waves. In each wave, the scheduler selects destination regions whose dependencies have been satisfied. All objects with destinations in those regions can be moved in parallel. Within a destination region, the collector can further parallelize by splitting the region into blocks, but it must still respect the order of objects within the region. If two objects in the same destination region have overlapping source and destination ranges, the one with the lower destination must be moved first. The collector can enforce this with a per-region atomic counter or by assigning blocks in ascending destination order. The wave structure provides parallelism across regions while keeping the critical path short. If live data is dense, the waves are small and the parallelism is limited. If there are large dead gaps, many regions can be processed in the same wave.

Copying an object is straightforward once the schedule permits it. The collector reads the object header to get the size and the forwarding pointer, then copies the body to the destination. Because the destination is at or below the source, a forward copy from low to high is safe even if the ranges overlap. A backward copy is unnecessary. For very large objects, the collector can split the copy into chunks and use multiple threads, but the chunks must be copied in ascending order to avoid overwriting unread source bytes. Large objects are rare, so the added complexity is usually not worth it. The move phase can also clear mark bits or write a forwarded marker in the old header, but those operations must not interfere with other threads that are still reading the header for size or forwarding information.

## Work partitioning and load balance

The mark phase and the compute-forwarding phase have different load-balancing characteristics. Marking is a graph traversal with irregular work: one object may have no references, while another may have thousands. Work stealing is the natural fit. A thread that finishes its local work steals from another thread's deque. The granularity of stealing matters. If the unit is a single object, stealing overhead can dominate for small objects. If the unit is a region, a thread may be stuck with a large region full of live data while other threads are idle. A common compromise is to use a work-stealing deque of object ranges, where each range contains enough objects to amortize the steal cost. The runtime can also use a mark stack per thread and steal half of another thread's stack when it becomes empty.

The compute-forwarding phase is more regular because it scans regions in address order. Each region has a live-byte count, and the collector computes an exclusive prefix sum over those counts. The prefix sum is a global step, but it is small compared to the object scanning. The local prefix sum within a region can be parallelized by splitting the region into blocks. Each block computes its own live-byte count, then a block-level prefix sum gives each block a starting offset within the region. The object-level prefix sum then runs inside each block. This hierarchical structure is the same idea as the region-level prefix sum, applied recursively. The number of levels should be chosen so that the leaf blocks are large enough to amortize the overhead of the extra counters but small enough to balance load across threads.

The update phase is embarrassingly parallel if the collector partitions by source region. Each thread scans its regions and updates references. The only shared state is the forwarding pointers, which are read-only during this phase. There is no dependency between regions because updating a reference in one object does not change the object's size or location. The load can be balanced by live bytes rather than object count, because updating a large array with many references costs more than updating a small object with one reference. A work queue of regions with live-byte weights works well. The collector can also split large arrays into separate work items, but that requires a second level of work distribution.

The move phase is the hardest to load-balance because of dependencies. A thread cannot simply grab any region; it must wait until the region's dependencies are satisfied. A centralized scheduler can maintain a ready queue of destination regions. When a region is moved, the scheduler checks which higher regions now have all their dependencies satisfied and adds them to the ready queue. The scheduler overhead is small if regions are large, but large regions reduce parallelism. A distributed approach uses atomic counters per destination region to track how many source regions must be moved before the destination region is ready. Each thread, after finishing a source region, decrements the counters of destination regions that depend on it. The first thread to bring a counter to zero claims the destination region. This avoids a central lock but requires a precomputed dependency graph. The dependency graph can be computed during the compute-forwarding phase by recording, for each destination region, the range of source regions that overlap it. Because sources are above destinations, the overlapping source regions form a contiguous range. The collector can store that range as two integers per destination region.

## Region sizing and the cost of global steps

Region size controls the granularity of every parallel phase. Small regions give fine-grained load balance and short dependency chains. They also increase the number of region counters, the size of the prefix-sum array, and the number of scheduler entries. Large regions reduce that overhead but can create long critical paths. If a single region contains a large fraction of the live heap, the thread that owns it becomes a bottleneck during forwarding computation, reference update, and object movement. The collector can mitigate this by splitting large regions dynamically, but that adds complexity to the forwarding protocol.

A useful rule is to size regions so that the number of regions is at least an order of magnitude larger than the number of collector threads. That gives the scheduler enough work items to balance load without making the global prefix sum too expensive. For a 64 GB heap and 64 threads, a region size of 1 MB yields 64,000 regions. A prefix sum over 64,000 counters is fast, even serial. A region size of 64 KB yields one million regions, which may still be acceptable but increases cache pressure. The region size should also be a multiple of the page size to avoid TLB thrashing and to make side-table mapping easier. If the collector uses a side table for forwarding pointers, the side table can be organized by region, so a region's forwarding entries are contiguous in memory.

The global prefix sum can be parallelized with a two-level scan. The collector first computes live bytes per super-region, where each super-region contains many regions. It computes an exclusive prefix sum over super-region counts, then each thread computes the prefix sum within its super-region. This reduces the depth of the global scan and improves cache locality. The super-region size can be chosen so that the per-thread work is balanced. The same hierarchical technique applies to the object-level prefix sum inside a region. The collector can use a tree reduction for the counts and a downward sweep for the offsets. The cost is logarithmic in the number of nodes, but the constant factors are small because the operations are simple additions.

The forwarding pointer storage also interacts with region size. If forwarding pointers live in object headers, region size does not affect the storage cost. If the collector uses a side table, the table can be allocated per region and indexed by object offset. A region with many small objects needs a dense side table or a hash table. A region with few large objects can use a sparse map. The collector can choose the representation based on the region's object density, but that adds a branch to every forwarding lookup. A uniform side table indexed by object address is simpler but wastes space for dead objects. The collector can compress the side table by storing entries only for live objects in address order, with a bitmap to indicate which objects are live. That reduces memory but adds a rank operation to find the entry for a given object. The rank operation can be parallelized with bit tricks, but it is another cost in the critical path.

## Trade-offs against evacuation and mark-sweep

Evacuation, or copying collection, avoids the move-phase dependency entirely. Live objects are copied from the source semispace to a destination semispace. The destination is a separate address range, so a thread can allocate space in the destination with a bump pointer and copy objects without worrying about overwriting sources. The only shared state is the allocation pointer, which can be made thread-local by giving each thread its own allocation buffer. Parallel evacuation is therefore much simpler than parallel sliding compaction. The cost is the second semispace. For a heap of size H, evacuation requires 2H of virtual address space and H of committed memory if the live set is small. Mark-compact requires H of address space and H of committed memory, but it must overwrite dead objects in place. If memory is constrained, mark-compact is more attractive. If pause time is the only concern and memory is plentiful, evacuation is often easier to engineer.

Mark-sweep avoids moving objects altogether. It marks live objects and then sweeps the heap to build free lists. There is no forwarding pointer, no update phase, and no move phase. Parallel marking is the same as in mark-compact. Parallel sweeping can be done by partitioning the heap into regions and having each thread sweep its regions. The pause time is shorter because there is no compaction. The cost is fragmentation. Over time, the heap becomes a patchwork of live objects and free holes. Allocation must search free lists, which is slower than bump-pointer allocation. Locality suffers because objects are not packed together. A mark-sweep collector can mitigate fragmentation with a compacting fallback, but that fallback is exactly the mark-compact algorithm we have been discussing.

Parallel mark-compact sits between these extremes. It avoids the second semispace of evacuation and the fragmentation of mark-sweep, but it pays with a more complex move schedule and an extra pass over live objects. The update phase is similar in cost to the reference update in evacuation, but the move phase is more constrained. The critical path of parallel mark-compact is the longest dependency chain in the move phase plus the barrier costs between phases. If the live heap is dense and uniformly distributed, the dependency chains are short and the collector can achieve good parallelism. If the heap has a few large live objects that move across long distances, those objects can serialize the move phase. The collector can mitigate this by splitting large objects into chunks, but that requires the chunks to be moved in order and adds synchronization.

Another trade-off is locality after collection. Sliding compaction preserves the allocation order of live objects. If the application allocated objects in a locality-friendly order, compaction preserves that order. Evacuation may preserve order if the collector copies objects in address order, but a parallel evacuation that uses thread-local allocation buffers will interleave objects from different threads, producing a different order. Mark-sweep preserves the original addresses, so it does not improve locality but also does not destroy it. For applications with strong allocation-order locality, sliding compaction can be better than parallel evacuation. For applications with no such locality, the difference is small. The collector designer must measure the workload rather than assume that one order is always better.

The final engineering question is whether the complexity of parallel sliding compaction is justified. If the runtime can afford a second semispace, evacuation gives simpler parallelism and often shorter pauses. If the runtime cannot afford the extra memory, mark-compact is the only compacting option. The three-pass structure, the forwarding protocol, and the dependency-aware move schedule are the price of memory efficiency. They can be implemented correctly with careful attention to barriers, atomicity, and region sizing. The result is a collector that can keep pauses short while using the heap densely, but it requires more machinery than either copying or mark-sweep.

## Phase barriers and the cost of rendezvous

A parallel mark-compact collector is a sequence of parallel phases separated by global barriers. The barriers are not an implementation detail; they are part of the correctness argument. The mark phase must finish before forwarding computation, because a forwarding pointer for an unmarked object would be meaningless. Forwarding computation must finish before reference update, because an update needs the destination of every target object. Reference update must finish before object movement, because moving an object overwrites the old copy that still contains the only references to other objects. Each barrier is a rendezvous point where every collector thread must arrive before any thread proceeds.

The cost of a barrier is not just the cost of the synchronization primitive. It is also the cost of the straggler. If one thread is delayed by a cache miss, a page fault, or a long copy, every other thread waits at the barrier. The pause time of a phase is therefore the maximum per-thread work, not the average. Load balancing must target the tail, not the mean. A collector that balances average work but leaves one thread with a large region will still have a long pause. This is why region sizing and work stealing are so important in parallel compaction. They are not throughput optimizations; they are pause-time optimizations.

Barrier implementation matters at scale. A centralized sense-reversing barrier with an atomic counter is simple, but every thread contends on the same cache line. A tree barrier reduces contention by having groups of threads synchronize locally and then a representative synchronize globally. The tree barrier has logarithmic depth, which is better for large thread counts. A dissemination barrier is another option, with O(log P) latency and no central counter. The collector should also consider whether the barrier needs to be a full memory fence. On weakly ordered architectures, the barrier must include a release operation before arrival and an acquire operation after departure. Otherwise, a thread may observe a forwarding pointer before the object header write that published it. The barrier is the natural place to put those fences, but the fences must be correctly paired.

Phase overlap is tempting but dangerous. Could a thread start updating references in its region while another thread is still computing forwarding pointers for a later region? Only if every target of every reference in the first region has already been forwarded. That is not guaranteed, because a reference can point to an object anywhere in the heap. The collector could use a two-level forwarding scheme where a region-level forwarding table is published first, then object-level pointers. But the object-level pointer is still needed to update the reference. The only safe overlap is between independent work items that do not read unpublished state. Root scanning, for example, can overlap with forwarding computation if roots are updated after the forwarding barrier. But root scanning itself must read forwarding pointers, so it cannot update roots before all forwarding pointers exist. The phases are mostly serial in their dependencies even if the work inside each phase is parallel.

## Roots, stacks, and code metadata

The root set is a first-class part of the update phase. Roots include thread stacks, registers, global variables, thread-local storage, code constants, inline caches, and runtime handles. In a precise runtime, the stack is described by stack maps that identify which slots contain references at each safepoint. The collector must walk each thread's stack, find the active frames, and update every reference slot. This is not a graph walk; it is a structured scan. The stack map tells the collector exactly which slots to read and write. The collector does not need to interpret the object graph, but it does need to handle the fact that a stack slot may contain a reference to an object that has already been forwarded.

Parallel root scanning can be partitioned by thread. Each collector thread can own one or more mutator threads and walk their stacks. If the number of mutator threads is small, a single collector thread may do all the stack work while others update the heap. That creates a straggler. The collector can split large stacks by frame ranges, but frame boundaries are irregular. A better approach is to have each collector thread scan a subset of threads and then steal frame ranges from a work queue. The stack maps make it possible to compute the number of reference slots per frame, so the work can be weighted by reference count rather than frame count.

Code metadata is easy to overlook. Compiled code may embed references in constant pools, inline caches, and relocation tables. These references are roots in the sense that they keep objects alive, but they are not on the stack. The collector must update them during the update phase. If the runtime uses code patching, the update must be done while the code is not executing. Since the mutator is stopped, that is already true. But the collector must still ensure that the code metadata is not being read by another collector thread while it is being updated. A simple partition by code module works if modules are independent. If a module is large, the collector can split it by constant pool index.

Weak references, soft references, and finalization queues need special treatment. They are not strong roots, so they do not keep an object alive during marking. After marking, the collector may discover that a weak reference points to a dead object. It must clear that reference rather than forward it. If the weak reference points to a live object, it must be updated like any other reference. The ordering is important: weak references should be processed after the mark phase but before the move phase. If they are processed after the move phase, the old object may already be overwritten. The collector can process weak references in parallel with the update phase, but it must coordinate with the mark phase to know which objects are live. A common design uses a separate weak-reference queue that is drained after marking and before forwarding computation, so that cleared references do not need forwarding pointers.

## Large objects and chunked moves

Large objects dominate pause time in compaction. A single multi-megabyte array can take longer to copy than thousands of small objects. The collector cannot ignore them, but it also cannot split them arbitrarily without breaking the forwarding protocol. The object has one header and one forwarding pointer. If the collector splits the copy into chunks, it must ensure that the chunks are copied in an order that does not overwrite source bytes that have not yet been read. For sliding compaction, the destination is at or below the source. A forward copy from low to high is safe. If the collector copies chunk 0 first, then chunk 1, and so on, it preserves the forward-copy order. Copying chunks in parallel is unsafe if their source and destination ranges overlap, because a later chunk's write could corrupt an earlier chunk's source. The collector can parallelize only non-overlapping chunks, or it can use a dependency counter per chunk. The complexity is rarely worth it for a single object, but it can help when several large objects are moved in the same wave.

Large objects also interact with region sizing. If an object spans multiple regions, the region-level live-byte count must account for the object's bytes in each region. The simplest approach is to assign the object to the region containing its header and count its full size there. Then the object's destination may cross region boundaries, which is fine for sliding compaction as long as the prefix sum is computed over objects rather than regions. But if the collector uses region-level prefix sums to assign destination bases, an object that spans regions can violate the assumption that each region's live bytes are compacted within a region-aligned destination range. A common solution is to place large objects in a separate large-object space that is compacted independently or not at all. If large objects are not moved, the collector must handle references to them without forwarding pointers. That is possible: the forwarding function can return the original address for objects in the non-moving space. The cost is fragmentation in the large-object space, but large objects are few and their fragmentation is easier to manage.

## NUMA, locality, and forwarding metadata placement

On NUMA machines, memory access latency depends on which node owns the physical page. A parallel compaction that computes a global prefix sum may move an object from one node to another. That can improve density but hurt locality if the object is later accessed by a thread on its original node. Some collectors partition the heap into node-local segments and compact within each segment. That preserves node locality but may leave free space at segment boundaries. The trade-off is similar to region sizing: smaller segments improve locality but increase fragmentation and prefix-sum overhead. The collector can also use first-touch allocation and thread affinity to keep mutator threads and their objects on the same node. During compaction, the collector should assign work to threads on the node that owns the source region, so that the copy reads local memory. The destination may be remote, but writes are often cheaper to absorb than reads.

Forwarding metadata placement matters for the same reason. If forwarding pointers are in object headers, they are already local to the object. If the collector uses a side table, the table should be allocated per node or per region so that lookups do not cross the interconnect. A global side table indexed by heap address will cause remote accesses for every reference update. A per-region side table can be placed on the same node as the region. The collector can also cache forwarding pointers for hot objects, but that adds a cache coherence problem: the cache must be invalidated if a forwarding pointer changes. Since forwarding pointers are written once and then read-only, a per-thread cache is safe after the forwarding barrier.

## Instrumentation and pause-time accounting

To tune a parallel mark-compact collector, the runtime needs to know where the pause time goes. The total pause is the sum of phase compute times plus barrier wait times plus the tail of the longest thread. Instrumentation should record, per phase, the maximum and average per-thread work, the number of barrier waits, and the number of work-stealing attempts. It should also record the number of live bytes, the number of live objects, and the distribution of object sizes. These counters are cheap to maintain if they are per-thread and merged at barriers. They are invaluable when a pause exceeds its target.

A simple model helps. Let T_phase be the compute time of a phase, and let W be the barrier wait. The pause contribution is approximately T_phase + W. If W is large, the phase is imbalanced or the barrier is slow. If T_phase is large and W is small, the phase is doing too much work per thread. The collector can adapt by changing region size, work-stealing granularity, or the number of threads. For the move phase, the critical path is the longest chain of dependencies. The collector can measure the depth of the dependency graph and the number of ready regions per wave. If the waves are shallow, parallelism is limited. If the waves are deep, the collector is doing well.

Instrumentation must not itself become a straggler. Writing a log entry for every object would dominate the pause. The collector should sample or aggregate. Per-region counters are usually enough. The runtime can also use hardware performance counters to measure cache misses and remote NUMA accesses during compaction. Those counters can explain why a phase is slower than expected. The goal is not to collect data for its own sake, but to close the loop: measure, adjust, and verify that the next pause is shorter.

## Correctness invariants and debugging parallel compaction

Parallel compaction has a small set of invariants that must hold at every barrier. After the forwarding phase, every live object has exactly one forwarding pointer, and the forwarding pointer is within the compacted heap. After the update phase, every reference in every live object and every root points to a forwarded object. After the move phase, every live object resides at its forwarding address, and no live object remains in the old heap. The collector can assert these invariants in debug builds. The assertions are expensive, but they catch bugs that are otherwise invisible until the heap is corrupted.

Common bugs include double forwarding, where a thread reads a forwarding pointer that has already been overwritten by a moved object; stale forwarding, where a reference is updated with an old destination; lost updates, where two threads update the same reference; and torn header reads, where a thread reads a partially written forwarding pointer. The update phase is especially prone to lost updates if two threads scan the same object. The region partitioning must guarantee that each object is scanned by exactly one thread. If regions overlap or if work stealing duplicates a range, the collector can update a reference twice. That is usually harmless if the update is idempotent, but it can be harmful if the second update reads a forwarding pointer that has been cleared.

Debugging parallel compaction is easier with a deterministic test harness. The collector can run with one thread, then two, then many, and compare the resulting heap layout. It can also inject artificial delays at barriers to expose races. A stress test that allocates objects of random sizes, drops references randomly, and forces collection at random safepoints will find many bugs. The collector should also verify that the mark phase and the compaction phase agree on liveness. If an object is marked live but not forwarded, the forwarding phase has a bug. If an object is forwarded but not marked, the mark phase has a bug.

## Adaptive region sizing and feedback control

Static region sizing is a compromise. A size that works for a heap of small objects may be too small for a heap with large arrays, and a size that works for a large heap may be too coarse for a small heap. An adaptive collector can start with a default region size and adjust it based on observed live-byte distribution. If a region contains a large fraction of the live heap, the collector can split it before the forwarding phase. Splitting a region requires updating the region counters and recomputing the prefix sum, but that is cheap compared to the rest of the collection. The collector can also merge small regions to reduce the number of counters. The adjustment should be conservative and hysteretic, because changing region size changes the work distribution and can cause oscillation.

Feedback control can target a pause-time budget. If the measured pause is above the budget, the collector can increase the number of regions, reduce work-stealing granularity, or increase the number of collector threads. If the pause is below the budget, it can reduce overhead by using larger regions and fewer barriers. The controller should account for the fact that some phases are memory-bound and some are compute-bound. Adding threads to a memory-bound phase may not help. The runtime can use the instrumentation counters to decide which phase is the bottleneck and adjust accordingly. The result is a collector that does not just implement parallel mark-compact, but tunes it to the workload and the machine.

## Safepoints, handshakes, and thread state transitions

Stop-the-world collection requires all mutator threads to reach a safepoint. A safepoint is a point in code where the thread's state is known and its stack can be scanned. The runtime inserts safepoint polls at loop back edges, method returns, and allocation sites. When the collector wants to start, it sets a global flag and waits for all threads to observe it. Threads that are running in native code or blocked in the OS may not poll; the runtime must handle them via handshakes. A handshake is a per-thread request to stop. The thread may be in a state where it cannot respond immediately. The collector must wait for a bounded time, then either proceed with the thread in a known state or use a fallback. The pause time includes the time to bring all threads to a safepoint. If one thread is stuck in a long-running native call, the pause can be long. Parallel compaction cannot begin until the handshake completes.

The thread state machine has states such as running, in-native, blocked, safepoint-requested, and safepoint. Transitions must be atomic. The collector uses a per-thread flag and a global counter. When a thread reaches a safepoint, it increments the counter and waits on a condition variable. The last thread to arrive signals the collector. The collector then proceeds. The reverse transition releases threads. The cost of the handshake is the latency of the slowest thread. To reduce it, runtimes use safepoint polling with a cheap load and branch. The poll must be placed so that no thread can run for too long without checking. The compiler must not hoist the poll out of a loop. The poll also must not be too frequent, or it hurts throughput. The trade-off is between safepoint latency and mutator overhead.

For parallel compaction, the handshake is a global barrier before the mark phase. The mark phase itself may use parallel threads, but the mutator threads are already stopped. The collector threads are separate. The handshake latency is part of the pause, but it is not part of the compaction work. Instrumentation should separate handshake time from phase time. If handshake time dominates, the runtime may need more safepoint polls or a different thread suspension mechanism. Some runtimes use thread-local handshakes that allow a thread to continue running while its stack is scanned, but that requires read barriers and is beyond stop-the-world compaction. For STW, the handshake is a necessary cost.

## Interior pointers, derived pointers, and compressed references

Precise tracing usually assumes that every reference points to the start of an object. Some runtimes allow interior pointers, which point into the middle of an object, often into an array or a string. Interior pointers complicate forwarding because the collector must find the object header from the interior address. The runtime may require that interior pointers be derived from a base pointer that is also live. A derived pointer is a base pointer plus an offset. The collector must update the base pointer and recompute the derived pointer. If the derived pointer is stored in a register or stack slot, the stack map must identify the base and the offset. If the offset is not known, the collector cannot safely update the derived pointer. Some runtimes forbid interior pointers except in well-defined contexts, such as JNI critical sections. In those contexts, the object may be pinned or the pointer may be converted to a handle.

Compressed references are another complication. A compressed oop is a 32-bit offset from a heap base. The collector must decompress to a full address, look up the forwarding pointer, and recompress. The compression scheme may use a shift, so the low bits of the compressed value are not zero. The collector must preserve the shift when recompressing. If the heap base changes after compaction, the compression base must be updated. In some runtimes, the heap base is fixed for the lifetime of the process, so compression is stable. In others, the heap may be relocated, and the compression base must be recomputed. The forwarding pointer itself may be stored as a compressed value to save header space. That works if the compacted heap fits within the compressed range. If not, the collector needs a full-width forwarding pointer for some objects.

Pointer tagging uses low bits of a reference to store metadata. The collector must mask off the tag before using the address and restore it after forwarding. If the tag encodes the object's type or a hash code, the collector must not lose it. The forwarding pointer write must be atomic with respect to the tag. A common approach is to store the forwarding pointer in a separate header word, leaving the tagged reference untouched. That avoids tag manipulation but costs header space. If the collector uses a side table, the tag is irrelevant because the table is indexed by the untagged address. The side table lookup must mask the tag first. The collector should document which bits are tags and ensure that the forwarding address is aligned so that its low bits are zero. If the forwarding address is not aligned, the tag bits may collide with the address bits.

Handles and JNI add another layer. A handle is a stable pointer to a slot that contains a reference. The collector updates the slot, not the handle. Handles are roots, so they are updated during the update phase. If a native method holds a handle across a safepoint, the collector must ensure that the handle remains valid. Because the mutator is stopped, the handle cannot be used concurrently. But the native method may have cached the object address in a local variable. That local variable is not visible to the collector unless the native method registers it as a root. Runtimes that support native code must provide a way for native code to pin objects or to use handles exclusively. Pinning prevents compaction of the pinned object. The collector must either skip pinned objects during compaction or move them to a non-moving space. Skipping creates holes; moving to a non-moving space requires a separate heap. Both options add complexity to the forwarding protocol.

## Hybrid and generational compaction

Many production runtimes use generational collection. Young objects are allocated in a nursery and collected by copying. Old objects are promoted to an old generation. A full collection may use mark-compact on the old generation. The combination changes the parallel compaction problem. The young generation can be collected independently with parallel evacuation, which is simpler. The old generation compaction must handle references from the young generation and from the old generation. Remembered sets and card tables track old-to-young references. During a full collection, the collector must scan the remembered sets as roots. The remembered sets may be large and irregular, so parallel scanning is important. The collector can partition the card table by region and have each thread scan its cards. A card may contain multiple references, so the work is not uniform. The collector can use a work queue of cards and steal when idle.

Generational compaction also allows incremental compaction. The collector can compact only a subset of the old generation, leaving the rest in place. That reduces pause time but creates a mix of compacted and non-compacted regions. References to non-compacted objects do not need forwarding pointers. The collector can use a forwarding function that returns the original address for objects in non-compacted regions. The update phase must check whether a target is in a compacted region. That check adds a branch per reference. The collector can optimize by storing a region map that indicates whether a region is compacted. The map can be a bitmap or a byte array. The branch is predictable if most references point to non-compacted regions, but it can hurt if the mix is even.

Hybrid compaction can also combine sliding and non-sliding compaction. For example, the collector can slide small objects and leave large objects in place. That avoids the large-object copy problem and reduces the critical path. The non-moving large objects must be marked as pinned. References to them are not updated. The forwarding function returns the original address. The collector must ensure that the large objects do not overlap the compacted region. If they do, the sliding compaction must skip over them, leaving holes. Those holes can be filled by later allocations or by a subsequent compaction. The trade-off is between pause time and fragmentation. If large objects are rare, the fragmentation is small. If they are common, the heap may become fragmented. The collector can periodically compact large objects during a longer pause or a concurrent phase.

Generational collectors also have to handle promotion. During a young collection, live objects are copied to the old generation. If the old generation is being compacted at the same time, the promotion must be coordinated. In a stop-the-world full collection, the young generation is usually collected first, then the old generation. The young survivors are promoted into the old generation before old-gen compaction. That means the old-gen compaction sees the promoted objects as live. The promotion itself can be parallelized with thread-local allocation buffers. The old-gen compaction then compacts the entire old generation, including the newly promoted objects. The order matters: promotion must complete before forwarding computation, because the promoted objects need forwarding pointers. The collector can overlap promotion with old-gen marking if the marking is concurrent, but in a stop-the-world collector the phases are serial.

A further refinement is to compact only the regions with the highest dead-byte density. The collector computes a density metric per region during marking. Regions above a threshold are compacted; regions below are left in place. The forwarding phase then computes destinations only for compacted regions. The update phase must consult the region map for every reference. The move phase schedules only the selected regions. This approach bounds the pause by limiting the amount of live data that moves. The cost is that the heap may not become fully dense. Over multiple collections, the collector can rotate which regions are compacted, eventually compacting the entire heap. The rotation policy can be based on region age, allocation rate, or a simple round-robin. The trade-off is between pause time and memory efficiency. A collector that compacts too little may waste memory; one that compacts too much may have long pauses. The right balance depends on the application's allocation pattern and the runtime's pause-time budget.
