# Parallel Incremental View Maintenance with Differential Dataflow: Collections, Frontiers, and Arrangements

Materialized views are a deceptively simple idea. A query defines a derived relation, and the system stores that relation so readers do not pay the cost of recomputing it. The interesting part begins when the base data changes. A view over a join of three relations, followed by a grouped aggregation and a filtered distinct, cannot in general be refreshed by appending a few rows to the output. A single deletion on the input may invalidate a group, a single insertion may change a join multiplicity, and a recursive query may require a fixpoint to be repaired rather than recomputed. Incremental view maintenance is the discipline of turning input changes into output changes without treating every change as an invitation to rerun the whole query.

There are several established approaches. Classical database systems use trigger graphs, delta rules, and maintenance queries generated from algebra. Stream processors use stateful operators, changelogs, and watermarks. Datalog engines use semi-naive evaluation and provenance. Differential dataflow occupies a useful point in this design space: it generalizes incremental computation over collections whose elements can be inserted or removed, it gives the runtime an explicit model of computational progress, and it represents operator state as indexed collections that can be shared, merged, and compacted. The model is especially relevant to parallel systems because it separates three concerns that are often entangled: the logical definition of a dataflow, the physical partitioning of state and work, and the progress protocol that determines when an operator can emit results or discard state.

This article examines differential dataflow as a substrate for parallel incremental view maintenance. The focus is not on a particular language binding or deployment topology. It is on the mechanics that matter when an engineer has to reason about correctness, memory growth, shuffle volume, skew, and determinism. The assumptions are modest but worth stating. Inputs arrive as changes: positive differences for insertions, negative differences for deletions, and possibly larger integer multiplicities for bag semantics. Queries are expressed as dataflow graphs over collections. Workers execute partitions of those collections. Operators may maintain state across time. We are interested in systems that can process both bounded historical data and unbounded streams under the same semantics, because that is where incremental maintenance becomes operationally valuable.

## The Maintenance Problem in Collection Terms

Let a relation be a multiset of records. A change to a relation is itself a collection of records annotated with an integer difference. An insertion of record `r` is `(r, +1)`. A deletion is `(r, -1)`. Replacing a row can be represented as a retraction followed by an insertion, or as a pair of differences that consolidate to the net effect. This bag semantics is deliberate. SQL's default relational model eliminates duplicates, but analytical workloads often need multiplicities, and bag semantics composes more cleanly with joins. A distinct operator can be layered on top when set semantics is required, but it introduces its own state and its own progress obligations.

For a join, the delta rule is the familiar product rule from calculus. If `A` and `B` are collections and `V = A join B`, then a change `dA` contributes `dA join B`, a change `dB` contributes `A join dB`, and the cross term `dA join dB` accounts for records inserted on both sides at the same logical time. In a batch system, one can compute the view from scratch. In an incremental system, the cost of a change should be proportional to the change and the state it touches, not to the size of the entire input. That is the promise. The bill arrives in the form of maintained state: to join `dA` against `B`, the system needs an index over `B` that is valid at the relevant time. If `B` has changed many times, the index must represent multiple versions or be compacted in a way that preserves the ability to answer future deltas.

Aggregation makes the state question sharper. A grouped sum over a multiset can be maintained by adjusting group totals as differences arrive. A grouped min or max cannot be maintained by a single scalar if deletions are allowed; the system needs enough information to recover the next extreme value, or it must recompute the group. A distinct operator must track multiplicities per value and emit a positive difference only when a value transitions from zero to one, and a negative difference only when it transitions from one to zero. Recursive queries add fixpoint iteration: a change to an edge in a transitive closure can trigger a bounded cascade of derived changes, and the runtime must know when the cascade has quiesced. These are not incidental implementation details. They determine whether incremental maintenance is a general-purpose systems primitive or a collection of query-specific tricks.

## Collections, Times, and Differences

Differential dataflow's core representation is a collection of triples `(data, time, diff)`. The `data` is the record. The `time` is a logical timestamp, partially ordered in general and often a product of an outer epoch and an inner iteration counter. The `diff` is an integer multiplicity. A collection is not a set of current rows; it is a set of changes indexed by logical time. The current value at a time is obtained by accumulating all differences at times not greater than that time, subject to the partial order. This is a multi-version representation, but it is not a version per transaction in the usual database sense. It is a representation of the dataflow's own computation history, and the runtime is free to consolidate and compact it as long as it preserves observable behavior for times that may still be produced.

The use of integer differences has two consequences. First, updates compose algebraically. Two changes to the same record at the same time can be summed. A positive and negative difference for the same record can cancel. Consolidation is therefore not an optimization bolted onto the side; it is part of the semantics of the collection. Second, the representation admits bag semantics without a separate duplicate-tracking layer. A record with difference `+3` is three copies, and a later `-1` leaves two. Joins multiply differences, filters pass them through, and aggregation folds them into group state. This uniformity is what allows a single operator library to serve relational queries, graph algorithms, and iterative computations.

Logical times are partially ordered because dataflow graphs can branch and merge, and because iteration introduces times that are not totally ordered with respect to the outer computation. A timestamp in an iterative dataflow might be `(epoch, iteration)`, where `epoch` advances with input batches and `iteration` advances within a fixpoint loop. The partial order allows the runtime to say that a result at `(5, 2)` is not necessarily before or after a result at `(6, 0)` unless the frontier rules establish that relationship. This matters for correctness. If an operator emits a difference at a time that is still subject to future changes, downstream operators must not treat the current accumulation as final. The frontier is the runtime's way of communicating which times are complete.

## Timely Frontiers and Progress

Timely dataflow supplies the progress protocol. Each operator holds capabilities, which are promises that it may still produce data at certain times. A frontier is a lower bound on the times at which future data may arrive. When all capabilities for a time are dropped, the frontier can advance. Operators downstream can then know that no further differences will arrive for times behind the frontier, and they may finalize outputs, discard state, or compact traces. This is not the same as event-time watermarking in a stream processor, although the two ideas are often compared. A watermark usually summarizes the progress of an external event-time domain. A timely frontier summarizes the progress of the dataflow itself: which internal logical times may still be produced by upstream operators. The distinction matters because a dataflow can have multiple nested iterations, and the frontier must track all of them without collapsing them into a single wall-clock or event-time timestamp.

In a parallel deployment, frontiers are exchanged among workers. Each worker owns a partition of the data and a set of capabilities. Progress messages are small compared with data messages, but they are synchronization points, and synchronization costs are real. A worker cannot advance its frontier merely because its local input is idle; it must know that no other worker can produce data for the relevant times. This is the price of coordination. The benefit is that operators can make safe decisions about state reclamation and output finalization without centralizing all data. The design is closest to a distributed progress tracker rather than a global barrier. The runtime attempts to keep progress messages off the critical path of data exchange, but a system with many workers and frequent iterations will still spend time advancing frontiers.

Frontiers also constrain consolidation. An arrangement may hold differences for many times. If the frontier has advanced past a range of times, the arrangement can merge those times into a single accumulated batch, provided the operator does not need to distinguish them later. If the frontier has not advanced, merging is still possible in some cases, but it must preserve the ability to answer queries at the un-advanced times. This is why arrangement compaction is tied to progress. Without a frontier, a stateful operator cannot know when it is safe to forget history. With a frontier, it can make a principled trade between memory and recomputation. The trade is not free: compacting too aggressively forces future deltas to touch larger merged batches, while compacting too lazily grows memory and slows lookups.

## Data-Parallel Operators and Exchange

The parallel execution model is data parallelism over collections. Records are partitioned across workers, typically by hash or range. Local operators such as map, filter, and project can run without coordination because they transform each record independently. Stateful operators that need to see all records with the same key, such as reduce, join, and distinct, require an exchange: records are repartitioned so that all records for a key land on the same worker. Exchange is an all-to-all communication step. It is also where many performance problems become visible. A hash function that distributes keys evenly in a batch workload may concentrate updates in a stream workload if the workload is skewed. A hot key can serialize an otherwise parallel operator, and no amount of worker count will fix the fact that one key's state must be updated in order.

There are standard mitigations, but each has a cost. One can partition hot keys further and aggregate partial results, which adds a second stage and more state. One can replicate small dimensions and broadcast them, which trades communication for memory. One can use range partitioning to keep related keys together, which improves locality for range queries but risks hotspots at range boundaries. One can detect skew at runtime and rebalance, which introduces coordination and data movement. Differential dataflow does not make these choices disappear; it gives a framework in which the choices are explicit. The collection abstraction says what must be computed. The partitioning strategy says where it is computed. The progress protocol says when it is safe to emit.

Determinism deserves attention. Integer differences consolidate exactly, so the logical result of a query is independent of the order in which differences arrive, as long as the same multiset of differences is processed. That is a strong property. It does not mean that every physical execution is deterministic. Floating-point aggregation is not associative, and a reduce operator that sums floats in arrival order can produce different results across runs. A system that promises reproducible outputs must either avoid floating-point aggregation, use a deterministic reduction tree, or carry enough provenance to reconcile results. The same caution applies to operators that depend on iteration order, such as some graph algorithms that pick a representative. Differential dataflow's algebra is exact for integers and for well-defined multiset operations; it is not a license to ignore numerical non-associativity.

Iteration is another parallel design point. A transitive closure or a page-rank-style computation is expressed as a loop with a feedback edge. Each iteration advances the inner timestamp. Differences produced in one iteration feed the next, and the frontier determines when the loop has quiesced. In parallel, workers may be at different iterations for different keys, and the runtime must not let a worker finalize a key while another worker may still contribute a difference at an earlier time. This is where the product-order timestamps earn their keep. A total order would force a global barrier per iteration and serialize the computation. A partial order allows independent progress where the dataflow permits it, at the cost of more complex progress tracking.

## Arrangements as Shared, Versioned Indexes

An arrangement is an indexed collection. It maps a key to the values associated with that key, each annotated with a time and a difference. Arrangements are the materialized state behind joins, reductions, and distinct. A join of two collections can be implemented by arranging both inputs by key and then probing one arrangement with the other. A reduce can be implemented by arranging the input by key and maintaining accumulated group state. The arrangement is not merely a cache. It is the operator's durable view of history, and it must be correct for all times that have not yet been finalized.

Arrangements are also shareable. If two queries join the same base relation by the same key, they can share the arrangement rather than each maintaining a private copy. Sharing reduces memory and consolidation work, but it couples the queries' lifetimes. An arrangement cannot be discarded until every consumer has advanced its frontier past the times it needs. This creates a form of garbage collection at the dataflow level. The runtime must track arrangement references, frontier progress, and batch compaction. A query that is slow or stalled can pin state for other queries. A query that is abandoned must release its capabilities and references so that the arrangement can be reclaimed. These are systems concerns, not query-language concerns, and they are often the difference between a prototype and an operable service.

The internal structure of an arrangement is a sequence of batches. Each batch holds sorted keys and accumulated differences. New updates are merged into batches, and batches are compacted as the frontier advances. The compaction policy controls a three-way trade among memory, lookup cost, and update cost. Many small batches make updates cheap but lookups expensive and memory overhead high. One large batch makes lookups efficient but updates costly, because a small delta may force a merge into a large sorted structure. A tiered policy keeps a small hot batch for recent updates and periodically merges it into larger cold batches. This is reminiscent of log-structured merge trees, but the comparison has limits: an arrangement is indexed by logical time and must preserve differences for un-finalized times, whereas an LSM tree is usually optimized for current-state reads and writes. The correctness requirements are different, and so are the compaction triggers.

Arrangement sharing also interacts with parallelism. If an arrangement is partitioned by key, each worker owns a shard. A shared arrangement must be accessible to multiple operators, possibly on different workers. A local sharing strategy avoids network traffic but may duplicate state across workers. A global sharing strategy saves memory but requires remote probes or a shuffle to the owner. Most systems choose a hybrid: partition by key, colocate operators that use the same key, and exchange only when the dataflow requires a different partitioning. The choice is visible in tail latency. A remote probe to a hot shard can dominate an otherwise cheap delta. Colocation reduces that latency but constrains the scheduler and can create resource hotspots.

## The Cost Model You Cannot Avoid

Incremental maintenance is often described as work proportional to the change. That statement is true only under assumptions. The work for a delta is proportional to the number of affected records, the number of operators that must be traversed, the state lookups those operators perform, and the consolidation and exchange costs incurred along the way. If a deletion touches a group whose state is a large arrangement batch, the lookup may touch more memory than the delta itself. If a join key is hot, the delta may serialize on one worker. If a query has a deep dataflow with many arrangements, a single input change may fan out into many state probes. The cost model is therefore closer to a graph traversal than to a row count. Engineers who plan capacity by input rate alone will be surprised by state size, compaction debt, and shuffle amplification.

The communication cost is similarly structural. A map or filter adds no exchange. A join adds an exchange for whichever side is not already partitioned correctly. A reduce adds an exchange by group key. An iterative operator adds a feedback path that may exchange every iteration. Each exchange is a potential all-to-all shuffle, and each shuffle is bounded by the slowest worker. Parallel speedup is therefore limited by skew, by the critical path through stateful operators, and by the frequency of frontier advancement. The frontier messages are small, but they are synchronization. A pipeline that advances frontiers every few records will spend more time coordinating than computing. A pipeline that batches updates reduces coordination overhead but increases latency and the size of each consolidation step. There is no universal setting; the right batching interval depends on the query's latency target and the skew of its keys.

Memory is the third axis. Arrangements retain history until the frontier permits compaction. A system with a slow consumer, a long-running iterative query, or a shared arrangement pinned by an abandoned query can accumulate state that is no longer useful to anyone. The runtime needs a reclamation story: reference counting, lease-based frontiers, or explicit cancellation that propagates through the dataflow. Without one, incremental maintenance degrades into a memory leak with good semantics. With one, the system can reclaim aggressively and accept recomputation when a late query asks for an old time. The trade between retention and recomputation is a policy decision, and it should be visible to operators rather than hidden in a default.

## Design Rules for Parallel Incremental Views

A few rules follow from the mechanics. First, define the update semantics before choosing an operator library. Bag semantics with integer differences is composable; set semantics with distinct requires explicit multiplicity state; non-monotonic aggregates require either enough state to recover after deletion or a recomputation path. Second, make the frontier part of the design, not an implementation detail. If an operator cannot advance its frontier because it holds a capability, it will pin state and block compaction. Third, treat arrangements as first-class shared resources. Their partitioning, sharing, and compaction policies determine memory and tail latency more than the query text does. Fourth, measure exchange volume and skew, not just throughput. A parallel dataflow that looks balanced by record count can be unbalanced by key frequency. Fifth, decide how deterministic outputs must be. Integer differences give exact multiset semantics, but floating-point reductions and order-sensitive operators need explicit treatment.

These rules are not specific to one runtime. They apply to any system that tries to maintain derived views under changes while executing across workers. Differential dataflow is valuable because it makes the rules explicit in its types and its progress protocol. It forces the designer to say what a difference means, when a time is complete, and where state lives. That explicitness is the difference between an incremental system that can be operated under load and one that merely works on a static snapshot. The remaining sections will examine operator-level patterns for joins, distinct, and iterative queries, then turn to scheduling, failure recovery, and the practical question of when incremental maintenance is worth its state.

## Join Patterns Under Differential Updates

A join is the operator where incremental maintenance stops being a local adjustment and becomes a graph traversal over state. The algebraic delta rule is simple, but the physical plan determines whether a small input change touches a small arrangement batch or fans out across an entire partition. In a differential dataflow, a binary join is typically implemented by arranging both inputs by the join key and then probing one arrangement with the other. The arrangement is keyed, sorted, and annotated with times and differences. When a delta arrives on the left input, the operator exchanges it by the join key if necessary, then probes the right arrangement for matching keys. The result is a collection of differences that carry the join multiplicity. A delta on the right input does the symmetric operation. If both sides change at the same logical time, the cross term must be computed as well, because an insertion on the left and an insertion on the right can create a new joined record that neither side's delta alone would produce.

This binary view extends to multiway joins through composition, but the shape of the join tree matters. Consider a query that joins `A`, `B`, `C`, and `D` on a chain of keys. A left-deep plan joins `A` with `B`, then with `C`, then with `D`. A delta on `A` must flow through every join, probing the arrangements for `B`, `C`, and `D` in sequence. A delta on `D` may need to probe a large intermediate arrangement built from `A`, `B`, and `C`. The number of arrangement probes per delta is not a constant; it depends on where the delta enters the tree and how many intermediate results are materialized. A bushy plan can reduce the depth for some deltas while increasing the number of arrangements that must be maintained. There is no universally best shape. The right choice depends on which inputs change most often, how selective the join keys are, and whether the intermediate results are themselves shared by other queries.

Differential dataflow's arrangement sharing changes the calculus. If two queries join the same relation on the same key, they can share the arrangement for that relation. A delta then updates one arrangement and both queries probe it. This is a significant saving in memory and consolidation work, but it couples the queries. The arrangement cannot be compacted past a time that either query still needs, and it cannot be dropped until both queries release their capabilities. A long-running analytical query can therefore pin state for a low-latency operational query. Systems that share arrangements need a policy for isolation, or at least a way to observe which consumers are holding a frontier back. Without that visibility, a single slow consumer becomes a global memory problem.

Parallel joins add exchange to the picture. If the left input is partitioned by one key and the right input by another, the join requires a repartitioning so that matching keys land on the same worker. This is an all-to-all shuffle, and its cost is proportional to the number of records whose partitioning must change. A delta that touches many keys can be more expensive to shuffle than to join. A delta that touches one hot key can serialize on a single worker even if the cluster has many cores. The usual mitigation is to consolidate differences before exchange. Because a join is linear in each input, summing differences for the same key before the shuffle is semantically safe. If a source partition has accumulated `+100` and `-99` for the same join key, the exchange only needs to carry `+1`. This pre-aggregation reduces shuffle volume, but it requires a local arrangement or hash table at the source, and that state has its own memory cost. The trade is between network bandwidth and source-side memory, and it shifts with the update pattern.

Hot keys require more than pre-aggregation. If one key receives a large fraction of updates, partitioning by that key concentrates work on one worker. One response is to split the key into subkeys and maintain partial join results, then combine them. This adds a second aggregation stage and more state, but it can restore parallelism. Another response is to replicate the small side of the join and broadcast it, so that each worker can probe a local copy without exchange. This is effective for dimension tables that change slowly, but it fails when the replicated side is large or updates frequently. A third response is to detect skew at runtime and migrate a portion of the key's state to another worker. Migration is expensive and must respect the frontier; moving state while a delta is in flight can produce duplicates or lost differences. The safest approach is to make skew visible in metrics and to choose a partitioning strategy that matches the workload's key distribution, rather than assuming a hash function will be fair.

## Distinct, Aggregation, and Non-Monotonic State

Distinct is a small operator with a large state obligation. To maintain a distinct view over a multiset, the runtime must know how many times each value is present. A positive difference that takes a value from zero to one produces a positive output difference. A negative difference that takes a value from one to zero produces a negative output difference. Changes that keep the count above zero or above one produce no output. The operator is therefore a reducer keyed by value, with a count as its accumulator. In parallel, values are partitioned by hash, so each worker owns a disjoint set of counts. The operator is simple, but it cannot forget a value until its count is zero and the frontier has advanced past the times that could reintroduce it. A value that is deleted and reinserted many times will cause repeated state transitions, and each transition is a difference that must be propagated downstream.

Aggregation has a similar shape, but the accumulator depends on the aggregate. `sum` and `count` are incremental in the strict sense: a new difference adjusts the accumulator by a computable amount. `min` and `max` are not. If the current minimum is deleted, the operator cannot recover the next minimum from a single scalar. It needs a multiset of values per group, or an ordered index that supports deletion. A common implementation keeps a map from value to count for each group. The minimum is the smallest key with a nonzero count. Deletion decrements the count and removes the key when it reaches zero. This is correct and incremental, but the state per group is proportional to the number of distinct values, not to the number of groups. A group with millions of distinct values is expensive to maintain even if its output is a single number. The alternative is to recompute the group from its base data when the current extreme is invalidated. That trades state for computation, and the right choice depends on how often extremes are deleted and how large the groups are.

`top-k` and percentile aggregates are worse. A top-k view must maintain enough information to recover the k-th item after arbitrary deletions. A count map can do this, but the operator must scan or index the map to find the k-th nonzero value. An ordered arrangement keyed by value within the group supports efficient updates and ordered scans, but it is a heavier data structure than a count map. Percentiles require an approximation or a full distribution. If the view is maintained incrementally, the approximation must be mergeable and must support deletion. Many sketch structures support insertion and merge but not deletion, or they support deletion only with a companion structure that tracks counts. Differential dataflow does not eliminate this algorithmic difficulty. It provides a uniform way to express the differences and a frontier that says when a window of data is complete, but the operator author still has to choose a state representation that can answer the query after retractions.

Windowed aggregation adds a time dimension. A sliding window over event time can be represented by assigning each record a logical time that includes the window, or by maintaining per-window state and emitting differences when a window closes. The frontier is what makes window closure safe. Once the frontier advances past the end of a window, no further records can arrive for that window, and the operator can finalize its output and discard the window's state. If the frontier is delayed by a slow input partition, windows remain open and state accumulates. This is the same progress problem as stream processing, but expressed in the dataflow's own logical time rather than in an external watermark. A system that mixes event-time windows with iterative queries must track both the event-time progress and the iteration progress, and the frontier must be the meet of the two. Otherwise, a window may be closed while an iteration is still producing records that belong to it.

## Iterative Queries and Nested Frontiers

Recursive queries are where differential dataflow's time model earns its complexity. A transitive closure, a reachability query, or a fixed-point computation is expressed as a dataflow with a feedback edge. Each pass through the loop advances an inner timestamp, often a pair of an outer epoch and an iteration counter. A change to an edge enters the loop as a difference, joins with the current set of paths, and produces new paths. Those new paths feed back into the loop and may produce more paths. The loop terminates when no new differences are produced and the frontier advances past the current iteration. In a batch setting, this is a fixpoint computation. In an incremental setting, the same loop must handle retractions. Deleting an edge may invalidate a large number of derived paths, and those invalidations must propagate through the loop as negative differences.

The interaction between retractions and bag semantics is subtle. If a path can be derived in multiple ways, its difference is the sum of the derivations. Deleting one edge removes one derivation, but the path may still exist through another. The runtime must not emit a negative difference for the path unless its total multiplicity drops to zero. This is why recursive queries often need a distinct or count layer on top of the recursive join. The join maintains derivation counts; the distinct operator converts counts to set membership. The combination is correct, but it is state-heavy. Every intermediate path and every derivation count must be retained until the frontier permits compaction. For dense graphs, the number of paths can be much larger than the number of edges, and the state can grow faster than the input.

Parallel iteration adds nested frontiers. Workers may be at different iterations for different partitions of the graph. A worker that has finished its local work cannot advance the global iteration frontier until all workers have finished, because a difference from another worker at an earlier iteration could still affect its results. This is a synchronization point, but it is not necessarily a full barrier. The timely progress protocol allows capabilities to be held per time, and the frontier advances when all capabilities for a time are dropped. If the dataflow is structured so that independent subgraphs have independent capabilities, they can progress at different rates. In practice, recursive queries often have a global feedback edge, and the iteration frontier advances in rounds. The cost of those rounds is the cost of progress messages plus the cost of any straggler that delays the frontier.

Skew is especially damaging in iterative queries. A high-degree vertex can dominate a join, and its state can be much larger than that of other vertices. If the graph is partitioned by source vertex, the worker owning a high-degree source does more work every iteration. If it is partitioned by destination, the same problem appears on the other side. Some systems use vertex-cut partitioning, where high-degree vertices are split across workers and their edges are replicated. This balances work but increases communication and state. Differential dataflow does not prescribe a partitioning strategy, but its exchange operator makes the cost visible. A designer can choose to partition by a key that spreads the high-degree vertices, or to pre-aggregate paths before exchange so that the shuffle carries counts rather than individual derivations. The latter is often effective because many paths share the same endpoints, and their differences can be summed before they cross the network.

## Scheduling and Failure Recovery in Parallel Maintenance

A parallel incremental view maintenance system is a scheduler as much as it is a query engine. The scheduler decides which workers host which partitions, when exchanges occur, how much batching to apply, and when to compact arrangements. Batching is the primary knob for progress overhead. If every input difference is processed immediately, the dataflow advances frontiers frequently, and the cost of progress messages can exceed the cost of computation. If differences are accumulated into larger epochs, the frontier advances less often, consolidation is more effective, and throughput improves. Latency suffers because a reader cannot observe the result until the epoch is processed. The right batching interval is a function of the query's latency target and the variance of input arrival. A system that exposes the epoch size as a policy can let operators choose between interactive and bulk maintenance.

Stateful operators should be colocated with the arrangements they probe. If a join operator is scheduled on a worker that does not own the relevant arrangement shard, every probe becomes a remote read. Colocation reduces network traffic but constrains the scheduler. It may force a particular partitioning of downstream operators, and it can create resource hotspots when one key is both hot and state-heavy. A scheduler that can migrate operators or arrangements in response to load is more flexible, but migration must be coordinated with the frontier. Moving an arrangement shard while it is being probed can produce inconsistent results unless the shard is quiesced or the migration is expressed as a difference stream. The latter is elegant but expensive: it turns a physical relocation into a logical data movement that must be consolidated and compacted like any other update.

Failure recovery is the least glamorous and most consequential part of the design. Arrangements are state, and state must survive worker failures if the view is to remain available. There are two broad strategies. The first is checkpointing: periodically persist arrangement batches, input offsets, and frontier information. On recovery, restore the latest checkpoint and replay input differences from the recorded offsets. The second is recomputation: discard the failed worker's state and rebuild it from the base data. Recomputation is simpler but can be much slower, especially for recursive queries with large intermediate state. Checkpointing is faster to recover but adds write amplification and coordination. A hybrid approach checkpoints large, stable arrangements and recomputes small, volatile ones. The choice depends on the cost of state reconstruction relative to the checkpoint interval.

Exactly-once semantics are essential for recovery. If an input difference is replayed after a failure, it must not be applied twice. Integer differences make this problem visible: applying `+1` twice produces `+2`, which is wrong. The system needs a durable input log with offsets, and the recovery procedure must resume from the last processed offset. If the input source cannot provide replayable offsets, the system must deduplicate using a unique identifier per difference. Deduplication itself requires state, and that state must be checkpointed or bounded by a time window. The frontier can help: once the frontier has advanced past a time, differences for that time are final, and deduplication state for that time can be discarded. This is another example of progress enabling reclamation.

Parallel recovery introduces the problem of partial state. If one worker fails, its arrangement shards are lost, but other workers may have already consumed differences that depend on those shards. The recovery procedure must either restore the failed shards to a consistent frontier or roll back the entire dataflow to a common checkpoint. Rolling back is simpler but can discard a large amount of work. Restoring a single shard requires that the shard's state be reconstructible from its own checkpoint plus the differences it has received since. If the shard was shared, its consumers must also be paused or rewound. This is a distributed garbage collection problem in reverse: instead of reclaiming state, the system must reconstruct it without violating the progress assumptions of its neighbors. Systems that treat arrangements as first-class shared resources need a first-class recovery story for them, not an afterthought.

## When Incremental Maintenance Earns Its State

Incremental maintenance is not free. It replaces recomputation with retained state, and retained state has memory, compaction, checkpointing, and coordination costs. The decision to maintain a view incrementally should be based on the ratio of update work to query work, the selectivity of the query, and the cost of recomputation. A view that is queried frequently and updated rarely is an obvious candidate. A view that is updated constantly and queried rarely may be cheaper to recompute on demand. A view with a large state and a small output, such as a distinct over a high-cardinality relation, may cost more to maintain than to rebuild. A view with a small state and a large output, such as a filtered projection, is almost always worth maintaining incrementally.

The shape of the update matters as much as the rate. An append-only workload is monotonic, and many aggregates can be maintained with simple accumulators. A workload with deletions forces the system to retain enough information to recover after retractions. A workload with updates that change join keys is effectively a deletion plus an insertion, and it touches both the old and new key's state. A workload with hot keys concentrates work and state on a few partitions. These properties are visible in the input differences, and a system can use them to choose a maintenance strategy. For example, it can maintain a view incrementally while deletions are rare, then switch to recomputation if the deletion rate crosses a threshold. The switch itself must be safe: the system must either drain the incremental state or rebuild it from a consistent snapshot.

A practical system should expose the cost model rather than hide it. Operators should report the size of their arrangements, the number of batches, the rate of compaction, the volume of exchange, and the age of the frontier. These metrics tell an operator whether a view is healthy or whether it is accumulating state that will eventually cause a latency spike. They also inform capacity planning. A cluster sized for input throughput may be undersized for state compaction, and a cluster sized for state may be idle during periods of low update volume. Incremental maintenance is a dynamic trade, and the system's observability should reflect that. The alternative is a view that works perfectly in a benchmark and fails in production when a single hot key or a stalled consumer pins an arrangement for hours.

The design rules from the earlier sections apply here as well, but they become economic rules. Share arrangements when the sharing saves more memory than the coupling costs. Batch updates when the latency budget allows. Partition by the keys that are both frequent and selective. Checkpoint the state that is expensive to rebuild. Recompute the state that is cheap to rebuild. The goal is not to maintain every view incrementally. The goal is to maintain the views whose incremental cost is lower than their recomputation cost, and to know which ones those are. Differential dataflow provides the primitives to express that choice: collections with differences, frontiers that define completeness, and arrangements that make state explicit. The remaining work is in the policies that decide when those primitives are used.

## Compaction as a Correctness-Preserving Rewrite

An arrangement is not a single immutable index. It is a sequence of batches, each of which is a sorted collection of keys mapped to value-time-difference triples. The runtime appends new batches for incoming differences and merges batches to control read and memory overhead. This process is often described as compaction, but the term can mislead if it suggests an ordinary storage optimization. In differential dataflow, compaction is a semantic rewrite: it changes the physical representation of a trace while preserving the accumulated collection for every logical time that may still be observed. The correctness condition is local and testable. For each key, for each time not behind the arrangement's effective frontier, the sum of differences in the compacted trace must equal the sum in the original trace. Differences that are zero can be dropped. Multiple batches containing the same key and time can be summed. Batches whose entire time range lies behind the effective frontier can be collapsed into a single accumulated batch, because no consumer can ask for an intermediate time within that range. The effective frontier is not the global dataflow frontier. It is the meet of the frontiers of all operators that hold a reference to the arrangement. A shared arrangement with one slow consumer has a more conservative effective frontier than a private arrangement with a single fast consumer. This is the first place where sharing becomes an operational liability rather than a memory win.

The physical layout of batches determines what compaction can do cheaply. A batch may be a sorted run with a sparse index over keys, or a radix-partitioned set of sorted runs. The sparse index allows a probe to skip blocks whose key range does not include the target key. The value-time-difference triples within a key are often stored as a small sorted list. If a key receives many updates, that list grows, and compaction must decide whether to merge it into a larger run or leave it as a hot delta. A tiered policy keeps a small in-memory hot batch and merges it into larger cold batches at exponentially increasing sizes. A leveled policy bounds the number of runs per level and rewrites more aggressively. A time-tiered policy groups batches by the logical time range they cover, which aligns naturally with frontier advancement. None of these policies is universally correct. The right choice depends on the ratio of point probes to range scans, the distribution of update frequencies, and the cost of rewriting cold data. A join that probes a few keys per delta benefits from a small hot batch and an accurate sparse index. A reduce that scans all values for a key benefits from large merged batches with sequential access.

Compaction scheduling is part of the dataflow's progress problem. A compaction job reads old batches and writes new ones. It must not retire an old batch while a reader is still probing it. The runtime therefore needs a reclamation discipline: reference counting per batch, epoch-based reclamation, or a lease tied to the frontier. If reclamation is too eager, a reader may observe a partially merged state. If it is too lazy, memory grows with the number of obsolete batches. The frontier helps, but it is not sufficient by itself. A reader may hold a capability for a time behind the frontier while still scanning an old batch. The runtime must distinguish between a capability that guarantees future output and a transient reference to physical state. The former affects compaction semantics; the latter affects memory reclamation. Conflating them leads either to unsafe compaction or to memory leaks. A robust implementation tracks both and exposes the difference in metrics.

Compaction debt is the accumulation of work that has not yet been performed. It is analogous to garbage collection debt, and it has similar symptoms: memory grows, read amplification increases, and latency becomes less predictable. A system that processes updates faster than it compacts will eventually spend all its time merging batches and none of its time serving queries. The remedy is backpressure or admission control. The dataflow can slow input ingestion when compaction debt exceeds a threshold, or it can prioritize compaction over low-priority updates. Backpressure must be applied at the source, not at the arrangement, because the arrangement cannot refuse a difference without violating the progress protocol. If a source holds a capability and cannot produce, it should drop the capability or delay its input; otherwise downstream operators will stall. This is another reason why capabilities must be managed explicitly. They are not merely bookkeeping; they are the mechanism that propagates backpressure through a dataflow.

## Capability Accounting in Nested Scopes

Timely capabilities are often introduced as tokens that operators hold and drop. The operational details matter. A capability is associated with a time and an operator instance. The frontier for a worker is the set of minimal times for which some capability exists. When a capability is dropped, the worker recomputes its local frontier and broadcasts updates to peers. The broadcast is not a full frontier each time; implementations send progress messages that summarize additions and removals. The protocol must handle duplicate messages, out-of-order delivery, and worker failure. A worker that receives a progress update cannot assume it has seen all prior updates. It must merge the update into its view of the peer's capabilities and recompute the frontier. This is a monotonic lattice: capabilities only decrease, and frontiers only advance. The monotonicity is what makes the protocol robust to message reordering. A late message that removes a capability cannot resurrect a time that has already been declared complete. If it could, downstream operators would have already finalized results incorrectly.

Nested scopes complicate the accounting because capabilities are not flat. A loop operator creates an inner scope with its own time domain. The outer scope holds a capability for the epoch; the inner scope holds capabilities for iteration times within that epoch. The loop may create new inner capabilities as long as the outer capability is held. When the inner scope has no more capabilities and no more differences to process, it drops its remaining inner capabilities, and the outer scope may advance. The rule is simple but easy to violate: an operator inside a loop must not hold an outer capability directly, or it will prevent the outer frontier from advancing even when the inner loop has quiesced. Instead, the loop operator should hold the outer capability and grant inner capabilities as needed. This hierarchical capability structure is what allows nested iteration to make progress without a global barrier per iteration.

The product order on timestamps creates a frontier that is an antichain, not a single number. A frontier might contain `(5, 3)`, `(6, 1)`, and `(7, 0)`. These times are incomparable: `(5, 3)` is not less than `(6, 1)` because the epoch is smaller but the iteration is larger. An operator that wants to know whether it can finalize a result at `(5, 3)` must check whether any frontier element is less than or equal to `(5, 3)`. If the frontier contains `(6, 1)`, that does not help, because a future difference at `(5, 4)` could still arrive and affect `(5, 3)`. This is why implementations store frontiers as antichains and use a partial-order comparison rather than a scalar watermark. It is also why progress messages are larger in nested dataflows. A scalar frontier is a single timestamp; an antichain can have multiple elements, and its size can grow with the number of independent branches in the dataflow. Systems that ignore this and collapse the frontier to a scalar will either stall progress or declare completion too early.

Capability leaks are the most common cause of frontier stalls. A leak occurs when an operator clones a capability and never drops the clone. The dataflow continues to function, but the frontier stops advancing, arrangements cannot compact, and memory grows. Leaks are difficult to diagnose because the dataflow may still produce correct results for a long time. The symptom is a growing gap between the input frontier and the operator's local frontier. Observability should therefore include per-operator capability counts and frontier lag. A capability count that does not decrease after an epoch is processed is a strong signal. A frontier lag that grows without bound indicates that some operator is holding a time that it no longer needs. Automated audits can help: at the end of an epoch, every operator should have dropped all capabilities for times that are strictly less than the current frontier, unless it has a pending difference for that time. If it has no pending difference, the capability is a leak.

Cancellation must also be capability-aware. When a query is cancelled, every operator in its dataflow must drop its capabilities. If cancellation merely stops reading input, operators will continue to hold capabilities and pin arrangements. The cancellation signal should propagate through the dataflow, and each operator should release its state and capabilities in a defined order. If the query shares an arrangement with another query, the shared arrangement must not be dropped until the other query's capabilities are considered. This is a reference-counting problem at the query level. A query registry can track which queries hold which arrangements, and a cancellation can decrement the reference count and trigger reclamation when it reaches zero. Without such a registry, shared arrangements are either never reclaimed or reclaimed while still in use.

## Operator Contracts and Verification

An incremental operator is not defined solely by a function from input collections to output collections. It is defined by a contract that says how it responds to differences over time. A useful contract has four parts. The first is the pointwise behavior: for any complete input collection at a time, the accumulated output at that time must equal the operator's non-incremental result on the accumulated input. The second is the difference behavior: for any input difference at a time, the operator must produce an output difference that, when accumulated, preserves the pointwise behavior. The third is the state invariant: any internal state the operator maintains must be sufficient to produce future differences and must not depend on times that have been finalized. The fourth is the progress obligation: the operator must drop capabilities when it can no longer produce output for a time. These four parts are independent, and a violation of any one produces a different class of bug. A pointwise bug gives wrong results even on a static dataset. A difference bug gives wrong results only after updates. A state invariant bug causes memory growth or incorrect retractions. A progress bug causes stalls or premature finalization.

Testing an incremental operator requires more than unit tests on static inputs. The most effective technique is differential testing against a batch implementation. The test harness generates a random sequence of insertions and deletions, applies them to the incremental dataflow, and after each epoch compares the accumulated view to a batch query on the current input. The comparison should be done at a frontier, not at an arbitrary moment, because the incremental view may not be complete until the frontier advances. The harness should also test retractions in isolation: insert a record, delete it, and verify that the view returns to its previous state. It should test duplicate insertions and over-deletions. Over-deletion is particularly valuable because it exercises the operator's behavior when a negative difference would make an accumulated count negative. In a well-formed input, that should not happen, but the operator should either reject the input or handle it in a defined way. Silent corruption is the worst outcome.

For recursive queries, differential testing must compare against a batch fixpoint, not a single batch query. The harness should compute the fixpoint on the current input and compare it to the accumulated output at the outer frontier. It should also test the effect of deleting an edge that participates in many derivations. A common bug is to emit a negative difference for a derived path when one derivation is removed, even though another derivation still supports the path. The batch comparison catches this because the batch fixpoint will still contain the path. The test should include graphs with cycles, multi-edges, and high-degree vertices. Cycles are important because they can cause the incremental loop to produce differences that cancel after several iterations. The frontier must not advance until the cancellation is complete.

Determinism deserves its own test. Integer differences consolidate exactly, so two runs that process the same multiset of differences at the same logical times should produce the same accumulated view. If the operator uses floating-point arithmetic, that guarantee is lost unless the reduction order is fixed. A test can run the same update sequence with different worker counts and partitioning strategies and compare the accumulated results. Differences indicate either non-associative arithmetic or an order-sensitive operator. The fix is not to forbid parallelism but to make the operator's reduction deterministic: sort keys before reducing, use a deterministic tree reduction, or represent values with an exact type. For top-k and percentile operators, ties must be broken by a deterministic secondary key. Otherwise, the view may contain one of several equally valid results, and consumers may see different results across runs.

Observability closes the loop between design and operation. The most useful metrics are frontier lag, capability count, arrangement batch count, compaction debt, exchange bytes per operator, and skew ratio by key. Frontier lag tells you whether progress is stalled. Capability count tells you whether an operator is leaking. Batch count and compaction debt tell you whether state is growing faster than it is being consolidated. Exchange bytes and skew ratio tell you whether parallelism is effective. A dashboard that shows these per operator and per query is more valuable than a global throughput number, because incremental maintenance failures are usually local: one hot key, one leaked capability, one shared arrangement with a slow consumer. The system should make those local failures visible before they become global outages.
