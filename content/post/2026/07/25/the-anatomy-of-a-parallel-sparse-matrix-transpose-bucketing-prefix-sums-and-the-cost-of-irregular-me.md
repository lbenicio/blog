# The Anatomy of a Parallel Sparse Matrix Transpose: Bucketing, Prefix Sums, and the Cost of Irregular Memory Access

Sparse matrix transpose is one of those operations that looks trivial on a whiteboard and becomes stubbornly difficult on a real machine. For a dense matrix, transpose is a blocked copy: you tile the matrix, load a tile into cache, and write it out in the opposite order. The hardware does not care much about the values; it cares about moving bytes in large, predictable bursts. For a sparse matrix, the nonzeros are the data, and their locations are dictated by the problem, not by the hardware. Transposing a sparse matrix means converting a row-oriented storage format into a column-oriented one, and that conversion is an irregular scatter. The scatter is the whole story.

This article is about the systems engineering of parallel sparse matrix transpose. We will assume the reader knows what a sparse matrix is and has seen compressed sparse row (CSR) and compressed sparse column (CSC) formats. We will not spend time on the mathematical definition of a transpose. Instead, we will focus on the mechanics: how to count, how to prefix-sum, how to partition work, how to avoid atomics when they hurt, and how to reason about memory traffic when the writes are scattered. The goal is not to present a single best implementation. There is no single best implementation. The goal is to expose the trade-offs so that you can choose an approach for your matrix, your hardware, and your downstream algorithm.

## Why transpose is not just a pointer swap

At first glance, transposing a sparse matrix in CSR to CSC looks like renaming arrays. In CSR, `row_ptr` has length `m + 1`, `col_ind` has length `nnz`, and `values` has length `nnz`. In CSC, `col_ptr` has length `n + 1`, `row_ind` has length `nnz`, and `values` has length `nnz`. The transpose of an `m x n` matrix is an `n x m` matrix. The nonzero count is unchanged. The values are unchanged. Only the indexing arrays change roles. So why is it hard?

The difficulty is that the output is not a simple permutation of the input arrays. In CSR, the nonzeros are grouped by row. In CSC, the nonzeros must be grouped by column. To produce the output, you must know where each nonzero belongs in the output. That requires counting how many nonzeros each column has, computing the starting offset for each column, and then scattering each input nonzero to its correct output position. The counting and offset computation are regular and parallelizable. The scatter is irregular. The scatter is where the performance goes.

There is also the question of ordering. In many CSR implementations, the column indices within a row are sorted. In many CSC implementations, the row indices within a column are sorted. If you transpose a matrix and expect the output to preserve that property, you cannot simply use atomic increments to assign output positions. Atomic increments give you unique positions, but they do not give you ordered positions. If thread A and thread B both write to column `j`, the order in which they increment the counter determines which row index ends up first. That order is nondeterministic. If your downstream algorithm relies on sorted indices for binary search or for merge-based kernels, you will need to restore the order. That restoration costs time and memory.

Transpose is also used in more contexts than people expect. Graph algorithms often store an adjacency list in CSR for outgoing edges and need CSC for incoming edges. Iterative solvers may need both `A * x` and `A^T * y`. Preconditioners such as incomplete LU factorization may need to work with both row and column views. Format conversion between libraries often requires a transpose. Symmetry detection and storage of only the upper triangle require a transpose to reconstruct the full matrix. In each case, the transpose is not the final computation; it is a preparation step. That means its cost is often hidden in a profile, but it can dominate if it is implemented naively.

## CSR and CSC: the two representations we are converting between

Let us fix notation. A sparse matrix `A` has `m` rows and `n` columns. It has `nnz` structurally nonzero entries. We store it in CSR with three arrays:

- `row_ptr`: an array of length `m + 1`. The nonzeros of row `i` are stored in positions `row_ptr[i]` through `row_ptr[i + 1] - 1`.
- `col_ind`: an array of length `nnz`. `col_ind[k]` is the column index of the `k`-th nonzero.
- `values`: an array of length `nnz`. `values[k]` is the value of the `k`-th nonzero.

The transpose `B = A^T` has `n` rows and `m` columns. In CSC, we store `B` with:

- `col_ptr`: an array of length `n + 1`. The nonzeros of column `j` of `A` are stored in positions `col_ptr[j]` through `col_ptr[j + 1] - 1` of the CSC arrays.
- `row_ind`: an array of length `nnz`. `row_ind[k]` is the row index of the `k`-th nonzero in CSC order.
- `values`: the same values as CSR, but reordered.

Notice that `col_ptr` for `A` is exactly the `row_ptr` for `B`. The transpose operation is therefore a conversion from CSR of `A` to CSR of `B`, where the roles of row and column are swapped. If you already have CSC of `A`, then transpose is just a conversion from CSC to CSR. The algorithms are symmetric. For the rest of this article, we will assume we are converting CSR of `A` to CSC of `A`, which is the same as CSR of `A` to CSR of `A^T`.

The key observation is that the output `col_ptr` is determined solely by the column counts of `A`. If we can compute the number of nonzeros in each column, we can compute `col_ptr` with an exclusive prefix sum. The output `row_ind` and `values` are determined by scattering each input nonzero to its column's region. The scatter order determines the order of `row_ind` within each column. If we process the input rows in increasing order, and for each row we process its nonzeros in increasing column order, then within each column the row indices will be increasing. That is the sequential invariant. Parallelism breaks it unless we take extra care.

## The sequential baseline: counting sort in disguise

The sequential transpose is a counting sort. It has three phases: count, prefix sum, and scatter.

Phase 1: Count the nonzeros per column.


for j = 0 to n-1:
    count[j] = 0
for i = 0 to m-1:
    for k = row_ptr[i] to row_ptr[i+1]-1:
        j = col_ind[k]
        count[j] += 1


Phase 2: Exclusive prefix sum to compute column offsets.


col_ptr[0] = 0
for j = 0 to n-1:
    col_ptr[j+1] = col_ptr[j] + count[j]


Phase 3: Scatter the nonzeros into the output arrays.


for j = 0 to n-1:
    next[j] = col_ptr[j]
for i = 0 to m-1:
    for k = row_ptr[i] to row_ptr[i+1]-1:
        j = col_ind[k]
        dest = next[j]
        next[j] += 1
        out_row_ind[dest] = i
        out_values[dest] = values[k]


This is `O(nnz + n)` time and `O(n)` extra space for `count` or `next`. The scatter writes to `out_row_ind` and `out_values` at positions determined by `next[j]`. If the matrix has random column indices, those writes are scattered across the output arrays. The read side is sequential: we read `col_ind` and `values` in CSR order. The write side is irregular. On a modern cache-based machine, the read side will stream at high bandwidth, but the write side will suffer from cache line underutilization, TLB misses, and write-allocate traffic. The sequential baseline is simple, but it is not necessarily fast.

The sequential baseline also preserves sorted order within columns. Because we process rows in increasing order, and within each row we process nonzeros in increasing column order, the `row_ind` values written to a given column are increasing. If the input CSR has sorted column indices, the output CSC will have sorted row indices. This is a useful property. Many parallel algorithms sacrifice it.

## Parallelizing the two-pass approach

The most direct parallelization is to parallelize the three phases. Phase 1 and phase 3 are the expensive ones. Phase 2 is a prefix sum over `n` elements, which can be parallelized with a standard scan, but it is often memory-bound and may not be the bottleneck unless `n` is very large.

Phase 1: Counting. We can partition rows among threads. Each thread processes a subset of rows and counts the columns it sees. The problem is combining the counts. If we use a single global `count` array and atomic increments, we get contention when many nonzeros share a column. If we use per-thread count arrays, we use `O(T * n)` memory, where `T` is the number of threads. For large `n`, that is unacceptable. A common compromise is to use per-thread counts for a block of columns, or to use a hierarchical scheme: each thread counts into a private array for a block of columns, then reduce the private arrays into a global count array. The reduction is a segmented sum. The trade-off is memory versus contention.

Phase 3: Scatter. After computing `col_ptr`, we need to assign each nonzero a unique destination. The simplest parallel approach is to use an atomic increment on `next[j]` for each nonzero. Each thread processes a subset of rows. For each nonzero, it does `dest = atomicAdd(&next[j], 1)`, then writes `out_row_ind[dest] = i` and `out_values[dest] = values[k]`. This is correct in the sense that every nonzero gets a unique destination, and the output arrays are filled. But it has three problems.

First, atomics on `next[j]` can be a bottleneck. If a column has many nonzeros, many threads will contend on the same counter. The contention serializes the scatter for that column. In the worst case, a dense column can make the parallel transpose slower than the sequential one.

Second, the order of `row_ind` within a column is nondeterministic. Threads interleave their atomic increments, so the row indices in a column may not be sorted. If the downstream algorithm expects sorted indices, you must sort each column after the transpose. That adds `O(nnz log nnz_per_col)` work, or `O(nnz)` if you use a counting sort per column, but it is still extra work.

Third, atomics generate memory traffic. Each atomic increment is a read-modify-write to a shared counter. The counter is likely in a cache line that is ping-ponged between cores. Even if the contention is low, the atomic operations themselves are more expensive than plain stores.

The two-pass approach can avoid atomics in phase 3 by computing per-thread offsets. After phase 1, we have global column counts. We can compute, for each thread and each column, how many nonzeros that thread will contribute. Then we can compute an exclusive scan across threads for each column. That gives each thread a starting offset for each column. Then each thread can scatter its nonzeros without atomics, because it knows exactly where to write. The cost is the extra scan across threads. If we have `T` threads and `n` columns, the scan requires `O(T * n)` work. For small `T`, this is fine. For large `T`, it can be expensive. We can reduce the cost by blocking columns: each thread only needs offsets for the columns it actually touches, or we can use a hierarchical scan over column blocks.

## Atomics, order, and the hidden cost of contention

The atomic approach is attractive because it is simple. It requires no per-thread count arrays, no cross-thread scan, and no extra memory. It is often the first implementation people write. It is also often the wrong implementation for matrices with skewed column counts.

Consider a matrix with one column that contains a large fraction of the nonzeros. This happens in graph adjacency matrices for high-degree vertices, in finite element matrices with a few dense columns, and in matrices from social networks. If many threads process rows that contain that column, they will all contend on the same `next[j]` counter. The atomic unit will serialize those increments. The rest of the matrix may be sparse, but the dense column becomes a serial bottleneck. This is a classic load imbalance problem, but it is hidden inside a single memory location.

There are several ways to mitigate this. One is to use per-thread local buffers for dense columns. Each thread accumulates its nonzeros for the dense column in a private buffer, then merges the buffers at the end. The merge can be parallelized by assigning each thread a contiguous range of the column's output region. This preserves order if the merge respects thread order. Another approach is to use a two-level counter: a global counter for the column, and per-thread sub-counters. Each thread increments its own sub-counter, and periodically flushes to the global counter. This reduces contention but adds complexity.

The order problem is deeper. Even if you avoid atomics, you may not preserve the sequential order. Suppose you partition rows among threads. Thread 0 processes rows 0-99, thread 1 processes rows 100-199, and so on. If each thread writes to its own region of the output column, the row indices within that column will be ordered by thread, but not necessarily by row. For example, thread 0 may write row 50 before row 10, depending on the order it processes its nonzeros. If you want sorted row indices, each thread must process its rows in increasing order and its nonzeros in increasing column order, and the output regions must be assigned in thread order. That is achievable with the per-thread offset approach: thread 0 gets the first block of the column, thread 1 gets the next block, and so on. Then the concatenation of thread blocks is sorted by row if each thread's block is sorted. This is a strong argument for the per-thread offset approach over atomics when sorted output is required.

## Memory access, cache lines, and the irregular write problem

The performance of sparse transpose is dominated by memory access, not by arithmetic. The counting phase reads `col_ind` sequentially. The scatter phase reads `col_ind` and `values` sequentially, but writes `out_row_ind` and `out_values` irregularly. The irregular writes are the problem.

A cache line is typically 64 bytes. If `values` are 8-byte doubles and `row_ind` are 4-byte integers, a cache line holds 8 values or 16 indices. In a dense transpose, you write full cache lines because you process a tile of columns and rows. In a sparse transpose, you write individual elements to positions determined by the column index. If the column indices are random, each write may touch a different cache line. The CPU may fetch the line before writing (write-allocate), which doubles the memory traffic for that write. The line may be evicted before the next write to the same line, so the next write fetches it again. The result is that the effective bandwidth for the scatter can be a fraction of the peak bandwidth.

There are several ways to improve locality. One is to sort the nonzeros by column before scattering. That is essentially what the counting sort does, but you can also bucket the nonzeros into column blocks. If you choose a block size that fits in cache, you can process one block at a time: gather all nonzeros whose columns fall in the block, then transpose them into a contiguous output region. This is a form of tiling for sparse matrices. The gather step is irregular, but it reads from the input; the scatter step writes to a contiguous region. The trade-off is that you need to store the gathered nonzeros somewhere, which uses memory and bandwidth.

Another technique is to use non-temporal stores for the output. Non-temporal stores bypass the cache and write directly to memory. They avoid write-allocate traffic, but they are only efficient if you write full cache lines. Sparse writes are partial, so non-temporal stores may not help unless you buffer a full line before writing. Buffering a full line requires knowing which elements belong to the same line, which is another form of bucketing.

NUMA adds another dimension. On a multi-socket system, memory is partitioned into nodes. A thread can access local memory faster than remote memory. If the output arrays are allocated on one node and written by threads on another node, the writes are remote. The first-touch policy of most operating systems means that the node that first writes a page owns it. If you initialize the output arrays in parallel with the same partitioning as the scatter, you can get good NUMA placement. If you initialize them sequentially, all pages are on one node, and half the threads will write remotely. The same applies to the `next` array and the count arrays. NUMA-aware allocation and first-touch initialization are not optional for large matrices.

## A note on scope

This article is not a survey of every sparse transpose algorithm. It is an attempt to build a mental model of the problem. The model has three parts: the format conversion, the parallel decomposition, and the memory system. The format conversion tells us what we need to compute: column counts, offsets, and a scatter. The parallel decomposition tells us how to divide the work: by rows, by columns, by blocks, or by buckets. The memory system tells us why the naive decomposition is slow: irregular writes, atomics, cache lines, and NUMA.

In the sections that follow, we will look at concrete implementations of these ideas. We will start with a shared-memory implementation using per-thread counts and a parallel prefix sum. We will then examine a bucketed implementation that trades extra memory for better locality. We will discuss how to handle sorted output without a post-sort. We will look at GPU implementations, where the irregular scatter is even more punishing because of the wide SIMT execution model. We will also consider distributed-memory implementations, where the transpose becomes a communication problem. Throughout, we will keep the trade-offs explicit: memory versus contention, order versus parallelism, and locality versus load balance.

## A shared-memory transpose with per-thread counts

The two-pass algorithm becomes concrete when we fix a row partition and a column-offset strategy. Suppose we have T threads and we partition the m rows into T contiguous ranges. Thread t owns rows [r_t, r_{t+1}). We want to compute, for every column j, the number of nonzeros contributed by each thread. If n is small enough that a dense array of length n fits comfortably in cache, each thread can maintain a private dense count array. The total memory is T * n * sizeof(index_t). For T = 64 and n = 1,000,000, that is 256 MB for 4-byte counts, which is too much. For n = 10,000, it is 2.5 MB, which is fine. The dense private count approach is the simplest and fastest when it fits.

When it does not fit, we have two options. The first is to use a sparse private count structure. Each thread keeps a list of (column, count) pairs, using a hash table or a sorted vector. The list is built by scanning the thread's rows. After the scan, the thread sorts its list by column. Then the global count array is built by merging the per-thread lists. The merge can be done in parallel by partitioning columns among threads, but it requires all per-thread lists. The second option is to block the columns. We choose a block size B, such that a dense array of length B fits in cache. Each thread maintains a private dense count array for the current column block. It scans its rows once for each block. That is, it reads the input T * (n / B) times? No, each thread reads its own rows once per block, so the total input read is T * (n/B) * (nnz/T) = nnz * (n/B). That is too much if n/B is large. Instead, we can scan the input once and, for each nonzero, increment the count for its column block in a per-thread dense array, and also record the nonzero in a per-block bucket. This is the bucketed approach we will discuss next. For the pure counting phase, a single pass with a hash table is often better than multiple passes.

Once the global column counts are known, we compute `col_ptr` with an exclusive prefix sum. A parallel prefix sum over n elements is a standard primitive. On a CPU, a work-efficient scan with two passes over the array is usually sufficient. The first pass computes block sums; the second pass scans the block sums and then scans each block. If n is large, the scan is memory-bound and may take a noticeable fraction of the total time. But it is regular and predictable, so it is rarely the bottleneck compared to the scatter.

The scatter phase is where the per-thread counts pay off. For each column j, we have a count c_t[j] for each thread t. We compute an exclusive scan over t for each j. That gives thread t a starting offset o_t[j] within the column's output region. Thread t then processes its rows in order. For each nonzero (i, j, v), it writes `out_row_ind[o_t[j]] = i`, `out_values[o_t[j]] = v`, and increments `o_t[j]`. No atomics are needed. The output region for column j is partitioned into T contiguous segments, one per thread. If the threads are ordered by their row ranges, and each thread processes its rows in increasing order, the concatenation of the segments is sorted by row. This is the key to preserving order without a post-sort.

The cost of this approach is the per-thread scan. If we store c_t[j] as a dense T x n array, the scan is O(T * n) work. For T = 64 and n = 1,000,000, that is 64 million operations, which is comparable to nnz for a moderately sparse matrix. But the scan is over a dense array, so it is cache-friendly and vectorizable. If T is large, we can reduce the cost by using a hierarchical scan: first scan over groups of threads, then within each group. Or we can use a sparse representation of c_t[j], only storing columns that thread t actually touches. The sparse scan is more complex but avoids work on columns with zero count for that thread. In practice, the dense per-thread scan is often acceptable for T up to a few dozen. For larger T, the bucketed approach is better.

## Bucketing by column blocks

The bucketed transpose trades extra memory and an extra pass over the data for better locality. The idea is to partition the columns into blocks of size B. We choose B so that the output region for a block fits in cache. For example, if the average number of nonzeros per column is small, a block of 1024 columns might occupy a few hundred kilobytes. The algorithm has three phases: count, bucket, and scatter.

Phase 1: Count the nonzeros per column and per column block. We can do this in a single pass over the input. For each nonzero (i, j, v), we increment `col_count[j]` and `block_count[j / B]`. The `col_count` array is used to compute the final `col_ptr`. The `block_count` array is used to allocate per-block buffers. If we want to avoid atomics, we can use per-thread counts and then reduce, as before. The block counts are small (n / B entries), so the reduction is cheap.

Phase 2: Bucket the nonzeros. We allocate a buffer for each column block. The size of the buffer is `block_count[b]` entries, where each entry stores a row index and a value. We then make a second pass over the input. For each nonzero, we compute its block `b = j / B` and append it to the buffer for block b. To append in parallel without atomics, we can use per-thread offsets within each block. We compute an exclusive scan of per-thread block counts, so each thread knows where to write its nonzeros in the block buffer. The writes to the block buffer are still scattered by block, but there are only n / B blocks, and each block is written by many threads. If B is large enough, the number of blocks is small, and the writes are more localized than the final scatter. Alternatively, we can use atomic increments on a per-block counter. The contention is lower because there are fewer blocks, but it can still be a problem if the matrix has a few dense column blocks.

Phase 3: Scatter each block. Now we process one column block at a time. The block buffer contains all nonzeros whose columns fall in that block. We count the nonzeros per column within the block. Since the block has only B columns, the count array is small and fits in cache. We compute an exclusive prefix sum over the B columns to get the offsets within the block. Then we scatter the nonzeros from the block buffer into the final output arrays. The destination for a nonzero in column j is `col_ptr[j] + offset_within_column`. The writes to the final output are now localized: all writes for a block go to a contiguous region of the output arrays, because `col_ptr` is monotonic and the block's columns are contiguous. This means we write full cache lines more often. The block buffer is read sequentially, so the read side is also efficient.

The cost of bucketing is the extra memory for the block buffers (nnz entries of row index and value) and the extra pass over the input. The input is read twice: once to count, once to bucket. The block buffer is written once and read once. The final output is written once. So the total memory traffic is roughly 2 * nnz * (sizeof(row) + sizeof(value)) for the input reads, plus nnz * (sizeof(row) + sizeof(value)) for the block buffer write and read, plus nnz * (sizeof(row) + sizeof(value)) for the final output write. That is about 4x the traffic of the two-pass algorithm, which reads the input once and writes the output once. But the two-pass algorithm's output writes are irregular and may cause write-allocate traffic that doubles or triples the effective traffic. If the bucketed approach achieves near-peak bandwidth on the final write, it can still win. The trade-off depends on the matrix's column distribution and the hardware's cache and memory system.

A refinement is to use multiple levels of bucketing. For very large n, a single level of blocks may still produce too many blocks to fit in cache. We can use a two-level scheme: first bucket by a coarse block, then within each coarse block, bucket by a finer block. This is analogous to radix sort. The number of levels is chosen so that the working set at each level fits in cache. The cost is more passes and more memory. In practice, one level is often enough for matrices that fit in a single node's memory. For matrices with billions of nonzeros, a distributed-memory approach is needed anyway.

## Preserving sorted order without a post-sort

Sorted row indices within each column are not always required, but when they are, the parallel transpose must be designed to produce them. The sequential algorithm produces sorted output because it processes rows in increasing order. In parallel, we can preserve this property by ensuring that the output positions for a column are assigned in row order. The per-thread offset approach does this if we follow two rules.

First, the row partition must be contiguous and ordered. Thread 0 gets the lowest rows, thread 1 gets the next, and so on. Second, the output regions within each column must be assigned in thread order. That is, thread 0 gets the first segment of the column, thread 1 gets the next, and so on. Then, if each thread processes its rows in increasing order and its nonzeros in increasing column order, the row indices written by thread 0 are all smaller than those written by thread 1, and within each thread's segment they are sorted. The concatenation is sorted.

The per-thread offset computation gives exactly this assignment. For column j, thread t's offset is `col_ptr[j] + sum_{s < t} c_s[j]`. If we compute the scan over threads in increasing thread order, the segments are ordered. The scatter then writes to the correct segment. No atomics are needed, and no post-sort is needed.

If we use atomics instead, the order is nondeterministic. We could still recover sorted order by sorting each column after the transpose. For columns with few nonzeros, an insertion sort or a small sorting network is cheap. For columns with many nonzeros, a parallel merge sort or a counting sort by row index is needed. The cost of sorting all columns is O(nnz log nnz_per_col) in the worst case, but it can be done in parallel. However, it adds another pass over the output, which may be expensive. In many cases, it is better to avoid atomics and preserve order during the scatter.

There is a middle ground: use atomics to get unique positions, but then perform a local sort within each column only if the column has more than a threshold number of nonzeros. For small columns, the probability of out-of-order writes is low, and the cost of sorting is negligible. For large columns, the cost of sorting is high, so it is better to use the per-thread offset approach. This hybrid strategy can be effective when the column count distribution is skewed.

Another approach is to use a merge-based scatter. Each thread writes its nonzeros for a column into a private buffer, already sorted by row. Then, at the end, the buffers are merged. The merge can be done in parallel by assigning each thread a portion of the output column and having it merge the appropriate prefixes of the private buffers. This is more complex but avoids the per-thread scan over all columns. It is essentially a parallel merge sort where the runs are already sorted. The cost is the merge, which is O(nnz) total if done efficiently. This approach is used in some GPU implementations, where each warp or block produces a sorted run.

## GPU considerations: warp-level scatter and segmented scans

On a GPU, the irregular scatter is even more punishing because of the SIMT execution model. A warp of 32 threads executes in lockstep. If the threads in a warp write to scattered addresses, the memory system must issue multiple transactions. If the addresses fall in different cache lines, the warp's store is split into many transactions, reducing effective bandwidth. The same applies to loads. The counting phase is less problematic because it reads `col_ind` sequentially, but the scatter phase writes `out_row_ind` and `out_values` at positions determined by the column index. If the column indices are random, each thread in a warp writes to a different cache line.

The standard solution is to use shared memory bucketing. Each thread block processes a tile of rows. It loads the nonzeros for those rows into shared memory, bucketed by column block. The threads then cooperatively write each bucket to global memory in a coalesced manner. Because the bucket for a column block is contiguous in the output, the writes can be arranged so that consecutive threads write consecutive addresses. This is the same idea as the CPU bucketed transpose, but the block size is chosen to fit in shared memory (typically 48 KB to 164 KB per SM). The shared memory buckets are filled using atomic increments in shared memory, which are fast but can cause bank conflicts. To reduce conflicts, the buckets can be padded, or the threads can use warp-level aggregation.

For counting, GPUs use parallel histogram techniques. A common approach is to have each thread block compute a local histogram in shared memory, then atomically add the local histogram to a global histogram. The local histogram avoids global atomics, which are slow. The global histogram is then used to compute `col_ptr` with a parallel prefix sum, such as `cub::DeviceScan`. The scatter phase can use `cub::DeviceScatter` or a custom kernel that uses the per-thread offset approach. Because GPUs have many threads, the per-thread scan over columns is expensive if done densely. Instead, GPUs often use a two-level approach: first compute per-warp or per-block counts for each column, then scan those counts, then scatter. The scan is done in shared memory for a block of columns, and the results are written to global memory.

Sorting the output is also more expensive on GPUs. If sorted order is required, it is usually better to design the scatter to produce sorted output directly. This means each thread block must process rows in order and write to its assigned segment of each column in order. The per-thread offset approach can be adapted to warps: each warp gets a segment of the column, and within the warp, the lanes write in order. This requires a warp-level scan over the counts for each column. Since a warp has only 32 lanes, the scan is cheap. The challenge is that a warp may touch many columns, so the per-column scan must be done for each column the warp touches. This can be done by iterating over the columns in the warp's bucket.

## Distributed-memory transpose: all-to-all as a sparse problem

In a distributed-memory setting, the matrix is partitioned across processes. A common distribution is by rows: each process owns a contiguous set of rows and stores them in CSR. To transpose the matrix, each process must send its nonzeros to the process that owns the corresponding column. If the columns are distributed by blocks, then each nonzero (i, j, v) must be sent to the process that owns column j. This is an all-to-all communication pattern.

The standard algorithm is a distributed counting sort. Each process first counts how many nonzeros it will send to each other process. This is a histogram over destination processes. The histogram is small (one entry per process), so it can be computed with a single pass over the local nonzeros. Then the processes exchange histograms using an all-to-all. After the exchange, each process knows how many nonzeros it will receive from each other process. It computes the receive offsets with a prefix sum. Then it sends the nonzeros using nonblocking sends and receives. The sends are irregular because the nonzeros are scattered across the local CSR arrays. To improve efficiency, the nonzeros can be buffered by destination process before sending. This is a form of bucketing by process. The buffer for each destination is filled in a first pass, then sent in a second pass. The receive side writes the received nonzeros into the local CSC arrays. The writes are again irregular, but they are localized by the sender's process.

The cost of distributed transpose is dominated by communication. The total volume of communication is nnz * (sizeof(row) + sizeof(value)), which is the same as the matrix size. If the matrix is large, this can be a significant fraction of the total runtime. The communication pattern is all-to-all, which can be inefficient on networks with limited bisection bandwidth. To reduce communication, one can use a 2D block distribution, where each process owns a block of rows and a block of columns. The transpose then only requires communication along one dimension. Alternatively, many algorithms avoid explicit transpose by using a distributed sparse matrix-vector multiply that can work with either row or column distribution, or by computing `A^T x` as a sequence of local operations and reductions. But when an explicit transpose is required, the distributed counting sort is the standard approach.

## The transpose as a permutation

The output of a sparse transpose is a permutation of the input nonzeros. For each input position `k`, there is an output position `p(k)`. The mapping is `p(k) = col_ptr[col_ind[k]] + rank(k)`, where `rank(k)` is the number of nonzeros before `k` in the input that have the same column. This rank is a prefix sum over a segmented sequence. If you process input in order, rank is easy; if parallel, you need to compute rank per element. Counting sort computes rank by counting per column and then, in scatter, using `next[j]` to assign ranks in encounter order. Parallel scatter with atomics assigns ranks in nondeterministic order. Per-thread offsets assign ranks in thread order. The permutation view clarifies that transpose is not a copy; it is a stable partition by column. Stability matters if you want sorted row indices. If you only need values, any permutation within column is fine. This view also suggests alternatives: if you have a parallel stable partition primitive, you can implement transpose as a stable partition of the `(column, row, value)` triples by column. A stable partition can be done with a counting sort or with a parallel merge. The cost is the same. But it highlights that the only data-dependent part is the column key. The row and value are payload. You can compress the key to a smaller type if `n` is small, or use a radix partition. If `n` is large, multiple radix passes may be needed. The permutation view also gives a lower bound: you must read every nonzero and write every nonzero, so the minimum memory traffic is `nnz * (sizeof(row) + sizeof(value))` in and out. Any algorithm that does more traffic must justify the extra work with better locality.

## Prefix sums: the quiet part of the transpose

The prefix sum over column counts is the part of the transpose that everyone assumes will be fast. It usually is, but its shape matters. A parallel exclusive scan over `n` elements can be implemented in several ways. The Hillis-Steele scan does `O(n log n)` work but has low depth, which is attractive on GPUs with many threads. The Blelloch scan does `O(n)` work but requires two passes and more synchronization, which is often better on CPUs. A work-efficient CPU scan typically uses a two-level approach: each thread scans a contiguous block in registers, writes the block sum, then one thread scans the block sums, and finally each thread adds its block offset. This is memory-bound for large `n`, but `n` is usually much smaller than `nnz`. The exception is a matrix that is nearly diagonal, where `n` and `nnz` are comparable. In that case, the scan can dominate, and the transpose becomes a scan problem rather than a scatter problem.

The more interesting scan is the one over threads for each column. The per-thread offset approach needs, for every column `j`, an exclusive scan of the per-thread counts `c_t[j]` over `t`. If stored densely as a `T x n` array, this is `O(T * n)` work. That is fine for small `T`, but it becomes expensive as `T` grows. A sparse segmented scan can do `O(nnz + n)` work by only scanning the columns that each thread actually touches. The implementation is more complex: each thread sorts its `(column, count)` pairs by column, then the counts are merged across threads in column order. The merge is a segmented scan where segment boundaries are columns. This is essentially a parallel merge of sorted lists. It avoids the dense `T x n` array but requires sorting or hashing per thread. For matrices with many columns and many threads, the sparse scan is often faster because it does not touch columns that a thread never sees.

There is also a two-level scan that is a compromise. Threads are grouped into small teams. Within each team, the counts are scanned densely. Across teams, the team sums are scanned. This reduces the dense work to `O((T / team_size) * n)` and keeps the scan simple. The team size is chosen so that the dense array fits in cache. This is the same hierarchical idea used in parallel prefix sums for large arrays. The scan is regular and vectorizable, so it is rarely the bottleneck unless the matrix is extremely skewed or `n` is very large. But it is a synchronization point: the scatter cannot begin until the scan is complete. On a CPU, that barrier costs a few microseconds. On a GPU, it costs a kernel launch or a grid-wide sync. For small matrices, the barrier can be a significant fraction of the total time. Fusing the scan with the scatter is difficult because the scatter needs the final offsets. You can use a single-pass approach with atomics, but then you lose order. The scan is the price of determinism and order.

## What to measure: counters, traffic, and the roofline of a scatter

Sparse transpose is memory-bound, so the first measurements should be memory counters. On a CPU, `perf stat` can report cache misses, LLC load and store misses, and TLB misses. The store misses are especially important. A naive scatter writes to `out_row_ind` and `out_values` at positions determined by the column index. If the column indices are random, each write may touch a different cache line. The CPU may fetch the line before writing, which doubles the traffic for that write. If the line is evicted before the next write to the same line, the next write fetches it again. The result is that the effective bandwidth for the scatter can be a fraction of the peak bandwidth. The `LLC-store-misses` counter tells you how many store misses occurred. If it is close to `nnz`, the scatter is touching almost every write as a miss. If it is much lower, some writes are coalescing.

The roofline model is useful here. The arithmetic intensity of transpose is essentially zero: it does no floating-point arithmetic beyond copying values. The performance is bounded by memory bandwidth. But the roofline for irregular access is lower than the peak bandwidth. The gap is the cost of irregularity. You can estimate the number of distinct cache lines touched by the scatter. If the output arrays have `L` cache lines and there are `nnz` writes, the expected number of distinct lines touched is `L * (1 - (1 - 1/L)^nnz)`. For large `nnz`, this approaches `L`. If `nnz` is much larger than `L`, many writes share lines, but they may be far apart in time. The working set of the scatter is the output array size, which is `nnz * (sizeof(row) + sizeof(value))`. If that exceeds the LLC, every write misses. Bucketing reduces the working set to the size of a column block, which can fit in cache. That is the main reason bucketing helps.

Measure the time per phase: count, scan, and scatter. Often the scatter is 60 to 80 percent of the total. If the scan is significant, optimize the prefix sum. If the count is significant, use a better histogram. Also measure NUMA effects. On a multi-socket system, a thread that writes to memory allocated on another socket pays a remote access penalty. The first-touch policy means that the node that first writes a page owns it. If you initialize the output arrays in parallel with the same partitioning as the scatter, you get good NUMA placement. If you initialize them sequentially, all pages are on one node, and half the threads will write remotely. Use `numactl` or `mbind` to control placement. Huge pages reduce TLB misses, which are common when the output array is large and the writes are scattered. On a GPU, use `ncu` to measure store efficiency and L2 throughput. If store efficiency is low, use shared memory bucketing. If atomics are a bottleneck, check the atomic throughput and consider per-thread offsets.

## Blocked formats and the transpose of dense blocks

Many sparse matrices have block structure. Finite element matrices with multiple degrees of freedom per node produce small dense blocks. Block sparse row (BSR) stores blocks of size `r x c`. The transpose of BSR is block sparse column (BSC). The algorithm is similar to scalar CSR to CSC, but it counts blocks per column block, prefix-sums the block counts, and scatters blocks. The advantage is that each memory access moves a block, so cache line utilization improves. A 3x3 block of doubles is 72 bytes, which is more than a cache line. A 2x2 block is 32 bytes, half a line. If blocks are stored contiguously, the scatter writes a contiguous block. The internal transpose of each block can be done with SIMD or register shuffles. If the block size is small, the overhead of block indexing may outweigh the benefits. If the matrix is not naturally blocked, you can still use a blocked format by grouping columns, but you may introduce zeros. That increases `nnz`. The trade-off is fill versus locality. For matrices from PDEs, blocking is natural and often already used. For graph matrices, blocks are rare.

Another hybrid is to store the matrix in CSR but transpose in tiles of rows and columns. You process a tile of rows, gather nonzeros in a tile of columns, transpose the tile, and write it out. This is like dense tiling for sparse matrices. The tile size is chosen so that the output tile fits in cache. The gather is irregular but local. This is a form of two-dimensional bucketing. It can be better than one-dimensional bucketing when the matrix has both row and column locality. The cost is extra buffering and a more complex control flow. In practice, one-dimensional bucketing by column blocks is simpler and captures most of the benefit for matrices with random column indices.

## Transpose from COO: when sorting is the transpose

If the input is in coordinate (COO) format, transpose is a sort. COO stores triples `(row, col, value)`. To transpose, swap row and col, then sort by `(col, row)` to get CSC order. A parallel radix sort can sort by col, then by row, or use a single pass with a composite key. Radix sort is regular and has predictable memory traffic. It may be faster than CSR-based counting sort if the input is already COO. If the input is CSR, converting to COO costs an extra pass. But if you need to transpose many times or if the matrix is dynamic, COO may be convenient. The counting sort from CSR is essentially a radix sort with one digit, the column. If `n` is large, a single digit is too large for a histogram, so you use multiple radix passes. Each pass partitions by a few bits of the column. The number of passes is `ceil(log_{2^r}(n))`. Each pass reads and writes `nnz` triples. The total traffic is `passes * nnz * (sizeof(row) + sizeof(value) + sizeof(col))`. This can be more than the two-pass CSR algorithm if `n` is large. But radix sort can be very fast because it is coalesced and uses shared memory on GPUs. On CPUs, a parallel radix sort with 8-bit digits is often used. The choice depends on the format and the hardware.

## Fusion: when not to materialize the transpose

Explicit transpose is not always necessary. If the only use of `A^T` is to compute `y = A^T x` once, you can compute it directly from `A` in CSR: for each row `i`, for each nonzero `(i, j, v)`, `y[j] += v * x[i]`. This is a scatter into `y`. It has irregular writes to `y`, but `y` is length `n`, which is much smaller than `nnz`. The writes to `y` may have contention if multiple threads update the same `j`. You can avoid atomics by partitioning rows and using per-thread `y` buffers, then reducing. The reduction is over `n` elements, which is cheap. This fused approach reads `A` once and writes `y`, avoiding the transpose entirely. If you need `A^T x` many times with different `x`, the explicit transpose may pay off because the transpose cost is amortized. The break-even point depends on the cost of transpose versus the cost of repeated irregular scatter. If transpose costs twice the cost of SpMV, then after two SpMVs the transpose is worth it. But if the fused scatter is slower due to atomics, the break-even may be one. Fusion can also be applied to format conversion: if you are converting from CSR to CSC and then immediately doing a CSC SpMV, you can fuse the transpose with the SpMV by computing the CSC on the fly. This is a form of kernel fusion. The challenge is that the transpose requires global synchronization to compute `col_ptr`, so fusion is limited to cases where the output format is not needed. For iterative solvers, you often need both `A` and `A^T`. You can store both formats, or you can use a single format and compute the other on the fly. The memory cost of storing both is `2 * nnz * (sizeof(row) + sizeof(value))` plus pointers. The compute cost of on-the-fly is the irregular access. On modern hardware with large memory, storing both is often acceptable. On memory-constrained devices, fusion is necessary.

## Autotuning and heuristics for choosing a transpose strategy

The design space is large. Parameters include thread count, row partition (contiguous versus strided versus guided), counting method (dense per-thread, sparse, atomic, bucketed), scatter method (atomic, per-thread offsets, bucketed), block size `B`, number of buckets, use of non-temporal stores, use of huge pages, and NUMA binding. Autotuning can be done offline with a set of representative matrices, or online with a few samples. Online autotuning must be cheap. You can sample the matrix to estimate the column distribution. Compute max column count, variance, number of columns, and `nnz`. Use heuristics: if max column count is less than 32, atomics are fine. If sorted output is required, use per-thread offsets. If `n` is less than 4096, dense per-thread counts. If `n` is greater than one million, bucketing with `B = 1024` or `4096`. If the matrix has blocks, use BSR. If GPU, use shared memory bucketing with `B = 256` or `512`. The best parameters depend on cache size, memory bandwidth, and core count. A simple autotuner can try three or four configurations and pick the fastest. The overhead is small compared to the transpose itself for large matrices. For small matrices, the overhead may dominate, so use a fixed default. Another approach is to use a cost model. The cost model estimates memory traffic: two-pass traffic is `nnz * (sizeof(row) + sizeof(value)) * (1 + write_allocate_factor)`. Bucketed traffic is `nnz * (sizeof(row) + sizeof(value)) * (2 + ...)`. The `write_allocate_factor` depends on the number of distinct cache lines touched, which depends on the column distribution. You can estimate it from a sample. The cost model can be calibrated on the target machine. This is more robust than fixed heuristics.

## Debugging and validating a parallel transpose

Parallel transpose has many failure modes. Common bugs include counts not zeroed, prefix sum off by one, race in atomic scatter, incorrect handling of empty rows or columns, integer overflow when `nnz` exceeds `2^31`, and incorrect row/column swap. Use 64-bit indices for large matrices. Validate against a sequential reference. Check that `col_ptr` is nondecreasing and `col_ptr[n] == nnz`. Check that each column's row indices are within bounds. Check that the multiset of `(row, col, value)` is preserved. If sorted output is expected, check that row indices are increasing within each column. Use a deterministic seed for random matrices. Use sanitizers: ThreadSanitizer for races, AddressSanitizer for out-of-bounds. For GPU, use compute-sanitizer. Reproducibility is another concern. If you use atomics, the output order is nondeterministic. If you need reproducibility, use per-thread offsets or sort the output. Nondeterminism can make debugging harder. Log the configuration and matrix features. Compare performance across runs. If performance varies, check for NUMA effects or thermal throttling. Use a warm-up run. Pin threads to cores. Disable turbo for stable measurements.

## Transpose in graph analytics and numerical software

In graph analytics, transpose is used to build reverse adjacency for pull-based BFS. For a directed graph, you need both outgoing and incoming edges. If the graph is stored in CSR, the transpose gives CSC. For a graph with billions of edges, the transpose can take minutes and consume memory bandwidth. Some frameworks avoid explicit transpose by storing both directions or by using a push-pull hybrid that only needs one direction at a time. For dynamic graphs, the transpose must be updated incrementally. Incremental transpose is harder because inserting an edge changes column counts and shifts offsets. You can use a dynamic format like adjacency lists with locks, or you can rebuild the transpose periodically. In numerical linear algebra, transpose is used for incomplete LU factorization, where you need both row and column access. It is also used in algebraic multigrid for restriction and prolongation. In sparse triangular solve, you may need to solve with `A^T`, which can be done by traversing the matrix in reverse order. Some libraries store both `A` and `A^T` to avoid transposing during the solve. The decision depends on the number of solves and the memory available. In machine learning, sparse transpose appears in sparse neural networks and graph neural networks. For graph neural networks, message passing often requires both directions. The transpose is a preprocessing step that can be fused with graph partitioning. In all these applications, the transpose is a means, not an end. The best implementation is the one that minimizes the end-to-end cost, which may mean avoiding the transpose entirely.
