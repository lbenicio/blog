# The Anatomy of the Linux Block Layer: blk-mq, I/O Schedulers, and the Cost of Queueing

Every storage benchmark you have ever read is, in some sense, a measurement of the Linux block layer. Not of the SSD, not of the filesystem, not of the application — of the layer in between, which decides how many commands are in flight, in what order they leave, and from which CPU they depart. When a device delivers a fraction of its rated throughput, the usual suspects are queue depth, request size, and CPU affinity, and all three of those are, at bottom, block-layer decisions.

This article is about that layer: what it actually does, why its architecture was replaced wholesale in the 2010s, and what the current design — blk-mq plus a small set of I/O schedulers — implies for anyone writing storage-bound software. The goal is not to catalog kernel functions. It is to build a mental model precise enough that you can predict, from a workload description, where the block layer will help you and where it will quietly cost you.

## The Layer Nobody Names

Consider the path of a single `pwrite()` to a file on an ext4 filesystem backed by an NVMe device.

The call enters the VFS, resolves the path to an inode, and reaches the filesystem. If the write is buffered, ext4 copies data into page cache pages, marks them dirty, and returns. Nothing has touched the block layer yet. Sometime later — on an `fsync()`, on memory pressure, or when the kernel's periodic flusher wakes — writeback walks those dirty pages and submits them for I/O.

At that moment a `struct bio` is constructed. A bio is a description of a range of a block device: a starting sector, a length, and a vector of memory segments (page, offset, length) that hold the data. Crucially, a bio is *not* a device command. It is a statement of intent, expressed in terms the block layer can merge, split, and reorder. The bio is submitted with `submit_bio()` and enters the block layer proper.

From there, the layer performs a sequence of transformations:

1. **Validation and splitting.** A bio may span more than the device can handle in one command, or cross a boundary the driver cannot express. The layer splits it into pieces that fit within limits such as `max_sectors_kb` (a software-imposed cap) and `max_hw_sectors_kb` (what the hardware can encode).
2. **Merging.** Adjacent bios targeting contiguous sectors may be coalesced into a single larger unit of work. This is the single most important optimization the block layer performs, because storage devices are far more efficient with large sequential commands than with many small ones.
3. **Queueing.** The resulting unit of work is placed on a queue associated with the device and, in the modern design, with a specific CPU.
4. **Scheduling.** A policy decides which queued unit to dispatch next.
5. **Dispatch.** The unit is converted into a driver-level command, given a tag, and handed to the device driver.
6. **Completion.** The device signals completion, the tag is released, and the bio is completed back up the stack, waking whoever was waiting.

The vocabulary matters here because the kernel's own terminology is easy to conflate. A **bio** is the filesystem's unit of intent. A **request** is the block layer's unit of work — one or more merged bios that will become one or more device commands. A **tag** is a slot in the device's command queue, and it is the scarce resource that everything else is ultimately negotiating over.

## The Elevator That Stopped Making Sense

For most of Linux's history, the block layer was organized around a single queue per device, and the scheduler sitting on that queue was called an *elevator*. The name was literal: on a rotating disk, the cost of a seek dominated everything else, so the scheduler's job was to reorder requests to minimize head movement — sweeping back and forth across the platters like an elevator servicing floors. Algorithms like SSTF, C-SCAN, and their variants were the subject of serious research, and Linux shipped several: `noop`, `deadline`, `anticipatory`, and `cfq` (the Completely Fair Queuer), each trading off throughput against fairness and latency.

Two things broke this model.

First, **seeks stopped being the dominant cost**. On flash, there is no head, and the cost of a random 4 KiB read is not categorically different from a sequential one in the way it was on a platter. Reordering for locality stopped buying much. What matters on flash is *parallelism*: how many independent commands the device can service simultaneously, and whether the software can keep that many in flight.

Second, **a single queue became a bottleneck in its own right**. A queue protected by a lock, touched by every CPU on the machine, is a coherence nightmare. On a 64-core server generating I/O from many threads, the queue lock and the cache line containing its head and tail become the hottest data in the kernel. The device might be capable of tens of thousands of outstanding commands across dozens of hardware queues, while the software funnels everything through one serialized structure.

The response was **blk-mq**, a multi-queue block layer. It was merged over several kernel releases and, after a transition period, the legacy single-queue path was removed entirely, leaving blk-mq as the only path through the block layer. The old elevator algorithms are gone. What replaced them is a different design with a different set of assumptions, and understanding those assumptions is the key to reasoning about storage performance on any modern kernel.

## blk-mq: The Data Structures

The central idea of blk-mq is that the queue is not one queue but a *hierarchy of queues*, arranged so that the common case — a submission from a CPU that has been submitting all along — touches only per-CPU data.

The structures, in the order a submission encounters them:

**The software queue (`struct blk_mq_ctx`).** There is one of these per CPU (strictly, per possible CPU). It is where bios land when they enter the block layer. Because it is per-CPU, insertion requires no cross-CPU synchronization in the uncontended case. This is the structure that eliminates the single-queue lock bottleneck.

**The hardware queue (`struct blk_mq_hw_ctx`).** There is one of these per *dispatch queue* the device driver exposes. Each hardware queue has its own dispatch list, its own tag space (or a share of one), and its own association with a completion path. The number of hardware queues is chosen by the driver — commonly one per CPU, or one per device queue, or some smaller number when the device cannot support more.

**The tag set (`struct blk_mq_tag_set`).** Tags are the finite resource: each represents a slot the device can hold an outstanding command in. The tag set owns the tag bitmap (or several, for shared tags) and the request structures themselves. A request's identity is essentially its tag.

**The mapping from CPU to hardware queue.** When a bio arrives on a CPU, blk-mq looks up which hardware queue that CPU is assigned to and inserts the resulting request into the corresponding software queue. If there are at least as many hardware queues as CPUs, the mapping is essentially one-to-one and no sharing occurs. If there are fewer — a device with 8 queues on a 64-core machine — then multiple CPUs map to the same hardware queue, and that queue's tag space is shared among them. This is the first place where a well-intentioned design can produce surprising contention.

The dispatch path then runs per hardware queue: a thread (or the submitting context, or a softirq) drains the software queues feeding a given hardware queue into its dispatch list, and from there into the driver. Because dispatch is per hardware queue, two CPUs dispatching to two different hardware queues do not contend with each other at all. That is the entire point of the design.

## Tags, Depth, and What "Queue Depth" Really Means

It is worth pausing on tags, because they are where the abstract architecture meets a hard physical limit.

A device advertises how many commands it can have outstanding. For NVMe this is expressed through the queue count and queue depth in the controller's capabilities: the specification permits a very large number of I/O submission queues, each with a large maximum depth, though real controllers implement far less. A SATA device, by contrast, has a single command queue with a depth of 32, and no amount of software cleverness changes that. A SCSI device may expose a queue depth in the hundreds.

This number is the ceiling on concurrency. Everything the block layer does — the per-CPU software queues, the tag allocation, the scheduler's dispatch decisions — exists to keep that ceiling occupied without exceeding it. Two failure modes follow directly:

- **Under-utilization.** If the application issues one synchronous write at a time and waits, the device sees a queue depth of one regardless of how deep it could go. The block layer cannot fix this; it has nothing to dispatch. This is why asynchronous I/O and `io_uring` matter so much more than any scheduler tuning on fast devices.
- **Tag starvation.** If the tag space is exhausted, submissions block or fail, and latency spikes. In blk-mq, tag allocation is per hardware queue (or shared across a group of queues via shared tags), so a workload that concentrates on one CPU can exhaust that CPU's share of tags while other queues sit idle. This is a real and frequently misdiagnosed source of tail latency on many-core machines.

The practical consequence is that "queue depth" is not one number. There is the depth the device supports, the depth the driver exposes, the depth the tag set allocates per hardware queue, and the depth the application actually maintains. Performance problems usually live in the gap between the last two.

## The Schedulers That Survived

When the legacy single-queue path was removed, the old elevator algorithms went with it. What remains is a small set of schedulers designed from the start for a multi-queue world: `none`, `mq-deadline`, `kyber`, and `bfq`. Each is selected per device via `/sys/block/<dev>/queue/scheduler`, and each embodies a different theory of what the block layer should optimize for.

The first thing to understand about these schedulers is that they are not global. In the old design, a single elevator saw every request destined for the device and could reorder across the entire workload. In blk-mq, scheduling happens per hardware queue. Each hardware queue has its own dispatch list, and the scheduler attached to it sees only the requests that have arrived on the CPUs mapped to that queue. There is no single point from which the whole device's I/O is visible.

This is a deliberate trade: the design gives up global knowledge to eliminate global contention. But it has consequences. A scheduler cannot enforce fairness between two processes whose I/O is flowing through different hardware queues, because it never sees both streams at once. It cannot globally prioritize reads over writes if those reads and writes are on different queues. The schedulers that survive either accept these limitations or work around them with shared state — and the workarounds are where the complexity lives.

### `none`: The Scheduler That Isn't

The `none` scheduler — historically called `noop` — does almost nothing. It dispatches requests from the hardware queue's list in the order they arrived, with no reordering, no prioritization, and no fairness. It is not, however, the absence of the block layer. Merging still happens, plugging still happens, and tags are still allocated. `none` simply declines to impose a policy on top of those mechanisms.

For a long time, `none` was considered appropriate only for devices that did their own scheduling — hardware RAID controllers with battery-backed cache, or storage arrays that reordered internally. That advice has inverted. On modern NVMe devices, `none` is frequently the best choice, and often the default. The reasoning is straightforward: an NVMe device has many hardware queues, each with a deep tag space, and it can service commands from those queues in parallel. The device itself has a sophisticated internal scheduler that understands its own flash geometry, wear leveling, and garbage collection. Any reordering the kernel does is at best redundant and at worst harmful, because it adds CPU overhead and delays dispatch without improving the device's decisions.

The exception is when the workload is not already well-behaved. If a single process is issuing a mix of latency-sensitive reads and bulk writes, `none` will let the writes flood the queue and the reads will wait. That is where the other schedulers earn their keep.

### `mq-deadline`: Bounded Latency by Construction

`mq-deadline` is a port of the old `deadline` elevator to blk-mq. Its goal is simple to state: ensure that no request waits longer than a configured deadline. It maintains, per hardware queue, two sorted lists — one for reads, one for writes — ordered by starting sector. It also tracks an expiration time for each request. Reads get a shorter deadline (500 ms by default) than writes (5 seconds), reflecting the usual assumption that a blocked read is more disruptive than a delayed write.

Dispatch proceeds in a specific order. The scheduler first checks whether any read request has expired; if so, it dispatches that. Then it dispatches from the read list in sector order, batching requests that are contiguous or nearly so. Only when the read list is empty or the batch is complete does it turn to writes. This read-priority bias is intentional: it keeps interactive and foreground workloads responsive even when the device is saturated with writeback.

The sector-order sorting provides a secondary benefit even on flash. While there is no head to seek, contiguous requests can sometimes be merged or handled more efficiently by the device's internal controller. More importantly, sorting by sector gives the scheduler a cheap way to batch requests that are likely to be part of the same file or the same sequential stream. The batching reduces the number of dispatch operations and gives the device larger, more efficient commands.

`mq-deadline` is a good default for SATA SSDs and for any device where the queue depth is modest and read latency matters. It adds CPU overhead compared to `none`, but the overhead is bounded and predictable. It does not attempt fairness between processes, and it does not try to model the device's internal behavior. It simply enforces a deadline and hopes that is enough.

### `kyber`: Explicit Latency Targets

`kyber` takes a different approach. Rather than sorting requests or enforcing deadlines after the fact, it tries to control the *rate* at which different types of I/O enter the device. It maintains two queues per hardware queue — one for reads and one for writes — and uses a token bucket for each. The token bucket limits how many requests of that type can be outstanding at once. When a request completes, a token is returned, allowing another request of that type to be dispatched.

The size of each token bucket is not fixed. `kyber` adjusts it dynamically based on measured latency. The administrator sets a target latency for reads and writes (for example, 2 ms for reads and 10 ms for writes). The scheduler monitors how long requests are actually taking. If reads are completing faster than the target, it increases the read token bucket, allowing more read concurrency. If they are slower, it shrinks the bucket. The same logic applies to writes. The result is a feedback loop that tries to keep each type of I/O within its latency budget while maximizing overall throughput.

This design is well-suited to fast devices with deep queues, where the bottleneck is often not the device's ability to service commands but the software's ability to manage them. By limiting concurrency to what the device can handle within the latency target, `kyber` avoids the tag starvation and queue buildup that can occur when too many requests are in flight. It is simpler than `bfq` and more adaptive than `mq-deadline`. Its weakness is that it does not provide fairness between processes; it treats all reads as one class and all writes as another.

### `bfq`: Fairness and Interactivity

`bfq`, the Budget Fair Queueing scheduler, is the most complex of the survivors. Its lineage goes back to the single-queue `cfq` scheduler, which was designed to provide fairness among processes on rotating disks. `bfq` reimplements that goal for multi-queue devices, with a focus on interactive responsiveness.

The core abstraction in `bfq` is the *budget*. Each process (or cgroup) that submits I/O gets a queue, and each queue is assigned a budget measured in sectors. The scheduler dispatches from a queue until its budget is exhausted, then moves to the next queue according to a virtual-time algorithm that approximates fair queueing. Queues that have been idle are given a boost, which is how `bfq` prioritizes interactive tasks that issue I/O in short bursts. The scheduler also tracks whether a queue's I/O is sequential or random and adjusts its budget accordingly, giving larger budgets to sequential streams to improve throughput.

The cost of this sophistication is CPU time. `bfq` maintains per-queue state, performs virtual-time calculations, and makes decisions that are far more involved than the simple list operations of `mq-deadline`. On a fast NVMe device, `bfq` can become the bottleneck itself, consuming multiple CPU cores just to schedule I/O. For this reason, it is rarely used on servers. Its natural habitat is the desktop and mobile world, where the workload is a mix of interactive applications and background tasks, and where a few milliseconds of added latency for a background write is a worthwhile trade for a responsive UI.

The existence of `bfq` alongside `none` illustrates the range of the design space. At one end, `none` trusts the device and the application to sort things out. At the other, `bfq` attempts to model and control the entire I/O workload in software. Most systems fall somewhere in between, and the choice of scheduler is really a choice about where to place the burden of scheduling: on the device, on the application, or on the kernel.

## The Cost of Queueing

Queueing is not free. Every request that enters the block layer consumes memory, CPU cycles, and cache lines. The deeper the queue, the more of these resources are consumed. This is the fundamental tension of the block layer: you need concurrency to saturate a fast device, but concurrency itself has a cost.

The lifecycle of a request begins with allocation. blk-mq maintains a pool of `struct request` objects, one per tag in the tag set. These are allocated at initialization and reused. When a bio is submitted, the block layer attempts to merge it into an existing request. If no merge is possible, it allocates a new request from the pool and assigns it a tag. The tag allocation itself is a per-hardware-queue operation, typically using a bitmap or a lockless data structure. On a busy system, tag allocation can become a contention point if many CPUs are submitting to the same hardware queue.

Once a request is allocated, it is inserted into the software queue for the CPU that submitted it. The software queue is a per-CPU list, so insertion is cheap. But the request is not yet on the hardware queue's dispatch list. The dispatch list is where the scheduler operates, and moving requests from software queues to the dispatch list requires a synchronization step. This is done by a per-hardware-queue dispatch mechanism, which may run in the context of the submitting process, in a softirq, or in a dedicated kernel thread (`kblockd`). The choice depends on the driver and the configuration.

The dispatch step is where the scheduler's policy is applied. For `none`, it is a simple splice of the software queue's list onto the dispatch list. For `mq-deadline`, it involves inserting into sorted lists and checking expiration times. For `bfq`, it involves updating virtual times and budgets. Each of these operations touches memory and consumes CPU. On a device capable of millions of IOPS, the scheduler's per-request cost can easily exceed the device's per-request service time, making the scheduler the limiting factor.

Completion is the other half of the lifecycle. When the device signals completion, an interrupt fires. The driver acknowledges the interrupt and schedules a softirq to process the completion. blk-mq uses per-CPU completion queues to avoid locking: the completion is placed on the queue of the CPU that submitted the request, and that CPU's softirq processes it. This is efficient, but it means that the CPU that submitted the I/O must also handle its completion. If a CPU is busy with application work, completion processing may be delayed, which in turn delays the release of tags and the dispatch of new requests. This is one reason why I/O-heavy workloads often benefit from spreading submissions across CPUs, or from using dedicated CPUs for I/O.

The memory cost of deep queues is also non-trivial. Each `struct request` is a few hundred bytes, and each tag set may have thousands of tags. On a system with many devices, the total memory consumed by request pools can be significant. More importantly, the requests and their associated data structures occupy cache lines that would otherwise be used by application data. Deep queues increase cache pressure, which can reduce overall system performance even if the device itself is not saturated.

Plugging is the block layer's primary defense against these costs. When a process submits multiple bios in a loop — as filesystems do during writeback — it can use `blk_plug` to accumulate them in a per-task list. The bios are not dispatched immediately. Instead, they are held until the plug is flushed, at which point they are submitted as a batch. This has two benefits. First, it reduces the number of times the software queue and dispatch list are touched, amortizing the cost of locking and list manipulation. Second, it gives the block layer a larger set of bios to merge, increasing the chance that adjacent bios will be coalesced into a single larger request.

The plug is flushed automatically when the task does certain things — calls `schedule()`, enters a different plugging context, or explicitly flushes. The kernel also has a timer that flushes plugs that have been held too long, to prevent latency spikes. The effectiveness of plugging depends on the workload. Sequential writeback generates long runs of adjacent bios, which plugging and merging handle very well. Random small I/O generates bios that cannot be merged, so plugging provides less benefit, though it still reduces lock contention.

Merging itself has a cost. To merge a bio into an existing request, the block layer must search for a candidate. blk-mq maintains, per software queue, a list of requests and a hash table keyed by sector. The search is fast, but it is not free. For workloads that are inherently random and unmergeable, the merge search is pure overhead. This is why some high-performance applications bypass the block layer's merging entirely by using direct I/O with large, pre-aligned requests, or by using `io_uring` with fixed buffers and careful alignment.

The cumulative effect of these costs is that the block layer's overhead per I/O is not constant. It depends on the request size, the merge rate, the queue depth, and the scheduler. For large sequential I/O, the overhead is amortized over many kilobytes or megabytes, and the block layer is not the bottleneck. For small random I/O, the overhead per 4 KiB operation can be a significant fraction of the total time, especially on fast devices where the device itself takes only microseconds to service a command.

This is the cost of queueing: not a single cost, but a collection of costs that scale with concurrency and inverse-scale with request size. The schedulers that survived are, in essence, different strategies for managing that trade-off. `none` minimizes the cost by doing almost nothing, betting that the device and the application will provide enough concurrency and enough request size to keep the overhead negligible. `mq-deadline` accepts some overhead to bound latency. `kyber` accepts some overhead to control concurrency. `bfq` accepts a lot of overhead to provide fairness. The right choice depends on which cost you can least afford.

## The Other Queues: Writeback, Throttling, and Congestion

A request does not begin life in blk-mq. For buffered I/O it begins as a dirty page, and the path from dirty page to bio is governed by a second set of queues and limits that are just as consequential as the tag space. The flusher threads decide when dirty data is written; the dirty page limits decide how long a process may keep dirtying memory before it is forced to wait; and writeback throttling decides how aggressively the kernel should push writeback when the device is already under pressure. These mechanisms sit above and around blk-mq, and they are the usual explanation for stalls that look like block-layer failures but are really memory-management decisions.

The dirty page limits are exposed as `vm.dirty_ratio`, `vm.dirty_background_ratio`, and their byte-based counterparts. When dirty data exceeds the background threshold, flusher threads wake and begin submitting writeback bios. When it exceeds the hard threshold, processes that try to dirty more pages are throttled in `balance_dirty_pages()`. The throttling is deliberate and adaptive: the kernel estimates how fast the device is cleaning pages and paces the dirtying process to match. From the application's perspective this appears as an unexplained pause in a write loop, often with the CPU idle and the disk busy. The block layer is doing exactly what it was told; the queue is full because writeback is trying to relieve memory pressure, not because the application asked for synchronous I/O.

Writeback throttling, or wbt, adds a block-layer feedback loop on top of that. It tracks the latency of writeback requests and the number of requests in flight, and when completion latency rises it reduces the amount of writeback the kernel will allow in flight. The knobs live under `/sys/block/<dev>/queue/wbt_lat_usec` and related files. The intent is to keep writeback from monopolizing a device and inflating the latency of foreground reads. Wbt is not a scheduler and does not reorder requests; it is an admission-control mechanism that decides how much writeback concurrency is healthy. On a desktop or a latency-sensitive server, it can be the difference between a responsive system and one that feels frozen during a large copy. On a dedicated storage node doing bulk writes, it can also be counterproductive, because it throttles the very traffic that is supposed to saturate the device. The correct setting depends on whether the device is shared between latency-critical and background work.

Congestion is the older, coarser cousin of these mechanisms. When a request queue approaches its limits, the block layer can mark the device as congested, and writers may back off or block. In the blk-mq world congestion is less centralized than it once was, because there is no single queue to inspect, but the concept survives in the tag allocation and writeback paths. The important point for diagnosis is that congestion is a signal, not a cause. A congested device is one where demand exceeds the configured concurrency, and the fix is usually to reduce the demand, increase the concurrency, or move the demand to a different device.

Cgroup I/O control is the third layer. The `io` controller in cgroup v2 can assign weights, absolute bandwidth limits, and IOPS limits to a group of processes. The blk-throttle mechanism enforces those limits by delaying bios before they reach the request queues; `bfq` can also enforce fairness using its own queueing model. This is the right tool when the problem is noisy neighbors rather than raw device saturation. It is also a reminder that the block layer is not a single policy point. Fairness can be imposed by the scheduler, by the cgroup controller, or by the application, and those choices interact. A process throttled to 1000 IOPS by a cgroup will not benefit from a deeper tag space, and a scheduler that tries to be fair among processes may fight a cgroup limit that is already enforcing fairness at a coarser granularity.

## Completion Is a Scheduling Problem Too

The submission path gets most of the attention, but the completion path determines whether the queue stays full. A device that can hold 1024 commands is only useful if completed commands are retired quickly enough to free their tags for new work. In blk-mq, completion begins with an interrupt from the device. The driver acknowledges the interrupt, identifies the completed commands, and schedules a softirq to process them. The completion is then routed, often back to the CPU that submitted the request, so that the bio can be completed in the context that has the relevant page cache and task state warm in its caches. This routing is controlled by `rq_affinity` under the device's queue directory. Setting it to complete on the submitting CPU improves locality; forcing all completions onto one CPU can become a bottleneck; disabling the affinity can spread completion work but may increase cache misses. The right choice depends on whether the workload is limited by cache locality or by a single CPU's interrupt and softirq capacity.

The softirq itself is a scheduling entity. If completions arrive faster than the CPU can process them, they are deferred to `ksoftirqd`, and the queue of pending completions grows. At that point the device may have free tags, but the software has not yet released them, so the effective queue depth falls. This is a common hidden limit on very fast NVMe devices: the device is idle, the application is waiting, and a CPU is busy running softirq processing for completions. Spreading interrupts across CPUs with IRQ affinity, increasing the number of hardware queues, or moving application threads away from the CPUs handling interrupts can all help. None of these are scheduler tunings in the traditional sense, but they are block-layer tunings in the sense that matters.

Polling is the alternative to interrupts, and it changes the cost model completely. Instead of the device interrupting the CPU, the CPU checks the completion queue directly. This avoids interrupt overhead and can reduce latency, but it consumes CPU cycles that could be used for other work. Linux exposes polling through several mechanisms: the `io_poll` queue flag, the `io_uring` `IORING_SETUP_IOPOLL` mode, and driver-specific polling support. Polling is attractive when the device is very fast, the queue depth is high, and CPU cycles are cheaper than the latency of an interrupt. It is a poor fit for a lightly loaded system, where the CPU would otherwise be idle. The block layer does not choose polling for you; it exposes the capability and lets the application or the administrator decide. That decision is another place where the cost of queueing is paid, because polling trades interrupt overhead for busy-waiting, and busy-waiting is only free if the CPU has nothing better to do.

Timeouts and error handling belong on this side of the lifecycle as well. A request that is dispatched but never completed holds its tag indefinitely until the timeout fires. The timeout handler may abort the request, reset the device, or escalate to a larger recovery action. During that window, the tag is unavailable, and if enough requests time out, the tag space can be exhausted even though the device is not physically busy. This is why a single failing drive or a marginal cable can produce system-wide I/O stalls rather than isolated errors. The block layer's error handling is designed to contain the damage, but containment takes time, and time is measured in tags.

## Reading the Queue from Userspace

The block layer is more observable than its reputation suggests, but the observability is spread across several interfaces. The first place to look is `/sys/block/<dev>/queue/`. The `scheduler` file shows which policy is active. `nr_requests` reports the request limit that the tag set and scheduler will respect. `max_sectors_kb` and `max_hw_sectors_kb` show the software and hardware limits on request size. `logical_block_size` and `physical_block_size` explain why some I/O is split or misaligned. `rotational` is a hint, not a guarantee, and it is frequently wrong on virtual devices. `nomerges` controls whether the block layer attempts to merge adjacent requests, and `rq_affinity` controls completion routing. `io_poll` and `io_poll_delay` expose polling support. `wbt_lat_usec` shows the writeback throttling target. Reading these files will not tell you why a workload is slow, but it will tell you which limits are in play.

The second place is the tracepoint and debugfs surface. `blktrace` and the block tracepoints expose request issue, completion, merge, and queue events with enough detail to reconstruct the lifecycle of individual I/O. `biosnoop` and similar tools built on BPF attach to the same tracepoints and print per-I/O latency with the issuing process, which is often enough to identify whether latency is in the device, the scheduler, or the completion path. The blk-mq debugfs files under `/sys/kernel/debug/block/` show the hardware queues, their CPU mappings, and their tag usage. When a system has more CPUs than hardware queues, those files make the sharing visible. When a single hardware queue is saturated while others are idle, they show that too.

The third place is the workload itself. `fio` with explicit `iodepth`, `numjobs`, and `ioengine` settings is the standard way to separate application concurrency from device concurrency. A test with `iodepth=1` measures latency; a test with `iodepth=128` measures the device's ability to keep tags occupied. Running both, and comparing the results, tells you whether the bottleneck is the application's submission rate or the block layer's ability to dispatch. The same logic applies in production: if the application issues one synchronous write at a time, no scheduler will make the device faster. If the application issues many asynchronous writes but the completion CPU is saturated, the scheduler is not the problem either.

Queue tuning is therefore not a one-time configuration. The right `nr_requests`, the right scheduler, and the right polling mode depend on the device, the workload, and the CPU topology, and they can change when any of those change. A setting that works on a 16-core machine with a SATA SSD is not the same setting that works on a 128-core machine with a PCIe Gen5 NVMe array. The block layer exposes the knobs because there is no single correct answer. The cost of queueing is real, but it is also measurable, and measurement is how the next tuning decision gets made.

## CPU Topology and the Geometry of blk-mq

The most useful mental correction when tuning blk-mq is to stop thinking of a device as having a queue count and start thinking of it as having a *shape*. That shape is the mapping from logical CPUs to hardware queues, and it determines which CPUs share a tag space, which CPUs share a dispatch list, and which CPUs contend for the same completion work. Two systems with the same NVMe drive, the same kernel, and the same workload can behave differently because their shapes differ.

A block device exposes `nr_hw_queues` under its queue directory. That number is chosen by the driver, sometimes constrained by the device, and sometimes influenced by module parameters or firmware. When `nr_hw_queues` is at least the number of possible CPUs, the mapping is close to one hardware queue per CPU and the common case is contention-free: a submission from CPU 7 lands in the software queue for CPU 7 and is dispatched to the hardware queue associated with CPU 7. When there are fewer hardware queues than CPUs, several CPUs are mapped to the same hardware queue. The kernel does not hide this; debugfs exposes the CPU list for each hardware queue, and that list is the first thing to inspect when a many-core machine shows uneven block-layer CPU time.

Sharing a hardware queue is not inherently bad, but it changes the cost model. The tag space is associated with the hardware queue, or with a shared tag set that covers a group of queues, depending on the driver and configuration. If eight CPUs share one hardware queue with sixty-four tags, then those eight CPUs are collectively negotiating over sixty-four slots. A single busy CPU can consume most of them, and the other seven can stall on tag allocation even though the device is not physically saturated. This is the block-layer version of a noisy neighbor problem, and it is invisible to tools that report only aggregate device utilization. The device looks busy, the application looks slow, and the explanation is a tag bitmap in a shared hardware queue.

The mapping is also not necessarily stable in the way an administrator expects. A process can migrate between CPUs, and blk-mq uses the submitting CPU at the moment of submission. A thread pinned to CPU 3 will consistently use CPU 3's software queue; an unpinned thread may use a different queue on every submission. Pinning can improve locality and make tag usage predictable, but it can also concentrate demand on one hardware queue when the scheduler would otherwise have spread it. The correct choice depends on whether the application is latency-sensitive or throughput-sensitive. For a latency-sensitive thread, pinning plus an aligned interrupt affinity can reduce jitter. For a throughput-oriented worker pool, letting the scheduler spread threads across CPUs usually produces better tag utilization.

NUMA adds a second dimension. A hardware queue has a NUMA node association, and the driver may create queues that are local to a socket or to a PCIe root complex. Request structures and tag bitmaps are allocated with node awareness where the kernel supports it. A submission from a CPU on node 0 to a hardware queue on node 1 is still correct, but it pays cross-node memory traffic for the request and for the completion path. On large machines this can be a few percent of throughput and a more noticeable amount of tail latency. The fix is not exotic: keep application threads, interrupts, and block queues on the same node when the device topology permits it. Check the queue's node and the interrupt's node before assuming the default placement is local.

Interrupt affinity deserves the same scrutiny as the queue map. Completion interrupts should generally land on the CPU that is mapped to the corresponding hardware queue, or at least on the same NUMA node. If `irqbalance` moves them elsewhere, completion processing competes with application work on a CPU that has no warm state for the request. The result is not a catastrophic slowdown, but it is a persistent tax. For isolated CPUs, the tax can become the dominant effect: an isolated CPU may still be in the block layer's CPU map, may still receive completion softirqs, and may still be interrupted unless IRQ affinity is set explicitly. `isolcpus` does not rewrite blk-mq's CPU map for you. Verify the map, verify the interrupt placement, and verify that the isolated CPU is not quietly doing completion work for a queue it does not own.

Hyperthreads make the shape more complicated. Each logical CPU appears separately in the block layer's CPU map, so two siblings on the same physical core can be mapped to different hardware queues and can submit I/O concurrently. They share execution resources, however, and completion softirqs on one sibling can slow application work on the other. A machine with 128 logical CPUs and 64 hardware queues may look well provisioned by queue count while still suffering because the queue-to-core mapping ignores sibling relationships. The debugfs view shows logical CPUs, not physical cores. Translating between the two is part of reading the shape correctly.

## Virtual Queues and the Scheduler You Cannot See

On a virtual machine, the block layer's queue shape is real but incomplete. A `virtio-blk` device can expose multiple virtqueues, and each virtqueue appears to the guest as a hardware queue. The guest's blk-mq layer maps vCPUs to those virtqueues and allocates tags as usual. From inside the guest, everything looks like a normal multi-queue device. Outside the guest, each virtqueue is serviced by a host-side backend, often a `vhost` worker thread or a userspace process. The host schedules those workers, the host schedules the physical device, and the host may impose its own queue depth, throttling, or quality-of-service policy. The guest's queue depth is therefore an *advertised* depth, not a guarantee of host-side parallelism.

This is not a reason to ignore guest tuning. It is a reason to interpret guest measurements carefully. If a guest sees high tag utilization and low throughput, the bottleneck may be the host's worker scheduling, the host's storage backend, or a rate limit applied outside the guest's view. If the guest sees low tag utilization, the problem is more likely local: too few outstanding requests from the application, a scheduler that is not dispatching, or a completion CPU that cannot keep up. The distinction matters because the fixes are in different places. Adding guest queues helps only if the host backend can service them in parallel and the physical device has the capacity to absorb the extra concurrency.

`virtio-scsi` adds another layer because it routes through the SCSI midlayer. The SCSI layer has its own queue depth, its own tag allocation, and its own error handling. The guest may see a queue depth derived from the host's `can_queue` and `cmd_per_lun` settings, and the effective depth may be lower than the number of virtqueues suggests. `virtio-blk` is simpler and often faster for pure block I/O, but it offers less of the SCSI command set. The choice between them is a choice about which layer should own the queueing policy, and that choice is visible in the block layer's behavior.

Cloud block storage makes the same point at a larger scale. A cloud volume may advertise a burst IOPS rate, a sustained IOPS rate, and a throughput ceiling, all enforced by token buckets outside the guest. The guest's blk-mq layer can have a deep tag space and a `none` scheduler, and the application can issue thousands of asynchronous requests, but the volume will still be limited by the provider's admission control. When the burst credits run out, latency rises and throughput falls, often in a step function that looks like a device failure. The block layer is not misbehaving; it is discovering a limit that lives in another administrative domain. Recognizing this pattern is part of reading the queue: a sudden, repeatable change in latency at a fixed IOPS level is more likely a throttling boundary than a scheduler problem.

Virtualization also changes the value of polling. In a guest, interrupt delivery involves the hypervisor, and the cost of a virtual interrupt can be higher and more variable than a physical one. Polling can avoid some of that cost, but it burns vCPU time that the host may be overcommitting. On an overcommitted host, a guest that busy-polls for I/O completions can starve its own application threads and increase the host's scheduling pressure. The right choice depends on the host's CPU overcommit ratio and on whether the guest's vCPUs are pinned. There is no universal setting, and the block layer's polling knobs are not a substitute for understanding the host's scheduling behavior.

## Little's Law and the Knee of the Latency Curve

Most queueing arguments in storage can be reduced to one identity: the number of requests in a stable system equals the arrival rate multiplied by the average time each request spends in the system. In symbols, `L = λW`. Here `L` is concurrency, `λ` is throughput, and `W` is latency. The identity is not an approximation; it is a conservation law for any stable system. It is also the fastest way to check whether a performance claim is internally consistent. If a device is doing 100,000 IOPS at an average latency of 200 microseconds, there must be about 20 requests in flight on average. If the application is issuing one synchronous request at a time, the device cannot be doing 100,000 IOPS unless each request completes in 10 microseconds, and even then the application is the limiting factor.

This identity explains why queue depth tuning is really concurrency tuning. A deep tag space is useful only if there are enough outstanding requests to fill it. A scheduler that reorders requests is useful only if there is a queue to reorder. An application that issues synchronous I/O has a concurrency of one, and no amount of block-layer configuration changes that. The first diagnostic question for a slow storage workload is therefore not which scheduler is active. It is how many requests the application actually keeps outstanding. `fio` with `iodepth=1` and `iodepth=64` answers that question in a way that no amount of `iostat` output can.

The second diagnostic question is where the system sits on the latency curve. For a simple queue, response time rises slowly while utilization is low and then rises sharply as utilization approaches one. Real devices are more complex, but the shape is familiar: there is a knee beyond which additional concurrency buys almost no throughput and costs a great deal of latency. Before the knee, adding outstanding requests increases throughput almost linearly. After the knee, the device is saturated, queues build, and the only thing that increases is waiting time. The knee is the operating point a throughput-oriented workload wants to approach and a latency-oriented workload wants to stay well below.

The knee is also where tail latency becomes the real story. Average latency can look acceptable while the ninety-ninth percentile is an order of magnitude worse, because queueing amplifies variance. A request that arrives just behind a burst waits for the entire burst to drain. A request that is unlucky enough to hit a garbage-collection pause or a host-side throttling window waits even longer. Schedulers can reduce tail latency by prioritizing certain classes of I/O or by limiting concurrency, but they do so at a cost. `mq-deadline` bounds read latency by dispatching reads first, which can delay writes. `kyber` limits concurrency to keep latency near a target, which can leave device capacity unused during quiet periods. `bfq` provides fairness and interactivity, which costs CPU time that a saturated device may not be able to spare. There is no scheduler that removes the trade-off; there are only schedulers that place the cost where the administrator has decided it is least harmful.

Little's law also gives a sanity check for queue depth settings. If the target is 500,000 IOPS at a target average latency of 100 microseconds, the required concurrency is about 50 outstanding requests. Setting a tag limit far below that guarantees the target is unreachable. Setting it far above that does not increase throughput once the device is saturated; it only increases the number of requests waiting and therefore the tail latency. The useful range is usually narrow, and it is bounded on one side by the device's service rate and on the other by the latency the workload can tolerate.

## A Practical Method for Queue Analysis

Queue analysis works best when it is treated as an experiment rather than a search for a magic sysctl. Start by writing down the objective in measurable terms: maximum throughput at a given percentile latency, minimum p99 latency at a fixed load, or fair allocation among a set of cgroups. These objectives lead to different configurations, and a change that improves one can easily degrade another. Without a stated objective, every tuning result is ambiguous.

Next, inventory the layers that can impose a limit. Record the device's `nr_hw_queues`, the queue depth or tag count, the active scheduler, `nr_requests`, `max_sectors_kb`, `rq_affinity`, the polling settings, the writeback throttling target, and any cgroup I/O limits. Record the CPU topology and the interrupt affinity for the device. This inventory is not busywork; it prevents the common mistake of tuning the scheduler when the real limit is a cgroup bandwidth cap, or adding queue depth when the real limit is a single completion CPU.

Then establish a baseline with a workload that resembles the production pattern. A synthetic benchmark with the wrong read-write ratio, the wrong request size, or the wrong concurrency will produce a configuration that is optimal for the benchmark and irrelevant to the application. Sweep concurrency rather than testing a single depth. The shape of the throughput and latency curves across the sweep is more informative than any single point. Look for the knee, and look for the point where tail latency begins to climb faster than throughput.

Change one variable at a time. If the baseline uses `none`, compare it with `mq-deadline` and `kyber` at the same concurrency and record both throughput and p99 latency, not just IOPS. If the baseline uses a deep queue, test whether reducing `nr_requests` improves tail latency without hurting throughput. If the system has more CPUs than hardware queues, test whether pinning application threads or adjusting interrupt affinity reduces contention on the shared queues. If the workload is write-heavy, check the dirty page limits and writeback throttling before blaming the scheduler; a write stall caused by `balance_dirty_pages()` will not respond to block-layer tuning at all.

Finally, keep the configuration under version control and re-test it when the device, the kernel, or the workload changes. The block layer's defaults are reasonable for general-purpose systems, but they are not a substitute for measurement. The cost of queueing is real, and it is paid in CPU time, memory, and latency. The only way to know which of those costs matters for a particular workload is to measure the queue from the application down to the device and back again.

## The Block Layer and Zoned Storage

Zoned storage devices, such as SMR HDDs and ZNS SSDs, impose a write-ordering constraint that the block layer must respect. Each zone has a write pointer, and writes within a zone must be sequential. The block layer exposes this through the zone block device interface, and blk-mq must ensure that requests to the same zone are not reordered by the scheduler. This is done with a per-zone write lock: when a write request is dispatched to a zone, the zone is locked until the request completes, preventing other writes from being dispatched to that zone. The lock is held in the request queue, and it interacts with the tag allocation because a tag is consumed while the lock is held. The effect is that concurrency is limited by the number of zones, not by the number of tags. A device with many zones can still achieve high concurrency, but a workload that writes to a single zone will be serialized. The `none` scheduler is often used for zoned devices because reordering is prohibited, but `mq-deadline` can still be used if it respects the zone locks. The block layer also supports zone append, where the device assigns the LBA, allowing the host to submit writes without knowing the write pointer. This reduces host-side serialization and can improve throughput. However, zone append is not supported by all devices, and the block layer must fall back to regular writes when it is not. The cost of zone write locking is that it can reduce the effective queue depth, especially for workloads that concentrate on a few zones. Understanding this interaction is important when tuning zoned storage.

## The Block Layer and Device Mapper

Device mapper creates virtual block devices by stacking targets on top of physical devices. Each dm device has its own request queue, and when a bio is submitted to a dm device, it is cloned and remapped to the underlying device. This means that a single I/O can traverse multiple block layers, each with its own queue, tag space, and scheduler. The underlying device's blk-mq layer sees the remapped bio, not the original. This stacking has several consequences. First, the tag space is not shared: a request on the dm device consumes a tag there, and the remapped request consumes a tag on the underlying device. If the dm device is configured with a large `nr_requests`, it can generate more I/O than the underlying device can handle, leading to tag exhaustion and stalls. Second, the scheduler on the underlying device may reorder requests that were already ordered by the dm layer, which can break assumptions made by targets like dm-crypt or dm-thin. Third, the completion path is also stacked: the underlying device completes the request, which then completes the dm request, which then completes the original bio. This adds latency and CPU overhead. For these reasons, stacking dm devices requires careful tuning. It is often best to set the scheduler on the underlying device to `none` and let the dm layer handle any necessary ordering. The `nr_requests` on both layers should be sized so that the underlying device is not overcommitted. Tools like `dmsetup` and `lsblk` can show the stacking relationship, and the block layer's debugfs files show the queues for each layer. Understanding the stacking is essential for diagnosing performance problems in virtualized or encrypted storage.
