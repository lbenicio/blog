Dynamic programming has a reputation for being sequential. The reputation is half deserved. A recurrence such as `F[i][j] = min(F[i-1][j], F[i][j-1]) + c[i][j]` reads like a chain of decisions, and the usual teaching implementation is a pair of nested loops. But the loop is only one topological order of a dependency graph. The graph, not the loop, determines the available parallelism. Once the table is viewed as a DAG, the questions become concrete: what is the width of the dependency frontier, how much work sits on the critical path, and what does it cost to schedule the frontier without destroying locality?

This article is about the engineering of that transformation. It is not a survey of DP problems. It is about a small set of structural techniques that make DP amenable to parallel execution: exposing independent states, transforming associative recurrences into scans, and choosing a schedule whose synchronization cost is smaller than the work it distributes. The techniques interact. A wavefront schedule that is correct on a shared-memory machine can be a poor choice on a distributed-memory machine because barrier cost grows with the number of participants. A parallel scan that is asymptotically superior can be slower than a sequential loop when the operator is cheap and the problem is small.

## The recurrence is a DAG, not a loop

Formally, a DP instance is a set of states S, a set of directed edges E where (u, v) means state v cannot be computed until state u is final, and a cost function for each state. A sequential implementation is a topological order of (S, E). A parallel implementation is a schedule: an assignment of states to processors and time steps that respects the edges. The distinction matters because topological orders are not unique. Different orders expose different amounts of independent work, and different schedules trade synchronization for locality.

Two quantities describe the DAG. The work T1 is the total cost of all states when executed by one processor. The span T∞ is the cost of the longest path, assuming unlimited processors and zero communication. The ratio T1/T∞ is an upper bound on achievable parallelism. Brent's theorem gives a schedule with makespan at most T1/P + T∞ on P processors. That bound is useful for reasoning, but it is not a performance model. It ignores memory bandwidth, synchronization, load imbalance, and the fact that many DP states have data-dependent costs.

The shape of the DAG determines which techniques apply.

A one-dimensional recurrence f[i] = f[i-1] + w[i] is a chain. T∞ = n, and there is no state-level parallelism. The only way to parallelize it is to change the operator: if the operation is associative, the recurrence is a reduction or a scan, and the DAG can be rebalanced into a tree.

A two-dimensional grid recurrence f[i][j] = min(f[i-1][j], f[i][j-1]) + c[i][j] has a frontier of width O(min(n, m)). The anti-diagonals are independent, so the DAG has parallelism proportional to the shorter dimension. This is the canonical wavefront.

An interval DP such as f[i][j] = min over k of f[i][k] + f[k+1][j] + cost(i, j) has O(n^2) states and O(n^3) work. The dependency is on shorter intervals. A level-by-level schedule processes all intervals of a given length; the width is largest at length n/2. The span is O(n) levels, but the work per level is very uneven, and each state's transition is itself a reduction over k. There is parallelism at two levels, and a scheduler must decide whether to exploit one, the other, or both.

A tree DP computes a value at each node from its children. A postorder traversal is sequential, but tree contraction can expose O(log n) span for associative combines. The catch is that tree contraction changes the shape of the computation and requires a representation that supports rake and compress operations.

The DAG abstraction assumes that dependencies are known. In most DP formulations they are, even when the transition costs are data-dependent. Some problems have data-dependent edges: a state may be reachable only through a subset of transitions, or a pruning rule may eliminate states. Then the DAG is known structurally but the effective work is not. Scheduling must be dynamic, and the cost model becomes a distribution rather than a fixed number.

## Three levers for exposing parallelism

There are three distinct ways to make a DP computation parallel, and they are often confused.

The first is state-level parallelism. Compute independent states at the same time. This is the wavefront approach. It preserves the recurrence exactly and does not change the arithmetic. Its cost is synchronization: every frontier is a barrier, and the barrier cost is proportional to the number of participating threads or processes. Its benefit is that the work per state is unchanged.

The second is transition-level parallelism. Split the work inside a single state. In interval DP, the min over k can be computed by a parallel reduction. In knapsack, the transition over items is sequential, but the capacity dimension can be processed in parallel if the update order is preserved. Transition-level parallelism reduces the span of a state but adds reduction overhead. It is most useful when the transition cost dominates the state count, and when the reduction is large enough to amortize the synchronization.

The third is algebraic parallelism. Replace the recurrence with an associative operation and use a parallel scan or a tree reduction. A linear recurrence f[i] = a[i] * f[i-1] + b[i] becomes a product of 2x2 matrices. The product is associative, so a parallel scan computes all prefixes in O(n) work and O(log n) span. The same idea applies to min-plus recurrences, shortest paths in a DAG with bounded treewidth, and regular-language recognition. The transformation is exact only when the operator is associative and the arithmetic is associative. Floating-point addition is not associative, so the transformed computation may produce a different result from the sequential one.

These levers are not exclusive. A wavefront schedule can use transition-level parallelism inside each state. An algebraic transformation can be combined with blocking to improve locality. The engineering question is which lever gives the best return for the synchronization budget.

## Wavefront scheduling in practice

The wavefront schedule for a two-dimensional grid is simple to describe. Assign each state a level equal to i + j. All states on the same level are independent, because every dependency goes from level s to level s+1. Process levels in order, and within a level process states in parallel.

```c
for (int s = 0; s <= n + m - 2; ++s) {
    int lo = max(0, s - (m - 1));
    int hi = min(n - 1, s);
    #pragma omp parallel for schedule(static)
    for (int i = lo; i <= hi; ++i) {
        int j = s - i;
        F[i][j] = combine(F[i-1][j], F[i][j-1]) + c[i][j];
    }
}
```

The code is correct and usually disappointing. The loop has a barrier at every level, so there are O(n + m) barriers. The amount of work per level rises from 1 to min(n, m) and then falls, so a static schedule leaves threads idle at the ends of the wavefront. The memory access pattern is diagonal, which is unfriendly to row-major layouts and to hardware prefetchers. And the parallel loop body is tiny, so the barrier and loop overhead can exceed the useful work.

Tiling addresses the first and third problems. Partition the table into B x B tiles. The tile DAG has edges from the tile above and the tile to the left. Process tiles in wavefront order, and process the interior of each tile sequentially or with vectorized code. The number of barriers drops by a factor of B, and each tile is cache-resident if B is chosen to fit the working set. The halo of the tile, one row and one column, must be available before the tile starts. For a stencil-like DP, the halo is small; for a recurrence with longer dependencies, the halo may be a band.

Skewed tiling is the standard refinement for stencil computations. Transform the coordinates so that the tile dependencies become axis-aligned, then schedule tiles in a rectangular wavefront. The transformation changes which tiles are adjacent in memory, so it is a locality optimization as much as a scheduling one. For DP, skewing can reduce the number of tiles on the critical path, but it can also increase the halo size and the amount of redundant computation at tile boundaries.

The choice between static and dynamic scheduling depends on the variance of tile cost. If every state has the same cost, a static wavefront assignment is fine. If costs are data-dependent, work stealing over tiles is better, but the steal must respect the tile DAG. A common compromise is to assign tiles to threads in a blocked wavefront order and let threads steal only from the next wavefront. This keeps the dependency invariant simple and limits the steal granularity.

On distributed memory, the wavefront becomes a communication pattern. A 2D block distribution assigns each process a rectangular subgrid. A process can compute its interior tiles independently, but it needs halo rows and columns from its neighbors. The wavefront order determines when those halos are produced. If the subgrids are square, the wavefront is a diagonal of processes; if they are thin, the wavefront is a line. The communication volume is proportional to the perimeter, and the latency is proportional to the number of wavefront steps. At large scale, the latency term dominates, and a pipelined schedule that overlaps communication with computation is necessary.

## The associativity escape hatch

The most powerful transformation is also the most fragile. If a recurrence is a scan over an associative operator, it can be evaluated with a parallel scan. The classical Blelloch scan performs O(n) work and O(log n) span; the Hillis-Steele scan performs O(n log n) work and O(log n) span but has a simpler communication pattern. The choice matters when work is cheap and synchronization is expensive.

Linear recurrences are the canonical example. The recurrence f[i] = a[i] f[i-1] + b[i] can be written as a matrix product:

```text
[ f[i] ]   [ a[i]  b[i] ] [ f[i-1] ]
[ 1    ] = [ 0     1    ] [ 1      ]
```

The 2x2 matrices compose associatively. A parallel scan of the matrices yields all prefixes. The same construction works for min-plus recurrences, where the matrix product uses addition and minimum instead of multiplication and addition. It also works for regular-language recognition, where the matrices are transition matrices of a finite automaton.

The fragility is in the operator. Associativity is a mathematical property; the implementation must preserve it. Floating-point addition is not associative, so a parallel scan over floating-point values can produce a different result from a sequential scan. For DP with floating-point costs, the difference can change which path is selected, not just the last bit. Reproducibility requires a fixed reduction tree, compensated arithmetic, or a deterministic order that defeats some of the parallelism. This is a real trade-off, not a theoretical nicety.

The next section turns to a concrete case where these levers collide: sequence alignment, where the recurrence is a grid, the transition cost is data-dependent, and the output is a path rather than a single value.

## Sequence alignment as a grid with a traceback

Sequence alignment is the canonical DP that refuses to stay a pure grid. The scoring recurrence for global alignment is still a grid, but the recurrence is not the only output. The score is a scalar; the alignment is a path. The score computation can be parallelized with wavefronts, but the traceback is a serial walk from the bottom-right corner to the top-left. That asymmetry shapes every parallel implementation.

For affine gap penalties, the state space expands. Instead of one value per cell, there are three: match, insert, delete. The dependencies are still local, but the diagonal wavefront now carries three values per cell. The insert state depends on the cell above, the delete state on the cell to the left, and the match state on the diagonal. All three are available on the previous anti-diagonal, so the wavefront schedule remains valid. The arithmetic per cell increases, which improves the arithmetic intensity and makes the parallel loop body less trivial. The barrier count is unchanged.

The traceback is the hard part. A naive parallel score computation followed by a sequential traceback leaves the machine idle for the traceback phase. The traceback length is O(n + m), which is small compared to the O(nm) score computation, but it is latency-bound and hard to parallelize. Checkpointing is the usual fix: store the score matrix at a coarse granularity, then recompute the intervening cells during traceback. This trades memory for computation. The recomputation can itself be parallelized, but the traceback path is still a chain.

Hirschberg's algorithm removes the memory bottleneck by computing the score in linear space and using divide-and-conquer to find the alignment. The algorithm computes forward and backward score vectors, finds the split point, and recurses on two subproblems. The subproblems are independent, so the recursion tree has parallelism. The span is O(n log n) if the score computations are sequential, or O(n) if they are parallelized. The work remains O(nm). Hirschberg is a classic example of algebraic restructuring: it changes the order of computation to reduce memory, and in doing so it exposes a different parallel decomposition.

## Tiling and skewing in alignment

The wavefront schedule for alignment is diagonal. On a row-major matrix, a diagonal access pattern is a strided access pattern. Every cell on the anti-diagonal touches a different row, so the cache lines fetched for one cell are not reused by its neighbors on the same diagonal. The next diagonal reuses the same rows, but the access order is reversed. This is exactly the pattern that hardware prefetchers handle poorly.

Tiling fixes the locality problem. Partition the score matrix into square tiles. A tile depends on the tile above, the tile to the left, and the tile diagonally above-left. The tile DAG is a grid with diagonal edges. Process tiles in a wavefront order. Inside a tile, the computation is sequential or vectorized, and the tile's working set fits in cache. The halo is one row and one column, plus the diagonal corner. The halo size is O(B), and the computation per tile is O(B^2), so the communication-to-computation ratio is O(1/B). This is the standard cache-blocking argument.

Skewing changes the tile coordinates so that the diagonal dependencies become axis-aligned. Let the new coordinates be u = i + j and v = i - j. The tile DAG becomes a rectangular grid in (u, v) space. The wavefront is now a wavefront of tiles in the transformed space. Skewing can reduce the number of synchronization steps and improve the locality of the tile schedule. The cost is that the tile shape is a parallelogram, and the halo is no longer a simple row and column. The skewing transformation is exact for the score computation, but the traceback must be mapped back to the original coordinates.

On GPUs, the wavefront is often implemented with a kernel launch per anti-diagonal. The launch overhead and the small amount of work per diagonal make this inefficient for long sequences. A better approach is to use a tiled kernel with a persistent thread block that processes a sequence of tiles along the wavefront. The block reads its halo from global memory, computes the tile, and writes the result. The dependency between tiles is enforced by a global counter or a semaphore. This is a software pipeline. The wavefront is no longer a barrier; it is a dataflow dependency.

## Banded and sparse recurrences

Many alignment problems do not need the full matrix. If the sequences are similar, the optimal alignment stays near the main diagonal. A banded DP computes only cells within a band of width w around the diagonal. The work drops from O(nm) to O(nw). The parallelism drops as well. The wavefront width is at most w, and the number of wavefront steps is O(n). The banded DAG is a chain of anti-diagonals of length w. The span is O(n), and the work is O(nw). The parallelism is O(w). For small w, the wavefront is too narrow to keep many processors busy. The alternative is to parallelize over the band's cells in a different way, or to use a parallel scan along the band.

Sparse DP is more irregular. In LCS, the only cells that can change the score are those where the two characters match. The dependency DAG can be restricted to the match points. Each match point depends on the best score from the previous match points in the upper-left quadrant. This is a dominance problem. The DAG is a partial order, and the wavefront is a set of match points with the same i + j. The width is the number of match points on an anti-diagonal, which can be much smaller than the matrix dimension. The work is proportional to the number of matches, plus the cost of the dominance queries. This is a classic example of a DP whose effective DAG is data-dependent. The scheduler must handle a variable number of tasks per wavefront.

## Bit-parallel and blocked methods

Bit-parallel methods pack multiple DP cells into a single machine word. The Myers algorithm for edit distance uses bitwise operations to compute an entire column in O(1) word operations. The parallelism is at the bit level, not the thread level. The work per column is O(n / w), where w is the word size. The span is O(m) columns. This is a different kind of parallelism, and it is often the fastest option for short sequences. For long sequences, the bit-parallel method can be combined with wavefront parallelism: process multiple columns in parallel, each using bit-parallel operations.

The Four Russians technique is another way to reduce work. It precomputes the transition for a block of cells. The block transition is a function from the input boundary to the output boundary. If the block is small, the function can be tabulated. The DP then becomes a sequence of block transitions. The block transitions are associative, so they can be composed in a parallel scan. This is the algebraic lever again. The precomputation cost is exponential in the block size, so the block size must be small. The method is most effective for bit-vector DP, where the state is a single word.

## Traceback and output-sensitive parallelism

The traceback is a path in the DP matrix. The path is a sequence of moves. The moves are not known until the score matrix is computed. The traceback can be parallelized by divide-and-conquer: find a point on the optimal path, then recursively trace the two halves. The point can be found by computing the forward and backward score vectors and finding the split that maximizes the sum. This is Hirschberg's algorithm. The recursion tree has O(n) leaves, and each level of the recursion does O(nm) work. The span is O(n log n) if the score computations are sequential, or O(n) if they are parallelized. The work is O(nm log n) if the split point search is not optimized. The standard implementation uses a linear-space score computation and a single split, so the work is O(nm) and the span is O(n log n).

The traceback can also be parallelized by checkpointing. Store the score matrix every k rows. During traceback, recompute the block between checkpoints. The recomputation is parallel. The traceback path is still sequential, but the recomputation dominates the cost. The checkpoint interval controls the memory-time trade-off. This is a common pattern in sequence alignment: the score computation is parallel, the traceback is sequential, and the checkpointing bridges the two.

## Load balancing and scheduling for irregular DP

The wavefront schedule is static when the work per cell is uniform. In alignment, the work per cell is uniform for a fixed scoring scheme, but the effective work can vary if the implementation prunes. X-drop pruning stops extending an alignment when the score drops below the best score by more than X. The pruned cells are not computed. The effective DAG is irregular. The wavefront has holes. A static schedule will assign work to threads that have nothing to do. A dynamic schedule is needed. The scheduler can use a work-stealing queue with dependencies. Each task is a tile. The task is ready when its dependencies are satisfied. The scheduler maintains a ready list. This is a general DAG scheduler.

The overhead of dynamic scheduling is significant for small tiles. The tile size must be large enough to amortize the scheduler overhead, but small enough to balance the load. The optimal tile size depends on the variance of the work. For X-drop, the variance can be high. A common approach is to use a two-level schedule: a static wavefront of large tiles, and dynamic work stealing within each tile. The static schedule enforces the global dependencies; the dynamic schedule balances the work inside the tile.

On distributed memory, the wavefront is a communication pattern. The processes are arranged in a grid. The wavefront is a diagonal of processes. Each process computes its tile and sends the halo to its neighbors. The communication is point-to-point. The latency is hidden by pipelining. The wavefront schedule is a pipeline: process p computes tile (i, j), then sends the halo to process p+1, which computes tile (i+1, j) or (i, j+1). The pipeline depth is the number of wavefront steps. The throughput is limited by the slowest process. Load balancing is critical. If the work is uniform, the pipeline is efficient. If the work is irregular, the pipeline stalls.

The limits of dependency-parallel recurrences are visible in these examples. The wavefront schedule exposes state-level parallelism, but the barrier cost and the diagonal memory access limit its scalability. Tiling and skewing reduce the synchronization cost, but they do not change the span. The algebraic transformations change the span, but they require associativity and they may change the result. The traceback is a sequential bottleneck that can be hidden by recomputation, but not eliminated. The next section moves from grids to trees, where the dependency graph is a tree and the wavefront is a postorder traversal.

## Tree DP and the postorder bottleneck

Tree dynamic programming is where the dependency graph stops looking like a grid and starts looking like a hierarchy. A typical recurrence is

```text
F[v] = combine over children c of (F[c] + w(v, c))
```

where combine is associative and commutative, or at least associative with a fixed child order. The dependencies point from children to parents. A postorder traversal is a topological order. The work is O(n). The span is the height of the tree, because the longest dependency chain runs from a leaf to the root. A balanced binary tree has height O(log n) and enormous width at the lower levels. A path has height O(n) and width one. The same recurrence can therefore be embarrassingly parallel or hopelessly sequential depending on the shape of the input.

The first parallel schedule for tree DP is a level-by-level traversal by height. Compute all leaves, then all nodes whose children are leaves, and so on. Nodes at the same height are independent. The frontier is the set of nodes whose children have all been finalized. The number of barriers is the height of the tree. For a balanced tree this is O(log n), which is attractive. For a deep tree it is O(n), which is fatal. The work per level is also uneven. In a balanced tree, the bottom level contains half the nodes and the top level contains one. A static assignment of levels to threads leaves most threads idle near the root. A dynamic ready queue is better: each node has a counter of unfinished children. When a child finishes, it decrements the parent counter. When the counter reaches zero, the parent is pushed onto a ready queue. Workers pop ready nodes and compute them. This is a standard dataflow schedule. It respects the DAG without a global barrier, and it adapts to irregular tree shapes.

The ready-queue schedule has its own costs. The counter update is an atomic operation or a reduction. The ready queue is a concurrent data structure. The parent combine may need to accumulate child values in a deterministic order, which conflicts with the order in which children finish. If the combine is not commutative, the implementation must either enforce an order or store child results and combine them in a second pass. That second pass is another traversal, and it may dominate the cost for small states. For large states, the combine itself is the bottleneck, and the scheduling overhead is amortized.

Memory behavior is another constraint. A postorder traversal visits a subtree contiguously if the tree is laid out in DFS order. A parallel ready-queue schedule visits nodes in an order determined by completion times, which can scatter accesses across the heap. The working set becomes the entire frontier, not a single subtree. For trees with large per-node state, this can destroy locality. A common compromise is to process subtrees sequentially below a cutoff size and only parallelize above it. The cutoff is chosen so that the sequential subtree fits in cache and the parallel tasks are large enough to amortize scheduling. This is the same granularity argument as tiling in grid DP, but the tile shape is a subtree rather than a square.

### Tree contraction as algebraic rebalancing

Tree contraction is the algebraic escape hatch for trees. The idea is to repeatedly remove leaves and degree-two nodes, composing the functions they represent, until the tree collapses to a small core. The two primitive operations are rake and compress. Rake removes a leaf and folds its contribution into its parent. Compress removes a degree-two node and composes the functions on its two incident edges. Each operation preserves the function computed by the remaining tree. After O(log n) rounds, the tree has constant size, and the final function can be evaluated. The span is O(log n), and the work is O(n) if the operations are constant-time.

The catch is the function representation. In a tree reduction where each node contributes a scalar and the combine is addition, the function is a scalar addition, and contraction is trivial. In a tree DP where each node has a small state, such as independent set with two states per node, the function is a small matrix or a pair of values, and contraction is still practical. In a tree knapsack, the state is a capacity profile, and the combine is a max-plus convolution. The function is a vector of length C, and composing two functions costs O(C^2) or O(C log C) depending on the structure. Contraction then has work O(n C^2) and span O(log n), which may be worse than a sequential O(n C) algorithm. The algebraic lever is only as good as the state representation.

There is a second catch: contraction changes the order of arithmetic. For floating-point costs, the result may differ from the sequential postorder. The same reproducibility problem that appears in parallel scans appears here. If the DP is used to select a path, a tiny difference can change the selected path. Deterministic contraction is possible by fixing the rake and compress order, but that reduces the available parallelism. The trade-off is between reproducibility and speed.

Tree contraction is most effective when the tree is balanced or when the contraction can be applied to a heavy path. It is less effective on star graphs, where the root has many children and no degree-two nodes to compress. A star graph has span one for the root combine if the combine is a parallel reduction over children, but the reduction itself has O(log n) span. The work is O(n). This is the same as a parallel reduction, and it is the best possible for a commutative combine. For a non-commutative combine, the star graph is a sequential chain of child combinations unless the combine is associative and can be rebalanced. Associativity is again the limiting property.

## Euler tours and heavy-light decompositions

An Euler tour flattens a tree into a sequence. Each node appears when it is entered and when it is exited. Subtree queries become contiguous intervals. If the tree DP is a reduction over the subtree, the Euler tour turns it into a range reduction, which can be computed with a parallel scan or a segment tree. This is a different decomposition from tree contraction. It does not change the arithmetic; it changes the memory layout and the scheduling. The scan has O(n) work and O(log n) span. The tree shape no longer matters for the span, only the associativity of the reduction. For a tree prefix sum, this is ideal. For a tree DP with a non-associative combine, the Euler tour does not help.

Heavy-light decomposition is a more general technique for path-like recurrences. The tree is decomposed into heavy paths, where each node chooses its heaviest child. The number of light edges on any root-to-leaf path is O(log n). A DP along a heavy path is a linear recurrence, which can be evaluated with a parallel scan. The light edges connect the paths. The computation proceeds in two phases: first compute the path-local functions, then combine them across light edges. The span is O(log^2 n) if the path scans use O(log n) span and there are O(log n) light edges. The work is O(n). This is a powerful result: a tree DP that looks sequential along a path can be parallelized by decomposing the tree into paths and using associative scans.

The practical difficulty is that heavy-light decomposition is data-dependent. The heavy child is determined by subtree sizes, which are themselves computed by a DP. The decomposition must be computed before the main DP, and that computation is a tree reduction. It can be parallelized with tree contraction or a parallel postorder. The overhead is acceptable for large trees but significant for small ones. The method also requires that the path recurrence be expressible as an associative operation. For min-plus path DP, the operation is matrix multiplication over the min-plus semiring, which is associative. For more complex states, the matrices grow, and the scan becomes expensive.

## Nested parallelism and the cost of barriers

Tree DP naturally suggests nested parallelism. A node can spawn tasks for its children, wait for them, and then combine. This is fork-join parallelism. It exposes the full width of the tree without a global barrier. The catch is that nested parallelism can oversubscribe the machine. If every internal node spawns a task, the number of tasks is O(n), and the scheduler must manage them. Work-stealing runtimes handle this well, but the overhead per task is nonzero. A cutoff is necessary: below a certain subtree size, execute sequentially. The cutoff should be chosen so that the sequential work per task is much larger than the steal overhead, and so that the subtree's working set fits in cache.

Barriers appear when the schedule is level-synchronized. A level-synchronized tree DP has a barrier at each height. The barrier cost grows with the number of threads. For a balanced tree, the height is O(log n), so the number of barriers is small. For a deep tree, the number of barriers is O(n), and the barrier cost dominates. The ready-queue schedule avoids global barriers but introduces atomic operations and queue contention. The choice depends on the tree shape and the state size. If the state is small, atomics are cheap and the ready queue is fine. If the state is large, the combine dominates and barriers may be acceptable.

Memory locality interacts with nesting. A depth-first layout keeps subtrees contiguous, which is good for sequential execution and for nested parallelism that processes subtrees independently. A breadth-first layout keeps levels contiguous, which is good for level-synchronized schedules. A hybrid layout can store the top levels in breadth-first order and the bottom subtrees in depth-first order. The top levels are where the parallel schedule needs to distribute work; the bottom subtrees are where sequential locality matters. This is a layout optimization that mirrors the schedule.

## From trees to general DAGs

Trees are a special case of DAGs. General DP DAGs can be grids, hypergraphs, or arbitrary dependency graphs. Scheduling a general DAG on parallel machines is NP-hard, but DP DAGs often have structure. Bounded treewidth is the most common structure. A tree decomposition maps the DAG onto a tree of bags. Each bag contains a set of states that must be processed together. The width of the decomposition bounds the state size and the amount of communication between bags. Dynamic programming over a tree decomposition is a tree DP whose states are tables over the bag. The parallel techniques for tree DP apply: process the decomposition tree in postorder, use tree contraction if the bag operations are associative, or use a ready queue if the tree is irregular.

The treewidth also bounds the available parallelism. If the treewidth is small, the bags are small, and the combine operations are cheap. The frontier between bags is small, so the communication is small. If the treewidth is large, the bags are large, and the combine operations dominate. The parallelism at the bag level is limited by the number of bags, which is O(n). The parallelism inside a bag is limited by the bag size. For a grid, the treewidth is O(min(n, m)), which matches the wavefront width. For a tree, the treewidth is one. For a complete graph, the treewidth is n, and there is no useful decomposition. The limits of dependency-parallel recurrences are therefore graph-structural limits. You cannot schedule your way out of a dense dependency graph.

Context-free grammar parsing is another example. The CYK algorithm fills a triangular chart. Each cell depends on pairs of smaller cells. The dependency graph is an interval DP. The wavefront is by interval length. The work is O(n^3), and the span is O(n) if each cell's transition is sequential. Transition-level parallelism can reduce the span of a cell to O(log n), but the overall span remains O(n) because the interval lengths are sequential. The same is true for matrix-chain multiplication and optimal binary search trees. The algebraic transformation can rebalance the transition, but it cannot remove the length dependency. This is a fundamental limit: if the recurrence depends on all smaller intervals, the length dimension is a chain.

The practical lesson is to identify which dimension is the chain and which dimensions are parallel. In a grid, the anti-diagonals are parallel. In an interval DP, the interval length is the chain, and the split point is the parallel reduction. In a tree, the height is the chain, and the children are the parallel reduction. In a general DAG, the critical path is the chain, and the ready set is the parallel frontier. The scheduler's job is to keep the frontier full without paying more in synchronization than the frontier work is worth. That is the same trade-off at every scale, from a single cache block to a distributed cluster.

## Scheduling without global barriers

The wavefront schedule described earlier is a barrier-synchronized schedule. Every anti-diagonal ends with a barrier, and every thread must wait for the slowest thread on that diagonal before starting the next. That is simple to reason about, but it is not the only option. A dataflow schedule treats each tile as a task with a predecessor count. When a predecessor finishes, it decrements the count. When the count reaches zero, the tile becomes ready and is pushed onto a ready queue. Workers pop ready tiles and execute them. There is no global barrier. The synchronization is per-tile, and it is proportional to the number of dependencies rather than the number of threads.

The dataflow approach has a different cost profile. It replaces barrier latency with atomic operations and queue contention. If tiles are large, the atomic cost is negligible. If tiles are small, the atomics become the bottleneck. The queue itself must be concurrent, and a naive lock-based queue will serialize. Work-stealing deques reduce contention because most operations are local, but dependency counters still require atomics or memory fences. The producer of a halo must ensure that the data is visible to the consumer before the consumer sees the decremented counter. That means a release fence on the producer side and an acquire fence on the consumer side. On weakly ordered architectures, these fences are not free. They can cost as much as a small barrier if they are issued too frequently.

A practical compromise is hierarchical synchronization. Within a thread block, use shared memory and barriers. Across blocks, use a global counter and a flag. The intra-block barrier is cheap because it is hardware-supported and the block is small. The inter-block dependency is coarse-grained because it happens once per tile. This is the structure of many persistent GPU kernels: a block processes a sequence of tiles, and a global atomic counter tells it which tile is ready. The block does not spin on the counter for every cell; it spins once per tile. The halo is read from global memory after an acquire fence.

The granularity of a task is the central tuning knob. A task that is too small pays more in synchronization than it earns in parallelism. A task that is too large creates load imbalance and reduces the number of tasks available to steal. For DP tiles, a useful rule is that the task should contain at least a few thousand arithmetic operations. A 32x32 tile with a simple min-plus transition contains about a thousand operations, which is marginal. A 64x64 tile contains four thousand, which is comfortable. The exact threshold depends on the machine. On a GPU, the threshold is higher because the cost of a global atomic is higher. On a CPU, the threshold is lower because the cache hierarchy can hide some of the latency.

The shape of the task matters as well. A square tile has a favorable surface-to-volume ratio: the halo is O(B) and the work is O(B^2). A long thin tile has a larger halo relative to its work, so it communicates more per cell. A skewed tile can change the dependency pattern so that the halo is smaller in one direction and larger in another. The best shape depends on the memory layout and the direction of the wavefront. If the matrix is stored in row-major order, a tile that spans several rows and a few columns may have better spatial locality than a square tile, because the rows are contiguous. The wavefront moves diagonally, so the tile shape should be chosen to make the diagonal access pattern as close to row-major as possible.

## A cost model for wavefront schedules

A simple cost model helps to decide between schedules. Let the DP have N states, each with cost c. Let the wavefront have L levels, and let the maximum number of states on a level be W. With P processors, the ideal time is Nc/P. The wavefront time is approximately L * (max_level_work / P + S), where S is the synchronization cost per level. If W < P, then max_level_work / P is less than c, and processors idle. The efficiency is W/P. This is why wavefront schedules are inefficient at the beginning and end of the table, where the diagonal is short. Tiling does not change W, but it reduces L by a factor of B and increases the work per level by a factor of B^2. The synchronization term L*S drops by B, which is the main benefit.

The memory term is often larger than the synchronization term. A simple grid DP reads two values and writes one value per cell. The arithmetic is one addition and one min. The arithmetic intensity is roughly one operation per three memory accesses. That is firmly memory-bound on most processors. The wavefront diagonal access pattern makes it worse because each cell on a diagonal belongs to a different row. The cache lines fetched for one cell are not reused by its neighbors on the same diagonal. The next diagonal reuses the same rows, but the access order is reversed, so the prefetcher may not recognize the pattern. Tiling converts the diagonal access into a sequence of row-major accesses inside a tile. The tile's working set fits in cache, so the memory traffic is reduced to the halo. The halo is O(B) per tile, and the tile has O(B^2) cells, so the traffic per cell is O(1/B). This is the same cache-blocking argument that applies to matrix multiplication and stencil codes.

Skewing can improve the memory pattern further. In a skewed tiling, the tile coordinates are transformed so that the wavefront becomes axis-aligned. The tiles are then visited in a rectangular order. The memory accesses inside a tile are still row-major, but the tile boundaries are slanted. The halo is no longer a simple row and column; it is a parallelogram. The halo size may increase, and the redundant computation at the boundaries may increase. The trade-off is between a better global schedule and a larger local halo. For long sequences, the better global schedule usually wins because the halo overhead is amortized over many tiles. For short sequences, the halo overhead may dominate.

The cost model should also account for the reduction inside a state. In an interval DP, each state performs a min over k. The reduction has cost O(length). The state-level wavefront parallelizes over intervals of the same length, but the reduction inside each interval is independent. If the reduction is done sequentially, the span of a state is O(n), and the overall span is O(n^2) if the lengths are sequential. If the reduction is parallelized, the span of a state drops to O(log n), but the work increases by a constant factor due to the reduction tree. The overall span is still O(n) because the length dimension is a chain. This is a common pattern: transition-level parallelism reduces the span of a state, but it cannot remove the chain in the state dimensions. The chain is a structural property of the recurrence, not an artifact of the implementation.

## Decoupled look-back and single-pass scans

The parallel scan is the algebraic escape hatch for linear recurrences. The classical Blelloch scan is work-efficient but requires two passes over the data and a global synchronization between them. The Hillis-Steele scan is simpler but does O(n log n) work. On modern GPUs, a third option is often better: the decoupled look-back scan. Each block computes the reduction of its segment and publishes it with a flag. Then each block looks back at the preceding blocks to find the exclusive prefix. When it finds a block that has already computed its inclusive prefix, it adds that value and publishes its own. The look-back is decoupled because blocks do not wait for all preceding blocks to finish; they only wait for the ones they need. The result is a single-pass scan with O(n) work and O(log n) span, and no global barrier.

The decoupled look-back pattern applies to any associative operator. For DP, the operator might be a min-plus matrix product, a max-plus convolution, or a regular-language transition. The look-back requires that the operator be associative and that the partial results be stored in a form that can be combined. The memory fence and atomic flag protocol is delicate. The flag must be set after the partial result is visible. The look-back must read the flag before reading the partial result, and it must handle the case where the flag is not yet set. This is a spin-wait, but the wait is short because the preceding block is likely to finish soon. The decoupled look-back is a form of speculative execution: a block may look back at several blocks before it finds one with a final prefix. The number of look-backs is bounded by the number of blocks, but in practice it is small.

For DP, the decoupled look-back can be used along a chain dimension. If the recurrence is a scan along the rows of a matrix, and the operation is associative, then the rows can be processed with a single-pass scan. The columns are independent, so they can be processed in parallel. This is a two-dimensional parallelization: one dimension uses a scan, the other uses independent tasks. The combination can be more efficient than a wavefront because it avoids the barrier per anti-diagonal. The catch is that the scan requires the operator to be associative. If the recurrence is not associative, the scan is not exact. For many DP problems, the recurrence is a min-plus matrix product, which is associative. For others, such as those with non-associative tie-breaking or floating-point accumulation, the scan may change the result.

## Case study: Viterbi decoding

The Viterbi algorithm is a dynamic program over a sequence and a state space. The recurrence is

```text
dp[t][s] = max over s' of (dp[t-1][s'] + trans[s'][s]) + emit[s][o_t]
```

The time dimension is a chain. The state dimension is parallel. At each time step, every state depends on all states at the previous time step. The work per time step is O(S^2) for a dense transition matrix. The span is O(T) if the state reduction is parallel, or O(T log S) if the reduction is a tree. The parallelism is O(S^2) per time step, which is large if S is large. This is a case where transition-level parallelism is the primary lever. The wavefront is not over a grid; it is over the state dimension. The time dimension is the chain.

On a GPU, the Viterbi algorithm can be implemented with one kernel launch per time step, but the launch overhead is prohibitive for long sequences. A better approach is a persistent kernel that processes multiple time steps. The state vector is kept in shared memory or registers. The transition matrix is read from global memory, but it is reused across time steps. If the transition matrix is sparse, the work is proportional to the number of edges. The graph is a weighted automaton. The Viterbi update is a max-plus matrix-vector product. For a dense matrix, the product is memory-bound because the matrix is large. Blocking the matrix into tiles and keeping the state vector in shared memory improves reuse.

Beam search prunes the state space to the top B states at each time step. The active set is data-dependent. The work per time step is O(B S) instead of O(S^2) if the transition is sparse, or O(B S) for a dense matrix if only the top B states are considered. The pruning makes the DAG irregular. A static schedule that assigns states to threads will be imbalanced. A dynamic schedule with a ready queue is better. The beam width B controls the parallelism. If B is small, the state dimension is too narrow to keep many processors busy. Then the parallelism must come from batching multiple sequences. In speech recognition, it is common to decode many utterances in parallel. Each utterance is an independent Viterbi chain. The batch dimension provides parallelism when the beam is narrow.

## Case study: knapsack and resource allocation

The 0/1 knapsack recurrence is

```text
dp[i][c] = max(dp[i-1][c], dp[i-1][c - w_i] + v_i)
```

The item dimension is a chain. The capacity dimension is parallel. For each item, all capacities can be updated independently if the previous row is available. The work is O(nC). The span is O(n) if the capacity update is parallel. The parallelism is O(C) per item. This is a simple wavefront with a one-dimensional frontier. The memory access pattern is a shift by w_i, which is not contiguous. If the weights are random, the access is scattered. A tiled implementation can group capacities into blocks and load the previous row into shared memory. The shift is then within the block, and the halo is one block. The halo size is the maximum weight, which can be large. If the weights are large, the halo is large, and the communication-to-computation ratio is poor. In that case, a different decomposition may be better: parallelize over items? No, items are a chain. Parallelize over multiple knapsack instances. This is common in resource allocation: many independent instances can be solved in parallel.

The unbounded knapsack recurrence is

```text
dp[c] = max(dp[c], dp[c - w_i] + v_i)
```

for each item i, and the capacity loop must be ascending. The dependency is from c - w_i to c, which is a chain along the capacity dimension for a fixed item. The item dimension is also a chain. The DAG is a grid with edges that skip by w_i. The wavefront is not a simple anti-diagonal because the edges are not unit steps. The parallelism is limited by the weights. If the weights are small, the chain is dense and the parallelism is low. If the weights are large, the chain is sparse and the parallelism is higher. This is an example where the DAG structure depends on the data. A scheduler that assumes unit dependencies will be wrong.

Resource allocation problems often have a stage dimension and a resource dimension. The stage is a chain, and the resource is parallel. The transition is a max-plus convolution over the resource allocated to the stage. The convolution can be computed with a parallel reduction, but the work is O(C^2) per stage if done naively. The algebraic lever applies if the convolution can be expressed as a min-plus matrix product. The matrix is triangular, and the product is associative. A parallel scan over stages is possible if the matrices are composed. The state size is C, so the matrix is C x C. The composition cost is O(C^3) or O(C^2) for triangular matrices. This is only practical for small C. For large C, the sequential O(nC) algorithm is better. The algebraic transformation trades work for span, and the trade-off depends on the state size.

## Case study: Floyd-Warshall and all-pairs shortest paths

Floyd-Warshall computes the shortest paths between all pairs of vertices in a graph. The recurrence is

```text
dp[k][i][j] = min(dp[k-1][i][j], dp[k-1][i][k] + dp[k-1][k][j])
```

The k dimension is a chain. The i and j dimensions are parallel. The work is O(n^3). The span is O(n) if the i,j update is parallel. The parallelism is O(n^2) per k step. This is a large amount of parallelism, but the memory traffic is also large. The update reads two values and writes one for each (i,j) pair. The access pattern is row-major if the matrix is stored in row-major order. The k-th row and k-th column are broadcast. The broadcast can be kept in cache or shared memory. The barrier per k step is the main synchronization cost. With n steps, the barrier count is n. For large n, the barrier cost can dominate.

Blocked Floyd-Warshall reduces the barrier count. The matrix is divided into tiles. The algorithm proceeds in three phases per block of k: update the diagonal tile, update the tiles in the same row and column, and update the remaining tiles. The diagonal tile update is sequential because it depends on itself. The off-diagonal updates are parallel. The number of barriers is O(n/B) instead of O(n). The diagonal tile update is a small Floyd-Warshall on B vertices, which can be done sequentially or with a parallel algorithm. The off-diagonal updates are matrix operations. This is a standard cache-blocked algorithm. On a GPU, the diagonal tile update can be done by a single thread block, and the off-diagonal updates by many blocks. The dependency between phases is enforced by a global barrier or by separate kernel launches.

The algebraic lever for all-pairs shortest paths is repeated squaring. The min-plus matrix product is associative, so the closure can be computed by repeated squaring in O(log n) matrix multiplications. Each multiplication is O(n^3) work. The total work is O(n^3 log n), which is worse than Floyd-Warshall's O(n^3). The span is O(log n) matrix multiplications, each with O(log n) span if the multiplication is parallelized. The overall span is O(log^2 n). This is a classic trade-off: more work, less span. For small n, Floyd-Warshall is better. For very large n and enough processors, repeated squaring may win. In practice, the extra work usually dominates, and blocked Floyd-Warshall is preferred.

## Data-dependent DAGs and speculative scheduling

The DAGs discussed so far are structurally known. Even when the transition costs are data-dependent, the set of states and the edges are known in advance. Some DP problems have data-dependent edges. X-drop pruning stops extending an alignment when the score falls below a threshold. Beam search keeps only the top B states. Branch-and-bound prunes subproblems whose bound is worse than the best known solution. In these cases, the effective DAG is discovered at runtime. A static schedule cannot know which states will be active. A dynamic scheduler is needed.

The dynamic scheduler can use a work-stealing queue with dependencies. Each state or tile is a task. The task is ready when its dependencies are satisfied. The scheduler maintains a ready list. When a task completes, it checks its successors and pushes the ready ones. The overhead of this scheme is the atomic operations and the queue management. To reduce overhead, tasks are grouped into larger units. A group of states that are likely to be active together can be a single task. If some states in the group are pruned, the task still does the work for the whole group. This is speculative execution: we compute states that might be pruned in order to keep the task granularity coarse. The trade-off is between wasted work and scheduling overhead.

The amount of overcomputation depends on the pruning rate. If the pruning rate is low, speculative execution is cheap. If the pruning rate is high, the wasted work can dominate. A common approach is to use a two-level schedule: a coarse static wavefront of tiles, and within each tile, a dynamic check for pruning. The tile is computed if any of its states are active. The inactive states within the tile are skipped. This keeps the scheduling coarse while allowing fine-grained pruning. The tile size is chosen so that the expected fraction of active states is high enough to justify the tile.

Memory management is another challenge for data-dependent DAGs. The set of active states may be large, and the memory allocation may be dynamic. A pool allocator with fixed-size blocks is common. The pool must be thread-safe. If the states are stored in a hash table, the hash table must support concurrent insertions and lookups. This is a significant engineering effort. For many applications, the data-dependent DAG is sparse enough that a compressed sparse row representation is better. The DP then becomes a graph traversal, and the scheduling problem becomes a graph scheduling problem.

## Reproducibility and numerical determinism

Parallel DP can produce different results from sequential DP even when the algorithm is mathematically identical. The cause is the non-associativity of floating-point arithmetic. A parallel reduction over floating-point values adds them in a different order than a sequential loop. The difference is usually tiny, but in DP the difference can change which transition is selected. If two paths have nearly equal cost, a tiny difference can flip the argmin. The selected path then changes, and the output is different. For applications that require bitwise reproducibility, this is unacceptable.

There are several ways to achieve deterministic parallelism. The simplest is to use integer arithmetic. If the costs are integers, the arithmetic is associative and the result is exact. Many DP problems in bioinformatics use integer scores for this reason. If the costs are floating-point, one can use a fixed reduction tree. The tree is defined by the block size and the reduction order, independent of the number of threads. The parallel reduction then produces the same result as a sequential reduction with the same tree. The cost is that the reduction order is fixed, which may limit the available parallelism. For example, a fixed binary tree reduction has O(log n) span regardless of the number of processors. If the number of processors is larger than the tree width, the extra processors are idle.

Compensated arithmetic can reduce the error but does not guarantee reproducibility. Kahan summation and Neumaier summation track the lost low-order bits and add them back. The result is more accurate, but the order of operations still matters. Two different orders can produce different results. To guarantee reproducibility, the order must be fixed. Some libraries provide reproducible reductions that use a fixed tree and compensated arithmetic. The cost is a constant factor of two to four in arithmetic operations. For DP, this may be acceptable if the transition cost is high.

Tie-breaking is another source of non-determinism. If two paths have the same cost, the sequential algorithm picks the first one in its scan order. A parallel reduction may pick a different one. To make the result deterministic, the comparison must include a tie-breaker, such as the index of the predecessor. The tie-breaker must be part of the reduction operation. For min-plus, the operation becomes a lexicographic min on (cost, index). This is associative if the tie-breaker is a total order. The cost is an extra comparison and an extra value to carry. For many DP problems, this is a small price for reproducibility.

## Autotuning and schedule search

The space of parallel schedules for a DP is large. The tile size, the tile shape, the skew factor, the number of threads per block, the vectorization width, the prefetch distance, and the schedule type are all parameters. Finding the best combination by hand is tedious. Autotuning searches the space by running the kernel on a set of representative problem sizes and measuring the time. The search can be exhaustive for a small space or guided by a model for a large space.

A cost model can prune the search. The model predicts the time from the problem size, the cache size, the memory bandwidth, and the synchronization cost. The model does not need to be perfectly accurate; it only needs to rank the candidates correctly. For DP, the model must account for the wavefront width, the tile halo, and the reduction cost. The wavefront width determines the parallelism. The tile halo determines the memory traffic. The reduction cost determines the arithmetic intensity. A simple model is

```text
time = max(compute_time, memory_time) + sync_time
```

where compute_time is the total work divided by the number of processors, memory_time is the total memory traffic divided by the bandwidth, and sync_time is the number of barriers times the barrier cost. The model can be calibrated on a small set of measurements. This is the roofline model applied to a parallel schedule.

Polyhedral compilation is a more systematic approach. The DP loops are represented as affine transformations of the iteration space. Tiling and skewing are loop transformations that can be expressed in the polyhedral framework. The compiler can generate a schedule that satisfies the dependencies and optimizes a cost function. The framework works well for regular grid DPs with affine dependencies. It is less effective for irregular DPs with data-dependent edges or non-affine reductions. For those, the schedule must be chosen by a runtime system or by a domain-specific heuristic.

Domain-specific languages for DP can hide the scheduling details. The user writes the recurrence in a high-level notation. The compiler analyzes the dependencies and generates a parallel schedule. The compiler can choose between wavefront, scan, and tree contraction based on the structure of the recurrence. This is an active area of research, but the fundamental trade-offs remain. The compiler cannot create associativity where none exists, and it cannot remove the critical path. It can only choose the best schedule for the given structure.

## Limits and open problems

The limits of dependency-parallel recurrences are structural. The critical path is the first limit. If the recurrence has a chain of length L, no schedule can have span less than L. The chain may be in the time dimension, the length dimension, or the tree height. The only way to reduce the span is to change the recurrence algebraically. That requires associativity, and it may increase the work. The trade-off between span and work is fundamental.

The second limit is memory bandwidth. DP is often memory-bound. The arithmetic per state is small, and the state is read and written multiple times. The wavefront access pattern is cache-unfriendly. Tiling and skewing improve locality, but they do not change the total memory traffic. They reduce the traffic by increasing reuse. The maximum reuse is bounded by the cache size. If the working set is larger than the cache, the traffic is proportional to the number of tiles, not the number of states. This is the same limit as in any cache-blocked algorithm.

The third limit is synchronization. Every parallel schedule needs some form of synchronization. Barriers, atomics, and fences all cost time. The cost grows with the number of threads and the frequency of synchronization. The wavefront schedule synchronizes at every level. Tiling reduces the frequency. Dataflow scheduling replaces barriers with per-tile atomics. There is no schedule with zero synchronization. The goal is to make the synchronization cost smaller than the work it distributes.

The fourth limit is the state size. If the state per node is large, the combine operation is expensive, and the parallelism at the node level is limited. Tree contraction and heavy-light decomposition can parallelize the tree structure, but the combine cost remains. For a state of size C, the combine may cost O(C^2) or O(C log C). The span of the combine is O(log C) if it is parallelized. The overall span is then the product of the tree span and the combine span. For large C, the combine dominates. This is why tree DP with large state spaces is often sequential in practice.

Open problems remain in automatic parallelization of irregular DPs. The DAG is data-dependent, and the optimal schedule depends on the input distribution. A scheduler that adapts online is needed. Machine learning could predict the pruning rate and choose the tile size. Hardware support for scans and reductions is improving, but the memory hierarchy is still the bottleneck. Near-memory computing could reduce the memory traffic by performing the DP updates in memory. This would change the cost model completely. The remaining question is how to make these choices automatically for a given recurrence and machine, without a human in the loop.
