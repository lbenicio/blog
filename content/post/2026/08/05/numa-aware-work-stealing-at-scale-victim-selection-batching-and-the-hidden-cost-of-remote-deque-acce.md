# NUMA-Aware Work-Stealing at Scale: Victim Selection, Batching, and the Hidden Cost of Remote Deque Access

Most work-stealing schedulers are designed around a simple abstraction: each worker has a deque, owners push and pop at one end, thieves steal from the other, and the cost of a steal is treated as roughly uniform. That abstraction is useful, but on non-uniform memory access machines it is incomplete. A steal is not only a synchronization event; it is a memory transaction against a deque that may live in another NUMA node. The task may be small, but the metadata access can be remote, cache-line ownership may move, and the stolen task may immediately touch data allocated on the victim's node. At scale, those effects change scheduler design.

This article examines work-stealing schedulers for large NUMA systems. It focuses on three linked decisions: how a thief chooses a victim, how many tasks a thief takes in one attempt, and how the deque and task metadata are laid out in memory. The goal is not to propose a universal scheduler. The goal is to make the cost model explicit so that design choices can be evaluated against the workloads they are meant to serve.

## Why work stealing survives

Work stealing remains attractive because it combines dynamic load balancing with locality. A worker usually operates on its own deque, so the fast path is local and cheap. When a worker runs out of work, it becomes a thief and looks for a victim with surplus tasks. This avoids a global ready queue, which would become a contention point and a coherence hot spot. It also avoids static partitioning, which can collapse under irregular task durations, data-dependent branching, or bursty arrival patterns.

The owner's fast path is the key. Push and pop at the owner's end are usually uncontended, and they can be implemented with a small number of atomic operations or with a single-threaded fast path plus a careful publication protocol for thieves. If the deque is empty, the owner does not spin on a global structure; it steals. If the workload is balanced, steals are rare. If the workload is unbalanced, steals move work without a central coordinator.

On a uniform-memory machine, the main costs are synchronization, failed steal attempts, and the loss of locality when a task moves. On a NUMA machine, the third cost becomes more complex. The task moves, but its data may not. The deque moves, but the cache line may remain in the victim's cache until coherence traffic forces a transfer. The thief may run on a core that is close to its own memory but far from the task's working set. A scheduler that balances runnable tasks without considering data placement can produce a machine that is busy but not efficient.

## The NUMA cost model

NUMA changes the meaning of local. A core can access local DRAM, remote DRAM attached to another socket, and memory attached to an accelerator or a CXL device. The exact ratios depend on the platform, but the qualitative shape is stable: remote accesses have higher latency, lower per-core bandwidth, and more variable behavior under contention. Coherence traffic also crosses interconnect boundaries. A cache line that is repeatedly read and written by cores on different nodes can bounce, and the interconnect can become the limiting resource.

For a work-stealing scheduler, the relevant memory objects are not only the tasks. They include the deque control block, the deque array, the task descriptors, the task's captured state, and the data the task will access. A steal touches the victim's deque control block and array. If the task is then executed on the thief's node, it may touch memory allocated by the victim. The scheduler can control the first two objects. It usually cannot control the third without cooperation from the runtime or the application.

This leads to a distinction between scheduling locality and data locality. Scheduling locality means that the thief and the victim are close in the topology, so the steal itself is cheaper. Data locality means that the stolen task's data is close to the thief, or that the cost of moving the task is offset by better load balance. These goals can conflict. A topology-aware thief may prefer a nearby victim with little work over a distant victim with a large batch, leaving a distant node overloaded. A data-aware thief may prefer a task whose data is already local, but the scheduler may not know which task that is without metadata that is expensive to maintain.

## Anatomy of a steal

A steal is often described as a single operation: pick a victim, attempt to take a task, and execute it if successful. In practice it is a sequence with several failure points. The thief reads the victim's deque state. It may read a top index and a bottom index, or a single atomic state, depending on the deque algorithm. It checks whether the deque is empty. If not, it attempts to reserve one or more tasks with an atomic compare-and-swap or a load-linked/store-conditional sequence. The reservation must be ordered with the owner's publication of the task. If the attempt fails, the thief backs off or chooses another victim. If it succeeds, the thief copies the task reference, updates the deque state, and then executes the task.

On a NUMA machine, each of these steps has a placement. The thief's read of the victim's state is a remote read if the deque is on the victim's node. The compare-and-swap is a remote atomic operation, which is more expensive than a local atomic operation and can generate coherence traffic. If the steal succeeds, the thief may write the task's state or increment a counter in the task descriptor, which may be another remote write. If the thief then executes the task, the task's data accesses may be remote.

The owner's fast path also matters. The owner pushes and pops on its local deque. If the deque is padded to avoid false sharing, the owner's control block and the thief's read of the top index may be on separate cache lines. That padding reduces coherence traffic on the owner's fast path, but it increases the number of cache lines a thief must fetch. The trade-off is not free. A scheduler that pads every deque aggressively may waste memory and increase the footprint of the scheduling metadata, which can hurt cache behavior when many deques are active.

## Victim selection

Victim selection is the first lever. The simplest policy is random selection among all workers. Random selection is robust against correlated access patterns, and it is cheap to implement with a per-thread pseudo-random generator. It does not require topology information. Its weakness is that it ignores distance. A thief may repeatedly choose a victim on a remote node when a nearby victim has work. Random selection also makes it difficult to reason about load imbalance, because the expected time to find work depends on the distribution of tasks and the number of workers.

A round-robin policy is also cheap, but it can create synchronization patterns. If all thieves advance through the same list of workers, they may converge on the same victims, especially when the number of thieves is large. A per-thief random offset can reduce that correlation, but the underlying distance problem remains.

Topology-aware selection uses a hierarchy. A worker first checks victims in its own NUMA node, then in neighboring nodes, then in the wider machine. The hierarchy can be represented as a tree or as a list of victim groups ordered by distance. This reduces remote steal traffic when local work is available. It also introduces a new failure mode: if local victims are empty but the thief keeps checking them, the thief wastes time on local failures before going remote. The policy needs a way to escalate after a bounded number of local failures. The escalation threshold is a tuning parameter. Too low, and the thief goes remote too early. Too high, and the thief idles while remote work exists.

A more sophisticated policy uses work stealing with victim hints. A victim can publish a hint that it has surplus work, or a thief can remember which victims succeeded recently. Hints can be cheap if they are per-node summaries rather than per-deque counters. A per-node summary can tell a thief which node has surplus work without reading every deque. The thief then chooses a victim within that node. The summary itself must be updated without becoming a contention point, so it is usually approximate and eventually consistent. Approximate hints are acceptable for scheduling, but they can cause herd behavior if many thieves react to the same hint. Randomization within the hinted node is a practical mitigation.

## Steal batching

The second lever is batch size. A thief can steal one task, a fixed number of tasks, or half of the victim's deque. Stealing one task minimizes the amount of work moved and keeps load balance fine-grained. It also maximizes the number of steal attempts, which is costly when each attempt is a remote atomic operation. Stealing half amortizes the steal cost over many tasks, but it can move more work than necessary. If the victim has a small surplus, stealing half may leave the victim with too little work and cause it to steal back later. That creates task ping-pong and additional remote traffic.

The choice interacts with NUMA. If a steal is remote, the fixed cost of the attempt is high, so batching is more attractive. But the tasks being moved may have data on the victim's node. Moving a large batch amplifies the data-locality problem: many tasks now run on a remote node, and each may touch remote memory. A small batch limits the damage per steal, but it increases the number of remote attempts. The right balance depends on task granularity and on how much of the task's working set is movable.

A useful design is adaptive batching. The thief starts with a small batch when the system is lightly loaded or when steal attempts are succeeding. If steal attempts are failing, the thief increases the batch size to amortize the cost of scanning and failed atomics. If the victim's deque is nearly empty, the thief takes only what is available. The adaptation can be per-thief, per-node, or global. Per-thief adaptation is simple and avoids shared state. Per-node adaptation can coordinate thieves on the same node, but it requires shared counters and can become a contention point. Global adaptation is usually too coarse for NUMA systems because the optimal batch size differs by node distance.

There is also a fairness question. Stealing half can be unfair to the victim if the victim is about to spawn more tasks. A victim that loses half its deque may immediately need to steal, which increases total steal traffic. Some schedulers use a steal-half-with-reserve policy, where the thief takes half of the surplus above a threshold. The threshold protects the victim's ability to continue without an immediate steal. The threshold should be large enough to avoid ping-pong but small enough to allow load balancing. It is a policy parameter that must be evaluated against the workload's task arrival pattern.

## Deque layout and memory ordering

The deque is the scheduler's central data structure, and its layout determines the cost of every steal. A common design uses a growable array with a top index and a bottom index. The owner pushes and pops at the bottom; thieves steal from the top. The indices are often packed into a single atomic word to allow a single compare-and-swap to reserve a task. The packing reduces the number of atomic operations, but it also constrains the deque size and requires careful handling of wraparound.

On NUMA systems, the deque should be allocated on the node where the owner runs. The owner's fast path then touches local memory. Thieves pay the remote cost, which is unavoidable if they are remote. The scheduler can reduce the number of remote thieves by using topology-aware victim selection. It can also reduce the cost per remote steal by batching. It cannot make a remote atomic operation local without moving the deque, which would move the cost to the owner.

Memory ordering is another source of hidden cost. The owner must publish a task before a thief can steal it. The publication usually requires a release store or a fence. The thief must acquire the task before executing it. On weakly ordered architectures, these fences can be expensive. The scheduler should use the weakest ordering that preserves correctness. For example, if the deque uses a single atomic state that encodes both indices and a tag, the compare-and-swap itself provides the necessary ordering. If the deque uses separate indices, the owner may need a release store on the bottom index and the thief an acquire load on the top index. The exact protocol depends on the deque algorithm, but the principle is the same: do not pay for a full fence on the owner's fast path if a release store is sufficient.

False sharing is also a layout concern. The owner's bottom index and the thieves' top index are written and read by different threads. If they share a cache line, every steal invalidates the owner's cache line and every push invalidates the thieves' view. Padding the indices onto separate cache lines reduces this interference. But padding increases the deque's memory footprint and the number of cache lines a thief must fetch. The right padding depends on the steal rate. A deque that is rarely stolen from does not need aggressive padding. A deque that is stolen from frequently may benefit from separating the owner's state from the thieves' state.

## Initial design principles

The analysis so far suggests a set of initial principles rather than a final design. First, make the owner's fast path local and cheap. Allocate deques on the owner's node, keep the owner's state on a cache line that thieves do not write, and use the weakest correct memory ordering. Second, make victim selection topology-aware but not topology-obsessed. Use a hierarchy with bounded local probing and randomized choice within a group. Third, make batching adaptive. Start small, grow on failure, and leave a reserve to avoid ping-pong. Fourth, measure the right things. A scheduler that reports only task completion time hides the cost of remote steals, failed attempts, and data-locality loss. Instrumentation should separate local steals, remote steals, failed attempts, batch sizes, and task migration events.

These principles are not independent. Aggressive padding helps the owner but increases the thief's fetch cost. Topology-aware selection reduces remote steals but can create local hot spots. Adaptive batching reduces failed attempts but can amplify data-locality loss. The scheduler designer must decide which cost dominates for the target workload. That decision is the subject of the next sections.

## Instrumentation before optimization: separating steal classes

The first practical step in NUMA-aware scheduler work is to stop treating every steal as the same event. A scheduler can record local steal attempts, same-node remote attempts, cross-node attempts, and cross-socket attempts separately, even if the underlying algorithm is identical. It should also distinguish an attempt that found an empty deque from an attempt that raced with the owner or another thief and lost. Those failures have different implications. An empty-deque failure suggests that victim selection is probing the wrong places. A lost race suggests contention on a deque that is genuinely productive, which may justify batching or backoff rather than changing victim order.

Useful counters are per worker and per node-pair. Per-worker counters expose imbalance: one thief may be doing most of the remote probing while another stays local. Per-node-pair counters expose topology effects: node A may steal successfully from node B but waste most of its attempts on node C because the hint or distance ordering is wrong. The counters should be cheap enough to remain enabled in production-like runs. Full tracing of every steal is useful for short experiments, but it changes the timing enough to hide the very effects being studied. A practical compromise is to aggregate counters in per-worker cache lines and periodically reduce them into a per-node matrix.

Latency histograms matter more than averages. A remote steal may usually complete in a few hundred nanoseconds and occasionally stall for several microseconds when the interconnect is congested or when the owner is in the middle of a large push burst. The average hides the tail, and the tail is often what limits scalability. The scheduler should record the time spent in victim selection separately from the time spent in the atomic reservation. If victim selection is slow, the topology policy or the hint structure is at fault. If the reservation is slow, the deque layout and coherence protocol deserve attention.

Batch size should be recorded as a distribution, not only as a mean. A scheduler that sometimes steals one task and sometimes steals sixty-four has different behavior from one that always steals eight, even if the mean is the same. The distribution interacts with victim starvation and ping-pong. Recording the victim's approximate deque depth at the time of the steal helps distinguish a productive large batch from an over-aggressive grab. Finally, record task migration events separately from task execution. A task that is stolen once and runs for a long time is cheap to migrate. A task that is stolen repeatedly and runs briefly is a sign that the scheduler is moving metadata more than work.

## The coherence cost of a remote deque read

A remote deque access is often modeled as a read with higher latency. That model is incomplete because the read changes cache-line ownership. If the victim's deque control block is in a modified state in the victim's cache, the thief's read must obtain a shared copy and may force a writeback or a cache-to-cache transfer. The victim's next push then needs exclusive ownership again, invalidating the thief's copy. A steal attempt that fails can still perturb the owner. The thief pays for the remote read, and the owner pays for the subsequent invalidation. Under high steal rates, the deque control block becomes a coherence hot spot even though the owner and thieves never write the same field.

The usual response is padding, but padding only separates fields. It does not eliminate the ownership transfer on the fields that must be read by thieves. Separating the owner's bottom index from the shared top index reduces false sharing on the owner's fast path, but the top index is still written by thieves when they reserve work. If the top index and the array pointer share a line, a thief's reservation can invalidate the owner's view of the array pointer, even though the pointer does not change. Layout should therefore group fields by writer and access frequency, not only by conceptual role. The owner's private state, the shared reservation state, and the array metadata may each deserve their own line if the steal rate is high enough to justify the footprint.

The deque array adds another layer. A thief that reserves a task must read the corresponding slot, which is usually remote. If the slot contains a pointer to a task descriptor, the thief then reads the descriptor, which may be remote again. That is two dependent remote loads before the task can execute. The task's own data may add a third. Batching helps because the thief can reserve a range and read several slots, but the reads are still remote and may touch several cache lines. A batch that spans multiple array lines can be more expensive than a batch of the same size that fits in one line. Some deques copy task references into a small local staging buffer during the reservation, so the remote atomic is followed by a compact set of reads rather than a scattered traversal.

Read-mostly metadata can be replicated to reduce remote reads, but replication introduces staleness. A per-node summary of deque depth is useful because thieves can read it locally and use it to choose a node. The summary does not need to be exact; it needs to be fresh enough to avoid sending thieves to empty nodes. Updating the summary on every push and pop would create a new hot spot, so it is usually updated lazily or sampled. The risk is herd behavior: many thieves see the same summary, choose the same node, and overload it. Randomizing the choice within the node and adding a small per-thief jitter to the summary value reduces that risk without requiring precise global state.

## Batching as an economic decision

Batching is often described as amortizing the cost of a steal. The more precise statement is that batching trades a fixed remote cost against a variable migration cost. Let the fixed cost include victim selection, the remote read of the deque state, the atomic reservation, and the dependent reads needed to obtain task references. Let the variable cost include the disruption to the victim and the data-locality loss when the stolen tasks execute on the thief's node. A batch of size k spreads the fixed cost over k tasks, so the fixed cost per task falls as k grows. The variable cost per task may rise if the batch includes tasks whose working sets remain on the victim's node, or if the batch leaves the victim with too little work and causes it to steal back.

The productive range for k depends on the success probability of a steal and the duration of the stolen tasks. If steals rarely succeed, a larger batch makes each successful steal more valuable, but it also increases the cost of a failed attempt only slightly because the failure occurs before the batch is read. If steals usually succeed, a smaller batch provides finer load balance and limits migration. The scheduler can estimate the recent success rate per node-pair and adjust the requested batch size. It should not adjust solely on failure count, because a failure caused by an empty deque is different from a failure caused by a lost race on a deep deque. The former argues for a different victim; the latter argues for a larger reservation or a backoff.

A reserve threshold is necessary to prevent the victim from being stripped. The thief should take from the surplus above a reserve, not from the victim's entire deque. The reserve can be expressed as a small constant or as a function of the victim's recent consumption rate. A fixed reserve is simple and predictable. An adaptive reserve can protect a victim that is in a burst of task generation, but it requires shared state that may itself become remote. A practical compromise is to keep the reserve local to the viction and expose only a coarse surplus hint. The thief then reserves up to a batch limit, and the atomic operation validates the actual deque state. If the validation fails because the victim consumed work, the thief retries or moves on rather than forcing the reservation.

Batching also changes the shape of contention. A thief that steals one task at a time performs many small atomics on the top index. A thief that steals a batch performs fewer atomics but holds the top index longer if the implementation uses a multi-step reservation. The best design is usually a single atomic that advances the top index by k, followed by reads of the claimed slots. That keeps the critical section short and lets the thief read the slots without blocking the owner. The trade-off is that the thief must handle the case where the owner has already popped or published tasks in a way that invalidates part of the claimed range. A tagged index or a generation counter can detect that case, but it adds bits and complexity to the reservation word.

## Hierarchical victim selection at scale

At small scale, a thief can scan a list of workers and find work quickly. At large scale, the scan cost and the probability of hitting empty victims both grow. A hierarchy helps, but the hierarchy must be designed around failure budgets rather than fixed levels. A thief should probe a bounded number of workers in its own node, then a bounded number in nearby nodes, and only then consider the wider machine. The bounds should depend on the number of workers per node and on the recent success rate at each level. If local probing has been failing consistently, the thief should escalate sooner. If remote probing has been succeeding, it may be worth paying the distance cost rather than spending more time on local empty deques.

The order within a level should not be a fixed round-robin shared by all thieves. A shared order causes convergence: every thief checks the same first victim, then the same second victim, and the resulting burst of remote reads can make a productive deque look contended. A per-thief randomized permutation, or a random starting offset combined with a stride, spreads the probes. Topology can still guide the choice by restricting the permutation to a node or a group of nodes. The goal is to preserve locality of probing without preserving correlation among thieves.

Per-node hints can reduce the cost of finding a productive node, but they must be updated without becoming a global counter. A useful structure is a small array of per-node credits, where a push increments the local node's credit and a successful remote steal decrements the thief's view of the victim node's credit. The credits are approximate and can go negative or stale. Thieves read them locally, choose a node with positive credit, and then choose a worker within that node at random. If the chosen worker is empty, the thief can try another worker in the same node before updating its view. This two-level selection avoids reading every deque and keeps most of the selection traffic local. The cost is that the credits can lag behind rapid changes in work distribution, so the scheduler needs an escape hatch: after a bounded number of hint-driven failures, it falls back to a broader scan.

Distance should influence the acceptable batch size and the acceptable failure budget. A cross-socket steal is expensive enough that it should be attempted with a larger batch or after a stronger local failure signal. A same-node steal can be attempted with a smaller batch and a shorter backoff. This does not mean that remote steals should always be larger; if the remote node is about to run out of work, a large batch may simply move the imbalance. The scheduler can cap the batch by the victim's advertised surplus and by the thief's own remaining capacity to execute tasks. A thief that steals more than it can run promptly has converted a scheduling problem into a memory-footprint problem.

## Task and data affinity metadata

The hardest part of NUMA-aware work stealing is that the scheduler usually controls task placement but not data placement. A task descriptor can be allocated on the owner's node, and the deque can be allocated on the owner's node, but the task's input may have been allocated elsewhere and may be shared with other tasks. The scheduler can attach affinity metadata to a task, such as a home node, a preferred node, or a migration cost estimate. The metadata must be cheap to produce and cheap to read. If every task carries a large affinity structure, the scheduler spends memory bandwidth on metadata instead of work. If the metadata is too coarse, it cannot distinguish a task that touches a small remote buffer from one that traverses a large remote graph.

A practical approach is to use a small home-node tag plus a migration penalty class. The tag is set when the task is created, based on the allocating worker or on an explicit application hint. The penalty class is a coarse estimate of how much the task will suffer if it runs away from its data. The thief can then prefer tasks whose home node matches the thief's node, or whose penalty class is low. This preference must be subordinate to load balance; otherwise the scheduler can leave a node overloaded because all its tasks have high penalties. The usual compromise is to allow locality-preserving steals first, then relax the preference when the imbalance exceeds a threshold. The threshold can be based on queue depth, on the age of the oldest task, or on the rate of failed local steals.

Task affinity also interacts with batching. A batch of tasks from the same home node may share data and cache lines, so moving them together can be cheaper than moving them one by one. A batch of tasks from different home nodes may have no locality benefit and may simply increase the thief's remote footprint. If the deque is ordered by creation time, a batch from one end may naturally contain tasks with similar affinity, but that is not guaranteed. A scheduler that wants affinity-aware batching needs either a per-affinity sub-deque or a reservation policy that inspects a small window of task tags before committing to a batch. The window inspection adds reads, so it is only worthwhile when the task's data footprint is large relative to the scheduling metadata.

Finally, the scheduler should distinguish between moving work and moving data. A remote steal moves the right to execute a task. It does not move the task's input, its output buffer, or the cache lines those objects occupy. Running the task remotely may be the right choice when the task is compute-heavy and its data is small, or when the data is read-only and can be replicated. It may be the wrong choice when the task writes to a large buffer that is shared with the victim's remaining tasks, because the writes will cross the interconnect and may invalidate the victim's cache lines. The scheduler cannot make this decision perfectly without application knowledge, but it can expose the decision to the runtime through task tags and can measure the result through remote-access counters. That measurement loop is more valuable than a fixed affinity policy, because the cost of being wrong changes with the workload, the topology, and the scale of the machine.

## Backoff, throttling, and the cost of being persistent

A failed steal is not free. It consumes interconnect bandwidth, moves cache-line ownership, and may invalidate the victim's private state. When many thieves fail against the same victim, the scheduler can enter a contention regime in which the victim spends more time servicing remote reads than executing tasks. The usual remedy is backoff: after a failed attempt, the thief waits before retrying. The design question is what to back off on and for how long.

A fixed pause is simple but fragile. If the pause is too short, thieves continue to hammer the same deque. If it is too long, the thief idles while work is available elsewhere. Exponential backoff with jitter is more robust, but it must be bounded. An unbounded backoff can make a thief invisible to the rest of the system, which is especially harmful when the workload has phases and a node that was empty becomes productive. The bound should be short enough that the thief re-enters the search within the time scale of a task, not the time scale of a scheduling epoch.

Distance should influence the backoff. A failed same-node steal is cheap, so a short pause is enough. A failed cross-socket steal has already paid a high cost, and repeating it immediately is unlikely to help unless the victim is in a burst of publication. A longer pause, or a switch to a different victim group, is usually better. The thief can also change the kind of probe: instead of reading the same deque again, it can consult a per-node hint or scan a different worker in the same node. Backoff and victim selection are therefore coupled. A scheduler that backs off without changing its target may simply repeat the same mistake more slowly.

Throttling is the aggregate version of backoff. Even if each thief behaves reasonably, the total steal rate can exceed what the interconnect or the victim's cache can sustain. A per-node token bucket can limit the number of remote steal attempts per unit time. Tokens are consumed by attempts and replenished at a rate that depends on the node's observed success rate and on the number of local workers. When tokens are exhausted, thieves must either wait or look for work locally. The token bucket must be distributed carefully; a single global counter would become the new hot spot. A per-thief local view of a shared rate, updated periodically, is usually sufficient. The goal is not precise rate limiting but avoidance of synchronized bursts.

Synchronized bursts are a real failure mode. If all thieves use the same backoff schedule and the same victim order, they can wake at the same time and probe the same deque. The resulting coherence storm can make a healthy victim look empty or contended. Randomizing the initial backoff, the victim order, and the probe interval breaks the synchronization. The randomization should be per thief and per attempt, not per node, so that thieves on the same node do not share a correlated pattern. A cheap per-thread PRNG is enough; the scheduler does not need cryptographic randomness.

There is also a question of when to stop stealing entirely. A thief that has failed many times may be better off doing useful local work: helping with a local task, running a maintenance routine, or entering a low-power wait. The scheduler should distinguish between a worker that is idle because there is no work and a worker that is idle because it cannot find work. The first case may call for a global barrier or a phase change. The second case calls for better victim selection or a different work discovery mechanism. Treating them as the same event hides the difference and leads to policies that either spin too long or sleep too eagerly.

## The owner's side of the steal

Most work-stealing designs optimize the thief's path, because the thief is the one paying the remote cost. But the owner's behavior determines how often thieves are needed and how expensive their attempts are. An owner that publishes tasks one at a time exposes a shallow deque and invites frequent steals. An owner that publishes in bursts can present a deeper deque, which allows thieves to take a meaningful batch and reduces the number of attempts. The trade-off is latency: a task that is held in a private buffer is not available to a thief, so the system may be less responsive to imbalance.

A practical middle ground is owner-side batching with a bounded delay. The owner accumulates newly created tasks in a local buffer and publishes them when the buffer reaches a threshold or when a short timer expires. The threshold can be small, such as four or eight tasks, and the timer can be tied to the owner's next scheduling point. This keeps latency bounded while giving thieves a deeper target. The owner can also publish a surplus hint when the buffer is large, so thieves know that a productive steal is likely. The hint is advisory; the actual reservation still validates the deque state.

The owner can reduce coherence cost by keeping its private bottom index on a separate cache line from the shared top index. It can also avoid writing the shared state on every push. Some deque designs maintain a published top index that is updated only when the owner has accumulated enough work to be worth stealing. Thieves read the published index and reserve from the unpublished region only if the published index indicates surplus. This reduces the frequency of remote reads and writes, but it complicates the empty-deque check. The owner must ensure that a task is fully initialized before it becomes visible, and the thief must not claim a task that the owner has already popped.

A more radical owner-side policy is work donation. Instead of waiting for a thief, the owner proactively pushes a batch of tasks to a nearby worker or to a per-node queue when it detects that its local deque is growing faster than it can drain. Donation can be cheaper than stealing because the owner knows which tasks are surplus and can choose a batch that preserves locality. It also avoids the failed attempts that plague thief-initiated stealing. The risk is that the owner may donate work that it will need soon, or that it may donate to a worker that is already busy. Donation policies therefore need feedback: the owner should donate only when the target has signaled capacity, and the target should be able to reject or return work. This turns the scheduler into a two-sided market, with all the complexity that implies.

## Memory tiers and the collapse of binary locality

On early NUMA machines, locality was roughly binary: a memory access was either local or remote. On current systems, there may be multiple tiers. Local DRAM, remote DRAM on another socket, memory attached to a different socket group, and CXL-attached memory can all have different latency and bandwidth. The distance matrix is no longer symmetric or transitive. Node A may be close to B, B close to C, and A far from C. A victim selection policy that orders nodes by a single distance scalar will make mistakes.

For work stealing, the tier of the deque and the tier of the task data may differ. A deque can be placed in local DRAM for fast owner access, while the task's input lives in CXL memory because it is large and infrequently accessed. Stealing such a task to a remote core may be cheap for the deque access but expensive for the data access. Conversely, a task with a small working set in local DRAM may be cheap to steal even across sockets. The scheduler cannot know this without metadata, but it can at least distinguish between the cost of the steal and the cost of execution. The two costs should be tracked separately, because they lead to different policies.

Memory tiers also affect batch size. A batch of tasks whose data is in a remote tier may be better left on the victim's node, even if the victim is overloaded, because moving the tasks would move the computation to the data's far side. A batch of tasks whose data is replicated or read-only can be moved more freely. If the runtime can mark tasks as tier-sensitive, the thief can prefer tasks with low tier sensitivity when stealing across tiers. The marking can be coarse: a single bit for movable versus pinned, plus a small home-node tag. The scheduler does not need a full cost model to benefit from avoiding obviously bad migrations.

The presence of CXL memory also changes the meaning of local capacity. A node may have plenty of local compute but little local memory, so tasks must allocate in a remote tier. In that case, the scheduler should not assume that a task allocated on the owner's node has its data on the owner's node. It should track the allocation tier separately from the execution node. A task may be created on node A, allocate its output on CXL, and be stolen by node B. The best execution node may be B if B is close to CXL, or A if the task's input is still in A's cache. This is a three-way placement problem, and a deque-based scheduler sees only one dimension of it.

## Multi-level stealing and the limits of a single deque

As machines grow, a single deque per worker may not be the right granularity. A worker may have a private deque for fine-grained tasks and a per-node deque for coarser work. Thieves can steal from the private deques first, then from the per-node deque, and finally from a global queue. The hierarchy gives the scheduler more control over locality and batch size, but it also creates new decisions: which level to probe, how long to stay at a level, and how to move work between levels. A task that is too coarse for a private deque may be split, but splitting adds overhead and may change the task's data locality. A task that is too fine for a per-node deque may be aggregated, but aggregation delays execution and can increase latency.

The hierarchy should be designed so that the common case is cheap. Most steals should succeed at the private level or at the per-node level, and the global level should be a fallback for phase changes and severe imbalance. The per-node level can be implemented as a small array of deques with a shared hint, not as a single contended queue. Thieves choose a sub-deque at random, which spreads contention and preserves some locality. The global level can be a work donation queue that is only used when a node has no work at all. If the global queue is used frequently, the scheduler has lost the locality benefits of work stealing and should reconsider its partitioning.

Multi-level stealing also changes the meaning of a failed steal. A failure at the private level may mean that the worker is busy, not that the node is out of work. A failure at the per-node level is a stronger signal. The thief should escalate only after a bounded number of failures at the current level, and the bound should depend on the level's expected depth and on the cost of the next level. A global probe is expensive, so it should be attempted only when local and per-node probes have failed enough times to justify the cost. The escalation policy is a control loop, and like any control loop it can oscillate if the thresholds are too tight or too loose.

## Guardrails for adaptive policies

Adaptive batching, adaptive victim selection, and adaptive backoff all depend on feedback. Feedback makes the scheduler responsive, but it also creates the possibility of oscillation and herd behavior. A node that becomes productive may attract many thieves at once, drain its deque, and then become empty. The thieves then switch to another node, which becomes the new hot spot. The system oscillates without making progress. Guardrails are needed to damp these effects.

Hysteresis is the simplest guardrail. A thief should not change its target or batch size on a single observation. It should require several consistent observations before adapting. The observations can be aggregated with an exponentially weighted moving average, which is cheap and smooths out noise. The smoothing factor should be chosen so that the scheduler reacts within a few task durations, not within a few nanoseconds. A scheduler that reacts to every failed steal will overfit to transient contention.

Randomization is another guardrail. Even with hysteresis, many thieves may make the same decision if they see the same hint. Adding jitter to the batch size, the backoff, and the victim order prevents perfect correlation. The jitter should be bounded so that the scheduler's behavior remains predictable. A batch size that varies between one and sixty-four is not predictable; a batch size that varies between four and eight is. The goal is to break synchronization without destroying the policy's intent.

Finally, adaptive policies should have a safe fallback. If the feedback is missing, stale, or inconsistent, the scheduler should fall back to a simple policy that is known to work: random victim selection, a fixed small batch, and a bounded backoff. The fallback does not need to be optimal. It needs to be robust enough to keep the system running while the adaptive policy recovers. This is especially important on NUMA machines, where a stale hint can send thieves to a node that is no longer productive and where a failed adaptation can create a coherence storm that is worse than the imbalance it was trying to fix.

## Deque lifetime, ownership return, and remote frees

A work-stealing scheduler is usually described as though deques and task descriptors live forever. At scale they do not. Worker pools shrink, epochs end, tasks complete, and memory that was allocated on one node is eventually released, possibly by a worker on another node. This is the part of the cost model that appears after the steal, and it can undo the care taken in victim selection and batching. A thief that successfully steals a task may later become the last owner of its descriptor. If it calls a general-purpose free, the allocator may have to touch metadata that lives on the allocation node, take a remote lock, or return a remote slab. The result is a second remote access that is easy to miss in a profiler that focuses on steal attempts.

The simplest discipline is to make the return path explicit. Task descriptors allocated from a per-node arena are not freed directly by a remote thief. Instead, the thief deposits the descriptor into a return structure associated with its home node. The home node drains the structure in batches, during a scheduling point or when the batch reaches a threshold. This converts many small remote frees into a smaller number of batched transfers. The return structure itself must be designed carefully: a single multi-producer queue per node can become a contention point when many thieves finish tasks at once, and each enqueue is a remote write. A per-thief stash that is periodically flushed to the home node is often better. The stash can be a small array of descriptor references, and the flush can be a single transfer of a cache line or a short run of lines.

The same reasoning applies to the deque. When a worker retires, its deque should not be freed by whichever thread observes the retirement. The deque was allocated on the worker's node and should be returned there after a quiescence period. Epoch-based reclamation or a hazard-pointer scheme can establish that no thief holds a stale reference. The important design point is that quiescence is not a global stop-the-world event. It should be scoped to the deque or to a group of deques, and the reclamation work should be amortized over normal scheduling points. A scheduler that performs a full fence and a global scan whenever a worker exits will show a latency spike precisely when the pool is changing size, which is often when the system is under pressure.

Ownership return also affects task results. A stolen task may produce a result that the victim's remaining tasks consume. If the result is written into an object allocated on the victim's node, the thief performs a remote write at completion. This is not a scheduling metadata access, but it is part of the migration cost. The scheduler can reduce the damage by keeping result objects separate from task descriptors and by allowing the runtime to choose a result home based on who consumes it. It should not assume that a task's execution node is also the right home for every object it touches. A compute-heavy task with a small result may be cheap to move; a task that appends to a large shared buffer may be expensive to move even if its descriptor is tiny.

Reference counting is a tempting solution and a common source of remote atomics. If every task descriptor has a global reference count, each acquire and release can become a remote operation when the descriptor is shared across nodes. For fork-join workloads, a better pattern is to make ownership exclusive for the duration of execution. The descriptor is transferred to the thief, executed, and returned through the home-node path. Shared state such as futures and counters lives in separate objects with their own placement policy. This keeps the hot task descriptor free of atomic reference counting and makes the return path predictable. When shared state is unavoidable, the runtime should batch updates or use per-node accumulators rather than incrementing a single remote counter per task.

Reclamation metadata has its own false-sharing hazards. A per-node return counter and a per-node free-list head may be updated by both local and remote workers. If they share a cache line with the deque's shared index, every return invalidates the deque state and every steal invalidates the return state. The layout should separate these structures by writer and by expected update rate. This is the same principle as deque padding, applied after the task finishes rather than before it starts. The scheduler's memory footprint grows, but the growth is bounded by the number of nodes and workers, not by the number of tasks. That bound is what makes the design practical at scale.

Allocator choice matters as much as the return protocol. A general-purpose allocator may keep per-thread caches that are cheap for the allocating thread but expensive for a remote return. A node-local arena with size classes can keep both allocation and return local when the descriptor never leaves its home node. When a descriptor does leave, the arena can expose a remote-return path that appends to a batch rather than taking a lock. The batch should be sized to match the allocator's slab granularity; returning one object at a time defeats the purpose. The scheduler should also avoid mixing descriptor sizes in the same return stream, because the home node then has to demultiplex the stream before it can reuse the memory. A small number of well-chosen size classes is easier to manage than a general heap and is usually sufficient for scheduler metadata.

## The operating-system boundary: worker placement and page movement

The scheduler's topology model is only as good as the operating system's placement decisions. A worker is not a fixed point in the machine. The OS may migrate a runnable thread between cores, wake it on a different socket after an interrupt, or move its pages through automatic NUMA balancing. If the scheduler assumes that worker 7 is always on node 2 because it was created there, a migration can turn the owner's local fast path into a remote one without any change in the scheduler's data structures. The deque remains on the original node, but the owner now accesses it from a different node. The result is a deque that is remote for both the owner and the thieves, which is the worst of both layouts.

The first defense is to pin scheduler workers to CPUs and to derive the node from the current CPU rather than from a creation-time hint. Pinning is not always allowed in containerized or oversubscribed environments, so the scheduler should also support a fallback. In the fallback, the worker can observe its current node at scheduling points and adjust its victim selection accordingly. It may also migrate its deque, but deque migration is expensive and must be rare. A simpler policy is to leave the deque where it is and treat the worker's current node as the node for steal purposes. This preserves correctness and avoids a storm of deque moves, at the cost of some remote owner accesses. The cost should be measured and exposed; otherwise the fallback silently becomes the normal case.

Pinning alone does not solve the page-placement problem. Automatic NUMA balancing may move a task's pages toward the CPU that accesses them, which sounds helpful but can invalidate the affinity metadata that the scheduler used to choose a victim. A task that was marked as home-node A may have its data migrated to node B after several remote executions. The scheduler's home tag becomes stale, and a thief that avoids the task because of the stale tag may leave work stranded. A robust design treats affinity metadata as a hint with a lifetime, not as a permanent property. The runtime can refresh the hint when it observes a page migration, or the scheduler can periodically age the tag and fall back to load-based selection. The important property is that a stale hint degrades performance but does not violate correctness or create permanent imbalance.

The OS also interacts with batching through CPU frequency and SMT. Two hardware threads on the same core share execution resources. A steal from an SMT sibling is topologically close in the cache hierarchy but can be expensive in throughput if both threads are already saturating the core. A victim selection policy that treats SMT siblings as the cheapest victims may increase the steal success rate while reducing effective compute. The scheduler should distinguish core distance from cache distance and should avoid sending a thief to a sibling that is already busy with a long-running task. This is another place where a single distance scalar is insufficient. The topology map needs at least three categories: same core, same node, and remote node, with additional detail for cache domains when the platform exposes it.

Interrupts and kernel work add a final source of asymmetry. A core that handles network interrupts may appear idle to the scheduler but have less available capacity than its neighbor. A thief that steals onto such a core may see high variance in task duration, which feeds back into the scheduler's load estimates and batch-size decisions. The scheduler cannot control interrupt placement, but it can avoid making decisions from instantaneous idle state alone. Using a short moving average of recent execution progress, rather than a single queue-depth sample, makes victim selection more robust to these transient effects. The same smoothing applies to adaptive batching: a batch size that reacts to one slow task will oscillate, while a batch size that reacts to a sustained change in completion rate will converge.

Container and cpuset boundaries deserve separate treatment because they can make a nominally NUMA-aware policy meaningless. A container may be restricted to a subset of CPUs that spans sockets, or to a single socket with memory interleaved across several nodes. The scheduler should query the allowed CPU set and build its topology from the allowed resources, not from the machine's full topology. Otherwise it may choose a victim on a node that the process cannot run on, or it may allocate a deque on a node whose memory is not in the container's cpuset. The fallback is not graceful: the allocation may succeed on a remote node, or it may fail and force a retry on a local node. Both outcomes add latency and make the scheduler's cost model wrong.

The practical interface between scheduler and OS is therefore not a single topology query at startup. It is a continuing exchange: the scheduler reports where its workers and deques are, the OS reports where the workers actually run and where pages have moved, and both sides avoid making irreversible decisions from stale information. A scheduler that treats the OS as a static map will work on a quiet benchmark and fail on a busy machine. A scheduler that treats the OS as an adversary will over-engineer around problems it cannot control. The useful middle ground is to pin when possible, observe when necessary, and keep every affinity decision reversible.
