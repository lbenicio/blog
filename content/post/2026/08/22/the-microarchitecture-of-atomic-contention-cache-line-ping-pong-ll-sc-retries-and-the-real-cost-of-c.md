# The Microarchitecture of Atomic Contention: Cache-Line Ping-Pong, LL/SC Retries, and the Real Cost of Compare-and-Swap

## The Primitive That Is Not Primitive

In parallel systems, atomic operations are often treated as building blocks with a fixed cost. A compare-and-swap (CAS) is described as a single instruction. A fetch-and-add is described as a single instruction. A load-linked/store-conditional (LL/SC) pair is described as a loop, but a cheap one. This mental model is convenient for algorithm analysis. It lets us reason about lock-free data structures in terms of steps and progress guarantees. It is also wrong in a way that matters at scale.

The cost of an atomic operation is not a constant. It depends on the cache-coherence state of the line, the topology of the interconnect, the number of cores attempting the same location, the memory ordering semantics required by the language and the algorithm, and the microarchitectural implementation of the primitive itself. Under no contention, an atomic operation can be nearly as cheap as a normal load or store. Under heavy contention, it can be orders of magnitude more expensive, and the throughput of the entire system can collapse to the rate at which a single cache line can be transferred between cores.

This article is about that collapse. It is about what happens below the instruction set architecture when many cores contend on a single atomic location. We will look at the coherence substrate, the anatomy of CAS and LL/SC, the ping-pong pattern that dominates contended atomics, and the design strategies that reduce the cost. The focus is on shared-memory multicore systems with cache coherence, which covers most server, desktop, and mobile CPUs today. The same principles apply, with variations, to GPUs, accelerators, and distributed shared memory, but the details differ.

The assumptions are important. We assume a cache-coherent shared-memory machine. We assume a memory model that is at least relaxed, with explicit acquire/release or fences available. We assume that atomic operations are implemented in hardware, not emulated by a global lock in the kernel. We assume that the workload has some degree of sharing; otherwise there is no contention. Under these assumptions, the central problem is that a cache line is the unit of coherence, and a single atomic location is a serialization point.

## The Cache-Coherence Substrate

To understand atomic contention, you have to understand cache coherence. In a multicore system, each core has private caches, usually L1 and L2, and often a shared last-level cache. Coherence protocols such as MESI and MOESI keep the private caches consistent. Each cache line is in one of several states: modified, exclusive, shared, or invalid. A core can read a line if it is in shared or exclusive state. It can write a line only if it is in modified or exclusive state. To write a line that is shared, the core must invalidate the other copies. That invalidation is a coherence transaction.

Atomic operations are writes. Even a CAS that fails is a read-modify-write operation in the coherence protocol, because the hardware must ensure that no other core can modify the line between the read and the conditional write. To do that, the core must acquire exclusive ownership of the line. If the line is already exclusive to that core, the atomic can complete locally. If the line is shared or owned by another core, the core must send a request to the coherence point, invalidate other copies, and wait for the line. Only then can it perform the compare and the conditional store.

This means that the cost of an atomic operation is dominated by the cost of acquiring exclusive ownership. In a small system with a snooping bus, that cost is the bus transaction. In a larger system with a directory-based protocol, that cost is a request to the home node, a set of invalidations to sharers, and a response with data. In a NUMA system, the home node may be remote, adding interconnect latency. The line itself becomes a token that must be passed between cores.

The coherence protocol also defines the order in which atomics to the same line are serialized. All cores see a single total order of modifications to a cache line. That order is the coherence order. For atomics to the same location, the coherence order is the atomic order. This is what makes CAS a linearization point. It is also what makes contended atomics a bottleneck. No matter how many cores you have, they cannot perform atomics to the same line faster than the coherence protocol can transfer ownership.

False sharing is the same problem in disguise. If two independent variables share a cache line, atomics to one variable will invalidate the other variable in other cores. The line ping-pongs even though the variables are logically independent. Padding and alignment are not cosmetic; they are part of the performance contract.

## The Anatomy of a Compare-and-Swap

A compare-and-swap takes an address, an expected value, and a new value. It reads the current value, compares it to the expected value, and if they match, writes the new value. It returns the old value or a success flag. At the ISA level, this may be a single instruction, such as x86's `LOCK CMPXCHG`, or a loop built from load-linked and store-conditional, such as ARM's `LDXR`/`STXR` or RISC-V's `LR`/`SC`.

On x86, `LOCK CMPXCHG` is a full barrier. The `LOCK` prefix ensures that the operation is atomic with respect to other cores and that memory ordering is sequential for that operation. Microarchitecturally, the core acquires the line in exclusive state, performs the compare, and conditionally writes. If the compare fails, the line is still acquired exclusively, and the write is suppressed. The operation still costs a coherence transaction. A failed CAS is not free; it is a read-modify-write that did not modify.

On ARM and RISC-V, the LL/SC pattern separates the load and the store. `LDXR` loads a value and marks a reservation on the address. `STXR` attempts to store and succeeds only if the reservation is still valid. If any other core writes to the reservation granule between the load and the store, the store fails. The reservation granule is often a cache line or a smaller unit. This means that a store to a different variable on the same line can cause a spurious failure. The programmer must retry the loop.

LL/SC has an advantage: it does not suffer from the ABA problem in the same way as CAS. If the value changes from A to B and back to A, the reservation is lost, and the store-conditional fails. The algorithm can detect that something happened. But LL/SC has its own cost: spurious failures. Under contention, the retry loop can spin many times, consuming issue slots and generating more coherence traffic. The failure rate depends on the reservation granule, the coherence protocol, and the access pattern.

The microarchitecture of LL/SC includes a reservation set or a lock flag in the cache. When a store-conditional fails, the core must re-execute the load-linked. If the line is bouncing between cores, the reservation is lost repeatedly. The loop becomes a coherence storm. The same is true for CAS retry loops. A CAS that fails because another core won the race must retry, which means another coherence transaction.

## Cache-Line Ping-Pong

The ping-pong pattern is the dominant behavior under atomic contention. Core A acquires the line, performs an atomic, and modifies it. Core B then acquires the line, invalidating A's copy. A then acquires it again, invalidating B's copy. The line bounces between cores. Each transfer is a coherence miss. The latency of each transfer includes the request, the snoop or directory lookup, the invalidation, the response, and the data transfer. The throughput of atomics to that line is one operation per transfer latency, regardless of how many cores are waiting.

This is why adding more cores can make a contended atomic counter slower, not faster. The cores spend their time waiting for the line, not doing useful work. The interconnect becomes the bottleneck. On a ring or mesh, the distance between cores affects latency. On a NUMA system, the home node and the remote memory add more latency. On a system with multiple sockets, the coherence traffic may cross an inter-socket link, which is much slower than on-package interconnect.

The ping-pong pattern is also why simple test-and-set locks scale poorly. A test-and-set lock is an atomic read-modify-write on a single lock word. Every waiter spins on that word, generating coherence traffic. When the lock is released, all waiters race to acquire it. One wins, the others fail and retry. The line bounces. A ticket lock improves fairness but still has all waiters spinning on a single counter. A queue lock, such as MCS or CLH, is designed to avoid this. Each waiter spins on its own node, which is usually on a different cache line. The lock holder passes the lock by writing to the next waiter's node. The coherence traffic is distributed, and the line does not ping-pong among all waiters.

The same principle applies to atomic counters. A single global counter is a serialization point. Sharded counters spread the contention across multiple cache lines. Each thread updates its own shard, and a reader sums the shards. The trade-off is that reads are more expensive and the value is not a single atomic location. But the write throughput scales with the number of shards, up to the point where the reader becomes the bottleneck.

## LL/SC Retries and the Cost of Optimism

LL/SC is an optimistic primitive. The load-linked reads a value and hopes that no one will write before the store-conditional. If someone does write, the store fails, and the loop retries. Under low contention, this is efficient. Under high contention, the retry rate can be very high. The core may execute the load-linked, get the line, compute, and then fail the store-conditional because another core wrote the line in the meantime. The work is wasted.

The retry loop also interacts with the memory ordering model. On some architectures, the load-linked and store-conditional have acquire and release semantics, or they can be combined with acquire/release variants. The ordering can add fences or barriers, which increase the cost. On other architectures, the primitives are relaxed, and the programmer must add explicit fences. The choice affects both correctness and performance.

The ABA problem is a separate issue. CAS can succeed even if the value changed from A to B and back to A. This can break algorithms that use pointers or version numbers. LL/SC avoids ABA because any write to the reservation granule invalidates the reservation. But LL/SC can still have spurious failures, and the reservation granule may be larger than the object, causing false conflicts. The trade-off is between the simplicity of CAS and the stronger detection of LL/SC.

## The Cost Model of Atomic Contention

We can build a simple cost model. Let `L` be the uncontended latency of an atomic operation, which is roughly the cache hit latency plus the instruction latency. Let `C` be the coherence transfer latency, which is the time to move the line from one core to another. Let `p` be the probability that an atomic attempt fails and must retry. The expected cost of an atomic operation under contention is roughly `C + p * (C + ...)`, which can be much larger than `L`. The throughput of atomics to a single line is bounded by `1 / C`, because the line can only be transferred so fast.

This model is crude, but it captures the essential trade-off. If `C` is much larger than `L`, and if contention is high, then the atomic operation is dominated by coherence. The number of cores does not help; it only increases the queue of waiters. The system becomes latency-bound on the interconnect.

The model also explains why backoff helps. If a core fails a CAS, it can wait for a short, randomized time before retrying. This reduces the chance that multiple cores collide again immediately. The cost is added latency for the successful operation. Under low contention, backoff is unnecessary and harmful. Under high contention, it can improve throughput by reducing coherence traffic. The optimal backoff depends on the critical section length, the number of contenders, and the coherence latency.

## Memory Ordering and Fences

Atomic operations are not just about atomicity; they are also about ordering. A CAS with sequential consistency is a full barrier. It prevents the compiler and the CPU from reordering memory operations across it. A relaxed atomic does not. The cost of ordering is real. On x86, a `LOCK` prefix is a full barrier. It drains the store buffer and may serialize the pipeline. On ARM, acquire and release are part of the load and store instructions, but they still constrain the memory system. On RISC-V, fences are explicit.

The trade-off is between correctness and performance. If an algorithm requires sequential consistency, you must pay for it. If it only requires acquire-release, you can use weaker primitives and avoid some fences. If it requires only relaxed atomics, you can avoid most ordering, but you must reason carefully about data races and synchronization. The memory model is a contract; violating it leads to bugs that are hard to reproduce.

The microarchitectural cost of fences comes from the need to order memory operations. A store buffer allows a core to continue executing while stores are pending. A fence may require the core to wait until the store buffer is drained. An acquire may prevent later loads from executing before the acquire completes. A release may prevent earlier stores from being visible after the release. These constraints can reduce instruction-level parallelism and increase latency.

## Contention Management Strategies

There is no single solution to atomic contention. The right strategy depends on the workload, the contention level, and the required semantics. Here are the main options and their trade-offs.

Backoff is the simplest. When an atomic fails, wait before retrying. Exponential backoff increases the wait after each failure. Randomized backoff reduces the chance of synchronized retries. The trade-off is latency: a core that backs off may miss a window when the lock is free. Backoff works well when contention is bursty and the critical section is short.

Queue locks, such as MCS and CLH, are designed for high contention. Each waiter enqueues a node and spins on its own node. The lock holder passes the lock by writing to the next node. The coherence traffic is distributed, and the lock is fair. The trade-off is more memory per waiter and more complex code. Queue locks are not always faster under low contention; the overhead of enqueueing can dominate.

Combining, such as flat combining, allows one thread to acquire the lock and execute the operations of many threads. The other threads publish their requests to a shared structure. The combiner executes them in a batch. This reduces the number of coherence transactions. The trade-off is latency for individual operations and the need for a shared publication structure.

Sharding partitions the contended data into multiple independent pieces. A counter can be sharded across cache lines. A hash table can be sharded by key. The trade-off is that global operations, such as reading the total, require aggregating the shards. Sharding is often the most effective way to scale writes, but it changes the semantics.

Read-copy-update (RCU) and seqlocks are read-optimized. Readers do not write shared lines, so they do not generate coherence traffic. Writers copy the data, update a pointer, and wait for readers to finish. The trade-off is memory reclamation complexity and the need for a grace period. RCU is excellent for read-mostly data structures.

Optimistic concurrency control, such as transactional memory or versioned locks, allows multiple threads to proceed speculatively and validate at commit. The trade-off is wasted work on conflicts and the need for a conflict detection mechanism. Under low contention, it can be very fast. Under high contention, it can thrash.

## Why This Matters for System Design

Atomic contention is not a micro-optimization. It is a scalability wall. It appears in counters, reference counts, allocators, locks, queues, and any shared mutable state. A system that looks scalable on paper can collapse when many cores hit the same cache line. The fix is not always a faster atomic instruction; it is often a different data structure or a different sharing pattern.

Profiling atomic contention requires hardware performance counters. Events such as cache misses, coherence misses, and remote cache hits can indicate ping-pong. Tools like `perf` on Linux can count these events. The exact event names vary by architecture. The key is to look for high miss rates on a small number of cache lines. If a single line is responsible for a large fraction of coherence traffic, you have found a contention point.

The design principles are straightforward. Minimize shared mutable state. Prefer per-thread or per-core data. Batch operations to amortize synchronization. Use read-mostly structures where possible. Choose the synchronization primitive that matches the contention level. Measure, do not guess. The cost of an atomic is not a constant; it is a function of the system.

## Inside the Coherence Controller: The Life of a Contended Atomic

When a core executes an atomic read-modify-write, the instruction does not travel to memory as a single indivisible packet. It is decomposed into a sequence of microarchitectural events: address generation, load-store unit allocation, cache lookup, coherence request, ownership acquisition, ALU operation, conditional or unconditional write, and response. The latency of the operation is the sum of those events, and under contention the coherence request dominates.

The load-store unit (LSU) is the entry point. It maintains a queue of pending memory operations. For an atomic, the LSU must ensure that the operation is not split by another core's write. On x86, the `LOCK` prefix turns the instruction into a locked read-modify-write. The LSU may assert a lock signal to the cache hierarchy. If the line is already in the modified or exclusive state in the local L1, the atomic can complete without a coherence transaction. The cache controller performs the read, the ALU computes the result, and the write updates the line. The line remains in modified state. This is the fast path.

If the line is in shared state, the local cache cannot write it. The cache controller sends an upgrade request—often called an invalidate or read-for-ownership (RFO)—to the coherence point. The coherence point may be a snooping bus, a shared last-level cache, a directory, or a home agent. The request asks for exclusive ownership. Other caches that hold the line must invalidate their copies. If another cache holds the line in modified state, it must supply the data and downgrade or invalidate. The requesting core waits for the data and the ownership grant. Only then does the atomic execute. The line is now exclusive to the requester.

This sequence is repeated for every atomic that misses in the local cache in the exclusive state. A failed CAS is not exempt. Even if the compare fails and no write occurs, the core has already acquired exclusive ownership. The coherence transaction has happened. The line may be left in exclusive state, which helps the next atomic from the same core, but it has already invalidated other copies. If another core immediately tries the same atomic, it must now acquire the line from the first core. The ping-pong begins.

The coherence controller has finite resources. Miss status holding registers (MSHRs) track outstanding cache misses. A core can have only a limited number of outstanding coherence requests. If many cores contend on the same line, their MSHRs may fill with requests for that line. Some designs merge multiple read requests for the same line, but an atomic requires exclusive ownership, which cannot be merged with another core's exclusive request. The requests serialize at the coherence point. The coherence point itself may have a queue. The queue depth determines how many contenders can be in flight. Beyond that, cores stall in the LSU or in the instruction pipeline.

The ordering point is critical. In a snooping system, the bus or the shared cache is the serialization point. In a directory system, the home node for the line is the serialization point. The home node receives requests, orders them, and sends invalidations to sharers. The order in which it processes requests becomes the coherence order. For atomics to the same location, that order is the atomic order. The home node may also be a bottleneck. If all cores send requests to the same home node, its request queue becomes a contention point. NUMA systems make this worse: the home node may be on a remote socket, and the request must traverse an inter-socket link.

On ARM and RISC-V, LL/SC uses an exclusive monitor. The load-linked sets a reservation in the local monitor, which is often in the L1 cache. The store-conditional checks the reservation. If the line has been evicted or invalidated, or if another core has written to the reservation granule, the store fails. The reservation granule may be a cache line, a sector, or a smaller unit. A write to a different variable on the same line can clear the reservation. This is a false conflict. The core must retry the loop, which means another load-linked and another coherence transaction if the line is no longer local.

The global monitor is the coherence point's view of the reservation. When another core writes to the line, the global monitor clears the reservation. The store-conditional then fails. The failure is not necessarily due to a true conflict on the same word; it can be due to any write to the granule. This makes LL/SC sensitive to false sharing and to cache evictions. A context switch or a capacity eviction can also clear the reservation, causing a spurious failure. The retry loop must be robust to these failures.

## The Atomic Operation Zoo: Not All Read-Modify-Writes Are Equal

Different atomic operations have different microarchitectural costs. A fetch-and-add is an unconditional read-modify-write. It reads the old value, adds a constant, and writes the new value. A compare-and-swap is conditional: it reads, compares, and writes only if the comparison succeeds. An exchange always writes. A test-and-set always writes. A bit-test-and-set may operate on a bit within a word, but the coherence unit is still the cache line.

The unconditional operations can sometimes be optimized in hardware. Some caches support atomic ALU operations near the cache array. The core sends an operation and an operand to the cache, and the cache performs the read-modify-write locally. This avoids bringing the line into the core's register file. The line still must be in exclusive state, but the data does not need to travel to the core and back. This can reduce latency and energy. Not all CPUs have this feature, and it may be limited to certain operations such as add, increment, or bitwise operations. Compare-and-swap is harder to offload because the comparison depends on the expected value, which must be known. Some designs still perform the compare in the cache, but the core must supply the expected value.

The cost hierarchy is roughly as follows. An uncontended atomic to a line already in modified state in the local L1 is a few cycles to a few tens of cycles. It is an L1 hit plus the ALU operation. An atomic to a line in shared state in the local L1 requires an upgrade, which is a coherence transaction to invalidate other sharers. The latency is the coherence latency, often tens to hundreds of cycles. An atomic to a line not present in the local cache requires a cache miss and a fill, plus ownership. The latency is the memory latency plus coherence. On a multi-socket system, this can be hundreds to thousands of cycles.

The throughput of atomics to a single line is bounded by the coherence transfer rate. Even if each core can issue an atomic every cycle, the line can only be owned by one core at a time. The line must be transferred from core to core. The transfer latency includes the request, the snoop or directory lookup, the invalidation, the data response, and the ownership grant. The inverse of that latency is the maximum throughput. If the transfer takes 100 cycles, the maximum throughput is one atomic per 100 cycles, regardless of the number of cores. Adding cores adds waiters, not throughput.

This is why atomic counters are often replaced with sharded counters. A single counter is a single line. Sharding spreads the counter across multiple lines. Each shard can be owned by a different core simultaneously. The aggregate throughput scales with the number of shards until the coherence point or the interconnect saturates. The cost is that reading the total requires reading all shards, which may be expensive and may not be linearizable. If linearizability is required, a global atomic is still needed, but it can be used less frequently.

## Measuring Contention: From Counters to Line-Level Attribution

You cannot fix atomic contention without measuring it. The first step is to identify whether contention exists. Hardware performance counters can help. Look for events related to cache misses, coherence misses, and remote cache hits. On Intel, events such as `mem_load_l3_miss_retired.remote_hitm` count loads that hit a modified line in another core. On AMD, events such as `ls_dc_miss` and `ls_dc_refill` can indicate cache misses, but the coherence-specific events may have different names. The exact event names vary by microarchitecture. The key is to look for a high rate of cache-to-cache transfers or HITM (hit modified) events.

`perf c2c` is a Linux tool that can attribute cache-line contention to specific lines and addresses. It records HITM events and stores, and it reports which cache lines are experiencing contention. It can distinguish between true sharing and false sharing. True sharing occurs when multiple cores access the same variable. False sharing occurs when they access different variables on the same cache line. `perf c2c report` shows the cache line, the offset, the number of HITM events, and the instructions or functions responsible. This is invaluable for finding hidden contention.

A synthetic microbenchmark can establish a baseline. Write a program with N threads, each incrementing a shared atomic counter in a loop. Measure the total operations per second. Then vary the number of threads, the backoff strategy, and the placement of the counter. Compare a single counter to a sharded counter. Pin threads to cores to avoid migration. Use `rdtsc` or `clock_gettime` to measure cycles or time. Run long enough to reach steady state. Repeat with different cache line alignments. This will show the ping-pong effect directly.

For LL/SC, measure the store-conditional failure rate. Instrument the retry loop to count failures. A high failure rate indicates contention or false sharing. If the failures are due to writes to other variables on the same line, padding the variables will help. If the failures are due to true contention on the same word, the algorithm needs a different strategy, such as backoff or combining.

Software instrumentation can supplement hardware counters. Per-thread counters for retries, backoff time, and critical section length can reveal patterns. But instrumentation changes timing and can hide the problem. Use it carefully, and prefer hardware counters when possible.

## Designing Contention-Aware Data Structures

The best way to handle atomic contention is to avoid it. Design data structures so that shared mutable state is minimized, and so that when it must be shared, the sharing is spread across many cache lines and many coherence points.

Counters are the canonical example. A single global counter is a serialization point. A sharded counter uses one counter per thread, per core, or per NUMA node. Each thread updates its own shard with a relaxed atomic or even a non-atomic increment if it is the only writer. A reader sums the shards. The sum is not linearizable unless the reader stops the world, but for statistics, it is often good enough. If a linearizable global counter is required, use a two-level scheme: per-thread shards and a global counter that is updated only when a shard reaches a threshold. This amortizes the global atomic across many local increments.

Reference counting is another common source of contention. Atomic reference counts are incremented and decremented on every object access. Under high concurrency, the reference count line ping-pongs. Biased reference counting assigns ownership to one thread, which can update the count non-atomically. Other threads use a separate atomic count. Deferred reclamation, such as RCU or hazard pointers, avoids reference counting entirely for read-mostly data. If reference counting is necessary, use per-thread reference counts and aggregate them when the count reaches zero.

Allocators are contention hotspots. A global free list requires an atomic operation on every allocation and free. Per-thread caches, per-CPU slabs, and magazines reduce the frequency of global atomics. Each thread allocates from its local cache. When the cache is empty, it refills from the global pool with a batch. When it is full, it returns a batch. The global atomic is amortized over many operations. This is the design of modern allocators such as tcmalloc and jemalloc. The trade-off is memory overhead and fragmentation.

Queues are often the heart of concurrent systems. A naive MPMC queue with a CAS on the head and tail will ping-pong those lines. A bounded ring buffer with per-producer and per-consumer indices can reduce contention. Each producer reserves a slot with a fetch-and-add on a producer index. The index is on its own cache line. The producer writes the data, then publishes a sequence number. Consumers follow a similar pattern. This is the design of the LMAX Disruptor. The sequence numbers are on separate cache lines, and the data slots are written without contention.

Work-stealing deques are another example. The owner of the deque pushes and pops from one end. Thieves steal from the other end. The owner can often operate without atomics because it is the only one modifying that end. Thieves use CAS on the steal end. This reduces contention and improves locality. The trade-off is that the deque must be designed to allow concurrent access from both ends without corrupting the structure.

Lock-free stacks and queues often use CAS loops. Under contention, the CAS retries can be expensive. Elimination and combining can help. In an elimination backoff stack, a push and a pop can cancel each other out without touching the central stack. This reduces contention on the top-of-stack pointer. Flat combining allows one thread to acquire a global lock and execute the operations of many threads. The other threads publish their requests to a shared structure. The combiner executes them in a batch. This reduces the number of coherence transactions at the cost of latency for individual operations.

Memory ordering is part of the design. Use the weakest ordering that preserves correctness. Relaxed atomics for statistics. Acquire/release for publication. Sequential consistency only when necessary. On x86, relaxed atomic loads and stores are normal instructions, while atomic read-modify-writes are locked. On ARM, acquire and release are part of the load and store instructions, but they still constrain the memory system. Avoid unnecessary fences. A fence can drain the store buffer and serialize the pipeline. Use acquire loads and release stores instead of full fences when possible.

Alignment and padding are not cosmetic. A shared atomic should be aligned to a cache line. Per-thread data should be padded to avoid false sharing. The cache line size is typically 64 bytes on x86 and many ARM cores, but it can be 128 bytes on some systems. Use `alignas` or a platform-specific macro. Check the actual cache line size at runtime if the code must be portable. False sharing can be as expensive as true sharing, and it is often harder to find because the variables are logically independent.

NUMA adds another dimension. Allocate shards on the local node. Use first-touch policy to ensure that memory is placed near the thread that uses it. Avoid remote atomics. If a global atomic is necessary, place the home node near the cores that access it most frequently. For read-mostly data, interleave the memory across nodes to spread the bandwidth.

The design principles are consistent: reduce the frequency of shared writes, increase the distance between writers, batch operations, and choose the weakest synchronization that preserves correctness. Atomic contention is a systems problem, not just an instruction problem. The microarchitecture determines the cost, but the data structure determines the frequency.

## Case Studies: Where the Line Actually Hurts

Contention is easiest to understand when it appears in a system that looks obviously parallel. A server process with 64 worker threads increments a global request counter on every request. The counter is one 8-byte word. At low load, the increment is invisible. At high load, the counter becomes a serialization point. Each thread must acquire the cache line exclusively, increment the word, and release the line. The line bounces between cores. Throughput does not scale with thread count; it collapses toward the rate at which the line can be transferred. The fix is not a faster increment instruction. The fix is to stop incrementing the same line from every thread. Per-thread counters, per-CPU counters, or a sharded counter with periodic aggregation change the sharing pattern. The aggregate read becomes slightly more expensive, but the write path stops generating coherence traffic on every request.

Reference counting is a subtler case. An object is shared across threads, and every copy of a smart pointer increments or decrements an atomic reference count. The object may be hot, but the reference count line is hotter. Every copy operation is a read-modify-write on the same cache line. Under high concurrency, the reference count ping-pongs even though the object itself is read-only. Biased reference counting assigns ownership to one thread, which updates the count non-atomically. Other threads use a separate atomic count. Deferred reclamation avoids the count entirely for read-mostly data. The lesson is that a reference count is not free bookkeeping; it is a hidden atomic on every lifetime transition.

Allocators show the same pattern at a larger scale. A global free list requires an atomic operation on every allocation and free. The free-list head is a single cache line. Every thread that allocates or frees contends on that line. Per-thread caches, per-CPU slabs, and magazines reduce the frequency of global atomics. Each thread allocates from a local cache. When the cache is empty, it refills from the global pool with a batch. When it is full, it returns a batch. The global atomic is amortized over many operations. The trade-off is memory overhead and fragmentation, but the scalability gain is usually worth it. The central free-list line is no longer touched on every allocation.

Lock-free queues are another common case. A naive multi-producer, multi-consumer queue uses CAS on the head and tail pointers. Under contention, those pointers ping-pong. If the head and tail share a cache line, the problem is worse: producers and consumers invalidate each other even when they are operating on different ends of the queue. A bounded ring buffer with per-producer and per-consumer indices reduces contention. Each producer reserves a slot with a fetch-and-add on a producer index. The index is on its own cache line. The producer writes the data, then publishes a sequence number. Consumers follow a similar pattern. The sequence numbers are on separate cache lines, and the data slots are written without contention. The queue still has a global order, but the coherence traffic is distributed across the indices and the slots.

Kernel and runtime systems use the same techniques. Per-CPU counters avoid global atomics on statistics paths. RCU avoids reference counting for read-mostly data. Per-CPU slabs avoid global allocator locks. The common principle is to move shared mutable state out of the hot path or to spread it across many cache lines. False sharing is the enemy in all of these cases. An array of per-thread statistics, where each entry is adjacent in memory, can be as bad as a single global counter. The entries are logically independent, but they share a cache line. Padding each entry to a cache line removes the false sharing. Tools such as `perf c2c` can attribute HITM events to specific lines and show whether the sharing is true or false.

## Lock-Free Algorithms Under Contention: Retry Amplification and Progress

A CAS loop is often described as a single logical operation. It is not. It is a protocol: read the current value, compute a candidate, attempt the CAS, and retry if the CAS fails. Under contention, the retry path is where the cost lives. A failed CAS is not a cheap read. On x86, a `LOCK CMPXCHG` that fails still acquires exclusive ownership of the line. The compare fails, the write is suppressed, but the coherence transaction has already happened. The core may keep the line in exclusive state, which helps if no other core takes it. Under contention, another core takes it immediately. The next attempt must acquire the line again.

This creates retry amplification. Suppose N cores are racing to update the same atomic word. One core wins and modifies the line. The other N-1 cores fail. Each failure is a coherence transaction that acquired ownership and then lost it. The losers retry, generating more ownership requests. The line ping-pongs among the losers even though only one update succeeds. The throughput of successful updates is bounded by the coherence transfer rate, but the coherence traffic is multiplied by the number of failed attempts. The system spends more time moving ownership than doing useful work.

The same amplification appears in LL/SC. A load-linked sets a reservation. The core computes a new value. The store-conditional succeeds only if the reservation is still valid. If another core writes to the reservation granule, the store fails. The core must retry the entire loop. The failure may be a true conflict on the same word, or it may be a false conflict caused by a write to a different variable on the same cache line. The reservation granule is often a cache line or a sector, so false sharing directly increases the store-conditional failure rate. A context switch or a capacity eviction can also clear the reservation, causing a spurious failure. The retry loop must be robust to these failures, but robustness does not make them free.

Progress guarantees are often confused with performance guarantees. A lock-free algorithm guarantees that some thread makes progress in a finite number of steps. It does not guarantee that every thread makes progress. Under contention, a particular thread can starve while others repeatedly win the CAS. A wait-free algorithm guarantees per-thread progress, but it usually requires more coordination and more atomic operations. An obstruction-free algorithm guarantees progress only when a thread runs in isolation. These guarantees are about liveness, not about throughput. A lock-free counter can be technically lock-free and still scale terribly because every operation contends on the same line.

Contention collapse is the practical consequence. As more cores are added, the throughput of atomics to a single line does not increase. It may decrease because more cores generate more ownership requests. The interconnect becomes saturated with invalidations and data transfers. The cores spend their time waiting for the line, not executing application code. The queue of waiters grows. The system is latency-bound on the coherence protocol. Adding cores increases the queue length, not the service rate.

Backoff and combining are responses to retry amplification. Backoff reduces the rate at which losers retry, lowering the coherence traffic. Combining allows one thread to execute the operations of many threads, reducing the number of ownership acquisitions. Both trade latency for throughput. The right choice depends on the critical section length, the number of contenders, and the cost of a coherence transfer. A short critical section with many contenders benefits from backoff or combining. A long critical section with few contenders may not. The algorithm must be designed for the contention regime it will actually encounter.

## Memory Ordering and the Cost of Publication

Atomicity and ordering are separate problems. An atomic operation can be relaxed and still be atomic. It guarantees that the read-modify-write is indivisible, but it does not order surrounding memory operations. Publication requires ordering. A thread initializes a data structure, then publishes a pointer with a release store. A reader acquires the pointer with an acquire load and then reads the data. The release store prevents the initialization from being reordered after the publication. The acquire load prevents the reader's subsequent loads from being reordered before the pointer load. This is the acquire-release contract.

The cost of that contract depends on the architecture. On x86, the memory model is TSO. A release store is a normal store with a compiler barrier. An acquire load is a normal load with a compiler barrier. A locked CAS is a full barrier. The hardware already orders stores and loads in most cases, so the explicit fence cost is often low. On ARM and RISC-V, the memory model is weaker. Release stores and acquire loads are special instructions or fences. They constrain the memory system and can reduce instruction-level parallelism. A full fence may drain the store buffer and wait for outstanding writes to become visible. Under contention, the store buffer may be full, so the fence waits longer. The ordering cost is not constant; it depends on the state of the memory system.

A sequential-consistent CAS is a full barrier. It orders all prior and subsequent memory operations. This is expensive when the algorithm only needs acquire-release semantics. A relaxed CAS plus explicit fences can be cheaper, but only if the fences are placed correctly. A common mistake is to use a relaxed CAS for publication and assume that the data will be visible. It will not be visible without a release. Another mistake is to use a full fence everywhere, paying for ordering that the algorithm does not need. The weakest ordering that preserves correctness is the right choice, but finding it requires reasoning about the memory model.

Seqlocks illustrate the interaction between ordering and contention. A writer increments a sequence number, updates the data, and increments the sequence again. Readers read the sequence, read the data, and re-read the sequence. If the sequence changed or is odd, the reader retries. The sequence line is written by the writer and read by readers. Under read-mostly workloads, the sequence line is shared and rarely invalidated. Under write-heavy workloads, the writer invalidates the readers' copies on every update. The readers then retry. The cost is optimistic concurrency: readers do work that may be discarded. The benefit is that readers do not write shared lines. The trade-off is favorable when writes are rare and reads are frequent.

The memory model is a contract, and the microarchitecture enforces it with real costs. Ordering constraints can serialize the pipeline, drain store buffers, and expose coherence latency. Under contention, those costs are amplified because the memory system is already saturated. The algorithm designer must choose the weakest ordering that preserves correctness and must measure the cost of the fences that remain. The next layer is measurement and hardware trends, where the same principles reappear in different forms.

## Hardware Trends That Change the Contention Equation

The cost model in the previous sections assumes a cache line, a coherence point, and a set of cores. Modern CPUs change all three. Core counts per socket have grown, but the number of coherence points has not grown at the same rate. A last-level cache may be split into slices, each with its own directory or tag array. A request for a line is routed to a slice by address hashing. That slice becomes the serialization point for the line. If many cores contend on the same address, they all target the same slice. The slice's request queue and its bandwidth become the bottleneck. The rest of the last-level cache may be idle. This is address-based contention that is invisible in the source code. Two variables that are far apart in memory can still map to the same slice if the hash collides. The hash is designed to spread addresses, but it cannot spread a single hot line.

The trend toward non-inclusive and exclusive caches changes the ownership path. In an inclusive hierarchy, a line in a private cache is also present in the last-level cache. An invalidation from the coherence point can be satisfied by invalidating the private copy. In a non-inclusive hierarchy, the last-level cache may not hold the line. The coherence point must track the private copies or probe them. Ownership acquisition may require a snoop to the private caches. The latency and the number of transactions increase. The atomic still acquires exclusive ownership, but the path is longer. The cost model's `C` is not a single number; it depends on where the line is and which caches hold it.

Atomic execution near the cache is another trend. Some processors can perform simple read-modify-write operations in the cache or in a memory-side accelerator. The core sends an operation and an operand, and the cache performs the update. The line does not need to travel to the core's register file. This reduces latency and energy for operations such as fetch-and-add. Compare-and-swap is harder because the comparison depends on the expected value. The core must supply the expected value, and the cache must perform the compare and conditionally write. Some designs support this, but the benefit is smaller. The important point is that the cost hierarchy is not fixed. The same instruction can have different costs on different microarchitectures. The algorithm should not assume a particular cost; it should measure.

Larger cache lines and sectors also change the false-sharing calculus. A 64-byte line is common, but some systems use 128-byte lines or fetch in sectors. A write to one sector may invalidate the whole line or only the sector. If the coherence granularity is a sector, false sharing is reduced. If it is the full line, false sharing is unchanged. The reservation granule for LL/SC may be a line or a sector. The programmer must know the granularity to pad correctly. The safe approach is to align shared atomics to the largest plausible coherence unit and to separate hot variables by at least that amount. The cost is memory overhead, but the alternative is hidden contention.

## Chiplets, Coherence Domains, and the New Distance

The move to chiplet-based processors adds a new dimension to atomic contention. A package may contain multiple dies, each with its own cores and cache slices. The dies are connected by a package-level interconnect. Coherence is maintained across the dies, but the latency is not uniform. A cache line may be homed on one die and requested by a core on another. The request crosses the die-to-die link. The link has lower bandwidth and higher latency than the on-die mesh. An atomic to a line that is homed on a remote die pays that cost on every ownership transfer. If the line ping-pongs between dies, the link becomes the bottleneck. The throughput of atomics to that line is bounded by the die-to-die link, not by the on-die coherence protocol.

This creates coherence domains. Cores within a domain have lower-latency coherence than cores across domains. The exact boundaries depend on the design. A domain may be a die, a cluster of cores, or a NUMA node. The key is that the cost of an atomic depends on the relationship between the requester and the home. A line that is local to a domain is cheap to acquire. A line that is remote is expensive. If many cores across domains contend on the same line, the line bounces across the slow link. The system may have many cores, but the atomic throughput is limited by the cross-domain path.

The design implication is to shard by domain. A per-domain counter is cheaper than a global counter because the line stays within the domain. A global counter that is updated from every domain pays the cross-domain cost on every update. If a global count is required, update it in batches. Each domain accumulates a local count and periodically adds it to the global count. The global atomic is amortized over many local operations. The same pattern applies to locks. A global lock that is acquired from every domain is a cross-domain serialization point. A hierarchical lock with per-domain locks and a global lock reduces the frequency of cross-domain acquisitions. The trade-off is more complex code and potential fairness issues.

Placement matters. The home node of a line is determined by the physical address. The operating system and the allocator control the physical address. First-touch allocation places the line on the node that first writes it. If the hot line is first touched by a core on one domain and then contended by cores on another, the home is remote for most contenders. The allocator can interleave or replicate the line, but replication changes the semantics. For read-mostly data, replication is fine. For a single atomic word, replication is not possible without a coherence protocol that supports it. The alternative is to place the line near the cores that write it most frequently. If the writers are spread across domains, no single placement is optimal. Sharding is the only way to avoid the cross-domain ping-pong.

The topology also affects queueing behavior. A cross-domain link may have a limited number of virtual channels. Atomic requests and responses compete with normal cache fills. Under heavy contention, atomic traffic can starve normal memory traffic. The system may slow down for unrelated workloads. This is a form of interference that is hard to see in application-level metrics. Hardware counters that report link utilization and queue occupancy can reveal it. The design principle is to keep atomic traffic local and to avoid making a remote line hot.

## Atomic Contention in Heterogeneous Systems

Heterogeneous systems add another layer. A CPU and an accelerator may share memory but not the same coherence domain. The accelerator may have its own caches and its own atomic units. System-scope atomics that cross the host-device boundary are much more expensive than device-scope atomics. They may require a round trip over a PCIe or an on-package link. The atomic operation may be serialized at a host bridge or a memory controller. The cost model's `C` becomes the link latency, which can be thousands of cycles. The throughput of system-scope atomics is correspondingly low. The design principle is to avoid fine-grained system-scope atomics. Use device-scope atomics within the accelerator and batch updates to the host. Use message passing or queues instead of shared atomic counters across the boundary.

Within an accelerator, atomics have their own microarchitecture. A GPU may perform atomics in a shared L2 cache. The L2 is partitioned into slices. Atomics to the same address serialize at the slice. The GPU can mitigate contention by aggregating atomics within a warp or workgroup. If all lanes in a warp increment the same counter, the hardware or the compiler can reduce the operations to a single atomic. The result is broadcast to the lanes. This is warp-aggregated atomics. It reduces the number of coherence transactions by the warp size. The same idea applies to workgroup-level reductions. The programmer can accumulate per-thread values in shared memory and perform one atomic per workgroup. The cost is a reduction step, but the atomic traffic is reduced by the workgroup size. The trade-off is favorable when the atomic is hot and the workgroup is large.

The memory scope is part of the contract. A device-scope atomic is only atomic with respect to other device-scope operations. A system-scope atomic is atomic with respect to the host and other devices. The stronger scope is more expensive. The algorithm should use the weakest scope that preserves correctness. If the data is only shared within the device, device scope is sufficient. If the data is shared with the host, system scope is required. The cost difference can be large. The programmer must know the scope of each atomic and must not use system scope by default.

The same principles apply to other accelerators. The key is to understand the coherence domain and the atomic granularity. An atomic that is cheap within a domain may be expensive across domains. The data structure should be partitioned by domain. The cross-domain communication should be coarse-grained. The atomic contention problem does not disappear; it moves to a different layer.

## Measurement in the Presence of Topology

Measuring contention in these systems requires more than counting cache misses. The topology matters. A high miss rate on a local line may be cheap; a lower miss rate on a remote line may be expensive. Hardware counters must be interpreted with the topology in mind. Uncore counters can report traffic on the die-to-die link and the memory controller. If atomic traffic is a significant fraction of the link traffic, the link is a bottleneck. Application-level throughput may be limited by the link, not by the cores.

Synthetic microbenchmarks should vary the placement. Pin threads to cores on the same domain and on different domains. Measure the atomic throughput in each case. The difference is the cross-domain cost. Vary the number of domains and the number of threads per domain. The throughput curve will show whether the bottleneck is the local coherence point or the cross-domain link. Use a sharded counter as a control. If the sharded counter scales but the single counter does not, the contention is on the single line. If neither scales, the bottleneck may be the interconnect or the memory controller.

The measurement must also account for frequency scaling and power management. An atomic-heavy workload may run at a lower frequency because coherence traffic consumes power. The throughput per cycle may be higher than the measured throughput per second suggests. Comparisons between configurations should use cycles or normalized time when possible. Absolute time is still important for the user, but microarchitectural analysis needs cycles.

Atomic contention is a moving target. The hardware changes, the topology changes, and the workload changes. The cost model is a guide, not a constant. The algorithm should be designed to adapt. Backoff parameters can be tuned at runtime. Sharding can be adjusted based on the number of active threads. The system should measure contention and change its behavior. The microarchitecture provides the signals; the software must listen.

This is not a conclusion. It is a continuation of the same problem into new hardware. The next layer is the interaction between contention and progress guarantees in real lock-free algorithms, where retry behavior and memory ordering meet the topology.
