# Morsel-Driven Parallelism: How Modern Query Engines Schedule Work Without a Global Plan

There is a version of parallel query execution that fits neatly on a whiteboard: take the physical plan, insert an exchange operator wherever a pipeline should fan out, assign each operator instance to a thread, and let the threads run. The plan *is* the schedule. Every operator knows how many threads it owns, every thread knows which fragment of the plan it executes, and the shape of the query determines the shape of the parallelism.

That model is easy to reason about, and it is wrong often enough to matter. The failure is rarely in the operators — hash joins, aggregations, and sorts parallelize fine in isolation. The failure is in the assumption that the *plan* can predict the *schedule*. It cannot, because the schedule depends on data distribution, on cache and memory topology, on which threads happen to be descheduled, and on the fact that a hash join's build side is almost never uniform.

Morsel-driven parallelism is the alternative that most high-performance analytical engines converged on. Rather than assigning work to threads at plan time, it defers assignment to runtime and makes the unit of work small enough to be scheduled dynamically. This article examines the design in detail: what a morsel actually is, why the dispatcher is a pull-based queue rather than a static partition, how NUMA topology turns a scheduling decision into a memory-locality decision, and where the model breaks down.

## Operator-level parallelism and its three bad assumptions

The classic approach — call it plan-driven or operator-level parallelism — extends the Volcano iterator model with an exchange operator. An exchange sits between two operators and moves tuples from N producer threads to M consumer threads, either by broadcasting (for the build side of a broadcast join) or by hash-partitioning on a key (for a partitioned join or a parallel aggregation). Each operator instance then runs the ordinary single-threaded `next()` loop over its own input partition.

This works, and it has worked for decades. But it rests on three assumptions that hold only sometimes.

**Assumption one: the plan knows the right degree of parallelism.** In a plan-driven engine, the number of partitions is a property of the plan node, fixed when the plan is instantiated. If the machine has 64 cores and the plan allocates 8 threads to a pipeline because the optimizer estimated a small cardinality, 56 cores idle. If the estimate is wrong in the other direction, threads contend for the same hash table buckets. Adaptive query execution can re-plan mid-flight, but re-planning is coarse: you get a new plan, not a finer-grained schedule, and the transition itself costs a barrier.

**Assumption two: partitioning produces balanced work.** Hash partitioning on a skewed key — a `country` column where one value is 40% of rows, a `user_id` with a power-law distribution — sends a disproportionate share of tuples to one partition. The thread that owns that partition becomes the critical path while the others finish and wait at the next pipeline breaker. The usual mitigations (salting the key, detecting skew and splitting hot partitions) are effective, but they add complexity to the plan and to the data movement, and they only work when the skew is detected before it is paid for.

**Assumption three: the plan's boundaries are the right scheduling boundaries.** A pipeline breaker — the build phase of a hash join, a sort, a blocking aggregation — is a barrier. Every thread must finish its input before any thread can proceed. If one partition is 5% slower, the entire pipeline pays that 5% as idle time. With several pipeline breakers in a query, these stalls compound, and the tail of one stage becomes the head of the next.

None of this means exchange-based parallelism is obsolete. It means the exchange is a *data movement* primitive, and using it as a *scheduling* primitive conflates two concerns. Morsel-driven execution keeps the exchange for data movement and replaces the scheduling with something dynamic.

## What a morsel is

A morsel is a small, contiguous chunk of tuples — small enough that the working set of a pipeline stage over one morsel fits in L2 cache. In practice, engines size morsels in the range of tens of thousands of tuples or a few hundred kilobytes, tuned per workload; the exact number matters less than the property it buys.

The critical design decision is what a worker does with a morsel. It does not execute one operator over the morsel and hand the result to the next operator. It executes the *entire pipeline* over the morsel — scan, filter, probe, aggregate — before returning to the dispatcher for more work.

That single change has several consequences.

**Intermediate results stay hot.** In the operator-at-a-time model, a tuple produced by a filter is written to a materialization buffer or passed through a virtual `next()` call, and by the time the downstream operator consumes it, the cache line may be gone. In the morsel model, the filter's output for a morsel is consumed by the probe almost immediately, while it is still in L1 or L2. The pipeline becomes effectively a loop over a small array, which is also the shape that compilers vectorize well.

**The degree of parallelism becomes a runtime fact.** There is no "number of partitions" in the plan. There is a dispatcher holding a queue of morsels and N worker threads pulling from it. If the OS schedules only 40 of 64 workers, 40 morsels are in flight. If the query is short and only 4 morsels exist, only 4 workers do anything — no idle threads parked on empty partitions, no wasted setup cost proportional to the configured parallelism.

**Load balancing is automatic and fine-grained.** A worker that draws a morsel from a hot region of the hash table takes longer than one drawing from a cold region, but the imbalance is bounded by the cost of one morsel, not by the cost of an entire partition. The next pull rebalances. This is the same argument that makes work-stealing schedulers robust to irregular parallelism, applied at the granularity of data rather than tasks.

The costs are real and worth stating plainly.

*Per-morsel overhead.* Each morsel requires pipeline setup: resetting aggregation state, positioning a scan cursor, possibly re-acquiring a reference to shared state. If morsels are too small, this overhead dominates and the engine spends its time in bookkeeping. If they are too large, the working set spills out of L2 and the locality argument evaporates. Morsel size is a tuning parameter with no universally correct value, and engines that expose or auto-tune it do so because the right answer depends on tuple width, operator mix, and cache size.

*Shared state.* A hash join's build side is shared across all workers. Morsels do not eliminate the need for partitioning or synchronization of that shared structure; they change the granularity at which it is accessed. In practice, engines partition the hash table by the same key used to partition the probe side, so each worker probes a partition it owns — which reintroduces the skew problem at the level of the shared structure, just with finer granularity and better amortization.

*Non-determinism.* With dynamic scheduling, the order in which morsels are processed is not fixed. Aggregations that are order-sensitive (floating-point sums, `LIMIT` without `ORDER BY`, anything relying on insertion order) produce different results run to run. Engines handle this by making aggregation order-insensitive, by fixing a deterministic merge order, or by accepting the non-determinism and documenting it. This is a genuine trade-off, not a bug to be fixed.

## The dispatcher: pull, not push

The dispatcher is the component that holds morsels and hands them to workers, and its design determines contention behavior at high core counts.

The simplest version is a single atomic counter over a contiguous array of morsel descriptors. A worker performs a fetch-add to claim the next index. This is nearly optimal at small core counts and degrades as cores grow: every claim writes the same cache line, so the line ping-pongs between sockets, and the atomic operation becomes a serialization point. At 64+ cores, the counter itself can become the bottleneck when morsels are short.

The standard fix is sharding: one queue per NUMA node, or per group of cores, with work stealing between queues. A worker prefers its local queue; if empty, it attempts to steal from a remote one. This is structurally similar to Cilk-style deques, with one important difference: morsels are not tasks with dependencies, so stealing is trivial. There is no join, no continuation, no parent-child relationship to maintain. The dispatcher can be a simple lock-free ring buffer or stack per node.

Pull versus push matters more than it first appears. In a push model, the dispatcher assigns morsels to workers and must track completion; a slow worker creates a backlog of assigned-but-unfinished work that the dispatcher cannot rebalance without preemption. In a pull model, a worker is idle precisely when it holds no morsel, so queue length is a direct measure of available parallelism. Pull also makes backpressure natural: if the morsel producer — the scan side — cannot keep up, workers simply find the queue empty and park.

The producer side deserves equal attention. Morsels do not appear from nowhere; something must split the input into them. For a columnar scan, that is straightforward: split row groups or column chunks into morsel-sized ranges. For a hash join probe, the probe side must itself be morselized, which means the build side's partition boundaries and the probe side's morsel boundaries have to be reconciled. Engines typically materialize the probe side into partitioned buffers first, then morselize each partition. That materialization is a pipeline breaker, and it is where a substantial fraction of the real cost lives.

## NUMA locality is a scheduling constraint, not an optimization

On a multi-socket machine, memory access latency and bandwidth depend on which node the data lives on. A worker on socket 0 reading a page allocated on socket 1 pays a remote-access penalty on every cache miss. For a memory-bandwidth-bound scan, that penalty can dominate the useful work.

Morsel-driven engines treat this as a scheduling constraint rather than a post-hoc optimization. The pattern looks like this:

- Memory is allocated with first-touch semantics, so a page lands on the node of the thread that first writes it.
- Workers are bound to nodes via thread affinity, and each node owns its own morsel queue.
- Morsels carry an affinity tag indicating where their data resides, and the dispatcher prefers to hand a morsel to a worker on that node.

The tension is between locality and balance. Strict node-local scheduling leaves workers idle when one node's queue drains while the other still has work. Allowing stealing across nodes recovers the balance but pays remote-access cost for the stolen morsels. The usual resolution is to steal only when the local queue is empty, and to steal a *batch* of morsels rather than one, amortizing the remote-access penalty across more work. Some engines go further and re-partition data at pipeline boundaries to restore locality, trading explicit data movement for subsequent local access.

This is where the abstraction earns its keep. Because the unit of work is small and self-contained, moving it between nodes is cheap and requires no re-planning. In an operator-level engine, moving work between nodes means moving a partition, which means an exchange, which means a barrier and a synchronization point.

There is a second-order effect worth naming: morsel-driven scheduling interacts with the memory allocator. If the allocator hands out memory from a global pool without node awareness, first-touch placement becomes accidental rather than intentional, and the affinity tags on morsels describe a topology that the data does not actually follow. Engines that take NUMA seriously end up owning their allocator, or at least their large-allocation path, for exactly this reason.

And once shared state, pipeline breakers, and vectorization enter the picture, the simple story above acquires several sharp edges — which is where the next part of this discussion picks up.

## Shared state and the limits of morselization

Morsels make the unit of scheduling small, but they do not make the data structures small. A hash join's build side is still a shared, mutable structure that every probe morsel must access. The question is not whether sharing exists, but at what granularity it is synchronized.

The common design is to partition the hash table by the join key, so that each probe morsel only touches one partition. If the probe side is also partitioned by the same key, a worker probing a morsel from partition *i* only reads the hash table partition *i*. This eliminates cross-partition synchronization, but it does not eliminate contention within a partition: multiple workers can be probing the same partition simultaneously if the dispatcher hands out morsels from the same partition to different workers. To avoid that, engines either assign each partition to a single worker (a partition-per-worker model, which reintroduces static assignment) or allow concurrent access with fine-grained latches or lock-free techniques.

Lock-free hash tables are attractive because they avoid the overhead of acquiring and releasing latches per morsel. But they impose their own costs. Insertions during the build phase require atomic compare-and-swap on bucket heads, and the memory ordering constraints (acquire-release semantics) can be expensive on some architectures. More importantly, lock-free structures are difficult to resize: if the build side grows beyond the initial capacity, resizing requires coordinating with concurrent readers, which typically means a global barrier or a complex epoch-based reclamation scheme. Many engines sidestep this by sizing the hash table from an estimate and accepting some waste, or by spilling to disk when the estimate is exceeded.

Even with partitioning, false sharing can degrade performance. If two workers are updating different counters or bucket heads that happen to reside on the same cache line, the line ping-pongs between cores. Morsel-driven engines mitigate this by padding shared structures to cache-line boundaries and by giving each worker thread-local state (e.g., per-thread hash tables for local aggregation) that is merged later. The merge is a pipeline breaker, but it is a cheap one compared to the cost of synchronizing every update.

The key insight is that morsel-driven scheduling shifts the synchronization burden from the scheduler to the data structures. The dispatcher is simple and lock-free; the complexity moves into the operators, which must be designed to tolerate concurrent access at morsel granularity. This is a deliberate trade-off: scheduling is made cheap and dynamic, while data structure access is made more complex but amortized over many tuples.

## Pipeline breakers: the barriers you cannot morsel away

A morsel can flow through a pipeline of operators without materializing intermediate results, but it cannot flow through a pipeline breaker. The build phase of a hash join must complete before any probe can begin. A sort must finish before the merge. A hash aggregation that spills must finish building before it can emit. These are hard barriers, and morsel-driven execution does not remove them.

What morselization does is make the work *within* a breaker parallel and load-balanced. Consider the build side of a hash join. The input is partitioned by the join key. Each partition is then morselized: workers pull morsels from the partition's queue and insert tuples into the partition's hash table. If one partition is larger than the others, its morsels are still small, so multiple workers can drain that partition's queue in parallel. The barrier remains, but the time spent behind the barrier is minimized because no single worker is stuck with an entire hot partition.

The same logic applies to sorting. A parallel sort can be decomposed into a local sort phase and a merge phase. In the local phase, each worker pulls a morsel, sorts it in memory, and writes it as a run. The runs are then merged. The merge phase can also be morselized: each worker pulls a range of the output and merges from the appropriate runs. But the merge is a barrier: all local sorts must finish before any merge can start. Morsel-driven execution does not overlap these phases; it only ensures that the local sort phase is well-balanced.

Some engines attempt to overlap phases by pipelining morsels through the barrier. For example, in a hash join, a worker could start probing a partition as soon as that partition's build is complete, even while other partitions are still building. This is possible if the build and probe are partitioned by the same key and each partition is independent. The dispatcher can then schedule probe morsels for partition *i* while build morsels for partition *j* are still running. This is a form of intra-query pipelining that morsel-driven scheduling enables naturally, because the unit of work is small and the dependencies are per-partition. The barrier is not global; it is per-partition.

However, per-partition pipelining introduces its own complexity. The dispatcher must track which partitions are ready for probing, and workers must not steal probe morsels for partitions that are not yet built. This requires a dependency graph between morsels, which is exactly the kind of structure that morsel-driven scheduling tries to avoid. In practice, many engines keep the global barrier for simplicity and rely on morselization to make the barrier short.

The materialization tax is another pipeline breaker that morselization cannot eliminate. Before a probe side can be morselized, it often must be materialized into partitioned buffers. This is a full pass over the probe input, writing tuples to buffers according to their partition. The pass itself can be morselized: workers pull morsels from the probe input, compute the partition for each tuple, and append to the corresponding buffer. But the buffers are shared, so writes must be synchronized or each worker must have its own set of buffers that are merged later. The merge is a barrier. The cost of this materialization is often a significant fraction of the total query time, and it is a cost that operator-level parallelism pays as well—the difference is that morsel-driven execution makes the materialization pass itself load-balanced.

## Vectorization and the morsel-vector interplay

Vectorized execution processes tuples in batches, using SIMD instructions to apply an operation to many tuples at once. The batch size is typically a few hundred to a few thousand tuples, chosen to fit in L1 cache and to amortize the overhead of function calls and loop setup. Morsels are larger—tens of thousands of tuples—and are chosen to fit in L2. The two concepts are complementary: a morsel contains multiple vectors.

The interplay matters because vectorization imposes constraints on morsel size. If a morsel is too small, the pipeline spends more time on vector setup and teardown than on useful work. If a morsel is too large, the intermediate results of the pipeline spill out of L2, and the locality benefit is lost. The sweet spot is usually a morsel size that is a multiple of the vector size, so that the last vector is not partially filled. Engines that auto-tune morsel size often round to the nearest multiple of the vector width.

Vectorization also changes the cost model for morsel processing. In a scalar pipeline, the cost of processing a morsel is proportional to the number of tuples. In a vectorized pipeline, the cost is proportional to the number of vectors, plus a fixed overhead per morsel. This means that larger morsels amortize the fixed overhead better, but they also increase the risk of cache misses. The optimal morsel size depends on the operator mix: a scan-heavy pipeline benefits from larger morsels, while a join-heavy pipeline benefits from smaller morsels because the hash table access pattern is less predictable.

Another interaction is with branch prediction. Vectorized code avoids branches by using selection vectors or by masking. But the data within a morsel may still be skewed, causing the selection vector to be dense in some regions and sparse in others. Morsel-driven scheduling can help by splitting skewed data into smaller morsels, so that each morsel is more uniform. This is a form of adaptive morselization that some engines implement: if a morsel is detected to be highly skewed (e.g., by monitoring the selectivity of a filter), it is split into smaller morsels before being handed to workers.

## Skew, determinism, and the operational cost of dynamic scheduling

Skew is the persistent enemy of any parallel execution model, and morsel-driven parallelism does not defeat it—it merely changes the granularity at which skew is felt. If a key is hot, the morsels that contain that key will take longer to process, regardless of how small they are. The advantage of morsels is that the imbalance is bounded by the cost of a single morsel, not by the cost of an entire partition. But if the hot key is spread across many morsels, each morsel still contains some hot tuples, and the worker processing that morsel will be slower. The tail latency is reduced, but it is not eliminated.

To handle skew, engines combine morsel-driven scheduling with skew-aware partitioning. For example, a hash join might detect that a partition is too large and split it into sub-partitions using a different hash function. The sub-partitions are then morselized separately, so multiple workers can process the hot key. This is a form of dynamic repartitioning that happens at runtime, guided by the observed sizes of partitions. The cost is additional data movement and a more complex dispatcher.

Determinism is another operational cost. With dynamic scheduling, the order in which morsels are processed is non-deterministic. For aggregations that are order-sensitive—floating-point sums, string concatenations, or any operation that is not commutative and associative—the result can vary from run to run. Engines handle this in several ways. The simplest is to make the aggregation order-insensitive by using a fixed merge order: each worker produces a partial aggregate, and the partials are merged in a deterministic order (e.g., by worker ID or by partition ID). This requires a barrier and a merge step, but it guarantees reproducibility. Another approach is to use a deterministic hash function and a deterministic scheduling policy, so that the same morsels are processed in the same order every time. This is rarely done in production because it limits the scheduler's ability to balance load.

Non-determinism also complicates debugging and profiling. If a query produces a wrong result, it may be due to a race condition that only manifests under a particular interleaving of morsels. Reproducing the bug requires reproducing the schedule, which is difficult. Some engines offer a deterministic mode for testing, where the dispatcher uses a fixed seed and the workers process morsels in a fixed order. This mode is slower but makes bugs reproducible.

The operational cost of dynamic scheduling is therefore not just the overhead of the dispatcher, but the loss of predictability. Plan-driven engines produce the same schedule every time, which makes performance tuning and debugging easier. Morsel-driven engines trade that predictability for robustness under skew and NUMA. The trade-off is worth it for large, complex queries on modern hardware, but it is a trade-off nonetheless.

## Scheduling policies: the dispatcher is not just a queue

A dispatcher that only implements first-come, first-served over a sharded queue is already a large improvement over plan-time assignment, but it leaves performance on the table. The order in which morsels are processed affects cache behavior, memory locality, and the length of the critical path. Engines that treat the dispatcher as a policy-free component miss this.

The first policy question is whether to use FIFO or LIFO. FIFO is fair and makes queue depth a meaningful measure of backlog. LIFO, by contrast, improves locality: the morsel most recently produced is the one most likely to have its input still in cache, and processing it next avoids evicting that data. LIFO also tends to shorten the critical path in recursive or divide-and-conquer workloads, because the work that unblocks the most downstream work is often the work that was just created. The cost is that old morsels can starve, which matters when the queue is long and the query has a deadline. A common compromise is to use LIFO for local queues and FIFO for stealing, so that a worker drains its own recent work first but does not leave remote work stranded.

The second question is whether morsels carry enough metadata to make cost-aware decisions. A morsel descriptor can include the estimated cardinality of its input, the selectivity of filters applied so far, the partition identifier, and an affinity tag. With that metadata, the dispatcher can approximate the critical path: a morsel that belongs to a partition with many remaining morsels is more valuable to schedule early than one from a partition that is almost drained. This is not full-blown list scheduling, which would require a dependency graph and a cost model, but it is a lightweight heuristic that recovers much of the benefit. Some engines go further and maintain a priority queue keyed by estimated remaining work per partition, so that workers are drawn toward the tail of the query rather than the head.

Cost-aware scheduling interacts with prefetching. If the dispatcher knows that the next morsel will scan a particular range of a column, it can issue a prefetch for that range before handing the morsel to a worker. The prefetch is not free—it consumes memory bandwidth—but it can hide latency for scans that would otherwise stall on DRAM. The same idea applies to hash table partitions: a worker that is about to probe partition i can prefetch the first cache lines of that partition's buckets. These are micro-optimizations, but at high core counts the difference between a stall and a prefetch is the difference between linear scaling and a plateau.

Work stealing deserves a more precise treatment than the usual steal-when-idle rule. Stealing a single morsel from a remote queue is often a poor trade: the remote-access penalty for the queue metadata and the stolen morsel's data can exceed the cost of the morsel itself. Stealing a batch—say, four to sixteen morsels—amortizes that penalty and gives the thief enough work to justify the trip. The batch size should adapt to the observed steal rate: if steals are rare, a larger batch is fine; if the system is oscillating between idle and overloaded, smaller batches reduce latency. Some engines also implement stealing with a backoff, so that a worker that fails to steal does not immediately retry and add contention to the remote queue.

Backpressure is the other half of the dispatcher's job. A pull-based queue naturally applies backpressure on the consumer side: if workers are slow, the queue grows, and the producer eventually blocks or spills. But the producer side can also be a bottleneck. If a scan cannot produce morsels fast enough, workers park and utilization drops. The dispatcher should therefore expose queue depth and production rate as signals that the query scheduler can use to adjust the number of active workers or to change the morsel size. A queue that is consistently empty means the engine is producer-bound; a queue that is consistently full means it is consumer-bound. Neither condition is fixed, because the operator mix changes as the query progresses.

Cancellation and early termination are policy concerns that plan-driven engines handle poorly. In a morsel-driven engine, a LIMIT can be enforced by having the dispatcher stop handing out morsels once the limit is reached. Workers that are already processing morsels finish them, but no new work is started. This is much cheaper than propagating a cancellation signal through a tree of operators. The same mechanism supports query timeouts and admission control: when a query is preempted, the dispatcher simply stops issuing morsels, and the workers drain. The morsel is the unit of cancellation, which makes preemption predictable and bounded.

The morsel lifecycle itself is worth designing carefully. A morsel is created by a producer, enqueued, claimed by a worker, processed, and retired. If the producer allocates a new descriptor for every morsel, the allocator becomes a contention point. Engines avoid this by pooling descriptors and by using per-worker free lists. Retirement is equally important: a morsel that has been processed must release its input buffers, or the pipeline will run out of memory. Reference counting is the usual mechanism, but it must be cheap enough to not dominate the per-morsel cost. In practice, morsel descriptors are small, fixed-size structures, and the buffers they point to are managed by the operator that produced them.

## Elastic workers, memory pressure, and the cost of spilling

Morsel-driven scheduling is often described as if the number of workers is fixed at query start. In a cloud setting, that assumption is wrong. The engine may run inside a container with a CPU quota, alongside other queries, on a machine whose available cores change as other workloads start and stop. The dispatcher must therefore tolerate a worker pool that grows and shrinks.

The simplest elastic policy is to maintain a target number of active workers and to let the OS scheduler decide which threads run. If the target is too high, threads contend for CPU and cache; if it is too low, the machine is underutilized. A better policy uses queue depth as the control signal: if the queue is non-empty and workers are idle, add a worker; if the queue is empty and workers are spinning, remove one. The hysteresis matters, because adding and removing threads has a cost—thread creation, stack allocation, NUMA binding—and oscillating between states wastes more than it saves. Engines that support elasticity usually create a pool of threads once and park them, rather than creating and destroying threads per query.

Memory pressure changes the calculus. A morsel-driven pipeline assumes that intermediate results fit in cache, but the build side of a hash join or the runs of a sort may not fit in memory at all. When memory is tight, the engine must spill. Spilling is a pipeline breaker, and it interacts badly with dynamic scheduling: if one worker spills while others are still building, the spilled partition may be read back before the build is complete, or the spill may be duplicated across workers. The usual solution is to make spilling a per-partition decision, coordinated by the dispatcher. When a partition's memory budget is exceeded, the dispatcher stops issuing build morsels for that partition, waits for in-flight morsels to finish, and then spills the partition as a unit. This is a barrier, but it is a local one, and it does not stall unrelated partitions.

Out-of-core execution also affects morsel size. When data is on disk, the cost of a morsel is dominated by I/O, not by cache misses. Larger morsels amortize the I/O setup and make sequential reads more efficient. Some engines therefore use a larger morsel size for spilling partitions and a smaller one for in-memory partitions. The dispatcher can carry a flag in the morsel descriptor indicating whether the morsel is memory-resident or disk-backed, and workers can adjust their prefetching accordingly. This is a form of adaptive morselization that responds to the storage hierarchy rather than to skew.

Resource governance is the multi-tenant version of the same problem. If two queries share a machine, their workers compete for cores, memory bandwidth, and last-level cache. Morsel-driven scheduling does not by itself provide isolation; it provides a unit of work that can be throttled. A governor can limit the number of morsels a query is allowed to have in flight, or it can assign a weight to each query and let the dispatcher choose among their queues. The latter is essentially a weighted fair queueing problem, and it is easier to solve when the unit of work is small and independent. Plan-driven engines, by contrast, must either partition cores statically or rely on the OS scheduler, which has no knowledge of query priorities.

Cache pollution is the hidden cost of multi-tenancy. A query that scans a large table evicts the working set of a concurrent query, even if the two queries are not competing for CPU. Morsel-driven engines can mitigate this by limiting the number of active morsels per query, so that each query's working set is bounded. The bound is not a hard guarantee—the hardware cache is shared and not partitionable—but it reduces the chance that one query's scan destroys another's hash table. Some engines go further and use cache allocation technology to partition the last-level cache between queries, though this is platform-specific and not universally available.

The cost of spilling is not only the I/O. It is also the loss of the pipeline's locality advantage. When a hash join spills, the probe side must read the spilled partition from disk, which means the morsels for that partition are no longer cache-resident. The dispatcher can compensate by scheduling the spilled partition's morsels together, so that the read-ahead is sequential, and by prefetching the next morsel while the current one is processed. This is a scheduling decision, not a data structure decision, and it is exactly the kind of decision that a global plan cannot make because it depends on runtime memory pressure.

## Distributed morsels and the network as a pipeline breaker

The morsel model extends naturally to a cluster, but the extension is not free. In a distributed engine, a morsel can be a unit of work on a single node, or it can be a unit of data transfer between nodes. The two roles are related but not identical, and conflating them leads to scheduling problems.

Consider a distributed hash join. The build side is shuffled to the nodes that will probe it, partitioned by the join key. The shuffle is a pipeline breaker: no probe can begin until the build side is complete and the partitions have arrived. In a morsel-driven design, the shuffle is also a producer of morsels. Each arriving partition is split into morsels, and the local dispatcher hands them to workers. The network becomes a backpressure source: if the receiving node's queue is full, the sender must slow down, or the receiver must spill. This is the same pull-based mechanism as in a single node, extended across the network.

The difference is latency. A local morsel queue can be drained in microseconds; a remote morsel may take milliseconds to arrive. The dispatcher must therefore prefetch aggressively and maintain a larger queue depth to hide network latency. It must also handle stragglers: if one node is slow, its partitions arrive late, and the downstream join stalls. Speculative execution—sending the same morsel to two nodes and taking the first result—is one mitigation, but it doubles the network cost. A cheaper mitigation is to schedule morsels from partitions that have already arrived while waiting for the slow partition, so that the join makes progress on the available data. This requires the dispatcher to track per-partition readiness, which is a lightweight dependency graph.

Fault tolerance is another distributed concern. If a node fails, the morsels it was processing must be re-executed. In a morsel-driven engine, re-execution is straightforward if the morsels are deterministic and their inputs are recoverable: the dispatcher re-enqueues the lost morsels on surviving nodes. The challenge is that the inputs may have been consumed or spilled. Engines that support fault tolerance typically materialize shuffle outputs to durable storage or recompute them from upstream morsels. The morsel boundary becomes a checkpoint boundary: a morsel is either fully processed or not at all, and its output can be recomputed from its input. This is a stronger guarantee than plan-driven engines usually provide, because the unit of recovery is small and independent.

The distributed dispatcher also has to decide where to run a morsel. Locality matters even more than on a single node: a morsel that reads from a remote shuffle partition pays network cost, while a morsel that reads from a local disk or memory pays much less. The scheduler can use the same affinity tags as on a single node, extended with a node identifier. The policy is to prefer the node that holds the data, then the node in the same rack, then any node. This is a scheduling problem that is well studied in data-parallel systems, and the morsel abstraction makes it tractable because the unit of work is small enough to move.

The network is also a pipeline breaker in a more subtle sense. A shuffle does not just move data; it changes the data distribution. After a shuffle, the partitions may be balanced even if the input was skewed, because the shuffle can repartition by a different key. But the shuffle itself can be skewed: if the join key is hot, one reducer receives most of the data. Morsel-driven scheduling does not fix the shuffle's skew, but it makes the reducer's work finer-grained, so the hot partition can be processed by multiple workers if the reducer's dispatcher splits it into morsels. The split is possible only if the shuffle output is materialized in a way that allows random access; a streaming shuffle that delivers tuples in order cannot be morselized arbitrarily. This is a design constraint that couples the shuffle implementation to the scheduling model.

Finally, distributed morsel-driven execution changes the meaning of no global plan. There is still a global query plan that describes the data flow between nodes, but the schedule—which morsel runs where and when—is decided locally by each node's dispatcher. Coordination is limited to partition readiness and backpressure signals. This is a form of decentralized scheduling that scales with the number of nodes, because no central scheduler has to track every morsel. The trade-off is that global optimization opportunities—such as co-locating two joins that share a build side—are harder to exploit, because no single component sees the whole picture. Engines that care about such optimizations reintroduce a global coordinator, but they keep the morsel as the unit of execution so that the coordinator's decisions can be revised at runtime.

## Morsels and compiled pipelines: where code generation meets dynamic scheduling

Query compilation and morsel-driven scheduling are often discussed separately, but in engines like HyPer they are two halves of the same design. The compiler fuses a chain of operators — scan, filter, probe, aggregate — into a single tight loop with no virtual calls, no tuple-at-a-time materialization, and registers allocated across operator boundaries. The morsel is what that loop iterates over. The dispatcher hands a worker a morsel, the worker calls into the compiled pipeline, and the pipeline processes the morsel's tuples from start to finish before returning.

This arrangement changes what "pull" and "push" mean. At the scheduling level, the model is pull-based: workers request morsels from a queue. Inside a morsel, the compiled pipeline is typically push-based: the scan produces a tuple and pushes it to the filter, which pushes it to the probe, and so on. There is no `next()` call chain, because the compiler has inlined the entire chain into one function. The morsel is the boundary between the dynamic, pull-based scheduler and the static, push-based dataflow. Confusing the two levels leads to design mistakes: a push-based scheduler cannot easily rebalance work, and a pull-based pipeline inside a morsel reintroduces the call overhead that compilation was meant to eliminate.

The morsel size directly affects the compiled code's behavior. A compiled pipeline has a prologue that sets up loop invariants and an epilogue that tears them down. If the morsel is too small, the prologue and epilogue dominate, and the engine spends its time in function entry and exit rather than in tuple processing. If the morsel is too large, the pipeline's working set spills out of L2, and the compiled code stalls on cache misses that the morsel abstraction was supposed to avoid. The compiler can help by specializing the pipeline for the morsel size — unrolling the inner loop, aligning vector accesses, and eliminating remainder handling — but specialization multiplies the number of compiled variants and increases compilation time.

Compilation time is itself a scheduling concern. Just-in-time compilation of a pipeline can take milliseconds, which is significant if the query only processes a few morsels. Engines handle this with adaptive compilation: interpret the first few morsels, measure the pipeline's cost, and compile only if the query is long enough to amortize the compilation. The morsel boundary is the natural place to make this decision, because the dispatcher knows how many morsels remain and how long each has taken. A pipeline that has processed ten morsels in ten milliseconds is a candidate for compilation; one that has processed two morsels in two microseconds is not.

Compiled pipelines also interact with NUMA in a way that is easy to overlook. The compiled code itself is shared across workers, so instruction cache and branch predictor state are shared. The data, however, is not. A worker on socket 0 running a compiled pipeline that reads socket 1 memory pays the remote-access penalty on every cache miss, and the compiler cannot fix that. The dispatcher can, by honoring morsel affinity tags. Some engines go further and compile separate pipeline variants for each NUMA node, so that the compiler can bake in node-specific prefetch distances and memory access patterns. This is a niche optimization, but it illustrates the general principle: morsel-driven scheduling gives the runtime the information needed to make locality decisions, and the compiler can consume that information if the engine exposes it.

## Instrumenting the dispatcher: observability without a global plan

A plan-driven engine has a natural observability story. Each operator instance is bound to a thread, so a profiler can attribute CPU time to a plan node by looking at the thread's stack. A morsel-driven engine has no such mapping. A worker processes many morsels from many operators, and the operator a morsel belongs to is a runtime property, not a static one. Observability must therefore be built into the dispatcher and the morsel descriptor.

The minimum viable instrumentation is a timestamp pair per morsel: one when the worker claims it, one when it finishes. From those timestamps, the engine can compute queue wait time, execution time, and worker utilization. Aggregated by partition, they reveal skew: if morsels from partition 7 consistently take ten times longer than morsels from partition 3, the engine knows the join key is hot and can trigger dynamic repartitioning. Aggregated by worker, they reveal imbalance: if one worker is consistently busy while others park, the dispatcher's stealing policy is not working.

Per-morsel timestamps are cheap enough to record in production if they are sampled. Recording every morsel can add noticeable overhead when morsels are short, because the timestamp calls themselves become a measurable fraction of the work. A common compromise is to record every Nth morsel, or to record only morsels that exceed a threshold. The threshold is adaptive: if the engine observes that most morsels finish in microseconds, it raises the sampling interval; if morsels are taking milliseconds, it lowers it. This is the same logic that sampling profilers use, applied at the granularity of work units rather than instructions.

Attribution is the harder problem. When a query is slow, the cause could be dispatcher contention, memory bandwidth saturation, lock contention on a shared hash table, or plain skew. The dispatcher's metrics can disambiguate. A queue that is consistently empty while workers are idle means the producer — the scan or the shuffle — is the bottleneck. A queue that is consistently full means the consumers are the bottleneck, and the engine should look at operator costs. A high steal rate means the local queues are imbalanced, which points to a partitioning problem. A high remote-access rate, measured with hardware counters, points to NUMA misplacement. None of these signals is conclusive on its own, but together they narrow the search space.

Debugging non-determinism is the operational cost of dynamic scheduling, and instrumentation is the only practical mitigation. If a query produces a wrong result, the bug may be a race condition that depends on a particular interleaving of morsels. Reproducing it requires reproducing the schedule. Some engines support a deterministic mode in which the dispatcher uses a fixed order and the workers process morsels in a fixed sequence. This mode is slower, but it turns a flaky failure into a reproducible one. The schedule log — which morsel went to which worker in which order — can be recorded and replayed, so that a production failure can be reproduced in a test environment. This is more machinery than a plan-driven engine needs, but it is the price of dynamic scheduling.

## Morsels beyond the CPU: accelerators, heterogeneous execution, and persistent memory

The morsel abstraction is not tied to CPU cores. It is a unit of data and work, and it can be dispatched to any device that can process it. GPUs are the most common accelerator, and the mapping is natural: a morsel is a batch of tuples transferred to device memory, and a GPU kernel processes the batch. The dispatcher becomes a host-side scheduler that manages device memory and kernel launches. The pull model still applies: when a GPU stream is free, it pulls the next morsel from the queue.

The constraints are different. Kernel launch overhead is measured in microseconds, and device-to-host transfer is measured in milliseconds for large batches. Morsels destined for a GPU must therefore be larger than CPU morsels, so that the launch and transfer costs are amortized. But GPU memory is limited, so the dispatcher must also track how many morsels are in flight on the device and apply backpressure when device memory is exhausted. The result is a two-level scheduler: a host-level dispatcher that hands morsels to devices, and a device-level scheduler that maps the morsel's tuples onto GPU threads. The morsel is the contract between the two levels.

Heterogeneous execution — CPU and GPU workers pulling from the same queue — introduces a cost-model problem. A morsel that is cheap on the CPU may be expensive on the GPU, and vice versa. A scan with a simple filter is often faster on the GPU because of its high memory bandwidth; a hash join probe with random access is often faster on the CPU because of its larger cache. The dispatcher must decide where to send each morsel, and the decision depends on the operator mix, the data size, and the current load on each device. This is a scheduling problem with heterogeneous workers, and it is harder than the homogeneous case because the relative speed of the workers changes with the workload. Engines that support heterogeneous execution typically use a simple heuristic — send large, bandwidth-bound morsels to the GPU and small, latency-bound morsels to the CPU — and refine it with runtime measurements.

Persistent memory changes the storage hierarchy in a way that affects morsel size. PMEM sits between DRAM and disk in latency and bandwidth, and it is byte-addressable, so a morsel can be memory-mapped directly from PMEM without a block-level read. The access latency is higher than DRAM, so the locality argument for small morsels is weaker; larger morsels amortize the PMEM latency better. The dispatcher can carry a flag indicating whether a morsel's data is in DRAM, PMEM, or on disk, and workers can adjust their prefetching accordingly. This is the same adaptive morselization idea that applies to skew, extended to the memory hierarchy.

SmartNICs and DPUs are a newer target. A morsel can be offloaded to a network card for filtering or partial aggregation, with the result returned to the host. The benefit is near-data processing: the morsel is processed where the data arrives, before it consumes host memory bandwidth. The cost is that the accelerator's programming model is more restrictive, and not every operator can be offloaded. The dispatcher must therefore know which operators are offloadable and which are not, and it must handle the case where an offloaded morsel fails and must be re-executed on the host. The morsel boundary makes this recovery tractable: the morsel's input is still available, so re-execution is a matter of re-enqueueing it.

## Anti-patterns and failure modes: when morsel-driven execution goes wrong

Morsel-driven execution is robust, but it is not foolproof. The failure modes are predictable, and most of them trace back to a mismatch between the morsel size, the dispatcher's contention behavior, and the hardware topology.

The most common anti-pattern is the morsel that is too small. When morsels contain only a few hundred tuples, the dispatcher's atomic operations, the pipeline prologue, and the per-morsel bookkeeping dominate the actual work. The symptoms are unmistakable: CPU utilization is high but throughput is low, the time spent in the scheduler is a significant fraction of total query time, and scaling stops at a handful of cores. The fix is to increase the morsel size or to batch multiple morsels into a single claim, so that the dispatcher is touched once per batch rather than once per morsel. Some engines implement a two-level scheme: a worker claims a batch of morsels, processes them in sequence, and returns to the dispatcher only when the batch is exhausted.

The opposite anti-pattern — the morsel that is too large — is subtler. A large morsel amortizes overhead, but it also defeats the load-balancing argument. If one morsel takes ten milliseconds and the query has a hundred morsels, the tail of the query is dominated by the slowest morsel. Large morsels also spill out of L2, so the pipeline's intermediate results are evicted before they are consumed. The symptoms are a long tail in morsel execution times and a high last-level cache miss rate. Adaptive morsel sizing, guided by the observed cache miss rate and the variance in morsel execution times, is the usual remedy.

Dispatcher contention is the third anti-pattern. A single atomic counter over a global morsel array is a serialization point at high core counts. Every claim writes the same cache line, so the line ping-pongs between sockets, and the atomic operation's latency becomes the throughput ceiling. The fix is sharding: one queue per NUMA node, with work stealing between queues. The shard count should be a small multiple of the node count, not the core count, because too many shards make stealing expensive and reduce the chance that a worker finds local work.

False sharing is a related failure. If two workers update counters or bucket heads that share a cache line, the line bounces between cores even though the workers are not logically contending. The fix is padding: shared structures are aligned to cache-line boundaries, and per-worker state is kept on separate lines. This is a well-known technique, but it is easy to forget when the shared structure is a morsel descriptor or a partition's remaining-work counter. The performance impact can be a factor of two or more on memory-bound workloads.

NUMA misplacement is the failure mode that morsel-driven scheduling is supposed to prevent, but it can happen anyway if the affinity tags are wrong or the allocator is not node-aware. If a morsel is scheduled on a worker whose node does not hold its data, every cache miss becomes a remote access. The symptom is high remote DRAM traffic and a scaling curve that flattens as cores are added. The fix is to make first-touch allocation explicit, to bind workers to nodes, and to prefer local morsels over remote ones. Stealing should be a last resort, and stolen morsels should be taken in batches to amortize the remote-access penalty.

Starvation is a scheduling-policy failure. LIFO queues improve locality, but they can starve old morsels if new work keeps arriving. In a query with a deadline, a starved partition may never finish, and the query hangs. The fix is to use FIFO for stealing and LIFO for local work, or to age morsels so that old ones are eventually promoted. The aging policy must be cheap, because it runs on every claim.

The convoy effect is a barrier-related failure. If all workers finish their morsels at approximately the same time and then hit a pipeline breaker, the breaker's queue is empty for a moment and then floods. The utilization graph shows bursts rather than a steady line. The fix is to stagger morsels so that workers arrive at the barrier at different times, or to pipeline the barrier per partition so that some workers can proceed while others wait. The latter is more effective but requires per-partition dependency tracking.

Finally, morselizing a trivial query is pure overhead. A query that scans a thousand rows and returns a single aggregate does not benefit from parallel scheduling; the dispatcher's setup cost exceeds the work. Engines should detect small queries and execute them single-threaded, bypassing the dispatcher entirely. The threshold is workload-dependent, but it is usually on the order of a few thousand tuples or a few milliseconds of estimated work. Without this fallback, morsel-driven execution adds latency to exactly the queries that should be fastest.
