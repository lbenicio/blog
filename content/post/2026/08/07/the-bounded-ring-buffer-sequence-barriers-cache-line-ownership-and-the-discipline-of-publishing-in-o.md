# The Bounded Ring Buffer: Sequence Barriers, Cache-Line Ownership, and the Discipline of Publishing in Order

A queue is the first data structure most of us learn to reason about with threads, and it is also the one where intuition fails most reliably. The version with a mutex around an array is correct, and for a few million operations per second across two threads it is fast enough that nobody looks at it again. Then the service moves to a two-socket machine, the message rate triples, and the same code collapses — not gradually, but by roughly an order of magnitude. Nothing about the algorithm changed. What changed is that every enqueue and every dequeue now has to negotiate with another core over ownership of a 64-byte cache line, and that negotiation is governed by latencies a hundred times larger than the arithmetic the queue actually performs.

This article is about the bounded ring buffer: the array-backed, index-masked, sequence-numbered queue that sits underneath the LMAX Disruptor, Linux's `io_uring` submission and completion rings, DPDK's descriptor rings, and a large fraction of the market-data and telemetry pipelines built in the last fifteen years. We will build it from the coherence problem upward rather than from the API downward, because the API is trivial and the coherence behavior is not. Along the way we will be precise about what each memory barrier actually orders, why the sequence number and the slot index are different quantities that must not be conflated, where the design stops being lock-free in the formal sense, and which optimizations buy throughput by spending tail latency.

## The Queue Is a Coherence Problem in Disguise

Start with the single-threaded picture. A ring buffer is an array of `capacity` slots, a `head` index where the consumer reads, and a `tail` index where the producer writes. Enqueue writes `slots[tail & (capacity - 1)]`, increments `tail`. Dequeue reads `slots[head & (capacity - 1)]`, increments `head`. Five instructions, no allocation, perfect locality. On one core this is close to optimal and there is nothing more to say.

The trouble is that `head` and `tail` are, in the language of the memory system, *shared mutable state*. The memory system does not share variables; it shares cache lines. A cache line on x86-64 and on most ARM cores is 64 bytes, and the unit of coherence is the line, not the word. If `head` and `tail` are declared next to each other in a struct — the obvious way to write it — they occupy the same line, and every store to `tail` by the producer invalidates the consumer's copy of that line, and every store to `head` by the consumer invalidates the producer's. Neither thread is touching the other's variable, yet each store forces the other core to refetch the entire line from the last writer's cache or from a shared level of the hierarchy.

This is false sharing, and its cost is not a constant factor. When both cores hammer the same line, the line ping-pongs between their private caches, and each transfer costs on the order of tens of nanoseconds on a single socket and considerably more when the transfer crosses a socket boundary through an interconnect. The steady state is not

a point of equilibrium but a continuous exchange of ownership. The line is either owned by the producer's core, owned by the consumer's core, or owned by neither in a shared state. Every store to `tail` by the producer requires an exclusive copy, which means invalidating the consumer's copy. Every store to `head` by the consumer does the same in reverse. The hardware does not know that the two threads are touching different variables; it only knows that they are touching the same line.

## Padding Is Necessary but Not Sufficient

The first fix is to separate `head` and `tail` into different cache lines. In C++11 and later, `alignas(64)` on a struct member or on a wrapper type achieves this. In Java, the Disruptor uses inheritance from a padded base class or the `@Contended` annotation. The goal is to ensure that no two frequently-written variables share a line. But padding alone is not enough if the sequence numbers are read by multiple threads. A read-only shared line is fine; it can be replicated in each core's cache in a shared state. The problem is when a line is written by one core and read by another, or written by both. The producer's sequence is written by the producer and read by consumers. That line will be shared, but it will be in a shared state most of the time, and only invalidated when the producer writes. That is acceptable if the write is infrequent relative to the reads. However, if consumers are constantly polling the sequence, they will constantly refetch the line after each write. This is a form of false sharing if the consumers are also writing their own sequences on the same line. So we pad each sequence to its own cache line.

The cost of a cache miss to a line owned by another core is roughly 40–80 ns on a modern x86. If the line is in a shared state, a read is cheap. A write requires exclusive ownership, which involves a request-for-ownership (RFO) and invalidation of other copies. This is the fundamental cost we are trying to minimize. The ring buffer's performance is dominated by how often we force a cache line to change ownership. Every atomic operation on a shared sequence is a potential ownership change. Every store to a data slot that shares a line with another thread's data is a potential false sharing event. The design of the ring buffer is therefore a study in minimizing ownership transfers.

## Sequence Numbers Are Not Indices

This is where the sequence number enters. A sequence number is not an index. An index is `sequence & (capacity - 1)`. The index wraps; the sequence does not. The sequence is a monotonically increasing 64-bit integer. It serves three purposes: it identifies a slot, it provides a total order over events, and it acts as a synchronization point. The consumer's sequence is the highest sequence it has consumed. The producer's sequence is the highest sequence it has published. The difference between them is the number of outstanding events. The ring is full when `producerSequence - consumerSequence >= capacity`. It is empty when they are equal.

The separation of sequence and index is not a cosmetic detail. It allows the ring to be bounded without ever resetting the sequence. A 64-bit sequence at a billion events per second takes over 500 years to wrap. Even at 10 billion events per second, it takes 58 years. The wrap-around problem is effectively solved by using a 64-bit counter. The index, on the other hand, wraps every `capacity` events. The mask operation `sequence & (capacity - 1)` requires that `capacity` be a power of two. This is a common constraint because it replaces a modulo with a bitwise AND. If `capacity` is not a power of two, you need a modulo, which is slower but still correct. The power-of-two constraint is a performance optimization, not a correctness requirement.

The sequence number also enables the barrier. A barrier is a condition on a sequence: wait until sequence `S` is greater than or equal to some value. This is a simple comparison. Because the sequence is monotonic, the barrier can be checked with a single load. If the sequence is not yet high enough, the thread spins. This is the essence of the sequence barrier. It is a lock-free wait in the sense that no lock is held, but it is a busy-wait. The wait can be bounded by a timeout or by parking the thread, but the fundamental mechanism is a spin on a sequence value.

## Memory Ordering: What the Barriers Actually Order

The critical insight is that publishing a sequence is a release operation. The producer must ensure that all writes to the data slot are visible before the sequence update is visible. This is a store-store ordering. On x86, stores are not reordered with other stores, so a simple compiler barrier (like `std::atomic_thread_fence(std::memory_order_release)`) is sufficient. On ARM, a `dmb ishst` or a store-release instruction is needed. The consumer, after reading the sequence, must ensure that subsequent reads of the data slot are not reordered before the sequence read. This is a load-load ordering. On x86, loads are not reordered with other loads, so a compiler barrier is enough. On ARM, a `dmb ishld` or a load-acquire is needed.

In C++11 and later, the portable way to express this is to use `std::atomic<long>` with `memory_order_release` for the store and `memory_order_acquire` for the load. This generates the correct instructions on all architectures. The compiler is not allowed to reorder memory operations across an atomic operation with acquire or release semantics. It is also not allowed to reorder non-atomic operations across it. This is the foundation of the publication protocol.

The sequence barrier itself is often implemented as a loop that loads the sequence with acquire semantics. The load-acquire ensures that any data written before the release store is visible after the acquire load. This is the happens-before relationship. Without it, the consumer might see the updated sequence but read stale data from the slot. This is a real bug that occurs on weakly ordered architectures and can be exposed by stress testing.

There is also the question of the compiler reordering the data writes after the sequence write. Even on x86, the compiler can reorder stores if it does not know about the synchronization. The `std::atomic` with release semantics prevents this. If you use a plain `volatile` variable, the compiler will not reorder volatile accesses with each other, but it can reorder non-volatile accesses across a volatile access. So `volatile` is not sufficient for publication. You need either an atomic with release semantics or an explicit compiler barrier (`std::atomic_signal_fence` or `asm volatile("" ::: "memory")`).

## The Sequence Barrier and the Discipline of Publishing in Order

A sequence barrier is a set of sequences that a consumer must wait for before it can proceed. In the Disruptor, a `SequenceBarrier` is created with a list of gating sequences. The consumer calls `waitFor(sequence)` which spins until all gating sequences are greater than or equal to the requested sequence. This is how a consumer waits for a producer. The producer, in turn, must not overwrite a slot until the consumer has advanced past it. This is enforced by the producer checking the consumer's sequence before claiming a slot. This creates a dependency cycle: producer waits for consumer, consumer waits for producer. In a bounded queue, this is unavoidable. The system is not lock-free in the formal sense because a thread can be blocked by another. However, the blocking is not via a lock; it is via a spin-wait. The spin-wait can be bounded by using `Thread.onSpinWait()` or `pause` instructions, but it is still a busy-wait. If the consumer is descheduled, the producer will spin until the ring is full, then it must either block or drop events. The Disruptor typically blocks by parking the thread after a certain number of spins. This is a policy decision, not a property of the data structure.

The discipline of publishing in order is what allows the consumer to see a consistent view of the ring. Without it, a consumer might see a sequence number that is ahead of the data, or a data slot that is overwritten before it is read. The sequence barrier enforces this order. The producer must not publish a sequence until all previous sequences are either published or known to be irrelevant. In the multi-producer case, the `availableBuffer` ensures that a consumer only reads a slot when its sequence has been published. The consumer's own sequence is updated only after it has processed the slot, which in turn gates the producer. This mutual gating is the essence of the bounded ring buffer. It is a contract: the producer promises not to overwrite until the consumer says it is done; the consumer promises not to read until the producer says it is ready. The sequence numbers are the tokens of that contract.

In a single-producer, single-consumer ring, the contract is simple. The producer writes the data, then stores the new tail sequence with release semantics. The consumer loads the tail sequence with acquire semantics, reads the data, then stores the new head sequence with release semantics. The producer loads the head sequence with acquire semantics before claiming new slots. This is a classic SPSC queue. It is not lock-free because the producer can be blocked by a full ring, and the consumer can be blocked by an empty ring. But it is wait-free for each thread if the other thread is not running? No, it is not wait-free because a thread can be blocked indefinitely if the other thread is not scheduled. It is a blocking queue with bounded capacity.

In a multi-producer ring, the tail must be claimed atomically. The Disruptor uses a `MultiProducerSequencer` that does a CAS loop to claim a sequence. Once claimed, the producer writes the data, then sets an `availableBuffer` entry for that sequence. The `availableBuffer` is an array of integers, one per slot, padded to cache lines. The producer writes the sequence number to the `availableBuffer[sequence & mask]` with release semantics. The consumer, when reading a slot, checks the `availableBuffer` entry with acquire semantics. If it matches the expected sequence, the data is ready. This design allows producers to publish out of order, but the consumer still processes in order. The `availableBuffer` acts as a per-slot publication barrier. It also avoids the need for a single tail sequence to be updated in order. However, the consumer must still wait for the next sequence to be available, which means it might spin on a slot that is not yet published. The `MultiProducerSequencer` advances a cursor only when the next contiguous sequence is available. This cursor is what the consumer's sequence barrier waits on. So the consumer sees a contiguous range of published sequences, but the cursor can be held back by a slow producer. This is head-of-line blocking. The producers themselves are not blocked from claiming and writing, but the consumer cannot see their data until the slow producer publishes. This is a form of blocking that is inherent in the multi-producer design.

## Batching and the Amortization of Coherence

Batching is the primary mechanism for amortizing coherence costs. Instead of claiming one slot at a time, a producer can claim a batch of N slots by doing a single CAS on the tail sequence (in the multi-producer case) or a simple addition (in the single-producer case). It then writes the data for all N slots, and finally publishes the last sequence. The consumer can similarly read a batch of N slots, process them, and then update its sequence once. This reduces the number of atomic operations and the number of cache line invalidations. The throughput improvement can be substantial: a batch of 32 can reduce the coherence traffic by a factor of 32. However, batching increases latency because the consumer must wait for the entire batch to be published before it can process the first event. This is the classic throughput-latency trade-off. In low-latency systems, batching is often disabled or limited to very small sizes. In high-throughput systems, large batches are used.

The batch size also affects the cache line ownership pattern. If a producer writes a batch of 32 slots, it will touch 32 cache lines. If those lines are not already owned by the producer's core, it will incur 32 RFOs. But it can do them in a burst, which may be more efficient than doing them one at a time with other work in between. The hardware can pipeline the RFOs. The consumer, reading a batch, will similarly fetch 32 lines. If the producer and consumer are on different cores, the lines will be transferred from the producer's cache to the consumer's cache. This is a bulk transfer, which is more efficient than a series of single-line transfers. The memory system is optimized for streaming, so batching aligns with the hardware's strengths.

In `io_uring`, the submission queue and completion queue are ring buffers that support batching. The application can submit multiple I/O operations by writing multiple entries and then updating the tail once. The kernel can process multiple completions and update the completion tail once. This amortizes the cost of the memory barrier and the cache line transfer. The `io_uring` interface also supports `IORING_SETUP_SQPOLL`, which allows the kernel to poll the submission queue, avoiding the need for a system call per batch. This is a further amortization of the cost of entering the kernel.

## Where It Stops Being Lock-Free

The bounded ring buffer is not lock-free in the formal sense. A lock-free algorithm guarantees that at least one thread makes progress in a finite number of steps, regardless of the actions of other threads. In a bounded ring buffer, if the consumer is stalled, the producer will eventually fill the ring and then cannot make progress. It must wait for the consumer. This is a blocking dependency. Even in the single-producer, single-consumer case, the producer can be blocked by a full ring. The consumer can be blocked by an empty ring. The system as a whole can make progress only if both threads are scheduled. This is not lock-free; it is a wait-free bounded queue only if you assume no thread can be indefinitely delayed. In practice, the spin-wait is often bounded by a timeout or a park, which makes it a blocking algorithm. The term "lock-free" is sometimes used loosely to mean "no locks", but that is not the formal definition. The Disruptor is often described as lock-free, but it is not. It is a bounded queue with backpressure. The backpressure is the price of bounded memory and cache-friendly access.

The lack of lock-freedom is not a defect. It is a design choice. A lock-free queue that allows unbounded growth would require dynamic memory allocation, which introduces its own coherence and latency problems. A bounded ring buffer trades the progress guarantee for predictable memory usage and cache locality. The backpressure is explicit: when the ring is full, the producer must wait or drop. This is often exactly what you want in a system that cannot afford unbounded queues. The discipline of publishing in order is what makes this trade-off work. By using sequence numbers and barriers, the ring buffer can achieve very high throughput with low latency, as long as the producer and consumer are both making progress. When one is not, the other will eventually block. That is the fundamental contract of the bounded ring buffer.

## Cache-Line Ownership Is a State Machine, Not a Counter

A cache line is not a scalar that moves between cores. It is a small state machine replicated across the coherence directory, and every load or store asks that machine to transition. In MESI terms the states are Modified, Exclusive, Shared, and Invalid. A read miss installs the line in Exclusive. A second reader moves both copies to Shared. A store to a Shared line requires an upgrade: the writer must invalidate every other copy before the store commits. That upgrade is the request-for-ownership, and it is the most expensive event in the queue's steady state.

Place the producer sequence and the consumer sequence in that model. The producer writes its sequence after publishing a batch. The consumer reads that sequence in its wait loop. If the consumer only reads, its copy can sit in Shared indefinitely. The producer's next write must invalidate that copy. The consumer's next read misses and refetches. That is one coherence transaction per producer publication, not per consumer poll. The poll loop itself, if it is a pure load, does not invalidate anything. This is why a spin-wait on a sequence is not automatically catastrophic: the cost is set by how often the writer writes, not by how often the reader reads.

The consumer's own sequence line has the mirror-image behavior. The consumer writes it after processing a batch. The producer reads it before claiming new slots. The producer's reads can keep the line Shared. The consumer's store invalidates the producer's copy. The producer's next read misses. Again, the cost is proportional to how often the consumer advances, not to how often the producer checks. This is the first reason batching is so effective: it reduces the frequency of the stores that force invalidations. A producer that publishes one event at a time forces one invalidation per event. A producer that publishes thirty-two events at a time forces one invalidation per thirty-two events.

The subtle failure is not the sequence line itself but the line it shares. If the producer sequence and the consumer sequence live in the same 64-byte line, then the producer's store to its sequence invalidates the consumer's copy of the consumer sequence, and the consumer's store to its sequence invalidates the producer's copy of the producer sequence. The two threads are not logically sharing a variable, but they are physically sharing a line, and the coherence protocol cannot tell the difference. Padding each sequence to its own line removes this particular false sharing. It does not remove the true sharing of the sequence line between its writer and its readers. True sharing is inherent in the protocol: the producer must write the sequence for the consumer to see it, and the consumer must write its sequence for the producer to see it. The goal is not to eliminate true sharing but to make each true sharing event carry as much useful work as possible.

The multi-consumer case makes the state machine more interesting. Each consumer has its own sequence, written by that consumer and read by the producer. If each sequence is on its own line, the producer's read set is a set of lines, one per consumer. When a consumer advances, it invalidates the producer's copy of that consumer's line. The producer's next scan of all consumer sequences must refetch that line. With many consumers, the producer can spend a significant fraction of its time refetching sequence lines rather than doing useful work. One mitigation is to have a single gating sequence that represents the slowest consumer, updated by a coordinator or by the consumers themselves through a min-reduction. That collapses many lines into one, at the cost of an extra handoff. Another is to group consumers into a hierarchy, where each group has a gating sequence and the producer reads only the group gates.

## The Polling Loop and the Latency Tail

The sequence barrier is a loop, and the shape of that loop determines the latency distribution as much as the throughput. A naive loop is a tight load and compare. On x86, that loop can issue a load every few cycles and keep the core's load unit busy. If the line is Shared, the load hits in L1 after the first fetch. If the producer writes, the line is invalidated and the next load misses. The loop then stalls for the duration of the miss, which is tens of nanoseconds. The loop does not waste memory bandwidth while it is stalled, but it does occupy a core. On a machine with more threads than cores, that occupancy is a real cost: the spinning thread prevents another thread from running.

The `pause` instruction on x86 and the `yield` or `wfe` instruction on ARM exist to reduce that cost. `pause` de-pipelines the loop, reduces power, and gives the sibling hyperthread a chance to make progress. It also delays the next load, which can reduce the rate of useless misses when the producer is not publishing. But it does not change the fundamental latency of seeing a new sequence: the consumer still must wait for the producer's store to become visible and for the line to arrive. A loop with `pause` will see the update a few cycles later than a tight loop, but it will consume fewer resources while waiting. In a latency-critical system, the tight loop may be preferred; in a throughput-oriented system with many consumers, `pause` is usually the right default.

When the wait is expected to be long, spinning is the wrong tool. Parking the thread on a futex, an eventfd, or a condition variable removes it from the run queue and frees the core, but it adds a kernel transition to the wake-up path. That transition costs on the order of a microsecond, which is enormous compared to a cache miss. The standard compromise is a hybrid: spin for a bounded number of iterations, then park. The bound is a policy knob. If it is too small, the queue parks and unparks under light load and pays the kernel cost. If it is too large, a descheduled consumer can burn a core indefinitely. The Disruptor exposes this as a wait strategy, and the same pattern appears in `io_uring` polling modes and DPDK's busy-poll loops.

The latency tail is where the bounded ring buffer shows its teeth. In a single-producer, single-consumer ring, a slow consumer does not slow the producer until the ring fills. Once it fills, the producer must wait. The producer's wait is not a lock, but it is a dependency: the producer cannot make progress until the consumer advances. If the consumer is descheduled, the producer spins or parks. The consumer's latency becomes the producer's latency. In a multi-producer ring, the coupling is worse. A single slow producer can claim a sequence, write its data slowly, and hold back the consumer's cursor. Other producers can claim later sequences and publish their data, but the consumer cannot advance past the hole. The ring fills, and all producers eventually block. This is head-of-line blocking, and it is a direct consequence of the in-order consumption contract. The available buffer makes publication out of order, but it does not make consumption out of order. If the application needs to tolerate stragglers, it must either use per-producer rings or add a timeout that abandons the stalled sequence.

## Sequence Arithmetic and the Capacity Contract

The arithmetic of the ring is small enough to fit on a napkin, but every term has a precise meaning. Let the producer cursor be the sequence of the last published event, starting at minus one for an empty ring. The next sequence to claim is `cursor + 1`. A producer claiming a batch of `n` events reserves sequences `cursor + 1` through `cursor + n` and then advances the cursor to `cursor + n` after publication. The consumer cursor is the sequence of the last consumed event, also starting at minus one. The next sequence to consume is `consumer + 1`. The ring is full when `cursor - consumer >= capacity`. It is empty when `cursor == consumer`. The slot for sequence `s` is `s & (capacity - 1)`, which requires `capacity` to be a power of two. If it is not, the slot is `s % capacity`, which is correct but slower.

The subtraction in the full check is where the sequence-as-counter design earns its keep. Because the sequences are monotonically increasing and never reset, the difference is always the number of outstanding events, even after the index wraps. A 64-bit sequence at a billion events per second wraps after roughly 584 years, so the wrap is not a practical concern. The index wraps every `capacity` events, and the mask handles that. The two quantities must not be conflated. A common bug is to store the index in the sequence field and then compare indices to determine fullness. That fails as soon as the ring wraps once: the index difference is no longer the number of outstanding events, and the full check becomes wrong. The sequence must be the source of truth; the index is derived.

The capacity contract is also a memory contract. The ring can hold at most `capacity` events, and the producer must not overwrite a slot that the slowest consumer has not yet consumed. The producer determines that by reading the gating sequence, which is the minimum of all consumer sequences. If there are no consumers, the gating sequence can be `cursor - capacity`, which means the producer is free to overwrite anything older than the capacity window. In a single-consumer ring, the gating sequence is just the consumer's cursor. The producer reads it before claiming a batch. If `cursor + n - gating >= capacity`, the producer cannot claim the batch without overwriting unread data. It must wait, drop, or fail. The choice is policy, but the arithmetic is not negotiable.

The sequence barrier uses the same arithmetic from the other side. A consumer waiting for sequence `s` loads the producer cursor and checks `cursor >= s`. If the producer publishes in batches, the cursor may jump past `s`, and the consumer can process a range of sequences in one pass. The barrier returns the highest available sequence, not necessarily the one requested. That is an optimization: the consumer can drain a batch without rechecking the barrier for each event. The barrier must still respect the gating sequences in a multi-consumer setup, because a consumer may be gated by another consumer's progress. The Disruptor's `SequenceBarrier` takes an array of gating sequences and waits until all of them are at least `s`. This is how a dependency graph is encoded: a downstream consumer waits for an upstream consumer, not just for the producer.

## The Available Buffer and Out-of-Order Publication

The multi-producer sequencer cannot simply advance a single cursor in order, because two producers may claim sequences concurrently and finish writing in a different order. The Disruptor solves this with an available buffer: an array of integers, one per slot, that records the sequence number that has been published in that slot. A producer claims a sequence with a CAS loop on the cursor, writes the data, and then stores the sequence number into `availableBuffer[sequence & mask]` with release semantics. The consumer, when it reaches a sequence, reads `availableBuffer[sequence & mask]` with acquire semantics. If the value equals the sequence, the data is ready. If not, the producer that claimed that sequence has not finished publishing, and the consumer must wait.

This design allows producers to publish out of order, but it does not allow the consumer to consume out of order. The consumer still advances its cursor contiguously. If sequence 100 is claimed by a slow producer and sequence 101 is published by a fast producer, the consumer cannot process 101 until 100 is available. The available buffer tells the consumer that 101 is ready, but the in-order contract forbids skipping 100. The ring can therefore fill with published-but-unconsumable events behind a single straggler. The available buffer is not a reordering buffer; it is a publication ledger. It makes the per-slot readiness explicit so that the consumer does not need to infer it from a single cursor.

The available buffer has its own cache-line behavior. Each entry is a small integer, and adjacent entries share cache lines. If two producers write adjacent slots, they may false-share on the available buffer line. The data slots themselves may also false-share if the event size is smaller than a cache line. Padding every available-buffer entry to a full cache line would eliminate the false sharing but would multiply the memory footprint by sixteen for 4-byte entries. Most implementations accept the false sharing because the writes are infrequent relative to the data writes, and because batching tends to make each producer claim a contiguous range of slots. A producer that claims a range of 32 slots will write 32 consecutive available-buffer entries, which touch two cache lines. The consumer reads them in order, so the lines are transferred in a predictable stream. The pathological case is many producers each claiming a single slot in an interleaved pattern; then the available-buffer lines ping-pong between cores. If that pattern is expected, a per-producer available buffer or a different publication scheme may be better.

The memory ordering on the available buffer is as important as on the main cursor. The producer's store to `availableBuffer[index]` must be a release operation, and the consumer's load must be an acquire operation. Without the release, the data writes could become visible after the availability flag, and the consumer could read a slot that is marked ready but still contains stale bytes. Without the acquire, the consumer's data reads could be reordered before the availability check, and it could read stale bytes even though the flag was observed. On x86, the store-release is a plain store plus a compiler barrier, and the load-acquire is a plain load plus a compiler barrier, because the hardware already provides the necessary ordering for these cases. On ARM, the release and acquire are actual instructions. The portable C++ atomics generate the right code on both.

## NUMA, Huge Pages, and the Physical Layout of the Ring

On a single-socket machine, the coherence traffic is local to one last-level cache and one memory controller. On a two-socket machine, the same traffic may cross an interconnect that is an order of magnitude slower than the local path. The ring buffer's sequences are shared between cores, so they will cross the interconnect if the producer and consumer are on different sockets. The data slots will also cross if the producer writes on one socket and the consumer reads on the other. The first rule of NUMA-aware ring buffer design is therefore to keep the producer and consumer on the same socket when possible. If that is not possible, the next best option is to allocate the ring on the socket where the consumer runs, because the consumer's reads are on the critical path for the producer's backpressure. The producer's writes will cross once, and the consumer's reads will be local. The opposite allocation makes every consumer read a remote access.

The allocation itself matters. A ring buffer is a large contiguous array, and on a NUMA system a first-touch policy will place the pages on the socket that first writes them. If the producer initializes the ring, the pages land on the producer's socket. If the consumer then reads them, every access is remote. Explicit NUMA allocation, such as `numa_alloc_onnode` on Linux, or `mbind` with `MPOL_BIND`, can place the pages where they are needed. DPDK goes further and uses huge pages, which reduce TLB pressure and make the physical layout more predictable. A ring buffer that fits in a few huge pages will have far fewer TLB misses than one spread across thousands of 4 KiB pages. The `io_uring` rings are mapped into user space by the kernel, and their placement is controlled by the kernel, but the same principle applies: the submission and completion queues should be on the same NUMA node as the threads that poll them.

The physical layout of the slots is a trade-off between false sharing and cache utilization. If each slot is padded to a 64-byte cache line, then a producer writing one slot does not invalidate the consumer's copy of an adjacent slot. But if the events are small, padding wastes most of the cache and reduces the effective capacity of the ring. If slots are packed tightly, multiple events share a line, and the producer's write to slot `i` can invalidate the consumer's copy of slot `i-1` if they are on the same line. In a ring, the producer and consumer are usually far apart in sequence when the ring is large, so they are unlikely to touch the same line at the same time. The dangerous case is a small ring or a batched access pattern where the producer is writing near the consumer's read position. The right choice depends on the event size and the capacity. For 64-byte events, the line is the slot. For 8-byte events, packing eight per line gives better cache utilization but requires care to avoid false sharing at the boundaries.

## The Claim Protocol: Reserving Work Before Writing It

The sequence barrier tells a consumer when it may read. The mirror problem is telling a producer when it may write. That is the claim protocol, and it is the part of the ring that most often gets blurred together with publication. Claiming a sequence and publishing a sequence are distinct operations, separated by the data write. In a single-producer ring, the claim is a plain load of the consumer's gating sequence, a comparison against capacity, and an increment of the producer cursor. There is no atomic read-modify-write because there is only one writer to the cursor. The producer can compute the next sequence, check that it does not overwrite unread data, and then write the data. The cursor increment is a local operation until the publication store. In a multi-producer ring, the cursor has multiple writers, so the claim must be atomic. The usual pattern is a compare-and-swap loop: load the current cursor, compute the candidate next cursor, check the gating sequence, and CAS. If the CAS fails, another producer claimed in the interval; retry. This loop is the multi-producer tax. It is not the data write that is expensive; it is the serialization of the claim. Every successful CAS invalidates the cursor line in every other producer's cache. The next producer to attempt a claim must refetch the line, observe the new cursor, and try again. Under contention, the cursor line becomes a hot spot that ping-pongs between cores. The throughput of the claim protocol is therefore bounded by the coherence latency of a single cache line, divided by the number of producers. Batching is the standard mitigation: a producer claims a range of N sequences in one CAS, writes N events, and publishes once. The CAS frequency drops by a factor of N, and the cursor line changes ownership less often. The cost is that a producer may claim more slots than it immediately needs, which can increase the ring's occupancy and delay other producers. The batch size is a policy knob that trades claim contention against memory pressure.

The claim protocol also has a safety obligation: a producer must not write to a slot until it has successfully claimed the sequence for that slot. If it writes first and claims later, another producer may claim the same sequence and overwrite the data. The claim is a reservation. The data write is a private operation on a reserved slot. The publication is the release store that makes the reservation visible to consumers. This three-step structure—reserve, write, publish—is the same in the Disruptor, DPDK, and io_uring. The names differ, but the ordering constraints do not. The consumer's side is symmetric: it must not read a slot until it has observed the publication, and it must not advance its own sequence until it has finished reading. The advance is a release store that tells the producer the slot is free. The producer's claim loop reads that sequence with acquire semantics. The ring is therefore a pair of release-acquire handshakes, one in each direction, with the data transfer in the middle.

## Memory Barriers in Practice: A Concrete Protocol

The abstract rules are easy to state and easy to get wrong in code. A concrete single-producer, single-consumer ring can be written with four atomic operations per batch. The producer reads the consumer's sequence with `memory_order_acquire`. It computes the available space. It writes the data for the batch. It stores the new producer sequence with `memory_order_release`. The consumer reads the producer's sequence with `memory_order_acquire`. It reads the data for the batch. It stores the new consumer sequence with `memory_order_release`. The producer's next read of the consumer sequence uses acquire. That is the entire protocol. The data writes and reads are ordinary non-atomic accesses. The atomics are only on the sequence variables. The release store on the producer sequence orders all prior data writes before the sequence update. The acquire load on the consumer side orders all subsequent data reads after the sequence read. The release store on the consumer sequence orders all prior data reads before the sequence update. The acquire load on the producer side orders all subsequent data writes after the sequence read. This is a classic message-passing pattern, and it is correct on any architecture that implements the C++ memory model.

The practical details are where the bugs live. On x86-64, a release store compiles to a plain store followed by a compiler barrier, because the hardware does not reorder stores. An acquire load compiles to a plain load followed by a compiler barrier, because the hardware does not reorder loads. The compiler barrier is not optional. Without it, the compiler can move the data writes after the sequence store, or the data reads before the sequence load. The `std::atomic` operations with the correct memory order prevent that reordering. A `volatile` variable does not. `volatile` prevents the compiler from eliding the access and from reordering volatile accesses with each other, but it does not prevent reordering of non-volatile data accesses across a volatile access. Using `volatile` for the sequence and ordinary stores for the data is a common mistake that works on x86 in practice and fails on ARM or under aggressive optimization. On ARM, the release store is a `stlr` instruction or a `dmb ish` followed by a store. The acquire load is an `ldar` or a load followed by `dmb ish`. The hardware can reorder loads and stores, so the barrier instructions are doing real work. The same C++ code generates the correct instructions on both architectures if the atomics are used correctly.

The multi-producer case adds one more barrier. The available buffer entry for a slot must be published with release semantics after the data write. The consumer must read it with acquire semantics before reading the data. The main cursor may be advanced by a producer only after the available buffer entries for the claimed range are published. The consumer's sequence barrier waits on the main cursor, but the main cursor is not advanced until the contiguous range is complete. This means the consumer can see a main cursor that is behind the available buffer. The available buffer is the per-slot truth; the main cursor is the contiguous summary. The release-acquire pair on the available buffer is what makes the per-slot publication safe. The release-acquire pair on the main cursor is what makes the contiguous range visible. Both are necessary. If the main cursor is advanced without the available buffer being published, the consumer may read a slot whose data is not yet written. If the available buffer is published without the main cursor being advanced, the consumer may not know that the contiguous range is ready. The two mechanisms are complementary.

## The Multi-Consumer Min and the Cost of Gating

A ring with multiple consumers is not merely a ring with more readers. The producer must know the slowest consumer's position before it can overwrite a slot. That position is the minimum of all consumer sequences. Computing the minimum is a read-mostly operation, but it touches one cache line per consumer. Each consumer advances its own sequence with a release store. That store invalidates the producer's copy of that consumer's line. The producer's next min computation must refetch the line. If consumers advance one event at a time, the producer's min computation becomes a stream of cache misses. The cost is proportional to the number of consumers times the advance rate. This is a true sharing cost, not false sharing. The producer genuinely needs to read the consumer sequences, and the consumers genuinely need to write them. The only ways to reduce the cost are to reduce the advance rate, to reduce the number of lines the producer reads, or to move the min computation off the producer's critical path.

Batching reduces the advance rate. A consumer that processes a batch of 64 events writes its sequence once per 64 events instead of once per event. The producer's min computation then sees a stable value for longer. A single gating sequence reduces the number of lines. One thread—often the slowest consumer or a dedicated coordinator—reads all consumer sequences and writes a single gating sequence. The producer reads only that one line. The coordinator's read set is still all consumer lines, so the coherence traffic has not disappeared; it has moved. But the producer's critical path is shorter, and the coordinator can run on a separate core or be folded into a consumer that is already reading those lines. A hierarchical gating scheme generalizes this: consumers are grouped, each group has a gate, and the producer reads the group gates. The depth of the hierarchy trades latency for a smaller read set. The Disruptor's `SequenceBarrier` allows a consumer to gate on other consumers, which builds a dependency graph rather than a flat min. A downstream consumer waits for its upstream dependencies, and the producer waits for the terminal consumers. The graph can be arranged so that the producer reads only the lines it needs, and the min is computed by the consumers that are already coordinating.

The multi-consumer min also affects the latency tail. A single slow consumer holds back the gating sequence, which holds back the producer, which eventually fills the ring. The other consumers can continue to consume published events, but the producer cannot reclaim the slots behind the slow consumer. This is head-of-line blocking at the consumer level. If the slow consumer is descheduled, the ring fills and all producers block. The system's throughput becomes the slow consumer's throughput. This is not a bug; it is the consequence of bounded memory and in-order reclamation. If the application cannot tolerate a straggler, it must either give each consumer its own ring or implement a timeout that evicts the straggler. Eviction is dangerous because the straggler may later resume and read a slot that has been overwritten. The safe version of eviction requires a generation counter or a separate overflow path. The bounded ring buffer does not solve the straggler problem; it makes the cost of the straggler explicit.

## Backpressure, Overload, and the Shape of the Tail

When the ring is full, the producer cannot claim a new sequence without overwriting unread data. The policy it chooses determines the shape of the latency distribution under overload. Blocking is the simplest: spin, park, or sleep until the consumer advances. The producer's latency becomes the consumer's latency plus the wait. Under normal load, the wait is zero. Under overload, the wait grows without bound if the consumer cannot keep up. The tail latency is unbounded, but no data is lost. Dropping is the alternative: the producer discards the event or overwrites the oldest. Dropping bounds the producer's latency, but it changes the contract. The consumer must be able to detect a gap. In a sequence-numbered ring, a gap is a sequence that will never be published. The consumer's barrier waits for it forever unless there is a separate signal. A common pattern is to advance the producer sequence past the dropped events and publish a sentinel or a gap marker. The consumer sees the sentinel and skips the sequence. This adds a branch to the consumer's hot path and a new state to the protocol. Overwriting the oldest event is worse: the consumer may be reading the slot when the producer overwrites it, which is a data race. To make overwriting safe, the producer must know that the consumer has finished with the slot, which is exactly the gating condition that made the ring full. So overwriting does not avoid the wait; it just moves the wait to the consumer's read path.

The choice of policy is not purely technical. A market-data feed may prefer to drop rather than block, because a stale price is worse than a missing one. A logging pipeline may prefer to block, because losing a log line is unacceptable. A telemetry pipeline may prefer to drop the oldest, because recent data is more valuable. The ring buffer itself does not choose; it provides the sequence arithmetic and the barriers, and the application layers the policy on top. The important thing is that the policy is explicit. A bounded ring buffer that silently blocks under overload will produce latency spikes that look like pauses. A bounded ring buffer that silently drops will produce gaps that look like lost messages. Neither is wrong, but neither is free.

The tail latency of a blocking ring is also affected by the wait strategy. A tight spin loop has the lowest wake-up latency but consumes a core. A `pause`-based loop reduces power and hyperthread interference but adds a few cycles to the detection time. A park-based loop frees the core but adds a kernel transition to the wake-up path. The optimal strategy depends on the expected wait time. If the consumer is usually only a few nanoseconds behind, spinning is best. If the consumer is often milliseconds behind, parking is best. A hybrid strategy spins for a bounded number of iterations and then parks. The bound must be tuned to the workload. Too small, and the queue parks and unparks under light load, paying the kernel cost. Too large, and a descheduled consumer burns a core. The Disruptor exposes this as a `WaitStrategy`, and the same trade-off appears in io_uring's `SQPOLL` mode and DPDK's busy-poll loops. There is no single best answer; there is only a best answer for a given latency target and core budget.

## The Ring as a Contract: Safety and Liveness

It is worth being precise about what the bounded ring buffer guarantees. Safety is easy: a consumer never reads a slot before it is published, and a producer never overwrites a slot before every consumer has consumed it. These are enforced by the sequence numbers and the memory barriers. Liveness is harder. The ring is not wait-free: a thread can be blocked by another thread's failure to advance. It is not lock-free in the formal sense: if the consumer is descheduled, the producer can fill the ring and then make no progress. The system as a whole can make progress only while there is space in the ring. Once the ring is full and the consumer is not running, no thread can complete an operation. This is a blocking dependency, even though no lock is held. The term lock-free is sometimes used to mean no locks, but the formal definition requires that at least one thread makes progress in a finite number of steps regardless of the actions of other threads. The bounded ring does not meet that definition. It is a bounded, blocking queue with non-blocking data structures. The distinction matters because it tells you what happens under thread failure. If a consumer dies, the producer will eventually block. If a producer dies, the consumer will eventually starve. The ring does not recover on its own. The application must detect the failure and restart or replace the thread.

This is not a defect. It is the price of bounded memory and cache-friendly access. A lock-free queue that allows unbounded growth must allocate, and allocation introduces locks, memory barriers, and unpredictable latency. A bounded ring buffer trades the progress guarantee for predictable memory usage and deterministic cache behavior. The backpressure is explicit. The sequence numbers make the dependency visible. The barriers make the handoff safe. The result is a data structure that is not lock-free, but is often faster and more predictable than one that is. The discipline of publishing in order is what makes the trade-off work. The producer publishes in order, the consumer consumes in order, and the sequence numbers are the tokens that enforce the contract. When both threads are running, the ring is a high-throughput, low-latency channel. When one is not, the other will eventually block.

## Where the Skeleton Shows Through: io_uring and DPDK

The same skeleton appears in two very different systems. In io_uring, the submission queue and completion queue are ring buffers with head and tail indices. The user writes SQEs into the submission queue, advances the tail with a release store, and the kernel consumes them, advancing the head with a release store. The kernel writes CQEs into the completion queue, advances the tail with a release store, and the user consumes them, advancing the head with a release store. The indices are masked by the ring size, which is a power of two. The barriers are the same release-acquire pairs we have been discussing. The `io_uring` library provides `io_uring_smp_store_release` and `io_uring_smp_load_acquire` to make the ordering explicit. The `SQPOLL` mode moves the kernel's consumption into a polling thread, which spins on the submission queue tail. That polling thread is the consumer in our sequence-barrier model, and its wait strategy is a busy spin. The `IOPOLL` mode moves the device polling into the kernel, which changes the latency profile but not the ring protocol. The ring is bounded by the number of entries the kernel allocated. When it is full, the user must wait or submit fewer operations. The backpressure is explicit in the return value of the submission call.

DPDK's `rte_ring` is closer to the Disruptor in its naming. It has `prod_head`, `prod_tail`, `cons_head`, and `cons_tail`. The producer reserves space by moving `prod_head` forward with a CAS in the multi-producer case, writes the objects, and then moves `prod_tail` forward to publish. The consumer reserves by moving `cons_head` forward with a CAS, reads the objects, and then moves `cons_tail` forward to release. The `prod_tail` is the publication point; the `cons_tail` is the gating point. The ring is lock-free for the single-producer, single-consumer case because there is no CAS on the fast path. The multi-producer case uses a CAS loop, and the same contention and batching trade-offs apply. DPDK also provides `rte_ring_sp_enqueue` and `rte_ring_mp_enqueue` to let the application choose the weaker but faster single-producer path when it knows there is only one writer. This is a recurring theme: the algorithm is the same, but the synchronization strength is a parameter. The more you know about the concurrency, the cheaper you can make the ring.

The Disruptor's `Sequencer` is the same idea with a different vocabulary. The `SingleProducerSequencer` avoids CAS on the claim path. The `MultiProducerSequencer` uses CAS and an available buffer. The `SequenceBarrier` is the consumer's wait mechanism. The `WaitStrategy` is the polling policy. The `RingBuffer` is the array of slots. The event processors are the consumers. The dependency graph is encoded in the barriers. The whole design is a direct expression of the sequence-numbered ring, and the performance comes from the cache-line discipline: pad the sequences, batch the claims, publish once, and keep the data slots away from the control lines. The same discipline appears in io_uring and DPDK, even though the APIs and the use cases are different. The bounded ring buffer is not a single data structure; it is a pattern for sharing an array between a producer and a consumer without letting the coherence protocol dictate the throughput. The sequence numbers are the contract, the barriers are the enforcement, and the cache lines are the physical reality that the design is built to respect.
