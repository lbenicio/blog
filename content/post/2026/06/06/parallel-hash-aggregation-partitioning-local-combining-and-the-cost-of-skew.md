Parallel hash aggregation is one of the deceptively simple operators in a query engine. A serial implementation is easy to sketch: scan the input, hash each grouping key, probe a hash table, and update the aggregate state. The parallel version looks equally easy until the first real workload arrives. Then the costs appear: contention on shared buckets, false sharing between aggregate states, memory pressure from high-cardinality groups, load imbalance from a single hot key, and the awkward fact that SQL aggregation is defined over multisets while parallel execution wants to decompose work into independent pieces.

This article examines the design of a parallel hash aggregation operator for a shared-memory, multi-core server. The assumed setting is a SQL-like engine executing a GROUP BY over an in-memory input, with a fixed number of worker threads and aggregate functions that are decomposable, such as COUNT, SUM, MIN, and MAX. AVG is treated as a pair of SUM and COUNT states. Holistic aggregates such as median, ordered-set aggregates, and DISTINCT aggregates require different treatment because their partial states are not simple fixed-size values. The goal is not to present benchmark numbers or to claim a universally best implementation. It is to make the design space explicit: what the operator must preserve, where the parallel costs come from, and which trade-offs are real.

## The operator contract

Before optimizing anything, it helps to state what parallel hash aggregation must produce. The logical input is a multiset of rows. The logical output is one row per distinct grouping-key value, with each aggregate computed over all input rows in that group. SQL does not promise output order unless the query has an ORDER BY, so the parallel operator is free to emit groups in any order. It is not free to change grouping semantics. NULL handling, collation, type coercion, and overflow behavior are part of the contract, not implementation details.

The aggregate functions impose a second contract: the operator must be able to combine partial states. COUNT is a sum of counts. SUM is a sum of partial sums, but only if the numeric type and overflow semantics permit reassociation. MIN and MAX are associative and commutative over their domains. AVG is representable as SUM plus COUNT, then divided at the end. A user-defined aggregate may expose a merge function, or it may not. If the aggregate is not decomposable, the engine must either serialize that aggregate, sort by group key and run a streaming aggregation, or fall back to a single-threaded path. Pretending that every aggregate is mergeable is a correctness bug waiting to happen.

There is also a cardinality contract. The operator must handle low-cardinality inputs, where there are few groups and many rows per group, and high-cardinality inputs, where almost every row is its own group. Those two cases stress different parts of the design. Low cardinality rewards local pre-aggregation and cheap combining. High cardinality rewards memory-efficient hash tables, good hash functions, and avoidance of unnecessary copying. A design that is excellent for one case can be mediocre for the other.

## Why a single shared hash table is usually the wrong first design

The simplest parallel design is one global hash table protected by fine-grained locks or updated with atomics. Each worker scans a slice of input and updates the shared table. For low-cardinality inputs, this can be attractive because every worker contributes to the same small set of groups. The problem is that the table becomes a contention point. Even with per-bucket locks, the hot buckets are exactly the ones that many workers touch. Atomics on the aggregate state avoid locks but move the cost to the cache-coherence protocol: every update to a shared cache line invalidates that line in other cores. The result is a design whose throughput collapses as worker count rises, even though the algorithmic work is small.

A single shared table also makes memory ordering harder to reason about. If workers publish new groups while others probe the table, the table needs a concurrent hash-table protocol: safe publication of keys and states, memory reclamation for resized tables, and a story for readers that encounter a bucket being migrated. None of this is impossible, but it is a large amount of complexity for an operator that usually has a better decomposition.

There are cases where a shared table is defensible. If the group count is tiny and the aggregate updates are cheap, a shared table with per-group atomic counters may be simpler than partitioning. If the engine already has a high-quality concurrent hash table and the workload is known to be low-cardinality, the shared design can avoid the partitioning pass. The trade-off is predictability: shared-state aggregation tends to have a sharp contention cliff, and the cliff moves with core count, cache topology, and input distribution. Partition-private aggregation has more moving parts, but its contention behavior is easier to control.

## Two-phase aggregation

The standard alternative is two-phase aggregation. In the first phase, workers partition input rows by the hash of the grouping key. In the second phase, each partition is aggregated independently, often by a single worker or by a small group of workers with local tables. The output is then either emitted directly or merged with partial results from other partitions.

Partitioning can be done in several ways. A radix partitioner computes the high bits of the hash and appends each row to a per-partition buffer. A simpler hash partitioner uses modulo or a bitmask to select a partition. The partition count is usually a power of two so that the selector is a mask rather than a division. The important property is that all rows with the same grouping key go to the same partition. That property turns a global aggregation problem into a set of independent local aggregation problems.

Partitioning is not free. It touches every input row, writes it to a buffer, and later reads it back. For wide rows, copying the entire row is expensive. A common optimization is to partition only the grouping key and a compact payload, or to partition references into the input when the input is stable and columnar. The trade-off is indirection: references save copying but add pointer chasing and can hurt cache locality. For narrow grouping keys and small aggregate inputs, copying the key and aggregate arguments into a compact tuple is often better than copying the full row.

A second optimization is pre-aggregation before partitioning. If a worker sees many rows with the same key in its local input slice, it can combine them into a local hash table first, then partition only the local groups. This reduces the number of rows that cross the partition boundary. It is especially effective for low-cardinality inputs. For high-cardinality inputs, the local table may contain almost as many entries as input rows, so pre-aggregation adds work without reducing the shuffle. The engine needs either a cardinality estimate or a bounded local table that spills or degrades gracefully when it grows too large.

## Partitioning choices and local hash tables

The partition count is a tuning parameter with real consequences. Too few partitions create large per-partition working sets and poor load balance. Too many partitions create more buffers, more metadata, and more merge overhead. A useful starting point is a small multiple of the worker count, but the right value depends on input size, group cardinality, and memory bandwidth. On NUMA systems, partition placement matters as well. If a worker writes into a partition buffer that lives on a remote NUMA node, the partitioning pass pays remote-memory latency. Allocating per-worker buffers on the local node and then merging or stealing partitions can reduce that cost, but it complicates the handoff.

Within a partition, the local hash table is usually an open-addressing table with linear probing. Open addressing has good cache behavior and avoids per-entry allocation. The table stores the grouping key and the aggregate state. For multiple aggregates, the state can be a struct of fixed-size fields, or a structure-of-arrays layout with separate arrays for each aggregate. The structure-of-arrays layout can improve vectorization and reduce padding when different aggregates have different sizes, but it adds address arithmetic and can hurt when the engine needs to update several aggregates for the same key. The trade-off is between cache-line utilization and update locality.

The hash table also needs a growth policy. Growing an open-addressing table requires rehashing every entry. For high-cardinality inputs, repeated growth can dominate the cost. A common approach is to size the table from a cardinality estimate when one is available, and otherwise grow geometrically with a bounded load factor. The load factor is a trade-off: lower load factors reduce probe lengths but waste memory; higher load factors save memory but increase cache misses and insertion cost. For aggregation, the table is usually insert-heavy and lookup-heavy, so a moderate load factor is often preferable to an aggressive one.

## Contention, false sharing, and memory ordering

Partition-private aggregation removes most logical contention, but it does not remove all hardware contention. False sharing is the classic trap. If two workers update separate aggregate states that happen to share a cache line, the cache line ping-pongs between cores even though the logical states are independent. The fix is to align hot per-worker state to cache lines or to batch updates so that a worker touches a cache line many times before another worker touches it. Padding is not free: it increases memory footprint and can reduce cache capacity. The engineering question is which states are hot enough to justify padding.

Memory ordering matters when partial results are published for merging. If a worker writes a partial aggregate state and then sets a ready flag, the flag must be a release store and the consumer must use an acquire load. Otherwise the consumer may observe the flag before the state is visible. In practice, many engines avoid this by joining workers at a barrier and then merging, which gives a happens-before edge through the synchronization primitive. That is simpler and usually fast enough. A lock-free merge path is possible, but it should be justified by a measured need, not by an assumption that barriers are too expensive.

There is also a subtler contention issue inside the partitioner. If all workers append to a shared per-partition buffer, the buffer's atomic counter becomes a hot spot. Per-worker buffers avoid this but require a later merge or a partition-stealing phase. The same pattern appears in local hash tables: per-worker tables avoid locks but create duplicate groups that must be combined. The design is fundamentally about choosing where to pay the combining cost: during partitioning, during local aggregation, or during the final merge.

## Skew: the real adversary

Static hash partitioning assumes that the hash function spreads groups evenly across partitions. That assumption fails when one key is hot. A single grouping key with millions of rows all hashes to one partition. One worker gets most of the work while the others finish early. Adding more workers does not help, because the hot key cannot be split by hash. The aggregate for that key is inherently sequential unless the engine can decompose the aggregate state and combine partial states from multiple workers.

There are several ways to handle skew. The engine can detect hot keys during a sampling phase and give them a dedicated path. It can use partial aggregation with a second-level combine for hot keys. It can salt the partition key and then combine salted partials, but salting changes the grouping key and requires a final merge per original key. It can fall back to a shared concurrent table for hot keys while keeping cold keys partition-private. Each option has a cost. Detection costs a pass or a sample. Salting increases the number of partial states and the merge work. A shared hot-key table reintroduces contention, though only for the hot keys. The right choice depends on how much skew the workload has and how expensive the aggregate state is to merge.

Skew is also a memory problem. A hot partition may contain many distinct groups that hash to the same partition even if no single key dominates. The partition's hash table grows large, and the worker may spill or fail. A robust design needs a fallback: spill the partition to disk, split the partition by additional hash bits, or switch to a sort-based aggregation for that partition. The fallback is part of the operator, not an afterthought. The next design question is how to detect the need for that fallback before the worker runs out of memory, and how to preserve the aggregate contract when the fallback changes the execution strategy.

## Fallback paths under memory pressure

The fallback question is not only about avoiding an out-of-memory error. It is about preserving the aggregation contract when the chosen execution strategy can no longer make progress. A partition-private hash table has a simple failure mode: the table grows until the worker cannot allocate another array, or the per-partition memory budget is exhausted. At that point the engine has three broad choices. It can spill partial aggregate states, it can split the partition into smaller key ranges, or it can abandon hash aggregation for that partition and switch to a sort-based path. Each choice has different implications for correctness, cost, and the amount of work that survives the transition.

Spilling partial states is the most natural option when the aggregate functions are mergeable. The worker serializes each entry as a grouping key plus the current aggregate state. On reload, the engine treats the spilled entries as another partial input: it probes the hash table again and combines states. This preserves all the work already done, because a partial SUM can be added to another partial SUM, a partial COUNT can be added to another COUNT, and a partial MIN or MAX can be compared with another partial MIN or MAX. The spill format must be self-describing enough to reconstruct the key and state, which usually means storing the key length, the key bytes, and a fixed-size state record. If the aggregate state is variable-length, such as a DISTINCT set, spilling becomes more complicated because the state itself may need to be serialized incrementally or converted into a sorted run of values.

Sort-based fallback is attractive when the partition has many distinct groups and the hash table is thrashing. Sorting the partition by grouping key converts the problem from random probes to a streaming scan. Once the rows are ordered, the engine can compute each group with a small constant amount of state, because all rows for a key are adjacent. The cost is the sort itself, which is O(n log n) comparisons and may require external merge passes if the partition does not fit in memory. For a partition that is already skewed, the sort may still be better than repeatedly spilling and rebuilding a hash table. The engine can also use a hybrid: hash aggregation until a memory threshold, then spill sorted runs, then merge the runs while combining aggregate states. That is essentially external hash aggregation, and it keeps the hash path efficient for the common case while bounding memory for the exceptional case.

Partition splitting is the third option. If a partition contains many distinct keys, the engine can rehash its entries using additional hash bits, producing several subpartitions. Each subpartition can then be processed independently, possibly by a different worker. This is a recursive form of radix partitioning. It reduces the working set per hash table and can turn one large partition into several smaller ones that fit in cache. The limitation is that splitting by extra hash bits does nothing for a single hot key. All rows with that key still land in the same subpartition, because the key is identical. To handle a hot key, the engine needs a different mechanism: it must decompose the key itself, not the hash space.

## Merge strategies and aggregate state design

Once local aggregation has produced partial tables, the engine must combine them into final groups. The merge phase is often overlooked because it is small for low-cardinality inputs, but it can become the dominant cost for high-cardinality inputs with many workers. If every worker builds a local table over the same key space, then each distinct key may appear in every worker's table. The merge then touches W times as many entries as there are distinct keys, where W is the number of workers. That multiplication is the hidden tax of pre-aggregation without partitioning. Partitioning first avoids the tax because each key is assigned to exactly one partition. Within that partition, however, multiple workers may still have partial states if the partition was processed by more than one worker or if hot-key salting was used.

The design of the aggregate state determines how cheap the merge is. A state that fits in a few machine words can be combined with a handful of instructions. A state that contains a pointer to a heap-allocated set or a list of values requires a more expensive merge, often with allocation and deduplication. For fixed-size states, the engine can use a structure-of-arrays layout during the merge: one array for keys, one array for each aggregate field. This allows the merge loop to read and write contiguous memory, which is friendlier to the cache and to the hardware prefetcher. The trade-off is that updates to multiple aggregates for the same key require touching several arrays, which may be worse than an array-of-structs layout when the state is updated together. The right layout depends on whether the merge is dominated by key comparisons or by state arithmetic.

Merge order matters for floating-point aggregates. SUM over floating-point values is not associative in the strict sense, because rounding depends on the order of additions. SQL engines often accept nondeterministic results for parallel floating-point SUM, but some applications expect reproducibility. If reproducibility is required, the engine must impose a deterministic reduction tree or sort the partial states by a stable order before combining. That constraint can eliminate some of the cheapest parallel merge strategies. Integer SUM has a different issue: overflow. If partial sums are computed in a wider type, the final combine can check overflow once. If partial sums are computed in the target type, an intermediate overflow may be masked or may wrap differently depending on how the work was partitioned. The aggregate contract must specify which behavior is acceptable.

MIN and MAX are easier because they are associative, commutative, and idempotent. The only subtlety is NULL handling. A partial state may be empty, meaning no non-NULL value has been seen. Merging an empty state with a non-empty state should return the non-empty state. Merging two empty states returns empty. COUNT has a similar empty-state concept, but COUNT(*) counts rows rather than non-NULL values, so the state is just a counter. AVG is represented as SUM and COUNT, and the final division happens after all partial states are merged. If the aggregate has a FILTER clause, the filter is applied before the state update, so partial states only include rows that passed the filter. That is a per-row decision and does not change the merge logic.

Holistic aggregates break the fixed-size state model. A median requires all values for a group, or at least a bounded approximation. A DISTINCT aggregate requires a set of distinct values. In a parallel hash aggregation, the partial state for such an aggregate is not a small scalar; it is a collection. Merging collections requires union, which may need hashing or sorting. If the collection is large, the merge can dominate memory and CPU. A common fallback is to sort the input by grouping key and then by the aggregate argument, so the final aggregate can be computed with a streaming pass. That sort-based path is not a hash aggregation anymore, but it may be the only correct way to parallelize a holistic aggregate without unbounded partial state.

## Hash table engineering for partitioned aggregation

The hash table inside a partition is where many small design decisions accumulate. The first is key encoding. Grouping keys can be integers, strings, decimals, dates, or composite tuples. The hash table needs a byte representation that preserves equality under the query's collation and type coercion rules. For fixed-width types, the encoding is usually the raw value or a normalized integer. For strings, the engine may hash the original bytes and compare with the collation only on hash collisions. That avoids copying and transforming every string, but it makes collision resolution more expensive. Alternatively, the engine can normalize strings into a canonical form and hash that form. Normalization costs a pass over the string but makes comparisons cheap. The right choice depends on the collision rate and the cost of the collation function.

The second decision is the probing scheme. Linear probing is simple, cache-friendly, and works well when the load factor is moderate. Robin Hood hashing reduces probe-length variance and can improve worst-case lookup times, but it increases insertion work because entries may be displaced. For aggregation, insertions and updates are the common operations, and lookups of existing keys are frequent. A simple linear-probing table with a stored hash fingerprint is often sufficient. The fingerprint lets the table reject most non-matching slots without comparing the full key. If the fingerprint is one byte, the false-positive rate is 1/256, which is low enough that full key comparisons are rare. SIMD can probe several slots at once, but that optimization is only worth the complexity when the table is large and the key comparison is expensive.

The third decision is memory allocation. A per-partition table should allocate from a per-worker arena rather than the global allocator. Global allocation can become a contention point when many workers grow tables at the same time. An arena also makes it cheap to release all memory for a partition after the merge. The growth policy is a trade-off between rehashing cost and memory waste. If the engine has a cardinality estimate, it can size the table once and avoid growth. If not, geometric growth with a bounded load factor is the usual choice. Rehashing an open-addressing table touches every entry and can be expensive for high-cardinality groups. An alternative is bucketed chaining, which allows incremental growth by adding new buckets, but chaining adds pointer chasing and per-entry allocation. For aggregation, the open-addressing table with a good initial estimate is usually the better default.

NUMA effects are part of the memory layout. If a worker processes a partition on a remote NUMA node, every table access pays remote latency. The engine can allocate partition tables on the node where they will be processed, but that requires knowing the assignment before allocation. A common approach is to let the worker that first touches a partition allocate its table, so the memory is local to that worker. If the partition is later stolen by another worker, the table becomes remote. Work stealing therefore has a NUMA cost that is easy to overlook. For large tables, the remote bandwidth may still be acceptable, but for small tables the latency can dominate. The engine may choose to keep partitions pinned to their original workers when the table is small, and only steal when the partition is large enough to amortize the remote access.

## Adaptive execution and the shape of the cost model

A static plan for parallel hash aggregation must choose the partition count, the initial table size, whether to pre-aggregate, and whether to use salting. Those choices interact with the input distribution, and the input distribution is often unknown until the query runs. Adaptive execution uses a sample or a first batch of rows to estimate cardinality and skew. A count-min sketch can identify heavy hitters without storing every key. A sample of the first few thousand rows can estimate the number of distinct groups and the fraction of rows belonging to the largest group. If the largest group is a small fraction, static hash partitioning is fine. If one key dominates, the engine should route that key to a special path before the main partitioning pass.

The cost model for parallel hash aggregation is dominated by the maximum partition time, not the average. If the input is perfectly balanced, each worker processes about N/P rows, and the total time scales down with P. If one partition contains a hot key with a large fraction of the rows, that partition's worker takes much longer than the others. The other workers finish early and sit idle. The speedup is then bounded by the serial fraction, much like Amdahl's law. If a single key accounts for half the rows, no amount of additional workers can reduce the time below the time needed to process that key, unless the aggregate state for that key can be decomposed and combined from multiple partial states. Salting is the standard way to decompose a hot key. The engine splits the hot key into S salted variants, distributes the rows across S partitions, and then merges the S partial states for the original key. The merge cost is S state combinations, which is negligible compared with the row processing cost if S is small. The challenge is detecting the hot key early enough and ensuring that the final merge knows which keys were salted.

A robust adaptive design often combines several mechanisms. It samples the input to find heavy hitters. It partitions most keys normally. It salts only the heavy hitters, using a separate table or a flag in the key encoding. It monitors per-partition memory and switches to spilling or sorting when a partition exceeds a threshold. It allows idle workers to steal subpartitions when the remaining work is uneven. Each mechanism adds complexity, but each addresses a failure mode that static partitioning cannot handle. The cost model is not a single formula; it is a set of regimes. In the low-cardinality regime, local pre-aggregation and cheap merging dominate. In the high-cardinality regime, hash table memory and cache behavior dominate. In the skewed regime, the maximum partition time dominates, and the only effective remedies are decomposition and dynamic work assignment. The next step is to make those regimes explicit in the operator's decisions, so that the engine can move between them without violating the aggregation contract.

## Work assignment and scheduling

Partitioning creates units of work, but the operator still has to decide who processes them. Static assignment maps partition `i` to worker `i mod W`. It is simple, has no coordination cost, and gives each worker a predictable set of partitions. It works when partitions are balanced and the input is evenly distributed. It fails when one partition is much larger than the others. Dynamic assignment uses a shared queue of partitions or subpartitions. Workers pop the next unit when they finish the current one. The queue can be a simple atomic counter over an array of partition descriptors, which avoids lock contention and preserves locality if the array is padded. The granularity matters. If the unit is an entire partition, a worker that gets a hot partition cannot be helped. If the unit is a small chunk of a partition, workers can share the hot partition's rows, but they need a way to combine their partial states. Chunking also increases scheduling overhead and can hurt cache locality because different workers touch the same partition's hash table. A common compromise is to make the unit a subpartition produced by additional radix bits. The subpartition is large enough to amortize scheduling and small enough to balance load. Hot keys still need salting because no amount of subpartitioning can split an identical key.

Work stealing is another option. Each worker has a deque of partitions. When idle, it steals from the back of another worker's deque. The stealing worker takes a partition and processes it locally. This reduces coordination on the common path and can improve locality because a worker usually processes its own partitions. The cost is that stolen partitions may be remote on NUMA systems, and the stolen hash table may already contain partial states that are now accessed from a different node. For small tables, the remote access can dominate. For large tables, the bandwidth may be acceptable. The engine can mitigate this by stealing only partitions above a size threshold, or by splitting a partition before stealing so that the stolen piece is small enough to rebuild locally. Rebuilding means rehashing the partial states, which is extra work but may be cheaper than remote memory traffic.

The scheduling policy also interacts with the merge phase. If workers process disjoint partitions, the merge phase can be parallelized by partition. Each worker merges its own partial tables and emits final groups. If workers share partitions through chunking or stealing, the merge must combine partial states from multiple workers. That can be done with a per-partition merge tree: each worker publishes its partial table, and a designated worker combines them. The merge tree can be flat, with one combiner per partition, or hierarchical, with several levels to reduce the fan-in. The flat merge is simpler and usually fast enough when the number of partial tables per partition is small. A hierarchical merge adds synchronization and intermediate storage but can reduce the critical path when many workers contribute to the same partition. The right choice depends on how often sharing occurs. If sharing is rare, the flat merge is the better default.

## Memory budgets and external aggregation

A parallel aggregation operator must operate within a memory budget. The budget may be global for the query, per worker, or per partition. A global budget is the most useful because it reflects the actual memory available to the process, but it requires coordination. If each worker independently decides to grow its table, the sum of their allocations can exceed the budget and trigger an out-of-memory error. A reservation protocol avoids this. Before growing a table, a worker requests memory from a shared accounting structure. The request is granted if the global budget allows it; otherwise the worker must spill or reduce its table. The accounting structure itself must be cheap to update, so it is usually a set of per-worker counters with a shared atomic total. Workers reserve in large chunks to amortize the atomic update, and they return unused memory when a partition finishes. The chunk size is a trade-off between accounting accuracy and contention. Too small a chunk makes the atomic counter a hot spot; too large a chunk wastes memory and can cause unnecessary spilling.

Spilling is the fallback when the budget is exhausted. The operator writes partial aggregate states to disk or to a temporary memory-mapped file. The spill format should be compact and self-describing. A typical record is a length-prefixed key followed by a fixed-size state. The state may include multiple aggregate fields, so the record layout is determined by the aggregate function list. If the aggregate state is variable-length, the record must include the state length or a separate offset table. Spilling is not just a memory-management detail; it changes the execution strategy. Once a partition has spilled, the worker may continue to build a smaller in-memory table for the remaining rows, or it may switch entirely to a sort-based path. Continuing with a smaller table is attractive because it preserves the hash path for the common case. Switching to sort is attractive when the partition is so large that repeated spilling would dominate. The engine can decide based on the number of spilled runs and the estimated cost of merging them.

External hash aggregation merges spilled runs by reading them back and combining states. If the runs are sorted by grouping key, the merge is a streaming k-way merge. If they are hash-partitioned, the merge probes a hash table again. Sorted runs have a predictable I/O pattern and allow the final aggregation to be computed with a single pass over the merged stream. Hash-partitioned runs require random access into the hash table, which can be slower on disk but may be faster when the runs are small enough to fit in memory. A hybrid approach spills sorted runs but uses a hash table for the in-memory portion. The sorted runs are merged first, producing a stream of partial states, and the stream is combined with the in-memory table. This keeps the fast path fast and bounds the memory of the slow path.

The spill path must preserve the aggregation contract. Rows that were already aggregated into a partial state must not be counted twice. When a partial state is spilled, it represents the combined contribution of many input rows. On reload, it is treated as a single input row with a pre-combined state. The combine function must be the same one used for in-memory merging. If the aggregate is not mergeable, the operator cannot spill partial states; it must spill raw rows or fall back to a sort-based aggregation. That distinction should be made in the operator's plan, not discovered at runtime. A plan that assumes every aggregate is mergeable will produce wrong results for holistic aggregates under memory pressure.

## Cache-conscious layout and vectorization

The performance of partitioned hash aggregation is often limited by memory access, not by arithmetic. The hash table layout determines how many cache lines each probe touches. Open addressing with linear probing is cache-friendly because a probe sequence walks contiguous slots. Storing a one-byte fingerprint in each slot lets the table reject most non-matching slots without reading the key. The key and state can be stored in separate arrays or in a single struct. A struct-of-arrays layout keeps the fingerprints and keys contiguous, which is good for probing, but the aggregate state may be updated only after a match. If the state is in a separate array, the update touches a different cache line. If the state is in the same struct, the probe reads more bytes per slot. The trade-off depends on the key size and the number of aggregates. For a small key and a small state, an array of structs is usually better because a single cache line contains both the key and the state. For a large key or many aggregates, a structure-of-arrays layout may be better because it avoids loading unused state fields during probing.

Vectorization can accelerate hash computation and probing. A batch of grouping keys can be hashed with SIMD instructions, producing a vector of hashes. The hashes can then be used to gather slots from the table. Gather instructions are available on modern CPUs, but they can be slow when the addresses are scattered. The benefit is highest when the table is small enough to fit in L2 cache and the keys are fixed-width. For variable-width keys, vectorization is harder because the key comparison is not a simple vector operation. The engine can still vectorize the hash computation and the fingerprint comparison, then fall back to scalar comparison for candidates. That hybrid approach captures most of the benefit without requiring a fully vectorized hash table.

Prefetching is another low-level technique. While probing for one key, the worker can prefetch the cache line for the next key's likely slot. The prefetch distance must be tuned to the memory latency and the amount of work between probes. Too short a distance does not hide latency; too long a distance evicts useful cache lines. For aggregation, the access pattern is often a mix of hits and misses. Hits are cheap because the slot is already in cache. Misses require a memory access. Prefetching helps most when there are many misses, which happens for high-cardinality groups. For low-cardinality groups, the table is small and the working set fits in cache, so prefetching adds little. An adaptive design can enable prefetching only when the table size exceeds a cache threshold.

NUMA-aware allocation is part of the memory layout. A partition table should be allocated on the node where it will be processed. If the worker that processes the partition is known at allocation time, the allocation can use the local node. If the partition may be stolen, the engine can allocate on the node of the worker that created the partition, or it can use interleaved allocation to spread the table across nodes. Interleaving can improve bandwidth for large tables but increases latency for small tables. The right policy depends on the table size and the access pattern. A common heuristic is to allocate small tables locally and interleave large tables. The threshold is architecture-dependent and should be tuned empirically.

## Correctness under parallelism

Parallel hash aggregation must preserve SQL semantics even when the execution order is nondeterministic. NULL handling is a frequent source of bugs. In `GROUP BY`, NULL values are considered equal to each other for grouping purposes, even though `NULL = NULL` is unknown in a `WHERE` clause. The hash function must map all NULLs to the same hash value, and the equality function must treat two NULLs as equal. If the engine uses a generic hash function that hashes the null bitmap, it must ensure that different null bitmaps with the same logical NULL key produce the same hash. A common approach is to encode the grouping key into a canonical form before hashing. The canonical form represents NULL with a dedicated tag, so the hash and equality functions are consistent.

Collation adds another layer. For strings, equality may be case-insensitive, accent-insensitive, or locale-specific. The hash function must be consistent with the equality function: if two strings are equal under the collation, they must have the same hash. The simplest way to guarantee this is to normalize the string to a canonical form and hash the normalized bytes. Normalization costs CPU and memory, but it makes probing cheap and avoids repeated collation calls during collisions. If the engine hashes the original bytes and applies the collation only on collision, it must ensure that the collision check uses the same collation as the query. That is correct but can be slow when many strings collide under the raw hash. The choice depends on the collation's cost and the collision rate.

Type coercion is a third source of subtle bugs. A grouping key may be an integer in one input and a decimal in another, or a date and a timestamp. The engine must coerce both to a common type before hashing and comparing. If coercion happens after hashing, two logically equal keys may hash differently. The operator should therefore receive a normalized key expression from the planner, or it should apply coercion before the hash computation. The same applies to composite keys: the encoding must be unambiguous, so that the concatenation of two fields cannot be confused with a different pair of fields. Length-prefixing variable-width fields is the usual solution. Fixed-width fields can be concatenated directly if their alignment and byte order are consistent.

Floating-point aggregates require special attention. SUM over floating-point values is not associative, so the result can vary with the order of partial combines. Some engines accept this nondeterminism; others require reproducible results. If reproducibility is required, the merge order must be fixed. That can be achieved by sorting partial states by a stable key before combining, or by using a deterministic reduction tree. Both options add cost. The engine should make the trade-off explicit in the query plan, perhaps with a flag that controls whether parallel floating-point aggregation is allowed to be nondeterministic. Integer SUM has an overflow contract. If the engine computes partial sums in a wider type, the final combine can detect overflow. If it computes in the target type, intermediate overflow may wrap or raise an error depending on the language semantics. The parallel decomposition must not change the observable behavior. That means the partial state type must be wide enough to represent any intermediate sum that the serial execution could produce, or the engine must detect overflow at the same points as the serial path.

Finally, the merge function for user-defined aggregates must be validated. A user-defined aggregate that claims to be mergeable but has side effects or order-dependent behavior can produce wrong results when partial states are combined out of order. The engine cannot verify the mathematical properties of an arbitrary merge function. It can only document the contract and provide a serial fallback. For built-in aggregates, the merge functions are known and can be tested exhaustively. Differential testing against a serial implementation is the most practical way to catch semantic bugs. Randomized inputs, including NULLs, duplicate keys, collation edge cases, and overflow boundaries, should be run through both paths and compared. Skew injection and memory-limit injection should also be part of the test suite, because the fallback paths are where correctness bugs often hide. A parallel aggregation operator is not correct because it passes a balanced benchmark; it is correct when it produces the same result as the serial operator under every input distribution and every memory budget.

## Instrumentation and observability for parallel aggregation

A parallel aggregation operator that cannot explain its own behavior is hard to tune and harder to trust. The first requirement is a set of counters that are cheap enough to leave enabled in production and detailed enough to diagnose the common failure modes. Per-worker counters should include input rows scanned, rows partitioned, local table entries created, local table probes, collision checks, partial states spilled, and bytes spilled. Partition-level histograms should record the number of rows and the number of distinct groups per partition. The most useful single number is the skew ratio: the size of the largest partition divided by the median partition size. A ratio near one indicates balanced work. A ratio in the tens or hundreds indicates that static partitioning is failing, either because of a hot key or because the hash function is poor.

Heavy-hitter detection deserves special instrumentation. A count-min sketch per worker can track approximate frequencies of grouping keys without storing every key. At the end of the local phase, workers merge their sketches to produce a global estimate of the top keys. If the top key accounts for more than a small fraction of rows, the operator can log a warning or trigger salting on the next execution. Exact top-K tracking is also possible with a bounded heap per worker, but it costs more CPU per row. The choice depends on whether the engine wants to diagnose skew after the fact or adapt to it during execution. For adaptive execution, the sketch must be updated during the scan, which adds a hash and a few counter updates per row. That is usually acceptable if the sketch is small and fits in cache.

Cache behavior is harder to instrument without hardware performance counters. If the engine has access to `perf` events or a similar API, it can sample cache misses and branch mispredictions per worker. Sampling is essential because counting every event is too expensive. The samples can be attributed to the local aggregation phase, the partitioning phase, or the merge phase. That attribution helps distinguish between a memory-bound table and a CPU-bound merge. Without hardware counters, the engine can still record table size, load factor, and average probe length. A rising average probe length with a stable load factor suggests hash collisions or a poor hash function. A stable probe length with a rising table size suggests cache capacity misses.

Instrumentation must not become the bottleneck. Per-row atomic counters are a mistake. Counters should live in thread-local structures and be flushed at phase boundaries or at the end of the query. If the engine needs live progress, it can flush every few thousand rows. The flush itself should be a relaxed atomic add or a plain write to a per-worker slot that a monitoring thread reads. The monitoring thread must tolerate stale values. For `EXPLAIN ANALYZE`, the operator should report the phase breakdown: partition time, local aggregation time, merge time, spill time, and the skew ratio. That breakdown is often more useful than a single total time because it shows which phase would benefit from tuning.

## Planner integration and cost-based decisions

The query planner decides whether to use parallel hash aggregation, sort-based aggregation, or a serial fallback. That decision should be cost-based, not rule-based. The inputs to the cost model are the estimated input cardinality, the estimated number of distinct groups, the estimated skew, the available memory, the degree of parallelism, and the decomposability of each aggregate. The planner also needs to know whether the input is already partitioned by the grouping key. If it is, the partitioning phase can be skipped. If it is not, the cost of repartitioning must be included.

A simple cost model can be expressed in terms of per-row and per-group costs. Let `N` be the input row count, `G` the number of distinct groups, `P` the number of workers, and `S` the skew factor, defined as the maximum partition row count divided by the average partition row count. The partitioned hash aggregation cost is approximately `N * c_partition + N * c_hash + G * c_state + G * c_merge * fan_in`. The sort-based cost is approximately `N * log(N) * c_compare + N * c_stream`. The shared-table cost is `N * c_atomic` plus a contention penalty that grows with `P` and the hotness of the groups. The skew penalty for partitioned hash is `(S - 1) * N / P * c_hash` if the hot partition cannot be split. Salting a hot key with `K` salts adds `K * c_salt` per hot row and `K * c_merge` per hot group, but it reduces the skew penalty by distributing the hot rows across `K` partitions. The planner should choose salting only when the skew penalty exceeds the salting cost.

The planner also needs a memory model. If the estimated group count `G` times the average state size exceeds the memory budget, the plan must include a spill path or choose sort-based aggregation. The memory estimate is uncertain because `G` is estimated. A robust plan includes a memory reservation and a fallback. The planner can allocate a memory grant to the operator, and the operator can request more at runtime. If the request is denied, the operator spills. The planner should not assume that the grant is sufficient. It should mark the plan as spill-capable if the aggregate functions are mergeable. If they are not, the plan must reserve enough memory for the worst case or use a sort-based path that can process groups in a streaming fashion.

Adaptive execution can refine the plan after a sample. The operator can read the first few thousand rows, compute a count-min sketch, and estimate `G` and the top-key frequency. If the estimate differs significantly from the planner's estimate, the operator can switch strategies. For example, if the sample shows a single key with 40 percent of the rows, the operator can enable salting for that key before the main partitioning pass. If the sample shows `G` close to `N`, the operator can disable pre-aggregation and size the local tables more aggressively. The sample itself costs a pass over a small number of rows, which is negligible for large inputs. The challenge is making the switch without violating the operator's contract. The switch must happen before any partial states are produced, or the operator must be able to merge states from both strategies. The simplest approach is to make the decision before the main scan and keep it fixed for the rest of the query.

Interaction with other operators matters. Partial aggregation below an exchange can reduce the number of rows that cross the exchange, but it adds CPU work. In a shared-memory engine, the exchange is a partition shuffle. If the shuffle is already partitioning by the grouping key, partial aggregation before the shuffle may be redundant unless it reduces the row count. The planner should estimate the reduction factor: the number of input rows divided by the number of distinct groups. If the reduction factor is large, pre-aggregation is beneficial. If it is close to one, pre-aggregation only adds overhead. The same logic applies to aggregation below a join: pushing a partial aggregation below the join can reduce the join input, but it can also change the join's cardinality estimate. The planner must re-estimate after the pushdown.

## Workload archetypes and tuning heuristics

Different workloads stress different parts of the design. A low-cardinality aggregation, such as a daily sales total by region, has few groups and many rows per group. The local hash tables are small and fit in cache. Pre-aggregation is highly effective because each worker can combine thousands of rows into a few local groups before partitioning. The partitioning phase then moves only local groups, not raw rows. The merge phase is cheap because the number of partial states is small. The main risk is false sharing between workers' local tables if the tables are small and adjacent in memory. Padding the per-worker tables to cache-line boundaries avoids that. Another risk is that the local table is so small that the hash function's distribution does not matter. In that case, a simple modulo partitioner is sufficient.

A high-cardinality aggregation, such as a distinct count of user IDs, has almost as many groups as rows. Pre-aggregation is ineffective because the local table grows to the size of the input slice. The operator should skip pre-aggregation and go directly to partitioning, or it should use a bounded local table that flushes to partitions when it reaches a threshold. The hash table must be sized from a cardinality estimate to avoid repeated rehashing. Open addressing with a one-byte fingerprint and a moderate load factor works well. The merge phase can dominate if every worker produces a partial state for every key. Partitioning first avoids that by assigning each key to exactly one partition. If the input is already partitioned by the key, the operator can skip the shuffle and aggregate each partition independently.

A hot-key workload has one or a few keys that account for a large fraction of rows. Static hash partitioning sends all rows for the hot key to one partition. That partition's worker becomes the critical path. The other workers finish early and idle. Salting is the standard remedy. The hot key is expanded into `K` salted variants, each of which goes to a different partition. Each salted partition computes a partial state for the hot key. A final merge combines the `K` partial states into the final result. The merge is cheap because `K` is small, typically the number of workers or a small multiple. The hard part is detecting the hot key before the partitioning pass. A sample or a count-min sketch can identify it. If the hot key is not detected, the operator can still fall back to a shared concurrent table for that key, but that reintroduces contention. Salting is usually better because it keeps the hot key's work distributed.

String keys with collation add CPU cost to hashing and comparison. If the collation is case-insensitive, the engine can normalize strings to lowercase before hashing. If the collation is locale-specific, normalization may be expensive. An alternative is to hash the raw bytes and apply the collation only when the fingerprint matches. That avoids normalizing every string but can produce more collisions. The engine can measure the collision rate and switch strategies if it is high. Dictionary encoding is another option when the same strings repeat many times. The dictionary maps each distinct string to an integer, and the aggregation operates on integers. The dictionary itself must be built in parallel, which is a separate aggregation problem. If the dictionary is already available from a columnar scan, the aggregation can use it directly.

Many aggregates on the same key stress the state layout. An array-of-structs layout keeps all aggregate fields for a key in one cache line, which is good when all fields are updated together. A structure-of-arrays layout keeps each aggregate in a separate array, which is good when different aggregates have different sizes or when the engine wants to vectorize updates. The best choice depends on the number of aggregates and the update pattern. If the query computes ten aggregates and every row updates all ten, an array-of-structs layout is usually better because it avoids touching ten different cache lines. If the query computes one expensive aggregate and several cheap ones, a hybrid layout may be best. The engine can also generate specialized code for the aggregate list, which eliminates per-aggregate function call overhead and allows the compiler to keep states in registers.

NUMA systems add another dimension. A partition table should be allocated on the node where it will be processed. If a worker steals a partition, the table may become remote. The engine can avoid stealing small partitions, or it can rebuild the table locally after stealing. Rebuilding costs a rehash of the partial states, but it may be cheaper than remote memory traffic. For large tables, the remote bandwidth may be acceptable, so stealing is fine. The threshold should be tuned per architecture. Interleaved allocation can spread a large table across nodes and improve bandwidth, but it increases latency for small tables. A common heuristic is to allocate small tables locally and interleave large tables.

## Operational concerns: cancellation, errors, and resource governance

A parallel aggregation operator runs inside a larger query execution. It must respond to cancellation, propagate errors, and release resources on every path. Cancellation is usually signaled by a shared flag. Workers should check the flag at safe points: between partitions, between chunks of rows, and during spill I/O. Checking the flag on every row is too expensive, but checking it every few thousand rows is cheap. If the flag is set, the worker stops, releases its local memory, closes any spill files, and returns. The coordinator waits for all workers to finish and then returns a cancellation error. The operator must not leave background threads running or temporary files on disk.

Error handling is similar. If one worker encounters an out-of-memory error, a disk write failure, or a bug in a user-defined aggregate, the other workers should stop as soon as possible. A shared error state can hold the first error and a flag that tells other workers to abort. The coordinator joins all workers and then rethrows the first error. If the operator uses a thread pool, the error must not corrupt the pool's state. Each task should be self-contained and should clean up its own resources. If the operator uses a barrier-based design, the barrier must not deadlock when one worker aborts. A common solution is to use a cancellation-aware barrier that returns an error to all waiters when any worker fails.

Memory accounting must be exception-safe. If a worker reserves memory from a global budget and then fails, the reservation must be released. The simplest way to guarantee this is to use a scope guard or RAII wrapper that releases the reservation in its destructor. The same applies to spill files and temporary buffers. If the operator uses a per-worker arena, the arena can be freed as a whole when the worker exits. That is simpler than tracking individual allocations. The global memory accounting structure must be updated with atomics, so the release must be atomic as well. A lost reservation can cause the query to fail later with a false out-of-memory error, which is difficult to debug.

Resource governance also includes disk space. Spilling can fill a temporary directory. The operator should check available disk space before writing a spill file, or it should handle write failures gracefully. If the disk is full, the operator can fall back to a sort-based path that uses less temporary space, or it can abort the query with a clear error. The planner can reserve temporary space as part of the query's resource grant. If the reservation is not available, the plan should not include spilling. Instead, it should choose a strategy that fits in memory or fail early with a clear message. Failing early is better than failing halfway through a long query.

Finally, the operator must be careful with user-defined aggregates. A UDA may have side effects, allocate memory, or depend on the order of updates. The engine cannot assume that its merge function is safe to call in parallel. The planner should mark a UDA as parallel-safe only if it is declared with a merge function and no side effects. If it is not parallel-safe, the aggregation must run serially or use a sort-based path that preserves the input order. The operator should also handle exceptions thrown by the UDA. If a UDA throws, the worker must clean up its state and propagate the error. The error should include the group key and the aggregate name, so the user can diagnose the problem. That diagnostic information is part of the operator's contract, even though it is not part of SQL semantics.
