_June 27, 2026_

A parallel compiler is a memory-allocation system wearing a compiler costume. It parses source files, builds syntax trees, resolves names, constructs intermediate representations, runs optimization passes, and emits code. Along the way it allocates an enormous number of small, short-lived objects: AST nodes, type references, temporary buffers, diagnostic fragments, worklist entries, and pass-specific metadata. When compilation is parallelized across files, functions, or modules, those allocations compete for the same heap. A general-purpose allocator with a global lock, or even a well-tuned thread-caching allocator, can become a serialization point that has little to do with the actual compiler work.

Arena allocation is an attractive response. Instead of allocating and freeing individual objects, a compiler allocates from a region and releases the whole region at once. A bump-pointer arena can make allocation a pointer increment and a bounds check. It removes per-object metadata, reduces fragmentation, and makes teardown predictable. A thread-local arena goes further: each worker thread owns its own region, so allocation does not require synchronization with other workers. For a compiler that already partitions work by thread, this looks like a natural fit.

It is not a free win. The moment an object allocated in a thread-local arena escapes to another thread, a shared cache, a diagnostic queue, or a long-lived module structure, the arena model becomes a correctness problem. The central engineering question is not whether to use arenas. It is which lifetimes are allowed to cross thread boundaries, how those boundaries are enforced, and what the compiler gives up in memory retention, determinism, and debuggability to avoid a global heap lock.

## The allocation problem in parallel compilers

Compilers are unusually allocation-heavy because they represent programs as graphs. A source file becomes a token stream, then a syntax tree, then a symbol table, then a typed intermediate representation, then a lowered form, then machine code. Each stage may create new nodes while retaining references to earlier structures. Many of those nodes are small and numerous. Some are immutable and shared. Some are mutated during a pass. Some are temporary and die before the next pass begins. A few must survive until the end of compilation because they are part of the final output or an incremental cache.

In a single-threaded compiler, the allocator can be simple and the lifetime rules can be implicit. In a parallel compiler, the same allocation pattern becomes a coordination problem. If every worker calls a global allocator for every AST node, the allocator's internal synchronization can dominate. If each worker uses a thread-local allocator, the compiler must ensure that no pointer from one worker's heap is dereferenced by another worker without a defined handoff. The second problem is harder than the first. Allocation speed is a performance concern; cross-thread lifetime is a correctness concern.

A parallel compiler also has non-obvious sharing. Interned strings, type descriptors, source file buffers, and diagnostic sinks are often shared across workers. A thread-local arena cannot own shared immutable data unless that data is copied into every arena or stored in a separate shared region. The design therefore needs more than one allocation domain. It needs a clear mapping from data categories to lifetime domains.

## What an arena is and what it is not

An arena is a region allocator. It obtains large blocks from the system allocator, hands out smaller allocations by advancing a pointer within the current block, and releases memory by discarding blocks or resetting the region. It does not support individual object deallocation in the general case. That is the point. The arena amortizes allocation and deallocation across many objects and makes lifetime a property of the region rather than of each object.

An arena is not a garbage collector. It does not trace references, move objects, or reclaim unreachable objects selectively. It also is not a general-purpose heap replacement. If an object must be freed while other objects in the same region remain live, an arena is the wrong tool. If object lifetimes are interleaved and unpredictable, an arena either retains memory longer than necessary or requires multiple regions with careful lifetime partitioning.

A thread-local arena is an arena owned by one thread. The owner can allocate without locking because no other thread is allowed to allocate from it. The owner can reset or destroy the arena when its work is complete. The difficult part is ownership transfer. A thread-local arena is safe only if every object allocated from it is either consumed by the owning thread or explicitly copied or transferred before the arena is released. There is no ambient safety property that makes cross-thread access correct.

## Why compilers are a special case

Compilers have a phase structure that maps well to arenas. Parsing a file produces a syntax tree that can be allocated in a file-local arena. Name resolution and type checking may allocate temporary tables that can be released after the module is checked. Optimization passes often create temporary IR nodes that can be discarded when the pass finishes. Code generation may allocate buffers that are copied into the final object file and then released. These phase-local lifetimes are exactly what arenas handle well.

Compilers also have data that does not fit the phase model. A module's exported symbol table may be needed by dependent modules. An incremental compilation cache may retain type information across builds. A diagnostic may be emitted by one worker and rendered by another. A linker or whole-program optimizer may need to inspect IR from multiple modules at once. These are escape paths. If a thread-local arena owns such data, the design must either copy it into a shared domain or transfer ownership of the arena itself.

The compiler's output also imposes determinism requirements. Parallel compilation should not change the emitted code, the order of diagnostics, or the contents of debug information. Arena allocation can affect determinism if addresses are used as identity, if iteration order depends on allocation order, or if memory reuse changes pointer values that leak into hashes. A thread-local arena makes allocation order thread-local, which is good for contention but dangerous for determinism if the compiler accidentally depends on address order. The design must separate logical identity from physical address.

## Thread-local arenas and the first lifetime boundary

The first lifetime boundary is the worker thread. Each worker owns a thread-local arena for transient allocations. The arena is created when the worker starts and reset at phase boundaries or when the worker's current task completes. The compiler must guarantee that no pointer into this arena is stored in a shared structure, passed to another worker, or retained after the reset. That guarantee cannot be left to convention. It needs an API boundary.

A practical approach is to make the arena type explicit in the compiler's internal interfaces. Functions that allocate transient data take a thread-local arena reference. Functions that return shared data return a shared reference or copy the result into a shared domain. The type system does not need to prove full escape analysis. It only needs to make the common escape paths visible. A transient AST node type is different from a module-owned AST node type. A diagnostic builder writes into a thread-local buffer and then freezes it into a shared diagnostic record. A string is interned in a shared immutable pool rather than copied into every arena.

This boundary also affects memory retention. A thread-local arena that is reset only at the end of a large compilation unit may retain memory for temporary objects that died much earlier. The compiler can use multiple arenas per worker, one per phase or one per task, and reset them at narrower boundaries. The trade-off is more arena management and more chances for an object to outlive its arena. Narrower lifetimes improve memory reuse but increase the number of handoff points that must be audited.

## Escape analysis as a policy, not a proof

It is tempting to solve the escape problem with compiler escape analysis. If the compiler can prove that an object does not escape its thread, it can allocate the object in a thread-local arena. If it escapes, it can allocate the object in a shared heap. This is a reasonable optimization inside a compiler that already has escape analysis, but it is a poor foundation for the memory model. Escape analysis is conservative. It may fail to prove non-escape for objects that are actually thread-local, and it may miss escape paths through indirect calls, callbacks, or data structures that are not visible to the analysis. A memory model that depends on a conservative analysis will either retain too much memory or require fallback allocations that undermine the arena's benefits.

A better model is policy-driven. The compiler defines allocation domains and rules for moving data between them. Transient data is allocated in a thread-local arena and must not escape. Module data is allocated in a module arena that outlives worker tasks and is synchronized at module boundaries. Shared immutable data is allocated in a global read-only region. Output data is copied into an output buffer or transferred to the consumer. The policy is enforced by types and APIs, not by a whole-program proof. Escape analysis can optimize within a domain, but it does not define the domain.

This distinction matters for debugging. When a cross-thread lifetime violation occurs, the compiler should fail in a controlled way rather than corrupt memory. In debug builds, arena references can carry an owner identifier and a generation counter. A dereference from the wrong thread or after a reset can be detected. In release builds, those checks may be compiled out, but the API boundaries remain. The goal is not to make unsafe code safe by assertion. The goal is to make the safe path the easy path and the unsafe path explicit.

The next sections will examine cross-thread handoff, arena ownership transfer, determinism under parallel allocation, and the memory-budget trade-offs that determine whether a thread-local arena design actually reduces cost rather than merely moving it.

## Cross-thread handoff: copies, transfers, and shared sinks

A thread-local arena is only safe while its contents remain private to the owning thread. The moment a worker wants to share a parsed function, a diagnostic, or a type descriptor, the compiler must choose a handoff discipline. There are three broad options: copy the data into a shared domain, transfer ownership of the arena that contains it, or freeze the arena and publish it as read-only. Each has different costs and failure modes.

Copying is the simplest. The worker allocates transient nodes in its thread-local arena, extracts the semantic payload, and writes a compact representation into a shared arena or a shared queue. The transient nodes are then discarded when the thread-local arena resets. This works well when the shared representation is much smaller than the transient working set. For example, a parser may build a large temporary syntax tree with parent pointers, annotations, and scratch buffers, then emit a small serialized AST or a set of symbol records. The copy is proportional to the output, not to the temporary allocation volume. The cost is explicit and easy to reason about.

Copying is less attractive when the shared data is large or when the compiler wants to avoid duplicating graph structure. A type checker may build a constraint graph in a thread-local arena and then need that graph for later optimization. Copying the graph into a shared arena can double peak memory and add a traversal that touches every node. In that case, transferring the arena is cheaper, provided no other thread holds pointers into it.

Ownership transfer moves the entire arena, or a set of blocks, from one thread to another. The receiving thread becomes the owner and is responsible for eventual reset or destruction. The sending thread must not allocate from or dereference the arena after the transfer. This is a move, not a share. In languages with affine types, the transfer can be enforced by the type system. In C or C++, it requires a disciplined API: an arena handle has an owner field, and transfer clears the sender's handle. Debug builds can assert that the sender's handle is null after transfer. Release builds rely on the API contract.

Transfer is especially useful in fork-join parallelism. A worker thread parses a function and builds its IR in a thread-local arena. When the worker finishes, it returns the arena handle to the coordinator. The coordinator can then merge the function into the module without copying the IR. The worker thread's arena is no longer thread-local in the strict sense; it has become a module-owned arena. The key invariant is that the worker has stopped using it before the transfer. If the worker publishes the handle while still allocating, another thread could observe a partially built structure. The transfer must happen after a synchronization point, such as a join or a release store.

Freezing is the third option. Instead of transferring ownership to a single thread, the worker converts its arena into an immutable region and publishes it to multiple readers. Freezing requires a release fence so that all writes to the arena are visible before the pointer is published. Readers use an acquire fence before dereferencing. The arena cannot be reset or mutated while any reader might access it. This is a read-only shared arena with a lifetime managed by reference counting or epoch-based reclamation. The cost is an atomic reference count per arena, not per object. That is usually acceptable, but it means the arena's memory is retained until the last reader drops it. If readers are long-lived, the arena becomes long-lived.

Shared sinks need a different treatment. Diagnostics, statistics, and output buffers are inherently cross-thread. A worker cannot allocate a diagnostic message in its thread-local arena and push a pointer to it into a global queue unless the queue's consumer runs on the same thread and before the arena resets. The safe pattern is to allocate the diagnostic payload in a shared arena or to copy it into a queue-owned buffer. A per-thread diagnostic queue can use a small thread-local buffer for formatting, then copy the final string into a shared queue node. The formatting scratch space is transient; the queue node is shared. This keeps the hot formatting path lock-free while the shared path pays a copy and a queue synchronization.

Handles are another way to avoid cross-thread pointers. Instead of passing a pointer to an object in a thread-local arena, the compiler passes a stable handle: an index into a per-module table, a symbol ID, or a content hash. The receiving thread resolves the handle through a thread-safe table. The table owns the object, or the object is copied into the table at publication time. Handles decouple logical identity from physical address, which also helps determinism. They add an indirection on access, but that indirection is often cheaper than a copy or a lock.

Work stealing complicates handoff because tasks may be created by one thread and executed by another. A task descriptor can live in a shared scheduler queue, but its payload should not point into the producer's thread-local arena unless the task is transferred with the arena. The cleanest design is to make the task own an arena handle. When the task is published, ownership of the handle moves to the scheduler. The thief that claims the task becomes the owner. The producer must not use the handle after publication. If the task is never stolen, the producer can execute it and retain ownership. This is a transfer at publication time. If the task needs to share data with other tasks, that data must be in a shared domain or frozen before publication.

## Determinism under parallel allocation

Parallel compilation must produce the same output as serial compilation. That includes machine code, object file layout, debug information, diagnostics, and incremental cache keys. Thread-local arenas do not automatically break determinism, but they make it easier to introduce accidental nondeterminism. The compiler must decide which parts of the output are order-sensitive and which parts are not.

The most common source of nondeterminism is address-based identity. If a hash map keys on pointer values, or if a sort compares pointers as a tie-breaker, the result depends on where objects were allocated. Thread-local arenas make addresses vary with thread scheduling and allocation order. Even a single-threaded arena can vary addresses across runs due to ASLR or different block sizes. The solution is to avoid using addresses as logical identity. Use stable IDs assigned from source locations, declaration order, or content hashes. If a pointer must be used as a temporary key, ensure that the final output is re-keyed or sorted by a stable field before emission.

Iteration order is another trap. Many compilers iterate over hash maps of symbols, types, or basic blocks. If the hash map's iteration order depends on insertion order, and insertion order depends on thread scheduling, the output can vary. The fix is to maintain an explicit order vector alongside the map, or to sort keys before iteration. Sorting adds a cost, but it is usually small compared to the rest of compilation. For diagnostics, collect messages per thread and sort them by source location and severity before printing. For symbol tables, sort by name or by a deterministic declaration index. For debug info, emit type and line tables in a canonical order.

Allocation order can affect layout even without address-based identity. If the compiler lays out a structure by allocating its fields in sequence, and those fields are allocated by different threads, the layout may interleave. If the layout is part of the output, such as a serialized AST or a bytecode format, the compiler must either allocate the final layout in a deterministic single-threaded pass or define a deterministic merge order. A common pattern is to parallelize the construction of per-function data, then concatenate the results in function ID order. Within a function, allocation is single-threaded and deterministic. Across functions, the order is fixed by the function ID, not by completion order.

Thread-local arenas can actually help determinism at the per-thread level. Each thread's allocation sequence is independent of other threads, so if the thread's work is deterministic, its internal addresses and iteration orders are deterministic relative to its own start. The nondeterminism comes from merging thread results. If the merge is deterministic, the overall output is deterministic. This suggests a design principle: keep nondeterminism contained in the thread-local domain, and make all cross-thread merges deterministic. Do not let thread completion order leak into the output.

Incremental compilation adds another dimension. Cache keys must be stable across runs and across thread counts. If a cache key includes a pointer, an arena offset, or a hash of a memory block that contains padding, it will change. Use semantic hashes: hash the fields that matter, not the raw bytes. If raw bytes must be hashed, zero out padding and avoid embedding addresses. Arena allocation can help here by making it easier to allocate objects without hidden metadata, but it does not remove the need for stable hashing.

Testing for determinism requires running the compiler multiple times with different thread counts and scheduling. Compare the outputs byte for byte. Use a deterministic allocator that fills freed memory with a pattern to catch reads of uninitialized or reset memory. Use thread sanitizers and address sanitizers in CI. In debug builds, add generation counters to arena handles and check them on every dereference. A use-after-reset in a thread-local arena is a common bug; it should fail loudly in tests, not silently produce wrong code.

## Memory-budget trade-offs

Arena allocation trades memory retention for speed. A thread-local arena is fast because it does not free individual objects, but that also means it cannot reclaim memory until the whole arena is reset. In a parallel compiler, this trade-off is multiplied by the number of threads. If each of 32 threads holds a partially used arena block, the compiler may retain hundreds of megabytes of mostly empty memory. The design must choose reset boundaries and block sizes with the memory budget in mind.

The first lever is reset frequency. A thread-local arena that is reset only at the end of compilation will retain every transient object for the entire run. A thread-local arena that is reset after every function or every optimization pass will reclaim memory sooner, but it will also invalidate any object that accidentally escaped. Narrower lifetimes reduce peak memory and increase the number of escape points that must be audited. The right boundary depends on the phase. Parsing a file may allocate a large syntax tree that is needed until the module is checked, so a file-local arena is appropriate. A single optimization pass may allocate many temporary nodes that die when the pass ends, so a pass-local arena is appropriate. The compiler should make the lifetime explicit in the phase's API.

The second lever is block size. Large blocks amortize allocation and reduce block-management overhead, but they increase the minimum memory retained per thread. Small blocks reduce retention but increase the number of blocks and the tail waste. A thread that allocates one small object in a 1 MB block wastes almost the entire block. A thread that allocates many small objects in a 1 MB block wastes only the tail. The allocator can adapt block size based on allocation rate and object size distribution. It can also use a shared block pool: when a thread resets its arena, its blocks return to a global pool for other threads to reuse. This reduces peak memory when threads are not all active at once, and it keeps allocation lock-free within a block. The pool itself needs synchronization, but only on block acquisition and release, not on every allocation.

The third lever is handoff strategy. Copying data to a shared domain costs memory and time, but it allows the thread-local arena to be reset immediately. Transferring an arena avoids the copy but keeps the arena's memory alive under the new owner. Freezing an arena for shared readers keeps it alive until the last reader finishes. The compiler should choose based on the size of the data and the expected lifetime. If a worker produces a small result from a large temporary working set, copy. If a worker produces a large result that is expensive to copy, transfer or freeze. If the result is needed by many readers for a long time, allocate it directly in a shared long-lived arena rather than transferring a thread-local arena.

The fourth lever is shared immutable data. Interned strings, type descriptors, and source file buffers are shared across threads. Allocating them in a global arena with a lock reintroduces contention. A sharded intern table with per-shard locks or a lock-free hash map can reduce contention, but the interned data itself is long-lived. This is a separate memory budget from transient thread-local arenas. The compiler should measure both. If interning consumes a large fraction of memory, it may be worth deduplicating more aggressively or using a compact representation. If transient arenas consume the budget, adjust reset boundaries or block sizes.

Measuring is essential. The compiler should track bytes allocated per phase, per thread, and per arena; bytes retained after reset; block waste; and handoff copy volume. These metrics reveal whether the arena design is actually saving memory or merely moving it. A phase that allocates 200 MB and retains 10 MB is a good candidate for a thread-local arena with a copy-out handoff. A phase that allocates 200 MB and retains 150 MB is a poor candidate unless the retained data is transferred to a long-lived owner. The metrics also help tune the number of threads. More threads may improve CPU utilization but increase peak memory due to per-thread arenas. In memory-constrained environments, a lower thread count with larger per-thread arenas may be faster overall than a higher thread count that triggers swapping.

Arena allocation is not a substitute for a memory budget. It is a tool for making allocation fast when lifetimes are known. The compiler must still decide what to retain, what to copy, and what to discard. Thread-local arenas make those decisions more visible, because the boundary between private and shared memory is explicit. That visibility is a benefit, not a cost, provided the compiler has the instrumentation to see where memory goes.

## Arena ownership transfer protocols

An arena handle is a capability, not a pointer. It grants the holder the right to allocate from a region and to reset or destroy it. In a parallel compiler, the handle must be moved between threads according to a strict protocol. The protocol can be modeled as a small state machine with states: owned, transferred, frozen, reset, and destroyed. Only the owned state permits allocation. The transferred state means the handle is in transit and must not be used. The frozen state permits read-only access by multiple readers. The reset state means the memory is available for reuse but the handle is invalid. The destroyed state means the memory has been returned to the system or to a block pool.

The state machine should be enforced by the API. A `take` operation moves an owned handle to the caller and leaves the source in the transferred state. A `give` operation accepts a transferred handle and moves it to owned by the receiving thread. A `freeze` operation converts an owned handle to a frozen handle and publishes it. A `reset` operation is only valid on an owned handle and returns its blocks to the pool. Attempting to allocate from a transferred or frozen handle is a programming error. In debug builds, the arena can store its current state and owner thread ID, and every operation can assert the expected state. In release builds, the state checks can be compiled out, but the API shape remains.

The most common transfer point is a join. A worker thread completes a task and returns its arena handle to the coordinator. The coordinator then owns the arena and can merge its contents into a module arena or freeze it for later readers. The worker must not use the handle after the return. In a language with move semantics, this is natural: the handle is a move-only type, and the compiler prevents use after move. In C or C++, the handle can be a `std::unique_ptr` with a custom deleter, or a struct with a `moved` flag that is checked in debug builds. The important invariant is that the worker stops allocating before the join completes. If the worker publishes the handle while still allocating, the coordinator may observe a partially built structure. The join provides the necessary synchronization: the worker's writes happen-before the coordinator's reads.

A second transfer point is task publication. A worker creates a task with an associated arena handle and pushes it to a shared scheduler queue. Ownership of the handle moves to the scheduler. If another worker steals the task, that worker becomes the owner. If the original worker executes the task, it can retain ownership. The scheduler must not inspect the arena's contents; it only stores the handle. The task descriptor itself should be allocated in a shared arena or in a separate scheduler arena, because it must be visible to multiple threads. The task's payload, which may be large and thread-local, travels with the handle. This pattern avoids copying the payload and keeps the hot path lock-free. The cost is that the arena's memory is retained until the task completes and its handle is reset or transferred again.

A third transfer point is sub-arena handoff. A worker may split its work into several sub-arenas, one per function or per basic block. When a sub-arena is complete, the worker can transfer it to a module builder without transferring the entire worker arena. This reduces the granularity of transfer and allows the worker to reset its main arena while the sub-arenas are still in use. The module builder collects sub-arenas in a list and freezes them into a module-owned arena. The list itself is a shared structure, so adding a sub-arena requires synchronization. A per-module lock or a lock-free stack can be used. The lock is held only for the list insertion, not for allocation within the sub-arena. This is a good compromise: allocation remains thread-local, and the shared synchronization is coarse-grained and infrequent.

Freezing is a transfer to a read-only domain. A frozen arena is immutable, so multiple readers can access it concurrently without locks. The publisher must ensure that all writes to the arena are visible before the frozen handle is published. This requires a release store on the handle and an acquire load by each reader. In C++, `std::atomic<FrozenArena*>` with `memory_order_release` and `memory_order_acquire` is sufficient. The frozen arena's lifetime is managed by reference counting or epoch-based reclamation. Reference counting adds an atomic increment and decrement per reader acquisition, which can be expensive if readers are short-lived. Epoch-based reclamation amortizes the cost: readers register an epoch, and the arena is reclaimed after all readers that could have seen it have advanced. For compiler workloads, frozen arenas often live for the duration of a module or a pass, so a simple reference count or a manual lifetime tied to the module is sufficient.

The protocol must also handle failure. If a worker panics or throws an exception, its arena handle may be left in an inconsistent state. The compiler should use RAII or defer statements to ensure that the handle is either reset or transferred before unwinding. In a parallel compiler, a panicking worker should not leave a shared structure pointing into its arena. The safest approach is to catch the panic at the task boundary, reset the worker's transient arena, and report the error through a shared diagnostic channel. The task's output is discarded. If the task had already transferred a sub-arena to a module builder, that sub-arena must be removed or marked invalid. This is easier if the module builder only accepts complete sub-arenas and if the transfer is atomic with respect to the task's completion.

## Shared arenas and synchronization domains

Thread-local arenas solve the allocation hot path, but they do not eliminate shared memory. The compiler still needs module-owned arenas, global read-only arenas, and output arenas. Each of these is a synchronization domain with its own lifetime and contention profile. The design should make the domains explicit and avoid mixing them.

A module-owned arena holds data that must survive until the module is fully compiled. It can be built by merging frozen sub-arenas from workers. The module arena itself does not need to support concurrent allocation if all merging happens at a single point, such as after a join. If multiple workers contribute to the same module concurrently, the module arena can be sharded by function or by symbol table partition. Each shard is owned by one worker at a time, and a shard is transferred to the module when the worker finishes. The module then owns a collection of shards. This avoids a global lock on the module arena and keeps allocation thread-local. The only shared operation is adding a shard to the module's list, which can use a mutex or a lock-free append. The list is read during later passes, but by then the module is frozen and no new shards are added.

A global read-only arena holds interned strings, type descriptors, and other immutable data that is shared across all modules. This arena is long-lived and may never be freed until the process exits. Allocation into a global arena can become a contention point if every worker interns strings. A single global bump pointer with a lock will serialize. A sharded intern table reduces contention: each shard has its own arena and its own lock. A string is hashed to a shard, and the shard is locked only for the duration of the intern operation. The lock is held for a short time, and the number of shards can be scaled with the number of threads. Alternatively, a lock-free hash map with atomic insertion can be used, but the arena allocation within the map still needs synchronization. Sharded arenas are simpler and often fast enough. The memory cost is that each shard retains its own blocks, so there is some tail waste. This is acceptable for a global arena that is expected to be long-lived.

An output arena holds the final object file, debug info, and any serialized metadata. It is written once and then flushed. Output arenas are usually single-threaded or merged in a deterministic order. If multiple workers produce output fragments, each fragment can be allocated in a thread-local arena and then transferred to the output assembler. The assembler concatenates fragments in a deterministic order, such as function ID order. The output arena can then be written to disk without further synchronization. The key is that the output order is determined by logical IDs, not by completion order. The output arena itself does not need to be thread-safe if the assembler is single-threaded. If the assembler is parallel, it can be sharded by output section, with each section owned by one thread.

Synchronization domains also have memory ordering requirements. When a frozen arena is published to a shared list, the publisher must use a release store. Readers must use an acquire load before dereferencing the arena. When a module arena is built by merging shards, the merge must happen after all shards are complete. A join or a barrier provides this ordering. If a lock-free list is used, the list's insertion operation must be a release store, and traversal must use acquire loads. These rules are standard, but they are easy to get wrong. The compiler should encapsulate them in a small number of primitives, such as `publish_frozen`, `acquire_frozen`, and `append_shard`. These primitives can be tested in isolation with thread sanitizers.

False sharing is a performance concern that becomes visible when arenas are per-thread. Each arena's metadata, such as the current bump pointer and the end pointer, is written frequently by the owning thread. If two threads' arena metadata share a cache line, the cache line ping-pongs between cores. The arena structure should be cache-line aligned and padded. The block pool's free list also needs padding if it is per-thread. In a compiler with many threads, false sharing can erase the benefits of thread-local allocation. Profiling with hardware counters can reveal it. The fix is straightforward but easy to forget.

NUMA effects are another concern. On a multi-socket machine, a thread-local arena should allocate memory from the NUMA node where the thread runs. If the thread migrates, the memory may be remote. The block pool can be per-node, and the arena can request blocks from the local node. If a task is stolen by a thread on another node, the transferred arena's memory may be remote for the thief. This is a performance issue, not a correctness issue. For large arenas, it may be worth copying the data to a local arena, but that defeats the purpose of transfer. In practice, work stealing is often limited to nearby cores, and the NUMA penalty is small compared to the cost of copying. The compiler should measure before adding NUMA-aware complexity.

Backpressure is the final synchronization concern. If a shared arena's lock is contended, workers may block. A worker that cannot acquire the lock can fall back to its thread-local arena and transfer the result later. This keeps the hot path moving. The shared arena can also batch transfers: instead of locking for each small object, the worker accumulates objects in a thread-local buffer and transfers the whole buffer when it is full. This amortizes the lock and reduces contention. The buffer itself is a small thread-local arena. The design should allow multiple levels of buffering: thread-local transient, thread-local transfer buffer, shared domain. Each level has a different lifetime and synchronization cost.

## Diagnostics, debug info, and observability

Diagnostics are a cross-thread concern that is often underestimated. A worker may detect an error deep in a pass and want to report it with a source location, a message, and possibly notes and suggestions. Formatting the diagnostic may allocate temporary strings and data structures. If those are allocated in the worker's thread-local arena, they must be copied into a shared diagnostic record before the arena resets. The shared record should be self-contained: it owns its strings and structured data. It can be allocated in a shared diagnostic arena or in a queue-owned buffer. The worker formats into a thread-local scratch buffer, then copies the final bytes into the shared record. The scratch buffer is reset after each diagnostic or after a batch. This keeps the hot formatting path lock-free and the shared path simple.

Diagnostic ordering is a determinism requirement. If workers emit diagnostics as they find them, the order depends on scheduling. The compiler should collect diagnostics per thread and sort them by source location, severity, and a stable sequence number before printing. The sequence number can be assigned from the source location or from a deterministic counter that is independent of thread scheduling. If diagnostics are emitted immediately for interactive use, the compiler can still buffer them per thread and flush in a deterministic order at the end of the compilation. For a long-running server, a sequence number can be used to order diagnostics across threads. The key is to avoid using wall-clock time or thread ID as the primary sort key.

Debug information has similar requirements. DWARF and PDB formats contain type tables, line tables, and symbol tables. These must be deterministic and stable across runs. If debug info is built from thread-local arenas, the merge order must be deterministic. A common pattern is to build per-function debug info in a thread-local arena, then transfer it to a module debug arena in function ID order. The module debug arena is then serialized in a single-threaded pass. Type tables are often shared across functions, so they may be interned in a global read-only arena. The intern table must be deterministic: the order of type entries should be based on a stable hash or a first-seen order that is itself deterministic. If first-seen order depends on thread scheduling, the debug info will vary. The compiler should sort type entries by a stable key before emission, or assign type IDs from a deterministic traversal of the module.

Observability is the ability to see where memory goes. A thread-local arena design should be instrumented from the start. Each arena can track bytes allocated, bytes retained after reset, number of blocks, and block waste. These counters are thread-local and updated without atomics on the hot path. When an arena is reset or transferred, its counters can be added to a global atomic accumulator or to a per-thread accumulator that is merged at the end. The compiler can then report memory usage per phase, per thread, and per arena. This data is invaluable for tuning reset boundaries and block sizes. It also helps detect leaks: if an arena's retained bytes grow without bound, the reset boundary is too wide or the arena is not being reset.

Debugging use-after-reset is a common challenge. In a release build, a use-after-reset may read stale data or corrupt the arena's metadata. In a debug build, the arena can poison memory on reset with a known pattern, such as 0xDEADBEEF. A read of poisoned memory may not crash immediately, but it can be detected by a memory checker or by an assertion on the pattern. A stronger approach is to use generation counters. Each allocation returns a handle that includes the arena's generation number. The handle is dereferenced through a function that checks the generation. If the arena has been reset, the generation has advanced, and the dereference fails. This adds overhead, so it is only enabled in debug builds. The handle can be a small struct with a pointer and a generation, or an index into a table. The table approach is safer because it does not expose raw pointers, but it adds indirection. For compiler internal data structures, raw pointers with debug checks are often acceptable.

Crash dumps and post-mortem debugging benefit from an arena registry. In debug builds, every arena can register itself in a global list with its owner thread, state, and allocation site. If the compiler crashes, the registry can be dumped to show which arenas were active and which thread owned them. This makes cross-thread lifetime violations easier to diagnose. The registry itself must be thread-safe, but it is only updated on arena creation and destruction, not on every allocation. In release builds, the registry can be disabled or kept minimal. The cost is small compared to the debugging benefit.

Logging from inside the allocator is a bad idea. It can allocate, which recurses, and it can introduce locks. Instead, the allocator can write to a per-thread lock-free ring buffer. A separate thread drains the buffers and writes them to a log. The ring buffer entries are fixed-size and contain only numeric data, such as arena ID, event type, and size. This keeps the hot path free of locks and allocations. The log can be enabled at runtime for debugging without recompiling. The same mechanism can be used for tracing allocation patterns and for collecting performance counters.

## Failure modes and testing strategies

A thread-local arena design has a small set of failure modes that should be tested explicitly. The first is use-after-reset. A test allocates an object, resets the arena, and then dereferences the object. In a debug build with generation counters, this should fail with a clear error. In a release build, it may silently read stale data. The test should be run under address sanitizer with poisoned memory to catch it. The second is cross-thread dereference. A test allocates an object on thread A, passes a raw pointer to thread B, and dereferences it on thread B. In a debug build with owner checks, this should fail. In a release build, it may work by accident if the memory is still mapped, which is why the test must be run with checks enabled. The third is double transfer. A test transfers an arena handle twice and checks that the second transfer is rejected. The fourth is partial transfer. A test transfers an arena while another thread is still allocating from it. This is a data race, and thread sanitizer should catch it. The fifth is leaked arena. A test creates an arena, never resets or transfers it, and checks that the arena registry reports a leak at shutdown.

Determinism tests are equally important. The compiler should be run with different thread counts, such as 1, 2, 4, and 8, and the outputs should be compared byte for byte. This includes object files, debug info, and diagnostics. If the outputs differ, the nondeterminism must be found and fixed. A deterministic allocator can help: it fills freed memory with a pattern and uses a fixed seed for any randomized behavior. The test should also vary the scheduling by inserting random delays or by using a deterministic scheduler that explores different interleavings. For a compiler, the most common nondeterminism sources are hash map iteration order, address-based sorting, and diagnostic emission order. These can be tested by compiling a large project and comparing the output across runs.

Model checking can verify the arena ownership protocol. The state machine for arena handles can be modeled in a formal specification language, such as TLA+ or Alloy. The model can check that no handle is used after transfer, that no arena is reset while a frozen reference exists, and that no two threads own the same arena at the same time. This is especially valuable for the transfer protocol, which is easy to get wrong. The model does not need to cover the entire compiler, only the arena lifecycle. Once the protocol is verified, the implementation can be tested against the model with a small test harness.

Stress tests should run the compiler on a large codebase with many threads for an extended period. The test should monitor memory usage, CPU utilization, and allocation rates. If memory grows without bound, there is a leak or a reset boundary that is too wide. If CPU utilization drops, there may be lock contention or false sharing. The stress test should also run with thread sanitizer and address sanitizer enabled. These tools slow down execution but catch races and use-after-free errors that are otherwise invisible. A continuous integration job can run a smaller stress test on every commit and a larger one nightly.

Fuzzing can explore allocation patterns. A fuzzer can generate random sequences of arena creation, allocation, transfer, freeze, reset, and destruction. It can check invariants after each operation, such as the arena state and the owner thread. This is a good way to find edge cases in the state machine. The fuzzer can also generate random cross-thread operations to test the synchronization primitives. The fuzzer should be run under sanitizers to catch memory errors. For a compiler, fuzzing the arena API is more targeted than fuzzing the whole compiler, because it isolates the memory model.

Finally, the compiler should have a way to disable thread-local arenas and fall back to a global allocator. This is useful for debugging and for comparing performance. If a bug appears only with thread-local arenas, the fallback can help isolate it. The fallback can be a compile-time flag or a runtime option. It should not change the compiler's output, only its performance and memory usage. This provides a safety net and a baseline for measuring the benefits of the arena design.

## Arena-aware data structures and APIs

A thread-local arena is only as useful as the data structures that allocate from it. If the compiler's containers default to a global heap, the arena becomes an optional fast path that few call sites use. The design should make the arena a first-class parameter in the internal API. A vector, hash map, or worklist should be constructible with an arena reference and should allocate all of its storage from that arena. The container itself may live on the stack or in a parent arena, but its backing buffer comes from the arena. This is a small change in languages with allocator parameters, and a larger change in languages where allocation is hidden behind constructors.

The first rule is to avoid hidden allocation. A function that returns a `std::vector` or a language-level list may allocate without an explicit arena. In a compiler, such functions are common in early prototypes and become performance problems later. The arena-aware API should return a view or a handle into arena-owned storage instead of an owning container. A parsed token stream can be a slice into an arena-owned buffer. A list of diagnostics can be a linked list of arena-allocated nodes with a shared tail pointer. A hash map can be an open-addressed table allocated from the arena, with keys and values stored inline or in the same arena. The container's destructor becomes a no-op; the arena reset reclaims everything.

The second rule is to separate logical ownership from physical allocation. A module may own a function, but the function's IR nodes may be allocated in a module arena or transferred from a worker arena. The module's API should not expose raw pointers that imply a specific arena. Instead, it should use handles or references with a lifetime parameter. In Rust, this is a lifetime; in C++, it is a type tag or a debug-only owner check. The goal is to make it difficult to store a thread-local pointer in a module-owned structure without an explicit copy or transfer. The type system does not need to be sound in the formal sense; it needs to make the common mistake visible in code review and detectable in tests.

The third rule is to design for deterministic iteration. Arena allocation order is not a stable iteration order. A hash map that iterates in bucket order will produce different orders depending on insertion order, which depends on thread scheduling. The container should either maintain an insertion-order list alongside the hash table or provide a `sorted_keys` method that returns a deterministic order. For symbol tables, insertion order can be made deterministic by processing declarations in source order, even if the work is parallelized by function. For type tables, a stable hash or a first-seen order based on a deterministic traversal is better than raw bucket order. The cost of sorting is usually small, and the determinism benefit is large.

The fourth rule is to make deallocation explicit but rare. An arena does not free individual objects, so a container that removes elements cannot reclaim their memory. This is acceptable for append-only structures such as token streams, IR node lists, and diagnostic queues. It is not acceptable for a worklist that grows and shrinks many times. For those, the compiler can use a free list within the arena: removed nodes are pushed onto a free list, and allocation pops from the free list before bumping the pointer. The free list is thread-local, so it needs no synchronization. This gives the arena some of the flexibility of a general heap without per-object metadata. The free list can be intrusive: the node's first word stores the next free pointer when the node is not in use. This requires the node to be at least pointer-sized, which is usually true for compiler IR nodes.

The fifth rule is to keep cross-arena references explicit. A node in a thread-local arena may reference a node in a module arena. That is safe if the module arena outlives the thread-local arena. The reverse is not safe. The API should distinguish `LocalRef<T>` from `SharedRef<T>` or use a lifetime parameter that prevents a shared structure from holding a local reference. In C++, a debug-only `ArenaRef<T>` can store an arena ID and check it on dereference. In release builds, the check is compiled out, but the type name still documents the intent. This is a pragmatic middle ground between full region typing and raw pointers.

## Reset scheduling and phase boundaries

The choice of reset boundary is the main lever for memory retention. A thread-local arena that is never reset is a memory leak with extra steps. A thread-local arena that is reset too often invalidates objects that are still needed. The compiler should define a small set of lifetimes and map each phase to one of them. A file-local lifetime covers parsing and syntax tree construction. A module-local lifetime covers name resolution and type checking for a module. A pass-local lifetime covers a single optimization pass. A task-local lifetime covers a single work item, such as optimizing one function. The arena for a task is reset when the task completes, before the worker picks up the next task. This is the narrowest useful boundary and the easiest to reason about.

Nested arenas make this practical. A worker has a task-local arena for transient allocations. When the task needs to produce a result that outlives the task, it transfers a sub-arena or copies the result into a module arena. The task-local arena is reset immediately, so the worker's memory footprint stays bounded. The module arena is owned by the coordinator or by a module builder. It is reset when the module is fully compiled and its output is emitted. If the module is part of an incremental cache, the module arena may be frozen and retained. The compiler should track which arenas are frozen and which are resettable. A frozen arena is not a leak; it is a cache entry. A resettable arena that is not reset is a leak.

Parallel loops need special attention. A parallel loop over functions may create a task-local arena per iteration. If the loop body allocates a large temporary structure, the arena grows to the size of the largest iteration. After the loop, the arena is reset. This is fine if the loop is short-lived. If the loop runs for a long time, the arena may retain memory for temporaries that died early in each iteration. The compiler can reset the arena at the end of each iteration, but that invalidates any result that must survive. The result should be copied or transferred before the reset. This is a classic trade-off: narrow resets reduce retention but increase handoff frequency. The compiler should choose based on the size of the result relative to the temporary working set.

Adaptive reset is possible but should be used carefully. The arena can track its high-water mark and reset when it exceeds a threshold, provided no live objects are in the arena. Without escape analysis, the compiler cannot know whether live objects exist. A conservative approach is to reset only at explicit phase boundaries, where the compiler knows that no thread-local pointers are live. This is simpler and safer. The phase boundary is a synchronization point: all workers finish the phase, then reset their arenas. The barrier ensures that no worker is still using its arena. The cost is a barrier per phase, which is usually negligible compared to the phase's work.

## Hybrid allocation and escape hatches

No compiler can put all data in thread-local arenas. Some data is inherently shared and long-lived. The design should provide escape hatches that are explicit and measurable. A `promote` operation copies an object from a thread-local arena into a shared arena and returns a shared reference. A `freeze` operation converts a thread-local arena into a read-only shared arena. A `global_alloc` operation allocates directly in a shared arena for data that is known to be shared from the start, such as interned strings or type descriptors. These operations should be rare and should be counted. If `promote` is called on every object, the arena design is not providing value; the compiler is just using a slower global heap.

The most common escape hatch is interning. Strings, identifiers, and type names are shared across threads. A thread-local arena can hold a temporary string, but the interned string must live in a global read-only arena. The intern operation hashes the string, looks it up in a sharded table, and returns a shared reference. The temporary string is then discarded when the thread-local arena resets. The intern table's memory is long-lived and should be measured separately. If interning dominates memory, the compiler may need a more compact representation, such as a string pool with offsets, or a deduplication pass that runs before interning.

Another escape hatch is the incremental cache. If the compiler supports incremental compilation, it must persist type information, symbol tables, and dependency graphs across builds. This data cannot live in a thread-local arena that is reset at the end of the build. It must be serialized into a cache file or stored in a long-lived arena. A common pattern is to build the cache entry in a thread-local arena, then serialize it to a byte buffer and write it to disk. The serialization copies the data, but it also decouples the cache from the arena's lifetime. On the next build, the cache is deserialized into a shared arena. This is slower than keeping the data in memory, but it is robust and avoids cross-build lifetime issues. If the compiler keeps an in-memory cache, it should use a dedicated cache arena with reference counting or epoch-based reclamation.

Diagnostics are a third escape hatch. A diagnostic must be rendered after the worker that produced it has moved on. The worker formats the diagnostic into a thread-local scratch buffer, then copies the final bytes into a shared diagnostic record. The shared record is allocated in a diagnostic arena that is reset after all diagnostics are printed. If diagnostics are streamed, the record is owned by the output queue and freed by the consumer. The formatting scratch buffer is reset after each diagnostic or after a batch. This keeps the hot formatting path lock-free and the shared path simple. The copy is proportional to the size of the diagnostic, which is small compared to the compiler's other allocations.

## Migration path from a global heap

Adopting thread-local arenas in an existing compiler is an incremental process. The first step is to measure allocation. Instrument the global allocator to record bytes allocated per phase and per thread. Identify the phases with the highest allocation rate and the shortest object lifetimes. Parsing, syntax tree construction, and optimization passes are usually good candidates. The second step is to introduce an arena type and a small set of arena-aware containers. Use them in one phase, such as parsing a single file. Keep the global allocator as a fallback. Measure the performance and memory impact. The third step is to enforce the lifetime boundary. Add debug checks that detect cross-thread dereferences and use-after-reset. Run the test suite with these checks enabled. Fix the violations by copying, transferring, or promoting data. The fourth step is to expand to more phases. Each phase should have an explicit arena lifetime and a clear handoff policy. The fifth step is to tune reset boundaries and block sizes based on the metrics collected in the first step. The sixth step is to remove the fallback for hot paths, but keep it as a debugging option. The migration should not change the compiler's output. Determinism tests should run at every step. If the output changes, the nondeterminism must be fixed before proceeding. The end state is a compiler where the hot allocation path is a thread-local pointer bump, shared data is explicitly promoted or frozen, and the global heap is used only for long-lived or genuinely shared structures. The remaining design question is how to expose these boundaries to compiler developers without making the common case verbose, and that is where API ergonomics and tooling become as important as the allocator itself.
