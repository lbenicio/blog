There is a moment in most systems engineers' careers when a build that has worked for months suddenly fails with a screen of `undefined reference to ...` errors, or a binary that links cleanly crashes inside `dlopen`, or a program that was fast as a static build becomes measurably slower after someone switches it to shared libraries. All three events are the linker and the loader talking to you. They are among the least studied and most consequential stages of the toolchain, and they are the point at which the abstract world of symbols and sections becomes concrete addresses in a process's address space.

The compiler's job is local: it translates one translation unit at a time and must assume that anything it cannot see might be defined somewhere else, in a file it will never read. The linker's job is global: it sees every object file, every archive member, and every shared library at once, and it is the first component that can answer questions like "where does this symbol actually live?" and "is this call direct or indirect?" The dynamic loader then answers a subset of those questions again at process startup, in a context where addresses are not known until the kernel has chosen a base address.

This article is about that pipeline: what a relocatable object file contains, how the linker resolves symbols, what relocations mean, why position-independent code needs a global offset table, and what all of it costs at runtime. The goal is not ELF trivia for its own sake. It is to make you able to reason about why link order matters, why `-fPIC` is not merely "a bit slower," why symbol interposition is a language-level hazard rather than a curiosity, and why the startup time of a process with a hundred shared-library dependencies is dominated by work that has nothing to do with your code.

## The linker's contract: a two-level model

A relocatable object file is an incomplete program. It contains machine code and initialized data, but it also contains holes: places where the compiler needed an address it could not compute. The compiler knows the offset of a function within its own section, and it knows the relative distance between two labels in the same translation unit, but it does not know where the section will land, whether a symbol will be defined by another object file, or whether a symbol will be interposed at runtime. So it emits a *relocation*: a record saying "at offset X in this section, insert a value computed from symbol S according to rule R."

The static linker — `ld`, `ld.lld`, `ld.gold`, or `mold` — consumes relocatable objects and static archives and produces either an executable or a shared object. Its work has three parts, and keeping them separate matters because error messages come from different ones:

1. **Symbol resolution.** Build a global symbol table from all inputs, decide which definition of each symbol wins, and report an error if a non-weak symbol is referenced but never defined, or defined more than once.
2. **Layout.** Assign a virtual address to every output section, and therefore to every symbol, subject to alignment constraints, the target's page size, and the linker script.
3. **Relocation.** Walk every relocation in every input and patch the corresponding bytes in the output, now that addresses are known. This is where most of the linker's CPU time goes, and it is embarrassingly parallel — which is why `lld` and `mold` are dramatically faster than the traditional `ld`.

Notice what is *not* on that list: parsing C++, template instantiation, or optimization. The linker is not a compiler in the usual sense. But it is the last program that gets to rewrite your machine code, and modern toolchains have pushed a great deal of work back into it. Link-time optimization hands the linker compiler IR rather than machine code, so the "linker" becomes a driver for a whole-program compilation pass. Identical code folding, section garbage collection, and relocation relaxation all rewrite the output in ways the compiler never anticipated.

The distinction between the *static* linker and the *dynamic* loader is the source of much confusion, so it is worth stating plainly. The static linker runs at build time and produces a file. The dynamic loader — `ld.so` on glibc systems, `ld-musl-*.so.1` on musl — runs at process startup on the user's machine, maps shared objects into the address space, and performs the relocations that could not be resolved at build time. Both do relocation processing. The difference is that the static linker knows every address in advance except for the base address of a position-independent executable, while the loader must discover the layout of the process as it goes.

## Two views of an ELF file

An ELF file is described by two independent tables, and conflating them is the most common source of confusion when reading `readelf` output.

The **section header table** is the link-time view. It describes named sections: `.text` for executable code, `.rodata` for read-only data, `.data` for initialized writable data, `.bss` for zero-initialized writable data, `.symtab` and `.strtab` for the symbol table and its string pool, `.rela.text` and `.rela.data` for relocations, and a long tail of toolchain-specific sections. The linker reads these, merges input sections with the same name into output sections, and applies relocations between them.

The **program header table** is the load-time view. Each entry describes a *segment*: a contiguous range of the file that should be mapped into memory with particular permissions. The kernel reads only this table when it executes the file. A typical dynamically linked executable has segments for the ELF header and program headers, the executable code, the read-only data, the writable data, the dynamic linking information, and a `PT_INTERP` segment naming the dynamic loader to run.

The mapping between the two views is the linker script's job. Input sections are placed into output sections, and output sections are assigned to segments. The default script on a GNU/Linux x86-64 system produces segments whose permissions follow the classic `R-X` / `R--` / `RW-` split, which is why `.rodata` sometimes shares a segment with `.text` and sometimes gets its own (`-z separate-code` changes this, at the cost of an extra page of address space).

Two details matter operationally. First, the section header table is optional at runtime. `strip` removes it, and a stripped binary still runs because the kernel never looks at it — but debuggers and disassemblers do, which is why stripping makes `gdb` less useful without making it useless. Second, the loader requires that each `PT_LOAD` segment satisfy a congruence condition: virtual address and file offset must be congruent modulo the page size. That constraint exists so `mmap` can map a page-aligned region of the file directly, without a copy, and it is why the linker inserts padding between segments.

One more structural point: `.bss` occupies no space in the file. It is a `SHT_NOBITS` section, meaning the section header declares a size but the file contains no bytes for it. The loader maps anonymous zero pages instead. This is why a program with a large global array of zeros is small on disk and large in memory, and why the size of a static array has no relationship to the size of the executable.

## Symbols: binding, visibility, and the rules of resolution

A symbol table entry has a name, a value (an offset within its section, or an absolute address), a size, a type, and — most importantly for resolution — a *binding* and a *visibility*.

The binding is one of `STB_LOCAL`, `STB_GLOBAL`, or `STB_WEAK`. Local symbols are visible only within the object file that defines them; they are what you get for `static` functions and variables, and for compiler-generated labels. Global symbols are visible to the whole link. Weak symbols are the interesting case, because they carry two distinct meanings that are often conflated:

- A **weak definition** can be overridden by a strong definition elsewhere. This is how a library provides a default implementation that an application can replace.
- A **weak reference** — an undefined weak symbol — does not cause a link error if it is never defined. Instead it resolves to zero. This is how optional hooks and feature probes are implemented, and it is also a common source of null-pointer crashes when the code forgets to check.

Visibility is a separate axis, and it determines whether the dynamic loader has extra work to do. The default is `STV_DEFAULT`, meaning the symbol is exported from a shared object and participates in interposition. `STV_HIDDEN` means the symbol is not exported at all and cannot be referenced from outside the object being built. `STV_PROTECTED` means the symbol is exported but references from within the defining shared object bind to the local definition rather than going through global lookup. `STV_INTERNAL` is similar to hidden and rarely used.

The practical consequence: a shared library built without `-fvisibility=hidden` exports every non-static function and global variable, including hundreds of internal helpers that were never meant to be part of its interface. Every one of those exports is a symbol the dynamic loader must hash, insert into its lookup tables, and consider during relocation. Exporting less is almost always better — it reduces load time, shrinks the dynamic symbol table, and eliminates a class of accidental interposition bugs. The standard advice for library authors is to compile with `-fvisibility=hidden` and annotate the intended public API explicitly.

Resolution itself follows a rule that surprises people coming from other languages: **the first definition in the lookup scope wins**. For a static link, the linker processes inputs in command-line order, and an archive is searched only for symbols that are undefined *at the moment the archive is encountered*. This is why `-lfoo -lbar` and `-lbar -lfoo` can produce different results, and why a library that depends on another must appear before it. `--start-group` and `--end-group` cause the linker to rescan the enclosed archives until no new symbols are resolved — a blunt but effective fix for circular dependencies.

For a dynamic link, the scope is the main executable followed by its dependencies in breadth-first order, followed by objects loaded with `dlopen`. Because the main executable comes first, it can interpose on any symbol defined in any shared library it links against. That behavior is essential for `LD_PRELOAD` and malloc replacement, and catastrophic when it happens by accident: a library that defines a function with a common name and does not hide it is silently participating in a namespace shared with every other library in the process.

Multiple strong definitions of the same symbol in different object files are an error — the One Definition Rule expressed at the linker level. But C++ requires the opposite for inline functions, templates, and virtual tables: the same definition legitimately appears in every translation unit that uses it. The toolchain reconciles this with **COMDAT groups**. The compiler emits each such definition in its own section, marked as part of a group with a signature, and the linker keeps one copy and discards the rest. This is also why an inline function whose definition changed between builds can produce baffling behavior: if two libraries were compiled against different versions of a header, the linker keeps whichever copy it saw first.

## Relocations: the linker's instruction set

A relocation entry is a tuple: an offset, a type, a symbol index, and an addend. The type is architecture-specific, and its meaning is defined by the platform's ABI document rather than by any language standard. On x86-64, the small set that appears in ordinary C and C++ code is roughly this:

- `R_X86_64_64` — write the absolute 64-bit address `S + A`.
- `R_X86_64_PC32` — write the 32-bit PC-relative displacement `S + A - P`, where `P` is the address of the relocated field. This is what a RIP-relative load, or a direct `call` to a known local symbol, produces.
- `R_X86_64_PLT32` — the same computation, with the additional meaning that the target may be a PLT entry. Modern compilers emit this for essentially every function call, and the linker relaxes it to a direct call when the target turns out to be local and non-preemptible.
- `R_X86_64_GOTPCREL` and `R_X86_64_GOTPCRELX` — write a displacement to the GOT slot for the symbol rather than to the symbol itself. The `X` variant is relaxable: if the linker can prove the symbol is local, it can rewrite the instruction to a direct `lea` or `mov` and discard the GOT slot entirely.
- `R_X86_64_RELATIVE` — write the load base plus an addend. This is how a pointer in a shared object's initialized data is represented: the value is known relative to the base but not absolutely.
- `R_X86_64_GLOB_DAT` and `R_X86_64_JUMP_SLOT` — fill a GOT slot or a PLT slot with the address of a symbol, resolved by the dynamic loader.
- `R_X86_64_COPY` — copy the initial value of a data object from a shared library into space allocated in the executable. This is the copy relocation, and it exists only to support non-PIC executables.
- `R_X86_64_TPOFF64` and relatives — compute offsets into thread-local storage.

Two formats exist for the relocation tables themselves. `SHT_REL` stores the addend implicitly, in the bytes being relocated; `SHT_RELA` stores it explicitly in the entry. x86-64 uses `RELA`, which is why `readelf -r` shows an addend column on that platform and not on i386.

The important observation is that *which* relocations appear in your object file is determined entirely by how the compiler was told to model each symbol — and that decision is what `-fPIC`, `-fPIE`, `-fno-semantic-interposition`, and visibility attributes control. A call to a function the compiler believes is local becomes a direct `call` with a `PLT32` relocation that the linker resolves to a relative displacement. The same call, when the compiler believes the function might be interposed, becomes a load from the GOT followed by an indirect call. The source code is identical; the machine code is not.

## The Global Offset Table and the Procedure Linkage Table

The GOT and PLT are the two data structures that make position-independent code work. They are not language features; they are ABI conventions, and their layout is specified in the x86-64 psABI. Understanding them is the difference between treating `-fPIC` as a magic flag and knowing exactly which instructions the compiler emitted and why.

The **Global Offset Table** is an array of addresses stored in the writable data segment. In a shared object, the GOT is the only place where absolute addresses of external symbols are kept. Code that needs the address of a global variable or function loads it from the GOT with a PC-relative displacement. On x86-64, that looks like `mov foo@GOTPCREL(%rip), %rax`, which is a single instruction that reads the GOT slot and puts the address in a register. On i386, the same operation requires a GOT pointer in a register (usually `%ebx`), which the function prologue must set up, consuming a register for the entire function body.

The first three GOT entries are reserved. `GOT[0]` holds the address of the `_DYNAMIC` section, which the dynamic loader uses to find the relocation tables. `GOT[1]` holds a pointer to the `link_map` structure for the current object, which identifies it in the loader's internal data structures. `GOT[2]` holds the address of `_dl_runtime_resolve`, the loader's trampoline for lazy symbol resolution. Everything after that is available for symbol addresses.

The **Procedure Linkage Table** is a parallel array of executable stubs, one per externally called function. Each PLT entry is a small code sequence. In the lazy-binding case, the first entry (PLT0) is special: it pushes `GOT[1]` and jumps to `GOT[2]`. Every other entry begins with an indirect jump through its corresponding GOT slot, followed by a `push` of the symbol's index and a jump to PLT0. When the program first calls an external function, the GOT slot still points to the instruction after the indirect jump — that is, to the `push` instruction. The jump therefore falls through to the push and the jump to PLT0, which invokes the resolver. The resolver looks up the symbol, writes its real address into the GOT slot, and jumps to it. Subsequent calls to the same function execute the indirect jump and go straight to the target, never touching the resolver again.

This design is why lazy binding is possible: the GOT slot is initially filled with a pointer back into the PLT, so the first call is a trap that triggers resolution. The cost is that the first call to each function is much more expensive than subsequent calls, and the PLT stubs and GOT entries consume memory even for functions that are never called.

Immediate binding, enabled by `-z now` or `LD_BIND_NOW=1`, resolves all `R_X86_64_JUMP_SLOT` relocations at load time. The GOT slots are filled with the real addresses before `main` runs, and the PLT stubs are never used as trampolines. This is required for full RELRO (`-z relro -z now`), which makes the GOT read-only after relocation, preventing a class of exploits that overwrite GOT entries to hijack control flow. The trade-off is startup time: the loader must perform all symbol lookups eagerly, even for functions that are never called. For long-running processes, this is usually a win; for short-lived command-line tools, it can be a loss.

A related optimization is `-fno-plt`. Instead of emitting a call to a PLT stub, the compiler emits an indirect call through the GOT: `call *foo@GOTPCREL(%rip)`. This eliminates the PLT stub entirely, saving a jump and a potential instruction-cache miss. But it changes the relocation type from `R_X86_64_PLT32` to `R_X86_64_GLOB_DAT`, which the loader resolves eagerly. In other words, `-fno-plt` trades lazy binding for a shorter call sequence. Whether that is faster depends on the workload: if the function is called often, the saved jump matters; if it is called rarely, eager resolution wastes startup time. Modern distributions increasingly build with `-fno-plt` because the call overhead is more predictable and the security posture is better.

## Position-Independent Code: The Indirection Tax

Position-independent code exists because shared libraries must be loadable at any virtual address. The dynamic loader chooses a base address for each library, and the code must work regardless of where it lands. On x86-64, the hardware provides PC-relative addressing, which makes data access cheap: a load from a global variable can be a single `mov` with a RIP-relative displacement. But function calls to external symbols are different. The compiler cannot know the distance to a function in another shared library, and even if it did, the symbol might be interposed. So it emits a call through the PLT or GOT.

The indirection tax is the sum of all the extra work that PIC requires. It has several components:

- **Extra instructions.** A direct call is a single `call` instruction with a 32-bit relative displacement. A PLT call is a `call` to the stub, then a `jmp` through the GOT. That is two branches instead of one. A GOT-based data access is a load from the GOT followed by a load from the address, whereas a direct access is a single load with an absolute or RIP-relative address. On i386, the GOT pointer consumes a register and requires prologue/epilogue instructions to save and restore it.
- **Memory traffic.** The GOT is in the data segment, which means every indirect call or data access touches a cache line that is separate from the code. In a tight loop that calls an external function, the GOT entry may be in L1, but it still competes for cache space with the actual data. The PLT stub itself is code, so it may cause an instruction-cache miss on first call, but after that it is usually cached.
- **Lost optimizations.** The compiler cannot inline a function that might be interposed, cannot constant-fold its address, and cannot assume that two calls to the same function go to the same place. This is the most significant cost, and it is not measured in instructions but in missed opportunities. `-fno-semantic-interposition` tells the compiler that the symbol will not be interposed, allowing it to inline and optimize as if the function were local. `-Bsymbolic` tells the linker to bind references within a shared object to the local definition, which eliminates GOT/PLT indirection for those calls. `-fvisibility=hidden` reduces the number of exported symbols, which both shrinks the dynamic symbol table and allows the compiler to treat more symbols as local.
- **Code size.** Each PLT entry is 16 bytes on x86-64, and each GOT entry is 8 bytes. A library with a thousand external calls has 16 KB of PLT stubs and 8 KB of GOT entries, plus the relocation tables that describe them. This is not huge, but it adds up across a process with hundreds of libraries.

The cost of PIC is not uniform. On x86-64, RIP-relative addressing makes data access nearly free, so the main cost is function calls. On i386, the GOT pointer in `%ebx` is a real register pressure problem, which is one reason why x86-64 code is often faster even at the same clock speed. On ARM, the situation is different again: ARM has PC-relative addressing but a limited range, so it uses literal pools and GOT entries in a different way.

It is worth noting that PIE executables pay the same tax as shared libraries. A PIE executable is essentially a shared object with an entry point, and it uses the same GOT/PLT machinery. This is why `-fPIE` and `-fPIC` produce similar code. The benefit of PIE is ASLR, which makes exploits harder; the cost is the indirection. Static PIE (`-static-pie`) removes the dynamic loader but keeps the position independence, so it still pays the GOT/PLT cost but avoids the loader's startup work. For programs that need ASLR but not shared libraries, static PIE is an attractive compromise.

## What the Dynamic Loader Does at Startup

When the kernel executes a dynamically linked program, it reads the `PT_INTERP` segment, which names the dynamic loader — typically `/lib64/ld-linux-x86-64.so.2`. The kernel maps the loader and the executable, then transfers control to the loader's entry point. The loader is itself a shared object, so it must relocate itself before it can do anything else. This is a delicate bootstrap: the loader's own relocations are processed by code that has already been relocated, using a minimal set of functions that avoid external dependencies.

Once the loader is running, it performs a sequence of steps that are largely invisible to the programmer but dominate startup time for programs with many dependencies:

1. **Load the main executable's dependencies.** The loader reads the `DT_NEEDED` entries from the executable's dynamic section. Each entry names a shared library. The loader searches for each library in a defined order: `DT_RPATH` (deprecated), `LD_LIBRARY_PATH`, `DT_RUNPATH`, the `ld.so.cache`, and finally the default system paths (`/lib`, `/usr/lib`). The cache is a binary file generated by `ldconfig` that maps library names to paths, avoiding a filesystem search. If a library is not found, the loader aborts with an error like `error while loading shared libraries: libfoo.so.1: cannot open shared object file`.
2. **Map each library.** For each library, the loader opens the file, reads its program headers, and maps the `PT_LOAD` segments into the address space with the appropriate permissions. It also maps the library's dynamic section and relocation tables. This step involves `mmap` calls and page faults, which can be expensive if the library is not already in the page cache.
3. **Build the link map.** The loader maintains a linked list of loaded objects, each represented by a `link_map` structure. The order of this list matters: it defines the global symbol lookup scope. The main executable is first, followed by its dependencies in the order they appear in `DT_NEEDED`, breadth-first. Libraries loaded later with `dlopen` are appended to the list (or inserted at the front if `RTLD_GLOBAL` is used? Actually `dlopen` with `RTLD_GLOBAL` adds to the global scope, but the order is still after the initial dependencies).
4. **Resolve symbols.** For each loaded object, the loader processes its relocation tables. Relocations that reference local symbols (`R_X86_64_RELATIVE`) are resolved immediately by adding the load base. Relocations that reference global symbols (`R_X86_64_GLOB_DAT`, `R_X86_64_JUMP_SLOT`) require a symbol lookup. The loader searches the global scope — the link map — for the symbol name. It uses a hash table to speed this up. The SysV hash table (`.hash`) is a simple hash with chaining. The GNU hash table (`.gnu.hash`) uses a Bloom filter to quickly reject lookups for symbols that are not present, which is significantly faster for large libraries. Most modern distributions use `--hash-style=gnu` or `--hash-style=both`.
5. **Run initializers.** After all relocations are processed, the loader calls the initialization functions of each library in dependency order. These are the functions registered with `__attribute__((constructor))` or the `.init_array` section. In C++, this includes static constructors and dynamic initialization of global objects. The order is important: a library's initializers run after its dependencies' initializers.

The cost of this process is dominated by symbol resolution and relocation processing. `LD_DEBUG=statistics` prints a summary of time spent in each phase. On a typical Linux system, a program linked against 50 shared libraries may spend 5–20 ms in the loader, with the majority of that time in symbol lookup and relocation. For a program that runs for hours, this is negligible; for a command-line tool that runs for milliseconds, it can be the difference between a snappy experience and a noticeable delay.

Lazy binding defers the cost of `R_X86_64_JUMP_SLOT` relocations until the first call to each function. This is why a program can start quickly even if it links against many libraries: the loader only resolves the data relocations eagerly, and function relocations are resolved on demand. The downside is that the first call to each function is slower, and the resolver itself must be thread-safe, which adds locking overhead in multithreaded programs. `LD_BIND_NOW=1` or `-z now` disables lazy binding, forcing all relocations to be processed at startup. This is often used in security-sensitive contexts because it allows full RELRO.

`dlopen` is a different story. When a program calls `dlopen`, the loader must load a new library, resolve its symbols against the global scope, and run its initializers. This is much more expensive than loading a library at startup because the loader cannot batch the work. `RTLD_LAZY` defers function relocations, but data relocations are always eager. `RTLD_NOW` forces all relocations to be resolved immediately. `RTLD_GLOBAL` adds the library's symbols to the global scope, which can cause interposition and slow down future symbol lookups. `RTLD_LOCAL` keeps the symbols private, which is usually the right choice unless the library is a plugin that needs to export symbols to other plugins.

## The Real Cost of Dynamic Linking

The cost of dynamic linking is not a single number. It is a combination of startup time, memory overhead, runtime indirection, and lost optimization opportunities. Each of these can be measured, and each has a different profile depending on the workload.

- **Startup time** is the most visible cost. A process that links against many shared libraries must map them, resolve symbols, and run initializers. On a cold page cache, this also involves reading the libraries from disk. The loader's work is proportional to the number of symbols and relocations, not the amount of code executed. A program that uses only a few functions from a large library still pays for the library's entire dynamic symbol table and relocation tables.
- **Memory overhead** includes the GOT, PLT, dynamic symbol tables, hash tables, and `link_map` structures. For a large library, these can add up to hundreds of kilobytes. The GOT and PLT are per-process, so they are not shared between processes, even though the library's code pages are shared. This is a form of memory duplication that static linking avoids.
- **Runtime indirection** is the cost of the extra jumps and loads in PIC code. It is small per call — a few cycles — but it can be significant in tight loops or in code that makes many cross-library calls. The indirect branch also puts pressure on the branch predictor, which may mispredict if the target changes.
- **Lost optimizations** are the hardest to quantify. When a function cannot be inlined, the compiler cannot specialize it, cannot eliminate redundant work, and cannot propagate constants. This can lead to code that is several times slower than a statically linked equivalent. `-fno-semantic-interposition`, `-Bsymbolic`, and visibility controls are the tools for recovering some of this performance, but they require the programmer to understand the symbol binding rules.

Static linking eliminates all of these costs, but it has its own drawbacks. The binary is larger, because it includes all the library code it uses. It cannot share library code pages with other processes, so memory usage can be higher if multiple processes use the same library. It also makes updates harder: a bug in a library requires recompiling and relinking every application that uses it. Dynamic linking was invented to solve these problems, and it does so at a cost that is usually acceptable.

The key is to be deliberate. Use `--as-needed` to avoid linking against libraries you do not use. Use `-fvisibility=hidden` to reduce the number of exported symbols. Use `-Wl,-z,now` and `-Wl,-z,relro` for security. Use `-fno-plt` if call overhead matters. Use `-Bsymbolic` or `-fno-semantic-interposition` if you control the library and want to avoid interposition. And measure: `LD_DEBUG=statistics` and `perf` will tell you where the time actually goes. The linker and the loader are not black boxes; they are programs with observable behavior, and understanding them is the first step to making them work for you rather than against you.

## Observing the linker and loader in practice

The previous sections described the machinery; the next step is to see it. The toolchain ships a set of readers that expose exactly what the linker and loader see, and using them turns vague performance complaints into specific measurements.

`readelf` is the primary tool for static inspection. `readelf -h` prints the ELF header, including the entry point and machine type. `readelf -l` prints the program headers — the load-time view — and is the fastest way to see which segments exist, their permissions, and their alignment. `readelf -S` prints the section headers, and `readelf -s` prints the symbol table. For dynamic linking, the interesting variants are `readelf --dyn-syms`, which shows only the dynamic symbol table, and `readelf -d`, which shows the dynamic section: `DT_NEEDED` entries, `DT_RPATH` and `DT_RUNPATH`, `DT_FLAGS` and `DT_FLAGS_1`, and the addresses of the relocation tables.

Relocations are visible with `readelf -r`. On x86-64, the output has columns for offset, type, symbol, and addend. Running it on a shared library shows the split between `R_X86_64_RELATIVE` (local, resolved by adding the base) and `R_X86_64_GLOB_DAT` or `R_X86_64_JUMP_SLOT` (global, requiring symbol lookup). The count of each is a rough proxy for loader work. A library with thousands of `JUMP_SLOT` relocations will be slow to load with `-z now` and will have a large PLT.

`objdump -d` disassembles code and makes the GOT/PLT visible. `objdump -d -j .plt` shows the PLT stubs; `objdump -d -j .plt.got` shows the secondary PLT used for GOT-based calls. `objdump -R` prints the dynamic relocations, and `objdump -s -j .got.plt` dumps the GOT contents. On a running process, `/proc/<pid>/maps` shows the load addresses of each shared object, and `gdb` can inspect the GOT and PLT at runtime.

The dynamic loader itself is observable through environment variables. `LD_DEBUG=libs` prints every library search and load. `LD_DEBUG=bindings` prints every symbol binding, which is overwhelming for large programs but invaluable for a single symbol. `LD_DEBUG=statistics` prints a summary of time spent in relocation processing, including the number of relocations and the time for each phase. `LD_VERBOSE=1` prints the loader version and the search path. `LD_SHOW_AUXV=1` prints the auxiliary vector, which contains the program headers' address, the entry point, and the hardware capabilities the kernel passed to the loader.

For startup time, `strace -c` counts syscalls and shows how much time is spent in `openat`, `mmap`, and `mprotect`. `perf stat -e page-faults,instructions,cycles` measures the cost of mapping and relocating. `hyperfine` compares two binaries with different linking strategies. A useful experiment is to build the same program with `-static`, `-static-pie`, and dynamic linking, then measure startup with `hyperfine --warmup 10`. The difference is usually dominated by the loader's symbol resolution, not by the code itself.

Common failure modes map directly to loader phases. `undefined reference to 'foo'` is a static linker error: no input defined `foo` in the current link. `cannot open shared object file` is a loader error: the `DT_NEEDED` entry names a library that was not found in the search path. `symbol lookup error: ... undefined symbol: foo` is a loader error during relocation: the library was found, but a symbol it needs is not exported by any object in the global scope. `version 'GLIBC_2.34' not found` is a versioning error: the binary was built against a newer glibc than the one at runtime. Each of these has a different fix, and knowing which phase produced the message saves time.

## Symbol versioning and ABI stability

Shared libraries are not just collections of symbols; they are versioned interfaces. The GNU toolchain implements symbol versioning, which allows a library to change the behavior or signature of a function without breaking existing binaries. The mechanism is visible in the dynamic symbol table: a symbol like `memcpy` may appear as `memcpy@@GLIBC_2.14` (the default version) and also as `memcpy@GLIBC_2.2.5` (a compatibility version). The `@@` marks the default version used by new links; the single `@` marks a non-default version that old binaries can still bind to.

Version information lives in three sections. `.gnu.version` holds a version index for each dynamic symbol. `.gnu.version_d` defines the versions provided by this object. `.gnu.version_r` lists the versions required from other objects. When the loader resolves a symbol, it checks both the name and the version. If a binary requires `foo@VER_1` and the library only provides `foo@@VER_2`, the lookup fails. This is why upgrading a library can break binaries that were linked against an older version, even though the symbol name still exists.

Library authors control versioning with a version script, passed to the linker with `--version-script=libfoo.map`. A version script can assign symbols to versions, mark versions as global or local, and hide everything not listed. This is the recommended way to export a stable ABI. A minimal script looks like:

```
LIBFOO_1.0 {
  global:
    foo_init;
    foo_process;
  local:
    *;
};
```

The `local: *` rule hides every symbol not explicitly listed, which is equivalent to `-fvisibility=hidden` but enforced at link time. It also prevents accidental exports from inline functions and template instantiations.

Versioning interacts with interposition in a subtle way. A versioned reference binds to a specific version, so an `LD_PRELOAD` library that defines `foo` without a version may not interpose on a versioned reference. To interpose, the preload library must define the same version, or the reference must be unversioned. This is one reason why replacing libc functions is harder than it looks: glibc's symbols are versioned, and a naive `malloc` replacement may not be called for all references.

The soname is the other half of ABI stability. When a library is built, `-Wl,-soname,libfoo.so.1` records a name in the `DT_SONAME` entry. The linker records that name in the executable's `DT_NEEDED` entry, not the path used at link time. At runtime, the loader searches for `libfoo.so.1`, not `libfoo.so`. The unversioned `libfoo.so` is a development symlink used only at link time. This convention allows multiple major versions to coexist: `libfoo.so.1` and `libfoo.so.2` can be installed side by side, and binaries linked against either will find the right one. Bumping the soname is a promise that the ABI changed incompatibly; failing to bump it is how distributions end up with 'symbol lookup error' after a routine upgrade.

## Thread-local storage and dynamic linking

Thread-local storage (TLS) is a C11 and C++11 feature that gives each thread its own copy of a variable. It is implemented by the compiler, the linker, and the loader together, and it is one of the few places where dynamic linking has a direct, measurable cost on every access.

The x86-64 ABI defines four TLS models, in increasing order of cost:

- **Local-exec** (`-ftls-model=local-exec`): the variable is in the executable's static TLS block, and its offset is known at link time. Access is a single instruction using the `%fs` segment register: `mov %fs:offset, %rax`. This is the fastest model, but it only works for variables defined in the main executable and not in a shared library.
- **Initial-exec** (`-ftls-model=initial-exec`): the variable is in the static TLS block, but its offset is assigned by the loader at startup. Access is still a single instruction, but the offset is loaded from the GOT: `mov foo@gottpoff(%rip), %rax; mov %fs:(%rax), %rdx`. This model works for shared libraries, but the variable must be allocated at load time, which limits the number of TLS variables and can fail with `dlopen`.
- **Local-dynamic** (`-ftls-model=local-dynamic`): the variable is in the module's dynamic TLS block, and its offset is computed by calling `__tls_get_addr`. Access requires a function call, which is expensive. This model is used when the module is loaded with `dlopen` and cannot use static TLS.
- **Global-dynamic** (`-ftls-model=global-dynamic`): the default for shared libraries. The variable may be interposed, so the lookup goes through the GOT and `__tls_get_addr`. Access is a function call, and the call may be optimized by the linker if the variable turns out to be local.

The loader allocates TLS blocks in two ways. Static TLS is allocated at startup for the main executable and its dependencies, using a fixed-size area in the thread control block. Dynamic TLS is allocated on demand for modules loaded with `dlopen`, using `__tls_get_addr` and a per-thread list. The distinction matters because static TLS is fast but limited: if too many libraries use initial-exec TLS, the loader may run out of static TLS space and fail to load a new library. This is a real failure mode in large applications that load many plugins.

The cost of TLS in shared libraries is therefore not just the instruction sequence; it is the loader's bookkeeping. Every thread must have a TLS block for every loaded module, and `dlopen` must update every thread's TLS state. For a process with many threads and many dynamically loaded modules, this can be significant. The practical advice is to use initial-exec TLS for variables that are accessed frequently and are known at startup, and to avoid TLS in plugins that are loaded and unloaded repeatedly.

## IFUNC and relocation-time dispatch

An indirect function (IFUNC) is a GNU extension that lets a library choose an implementation of a function at load time, based on the CPU features available. The mechanism is a symbol of type `STT_GNU_IFUNC` whose value is a resolver function. When the loader processes a relocation for that symbol, it calls the resolver, which returns the address of the implementation to use. The result is written into the GOT or PLT slot, and all subsequent calls go directly to the chosen implementation.

IFUNC is how glibc selects optimized `memcpy`, `strlen`, and similar functions for different x86-64 microarchitecture levels. The resolver runs once per process, early in startup, and can inspect `CPUID` or the auxiliary vector. The cost is a small amount of loader work at startup, but the benefit is that the hot path is a direct call to the best implementation. The downside is complexity: the resolver must be written in a way that does not itself depend on the function being resolved, and debugging is harder because the symbol address is not known until runtime.

IFUNC also has security implications. Because the resolver runs before RELRO is applied, and because it can return any address, a compromised resolver can redirect calls to arbitrary code. For this reason, some hardened systems disable IFUNC or restrict it. In ordinary application code, IFUNC is rarely needed, but it is worth knowing that it exists because it explains why some glibc functions appear to have no fixed address in the symbol table.

## Linker relaxation: the optimizer you didn't know you had

The linker is often described as a patcher: it resolves symbols and fills in addresses. But modern linkers do more. They rewrite instructions. This process is called *relaxation*, and it is one of the reasons why the linker is not just a dumb concatenator of object files. Relaxation happens after symbol resolution and layout, when the linker knows the final address of every symbol and whether each symbol is preemptible. If a relocation can be satisfied with a shorter or faster instruction sequence, the linker replaces it.

The most common relaxations on x86-64 involve the GOT and PLT. Consider a load of a function's address: `mov foo@GOTPCREL(%rip), %rax`. The compiler emits this when it cannot assume that `foo` is local. The relocation is `R_X86_64_GOTPCRELX`. If the linker determines that `foo` is local—because it has hidden visibility, is static, or because the linker was told to bind locally with `-Bsymbolic`—it can replace the GOT load with a direct `lea foo(%rip), %rax`. This eliminates a memory access and a GOT entry. The same applies to calls: `call foo@PLT` with an `R_X86_64_PLT32` relocation can become a direct `call foo` if `foo` is local and within the ±2 GB range of PC-relative addressing. This removes the PLT stub and the indirect jump, turning a two-branch sequence into one.

TLS accesses are another area where relaxation pays off. A general-dynamic TLS access requires a call to `__tls_get_addr`, which is expensive. If the linker can prove that the variable is local and that the module is loaded at startup (so it can use static TLS), it can relax the access to initial-exec or local-exec, replacing the function call with a simple `mov` from the `%fs` segment. This is a dramatic improvement: a call becomes a load.

The conditions for relaxation are strict. The symbol must be non-preemptible. This means it must be local to the module, or the linker must be told that interposition is not allowed. `-fno-semantic-interposition` tells the compiler to assume no interposition, which allows it to emit relaxable relocations. `-Bsymbolic` tells the linker to bind references within a shared object to the local definition, which enables relaxation. `-fvisibility=hidden` makes symbols local, which also enables relaxation. Without these, the linker must assume that any global symbol could be interposed, and it cannot relax.

Relaxation is on by default for most targets. On x86-64, the linker performs it automatically when the conditions are met. On other architectures, such as ARM or RISC-V, it may need to be enabled with `-Wl,--relax`. The linker also performs relaxation for other relocation types, such as `R_X86_64_GOTPCREL` (non-X variant) in some cases, and for TLS models.

The impact of relaxation can be measured. A shared library built without `-fvisibility=hidden` will have many PLT entries and GOT slots. The same library built with `-fvisibility=hidden` will have far fewer. The difference in code size can be tens of kilobytes, and the difference in call overhead can be a few cycles per call. In a tight loop that calls an internal function millions of times, this adds up.

Relaxation also interacts with link-time optimization (LTO). LTO gives the linker the whole program's IR, so it can inline functions and propagate constants across translation units. Relaxation is a lower-level optimization that works on machine code. Both can be used together: LTO can eliminate the need for a call entirely, while relaxation can optimize the calls that remain.

Understanding relaxation is important because it explains why symbol visibility and binding decisions have a direct impact on the generated code. When you hide a symbol, you are not just reducing the dynamic symbol table; you are enabling the linker to rewrite instructions. When you use `-Bsymbolic`, you are telling the linker that interposition is not wanted, which unlocks a whole set of optimizations. The next time you wonder why a shared library is slower than a static build, check whether relaxation is being blocked by overly permissive symbol visibility.

## The C++ dynamic linking tax: vtables, RTTI, and exception handling

C++ adds several features that interact with dynamic linking in ways that C does not. Virtual functions, run-time type information, exceptions, and global constructors all rely on data structures that require relocations and symbol resolution. In a dynamically linked program, these features carry an additional cost that is often invisible until you measure startup time or profile a hot path.

Virtual functions are implemented with vtables. Each polymorphic class has a vtable, an array of function pointers. The vtable is placed in the read-only data section (`.data.rel.ro`), which is writable during relocation and then made read-only. In a shared library, the vtable entries are addresses of functions. If those functions are not hidden, the vtable entries may be subject to interposition. The compiler emits a relocation for each entry. At load time, the dynamic loader must process these relocations. Unlike function calls, which can use lazy binding, data relocations are always eager. A class with a hundred virtual functions adds a hundred relocations that must be resolved before `main` runs.

The vtable symbol itself—for example, `_ZTV5Shape`—is a global symbol. If it is not hidden, it can be interposed. This means that a virtual call in one library might dispatch to a vtable from another library, which is rarely intended. This is a form of accidental interposition that can cause subtle bugs. `-fvisibility=hidden` hides the vtable symbol, preventing interposition and enabling the linker to relax the relocations. For a library that defines many polymorphic classes, this can significantly reduce load time.

Run-time type information (RTTI) is another source of dynamic linking overhead. `typeid` and `dynamic_cast` use `std::type_info` objects, which are global symbols. These objects are subject to interposition. `dynamic_cast` calls `__dynamic_cast` from libstdc++, which performs a runtime search through the type hierarchy. This search may involve comparing type_info objects by name, which can require string comparisons. If the type_info objects are in different shared libraries, the comparison uses the symbol name, which is slower than comparing addresses. This is a hidden cost of dynamic linking for C++: RTTI across shared library boundaries is more expensive than within a single binary. The `dynamic_cast` operation itself is already expensive; dynamic linking makes it worse.

Exception handling is similarly affected. Exceptions use `.eh_frame` and `.gcc_except_table` sections. The `.eh_frame` is a DWARF-like table that describes how to unwind the stack. It is in the read-only data and is relocated. The `.gcc_except_table` describes which catch blocks apply to which ranges of code. Both require relocations. The unwinder itself is in `libgcc_s.so` or `libunwind.so`, which adds a shared library dependency. Throwing an exception involves walking the stack and calling personality routines, which may involve symbol lookups. This is why exceptions are expensive in C++ and even more so in dynamically linked programs. A program that throws exceptions in a hot path will pay for the unwinder's symbol resolution on every throw.

Static initialization and destruction add startup and shutdown costs. Global constructors in C++ are run by the dynamic loader via `.init_array`. The order is dependency order. The loader calls `__cxa_atexit` to register destructors, which are run at exit or `dlclose`. The `__dso_handle` is a hidden symbol that identifies the shared object. This adds overhead at startup and shutdown. A program with many global constructors will have a slower startup, and a library with global constructors will slow down every process that loads it.

All these features add relocations, symbol table entries, and runtime indirection. A C++ shared library with many virtual classes will have a larger dynamic symbol table and more relocations than an equivalent C library. This increases load time and memory usage. The practical advice is to use `-fvisibility=hidden` and explicitly export only the intended API. Avoid global constructors in headers. Use `-fno-rtti` if you don't need RTTI. Use `-fno-exceptions` if you don't need exceptions. Use `-fno-semantic-interposition` to allow the compiler to optimize virtual calls and RTTI within the library. These are language-level decisions that affect the entire program, but they can dramatically reduce the dynamic linking tax for C++.

## The hidden costs of `dlopen` and `dlsym`

`dlopen` is a powerful tool for plugins, but it has costs that are not obvious. Unlike libraries loaded at startup, `dlopen` cannot batch work. Each call performs a full load, relocation, and initialization cycle. The dynamic loader must open the file, map its segments, resolve its relocations against the global scope (if `RTLD_GLOBAL`) or a local scope, and run its initializers. It also updates the link map and TLS state. It must acquire locks to protect these data structures, which can cause contention in multithreaded programs.

The cost of `dlopen` is proportional to the number of relocations and symbols in the library. A library with thousands of relocations will take milliseconds to load. If the library is loaded with `RTLD_NOW`, all relocations are resolved eagerly; with `RTLD_LAZY`, function relocations are deferred, but data relocations are still eager. The loader also allocates memory for the link map, symbol tables, and TLS blocks. This memory is not freed until `dlclose`, and even then, some allocations may persist.

`RTLD_GLOBAL` adds the library's symbols to the global scope, which can slow down future symbol lookups because the hash tables grow. `RTLD_LOCAL` avoids this but limits symbol visibility. In general, `RTLD_LOCAL` is the right choice unless the library is a plugin that needs to export symbols to other plugins.

`dlsym` performs a symbol lookup in the specified handle's scope. It uses the same hash tables as the loader. For a large library, this can be slow. It is often called in a loop, which is a performance anti-pattern. Cache the result. `dlsym` with `RTLD_DEFAULT` searches the global scope, which can be very slow. `dlsym` is thread-safe but may involve locking.

`dlclose` decrements the reference count and, if zero, unloads the library. It runs destructors, unmaps segments, and removes the library from the link map. It also frees TLS blocks. This can be expensive and is often not done because of bugs or because the library is used again. Unloading a library that has registered `atexit` handlers or TLS destructors can be tricky. The loader must ensure that no thread is executing code from the library. In practice, many programs never call `dlclose` because the cost and risk outweigh the benefits.

The practical advice is to load plugins once at startup if possible, rather than repeatedly. Use `RTLD_LOCAL` unless you need to export symbols. Use `RTLD_NOW` if you want to catch missing symbols early, but be aware of startup cost. Cache `dlsym` results. Avoid `dlclose` unless you have a good reason; it rarely saves memory and can introduce subtle bugs. Consider using a plugin system that loads all plugins at startup and keeps them loaded. In a long-running process, repeatedly loading and unloading plugins can fragment the loader's internal data structures and grow memory usage. This is a known issue in some applications, and it is another reason to keep plugins loaded.

## Interposition in practice: `LD_PRELOAD` and its limits

`LD_PRELOAD` is the most direct demonstration of the loader's global scope. A preloaded object is mapped after the main executable but before its dependencies, so its definitions win for any unversioned, default-visibility symbol. That makes it useful for shims: a custom `malloc`, a fault-injecting `open`, or a tracing wrapper around `pthread_mutex_lock`. It is also fragile. A preloaded symbol only interposes if the reference is not bound locally, not protected, and not versioned to a specific provider. Calls that the linker relaxed to direct branches, or that were compiled with `-Bsymbolic`, bypass the preload entirely. Versioned references such as `memcpy@GLIBC_2.14` require the preload to supply a matching version, which is why replacing libc functions often fails silently.

The same scope rules explain why `dlsym(RTLD_NEXT, ...)` is the standard way for a shim to call the original implementation. `RTLD_NEXT` starts the search after the current object in the link map, so the shim does not recurse into itself. But the link map order is not the source order you wrote; it is the loader's breadth-first dependency order. A library loaded later with `RTLD_GLOBAL` can change what `RTLD_NEXT` finds, and a library loaded with `RTLD_LOCAL` cannot be found at all. Interposition is therefore a property of the whole process, not of a single library. Tests that pass in a small binary can fail in a large application because another dependency has already claimed the name.

The practical lesson is to treat exported symbols as a process-wide namespace. Hide everything not meant to be public, version what you do export, and avoid relying on preload order unless you control every dependency. When a shim works in isolation but not in production, the loader's link map is usually the reason. That is not a bug in your shim; it is the contract.
