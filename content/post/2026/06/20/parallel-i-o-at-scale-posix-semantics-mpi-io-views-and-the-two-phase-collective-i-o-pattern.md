For most of the history of parallel computing, I/O was the part of the machine you designed around rather than the part you optimized. You sized the interconnect for the solver's halo exchanges, you sized memory for the decomposition, and you accepted that the checkpoint would take a while. That era is over. The compute-to-storage ratio has widened dramatically: a single node with tens of cores, a few GPUs, and hundreds of gigabytes of memory can produce data far faster than any single storage target can absorb, and the aggregate rate at which a cluster can generate results now routinely exceeds the aggregate rate at which its parallel file system can persist them.

The failure mode this produces is remarkably consistent, and remarkably instructive. A parallel program that reads and writes "correctly" — every rank opens the shared file, seeks to the offset it owns, and issues `read` and `write` calls for its own portion of the domain — can run an order of magnitude slower than a program that moves exactly the same logical bytes with a different *physical* shape. Nothing about the application's data changed. What changed is the number, size, alignment, and concurrency of the requests that actually reached the storage devices, and the amount of coordination the file system had to perform to keep the resulting interleaving consistent with the semantics the program asked for.

This article is about that gap. It starts with the POSIX substrate and the specific ways it fails to compose across processes and hosts, then builds up the MPI-IO model — file views, etypes, filetypes, collective versus independent operations — as an explicit separation between the access pattern an application *has* and the access pattern a storage system *wants*. From there it examines the two classical implementation strategies that bridge the two: data sieving and two-phase collective I/O. Throughout, the emphasis is on the cost model rather than on any particular file system, because the cost model is what transfers between Lustre, GPFS, DAOS, NFS, and whatever replaces them.

## The POSIX substrate, and why it doesn't compose

POSIX gives us a small, elegant interface: `open`, `read`, `write`, `lseek`, `close`, plus the offset-explicit variants `pread` and `pwrite`. The elegance is real, and so is the set of assumptions baked into it.

The file offset is a property of the *open file description*, not of the file descriptor and not of the process. It is shared by descriptors duplicated with `dup`, and it is inherited across `fork`. Two threads calling `read` on the same descriptor therefore contend for the same offset. The kernel makes the offset update atomic with respect to the data transfer, so a single `read` will not return a torn mixture of two other reads, but which thread receives which region is entirely unpredictable. That is not a data race in the C memory-model sense if you are calling the syscall directly, but it is a logical race, and it is the reason that partitioned parallel access must not be built on the shared offset.

`pread` and `pwrite` take an explicit offset and leave the shared offset untouched. They are specified to be atomic with respect to one another on regular files, which is precisely the property that makes them the correct primitive for a fixed, partitioned access pattern: rank *p* owns a disjoint byte range, and no coordination is required beyond agreeing on the partition. `O_APPEND` solves a different problem — the offset is set to end-of-file and the write performed atomically with respect to other appending writers, which makes append-only logs safe without locking, and which is useless for random access.

Buffering is the second assumption. A `write` into the page cache returns as soon as the data has been copied into kernel memory, not when it is durable. `fsync` and `fdatasync` force the data out, and the durability of a checkpoint is only as good as the last one you called. The page cache is a per-host optimization, and it becomes a liability the moment multiple hosts write the same file: the kernel does not maintain cache coherence across nodes, so what one host sees in its page cache may not be what another host sees on the backing store. Network file systems paper over this with weaker consistency models — close-to-open consistency on NFS being the canonical example — which means that a program relying on POSIX-on-a-local-disk intuitions about visibility is relying on something that was never guaranteed.

`O_DIRECT` bypasses the page cache. It eliminates the double buffering that otherwise copies data from the device into the page cache and then from the page cache into the application buffer, but it imposes alignment constraints (offset, length, and often buffer address must be multiples of the logical block size), it disables readahead, and its semantics are Linux-specific and have historically been inconsistent across file systems. `mmap` offers a third path: page-fault-driven I/O, with `MAP_SHARED` writes visible to other processes on the same host through the page cache, and with `msync` as the explicit flush point. It is attractive for read-mostly data and awkward for write-heavy patterns, because the ordering and timing of dirty-page writeback are not under the application's control. Vectored I/O (`readv`, `writev`, `preadv`, `pwritev`, and on Linux `preadv2`/`pwritev2` with flags such as `RWF_NOWAIT`) reduces syscall count for scattered buffers, but it does not change the physical shape of what reaches the device.

Underneath all of this sits a cost structure that is the entire reason parallel I/O is hard. Every request carries a fixed cost: the syscall itself, the file system's translation of a byte range into block-layer operations, the block layer's queueing and merging, and the device's own per-request overhead. On a spinning disk, seek and rotational latency dominate and are measured in milliseconds. On NVMe, per-request latency is tens of microseconds and the limiting factors become queue depth and sustained bandwidth. On a network file system, a request may be an RPC with a full round trip, plus metadata operations that serialize on a server. In every case, cost per byte falls steeply as request size grows, and the fixed cost per request is paid whether you move 4 KiB or 4 MiB.

That single observation drives the rest of the article. Parallel I/O is, to a first approximation, the discipline of amortizing fixed per-request costs: issuing fewer, larger, better-aligned requests, with enough concurrency in flight to keep the device queues full, and with a physical layout that matches how the storage system distributes data.

## Why the naive parallel pattern collapses

Consider the four patterns that most parallel codes reach for first.

**One shared file, offset-explicit access by every rank.** Each rank computes the byte range it owns and issues `pread`/`pwrite` for it. If each rank owns one large contiguous block, the physical shape is decent: N concurrent large requests to disjoint offsets, which a parallel file system can distribute across storage targets. If instead each rank owns every Nth record — the natural layout when the domain decomposition is along the fastest-varying dimension, or when the file is row-major and the decomposition is columnar — then each request is small and the file system sees a storm of tiny, interleaved accesses. On a local SSD this becomes syscall-bound; on a parallel file system it becomes metadata- and lock-bound, because preserving POSIX semantics for a file with multiple concurrent writers typically requires either serialization or per-byte-range locking. The pathological version is the case where N writers to one file perform worse than a single writer would, because the coordination overhead grows with N while the useful work does not.

**One file per rank.** This eliminates contention entirely: each rank writes a sequential stream to its own file, and the file system's per-file locking is uncontended. The costs are less obvious and show up at scale. Metadata operations — create, open, close, stat — scale linearly with rank count and land on a metadata server that is usually the least scalable component of the system. Reading the data back requires either N readers (reproducing the original problem in the opposite direction) or a merge step that has to know the rank-to-file mapping. And the aggregate file count grows with job size, which is fine for a few thousand ranks and increasingly unpleasant for a few hundred thousand.

**Memory-map the whole file and let the kernel sort it out.** For read-mostly workloads with good locality this is often excellent. For writes it is close to the worst of all worlds: dirty-page writeback order is uncontrolled, the writeback thread becomes a hidden source of contention, and on a shared file system the coherence model is not the one the programmer assumed.

**A single I/O rank or a serial writer.** One process reads or writes everything on behalf of the others. This is simple, it produces perfectly sequential access, and for moderate data volumes it is often surprisingly competitive — which is why it survives in production codes. But it caps throughput at one node's I/O bandwidth and forces all data through one process's memory, so it does not survive the transition to petabyte-scale output.

The common thread is that the *logical* access pattern — which bytes does rank *p* own — is usually fixed by the domain decomposition, and the *physical* access pattern is a separate design decision. Conflating them is what produces the collapse. Making the separation explicit is the entire point of MPI-IO.

## The MPI-IO model: views, etypes, filetypes

MPI-IO reframes file access in terms that let an implementation reorganize I/O without changing what the application asked for.

A file is a linear sequence of bytes — the *flat file*. Each process establishes a **file view** consisting of a displacement, an **etype** (the unit of access, in bytes), and a **filetype** (a derived datatype describing the set of regions that this process is permitted to touch). An individual read or write specifies a buffer and a count of etypes; the byte ranges actually transferred are determined by the typemap of the filetype. Everything else in the interface follows from that structure.

The operations come in two flavors. `MPI_File_read` and `MPI_File_write` are *independent*: each process's request is handled on its own. `MPI_File_read_all` and `MPI_File_write_all` are *collective*: all processes in the communicator participate, and the implementation is free to reorganize the data movement across processes. That freedom is the source of every optimization discussed later. There are also shared-file-pointer variants (`MPI_File_read_shared` and friends), which coordinate an offset across processes; they are convenient for streaming workloads but assign regions to processes nondeterministically, which is almost never the semantics a partitioned domain decomposition wants. Separately, `MPI_File_set_atomicity` lets an application relax or enforce the atomicity the implementation must provide, and the `MPI_MODE_UNIQUE_OPEN` hint tells the implementation that no other process or program will open the file — which unlocks optimizations that would otherwise be unsafe.

The crucial mechanical step is that MPI-IO converts a `(filetype, count, offset)` tuple into a list of byte ranges, sometimes called the flattened typemap or access plan. This is where derived datatypes earn their keep. A filetype built with `MPI_Type_create_subarray` — with explicit array sizes, subsizes, starts, and an order that may be `MPI_ORDER_C` or `MPI_ORDER_FORTRAN` — describes a multidimensional slab of a global array. MPI-IO flattens that description into offsets and lengths. If the flattened form is one long contiguous range, the implementation can issue one large request. If it is thousands of short ranges, the implementation will issue thousands of small requests unless something intervenes.

That gives the programmer two levers. The first is layout: choose a decomposition (and a filetype) whose flattened form is contiguous, or at least composed of large runs. The second is delegation: rely on the implementation's coalescing machinery to bridge the gap between a scattered access plan and a storage system that wants large aligned requests. The rest of this article is about the second lever — but it is worth noting that the first is usually cheaper. Choosing etype and filetype well, and choosing a decomposition that produces contiguous runs, costs nothing at runtime; coalescing costs memory and communication.

It is also worth noting where this sits in the stack that most scientific applications actually use. Parallel HDF5 and parallel NetCDF-4 are built on MPI-IO. When you write a hyperslab into a chunked HDF5 dataset, the chunking strategy determines the shape of the access plan that eventually reaches MPI-IO, and the access plan determines whether the I/O is a handful of large requests or a cloud of small ones. The same cost model propagates all the way down.

Once an implementation can see the access plan, the question becomes what it can do with it. The two classical answers are data sieving and two-phase collective I/O, and they attack the problem from opposite directions: one reduces the number of requests by reading or writing more than was asked for, the other reduces the number of requests by moving data between processes first. The next section takes them apart, starting with the cost model that decides which one wins.

## The cost model that decides

Every technique in the rest of this article is an attempt to move one term in a single equation. Stripped to its essentials, the wall-clock time to complete a parallel I/O operation looks like

```
T  ≈  α·R  +  β·B  +  γ·C  +  δ·M
```

where `R` is the number of requests that reach the storage system, `B` is the number of bytes actually moved, `C` is the amount of coordination — locks taken, metadata operations issued, RPCs completed, messages exchanged — and `M` is the memory footprint the implementation is allowed to use. The coefficients are not constants. `α`, the fixed cost per request, shrinks as requests grow, because the block layer merges adjacent requests, because the device amortizes command overhead over more sectors, and because a file system that can hand a single large extent to a single storage target avoids splitting work across targets. `β`, the per-byte cost, is roughly flat until you saturate a link, at which point it becomes the only term that matters. `γ` is the one that surprises people: on a parallel file system it is frequently the dominant term, and it is the term that grows with the number of *processes* rather than the number of bytes.

Two derived quantities explain most of the observed behavior. The first is **in-flight concurrency**, which follows from Little's law: to sustain a bandwidth `W` across a path with latency `L`, you need roughly `W·L` bytes outstanding at all times. On a local NVMe device, `L` is tens of microseconds, so a handful of outstanding requests will saturate the device and request size barely matters. Across a network file system, `L` is a round trip — hundreds of microseconds to milliseconds — so `W·L` is large, and if your requests are small you will run out of concurrency long before you run out of bandwidth. The same 4 KiB request that saturates a local SSD leaves a parallel file system client idle most of the time. The second derived quantity is **density**: the fraction of the bytes you touch that you actually wanted. Density is what separates a strided access pattern that is cheap to fix from one that is not.

Alignment deserves its own sentence because it is invisible in the API and expensive in the hardware. A request that is not a multiple of the file system block size may be split by the client; a request that crosses a RAID stripe boundary may trigger a read-modify-write of parity; a request that is not a multiple of the Lustre stripe size may land unevenly across object storage targets, leaving some targets idle and others oversubscribed. None of this is visible in the return value of `pwrite`. All of it is visible in the throughput graph.

The practical consequence is that the objective is not "minimize bytes" but "minimize `α·R` subject to keeping `B` close to the logical minimum and `C` small." Data sieving and two-phase collective I/O are two different attacks on `R`, and they pay for the reduction in different currencies.

## Data sieving: trading bytes for requests

The idea behind data sieving is almost embarrassingly simple. Suppose a process needs 64 scattered 1 KiB regions spread across a 4 MiB span of the file. Issuing 64 small reads costs `64·α` plus the coordination of 64 separate requests. Issuing *one* read of the entire 4 MiB span costs `1·α` plus `4 MiB·β`, and then the application — or rather the MPI-IO implementation, on the application's behalf — extracts the 64 wanted regions from the buffer it just filled. The number of requests drops by a factor of 64. The number of bytes moved rises by a factor of 64. Whether that is a win depends entirely on the ratio of `α` to `β` and on how dense the access is.

The general statement is that sieving wins when

```
α·(k − 1)  >  β·(B_physical − B_logical)
```

where `k` is the number of small requests that would otherwise be issued. Since `B_physical − B_logical = B_logical·(1/density − 1)`, the condition is a direct comparison between the per-request cost and the wasted bandwidth. On a local disk with a cheap syscall and expensive seeks, sieving is nearly always right. On a high-latency network file system where the RPC round trip dominates, sieving is *even more* right — up to the point where the wasted bytes saturate the link. On a dense NVMe array where `α` is small and `β` is the binding constraint, sieving can easily be a pessimization.

**Read sieving** is the straightforward form: over-read, then discard. **Write sieving** is the form that requires care. To write 64 scattered 1 KiB regions, the implementation must read the enclosing 4 MiB span, overlay the new data in the buffer, and write the whole span back. That is a read-modify-write cycle, and it is only correct if no other process modifies the same enclosing span between the read and the write. Implementations therefore take a lock on the region for the duration of the cycle. The lock converts a bandwidth optimization into a serialization point, and this is why write sieving behaves so differently from read sieving under high concurrency: the operation holds an exclusive claim on a region that is much larger than the data it actually changes, and every other writer whose data happens to fall inside that region must wait. A pattern that is 10% dense will hold a lock on ten times the region it modifies.

Two implementation details matter in practice. First, the enclosing span is bounded. Implementations expose a buffer-size limit — ROMIO calls the relevant hints `ind_rd_buffer_size` and `ind_wr_buffer_size` — and when the enclosing span exceeds it, the operation is split into multiple sieving windows. That caps memory use and also caps the damage from a pathological sparse pattern, but it means a sufficiently large strided access degrades back toward one request per window. Second, sieving is a *per-process* optimization. It requires no collective participation, no communication, and no agreement among ranks. That makes it the only tool available to an application that genuinely cannot call collective I/O, and it makes it the fallback that independent MPI-IO operations fall back to.

## Two-phase collective I/O: trading communication and memory for contiguity

Sieving attacks `R` by enlarging each request. Two-phase collective I/O attacks `R` by changing *who issues* each request. The observation behind it is that the logical decomposition and the file layout usually disagree: rank *p* owns a block of the domain that maps to a strided set of byte ranges in the file, while the storage system would prefer that some process write a long contiguous run. Rather than force every process to write its own strided pattern, the collective operation rearranges the data first.

**Phase one is communication.** Each process sends the bytes it owns logically to the process that owns the corresponding *file* region. **Phase two is I/O.** Each process writes the contiguous region it now holds. The processes that perform the actual I/O are called *aggregators*, and the file is partitioned into contiguous *file domains*, one per aggregator. If the file is partitioned into as many domains as there are aggregators, and each domain is written as a single large aligned request, then `R` collapses from "one request per process per contiguous run" to "one request per aggregator."

The cost is explicit and easy to reason about. The communication phase moves approximately `B_logical` bytes — each byte crosses the network once — plus a number of messages proportional to the number of (sender, aggregator) pairs that have data to exchange. The memory cost is the aggregator buffer: each aggregator must hold its file domain, or at least the portion of it being processed in the current round, before writing it out. That is why two-phase is governed by a buffer-size parameter: when a file domain exceeds the buffer, the operation runs in multiple rounds, each round performing a complete exchange-and-write cycle. More rounds means more communication overhead and more synchronization, but bounded memory.

The exchange is not a naive all-to-all. The implementation already has the flattened access plans of every process, so it can compute a *schedule*: an exact description of which byte ranges each process must send to which aggregator, and in what order. Because the schedule is known in advance, the exchange can be carried out with point-to-point messages in an order that cannot deadlock, without any process ever holding more than its share of the buffer. This is the payoff for the view abstraction described earlier: because the application declared its access pattern as a datatype rather than as a sequence of syscalls, the implementation can reason about the pattern globally.

The tuning question is how many aggregators to use, and the answer is dictated by the storage topology rather than by the process count. Too few aggregators and the I/O phase cannot generate enough concurrent requests to fill the device queues — you have recreated the single-writer bottleneck. Too many aggregators and each file domain shrinks, the per-request size falls, and the communication phase acquires more participants and more messages for the same volume of data. The sweet spot is usually on the order of the number of storage targets the file is striped across, or the number of client nodes, whichever is smaller. Implementations expose this as an aggregator-count hint (`cb_nodes` in ROMIO) alongside the buffer-size hint (`cb_buffer_size`), and the two must be tuned together: increasing the aggregator count without increasing the total buffer budget shrinks each aggregator's share and forces more rounds.

Two-phase I/O has a well-defined set of losing conditions, and recognizing them is as valuable as recognizing the winning ones. If the logical access pattern is already contiguous and aligned, the communication phase is pure overhead — the implementation should detect this from the access plans and skip straight to I/O, and good implementations do. If each process contributes only a few bytes, the message count in the communication phase can dominate the byte volume, and the operation becomes latency-bound on the interconnect rather than on storage. And if the process count is very large while the per-process data is small, the `O(P)` term in the message count eventually outweighs the `O(B)` term in the byte volume.

## Composing the two, and the knobs that control them

The two techniques are not alternatives; they compose, and in practice they are usually both active. Two-phase I/O determines *which* process issues a request and over what region; sieving determines *how* that process fills or drains its buffer. An aggregator whose file domain is dense writes it as one large request. An aggregator whose domain contains holes — because the collective partition did not perfectly match the file layout — can sieve within the domain, reading or writing the enclosing span and extracting or overlaying the wanted pieces. The layers stack: collective rearrangement at the top, per-process coalescing underneath, and the block layer's own merging at the bottom.

The controls are correspondingly layered. At the top, hints that enable or disable collective buffering for reads and writes separately (`romio_cb_read`, `romio_cb_write`) and that set the aggregator count and buffer size. In the middle, hints that enable or disable data sieving (`romio_ds_read`, `romio_ds_write`) and that set the sieving window. At the bottom, hints that describe the file system itself — stripe count, stripe unit, the device to start striping at — which the implementation uses to align requests to the underlying layout. The reason these are hints rather than parameters is that the implementation is free to ignore them when the access plan makes them irrelevant, and the reason they matter is that the correct values are properties of the machine, not of the application.

This is also where the modern variants of the pattern live. **Node-level aggregation** inserts a shared-memory stage before the network stage: ranks on the same node combine their contributions in a shared buffer, and one rank per node performs the network exchange. This reduces the message count by the number of ranks per node without changing the byte volume, and it is the natural fit for architectures where intra-node bandwidth vastly exceeds inter-node bandwidth. **Subfiling** attacks the metadata term instead: rather than one file with one set of locks and one stripe configuration, the logical file is backed by a set of subfiles, each written by a subset of aggregators, with a small index describing the mapping. The application still sees one file; the metadata server sees many fewer contended operations; and each subfile can be striped independently. Both variants are recognizably the same idea — separate the logical access pattern from the physical one, and pay for the separation in memory and messages rather than in requests.

What none of this changes is the underlying arithmetic. The number of requests that reach the storage system is what you are buying down, the bytes you move are what you are paying with, and the memory and messages are the transaction fee. An application that understands which of those three it has in surplus will choose its hints well; an application that does not will find that the default configuration is tuned for someone else's workload.

## Reading the access plan: how to tell what your code actually does

Before tuning anything, you need to know what your program is actually asking the file system to do. The application's source code describes a logical access pattern; the storage system sees a physical one; and the gap between them is where every performance problem lives. Closing that gap begins with instrumentation.

The first and cheapest tool is the system call trace. Run a single rank under `strace -e trace=openat,read,write,pread64,pwrite64,fsync,close -f` and look at the distribution of sizes and offsets. A healthy collective write shows a small number of large `pwrite64` calls, often several megabytes each, with offsets that tile the file. A collapsing pattern shows thousands of calls in the tens or hundreds of kilobytes, interleaved across ranks, with offsets that jump around. The trace is per-rank, so run it on a representative rank and on a rank at the edge of the decomposition, where the access pattern is usually worst. On a network file system, `strace` shows the syscall the client makes, not the RPC the client sends, but the sizes and offsets are still the ones that matter.

The second tool is a profiling library that understands MPI-IO. Darshan is the standard choice: it interposes on the I/O calls, records histograms of request sizes, access patterns (sequential, strided, random), file counts, and per-rank counters, and writes a compact log that can be analyzed after the job. Recorder does something similar with more emphasis on capturing the exact sequence of operations. Both will tell you, without any code changes, whether your job opened ten files or ten thousand, whether the reads were sequential or strided, and how much time was spent in I/O versus computation. TAU and mpiP provide complementary views, including the time spent inside MPI-IO calls and the imbalance across ranks.

The third tool is the MPI-IO implementation's own introspection. After `MPI_File_open`, `MPI_File_get_info` returns the hints that are actually in effect, which is not always the set you passed in — implementations may override, ignore, or add hints. `MPI_File_get_view` returns the current file view, including the etype, filetype, and displacement. If you are building filetypes programmatically, flatten them yourself with `MPI_Type_get_envelope` and `MPI_Type_get_contents`, then walk the resulting typemap to compute the number of contiguous runs and their lengths. That number is the single best predictor of how many requests the implementation will issue. A filetype that flattens to one run per rank is ideal. A filetype that flattens to one run per element is a warning sign, and the fix is either a different decomposition or a collective operation that lets the implementation rearrange the data.

For higher-level libraries, the introspection moves up a layer. In HDF5, `h5dump -p` shows the chunking and filters of every dataset, and `h5stat` summarizes the file's metadata. `H5Dget_chunk_info` and `H5Dget_chunk_storage_size` let you query chunk layout at runtime. In NetCDF-4, `ncdump -h -s` shows the chunking and compression settings. The point of looking is the same: the chunk shape determines the access plan that reaches MPI-IO, and the access plan determines whether the I/O is a handful of large requests or a cloud of small ones.

Finally, measure density. Density is the ratio of logical bytes the application wanted to physical bytes that crossed the wire. You can estimate it from the access plan: sum the lengths of the contiguous runs, divide by the span from the first byte to the last. A density near 1.0 means the pattern is already contiguous and collective buffering will not help. A density near 0.01 means the pattern is extremely sparse, and the choice between sieving and two-phase depends on whether the wasted bytes or the wasted requests cost more.

## Checkpointing as the canonical collective write

Checkpointing is the workload that most parallel I/O research is implicitly about, and it is the one where the cost model is easiest to see. A checkpoint writes a consistent snapshot of the simulation state to durable storage so that the job can restart after a failure. The logical volume is fixed by the problem size. The physical shape is entirely under the application's control.

The naive checkpoint opens one file, seeks to each rank's offset, and writes each rank's subdomain. If the subdomain is a contiguous block of the global array and the file is laid out in the same order, the physical pattern is N concurrent large writes to disjoint offsets — which is close to what the storage system wants, provided the file is striped across enough targets. If the subdomain is a slab that is contiguous in memory but strided in the file, or if the file is written in a different order than the decomposition, the pattern degrades. The fix is a filetype built with `MPI_Type_create_subarray` that describes the subdomain in file coordinates, combined with a collective write. The implementation then has the access plans of every rank and can decide whether to shuffle data between processes before writing.

The tuning parameters for a checkpoint are the same three that govern any collective write: the number of aggregators, the size of the aggregator buffer, and the alignment of the file domains to the underlying stripe. The aggregator count should be on the order of the number of storage targets the file is striped across, not the number of ranks. The buffer size should be large enough that each aggregator writes at least a few megabytes per round, because below that the per-request cost dominates. Alignment is a property of the file system: on Lustre, the stripe count and stripe size determine how a contiguous file domain is distributed across object storage targets, and a file domain that is not a multiple of the stripe size will leave some targets idle. Setting the striping hints through `MPI_Info` — or, in HDF5, through `H5Pset_alignment` — lets the implementation choose file domains that match the layout.

Checkpointing at scale adds two more dimensions. The first is frequency: a checkpoint that takes ten minutes on a job that runs for an hour is a 17% overhead, and the optimal interval is a function of the failure rate and the cost of restarting from scratch. The second is hierarchy: writing every checkpoint to the parallel file system is wasteful if most checkpoints are never used. Multilevel checkpointing writes frequent, cheap checkpoints to node-local storage or to a burst buffer, and promotes them to the parallel file system less often. Libraries such as SCR and VeloC implement this pattern, and they change the I/O problem from 'write a petabyte to Lustre' to 'write a few terabytes to local SSD and a smaller amount to Lustre.' The cost model is the same, but the coefficients are different: local storage has lower latency and higher per-request cost tolerance, while the parallel file system is reserved for the operations that need durability and global visibility.

Reading a checkpoint back is the mirror image, and it is often the harder direction. A restart may need to redistribute the data across a different number of ranks than the original run, which means the read pattern is not the inverse of the write pattern. Collective reads with explicit file views handle this: each rank declares the region it needs, the implementation computes the schedule, and the data is shuffled during the read. The alternative — every rank reading the whole file and extracting what it needs — is sometimes faster for small restarts and always simpler, but it does not scale.

Compression is the wild card. Applying a lossless filter before writing reduces the bytes that cross the wire, which directly reduces the `β·B` term. It also adds CPU cost, which is invisible in the I/O equation but very visible in the application's runtime. The trade is favorable when the job is I/O-bound and the compression ratio is high; it is unfavorable when the job is compute-bound or when the data is incompressible. In HDF5, filters are applied per chunk, which means a compressed chunk must be read whole, decompressed, modified, recompressed, and written back. That is a read-modify-write cycle, and if multiple ranks modify the same chunk, the contention is severe. The layout decision — one chunk per rank, or chunk shapes aligned with the decomposition — matters more than the filter choice.

## Strided access, transposition, and the layout decision

The most common source of pathological I/O in scientific codes is a mismatch between the domain decomposition and the file layout. Consider a two-dimensional array stored in row-major order and decomposed by columns: rank *p* owns all rows for a contiguous set of columns. In memory, each rank's data is strided — one element per row, then a gap. In the file, if the array is written in row-major order, the same strided pattern appears. Each rank's access plan flattens to one run per row, which for a 10,000-row array is 10,000 runs per rank. The implementation will either issue 10,000 small requests or invoke collective buffering to rearrange the data, and the rearrangement is a transpose.

The transpose is not free, but it is often cheaper than the alternative. The communication volume is the same as the data volume, and the message count depends on how many (sender, aggregator) pairs have data to exchange. For a columnar decomposition, every rank has data for every file domain, so the schedule is dense and the message count is `O(P^2)` in the worst case. That is the regime where two-phase collective I/O stops being a clear win and the layout decision becomes the better lever.

The layout decision has three forms. The first is to change the decomposition: use a block-cyclic distribution, or decompose along the fastest-varying dimension instead of the slowest. This changes the access plan from many small runs to fewer large ones, at the cost of changing the communication pattern in the solver. The second is to change the file layout: write the array in a transposed order, or use a chunked format where the chunk shape matches the decomposition. HDF5 and NetCDF-4 make this explicit: the chunk shape is the unit of I/O, and a chunk shape that matches the per-rank subdomain turns a strided access into a contiguous one. The third is to accept the stride and let the implementation handle it, which is viable when the collective machinery is well-tuned and the process count is moderate.

The chunking decision interacts with everything else. A chunk that is too small produces many small I/O requests and a large metadata footprint. A chunk that is too large wastes bandwidth when only part of it is needed, and it forces a read-modify-write cycle when a rank writes a subregion. The ideal chunk size is a function of the access pattern, the page cache, and the storage system's preferred request size. In HDF5, `H5Pset_chunk_cache` controls the per-dataset chunk cache: `rdcc_nslots` sets the number of hash slots, `rdcc_nbytes` sets the cache size in bytes, and `rdcc_w0` sets the preemption policy. A cache that is too small thrashes; a cache that is too large competes with the application's own memory. The defaults are conservative, and tuning them is one of the few HDF5 knobs that reliably moves the needle.

There is a deeper point here about where optimization belongs. The access plan is determined by the combination of the decomposition, the file layout, and the datatype. Changing any of those is a design-time decision that costs nothing at runtime. Changing the I/O hints is a runtime decision that costs memory and communication. The cheapest fix is always the one that makes the access plan contiguous in the first place, and the most expensive fix is the one that tries to paper over a bad access plan with a bigger buffer.

## Asynchronous I/O, overlap, and the limits of hiding latency

Everything so far has assumed that I/O happens while the application waits. That assumption is often false, and the techniques for breaking it are the last major lever.

MPI-IO provides nonblocking operations: `MPI_File_iread`, `MPI_File_iwrite`, and the collective variants `MPI_File_iread_all` and `MPI_File_iwrite_all`. These return a request handle, and the application can continue computing while the I/O is in progress. The implementation is free to use a progress thread, a background thread, or to rely on the application calling `MPI_Test` or `MPI_Wait` to make progress. The practical constraint is that the buffer must not be modified until the request completes, which means the application needs double buffering: one buffer being written, one buffer being filled by the computation. The memory cost is real, but the latency hiding is often worth it.

The gain from overlap is bounded by the same Little's law arithmetic that governs everything else. If the I/O is bandwidth-bound, overlapping it with computation does not make it faster; it only hides the latency. If the I/O is latency-bound — small requests, high round-trip time — overlap can recover most of the lost time, because the application is no longer idle while waiting for each request. The best case is a checkpoint that is written asynchronously while the simulation continues, so the checkpoint cost is paid in bandwidth and memory rather than in wall-clock time. The worst case is a checkpoint that is already saturating the storage system, in which case the computation and the I/O compete for the same resources and the total time is unchanged or worse.

The consistency problem is what makes asynchronous checkpointing hard. If the simulation continues while the checkpoint is being written, the data being written may change underneath the I/O. The application must either copy the data into a stable buffer before starting the write, or arrange for the data to be immutable for the duration of the write. Copy-on-write snapshots — via `fork`, `mmap`, or a dedicated snapshot mechanism — solve the problem at the cost of page-table manipulation and memory. The alternative is to stop the simulation, write the checkpoint, and resume, which is synchronous checkpointing and is what most codes do. The choice is a trade between memory, complexity, and wall-clock time.

On the hardware side, two developments change the overlap calculus. The first is `io_uring` on Linux, which provides a submission queue and a completion queue for asynchronous I/O and can reduce the syscall overhead of many small operations. The second is GPUDirect Storage, which allows data to move directly between GPU memory and storage devices, bypassing the CPU and the page cache. Both reduce the per-request cost `α` and the per-byte cost `β` for the paths they accelerate, but neither changes the fundamental need to issue large, aligned, concurrent requests. A GPU that can generate data at hundreds of gigabytes per second still needs the storage system to be fed in large chunks, and the two-phase pattern is still the way to assemble those chunks from the distributed pieces that the application produces.

The final constraint is that overlap does not create bandwidth. If the job's I/O demand exceeds the storage system's capacity, no amount of asynchronous programming will fix it. The only fixes are to write less data — through compression, through lower precision, through checkpointing less often — or to write it to a faster tier. Overlap is a latency optimization, and it should be applied after the bandwidth problem is solved, not before.

## Consistency, atomicity, and the semantics of collective completion

MPI-IO's atomicity mode is a property of the file handle, set with `MPI_File_set_atomicity` and queried with `MPI_File_get_atomicity`. When atomicity is enabled, every operation on the file appears to occur instantaneously with respect to every other operation: a read never observes a partially completed write, and two writes to overlapping regions are serialized in some order. When atomicity is disabled, the implementation is free to use optimizations that assume no conflicting concurrent access — write sieving, for example, which performs a read-modify-write cycle over an enclosing span and would be unsafe if another process modified that span in between. The default is implementation-dependent, but the common case is non-atomic, and applications that require atomicity must request it explicitly. The cost is real: atomicity forces locking or serialization at a granularity the implementation chooses, and on a parallel file system that granularity is often a lock on a region or a file. For a partitioned write where each rank owns a disjoint byte range, atomicity buys nothing and costs throughput. For a shared-file-pointer write, or for any pattern where two ranks might touch the same byte, it is the only thing that makes the result well-defined.

The consistency model is separate from atomicity, and it is the part that most applications get wrong. MPI-IO distinguishes between independent and collective operations in terms of what is guaranteed after completion. After a collective operation — `MPI_File_write_all`, for example — the data written by every process in the communicator is visible to every process in the communicator. That is a strong guarantee, and it is what makes the two-phase pattern safe: the aggregators write the file domains, and when the collective call returns, every rank can read any byte that was written. After an independent operation, no such guarantee exists. A write by rank 0 may sit in rank 0's client cache or in the file system's metadata layer, invisible to rank 1, until some synchronization occurs. The synchronization primitive is `MPI_File_sync`, which makes all previously written data visible to all processes in the communicator. It is not `fsync`: it guarantees visibility, not durability. A checkpoint that calls `MPI_File_sync` and then crashes may still lose data that was in a volatile cache. For durability, the application needs the underlying file system to flush, which may mean calling `fsync` on the file descriptor if the implementation exposes it, or using a higher-level library that provides a flush operation with durability semantics.

Failure semantics are where the POSIX substrate shows its age. POSIX provides no transactional writes. If a process dies in the middle of a write, the file may contain a partially updated region, and there is no way to roll back. The standard workaround is the write-rename pattern: write the new checkpoint to a temporary file, close it, and rename it to the final name. On a local file system, `rename` is atomic: a reader either sees the old file or the new one, never a mixture. On a parallel file system, `rename` is usually atomic as well, because it is a metadata operation handled by the metadata server. But the pattern has a cost: the temporary file and the final file both exist for a moment, so the storage system must have room for two copies, and the rename itself is a metadata operation that may serialize. For a checkpoint that consists of many files — one per rank, or a set of subfiles — the atomic unit is harder to define. One approach is to write all the files into a temporary directory and rename the directory, which is atomic on most file systems. Another is to write a small manifest file last, containing the list of data files and their checksums; the manifest is the commit point, and a restart reads the manifest first and ignores any data files not listed. The manifest approach is more flexible and is what many large-scale checkpoint libraries use.

## The metadata term: why file counts and chunk counts matter

The cost model in the previous sections treated `γ·C` — coordination — as a single term. In practice, coordination splits into two very different costs: the cost of moving bytes through the network, and the cost of metadata operations. The second is the one that scales with the number of files and the number of chunks, and it is the one that most often surprises applications at scale.

A parallel file system separates metadata from data. Lustre has metadata servers (MDSs) that handle inodes, directory entries, and file layouts; GPFS has a similar separation. The metadata servers are typically fewer in number than the data servers, and they are not designed to handle the same request rate. A single `open` on a parallel file system may require a round trip to the metadata server to fetch the inode and the layout. A `close` may require another. A `create` requires a directory entry update, which may take a lock on the directory. When a job with 100,000 ranks opens one file per rank, it issues 100,000 opens, 100,000 closes, and 100,000 creates. If the metadata server handles a few thousand operations per second, the job spends tens of seconds in metadata before any data moves. That time is pure overhead, and it grows linearly with rank count.

The same problem appears inside a single file when the file format uses many small chunks. HDF5 and NetCDF-4 store chunked datasets with an index — a B-tree or a hash table — that maps chunk coordinates to file offsets. Writing a chunk requires updating the index, which is a metadata operation inside the file. If the chunk size is small and the access pattern touches many chunks, the index updates can dominate the data transfer. The chunk cache mitigates this by batching index updates, but the cache is finite, and a pattern that touches more chunks than the cache can hold will thrash. The lesson is that chunk size is not just an I/O size parameter; it is a metadata parameter. A chunk that is too small produces many index updates; a chunk that is too large wastes bandwidth when only part of it is needed.

Subfiling is one response to the metadata problem. Instead of one file with one inode and one set of locks, the logical file is backed by a set of subfiles, each written by a subset of aggregators. The application still opens one file, but the metadata server sees a smaller number of contended operations, and each subfile can be striped independently. The index that maps logical offsets to subfiles is small and is read once at open time. The trade is additional complexity in the library and a less standard file format. Object storage takes the separation further: there is no directory hierarchy in the POSIX sense, and metadata operations are HTTP requests or RPCs to a metadata service. The consistency model is often weaker, and the cost of a metadata operation is a network round trip. Applications that were designed around POSIX directory semantics — create a file, write it, rename it — must be redesigned for a world where rename may not be atomic and where listing a directory may be expensive.

## Portability and the hint landscape

The hints that control MPI-IO's collective buffering and data sieving are not part of the MPI standard. They are implementation-specific keys in an `MPI_Info` object. The keys that most applications use — `cb_buffer_size`, `cb_nodes`, `ind_rd_buffer_size`, `ind_wr_buffer_size`, `romio_cb_read`, `romio_cb_write`, `romio_ds_read`, `romio_ds_write`, `striping_factor`, `striping_unit`, `start_iodevice` — come from ROMIO, the MPI-IO implementation used by MPICH and several vendor MPI libraries. Open MPI has its own implementation, OMPIO, which accepts many ROMIO keys for compatibility but may interpret them differently. Other implementations, such as those targeting DAOS or object stores, may ignore them entirely.

The portable approach is to treat hints as requests, not commands. Set the hints you believe are correct, open the file, then call `MPI_File_get_info` to see which hints are actually in effect. The returned info object may contain the hints you set, modified values, or additional hints that the implementation added. If a critical hint was ignored, the application can fall back to a different strategy: for example, if collective buffering is unavailable, the application can implement its own two-phase exchange using point-to-point messages and independent I/O. This is more work, but it is the only way to write code that performs well on more than one machine.

The higher-level libraries hide some of this portability problem but introduce their own. HDF5's `H5Pset_fapl_mpio` attaches an `MPI_Info` object to the file access property list, so the same hints propagate down to MPI-IO. `H5Pset_dxpl_mpio` selects collective or independent transfer mode for a dataset transfer. `H5Pset_alignment` sets the alignment of raw data in the file. NetCDF-4 uses the same HDF5 layer underneath, so the same knobs apply. The advantage is that these calls are portable across HDF5 versions and platforms. The disadvantage is that the effective MPI-IO hints are still implementation-specific, and the HDF5 defaults may not match the storage system's preferred request size.

Auto-tuning is the alternative to manual hint selection. Some implementations attempt to detect the access pattern at runtime and choose the buffering strategy automatically. This works well when the pattern is stable and the implementation's heuristics match the storage system. It works poorly when the pattern changes over time, or when the implementation's model of the storage system is wrong. The application can help by providing hints about the expected pattern — for example, an `access_style` hint that says the access is sequential, strided, or random — but not all implementations use these hints. The practical recommendation is to start with defaults, measure, and then tune one hint at a time. Document the hints that worked on each machine, and use environment variables or a configuration file to apply site-specific settings without recompiling. ROMIO supports a `ROMIO_HINTS` environment variable that points to a file of hints, which is a useful mechanism for site-wide tuning.

## A decision procedure for a new access pattern

When you are faced with a new I/O pattern, the following procedure will get you most of the way to a good configuration. It is not a substitute for measurement, but it will tell you what to measure.

1. Characterize the logical access pattern. What is the domain decomposition? What is the file layout? Build the filetype, flatten it, and count the number of contiguous runs per rank. Compute the density: the sum of the run lengths divided by the span from the first byte to the last. A density near 1.0 means the pattern is already contiguous; a density near 0.01 means it is extremely sparse.

2. If density is high and the runs are large — say, at least a few hundred kilobytes each — use independent I/O with explicit offsets. Collective buffering will only add communication. Make sure the offsets are aligned to the file system's block size and, if possible, to the stripe size.

3. If density is low but the wasted bytes are cheap — local SSD, high-bandwidth interconnect, or a storage system where per-request cost is small — enable data sieving. Set `romio_ds_read` and `romio_ds_write` to `enable`, and set the sieving window sizes (`ind_rd_buffer_size`, `ind_wr_buffer_size`) to a few megabytes. Watch the read-modify-write cost for writes: if multiple ranks write to the same enclosing span, sieving will serialize them.

4. If density is low and the network is the bottleneck — a parallel file system with high latency, or a storage system where per-request cost is high — enable two-phase collective I/O. Set `romio_cb_read` and `romio_cb_write` to `enable`. Set `cb_nodes` to the number of storage targets the file is striped across, or to the number of client nodes, whichever is smaller. Set `cb_buffer_size` so that each aggregator has at least a few megabytes of buffer per round. If the file domain is larger than the buffer, the operation will run in multiple rounds; increasing the buffer reduces the number of rounds but increases memory use.

5. If the access pattern is strided in a way that collective buffering cannot fix — for example, every rank needs data from every file domain, so the communication schedule is dense — change the layout. Use a chunked format with a chunk shape that matches the per-rank subdomain. Use subfiling to reduce metadata contention. Use a different decomposition if the solver allows it. Layout changes are design-time decisions and cost nothing at runtime; they are almost always cheaper than runtime coalescing.

6. Measure again. Use Darshan or Recorder to see the actual request sizes and counts. Use `MPI_File_get_info` to see the effective hints. Compare the achieved bandwidth to the storage system's peak. If the achieved bandwidth is far below peak, the bottleneck is probably request count or metadata, not raw bandwidth. Iterate on the hints that affect those terms.

The procedure is deliberately simple because the underlying arithmetic is simple. You are trying to minimize the number of requests that reach the storage system, keep the bytes moved close to the logical minimum, and keep the coordination and memory costs within budget. Every technique in this article is a way of trading one of those quantities for another. The right trade depends on which quantity is scarce on your machine, and that is a measurement question, not a theoretical one.
