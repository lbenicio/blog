# The Anatomy of a Parallel N-Body Simulation: Barnes-Hut Trees, Morton Ordering, and Load-Balanced Traversal

N-body simulation is one of those workloads where the naive algorithm is simple and the scalable algorithm is not. Direct all-pairs force evaluation is easy to write and easy to parallelize: every particle interacts with every other particle, and the work is a dense matrix of independent force contributions. Its cost is O(N^2), which is acceptable for small N and increasingly hostile as N grows. Barnes-Hut reduces the asymptotic cost by grouping distant particles into tree nodes that carry aggregate mass and a center of mass. The approximation is well known. The engineering is not.

The interesting part of a parallel Barnes-Hut simulation is not the force formula. It is the tree, the memory layout, the scheduling policy, the load balance, and the synchronization discipline. A correct serial implementation can be surprisingly short. A parallel implementation that scales well on a multicore machine with non-uniform memory access, irregular particle density, and a tree that changes every timestep is a systems problem. This article examines that problem from the inside out.

For scope, assume a 3D Barnes-Hut simulation with a monopole approximation and softened gravitational or electrostatic forces. Particles have position and mass. The simulation advances in timesteps. At each timestep, the tree is rebuilt or updated, and each particle traverses the tree to accumulate force. The target is shared-memory parallelism on a multicore CPU first; distributed-memory concerns are separate and will be treated later. The goal is not to present a universal winner. It is to expose the decisions that remain important when N grows and core count grows with it.

## The Cost Model and the Approximation Contract

Barnes-Hut replaces the direct sum over all particles with a traversal over an octree. Each internal node stores the total mass of its subtree and the mass-weighted center of mass. For a particle at position p and a node with center of mass c, the traversal computes the distance d between p and c and the node size s. If s/d is below a threshold theta, the node is treated as a single interaction. Otherwise, the traversal descends into the node's children. Leaves are handled directly, either by iterating over the particles in the leaf or by using a small direct kernel.

The approximation contract is local: each particle decides whether a node is far enough away to be aggregated. That locality is what makes Barnes-Hut attractive. It also makes the cost model irregular. The textbook complexity is O(N log N) for a reasonably balanced tree, but the constant depends on theta, leaf capacity, particle distribution, and the cost of memory access. A smaller theta means more traversal and more accuracy. A larger theta means fewer interactions and more approximation error. The trade-off is not a single knob; it interacts with tree shape and density.

The cost model has three phases. Tree construction builds or updates the spatial hierarchy. Traversal computes force contributions. Integration updates positions and velocities. In a parallel implementation, each phase has different synchronization and load-balancing properties. Tree construction is a reduction over particles and spatial buckets. Traversal is an irregular graph walk with per-particle private accumulation. Integration is a dense per-particle update. Treating the whole timestep as one parallel loop hides these differences and usually produces poor performance.

There is also a memory cost. A pointer-based octree with one allocation per node is convenient and cache-hostile. An array-based tree with contiguous node metadata is more work to build but easier to traverse. The choice affects both serial and parallel behavior. The approximation contract does not care about the layout, but the hardware does.

## Why Parallel N-Body Is a Systems Problem

A parallel N-body simulation is not just a loop over particles. It is a sequence of irregular traversals over a spatial data structure that changes as particles move. The tree is rebuilt or updated frequently, so the parallelization strategy must account for construction cost, traversal cost, and the cost of moving data between phases. The workload is dynamic, and the density is rarely uniform.

Consider a uniform random distribution. The octree is reasonably balanced, and the traversal work per particle is similar. Consider a galaxy simulation with dense clusters and sparse voids. The tree is deep in dense regions and shallow in sparse regions. Particles in dense regions traverse more nodes and perform more direct interactions. Particles in sparse regions may aggregate large nodes quickly. A static partition of particles across threads will produce load imbalance. The imbalance is not a minor tuning issue; it is a structural property of the data.

There is also a synchronization issue. Force accumulation per particle is naturally private: if each particle is owned by exactly one thread, no atomics are needed for the force vector. The tree build is different. Building aggregate mass and center of mass requires reductions over particles. If the tree is rebuilt in parallel, the reduction must be coordinated. If the tree is updated incrementally, the update must handle particles moving between nodes. The synchronization discipline depends on whether the tree is rebuilt from scratch, rebuilt from sorted particles, or updated in place.

Floating-point reproducibility is another systems concern. Parallel reductions change the order of additions. If the application requires deterministic results across runs or thread counts, the reduction order must be fixed. That can mean a fixed reduction tree, compensated summation, or deterministic partitioning. None of these choices is free. They trade performance for reproducibility. The right answer depends on whether the simulation is used for exploratory visualization, where small nondeterminism is acceptable, or for regression testing and publication, where bitwise reproducibility may be required.

## Barnes-Hut Tree Construction

A Barnes-Hut tree is an octree. Each internal node covers a cubic region and has up to eight children. Particles are inserted into leaves. A leaf has a capacity; when it overflows, it is subdivided. Each node stores the total mass of its subtree and the center of mass. The center of mass is the mass-weighted average of the particles in the subtree. The total mass is the sum of the particle masses.

There are two common construction strategies. The first is top-down recursive insertion. Start with a root cube that contains all particles. Insert particles one by one. When a leaf exceeds capacity, subdivide it and redistribute its particles. This is simple and adaptive. It is also pointer-heavy and allocation-heavy. The second strategy is bottom-up construction over Morton-sorted particles. Compute a spatial code for each particle, sort by code, and build leaves and internal nodes from contiguous ranges. This is more array-friendly and easier to parallelize. The trade-off is that the tree shape is determined by the spatial ordering and the chosen depth, not by incremental insertion.

Leaf capacity is a real tuning parameter. Larger leaves reduce the number of tree nodes and the depth of the tree. They also increase the number of direct interactions within leaves. Smaller leaves increase tree depth and traversal overhead but reduce direct work inside leaves. The best value depends on theta, the cost of a direct interaction, and the cost of a node visit. There is no universal constant.

Duplicate or near-duplicate positions are a practical hazard. If many particles occupy the same coordinates, recursive subdivision can continue until the maximum depth is reached. A robust implementation needs a maximum depth, a jitter policy, or a special case for coincident particles. The choice affects accuracy and determinism. Jitter changes the physics slightly. A maximum depth preserves determinism but may create dense leaves that are expensive to traverse. Either way, the tree builder must handle the degenerate case explicitly.

## Morton Ordering and Data Layout

Morton ordering, also called Z-order, maps a 3D point to a single integer by interleaving the bits of its quantized coordinates. Particles sorted by Morton code tend to be spatially close in memory. That locality is useful for tree construction and for traversal. The sort itself is a standard parallel sort or a radix sort over the codes. After sorting, particles can be reordered into contiguous arrays. The tree can then be represented as ranges over the sorted particle array.

A linear octree representation is a natural fit. Each leaf corresponds to a contiguous range of particles. Each internal node stores a range and child offsets. The node metadata can be stored in a flat array. The particle data can be stored in a structure-of-arrays layout: positions in one array, masses in another, velocities in another. The traversal reads node metadata and particle positions. The structure-of-arrays layout makes vectorization and cache-friendly streaming easier, while the node metadata array keeps pointer chasing under control.

Morton ordering is not a load balancer. It clusters spatially, but it does not equalize work. A dense cluster still produces more traversal work than a sparse void. The ordering helps locality and tree construction, but it does not solve the scheduling problem. That distinction matters. A common mistake is to assume that spatial locality implies balanced work. It does not. The scheduler still needs to account for density and traversal cost.

There are alternatives. Hilbert ordering often provides better spatial locality than Morton ordering because it avoids some of the long jumps in the Z-order curve. The cost is that Hilbert codes are more expensive to compute. For a simulation that rebuilds the tree every timestep, the code computation cost matters. Morton ordering is cheap and usually good enough. The right choice depends on how often the tree is rebuilt and how much locality matters for the traversal kernel.

Quantization is another trade-off. The Morton code needs a fixed number of bits per dimension. Too few bits cause collisions and large leaves. Too many bits create large codes and potentially many empty nodes. The bit width should be chosen relative to the particle distribution and the desired leaf capacity. The tree builder should also handle empty octants explicitly or avoid creating them. Empty nodes waste memory and traversal time.

The traversal phase is where these layout choices pay off or fail. We will examine that next.

## Parallel Traversal Kernels

The traversal phase is read-only with respect to the tree. Each particle owns a private force accumulator. That property is the foundation of a simple parallelization: assign disjoint sets of particles to threads, let each thread traverse the same immutable tree, and write forces only to its own particles. No locks, no atomics, no contention on the tree. The synchronization cost is reduced to a barrier between the force phase and the integration phase. The difficulty is not correctness; it is keeping the threads busy and the memory system happy.

### Iterative Traversal and Stack Discipline

A recursive traversal maps directly to the algorithm: test a node, accept it, or descend into its children. In a parallel kernel, recursion is usually replaced by an explicit stack. Each thread keeps a stack of node indices. The maximum depth of the tree bounds the stack size, so the stack can be a fixed-size array allocated once per thread. This avoids allocation in the inner loop and keeps the traversal state in registers and L1 cache. The stack entry can be a single integer if nodes are stored in a flat array. If the traversal needs to carry additional state, such as a distance bound or a partial force, the entry can be a small struct. The goal is to make a node visit cheap: load node metadata, compute the distance squared, compare against the opening criterion, and either accumulate or push children.

The opening criterion is usually evaluated as s^2 < theta^2 * d^2 to avoid a square root. The node size s and center of mass c are stored in the node record. The particle position p is loaded once and kept in registers for the duration of the traversal. For each visited node, the kernel computes the displacement vector, the squared distance, and the acceptance test. If the node is accepted, it adds a monopole contribution to the force accumulator. If the node is a leaf, it either accepts the whole leaf or iterates over the particles in the leaf. The leaf range is stored in the node record, so the direct kernel can stream particle positions from the sorted particle array.

### Fused Traversal Versus Interaction Lists

There are two broad ways to structure the traversal. A fused traversal accumulates forces as it walks the tree. It uses one pass, minimal temporary storage, and good locality for the particle's force accumulator. An interaction-list traversal first collects accepted nodes and rejected leaves into per-particle lists, then evaluates the lists in a second pass. The list approach can improve vectorization because accepted nodes can be processed in batches with the same particle. It can also sort interactions by node to improve memory locality across particles. The cost is extra memory traffic and a more complex kernel. On a multicore CPU, the fused traversal is often the better default because the tree is already in cache and the force accumulator is small. The list approach becomes attractive when the traversal is memory-bound and the accepted-node evaluation can be vectorized or when the same tree is traversed by many particles in a way that benefits from batching.

### Memory Layout and Prefetching

The traversal is a pointer-chasing workload unless the tree is stored in arrays. A flat node array with child offsets converts pointer chasing into index arithmetic. Each node record should be cache-line friendly. A common layout stores mass, center of mass (three floats or doubles), node size, child offset, and particle range. If the record is larger than a cache line, a node visit may touch two lines. Padding and alignment matter. The child offset can be an index into the same array; children of a node are often stored contiguously, so the traversal can prefetch the first child while processing the current node. The particle data should be in a structure-of-arrays layout: positions in one array, masses in another, velocities in another. The direct leaf kernel then streams positions and masses without loading unused fields.

Prefetching is difficult because the next node depends on the acceptance test. However, the children of a node are known before the test. A thread can issue prefetches for all children before deciding which one to visit. This is speculative but often useful because the tree is shallow and the children are likely to be visited. Another technique is to store the bounding box or size of each child in the parent record, so the opening test for children can be evaluated without loading the child record. If a child is accepted, the traversal can accumulate its mass from the parent's cached copy. This reduces node visits but increases parent record size. The trade-off is between metadata bandwidth and node visit count.

### SIMD and Divergence

Vectorizing the traversal is not straightforward because different particles make different decisions at the same node. One approach is to process multiple particles per thread and evaluate the same node for all of them. The opening test becomes a vector comparison. Particles that accept the node are accumulated; particles that reject it are marked for descent. The thread then descends only for the subset that rejected the node. This is a form of particle grouping. It increases arithmetic intensity and amortizes node metadata loads across several particles. The cost is divergence management: the thread must maintain multiple stacks or a compacted list of active particles. If the particles are spatially close, they tend to make similar decisions, so divergence is low. Morton ordering helps here because adjacent particles in the sorted array are spatially close. A common compromise is to vectorize the direct leaf kernel, where the work is uniform, and keep the tree traversal scalar. The direct kernel often dominates the interaction count for large theta, so this captures much of the available SIMD benefit without the complexity of vectorized tree walking.

## Work Estimation and Scheduling

The traversal kernel is irregular. The number of node visits and direct interactions per particle depends on the local density and the particle's position relative to the tree. A static partition of particles into equal-sized chunks will not produce equal work. The scheduler must either predict the work or adapt to it.

### Cost Models from Previous Timesteps

Particles move slowly relative to the tree size in many simulations. The tree from the previous timestep is a good predictor of the current tree. The traversal cost per particle can be recorded during the previous force evaluation: node visits, accepted nodes, and direct interactions. These counters can be combined into a scalar cost. The cost array is then used to partition the current timestep. For the first timestep, there is no history. A sample of particles can be traversed to estimate costs, or the scheduler can use a simpler proxy such as leaf occupancy or local density. The proxy does not need to be perfect; it only needs to avoid gross imbalance. If the simulation uses adaptive timesteps or sudden perturbations, the previous cost may be stale. In that case, a hybrid approach that starts with the previous cost and then steals work dynamically can recover.

### Static Partitions and Morton Locality

A static partition divides the Morton-sorted particle array into T contiguous ranges. This preserves spatial locality: each thread reads a contiguous region of the particle array and traverses a similar part of the tree. The problem is that dense clusters are contiguous in Morton order, so one range may contain a cluster and another may contain a void. Equal particle counts do not mean equal work. A cyclic distribution interleaves particles across threads, which mixes densities but destroys locality and increases cache misses. A blocked-cyclic distribution with a moderate block size is a compromise: it mixes densities at a coarse granularity while keeping some locality. The block size should be large enough to amortize scheduling overhead and small enough to balance work.

### Cost-Aware Partitioning

If per-particle costs are available, the scheduler can compute a prefix sum over the cost array and split the particles into ranges of approximately equal total cost. Each thread receives a contiguous range in Morton order, but the range lengths vary. This preserves locality within a range and balances the total work. The prefix sum can be computed in parallel, and the split points can be found with a binary search or a parallel partition. The overhead is small relative to a full force evaluation. The partition can be recomputed every timestep or every few timesteps. Recomputing every timestep is usually affordable because the cost array is already in cache from the previous traversal. The main risk is that the cost model is inaccurate, so the actual work still varies. A dynamic fallback is still useful for the tail.

### Dynamic Scheduling and Work Stealing

Dynamic scheduling assigns work to threads on demand. A shared atomic counter hands out chunks of particles. When a thread finishes a chunk, it fetches the next one. This adapts to actual work without a cost model. The chunk size is the key parameter. Small chunks balance well but increase atomic contention and reduce locality. Large chunks reduce overhead but may leave threads idle at the end. Guided self-scheduling starts with large chunks and decreases the chunk size as the remaining work shrinks. This often works well for irregular loops. Work stealing is a more decentralized alternative. Each thread maintains a deque of particle ranges. When a thread runs out of work, it steals a range from another thread's deque, typically taking half of the remaining range. Work stealing handles irregularity and load imbalance without a global counter. The overhead is in the stealing protocol and the loss of locality when a stolen range is far from the thief's previous work. In an N-body simulation, the stolen range is still a contiguous set of particles, so the thief traverses the tree in a different region but with local particle data. The tree itself is shared and read-only, so there is no false sharing on tree metadata.

### Combining Static and Dynamic

A practical scheduler often combines cost-aware static partitioning with dynamic stealing. The static partition gives each thread a balanced initial range. If a thread finishes early, it steals from the tail of another thread's range. This limits stealing overhead and preserves the cost model's locality. The combination is robust to cost model errors and to variations in thread performance. The scheduler should also consider the cost of the barrier. If the force phase is short, the scheduling overhead can dominate. In that case, a simple static partition with a good cost model may be better than a complex dynamic scheduler.

## Synchronization, Reduction, and Memory Consistency

The force phase is embarrassingly parallel if each particle is owned by exactly one thread. The tree is read-only, so no synchronization is needed for tree access. The force accumulator is private to the thread, so no atomics are needed for force updates. The only synchronization is at the phase boundaries: the tree must be complete before traversal begins, and all forces must be complete before integration begins. A barrier between phases is sufficient. If the implementation uses double buffering for positions, the integration phase can write to a separate array while other threads finish reading the old positions. This is not necessary for a simple timestep, but it can overlap phases if the tree build for the next timestep does not depend on the new positions. In practice, the tree build does depend on the new positions, so the phases are sequential.

False sharing can occur at the boundaries of particle ranges. If two threads write forces for adjacent particles, the cache line ping-pongs between cores. The solution is to align ranges to cache lines or to use per-thread force buffers that are reduced at the end. Per-thread buffers avoid false sharing but add a reduction step. For large N, the reduction is cheap. For small N, it may be significant. The choice depends on the number of particles per thread and the cost of the force evaluation.

NUMA effects are also important. The tree and particle arrays should be allocated with first-touch in mind. If a single thread initializes the entire particle array, all pages are placed on one NUMA node. The other threads will then access remote memory. Parallel initialization, where each thread initializes the particles it will process, distributes the pages. The tree build should also be NUMA-aware if it is parallel. The force array should be initialized by the thread that will write it. These details are not part of the algorithm, but they determine whether the parallel implementation scales.

## Traversal Variants and Practical Tuning

The traversal kernel has several tunable parameters: theta, leaf capacity, maximum tree depth, and the direct kernel's unroll factor. Theta controls the accuracy and the number of interactions. Leaf capacity controls the balance between tree depth and direct work. Maximum depth prevents infinite subdivision for coincident particles. The direct kernel should be unrolled and vectorized because it is a dense loop over a small number of particles. The tree traversal is harder to vectorize, so it is often left scalar. The performance counters that matter are node visits per particle, direct interactions per particle, cache misses per interaction, and instructions per cycle. A change that reduces node visits but increases cache misses may be a net loss. The traversal is memory-bound, so improving locality usually beats reducing arithmetic.

Tree reuse is another practical optimization. If particles move less than a fraction of the leaf size, the tree can be reused for several timesteps. The center of mass of each node can be updated without rebuilding the tree. This saves construction time but may increase traversal cost if the tree becomes stale. The decision depends on the simulation's velocity distribution and the accuracy requirements. A common approach is to rebuild the tree every timestep for accuracy and to optimize the construction phase instead. The construction phase can be parallelized with Morton sorting and a parallel reduction over the sorted particles. The traversal phase then reads a tree that is already in a cache-friendly layout.

The next set of concerns is distributed-memory decomposition, where the tree and particles are partitioned across nodes and the traversal requires communication. But before that, the shared-memory traversal and scheduling choices described here determine the baseline performance that any distributed implementation must preserve.

## Distributed-Memory Decomposition and Halo Exchange

In a distributed-memory setting, the particle array and the tree are no longer shared. Each MPI rank owns a subset of particles and is responsible for computing their forces. The first question is how to partition the particles. A spatial partition is usually better than a random partition because it limits the number of ranks that need to exchange data. A common approach is to assign each rank a contiguous range of the Morton-sorted particle array. The range corresponds to a spatial region, though the Z-order curve does not map to a simple rectangular box. The rank that owns a range owns the particles in that range and builds a local tree over them.

The challenge is that a particle's force depends on particles outside its rank's range. Barnes-Hut does not eliminate the need for remote information; it only compresses it. A rank can approximate a distant group of particles with a single multipole node, but it still needs that node's mass and center of mass. The local tree contains only local particles. To compute forces for its particles, a rank must import enough information from other ranks to cover the rest of the domain.

The traditional solution is a halo exchange. Each rank identifies the particles that are close enough to its boundary to be needed by its neighbors. Those particles are sent to the neighbors, which insert them into their local trees or use them in direct interactions. The halo width depends on the opening criterion and the tree structure. In a direct all-pairs simulation, the halo would need to include all particles within the cutoff radius. In Barnes-Hut, the halo can be much smaller because distant particles are aggregated. However, the halo is not a fixed geometric width. A rank may need multipole nodes from far away, not individual particles. Halo exchange of particles is therefore only part of the story.

A more scalable approach is to exchange tree nodes rather than particles. Each rank builds a local tree and then sends a compressed representation of its tree to other ranks. The receiving rank uses the imported nodes as additional interaction sources. The set of imported nodes is called a local essential tree (LET). The LET contains the nodes from remote trees that are far enough from the local particles to be accepted by the opening criterion. The local rank does not need the remote particles themselves, only the aggregate mass and center of mass of the accepted nodes. This reduces communication volume and makes the exchange independent of the number of particles per node.

The construction of the LET is a communication problem. Each rank needs to know which remote nodes are essential. A naive solution is to have every rank send its entire tree to every other rank. That is O(P^2) communication and defeats scalability. A better solution uses the spatial decomposition. Ranks exchange tree nodes only with ranks that own nearby regions. The exchange can be organized hierarchically: a rank first sends its root node to all others, then refines only for the regions that are close enough to require more detail. This is analogous to a parallel tree traversal where the communication pattern follows the tree structure.

The opening criterion determines how much detail is needed. For a local particle, a remote node is accepted if its size divided by the distance is below theta. A rank can compute a bounding box for its local particles and for each remote node. If the remote node is accepted for all local particles, only the node's multipole is needed. If the node is rejected for some local particles, the rank may need its children. The exchange can be driven by a dual-tree traversal: the local tree and the remote tree are traversed simultaneously, and the communication requests are generated when a remote node is accepted or when a local node is reached. This is the same idea used in fast multipole methods, but with only the monopole term.

The communication volume depends on theta, the distribution, and the number of ranks. Smaller theta means more nodes are rejected and more detail is needed. A dense cluster near a rank boundary can require many nodes from the neighboring rank. The communication pattern is irregular, so it is difficult to predict and optimize statically. The rank must be prepared to handle a variable number of imported nodes. A common implementation stores imported nodes in a separate array and traverses both the local tree and the imported node list. The traversal order can be chosen to maximize locality: local nodes first, then imported nodes, or interleaved by spatial position.

## Global Trees, Local Trees, and the Local Essential Tree

There are three broad strategies for distributed Barnes-Hut trees. The first is a replicated global tree. Every rank stores the entire tree and all particles. This is simple and requires no tree communication, but the memory cost is O(N) per rank. It only works when N is small enough to fit on every rank. The second strategy is a distributed global tree. The tree is partitioned across ranks, and each rank owns a subtree. Traversal for a particle may require visiting nodes owned by other ranks. This requires remote memory access or message passing for each node visit. The communication pattern is irregular and latency-sensitive. The third strategy is the local tree plus LET. Each rank builds a tree over its own particles and imports only the nodes it needs. This is the most common approach for large simulations because it keeps the tree local and makes communication coarse-grained.

The local tree approach has a subtlety: the local tree is built only over local particles. When a particle is near the boundary of the rank's domain, its local tree may not have enough detail in the direction of the neighboring domain. The imported LET fills that gap. The LET must be rebuilt or updated when particles move or when the tree changes. If the tree is rebuilt every timestep, the LET must also be rebuilt. This can be expensive if the communication is frequent. One optimization is to rebuild the local tree every timestep but update the LET only when the particle distribution changes significantly. Another is to use a fixed spatial decomposition and exchange halos of particles, then build a local tree that includes both local and halo particles. This is simpler but can be wasteful if the halo is large.

The choice between particle halos and tree node exchange depends on the cost of communication relative to the cost of tree construction. Particle halos require sending particle data, which is larger per particle than a multipole node. But particle halos allow the receiving rank to build a single tree that includes all particles it needs, which simplifies traversal. Tree node exchange requires less data but more complex bookkeeping. In practice, many codes use a hybrid: they exchange particles for nearby regions and tree nodes for distant regions. The nearby regions are handled by direct interactions or by a local tree that includes the halo particles. The distant regions are handled by imported multipole nodes.

The local essential tree is not just a data structure; it is a contract. The local rank promises that the imported nodes are sufficient to compute forces within the requested accuracy. The remote rank promises that the nodes are up to date. If particles move, the remote rank must update its tree and send new nodes. The synchronization required to maintain this contract can be significant. A common approach is to use a timestep barrier: all ranks finish moving particles, then all ranks rebuild their trees, then all ranks exchange LETs, then all ranks compute forces. This is simple but prevents overlap. More advanced schemes overlap communication with computation by exchanging LETs for the next timestep while computing forces for the current one. This requires double buffering and careful dependency tracking.

## Communication-Aware Load Balancing

Load balancing across ranks is harder than load balancing within a rank. Within a rank, the scheduler can steal work from other threads with low overhead. Across ranks, work stealing requires messages and can be expensive. The partition must be chosen to balance both computation and communication. A partition that gives each rank an equal number of particles may still be imbalanced because the traversal cost per particle varies. A partition that gives each rank an equal amount of work may require more communication if the work is spread across many small regions.

The standard tool for distributed load balancing is a space-filling curve partition. The Morton-sorted particle array is cut into P contiguous ranges, one per rank. The cut points are chosen so that each range has approximately equal estimated work. The work estimate can come from the previous timestep's traversal counters. This approach preserves the spatial locality of the Morton order and limits communication to neighboring ranks. The communication pattern is local: a rank only needs data from ranks that own adjacent ranges. The number of neighbors is small, which keeps the LET exchange manageable.

However, Morton order is not perfect. The Z-order curve can create long jumps between ranges that are adjacent in the sorted order but far apart in space. This can cause a rank to communicate with a rank that is physically distant. Hilbert order reduces this problem but is more expensive to compute. A more robust approach is to use a graph partitioner. The graph is built with particles as vertices and edges between particles that are close enough to interact. The partitioner minimizes the edge cut, which corresponds to communication. Graph partitioning can produce better balance and lower communication than a space-filling curve, but it is more expensive to run and must be repeated when the distribution changes. For large simulations, the cost of graph partitioning may be justified if it reduces communication significantly.

The load balancing decision also depends on the communication model. If the network is fast and the simulation is compute-bound, a simple Morton partition may be sufficient. If the network is slow or the simulation is communication-bound, a graph partitioner may be necessary. The trade-off is not static; it changes with the number of ranks and the particle distribution. A practical approach is to start with a Morton partition and then refine it with a few iterations of graph partitioning or with a diffusion-based load balancer. The refinement can be done in parallel and only every few timesteps.

Data migration is the cost of repartitioning. When the partition changes, particles must move between ranks. The migration cost is proportional to the number of particles that change ownership. If the partition is recomputed every timestep, the migration cost can be high. A common strategy is to repartition only when the imbalance exceeds a threshold. The threshold can be based on the measured load imbalance or on the predicted cost of migration. The decision is a trade-off between the cost of imbalance and the cost of migration. In many simulations, the distribution changes slowly, so repartitioning every tens or hundreds of timesteps is sufficient.

## Hybrid Parallelism and Overlap

Modern HPC systems are hierarchical. A node contains multiple sockets, each with multiple cores, and each core may support multiple hardware threads. The memory hierarchy is non-uniform. A distributed Barnes-Hut simulation should exploit this hierarchy. The natural approach is a hybrid MPI plus threads model. Each MPI rank is assigned to a socket or a NUMA domain. Within a rank, multiple threads share the local tree and the particle arrays. The threads use the shared-memory scheduling techniques described earlier. The MPI ranks communicate only when they need to exchange LETs or halo particles.

This hybrid model reduces the number of MPI ranks and therefore the number of messages. It also allows the threads within a rank to share the tree and the imported nodes, which reduces memory pressure. The shared-memory traversal can use the same cost-aware scheduling and work stealing as a pure shared-memory implementation. The MPI communication is then overlapped with the thread-parallel traversal. Nonblocking MPI calls can be issued for the next timestep's LET while the threads compute the current forces. The threads can also prefetch remote data into local buffers.

The overlap is not automatic. The traversal must be divided into phases: a local phase that does not depend on remote data, and a remote phase that does. The local phase can start as soon as the local tree is built. The remote phase waits for the LET. If the LET is large, the wait can be significant. A common technique is to split the LET into small messages and process them as they arrive. The traversal can be reordered to process local nodes first, then remote nodes as they become available. This requires a traversal that can be paused and resumed, or a task-based approach where each imported node is a task.

The performance of the hybrid model depends on the ratio of computation to communication. If the computation per particle is high, the communication can be hidden. If the computation is low, the communication dominates. The ratio can be controlled by theta and leaf capacity. A larger theta reduces computation and increases the relative cost of communication. A smaller theta increases computation and makes it easier to hide communication. The optimal parameters for a distributed simulation may differ from those for a shared-memory simulation. The tuning process must consider the network latency and bandwidth, not just the cache hierarchy.

The next step is to consider the interaction between the tree build and the communication. The tree build is a parallel reduction over particles. In a hybrid model, the reduction is first within a node, then across MPI ranks. The global tree is not built explicitly; instead, each rank builds a local tree and the LET exchange provides the global information. The local tree build can be parallelized with the same Morton sorting and prefix sum techniques used in the shared-memory case. The MPI ranks exchange only the tree nodes that are needed. The communication pattern is determined by the spatial decomposition, which is itself determined by the load balancing. This creates a feedback loop: the load balancer needs to know the communication cost, but the communication cost depends on the partition. Breaking this loop requires a cost model that estimates both computation and communication for a given partition. The cost model can be calibrated with measurements from previous timesteps.

## Instrumentation Without Distorting the Workload

A parallel Barnes-Hut code can be tuned by intuition for a while, but beyond a few hundred thousand particles the intuition runs out. The same particle can be cheap in one timestep and expensive in the next because its neighborhood changes, because the tree shape changes, or because a dense cluster moves across a leaf boundary. To make scheduling decisions and to explain performance, the implementation needs measurements. The measurements must be cheap enough that they do not become the workload.

The first distinction is between structural counters and hardware counters. Structural counters describe the algorithm: how many nodes a particle opened, how many nodes it accepted, how many particles it evaluated directly in leaves, how many direct pairs it formed, how deep its stack grew, and how many imported nodes it visited. Hardware counters describe the machine: cycles, instructions, cache misses, memory bandwidth, and stalls. Structural counters are portable and directly useful for load balancing. Hardware counters are platform-specific and useful for explaining why a structural change helped or hurt. A production code should be able to collect both, but not at the same time in the inner loop.

The naive way to collect structural counters is to increment a shared counter for every node visit. That is a mistake. A shared counter in the traversal kernel serializes the workload and turns a read-only tree walk into a contention benchmark. The correct pattern is a per-thread accumulator. Each thread keeps a small struct with counters for opened nodes, accepted nodes, leaf particles, and direct pairs. The struct stays in registers or L1 cache. At the end of the force phase, the per-thread structs are reduced into a global summary. The reduction is cheap and happens once per timestep. If the code needs per-particle costs for scheduling, each thread writes a compact cost value into a per-particle array. The cost value can be a weighted sum of the counters, or it can be a packed integer with separate fields. A packed integer is often better because it preserves the components for later analysis without additional memory traffic.

The cost of counting is not zero. An increment in the inner loop can prevent vectorization, increase register pressure, and add instructions to a kernel that is already memory-bound. The implementation should therefore support at least two modes. In the fast mode, counters are compiled out or reduced to a single sampled counter. In the instrumented mode, counters are collected for every particle. The instrumented mode is used for calibration runs, for diagnosing load imbalance, and for generating the cost array used by the scheduler. The fast mode is used for production. A useful compromise is to count only at the leaf level and to estimate node visits from the tree depth. That loses accuracy but keeps the inner loop clean.

Phase timers are the other half of instrumentation. A timestep is not one homogeneous phase. It includes sorting or reordering particles, building or updating the tree, computing local aggregates, exchanging imported nodes, traversing the tree, and integrating positions. Timing the whole timestep hides which phase changed. The timers should be placed at phase boundaries and should include the cost of synchronization. A barrier before starting a timer and a barrier after stopping it gives a clean measurement, but the barriers themselves perturb the schedule. For relative comparisons, the perturbation is usually acceptable. For absolute throughput, the timers should be sampled over many timesteps and the barrier cost should be estimated separately.

The most useful derived metric is not total time but work per unit time and imbalance ratio. Work per unit time is the number of direct interactions plus a weighted number of node visits divided by the traversal time. It tells whether a change improved the kernel or merely moved work between phases. The imbalance ratio is the maximum thread work divided by the mean thread work. A ratio near one means the scheduler is doing its job. A ratio well above one means either the cost model is wrong or the dynamic scheduler is not stealing effectively. The ratio should be measured for the force phase alone, not for the whole timestep, because tree construction and integration have different balance properties.

Hardware counters answer a different question. If the traversal time increases while the structural work stays constant, the cause is likely cache behavior, memory bandwidth, or frequency scaling. Cache misses per accepted node and instructions per direct interaction are more informative than raw cache miss totals. A node visit that misses in L2 but hits in L3 is cheaper than a visit that goes to DRAM. The tree layout should be evaluated with that hierarchy in mind. A flat node array with contiguous children may reduce L2 misses but increase the size of each node record. A compact record may fit more nodes in L2 but require more index arithmetic. The counters should be used to choose between layouts, not to justify a layout after the fact.

Instrumentation also has a social function. It makes performance claims reproducible. A statement that a scheduling policy is better should be accompanied by the workload distribution, the theta value, the leaf capacity, the thread count, and the measured imbalance. Without those, the result is an anecdote. The counters and timers are the evidence that lets another engineer reproduce the experiment or explain why it does not transfer.

## Accuracy Budgets as Engineering Contracts

The opening angle theta is often treated as the accuracy knob. It is not an accuracy guarantee. Theta controls when a node is accepted, but the error of a Barnes-Hut force evaluation depends on the mass distribution inside the accepted node, the distance from the particle to the node, the softening, the leaf capacity, and the history of the tree. A simulation that uses a single theta value and assumes the error is bounded is making an implicit contract without checking it.

A better approach is to define an accuracy budget. The budget states how much error the application can tolerate in the force, how that error is measured, and which sources of error consume the budget. The sources are not independent. The monopole approximation contributes error when a node is accepted. The direct leaf evaluation contributes error only through floating-point rounding, but the leaf capacity determines how many interactions are exact and how many are aggregated. Softening changes the force law and therefore changes the error relative to the unsoftened model. Integration error accumulates across timesteps. A stale tree adds error when particles move after the tree was built. Morton ordering itself does not change the physics, but the quantization used to compute codes can affect the tree shape and therefore the set of accepted nodes.

The monopole error is often described as second order in the opening angle. That description is useful but incomplete. The center of mass removes the dipole term, so the first neglected term is the quadrupole. The size of that term depends on the shape of the mass distribution. A spherical node has a small quadrupole; a elongated or asymmetric node can have a larger one. Two nodes with the same size and the same center of mass can produce different errors. A conservative opening criterion should therefore use the node's bounding radius or the distance to the nearest point of the node, not only the distance to the center of mass. The center-of-mass criterion is cheaper, but it can accept a node whose mass is concentrated toward the particle. The bounding-box criterion is more expensive but gives a tighter error estimate.

An accuracy budget should be validated against a direct sum. For small N, the direct sum is the reference. The validation should compare not only the mean relative error but also the distribution of errors. A mean error of one percent can hide a tail where a few particles have ten percent error. The tail matters because those particles can dominate the energy error or the trajectory divergence. The comparison should be done for several distributions: uniform random, a concentrated cluster, a thin disk, and a mixture of dense and sparse regions. A theta value that works for a uniform distribution may fail for a cluster because the cluster produces deep trees and asymmetric nodes.

For large N, a full direct sum is too expensive. The validation can sample particles and compute their forces directly against all particles. The sample should be stratified by spatial region and by estimated cost. Particles in dense regions and particles near tree boundaries are more likely to reveal errors. The sampled direct sum does not prove the global error bound, but it catches gross mistakes in the opening criterion, the center-of-mass calculation, and the leaf handling.

The error budget also interacts with load balancing. A smaller theta increases the number of accepted nodes and direct interactions, which increases work and usually increases imbalance. The scheduler must be tuned for the theta that the application actually uses. A cost model calibrated at theta equal to 0.7 may be wrong at theta equal to 0.4 because the relative cost of node visits and direct interactions changes. The accuracy choice and the scheduling choice are therefore coupled. The application should document both and should revalidate when either changes.

Finally, the error budget should be part of the configuration, not a comment in the source. The configuration should record theta, leaf capacity, softening, maximum depth, and the tree reuse policy. A regression test should compare the force error against the reference for a fixed particle set. If the error exceeds the budget, the test fails. That is a stronger contract than a note that the simulation is approximate.

## Determinism Modes and Their Costs

Determinism is often discussed as a binary property. In practice, a parallel simulation needs at least three modes. The fast mode prioritizes throughput and may use dynamic scheduling, approximate cost models, and compiler optimizations that change floating-point association. The deterministic mode fixes the order of reductions and the tree build so that repeated runs with the same thread count produce the same result. The bitwise mode fixes the result across thread counts and across runs, which is stronger and more expensive.

It is useful to separate the sources of nondeterminism. The force phase is often more deterministic than people assume. If each particle is owned by exactly one thread and the tree is fixed, the particle's traversal order is fixed by the stack discipline. Changing which thread computes the particle does not change the order in which that particle visits nodes. The force accumulator is private, so there is no atomic addition and no interleaving. The nondeterminism comes from the tree build, from reductions across threads, and from any phase that changes the particle order or the tree metadata. A dynamic scheduler that steals particle ranges does not change the per-particle force if the tree and the traversal order are unchanged. It changes when the particle is computed, not how.

The tree build is the main source. Building aggregate mass and center of mass is a reduction over particles. If the reduction is parallel and the reduction tree depends on the thread count, the floating-point result can differ. A fixed reduction tree, independent of thread count, makes the result deterministic. The cost is that the reduction may not use all threads efficiently. A hierarchical reduction that first reduces within fixed blocks and then reduces the block results in a fixed order is a good compromise. The block size is fixed, so the order is fixed, but the within-block reduction can still be parallel.

Sorting is another source. A parallel sort must be stable or must use a deterministic tie-break. Morton codes can collide, especially when the quantization is coarse or when particles share coordinates. If the sort is unstable, particles with the same code can appear in different orders across runs. That changes the leaf ranges and the tree shape. The tie-break should use a stable particle identifier. The identifier should be independent of the thread that initialized the particle. A deterministic tie-break is cheap and removes a whole class of reproducibility bugs.

The opening criterion and the direct kernel also need deterministic arithmetic. Compiler flags that allow reassociation or contraction can change results across builds. That is acceptable in fast mode but not in bitwise mode. The bitwise mode should use a fixed evaluation order, avoid fused multiply-add differences unless they are part of the contract, and avoid math library functions that are not correctly rounded. The cost is usually small for the traversal kernel, but it can be larger for the tree build because the reduction is where most of the floating-point variation occurs.

Deterministic scheduling is possible without giving up all load balancing. A cost-aware static partition is deterministic if the cost array and the split points are deterministic. A deterministic work-stealing policy can also be used: the victim selection and the amount stolen are fixed by thread identifier and range identifier, not by timing. The result is reproducible while still adapting to imbalance. The cost is that the schedule may be less efficient than a timing-dependent policy. For many simulations, the difference is small compared with the cost of debugging a nondeterministic result.

A practical code should expose determinism as a runtime option and should document the cost. The fast mode should be the default for production runs that only need statistical reproducibility. The deterministic mode should be used for regression tests and for publications that require repeatable trajectories. The bitwise mode should be used when results must be compared across machines or thread counts. The modes should share the same physics and the same tree layout; only the reduction order and scheduling policy should change. That keeps the comparison meaningful.

## Defensive Tree Maintenance and Failure Modes

Most Barnes-Hut failures are not failures of the approximation. They are failures of the tree maintenance code. The tree is rebuilt or updated every timestep, and the update path is where degenerate geometry, stale metadata, and boundary conditions cause trouble. A defensive implementation should make those failure modes explicit.

Coincident particles are the classic case. If several particles have the same position, recursive subdivision can continue until the maximum depth is reached. A leaf with many coincident particles is not wrong, but it can be expensive because the direct kernel evaluates all pairs within the leaf. The implementation should either cap the depth and accept a dense leaf, apply a deterministic jitter, or use a special leaf representation that handles the coincident group as a single aggregate. The choice affects accuracy and reproducibility. A maximum depth with a dense leaf is deterministic and preserves the physics, but the cost can be high. Jitter is cheaper but changes the result. The application should choose deliberately and should record the choice in the configuration.

Zero-mass nodes are another case. If a node has zero total mass, its center of mass is undefined. The traversal should skip such nodes rather than divide by zero. The tree builder should also avoid creating empty octants when possible. Empty nodes waste memory and traversal time. A linear octree can skip empty ranges entirely, but the indexing must still be correct. The builder should validate that every child range is within the parent range and that the ranges do not overlap.

Stale trees are a performance and accuracy hazard. If the tree is reused across timesteps, the node centers of mass must be updated. A particle that moves far enough can change the set of nodes that should be accepted for a given opening angle. The implementation should bound the reuse by a displacement criterion: if a particle moves more than a fraction of the leaf size, rebuild the tree. The fraction should be tied to theta. A larger theta tolerates more staleness because the accepted nodes are larger and the error is less sensitive to small displacements. A smaller theta requires more frequent rebuilding. The criterion should be checked before the force phase, not after, so that the tree used for forces is consistent with the positions.

Incremental updates are attractive because they avoid rebuilding the whole tree. The update must move a particle from its old leaf to its new leaf, update the mass and center of mass along both paths, and split or merge leaves as needed. Splitting is straightforward; merging is harder because it can cascade. A common compromise is to split on overflow but not to merge on underflow until the next full rebuild. That keeps the tree valid and avoids the cost of cascading merges. The tree may become sparse, but the traversal still works. The cost model should account for the sparse nodes because they add node visits without adding useful aggregation.

Finally, the implementation should include assertions and unit tests for the tree invariants. Every particle should belong to exactly one leaf. Every leaf range should be within its parent range. Every internal node should have at least two non-empty children unless it is a leaf. The total mass of a node should equal the sum of its children's masses within rounding tolerance. The center of mass should lie within the node's bounding box. These checks are cheap in debug builds and catch the errors that otherwise appear as mysterious force spikes or missing particles. The checks are not a substitute for validation against a direct sum, but they make the failure modes visible before they corrupt a long simulation.
