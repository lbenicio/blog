# NUMA-Aware Memory Placement for Parallel In-Memory Systems: First-Touch, Thread Affinity, and the Cost of Remote Access

## The problem hiding behind the socket boundary

A parallel in-memory system that runs on one socket can often pretend that memory is a flat, uniform resource. Every core sees the same memory controller, the same last-level cache complex, and roughly the same latency to DRAM. That fiction breaks as soon as the process spans two or more sockets, or a single socket with multiple memory controllers and sub-NUMA clusters. The CPU is no longer the only scarce resource. The placement of pages, the placement of threads, and the traffic between them become first-class design variables.

Non-uniform memory access, or NUMA, is not a single feature. It is a family of hardware organizations in which a processor and some memory are closer to each other than to other memory. A NUMA node is usually a set of cores plus a memory controller and its attached DRAM. Accessing local memory goes through the local controller. Accessing remote memory goes through an interconnect and then through another node's controller. The latency difference is real, but latency is only part of the story. Remote bandwidth is shared with cache-coherence traffic, I/O, and other remote accesses. A workload can be latency-bound, bandwidth-bound, or limited by the interconnect's queueing behavior, and each case demands a different placement strategy.

This article is about the engineering discipline of NUMA-aware memory placement for parallel in-memory systems: databases, caches, graph engines, stream processors, scientific kernels, and machine-learning runtimes that keep their working set in RAM. The focus is on shared-memory systems, not distributed systems that happen to use many machines. The assumptions are ordinary: x86-64 or ARM64 servers, Linux or a comparable kernel, hardware with exposed NUMA topology, and applications that can control thread and memory placement to some degree. The goal is not to promise a single configuration. It is to make the trade-offs explicit.

## A mental model of NUMA hardware

The kernel discovers NUMA topology from firmware tables such as ACPI SRAT and SLIT. SRAT describes which memory ranges and processors belong to which proximity domain. SLIT provides relative distances between domains. Tools such as `numactl --hardware`, `lscpu`, and `lstopo` expose a simplified view. The details matter because modern servers are not always symmetric. A machine may have two sockets, each with multiple memory controllers. It may expose sub-NUMA clustering, where one socket is split into two or more NUMA nodes to improve locality. It may have high-bandwidth memory and ordinary DRAM on the same package, with different distances and capacities. It may attach memory over a coherent interconnect such as CXL, creating a slower tier that is still cache-coherent.

The simplest model is a graph. Nodes are vertices. Edges have distances. A thread on node 0 accessing a page on node 0 is local. A thread on node 0 accessing a page on node 1 is remote. The distance is not a fixed constant. It depends on the interconnect topology, the number of hops, and the current load. On many two-socket systems, remote access is slower but not catastrophically so. On larger systems, the difference can be larger. On systems with memory-side caches or tiered memory, the effective latency depends on whether the line is cached near the memory controller.

Bandwidth is the more subtle constraint. Local DRAM bandwidth is bounded by the memory controller and the number of channels. Remote bandwidth is bounded by the interconnect and by the remote node's controller. If every thread on every node streams through remote memory, the interconnect becomes the bottleneck. If threads are spread across nodes and access local memory, aggregate bandwidth can be higher. This is why interleaving pages across nodes can help streaming workloads even though it guarantees that some accesses are remote. The point is not to eliminate remote access. The point is to avoid concentrating it on one path.

Cache coherence adds another layer. When a core writes a cache line, it must invalidate or update other copies. If the line is shared across nodes, the coherence traffic crosses the interconnect. False sharing, where two threads on different nodes write to different variables on the same cache line, can generate a ping-pong pattern that consumes interconnect bandwidth and adds latency to unrelated work. Padding and per-node sharding are common defenses. They cost memory and can hurt cache utilization, but they often pay for themselves in write-heavy parallel code.

## Page placement is physical, not virtual

Virtual memory hides physical placement from the program. A virtual page maps to a physical frame, and that frame lives on some NUMA node. The mapping is controlled by the operating system and the hardware page tables. The application can influence it through allocation policies, but it cannot assume that a virtual address range is local. This is the root of many NUMA bugs. A data structure is allocated, initialized, and then used by threads that run on different nodes. The pages may have been placed on the node of whichever thread first touched them. If that thread was on the wrong node, every subsequent access is remote.

First-touch is the default behavior for anonymous memory on many Linux systems. When a thread first writes to a page, the kernel allocates a physical frame, usually from the node of the thread's current CPU. Reading a page that was never written may also trigger allocation, depending on the mapping and the kernel's behavior. The implication is direct: the thread that initializes a page determines its node. If initialization is parallel and the threads are placed differently from the compute phase, the pages can be systematically misplaced. A common pattern is to allocate a large array with `malloc`, initialize it in a parallel loop, and then run a compute loop with a different OpenMP schedule or thread affinity. The compute loop inherits pages that were placed by the initializer threads.

The fix is not always to pin threads. Sometimes the right answer is to initialize with the same affinity as the compute phase. Sometimes it is to use an explicit memory policy. Linux exposes policies through `mbind`, `set_mempolicy`, and the `numactl` command. `MPOL_BIND` restricts allocation to a set of nodes. `MPOL_PREFERRED` prefers one node but allows fallback. `MPOL_INTERLEAVE` spreads pages across nodes in a round-robin fashion. `MPOL_LOCAL` allocates on the node of the faulting thread. These policies can be set per process or per memory range. They interact with cgroups, container runtimes, and the kernel's automatic page migration.

Automatic NUMA balancing is a separate mechanism. The kernel can periodically unmap pages, take faults, and migrate pages toward the nodes that access them most. This can help long-running workloads with changing access patterns. It can also add overhead, cause page migrations that interfere with latency-sensitive code, and thrash when access patterns are mixed. The trade-off is between adaptivity and predictability. For a database with a stable sharding scheme, explicit placement is often better. For a general-purpose service with unpredictable access, automatic balancing may be a reasonable default. The kernel's decisions are heuristics, not guarantees.

Huge pages change the granularity of placement. A 4 KiB page can be placed independently. A 2 MiB transparent huge page or a 1 GiB hugetlbfs page is a single unit. First-touch on a huge page places the entire page on one node. If the page is large and the working set is spread across nodes, this can create remote access for many threads. Interleaving huge pages across nodes can balance bandwidth, but it can also increase remote latency for pointer-chasing workloads. Huge pages reduce TLB misses and page-table overhead, but they can increase internal fragmentation and make migration expensive. The choice depends on access pattern, not on a universal rule.

## Thread placement and allocator behavior

Thread placement is the other half of the problem. A page can be local only relative to a node. If threads migrate between nodes, the same page is local for some accesses and remote for others. Linux tries to keep threads on their current node, but the scheduler can move them for load balancing, thermal reasons, or because of cgroup constraints. Affinity masks restrict migration. `sched_setaffinity`, `taskset`, `numactl --physcpubind`, and OpenMP's `OMP_PROC_BIND` and `OMP_PLACES` can pin threads to cores or nodes. MPI runtimes and job schedulers such as SLURM provide similar controls. The details are easy to get wrong because hardware threads, core siblings, and NUMA nodes form a hierarchy.

Pinning is not free. If a thread is pinned to one core, it cannot run elsewhere when that core is busy. If a parallel loop has imbalanced work, pinning can turn a small imbalance into a large tail. If the machine is shared, pinning can conflict with other jobs. The trade-off is locality versus flexibility. A common compromise is to bind threads to a node but not to a specific core, or to bind to a set of cores that share a last-level cache. The right granularity depends on the workload and the scheduler.

Memory allocators add another layer of indirection. General-purpose allocators such as glibc `malloc`, jemalloc, and TCMalloc maintain per-thread or per-CPU caches to reduce contention. Those caches may hold memory from a node that is not the current thread's node. A thread can allocate on node 0, migrate to node 1, and then free the object on node 1. The allocator may return the memory to a cache on node 1 or to a global pool. Over time, the heap can become a mixture of local and remote pages. Some allocators expose arena or node binding. jemalloc, for example, has arenas and can be configured with `MALLOC_CONF` options related to per-CPU and per-arena behavior. TCMalloc has per-CPU caches and can be tuned. glibc malloc has per-thread arenas and `MALLOC_ARENA_MAX`. None of these are NUMA-aware by default in the sense of guaranteeing local placement. They reduce contention, but they do not replace an explicit placement policy.

The interaction between allocator caches and NUMA is especially important for long-running services. A request handler may run on node 0, allocate a buffer, and pass it to a background thread on node 1. The buffer is remote for the background thread. If this happens often, the service accumulates remote traffic. A NUMA-aware design might use per-node object pools, per-node queues, and explicit handoff rules. The cost is complexity. The benefit is predictable locality.

## Interleaving, replication, and partitioning

There are three broad strategies for placing shared data across NUMA nodes: interleaving, replication, and partitioning. They are not mutually exclusive, and real systems often combine them.

Interleaving spreads pages across nodes, usually at page granularity. It is attractive for read-only or streaming data because it balances bandwidth across memory controllers. A parallel scan of a large array can benefit from interleaving even though half the accesses are remote, because the aggregate bandwidth is higher than if all pages were on one node. Interleaving is less attractive for pointer chasing, small random reads, or latency-sensitive code. The remote latency is paid on every access, and the interconnect may become a queueing point under load. Interleaving also makes page placement less predictable, which complicates profiling and capacity planning.

Replication keeps a copy of read-mostly data on each node. A thread reads its local copy and avoids remote traffic entirely. The cost is memory footprint and update complexity. If the data is immutable, replication is simple. If it changes, the system must propagate updates and decide how to handle consistency. For small configuration tables, routing tables, or machine-learning parameters, per-node replicas can be effective. For large datasets, replication may be impossible because the memory is not available. Replication also interacts with cache coherence: if replicas are on different nodes and are written, the coherence protocol must invalidate remote copies. Read-mostly is the key condition.

Partitioning assigns each piece of data to a node and routes accesses to the owning node. A sharded hash table, for example, can place shard 0 on node 0 and shard 1 on node 1. A thread on node 0 that needs shard 1 pays remote access, but the system can minimize cross-shard traffic by co-locating related data. Partitioning is the natural strategy for write-heavy workloads because it avoids coherence ping-pong on shared cache lines. It also scales with the number of nodes, provided the partitioning is balanced and the routing is cheap. The hard part is choosing the partition key and handling skew. A hot shard on one node can saturate that node's memory controller while other nodes are idle.

The choice among these strategies depends on the access pattern, the read-write ratio, the size of the working set, and the cost of synchronization. A streaming analytics job may interleave. A read-mostly cache may replicate. A transactional database may partition. A graph engine may do all three: partition vertices, replicate high-degree vertices, and interleave edge lists. The common mistake is to treat NUMA as a deployment detail rather than a design constraint. By the time the system is in production, the placement policy is buried in kernel defaults, allocator configuration, and thread affinity settings. Making it explicit early is cheaper than debugging remote traffic later.

## Observability: what to measure and what not to trust

NUMA problems are hard to see with CPU profiles alone. A function can be hot because it is doing useful work, or because it is waiting on remote memory. A flat profile may hide the interconnect. The first step is to confirm the topology and the placement of threads and pages. `numactl --hardware` shows nodes and distances. `lscpu` shows sockets, cores, and threads. `lstopo` from hwloc renders the hierarchy. `numastat` shows per-node memory statistics and allocation misses. `/proc/self/numa_maps` shows how a process's virtual memory ranges map to nodes. `/sys/devices/system/node/node*/meminfo` shows per-node memory usage.

The kernel's `/proc/vmstat` exposes counters such as `numa_hit`, `numa_miss`, `numa_foreign`, `numa_interleave`, `numa_local`, `numa_other`, and `numa_pages_migrated`. Their exact meanings are subtle and have changed across kernel versions. They are useful for spotting trends, but they are not a substitute for hardware performance counters. `perf stat` can count local and remote memory accesses on some CPUs. `perf mem` can sample loads and stores. `perf c2c` can detect cache-line contention and HITM events that indicate cross-node sharing. Vendor tools such as Intel VTune and AMD uProf provide similar views with more polish. eBPF tools can trace page faults, scheduler migrations, and allocator behavior.

Measurement has traps. Sampling memory accesses is biased by the sampling period and by the code that happens to be running. Counters may not distinguish between local DRAM, remote DRAM, and memory-side cache hits. Page migration counters can increase without improving performance if the kernel is thrashing. The most reliable approach is to combine coarse-grained counters with controlled experiments: run the same workload with different placement policies, hold the thread mapping fixed, and measure both throughput and tail latency. The goal is not to attribute every nanosecond. It is to determine whether the bottleneck is local bandwidth, remote latency, coherence traffic, or something else entirely.

## Workload families and their placement instincts

Different workloads have different instincts. A bandwidth-bound streaming kernel wants data spread across nodes and threads spread across cores, with each thread reading mostly local or interleaved pages. A latency-bound pointer-chasing workload wants its working set on the node where the thread runs, even if that means less aggregate bandwidth. A shared read-only table wants replication or per-node copies. A write-heavy hash table wants partitioning and padding to avoid false sharing. A producer-consumer pipeline wants the queue and the consumer on the same node, with the producer either on the same node or connected by a carefully sized remote handoff. A graph traversal with irregular access is the hardest case: the working set may not fit, the access pattern is data-dependent, and interleaving may be the only way to avoid a single-node hotspot.

The next sections apply these mechanics to concrete systems: parallel initialization patterns, per-node allocators, sharded indexes, streaming data structures, and the interaction between NUMA placement and modern memory tiers. The central question remains the same: which accesses should be local, which can be remote, and what does the system pay for each choice?

### Parallel initialization as a placement contract

A parallel program has at least two placement phases: the phase that creates pages and the phase that uses them. Treating them as independent is the source of many NUMA regressions. The initialization loop is not just setup; it is the moment when the operating system chooses physical frames. If the initialization loop and the compute loop have different thread-to-node mappings, the compute loop starts with a placement debt.

The cleanest pattern is to make the contract explicit. Decide which node should own each page, then ensure that a thread on that node performs the first write. For a one-dimensional array split across nodes, that means partitioning the index range by node and initializing each range from a thread bound to that node. In OpenMP, this can look like:

```c
#pragma omp parallel for schedule(static)
for (size_t i = 0; i < n; ++i) {
    a[i] = 0;
}
```

This is only NUMA-aware if the OpenMP runtime binds threads consistently and if the loop's static chunks align with node boundaries. `OMP_PROC_BIND=close` and `OMP_PLACES=cores` help, but the mapping from iteration chunks to nodes is not guaranteed. A more explicit version uses `numa_run_on_node` or `sched_setaffinity` before the parallel region, then divides the work by node. The cost is portability; the benefit is that the placement is visible in the source.

Explicit allocation APIs make the contract even clearer. `numa_alloc_onnode(size, node)` returns memory whose pages are intended for that node. `numa_alloc_local(size)` uses the calling thread's current node. `numa_alloc_interleaved(size)` spreads pages across all nodes. These functions are wrappers around `mmap` plus `mbind` or `set_mempolicy`, and they are available in `libnuma`. They do not eliminate first-touch; they set a policy that the kernel applies when pages are faulted in. If the policy is `MPOL_BIND`, the kernel allocates only from the specified nodes. If it is `MPOL_PREFERRED`, it tries the preferred node and falls back. If it is `MPOL_INTERLEAVE`, it cycles through the nodemask.

The order of operations matters. Calling `mmap` and then `mbind` is not atomic. Pages that are faulted in between the two calls may be placed according to the old policy. Calling `set_mempolicy` before `mmap` avoids that race for the calling thread, but `set_mempolicy` is per-thread and inherited in ways that can surprise. `mbind` on a range is more local, but it requires page-aligned addresses and lengths. `MPOL_MF_MOVE` can migrate pages that already exist, but migration is expensive and can fail under memory pressure. For large allocations, the safest sequence is to reserve the virtual range, apply the policy, and only then touch the pages.

`MAP_POPULATE` deserves a warning. It prefaults the mapping, but it does so in the context of the calling thread. If a single thread calls `mmap(..., MAP_POPULATE)` for a multi-gigabyte region, all pages are placed on that thread's node. That is rarely what a parallel program wants. Parallel initialization is usually better: let each thread fault its own range. `MADV_POPULATE_WRITE` can be used per range, but the same rule applies: the thread that calls it determines the placement.

Huge pages change the unit of the contract. A 2 MiB transparent huge page is placed as a whole. If two threads on different nodes touch different 4 KiB subpages of the same huge page, the first touch places the entire 2 MiB page. The second thread then accesses remote memory for its part. To avoid this, align node partitions to huge-page boundaries and ensure that each huge page is touched by threads on a single node. `madvise(MADV_HUGEPAGE)` encourages the kernel to use huge pages; `MADV_NOHUGEPAGE` discourages them. `MADV_COLLAPSE` can attempt to collapse existing small pages into a huge page, but the collapse may fail if the pages are not contiguous or if the policy does not allow it. For latency-sensitive pointer chasing, huge pages can reduce TLB misses but increase remote access if the working set is spread. For streaming, they usually help.

If the initialization phase cannot be changed, `move_pages` can correct placement after the fact. It takes an array of page addresses and target nodes, and it migrates pages that are not already on the target. The cost is proportional to the number of pages moved, and the migration itself consumes memory bandwidth. It is a repair tool, not a design. The same is true of automatic NUMA balancing: it can fix a bad initial placement, but it does so with kernel heuristics and background overhead. A program that knows its access pattern should not rely on the kernel to guess it.

### Per-node allocators and the cost of remote free

General-purpose allocators are optimized for contention, not for locality. A thread-local cache can satisfy most allocations without a lock, but the memory in that cache may belong to any node. When a thread migrates, its cache follows the thread, not the node. The result is a heap that drifts. A service that runs for days can accumulate a large fraction of remote pages even if every individual allocation was local at the time it was made.

A NUMA-aware allocator starts with per-node arenas. Each arena owns a contiguous region of virtual address space that is bound to one node. Threads allocate from the arena of their current node. If a thread needs an object from another node, it either allocates remotely or requests a transfer. The design question is how to handle frees. Freeing an object to the arena that owns it is the natural choice, but the freeing thread may be on a different node. The free operation then becomes a remote write to the owning arena's metadata. If frees are frequent, that remote traffic can dominate.

The standard solution is a remote free queue. Each arena has a small queue for objects freed by remote threads. The freeing thread pushes the pointer onto the queue with an atomic operation. The owning arena drains the queue in batches when it needs memory or when the queue crosses a threshold. Batching amortizes the remote access and turns many small writes into a few cache-line transfers. The queue itself must be cache-line padded to avoid false sharing between the producer and consumer indices. A ring buffer with a capacity of a few hundred entries is usually enough; if the queue fills, the freeing thread can either allocate a temporary local buffer or fall back to a slower path.

The same idea applies to object pools. A per-node pool of fixed-size objects can be a simple free list. The free list head is a pointer in the arena's metadata. Local allocations and frees are just pointer swaps. Remote frees go through the queue. If the workload has a clear producer-consumer structure, the pool can be specialized: the producer allocates from its node, the consumer frees to the producer's node, and the queue carries the objects back. This is a form of ownership transfer. It works well when the object size is small and the handoff rate is moderate. For large objects, the cost of copying or migrating may be lower than the cost of repeated remote access.

Allocator configuration matters. jemalloc exposes `narenas`, `percpu_arena`, and `background_thread` options. Setting `percpu_arena:phycpu` or a similar mode can create per-CPU arenas that reduce cross-thread frees, but it also increases memory fragmentation and metadata overhead. TCMalloc has per-CPU caches and options for total thread cache size. glibc malloc uses per-thread arenas and `MALLOC_ARENA_MAX`. None of these settings are universally correct. The right values depend on the number of threads, the allocation size distribution, and the lifetime of objects. A service with many short-lived objects benefits from larger caches; a service with long-lived objects benefits from fewer arenas and more predictable placement.

A subtle cost is the remote free of large objects. When a large object is freed to a remote arena, the allocator may need to update metadata, coalesce with neighbors, and possibly return pages to the kernel. If the object spans multiple pages, the metadata updates touch multiple cache lines on the owning node. A deferred free queue that stores `(pointer, size)` pairs can batch these updates, but it also delays memory reuse. Under memory pressure, the delay can cause the process to allocate new pages while freed pages sit in a remote queue. The allocator needs a policy for draining queues when free memory is low. A simple approach is to drain all remote queues before requesting more memory from the kernel. That adds latency to the allocation slow path but keeps the footprint bounded.

For long-running systems, it is worth measuring the fraction of remote frees. A counter in the allocator can track how many objects are freed to a node different from the one where they were allocated. If that fraction is high, the workload has a locality mismatch that no allocator can fix. The data flow itself may need to change: co-locate producers and consumers, partition queues by node, or migrate the object instead of passing a pointer. The allocator can only make the best of the access pattern it is given.

### Sharded indexes and partitioned data structures

Sharded indexes are the most direct way to apply partitioning. A hash table, B-tree, or radix tree is split into shards, and each shard is bound to a node. The routing function maps a key to a shard. A lookup from a thread on node 0 to a shard on node 1 is a remote access, but the number of remote accesses can be controlled by the routing and by caching.

The first design choice is the shard key. If the key is well distributed, each node gets a balanced share of the data and the traffic. If the key is skewed, one node becomes a hotspot. A common mistake is to hash the key and then use the hash modulo the number of nodes. That works until the number of nodes changes or until the hash function has a bias. Consistent hashing or a fixed number of virtual shards mapped to nodes can make rebalancing easier. The virtual shards can be migrated between nodes with `move_pages` when the load changes.

The second choice is the granularity of the shard. A single large shard per node is simple, but it can create lock contention and memory imbalance. Many small shards per node allow finer-grained migration and better load balancing, but they increase metadata overhead and the cost of routing. A middle ground is to use a fixed number of shards that is a multiple of the number of nodes, and to map shards to nodes in a way that keeps related keys together. For a B-tree, the root and upper levels can be replicated on every node, while the leaves are partitioned. The root is small and read-mostly, so replication is cheap. The leaves are large and write-heavy, so partitioning avoids coherence traffic.

Locking must follow the same placement. A per-shard lock should live on the same node as the shard's data. If the lock is on a different node, every lock acquisition is a remote access. The lock word and the data it protects should share a cache line only if they are always accessed together; otherwise, padding the lock to its own cache line avoids false sharing with the shard's first data element. For read-mostly shards, a read-write lock or a sequence lock can reduce contention. For write-heavy shards, a simple spinlock or a queued lock may be better. The choice depends on the critical section length and the number of contenders.

Caching remote shards is often more effective than trying to make every access local. A thread on node 0 that repeatedly reads a small record from a shard on node 1 can keep a local copy in a per-thread cache. The cache must be invalidated when the record changes. If the record is immutable or versioned, invalidation is cheap. If it is mutable, the cache needs a coherence protocol, which brings back the same problem at a higher level. A version number per record can be checked with a local atomic read; if the version matches, the cached copy is valid. This is a form of software caching that trades memory for remote traffic.

For graph workloads, partitioning is harder because the access pattern is irregular. A vertex's adjacency list can be placed on the same node as the vertex, but edges cross partitions. High-degree vertices can be replicated to every node, while low-degree vertices are partitioned. Edge lists can be interleaved across nodes to balance bandwidth, but that increases the latency of each edge traversal. A common compromise is to partition vertices by a graph partitioner and to replicate the adjacency lists of boundary vertices. The replication factor depends on the cut size. If the graph is dense, replication may be too expensive; if it is sparse, it can eliminate most remote accesses.

Remote read amplification is a key metric. If a single logical operation requires many remote cache-line transfers, the interconnect becomes a bottleneck even if the total number of operations is low. Batching can help: instead of fetching one record at a time, the thread fetches a batch of records from the remote shard in one request. The remote node processes the batch and returns a compact result. This turns many small remote accesses into a few larger ones and amortizes the interconnect latency. The cost is additional buffering and a more complex protocol. For latency-sensitive operations, batching may add too much delay. The trade-off is between throughput and tail latency, and it is one of the recurring decisions in NUMA-aware data structure design.

### Queues, rings, and the geography of a handoff

A queue is often the place where NUMA locality is won or lost. The queue is shared by definition, but its metadata and payload do not have to be equally remote. A naive ring buffer places the head index, the tail index, the capacity, and the first data slot on the same page or cache line. Producers and consumers on different nodes then write to neighboring words, causing false sharing and coherence traffic long before the queue is full. Padding the indices and separating them from the payload is the first fix. The second is to decide which node owns the queue and which node owns the items.

A single queue owned by node 0 and consumed by node 1 turns every dequeue into a remote read of the tail index and a remote read of the payload. The remote index access may be unavoidable for strict ordering, but the payload can be copied in batches. A consumer can drain a batch of descriptors from the remote queue, then fetch the corresponding payloads with a small number of bulk reads. If the payloads are large, the copy cost may dominate. If they are small, batching amortizes the interconnect latency and reduces the number of round trips. The queue protocol should expose a batch operation rather than forcing callers to loop over single-element operations. The batch size becomes a tunable that trades latency for throughput.

A more scalable pattern is a per-node queue with a routing rule. A producer on node 0 that needs to send work to node 1 enqueues into node 1's inbound queue. The producer pays a remote write, but the consumer reads locally. If the producer sends many small messages, the remote writes can be combined using a local staging buffer and a periodic flush. If the producer sends one large message, the remote write is a streaming copy and the consumer's local read is cheap. The routing rule should avoid a hot queue. A single inbound queue per node can become a contention point when many producers target the same consumer. Multiple queues per node, each with a single producer or a small producer group, reduce contention but increase polling overhead.

Work stealing adds a different geometry. Idle threads steal from other nodes when local queues are empty. The steal operation is inherently remote, but it should be rare in a well-balanced workload. A thief should steal a batch, not a single item, so that the remote access is amortized. The victim's queue needs a separate steal index or a lock that does not interfere with local pushes and pops. If the victim and thief contend on the same cache line, the steal itself becomes a source of cross-node traffic. A common design places the local front and back indices on the owner's node and a separate steal cursor on its own cache line. The owner updates the steal cursor only when it observes a steal, or the thief updates it with an atomic compare-and-swap. The exact protocol matters less than the separation of frequently written words.

Backpressure is a placement concern too. When a remote queue fills, the producer must either block, drop work, or spill to a local overflow buffer. Blocking a producer on node 0 because a consumer on node 1 is slow couples the two nodes and can leave local cores idle. A local overflow buffer keeps the producer busy but consumes memory on the producer's node and delays the visibility of the backlog. The queue should expose a high-water mark and a low-water mark so that the producer can adapt before the hard limit. The watermarks themselves should be read locally when possible. A cached copy of the consumer's progress, updated periodically, is often enough. Exact global progress tracking turns every enqueue into a remote read and defeats the purpose of the local fast path.

Counters and statistics need the same treatment. A global enqueue counter updated by every producer is a coherence hotspot. Per-node counters summed on demand are cheaper, even if the sum is slightly stale. The same rule applies to queue depth, dropped-item counts, and latency histograms. If the system exposes these values through a monitoring interface, the reader should aggregate per-node values rather than force every writer to touch a shared cache line. Observability must not become the dominant source of remote traffic.

### Locks, atomics, and the cost of a shared word

An uncontended atomic operation is cheap when the cache line is local. It is not cheap when the line is owned by another node. A test-and-set or compare-and-swap on a remote line requires a request to the home node, a coherence transition, and a response. Under contention, the line migrates between nodes, and each acquisition pays the interconnect latency. The usual advice to reduce lock hold times is still correct, but it is incomplete. A short critical section on a remote lock can spend more time acquiring the lock than doing the protected work.

The placement of the lock should follow the placement of the data it protects. A shard on node 1 should have its lock on node 1. If the lock is embedded in the shard's first cache line, a thread on node 0 that acquires the lock also fetches the first data element, which it probably needs anyway. If the lock is on a different node, the acquisition is a separate remote round trip. Padding the lock to its own cache line is useful when the protected data is accessed by many readers and the lock is written only by writers. In that case, separating the lock from the data avoids invalidating the data line on every lock update. The choice depends on whether the lock and the data are accessed together.

Queued locks are often better than spinning on a remote word. An MCS lock or a similar queue-based lock gives each waiter a local node on which to spin. The tail pointer is still shared, but the contention is on the enqueue operation rather than on repeated reads of a single locked flag. The waiter's node field can be used to decide whether to spin or to yield. A waiter on a remote node may be better off sleeping than burning interconnect bandwidth. The lock implementation can also batch handoffs: instead of waking one waiter at a time, it can transfer ownership to a group of waiters on the same node. This reduces the number of coherence transactions at the cost of fairness and latency for waiters on other nodes.

Read-mostly data benefits from avoiding locks altogether. A sequence lock or a read-copy-update scheme lets readers proceed without writing a shared word. Readers may still fetch remote data, but they do not generate coherence traffic on a lock line. The writer pays the synchronization cost, and the reader's cost is bounded by the data access. For a per-node replica, the reader can often read entirely locally and only check a version number. The version number should be padded and updated infrequently. If the version changes on every write, readers on remote nodes will repeatedly invalidate their caches and refetch the data. Batching updates or using epoch-based reclamation can reduce that churn.

Atomics on shared counters are a common hidden cost. A counter that every thread increments is a single cache line that moves between nodes. Even if the counter is only used for diagnostics, it can consume a measurable fraction of interconnect bandwidth. The fix is to shard the counter by node and sum the shards when the value is needed. The shards should be padded to avoid false sharing with adjacent data. If the counter must be exact at every read, sharding adds a synchronization problem, but many counters do not need exact instantaneous values. They need a trend, a rate, or a threshold check. Those uses can tolerate a small delay.

False sharing is especially damaging across nodes because the coherence protocol cannot distinguish between two independent variables. Two threads on different nodes that write to different fields of the same struct will ping-pong the cache line even though there is no logical sharing. The compiler may pack the fields tightly, and the hardware may fetch the whole line. Padding, alignment attributes, and per-node replicas of hot fields are the standard defenses. The cost is memory footprint. For a hot structure with millions of instances, padding every instance can waste gigabytes. A better approach is to restructure the data so that fields written by different nodes live in different arrays or different cache lines only for the hot instances. The design should be driven by measured contention, not by blanket padding.

### Memory tiers, CXL, and migration as a first-class operation

Modern servers are increasingly tiered. A package may have high-bandwidth memory close to the cores, ordinary DRAM on the same socket, and additional memory attached through a coherent interconnect such as CXL. Each tier has a different capacity, latency, and bandwidth. The NUMA graph becomes a weighted graph with multiple resources per node. A thread on node 0 may access local DRAM at one latency, local high-bandwidth memory at another, and CXL memory at a third. The kernel may expose these as separate NUMA nodes or as memory tiers within a node, depending on the platform and the kernel version. The application cannot assume that every node has the same amount of fast memory.

Placement policy must account for capacity as well as latency. If the fast tier is small, the system cannot place the entire working set there. It must decide which pages benefit most from being close. A page that is accessed frequently and randomly benefits from low latency. A page that is streamed once benefits from bandwidth and may be fine in a slower tier. A page that is written once and read rarely should not consume fast capacity. The policy needs a notion of value per page, not just a notion of local versus remote. Hardware access counters, sampling, and software hints can provide that value estimate. The estimate is noisy, so the policy should use hysteresis and avoid migrating pages on every small change.

Migration is a data copy, and it competes with the workload for bandwidth. Moving a 2 MiB huge page from slow memory to fast memory consumes bandwidth on both the source and destination paths. If the page is being accessed concurrently, the migration must coordinate with the access, either by unmapping the page, using a kernel migration entry, or copying under a lock. The latency spike during migration can be worse than the steady-state remote access it was meant to fix. For this reason, migration should be batched and scheduled when the system has spare bandwidth or when the benefit is large. A policy that migrates one page at a time in response to every fault is likely to thrash.

Explicit migration gives the application control. `move_pages` can move a range of pages to a target node, and `mbind` with `MPOL_MF_MOVE` can apply a policy and migrate existing pages. These operations are not free, and they can fail if the target node lacks memory. The application should treat migration as a transaction: reserve capacity on the target, migrate in batches, verify the result, and update its placement metadata. If the migration fails partway through, the range may be split across nodes. The application must tolerate that split or roll back. A transactional approach also makes it possible to measure the cost and benefit of each migration decision.

Page size determines the granularity of the decision. A 4 KiB page allows fine-grained placement but requires more page-table entries and more migration operations. A 2 MiB huge page reduces overhead but forces a coarse decision. If only part of a huge page is hot, promoting the whole page wastes fast capacity. If the hot part is spread across many huge pages, demoting the cold parts is expensive. Some systems support sub-page access tracking or huge-page splitting, but these mechanisms add complexity. A practical approach is to use huge pages for large streaming regions and small pages for irregular, latency-sensitive structures. The allocator and the application should agree on the page size before the memory is faulted in.

Tiered memory also changes the meaning of local. A thread's local node may have fast memory that is full, so the allocation falls back to a slower tier. The kernel policy may prefer local slow memory over remote fast memory, or the reverse. `MPOL_PREFERRED_MANY` and weighted interleave policies allow the application to express preferences across multiple nodes. The weights can reflect bandwidth or capacity. A weighted interleave that sends most pages to fast memory and a few to slow memory can balance capacity and performance better than a strict bind. The weights should be validated with experiments, because the effective bandwidth of a tier depends on the access pattern and on the load from other tenants.

Finally, the operating system's automatic tiering and the application's explicit policy can conflict. If the kernel promotes pages based on its own sampling while the application migrates the same pages based on its own model, the two policies can fight. The result is extra copying and unstable placement. The application should either disable automatic migration for its ranges or align its policy with the kernel's observations. A clear ownership model is necessary: the kernel owns anonymous memory by default, or the application owns it through explicit advice and migration. Mixed ownership is possible, but it requires monitoring and a way to detect when the two policies disagree. The placement layer should expose enough counters to show migration attempts, successes, failures, and the resulting distribution across tiers. Without that visibility, tiering becomes another source of hidden remote access.

## Placement budgets: treating remote access as a finite resource

A NUMA machine has a finite amount of local bandwidth per node and a finite amount of interconnect bandwidth between nodes. The interconnect is not a transparent pipe. It carries cache-coherence traffic, remote memory requests, and sometimes I/O. When a workload uses remote memory, it spends a resource that other threads on other nodes may also need. A placement budget makes that resource explicit. Instead of asking whether an access is local or remote, ask what fraction of accesses can be remote before the interconnect becomes the bottleneck.

For a latency-bound workload, the budget is small. A pointer chase that follows a chain of dependent loads cannot hide remote latency with parallelism because each load depends on the previous one. The only effective fix is to move the data or the thread so that the chain is local. Interleaving pages across nodes is actively harmful in this case, because it guarantees that a fraction of the dependent loads pay the full remote latency. For a bandwidth-bound workload, the budget is larger. A streaming kernel can tolerate remote accesses if the interconnect has spare capacity and if enough independent requests are in flight. The limit is not the latency of one access but the number of outstanding misses the core can sustain. If remote latency is twice local latency, a core needs roughly twice as many outstanding requests to achieve the same bandwidth. Memory-level parallelism is finite, so remote bandwidth per core is often lower even when the interconnect is not saturated.

A useful exercise is to write down a per-node budget for the workload. Suppose node 0 has 100 GB/s of local bandwidth and the interconnect can sustain 60 GB/s of remote traffic. If the workload needs 120 GB/s of aggregate bandwidth, it cannot get there by placing all data on node 0. It must spread the data and accept some remote traffic, or it must reduce the total bandwidth requirement. The budget also has a latency component. If the service-level objective is a 99th-percentile latency, the tail is often caused by queueing on the interconnect. A remote access that is fast when the interconnect is idle can become slow when many threads are streaming. The budget should be expressed in terms of both average bandwidth and tail latency, not just average latency.

Capacity is the other half of the budget. Fast memory is limited. A tiered system cannot promote every page. The placement layer needs a value estimate: how much does this page benefit from being close, and how much does it cost to move? A page that is read once per hour should not occupy fast memory. A page that is read millions of times per second and has poor locality should. The estimate can come from hardware counters, software sampling, or explicit hints. The policy should use hysteresis: promote after sustained benefit, demote after sustained idleness, and avoid migrating in response to transient spikes. Migration itself consumes bandwidth, so the budget must reserve capacity for moving data. A system that spends 20% of its bandwidth migrating pages to save 10% of access latency is losing.

## Runtime integration: making placement a property of the scheduler

Placement policies only matter if the runtime respects them. A thread pool that creates workers on demand and lets the scheduler place them will scatter threads across nodes. A runtime that wants NUMA awareness should create per-node worker pools, bind each pool to its node, and route work to the pool that owns the data. This is a structural decision, not a configuration flag. It affects how tasks are queued, how futures are completed, and how memory is allocated.

For OpenMP, the relevant controls are `OMP_PROC_BIND`, `OMP_PLACES`, and `OMP_NUM_THREADS`. Binding threads to cores or sockets reduces migration, but it does not by itself make memory local. The parallel loop must also partition work so that the thread that initializes a range is the thread that uses it. For task-based runtimes such as TBB or a custom thread pool, the scheduler should prefer to run a task on the node where its input data resides. That requires a way to tag tasks with a preferred node and a way to steal work across nodes without destroying locality. A simple policy is to steal only when the local queue is empty and to steal a batch rather than a single task. A more sophisticated policy can steal only tasks whose data is remote anyway, so the steal does not make locality worse.

Asynchronous runtimes add another layer. An event loop that runs on node 0 and handles I/O for data on node 1 will copy or access remote memory. If the runtime has per-node event loops, the I/O completion can be delivered to the loop on the node that owns the buffer. This requires NIC queue steering, interrupt affinity, and a way to map file descriptors or sockets to nodes. It is more work than a single global event loop, but it avoids a central node becoming a memory hotspot. The same principle applies to thread-per-core designs: each core should own a slice of the data and a slice of the work, and cross-core communication should be explicit and batched.

Allocator integration is part of the runtime contract. A per-node thread pool should use a per-node allocator arena. When a task allocates a buffer, the buffer should come from the node where the task runs. When the buffer is passed to another node, the handoff should be visible in the code, not hidden in a global allocator cache. Some runtimes expose allocation hooks; others require a custom allocator. In either case, the goal is the same: make the node of allocation a property of the task, not an accident of which thread happened to call `malloc`.

## Case study: sharded in-memory index with mixed reads and writes

Consider an in-memory index that supports point lookups and range scans over a large key space, with a read-heavy but write-active workload. The index is sharded by key hash. Each shard is assigned to a node. The routing table is small and read-mostly, so it is replicated on every node. A lookup from a thread on node 0 first checks the local routing table. If the key belongs to a shard on node 0, the lookup proceeds entirely locally. If it belongs to a shard on node 1, the thread either performs a remote read or sends a batched request to a per-node request queue.

The write path is local to the shard owner. A write to a key on node 1 is routed to node 1, where it acquires the shard's lock, updates the data, and bumps a version number. The lock and the shard metadata are on node 1. The version number is padded and updated with a release store. Readers on other nodes that cache remote records can check the version with an acquire load. If the version matches, the cached copy is valid. If not, they refetch. This turns most reads into local reads after a warm-up period, at the cost of memory for the cache and complexity in the invalidation protocol.

Range scans are the hard case. A scan may cross shard boundaries and therefore nodes. The scan coordinator can split the range by shard, send sub-scans to the owning nodes, and merge the results. Each sub-scan runs locally on its node and returns a compact batch. The coordinator pays the remote communication once per batch rather than once per record. The batch size should be large enough to amortize the interconnect latency but small enough to keep tail latency bounded. If the scan is latency-sensitive, the coordinator can stream results as they arrive and avoid waiting for the slowest shard. If the scan is throughput-oriented, it can wait for all shards and merge in order.

The shard count should be a multiple of the node count, and the mapping from shard to node should be stable. If a node is added or removed, shards can be migrated with `move_pages` or by rebuilding the index on the new node. Migration should be batched and throttled. During migration, the shard can serve reads from the old node while writes are forwarded to the new node, or it can be locked briefly. The choice depends on the acceptable downtime. The metrics that matter are remote read rate, remote write rate, cache hit rate for remote records, migration bandwidth, and the tail latency of cross-node scans. If remote read rate rises without a corresponding drop in local read rate, the routing or the cache is failing.

## Case study: streaming aggregation with per-node partials

A streaming aggregation reads events from a network or a log, groups them by key, and maintains counters, sums, or sketches. The ingest path is often attached to one NUMA node because the NIC or the storage controller is on that node. If all events arrive on node 0 and all aggregation state lives on node 1, every event pays a remote access. The first step is to distribute the ingest. Modern NICs support receive-side scaling and multiple queues. Each queue can be steered to a core on a specific node, and the interrupt or polled-mode driver can run on that node. With multiple NICs or a NIC with multiple ports, each port can be affinitized to a different node.

Once events arrive on the correct node, the aggregation state can be partitioned by key. Each node owns a subset of keys and maintains partial aggregates. An event for a key owned by another node is either forwarded immediately or accumulated in a local buffer and forwarded in a batch. Batching is essential: per-event forwarding turns the interconnect into a message bus. A batch of a few hundred events amortizes the remote write and gives the receiver a contiguous block to process. The receiver updates its partial aggregates locally. At query time, the coordinator merges partials from all nodes. If the query is frequent, the partials can be periodically combined into a replicated snapshot, but that reintroduces write traffic. A common compromise is to keep partials per node and merge on demand, with a background compaction that reduces the number of partials for hot keys.

Backpressure must be node-aware. If node 1's inbound queue is full, node 0 should not block all its local work. It can spill to a local overflow buffer, drop low-priority events, or shed load. The choice depends on the semantics of the stream. A monitoring pipeline may prefer to drop old events; a billing pipeline may prefer to block. The queue watermarks should be local reads when possible, with a cached view of the remote consumer's progress. Exact global backpressure couples the nodes and turns a local overload into a cluster-wide stall.

The aggregation data structures should be sized for the node, not for the whole machine. A per-node hash table can be smaller and can use huge pages without forcing a single global table to span nodes. If the key distribution is skewed, one node may own a hot key and become a bottleneck. The system can split the hot key's state across nodes and combine at query time, or it can replicate the hot key and accept coherence traffic. The right answer depends on the update rate. A hot key updated millions of times per second is better partitioned; a hot key read millions of times per second is better replicated.

## Case study: graph traversal and irregular access

Graph traversal is the least forgiving NUMA workload. The access pattern is data-dependent, the working set is often larger than cache, and the graph may not fit in one node's memory. A vertex-centric traversal reads a vertex's adjacency list, visits neighbors, and updates their state. If vertices are partitioned by node, most neighbor visits are remote. If edges are partitioned by node, the traversal must gather edge lists from multiple nodes. Neither choice is universally better.

A common design partitions vertices and replicates the adjacency lists of high-degree vertices. Low-degree vertices are stored on their owner node. When a thread on node 0 visits a high-degree vertex, it reads the local replica. When it visits a low-degree vertex on node 1, it pays a remote read. The replication factor is controlled by a degree threshold. If the threshold is too low, too many vertices are replicated and memory is wasted. If it is too high, high-degree vertices cause remote reads. The threshold can be tuned by measuring remote read amplification.

Worklists should be per-node. A thread that discovers a new frontier vertex enqueues it to the worklist of the vertex's owner node. The owner node processes its local worklist. If a node runs out of work, it steals a batch from another node. The steal should be large enough to amortize the remote access but small enough to balance load. The stolen batch may contain vertices that are remote to the thief, so the thief will pay remote reads for them. That is acceptable if the alternative is idle cores. The scheduler can prefer to steal work whose vertices are already remote to the victim, reducing the total remote traffic.

Prefetching can hide some remote latency, but it is difficult in a graph traversal because the next address depends on the current vertex's data. Software prefetch of the adjacency list works if the list is contiguous. Hardware prefetchers may not help with pointer chasing. Huge pages reduce TLB misses and can improve performance, but they also make the placement granularity coarser. If a huge page contains vertices owned by two nodes, one of them will be remote. Aligning vertex partitions to huge-page boundaries avoids that. The graph layout should be built with the NUMA topology in mind, not as an afterthought. A traversal that is fast on a single socket can be several times slower on two sockets if the partition is poor.

## Deployment and validation: keeping placement honest

Placement policies decay in production. A container runtime may restrict the process to a subset of CPUs, a job scheduler may migrate it, or a kernel upgrade may change the default memory policy. The deployment layer must preserve the topology contract. In Kubernetes, the CPU Manager with the static policy and the Topology Manager with the `single-numa-node` policy can pin a pod to one NUMA node. That is useful for latency-sensitive workloads, but it also limits the pod to that node's memory and cores. For workloads that need multiple nodes, the topology manager can use a `restricted` or `best-effort` policy. The pod should request guaranteed QoS and huge pages explicitly if it needs them. The container's cpuset should include the cores of the intended nodes, and the memory should be allocated from those nodes.

Outside orchestrators, systemd units can set `CPUAffinity` and `NUMAPolicy`. The kernel command line can disable automatic NUMA balancing for a machine that runs a latency-sensitive service, but that is a global decision. IRQ affinity matters too: a NIC interrupt that fires on node 0 but wakes a thread on node 1 adds a cross-node wakeup. The interrupt handler and the thread it wakes should be on the same node when possible. `irqbalance` may override manual settings, so the service should either manage IRQs itself or configure `irqbalance` to respect its affinity.

Validation should be continuous, not a one-time benchmark. A placement regression test can run a small version of the workload with a known topology, assert that the fraction of remote accesses stays below a threshold, and fail the build if it does not. The test should use hardware counters where available and fall back to `numastat` or `/proc/self/numa_maps` where they are not. It should run with the same thread affinity and allocator configuration as production. Synthetic topologies, such as a two-node VM or a container with a restricted cpuset, can catch bugs earlier than a full server. The test should also cover migration: allocate a range, bind it to one node, move it to another, and verify that the pages actually moved. If the kernel refuses the migration because of memory pressure or policy, the application should know and adapt.

The most valuable validation is an A/B experiment on real hardware. Run the workload with two placement policies, hold everything else constant, and compare throughput, tail latency, and remote access counters. The result is often surprising. A policy that looks good on paper may lose because it increases page faults, reduces cache hit rate, or causes allocator contention. The only way to know is to measure. Placement is not a one-time configuration. It is a property of the system that must be tested, observed, and maintained as the hardware, kernel, and workload evolve.
