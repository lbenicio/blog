Most lock-free code you read is written against one primitive: compare-and-swap. A published algorithm says "atomically compare `old` with the value at `p` and, if equal, install `new`", and the implementation is `LOCK CMPXCHG` on x86, `__sync_val_compare_and_swap` in a compiler builtin, or `compare_exchange_weak` on an atomic type in your language of choice. That framing is so pervasive that CAS is often treated as *the* atomic primitive — the thing hardware gives you, from which everything else is derived.

That is an x86-centric reading of history. On ARM, POWER, RISC-V, and MIPS — which between them cover most phones, most embedded systems, and a substantial and growing share of servers — the fundamental primitive is a *pair* of instructions: **load-linked** and **store-conditional**. The pair does not compare values. It watches memory. The difference is not a portability footnote that the compiler's atomic library abstracts away. It changes what "atomic" means at the hardware level, which algorithms are cheap, which are awkward, and which are outright impossible, and it changes how a retry loop should be structured if you care about throughput under contention.

This article is a deep dive into that mechanism. We will look at what the exclusive monitor really is, what the architecture guarantees and refuses to guarantee, why the load-linked/store-conditional pair sidesteps the classic ABA problem without any tagging scheme, where it silently costs more than a compare-and-swap, and how the story differs across ARMv8-A (including the Large System Extensions), POWER, RISC-V, MIPS, and the Alpha architecture where the idiom first became mainstream. Along the way we will look at what happens when you port a CAS-based algorithm mechanically, and why some of the most carefully tuned lock-free code in the Linux kernel has separate implementations per architecture rather than one generic one.

## The reservation model, concretely

Here is a compare-and-swap written the way an ARMv8-A programmer writes one:

```c
/* arm64: CAS built from the load-linked/store-conditional pair */
static inline bool cas_u64(uint64_t *addr, uint64_t expected, uint64_t desired)
{
    uint64_t observed;
    uint32_t status, result;

    __asm__ volatile(
        "1: ldaxr  %[obs], [%[a]]         \n"
        "   cmp    %[obs], %[exp]         \n"
        "   b.ne   2f                     \n"
        "   stlxr  %w[st], %[des], [%[a]] \n"
        "   cbnz   %w[st], 1b             \n"
        "   mov    %w[res], #1            \n"
        "   b      3f                     \n"
        "2: clrex                         \n"
        "   mov    %w[res], #0            \n"
        "3:                               \n"
        : [obs] "=&r"(observed), [st] "=&r"(status), [res] "=&r"(result)
        : [a] "r"(addr), [exp] "r"(expected), [des] "r"(desired)
        : "cc", "memory");

    return result != 0;
}
```

Two things in that snippet are load-bearing, and neither of them is the comparison.

`LDAXR` reads the word **and** asks the executing core's *exclusive monitor* to start watching the block of memory that contains it. `STLXR` performs the store only if that monitor still holds a valid reservation for that block. If it does not, the store does not happen at all — it is not speculated and rolled back, it simply never reaches memory — and the status register comes back non-zero. The `cbnz` jumps back to the load, and it must be a *load*, not just a re-issue of the store, because a failed store-conditional is a hint that the value may have changed underneath you.

Notice what the comparison is doing here. It is an *optimization*: if the loaded value is already not what we expected, there is no point attempting the store, so we bail out early, and the `CLREX` on the bail-out path drops the reservation we no longer need. The atomicity, however, comes entirely from the monitor. If we deleted the `cmp`/`b.ne` pair, the code would still be correct; it would just perform a store-conditional that usually writes back the same value it read. In a true compare-and-swap, by contrast, the comparison *is* the atomicity: the hardware compares and installs in one indivisible step, and there is no separate notion of a reservation that can be lost.

This is the mental model to hold onto: **load-linked establishes a bet, store-conditional collects it**. The bet is "nobody has written to this block since I looked." The hardware is not comparing your expected value against memory; it is answering a question about write history. Everything interesting about the primitive follows from that inversion.

## Write-detection versus value-detection

The classic ABA problem is the clearest way to see the difference. A thread loads a pointer, sees value `A`, and computes a new value. Before it can install it, another thread pushes a node, pops it, and the allocator hands the same address back — memory now reads `A` again, but the data structure around it has been torn and rebuilt twice. A compare-and-swap succeeds because the bits match, and the algorithm corrupts itself from a perfectly legal-looking interleaving.

With a real load-linked/store-conditional pair, the second writer's store — even a store of the *same value* — invalidates the reservation that the first thread's load-linked established. The store-conditional fails, the loop reloads, and the algorithm sees the new state instead of blindly overwriting it. Value-based ABA on the monitored location is not mitigated; it is structurally impossible, because there is no value comparison in the commit path at all.

This is worth stating precisely, because the claim is often overstated in both directions.

- **On the monitored location, ABA is gone.** Any write to the monitored block, including a write of an identical value, kills the reservation. A tagging scheme (pointer plus version counter in a double-width CAS) exists on LL/SC machines for other reasons, but not for this one.
- **On adjacent locations, nothing is solved.** If your algorithm's correctness depends on two independent words staying consistent with each other, LL/SC gives you no help unless the architecture offers a multi-word form. ARM's `LDXP`/`STXP` and POWER's `LQARX`/`STQCX.` monitor a 128-bit pair; the generality of "N words atomically" is still not free.
- **The monitor is not a transaction.** It does not roll back other stores, does not isolate readers, and does not survive a context switch.

There is a second, less obvious consequence of write-detection, and it is the source of most of the surprise when people benchmark LL/SC code for the first time. A compare-and-swap contends on a *word*. A store-conditional contends on a *block*. If two threads are doing load-linked/store-conditional on two different counters that happen to share a cache line, they can fail each other's stores even though they never touch the same bytes. The granularity of the exclusive monitor is implementation-defined rather than architectural, and real cores have shipped with monitors that track far more than the accessed word — often a cache line or more. The practical upshot is that padding and layout discipline, which you already want for false sharing, is *more* important here than on x86, because the failure mode is not a slower cache transfer but a retry of your critical section.

## The clauses that bite in production

An LL/SC loop is easy to write and easy to write wrongly. The following constraints are the ones that show up repeatedly in porting bugs and in postmortems of "works on the dev board, livelocks in the rack" failures.

### The store must go to the same place

On ARM, the store-conditional must use the same address *and* the same access size as the load-exclusive; a mismatch is constrained unpredictable, and in practice means the store never succeeds or the behaviour is container-specific. This kills a pattern that is idiomatic in CAS code: load a location, decide based on it, and store to a *different* location — a head pointer validated against a tail pointer, say. With CAS you can lean on the second location's own atomicity. With LL/SC you cannot, because the reservation you hold is for the first address. Anything that resembles "read one place, write another, atomically" needs either a 128-bit pair, a lock, or a redesign that funnels both words into one monitored block.

### Failure is an expected outcome, not an error

A store-conditional can fail spuriously with no competing writer at all. Interrupts taken between the load and the store clear the reservation on most designs; so does a context switch, an exception return, an explicit `CLREX` from a signal handler, and — on some implementations — eviction of the monitored line from the local cache under pressure. This means the loop must be a loop. An `if` around a store-conditional, which is a tempting simplification when you "know" there is no contention, is a correctness bug: the write is silently dropped.

The failure convention is also a classic off-by-inversion bug when moving between architectures. On ARM, `STXR`/`STLXR` write **0 to the status register on success** and non-zero on failure. On RISC-V, `SC.W`/`SC.D` write **0 to the destination register on success** and non-zero on failure — apparently the same convention until you notice that ARM's `CBNZ` and RISC-V's `BNEZ` are therefore branching on the *opposite* condition. POWER inverts it again: `STWCX.` sets the `EQ` bit of `CR0` on success, so a successful store is signalled by a condition register bit being *set*.

### Ordering is not included

`LDXR`/`STXR` are ordinary, relaxed accesses that happen to have monitor side effects. They provide no acquire or release ordering on their own; the `A` variants (`LDAXR`, `STLXR`) do. Even with the acquire/release forms, ordinary loads and stores you perform *inside* the critical section are not automatically ordered by the exclusive pair, and on a weakly ordered machine a store you perform between the load-linked and the store-conditional is a real hazard: it may be observed by another core before your atomic update commits, and it may itself clear your reservation if it touches the monitored block. The safe discipline is the one kernel developers converge on: between the load-linked and the store-conditional, do register arithmetic and nothing else, and put any real side effects after the store succeeds.

### Memory type, exceptions, and debuggers

On ARM, load-exclusive and store-exclusive to Device memory are unpredictable; the target must be Normal memory with a cacheable attribute. On virtualized and emulated platforms, exclusives are sometimes implemented with a global monitor or a trap-and-emulate path, which can turn a tight retry loop into something with wildly different failure statistics than bare metal — a routine source of "the algorithm regressed in CI" reports. And single-stepping under a debugger clears the reservation between every instruction, so an LL/SC loop will appear to spin forever or take the failure path every time. If you have ever watched a lock-free test hang only under `gdb`, this is usually why.

## A short architectural tour

Three families dominate, and their differences are instructive rather than cosmetic.

**ARMv8-A** offers `LDXR`/`STXR` for word and doubleword, `LDXP`/`STXP` for a 128-bit pair, the acquire/release `LDAXR`/`STLXR` and `LDAXP`/`STLXP`, and `CLREX` to drop a reservation explicitly. ARMv8.1-A added the Large System Extensions — `CAS`, `CASP`, `LDADD`, `SWP`, and friends — which are single-instruction atomics of exactly the kind the reservation model was supposed to replace. That is not a repudiation of LL/SC so much as an acknowledgment of its operational costs: retry loops burn issue slots, contend on monitors, and mispredict branches, and a single `CASAL` is cheaper for the overwhelmingly common read-modify-write case. Modern ARM code uses LSE where available and falls back to LL/SC where the CPU is older, which is why `-march=armv8.1-a` changes generated atomic sequences in ways that show up in profiles.

**POWER** has `LWARX`/`STWCX.` and `LDARX`/`STDCX.` for word and doubleword, plus `LQARX`/`STQCX.` for 128 bits on POWER8 and later. The reservation is lost on context switch and on a small set of implementation-defined events, and POWER's historical reservation granule has been large enough that false conflicts between adjacent words were a genuine performance topic in the multi-core era. POWER's memory model is weaker than ARM's in some respects, so the ordering discipline around the pair matters more, not less.

**RISC-V** specifies `LR.W`/`SC.W` and `LR.D`/`SC.D`, with the standard inverted-ish convention that the destination register receives zero on success. Crucially, the specification ties its forward-progress guarantee to *constrained* loops: the eventual success of a retry is only guaranteed if the paired `LR` and `SC` are to the same address, in a short loop with no other memory operations, no loads or stores, and no nested LR/SC sequences. Outside that envelope, an implementation is permitted to fail the store-conditional forever. This turns a performance heuristic into a documented correctness boundary, and it is the sharpest statement in any mainstream ISA of what "just retry" actually assumes.

**MIPS** has `LL`/`SC`, and the older convention that exception handlers must not clobber a live link register; that constraint shaped MIPS kernel entry code for years. **Alpha**, where the idiom entered the mainstream, had `LDL_L`/`STL_C` with a similarly explicit notion of the lock flag register — and Alpha's famously relaxed memory model is part of why the load-linked/store-conditional literature and the memory-consistency literature grew up together.

**x86** has none of this. It offers `LOCK CMPXCHG`, `LOCK XADD`, and the implicitly locked `XCHG`, with the cache-locking implementation and total store order that make them work. Its ABA problem is real and must be solved in software. The two designs represent genuinely different hardware bets about what concurrency should cost, and a codebase that has only ever been compiled for x86 has never had to confront the difference.

That difference has consequences that go well beyond syntax — for how you tag versions, for what a "retry" costs under contention, for which well-known lock-free algorithms port cleanly and which need to be replaced outright, and for how memory reclamation interacts with an operation that can fail without writing anything.

## Tagged pointers are not obsolete on LL/SC

A common overcorrection after learning the reservation model is to conclude that version counters, tagged pointers, and the whole apparatus of ABA mitigation can be deleted from any codebase that targets ARM, POWER, or RISC-V. That conclusion is wrong, and it is wrong in a way that produces subtle corruption rather than clean crashes.

The confusion comes from conflating two different jobs that tagging performs. The first job is to make a compare-and-swap safe against value-based ABA on the location being swapped. LL/SC does that for free, and on that specific job, tagging is indeed redundant. The second job is to make a *decision* safe when that decision depends on more than one location, or when it spans more than one atomic operation. LL/SC does nothing for that job, because the reservation is scoped to the monitored block and to the interval between one load-linked and one store-conditional.

Consider a lock-free hash table where each bucket is a pointer to a chain of nodes, and each node has a `next` pointer. An insertion reads the bucket head, reads the first node's `next`, and then conditionally updates the bucket head. If you implement the bucket update with LL/SC, the reservation covers the bucket head. A concurrent thread that modifies the first node's `next` does not invalidate that reservation, because `next` is a different address. The store-conditional can therefore succeed even though the chain was rearranged underneath you. The algorithm's correctness depended on the chain being stable between the read of `next` and the update of the head. LL/SC gives you atomicity on the head, but it does not give you atomicity on the head-plus-next pair. You still need a version counter on the node, a hazard-pointer-style validation of `next`, or a redesign that funnels the decision into a single monitored word.

The same issue appears in lock-free queues. The Michael-Scott queue uses a compare-and-swap on the tail pointer and a separate compare-and-swap on a node's `next` pointer. Each is an independent atomic operation. LL/SC handles each one correctly, and it eliminates ABA on each individual pointer. But the algorithm's invariant — that the tail pointer points to the last node, and that the last node's `next` is null — spans two locations. A thread that updates the tail with LL/SC can be interleaved with a thread that updates `next` with LL/SC, and the reservation on the tail does not detect the write to `next`. The algorithm still needs its usual validation logic, and it still needs a memory reclamation scheme that keeps the nodes alive. Tagging is not the answer here either; the answer is careful validation and reclamation, exactly as on x86.

There is also the multi-word problem. ARM's `LDXP`/`STXP` and POWER's `LQARX`/`STQCX.` monitor a 128-bit pair, which is enough for a pointer plus a 64-bit version counter. That is the standard way to get a tagged pointer atomically on those architectures. But the pair is still only two words, and it is not available on every implementation. RISC-V's base ISA has no multi-word LL/SC at all; the `Zacas` extension adds native compare-and-swap instructions, but without it you are limited to single-word `LR`/`SC`. If your algorithm needs a pointer plus a version plus a reference count, no single LL/SC pair will cover it. You need a lock, a different data structure, or a design that packs the state into one word.

So the rule is not "LL/SC makes tagging unnecessary." The rule is narrower and more useful: **LL/SC makes tagging unnecessary for the specific hazard of a write to the monitored location that restores the same value.** Every other reason you might tag — multi-word consistency, reclamation epochs, detecting changes to adjacent locations, packing a state machine into a pointer — remains exactly as relevant as it is on x86.

## What a retry actually costs

A failed store-conditional is not a no-op that the pipeline absorbs for free. It is a branch, and on the architectures that use the reservation model, that branch is usually the one that mispredicts. The cost profile is different enough from a failed compare-and-swap that code tuned on x86 can regress badly when ported naively.

On x86, a `LOCK CMPXCHG` that fails because the value did not match still performs the cache-line ownership transfer, but it does not require a re-load. The loop can re-execute the compare-and-swap with the same expected value, and the line is already in the local cache in the exclusive state. The failure is a flag setting and a branch. The data movement happened once, at the start of the attempt.

On an LL/SC machine, a failed store-conditional means the load-linked must be re-executed. That load is a real load. If the competing writer invalidated the line in your local cache, the re-load misses and fetches the line again. The failed store-conditional also clears the reservation, so the subsequent load-linked has to establish a new one, which may itself be a slow operation on cores where the monitor is a shared resource. The result is that under contention, an LL/SC loop can spend a much larger fraction of its time in cache-miss and monitor-management overhead than a CAS loop doing the same logical work.

There is a second-order effect that matters even more in practice: the retry loop is a critical section, and its length is visible to the hardware. The time between the load-linked and the store-conditional is the window in which an interrupt, a context switch, or an unrelated store to the same monitored block can clear the reservation. A loop that does a lot of computation between the load and the store — validating a node, walking a list, computing a checksum — will fail far more often than a loop that does a few register operations. The discipline that experienced LL/SC programmers adopt is to compute the new value *before* the load-linked, then do the load, compare, and store as a tight sequence. If the store fails, the loop reloads and recomputes only the minimum necessary. This is the opposite of the CAS style where the load and the computation are naturally interleaved, and it changes how you structure the code.

Ordering has a similar trap. A store-conditional that fails provides no release ordering, because it did not perform a store. If you use `STLXR` and then rely on the release semantics to publish a data structure that you initialized earlier, a failed store-conditional gives you nothing. The loop must be structured so that any ordering requirement is satisfied only on the success path, and any initialization that must be visible before the atomic update must be ordered by a separate barrier or by the acquire/release form of the successful store. This is a common source of bugs in code that was mechanically translated from a `LOCK CMPXCHG` loop, where the failed compare-and-swap also provides no ordering but the successful one does, and the compiler's builtin hides the distinction.

Finally, there is the thundering-herd problem. When many cores contend on one location, a compare-and-swap serializes them at the cache line, but each failure is cheap. An LL/SC loop serializes them at the monitor, and each failure forces a re-load that may bounce the line between cores. Backoff — randomized or exponential — is not optional in high-contention LL/SC code. It is the difference between a loop that makes progress and one that spends all its time invalidating its own reservations.

## Memory reclamation and the failure path

The interaction between LL/SC and memory reclamation is where the reservation model's write-detection semantics produce their most useful property: **a failed store-conditional writes nothing.** It does not publish a pointer, does not increment a reference count, does not modify a node, and does not create a new reference that a reclamation scheme must track. The only side effect is the clearing of the local reservation, which is invisible to other threads.

This matters for hazard pointers, epoch-based reclamation, and reference counting because those schemes are built around the idea that an operation can be attempted and abandoned without leaving a trace. A compare-and-swap has the same property — a failed `LOCK CMPXCHG` also writes nothing — so this is not unique to LL/SC. But the LL/SC version makes the property more explicit and more reliable, because the failure is signalled by the store not happening rather than by a comparison result. There is no window in which the store is speculated and then rolled back, and no possibility of a successful store that you later discover was based on stale data.

The more interesting interaction is with validation. In a hazard-pointer algorithm, a thread loads a pointer, publishes it as a hazard, and then must validate that the pointer is still the value in the location it read. On x86, validation is typically a second load plus a compare-and-swap or a memory barrier. On an LL/SC machine, you can combine the load and the validation into a single load-linked, but you cannot use the store-conditional as a validation because it writes. A store-conditional with the same value would still be a write, and it would be observable to other threads and to the reclamation scheme. So hazard pointers still need a separate validation step. What LL/SC gives you is a cheaper atomic update once validation succeeds: the update itself is a load-linked/store-conditional pair that cannot suffer ABA on the pointer, so you do not need to tag the pointer with a version counter just to make the update safe. The reclamation scheme still has to keep the node alive, but the atomic operation is simpler.

RCU is a different case. RCU readers do not use LL/SC; they just read. RCU updaters can use LL/SC to install a new pointer without ABA, which is convenient, but the grace period is still required to ensure that no reader is still looking at the old object. The reservation model does not shorten the grace period, does not eliminate the need for `synchronize_rcu`, and does not change the fact that a reader can be preempted while holding a reference. It only changes how the pointer update is performed.

Reference counting is where the failure path's write-nothing property is most directly useful. A classic pattern is "increment the reference count only if it is non-zero," which on x86 is a compare-and-swap loop that reads the count, checks for zero, and conditionally increments. On LL/SC, the same loop is a load-linked, a check for zero, and a store-conditional. If the store-conditional fails, the count was modified concurrently, so the loop retries. The failed attempt did not increment the count, so there is no need to undo anything. This is the same as the CAS version, but the LL/SC version makes the retry condition explicit: the reservation was lost, so the value you read may be stale, and you must reload before deciding again. That is a good discipline, and it is one of the reasons LL/SC loops are often easier to reason about than CAS loops, even when they are slower.

The practical constraint that reclamation code must respect is that the LL/SC window is not a transaction. It does not isolate you from other threads, does not prevent a context switch, and does not keep a node alive. If you need to read a node's fields and then update a pointer based on them, you must ensure that the node cannot be freed between the read and the update. Hazard pointers, RCU, or a garbage collector are still required. LL/SC gives you a safe way to perform the update; it does not give you a safe way to read the data the update depends on.

## Porting a CAS algorithm: a checklist

When you take a lock-free algorithm written against compare-and-swap and port it to an LL/SC machine, the mechanical translation — replace the CAS builtin with an LL/SC loop — will often compile and often pass a light test. The failures show up under contention, on weaker memory models, or after a scheduler change. The following checklist catches the majority of the real problems.

**1. Does the algorithm compare a value at a location other than the one it updates?** If the decision to store depends on a value read from a different address, LL/SC will not make that decision atomic. You need a multi-word LL/SC if the two locations can be monitored together, or you need a lock or a redesign. This is the single most common porting bug.

**2. Does the algorithm perform multiple atomic updates that must be mutually consistent?** If it updates a head and a tail, or a pointer and a count, and correctness requires that no other thread observes an intermediate state, LL/SC on each location separately is not enough. You need a 128-bit pair, a lock, or a design that combines the state into one word.

**3. Does the algorithm treat a failed atomic operation as evidence of contention?** On x86, a failed compare-and-swap means the value changed. On LL/SC, a failed store-conditional can be spurious: an interrupt, a context switch, or a store to an adjacent word in the same monitored block can clear the reservation without any competing writer to the location you care about. If the algorithm uses failure as a signal — to back off, to hand off work, to set a flag — that logic must be re-examined. It is usually safe to retry, but it is not safe to assume that a failure means another thread made progress.

**4. Does the algorithm use a compare-and-swap as a try-lock?** A failed try-lock on x86 means the lock is held. A failed store-conditional on LL/SC might mean the lock is free but the reservation was cleared. Retrying is correct, but it can livelock if the reservation is cleared repeatedly by an unrelated event. You may need a bounded retry with a fallback to a blocking lock, or a different algorithm.

**5. Does the algorithm rely on the ordering of a failed atomic operation?** A failed compare-and-swap provides no ordering on x86, and a failed store-conditional provides no ordering on ARM, POWER, or RISC-V. If the algorithm was relying on the atomic operation to act as a barrier on both paths, it is already wrong on x86, and it will be wrong on LL/SC for the same reason. Fix the ordering explicitly.

**6. Does the algorithm assume that the atomic operation is a single instruction?** Some algorithms use the atomic operation as a cheap way to get a unique value, a ticket, or a sequence number. LL/SC can do this, but the loop must reload after a failure, and the value it computes may change between attempts. If the algorithm assumes that the value it read before the store is the value it will install, that assumption is false under contention. The store-conditional only guarantees that no write occurred to the monitored block since the load-linked; it does not guarantee that the value you loaded is still the value you want to install.

**7. Does the algorithm use a tagged pointer to detect changes to a location that is not the one being updated?** This is the multi-location problem again, but it appears in a specific form: a version counter on a node that is incremented when the node's contents change. LL/SC on the node's pointer does not detect a change to the node's contents. If the algorithm uses the version counter to validate the contents, that validation is still necessary. The version counter may still be needed even though ABA on the pointer is solved.

**8. Does the algorithm use a compare-and-swap to implement a fetch-and-add or a bit-set?** These translate cleanly to LL/SC, but the loop must be a loop. A single load-linked, modify, store-conditional is not enough, because the store-conditional can fail. The retry must reload and recompute the new value from the freshly loaded value. This is straightforward but easy to get wrong when the original code used a single `LOCK XADD`.

The checklist is not exhaustive, but it covers the failure modes that show up in real ports. The underlying theme is that LL/SC is not a drop-in replacement for CAS. It is a different primitive with a different scope of atomicity, and the scope is the monitored block, not the algorithm's invariant.

## Forward progress and the constrained loop

The reservation model's most underappreciated property is that it does not promise that a store-conditional will ever succeed. The architecture manuals say that a store-conditional may fail spuriously, and that the loop must be prepared to retry. They generally do not say that the retry is guaranteed to terminate.

RISC-V is the exception. Its specification defines a *constrained* LR/SC loop: the load-reserved and store-conditional must be to the same address, the loop must be short, it must contain no other memory operations, no other loads or stores, and no nested LR/SC sequences. Within that envelope, the implementation guarantees eventual success. Outside it, the implementation is permitted to fail the store-conditional forever. This is a correctness boundary, not a performance hint. It means that a RISC-V LL/SC loop that does anything nontrivial between the load and the store — calls a function, accesses a different cache line, takes a lock — is not guaranteed to make progress, even if it is correct on every existing implementation.

The other architectures are less explicit, but the practical situation is similar. ARM and POWER guarantee that a store-conditional can fail spuriously, and they design their monitors so that a tight loop on a single word will eventually succeed under normal conditions. But there is no architectural guarantee that a context switch, an interrupt storm, or a pathological pattern of false conflicts will not starve the loop indefinitely. In a preemptive multitasking system, a thread can be preempted between the load-linked and the store-conditional, and every time it resumes, the reservation is gone. If the scheduler consistently preempts that thread at that point, the loop can livelock. This is rare in practice, but it is the reason why production lock-free code often includes a retry counter and a fallback to a blocking lock after some number of failures.

The forward-progress question also affects the choice between LL/SC and native atomics on ARMv8.1-A and later. The Large System Extensions add `CAS`, `CASP`, `LDADD`, and similar instructions that are single-instruction atomics with the same semantics as x86's locked operations. These instructions do not have the spurious-failure problem, because they are not reservation-based. They are generally faster under contention, and they are the reason why modern ARM compilers will emit `CASAL` instead of an LL/SC loop when targeting a CPU that supports LSE. The LL/SC path remains as a fallback for older CPUs, and it remains the only option on RISC-V without `Zacas` and on many embedded cores.

For a lock-free algorithm designer, the practical conclusion is that LL/SC is a fine primitive for tight, single-word updates, and it is a poor primitive for anything that needs a progress guarantee under adversarial scheduling. If your algorithm requires that some thread makes progress in a bounded number of steps, you should either stay within the constrained loop envelope, use a native atomic instruction where available, or provide a fallback path that does not depend on the reservation model. The reservation model is not a lock-free guarantee; it is a mechanism for detecting writes, and it will happily fail forever if the writes keep coming.

## Inside the exclusive monitor: what the hardware actually tracks

The reservation model is often described as a single bit per core, but real implementations are more elaborate. A core that executes a load-linked typically sets a bit in a local monitor and records the address, or the cache line containing it. The local monitor is cleared by an explicit `CLREX`, by a context switch, by an exception return, and by any subsequent load-linked to a different address. On some cores, the local monitor is a small CAM with a handful of entries; on others, it is a single reservation register. The architectural guarantee is only that a store-conditional to the same address will succeed if no intervening write occurred; the implementation may use a single register or a larger structure, and it may fail the store-conditional for reasons that have nothing to do with the address you are updating.

The global monitor is the part that sees other cores. It is tied to the cache coherence protocol. When a core executes a load-linked, it typically obtains the line in a shared or exclusive state and marks it as monitored. A store-conditional then requires the line to still be in a state that permits the store, and the global monitor checks whether any other core has written to the monitored block since the load-linked. In a MESI-like protocol, a write by another core invalidates the local copy, which clears the reservation. In a directory-based protocol, the directory may track the reservation explicitly or may rely on the same invalidation. The upshot is that the reservation is not an abstract token; it is a property of the cache line's coherence state.

This explains a behavior that surprises programmers who think of LL/SC as a lightweight CAS. A store-conditional can fail because the line was evicted from the local cache, because another core performed a write to a different word in the same line, or because the core took an interrupt. None of those events changed the value at the address you loaded. The store-conditional is not answering 'did the value change?' It is answering 'is the line still in the state I left it in, and has anyone written to the monitored block?' That is a stricter question, and it is why LL/SC loops can fail more often than the logical contention on the word would suggest.

The monitor also has a limited lifetime. On most architectures, a reservation does not survive a context switch. If the thread is descheduled between the load-linked and the store-conditional, the store-conditional will fail when the thread resumes, even if no other thread touched the address. This is a safety property: the hardware cannot let a store-conditional succeed after an arbitrary interval, because the world may have changed. But it is also a performance hazard. A thread that is preempted at the wrong moment will lose its reservation and must retry, and if the scheduler is unfair, it can lose repeatedly. This is one reason why LL/SC loops are kept short and why some kernels disable preemption around them.

## Granularity, false conflicts, and layout discipline

The size of the monitored block is implementation-defined, and this is the single most important non-architectural detail for performance. ARM's documentation says the reservation granule is at least the size of the access, but it may be larger; in practice, many cores monitor a cache line. POWER's reservation granule has historically been large, and some implementations have been reported to monitor 128 bytes or more. RISC-V allows the reservation set to be any set of bytes that includes the accessed word, and the specification encourages implementations to use a cache line. Alpha's lock flag was associated with a cache line as well.

The consequence is false conflicts. Suppose two threads each increment a different counter, and the two counters share a cache line. Thread A executes `LDXR` on counter A, establishing a reservation on the line. Thread B executes `LDXR` on counter B, establishing a reservation on the same line. Thread A computes its new value and executes `STXR`. If thread B has not written yet, thread A's store may succeed, but it will invalidate thread B's reservation. Thread B's `STXR` then fails, even though thread B is updating a different word. Thread B retries, reloads, and tries again. Under sustained contention, the two threads can ping-pong the line and fail each other's store-conditionals indefinitely. This is not false sharing in the usual sense -- the threads are not sharing a variable -- but it is a false conflict on the reservation granule.

The fix is the same as for false sharing, but the required discipline is stricter. Hot LL/SC variables should be placed on separate cache lines, with padding and alignment. In C and C++, `alignas(64)` or the architecture's cache line size can be used. In the Linux kernel, `____cacheline_aligned` and `____cacheline_aligned_in_smp` are used for exactly this purpose. The cost is memory footprint, which matters in embedded systems and in data structures with many small atomic counters. A common compromise is to group counters that are updated by the same thread and separate counters that are updated by different threads. This is a data layout decision that has no equivalent on x86, where two independent `LOCK CMPXCHG` operations on different words in the same line contend for ownership but do not fail each other's stores; the second operation simply waits for the line and then succeeds if the value matches.

The granule also affects nested reservations. Most cores support only one active reservation per hardware thread. If you execute a load-linked, then another load-linked to a different address, the second one replaces the first. A subsequent store-conditional to the first address will fail. This means that LL/SC sequences cannot be nested, and a function that uses LL/SC cannot be called from within another LL/SC sequence. The compiler and the programmer must both respect this. In practice, this is why LL/SC is a poor fit for algorithms that need to atomically update two independent locations: you cannot hold two reservations at once. The multi-word forms are the exception, and they are limited to a fixed pair.

## Multi-word reservations: what they buy and what they do not

ARMv8-A provides `LDXP` and `STXP` for a 128-bit aligned pair, and `LDAXP`/`STLXP` for the acquire/release forms. POWER8 and later provide `LQARX` and `STQCX.` for a 128-bit pair. These instructions extend the reservation model to two registers, but they do not generalize to arbitrary N. The pair must be aligned to 16 bytes, and the reservation still covers an implementation-defined block that may be larger than 16 bytes. The store-conditional writes both words only if the reservation is still valid; if either word was written by another core, the store fails and neither word is written. This is a genuine two-word atomic update, and it is the standard way to implement a tagged pointer or a double-width compare-and-swap on these architectures.

What multi-word LL/SC does not give you is a transaction. It does not isolate the two words from other memory, does not provide rollback of other stores, and does not allow you to read one word, decide based on another, and then write both if unrelated locations changed. The reservation is still scoped to the monitored block. If your algorithm needs to update a pointer and a counter that are not adjacent, or if it needs to validate a third location, the 128-bit pair will not help. You need a lock, a different data structure, or a redesign that packs the state into the pair.

RISC-V's base ISA has no multi-word LL/SC. The `Zacas` extension adds native `AMOCAS` instructions for 32-bit, 64-bit, and 128-bit compare-and-swap, but those are not reservation-based. Without `Zacas`, a RISC-V implementation that needs a tagged pointer must either use a single word with a packed tag and pointer, or use a lock. MIPS has `LLD`/`SCD` for 64-bit values but no 128-bit pair. Alpha had `LDQ_L`/`STQ_C` for 64-bit but no 128-bit pair. The practical result is that the multi-word reservation is an ARM and POWER feature, and even there it is limited to two words.

The performance of multi-word LL/SC is also worth noting. A 128-bit exclusive access is typically slower than a single-word access, and it may not be supported on all implementations. On some ARM cores, `LDXP`/`STXP` are implemented but have lower throughput than `LDXR`/`STXR`. On POWER, `LQARX`/`STQCX.` may have additional alignment and privilege constraints. If your algorithm can be made to work with a single word, it is usually better to do so. The multi-word form is a tool for specific cases, not a general-purpose upgrade.

## Compiler mappings and the constrained loop in practice

When you write `atomic_compare_exchange_weak` in C11 or `compare_exchange_weak` in C++11, the compiler is allowed to use LL/SC on architectures that have it. The `weak` form is explicitly permitted to fail spuriously, which maps naturally to a store-conditional that fails even when the value matches. The `strong` form must not fail spuriously, so the compiler must loop until either the value mismatches or the store-conditional succeeds. The generated code is essentially the loop we saw earlier: load-linked, compare, branch out on mismatch, store-conditional, branch back on failure. The compiler must also ensure that the loop body does not contain memory operations that would violate the constrained loop on RISC-V or clear the reservation on other architectures. This is why the compiler often emits the loop in a small out-of-line function or with careful register allocation.

The mapping is not always obvious from the source. On ARM64, GCC and Clang will emit `LDAXR`/`STLXR` for `compare_exchange` when targeting an older CPU, and `CASAL` when targeting ARMv8.1-A or later. The `-moutline-atomics` option makes the choice at runtime, using a function that checks a capability variable and branches to either the LSE sequence or the LL/SC sequence. This is why the same binary can behave differently on different ARM servers, and why profiling a lock-free workload on one machine may not predict its behavior on another. The runtime check adds a branch and a load, but it allows a single binary to run efficiently on both older and newer CPUs.

On RISC-V, the compiler must respect the constrained loop. The specification requires that the `LR` and `SC` be in a short loop with no other memory operations. If the compiler spills a register to the stack between the `LR` and the `SC`, the loop is no longer constrained, and the implementation is permitted to fail the `SC` forever. Compilers for RISC-V therefore try to keep the loop body register-only. They may also use `Zacas` instructions when available, which do not have the constrained-loop restriction. If you are writing inline assembly, you must ensure that the loop body has no loads or stores, including no spills. This is a subtle constraint that is easy to violate when the loop contains a function call or a complex expression.

The same issue appears on ARM and POWER, but the architectures are more forgiving. ARM does not have a formal constrained-loop requirement, but a store-conditional can fail if the reservation is cleared by an interrupt or a context switch. A long loop body increases the window for those events. POWER has similar behavior. The practical advice is the same: keep the LL/SC window as short as possible, do not call functions, do not take locks, and do not perform unrelated memory accesses. If you need to do work, do it before the load-linked, and only recompute the minimum necessary on retry.

## The architectures that never added a native CAS

ARMv8.1-A added the Large System Extensions, which include `CAS`, `CASP`, `LDADD`, `SWP`, and other single-instruction atomics. RISC-V's `Zacas` extension adds `AMOCAS`. These are native compare-and-swap instructions that do not use the reservation model. They are generally faster under contention, they do not fail spuriously, and they do not have the constrained-loop problem. But not every architecture has followed this path.

POWER has not added a native compare-and-swap. POWER8 and later have `LQARX`/`STQCX.` for 128-bit pairs, but the only way to perform a compare-and-swap is to use `LWARX`/`STWCX.` or `LDARX`/`STDCX.` in a loop. This is not a legacy detail; it is the current state of the architecture. A POWER programmer who wants a compare-and-swap writes an LL/SC loop, and the performance characteristics of that loop are the performance characteristics of the architecture's atomic operations. This is one reason why POWER's memory model and reservation model have been studied so heavily: there is no escape hatch.

MIPS has `LL`/`SC` and `LLD`/`SCD`, and no native compare-and-swap in the base ISA. Some MIPS implementations have added `CMP` or similar instructions, but they are not universal. RISC-V without `Zacas` is in the same position. Alpha had `LDL_L`/`STL_C` and no native compare-and-swap. The result is that a large fraction of the world's CPUs still rely on the reservation model for their atomic read-modify-write operations, and a lock-free algorithm that assumes a native CAS is not portable to them without a loop.

This matters for algorithm design because the loop is not just a syntactic wrapper. It changes the failure modes, the contention behavior, and the forward-progress guarantees. An algorithm that is wait-free on a native CAS may be only lock-free on an LL/SC loop, because the loop can retry indefinitely. An algorithm that uses a CAS to implement a try-lock may need a bounded retry on LL/SC to avoid livelock. An algorithm that uses a CAS to implement a fetch-and-add may need to reload and recompute on every failure. These are not minor differences; they are the difference between an algorithm that works and one that spins.

## LL/SC-friendly algorithm design: the Treiber stack and beyond

The Treiber stack is the simplest lock-free data structure, and it is a good test case for the reservation model. The push operation is:

```c
void push(Node *n) {
    Node *old_head;
    do {
        old_head = head;
        n->next = old_head;
    } while (!cas(&head, old_head, n));
}
```

On an LL/SC machine, the `cas` becomes `LDXR` on `head`, a store to `n->next`, and `STXR` on `head`. The store to `n->next` is a memory operation between the load-linked and the store-conditional. On RISC-V, that would violate the constrained loop if `n->next` is not in a register. In practice, the compiler may keep `n` in a register and the store to `n->next` is a store to memory, which is a memory operation. The RISC-V constrained loop requires no other memory operations. So a naive Treiber stack push on RISC-V is not a constrained loop. Does that mean it can fail forever? The specification says that outside the constrained loop, the implementation is permitted to fail the store-conditional forever. In practice, implementations do not fail forever, but the guarantee is not there. To stay within the constrained loop, the push must set `n->next` before the load-linked, or use a different algorithm. This is a concrete example of how the reservation model changes the shape of a lock-free algorithm.

The pop operation is similarly affected. A typical pop reads `head`, reads `head->next`, and then CASes `head` to `head->next`. The read of `head->next` is a load between the load-linked and the store-conditional if the load-linked is on `head`. On RISC-V, that is another memory operation, violating the constrained loop. On ARM and POWER, it is allowed, but it increases the window and can clear the reservation if `head->next` is in the same monitored block. The safe pattern is to load `head` with a plain load, load `head->next` with a plain load, and then use LL/SC only for the final update, with a validation that `head` has not changed. But that validation is a second load, which is also a memory operation. The result is that a Treiber stack on RISC-V may need to use a lock or a different structure if it wants a forward-progress guarantee.

This is not to say that LL/SC is unusable for these algorithms. It is to say that the algorithms must be designed with the reservation model in mind. The patterns that work well are those that keep the LL/SC window to a single word and a few register operations. A fetch-and-add, a bit-set, a lock acquisition, and a reference count increment all fit this pattern. A stack push that writes a node's `next` pointer does not, unless the write is moved outside the window. A queue that updates a tail pointer and a `next` pointer does not, because the two updates are in different locations. The reservation model rewards algorithms that pack their state into one word and penalizes those that scatter it across several.

## `CLREX`, barriers, and the things that are not reservations

A surprising number of LL/SC bugs come from treating instructions that look related as if they were the same kind of thing. `CLREX` is not an atomic abort. It clears the executing hardware thread's local reservation and nothing else. It does not write memory, does not invalidate another core's reservation, does not force a competing store-conditional to fail, and does not order any loads or stores. If one thread executes `CLREX` after a load-linked, another thread's reservation on the same line is unaffected; if that other thread's line has not been written, its store-conditional can still succeed. The only indirect effect is through a store: if the `CLREX` path also writes to the monitored block, that write is what kills the reservation.

This matters because `CLREX` is often inserted defensively on every exit path from an LL/SC sequence. That is usually harmless, but it can hide a structural problem. If a function performs a load-linked, decides not to attempt the store, and returns without clearing the reservation, a later store-conditional to the same address in the same hardware thread could succeed on the strength of the old reservation rather than a fresh load. The right discipline is not to sprinkle `CLREX` everywhere; it is to make every load-linked have exactly one matching store-conditional or an explicit `CLREX` on the path that abandons it, and to keep the reservation's lifetime visible in the control flow.

Memory barriers are a separate axis. A `DMB` or `DSB` orders memory accesses; it does not create, extend, or preserve a reservation. Placing a barrier between the load-linked and the store-conditional does not make the pair more atomic, and on some cores it lengthens the window in which an interrupt or an unrelated write can clear the monitor. Conversely, `CLREX` is not a fence: clearing the reservation does not publish prior stores, does not prevent later loads from being reordered before it, and does not substitute for the release ordering that a successful store-conditional with release semantics provides. The acquire/release variants of the exclusive instructions combine two jobs, but the plain forms do neither job for you.

The same distinction appears at the compiler boundary. An `asm volatile` block with a `"memory"` clobber tells the compiler not to move memory operations across the block; it says nothing to the hardware about ordering. A hardware fence tells the hardware about ordering; it says nothing to the compiler unless the compiler emitted it for that reason. LL/SC loops need both kinds of ordering to be correct, and they need the reservation state to be managed independently of both. Once you separate those three concerns — reservation lifetime, compiler reordering, and hardware memory order — most of the folklore around LL/SC stops being mysterious. The reservation is state, not a lock; the barriers are ordering, not state.
