Every compiler engineer eventually meets a particular kind of bug report: a program got *slower* after a change that touched nothing in its hot path. The regression is not in the code generator, not in the register allocator, and not in the instruction selector. It is in the *order* of the optimization passes. A pass was inserted three stages earlier, or a canonicalization was moved after inlining instead of before, and now the loop vectorizer sees a shape it no longer recognizes. The generated code is still correct. It is simply worse, and the reason is a global property of the pipeline rather than a local property of any pass.

This is the phase-ordering problem, and it has been a known annoyance for as long as optimizing compilers have existed. The standard response is to hand-tune the pipeline: run the aggressive inliner, then constant propagation, then dead code elimination, then a second round of the inliner, then the loop passes, then a cleanup sweep. The ordering is a heuristic, defended by benchmarks and institutional memory, and it is fragile in exactly the way heuristics are fragile.

Equality saturation is an alternative framing. Instead of choosing a sequence of rewrites and committing to each result, you build a data structure that represents *all* the programs reachable by applying your rewrite rules, and you choose the best one at the end. The data structure is the **e-graph** (equivalence graph), and the machinery that makes it work — congruence closure, rebuilding, e-matching, and extraction — is a genuinely interesting corner of computer science that has moved from SMT solvers into mainstream compiler infrastructure over the last several years.

This article covers the design space in detail: what an e-graph is, why the naive version is quadratic, how congruence closure is maintained incrementally, how rewrite rules are matched against equivalence classes, why extraction is the hard part, and where the approach breaks down. It assumes you are comfortable with union-find, hash consing, and the general shape of a compiler IR.

## The Phase-Ordering Problem, Restated

An optimizing compiler is, at its core, a function from a program to a program, factored into a sequence of smaller functions. Each pass has an implicit precondition — the shape of the IR it knows how to improve — and an implicit postcondition. Constant propagation wants to see loads from known-constant addresses. Dead code elimination wants to see unused definitions with no side effects. Loop-invariant code motion wants a loop with a recognizable induction variable and a body free of aliasing stores.

These preconditions are not compositional. Inlining a function can expose a constant; constant propagation can make a branch statically dead; removing that branch can make a load unreachable; removing the load can make a store dead; removing the store can make a loop body empty; an empty loop body can make the entire loop dead. Every one of those steps is a separate pass in a conventional pipeline, and every one of them depends on the previous one having already run. Run them in the wrong order and you get a strictly worse program, with no error message.

The space of possible orderings is enormous. If you have *k* passes and you are willing to run each at most once, there are *k*! orderings. Real pipelines run some passes multiple times and use fixpoint loops for a subset of them, which makes the space larger still, and the objective function — runtime on a workload — is noisy, non-differentiable, and expensive to evaluate. Compilers therefore do not search this space. They pick a point in it, using a combination of folklore, benchmark-driven tuning, and the occasional superoptimizer-style experiment.

The consequences are familiar. Optimizations are missed because the pass that would have enabled them ran too early. Performance is fragile because a change in one pass's canonical form ripples through the pipeline. And the pipeline itself becomes hard to reason about: the *n*-th pass in the list is not independently meaningful, because what it does depends on the state left behind by the previous *n* − 1.

Two broad alternatives exist. The first is **superoptimization**: search over the space of instruction sequences directly, using exhaustive enumeration for tiny windows or stochastic search for larger ones. That approach is powerful but local — it optimizes a window of instructions, not the program's algebraic structure. The second is **equality saturation**: express optimizations as equations, apply them all without ordering them, and pick the best result afterward. That is the subject of the rest of this article.

## Term Rewriting and Why Greedy Fixpoint Iteration Fails

A rewrite rule is a directed equation, written `l → r`, meaning "any subterm matching `l` may be replaced by the corresponding instance of `r`." Compilers use directed rules because directionality gives you a termination argument: if every rule strictly decreases some well-founded measure, the rewrite system terminates, and a simple loop that applies rules until none match will halt.

The trouble is that many of the most valuable algebraic facts are not naturally directional. Commutativity — `x + y = y + x` — has no decreasing direction. Neither does associativity. Distributivity, `x * (y + z) = x*y + x*z`, is directional in one sense (it pushes multiplication inward) but the reverse direction is equally useful for factoring common subexpressions, and choosing one direction permanently forecloses the other.

When a rewrite system is non-terminating, a naive loop diverges. When it is non-confluent — meaning two different rules can apply to the same term and lead to different normal forms — the result depends on which rule you happened to try first. Confluence is decidable for terminating systems (via the Knuth–Bendix critical pair criterion) but the check itself is expensive, and real optimization rule sets are neither confluent nor terminating.

A conventional compiler handles this by being aggressively greedy. It applies the first matching rule, or the rule with the best local cost delta, or the rule that a heuristic table says is most likely to help. Then it moves on. The result is a single point in a search space that might contain millions of equivalent programs, chosen by a local decision made without knowledge of the global consequence.

This is not a theoretical complaint. Consider a strength-reduction rule that rewrites a multiply-by-power-of-two into a shift. Applied greedily, it looks like a clear win. But if a later pass would have recognized the multiply as part of a reduction pattern and vectorized the loop, the early rewrite has destroyed the pattern. A cost model that only sees the local expression cannot know this. The information needed to make the decision lives in the *interaction* between rules, and greedy rewriting throws that information away at the moment it commits.

What you want, in principle, is to apply every rule everywhere, keep every intermediate result, and defer the choice of which result to keep until you can evaluate the whole set with a global cost model. The obvious implementation — a tree of all possible rewrites — explodes exponentially. The e-graph is the data structure that makes this tractable, by noticing that most of those distinct programs share most of their structure.

## E-Graphs: Equivalence Classes as a Data Structure

An e-graph is a set of **e-classes**. Each e-class is a set of **e-nodes**. Each e-node is an operator applied to a list of *e-classes* — not to e-nodes, and not to subterms. This last detail is the whole trick.

Concretely, an e-node looks like `(+ c1 c2)`, where `c1` and `c2` are identifiers of e-classes. The e-class containing that node represents "the set of all terms that can be formed by picking a term from `c1`, a term from `c2`, and applying `+`." Because children are referenced by class rather than by node, a single e-node stands for many different terms simultaneously.

The e-graph maintains one invariant, called **congruence**: if two e-nodes have the same operator and their corresponding children belong to the same e-classes, then those two e-nodes belong to the same e-class. Equivalently, the e-graph represents the least equivalence relation on terms that is closed under congruence — if `a` and `b` are known equal, and `f` is a function symbol, then `f(a)` and `f(b)` must be equal too.

The set of terms denoted by an e-graph is defined recursively: choose an e-class, choose any e-node in it, and recursively choose terms for each child class. The result is a term. The collection of all such terms is the language of the e-graph, and it can be exponentially larger than the number of e-nodes. A chain of *n* e-nodes where each class contains two alternatives denotes 2^*n* distinct terms. This is the compression that makes equality saturation practical: one polynomial-size data structure holds an exponential set of candidate programs.

Two operations dominate the implementation:

- **Union**: merging two e-classes into one, because a rewrite rule has established that two terms are equal.
- **Add**: inserting a new e-node, creating a fresh e-class for it if the node is not already present.

Union and add are both implemented with well-known primitives. E-class membership is tracked with a union-find structure using path compression and union by size, giving near-constant amortized cost for `find`. E-nodes are interned with a hash-cons table keyed by `(operator, canonical child class ids)`, where "canonical" means the union-find representative of each child class. Interning gives you the congruence invariant almost for free on insertion: if you build a node whose canonical key already exists, you have discovered a congruence and must merge the two classes.

That "almost" is doing real work. Insertion is easy. *Merging* is where the cost lives, because merging two classes invalidates the canonical keys of every e-node that referenced either of them.

## Congruence Closure and Rebuilding

Congruence closure as a decision procedure — given a finite set of ground equations, decide whether two terms are equal — is a classical problem. Nelson and Oppen's algorithm for the quantifier-free theory of equality with uninterpreted functions is the version most people encounter first, in the context of SMT solvers. Downey, Sethi, and Tarjan later gave a bound of *O*(*n* log *n*) for the common-subexpression problem using union-find plus a careful signature table.

Those algorithms assume you process a batch of equations and compute the closure. Equality saturation needs the *incremental* version: equations arrive one at a time, from rewrite rules, interleaved with queries, and the structure must stay consistent throughout. The naive incremental approach is straightforward and quadratic. On every union of classes `A` and `B`, walk the entire e-graph, re-canonicalize every e-node's child list, and re-insert each into the hash-cons table. Any two e-nodes that now collide get merged, which may trigger more merges, and the process repeats until a fixpoint. Correct, and unusably slow: each union costs *O*(*n*), and saturation performs a great many unions.

The fix is to track the reverse edges. Alongside the e-graph, maintain for each e-class a list of **parents**: the e-nodes that reference this class as one of their children. This is a standard use-def / def-use duality. When classes `A` and `B` merge, only the parents of `A` and `B` can have stale canonical keys — every other e-node's children are unchanged. So instead of scanning the graph, you scan the parent lists of the merged classes, re-canonicalize each parent, and re-insert it into the hash-cons table. If the insertion collides with an existing e-node in a different class, that is a new congruence, and you enqueue a merge for those two classes and continue.

This worklist-based repair is usually called **rebuilding**, and it is the phase that separates a toy e-graph from a usable one. A few implementation details matter a great deal in practice:

- **Process the worklist in batches.** Merges discovered during a repair pass are queued and applied together rather than one at a time. Batching lets you deduplicate work: an e-class that appears in the parent lists of several merged classes should be re-canonicalized once, not once per merge.
- **Repair only what changed.** Re-canonicalizing a parent whose children's representatives are unchanged is wasted work. A cheap check — compare the new canonical key against the cached one — skips the common case.
- **Recompute analyses during rebuilding.** Many systems attach a value to each e-class: a constant-folded value, a cost, a set of free variables. If those analyses are recomputed eagerly on every union, the cost is proportional to the number of unions. Deferring them to the rebuild phase, where they can be recomputed in dependency order and cached, is substantially cheaper. The `egg` library made this decomposition explicit, treating rebuilding as a first-class phase of the saturation loop rather than an implementation detail of union.
- **Handle parent-list growth.** Parent lists can accumulate duplicates, and long-lived e-classes can acquire very large parent lists. Periodic deduplication, or storing parents as a set rather than a list, trades memory for time in a way that depends on the workload.

Even with all of this, rebuilding is not free. It is typically a significant fraction of total runtime in equality saturation, because every merge in a large e-graph can touch many parents, and saturation performs merges continuously. The practical consequence is that the *shape* of the rewrite rule set matters as much as the constant factors: rules that create many small merges scattered across the graph are much more expensive than rules that merge a few large classes.

There is also a subtle correctness point. Rebuilding must be run to a fixpoint before any query — e-matching or extraction — observes the e-graph. If a congruence is discovered but not propagated, the e-graph is temporarily unsound: it claims two terms are distinct when they are not. Most implementations make this safe by construction, running the rebuild loop until the worklist is empty before returning control to the saturation driver.

With the invariant maintained, the next question is how rewrite rules actually find their matches inside this structure. A rule like `(x + 0) → x` is not matched against a term; it is matched against an e-graph in which `x` may itself denote thousands of distinct terms, and in which the same subterm may be reachable through several paths. That problem — e-matching — is where the next section picks up.

## E-Matching: Finding Rewrites in a Graph of Equivalences

When a rewrite rule is applied to a term, matching is a simple recursive descent: compare the pattern's operator with the term's operator, recurse on children, and bind variables to subterms. Inside an e-graph, the same rule must be matched against a structure where a single e-class can contain hundreds of e-nodes, each representing different equivalent terms, and where the same subterm can be reached through multiple paths. The pattern is not matched against a term; it is matched against a *set* of terms, and the matcher must find every substitution of pattern variables to e-classes that makes the pattern a valid term in the e-graph.

Formally, an e-matching problem is: given an e-graph and a pattern `p` with variables `x1, ..., xn`, find all mappings `σ` from variables to e-classes such that the instantiated pattern `σ(p)` is represented by some e-class in the e-graph. The result is a set of matches, each of which can be used to add the rule's right-hand side and union it with the matched left-hand side.

The naive algorithm enumerates all terms denoted by the e-graph and matches the pattern against each. That is exponential in the worst case and immediately impractical. The standard alternative is a bottom-up dynamic program over the pattern's structure. For each subpattern `q`, compute the set of e-classes that match `q`. The base case is a variable, which matches every e-class (subject to any side conditions). For a pattern `f(q1, ..., qk)`, an e-class matches if it contains an e-node `f(c1, ..., ck)` such that each `ci` matches `qi`. This is a fixpoint computation: start with the variable matches, then iterate over pattern operators, using the e-graph's e-nodes to propagate matches upward. The algorithm terminates when no new matches are found, and its cost is roughly `O(|pattern| * |e-graph|)` in the common case, though repeated variables can cause a combinatorial explosion because the same variable must bind to the same e-class in all its occurrences.

Repeated variables are the source of e-matching's worst-case complexity. A pattern like `(x + x)` requires that both occurrences of `x` bind to the same e-class. In a bottom-up matcher, this becomes a constraint satisfaction problem: you must intersect the sets of candidate e-classes for each occurrence and then verify that the resulting e-class actually contains an e-node matching the whole pattern. In the worst case, e-matching is NP-hard, because it subsumes subgraph isomorphism when the pattern has many repeated variables and the e-graph has many equivalent nodes. Practical patterns are small, so the exponential blowup rarely materializes, but it is a real limit on how expressive rewrite rules can be.

Implementations use several techniques to keep e-matching fast. The first is **pattern compilation**: translate the pattern into a bytecode program or a finite automaton that is executed against the e-graph. This avoids re-interpreting the pattern structure on every match and allows the matcher to be optimized once. The second is **indexing**: build an index from operator symbols to the e-nodes that use them, so the matcher can skip e-nodes that cannot possibly match. The third is **relational e-matching**: represent the e-graph as a set of relations — `e_node(id, operator)`, `child(node, index, class)`, `class_of(node, class)` — and compile the pattern into a relational query with joins. The query is then evaluated using worst-case optimal join algorithms, which avoid the redundant work that naive backtracking performs when multiple variables range over overlapping sets. Relational e-matching is particularly effective for patterns with repeated variables, because the join order can be chosen to enforce equality constraints early.

A fourth technique is **incremental e-matching**. Instead of re-matching every rule against the entire e-graph on each saturation iteration, the matcher can record which e-classes were affected by the last round of unions and only re-examine matches that involve those classes. This is analogous to incremental view maintenance in databases. It is not always a win — the bookkeeping can outweigh the savings for small e-graphs — but for large e-graphs with many rules, it can reduce matching time from a bottleneck to a minor cost.

Side conditions complicate e-matching further. Many useful rewrite rules are not unconditional equations. A rule like `(x / y) → (x * (1/y))` is only valid when `y` is known to be nonzero. A rule like `(x << c) → (x * 2^c)` is only valid when `c` is a constant. In an e-graph, `y` is an e-class that may contain many different terms, some nonzero and some not. The matcher must consult an **e-class analysis** — a value computed for each e-class, such as a constant-folding result or a set of known properties — to decide whether the side condition holds for a particular match. This means that analyses must be kept up to date during rebuilding, and that e-matching is not purely syntactic: it depends on the semantic information attached to classes.

## Extraction: Turning an E-Graph Back into a Program

Saturation produces an e-graph that represents a vast set of equivalent programs. The final step is **extraction**: choose one program from that set, ideally the one with the lowest cost according to a model of runtime, code size, or some other objective. Extraction is where equality saturation meets the real world, and it is also where many of the approach's practical difficulties live.

The simplest extraction algorithm is a bottom-up dynamic program over the e-graph. Assign each e-class a cost, defined as the minimum over its e-nodes of the cost of the operator plus the sum of the costs of its child e-classes. If the e-graph is acyclic, this recurrence has a well-defined solution: process the e-classes in topological order, compute costs, and then reconstruct the chosen program by walking down from the root class, picking the e-node that achieved the minimum at each step. The result is a tree, because the reconstruction duplicates shared subexpressions. That duplication can be undesirable — it may increase code size and miss common-subexpression elimination opportunities — but it is simple, fast, and correct.

Cycles in the e-graph break the simple recurrence. A cycle arises when an e-class contains an e-node that refers back to the same class, directly or indirectly. This is common: a rule like `x → x + 0` (if oriented in the wrong direction) creates a cycle, and so do rules that introduce recursive definitions. In a cyclic e-graph, the cost of an e-class may depend on itself, so the recurrence becomes a system of equations. For non-negative operator costs, the system is monotone, and a fixed-point iteration starting from infinity converges to the least solution. But the least solution may be infinite if every alternative in a cycle has positive cost; in that case, the e-class has no finite-cost term, and extraction must avoid it. Practical extractors handle cycles by computing strongly connected components, solving each component with a fixed-point iteration, and then ensuring that the final extracted program does not contain a cycle. If a cycle is unavoidable, the extractor must either fail or fall back to a non-cyclic alternative from outside the cycle.

DAG extraction, which shares common subexpressions, is more complex. The cost of a shared node is paid once, so the objective is no longer a simple sum over the tree. This is the **minimum-cost DAG covering** problem, and it is NP-hard in general. Exact solutions use integer linear programming or branch-and-bound, which are too slow for large e-graphs. Practical systems therefore use heuristics: extract a tree, then run a common-subexpression elimination pass on the result; or greedily share subgraphs that appear multiple times and have high cost; or use a dynamic program that approximates sharing by considering the number of uses of each e-class. The trade-off is between optimality and scalability, and most equality saturation systems choose scalability.

The cost model itself is a design decision. A simple model assigns each operator a constant cost, such as 1 for arithmetic and 3 for a memory load. More sophisticated models account for instruction latency, register pressure, or cache behavior. The cost model must be compositional: the cost of an e-node must be computable from the costs of its children. This rules out costs that depend on global properties, such as the total number of live registers, unless those properties are approximated by an e-class analysis. Even then, the approximation may be poor, and the extracted program may not be optimal under the true runtime cost. This is a fundamental limitation: equality saturation optimizes against a *model*, not against the hardware.

## Running the Saturation Loop

The equality saturation algorithm is conceptually simple. Start with an e-graph containing the input program. Then repeat the following steps until a termination condition is met:

1. For each rewrite rule, run e-matching to find all matches in the current e-graph.
2. For each match, instantiate the rule's right-hand side, add the resulting e-nodes to the e-graph, and union the new root with the matched left-hand side.
3. Rebuild the e-graph to restore congruence.
4. Optionally, run e-class analyses to update semantic information.
5. Check for saturation: if no new e-nodes were added and no new unions occurred, stop.

In practice, saturation rarely reaches a true fixpoint. Rewrite rules like commutativity and associativity generate an infinite sequence of equivalent terms, so the e-graph would grow without bound. Even terminating rule sets can take many iterations to saturate, and the e-graph can become very large before they do. Implementations therefore impose limits: a maximum number of iterations, a maximum number of e-nodes, a time budget, or a combination. When a limit is hit, the loop stops and extraction proceeds on the current e-graph. The result is not guaranteed to be the best possible program, but it is often better than what a fixed pipeline would produce.

Rule scheduling is a major performance factor. Applying every rule on every iteration is expensive, and many matches are redundant. Some systems use a priority queue to apply rules that are likely to produce useful merges first. Others group rules into phases: first simplify, then factor, then explore. The `egg` library, for example, supports **rule sets** and **schedulers** that control which rules are applied and in what order. A common strategy is to run a set of "cleanup" rules to a fixpoint, then a set of "exploration" rules for a bounded number of iterations, then cleanup again. This mimics the structure of a traditional compiler pipeline while retaining the ability to explore multiple alternatives.

E-graph size is the central scalability challenge. Each union can merge two large classes, and each merge can trigger a cascade of congruence-driven merges. The number of e-nodes can grow exponentially in the number of iterations, even though the e-graph represents an exponentially larger set of terms. Techniques for controlling growth include:

- **E-node deletion**: remove e-nodes that are subsumed by other e-nodes in the same class, or that are never used in any extraction. This is safe only if the deleted e-node is not the sole representative of some equivalence.
- **E-class merging**: merge classes that are equivalent under the current analyses, even if no rewrite rule directly relates them. This can reduce the number of distinct classes.
- **Cost-based pruning**: during saturation, periodically extract a best program and use its cost to prune e-nodes that cannot possibly lead to a better result. This is tricky because pruning can remove the very alternatives that would enable a later improvement.
- **Limiting rule applications**: cap the number of times a rule can be applied, or the number of new e-nodes it can create. This sacrifices completeness for tractability.

Another practical issue is **rebuilding cost**. As noted earlier, every union invalidates the canonical keys of parent e-nodes, and rebuilding must repair them. In a large e-graph with many unions per iteration, rebuilding can dominate runtime. Implementations optimize it by batching unions, deduplicating parent lists, and recomputing analyses lazily. The `egg` library's rebuild phase is a good example of a carefully engineered solution: it processes a worklist of dirty e-classes, re-canonicalizes their parents, and merges any congruent e-nodes it discovers, all in a single pass that avoids redundant work.

## Where Equality Saturation Breaks Down

Equality saturation is not a universal replacement for traditional optimization pipelines. It has clear limitations, and understanding them is essential to using it effectively.

The first limitation is **scale**. E-graphs can grow very large, and e-matching against a large e-graph is expensive. Current systems work well on small, compute-intensive kernels — linear algebra, digital signal processing, floating-point arithmetic — where the program is a few hundred operations and the rewrite rules are algebraic. Scaling to large programs with control flow, memory, and complex data structures is an open research problem. One approach is to apply equality saturation locally, to small regions of a larger program, and then stitch the results together. Another is to use e-graphs as a component within a traditional pipeline, rather than as the entire optimizer.

The second limitation is **extraction optimality**. As discussed, optimal DAG extraction is NP-hard, and practical extractors use heuristics. The extracted program may not be the best one in the e-graph, and the cost model may not reflect actual runtime. This gap between the model and reality is a source of disappointing results: an e-graph may contain a program that is twice as fast as the extracted one, but the extractor cannot find it because its cost model is wrong or because it cannot share subexpressions optimally.

The third limitation is **rule set design**. Equality saturation is only as good as the rewrite rules it is given. Writing a good rule set is an art: rules must be correct, terminating (or at least bounded), and expressive enough to capture the optimizations you care about. Rules with side conditions require analyses, and rules that generate many matches can cause the e-graph to explode. There is no automatic way to derive a rule set from a specification, and hand-tuning is still the norm.

The fourth limitation is **integration**. Equality saturation operates on a term-like IR, but real compilers have IRs with control flow, memory effects, and side effects. Encoding those features into an e-graph is possible but awkward. Memory operations, in particular, are hard to model because they are not pure functions: two loads from the same address may return different values if a store occurs in between. Some systems handle this by treating memory as a state that is threaded through the program, but that increases the size of the e-graph and complicates e-matching. Others restrict equality saturation to pure, side-effect-free regions and use traditional passes elsewhere.

Despite these limitations, equality saturation has found a foothold in domains where its strengths outweigh its weaknesses: optimizing tensor computations, rewriting floating-point expressions for numerical stability, synthesizing instruction sequences, and simplifying queries in database systems. The core ideas — e-graphs, congruence closure, e-matching, and extraction — are general, and as the tooling improves, the approach is likely to spread to more areas of compiler construction. The phase-ordering problem is not going away, and equality saturation is the most principled attack on it that we have.

## The `egg` Library: Design Decisions That Shaped the Field

If you spend any time with equality saturation today, you will encounter `egg`, a Rust library that has become the de facto standard implementation. `egg` did not invent e-graphs, but it made them accessible, fast, and extensible, and its design choices have influenced nearly every subsequent system. Understanding those choices is a useful way to see how the abstract data structure becomes a practical tool.

The core abstraction in `egg` is the `Language` trait. A language defines the set of operators that can appear in e-nodes, along with the arity of each operator. The `define_language!` macro generates the boilerplate, so a simple language might look like `(+ a b)`, `(* a b)`, `(sqrt a)`, and so on. Because the language is a trait, `egg` can work with any term-like IR, from arithmetic expressions to tensor graphs to compiler IR. This genericity is a key reason for its adoption.

An `EGraph<L, N>` is parameterized by the language `L` and an analysis `N`. The analysis trait lets you attach semantic information to each e-class: a constant value, a set of free variables, an error bound, a cost estimate. The analysis is updated during rebuilding, and it can be queried during e-matching to check side conditions. For example, a constant-folding analysis might compute that an e-class represents the number `42`, which then allows a rule like `(x * 0) -> 0` to fire unconditionally.

The e-graph itself is stored in struct-of-arrays style: a `Vec<L>` holds the e-nodes, a `UnionFind` maps e-node ids to e-class ids, and a `HashMap<L, Id>` implements hash-consing. Each e-class has a `Class` struct containing a list of e-node ids and the analysis data. This representation is compact and cache-friendly, and it is one of the reasons `egg` is fast enough for real workloads.

Rebuilding in `egg` is a first-class phase, not an afterthought. The `rebuild` method maintains a `HashSet<Id>` of dirty e-classes. When a union occurs, the merged classes are marked dirty. Then `rebuild` pops a dirty class, looks at its parents, re-canonicalizes each parent's child list, and re-inserts it into the hash-cons table. If the insertion discovers a congruent e-node in another class, that pair is merged and the resulting class is marked dirty. The loop continues until the dirty set is empty. This worklist-based approach avoids the quadratic scan of the naive algorithm, and it is carefully optimized to skip parents that have not actually changed.

The `Runner` drives saturation. It takes a set of `Rewrite` objects, each of which pairs a `Pattern` (the left-hand side) with an `Applier` (the right-hand side). A `Searcher` finds all matches of the pattern in the e-graph; the applier then adds the instantiated right-hand side and unions it with the matched left-hand side. The runner supports limits on iterations, e-node count, and time, and it can be configured with a scheduler that controls which rules run in which order. This flexibility is essential for making saturation tractable on real problems.

Extraction in `egg` is performed by an `Extractor`. It computes the cost of each e-class bottom-up, using the cost model provided by the analysis. For acyclic e-graphs, a simple recursive memoized function works. For cyclic e-graphs, `egg` uses a fixed-point iteration that starts with infinite costs and repeatedly relaxes them until no cost decreases. The extractor then walks down from the root, choosing at each step the e-node that achieved the minimum cost, producing a tree. `egg` also provides an `explain` module that can produce a proof of why two e-classes are equal, which is useful for debugging and for verified compilation.

## Case Study: Herbie and Floating-Point Rewriting

Herbie is a tool that improves the numerical accuracy of floating-point expressions. Given an expression like `(1 - cos(x)) / x^2`, which suffers from catastrophic cancellation for small `x`, Herbie searches for an equivalent expression with lower error, such as `(sin(x/2) / (x/2))^2 / 2`. This is a rewriting problem, and the space of possible rewrites is large and non-confluent. Early versions of Herbie used a custom e-graph implementation; later versions adopted `egg`.

Herbie encodes floating-point expressions as e-nodes for arithmetic operations, elementary functions, and constants. The rewrite rules include algebraic identities, but also rules that are specific to floating-point accuracy: reassociation to avoid cancellation, distribution to expose common factors, and replacements of unstable expressions with stable equivalents. Many of these rules are not universally valid; they depend on the sign or magnitude of subexpressions. Herbie handles this by attaching an analysis to each e-class that estimates the range of values it can take. The e-matcher consults this analysis to decide whether a rule's side condition holds.

The cost model combines two objectives: accuracy and speed. Accuracy is estimated by sampling the expression at many random inputs and measuring the maximum error relative to a high-precision reference. Speed is estimated by counting floating-point operations. Herbie extracts the expression that minimizes a weighted combination of the two. Because sampling is expensive, the analysis is computed lazily and cached per e-class.

Herbie's use of e-graphs allows it to explore a large space of rewrites without committing to a sequence. This is important because the best rewrite often depends on the context: a reassociation that helps in one part of the expression can hurt in another. By keeping all alternatives alive, Herbie can find combinations that a greedy rewriter would miss. The results speak for themselves: Herbie has found improvements for thousands of expressions, and it is used in domains from scientific computing to game development.

## Case Study: Tensat and Tensor Graph Optimization

Tensat (Tensor Saturation) applies equality saturation to tensor computation graphs. These graphs, common in deep learning frameworks, consist of operations like matrix multiplication, convolution, element-wise addition, and activation functions. The goal is to find an equivalent graph that runs faster on a given target, such as a CPU or GPU.

Tensat encodes tensor operations as e-nodes in a custom language. The rewrite rules capture algebraic properties: associativity of matrix multiplication, distributivity of addition over multiplication, commutativity of certain operations, and fusion rules that combine operations like `relu(matmul(A, B))` into a single fused node. These rules are not directed in a traditional sense; they are applied in both directions, and the e-graph keeps all resulting graphs.

The extraction problem is particularly challenging in Tensat because the cost of a tensor graph is not compositional in a simple way. The runtime of a fused operation is not just the sum of the runtimes of its parts; it depends on memory bandwidth, cache behavior, and the specific hardware. Tensat uses a cost model based on measured runtimes of individual operations and a heuristic for estimating fusion costs. It also uses a custom extractor that can share common subgraphs, because sharing a large matrix multiplication can be a significant win.

Tensat's results showed that equality saturation can find optimizations that go beyond what hand-written rules or auto-scheduling produce. In some cases, it discovered tensor graph rewrites that reduced runtime by 1.5x or more compared to TVM's auto-scheduler. The main limitation is scale: tensor graphs can be large, and the e-graph can grow quickly. Tensat mitigates this by using a restricted rule set and by pruning e-nodes that are unlikely to be part of the optimal extraction.

## Case Study: Diospyros and Vectorization

Diospyros is a tool for vectorizing digital signal processing kernels. It uses equality saturation to simultaneously explore vectorization and instruction selection. The input is a loop over an array, expressed in a simple IR; the output is vectorized code that uses SIMD instructions.

Diospyros defines an e-graph language that includes both scalar and vector operations. The rewrite rules encode vectorization patterns: a scalar operation can be replaced by its vector equivalent when its operands are vectors, and a vector operation can be split into multiple scalar operations. The rules also encode algebraic identities that are useful for vectorization, such as reassociation to create longer vectors and distribution to expose parallelism.

A key challenge is handling memory access. Loads and stores are not pure functions, so Diospyros restricts the e-graph to straight-line code with no aliasing stores inside the region being optimized. This is a common pattern: use equality saturation on a pure sub-region, then integrate the result into the larger program.

The cost model in Diospyros is based on instruction count, register pressure, and the lane count of available SIMD instructions. The extractor must choose a consistent vector width across the whole kernel, which is a global constraint that is not captured by the local cost model. Diospyros handles this by running extraction for several candidate vector widths and choosing the best result. This is an example of how equality saturation often needs to be combined with a search over a small number of global parameters.

## Integration in Production Compilers: Cranelift's E-Graph Pass

Cranelift, the code generator used by Wasmtime, added an e-graph-based optimization pass that runs on a per-basic-block basis. This is a significant step because it brings equality saturation into a production compiler, albeit in a limited form.

The pass translates Cranelift IR into an e-graph language that includes arithmetic, bitwise operations, comparisons, and memory operations. It runs saturation with a set of algebraic rules derived from instruction set semantics: reassociation, commutativity, distributivity, constant folding, and strength reduction. Because the pass is limited to a single basic block, it does not need to handle control flow. Memory operations are modeled by threading a memory state through the e-graph, so that a load can be reordered with respect to stores only when it is provably safe.

The cost model is based on the estimated cost of each instruction on the target architecture. The extractor chooses the cheapest equivalent program. The pass is optional and can be enabled for functions where it is likely to help. In practice, it finds optimizations that the traditional pipeline misses, such as reassociations that expose constant folding across several operations, or combinations of bitwise operations that simplify to a single instruction.

The Cranelift experience highlights both the promise and the challenges of integration. The promise is that equality saturation can find better code without hand-tuning pass order. The challenge is that the e-graph must be carefully scoped to avoid blowup, and the cost model must be accurate enough to make good choices. The pass is still under active development, but it demonstrates that e-graphs can be a practical component of a production compiler.

## Alternative E-Graph Designs: Colored E-Graphs, Proofs, and Higher-Order Terms

The basic e-graph has been extended in several directions to address its limitations. Colored e-graphs attach a set of colors (or tags) to each e-node, recording which rewrite rules or which source expressions produced it. This provenance information is useful for debugging, for guiding extraction, and for producing explanations. For example, if you want to know why two terms are equal, a colored e-graph can show the chain of rewrites that connected them.

Proof-producing e-graphs go further: they store the sequence of unions and the rules that caused them, so that a formal proof of equivalence can be reconstructed. This is essential for verified compilation, where you need a machine-checkable certificate that the optimized program is equivalent to the original. The `egg` library provides an `explain` module that produces such proofs, and it has been used in research on verified optimization.

Higher-order e-graphs handle languages with binders, such as lambda calculus or languages with `let` and `lambda`. The naive encoding of binders into an e-graph causes an explosion because there are many ways to rename bound variables (alpha-equivalence). Techniques from nominal logic and de Bruijn indices can be used to represent binders canonically, but substitution and capture-avoiding rewriting remain challenging. This is an active area of research, with systems like `egg`-based lambda calculi exploring the design space.

Another variant is the cyclic e-graph, which explicitly allows cycles. Cyclic e-graphs are useful for representing recursive programs and loops, but they complicate extraction because the cost of an e-class may depend on itself. Fixed-point iteration and strongly connected component analysis are used to handle cycles, but optimal extraction from a cyclic e-graph is even harder than from an acyclic one.

## Open Problems and Active Research

Equality saturation has made remarkable progress, but several open problems remain. The most pressing is scalable DAG extraction. Optimal extraction with sharing is NP-hard, and current heuristics can leave significant performance on the table. Better approximation algorithms, or exact algorithms that work on structured e-graphs, would be a major advance.

Handling effects and control flow is another frontier. Most successful applications restrict equality saturation to pure, straight-line code. Extending it to memory, exceptions, and control flow requires new representations and new reasoning techniques. Some promising work uses e-graphs with memory states or with continuations, but these are not yet mature.

Automated rule set design is a long-standing dream. Writing good rewrite rules is an art, and the quality of the result depends heavily on the rule set. Can we synthesize rules from a semantics? Can we verify that a rule set is correct and terminating? These questions are starting to be addressed with techniques from program synthesis and formal verification.

Finally, integration with existing compilers is an ongoing effort. The Cranelift pass is a proof of concept, but broader adoption will require better tooling, better cost models, and a clearer understanding of when equality saturation pays off. The phase-ordering problem is not going away, and equality saturation remains the most principled attack on it that we have.

## Engineering an E-Graph for Real Workloads

An e-graph that is correct on paper can still be unusable in practice. The difference is almost always engineering: how nodes are stored, how often the structure is traversed, and how much information is recomputed from scratch. A production e-graph implementation is a data-oriented system, not an object graph. E-nodes live in a contiguous arena, usually a `Vec` or a slab, indexed by a small integer id. Children are stored as a fixed-size array or a small inline vector; variable-arity languages pay a pointer indirection only when necessary. The union-find structure is a separate array of parent pointers with path compression and union by rank or size. Hash-consing uses an open-addressing table keyed by `(operator, canonical child ids)`, with the hash computed once and cached.

Parent lists deserve special attention. They are the reverse edges that make rebuilding incremental, and they are also the largest source of memory overhead. A naive `Vec<Vec<Id>>` allocates a heap vector for every e-class, even those with one parent. A common optimization is an intrusive linked list: each e-node stores a `next_parent` pointer, and each e-class stores a head pointer. This eliminates per-class allocation and makes iteration cache-friendly, at the cost of slightly more complex insertion and removal. Another option is a single flat `Vec<(child, parent)>` with per-class ranges, rebuilt periodically. The right choice depends on the ratio of unions to e-nodes and on how often parent lists are traversed.

Profiling an e-graph workload is not like profiling a conventional compiler pass. The time is rarely spent in one obvious function. It is spread across e-matching, rebuilding, analysis recomputation, and extraction. A useful first step is to instrument the saturation loop with counters: e-nodes, e-classes, matches per rule, unions per iteration, rebuild worklist size, and time per phase. These counters tell you whether the e-graph is growing because a rule is too productive, whether rebuilding is the bottleneck, or whether extraction is unexpectedly expensive. Rule-level counters are especially valuable. A single rule can account for most of the e-graph growth; disabling it or adding a side condition often turns an intractable saturation into a fast one.

Visualization is another practical tool. Dumping the e-graph to DOT and rendering it with Graphviz makes structural problems obvious: a dense cluster of classes connected by a commutative rule, a long chain of reassociations, or a class that has absorbed half the graph. Interactive e-graph viewers let you step through rewrites and inspect individual classes. They are not a substitute for profiling, but they turn a wall of counters into a shape you can reason about.

Memory management matters more than in a traditional compiler because e-graphs are long-lived during saturation and can grow to millions of nodes. Generational indices, arena reset, and periodic compaction are common. Some systems use a garbage collector for e-nodes that are no longer reachable from any root, but reachability is subtle: an e-node is useful if it can contribute to some extracted term, and that depends on the cost model and the root set. Conservative approaches keep everything until extraction, then free the whole arena. Aggressive approaches prune during saturation, which risks removing the alternative that would have enabled a later improvement.

## Rule Authoring as a Discipline

Writing rewrite rules for equality saturation is closer to library design than to writing a compiler pass. A good rule set is layered. The first layer contains cleanup rules that normalize the representation: constant folding, identity elimination, canonical ordering of commutative operands, and simplification of nested casts. These rules are safe, terminating, and should be run to a fixpoint before any exploration begins. The second layer contains exploration rules that expand the space: distributivity, associativity, factorization, and algebraic identities. These are the rules that find non-obvious optimizations, and they are also the rules that cause e-graph explosion. The third layer contains target-specific rules that encode instruction set semantics: strength reduction, fused multiply-add formation, vectorization patterns, and memory access combining.

Bidirectional rules are a common source of trouble. In a directed rewrite system, you choose a direction to guarantee termination. In equality saturation, direction does not affect correctness, but it does affect growth. A rule that is applied in both directions can create a cycle of equivalent terms that never saturates. The usual solution is to write two rules and schedule them in different phases, or to make one direction conditional on a cost heuristic. For example, distributivity can be applied outward during exploration and inward during cleanup, with a bound on the number of applications in each phase.

Side conditions are what make rules practical. An unconditional rule like `(x * 0) -> 0` is rarely valid in a language with floating-point NaN or trapping arithmetic. A rule like `(x / y) -> (x * (1/y))` is only valid when `y` is known nonzero. E-class analyses provide the information needed to check these conditions. A constant analysis can prove that `y` is a literal; a range analysis can prove that `y` is outside the zero interval; a sign analysis can prove that `y` is positive. The analysis must be sound: if it claims a property that does not hold, the rewrite is unsound and the compiler miscompiles. This is the same contract as any compiler analysis, but the consequence is more direct because the rewrite is applied immediately.

Rule scheduling is the main lever for controlling saturation. A common pattern is: run cleanup to fixpoint, run exploration for a bounded number of iterations, run cleanup again, and repeat until a time or size budget is exhausted. Within each phase, rules can be prioritized by expected benefit. Rules that merge large classes or expose constant folding are usually worth running first. Rules that create many new e-nodes but rarely merge are candidates for later phases or for tighter bounds. Some systems use a priority queue keyed by the number of matches or the cost delta of previous applications. Others use a simple round-robin schedule and rely on limits to stop runaway growth.

Testing a rule set is as important as testing a compiler pass. Each rule should have unit tests on small terms: apply the rule, check that the result is equivalent under a reference interpreter, and check that the e-graph remains consistent. Property-based testing can generate random terms, apply random sequences of rules, and verify equivalence after every step. Fuzzing can search for rule combinations that cause non-termination, exponential growth, or miscompiles. Proof-producing e-graphs make this easier: if the system can emit a proof of equivalence, the test can check the proof instead of re-running the reference interpreter. Even without proofs, differential testing against an unoptimized baseline catches most soundness bugs.

## Cost Models, Extraction, and the Last Mile

The cost model is the objective function of equality saturation. A simple model assigns each operator a constant cost: arithmetic costs one, a memory load costs three, a division costs ten. This is enough to prefer `x + x` over `2 * x` in some contexts, but it is far from a model of runtime. Real costs depend on instruction selection, register pressure, instruction latency, throughput, and cache behavior. A cost model that ignores these factors can lead extraction to choose a program that looks cheap in the e-graph but compiles to slow code.

Compositionality is the key constraint. For bottom-up extraction, the cost of an e-node must be computable from the costs of its children. This rules out costs that depend on the whole program, such as the total number of live registers or the length of the critical path. Some systems approximate these global properties with e-class analyses: a register-pressure analysis can annotate each class with an estimated pressure, and the cost model can use that estimate. The approximation is necessarily local, and it can be wrong, but it is often better than ignoring the property entirely.

Extraction algorithms range from simple to sophisticated. The bottom-up dynamic program is the default: compute the minimum cost of each e-class, then reconstruct the tree by choosing the e-node that achieved the minimum. This is fast and works well when the e-graph is acyclic. For cyclic e-graphs, the same recurrence becomes a fixed-point problem. Start with infinite costs, relax each e-class by considering its e-nodes, and repeat until no cost decreases. If an e-class remains at infinity, it has no finite-cost term, and extraction must avoid it. Strongly connected components can be solved independently, which speeds up the iteration.

DAG extraction is where the last mile gets hard. Sharing a subexpression means paying its cost once, so the objective is no longer a sum over a tree. This is the minimum-cost DAG covering problem, and it is NP-hard. Exact methods use integer linear programming or branch-and-bound, which are practical only for small e-graphs. Heuristics include: extract a tree and then run common-subexpression elimination; greedily share subgraphs that appear multiple times and have high cost; or use a dynamic program that tracks the number of uses of each e-class. Each heuristic trades optimality for scalability. In practice, the difference between a good heuristic and the optimum is often small, but it can be large for graphs with many shared expensive operations.

Multi-objective extraction is common in real applications. Herbie balances accuracy and speed; a compiler might balance code size and runtime; a tensor compiler might balance latency and memory footprint. The simplest approach is a weighted sum, but choosing weights is arbitrary and can hide Pareto-optimal alternatives. Better approaches compute a Pareto front or use lexicographic ordering. For example, extract the fastest program subject to a code-size bound, or the smallest program subject to a runtime bound. These constrained problems are harder, but they match how engineers actually make trade-offs.

Context-dependent costs are another complication. The cost of a vector operation depends on the vector width, which must be consistent across the whole kernel. The cost of an instruction depends on the register allocation, which is a global decision. Equality saturation cannot easily encode these global constraints in a local cost model. The usual solution is to run extraction for several candidate global parameters, then choose the best result. This turns a global optimization into a small search over parameters, which is often good enough.

## Parallelism and Incremental Saturation

Equality saturation is naturally parallel in some phases and stubbornly sequential in others. E-matching is the easiest to parallelize: the e-graph is read-only during matching, so different rules or different parts of the e-graph can be processed concurrently. The matches are collected into a shared queue, and the application phase runs sequentially or with fine-grained locks. The challenge is load balancing: some rules produce many matches, others few, and the cost of a match depends on the size of the right-hand side. Work-stealing schedulers help, but the overhead can outweigh the benefit for small e-graphs.

Rebuilding is harder to parallelize because it mutates the union-find structure and the hash-cons table. A merge can invalidate the canonical keys of parents anywhere in the graph, and two threads cannot safely merge overlapping classes without synchronization. Some systems use a single-threaded rebuild phase and parallelize only matching and extraction. Others use fine-grained locks on e-classes, but lock contention and deadlock avoidance add complexity. Transactional memory is an attractive research direction, but it is not yet practical for large e-graphs.

Incremental saturation reuses work across compilations. If a function is compiled repeatedly with small changes, the e-graph from the previous compilation can be loaded and updated with the new terms. This is analogous to incremental compilation in an IDE. The challenge is invalidation: a change in one part of the program can affect the equivalence classes in another part, and the e-graph must be repaired consistently. Persistent e-graphs, which support efficient snapshots and rollback, are a step in this direction. They allow the compiler to keep a baseline e-graph and apply deltas, rather than rebuilding from scratch.

## Interfacing with Traditional Compilers

The most successful deployments of equality saturation do not replace the entire compiler. They replace a pass, or augment a pass, within a traditional pipeline. The key is scoping. Equality saturation works best on pure, straight-line regions: basic blocks, loop bodies without aliasing stores, expression trees, and tensor graphs. The compiler lifts the region into an e-graph language, saturates, extracts, and lowers the result back into the IR. The rest of the pipeline continues as before.

Lifting and lowering are not trivial. The e-graph language must be expressive enough to capture the region's semantics, but small enough to keep e-matching fast. Memory operations are the usual sticking point. A load is not a pure function of its address; it depends on the memory state. The standard technique is to thread a memory state through the e-graph: each load and store takes a state as an extra argument, and a load can be reordered with a store only when the analysis proves they do not alias. This encoding is correct but increases the size of the e-graph and complicates every rule that touches memory.

Control flow is another boundary. Equality saturation does not naturally represent branches, loops, or exceptions. Some systems use if-conversion to turn small branches into predicated operations, then saturate the resulting straight-line code. Others apply saturation only to the bodies of loops or to individual basic blocks. The Cranelift pass is an example of the latter: it runs per basic block, which keeps the e-graph small and avoids the need to model control flow. The trade-off is that optimizations requiring a global view, such as loop-invariant code motion, are left to traditional passes.

Integration also raises correctness questions. The extracted program must be equivalent to the original, and the equivalence must hold in the presence of the compiler's other assumptions. If the e-graph language has different semantics from the IR, the lifting and lowering steps must be proven correct. If the rules rely on analyses, those analyses must be sound. In a production compiler, the safest approach is to validate the extracted program against the original using a translation validator or a reference interpreter. This adds compile-time cost, but it catches miscompiles before they reach users.

Finally, compile-time budgets are essential. Equality saturation can be slow, and a compiler that takes minutes to optimize a function is unacceptable. Production systems impose strict time and size limits, and they fall back to the original program or to a traditional pass when the limits are exceeded. The fallback must be fast and correct, and it must not depend on the e-graph being in a consistent state. This is a small engineering detail with a large impact on deployability.
