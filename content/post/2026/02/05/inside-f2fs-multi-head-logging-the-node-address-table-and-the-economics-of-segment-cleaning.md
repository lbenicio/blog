## The file system that disagrees with its device

Most file systems are written against an abstraction that says storage is a large array of fixed-size blocks, that block N can be overwritten in place at any time, and that writing block N costs about the same as writing block M. On spinning disks this was approximately true, modulo seek time, which the block cache and the I/O elevator were supposed to hide. On NAND flash it is false in two independent ways, and the file system's relationship to its device becomes adversarial rather than neutral.

F2FS — the Flash-Friendly File System — was developed at Samsung and merged into Linux 3.8 in 2013 specifically to take the flash side of that argument seriously. This article is a close reading of its design: what it assumes about the device underneath it, where those assumptions come from, and what the file system does differently as a result. The interesting part is not that F2FS is log-structured. Plenty of file systems are. The interesting part is that F2FS is *several* logs at once, and that nearly every other design decision in the file system follows from that one choice.

## What the flash translation layer hides

NAND flash has three properties that a block device does not have.

First, reads and writes are page-granular, but erases are block-granular, and an erase block is large — hundreds of kilobytes to several megabytes, containing many pages. Second, a page that has been programmed cannot be reprogrammed until its entire erase block has been erased. Third, each erase block tolerates a finite number of program/erase cycles before it wears out.

The consequence is that no flash device you can buy exposes raw NAND. Instead it exposes a **flash translation layer** (FTL) behind a conventional block interface. The FTL maintains a map from logical block addresses (LBAs) to physical pages. When the host writes LBA 1000, the FTL does not modify whatever physical page currently holds LBA 1000. It programs a fresh page somewhere else, updates the map, and marks the old page invalid. The host sees an overwrite; the flash sees an append.

That trick has a cost. Invalid pages accumulate, and the only way to reclaim them is to erase the erase blocks that contain them — but an erase block is usually a mix of valid and invalid pages. So the FTL's garbage collector picks a victim erase block, copies every still-valid page out of it into a fresh block, and then erases the victim. Those copies are writes the host never asked for. The ratio of flash writes to host writes is called **write amplification**, and it is the number that governs both endurance and steady-state throughput on any flash device.

Write amplification is not a property of the device alone. It is a property of the interaction between the device and the workload. If the host writes in large sequential runs and never revisits old data, the FTL's garbage collector rarely has to copy anything: by the time it picks a victim, almost every page in it is already invalid, and it can erase without moving data. If the host scatters small overwrites uniformly across the address space, valid pages are uniformly distributed across erase blocks, and every garbage collection cycle copies a large fraction of a block in order to reclaim a small amount of space. Same device, same number of host writes, wildly different flash traffic.

There is a second, subtler coupling. The FTL cannot know when the host has freed an LBA unless the host says so. **TRIM** — and its modern equivalents, discard and the `BLKDISCARD` ioctl — exist for exactly that purpose. Without them, the FTL treats every LBA that has ever been written as live, and its garbage collector dutifully copies stale file data across the device forever.

So the picture is this: a file system sitting on flash is allocating out of a pool whose reclamation cost depends on the *age distribution* of the data it writes and on how accurately it reports frees. F2FS was designed around both facts.

## Log-structured file systems: right shape, wrong granularity

The log-structured file system, from Rosenblum and Ousterhout's 1991 work, is the obvious response. Never overwrite anything. Append every write — data, metadata, inodes, directory entries — to the tail of a single log. Keep an in-memory map from logical object to log address. Periodically write a checkpoint that records the current mapping, so that recovery does not require scanning the entire volume.

On flash this maps almost perfectly onto the device's actual behavior. A log append is a fresh program to a fresh page, which is precisely what the FTL wants to see, and a monotonically advancing write pointer is the friendliest possible access pattern for an internal garbage collector.

The problem is reclamation. A log-structured file system must eventually free the space occupied by dead data, and it does so by **cleaning**: choosing segments whose contents are mostly invalid, copying out whatever is still live, and returning the segment to the free pool.

The cost of cleaning is proportional to the amount of live data in the segments you choose to clean. That gives rise to the central economics of log-structured design: you want to clean segments that are nearly empty, and you want the segments you write to become nearly empty as fast as possible. Both goals are really the same goal — *grouping data by expected lifetime*.

If you write a long-lived file's data into the same segment as a burst of temporary files, then by the time the temporary files are deleted, the segment is mostly live. The cleaner must copy the long-lived data somewhere else in order to reclaim the small dead fraction. That data will then be copied again, and again, each time it happens to share a segment with something short-lived. This is the classic complaint against single-log LFS designs, and it is the thing F2FS's architecture is organized to avoid.

The textbook fix is to separate hot data from cold data into distinct logs. It is easy to state and hard to implement, because a file system cannot know a file's future access pattern. F2FS's answer is a small set of heuristics that are usually right, plus a large set of knobs for when they are not — and, crucially, a design in which being wrong about temperature costs cleaning efficiency and nothing else.

## Six logs, not one

F2FS divides all writes into six **active logs**, one for each combination of temperature (hot, warm, cold) and kind (data, node):

- hot data
- warm data
- cold data
- hot node
- warm node
- cold node

Each active log is a segment that is currently being appended to. At any instant the volume has exactly six open write frontiers, and the main area of the device is a pool of segments being consumed by six independent streams. When one of those segments fills, F2FS closes it, allocates a fresh free segment for that log, and continues. This is what "multi-head logging" means, and it is the single decision from which most of the rest of the file system follows.

The data/node split exists because metadata and file data have utterly different update frequencies, and mixing them reproduces exactly the pollution problem described above. A directory's entries are rewritten on nearly every file creation in that directory. A 200 MB video file's data blocks are written once and never touched again. If those two things land in the same segment, that segment is guaranteed to be expensive to clean for the entire lifetime of the video. Separating them costs a small amount of bookkeeping and removes an entire class of pathological cleaning behavior.

The three-way temperature split is a coarser bet. Two temperatures would capture most of the benefit. Three fits the categories a file system can actually distinguish — directory entries and freshly written file data at the hot end, ordinary file data in the middle, media files, archives, and packages at the cold end. The labels are hints, not contracts. Nothing in the on-disk format depends on them being correct, which is the property that makes a heuristic tolerable in the first place.

### How F2FS decides

A block's temperature is decided at write time, from whatever signal is available.

For data blocks, F2FS looks at the inode. Directories and their entries are treated as hot. Regular files are classified using a combination of heuristics: a built-in table of file extensions presumed cold (media, archives, compressed packages) and a table of extensions presumed hot (database files and similar), both of which can be adjusted at runtime through the per-device sysfs interface rather than by rebuilding the kernel. Files that have never been read, files opened read-only, and files whose data has not been touched recently are biased toward cold.

For node blocks, the level in the tree matters. A direct node block points at file data and is rewritten whenever that data moves, so it is hotter than an indirect node block, which is rewritten only when the shape of the tree changes. The mapping from node type to active log is therefore a statement about expected rewrite frequency, not about importance.

The extension tables are the most obviously heuristic part of the design, and also the most obviously tunable. A build server full of object files and a phone full of JPEGs want different answers, and F2FS lets you give different answers per device without touching the source.

### Segments, sections, and zones

Below the logs, F2FS organizes the volume as a three-level hierarchy. The base unit is a **segment**: 512 blocks of 4 KiB, so 2 MiB. Segments are grouped into **sections**, and sections into **zones**. The default geometry on many devices is one segment per section and one section per zone, so the three levels collapse onto the same 2 MiB unit — but on larger devices `mkfs.f2fs` can be told to group more aggressively.

The hierarchy exists because the allocator needs a unit coarser than a segment for two distinct purposes. Sections are the unit of *locality*: when an active log needs a new segment, F2FS prefers to draw it from a section the same log is already using, so a single stream's writes stay physically close together instead of being scattered across the address space. Zones are the unit of *restraint*: the original design limits how many distinct regions of the device are being written simultaneously, on the theory that a few well-separated sequential streams are easier for an FTL to handle than dozens of interleaved ones. Whether that theory still holds for a modern device with a large internal write buffer and its own scheduler is an open question — and it is one of the reasons F2FS exposes the geometry instead of hard-coding it.

Next: the three-layer address space — logical block addresses, physical block addresses, and node IDs — and why F2FS needs an indirection layer that a conventional log-structured file system does not have.

## Three address spaces, only one of which is a block number

A file system normally has one way to name a block: a logical block number inside a file, resolved through a mapping to a device block. F2FS has two names for a block and one for a node, and the split is not cosmetic.

At the leaf, a data block is named by a **block address**. In the inode and node blocks, this is stored as a device block number: the physical block in the main area where the data lives. A file's logical block 7 is found by walking the inode's address array. At the bottom of that walk, the entry is the block address of the data page. There is no separate data-block indirection table. If the data page moves, the entry that points to it must be rewritten.

At an interior level, a node block is named by a **node ID** (`nid`). A node ID is a 32-bit identifier, stable for the lifetime of the node, and not a block address. The inode points to a direct node by nid; a direct node points to data by block address; an indirect node points to a direct node by nid; a double-indirect node points to an indirect node by nid. The inode itself is a node, and for an inode node the inode number and the node ID are the same value. A directory entry stores an inode number, so resolving a directory entry to an inode is a NAT lookup, not a scan of the directory's data.

The **node address table** is the mapping from nid to block address. It is a flat table indexed by nid, not a B-tree, and it has one entry per possible node. Each entry says where the current version of that node lives. The NAT is cached in memory; a node lookup that misses the cache reads the NAT block, then reads the node block. The NAT is not itself one of the six active logs. It is a separate metadata area whose updates are batched in a NAT journal and made durable by the checkpoint.

Every node block ends with a footer. The footer records the node's nid, its inode number, its node type, and a checkpoint version. The nid in the footer is a self-check: if a block is reached through a NAT entry that claims it is nid 42, the footer must also say 42. The checkpoint version lets recovery tell a node written before the last checkpoint from one written after it, which matters because the NAT and the node block are written separately.

Why not use a NAT for data blocks too? Because data blocks are leaves. A data block is referenced by exactly one entry in one node (hard links share an inode, not a data block), so moving it requires finding that one entry and rewriting it. A node block is interior: it is referenced by its parent through a nid. If node blocks were named by physical block address, moving a node during cleaning would require rewriting its parent, and that parent write might require rewriting its parent, and so on up to the inode. The NAT collapses that cascade into a single entry update. The asymmetry is the price of making the tree cheap to relocate.

It also makes inode lookup cheap. A directory entry contains an inode number. The inode number is the nid of the inode block. To open the file, F2FS looks up that nid in the NAT and reads the block. The inode can move without the directory entry changing. A conventional file system with inodes at fixed locations does not need this; a log-structured file system that moves everything does.

## The NAT is an indirection tax, not a free abstraction

The NAT is not free. Every node access potentially costs an extra metadata read, and every node relocation costs a NAT update. F2FS keeps the NAT resident in memory in normal operation, and it journals NAT changes so that it does not have to write a NAT block for every node write. But the table is still a second structure that must be kept consistent with the node blocks it points to.

The consistency rule is simple: a NAT entry must point to the current copy of the node, and the node's footer must agree with the entry. When the cleaner moves a node, it writes the node to a new block, updates the NAT entry, and only then can the old block be invalidated. When a node is updated normally, the new version is appended to a node log, the NAT entry is updated to the new block address, and the old block becomes stale. The old block is not erased immediately; it is marked invalid in the SIT, and the cleaner will reclaim it later.

The NAT journal is what keeps this from becoming a write-amplification disaster. If every node write forced a synchronous NAT write, the NAT area would become a hot spot and the device would see a small random write for every node update. Instead, F2FS accumulates NAT changes in the checkpoint's NAT journal and writes them in batches. The checkpoint is the point at which the journal and the table are reconciled. Between checkpoints, the in-memory NAT is authoritative; after a crash, recovery replays the journal to reconstruct it.

This is also why the node footer carries a checkpoint version. Suppose a node block was written, then the checkpoint was taken, then the machine crashed before the corresponding NAT block was updated. Recovery needs to know whether the node block is newer than the NAT entry or the other way around. The version in the footer and the version associated with the NAT entry give recovery an ordering. Without it, the NAT could point at a block that has already been reused, or a valid node could be treated as stale.

## SIT: the cleaner's balance sheet

The **segment information table** answers a different question: for each segment in the main area, how many of its 512 blocks are still valid, and which ones? The SIT entry for a segment contains a valid-block count and a bitmap. The count is what the cleaner uses to rank victims. The bitmap is what the cleaner uses to know exactly which blocks it must copy if it chooses that segment.

The SIT is updated on every allocation and every invalidation. When a block is written, its segment's valid count goes up and its bit is set. When a block is overwritten or deleted, its bit is cleared and the count goes down. Those updates are also batched. The checkpoint carries a SIT journal and the allocation bitmap, so a mount does not have to scan every segment to rebuild the table.

Without the SIT, the cleaner would have two bad options. It could scan candidate segments and count valid blocks by reading the SSA, which is expensive and would turn cleaning into a read-amplification problem. Or it could trust a coarse estimate, which would make victim selection unreliable and increase the number of live blocks copied per cleaning cycle. The SIT turns cleaning into a table lookup: pick the segment with the fewest valid blocks, copy those blocks, erase the segment, return it to the free pool.

The SIT also makes the cleaner's cost visible. If a segment has 10 valid blocks out of 512, cleaning it costs 10 block copies plus the metadata writes needed to update the owners of those blocks. If a segment has 400 valid blocks, cleaning it costs 400 copies to reclaim 112 blocks of space. The ratio is terrible, and the cleaner should not choose it unless the free pool is desperate. The SIT is the ledger that makes that comparison possible.

## SSA: the reverse map that makes relocation possible

The forward references in F2FS point from parent to child: an inode points to a direct node by nid, a direct node points to data by block address. The cleaner needs the opposite direction. Given a valid block in a victim segment, it needs to know who owns that block so it can rewrite the owner's reference after moving the block.

That is the **segment summary area**. The SSA stores, for each block in the main area, a summary entry. For a data block, the entry identifies the parent node's nid and the offset within that node where the block address is stored. For a node block, the entry identifies the node's own nid. The SSA is written per segment as a summary block; it is not a B-tree, and it is not consulted on the normal read path. It is a reverse map for cleaning and recovery.

The cleaning sequence for a data block is therefore: read the SSA entry, find the parent node, read the parent, replace the old block address with the new one, write the parent as a new node version, update the parent's NAT entry, write the data block to its new location, and update the SIT for both the old and new segments. The data block move is one write; the parent node update is a second write; the NAT update is a third piece of metadata. This is why cleaning a data block is more expensive than the raw block copy suggests.

For a node block, the sequence is shorter: write the node to a new block, update its NAT entry, and update the SIT. No parent rewrite is needed, because the parent refers to the node by nid and the nid has not changed. The NAT is the only forward reference that must be changed.

The SSA is also a check on the SIT. If the SIT says a block is valid, the SSA should identify an owner that still points to it. If the SIT says a block is invalid, the SSA entry may be stale, but the cleaner will not copy it. A mismatch between the two is a file system inconsistency, and `fsck.f2fs` has to resolve it. The two tables are not redundant: the SIT is an aggregate for victim selection, and the SSA is the per-block ownership record for relocation.

## Checkpoint: the consistency point for six moving tails

Six active logs mean six write frontiers. At any instant, the hot data log has a current segment and an offset, the warm data log has another, the cold node log has another, and so on. A crash can leave those six tails at different points, with some blocks written and some not. The checkpoint is the structure that makes that state recoverable.

A checkpoint records the current segment and offset for each active log, the NAT and SIT journals, the orphan inode list, and the allocation state needed to know which segments are free, which are active, and which are being cleaned. It is written to two fixed locations with sequence numbers, so a torn checkpoint can be detected and the older copy used. The checkpoint is not a transaction log for every write; it is a periodic snapshot that bounds recovery. Between checkpoints, F2FS relies on the journals and on roll-forward recovery for synchronized writes.

The important point is that the checkpoint does not need to describe every block in the six logs. It needs to describe where each log's tail is and which metadata changes are committed. The blocks behind the tails are already described by the NAT, the SIT, and the SSA. The checkpoint ties those descriptions to a single consistent instant, so that a mount can reconstruct the six logs without scanning the entire volume and guessing which blocks belong to which generation.

That is the architecture in miniature: the six logs decide where writes go, the NAT decides how node blocks are found after they move, the SIT decides which segments are worth cleaning, and the SSA decides who must be updated when a block is moved. The checkpoint is the point at which all of those structures agree. The economics of cleaning are the economics of keeping that agreement cheap.

## Two garbage collectors in series

The cleaner described so far is only one of two garbage collectors that stand between an application write and a physical NAND program. The other is the flash translation layer's own collector, and the two are not independent. They are in series, and the cost of the first becomes part of the input to the second.

When F2FS decides to clean a segment, it reads the live blocks, writes them to the tail of the appropriate active log, and updates the metadata that points to them. Those writes are ordinary host writes as far as the device is concerned. The FTL sees a new LBA, programs a fresh page, and marks the old LBA invalid. The F2FS cleaner has reclaimed space in its own logical address space, but it has not erased anything. The physical pages that held the old copies are now invalid, and they will be reclaimed by the FTL's collector when it chooses the erase block that contains them.

This means the total flash write amplification is not a property of F2FS alone or of the device alone. If H is the volume of application writes, C is the volume of F2FS cleaner writes, and G is the volume of FTL garbage collection copies, then the flash sees H + C + G programs. The F2FS-level write amplification is (H + C)/H. The FTL-level write amplification is (H + C + G)/(H + C). The product is the total: (H + C + G)/H. A ten percent increase in C does not just add ten percent; it also increases the base on which G is computed. Reducing C helps twice.

F2FS can influence G as well as C. If its six active logs produce six sequential streams in six distinct LBA regions, the FTL's collector sees large runs of invalid pages when those regions are eventually reclaimed. If F2FS's cleaning produces a burst of random relocations, the FTL sees a scattered write pattern and its collector must copy more live pages per erase block. The temperature separation and the section-based allocation are therefore not only about F2FS's own cleaning cost. They are also a way of presenting a friendly access pattern to the device underneath. The file system is trying to make the FTL's job easier, even though it cannot see the FTL's internal state.

The two collectors also interact through frees. When F2FS invalidates a block in its SIT, the FTL does not automatically know that the corresponding LBA is dead. The FTL's map still says the LBA is live. Only a discard or a subsequent overwrite tells it otherwise. Without that information, the FTL's collector treats stale file data as live and copies it across the device. F2FS's discard support is the bridge between the two layers: it translates a logical free into a device-level hint. The economics of discard are the economics of avoiding a copy in the other collector.

## The cleaner's arithmetic: utilization, cost, and write amplification

The SIT gives the cleaner a per-segment valid block count. That count is the input to a simple and brutal cost model. Let a segment contain s blocks, and let v of them be valid. The utilization is u = v/s. To clean the segment, the cleaner must copy v blocks, plus whatever metadata writes are needed to update the owners of those blocks. If the average metadata cost per copied block is m, the total write cost is v(1 + m). The space reclaimed is s - v = s(1 - u). The cleaning write amplification per reclaimed block is therefore u(1 + m)/(1 - u).

That expression is hyperbolic in u. At u = 0.1, with m = 0.1, the cost is about 0.12 writes per reclaimed block. At u = 0.5, it is about 1.1. At u = 0.9, it is about 9.9. The last case is catastrophic: the cleaner writes ten blocks to free one. The difference between a segment that is ten percent full and one that is ninety percent full is not a factor of nine in cost; it is a factor of roughly eighty. This is why victim selection matters more than almost any other tuning knob. A cleaner that always picks the segment with the fewest valid blocks can stay in the cheap part of the curve. A cleaner that is forced to pick a nearly full segment has already lost.

The distribution of u across the volume is determined by the write pattern and by the temperature separation. In a single-log design, every segment sees the same mix of hot and cold data, so u tends to be similar across segments and tends to be high. In F2FS, the hot logs produce segments that become invalid quickly, so their u is low. The cold logs produce segments that stay valid for a long time, so their u is high. The cleaner can clean the hot segments cheaply and leave the cold segments alone. But the cold segments still occupy space. If the workload deletes a large cold file, its segments become u = 0 and are suddenly cheap. If the workload never deletes cold data, those segments never need cleaning, and they are not a problem. The problem is pollution: a cold segment that also contains hot data will have a high u even after the hot data is deleted, because the cold data remains. Cleaning it costs a copy of the cold data. Temperature separation is the mechanism that keeps the hot data out of the cold segments, so that the cold segments can be left alone until they are either fully dead or never cleaned at all.

The cleaner's arithmetic also shows why the free-space target cannot be zero. If the free pool is empty, the cleaner must clean the first segment it can find, regardless of u. That segment may be nearly full. The cost of that emergency cleaning is high, and it may trigger more cleaning because the copied blocks consume free space. A small reserve of free segments acts as a shock absorber. It lets the cleaner wait for a better victim. The size of that reserve is the overprovisioning ratio, and it is the most direct lever an administrator has over the cleaning cost.

## Victim selection, free-space targets, and the latency tail

F2FS does not clean a segment the moment it becomes closed. It waits until the free segment count falls below a threshold, then a background thread starts looking for victims. If the count falls further, the allocation path itself may trigger a foreground cleaning operation. The difference between the two is latency. Background cleaning runs asynchronously; foreground cleaning blocks the thread that needs a new segment. A foreground clean can turn a write into a read-modify-write sequence: the allocator waits while the cleaner reads live blocks, writes them elsewhere, updates metadata, and finally frees a segment. The application sees a latency spike that has nothing to do with its own I/O pattern.

The cleaner's victim selection is therefore a scheduling problem as well as a cost problem. It wants to clean segments with low u, but it also wants to clean them early enough that the free pool never runs dry. Those two goals pull in opposite directions. A segment with low u is cheap to clean now. A segment with high u might become cheap later if its data is deleted. Waiting is free in terms of writes, but it consumes free space. The classic cost-benefit policy from log-structured file systems balances the benefit of freeing space against the cost of copying live data, and it uses the age of the segment as a proxy for how likely the remaining data is to die soon. F2FS's cleaner is in this family. It ranks candidates by valid block count and uses age and section locality as tie-breakers. The exact weights are implementation details, but the shape of the tradeoff is universal.

The latency tail is the reason overprovisioning is not just a throughput optimization. A larger free pool means the background cleaner can run at a leisurely pace. It can wait for segments to age. It can avoid foreground cleaning entirely. The cost is capacity: every segment reserved for cleaning is a segment the file system cannot use for files. The administrator is buying a lower variance in write latency and a lower cleaning write amplification with the currency of capacity. On a device that is mostly read-only, that currency is cheap; on a device that is nearly full and write-heavy, it is expensive.

## Cleaning is not uniform across the six logs

The six active logs do not have the same cleaning economics. Each one has a characteristic update frequency, and that frequency determines the expected utilization of its segments.

The hot data log holds directory entries, small temporary files, and other metadata-like data that is rewritten frequently. A segment in this log fills with entries that are likely to be overwritten or deleted soon. By the time the cleaner looks at it, most of its blocks are invalid. Its u is low, and cleaning it is cheap. The hot node log is similar: direct node blocks are rewritten whenever the file data they point to moves. They have a short lifetime in the log.

The warm data log holds ordinary file data. Its update frequency depends on the workload. A file that is written once and read many times produces warm segments that stay valid. A file that is rewritten in place produces warm segments that churn. The cleaner's cost here is moderate.

The cold data log holds media files, archives, and other data that is written once and rarely touched. A cold segment can remain almost fully valid for the lifetime of the file. Cleaning it is expensive, so the cleaner avoids it. This is not a problem as long as the cold data is not deleted. If it is deleted, the segment becomes cheap. The danger is a cold segment that has been polluted by hot data. The hot data dies quickly, but the cold data remains, so the segment's u stays high. The cleaner must either copy the cold data or leave the segment in place. Temperature separation prevents this by keeping the hot data out of the cold log in the first place.

The cold node log holds indirect node blocks. They are rewritten only when the shape of the file's node tree changes, which is rare. Their segments are similar to cold data segments: high u, expensive to clean, and best left alone.

The free segment pool is shared across all six logs, but the allocator must ensure that each log has a current segment to write into. If the cold log runs out of free segments, the cleaner must clean a cold segment, which is expensive. If the hot log runs out, cleaning is cheap. The SIT's per-segment valid counts let the cleaner choose victims from the log that needs space, and the temperature separation ensures that the cheap victims are concentrated in the hot logs. The overall cleaning cost is a weighted average of the per-log costs, and the weights are the allocation rates of the logs. A workload that writes mostly cold data will have a higher cleaning cost than a workload that writes mostly hot data, even if the total write volume is the same.

## When the FTL disappears: zoned namespaces and the single-level cleaner

The two-level model of F2FS cleaning plus FTL garbage collection assumes that the device hides its physical layout behind a block interface. Zoned namespaces remove that assumption. A ZNS device exposes zones that must be written sequentially, and it does not perform garbage collection internally. The host is responsible for resetting zones and for moving live data out of them before resetting. The FTL's collector disappears, and F2FS's cleaner becomes the only reclamation mechanism.

This changes the economics in a way that is mostly simplifying. The total write amplification is no longer a product of two stages; it is just the F2FS-level amplification, (H + C)/H. The FTL's G is zero because there is no FTL GC. But the constraints are stricter. A zone cannot be partially overwritten; it must be reset as a unit. The cleaner must copy every live block out of a zone before it can reset it. The zone's write pointer must advance sequentially, so the cleaner's writes must go to the tail of the appropriate active log. F2FS's multi-head logging maps naturally onto this model: each active log can be assigned to a zone, and the six logs become six write pointers. The temperature separation keeps hot and cold data in different zones, so the cleaner can reset hot zones cheaply and leave cold zones alone.

The benefit is that the host knows the true cost of reclamation. It can see the zone capacity, the write pointer, and the number of valid blocks. It can make better victim selection decisions than an FTL that only sees LBAs. The cost is that the host must manage the free zone pool explicitly. There is no device-level overprovisioning to absorb mistakes; the host's overprovisioning is the only buffer. F2FS's segment cleaner, which was already responsible for its own logical reclamation, becomes the entire reclamation system. The architecture was designed for a world where the device hides its GC; in a ZNS world, the same architecture is exposed and must stand on its own.

## Discard, overprovisioning, and the price of free space

Discard is the mechanism by which F2FS tells the FTL that a block is dead. Without it, the FTL's map treats every LBA that has ever been written as live, and its collector copies stale file data across the device. With it, the FTL can mark the LBA invalid and avoid that copy. The benefit of discard is a reduction in G, the FTL's garbage collection traffic. The cost is the discard command itself, which may be slow and may serialize with other I/O. F2FS batches discards and issues them from a background workqueue, and it allows the administrator to choose the discard unit: per block or per segment. The tradeoff is between the precision of the hint and the number of commands. A segment-level discard is one command for many blocks, but it tells the FTL that the entire segment is dead, which is only true if the cleaner has already moved all live data out of it. A block-level discard is more precise but more expensive.

Overprovisioning is the other lever. F2FS reserves a configurable percentage of the device as free space that the file system does not allocate. Those reserved segments serve as the cleaner's working pool. They let the cleaner wait for segments to age, which lowers the average u of the segments it cleans, which lowers C. They also reduce the logical capacity of the file system. The administrator is trading capacity for cleaning efficiency. The optimal ratio depends on the workload: a write-heavy workload with high churn benefits from more overprovisioning, while a read-only or archival workload needs less. The device's own overprovisioning is separate and is hidden from F2FS. If F2FS uses all the logical space it sees, the FTL's only reserve is its internal one. If F2FS reserves some space, the FTL sees a less-full device, which also helps its collector. F2FS-level overprovisioning is therefore not just a file-system optimization; it is also a way of giving the FTL room to work. The price of free space is paid twice: once in lost capacity, and once in the cleaning writes that are avoided.

## The write path: from VFS to six logs

When an application calls write(2), the data lands in the page cache of the inode. F2FS does not write it to the device immediately. The page is marked dirty, and the writeback machinery will eventually call f2fs_write_data_page. The same is true for metadata: when a file is created or a directory entry is added, the inode and the directory's data blocks are dirtied in memory. The file system's job at writeback time is to decide where each dirty block goes and to update the structures that point to it.

The first decision is the block's type. F2FS distinguishes between data blocks and node blocks. A data block holds file contents or directory entries. A node block holds the inode itself, a direct node, an indirect node, or a double-indirect node. The type is determined by the context of the write: f2fs_write_data_page is called for data pages, and f2fs_write_node_page for node pages. The inode's own block is a node block, and it is written through the node path.

The second decision is the temperature. For a data block, F2FS calls f2fs_get_data_type, which inspects the inode. If the inode is a directory, the block is hot. If it is a regular file, the function consults the extension tables and the file's access history. A file that has never been read is biased cold; a file that has been read recently is biased warm. The extension tables map known suffixes to temperatures: .mp3, .jpg, .zip, and .apk are cold; .db and .sqlite are hot. These tables are exposed in sysfs and can be changed at runtime. For a node block, f2fs_get_node_type looks at the node's level. A direct node is hot; an indirect node is warm; a double-indirect node is cold. The inode block itself is hot, because it is updated on every file size change and every timestamp update.

Once the type and temperature are known, F2FS calls f2fs_allocate_data_block. This function selects the active log for that combination. There are six active logs, and each has a current segment and a write pointer. The allocator picks the log that matches the type and temperature, and if that log's current segment is full, it closes the segment and allocates a new one from the free pool. The free pool is a list of segments that have been cleaned and are ready to be written. If the free pool is empty, the allocator triggers the garbage collector, which we will discuss later.

The block is then written to the current segment at the write pointer. The write pointer advances. The SIT entry for the segment is updated: the valid block count is incremented, and the bitmap bit for the block is set. The SSA entry is also updated: for a data block, it records the parent node's nid and the offset within that node; for a node block, it records the node's own nid. These updates are in memory; they are not written to the device immediately. They are journaled in the SIT and SSA journals, which are part of the checkpoint.

If the block is a node block, the NAT entry for its nid must be updated to point to the new block address. This update goes into the NAT journal. If the block is a data block, the parent node must be updated to point to the new block address. That parent node is itself a node block, so it goes through the node write path: it is allocated to a node log, written, and its NAT entry is updated. This can cascade if the parent is an indirect node, but the cascade stops at the inode, whose nid is fixed and whose NAT entry is updated last.

The write path is therefore a chain of allocations and metadata updates. A single data block write can cause one data block write, one or more node block writes, and several NAT and SIT updates. The checkpoint is what makes this chain durable. Until the checkpoint is written, the updates are only in memory and in the journals. If the system crashes, recovery replays the journals and reconstructs the in-memory state. The checkpoint is taken periodically, and it records the current write pointers for all six logs, the NAT and SIT journals, and the orphan inode list.

## The read path: resolving a node ID

Reading a file is simpler than writing it, but it still requires walking the node tree. When an application calls read(2), the page cache is checked first. If the page is present, the read is satisfied without touching the device. If it is not, f2fs_read_data_page is called. To read the data, F2FS must find the block address of the file's logical block.

The inode is the starting point. The inode number is the nid of the inode block. F2FS looks up that nid in the NAT. The NAT is cached in memory; if the entry is present, the block address is known immediately. If not, F2FS reads the NAT block that contains the entry. The NAT is a flat array, so the block containing a given nid is computed by division: nid / NAT_ENTRY_PER_BLOCK. The NAT block is read, the entry is extracted, and the NAT cache is updated.

With the inode's block address, F2FS reads the inode block. The block is verified by checking its footer: the footer must contain the expected nid and a valid checkpoint version. The inode block contains the file's metadata and the root of its node tree. For a small file, the inode may contain direct block addresses, in which case the data block address is found immediately. For a larger file, the inode points to a direct node by nid. F2FS looks up that nid in the NAT, reads the direct node block, and finds the data block address in its array. For even larger files, the inode points to an indirect node, which points to a direct node, and so on.

Each node block read is a separate I/O. A cold read of a large file can therefore require several metadata reads before the data block is reached. F2FS mitigates this with the node cache, which keeps recently used node blocks in memory. The NAT cache does the same for NAT entries. On a warm cache, the only I/O is the data block itself. On a cold cache, the read path is a sequence of dependent reads: NAT block, node block, next node block, data block. The latency of a cold read is the sum of those latencies, and it is one of the reasons F2FS performs well on sequential reads but can be slower on random reads of cold files.

The SSA is not consulted on the read path. It is a reverse map, used only by the cleaner and by recovery. The read path uses the forward references: inode to node, node to data. The NAT is the only indirection that is not stored in the node tree itself. This is why the NAT is so important: without it, every node read would require a scan of the parent, and the read path would be much longer.

## The garbage collector in practice: threads, modes, and urgency

F2FS runs its cleaner in a dedicated kernel thread, f2fs_gc_thread. The thread sleeps until it is woken by the allocator when the free segment count falls below a threshold. The threshold is a function of the overprovision ratio and the number of reserved segments. When the thread wakes, it calls f2fs_gc, which selects a victim segment and cleans it.

Victim selection uses a cost-benefit policy. The cleaner maintains a list of dirty segments, each with a valid block count from the SIT. It computes a score for each candidate: the benefit of freeing the segment's dead space divided by the cost of copying its live blocks. The benefit is proportional to the segment's age, on the theory that older segments are more likely to contain data that will never be read again. The cost is proportional to the valid block count. The segment with the highest score is chosen. If the score is below a threshold, the cleaner may decide to wait, but if the free pool is critically low, it must clean something regardless.

F2FS supports several GC modes, controlled by sysfs. The gc_idle knob has three values. When set to 0, the GC thread runs whenever it is needed, regardless of I/O load. When set to 1, the GC thread only runs when the device is idle, which reduces interference with foreground I/O but can lead to free-space exhaustion under sustained write load. When set to 2, the GC thread runs in "urgent" mode, cleaning as aggressively as possible. The gc_urgent knob is a separate switch that forces the GC thread to run continuously, ignoring the free-space threshold. It is used for testing and for devices that have accumulated a large amount of invalid data. The gc_merge knob allows the GC to merge with the allocation path, so that a segment is cleaned as part of the allocation that needs it, rather than in a separate thread.

Foreground GC happens when the allocator cannot find a free segment and the background thread has not freed one in time. The allocator calls f2fs_gc synchronously, which means the thread that needs the segment blocks until the cleaner finishes. This is the source of the latency spikes described earlier. The foreground GC can also be triggered by a checkpoint, because the checkpoint needs free space to write the new checkpoint blocks. F2FS tries to avoid foreground GC by keeping a reserve of free segments, but if the workload is write-heavy and the overprovision is small, foreground GC is inevitable.

The GC thread also handles discard. After a segment is cleaned and its live blocks are moved, the segment is erased and returned to the free pool. F2FS can issue a discard for the segment, telling the FTL that the LBAs are no longer needed. The discard is issued from a separate workqueue, f2fs_discard_work, which batches discards and submits them to the block layer. The discard unit can be set to segment or block. Segment-level discard is more efficient but less precise; block-level discard is more precise but generates more commands. The choice depends on the device's discard performance and on the workload's sensitivity to discard latency.

## Orphan inodes and the recovery of unlinked files

When a file is unlinked, its directory entry is removed, but the inode is not freed if the file is still open. The file system must keep the inode alive until the last file descriptor is closed, and then it must free the inode and its data blocks. F2FS handles this with an orphan inode list. When a file is unlinked and its link count drops to zero but it is still open, F2FS adds its inode number to the orphan list. The list is stored in the checkpoint. When the file is finally closed, F2FS removes the inode from the orphan list and frees it.

If the system crashes while an inode is on the orphan list, recovery must clean it up. On mount, F2FS reads the orphan list from the checkpoint and deletes each orphan inode. This prevents space leaks from unlinked but open files that were never closed. The orphan list is also used by fsck.f2fs to detect inconsistencies. The list is small and is updated only when files are unlinked or closed, so it does not add significant overhead to the write path.

The orphan inode list interacts with the garbage collector. An orphan inode's data blocks are still valid until the inode is deleted, so the cleaner will treat them as live. Once the inode is deleted, its blocks become invalid, and the segments that contain them become cheaper to clean. This is another reason why the cleaner prefers to wait: a segment that contains orphan data may become much cheaper after the orphan is cleaned up. The checkpoint's orphan list is therefore part of the cleaner's information set, even though the cleaner does not read it directly.

## Tuning and observability: sysfs, debugfs, and f2fs-tools

F2FS exposes a large number of tuning knobs through sysfs, under /sys/fs/f2fs/<device>/. The most important are the GC knobs: gc_idle, gc_urgent, and gc_merge. The discard knob controls whether discard is enabled and what unit is used. The iostat_enable knob turns on per-operation statistics, which can be read from /sys/fs/f2fs/<device>/iostat. The extension tables are in /sys/fs/f2fs/<device>/extension_list, and they can be modified at runtime to change the temperature classification of file extensions.

Debugfs provides a deeper view. /sys/kernel/debug/f2fs/ contains per-device directories with files that dump the segment information, the NAT, the SIT, and the SSA. The "status" file shows the current state of the six active logs, the free segment count, and the number of dirty segments. The "victim" file shows the cleaner's current victim selection. These files are useful for understanding why the cleaner is behaving the way it is, and for tuning the overprovision ratio.

The f2fs-tools package provides mkfs.f2fs, fsck.f2fs, and dump.f2fs. mkfs.f2fs creates the file system and sets the initial geometry: the segment size, the section size, the zone size, and the overprovision ratio. The -l option sets the label, -s sets the segment size, -z sets the zone size, and -o sets the overprovision ratio. The -O option enables features like compression, inline data, and verity. fsck.f2fs checks and repairs the file system, using the SIT, SSA, and NAT to detect inconsistencies. dump.f2fs prints the contents of the metadata structures, which is useful for debugging.

The overprovision ratio is the most consequential mkfs parameter. It determines how many segments are reserved for the cleaner. A ratio of 5% is typical for mobile devices; a ratio of 20% or more may be appropriate for write-heavy servers. The ratio is set at mkfs time and cannot be changed without reformatting, so it must be chosen with the workload in mind. The discard unit and the GC mode, by contrast, can be changed at mount time or at runtime through sysfs. This asymmetry reflects the fact that overprovisioning changes the on-disk layout, while the other knobs change only the runtime policy.

## Compression and the cold-data log

F2FS supports transparent compression on a per-file or per-directory basis. When enabled, data blocks are compressed before being written to the cold data log. The compression is cluster-based: a cluster of four blocks (16 KiB) is compressed into one or more blocks, and the compressed blocks are written sequentially. The inode records the compression algorithm and the cluster size.

Compression changes the cleaning economics in two ways. First, it reduces the volume of data written to the cold log, which lowers the allocation rate of the log that is hardest to clean. A cold segment fills more slowly, so the cleaner has more time to wait for it to age. Second, it makes the cold segments more homogeneous: compressed blocks have similar lifetimes, so a cold segment is less likely to be polluted by short-lived data. The cost is that compression must be undone on read, which adds CPU time to the read path. But since cold data is rarely read, that cost is usually hidden.

The interaction with the SIT is subtle. A compressed cluster may occupy fewer blocks than the uncompressed data, so the SIT's valid block count for a cold segment reflects the compressed size, not the logical size. The cleaner still copies valid blocks, but there are fewer of them. This is one of the few cases where a file system feature directly reduces the cleaner's write amplification without changing the temperature heuristics.
