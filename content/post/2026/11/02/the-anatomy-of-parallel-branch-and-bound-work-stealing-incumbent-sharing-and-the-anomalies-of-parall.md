Parallel branch-and-bound is the workhorse behind mixed-integer programming solvers, constraint-programming engines, scheduling and packing tools, and a long tail of domain-specific optimizers. It is also one of the least parallel-friendly algorithms that people routinely try to parallelize, and the gap between those two facts is where most of the engineering effort gets spent.

The reason is structural. Branch-and-bound does not have a fixed amount of work. Its work is defined by a tree that it builds as it searches, and the shape of that tree depends on the quality of the feasible solutions it happens to find and on the order in which it visits nodes. A single good incumbent discovered early can prune an exponential number of subtrees; the same incumbent discovered late is nearly worthless. Parallelism changes which nodes are visited when, which changes which incumbents are found when, which changes the tree. You are not parallelizing a computation; you are perturbing a search.

This article is about the design space that results. It is not a tutorial on branch-and-bound and it is not a survey of solvers. It is an attempt to lay out the axes along which parallel branch-and-bound implementations actually differ, the coupling channels that constrain them, and the anomalies that make naive speedup reasoning wrong.

## 1. Branch-and-bound is a family, not an algorithm

It is tempting to treat branch-and-bound as a single algorithm with a few tuning knobs. It is more accurate to treat it as an interface with four required components, each of which admits radically different implementations:

1. **A branching rule.** Given a subproblem (a *node*), produce a finite set of child subproblems whose feasible regions partition the parent's feasible region. For a mixed-integer program this is typically a variable-selection rule plus a rounding direction; for a constraint program it is a variable/value ordering plus propagation; for a scheduling problem it may be a disjunctive split on a machine or a precedence.
2. **A bounding function.** Given a node, produce a value that is a valid lower bound (for minimization) on the objective over the entire subtree rooted at that node. This is usually a relaxation — an LP relaxation, a Lagrangian relaxation, a constraint-propagation-derived bound, or a combinatorial bound.
3. **A pruning rule.** Decide whether a node can be discarded because its bound is no better than the current incumbent, because its feasible region is empty, or because of a dominance argument that shows the subtree cannot contain a strictly better solution than one already known.
4. **A node-selection strategy.** Decide which of the currently open nodes to explore next.

Every one of these is a design decision with real consequences, and the choices interact. A weak bounding function makes node selection almost irrelevant because pruning never fires. A strong bounding function makes node selection dominant because the order in which you visit nodes determines how quickly you find a good incumbent. A branching rule that produces unbalanced children changes the memory profile of the search and therefore changes which node-selection strategies are even feasible.

Parallelism is a fifth axis that cuts across all four. It is not orthogonal: parallelizing the search changes the effective node-selection order, changes which incumbents are available to which workers at which times, and therefore changes the pruning that actually occurs. The rest of this article is about that interaction.

## 2. The sequential core, stated precisely

To reason about parallelism we need a precise statement of what the sequential algorithm guarantees, because those guarantees are exactly what parallel implementations weaken.

Let a problem be a pair $(S, f)$ where $S$ is a set of feasible solutions and $f: S \to \mathbb{R}$ is an objective to be minimized. Define a *node* $n$ by a feasible region $S_n \subseteq S$. The root has $S_{root} = S$. A branching rule maps a node to children $n_1, \dots, n_k$ with $\bigcup_i S_{n_i} = S_n$ and $S_{n_i} \cap S_{n_j} = \emptyset$ for $i \neq j$. A bounding function $\ell$ satisfies $\ell(n) \le \min_{x \in S_n} f(x)$ for every node. A node is *pruned by bound* when $\ell(n) \ge U$, where $U$ is the value of the best known feasible solution, called the *incumbent*.

Three invariants make the sequential algorithm correct:

- **Validity.** $\ell$ is a true lower bound on the subtree, not an estimate.
- **Exhaustiveness.** The branching rule eventually partitions the region into leaves that are either solved exactly or proven infeasible.
- **Non-destructiveness of pruning.** A node is discarded only when it provably cannot contain a solution strictly better than the incumbent.

Termination follows from the finiteness of the tree (for finite-domain problems) plus the fact that the incumbent only improves and is bounded below. For problems with continuous variables, termination requires an absolute or relative gap tolerance, and the algorithm's contract becomes "return a solution within $\epsilon$ of optimal" rather than "return the optimum."

That contract is worth stating explicitly because parallelism tends to erode it. A parallel search that shares incumbents asynchronously is still correct — the incumbent is always a real feasible solution — but the *set of nodes pruned* depends on timing. Two runs with identical inputs and different thread interleavings can explore different trees and return the same optimal value via different paths. That is usually acceptable, but it destroys reproducibility, which matters for debugging, for certification, and for any workflow that needs to explain why a bound was what it was.

### Node selection and the memory trade-off

The node-selection strategy determines the shape of the search, and it also determines the memory footprint. The two dominant strategies sit at opposite ends:

- **Best-first search** maintains a priority queue of open nodes ordered by $\ell$. It minimizes the number of nodes expanded to prove optimality for a given bounding function, but its queue can grow to the size of the explored tree. For hard instances that is a memory catastrophe.
- **Depth-first search** maintains a stack and expands the most recently created node. Its memory is proportional to the depth of the tree, which is small, but it may explore enormous subtrees whose bounds are far worse than the global best open node.

Production solvers almost always use a hybrid. A common pattern is best-first selection with periodic depth-first *dives*: pick the globally most promising node, then follow a chain of branching decisions to a leaf, generating incumbents cheaply. Another pattern is a two-tier scheme where a bounded-size priority queue is combined with a depth-first fallback when the queue exceeds a threshold. The threshold is not a tuning detail; it is the mechanism that keeps the solver inside a memory budget.

This matters for parallelism because the memory trade-off is not preserved under parallelization. If $p$ workers each maintain a private best-first queue, the aggregate memory is $p$ times larger, and the queues diverge: each worker's notion of "most promising" is computed against a different incumbent and a different set of locally known nodes. The search fragments.

## 3. Four parallelization axes

When people say "parallel branch-and-bound" they usually mean one of four quite different things. Conflating them is the source of a great deal of confused performance analysis.

**Parallel tree search.** The tree is partitioned across workers, and each worker explores a subset of nodes. This is the most general form and the one with the hardest coupling problems, because the incumbent is shared and pruning is global. It is the subject of most of this article.

**Parallel portfolio.** Several complete solvers, or several configurations of one solver, run on the same instance simultaneously, and the first to finish wins. This is embarrassingly parallel in the sense that no state is shared except the incumbent and the termination signal. Its scaling is bounded by the number of meaningfully distinct configurations, which is small — typically single digits. Its value is variance reduction rather than throughput: on a heavy-tailed instance distribution, running eight configurations and taking the best often beats running one configuration eight times longer, because the tail is dominated by instances where the default heuristic happens to be wrong.

**Parallel bounding.** The bounding function itself is parallelized: the LP relaxation is solved by a concurrent simplex or a parallel interior-point method, or the constraint propagation is parallelized, or the subproblem solver is a parallel dynamic program. This is the axis that most resembles ordinary numerical parallelism, and it inherits the usual concerns — sparse factorization, load balance in the linear algebra, and the fact that LP relaxations at deep nodes are small and do not parallelize well.

**Parallel cut generation and separation.** In a cutting-plane or branch-and-cut framework, the separation routines that find violated valid inequalities are run concurrently. This is a genuinely useful axis because separation is often a large fraction of node time and because the subroutines are independent given the current LP solution.

Most real solvers combine at least two of these. The important observation is that they have different scaling ceilings and different failure modes. Portfolio scaling dies at small $p$. Bounding scaling dies when nodes get small. Cut separation scales well but only until the LP solve dominates. Tree search has no intrinsic ceiling but suffers from the coupling problems described below.

## 4. Three coupling channels

A parallel tree search is a distributed system, and like any distributed system it is defined by what its components must share. There are three channels, and they have very different latency and bandwidth requirements. Designs that treat them as one channel tend to be bad.

**The search channel.** Nodes must move between workers. A worker that finishes its local work needs to obtain more; a worker that generates more nodes than it can process needs to give some away. This channel carries the bulk of the data and its throughput determines whether workers stay busy. The unit of transfer is a node, and a node's size varies enormously: a shallow node may carry a large LP basis, a set of local cuts, a propagation trail, and a variable-fixing state; a deep node may be a handful of integers. Transferring a node is not a memcpy.

**The incumbent channel.** Workers must publish improved feasible solutions and learn about improvements from others. This channel carries tiny messages — a value and a solution vector — but its *latency* is critical, because the incumbent determines pruning. A stale incumbent means wasted work; a fresh incumbent means deleted subtrees. Crucially, the incumbent channel is a broadcast with a monotone value: only improvements matter, so it can be implemented as a lock-free single-writer-per-improvement register with relaxed reads.

**The memory and cut channel.** In branch-and-cut, nodes share a pool of globally valid inequalities, and in constraint programming they may share a global constraint store. This channel is the hardest to distribute because the shared state is both large and semantically load-bearing: a cut that is valid globally can be added to any node's relaxation, but the bookkeeping of which cuts are active where, and the LP basis updates that follow, are expensive to replicate.

The practical consequence is that the three channels want different mechanisms. The search channel wants batched, asynchronous, high-throughput transfer with coarse granularity. The incumbent channel wants immediate, low-latency, lock-free broadcast with fine granularity. The memory channel wants either full replication (simple, memory-hungry) or a shared store with careful consistency (complex, memory-efficient).

A common design mistake is to route all three through a single central coordinator, which then becomes both a bandwidth bottleneck and a latency bottleneck. The incumbent channel in particular should almost never traverse a central server, because the cost of a round trip through a coordinator is paid on the critical path of every pruning decision.

## 5. Work distribution: the tree does not exist yet

Here is the property that separates parallel branch-and-bound from nearly every other parallel workload. In a parallel loop, the iteration space is known before execution begins. In parallel graph traversal, the graph is known and only the frontier is discovered. In branch-and-bound, the *tasks themselves are the output of the computation*. You cannot enumerate the nodes in advance because generating a node requires branching its parent, and branching is part of the search.

This has several consequences.

First, **static partitioning is impossible in any meaningful sense.** You cannot split the tree into $p$ balanced pieces because the tree has not been built. Any attempt to partition up front must partition the *problem* rather than the *search* — for example, by fixing different subsets of variables at the root — and that produces wildly unbalanced subproblems whose difficulty is not predictable from their size.

Second, **granularity is uncontrolled.** A node's processing cost spans many orders of magnitude. A node near the root may require solving a large LP, running expensive separation, and generating hundreds of children; a node near a leaf may be resolved by propagation in microseconds. Any work-distribution scheme with a fixed granularity will either waste time on tiny transfers or leave workers idle waiting for large ones. The standard mitigation is *adaptive granularity*: a worker that donates work donates a subtree rather than a single node, and the size of the donated subtree is chosen based on the donor's estimate of how much work remains. Getting that estimate right is a research problem in its own right.

Third, **the work is discovered incrementally and the discovery is coupled to the incumbent.** A worker that receives a subtree and then learns of a better incumbent may find that most of the subtree is prunable. The donated work was real when it was donated and is worthless when it arrives. This is not a bug; it is the fundamental tension between distributing work and sharing information.

The distribution mechanisms that have been used in practice fall into a few families:

- **Centralized pool.** A master process holds the open-node queue; workers request nodes and return children. Simple to reason about, easy to make deterministic, and a hard scalability ceiling: the master's throughput caps the system.
- **Distributed pool with hashing.** Workers own partitions of the node space, addressed by a hash of some node identifier. This removes the central bottleneck but makes it hard to maintain a global best-first order, and it complicates load balancing because a worker's partition may be hot.
- **Work stealing.** Each worker maintains a private deque; idle workers steal from the tail of a victim's deque while the victim pushes and pops from the head. This is the design popularized by Cilk-style runtimes and it works well when the work is fork-join shaped. Branch-and-bound is not fork-join shaped, but the stealing discipline still applies: stealing from the tail tends to take larger subtrees, which is exactly what you want for coarse-grained work.
- **Work donation (pushing).** Instead of idle workers pulling, busy workers push excess subtrees to a shared structure or directly to known-idle peers. Pushing can reduce latency relative to pulling when the donor knows it has surplus, but it requires the donor to spend time deciding what to give away, and a poorly chosen donation can hand a peer a subtree that is about to become worthless.

The choice among these is not a matter of taste. It depends on the ratio of node-processing time to node-transfer time, on whether the incumbent channel is fast enough to make donated work go stale, and on whether the implementation needs determinism. That last point deserves emphasis: deterministic parallel branch-and-bound is achievable — you can fix the order in which nodes are expanded by assigning each node a deterministic priority and having workers process nodes in a globally consistent order — but the cost is that workers must synchronize on the frontier, which reintroduces the central bottleneck in a different form. Nondeterministic search is faster in expectation and harder to debug, certify, and reproduce.

This is where the design space starts to bite. The next part of this article examines the mechanisms in detail: how incumbent sharing is implemented without a lock on the critical path, why parallel pruning produces speedup anomalies that violate the intuition from loop parallelism, how memory management for open nodes becomes the binding constraint at scale, and what the distributed and accelerator variants of branch-and-bound look like when the tree must be split across machines rather than cores.

## 6. Incumbent sharing without a lock on the critical path

The incumbent channel is the smallest and most important channel in a parallel branch-and-bound. It carries only improvements, and improvements are monotone: for minimization, the incumbent value only decreases. That monotonicity is what makes lock-free sharing both possible and safe. A worker that reads a stale incumbent reads a value no better than the current one. If it prunes a node because the node's bound is at least the stale value, the same pruning is valid against the current value. Stale information can cause a worker to do too much work, never too little. This asymmetry is the foundation of every practical incumbent-sharing scheme.

The usual representation is an immutable record containing the objective value, the feasible solution vector, and a version or epoch number. The record is constructed completely, then published by an atomic pointer swap. Readers load the pointer and treat the record as read-only. A writer that finds a better feasible solution reads the current pointer, compares values, and attempts a compare-and-swap; if the swap fails because another worker improved the incumbent first, the writer either retries with the new record or discards its candidate. The result is a single-writer-at-a-time, multi-reader monotone register with no lock on the read path. The memory ordering needs care: the record must be fully initialized before the pointer is published, and readers must acquire the pointer before reading the record. In practice this is a release store and an acquire load, or a relaxed load plus a fence where the cost matters. The important point is that the critical path for pruning is a pointer load, not a lock acquisition.

Two design choices dominate the performance of this channel. The first is polling frequency. A worker can check the incumbent before every node, after every bounding operation, or only when it is about to push children. Checking too often adds atomic loads and branch instructions to hot loops; checking too rarely leaves the worker pruning against stale information. The right frequency is tied to node cost. If a node takes milliseconds, checking once per node is cheap. If a node takes microseconds, the check itself can become a measurable fraction of the work, and the implementation should batch checks or refresh a local copy on a timer or after a fixed number of expansions. The second choice is push versus pull. A publisher can write to a shared atomic that every worker polls, or it can send messages to workers that update local copies. Shared atomics are simpler and have lower latency for small core counts; message-based dissemination scales better across sockets and machines but introduces a delay before a worker sees the improvement. In a distributed setting the usual compromise is a gossip or tree broadcast: improvements propagate in logarithmic rounds, and workers tolerate a bounded lag.

The correctness boundary is the feasibility of the incumbent. A candidate solution must be verified before it is published. In a mixed-integer solver this means checking integrality, variable bounds, and constraint feasibility, and computing the objective from the verified vector rather than trusting a relaxation value. In a constraint program it means checking that the assignment satisfies every constraint, including global constraints whose propagation may have been incomplete. Publishing an infeasible candidate is not a performance bug; it is a correctness bug that can cause the search to prune the true optimum. For this reason the incumbent channel should be treated as a certified channel, not as a heuristic hint. Heuristic solutions can be shared, but they should be labeled as such and never used for pruning until they are certified. Some systems maintain two registers: a bound register that holds a valid lower bound on the optimal value and a solution register that holds the best certified feasible solution. The bound register can be updated by relaxation-derived bounds and by certified incumbents; the solution register only by certified solutions. This separation makes the pruning logic explicit and prevents a common class of bugs in which a heuristic value is accidentally used as a pruning threshold.

The interaction with work stealing is subtle. A stolen subtree may be prunable by the time it arrives. The receiver should check the root bound of the stolen subtree against the current incumbent before doing any expensive reconstruction. This prune-on-receive rule avoids the worst case in which a worker pays the transfer cost for a subtree that is immediately discarded. The donor can also prune before donating, but it should do so against the incumbent it knows at donation time; if its information is stale, it may donate work that the receiver will discard, which is wasteful but safe. The opposite error — filtering donations against a future incumbent that the donor has not yet seen — is impossible, so the asymmetry holds. The practical cost is that prune-on-receive can turn a steal into an empty steal. A work-stealing runtime that counts empty steals as evidence of load imbalance may then over-steal, adding overhead without moving useful work. The fix is to distinguish empty because no work exists from empty because the work was pruned, and to adjust the stealing policy accordingly.

## 7. The anomalies of parallel pruning

The speedup reasoning that works for loop parallelism starts with a fixed amount of work. If a sequential program takes time T and you run it on p processors, the best you can hope for is T/p, and efficiency is at most one. Branch-and-bound violates the premise. The amount of work is not fixed; it is a function of when incumbents are found and which nodes are pruned. Parallelism changes both. The result is that speedup can exceed p, can be less than one, and can be non-monotone in p. These are not measurement errors or rare corner cases. They are the normal behavior of a search whose pruning decisions are coupled to a shared, asynchronously updated incumbent.

The clean way to see the anomaly is to separate the search tree from the pruning events. A sequential run produces a sequence of incumbent discoveries and a sequence of node expansions. A parallel run produces a different sequence because workers process nodes in a different order and because incumbents propagate with delay. The final optimal value is the same, assuming the search is complete and the bounds are valid, but the set of expanded nodes can be larger or smaller. Let W(S) be the work of the sequential run and W(P) the work of the parallel run. Wall-clock time is roughly W(S) for the sequential run and W(P)/p plus communication and synchronization overhead for the parallel run. If W(P) is smaller than W(S), speedup can exceed p. If W(P) is larger, the parallel run can be slower than the sequential one even with perfect load balance. The anomaly is entirely in the ratio W(P)/W(S), and that ratio is controlled by incumbent timing.

The first anomaly is incumbent-timing. A good incumbent found early prunes an exponential number of subtrees; the same incumbent found late is nearly worthless. Sequential depth-first search with a good branching heuristic often dives to a good leaf quickly. That dive is a fragile sequence of choices: at each level the heuristic picks a child, and the path ends at a feasible solution. Parallel work stealing can break the dive. If the root's children are distributed to different workers, no single worker follows the full path, and the good incumbent may be found later than in the sequential run. The parallel run then explores more nodes before pruning begins. The opposite can also happen. Sequential best-first search may spend a long time expanding promising nodes near the root before it reaches any leaf. Parallel workers can dive in different directions simultaneously, so at least one worker may reach a good leaf early. In that case the parallel run finds the incumbent sooner and prunes more. Which effect dominates depends on the branching heuristic, the node-selection strategy, and the work-distribution policy. There is no general answer, which is why parallel branch-and-bound benchmarks are so noisy.

The second anomaly is work destruction. A worker can invest heavily in a subtree, only to learn that another worker has found an incumbent that prunes the entire subtree. The invested work is wasted. In a sequential run the same incumbent might have been found before the investment began, or after it finished, but the order is fixed and the waste is part of the sequential cost. In a parallel run the waste is amplified because workers cannot retract work already done. They can stop, but they cannot un-expand the nodes they have already processed. Total CPU time includes this wasted work, and it can dominate useful work when incumbent improvements are frequent. The mitigation is not to stop sharing incumbents; that would make pruning stale and waste even more work. The mitigation is to tune the sharing rate and the granularity of work. If improvements are frequent, workers should process smaller chunks so they can react quickly. If improvements are rare, larger chunks reduce communication overhead. An adaptive policy can estimate the recent improvement rate and adjust donation size. The danger is thrashing: improvements arrive so often that workers repeatedly discard work and steal new work, and the overhead of reacting exceeds the work saved. A simple hysteresis rule — only discard local work when the incumbent improvement exceeds a threshold, or only rebalance after a fixed number of improvements — often helps.

The third anomaly is frontier thrashing. Work stealing moves subtrees between workers. An incumbent update can make a stolen subtree worthless. The receiver prunes it on arrival, and the donor may then donate another subtree that is also worthless. The system spends its time moving and discarding work instead of processing it. This is especially common when the incumbent channel is fast and the search channel is slow: workers learn immediately that their work is obsolete, but the work has already been serialized, transferred, and queued. The fix is to make the search channel aware of the incumbent epoch. A donated subtree can carry the incumbent version at donation time; the receiver can compare that version with the current version and discard the subtree without reconstruction if the version is too old and the root bound is prunable. This is a cheap check that avoids the expensive part of the transfer. It does not eliminate the transfer cost, but it reduces the cost of stale donations.

The fourth anomaly is bound staleness. A worker that polls the incumbent infrequently will process nodes that are already prunable. The lag is bounded by the polling interval, but the wasted work is proportional to the node-processing rate times the lag. In a distributed system the lag can be milliseconds or seconds, which is enormous compared with the cost of a small node. The usual remedy is to make the incumbent channel push-based for local workers and pull-based for remote workers, and to make the polling interval adaptive to the observed improvement rate. When improvements are frequent, poll more often; when the incumbent is stable, poll less. The monotone-register design makes this safe: a stale read never causes incorrect pruning, only missed pruning. The performance question is how much missed pruning the system can afford. That depends on bound quality. If bounds are weak, pruning is rare and stale incumbents cost little. If bounds are strong, pruning is the dominant mechanism and stale incumbents can cost a great deal.

The fifth anomaly is search-order inversion. Best-first search depends on a global priority order. Parallel workers with local queues approximate that order, but they do not reproduce it. A worker may process a locally best node that is globally mediocre while the global best node sits in another worker's queue. Work stealing typically steals from the tail of a deque, which tends to take large subtrees rather than high-priority nodes. That is good for load balance and bad for best-first order. The result is that the parallel search can expand many more nodes than the sequential best-first search for the same incumbent sequence. The anomaly is not caused by pruning at all; it is caused by the loss of global priority. It interacts with pruning because a worse order delays incumbent discovery, which in turn weakens pruning. The mitigation is to maintain some global priority information, for example by periodically sharing the best open node from each worker, or by using a two-tier queue with a small global priority queue and larger local queues. The global queue preserves the most important ordering decisions; the local queues provide throughput.

These anomalies explain why speedup curves for parallel branch-and-bound are often non-monotone. Adding workers can help by finding incumbents earlier and by increasing throughput. It can hurt by fragmenting the search, destroying work, and losing global priority. The net effect can be positive at p=2, negative at p=4, and positive again at p=8. A benchmark that reports a single speedup number at a single thread count is almost meaningless. The useful measurements are the distribution of time-to-first-incumbent, time-to-optimality, and total work across thread counts and random seeds. The parallel run is not a faster version of the sequential run; it is a different search that happens to solve the same problem.

## 8. Memory is the binding constraint

The open-node frontier is where parallel branch-and-bound runs out of resources. Sequential depth-first search has a small memory footprint: the stack grows with the depth of the tree, and the depth is usually modest. Parallel best-first search has a much larger footprint. Each worker may maintain a priority queue, and the aggregate queue can grow to the size of the explored tree. The memory cost is not just the node count; each node may carry an LP basis, a set of local cuts, a propagation trail, and a variable-fixing state. A node near the root can be megabytes; a node near a leaf can be bytes. The distribution of node sizes is heavy-tailed, and aggregate memory is dominated by the large nodes.

The first consequence is that the memory budget becomes a global constraint on the search. A sequential solver can choose a node-selection strategy that keeps memory within a limit. A parallel solver must enforce the limit across workers. If each worker independently enforces a local limit, the aggregate can exceed the global limit by a factor of p. If a central coordinator enforces the global limit, it becomes a bottleneck. The practical compromise is a shared memory accounting service with periodic updates: workers reserve memory in chunks, and the coordinator tracks the total. The reservation granularity trades accuracy for communication. A worker that reserves a large chunk can run without coordination but may hold memory it does not need. A worker that reserves a small chunk coordinates often but uses memory efficiently. The right choice depends on the ratio of node-processing time to coordination time.

The second consequence is that node transfer is expensive. A node is not a small message. It may include a warm-start basis for the LP relaxation, and transferring that basis can cost more than solving the LP from scratch at the destination. This changes the economics of work stealing. Stealing a large subtree with a rich node state may be a net loss if the receiver could have generated a similar subtree cheaply. The donor should estimate the transfer cost and prefer to donate subtrees whose roots have compact state. If the state is large, it may be better to donate a description of the subtree — the branching decisions that define it — and let the receiver reconstruct the state by re-solving. This is a form of lazy transfer: send the path, not the basis. The receiver pays the reconstruction cost, but the transfer cost is much lower. The choice between eager and lazy transfer depends on the relative cost of serialization and re-solving, which varies by problem class.

The third consequence is that pruning leaves dead nodes in the queues. A worker that learns of a better incumbent cannot afford to scan its entire queue and remove every prunable node. The standard technique is lazy deletion: leave the nodes in the queue, and check the bound when a node is popped. If the node is prunable, discard it and pop the next. This keeps pruning cost proportional to the number of nodes actually examined, not the number of nodes in the queue. The downside is that the queue can fill with dead nodes, increasing memory and slowing priority queue operations. Periodic compaction can remove dead nodes, but compaction itself costs time and memory. The balance is another tuning problem: compact too often and overhead dominates; compact too rarely and the queue becomes a memory leak.

The fourth consequence is the shared cut pool. In branch-and-cut, globally valid inequalities are generated at one node and can be used at another. Sharing cuts is valuable because it strengthens bounds everywhere, but the cut pool is large and its consistency is delicate. A cut is valid globally only if it is derived from a valid relaxation and a valid separation procedure. Once a cut is added to the pool, every node that uses it must have a relaxation that includes it. If nodes are transferred between workers, the cut pool must be transferred or replicated. Full replication is simple but memory-hungry; a shared pool is memory-efficient but requires synchronization. The common compromise is a shared pool with local caches: each worker keeps the cuts it has used and fetches new cuts on demand. The cache reduces synchronization but can become stale. Stale cuts are still valid, so they do not cause incorrect pruning; they only fail to strengthen the bound as much as the latest pool would. This is the same monotonicity argument as the incumbent channel, applied to cuts.

The memory constraint interacts with the anomalies. A parallel search that fragments the frontier and fills queues with dead nodes will hit the memory limit sooner, which forces more aggressive pruning and more work stealing, which in turn creates more dead nodes. The system can enter a state where most of its time is spent managing memory rather than solving nodes. This is the parallel analogue of a sequential solver that thrashes between best-first and depth-first because its queue exceeds the memory budget. The difference is that the parallel version has more queues and more opportunities for divergence. The design lesson is that memory management cannot be an afterthought in parallel branch-and-bound. It is a first-class part of the search policy, and it must be coordinated with work distribution and incumbent sharing.

## 9. When the tree leaves the machine: distributed branch-and-bound

Moving from cores to nodes changes the constants by orders of magnitude, and some of the design choices invert. On a shared-memory machine, the incumbent channel can be a pointer load and the search channel can be a lock-free deque. Across machines, every incumbent update is a network message and every stolen subtree is a serialization problem. The latency of a remote read is microseconds at best and milliseconds in a congested cluster; the bandwidth is shared with every other worker. The monotonicity argument still holds, but the cost model that made lock-free sharing attractive no longer applies. A worker that polls a remote incumbent on every node will spend most of its time waiting for the network. A worker that polls rarely will prune against stale information for a long time. The design must therefore make the incumbent channel hierarchical: a local shared register per node, updated by a background thread that receives broadcasts from other nodes. The local register is read with the same cheap load as in the shared-memory case; the background thread pays the network latency. The lag between a remote improvement and a local read is the broadcast period plus the network delay, and that lag is a tunable parameter. It should be set relative to the node-processing time, not to the network round-trip time, because the goal is to bound wasted work, not to minimize message latency.

Termination detection is another problem that does not exist in shared memory. In a shared-memory solver, the search is finished when all workers are idle and no worker holds an open node. In a distributed solver, a worker may be idle while a message containing work is in flight, and a worker may hold a node while another worker is about to send it more. The standard solution is a distributed termination detection algorithm, often a token ring or a credit scheme. The algorithm must account for messages in flight and for work that has been donated but not yet received. A common bug is to declare termination while a donation is in transit, which loses work and can produce a suboptimal answer. The fix is to make donations part of the termination protocol: a donor that has sent work is not idle until it receives an acknowledgment, and a receiver that has been promised work is not idle until the work arrives or the promise is withdrawn. This adds a round trip to every donation, which is expensive. A cheaper alternative is to use a global epoch and a quiescence detector that tolerates in-flight messages by counting outstanding sends and receives. The detector is correct as long as every send is matched by a receive and every worker eventually reports its state.

Load balancing across machines is harder because the cost of moving work is high and the cost of idling is also high. The usual approach is hierarchical: within a node, workers steal from each other with low latency; across nodes, a small number of donor threads exchange large subtrees. The subtree size should be chosen so that the transfer cost is a small fraction of the expected processing time. That means the donor must estimate the subtree's remaining work, which is exactly the estimate that is hard to make. A practical heuristic is to donate a subtree whose root is at a certain depth or whose bound is within a certain factor of the donor's best bound. The donor can also donate a fraction of its local queue, for example the worst half by bound, on the theory that the receiver can use the work even if it is not the best. This is a form of work donation that sacrifices global priority for load balance. It is often the right trade-off across machines, where the alternative is idle capacity.

Fault tolerance is rarely a first-class concern in parallel branch-and-bound research, but it becomes one at scale. A node failure can lose a subtree that no other worker has a copy of. Checkpointing the entire search state is expensive because the state includes the open-node queues, the incumbent, and the cut pool. A more practical approach is to replicate work at donation time: the donor keeps a copy of a donated subtree until the receiver acknowledges that it has been processed or re-donated. This is a form of lineage-based recovery. If a worker fails, its parent in the donation tree can re-donate the subtree. The cost is memory for the retained copies and bookkeeping for acknowledgments. The benefit is that the search can survive failures without global checkpointing. The design is analogous to fault-tolerant work stealing in other domains, and it shares the same tension: retaining work reduces the risk of loss but increases memory pressure, which is already the binding constraint.

## 10. Accelerator and heterogeneous variants

GPUs and other accelerators are attractive for branch-and-bound because bounding is often the dominant cost and bounding is frequently a dense numerical kernel. The LP relaxation at a node is a linear program, and a batch of LP relaxations from many nodes can be solved concurrently. That batch is a natural fit for a GPU: the linear algebra is regular, the data is contiguous, and the parallelism is wide. The catch is that the tree search itself is irregular. Branching is data-dependent, node selection is a priority queue operation, and the set of active nodes changes unpredictably. A GPU kernel that tries to follow the tree will suffer from divergence, load imbalance, and frequent host-device synchronization. The practical pattern is therefore a split: the CPU runs the search, maintains the frontier, and decides which nodes to expand; the GPU solves batches of relaxations or evaluates batches of bounds. The CPU sends a batch of node descriptions to the GPU, the GPU returns bounds and maybe reduced costs, and the CPU uses those results to prune and branch. The batch size must be large enough to amortize the transfer and small enough to keep the search responsive to incumbent updates. This is the same granularity trade-off as work stealing, but with a much higher fixed cost per batch.

The bounding kernel itself must be designed for the accelerator. A simplex method is inherently sequential in its pivoting, so GPU implementations often use interior-point methods or first-order methods for the relaxation, or they use a parallel simplex with a different pivot rule. The choice changes the quality of the bound and the cost of the bound. A weaker bound computed quickly may be better than a stronger bound computed slowly if the search is bound-limited rather than node-limited. This is a recurring theme: in parallel branch-and-bound, the best sequential component is not always the best parallel component. A bounding routine that is optimal for a single node may be a poor fit for a batch. The designer must evaluate the entire search, not the component in isolation.

Memory is the other constraint on accelerators. GPU memory is fast but small, and the open-node frontier can exceed it. The CPU must therefore manage the frontier and stream node data to the GPU. Unified memory can simplify the programming model, but it does not eliminate the transfer; it only hides it behind page faults, which can be slower and less predictable than explicit transfers. For branch-and-bound, predictable transfer is usually preferable because the search needs to react to incumbent updates within a bounded time. A page fault that stalls the GPU for milliseconds is a latency spike that can waste a large amount of work. Explicit batching gives the scheduler control over when transfers happen, at the cost of more complex code.

Heterogeneous clusters add another layer. A node may have multiple CPUs, a GPU, and a network interface. The search must decide which work goes to which device. The decision depends on the node's size, the availability of a warm-start basis, and the cost of moving data. Small nodes are best kept on the CPU; large nodes with dense relaxations are candidates for the GPU. This is a scheduling problem that is not well solved by static rules. A work-stealing runtime can treat the GPU as a special worker with a different cost model, but the stealing policy must account for the fact that a stolen node may need to be serialized to the GPU and that the GPU may be busy for a long time. The simplest correct approach is to give the GPU a dedicated queue of large nodes and let the CPU workers handle the rest. The queue must be bounded, and the CPU must be able to reclaim work from the GPU if the GPU is saturated or if the incumbent improves. Reclaiming work from a GPU is harder than reclaiming from a CPU because the GPU may be in the middle of a kernel. The usual solution is to let the kernel finish and then discard the result if it is no longer needed. This is another form of wasted work, and it must be included in the cost model.

## 11. Determinism, reproducibility, and certification

Parallel branch-and-bound is nondeterministic in several independent ways. The order in which workers acquire nodes depends on thread scheduling. The time at which an incumbent becomes visible depends on memory ordering and network delays. The numerical results of a bounding routine can depend on the order of floating-point operations, which can vary with vectorization, thread count, and library version. Even the set of cuts generated can vary if separation is parallelized and cuts are added in a different order. The final optimal value is usually stable, but the path to it is not. This is acceptable for many applications, but it is a serious problem for debugging, for certification, and for any workflow that needs to reproduce a result exactly.

There are several levels of reproducibility, and it is useful to name them. At the weakest level, the solver returns the same optimal value on every run. This is the level most users care about, and it is usually achievable because the bounds are valid and the search is complete. At the next level, the solver returns the same incumbent solution. This is harder because a different search path can find a different optimal solution. At the next level, the solver expands the same set of nodes in the same order. This is the level that deterministic parallel search aims for, and it requires a global order on nodes and a synchronization mechanism that ensures workers process nodes in that order. The strongest level is bitwise reproducibility of all intermediate values, including floating-point bounds and LP bases. This is rarely achievable in parallel because floating-point summation and linear algebra are order-dependent. The practical target is usually the second or third level, with a documented tolerance for numerical differences.

Deterministic parallel branch-and-bound is possible if the node-selection order is made independent of timing. One way is to assign each node a unique priority based on its bound and a tie-breaking key, and to require that workers process nodes in globally increasing priority. This is essentially a parallel priority queue with a fixed order. The cost is that workers must synchronize on the frontier, which reintroduces a central bottleneck. A more scalable approach is to partition the priority space: each worker owns a range of priorities, and nodes are routed to the owner of their priority. Workers can process their ranges independently, and the global order is preserved because the ranges are disjoint and ordered. The catch is that the priority of a node is not known until its bound is computed, and the bound depends on the incumbent, which changes. If the priority is recomputed when the incumbent improves, nodes can move between ranges, which breaks the ownership invariant. To avoid this, the priority can be based on a static key such as the branching path, with the bound used only within a range. This gives a deterministic order that is independent of the incumbent, at the cost of a search order that may be worse than best-first. The trade-off between determinism and performance is fundamental; there is no free lunch.

Certification is a different concern from reproducibility. A certificate is a proof that the returned solution is optimal, or that the returned bound is valid. In mixed-integer programming, certificates can take the form of a dual bound from the LP relaxation plus a proof that the branching tree is exhausted, or a proof of infeasibility for the gap. In constraint programming, a certificate may be a set of nogoods or a resolution proof. Parallel search complicates certification because the proof is distributed across workers. Each worker produces a fragment of the proof, and the fragments must be combined into a single valid proof. If the proof format is designed for sequential search, the parallel fragments may not compose. This is an active area of research, and it is one of the reasons why some solvers disable parallelism when certification is required. The alternative is to design the proof format for parallel composition from the start, with explicit dependencies between fragments and a checker that can verify the composition. The checker itself can be parallelized, but it must be deterministic and independent of the search order. A certificate that depends on the order in which workers happened to run is not a certificate; it is a log.

## 12. Measuring parallel branch-and-bound without lying to yourself

The final design axis is measurement. Parallel branch-and-bound is easy to benchmark badly, and most published speedup numbers are not comparable across implementations. The first problem is the baseline. A speedup of 8 on 8 cores relative to a single-threaded run of the same parallel solver is not the same as a speedup of 8 relative to a well-tuned sequential solver. The parallel solver may have a different node-selection policy, a different memory limit, and a different cut pool. The only meaningful baseline is the best sequential configuration on the same instance, and even that is ambiguous because the best sequential configuration may depend on the time limit. A solver that uses best-first search may be optimal for proving optimality but terrible for finding a first incumbent. A solver that uses depth-first search may find incumbents quickly but take longer to prove optimality. The parallel solver may combine both, so the comparison is not apples to apples.

The second problem is the instance set. Branch-and-bound performance is heavy-tailed. A few instances dominate the total time, and the speedup on those instances may be very different from the speedup on the rest. Reporting a geometric mean of speedups across instances hides the tail. Reporting a total time over a set with a time limit hides the instances that were not solved. The useful presentation is a performance profile or a cactus plot that shows the distribution of solve times, plus a separate analysis of the hard instances. The hard instances are where parallelism matters, and they are also where the anomalies are most visible.

The third problem is the measurement itself. Wall-clock time includes communication, synchronization, and idle time. CPU time includes wasted work from stale incumbents and pruned subtrees. Node count includes nodes that were expanded and then discarded. A single number cannot capture all of these. A useful benchmark reports at least four quantities: time to first incumbent, time to optimality, total CPU time, and peak memory. It should also report the number of nodes expanded, the number of nodes pruned, the number of work steals, and the number of incumbent updates. These counters explain why a speedup is what it is. Without them, a speedup number is a rumor.

The fourth problem is variance. Because the search is nondeterministic, a single run is not a measurement. The distribution of runtimes across seeds can be wide, especially near the point where the incumbent timing changes the search path. A benchmark should run multiple seeds and report the median and the spread. If the spread is large, the mean is misleading. If the spread is small, the instance is probably not sensitive to incumbent timing, which means it is not a good test of the parallel design. The most informative instances are those where the parallel run sometimes wins big and sometimes loses, because they expose the coupling between work distribution and pruning.

The fifth problem is scaling mode. Strong scaling fixes the problem and increases the thread count. Weak scaling increases the problem size with the thread count. Branch-and-bound does not have a natural notion of problem size that scales smoothly, because a slightly larger problem can be exponentially harder. Weak scaling is therefore almost meaningless unless the problem family has a controlled parameter that changes the tree size predictably. Strong scaling is the usual choice, but it is limited by the fact that the sequential baseline may be memory-bound or bound-limited rather than compute-bound. If the sequential solver is already using all available memory bandwidth, adding cores will not help. The parallel design must address the actual bottleneck, which may be memory, not computation.

These measurement issues are not separate from the design. They are the feedback loop that tells you whether the design is working. A parallel branch-and-bound implementation that cannot explain its speedup in terms of incumbent timing, work distribution, and memory pressure is not ready to be trusted.

## 13. Presolve, restarts, and the parallel boundary

Almost every production solver runs a sequential presolve before the parallel search begins. Presolve tightens variable bounds, fixes variables, removes redundant constraints, and detects infeasibility. It is sequential because its deductions are global: a bound change on one variable can trigger a cascade elsewhere, and parallelizing the cascade requires synchronization that often costs more than the work it saves. The parallel boundary is therefore a deliberate serialization point. The search starts only after presolve has reached a fixed point or a time limit.

Restarts complicate that boundary. A sequential solver can restart from the root with a new incumbent, a new set of cuts, or a learned clause database, discarding the current tree but keeping the knowledge. A parallel solver cannot discard the tree cheaply because workers hold disjoint subtrees and local state. If it restarts, it must either collect and redistribute the useful knowledge or accept that each worker restarts from its own local state. The first option requires a global barrier and a merge of incumbents, cuts, and nogoods. The second option preserves parallelism but loses the global learning that makes restarts effective. The practical compromise is to make restarts rare and to make them incremental: keep the tree, but update the incumbent and the cut pool, and let workers prune locally. This preserves the parallel boundary while still capturing most of the benefit of a restart.
