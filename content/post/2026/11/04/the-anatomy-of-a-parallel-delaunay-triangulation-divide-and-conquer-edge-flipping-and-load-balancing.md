# The Anatomy of a Parallel Delaunay Triangulation: Divide-and-Conquer, Edge Flipping, and Load Balancing

Delaunay triangulation is one of those algorithms that looks embarrassingly parallel until you try to write one. The input is just a set of points. The output is a planar graph with a simple structural guarantee. There is no obvious sequential dependency between distant parts of the plane. Yet production-quality parallel Delaunay implementations are rare, and the ones that exist tend to be highly specialized. The reason is not that the problem is theoretically hostile to parallelism. It is that the work is irregular, the data structures are pointer-heavy, the predicates are delicate, and the critical path runs through a small number of topological merges or cavity updates that do not decompose cleanly.

This article examines parallel Delaunay triangulation as a systems problem. We will look at the sequential algorithms that define the baseline, the specific places where parallelism breaks down, and the main strategies used to recover it: parallel divide-and-conquer, speculative incremental insertion, conflict-graph scheduling, and edge flipping. The goal is not to present a single winning implementation. It is to map the design space and to make the trade-offs explicit, because the right choice depends heavily on point distribution, required robustness, memory budget, and whether the triangulation is built once or maintained dynamically.

## Why Delaunay triangulation is a parallel systems problem

A Delaunay triangulation of a point set is a triangulation in which no point lies strictly inside the circumcircle of any triangle. Equivalently, it is the straight-line dual of the Voronoi diagram. The empty-circumcircle condition gives the triangulation several useful properties: it maximizes the minimum angle among all triangulations of the same point set, it is unique for points in general position, and it supports efficient nearest-neighbor, interpolation, mesh generation, and surface reconstruction workflows.

The computational geometry literature treats Delaunay triangulation as a solved problem in the sequential setting. Divide-and-conquer, sweep-line, and incremental insertion algorithms all achieve O(n log n) expected or worst-case time under standard assumptions. The engineering literature treats it as a solved problem in the single-threaded setting as well: robust libraries such as CGAL and Triangle provide production implementations that handle degeneracies, exact predicates, and constrained edges.

The parallel setting is different. The input size may be large enough that a single thread is too slow, but the triangulation is not a dense linear algebra kernel. It does not map to matrix multiplication, stencil computations, or reductions. It is a dynamic graph algorithm with irregular memory access, unpredictable branch behavior, and a topology that changes as the algorithm runs. The output size is linear in the number of points, but the intermediate state can be much larger, and the order in which triangles are created and destroyed matters for correctness.

This makes Delaunay triangulation a useful case study for parallel systems design. It forces us to confront questions that also appear in parallel graph processing, parallel mesh refinement, and parallel computational geometry: How do we partition irregular work? How do we handle speculative updates to a shared topology? How do we keep predicates deterministic across threads? How do we avoid memory allocation becoming the bottleneck? These questions are more interesting than the triangulation itself.

## The sequential baseline

Before parallelizing anything, we need a precise model of the sequential algorithm. There are three main families, and each parallelizes differently.

### Empty circumcircle and the legal edge predicate

The fundamental predicate is `incircle(a, b, c, d)`: given three points that form a counterclockwise triangle `abc`, is point `d` inside the circumcircle of `abc`? If yes, the edge opposite `d` is illegal and must be flipped. The `orient2d` predicate determines whether three points are counterclockwise, collinear, or clockwise. These two predicates are the core of most Delaunay algorithms.

Floating-point evaluation of `orient2d` and `incircle` is fast but not robust. Near-degenerate inputs can produce inconsistent answers, which in turn produce invalid triangulations, infinite loops, or crashes. Robust implementations use adaptive-precision arithmetic: compute with floating point, estimate the error bound, and fall back to exact arithmetic only when the sign is uncertain. This fallback is rare in typical inputs but common in adversarial or structured inputs, such as points on a grid or on a circle.

For parallel implementations, robustness has a second consequence: determinism. If two threads evaluate the same predicate with different rounding modes, or if they resolve a tie in different orders, they can produce different triangulations. A parallel algorithm that is correct but nondeterministic is often unacceptable in mesh generation and geometry processing pipelines, because downstream stages may depend on the exact topology.

### Three algorithmic families

Incremental insertion builds the triangulation one point at a time. For each new point, it locates the containing triangle, identifies the cavity of triangles whose circumcircles contain the point, removes them, and retriangulates the cavity. The Bowyer–Watson algorithm is the canonical form. With a good point-location structure and randomized insertion order, expected time is O(n log n). The algorithm is simple and dynamic, but it mutates the triangulation globally: a single insertion can affect a cavity that spans many triangles.

Divide-and-conquer splits the point set by a vertical or horizontal line, recursively triangulates each half, and merges the two triangulations along their common boundary. The merge computes the lower and upper common tangents and then walks the boundary, flipping edges as needed. The classic Guibas–Stolfi algorithm is the standard reference. The recursion is naturally parallel, but the merge is a sequential walk that can touch a large fraction of the boundary.

Sweep-line algorithms sort points by x-coordinate and maintain a frontier of edges. They are efficient and can be made robust, but the frontier is a dynamic structure with complex update rules. Parallelizing a sweep-line algorithm requires either a parallel sort followed by a pipelined sweep or a spatial decomposition that breaks the sweep into independent strips. Both approaches introduce boundary reconciliation work.

Each family has a different parallelization profile. Divide-and-conquer has coarse-grained independent subproblems and a concentrated merge bottleneck. Incremental insertion has fine-grained dynamic work and a shared topology that resists partitioning. Sweep-line has a global order and a moving frontier that is difficult to split without duplicating work.

## Where parallelism breaks down

The first step in designing a parallel Delaunay algorithm is to identify the actual bottlenecks. They are not always where the sequential profiles suggest.

### Irregular topology and pointer chasing

A triangulation is a planar graph. In a half-edge data structure, each edge has a twin, a next pointer, and a vertex pointer. Traversing the triangulation means following pointers, which means cache misses. In a parallel setting, multiple threads traversing the same triangulation can thrash the cache and contend on the same cache lines. Even read-only traversal can suffer from false sharing if the data structure stores frequently read fields next to frequently written fields.

Array-based representations improve locality. Instead of pointers, store vertex indices and triangle indices in flat arrays. This makes traversal more predictable and allows prefetching. It also makes parallel updates harder, because resizing an array while other threads read it requires synchronization or a two-phase commit. A common compromise is a chunked array: fixed-size blocks of triangles, with a global directory that maps block IDs to block pointers. Blocks can be allocated and freed independently, and traversal can prefetch the next block.

### Dynamic work and load imbalance

The amount of work per point or per triangle is highly variable. A point inserted into a sparse region touches a small cavity. A point inserted into a dense cluster touches a large cavity. A merge step between two triangulations can be short or long depending on the shape of the boundary. Static partitioning by point count or spatial region produces severe imbalance on clustered inputs.

Work stealing helps, but only if the work is decomposed into tasks that are small enough to balance and large enough to amortize scheduling overhead. The granularity problem is acute in computational geometry because a task may allocate memory, traverse a cavity, and update a half-edge structure. If tasks are too small, the scheduler dominates. If tasks are too large, the tail of the computation is serialized.

### Memory allocation and reclamation

Delaunay triangulation is allocation-heavy. Incremental insertion creates and destroys triangles. Divide-and-conquer creates sub-triangulations that are merged and partially discarded. A naive implementation calls `malloc` and `free` for every triangle, which serializes on the allocator's internal locks and fragments memory. Parallel allocators with thread-local arenas help, but they introduce cross-thread frees: a triangle allocated by one thread may be freed by another during a merge or cavity update.

Region-based allocation is a common answer. Each task or thread owns a region. Triangles allocated in that region are freed together when the region is no longer needed. This avoids per-object free and reduces contention, but it requires careful lifetime analysis. In a divide-and-conquer merge, the two input triangulations may be partially consumed; the surviving triangles need to be copied or promoted into a new region. The copy cost can be significant, and it competes with the actual geometric work.

### Robust predicates and determinism

Robust predicates are not just a correctness concern; they are a parallel performance concern. Exact arithmetic fallback is slow, and if many threads hit the fallback simultaneously, the parallel speedup can collapse. Adaptive predicates usually cache the error bound and the exact result, but the cache is per-call or per-thread. Sharing a cache across threads requires synchronization, which can be worse than recomputing.

The deeper issue is determinism. Suppose two threads insert points that affect the same edge. The final triangulation may depend on which insertion is applied first. In a sequential algorithm, the order is fixed. In a parallel algorithm, the order is determined by the scheduler. To preserve determinism, the algorithm must either impose a total order on conflicting updates or make the updates commutative. Edge flipping is commutative in some cases, but cavity retriangulation is not. A common solution is to assign each point a unique priority and to resolve conflicts by priority. This makes the result deterministic but can introduce priority inversion and starvation if low-priority points are repeatedly preempted.

## Parallel divide-and-conquer

Divide-and-conquer is the most natural starting point for parallelization because the recursion exposes independent subproblems. The challenge is the merge.

### Splitting and recursive tasks

The point set is split by a line, typically a vertical line through the median x-coordinate. Each half is triangulated recursively. In a parallel implementation, the two recursive calls become tasks that can run on different threads. The recursion continues until the subproblem size falls below a threshold, at which point a sequential base case is used. The threshold controls the trade-off between parallelism and overhead. Too small a threshold creates many tiny tasks; too large a threshold leaves cores idle.

The split itself must be balanced. A median split by x-coordinate is not necessarily balanced in terms of geometric complexity. If the points are clustered, one half may contain most of the difficult structure. More sophisticated splits use spatial medians, k-d tree partitions, or sampling to estimate the work. The split can also be adaptive: if the recursion detects imbalance, it can re-split a subproblem into more than two parts.

### Merging two triangulations

The merge is the sequential core. Given two triangulations separated by a vertical line, the algorithm finds the lower common tangent and the upper common tangent. It then walks from the lower tangent to the upper tangent, comparing the circumcircles of the candidate triangles on each side. If an edge is illegal, it is flipped. The walk continues until the upper tangent is reached.

The merge is inherently sequential because each flip changes the boundary and affects the next comparison. Parallelizing the merge requires either speculative execution or a different decomposition. One approach is to split the merge into independent segments: if the boundary is long, multiple threads can process disjoint segments and then reconcile the flips at the segment boundaries. This is analogous to parallel merge in merge sort, but the reconciliation is more complex because a flip can propagate across segment boundaries. Another approach is to use a parallel priority queue of candidate edges, but the dependency structure is not a simple DAG.

In practice, many parallel implementations accept a sequential merge and parallelize only the recursion. This yields good speedups when the merge is a small fraction of total work, which is often true for uniformly distributed points. For clustered or adversarial inputs, the merge can dominate, and the speedup saturates. Amdahl's law is not just a theoretical concern here; it is a practical limit that depends on point distribution.

### Task granularity and work stealing

A work-stealing scheduler is a good fit for divide-and-conquer because the recursion creates a tree of tasks. Each thread maintains a deque of tasks. When it runs out of work, it steals from another thread's deque. The granularity threshold determines the number of tasks and the steal rate. If the threshold is too low, the scheduler overhead and cache misses from stealing dominate. If it is too high, the last tasks become a serial tail.

The merge step complicates work stealing because it is not a leaf task that can be stolen. It is a join point that requires both child triangulations to be complete. A thread that finishes its half must wait for its sibling before merging. If the sibling is stolen and runs slowly, the waiting thread is idle. One mitigation is to let the waiting thread help with other tasks, but the merge itself cannot start until both halves are ready. This is a classic fork-join bottleneck.

### The merge bottleneck

The merge bottleneck is the central obstacle in parallel divide-and-conquer. It can be reduced by choosing a split that minimizes the boundary length, by merging in a hierarchical fashion, or by using a different algorithm for the top levels of the recursion. For example, a parallel implementation might use divide-and-conquer for the lower levels and a parallel incremental algorithm for the upper levels, where the point set is small enough that cavity conflicts are manageable. Hybrid algorithms are common in practice because no single strategy dominates across all input distributions.

## Parallel incremental insertion and flipping

Incremental insertion is attractive because it is dynamic and can be parallelized speculatively. The idea is to insert multiple points concurrently, detect conflicts, and resolve them by rolling back or serializing the conflicting updates.

### Conflict graphs and spatial hashing

A conflict graph records which insertions affect overlapping regions of the triangulation. If two points are far apart, their cavities are disjoint, and they can be inserted in parallel. If their cavities overlap, they conflict. Spatial hashing is a common way to detect conflicts: hash the triangles or the bounding boxes of cavities into buckets, and check for collisions before committing an insertion.

The conflict graph can be built incrementally. Each thread claims a set of triangles, inserts its point, and records the triangles it touched. Before committing, it checks whether any of those triangles were claimed by another thread. If so, it aborts and retries. This is essentially optimistic concurrency control for a geometric data structure. The abort rate depends on the density of points and the size of cavities. In dense regions, aborts can be frequent, and the algorithm can livelock if retries are not prioritized.

### Speculative cavity retriangulation

A cavity is the set of triangles whose circumcircles contain the new point. The cavity is star-shaped with respect to the new point, so it can be retriangulated by connecting the new point to the boundary vertices. This retriangulation is local, which makes it a good candidate for speculative execution. A thread can compute the cavity and the new triangles without modifying the shared triangulation. It then attempts to commit the change by replacing the cavity triangles with the new triangles. The commit requires a compare-and-swap or a lock on the affected triangles.

Speculative execution is efficient when cavities are small and conflicts are rare. It is inefficient when cavities are large, because the speculative work is wasted on abort. The size of a cavity is related to the local density of points. In a uniform distribution, cavities are small and bounded. In a clustered distribution, cavities can be large and overlapping, and the abort rate rises.

### Locking, transactions, and rollback

Locking is the conservative alternative. A thread locks the triangles it intends to modify, computes the cavity, and commits. Locking avoids wasted work but serializes conflicting insertions. Fine-grained locking on individual triangles can be expensive because each lock acquisition is a cache miss and a potential contention point. Lock striping or hierarchical locking can reduce overhead, but the lock granularity must match the cavity size.

Transactional memory is conceptually appealing: the cavity update is a transaction that either commits or aborts. Hardware transactional memory (HTM) can handle small transactions with low overhead, but cavity updates often exceed the hardware buffer size. Software transactional memory (STM) provides larger transactions but adds instrumentation overhead. In practice, STM for Delaunay triangulation is rarely faster than fine-grained locking, because the transaction footprint is large and the conflict rate is high.

Rollback is the hardest part. If a thread aborts after modifying some triangles, it must restore the previous state. This requires either undo logs or a copy-on-write representation. Undo logs add memory and complexity. Copy-on-write duplicates triangles, which increases allocation pressure. A common compromise is to make the commit phase atomic: compute everything speculatively, then perform the actual pointer updates under a short lock. The speculative phase does not modify shared state, so rollback is unnecessary.

### Deterministic conflict resolution

To keep the result deterministic, conflicting insertions must be ordered. A common technique is to assign each point a priority based on its index or a hash of its coordinates. When two insertions conflict, the one with the higher priority wins; the other is retried later. This is similar to priority-based scheduling in parallel graph algorithms. It guarantees a deterministic triangulation if the priority order is a total order and the retry logic preserves it. The cost is potential starvation: a low-priority point may be repeatedly preempted by higher-priority points. Priority aging or a bounded retry count can mitigate this, but both add complexity.

## Data structures and memory layout

The data structure choice is not independent of the parallelization strategy. It determines the granularity of locks, the cost of traversal, and the feasibility of speculative execution.

### Half-edge vs. array-based

A half-edge structure is expressive and supports constant-time adjacency queries. Each half-edge stores a twin, a next, a vertex, and possibly a face. The pointers make it easy to walk the triangulation, but they also make it hard to serialize, copy, and partition. Array-based structures store vertices and triangles in flat arrays. They are more compact and more cache-friendly, but adjacency queries require index arithmetic and may touch multiple arrays. For parallel algorithms, array-based structures are often preferred because they can be partitioned into chunks that are updated independently.

A hybrid approach is a block-based half-edge structure: triangles are grouped into fixed-size blocks, and each block stores local adjacency. Cross-block edges are represented by block IDs and local indices. This preserves locality within a block and allows blocks to be locked independently. The cost is extra indirection for cross-block traversal, which can hurt performance if the triangulation is sparse.

### NUMA and locality

On NUMA machines, memory access latency depends on which socket owns the memory. A parallel Delaunay algorithm that allocates triangles on the thread that created them will naturally distribute memory across sockets. However, the merge step and conflict resolution may require threads to access triangles allocated by other threads. This creates remote memory traffic. NUMA-aware allocation can mitigate this by allocating sub-triangulations on the socket that will process them, but the merge step still crosses socket boundaries.

Locality also matters within a socket. A thread that inserts a point into a dense region will touch many triangles in a small area. If those triangles are spread across cache lines and pages, the thread will suffer cache misses and TLB misses. A space-filling curve ordering of triangles can improve locality, but maintaining that ordering under dynamic updates is expensive. Some implementations use a static ordering for the initial build and accept degradation during updates.

### Allocation strategies

Allocation is a first-class concern. A parallel Delaunay implementation that uses a general-purpose allocator will spend a significant fraction of time in `malloc` and `free`. Thread-local arenas reduce contention but do not eliminate cross-thread frees. Region-based allocation with explicit ownership is more predictable: each task owns a region, and triangles are freed when the task completes. The downside is that long-lived triangles must be copied out of the region, which adds a copy cost. For divide-and-conquer, the merge step is the natural point to copy surviving triangles into a new region. For incremental insertion, the cavity triangles are freed immediately, so a small per-thread free list may be sufficient.

Memory reclamation also affects correctness. If a triangle is freed while another thread is reading it, the reader may see stale or corrupted data. Epoch-based reclamation or hazard pointers can protect readers, but they add overhead to every traversal. In practice, most parallel Delaunay implementations avoid lock-free reclamation by using a global phase barrier: all threads finish a phase, then a serial compaction or cleanup step runs. This is simpler and often faster, but it limits scalability.

## What comes next

The picture so far is that parallel Delaunay triangulation is not a single algorithm but a family of algorithms with different bottlenecks. Divide-and-conquer gives coarse-grained parallelism with a merge bottleneck. Incremental insertion gives fine-grained speculative parallelism with conflict and rollback costs. Both depend on robust predicates, deterministic conflict resolution, and memory allocation strategies that do not serialize. The next sections will examine how these pieces fit together in practice: how to choose a split for divide-and-conquer, how to schedule speculative insertions without livelock, how to evaluate the cost of robust predicates under parallelism, and how to reason about the end-to-end performance of a parallel triangulation on realistic point distributions.

## Choosing the split: geometry, work, and locality

A divide-and-conquer triangulation is only as balanced as its splits. The textbook choice is a vertical line through the median x-coordinate, which guarantees that the two point sets have equal cardinality. Cardinality balance is not work balance. A median x-split can put almost all of the geometric complexity on one side, especially when points form vertical bands, rings, or anisotropically clustered regions. The recursion then produces two tasks of equal size but wildly different cost, and the cost is dominated by cavity sizes, boundary lengths, and merge walks rather than by point count.

A better split estimator samples the input and predicts three quantities: the number of points on each side, the expected length of the separating boundary, and the local density near that boundary. The boundary length matters because the merge cost scales with the number of edges visited along the common boundary, not with the number of points. A split that cuts through a dense cluster creates a long, jagged boundary and a merge that touches many triangles. A split that follows a natural gap in the point set creates a short boundary and a cheap merge. For clustered inputs, a spatial median or a recursive bisection on a k-d tree is often more balanced in work than a strict x-median. The k-d tree partition also gives a cheap way to compute bounding boxes and density estimates for the two halves.

Locality complicates the choice. A split that is geometrically clean may still produce subproblems whose points are scattered in memory. If the input arrives in a random order, each recursive task will stream through the same array and pull in cache lines that belong to the other task. The result is false sharing at the cache-line level and poor prefetch behavior. A preprocessing sort by a space-filling curve, such as Morton order or Hilbert order, makes contiguous ranges correspond to spatial regions. The split then becomes a range split in the sorted array, and each task reads a compact slice. The recursive structure still needs care: a Hilbert range is not a perfect geometric half-plane, so the merge boundary may be more irregular than a median cut. In practice, the locality gain usually outweighs the extra boundary complexity, especially for large point sets that do not fit in cache.

Another option is to avoid a single split line and use strips. The plane is divided into vertical strips, each strip is triangulated independently, and adjacent strips are merged in a tree. This is appealing for parallel pipelines because the strip triangulations have no shared state. The difficulty is that strip boundaries cut through the Delaunay structure, and the merge between two strips can be as expensive as the merge in recursive divide-and-conquer. The advantage is scheduling: strips can be sized to the number of cores, and the merge tree can be arranged to keep many merges in flight. The disadvantage is that a strip with a dense cluster can dominate, and the fixed strip geometry makes it harder to adapt to the data. Adaptive strips, sized by estimated work rather than by coordinate range, recover some of the balance but require a preliminary density estimate.

A practical implementation often uses a hybrid split policy. The first few levels use a work estimate from sampling and choose among an x-median, a y-median, a spatial median, and a Morton range split. Lower levels use a simpler median split because the subproblems are small and the sampling overhead is no longer worth it. The policy is tuned by measuring the merge fraction and the tail latency on representative inputs. The important point is that the split is a scheduling decision as much as a geometric one. It determines task sizes, memory ownership, and the shape of the dependency graph.

## Scheduling speculative insertions without livelock

Incremental insertion has a different scheduling problem. The natural unit of work is a point, but a point cannot be inserted until its containing triangle is stable and its cavity can be computed against a consistent topology. If many threads insert points concurrently, they must detect conflicts and decide which insertion commits. The scheduling policy determines whether the system makes progress or spends its time aborting and retrying.

The first requirement is a total order on insertions. A unique priority per point, derived from the input index or a hash of the coordinates, gives a deterministic tie-breaker. When two insertions conflict, the higher-priority insertion wins and the lower-priority insertion is postponed. This is simple, but it can create a convoy effect: a high-priority point in a dense region repeatedly aborts nearby low-priority points, and the low-priority points never make progress. Priority aging, where a point's effective priority increases with each retry, prevents starvation, but it weakens the deterministic order. A common compromise is to use priority only within a conflict window. Points outside the window are ordered by the scheduler, and the final triangulation is deterministic because the window boundaries are deterministic.

The second requirement is a conflict detector that is cheaper than the insertion itself. Spatial hashing of cavity bounding boxes is a good first filter. Each thread computes the bounding box of the cavity it intends to modify and inserts the box into a concurrent hash table keyed by a coarse grid cell. If the cell already contains an overlapping box, the thread aborts before doing the expensive retriangulation. The hash table must support deletion, because a committed cavity no longer reserves its cells. Epoch-based reclamation or a per-epoch hash table avoids the cost of fine-grained deletion. The filter is conservative: boxes may overlap even when cavities do not. That is acceptable if the false-positive rate is low. In dense regions, the boxes are small but numerous, and the hash table becomes a contention point. Sharding the table by cell and using per-shard locks or lock-free buckets helps, but the table should not become the bottleneck.

The third requirement is bounded retry. A thread that aborts should not immediately retry the same point in the same region. A short backoff, or a move to a different work queue, reduces repeated collisions. More effective is to reorder the remaining points by locality. If a thread aborts on a point in a dense cluster, it can switch to a point in a sparse region and return later. This is a form of work stealing at the point level. The scheduler needs a queue that supports priority and locality, or a set of queues partitioned by spatial cell. The partitioned queue is simpler: each cell has a deque, threads steal from other cells, and a thread that aborts pushes the point back to its cell's deque with a retry counter. The retry counter can be used to promote the point to a separate queue that is processed in a later phase.

A phase-based schedule is often more robust than fully asynchronous insertion. In each phase, a batch of points is selected, a conflict graph is built from their predicted cavities, and maximal independent sets are inserted in parallel. The conflict graph can be built with a parallel sweep or a spatial hash. Maximal independent sets guarantee that no two insertions in the same set conflict, so the insertions can run without locks. The number of phases depends on the batch size and the density. Large batches expose more parallelism but take longer to build the conflict graph. Small batches reduce graph construction cost but increase synchronization. The batch size should be tuned to the cavity-size distribution: if most cavities are small, large batches are fine; if cavities are large and overlapping, smaller batches avoid wasted graph construction.

The phase-based approach also makes rollback easier. Within a phase, a point either commits or is deferred. There is no partial cavity update that must be undone. The cost is that the conflict graph is conservative and may serialize points that could have been inserted concurrently. The benefit is predictable progress and easier debugging. Many production systems prefer predictability over the last few percent of throughput.

## Robust predicates as a parallel performance surface

Robust geometric predicates are usually discussed as a correctness issue, but in parallel code they are also a performance surface. The fast path of an adaptive `orient2d` or `incircle` is a few floating-point operations plus an error bound. The slow path is exact arithmetic, which can be orders of magnitude slower. If the input contains many near-degenerate configurations, the slow path becomes common. Threads that hit the slow path simultaneously can serialize on shared exact-arithmetic state, or they can exhaust the instruction cache with large arbitrary-precision routines.

The first design decision is where to put the filter. A filter that is evaluated per predicate call adds branch overhead but keeps the fast path short. A filter that is evaluated per batch amortizes the branch and allows vectorization. Batch predicates are attractive for conflict detection and cavity construction, where many candidate triangles are tested against the same point. The batch can be sorted by a cheap orientation test, and only the uncertain cases go to the exact path. This reduces divergence and improves instruction-level parallelism. The batch size should be large enough to amortize setup but small enough to fit in cache.

The second decision is how to cache exact results. Near-degenerate points often produce repeated predicate calls with the same or nearly the same arguments. A thread-local cache can avoid recomputing exact signs, but it must be bounded and cleared between phases to avoid stale entries. A shared cache requires synchronization and can become a contention point. In most cases, a small thread-local direct-mapped cache is enough. The cache key should include the point coordinates or stable point IDs, not pointers, because pointers change when triangles are reallocated.

Determinism is inseparable from robustness. Symbolic perturbation, such as Simulation of Simplicity, gives a consistent answer for degenerate cases, but it changes the geometric meaning of the triangulation. If one thread applies perturbation and another does not, the result is inconsistent. The perturbation rule must be global and deterministic, and it must be applied identically in every predicate. A simpler alternative is to reject degenerate inputs or to preprocess them by adding a tiny deterministic jitter. Jitter changes the input and may be unacceptable for mesh generation, but it makes the parallel algorithm much easier to reason about. The choice depends on the contract with downstream consumers.

Robustness also affects load balance. A dense cluster of cocircular points can force many exact fallbacks in one region while other regions run on the fast path. The scheduler sees this as a long-running task, but the task is not doing more geometric work; it is doing more arithmetic. Work stealing can move other tasks to idle cores, but it cannot split the slow task if the slow task is a single cavity update. Finer task granularity, such as splitting a large cavity into independent fans, can help, but the cavity is a topological unit and cannot always be split without changing the commit protocol. The practical answer is to detect slow regions early, allocate more threads to them, and accept that exact arithmetic is a local bottleneck rather than a global one.

## Measuring the end-to-end system

A parallel triangulation should be evaluated with phase-level counters, not just total wall-clock time. The useful counters are: time in splitting and sorting, time in recursive triangulation, time in merge, time in cavity computation, time in predicate fallback, time in allocation, time in conflict detection, abort count, retry count, and peak memory. These counters explain why a run scales or fails to scale. A run with a high merge fraction needs a different split policy or a hybrid algorithm. A run with a high abort rate needs better conflict detection or a phase-based schedule. A run with a high allocation fraction needs region allocation or a different data structure.

Strong scaling and weak scaling answer different questions. Strong scaling fixes the input and increases the core count; it reveals the serial fraction and the merge bottleneck. Weak scaling increases the input proportionally with the core count; it reveals whether the algorithm can maintain constant work per core and whether memory bandwidth or allocation becomes the limit. A triangulation that weak-scales well but strong-scales poorly has a large serial component, often the top-level merge. A triangulation that strong-scales well but weak-scales poorly is probably hitting a memory or allocator limit.

Input distribution matters more than most benchmarks admit. Uniform random points are the easy case: cavities are small, the merge boundary is short, and load is naturally balanced. Grid points and points on a circle are the hard case: many cocircular quadruples, many exact fallbacks, and a triangulation with many valid alternatives. Clustered points are hard for a different reason: cavities are large and overlapping, and static splits are unbalanced. A credible performance evaluation includes at least these three families, plus a real-world mesh or terrain dataset. Reporting only uniform random points hides the failure modes that matter in production.

The final system-level lesson is that no single optimization dominates. Split selection, conflict scheduling, predicate filtering, and allocation strategy interact. A change that improves one phase can worsen another. The only reliable way to make progress is to instrument the phases, vary one design choice at a time, and measure on inputs that stress different parts of the algorithm. The triangulation itself is a simple geometric object; the difficulty is in the scheduling and memory behavior around it.

## Parallel edge flipping as a local repair mechanism

Edge flipping is often described as a sequential cleanup step, but it can also serve as the primary parallel repair mechanism for a triangulation that has been perturbed by batch insertion, point deletion, or constrained edge recovery. The operation is deceptively local: two adjacent triangles share an edge, and if the edge is illegal under the empty-circumcircle test, it is replaced by the opposite diagonal. In a half-edge structure this touches four triangles, five vertices, and a handful of adjacency pointers. In an array-based structure it touches two triangle records and the neighbor links of their neighbors. The locality is attractive because it suggests that many flips can run concurrently. The difficulty is that legality is a global property disguised as a local predicate. Flipping one edge changes the circumcircles of the two new triangles, which can make a previously legal neighboring edge illegal. Two flips that appear independent can therefore interfere through a shared triangle or through a chain of adjacency that is not obvious from the edge list alone.

A parallel flipping engine needs a conflict model. The simplest model treats two flips as conflicting if they share a triangle, share a vertex, or are adjacent across a triangle edge. This is conservative but easy to check with a spatial hash or a per-triangle lock word. A less conservative model checks whether the two flips affect overlapping circumcircles. The latter is more precise but requires geometric computation and can be as expensive as the flip itself. In practice, the shared-triangle model is usually sufficient because the number of flippable edges in a batch is small relative to the number of triangles, and the false-conflict rate is low. The engine builds a conflict graph, computes a maximal independent set, and flips that set in parallel. It then rebuilds the worklist of illegal edges and repeats. This is a bulk-synchronous form of Lawson flipping. The number of rounds depends on how far the illegality propagates. In a well-shaped triangulation, most rounds are short. In a triangulation with long thin triangles, a single insertion can create a cascade that touches a large region, and the parallel engine degenerates into a sequence of small independent sets.

Termination is the subtle part. Sequential Lawson flipping terminates because each flip increases a lexicographic measure of the triangulation, such as the sorted vector of angles or the minimum angle. A parallel independent set of legal flips also increases the same measure, because each individual flip is legal and the measure is monotone under legal flips. However, if the engine uses a priority order to choose among conflicting flips, it must ensure that the priority does not allow a flip that undoes an earlier flip. A simple way to guarantee progress is to assign each edge a stable priority and only flip an edge if it is illegal and its priority is higher than the priorities of all currently conflicting edges. This serializes conflicting flips without introducing a global lock. It also gives a deterministic result if the priority is derived from vertex IDs rather than from memory addresses. The cost is that low-priority illegal edges may wait for many rounds. A bounded number of rounds per phase, followed by a sequential fallback for the remaining illegal edges, keeps the algorithm predictable.

Parallel flipping is most useful when the triangulation is already close to Delaunay. Batch insertion can create a small number of illegal edges around each new point. If the points are inserted in a phase, the illegal edges from different points are often disjoint, and a few rounds of parallel flipping restore the Delaunay property. This is cheaper than recomputing cavities for every point and it avoids the rollback complexity of speculative insertion. The hybrid is natural: use speculative insertion for the initial placement, then use parallel flipping for legalization. The insertion phase can be optimistic because it only needs to produce a valid triangulation, not a Delaunay one. The flipping phase then enforces the empty-circumcircle condition. Separating the two concerns makes each phase easier to schedule and to debug.

## Load balancing as a runtime contract

Load balancing in parallel Delaunay triangulation is not a one-time partition of the input. It is a runtime contract between the scheduler, the geometry, and the memory system. The contract has three clauses: every thread should have useful work until the end of the computation, the cost of moving work should be small relative to the cost of doing it, and the movement should not destroy locality. Work stealing satisfies the first clause in a weak sense: if there is work somewhere, an idle thread can find it. It does not automatically satisfy the second or third. A stolen task may carry a large amount of state, such as a sub-triangulation with its own allocation region, and moving that state across sockets can cost more than the task itself. A stolen task may also be spatially far from the thief, so the thief touches memory that is cold in its cache and remote on a NUMA machine.

A better contract starts with a cost model. The cost of a triangulation task is not proportional to the number of points alone. It is roughly the sum of three terms: the cost of locating and retriangulating cavities, the cost of merging boundaries, and the cost of predicate fallbacks. Cavity cost scales with the number of triangles in the cavity, which depends on local density and on the insertion order. Merge cost scales with the length of the common boundary, which depends on the split geometry. Predicate cost scales with the number of near-degenerate configurations, which is high for grids, circles, and cocircular clusters. A scheduler that only counts points will systematically underestimate dense clusters and overestimate sparse regions. A practical cost model samples the input, estimates local density with a grid or k-d tree, and assigns each task a weight. The weights are updated as the computation runs, because cavities and merges reveal the true cost.

With a cost model, the scheduler can do more than steal. It can split large tasks before they become the tail. A recursive divide-and-conquer task that is predicted to be expensive can be split one level deeper, even if its point count is below the nominal threshold. The extra split increases the number of tasks and the merge overhead, but it reduces the maximum task duration. This is especially important for the top-level merge, which is the classic serial tail. If the top-level merge is predicted to be long, the algorithm can switch to a segmented merge: the boundary is divided into overlapping segments, each segment is processed by a thread, and the segment boundaries are reconciled by a short sequential pass. The overlap is necessary because a flip near a segment boundary can affect the next segment. The reconciliation pass rechecks the edges near the boundaries and flips any that became illegal. Segmented merge does not eliminate the serial component, but it can turn a single long walk into several shorter walks that run concurrently.

Spatial queues are a better fit for incremental and flipping workloads than a single global deque. The plane is divided into a grid of cells, and each cell has a deque of pending points or illegal edges. A thread processes work from its current cell, then steals from neighboring cells before stealing from distant ones. This preserves locality because a stolen task is likely to touch triangles near the thief's recent work. It also reduces contention because most steals are local. The grid should be sized to the number of threads and the density of points. Too coarse a grid creates large cells with many tasks and high contention. Too fine a grid creates many empty cells and high steal overhead. An adaptive grid that splits cells when their queues grow beyond a threshold and merges them when they shrink keeps the structure balanced without a global rebalancing pass.

Tail latency is the real enemy. Average utilization can look excellent while one thread runs a single expensive cavity for seconds. The scheduler should track the longest-running task and the number of idle threads. If the longest task exceeds a threshold, the scheduler can attempt to split it. Some tasks are splittable: a large cavity can be retriangulated as a fan from the new point, and the fan triangles can be created in parallel if the boundary vertices are partitioned. Other tasks are not: a merge walk has a strict dependency chain. For unsplittable tasks, the only remedy is to ensure they are rare. A hybrid algorithm that uses divide-and-conquer for the bulk and incremental insertion for the remainder can keep the maximum task size bounded. The scheduler should also avoid assigning a long task to a thread that is already behind; work stealing can move short tasks away from the critical path, but it cannot move the critical path itself.

## Hybrid pipelines: build, update, repair

No single parallel Delaunay algorithm is best for every phase of a real pipeline. A mesh generator may build an initial triangulation from a large static point set, then insert Steiner points in batches, then remove sliver triangles, then enforce constrained edges. Each phase has a different work profile. The build phase is dominated by recursive splitting and merging. The update phase is dominated by cavity computation and conflict detection. The repair phase is dominated by local flipping and predicate evaluation. Trying to force one algorithm to handle all three leads to compromises that hurt every phase.

A hybrid pipeline assigns the right algorithm to each phase. The initial build uses parallel divide-and-conquer because the input is static and the recursion exposes coarse-grained parallelism. The split policy is chosen from the cost model, and the merge is either sequential or segmented depending on the predicted boundary length. The update phase uses speculative incremental insertion with a phase-based conflict graph. Points are inserted in batches, and each batch is legalized by parallel flipping. The repair phase uses a worklist of illegal edges and a spatial queue. Constrained edges are marked and excluded from flipping. If a constrained edge is violated, the algorithm falls back to a cavity retriangulation that respects the constraint, which is a more expensive but local operation.

The transitions between phases are synchronization points. They are also opportunities for memory compaction and rebalancing. After the build phase, the triangulation may be fragmented across many allocation regions. A compaction pass can copy triangles into a single array or into a small number of blocks, improving locality for the update phase. The compaction is parallel if the triangle order is determined by a space-filling curve. Each thread scans a range of the curve, writes its triangles to a local buffer, and then the buffers are concatenated. The cost is a full copy of the triangulation, which is O(n) and memory-bandwidth bound. It is worth doing if the update phase is long and if the fragmentation is severe. If the update phase is short, the copy may dominate.

Hybrid pipelines also need a fallback path. When a subproblem is small, degenerate, or highly constrained, the parallel scheduler should hand it to a sequential routine. The sequential routine can use exact arithmetic without worrying about thread contention, and it can use a simpler data structure. The threshold for falling back should be based on measured overhead, not on a fixed point count. A subproblem with 100 points in a dense cluster may be more expensive than a subproblem with 1000 points in a uniform region. The cost model should drive the decision. The fallback path should also be deterministic, so that the parallel result matches the sequential result for the same input.

## Determinism, reproducibility, and debugging

Parallel geometry code is hard to debug because failures are nondeterministic. A race may occur only when two threads happen to touch the same triangle in a particular order. A predicate may return a different sign because a floating-point value was computed with a different instruction sequence. A triangulation may be valid on one run and invalid on the next. The first line of defense is a determinism contract. The contract states which parts of the output must be identical across runs and thread counts. For many applications, the vertex order and the triangle order must be identical. For others, only the geometric triangulation must be identical up to relabeling. The contract determines how much effort is required for deterministic scheduling.

If full determinism is required, conflicting updates must be ordered by a total order that does not depend on timing. Priority by vertex ID is the usual choice. The scheduler may still run tasks in any order, but the commit order is fixed. This can reduce parallelism if the priority order is correlated with the spatial order. A common compromise is to use priority only within a conflict window and to allow the scheduler to reorder non-conflicting work. The window boundaries are deterministic, so the final result is deterministic even though the execution order is not. The cost is a more complex scheduler and a need to prove that the window boundaries do not depend on thread timing.

Debugging tools are essential. A validation pass after each phase can check Euler's formula, triangle orientation, empty circumcircles, and constrained edge preservation. The validation can be parallel: each thread checks a range of triangles, and a reduction combines the results. The reduction must be deterministic if the validation result is used in production. Thread sanitizers and race detectors can find data races, but they are slow and may not understand the geometric invariants. A better approach is to add phase barriers and to run with a single thread per phase in debug builds. This serializes the execution and makes races disappear, but it also makes the debug build slow. A middle ground is to run with two threads and a deterministic scheduler that records the order of commits. The record can be replayed to reproduce a failure.

Reproducibility across machines is harder. Floating-point results can differ because of fused multiply-add, different math libraries, or different compiler optimizations. Robust predicates reduce the impact because they fall back to exact arithmetic when the sign is uncertain. The exact fallback must be portable and deterministic. Arbitrary-precision arithmetic is deterministic if it uses integer operations only. The fast path can differ across machines, but the final sign should not. If the fast path returns a sign that is later contradicted by the exact path, the exact path wins. This is the standard adaptive-precision design. The parallel implementation must ensure that the exact path is used consistently, even if one thread has a different fast-path result. A shared sign cache can help, but it must be keyed by the exact arguments, not by the fast-path result.

## Memory bandwidth, cache, and NUMA

Delaunay triangulation has low arithmetic intensity. For each triangle created or destroyed, the algorithm performs a handful of predicate evaluations and many pointer or index updates. The predicate evaluations are cheap compared to the memory traffic. This means that parallel speedup is often limited by memory bandwidth rather than by core count. Adding more threads can increase contention on the memory bus and reduce per-thread performance. The practical limit is reached when the working set no longer fits in the last-level cache and the algorithm becomes a streaming workload over the triangulation arrays.

Data layout is the primary lever. A structure-of-arrays layout stores vertex coordinates in one array, triangle vertices in another, and neighbor indices in a third. Traversal of a cavity reads triangle vertices and neighbor indices, then reads vertex coordinates for the predicate. If the arrays are separate, the prefetcher can handle multiple streams. If the layout is an array of structures, each triangle access pulls in unused fields and wastes bandwidth. The triangle record should be as small as possible. Use 32-bit indices when the number of vertices is below the 32-bit limit. Pack flags, such as constrained-edge markers, into unused bits. Store the neighbor indices in a fixed order that matches the triangle vertex order, so that the neighbor across a given edge is at a predictable offset. This reduces branch mispredictions and improves prefetching.

False sharing is a subtle bandwidth killer. Counters, allocator free lists, and lock words are frequently written by many threads. If two counters share a cache line, each write invalidates the line for the other thread. Pad the counters to a cache line and aggregate them at the end of the phase. For allocators, use per-thread arenas with cache-line-aligned headers. Avoid global atomic counters on the fast path. If a global counter is necessary, use a sharded counter with per-thread increments and a periodic reduction.

NUMA adds another dimension. On a multi-socket machine, memory allocated by one socket is slower to access from another. The first-touch policy means that the socket that first writes a page owns it. A parallel divide-and-conquer build naturally distributes pages across sockets because each thread allocates its own sub-triangulation. The merge step then reads pages from both sockets. If the merge is short, the remote traffic is negligible. If the merge is long, the remote traffic can dominate. A NUMA-aware implementation can migrate pages or copy the boundary region to the merging thread's socket. Page migration is expensive and may not be supported in all environments. Copying the boundary region is simpler: the merge thread copies the triangles near the boundary into a local buffer, performs the merge, and writes the result back. The copy cost is proportional to the boundary length, which is exactly the quantity that determines the merge cost. This is a reasonable trade-off.

## A practical checklist for implementers

Before writing a parallel Delaunay triangulation, answer these questions. What is the determinism contract? If the output must be byte-identical across runs, priority-based conflict resolution and deterministic reductions are mandatory. If only the geometric triangulation must match, the scheduler has more freedom. What is the input distribution? Uniform random points are the easy case. Grids, circles, and clusters expose predicate fallbacks and load imbalance. What is the update pattern? A static build can use divide-and-conquer. A streaming update needs incremental insertion and flipping. A mixed workload needs a hybrid pipeline. What is the memory budget? Region-based allocation and compaction are only worth it if the triangulation is large enough to overflow cache. What is the validation strategy? A parallel validator that checks empty circumcircles and Euler's formula after each phase catches most topology bugs. What is the fallback path? A sequential routine for small or degenerate subproblems keeps the parallel code simple and correct. What is instrumented? Phase timers, abort counts, retry counts, steal counts, and peak memory explain performance better than total wall-clock time. What is the target hardware? NUMA, cache size, and core count determine whether memory bandwidth or synchronization is the limiting factor. Answering these questions before coding does not guarantee a fast implementation, but it prevents the most common failure mode: optimizing a phase that is not the bottleneck while ignoring the phase that is.
