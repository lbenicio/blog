# The Parallel External Memory Model: I/O Complexity, Cache-Aware Scheduling, and Multi-Core Algorithms That Respect the Memory Hierarchy

## The memory hierarchy is the real parallel machine

Modern processors are fast. Memory is not. A single core can issue several instructions per cycle, but a DRAM access can cost hundreds of cycles. Caches hide some of that latency, but they are small. When data exceeds cache capacity, every algorithm becomes a memory algorithm. The CPU is no longer the scarce resource. Bandwidth is. This is the memory wall, and it has not gone away. It has become more complicated.

On a multi-core chip, the problem compounds. Many cores share the same memory controllers, the same last-level cache, the same DRAM bus. If each core streams data from DRAM, they contend. The aggregate bandwidth does not scale linearly with cores. Adding cores can even reduce performance if the working set no longer fits in cache and the memory system saturates. This is the multicore bandwidth wall.

Most algorithm analysis ignores this. The RAM model assumes uniform memory access. The PRAM model assumes processors can access shared memory in constant time. These models are useful for reasoning about computation, but they are misleading for data-intensive workloads. They do not capture the cost of moving data between memory levels. They do not explain why a blocked matrix multiply beats a naive triple loop by an order of magnitude. They do not explain why a hash join can be slower than a sort-merge join when the hash table spills.

The external memory model, introduced by Aggarwal and Vitter in 1988, was a response to this. It abstracts the memory hierarchy into two levels: a fast cache of size M and a slow external memory of unbounded size. Data moves between them in blocks of size B. The cost is the number of block transfers, or I/Os. This simple model captures the essential behavior of algorithms on large data. It predicts the I/O complexity of sorting, matrix multiplication, list ranking, and many other problems. It has been remarkably successful.

The parallel external memory model, or PEM, extends this to P processors. Each processor has its own private cache of size M. They share the external memory. Each processor can read or write one block at a time. The cost is the parallel I/O complexity: the maximum number of I/Os performed by any single processor. This model is the subject of this article. It is a bridge between parallel algorithms and the memory hierarchy. It tells us what is possible when data does not fit in cache and many cores must cooperate.

## Why a parallel external memory model?

The PRAM model has been the standard for parallel algorithms for decades. It assumes P processors, each with constant-time access to shared memory. It ignores caches, bandwidth, and locality. For small problems, this is fine. For large problems, it is not. A PRAM algorithm that performs O(N log N) work may have terrible cache behavior. It may thrash the cache and spend most of its time waiting on memory. The PRAM model cannot distinguish between an algorithm that reads data sequentially and one that reads it randomly. Both cost O(1) per access in the model. In reality, the difference can be two orders of magnitude.

The external memory model fixes this for sequential algorithms. It has a single processor and a two-level memory hierarchy. It has been used to design I/O-optimal algorithms for sorting, searching, matrix multiplication, computational geometry, graph algorithms, and string processing. It has also been used to prove lower bounds. For example, sorting N items requires Ω((N/B) log_{M/B}(N/B)) I/Os. This lower bound is tight: merge sort with a multi-way merge achieves it.

The PEM model extends the external memory model to multiple processors. It is not simply the external memory model with P times the bandwidth. The processors have private caches. They cannot share cached data. If two processors need the same block, they must each read it from external memory. This is a crucial difference from shared-memory multicore systems with cache coherence. In a coherent system, a block can be cached once and shared. In PEM, caches are private, so sharing costs extra I/Os. This makes data partitioning and replication important. It also makes load balancing harder. If one processor has more I/Os than the others, the whole computation waits.

The PEM model is useful for several reasons. First, it provides a formal framework for designing parallel algorithms that are aware of the memory hierarchy. Second, it gives lower bounds that tell us when an algorithm is optimal. Third, it helps explain why some parallel algorithms scale and others do not. Fourth, it is a stepping stone to more realistic models, such as multi-level memory hierarchies, NUMA systems, and distributed memory.

## The PEM model in detail

The PEM model has three parameters: P, M, and B. P is the number of processors. M is the size of each processor's private cache, measured in words. B is the block size, also measured in words. The external memory is shared and has unbounded capacity. Each processor can perform one I/O at a time: it can transfer one block of B contiguous words between its cache and external memory. The cost of an algorithm is the parallel I/O complexity, which is the maximum number of I/Os performed by any single processor. Computation is usually assumed to be free, or at least not the bottleneck. This is a simplification, but it is reasonable for memory-bound problems.

There are several assumptions that are commonly made. The tall cache assumption states that M ≥ B^2. This ensures that a block can be used effectively and that multi-way merging is efficient. The ideal cache assumption states that the cache replacement policy is optimal offline, or that it is LRU and the algorithm is cache-oblivious. In practice, LRU is not always optimal, but many algorithms have good behavior under LRU. The model also assumes that I/Os are atomic and that there is no contention on the external memory bus. In reality, P simultaneous I/Os may not achieve P times the bandwidth. The model is optimistic in this regard.

The PEM model is closely related to the parallel disk model, or PDM, which has multiple disks. In PDM, each disk can perform one I/O at a time. The goal is to maximize parallelism across disks. PEM is similar, but the parallelism comes from processors, not disks. The two models share many techniques. In fact, algorithms designed for PDM often work in PEM, and vice versa.

One important distinction is between cache-aware and cache-oblivious algorithms. A cache-aware algorithm knows M and B and uses them in its design. A cache-oblivious algorithm does not know M and B, yet it performs well for all values of M and B simultaneously. The classic example is the cache-oblivious merge sort, which uses a recursive layout. In PEM, most algorithms are cache-aware. There is some work on parallel cache-oblivious algorithms, but it is more complex. The reason is that parallelism and cache obliviousness can conflict. A cache-oblivious algorithm may have a recursive structure that is hard to parallelize efficiently. It may also have more I/Os than a cache-aware algorithm. For many problems, cache-aware PEM algorithms are optimal.

The I/O complexity of a PEM algorithm is usually expressed in terms of sort(N), which is the I/O complexity of sorting N items in the external memory model. sort(N) = Θ((N/B) log_{M/B}(N/B)). In PEM, the parallel sort complexity is often Θ(sort(N)/P) for a range of P. This means that sorting can be perfectly parallelized, up to a point. The point at which it stops scaling is when P is so large that each processor has less than M items, or when the merge phase becomes communication-bound. In practice, this is a useful guideline.

## Designing algorithms for PEM

Designing algorithms for PEM requires a different mindset than designing for PRAM. In PRAM, the goal is to minimize parallel time, which is the number of steps. In PEM, the goal is to minimize parallel I/Os, which is the maximum number of block transfers per processor. This means that load balancing is critical. If one processor does twice as many I/Os as the others, the parallel time doubles. So algorithms must distribute I/O work evenly. This often requires careful partitioning and scheduling.

Another key issue is data sharing. In PEM, caches are private. If two processors need the same data, they must each read it from external memory. This is different from a coherent shared-memory system, where the data can be cached once and shared. To avoid redundant I/Os, algorithms must partition data so that each block is read by as few processors as possible. Sometimes this means replicating data, which increases I/O but reduces contention. Sometimes it means reorganizing data so that each processor works on a disjoint subset. The trade-off depends on the problem.

A common technique in PEM is to use sorting as a subroutine. Many problems can be reduced to sorting. For example, list ranking, connected components, and minimum spanning tree can all be solved in O(sort(N)) I/Os in the external memory model. In PEM, the parallel versions often achieve O(sort(N)/P) I/Os. The idea is to use parallel sorting to redistribute data, then perform local computations. This is a powerful approach. It means that if you have a fast parallel external sort, you can build many other algorithms on top of it.

Another technique is distribution sweeping. This is used in computational geometry. The idea is to partition the plane into vertical slabs, then sweep a line across the slabs. Each processor handles a subset of the slabs. The algorithm uses sorting to distribute the events. It achieves O(sort(N)) I/Os in EM, and O(sort(N)/P) in PEM for many problems. Examples include orthogonal range searching, segment intersection, and closest pair.

Time-forward processing is another technique. It is used for problems on trees and DAGs. The idea is to process nodes in topological order, but to batch the I/Os. Instead of reading and writing each node individually, you sort the edges and process them in a streaming fashion. This reduces random I/Os. In PEM, time-forward processing can be parallelized by partitioning the tree into subtrees and processing them independently.

Multi-way merging is the workhorse of external memory sorting. In EM, you can merge M/B sorted runs at once. In PEM, you can parallelize the merge by splitting the runs among processors. The challenge is to balance the load. If one run is much larger than the others, the processor handling it will do more I/Os. To avoid this, you can use a technique called parallel multi-way merge with splitters. You sample the runs, choose splitters, and partition the data so that each processor gets roughly equal work. This is similar to parallel sample sort. The I/O complexity is O((N/(B P)) log_{M/B}(N/B)) for sorting.

Matrix multiplication is another classic problem. In EM, the optimal I/O complexity is O(N^3/(B sqrt(M))). The algorithm uses blocking: it partitions the matrices into tiles of size sqrt(M) x sqrt(M). Each tile fits in cache. The algorithm multiplies the tiles and accumulates the results. In PEM, you can distribute the tiles across processors. The parallel I/O complexity is O(N^3/(B P sqrt(M))) for a range of P. The challenge is to avoid redundant reads. If multiple processors need the same tile, they must each read it. To minimize this, you can replicate tiles or use a schedule that maximizes reuse. In practice, this is similar to cache blocking in high-performance computing. The PEM model provides a theoretical foundation for why blocking works.

Graph algorithms are more challenging. In EM, breadth-first search can be done in O(sort(N + E)) I/Os per level. If the graph has large diameter, this can be many passes. In PEM, you can parallelize each level. The frontier is distributed among processors. Each processor reads its portion of the frontier, then reads the adjacency lists of the frontier vertices. This requires random I/Os unless the graph is sorted by vertex ID. To improve locality, you can sort the edges and use a technique called direction-optimizing BFS. This switches between top-down and bottom-up traversal depending on the frontier size. In PEM, the I/O complexity is O(sort(N + E) * D / P) where D is the diameter, but this is a rough bound. In practice, the number of passes is the dominant factor. Reducing the number of passes is more important than reducing the I/Os per pass.

List ranking is a fundamental problem in parallel algorithms. It is used in Euler tour, tree contraction, and many graph algorithms. In EM, list ranking can be solved in O(sort(N)) I/Os. In PEM, the parallel version achieves O(sort(N)/P) I/Os. The algorithm uses pointer jumping, but pointer jumping causes random I/Os. To avoid this, you can use a technique called independent set contraction. You find a large independent set of nodes, remove them, and update the pointers. This reduces the problem size by a constant factor in each round. After O(log N) rounds, the list is small enough to fit in cache. The I/O complexity is O(sort(N)) because each round requires sorting. In PEM, the rounds can be parallelized, but the independent set computation requires communication. This is a good example of how PEM algorithms combine parallel and external memory techniques.

## Practical considerations and gaps

The PEM model is an abstraction. Real hardware has many features that it ignores. Modern CPUs have multiple levels of cache, hardware prefetchers, out-of-order execution, and SIMD units. Memory systems have NUMA effects, where access to remote memory is slower. Storage devices have different block sizes, write amplification, and wear leveling. The PEM model assumes a single block size B and a single cache size M. In reality, there is a hierarchy: L1, L2, L3, DRAM, SSD. An algorithm that is optimal for one level may not be optimal for another. Multi-level PEM models exist, but they are more complex.

Another gap is the cost of computation. The PEM model assumes computation is free. For some problems, such as sorting, the I/O cost dominates. For others, such as matrix multiplication with small matrices, the computation cost may be significant. In practice, you need to balance both. The roofline model is a useful tool for this. It plots performance against operational intensity. PEM provides the I/O bound; the roofline provides the compute bound. The actual performance is the minimum of the two.

Contention on the external memory bus is another issue. The PEM model assumes that P processors can each perform one I/O per step without interfering. In reality, the memory controller has limited bandwidth. If all processors stream data, they may saturate the bus. The effective bandwidth per processor decreases as P increases. This is the memory bandwidth wall. To mitigate this, algorithms must be bandwidth-aware. They should reuse data in cache as much as possible. They should also use non-temporal stores and prefetching to hide latency. The PEM model does not capture these effects, but it provides a starting point.

Cache coherence is also ignored. In a coherent shared-memory system, a block can be cached by multiple processors. When one processor writes to it, the others must invalidate their copies. This can cause false sharing and coherence traffic. PEM assumes private caches with no coherence. This is more like a distributed memory system with explicit message passing. In fact, PEM algorithms often resemble distributed algorithms. The difference is that the external memory is shared, so there is no network. But the private caches mean that data must be explicitly communicated through external memory. This is a useful mental model.

Finally, the PEM model is not a replacement for empirical performance engineering. It is a guide. It tells you what is theoretically possible. It helps you identify bottlenecks. It suggests algorithmic structures that are likely to be efficient. But you still need to measure and tune. You need to choose block sizes, schedule I/Os, and manage memory. You need to understand the specific hardware you are targeting. The PEM model is a tool, not a recipe.

In the next sections, we will look at specific PEM algorithms in more detail. We will examine parallel sorting, matrix multiplication, graph traversal, and list ranking. We will discuss the techniques used to achieve optimal I/O complexity. We will also look at how these algorithms map to real hardware, and where the model breaks down. We will not conclude yet; there is more to cover.

## Parallel sorting in PEM: sample, distribute, merge

A PEM sort is not a local sort with a merge pasted on at the end. The parallel structure changes where the I/O is spent. The useful mental model is a sequence of global data movements: read the input, produce sorted runs, choose splitters, redistribute elements into buckets, then merge each bucket. Each phase has a different failure mode. Local sorting fails if N/P is much larger than M, because a processor cannot sort its chunk in cache. Splitter selection fails if the samples are unrepresentative, because one processor gets a bucket that is much larger than the others. Distribution fails if writes are not buffered, because the algorithm emits a block transfer for every small bucket append. Merging fails if the fan-in is chosen without regard to M/B, because the merge becomes a sequence of random reads.

The standard cache-aware PEM sort uses sample sort for the redistribution step and multiway merging for the final step. Each processor starts with a contiguous chunk of N/P elements. If the chunk fits in cache, the processor sorts it with an in-cache algorithm and writes one sorted run. If it does not fit, the processor first performs a sequential external sort on its chunk. The output is P sorted runs. At this point, a pure P-way merge would work, but it would concentrate too much work on the processor that owns the largest run or the largest merge partition. Sampling avoids that.

Each processor draws a sample from its run. The samples are written to external memory, read by one or more processors, and sorted. From the sorted sample, the algorithm chooses P-1 splitters. The splitters define P buckets. Every element in every run is then routed to exactly one bucket. The routing is done by each processor scanning its own run and writing to per-bucket output buffers. The buffers are the key implementation detail. A processor cannot afford to write one element at a time to each of P buckets. It keeps a block-sized buffer per bucket, flushes when full, and uses asynchronous writes where available. In the PEM cost model, this buffering is assumed to be free; in a real system it consumes cache space and reduces the effective M. That hidden tax is one reason theoretical PEM sorts often need larger caches than the formula suggests.

After distribution, each processor is assigned one or more buckets. Because the splitters were chosen from samples, the buckets are balanced with high probability. The processor reads its bucket and merges the sorted pieces. If the bucket contains data from many runs, the merge fan-in may exceed M/B. In that case, the merge is done in multiple passes, or the bucket is sorted again as a standalone external sort. The final output is written in sorted order. The dominant I/O term is the same as sequential sorting, divided by P, plus lower-order terms for sampling and bucket metadata. The exact constant depends on how many passes the merge needs and how much over-sampling was used to control skew.

Over-sampling is the usual defense against bad splitters. Instead of taking one sample per processor, take several and choose splitters that are spaced by rank rather than by sample position. The extra samples cost a small number of I/Os, but they make the maximum bucket size close to N/P with high probability. Deterministic regular sampling is also possible: sample every k-th element from each run, sort the samples, and choose splitters at fixed ranks. This avoids randomness but can be fooled by adversarial input distributions. In PEM, adversarial inputs are a real concern because the model assumes the algorithm sees the whole input and the cost is worst-case. A randomized sample sort with a careful over-sampling factor is often preferred because the probability of a bad split can be made polynomially small.

The merge phase is where the sequential sorting factor re-enters. If the bucket fits in cache, the merge is an in-cache operation and costs only the reads and writes of the bucket. If the bucket does not fit, the processor performs a multiway merge with fan-in M/B. The number of passes is logarithmic in the bucket size divided by M. The parallel I/O complexity therefore has the familiar shape: the sequential sort cost divided by P, plus a term for the distribution phase. The distribution phase reads each element once and writes it once, so it is linear in N/B per processor on average. That linear term is small compared with the logarithmic sort term for large N, but it becomes visible when N/P is close to M. At that point, local sorting is cheap and the redistribution dominates. This is the PEM analogue of the point where parallel overhead overwhelms useful work.

There is also a communication pattern hidden in the distribution phase. Each processor writes to P buckets, and each bucket is later read by a different processor. This is an all-to-all exchange through external memory. The PEM model charges each processor for its own reads and writes, but it does not charge for contention on the shared memory bus. In practice, the distribution phase is often the most bandwidth-intensive part of a parallel sort. If all processors flush their buffers at the same time, the memory system sees a burst of writes to scattered locations. A good implementation staggers the flushes, uses large contiguous extents per bucket, and avoids false sharing between bucket buffers. These are not details that the PEM model captures, but they determine whether the theoretical I/O bound is approached.

## Matrix multiplication: tiling with replicated reads

Matrix multiplication exposes a different PEM problem. Sorting is about redistributing data once and then merging. Matrix multiplication is about reusing data many times. The sequential blocked algorithm partitions the matrices into square tiles of size T, where three tiles (one from A, one from B, one from C) fit in cache. The condition is roughly 3T^2 ≤ M, so T is on the order of sqrt(M). Each output tile is computed by streaming over the corresponding row tile of A and column tile of B. The number of I/Os is proportional to N^3/(B sqrt(M)) for N×N matrices. The tiling is not an optimization added after the fact; it is the only way to keep the cache busy with useful multiplies instead of repeated loads.

In PEM, the same tiling appears, but the scheduling question changes. There are P processors and P private caches. The output matrix C is partitioned into tiles, and each processor is assigned a set of output tiles. To compute one output tile, a processor needs an A row tile and a B column tile. If two processors compute different output tiles that share the same A row tile, they each read that A tile from external memory. The private caches do not help each other. This is the central difference from a coherent shared-memory machine, where the A tile could be cached once and shared. In PEM, sharing costs redundant reads unless the algorithm explicitly replicates or reorganizes the data.

A naive PEM schedule assigns output tiles to processors in row-major order. That gives each processor a contiguous block of C, but it does not guarantee that the A and B tiles needed by different processors are disjoint. The aggregate number of reads can be much larger than the minimum, even though the maximum per-processor I/O count looks balanced. This is a subtle but important point: the PEM cost is the maximum per-processor I/O count, not the total I/O volume. A schedule that makes every processor read the same popular A tile has a small maximum, because each processor reads the tile once. But the total traffic is P times the tile size. On a real memory bus, that aggregate traffic is what saturates bandwidth. PEM algorithms for matrix multiplication therefore often aim for two things at once: a balanced per-processor cost and a low total communication volume. The model rewards the first; the hardware punishes the second.

There are several ways to reduce redundant reads. One is to assign each processor a block of rows of C, so that a single A row tile is reused across all the output tiles in that row block. The processor reads the A row tile once and keeps it in cache while it streams over the corresponding B column tiles. The B tiles are shared across processors, so each processor still reads them independently. Another schedule assigns blocks of columns, which reverses the trade-off. A third approach partitions C into square blocks and replicates the necessary A and B tiles so that each processor works on a private copy. Replication costs I/Os, so it only helps if it replaces a larger number of redundant reads. The optimal choice depends on the ratio of N to M and on how many output tiles each processor owns.

A more sophisticated view treats the computation as a three-dimensional iteration space over (i, j, k) tile indices. Each point represents a multiply-accumulate of an A tile and a B tile into a C tile. The schedule is a projection of this space onto processors and time. Blocking in the i and j dimensions improves C reuse. Blocking in the k dimension improves A and B reuse but requires temporary accumulators. In PEM, the cache size limits how many tiles can be live at once. The schedule must ensure that the working set of A, B, and C tiles fits in M; otherwise the cache thrashes and the I/O count explodes. This is the same constraint as sequential blocking, but now it must hold for every processor independently, and the schedule must avoid making different processors compete for the same external memory blocks at the same time.

The communication-avoiding perspective is useful here. For a tiled matrix multiplication, the minimum number of words that must move through the memory hierarchy is related to the surface area of the computation graph. Tiling reduces the surface area by keeping a block of data in cache across many arithmetic operations. In PEM, the parallel schedule adds another surface: the boundary between processors. Data that crosses that boundary must go through external memory, even if it is conceptually shared. The best PEM algorithms minimize both surfaces. They choose tile sizes that fit the private cache, and they choose processor assignments that keep the cross-processor boundary small. This is why matrix multiplication in PEM looks like a combination of cache blocking and distributed data partitioning, not just a parallel loop around a sequential kernel.

Finally, matrix multiplication illustrates why PEM analysis must be paired with a bandwidth model. The per-processor I/O count can be made equal across processors by giving each one the same number of output tiles. But if those tiles require overlapping A and B data, the aggregate read volume can exceed the available bandwidth. A schedule that is optimal in the PEM max metric may be suboptimal on hardware. The practical fix is to measure both per-processor I/O and total I/O, and to prefer schedules that do not rely on massive replication. The model points in the right direction; the implementation has to close the gap.

## Graph traversal in PEM: frontiers, sorted edges, and the cost of not being able to share

A graph traversal in PEM is not a loop over vertices with a shared visited array. There is no shared cache. The frontier is a distributed work queue, and every edge that crosses a processor boundary is a potential block transfer. The practical question is not whether the algorithm is breadth-first, depth-first, or direction-optimizing. It is how the frontier and the edge list meet in external memory. If the edge list is sorted by source vertex, scanning the adjacency lists of a sorted frontier is a streaming merge. If the frontier is unsorted, the same scan becomes a gather of scattered adjacency blocks. The I/O difference is the difference between a sequential read and a random read, and it usually dominates the arithmetic.

The push phase begins with a frontier F and a graph stored as sorted edges or compressed sparse row. Each processor receives a contiguous range of frontier vertices. It sorts that range by vertex ID if it is not already sorted, then merges the range with the edge list. For every frontier vertex u, the merge emits its neighbors v. The emitted neighbors are candidates for the next frontier. They are not yet unique. A vertex may be discovered by many predecessors in the same level. The next frontier must therefore be deduplicated, usually by sorting the candidate list and removing adjacent duplicates. The cost of one level is O(sort(F + E_F)) per processor in the worst case, where E_F is the number of edges incident to the frontier. The maximum per-processor share is controlled by partitioning F so that each processor gets roughly the same number of incident edges, not the same number of vertices. High-degree vertices make vertex-count balancing useless. A single hub vertex can give one processor more adjacency blocks than a thousand low-degree vertices. The partitioner must either split the adjacency list of a high-degree vertex into chunks or assign the whole vertex to one processor and accept the imbalance.

The pull phase reverses the direction. Instead of scanning adjacency lists of frontier vertices, it scans all edges and checks whether the target is in the frontier. That sounds wasteful, and it is when the frontier is small. But when the frontier is large, pulling is sequential over the edge array and avoids random gathers. Each processor owns a range of edges, reads the target vertex, tests membership in the frontier, and emits the source if the test succeeds. The membership test is the hard part. A distributed frontier cannot be queried in constant time from every processor. The practical solution is to materialize the frontier as a sorted array or a Bloom filter. A sorted array supports binary search against cached pages, but the accesses are still random. A Bloom filter can reject most non-frontier vertices with a small number of cached probes, but it has false positives. In PEM, both structures add I/Os: the sorted array must be read, and the Bloom filter must be built and distributed. The benefit is that the edge scan stays streaming.

Direction-optimizing traversal switches between push and pull based on frontier size and edge density. The switch point is not a universal constant. It depends on the ratio of the frontier to the number of edges, the block size, and the cache size. In PEM, the switch should be made when the cost of random adjacency gathers exceeds the cost of a sequential edge scan plus membership tests. A simple heuristic is to estimate the number of incident edges for the frontier. If that number is a large fraction of the total edge count, pull wins. If it is small, push wins. The heuristic must be computed from metadata, not by sampling external memory, because the sampling itself costs I/Os.

The private-cache assumption changes the sharing economics. In a shared-memory graph traversal, all cores can read a hub vertex from the last-level cache. In PEM, each processor that needs the hub reads it from external memory independently. If the hub is needed by all P processors, the redundant read volume is P times the hub size. This is why high-degree vertices are a special case in PEM graph algorithms. One option is to replicate the hub adjacency list into P copies, one per processor, so that each processor reads a contiguous local copy. That costs P times the storage and one initial write per copy, but it replaces repeated random reads with sequential reads. Another option is to assign the hub to a single owner processor and have other processors send frontier queries to it through external memory. That is a message-passing design disguised as an external memory algorithm. It reduces redundant reads but adds communication rounds and a serial bottleneck at the owner. The right choice depends on how many times the hub is touched and how large its adjacency list is relative to M.

Multi-core graph traversal also exposes the barrier problem. Each BFS level is a superstep. All processors must finish emitting candidates before the next frontier can be deduplicated and distributed. A single straggler processor delays the whole level. Stragglers arise from degree skew, from uneven cache behavior, and from contention on the memory bus when many processors flush candidate buffers at once. A cache-aware implementation staggers flushes and uses per-processor output buffers sized to a block. It also separates the emit phase from the deduplication phase so that the memory system sees long sequential writes rather than interleaved random writes. These are implementation details that the PEM cost model does not charge for, but they determine whether the theoretical per-processor I/O bound is approached.

Sparse graphs and dense graphs need different representations. For sparse graphs, compressed sparse row with sorted neighbor lists is natural. For dense graphs, an adjacency matrix permits pull-based traversal to scan complete rows sequentially. In PEM, the dense representation can be better even for moderately sparse graphs if the frontier is large, because the scan is perfectly streaming. The sparse representation is better when the frontier is small and only a few adjacency lists are touched. This is the same trade-off as sequential graph processing, but the parallel version adds the cost of partitioning the matrix or the edge list across processors. A row-partitioned adjacency matrix gives each processor a contiguous block of rows, which is good for pull. A column-partitioned matrix is good for push. A hybrid partition can switch without a global redistribution, at the cost of extra metadata.

## List ranking and contraction: batching irregular dependencies

List ranking is the canonical irregular problem in parallel algorithms. Each node points to a successor, and the goal is to compute the distance from every node to the end of the list. The sequential algorithm follows pointers and is O(N) time but has no parallelism. The PRAM algorithm uses pointer jumping: each node updates its successor to its successor's successor, and accumulates the skipped distance. After O(log N) rounds, every node knows its rank. Pointer jumping is elegant in the PRAM model because every round is a set of independent constant-time operations. In PEM, every round is a set of random reads. A node's successor may be anywhere in external memory. If the list is stored in arbitrary order, pointer jumping turns into a sequence of random block transfers, and the logarithmic round count multiplies the I/O cost. The algorithm is parallel in computation but serial in memory behavior.

The external memory solution is contraction. Instead of jumping every pointer, the algorithm selects an independent set of nodes, removes them, and splices their predecessors directly to their successors. An independent set in a linked list is a set of nodes with no two adjacent. If a constant fraction of the nodes is removed in each round, the list shrinks geometrically, and after O(log N) rounds the remaining list fits in cache. The final ranks are computed sequentially in cache. The removed nodes get their ranks by adding the accumulated distances of their successors. The key is that each round can be implemented with sorting and scanning rather than pointer chasing.

A round proceeds in three batched steps. First, select the independent set. A randomized rule marks each node with probability p and then removes marks that are adjacent to another mark. A deterministic rule can use the low bits of node IDs or a coin-tossing hierarchy, but the randomized version is simpler and gives a constant expected fraction. Second, for every selected node v, find its predecessor p and its successor s. The predecessor is not stored in the forward list, so it must be computed. One way is to sort the selected nodes by successor and join with the list to recover predecessors. Another is to maintain a backward pointer, which doubles the storage but simplifies the join. Third, emit an update for p: its new successor becomes s, and its accumulated distance increases by the distance from p to v plus the distance from v to s. The updates are sorted by predecessor and applied in a single scan. The selected nodes are removed from the active list.

The I/O cost of a round is dominated by the sorts and scans over the active nodes. Each round reads the active list, writes the selected set, sorts updates, and writes the contracted list. The active list shrinks by a constant factor, so the total cost over all rounds is a geometric series. In the external memory model, the total is O(sort(N)). In PEM, the same structure holds if the sorts are parallel external sorts and the scans are partitioned evenly. The maximum per-processor I/O count is O(sort(N)/P) for a range of P, provided that the selected nodes and the updates are balanced across processors. Balancing is not automatic. The selected set is random, so the number of updates per processor is random. A processor that owns a dense cluster of selected nodes may do more work. Over-sampling and dynamic assignment of update ranges can smooth this, but they add communication.

The harder issue is that contraction creates irregular communication. A selected node's predecessor may be owned by a different processor. The update must cross a processor boundary through external memory. The sort by predecessor is exactly the all-to-all exchange that routes the update to the owner. This is why list ranking in PEM is a sorting problem in disguise. The pointer structure is irregular, but the algorithm converts it into a sequence of sorts and scans. The private caches do not help with the irregular joins; they only help with the local scans. The external memory sort is the communication fabric.

There is a practical variant called independent set contraction with path compaction. Instead of removing only an independent set, the algorithm contracts short paths into single supernodes. A path of length k can be replaced by one node with a weight k. This reduces the number of rounds when the list has long chains. The supernode's successor is the end of the path, and its weight is the number of original nodes on the path. The contraction is still batched with sorting, but the path finding requires a scan of the active list. The benefit is fewer rounds and less metadata. The cost is that path finding is a sequential scan over the active list, which is I/O efficient if the list is stored contiguously. In PEM, the active list can be stored in a compact array after each round, so the scan is streaming. This is a good example of how a PEM algorithm chooses a representation that makes the next phase I/O efficient, rather than preserving a pointer structure that is convenient for the PRAM model.

List ranking also illustrates the difference between per-processor I/O and total I/O. If each processor sorts its own chunk and then the chunks are merged, the per-processor cost is balanced, but the merge may read the same pivot blocks from many processors. The total I/O volume can be larger than the per-processor maximum. In a real multi-core system, the memory bus sees the total volume. A PEM-optimal list ranking may therefore need a communication-avoiding merge, where the splitters are chosen to minimize cross-processor traffic, not just to balance the bucket sizes. The model gives the lower bound; the implementation has to decide how much extra traffic is acceptable.

## Cache-aware scheduling as a resource allocation problem

Once the algorithmic structure is fixed, the remaining PEM question is scheduling. A PEM schedule assigns tiles, buckets, frontier ranges, or list updates to processors and orders the I/Os within each processor. The objective is to minimize the maximum per-processor I/O count while keeping the total I/O volume low enough that the shared memory bus is not saturated. These two objectives can conflict. A schedule that balances the maximum may replicate data so that every processor has a private copy. Replication increases total volume. A schedule that minimizes total volume may concentrate work on a few processors. The best schedule depends on whether the hardware is latency-bound or bandwidth-bound. PEM's max metric is closer to a latency-bound view, where the slowest processor determines the finish time. A bandwidth-bound view would minimize total volume or the maximum per-processor bandwidth demand.

Cache-aware scheduling also has to respect the private cache capacity M. A processor cannot interleave too many tasks that each require a different working set. If it does, the working sets evict each other and the I/O count rises. The schedule should group tasks that share data, so that a tile read for one task is still in cache for the next. This is temporal locality at the schedule level. In matrix multiplication, it means processing a block of output tiles that share A and B tiles before moving on. In graph traversal, it means processing a range of frontier vertices whose adjacency lists are contiguous in the edge array. In sorting, it means flushing a bucket buffer only when it is full and then finishing that bucket before starting another. These grouping decisions are not captured by the PEM cost formula, but they determine the constant factors.

The multi-core memory hierarchy adds another layer. Each core may have a private L1 and L2, and share an L3. The PEM model collapses all private levels into M and treats external memory as shared. A real schedule must decide which data to keep in L1, which in L2, and which to stream through L3. A tile that fits in M may still not fit in L1, so the processor will do multiple L2-to-L1 transfers. Those transfers are not counted as I/Os in PEM, but they cost cycles. A cache-aware schedule therefore often uses a two-level blocking: a large tile that fits in M for external memory, and a smaller sub-tile that fits in L1 for computation. The PEM analysis applies to the outer tile; the inner tile is a hardware-specific optimization. This is a healthy separation of concerns. The model predicts the external memory traffic; the implementation tunes the on-chip traffic.

Finally, scheduling must handle the fact that I/Os are not instantaneous. A processor can overlap computation with I/O if it has independent work. PEM usually assumes that I/O and computation are serialized or that computation is free, but real systems have asynchronous DMA, prefetching, and non-blocking writes. A schedule that exposes independent I/O requests can hide latency. A schedule that alternates read and compute on the same data cannot. This is why PEM algorithms often use double buffering: while one block is being processed, the next block is being fetched. The buffer occupies cache space, so it reduces the effective M. The algorithm must be designed with that reduction in mind. In the theoretical model, double buffering is free; in practice, it is a trade-off between latency hiding and cache capacity. A careful PEM implementation budgets for it explicitly, choosing tile sizes that leave room for the buffers and measuring the resulting I/O count against the model's prediction.

## Multi-level memory hierarchies and recursive blocking

The PEM model assumes two levels: private cache and shared external memory. Real machines have more. A core may have L1, L2, L3, DRAM, and possibly non-volatile memory. Each level has its own block size and capacity. An algorithm that is optimal for one level may be suboptimal for another. The standard response is recursive blocking: partition the problem into subproblems that fit in the largest cache, then recursively partition each subproblem for the next level. This is the essence of cache-oblivious algorithms, but it also applies to cache-aware multi-level designs.

In a multi-level PEM, the cost of an algorithm is the sum of I/Os at each level, or more precisely, the maximum over processors of the weighted sum of transfers at each level. The weights reflect the latency and bandwidth of each level. If the levels are well-separated (e.g., L1 latency 4 cycles, L2 12 cycles, L3 40 cycles, DRAM 200 cycles), the DRAM traffic dominates. But if the algorithm has poor L1 locality, the L1 traffic can become the bottleneck. A multi-level analysis forces the designer to consider all levels simultaneously. The usual technique is to choose a tile size that fits in the smallest cache (L1), then a super-tile that fits in L2, and so on. The algorithm is a nested loop over these tiles. The I/O complexity at each level is determined by the number of times a tile is loaded from the next level.

For parallel algorithms, the multi-level structure adds a dimension: the private caches of different processors. If two processors share an L3, they can share data through L3, but not through L1 or L2. The PEM model with private caches assumes no sharing at any level. A more realistic model would have a shared last-level cache. This is the subject of the "parallel external memory with shared cache" model, or PEM-S. In PEM-S, the shared cache is a resource that all processors contend for. The I/O complexity is the number of transfers between the shared cache and external memory, plus the transfers between private caches and the shared cache. The scheduling problem becomes a cache partitioning problem: how much of the shared cache should each processor use? If one processor hogs the shared cache, others suffer. A fair schedule allocates cache space proportionally to the working set sizes. This is analogous to bandwidth allocation in a network.

Recursive blocking also helps with NUMA effects. On a NUMA machine, memory is physically distributed across sockets. Accessing remote memory is slower than local memory. A PEM algorithm that treats all external memory as uniform will perform poorly if it repeatedly accesses remote memory. The fix is to partition data so that each processor works on data stored in its local memory. This is a form of data placement. The algorithm must be aware of the memory topology. In PEM terms, the external memory is not a single monolithic store; it is a collection of local stores with different access costs. A NUMA-aware PEM algorithm minimizes remote I/Os by replicating or migrating data. The cost model must include a penalty for remote accesses. This is an active area of research.

## Cache-oblivious parallel algorithms: promise and pitfalls

Cache-oblivious algorithms are attractive because they do not require tuning for a specific M and B. A single algorithm performs well across all cache sizes. The classic example is the cache-oblivious merge sort, which uses a recursive layout and a funnel heap. In the sequential world, cache-oblivious algorithms can match the I/O complexity of cache-aware algorithms for many problems. In the parallel world, the situation is more complicated.

The main challenge is that cache obliviousness and parallelism often conflict. A cache-oblivious algorithm typically has a recursive divide-and-conquer structure. To parallelize it, you must expose parallelism at the top levels of the recursion. But the top levels are exactly where the working set is large and the cache behavior is poor. If you parallelize naively, each processor may thrash its private cache. The solution is to use a parallel recursive structure that is also cache-oblivious. This is called a parallel cache-oblivious algorithm. The goal is to achieve both optimal parallel I/O complexity and optimal sequential cache behavior.

One approach is to use a "parallel funnel" structure. A funnel is a data structure that merges k sorted lists in O(k log k) I/Os. In parallel, you can split the funnel into independent sub-funnels, each handled by a different processor. The sub-funnels communicate through a shared buffer. The I/O complexity is O(sort(N)/P) for a range of P, provided that the funnel is laid out recursively. This works for sorting and for some graph problems. However, the constant factors are often larger than those of cache-aware algorithms. The cache-oblivious algorithm may do more I/Os in practice, even if the asymptotic complexity is the same.

Another pitfall is that cache-oblivious algorithms assume an ideal cache replacement policy. In reality, LRU is not always optimal. A cache-oblivious algorithm that is optimal under the ideal model may perform poorly under LRU. This is especially true for algorithms that have cyclic access patterns. In a parallel setting, the problem is worse because multiple processors compete for cache. The LRU policy may evict a block that is about to be used by another processor. Cache-aware algorithms can avoid this by explicitly scheduling accesses. Cache-oblivious algorithms rely on the replacement policy to do the right thing. This is a leap of faith that is not always justified.

Despite these challenges, parallel cache-oblivious algorithms are an active research area. They are particularly useful for platforms where the cache parameters are unknown or vary widely, such as heterogeneous multi-core systems or cloud environments. A single binary can run efficiently on different machines without recompilation. The overhead is usually a constant factor, which may be acceptable for many applications. The key is to design the algorithm so that the recursive structure is parallelizable and the base cases are large enough to amortize the overhead.

## Lower bounds and the cost of communication

The PEM model provides lower bounds on the parallel I/O complexity of problems. These bounds tell us when an algorithm is optimal and when it is not. The most famous lower bound is for sorting: any PEM algorithm that sorts N items requires Ω((N/B) log_{M/B}(N/B) / P) I/Os per processor, for a wide range of P. This bound is tight: the sample sort algorithm described earlier achieves it. The lower bound is derived from the fact that sorting requires moving data across the memory hierarchy. The number of possible permutations is N!, and each I/O can distinguish at most a certain number of them. The bound is information-theoretic.

Similar bounds exist for matrix multiplication, list ranking, and many graph problems. For matrix multiplication, the lower bound is Ω(N^3/(B sqrt(M) P)) for a range of P. This bound is also tight. For list ranking, the lower bound is Ω(sort(N)/P). These bounds are useful because they tell us the best possible performance. If an algorithm is within a constant factor of the lower bound, it is optimal. If it is far from the bound, there is room for improvement.

However, lower bounds in PEM are not the whole story. They assume that the only cost is I/O. They ignore computation, synchronization, and contention. In practice, an algorithm that is optimal in the PEM model may be slower than a suboptimal algorithm that has better constant factors or less synchronization. For example, a PEM-optimal graph traversal may have many rounds of communication, each with a barrier. The barrier cost can dominate the I/O cost. A less I/O-efficient algorithm with fewer rounds may be faster. This is why practical algorithm design must consider both the asymptotic I/O complexity and the constant factors.

Another limitation is that PEM lower bounds assume a specific machine model. They may not apply to machines with caches that are shared or with different block sizes. They also assume that the algorithm is deterministic. Randomized algorithms can sometimes beat deterministic lower bounds, though usually only by a constant factor. The lower bounds are a guide, not a straitjacket. They help us understand the fundamental limits of parallel external memory algorithms.

## From PEM to practice: NUMA, GPUs, and distributed memory

The PEM model is an abstraction, but it has influenced the design of real systems. The most direct influence is in the design of parallel external sorting libraries, such as those used in databases. These libraries use sample sort, multi-way merging, and careful buffer management. They are aware of the cache hierarchy and the number of cores. They often achieve near-optimal performance on large datasets.

NUMA systems are a natural fit for PEM-like thinking. In a NUMA machine, each socket has its own memory controller and local DRAM. Accessing remote DRAM is slower. A PEM algorithm can be adapted by treating each socket's local memory as a separate external memory. The algorithm partitions data so that each processor accesses mostly local memory. The I/O cost includes a penalty for remote accesses. This is equivalent to a PEM model with non-uniform external memory. The scheduling problem becomes a data placement problem: which data should be replicated, and which should be migrated? The answer depends on the access patterns. For read-only data, replication is often best. For write-heavy data, migration or partitioning is better.

GPUs present a different challenge. A GPU has many cores, a deep memory hierarchy, and very high bandwidth. The PEM model with P processors and private caches does not map directly to a GPU, because GPU cores share a memory hierarchy and have explicit scratchpad memory. However, the principles of blocking and tiling are essential for GPU performance. A GPU kernel that does not use shared memory will be memory-bound. The PEM model can be adapted by treating the shared memory as the private cache and the global memory as external memory. The number of processors is the number of thread blocks. The I/O complexity is the number of global memory transactions. This is a useful way to reason about GPU algorithms. Many GPU sorting and matrix multiplication algorithms are designed with this in mind.

Distributed memory systems, such as clusters, are even further from PEM. In a cluster, each node has its own memory and disk, and nodes communicate over a network. The PEM model assumes a shared external memory. A distributed PEM model would have multiple external memories and a network. The cost would include both I/O and communication. This is the subject of the "parallel external memory with communication" model. The algorithms are similar, but the communication patterns are more complex. MapReduce and its successors are practical frameworks for this model. They use sorting and shuffling to redistribute data. The PEM model provides a theoretical foundation for why these frameworks work and what their limits are.

In all these cases, the PEM model is not a perfect predictor of performance. It is a tool for thinking about the memory hierarchy. It helps you identify the data movement that matters. It suggests algorithmic structures that are likely to be efficient. The rest is engineering: measuring, tuning, and adapting to the specific hardware. The model is a starting point, not a destination.
