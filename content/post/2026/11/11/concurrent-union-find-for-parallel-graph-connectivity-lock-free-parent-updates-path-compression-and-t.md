# Concurrent Union-Find for Parallel Graph Connectivity: Lock-Free Parent Updates, Path Compression, and the Cost of Remapping

Union-find, also called disjoint-set union (DSU), is one of the few data structures whose sequential behavior is almost invisible: `find` follows parent pointers until it reaches a root, `union` links one root under another, and path compression flattens the tree for later queries. The result is a near-constant amortized cost that made DSU a default choice for Kruskal's algorithm, connected components, cycle detection, and image segmentation. In parallel graph analytics the same structure appears in spanning-forest construction and component labeling. The tempting port is to put a mutex around `find` and `union`, or to wrap parent pointers in atomics and hope. Both approaches can be made correct, but they answer different questions. This article is about the second approach: a shared-memory concurrent union-find for graph connectivity, with lock-free parent updates, atomic path compression, and explicit remapping strategies for reducing contention. The discussion assumes a multicore CPU, large immutable edge lists, and a graph algorithm that can tolerate weak intermediate observations as long as the final partition is correct. It does not assume a specific language's memory model beyond acquire/release atomics and compare-and-swap.

The first point is semantic. A general-purpose DSU is usually specified as an abstract data type: `make_set(x)`, `find(x)`, and `union(x,y)`, with operations linearizable. A connectivity algorithm rarely needs that full contract. It processes a set of edges and asks whether two vertices are in the same component after some or all edges have been incorporated. Because `union` is commutative and idempotent, the final partition depends on the set of edges, not their order. That relaxation matters. A concurrent implementation may let `find` return a root that was valid at an earlier moment, or may temporarily fail to expose a union to another thread, as long as every completed `union(a,b)` eventually makes `a` and `b` connected and no completed union is lost. Algorithms that require a snapshot-consistent DSU need stronger reasoning, usually a lock or a different structure. Algorithms that only need eventual connectivity can use optimistic parent-pointer updates and tolerate transient staleness. This distinction should be stated in the API, not discovered later in a debugger.

## Baseline: atomic parent pointers and root-only linking

The simplest concurrent representation is an array of atomic indices. Vertex `i` is a root when `parent[i] == i`. `find(i)` loops through parent pointers until it reaches a self-parent. `union(a,b)` calls `find` on both, and if the roots differ, it links one root to the other with a compare-and-swap. The CAS condition is the important part: the source must still be a root. If `parent[ra]` is no longer `ra`, another thread has already attached that root, so the caller retries. Linking only roots preserves the forest invariant. No thread ever changes a non-root into a root, and no thread creates a cycle by pointing a node into its own descendant, because a root has no ancestor at the moment it is linked.

A naive version loads rank or size, chooses the root with the smaller rank, and CASes the parent pointer. That is almost right, but it leaves a race on the metadata. Two threads can observe the same two roots, both decide that root A should link to root B, and one CAS succeeds while the other fails. That part is benign. The problematic case is two different links involving the same root with stale rank values. If rank is a separate atomic integer, the parent update and rank update are not atomic together. A thread can read rank 4 for root A, link A under B, and then increment B's rank, while another thread simultaneously read B's old rank. The resulting tree is still a forest, but the rank is now a heuristic rather than an invariant. That may be acceptable, but the bound on tree depth is no longer the sequential union-by-rank bound.

There are two practical fixes. The first is to pack parent and rank into one atomic word and CAS the whole word. With 64-bit atomics, a typical implementation reserves 8 or 16 bits for rank and the rest for vertex index, or uses a 32-bit index and a 32-bit rank. The second is to use union by size and accept approximate sizes, or use a separate atomic rank with a relaxed notion of balance. Packing is often cleaner because every successful link changes exactly one atomic word, and every reader sees a consistent parent-plus-rank pair. If the graph exceeds the index range of the packed word, use a different representation: 64-bit indices, a separate atomic rank, and document that balancing is advisory. The trade-off is not academic; it determines whether a formal argument about depth applies or whether the implementation only has an empirical expectation.

Memory ordering also deserves a concrete choice. Parent pointers are synchronization data. A root's link must become visible to threads that later traverse from a child. Acquire loads on parent and release CAS on the link are a defensible default. Relaxed atomics may be faster on some architectures, but they weaken the guarantee that a completed union is promptly observed by another thread. If the algorithm's correctness depends on eventual visibility, acquire/release is not overkill. Full sequential consistency is usually unnecessary, but the cost of acquire/release on x86 is often low; the harder cost is cache-line ping-ponging on hot roots.

## Path compression is a write optimization with a concurrency tax

Path compression is where sequential DSU gets its practical speed. After finding the root, the traversal rewrites parent pointers so future finds are shorter. Under concurrency, the same idea becomes a set of CAS operations racing with other compressions and with union links. The safe version is conservative: during `find`, remember the path; at the end, attempt to CAS each node's parent from the observed parent to the root. If a CAS fails, another thread changed the pointer; re-read and continue or abandon that node. The resulting structure remains a forest because every successful CAS points a node to a node that was an ancestor when observed. Even if the ancestor later acquires a parent, the pointer is still upward.

Path halving is a cheaper variant. For a non-root `x`, read `p = parent[x]`; if `p` is not a root, read `g = parent[p]` and CAS `parent[x]` from `p` to `g`. This shortens the path by one level without walking the full path twice. It creates more writes than read-only find, which is the central trade-off: compression reduces future traversal length but increases atomic contention and cache-line writes. In a parallel connected-components kernel, the hot vertices often sit near the roots of large stars. Path halving on every find can turn a read-mostly phase into a write-heavy one. Some implementations compress only after several traversals, compress only below a threshold depth, or use a two-phase find that records the path and compresses in a second pass. None of these is universally best; the right choice depends on the edge distribution and the number of repeated finds per vertex.

The deeper concurrency issue is that path compression can conflict with the union-by-rank argument. Compression changes depth without changing rank. That is fine sequentially: rank is an upper bound on height, not an exact height. Under concurrency, a compression can make a node point to a root that is about to be linked, and a link can make a compressed path one hop longer than expected. The forest remains valid, and the amortized argument becomes harder to state. For engineering, the important consequence is that rank is a contention-reduction heuristic, not a proof of lock-free bounded depth. If the workload needs a hard depth bound, a different algorithm or a sequential per-component phase is more appropriate.

## Find semantics, linearizability, and root caching

It is useful to separate `find` as a traversal from `find` as a linearizable read. A traversal returns a root by following the parent chain visible to the caller. That root may be a legitimate root of the component at the time it was read, and it may cease to be a root before the caller uses the result. For the monotonic connectivity contract, that is acceptable: a stale root is still a vertex in the same component, and a later union will connect it. For a contract that requires `find` to reflect all unions completed before the call, the implementation needs stronger synchronization or a validation loop that rechecks the root after reading it. Many graph kernels quietly assume the stronger contract and then fail under stress because the parent chain changed between the connectivity test and the edge insertion.

Root caching is the natural optimization and the natural source of bugs. A thread can cache the last known root for a vertex and validate the cache by checking whether `parent[cached_root] == cached_root`. If the cached root is no longer a root, the thread recomputes. This turns repeated finds on stable components into a single load and a single validation load. The cost is that the validation itself is a read of a contended cache line, and the cache can be invalidated by a single union in a large component. In hot components, root caching can reduce traversal depth while increasing the number of threads hammering the same root cache line. The usual engineering answer is to cache per thread or per work chunk, not globally, and to invalidate a cache entry on a failed validation rather than on every global union.

## Contention, ABA, and remapping

The first performance wall in concurrent DSU is not correctness but contention. Many edges in real graphs are incident to a small number of high-degree vertices. Those vertices' roots become atomic hot spots. A CAS loop on the same cache line from dozens of cores spends most of its time in cache-coherence traffic. Lock-free does not mean wait-free; a thread can retry indefinitely while other threads make progress. If the graph algorithm has a barrier after each phase, a single hot root can lengthen the phase even though the work is logically parallel.

ABA is less of a problem when vertex indices are stable and never reused. A CAS on `parent[root]` from `root` to `new_root` fails if the value is not `root`; the only way for it to succeed incorrectly is for the value to return to `root` after having changed. In a DSU, once a root is linked under another root, it is no longer a root, and the implementation never makes it a root again. So the classic ABA pattern does not arise from linking alone. It can arise if the implementation reuses indices during remapping or if it compresses by writing a temporary sentinel. The practical rule is to keep vertex identities stable for the lifetime of the concurrent structure. If remapping reuses slots, add a version tag to the packed word or forbid reclamation while operations are in flight. This is a design constraint, not a micro-optimization.

Remapping is the standard escape hatch. Instead of running one global DSU over a billion vertices, partition the edge list into chunks, build thread-local or block-local DSUs, and then merge only the representative roots globally. The local phase has no cross-thread CAS traffic and can use a sequential DSU with full path compression. The global phase sees far fewer unions, because most edges inside a chunk are absorbed locally. The cost is extra memory for local parent arrays and a second pass over representatives. A related technique is component remapping: after each phase, assign dense component IDs to roots, then re-index edges by component ID before the next phase. This can shrink the active vertex set dramatically, but the remap itself is a parallel sort or hash pass and can dominate if components are large and stable. The trade-off is contention versus remapping overhead. For graphs with a giant component and many small components, two-level DSU often wins because the giant component's hot root is touched by fewer global unions. For graphs with many medium components, the remap overhead may exceed the saved CAS traffic.

A third option is to avoid global DSU during traversal and use a different connectivity algorithm entirely, such as label propagation, Shiloach-Vishkin, or a parallel spanning forest. Those algorithms have their own convergence and work-efficiency trade-offs. Concurrent DSU is attractive when the graph is processed as an unordered edge stream and the final partition is the only required output. It is less attractive when the algorithm needs deterministic component labels or frequent membership queries during the traversal. The implementation should expose which contract it provides. A lock-free parent array that returns stale roots is not a drop-in replacement for a linearizable DSU.

The remaining design space starts with scheduling: whether to batch edges by source vertex, sort by component, use per-thread local DSUs, or interleave a global phase with periodic remapping. Those choices change the contention pattern more than the atomic instruction choice does. They also determine whether path compression is a net win or a source of cache-line churn. The next sections will examine those scheduling strategies and the conditions under which each one is defensible.

## Scheduling the edge stream

The scheduling layer determines how many times the concurrent DSU is touched and by whom. A lock-free parent array with perfect atomics still performs poorly if every edge causes a global `find` and `union` on the same few roots. Scheduling changes the shape of the problem before the DSU sees it. The useful distinction is between edge-centric and vertex-centric scheduling. In an edge-centric schedule, threads pull edges from a shared queue and apply each edge directly to the global DSU. This is simple and has good load balance for uniform edge costs, but it maximizes contention: every edge that crosses components performs at least two global finds and one CAS. In a vertex-centric schedule, a thread owns a vertex or a range of vertices and processes all incident edges together. The thread can find the source root once, then reuse it for the whole batch. If the vertex is a high-degree hub, the batch is long, and other threads working on neighbors may still contend on the hub's root. The schedule should therefore split high-degree vertices into multiple work items rather than treating them as atomic units.

### Batching by source and degree

A practical hybrid is to classify vertices by degree. Low-degree vertices are processed as single work items: one thread reads the adjacency list, finds the source root once, and unions each neighbor. High-degree vertices are split into chunks of adjacency entries. Each chunk is a work item that produces a set of component pairs rather than performing global unions immediately. For example, a chunk of 1024 edges from a hub can be reduced locally: build a small local DSU over the hub and the neighbors in that chunk, then emit only the representative pairs that remain distinct. This reduces the number of global unions from 1024 to at most the number of distinct components touched by the chunk. If the hub's neighbors are mostly already in the same component, the reduction is large. The cost is a small local DSU and a second pass over the chunk. The local DSU can be a fixed-size array with a stack for touched slots, avoiding dynamic allocation. This pattern is especially effective for power-law graphs, where a few vertices have degree orders of magnitude larger than the median.

The chunk size is a tuning knob. Small chunks increase the number of work items and reduce per-item reduction benefit; large chunks increase load imbalance and may create a long tail. A common choice is to make chunk size proportional to the average degree or to a fixed number of cache lines. The work item should also carry the vertex ID so that the local DSU can be keyed by vertex ID rather than by adjacency position. If the graph is stored in compressed sparse row (CSR) format, a chunk is a contiguous slice of the neighbor array. That gives good memory locality. If the graph is edge-partitioned across threads, the chunk is already a local edge list.

### Per-thread local DSUs

The next step is to give each thread a private DSU for the duration of a phase. Edges assigned to the thread are processed sequentially with full path compression and union by rank. No atomics are needed. The local DSU can be a dense array over a contiguous vertex range, or a hash map from global vertex ID to local slot. Dense arrays are faster but require that the thread's edges are confined to a vertex range. Hash maps are more flexible but add lookup overhead. A middle ground is a two-level array: a global-to-local index array with atomic or per-thread initialization. If each thread owns a disjoint vertex range, the local index is just `global_id - range_start`. If ranges overlap, use a per-thread hash table.

At the end of the phase, each thread emits cross edges: for each edge that connects two different local components, emit the pair of local roots. These pairs are the only input to the global merge. The local DSU can then be discarded or reset for the next phase. The global merge sees a much smaller graph: vertices are local roots, edges are cross edges. The number of cross edges depends on the partition. If the partition is by vertex range, the cut is proportional to the number of edges crossing range boundaries. For random graphs with many ranges, the cut can still be a large fraction of the edge set. If the partition is by edge, the cut is controlled by the edge partitioner. A good edge partitioner balances edges and minimizes vertex replication; the local DSU then operates on replicated vertices, and the global merge must handle duplicates. Duplicates are harmless for connectivity because union is idempotent, but they increase the number of global unions. The implementation can deduplicate cross edges by sorting or hashing before the merge.

### Merging local DSUs

The global merge can be another concurrent DSU, but it operates on local root IDs rather than original vertices. If the number of local roots is small, a sequential merge on one thread is often fastest. If it is large, shard the global DSU by root ID and let threads merge shards independently. Cross-shard unions require a coordination step: either a lock per shard pair or a second-level DSU over shard representatives. A simpler approach is to build a graph of local roots and run a parallel connected-components algorithm on that graph. The graph is small, and the algorithm can be a label propagation or a Shiloach-Vishkin pass. The final component labels are then mapped back to original vertices by composing local root labels with global labels. This two-level design avoids the worst contention because the global DSU never sees the original edge stream.

The cost of merging is not just the global unions. It includes the extraction of cross edges, the construction of the local-root graph, and the final label composition. For a graph with a giant component, the local DSUs will each have one large component and many small ones. The cross edges will mostly connect the large components, so the global merge will quickly form a giant component and then do many redundant unions. Deduplicating cross edges by component pair can help: before the global merge, replace each local root with a canonical local component ID, then hash pairs. If the same pair appears many times, only the first union matters. This is a form of remapping at the local-root level.

## Remapping as a phase boundary

Remapping is most effective when it is treated as a phase boundary rather than a concurrent operation. After a phase, the active component IDs are remapped to dense integers. The next phase then operates on a smaller ID space, which improves cache locality and reduces the number of distinct roots. The remap can be done with a parallel prefix sum over a flag array that marks roots. Each root gets a new ID equal to its prefix sum. Non-roots can be updated lazily or left alone if the next phase only queries roots. If the next phase processes edges, each edge endpoint must be mapped to its root and then to the new ID. That requires a `find` for each endpoint, which is the same work the DSU would do anyway. The benefit is that subsequent global unions use dense IDs and touch a compact array.

The cost of remapping is often underestimated. A full remap over all vertices scans the parent array, writes a flag for each root, performs a prefix sum, and scatters new IDs. For a graph with a billion vertices, that is a billion memory accesses per phase. If the component structure is stable, the remap does not reduce the active set much, and the cost is wasted. An adaptive policy is necessary. Remap only if the number of roots after the phase is below a threshold, or if the previous phase reduced the root count by a significant fraction. A common heuristic is to remap when `roots_new < roots_old / 2` and `roots_old > 64 * num_threads`. If the root count is already small, the contention is low, and remapping is unnecessary. If the root count is large but not shrinking, the graph may have many small components, and remapping may still help by compacting IDs. The policy should be based on measurements, not assumptions.

A lighter-weight alternative is to remap only the local roots, not all vertices. The global merge operates on local roots, so only those IDs need to be dense. The number of local roots is at most the number of vertices touched by a thread, which is usually much smaller than the total vertex count. The remap then uses a hash table or a sort of the local root list. This avoids scanning the full parent array. The trade-off is that the local root list must be collected during the local phase, which adds a write per local root. That write is cheap compared to a global scan. For multi-phase algorithms, this local-root remap can be repeated each phase with low overhead.

## Work stealing and load balance

Static assignment of work items to threads is simple but can suffer from tail latency. If one work item contains a high-degree vertex and a large component, it may take much longer than the others. Work stealing can balance the load, but it interacts with the DSU state. If work items are self-contained local DSUs, stealing is safe: a thief takes an unprocessed item and builds its own local DSU. If work items share a thread-local DSU, stealing requires either transferring the DSU state or merging the thief's results into the victim's DSU. Transferring state is complex; merging is often cheaper. A common design is to make each work item independent and to merge all local DSUs at the end of the phase. Work stealing then only moves the computation, not the data structure.

Work stealing also changes the contention pattern. A hot vertex that would have been processed by one thread may now be processed by several thieves, each performing global unions on the same root. This can increase CAS failures. To mitigate, the work item should include a local reduction step before any global union. If a thief processes a chunk of a hub's edges, it reduces them locally and emits only cross-component pairs. The global unions are then fewer and can be batched. Another mitigation is to use a backoff strategy on CAS failures: if a CAS fails, the thread can process a few more local edges before retrying, or it can push the union into a per-thread pending buffer. The buffer is flushed when it reaches a size threshold or when the local phase ends. Batching unions by root can also help: if a thread has multiple unions involving the same root, it can perform one CAS for the root and then link the others under the new root. This is a form of local union-by-root that reduces repeated CAS on the same cache line.

## Atomic and memory layout details that survive scheduling changes

The scheduling design constrains the atomic layout. If the global DSU is only used for local roots, the index space is smaller, and a 32-bit packed word is enough for many graphs. If the global DSU operates on original vertices, a 64-bit word may be necessary. The packed word should be laid out to make the common operation cheap. For a root, the parent field equals the index. For a non-root, the parent field is the ancestor. The rank field is only meaningful for roots. A common layout is low 32 bits for parent, high 32 bits for rank. Reading the parent requires a mask and a shift. If the parent is the low bits, `parent = word & 0xffffffff`. If the index space fits in 40 bits, use low 40 bits for parent and high 24 bits for rank and version. The version can be used to detect remap ABA, but it consumes bits. An alternative is to keep a separate generation array and never reuse a slot while a thread may hold a reference. Since remapping happens at phase boundaries, a barrier can make version tags unnecessary. The simpler layout is usually the right one unless the implementation supports concurrent remapping.

False sharing is a persistent issue. Adjacent entries in the parent array share a cache line. When two threads update different roots that happen to be in the same line, the line ping-pongs even though the threads are logically independent. Sharding the parent array by high bits of the vertex ID reduces false sharing because updates to different shards touch different cache lines. The cost is that `find` must determine the shard, and unions across shards need coordination. For a global DSU over local roots, the root IDs are dense and may be allocated sequentially, so false sharing is likely. Padding each root to a cache line is too expensive for large arrays. A compromise is to pad shards or to use a per-thread pending buffer so that updates to the same cache line are batched. If the algorithm has a phase barrier, false sharing during a phase may be acceptable if the phase is short. If the phase is long, sharding is worth the complexity.

## Measuring contention and remap cost

A concurrent DSU should be instrumented before it is optimized. The most useful counters are the number of CAS attempts, the number of CAS failures, the number of `find` steps, and the number of remaps. CAS failures are a direct measure of contention. If the failure rate is high, adding local batching or remapping is likely to help. If the failure rate is low but the runtime is high, the bottleneck may be memory latency or load imbalance. The number of `find` steps measures the effectiveness of path compression. If the average path length is growing, the compression policy may be too conservative. If the average path length is low but CAS failures are high, the compression writes may be causing contention. The remap cost can be measured by timing the remap phase separately. If the remap is more than a small fraction of the total runtime, the policy should be adjusted.

A simple cost model can guide tuning. Let `m` be the number of edges, `c` the number of cross edges after local reduction, `r` the number of active roots, and `p` the number of threads. The local phase costs roughly `O(m)` sequential work per thread plus local DSU overhead. The global phase costs `O(c)` global unions plus contention, which is superlinear in the number of unions per hot root. The remap costs `O(r)` or `O(V)` depending on the scope. Remapping is worthwhile if it reduces `r` enough to lower the global phase cost by more than the remap cost. In practice, the global phase cost is often dominated by a few hot roots, so reducing the number of roots is less important than reducing the number of unions per root. Deduplicating cross edges by component pair can be more effective than a full remap. The two techniques are complementary: deduplication reduces the number of global unions, and remapping reduces the ID space and improves locality.

The final consideration is determinism. A concurrent DSU with union-by-rank or union-by-size produces a partition that is correct but may have different root labels on different runs. If the application needs deterministic component labels, the DSU should not be the source of labels. Instead, after the final partition is computed, run a deterministic relabeling pass: for each component, choose the minimum vertex ID as the canonical label, then assign dense labels in increasing order. This pass is parallel and can be done with a reduction over the parent array. It does not require the DSU to be deterministic. Trying to make the DSU itself deterministic by always linking the smaller root under the larger root is possible, but it can create deep trees under adversarial edge orders and can increase contention on the smaller root. It is usually better to keep the DSU's internal choices heuristic and to canonicalize labels at the end.

These scheduling, remapping, and layout choices are where a concurrent union-find implementation becomes a graph algorithm rather than a data structure. The atomic parent pointer is the core, but the surrounding pipeline determines whether the core is exercised once per edge or once per component. The next design decisions concern validation: how to test a structure that is allowed to be stale, how to distinguish a benign race from a bug, and how to build a stress harness that exercises the contention paths without requiring a cluster.

## Validation: testing a structure that permits staleness

The contract chosen for the concurrent DSU determines what a test can prove. For an eventual-connectivity contract, the primary oracle is the final partition: after all edge-processing work has completed and all threads have joined, the set of connected components must equal the set produced by a sequential DSU over the same edge multiset. That comparison is stronger than checking a few sample queries because it exercises every vertex and every edge, including duplicates, self-loops, and edges that arrive after their endpoints are already connected. It also avoids depending on root labels. The concurrent implementation may choose different representatives than the sequential one, so the test should canonicalize both partitions before comparing them. A deterministic canonicalization pass assigns each component the minimum vertex ID in that component, then maps those minima to dense labels in sorted order. This pass is independent of the DSU's internal link choices and gives a stable output for differential testing.

The edge multiset matters. A test that uses only a simple path or a random graph with one edge per pair misses the cases that create contention and the cases that create structural hazards. The harness should generate several families: a star with one high-degree center, a graph with several hubs connected to each other, a long path that stresses path compression, a grid or mesh with many short cycles, a graph with many isolated vertices, and a graph with one giant component plus many small components. Each family should be run with multiple edge permutations. Because union is commutative and idempotent, the final partition must not depend on the permutation. If it does, the bug is in the concurrent protocol or in the edge-processing schedule, not in the graph generator.

### The final partition is the primary oracle

The final-partition check should be complemented by an edge-coverage check. For every edge in the input, after quiescence, the canonical label of both endpoints must be equal. This catches a class of bugs where the DSU forms a plausible partition but loses an edge because a CAS failure was treated as a completed union. The check is cheap if the canonical labels are stored in an array. It is also useful to verify that the number of components equals the sequential count and that the size of each component matches the sequential size. Size comparison catches accidental merges that preserve the component count but combine the wrong vertices. A hash of the sorted component sizes plus the sorted canonical labels gives a compact fingerprint for regression tests.

The test should run the same edge set through several thread counts: one thread as a control, two threads to expose simple races, and then four, eight, and an oversubscribed count. Oversubscription is important because it changes the interleaving without requiring a large machine. The one-thread run should use the same code path as the multi-threaded run, with the same atomics and the same link protocol. A separate sequential implementation is useful as an oracle, but it does not validate the concurrent code path. If the one-thread concurrent run fails, the bug is likely in the link protocol or the packed-word layout, not in a multi-threaded race.

### Invariant checks at quiescence

At quiescence, the parent array must satisfy a small set of structural invariants. Every parent entry must be a valid vertex index. A root is exactly a vertex whose parent entry equals its own index. Every non-root must have a parent that is not itself. Following parent pointers from any vertex must terminate at a root. There must be no cycles. The rank field, if packed with the parent, must be within its allocated range. The rank is advisory, so it need not equal the tree height, but a root's rank should not decrease unless the implementation explicitly resets it during remapping. If the implementation uses union by size, the size field should be at least one and should not exceed the number of vertices in the component. These checks are sequential in the simplest form, but they can be parallelized by partitioning the parent array and using a second pass to resolve cross-partition chains.

Cycle detection needs care because a cycle in a parent array is not always obvious from local checks. A vertex can point to a parent that points back to it through a long chain. The check should use a visited array with three states: unvisited, in-progress, and finished. A depth-first traversal from each vertex marks in-progress nodes; if a traversal reaches an in-progress node, there is a cycle. For large graphs, the visited array can be a byte array and the traversal can be iterative to avoid stack overflow. The check is only valid at quiescence. During concurrent operation, a traversal can observe a transient chain that looks cyclic because it read parent pointers at different times. That is not necessarily a bug. The validation suite should therefore separate quiescent checks from concurrent stress. A barrier before the quiescent check is mandatory.

The packed-word invariant is easy to miss. If the parent field is 40 bits and the rank field is 24 bits, a bug in the mask or shift can make a valid parent look like a different vertex. The test should include vertices whose indices exercise the high bits of the parent field, not just small indices. A graph with a sparse vertex ID space is useful here: if the implementation remaps IDs, the test should also run without remapping to exercise the full index range. The packed word should be checked for accidental sign extension. If the parent field is stored in the low bits and the word is signed, shifting or masking can produce a negative index. The validation harness should assert that every extracted parent is non-negative and less than the vertex count.

### Stress harness design

A stress harness is not just a loop around the algorithm. It controls the schedule, the graph shape, the thread count, and the observation points. The edge list should be shuffled with a deterministic seed so that a failure can be reproduced. The shuffle should be independent of the thread assignment; the same edge order can be processed by different work-stealing schedules. The harness should record the seed, the thread count, the remap policy, and the work-item size in a failure report. Without those parameters, a rare failure is difficult to reproduce.

The harness should also inject delays at selected points. A delay before a CAS is not the same as a delay after a CAS. A delay after reading a root but before linking it can expose a stale-target race. A delay after a successful CAS but before updating a local cache can expose a stale-cache bug. The delays should be deterministic and sparse; a random delay on every operation changes the schedule so much that the failure may disappear. A common technique is to use a test-only atomic wrapper that counts operations and pauses at a specified operation number. The pause can be a spin loop or a condition variable. This gives reproducible interleavings without requiring a full deterministic scheduler.

The harness should run under thread and address sanitizers when possible. ThreadSanitizer can catch missing atomics and improper memory ordering, but it can also report races on data that is intentionally protected by a higher-level protocol. The implementation should keep its synchronization explicit so that the sanitizer's reports are actionable. AddressSanitizer catches out-of-bounds accesses in the parent array and use-after-free in remapping. If the implementation uses a custom allocator for local DSUs, the allocator should be tested with the same sanitizer settings. Memory leaks are less of a correctness issue in a short-lived graph kernel, but they matter in a long-running service that repeatedly builds DSUs.

### The mutual-link race

A validation suite should include a specific two-root race that the simple CAS-on-source protocol does not handle. Suppose vertices A and B are roots. Thread T1 reads both roots and decides to link A under B. Thread T2 reads both roots and decides to link B under A. If T1's CAS on parent[A] succeeds and T2's CAS on parent[B] succeeds, the parent array contains A pointing to B and B pointing to A. That is a cycle. The forest invariant is broken even though each CAS changed a value that was a root at the time it was read. The problem is that the target of a link can stop being a root before the source CAS succeeds. The source CAS only checks that the source is still a root; it does not check that the target is still a root.

This race is easy to miss in a unit test that uses one thread or that always links in a fixed direction. It is also easy to miss in a stress test that uses a random graph with few roots, because the window is narrow. A targeted test should create two roots and two threads, synchronize them just before the CAS, and force both to attempt the opposite link. The test should repeat many times with different timings. If the implementation uses a packed word, the test should also vary the rank values so that the link decision changes. A cycle detector at quiescence will catch the failure, but the failure may be rare. The targeted test makes it deterministic.

The fix is to make the link direction a deterministic function of the roots' metadata. A total order on roots, such as comparing rank first and vertex ID second, ensures that two threads observing the same pair of roots choose the same source and target. If the ranks differ, the lower-rank root links under the higher-rank root. If the ranks are equal, the lower vertex ID links under the higher vertex ID. This is a standard union-by-rank rule with a tie-break. The tie-break is not just for determinism; it prevents mutual linking. If T1 and T2 both see A and B as roots with the same rank, both choose the same direction. One CAS succeeds and the other fails because the source is no longer a root. If the ranks differ, both choose the lower-rank root as the source. The target may later be linked under another root, but the source cannot be linked under the target in the opposite direction because the order is strict. The resulting chain remains acyclic.

The deterministic order does not eliminate all races. A thread can read a root's rank, then another thread can link that root under a different root and increase the new root's rank. The first thread's CAS may still succeed if its source is still a root. The link direction was based on stale metadata, but the direction is still acyclic because the target's order was higher than the source's order at the time of the read. If the target later links to an even higher-order root, the chain remains upward. If the source later becomes a target of another link, the source's parent is already set, so the CAS fails. The key is that the order is a partial order on the roots' identities and ranks, and every successful link moves from a lower-order root to a higher-order root. A cycle would require a link from a higher-order root to a lower-order root, which the protocol forbids. This argument is simpler than a full linearizability proof and is sufficient for the eventual-connectivity contract.

### Histories and linearizability checks

If the API promises a stronger contract than eventual connectivity, the validation suite needs operation histories. A linearizability check records each operation's invocation and response times, the arguments, and the result. For a DSU, `find` returns a root, and `union` returns a success or a failure. The checker then searches for a sequential ordering of the operations that respects the real-time order and produces the same results. For small graphs and short histories, an exhaustive search is feasible. For larger histories, the checker can use a partial-order reduction or a model checker. The important point is that the checker must know the abstract specification. A concurrent DSU that returns stale roots is not linearizable with respect to a specification that requires `find` to return the current root. It may be linearizable with respect to a weaker specification that allows a `find` to return any vertex in the same component as the true root, provided the component relation is consistent. The test should not use a checker whose specification is stronger than the implementation's contract.

A practical alternative is to test a monotonic property instead of full linearizability. For every completed `union(a,b)`, the final partition must place `a` and `b` in the same component. For every `find(x)` that returns `r`, the final partition must place `x` and `r` in the same component. These properties are weaker than linearizability, but they catch lost unions and incorrect root returns. They are also cheap to check after the run. If the implementation caches roots, the test should record the cached root and verify that it was a valid root at some point. A cached root that was never a root indicates a bug in the cache validation. A cached root that was a root but later stopped being one is acceptable under the weak contract.

### Memory reclamation and remapping tests

Remapping introduces a second lifetime problem. If remapping reuses vertex slots, a thread can hold a parent index that refers to a slot that has been reassigned to a different vertex. The classic ABA pattern becomes possible: a CAS on a parent pointer can succeed because the slot's value returned to the expected value after being reused. The validation suite should force remapping at random points and then check that no stale parent points to a reused slot. If the implementation uses version tags in the packed word, the test should verify that the version changes on every remap. If the implementation uses a barrier between phases, the test should verify that no operation is in flight during the remap. A barrier is easier to validate than a concurrent remap, but it limits the algorithm's structure. The test should match the implementation's chosen policy.

Memory reclamation for local DSUs is simpler because local DSUs are usually discarded at phase boundaries. The test should still check that a discarded local DSU is not referenced by a global pending buffer. A common bug is to emit a cross edge that points to a local root, then free the local DSU before the global merge consumes the edge. The edge's endpoint is an integer, so it does not dangle, but the integer may no longer correspond to a valid local root. The global merge must either copy the local root's identity into a stable array or keep the local DSU alive until the merge completes. The validation suite should use a small local DSU size and a large number of cross edges to make this bug likely. A sanitizer will not catch it because the memory is still valid; only a semantic check of the local root table will.

### Telemetry and failure injection

The validation suite should collect counters that explain failures. The most useful counters are CAS attempts, CAS failures, find steps, compression attempts, compression failures, local unions, global unions, cross edges emitted, cross edges deduplicated, remaps, and remap time. These counters should be per thread and aggregated at the end. Per-thread counters avoid turning the measurement into a contention source. If the counters are updated with relaxed atomics, the overhead is small. The counters should be included in the failure report so that a rare failure can be correlated with contention. A failure that occurs when CAS failures are high is likely a protocol bug; a failure that occurs when CAS failures are low is more likely a logic bug in the edge schedule.

Failure injection is the complement of telemetry. A test-only atomic wrapper can force a CAS to fail even when the expected value is present. This tests the retry path without requiring a real race. The wrapper should be used sparingly because it changes the algorithm's progress properties. A forced failure after a successful CAS can test whether the caller incorrectly assumes that a successful CAS means the union is complete. A forced failure before a CAS can test whether the caller leaves the data structure in a consistent state. The wrapper should record the injection point so that a failure is reproducible. The same wrapper can be used to test path compression: force a compression CAS to fail and verify that the find still returns a valid root.

### Differential testing across schedules

The final validation layer is differential testing across schedules. The same edge multiset should be processed with different work-item sizes, different work-stealing policies, different remap thresholds, and different thread counts. The final partition must be identical after canonicalization. This catches bugs that depend on the order in which local DSUs are merged. It also catches bugs in the remap policy: a remap that changes the partition is a correctness bug, not a performance tuning issue. The test should compare not only the final partition but also the number of global unions and the number of cross edges. A large difference in those counts between schedules is a sign that the local reduction is not working as intended.

The differential test should include a schedule with no work stealing and a schedule with aggressive work stealing. Work stealing changes which thread owns a local DSU, so it changes the local root IDs. The canonical partition should still match. The test should also include a schedule with a remap after every phase and a schedule with no remap. If the remap is correct, the partition should match. If the remap is only a performance optimization, the test should verify that it does not change the component structure. A remap that changes the partition is a bug even if the new partition is still a valid connectivity partition, because the remap is supposed to preserve the equivalence relation.

The validation work is not separate from the design work. The mutual-link race shows that the link protocol needs a deterministic order. The remap tests show that slot reuse needs a version tag or a barrier. The telemetry shows whether path compression is helping or hurting. The stress harness shows whether the scheduling choices are robust. These are all design decisions that should be made before the implementation is tuned. The remaining work is to connect the validation results to a tuning loop: measure contention, choose a remap threshold, choose a compression policy, and verify that the final partition remains correct under every schedule. That loop is where the atomic parent pointer stops being a data structure detail and becomes part of the graph algorithm's performance model.

## Adaptive compression and read-mostly phases

A fixed compression policy is rarely optimal across an entire graph workload. The edge stream often has phases: an early phase where many edges connect previously isolated vertices and unions dominate, a middle phase where components grow and finds become longer, and a late phase where most edges are intra-component and finds dominate. The concurrent DSU can adapt by tracking a small amount of state per thread or per shard. One approach is to maintain a saturating counter of find depth. When the average sampled depth is below a threshold, `find` performs only the traversal and skips compression. When the depth rises, compression is re-enabled. The counter should be updated with relaxed atomics or thread-local variables, and the threshold should be chosen from the graph's degree distribution rather than a universal constant. For a graph with a long path, a depth threshold of two or three is too aggressive; for a star, almost every find is already one hop, so compression is wasted work.

A second adaptive lever is the compression operation itself. Path halving writes one pointer per two steps. Full path compression writes every node on the path to the root. Path splitting writes every node to its grandparent, which is similar to halving but can be implemented as a single pass. Under contention, the write cost is not the instruction cost but the cache-line ownership transfer. If the CAS failure rate on compression exceeds a threshold, the implementation can temporarily switch to read-only finds for the affected root or shard. The switch can be per thread: a thread that experiences repeated compression failures stops compressing for a fixed number of operations. This is a form of local backoff that does not require global coordination. The danger is that a thread may stop compressing exactly when compression would help most. The backoff should therefore be bounded and followed by a probe: after the backoff window, attempt one compression and measure whether it succeeds. If it fails again, extend the window; if it succeeds, reset the window.

A third lever is batching compression. Instead of compressing during `find`, a thread can record the path in a small stack and compress after the find returns. The stack is thread-local and has a fixed capacity. If the path exceeds the capacity, the thread compresses the first part and continues. This separates the read phase from the write phase and can improve locality: the thread walks the path once, then writes the same cache lines it just read. It also allows the thread to skip compression if the root is about to be linked by a pending union. The cost is the stack management and the extra pass. For short paths, the overhead is not worth it; for long paths, it can reduce the number of atomic operations because the thread can use a single CAS per node instead of interleaving reads and writes.

## Edge preprocessing and local reduction details

The concurrent DSU is not the first place to optimize. Edge preprocessing can remove work before any atomic operation. Self-loops can be dropped immediately; they never change connectivity. Duplicate edges can be deduplicated if the graph representation allows it. A parallel sort or hash-based deduplication costs a pass over the edge list, but it can reduce the number of `find` calls substantially on graphs with repeated edges. The decision should be based on the duplicate rate. If duplicates are rare, deduplication is wasted bandwidth. If duplicates are common, as in some web graphs and social graphs, deduplication can pay for itself before the DSU sees the first edge. A cheaper alternative is to deduplicate only within each work item during local reduction, which catches duplicates that are close in the edge order without a global pass.

Local reduction deserves practical detail. A work item that processes a chunk of edges can build a local DSU over the vertices in the chunk. The local DSU can be a dense array indexed by a local slot. To avoid clearing the array for every work item, use a timestamp array: each slot stores the last epoch in which it was initialized. When a vertex is first seen in the current epoch, its parent is set to itself and its timestamp is updated. The work item's epoch is a thread-local counter. This avoids an O(vertex_count) clear per chunk. The local DSU should also track which slots were touched so that the work item can iterate over them when emitting cross edges. A simple stack of touched slots is enough. The local union operation can use union by rank or size with full path compression because it is single-threaded.

When emitting cross edges, the work item should canonicalize each local root pair. If the chunk has many edges between the same two local components, the same pair is emitted repeatedly. A small local hash table keyed by the pair can deduplicate before the global merge. The hash table can be a fixed-size array with open addressing and a timestamp, again avoiding a clear per chunk. The canonical pair should be ordered, for example `(min(root_a, root_b), max(root_a, root_b))`, so that the hash key is stable. The number of emitted pairs is then at most the number of distinct component pairs touched by the chunk. For a hub chunk whose neighbors are mostly in one component, this can reduce the global union count by orders of magnitude. The cost is the hash table probes and the extra memory per work item. The work item should be sized so that the hash table fits in cache; otherwise the deduplication becomes a memory bottleneck.

## Operational concerns: memory footprint, NUMA, and oversubscription

The atomic parent array is only one part of the memory footprint. For a graph with `V` vertices, a packed 64-bit parent array costs `8V` bytes. A separate rank array adds `4V` or `8V` bytes. A local DSU per thread adds a dense array over the thread's vertex range, which can be much larger than the global array if ranges overlap. The implementation should decide whether local DSUs are dense or hash-based. Dense local DSUs are faster but require a partition that gives each thread a contiguous range. Hash-based local DSUs are more flexible but have higher per-operation cost. For graphs that fit in memory, the dense option is usually better. For graphs that do not, the local DSU should be sharded and processed in blocks.

NUMA effects are significant for concurrent DSU. A parent array that is allocated on one socket will cause remote atomics for threads on the other socket. The array should be allocated with first-touch policy: each thread initializes the portion of the array it will use. If the graph partition is by vertex range, the range should be aligned with NUMA nodes. If the partition is by edge, the edge partitioner should also balance the vertices touched by each thread across sockets. Remote atomics are much more expensive than local atomics, and a single hot root on a remote socket can dominate the runtime. Sharding the parent array by high bits can help because each shard can be allocated on a different socket. The `find` operation then has to determine the shard, but the shard lookup can be cached per path.

Oversubscription is another operational trap. Running more threads than hardware cores may improve load balance for memory-bound work, but it increases CAS retries and context switches for atomic-heavy work. The concurrent DSU should be benchmarked with thread counts from one to twice the core count. If the runtime increases sharply beyond the core count, the atomic contention is the likely cause. The implementation can use a thread pool with a fixed number of workers and a separate work queue. The number of workers should be a tuning parameter, not a hard-coded constant. For phases that are dominated by local reduction, oversubscription may be harmless. For phases that are dominated by global unions, it is usually harmful. The scheduler can switch between a local phase with many workers and a global phase with fewer workers, but that requires a barrier and a reconfiguration step. A simpler approach is to keep the worker count fixed and to reduce the global union rate through local reduction and remapping. The operational goal is to make the global phase small enough that oversubscription does not matter.
